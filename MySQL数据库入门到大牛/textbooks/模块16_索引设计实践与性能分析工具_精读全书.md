## 128-索引的分类
> 对应分集：P128 | 原始标题：《128-索引的分类》

在彻底掌握了 InnoDB 底层的行格式、数据页内部结构、区、段以及表空间之后，我们从物理存储层正式步入逻辑调优与开发实战的核心领域——**索引的创建与设计原则**。

很多开发者在日常开发中有一个误区：既然索引能够成倍提升查询速度，那么只要看哪个字段顺眼、或者只要查询条件里经常出现某个字段，就盲目地为其创建索引。实际上，索引是一把双刃剑，它在提升读性能的同时，不仅会吞噬宝贵的磁盘与缓冲池空间，还会对 `INSERT`、`UPDATE`、`DELETE` 等写操作带来沉重的维护负担。在极端情况下，不合理的索引甚至会导致查询优化器做出错误判断，性能适得其反。

要真正用好索引、优化好索引，首要的前提是**把索引的分类搞得明明白白**。很多资料在谈论索引分类时往往概念杂糅，把“唯一索引”、“二级索引”、“联合索引”混为一谈，导致学习者产生严重的认知混乱。为此，我们将索引严格划分为**三个正交独立的技术维度**进行体系化解构。

---

### 索引的多维分类全景架构

索引绝不能简单用“有哪几种”来单向罗列，而必须从其**业务逻辑约束**、**底层物理组织**以及**覆盖列数量**三个维度分别定义：

```text
索引的三维分类全景：

               +-------------------------------------------------------------+
               |                     MySQL 索引分类体系                      |
               +------------------------------+------------------------------+
                                              |
      +---------------------------------------+---------------------------------------+
      |                                       |                                       |
      v                                       v                                       v
[ 1. 功能逻辑维度 ]                   [ 2. 物理实现维度 ]                     [ 3. 作用字段个数维度 ]
+---------------------+               +---------------------+                 +---------------------+
| - 普通索引 (Index)  |               | - 聚簇索引 (Clustered|                 | - 单列索引 (Single) |
| - 唯一索引 (Unique) |               | - 非聚簇/二级索引   |                 | - 联合索引 (Composite|
| - 主键索引 (Primary)|               |   (Secondary Index) |                 +---------------------+
| - 全文索引 (Fulltext|               +---------------------+
| - 空间索引 (Spatial)|
+---------------------+
```

> **读图说明**：同一个物理索引在三个维度上拥有复合属性。例如一个建立在 `(emp_id, dept_id)` 上的主键，在功能逻辑上是主键索引，在物理实现上是聚簇索引，在作用字段上是联合索引。三个维度相互交织，绝非割裂互斥。

---

### 功能逻辑维度的五大索引类型

功能逻辑维度关注的是**索引对所修饰字段施加的业务约束及特定检索算法**。

#### 普通索引（Normal Index）

普通索引是数据库中最基础的索引形态，使用关键字 `INDEX` 或 `KEY` 定义：
- **无附加约束**：不对列值施加任何唯一性、非空性约束，允许列中存在重复值和 `NULL` 值；
- **通用性**：可以创建在几乎任何 MySQL 允许建立索引的基础数据类型上；
- **核心定位**：纯粹为了加速 `WHERE` 条件过滤或 `ORDER BY` 排序操作。

#### 唯一索引（Unique Index）

唯一索引通过关键字 `UNIQUE INDEX` 声明，对字段值施加了强一致性的物理约束：
- **唯一性保证**：除 `NULL` 外，索引列的值必须全局唯一。虽然可以有多个 `NULL`（MySQL 认为 NULL 不等于 NULL），但不允许出现任何重复的非空值；
- **多索引共存**：与主键不同，一张表中可以根据业务需求定义多个唯一索引（例如 `email`、`phone_number`）；
- **与约束的孪生关系**：在 DDL 中添加唯一约束（`UNIQUE CONSTRAINT`）时，系统底层会自动创建同名的唯一索引；若要删除唯一约束，其本质也是通过 `DROP INDEX` 移除底层对应的唯一索引；
- **检索优势**：在 B+ 树叶子节点中执行点查（Point Lookup）时，一旦匹配到目标值即可立刻终止页内单向链表遍历，无需向后探测。

#### 主键索引（Primary Key Index）

主键索引是建立在 `PRIMARY KEY` 约束上的特殊唯一索引：
- **双重严格约束**：不仅要求列值绝对全局唯一，而且严格禁止任何 `NULL` 值（`UNIQUE + NOT NULL`）；
- **实例唯一性**：一张数据表**只能且必须有且仅有一个**主键索引；
- **物理决定权**：在 InnoDB 中，主键索引直接等同于**聚簇索引（Clustered Index）**。主键的排序规则决定了整张表中数据行在物理磁盘和数据页中的排列顺序。由于同一批数据行在物理空间中只能按照一种顺序组织存放，不可能物理分裂存储两份，因此主键索引在物理层面绝不可能存在两个。

#### 全文索引（Full-Text Index）

全文索引（`FULLTEXT INDEX`）是应对长文本模糊匹配与关键词检索的专用索引技术：
- **传统 LIKE 瓶颈**：当对 `TEXT`、`VARCHAR` 大字段执行 `LIKE '%keyword%'` 模糊匹配时，前导通配符会导致传统 B+ 树索引彻底失效，引发全表扫描；
- **分词与倒排机理**：全文索引采用**分词算法（Tokenization）**对目标文本切词，构建**倒排索引（Inverted Index）**，记录每个单词出现的数据行及偏移量；在查询时根据词频、逆文档频率（TF-IDF）等相关度打分快速返回匹配行；
- **适用场景**：适用于海量自然语言文本的关键词检索，小规模数据集上其收益无法对冲底层构建开销。

#### 空间索引（Spatial Index）

空间索引通过关键字 `SPATIAL INDEX` 声明：
- **数据类型绑定**：仅允许建立在空间地理数据类型（`GEOMETRY`、`POINT`、`LINESTRING`、`POLYGON` 等）上；
- **底层算法**：空间索引不再使用一维 B+ 树，而是基于多维空间组织的高效 **R-Tree** 算法实现；
- **约束条件**：空间索引所修饰的列必须显式声明为 `NOT NULL`。

### 物理实现维度的核心分野：聚簇索引与非聚簇索引

物理实现维度关注的是**索引树的叶子节点到底存放了什么实体内容**，直接决定了查询过程中是否需要产生二次 I/O。

#### 聚簇索引（Clustered Index）

聚簇索引是 InnoDB 表存储的基石，其核心特征为“**索引即数据，数据即索引**”：
- **叶子节点内容**：叶子节点的数据页中完整保存了该数据行的所有列值（包括用户自定义的所有业务字段及隐藏列）；
- **自动构建机制**：
  1. 若显式指定主键，InnoDB 默认选取主键作为聚簇索引；
  2. 若未指定主键，自动选取表中第一个被声明为 `UNIQUE NOT NULL` 的列作为聚簇索引；
  3. 若以上均不存在，InnoDB 会自动在行尾隐式生成一个 6 字节的 `DB_ROW_ID` 隐藏列，以此构建聚簇索引。

#### 非聚簇索引 / 二级索引（Secondary Index）

非聚簇索引亦称辅助索引或二级索引：
- **叶子节点内容**：叶子节点仅存放**索引列本身的值**以及该行对应的**主键值（Primary Key）**，并不包含整行的数据全貌；
- **回表（Bookmark Lookup）机制**：当通过二级索引查询非索引字段时，存储引擎首先在二级索引 B+ 树中查出对应的主键值，随后拿该主键值到聚簇索引 B+ 树中重新进行一次自顶向下的寻址，这一过程称为“回表”。

```text
二级索引与聚簇索引的物理联动与回表机制：

[ 二级索引 B+ 树 (按 name 建立) ]
        +---------------+
        |  目录项节点   |
        +-------+-------+
                |
                v
        +---------------+
        |  name  |  id  |  <--- 叶子节点仅存放索引列值与对应主键 ID
        +-------+-------+
                |
                | (拿着主键 ID 发生回表)
                v
[ 聚簇索引 B+ 树 (按主键 id 建立) ]
        +---------------+
        |  目录项节点   |
        +-------+-------+
                |
                v
        +-----------------------------------+
        |  id  |  name  |  age  |  address  |  <--- 提取整行真实数据
        +-----------------------------------+
```

> **读图说明**：通过二级索引检索时，如果在叶子节点中找不到查询所需的全部字段，就必须通过主键指针跨树跳入聚簇索引再次检索，这直接增加了磁盘随机 I/O 与 CPU 页内检索成本。

### 作用字段个数维度：单列索引与联合索引

根据索引所覆盖的数据列数量，可划分为单列与多列索引。

#### 单列索引（Single-Column Index）

单列索引仅包含表中的单一字段。一个表中可以创建多个独立的单列索引。
但必须注意：当一条查询语句的 `WHERE` 条件中包含多个带有单列索引的字段时，MySQL 通常只会选择其中代价最低的一个单列索引生效（某些场景下会触发 `Index Merge` 索引合并，但性能通常不如针对性优化的联合索引）。

#### 联合索引（Composite Index）与最左前缀原则

联合索引（亦称复合索引、多列索引）是由表中的多个字段按照特定的排列顺序共同构建而成的单一索引结构：
```sql
CREATE INDEX idx_id_name_gender ON student(id, name, gender);
```

联合索引在底层只生成一棵 B+ 树：
1. **排序层级严格依赖声明顺序**：先按照第一个字段排序；只有当第一个字段的值完全相同时，才按照第二个字段排序；同理，只有前两个字段均相同时，才按第三个字段排序；
2. **最左前缀原则（Leftmost Prefix Rule）**：
   查询条件中如果想要命中联合索引，必须严格从索引的最左列开始匹配。如果跳过最左列（例如查询条件仅有 `WHERE name = '张三'`），由于整个 B+ 树在根部并非全局按 `name` 排序，该联合索引将彻底失效无法用于二分查找定位。

### 全文检索的演进历程与现代工程选型权衡

全文索引在 MySQL 发展史中经历过深刻的架构迭代，并在现代互联网架构中有着清晰的定位边界。

#### 引擎支持与中文分词版本演进

1. **MySQL 3.x / 5.5 时代**：全文索引早期仅属于 MyISAM 存储引擎的专属特性，事务型引擎 InnoDB 无法创建 `FULLTEXT` 索引；
2. **MySQL 5.6 破局**：从 MySQL 5.6 开始，InnoDB 存储引擎正式提供了对全文索引的原生支持，弥补了高并发事务表无法兼具全文检索的短板；
3. **MySQL 5.7.6 与 ngram 解析器**：
   - MySQL 原生分词器默认以空格、标点符号作为单词边界。对于英文等以空格天然分词的西方语言表现极佳，但对于中文、日文、韩文（CJK）这种词与词连续书写的象形表意文字，默认分词器完全无法切分词义；
   - 自 **MySQL 5.7.6** 起，官方正式内置了 **`ngram` 全文解析器**。该解析器采用滑动窗口的 $N$-gram 分词技术（默认切分长度为 2 个字符），使 MySQL 具备了开箱即用的原生中文全文检索能力。

#### 现代工业架构中的技术选型权衡

尽管 MySQL 5.7/8.0 在底层已经完备支持了基于 InnoDB 的中文全文检索，但在主流互联网企业（如电商商品搜索、论坛长文搜索、站内信检索等）的实际落地中，极少直接把大规模全文检索任务强行压在 MySQL 上。

其核心架构权衡在于：
- **资源隔离与 CPU 开销**：全文检索的分词计算、相关度排名计算属于计算密集型任务。高并发全文检索会迅速榨干数据库服务器的 CPU 算力，直接阻塞甚至拖垮核心交易事务；
- **倒排索引维护代价**：频繁的写操作（`INSERT` / `UPDATE`）会导致倒排索引的大量碎片化，影响常规 OLTP 事务吞吐；
- **专业搜索引擎分流**：现代工业级架构通常采用“**MySQL 负责核心事务交易（OLTP），专业分布式搜索引擎（如 Elasticsearch、Solr）负责全文检索**”的动静分离架构。通过 Canal、Debezium 等 CDC（Change Data Capture）组件监听 MySQL 的 binlog 日志，将文本异步同步至 Elasticsearch 集群进行倒排构建与高并发复杂搜索，保障核心数据库轻装前行。

### 各存储引擎对索引类型的支持对照

不同存储引擎受限于其核心架构与设计目标，对各类索引的底层支持能力存在严格边界：

| 存储引擎（Engine） | B+ 树索引 | Hash 索引 | 全文索引（FULLTEXT） | 空间索引（SPATIAL） |
| :--- | :--- | :--- | :--- | :--- |
| **InnoDB** | 支持（默认索引结构） | 不支持手动显式创建（内部自带自适应哈希 AHI） | 支持（MySQL 5.6 起全面支持） | 支持（MySQL 5.7 起全面支持） |
| **MyISAM** | 支持（默认索引结构） | 不支持 | 支持（历史上最早支持） | 支持 |
| **MEMORY** | 支持 | 支持（MEMORY 引擎默认索引结构） | 不支持 | 不支持 |

> **核心结论**：
> 掌握索引分类，绝非死记硬背名词。在实际工程中，必须依据功能逻辑的业务约束（唯一/非空）、物理实现的 I/O 成本（聚簇/回表）、覆盖列的联合前缀规律，以及底层存储引擎的物理边界，做出一锤定音的最优技术选型。

## 129-表中添加索引的三种方式
> 对应分集：P129 | 原始标题：《129-表中添加索引的三种方式》

在 MySQL 的实际开发与数据库调优中，索引（Index）的合理设立是决定查询性能的胜负手。回顾基础篇关于“数据表约束”的定义过程，我们通常有两种时机来为字段设置完整性约束：一种是在执行 `CREATE TABLE` 建表时直接同步声明；另一种则是在数据表已经存在后，通过 `ALTER TABLE` 语句按需追加或调整。

索引的创建机制与约束完全同构。从构建时机与底层语法的大方向划分，为表添加索引同样分为“建表时定义”与“建表后追加”两大核心场景。在建表后追加场景下，MySQL 提供了 `ALTER TABLE ... ADD` 与 `CREATE INDEX ... ON` 两种并行的语法途径。本讲将从建表阶段的隐式与显式创建出发，深入剖析单列索引、唯一索引、联合索引（结合 B+ 树排序与最左前缀底层原理解析）、全文索引与空间索引的声明语法，并系统梳理表结构已存在时的两套追加方案。

---

### 数据表创建阶段的索引添加（CREATE TABLE）

在定义新数据表结构的 `CREATE TABLE` 语句中，索引可以通过声明特定约束触发系统“隐式”生成，也可以通过显式关键字进行精细化定义。

#### 约束驱动的隐式索引创建

在数据库理论与存储引擎底层，约束负责保障数据的实体完整性与引用完整性，而索引则是底层实现高效完整性校验的物理数据结构。当我们在建表语句中声明主键约束、唯一性约束或外键约束时，MySQL 存储引擎会自动在对应字段上生成关联索引，这种方式称为隐式创建。

```sql
CREATE DATABASE IF NOT EXISTS dbtest2;
USE dbtest2;

-- 1. 创建部门表（声明主键约束）
CREATE TABLE dept (
    department_id INT PRIMARY KEY,
    department_name VARCHAR(20)
);

-- 2. 创建员工表（声明主键、唯一约束与外键约束）
CREATE TABLE emp (
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(20) UNIQUE,
    dept_id INT,
    CONSTRAINT fk_emp_dept_id FOREIGN KEY (dept_id) REFERENCES dept(department_id)
);
```

执行上述建表语句后，通过查看索引指令可以验证存储引擎的底层行为：

- **主键约束（PRIMARY KEY）**：在 `dept` 表与 `emp` 表的主键字段上，系统自动构建了聚簇索引（Clustered Index），索引名称固定为 `PRIMARY`。
- **唯一性约束（UNIQUE）**：在 `emp.emp_name` 字段上自动构建了唯一索引。由于建表时未单独为该唯一约束命名，系统默认将该字段名 `emp_name` 作为索引名称。
- **外键约束（FOREIGN KEY）**：在 `emp.dept_id` 字段上自动构建了普通外键索引，系统默认使用外键约束名 `fk_emp_dept_id` 作为该索引的标识名。

> **结论**：主键约束对应主键索引，唯一约束对应唯一索引，外键约束对应外键索引。隐式索引无需额外编写索引声明指令，随表结构约束的定义而由系统自动生成。

#### 显式定义普通索引与查看机制

如果我们需要在非约束字段上提升检索效率，就必须在建表语句的列定义尾部显式声明索引结构。

显式定义索引的完整基础语法格式如下：

```sql
CREATE TABLE 表名 (
    字段名 字段类型 [约束条件],
    ...
    [UNIQUE | FULLTEXT | SPATIAL] [INDEX | KEY] [索引名] (字段名[(长度)] [ASC | DESC])
);
```

语法关键要素解析：
1. **关键字等价性**：`INDEX` 与 `KEY` 在语法层面完全等价，均表示索引定义。在工程规范中，强烈建议统一书写为 `INDEX`，以提升代码语义的纯粹性与可读性。
2. **命名缺省策略**：若未显式指定 `[索引名]`，MySQL 默认采用被索引的第一个字段名称作为该索引的名字。然而在严谨的生产开发中，务必显式命名（如采用 `idx_字段名` 或 `uk_字段名`），确保“见名知意”。
3. **前缀长度与排序**：针对变长字符列可指定前缀截取长度 `(长度)`；尾部可选 `ASC`（升序，默认）或 `DESC`（降序，MySQL 8.0 起支持物理倒序存储）。

以下通过 `book` 演示表构建普通单列索引：

```sql
CREATE TABLE book (
    book_id INT,
    book_name VARCHAR(100),
    authors VARCHAR(100),
    info VARCHAR(100),
    comment VARCHAR(100),
    year_publication YEAR,
    -- 声明普通单列索引
    INDEX index_bname (book_name)
);
```

数据表创建成功后，可以通过两种命令行方式精确查看索引结构：

**方式一：查看建表原始语句**
```sql
SHOW CREATE TABLE book \G
```
在控制台终端中使用 `\G` 格式化展示，可以看到系统在表定义中自动补充了 `KEY index_bname (book_name)`，证实索引定义已被数据字典正确解析。

**方式二：查看索引元数据字典**
```sql
SHOW INDEX FROM book;
```

执行该指令后返回的结果集中，核心字段的技术含义见下表：

| 字段名 | 典型返回值 | 核心工程含义与判定规则 |
| :--- | :--- | :--- |
| `Table` | `book` | 当前索引所属的数据表名 |
| `Non_unique` | `1` | 唯一性标记。`0` 表示唯一索引（False，不可重复）；`1` 表示非唯一索引（True，允许重复值） |
| `Key_name` | `index_bname` | 索引名称。若是主键索引则固定显示为 `PRIMARY` |
| `Seq_in_index` | `1` | 该列在复合索引中的物理顺序序号（从 1 开始递增） |
| `Column_name` | `book_name` | 构成该索引的具体列名 |
| `Index_type` | `BTREE` | 索引的物理数据结构，在 InnoDB/MyISAM 中默认为 B+ 树（写作 BTREE） |
| `Visible` | `YES` | 索引在优化器中是否可见（MySQL 8.0 新增特性） |

通过执行计划分析工具 `EXPLAIN`，可以验证所建索引是否生效：

```sql
EXPLAIN SELECT * FROM book WHERE book_name = 'MySQL高级';
```

在返回的执行计划中：
- `possible_keys`：显示优化器评估后可能用到的候选索引，此时包含 `index_bname`；
- `key`：显示优化器实际决定采用的索引，显示为 `index_bname`；
- 若未使用索引，`key` 列将呈现为 `NULL`，意味着执行了全表扫描（type 为 ALL）。

#### 显式定义唯一索引与 NULL 值特性

唯一索引（UNIQUE INDEX）要求索引列的取值必须保持唯一，但与主键索引存在根本区别：唯一索引允许存在空值 `NULL`。

```sql
CREATE TABLE book1 (
    book_id INT,
    book_name VARCHAR(100),
    authors VARCHAR(100),
    info VARCHAR(100),
    comment VARCHAR(100),
    year_publication YEAR,
    -- 声明唯一性索引
    UNIQUE INDEX uk_idx_cmt (comment)
);
```

通过 `SHOW INDEX FROM book1;` 查验，该条记录的 `Non_unique` 值为 `0`，表明非唯一性为假（即必须唯一）。

在数据写入场景中，唯一索引体现出严格的双向特征：
1. **重复值拦截**：当插入两行完全一致的字符串时，MySQL 引擎将直接报错抛出 `Error Code: 1062. Duplicate entry '...' for key 'book1.uk_idx_cmt'`。
2. **NULL 值的宽容性**：向 `comment` 字段连续插入多次 `NULL` 值均能顺利写入成功。根据 SQL 标准及 MySQL 内部实现，`NULL` 代表“未知”，任何两个 `NULL` 进行相等性比较（`NULL = NULL`）其结果均为未知（UNKNOWN），因此唯一索引允许多行数据同时为 `NULL`。

```sql
-- 正常插入第 1 行
INSERT INTO book1 (book_id, book_name, comment) 
VALUES (1, 'MySQL高级', '适合有数据库开发经验的人员学习');

-- 再次插入完全相同 comment 将报错 Duplicate entry
-- INSERT INTO book1 (book_id, book_name, comment) VALUES (2, 'Java进阶', '适合有数据库开发经验的人员学习');

-- 连续插入 NULL 值均可成功执行
INSERT INTO book1 (book_id, book_name, comment) VALUES (3, 'Spring技术内幕', NULL);
INSERT INTO book1 (book_id, book_name, comment) VALUES (4, 'Redis深度历险', NULL);
```

> **定义**：声明唯一索引的列在插入或修改数据时必须保证非空值的唯一性；该列可以添加 `NULL`，且允许多次重复添加 `NULL`。

#### 主键索引的隐式定义与删除陷阱

主键索引本质上完全依托主键约束隐式构建，语法层面并不存在独立的 `CREATE PRIMARY INDEX` 语句。

```sql
CREATE TABLE book2 (
    book_id INT PRIMARY KEY,
    book_name VARCHAR(100),
    authors VARCHAR(100),
    info VARCHAR(100),
    comment VARCHAR(100),
    year_publication YEAR
);
```

由于主键在一个表中具有唯一性，删除主键索引的操作正是通过移除主键约束来实现的：

```sql
ALTER TABLE book2 DROP PRIMARY KEY;
```

> **易错点**：如果主键字段同时被定义了自增属性 `AUTO_INCREMENT`（例如 `book_id INT AUTO_INCREMENT PRIMARY KEY`），直接执行 `ALTER TABLE book2 DROP PRIMARY KEY;` 会引发 MySQL 报错：
> `Incorrect table definition; there can be only one auto column and it must be defined as a key`。
> 这是因为 MySQL 底层强制规定：带有 `AUTO_INCREMENT` 属性的列必须被定义为键（主键或唯一键）。因此，若要删除带自增属性的主键索引，必须先通过 `ALTER TABLE` 修改字段定义去除其 `AUTO_INCREMENT`，然后再执行 `DROP PRIMARY KEY`。

#### 联合索引与底层 B+ 树排序机制

联合索引（复合索引）是指由表中的两个或两个以上字段共同组成的索引结构。

```sql
CREATE TABLE book4 (
    book_id INT,
    book_name VARCHAR(100),
    authors VARCHAR(100),
    info VARCHAR(100),
    comment VARCHAR(100),
    year_publication YEAR,
    -- 声明三列联合索引
    INDEX mul_bid_bname_info (book_id, book_name, info)
);
```

创建成功后执行 `SHOW INDEX FROM book4;`，元数据结果中会呈现三行记录，其 `Key_name` 均为 `mul_bid_bname_info`，但 `Seq_in_index` 严格呈现为 `1`、`2`、`3`：

```text
+-------+------------+--------------------+--------------+-------------+
| Table | Non_unique | Key_name           | Seq_in_index | Column_name |
+-------+------------+--------------------+--------------+-------------+
| book4 |          1 | mul_bid_bname_info |            1 | book_id     |
| book4 |          1 | mul_bid_bname_info |            2 | book_name   |
| book4 |          1 | mul_bid_bname_info |            3 | info        |
+-------+------------+--------------------+--------------+-------------+
```

这一物理序号不可调换，它完全映射了底层的 B+ 树物理存储结构：

```text
+-------------------------------------------------------------------------+
|                  联合索引 B+ 树非叶子节点键值比较逻辑                    |
+-------------------------------------------------------------------------+
| 第一排序主键: book_id (按 ASC 绝对有序排列)                             |
|       │                                                                 |
|       ├─ 若 book_id 各不相同: 直接依 book_id 路由分支                   |
|       │                                                                 |
|       └─ 若 book_id 相同 (如多个 1001):                                 |
|               │                                                         |
|               └─ 第二排序维度: book_name (在同一 book_id 内严格升序)    |
|                       │                                                 |
|                       └─ 若 book_name 亦相同:                           |
|                               │                                         |
|                               └─ 第三排序维度: info (在组内升序排列)    |
+-------------------------------------------------------------------------+
```
> **读图说明**：联合索引底层的 B+ 树仅有一棵，树中键值并非各字段随意拼接，而是严格按照声明字段的从左至右顺序逐级确立排序维度。

这种内部拓扑结构直接催生了著名的“最左前缀原则”（Leftmost Prefix Principle）：
- **情况 A**：查询条件包含首列与次列：
  ```sql
  EXPLAIN SELECT * FROM book4 WHERE book_id = 1001 AND book_name = 'MySQL';
  ```
  执行计划显示 `key` 为 `mul_bid_bname_info`，成功利用 B+ 树根节点的有序性命中索引。
- **情况 B**：跳过首列，直接查询次列：
  ```sql
  EXPLAIN SELECT * FROM book4 WHERE book_name = 'MySQL';
  ```
  执行计划显示 `key` 为 `NULL`，索引彻底失效。因为在全局视角下，`book_name` 是散乱无序的（只有在 `book_id` 固定的子集内才有序），B+ 树无法根据无序字段进行二分或树状跳跃路由，只能退化为全表扫描。

#### 全文索引（FULLTEXT）与空间索引（SPATIAL）

##### 全文索引（FULLTEXT INDEX）
全文索引用于支撑海量长文本的高性能模糊关键字匹配，其检索方式彻底摆脱了效率极低的全表扫描 `LIKE '%关键字%'`。

```sql
CREATE TABLE test4 (
    id INT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(100),
    body TEXT,
    fulltext_content VARCHAR(255),
    -- 创建基于截取长度的前缀全文索引
    FULLTEXT INDEX futxt_idx_cnt (fulltext_content(50))
);
```

全文索引的核心技术约束与工程规范包括：
1. **字段类型限制**：全文索引只能构建在 `CHAR`、`VARCHAR`、`TEXT` 及其变体文本列上。
2. **前缀截断参数**：如 `fulltext_content(50)`，仅提取列内容的前 50 个字符构建词法索引树。这能够有效防止单个索引项体积膨胀，大幅增加单个 16KB 数据页能够容纳的索引条目数量，提升内存缓存击中率。
3. **引擎演进版本**：MySQL 5.5 及以前版本仅 MyISAM 引擎支持全文索引；自 MySQL 5.6.4 起，InnoDB 存储引擎正式支持基于倒排索引（Inverted Index）的 FULLTEXT。
4. **语法调用要求**：全文检索必须使用专门的 `MATCH(...) AGAINST(...)` 语法：
   ```sql
   SELECT * FROM test4 WHERE MATCH(fulltext_content) AGAINST('database');
   ```
   该机制检索速度比传统的 `LIKE '%database%'` 快数倍至数十倍，但在分词与停用词策略下，其结果集注重相关度排序，精度特征与完全模糊包含存在细微差异。
5. **数据写入规范**：在处理千万级文本导入时，强烈建议采取“先批量导入数据，再集中创建全文索引”的策略。若先建索引后写数据，每一行插入都会伴随复杂的分词与倒排列表维护，导致写入吞吐呈断崖式下跌。

##### 空间索引（SPATIAL INDEX）
空间索引基于 R 树（R-Tree）数据结构，专门用于多维空间坐标数据的检索加速。

```sql
CREATE TABLE test_spatial (
    geo_id INT PRIMARY KEY,
    geo_point GEOMETRY NOT NULL,
    -- 创建空间索引
    SPATIAL INDEX sp_idx_point (geo_point)
);
```

> **注意**：空间索引只能建立在四种空间数据类型（`GEOMETRY`、`POINT`、`LINESTRING`、`POLYGON`）之上，且被索引的列必须显式约束为 `NOT NULL`，否则建表将直接抛出语法错误。

### 既有数据表追加索引方式一：ALTER TABLE ... ADD

当数据表已经上线并存在既有数据时，直接修改原建表语句已不可行，必须借助 DDL 数据定义语句进行动态追加。第一种主流方式是使用 `ALTER TABLE ... ADD` 语法。

定义基准数据表：
```sql
CREATE TABLE book5 (
    book_id INT,
    book_name VARCHAR(100),
    authors VARCHAR(100),
    info VARCHAR(100),
    comment VARCHAR(100),
    year_publication YEAR
);
```

#### 添加单列普通索引
```sql
ALTER TABLE book5 ADD INDEX idx_cmt (comment);
```
执行后通过 `SHOW INDEX FROM book5;` 可见普通索引 `idx_cmt` 已追加完成，`Non_unique` 为 `1`。

#### 添加唯一索引
```sql
ALTER TABLE book5 ADD UNIQUE INDEX uk_idx_bname (book_name);
```
追加后，表中 `book_name` 字段被施加唯一性约束校验，且对应索引项的 `Non_unique` 为 `0`。

#### 添加多列联合索引
```sql
ALTER TABLE book5 ADD INDEX mul_bid_bname_info (book_id, book_name, info);
```
在追加多列索引时，必须按照工程查询频次精确确定参数顺序。最常作为过滤条件、区分度最高的核心字段必须置于最左端，确保业务 SQL 能够最大化命中前缀检索规则。

---

### 既有数据表追加索引方式二：CREATE INDEX ... ON

为既有表追加索引的第二种方式是使用独立的 `CREATE INDEX` 语句，该语法更加直观地突出了“将独立索引对象绑定到某张表”的语义。

定义基准数据表：
```sql
CREATE TABLE book6 (
    book_id INT,
    book_name VARCHAR(100),
    authors VARCHAR(100),
    info VARCHAR(100),
    comment VARCHAR(100),
    year_publication YEAR
);
```

#### 语法映射与普通索引创建
```sql
CREATE INDEX idx_cmt ON book6 (comment);
```
该指令将索引名定义置于前侧，通过 `ON 表名 (字段名)` 确立归属。

#### 唯一索引创建
```sql
CREATE UNIQUE INDEX uk_idx_bname ON book6 (book_name);
```
在 `CREATE` 与 `INDEX` 之间嵌入修饰符 `UNIQUE`，实现对唯一索引的创建。

#### 复合索引创建
```sql
CREATE INDEX mul_bid_bname_info ON book6 (book_id, book_name, info);
```

### 索引添加方式的工程对比与语法等价性

无论是在建表后采用 `ALTER TABLE ... ADD INDEX` 还是 `CREATE INDEX ... ON`，在 MySQL 内部优化器与数据字典中均具有完全等价的物理行为。

两种追加语法的结构映射关系总结如下表：

| 目标索引类型 | ALTER TABLE 追加语法 | CREATE INDEX 追加语法 |
| :--- | :--- | :--- |
| 普通单列索引 | `ALTER TABLE 表名 ADD INDEX idx_名 (列);` | `CREATE INDEX idx_名 ON 表名 (列);` |
| 唯一索引 | `ALTER TABLE 表名 ADD UNIQUE INDEX uk_名 (列);` | `CREATE UNIQUE INDEX uk_名 ON 表名 (列);` |
| 复合多列索引 | `ALTER TABLE 表名 ADD INDEX idx_名 (列1, 列2);` | `CREATE INDEX idx_名 ON 表名 (列1, 列2);` |
| 全文索引 | `ALTER TABLE 表名 ADD FULLTEXT INDEX futxt_名 (列);` | `CREATE FULLTEXT INDEX futxt_名 ON 表名 (列);` |
| 空间索引 | `ALTER TABLE 表名 ADD SPATIAL INDEX sp_名 (列);` | `CREATE SPATIAL INDEX sp_名 ON 表名 (列);` |

> **提示**：`CREATE INDEX` 语法本质上是 `ALTER TABLE` 语句的一个高级语法糖封装。唯一例外是主键索引的添加：`CREATE INDEX` 无法用于创建主键索引（不能写 `CREATE PRIMARY KEY INDEX`），若要为既有表追加主键，只能使用 `ALTER TABLE 表名 ADD PRIMARY KEY (主键列);`。日常工程中掌握其中一套并熟知相互转化规则即可游刃有余。

## 130-删除索引与索引新特性：降序索引、隐藏索引
> 对应分集：P130 | 原始标题：《130-删除索引与索引新特性：降序索引、隐藏索引》

在数据库的生命周期管理中，索引并非越多越好。随着业务迭代，某些早期设立的索引可能会沦为低频访问甚至零命中的冗余索引；或者在面临海量数据批量导入与清洗（ETL）场景时，如果表上挂载了过多二级索引，每一条写入和更新都会强行触发多个 B+ 树的实时重平衡与磁盘 I/O 刷盘，导致写入吞吐严重劣化。此时，临时或永久删除多余索引成为数据库调优的必要手段。

从语法体系上看，删除索引的操作与添加索引保持着对称的映射关系。而在 MySQL 8.0 中，官方引入了两项极具工程价值的索引新特性——真正支持物理降序存储的“降序索引”，以及支撑索引平滑“软删除”与效能评估的“隐藏索引”。本讲将从常规索引删除语法讲起，深入探究删除字段引发的联合索引级联重构机理，并跨版本横向对比 MySQL 5.7 与 8.0 在降序索引与隐藏索引上的底层行为与执行计划差异。

---

### 数据表既有索引的删除机制

与表建好后追加索引的两种语法（`ALTER TABLE ... ADD` 和 `CREATE INDEX ... ON`）完全对应，删除索引同样具备两套高度等价的指令体系。

#### 语法规则与基础删除操作

以已构建多个索引的演示表 `book5` 为例：

```sql
-- 方式一：基于 ALTER TABLE 进行删除
ALTER TABLE book5 DROP INDEX idx_cmt;

-- 方式二：基于 DROP INDEX ... ON 语法进行删除
DROP INDEX uk_idx_bname ON book5;
```

两套语法的工程对照关系如下：
- **`ALTER TABLE 表名 DROP INDEX 索引名;`**：直接在目标表对象上发起结构变更，指明要丢弃的索引标识。
- **`DROP INDEX 索引名 ON 表名;`**：显式强调删除某个索引对象，末尾必须携带 `ON 表名` 明确归属范围。

> **易错点**：如果索引字段被声明了 `AUTO_INCREMENT`（自增约束），对应的唯一索引或主键索引绝对不能被直接删除。因为 MySQL 存储引擎底层强制要求自增列必须依托于主键约束或唯一约束而存在。若强行删除承载该唯一性的索引，唯一约束随之失效，自增列将失去存在前提，系统将直接报错拦截：`Incorrect table definition; there can be only one auto column and it must be defined as a key`。

#### 删除数据列对联合索引的底层重构与级联影响

在生产开发中，经常会遇到因业务重构而删除表中某个字段的操作（`ALTER TABLE 表名 DROP COLUMN 字段名;`）。如果该字段恰好参与了联合索引（复合索引）的构成，MySQL 内部会对索引数据字典及底层 B+ 树进行自动重排与级联维护。

假设存在由三列构成的联合索引 `mul_bid_bname_info (book_id, book_name, info)`：

```text
+--------------------------------------------------------------------------+
|                     联合索引随字段删除的级联演变历程                     |
+--------------------------------------------------------------------------+
| 初始状态:                                                                |
|   复合索引包含三列: (1: book_id, 2: book_name, 3: info)                   |
|                                                                          |
| 阶段一: 执行 ALTER TABLE book5 DROP COLUMN book_name;                    |
|   中间列被删除 ──> 索引自动重置为两列: (1: book_id, 2: info)             |
|                                                                          |
| 阶段二: 执行 ALTER TABLE book5 DROP COLUMN book_id;                      |
|   最左排序列被删除 ──> 索引结构蜕化为单列普通索引: (1: info)              |
|                                                                          |
| 阶段三: 执行 ALTER TABLE book5 DROP COLUMN info;                         |
|   组成索引的所有列全部被移除 ──> 系统自动从数据字典中彻底注销该索引对象  |
+--------------------------------------------------------------------------+
```
> **读图说明**：当删除表中的某一列时，若该列是复合索引的成员，存储引擎会自动将该列从索引键中剔除并重排其余列的 `Seq_in_index` 序号；当索引所覆盖的所有字段均被物理删除时，整个索引对象随之自动消亡。

### MySQL 8.0 新特性之一：降序索引（Descending Index）

在多字段联合排序场景中，排序方向的不一致往往是导致全表扫描与文件排序（Filesort）的元凶。MySQL 8.0 彻底解决了这一历史遗留痛点。

#### 降序索引的演进历史与存储引擎约束

降序索引的语法（在列名后追加 `DESC`）早在 MySQL 4.x 时代就已经被语法解析器接受，但直到 MySQL 5.7 为止，其底层的物理存储引擎始终**完全忽略** `DESC` 关键字。无论在建表语句中声明了多少个 `DESC`，存储引擎在底层 B+ 树叶子节点中依然一律按照 `ASC`（升序）物理存储。

到了 MySQL 8.0，降序索引才真正迎来了存储引擎层面的物理落地，但该特性有明确的边界条件：
- **引擎支持**：仅限 `InnoDB` 存储引擎支持真实的降序物理存储；
- **核心价值**：消除多字段混合方向排序时的反向扫描瓶颈，避免高消耗的临时表与内存/磁盘文件排序。

#### MySQL 5.7 与 8.0 跨版本底层行为与执行计划对比

为了直观验证降序索引在两个版本中的差异，我们在两套环境下分别构建包含 800 条记录的测试表 `ts1`：

```sql
CREATE TABLE ts1 (
    a INT,
    b INT,
    INDEX idx_a_asc_b_desc (a ASC, b DESC)
);
```

##### 数据字典解析差异
在两套版本中分别执行 `SHOW CREATE TABLE ts1 \G`：
- **MySQL 5.7 输出**：`KEY idx_a_asc_b_desc (a, b)`。字段 `b` 后面的 `DESC` 被静默擦除，底层退化为普通的升序索引。
- **MySQL 8.0 输出**：`KEY idx_a_asc_b_desc (a, b DESC)`。明确保留了降序物理定义，代表 B+ 树叶子节点中，相同 `a` 值下的 `b` 键值是严格按照从大到小物理排列的。

```text
+-----------------------------------------------------------------------+
|                 底层 B+ 树中叶子节点数据排列对比 (a=1 时)             |
+-----------------------------------------------------------------------+
| MySQL 5.7 (忽略 DESC，强行升序):                                      |
|   ┌───────────────┬───────────────┬───────────────┐                   |
|   │ a=1, b=10     │ a=1, b=20     │ a=1, b=30     │ (物理正向递增)    |
|   └───────────────┴───────────────┴───────────────┘                   |
|                                                                       |
| MySQL 8.0 (真实物理降序支持):                                         |
|   ┌───────────────┬───────────────┬───────────────┐                   |
|   │ a=1, b=30     │ a=1, b=20     │ a=1, b=10     │ (物理正向递减)    |
|   └───────────────┴───────────────┴───────────────┘                   |
+-----------------------------------------------------------------------+
```
> **读图说明**：5.7 无法在物理节点中逆序存储，查询若要求 `b DESC` 只能反向扫描双向链表；8.0 在数据写入时即按真实方向构造 B+ 树有序链表。

##### 批量数据注入测试
编写存储过程向 `ts1` 灌入 800 条测试数据：

```sql
DELIMITER //
CREATE PROCEDURE insert_ts1()
BEGIN
    DECLARE i INT DEFAULT 1;
    WHILE i < 800 DO
        INSERT INTO ts1 (a, b) VALUES (CEIL(RAND() * 100), CEIL(RAND() * 100));
        SET i = i + 1;
    END WHILE;
    COMMIT;
END //
DELIMITER ;

CALL insert_ts1();
```

##### 执行计划性能实测与 Filesort 消除
执行针对混合排序场景的带限制检索：

```sql
EXPLAIN SELECT * FROM ts1 ORDER BY a ASC, b DESC LIMIT 5;
```

对比两个版本的优化器反馈：

| 评估指标 | MySQL 5.7 执行结果 | MySQL 8.0 执行结果 | 技术归因 |
| :--- | :--- | :--- | :--- |
| `possible_keys` | `NULL` | `NULL` | 纯排序列检索，无需候选过滤索引 |
| `key` | `NULL` | `idx_a_asc_b_desc` | 8.0 成功借用索引内部的物理排序 |
| `rows` | `799` | `5` | 5.7 全表扫描 799 行并排序；8.0 仅精准抓取前 5 行 |
| `Extra` | `Using filesort` | `Backward index scan; Using index`（或直接使用索引消除排序） | 8.0 彻底根除了高开销的文件排序操作 |

> **注意**：降序索引的收益前提是查询条件的排序方向与索引声明严格同构（或完全反向对称）。如果声明的索引为 `(a ASC, b DESC)`，而业务 SQL 编写为 `ORDER BY a DESC, b DESC`，排序向量无法与树内部结构对齐，优化器将再次退化为 `Using filesort`。

### MySQL 8.0 新特性之二：隐藏索引（Invisible Index）

在大型互联网生产环境中，DBA 或开发人员面临的一个经典两难困境是：某张核心表上有个可疑的低效索引，想要将其删除以释放写入性能，但又极度担心业务代码中有隐蔽的历史 SQL 强依赖该索引；一旦贸然执行物理 `DROP INDEX`，若导致生产环境发生慢查询雪崩，大表上重新执行 `ADD INDEX` 往往耗时数小时并伴随严重的锁等待与 I/O 争抢。

MySQL 8.0 引入的隐藏索引（Invisible Index）机制，正是为解决这一痛点量身定制的“软删除”（Soft Delete）与灰度验证架构。

#### 隐藏索引的核心价值与软删除理念

隐藏索引的设计精髓在于：**将索引对查询优化器的“可见性”与“物理存储维护”彻底解耦**。

```text
+-----------------------------------------------------------------------+
|                    隐藏索引 (Invisible) 的核心工作状态                |
+-----------------------------------------------------------------------+
| 读流量 (SELECT 查询):                                                 |
|   优化器评估候选集 ──> 发现索引被标记为 INVISIBLE ──> 视而不见(不可见) |
|   效果等同于该索引已被删除。                                          |
|                                                                       |
| 写流量 (INSERT / UPDATE / DELETE):                                    |
|   存储引擎底层 ──> 依然对该索引的 B+ 树进行实时双向维护与数据写入。   |
|   数据字典状态保持最新，不产生数据断层。                              |
|                                                                       |
| 生产灰度验证周期:                                                     |
|   观察 1~2 周 ──┬─> 线上无慢查询报警: 执行物理 DROP INDEX (安全着陆)  |
|                 └─> 线上突发慢 SQL: 一秒执行 ALTER VISIBLE 瞬间恢复!  |
+-----------------------------------------------------------------------+
```
> **读图说明**：隐藏索引犹如数据库层面的安全“软着陆”，既能达到模拟删除的实测效果，又具备秒级无损回滚的兜底能力。

此外，隐藏索引还可以用于精准分析单条 SQL 的性能收益：通过在会话中切换其可见状态，执行 `EXPLAIN` 前后对比，即可确切获知该索引带来的执行路径演变。

> **易错点**：主键索引（PRIMARY KEY）绝对不允许被设置为隐藏索引！在 InnoDB 架构中，主键作为聚簇索引的组织基准，存储着全部物理数据。如果主键被隐藏，系统将陷入无法确定数据行物理定位的逻辑混乱，MySQL 语法层面对此做出了强制拦截。

#### 隐藏索引的创建与可见性动态切换

隐藏索引可以通过建表、追加或就地变更三种方式进行灵活操控。

##### 建表时定义不可见索引
```sql
CREATE TABLE book7 (
    book_id INT,
    book_name VARCHAR(100),
    authors VARCHAR(100),
    info VARCHAR(100),
    comment VARCHAR(100),
    year_publication YEAR,
    -- 显式指定 INVISIBLE 关键字
    INDEX idx_cmt (comment) INVISIBLE
);
```
执行 `SHOW INDEX FROM book7;` 查看元数据，最后一列 `Visible` 的值显示为 `NO`。

此时执行查询计划分析：
```sql
EXPLAIN SELECT * FROM book7 WHERE comment = 'MySQL高级';
```
在执行计划中，`possible_keys` 与 `key` 均呈现为 `NULL`，`type` 为 `ALL`，说明优化器完全忽略了该索引的存在。

##### 表建好后追加不可见索引
```sql
-- 通过 ALTER TABLE 追加
ALTER TABLE book7 ADD UNIQUE INDEX uk_bname (book_name) INVISIBLE;

-- 通过 CREATE INDEX 追加
CREATE INDEX idx_year ON book7 (year_publication) INVISIBLE;
```

##### 动态平滑切换可见性（秒级切换）
如果某索引之前是可见状态（`Visible = YES`），希望对其进行下线灰度观测：
```sql
ALTER TABLE book7 ALTER INDEX idx_year INVISIBLE;
```
若观察期间发现业务查询受阻，需要紧急回滚恢复，无需重建数据，直接执行：
```sql
ALTER TABLE book7 ALTER INDEX idx_year VISIBLE;
```
恢复后立即执行 `EXPLAIN`，优化器即可重新选取该索引。

#### 性能隐患警示与优化器开关参数

关于隐藏索引的高级运维，必须牢记以下核心工程原则：

1. **写放大与系统开销隐患**：
   > **注意**：索引在处于不可见状态期间，**其底层的 B+ 树在执行 DML 操作时依然进行实时维护与持久化更新**。如果一个索引被长期设置为隐藏状态且未予理睬，它将成为纯粹的性能负资产——只消耗系统的内存缓存与磁盘写 I/O，却无法为任何 SELECT 查询提供加速。因此，隐藏索引只能作为临时的灰度验证过渡状态，一旦验证完毕，必须果断执行 `DROP INDEX` 进行物理卸载。

2. **优化器全局/会话开关控制**：
   默认情况下，优化器变量 `optimizer_switch` 中的 `use_invisible_indexes` 开关处于 `off` 状态：
   ```sql
   SELECT @@optimizer_switch;
   -- 内部包含 use_invisible_indexes=off
   ```
   若在特定排错测试场景下，希望让当前会话的优化器直接识别并利用所有不可见索引，可临时开启该选项：
   ```sql
   SET SESSION optimizer_switch = 'use_invisible_indexes=on';
   ```
   此时再次对不可见索引字段执行 `EXPLAIN`，优化器将突破限制重新调用该索引。测试完毕后务必及时切回 `off`，保持生产基线统一。

#### 随机生成函数与主从复制 binlog 信任机制

为了模拟逼真的业务数据，我们需要编写存储函数以生成随机字符串与随机数值。但在 MySQL 中创建自定义存储函数时，控制台常抛出如下经典报错：

```text
ERROR 1418 (HY000): This function has none of DETERMINISTIC, NO SQL, 
or READS SQL DATA in its declaration and binary logging is enabled 
(you *might* want to use the less safe log_bin_trust_function_creators variable)
```

这一报错背后隐藏着 MySQL 核心的高可用架构逻辑：

```text
+--------------------------------------------------------------------------+
|                 log_bin 与主从复制中的函数安全约束机理                    |
+--------------------------------------------------------------------------+
| 主机 (Master):                                                           |
|   执行包含 RAND() 随机逻辑的自定义函数 ──> 生成随机数据行                 |
|   写入二进制日志: 将操作语句记录到 binlog                                 |
|                                                                          |
| 网络传输 ──> binlog 增量复制同步                                         |
|                                                                          |
| 从机 (Slave):                                                            |
|   I/O 线程拉取日志 ──> SQL 线程重放(Replay)同一函数                       |
|   从机再次执行 RAND() ──> 产生完全不同的随机值! ──> 主从数据严重不一致!  |
+--------------------------------------------------------------------------+
```
> **读图说明**：当数据库开启了二进制日志（`log_bin`）以支持主从同步或数据恢复时，如果自定义函数内部包含非确定性算法（如 `RAND()`），主从两端各自运行会产生不同数据。为了防止数据不一致，MySQL 默认将系统参数 `log_bin_trust_function_creators` 设为 `0`（不信任函数创建者）。

在本地单机测试或明确数据生成的场景下，我们必须提升权限全局开启信任：

```sql
-- 查看当前变量配置 (默认通常为 0)
SHOW GLOBAL VARIABLES LIKE 'log_bin_trust_function_creators';

-- 全局开启信任参数 (若需永久生效，需写入 my.cnf/my.ini 中的 [mysqld] 段)
SET GLOBAL log_bin_trust_function_creators = 1;
```

设置完毕后，顺利创建随机生成函数：

```sql
DELIMITER //

-- 1. 生成指定长度的随机中文字符/英文字符串函数
CREATE FUNCTION rand_string(n INT) RETURNS VARCHAR(255)
BEGIN
    DECLARE chars_str VARCHAR(100) DEFAULT 'abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ';
    DECLARE return_str VARCHAR(255) DEFAULT '';
    DECLARE i INT DEFAULT 0;
    WHILE i < n DO
        SET return_str = CONCAT(return_str, SUBSTRING(chars_str, FLOOR(1 + RAND() * 52), 1));
        SET i = i + 1;
    END WHILE;
    RETURN return_str;
END //

-- 2. 生成指定区间随机整数函数
CREATE FUNCTION rand_num(from_num INT, to_num INT) RETURNS INT
BEGIN
    DECLARE i INT DEFAULT 0;
    SET i = FLOOR(from_num + RAND() * (to_num - from_num + 1));
    RETURN i;
END //

DELIMITER ;
```

### 适合创建索引的情况 1：字段数值具备唯一性限制

#### 规则内涵与工程标准

在业务表建模中，只要某个业务字段（或由多个业务字段拼装而成的组合字段）在现实物理世界中具备唯一特性（如身份证号、员工工号、学籍编号、订单流水号），**必须将其建立为唯一索引（UNIQUE INDEX）**。

> **结论**：阿里巴巴《Java 开发手册》MySQL 规约中做出强制规定：业务上具有唯一特性的字段，即使是多个字段的组合，也必须建成唯一索引。

很多开发人员存在一种思维误区：担心给字段加上唯一索引后，每次执行 `INSERT` 时存储引擎都要进行一次唯一性校验，从而拖垮写入性能。实际上，对于非超大规模高频并发瞬时写入场景，维护唯一索引所增加的纳秒级微小开销几乎可以忽略不计；但它对查询性能的提升，以及对底层业务数据完整性的防御作用，收益是不可估量的。

#### 底层 B+ 树检索阻断机制

从 B+ 树物理结构剖析，唯一索引与普通索引在定位目标值时存在根本性差异：

```text
+--------------------------------------------------------------------------+
|                  唯一索引与普通索引在 B+ 树叶子页的检索差异              |
+--------------------------------------------------------------------------+
| 目标值: 检索 student_id = 10025                                          |
|                                                                          |
| 普通索引检索流程:                                                        |
|   根节点/目录页二分查找 ──> 定位叶子数据页 ──> 二分查找到 10025          |
|   ──> 无法确定后续是否仍有 10025 ──> 沿单向/双向链表向后顺序线性扫描     |
|   ──> 直至遇到首个 10026 ──> 若恰好处于页边界，还需触发跨页 I/O 读下一页! |
|                                                                          |
| 唯一索引检索流程:                                                        |
|   根节点/目录页二分查找 ──> 定位叶子数据页 ──> 二分查找到 10025          |
|   ──> 机制判定: 数据行全局唯一 ──> 立即停止扫描! 零多余 I/O 消耗!         |
+--------------------------------------------------------------------------+
```
> **读图说明**：普通索引在命中第一条匹配记录后必须继续向后试探扫描，直到确认不同值出现；唯一索引一旦在叶子节点比对命中，直接阻断检索流程，具有最严谨的短路特性。

### 适合创建索引的情况 2：频繁作为 WHERE 查询条件的字段

在实际业务系统中，高频出现在 `WHERE` 过滤子句中的列是设立索引最直观的候选对象。

#### 百万级数据下的实测对照

在 100 万条记录的 `student_info` 表中，针对学号 `student_id` 执行精确等值查询。

##### 无索引状态下的基准测试
```sql
SELECT * FROM student_info WHERE student_id = 12345;
```
- **实测耗时**：`276 ms`（0.276 秒）；
- **执行过程**：优化器无可用索引，被动发起全表扫描（Full Table Scan），顺序逐行解析 100 万行物理记录。

##### 追加普通单列索引
```sql
ALTER TABLE student_info ADD INDEX idx_sid (student_id);
```
> **提示**：为 100 万行表追加索引本身需要消耗一定系统时间（实测约数秒）。这是因为存储引擎需要分配独立的索引空间（扩展 `.ibd` 物理文件体积），对目标字段执行全局排序并依次构建 B+ 树节点。这如同 Redis 提前将数据载入内存，前期投入的物理与构建成本，是为了换取日后数万次查询的高速红利。

##### 索引构建后的检索表现
```sql
SELECT * FROM student_info WHERE student_id = 12345;
```
- **实测耗时**：`43 ms`（0.043 秒）；
- **性能增益**：耗时从 276ms 下降到 43ms，查询性能瞬间提升 6 倍以上。多次重复取平均值，增益更为稳定明显。

### 适合创建索引的情况 3：经常作为 GROUP BY 和 ORDER BY 的列

业务查询中不仅存在条件过滤，还大量充斥着数据汇总（`GROUP BY`）与结果集排序（`ORDER BY`）。这两类操作往往消耗大量的 CPU 算力与临时内存缓冲区。

#### 索引消除排序的底层机理

B+ 树的物理组织结构决定了其叶子节点内部不仅通过行记录指针串联，各个数据页之间亦由双向链表相连，整个索引在逻辑与物理上**天然严格有序**：
- **对于 `ORDER BY`**：若排序字段命中索引，存储引擎只需沿着有序链表顺次抓取数据即可，彻底免去全表载入内存或借助磁盘进行的快速排序（消除 `Using filesort`）。
- **对于 `GROUP BY`**：分组的本质是将相同值的行聚拢在一起。因为索引已提前排好序，所有相同值的记录物理上彼此紧密相邻。引擎只需顺序扫描一次链表，在值跳变处进行分组归集即可，无需维护哈希表或额外构建内部临时表（消除 `Using temporary`）。

#### GROUP BY 单独作用下的实测

在 100 万行表上按学号进行选课分组统计：
```sql
SELECT student_id, COUNT(*) AS course_count 
FROM student_info 
GROUP BY student_id 
LIMIT 100;
```
- **在存在 `idx_sid` 索引时**：实测耗时 `41 ms`；
- **执行 `DROP INDEX idx_sid ON student_info;` 卸载索引后**：实测耗时飙升至 `866 ms`！
- **对比分析**：性能相差逾 20 倍。无索引时，MySQL 必须在内存建立临时表对 100 万行数据执行聚合哈希计算，带来极重的 I/O 与 CPU 压力。

#### 联合查询场景下联合索引的列序博弈

当一条业务 SQL **同时包含 GROUP BY 与 ORDER BY** 时，索引的设计策略将变得极为敏感与微妙。

实测目标 SQL：
```sql
SELECT student_id, COUNT(*) AS cnt, create_time 
FROM student_info 
GROUP BY student_id 
ORDER BY create_time DESC 
LIMIT 100;
```

> **易错点**：执行上述语句若遭遇 `ERROR 1055 (42000): Expression #3 of SELECT list is not in GROUP BY clause... which is not functionally dependent on columns in GROUP BY clause; this is incompatible with sql_mode=only_full_group_by` 拦截，需先调整会话模式移除严格模式：
> ```sql
> SET @@sql_mode = REPLACE(@@sql_mode, 'ONLY_FULL_GROUP_BY,', '');
> ```

##### 方案一：分别设立两个独立的单列索引
```sql
ALTER TABLE student_info ADD INDEX idx_sid (student_id);
ALTER TABLE student_info ADD INDEX idx_ctime (create_time);
```
执行上述复杂 SQL：
- **实测耗时**：`5.212 秒`！
- **EXPLAIN 解析**：优化器在 `idx_sid` 与 `idx_ctime` 之间只能二选一。依照 SQL 逻辑执行生命周期，先走 `GROUP BY` 后走 `ORDER BY`，优化器被迫选择 `idx_sid`。这意味着 `ORDER BY create_time` 无法利用索引，系统对海量分组中间结果强行执行了昂贵的 `Using filesort`。

##### 方案二：构建严格列序的联合索引（GROUP BY 列在左，ORDER BY 列在右）
```sql
-- 清理旧索引并构建联合索引
DROP INDEX idx_sid ON student_info;
DROP INDEX idx_ctime ON student_info;

ALTER TABLE student_info ADD INDEX idx_sid_ctime (student_id, create_time);
```
重新执行查询：
- **实测耗时**：`0.257 秒`！
- **性能飞跃**：从 5.212 秒骤降到 0.257 秒，性能暴增 20 倍以上！因为在 `student_id` 分组之后，组内天然依赖联合索引的第二列保持 `create_time` 有序，彻底消除了内存二次重排。

##### 方案三：错误反转联合索引列序（ORDER BY 列在左，GROUP BY 列在右）
```sql
DROP INDEX idx_sid_ctime ON student_info;

ALTER TABLE student_info ADD INDEX idx_ctime_sid (create_time, student_id);
```
重新执行查询：
- **实测耗时**：反弹至 `3.790 秒`；
- **机理剖析**：由于最左前缀原则，由于首先进行的是 `GROUP BY student_id`，优化器无法跳过首列 `create_time` 直接使用次列排序，导致联合索引彻底无法为分组提供支撑，执行退化。

> **结论**：当查询中同时存在 `GROUP BY` 与 `ORDER BY` 时，应建立联合索引，且**必须严格将 `GROUP BY` 的字段置于联合索引的最左侧，将 `ORDER BY` 的字段置于其后**；在 MySQL 8.0 中若 ORDER BY 频繁使用降序，建议在定义索引时对对应列直接指明 `DESC`。

### 适合创建索引的情况 4：UPDATE、DELETE 语句中的 WHERE 条件列

开发人员往往只关注 `SELECT` 语句的索引配置，却容易忽视写入与变更操作中的索引价值。

#### 检索与更新的联动成本

在执行 `UPDATE` 或 `DELETE` 语句时，无论底层要修改多少字段，存储引擎的第一步操作**永远是依据 WHERE 子句中的检索条件在物理磁盘上将待操作的数据行检索出来**。

```sql
UPDATE student_info SET student_id = 10002 WHERE name = '411222199010123456';
```

##### 条件列无索引时的表现
- **实测耗时**：`0.633 秒`。
- **并发隐患**：在 InnoDB 引擎中，为了定位到满足 `name` 条件的记录，全表扫描会导致引擎对扫描过的全部记录行加互斥锁（X 锁），极易导致整个表的并发更新完全阻塞，甚至诱发毁灭性的死锁雪崩。

##### 为 WHERE 列追加索引
```sql
ALTER TABLE student_info ADD INDEX idx_name (name);
```
构建索引后再次执行相同的 `UPDATE` 变更：
- **实测耗时**：降至 `0.001 秒`（1 毫秒）！
- **性能提升**：执行速度飙升逾 600 倍，且 InnoDB 精准加行锁，彻底杜绝了大范围锁表隐患。

> **结论**：对数据依据某列筛选后再进行 UPDATE 或 DELETE 操作时，必须为 WHERE 过滤列建立索引。如果**被更新的字段是非索引列**（如上述语句中更新 `student_id`，而该列此时若无复杂冗余索引维护），性能提升将达到极致峰值，既享受了毫秒级精确定位的收益，又免去了多棵 B+ 树的级联维护开销。

### 适合创建索引的情况 5：DISTINCT 去重操作字段

在报表统计与业务防重逻辑中，经常需要执行去重查询：

```sql
SELECT DISTINCT student_id FROM student_info;
```

#### 无索引与有索引的底层执行差异

去重操作的核心逻辑在于“相同键值的判定与合并”：
- **无索引状态**：数据在物理磁盘上是散乱无序存放的。存储引擎必须进行全表扫描，将 100 万行记录逐一加载到内存临时表（或临时哈希表）中进行唯一性判定，或者在临时表中执行全量排序后去重。在百万级表实测中，该操作耗时高达 `0.683 秒`。
- **构建索引后**：在 `student_id` 字段上建立 B+ 树索引后，所有相同值的键在叶子节点的数据页中**物理天然连续相邻**。引擎只需顺着叶子节点链表进行单遍流式扫描，一旦当前键与前一个键不同便输出结果，遇到相同键直接指针前移跳过。实测耗时骤降至 `0.010 秒`（10 毫秒），性能提升近 70 倍。

> **结论**：DISTINCT、ORDER BY 与 GROUP BY 底层完全复用了 B+ 树物理有序的红利。对于高频进行 DISTINCT 去重的列，建立索引能够直接消除内存临时表与磁盘哈希计算。

### 适合创建索引的情况 6：多表 JOIN 连接操作时的索引规范

多表关联是关系型数据库的核心能力，也是慢 SQL 滋生的重灾区。在多表连接场景中构建索引，必须恪守以下三项工程铁律。

#### 关联表数量的硬性上限控制

> **注意**：在业务 SQL 编写中，**JOIN 连接的表数量尽量不要超过 3 张**。

从执行引擎底层机制剖析，MySQL 处理多表关联主要采用嵌套循环连接（Nested-Loop Join, NLJ）算法及其变体。每增加一张关联表，就相当于在代码底层增加了一层 `for` 循环：
- 单表查询复杂度为 $O(N)$；
- 双表关联在最坏无索引情况下呈两层循环 $O(N^2)$；
- 三表关联则急剧攀升至 $O(N^3)$。

一旦关联表达到 4~5 张且数据量庞大，笛卡尔乘积的中间结果集将呈指数级爆炸，极易耗尽系统内存与缓冲区，拖垮整机性能。

#### WHERE 过滤列与 ON 连接列的协同索引

在多表关联查询中，必须对驱动表与被驱动表的关键列设立精准索引：

```sql
-- 学生表与课程表关联查询
SELECT s.student_id, s.name, c.course_name 
FROM student_info s 
JOIN course c ON s.course_id = c.course_id 
WHERE s.name = 'AbcDef';
```

1. **WHERE 过滤列构建索引**：
   在 `student_info.name` 无索引时，执行该关联查询耗时 `0.227 秒`；一旦为 `name` 字段追加索引 `idx_name`，耗时瞬间降至 `0.001 秒`（1 毫秒），性能提升两百倍以上。
2. **ON 连接键构建索引**：
   对于连接条件 `ON s.course_id = c.course_id`，被驱动表（此处为 `course`）的连接键 `course_id` 必须建立索引。驱动表匹配出的每一行，都能通过被驱动表连接键上的 B+ 树以 $O(\log N)$ 复杂度极速命中，彻底避免在被驱动表上做全表轮询。

#### 关联字段数据类型一致性陷阱与隐式转换失效

> **易错点**：连接条件两端的字段类型**必须保持物理层面的绝对一致**（不仅数据类型要相同，字符集与校对规则亦须一致）。

若 `student_info.course_id` 声明为 `INT`，而 `course.course_id` 误声明为 `VARCHAR`：
- 在执行连接时，由于类型不同，MySQL 优化器会自动注入隐式类型转换函数（如内部调用 `CAST()` 将字符串转换为数字）；
- 依据索引失效准则，**在索引字段上应用任何内置函数或进行计算，该列的索引将彻底失效**；
- 最终导致即便为 `course.course_id` 建了索引，优化器也无法使用，系统被迫退化为海量磁盘全表嵌套扫描。

### 适合创建索引的情况 7：优先选用较小的数据类型构建索引

在表结构设计与字段选型阶段，在满足业务最大上限的前提下，应严格遵循“能小则小”的原则（如在整型中，优先顺序为 `TINYINT < SMALLINT < MEDIUMINT < INT < BIGINT`）。

这一选型不仅减少了物理表数据的体积，更对索引树的性能产生了深远影响：

```text
+--------------------------------------------------------------------------+
|                  键值类型大小对 B+ 树物理页容量与树高的影响              |
+--------------------------------------------------------------------------+
| InnoDB 物理数据页固定大小: 16 KB                                         |
|                                                                          |
| 场景 A: 采用大类型 (如 BIGINT 或长 VARCHAR, 单个键值+指针占 100 字节)   |
|   16 KB 目录页容纳项 = 16384 / 100 ≈ 163 项                              |
|   数据量 1000 万时 ──> 树高度膨胀至 4 层 ──> 检索单行需 4 次磁盘 I/O!     |
|                                                                          |
| 场景 B: 采用紧凑类型 (如 INT, 单个键值+指针仅占 14 字节)                 |
|   16 KB 目录页容纳项 = 16384 / 14 ≈ 1170 项                             |
|   数据量 1000 万时 ──> 树结构扁平 (仅需 2~3 层) ──> 检索仅需 2~3 次 I/O!|
+--------------------------------------------------------------------------+
```
> **读图说明**：键值占用字节越小，单个 16KB 数据页能够容纳的索引条目就越多，这不仅能显著压缩整棵 B+ 树的层高（减少寻址所需的磁盘 I/O 次数），还能大幅提高内存 Buffer Pool 的缓存命中率。

此外，在 InnoDB 引擎中，**所有二级索引的叶子节点均需要存储主键值**。如果主键字段被错误地定义为超长类型，这一冗余开销将在表上的每一个二级索引中被成倍放大，最终引发全表索引物理空间的灾难性膨胀。

### 适合创建索引的情况 8：长文本字段构建前缀索引（Prefix Index）

对于变长字符列（如 `address VARCHAR(120)`），如果直接为全字段创建索引，整段长文本都会被完整复制到 B+ 树的每一个节点中。这不仅严重浪费内存与存储空间，而且在树节点遍历比较时，逐字符对百字节字符串进行比对将极度消耗 CPU。

#### 前缀索引的截断机制与回表比对

解决方案是只截取长字符串的前 $n$ 个字符构建索引，即前缀索引：

```sql
-- 仅截取 address 字段的前 12 个字符建立索引
ALTER TABLE student_info ADD INDEX idx_addr (address(12));
```

前缀索引的物理查询与回表流转机制如下：

```text
+--------------------------------------------------------------------------+
|                        前缀索引的二次验证与回表流程                      |
+--------------------------------------------------------------------------+
| 查询条件: WHERE address = '北京市海淀区中关村南大街1号院'               |
|                                                                          |
| 步骤 1: 扫描前缀索引树                                                   |
|   依据前 12 字符 ('北京市海淀区中关村南') 进行二分查找与精确定位         |
|                                                                          |
| 步骤 2: 提取主键 ID                                                      |
|   若有多行记录的前 12 字符完全一致，索引树中均视为命中候选               |
|   分别获取它们对应的聚簇主键 (如 id = 101, 102)                          |
|                                                                          |
| 步骤 3: 走聚簇索引回表                                                   |
|   利用主键 ID 回表抓取整行完整物理数据                                   |
|                                                                          |
| 步骤 4: 内存完整字符精准核验                                             |
|   在 Server 层内存中，将完整的 120 字符逐一比对，剔除前缀相同但后缀不同的   |
|   无效记录，输出最终准确行                                               |
+--------------------------------------------------------------------------+
```
> **读图说明**：前缀索引仅负责在索引阶段实现高比例的粗筛过滤，最终的一致性由回表后的完整列比对予以兜底保障。

#### 区分度计算与最佳截取长度选取公式

截取长度 $n$ 的选取是一门精准的权衡艺术：截得过长，达不到压缩空间的目的；截得过短，大量记录的前缀相互重复，导致回表次数过多，性能退化。

科学的评估方法是借助基数与区分度公式进行比值分析：

$$\text{区分度} = \frac{\text{COUNT}(\text{DISTINCT } \text{LEFT}(column\_name, n))}{\text{COUNT}(*)}$$

通过逐步增加长度 $n$，观察区分度曲线的收敛情况：

```sql
SELECT 
    COUNT(DISTINCT LEFT(address, 10)) / COUNT(*) AS sel10,
    COUNT(DISTINCT LEFT(address, 15)) / COUNT(*) AS sel15,
    COUNT(DISTINCT LEFT(address, 20)) / COUNT(*) AS sel20,
    COUNT(DISTINCT LEFT(address, 25)) / COUNT(*) AS sel25
FROM student_info;
```

> **结论**：
> 1. 阿里巴巴《Java 开发手册》做出强制规定：在 VARCHAR 字段上建立索引时，必须指定索引长度，没必要对全字段建立索引，根据实际文本区分度决定索引长度即可。
> 2. 依据大量生产经验，前缀长度通常取到 **20 左右**时，其区分度即可达到 **90% 以上**（即比值大于 0.9），此时继续增加长度带来的区分度边际收益极低，应当止步于该长度。

#### 前缀索引对 ORDER BY 排序的致命制约

> **注意**：**前缀索引无法直接用于 ORDER BY 排序**！
> 这是因为前缀索引树只维护了前 $n$ 个字符的相对次序。当多条记录的前 $n$ 个字符完全相同时，它们在索引树中的排列是随机或依主键排列的，无法反映第 $n+1$ 个字符及以后的真实字母顺序。因此，一旦对声明了前缀索引的列执行 `ORDER BY address`，优化器将判定该索引对全局排序无效，系统被迫退化为高开销的 `Using filesort`。

---

### 适合创建索引的情况 9：区分度（散列性）高的列适合建索引

#### 列的基数与散列度定义

- **列的基数（Cardinality）**：指某一列中不重复数值的实际物理个数。例如某列包含 9 条数据，其值为 `(2, 5, 8, 2, 5, 8, 2, 5, 8)`，其记录数是 9，但去除重复后只有 3 个独立值，因此该列的基数仅为 3。
- **基数与分散性的关系**：在总行数恒定的前提下，**基数越大，该列中的数据越分散（区分度越高）；基数越小，数据分布越集中（区分度越低）**。

#### 低基数列的索引反噬效应

以 100 万条记录的 `student_info` 表中的 `gender`（性别）字段为例：
- 该列的值非男即女，基数只有 2；
- 区分度仅为 $2 / 1000000 = 0.000002$；
- 若在此列建立索引并执行 `WHERE gender = '女'`，优化器通过统计信息发现该查询将命中约 50 万行数据。如果走二级索引，系统需要执行 50 万次二级索引寻址和 50 万次聚簇回表随机 I/O，其开销远超直接进行一次从头到尾的单遍物理全表顺序扫描。因此，优化器会直接放弃该索引。

> **提示**：在工程实践中，通常要求字段的区分度超过 **33%** 时才具备建立索引的价值；主键与唯一键的区分度为 100%（值为 1），是最理想的索引构建对象。

---

### 适合创建索引的情况 10 与 11：联合索引的列序与架构优势

#### 情况 10：高频列与最高区分度列置于联合索引最左端

联合索引严格遵循最左前缀原则。当构建由多列构成的复合索引时，**必须将业务查询中最频繁出现、且字段区分度最高的列置于最左侧**：

```sql
-- 业务最常按 student_id 单独查，或者与 course_id 联合查
ALTER TABLE student_info ADD INDEX idx_sid_cid (student_id, course_id);
```
此种结构能够完美支持：
1. `WHERE student_id = ? AND course_id = ?`（完全命中）
2. `WHERE student_id = ?`（命中首列）

若反向声明为 `(course_id, student_id)`，那么高频单独查询 `WHERE student_id = ?` 将彻底无法利用该索引。

#### 情况 11：多字段检索时联合索引显著优于多个单列索引

很多初学者容易犯下“针对每一个过滤字段分别建一个单列索引”的错误：
- 为表分别建立 `idx_sid(student_id)`、`idx_ctime(create_time)`、`idx_cid(course_id)` 三个独立索引；
- 当执行多条件查询时，MySQL 优化器在绝大多数情况下**只能在多个候选索引中择优选取其中一个**，其余两个索引不仅在查询中完全处于闲置失效状态，而且在每次数据写入更新时，存储引擎还要同时为这 3 棵独立的 B+ 树做维护与磁盘刷盘。

而如果将其归并为一个联合索引 `idx_sid_ctime_cid (student_id, create_time, course_id)`：
- 仅需维护一棵物理 B+ 树，写入与磁盘开销骤减；
- 单条复杂 SQL 能够一举利用多列联合过滤，大幅削减回表数据量；
- 在特定查询下还能达成“覆盖索引”（Covering Index），彻底免除回表操作。

---

### 单表索引数量限制规范（单表 ≤ 6 个）与优化器开销

在掌握了诸多适合创建索引的场景后，必须始终保持系统级架构克制。

> **结论**：**单张数据表上的索引数量通常严格控制在 6 个以内**。

设置这一红线背后存在三大底层支撑因素：

| 约束维度 | 底层物理与运行时机理剖析 |
| :--- | :--- |
| **磁盘与内存空间膨胀** | 每个索引都是一棵独立的物理 B+ 树。在海量数据表上，索引体积常常迅速超越原始数据表本身的物理体积，急剧挤占宝贵的 Buffer Pool 缓存内存。 |
| **DML 写入性能劣化** | 执行 `INSERT`、`UPDATE`、`DELETE` 操作时，所有受影响的二级索引必须同步进行节点寻找、页分裂、页合并与磁盘重写入，导致写性能断崖式下跌。 |
| **优化器成本计算与解析延迟** | 在 SQL 执行编译阶段，基于成本的优化器（CBO）必须评估 `possible_keys` 中的每一个候选索引，计算其预计 I/O 成本与 CPU 耗时。单表挂载索引过多，会导致优化器在路径枚举与代价计算上消耗大量 CPU 算力与执行时间，严重拖慢查询的响应起步。 |

## 133-不适合创建索引的7种情况
> 对应分集：P133 | 原始标题：《133-不适合创建索引的7种情况》

很多人学完索引之后，往往会陷入一个极端的认知误区——觉得索引既然能让查询飞起来，那索性把表里所有的字段都加上索引，或者只要看哪个字段顺眼就给它挂个 B+ 树。这种“索引多多益善”的想法在实际生产中是非常危险的。上一讲我们系统剖析了适合创建索引的 11 种经典业务场景，这一讲我们就必须把天平拨回来，严肃看一看究竟在哪些情况下**坚决不适合创建索引**。

索引从来不是免费的午餐，它是一把极其锋利的双刃剑：在大幅降低 `SELECT` 检索耗时的同时，必然会增加磁盘文件的物理开销，并且在每一次 `INSERT`、`UPDATE`、`DELETE` 时增加动态维护 B+ 树平衡与节点分裂的巨大代价。我们将开发中最容易踩坑的 7 种反模式场景归纳如下，帮助你在库表设计时建立清晰的取舍边界。

---

### 过滤与排序结构中无引用的冷门字段

在 `WHERE` 条件、`GROUP BY` 分组或 `ORDER BY` 排序等查询子句中完全使用不到的字段，绝对不要去为其创建索引。

索引的核心价值在于提供基于键值有序排列的快速定位（二分查找）或消除排序动作（FileSort）。如果一个字段在系统的所有业务 SQL 中都只作为 `SELECT` 投影列表中的普通输出项，而从未出现在过滤或分组排序子句中，那么为它建立 B+ 树索引纯粹是在浪费存储与维护资源。

> **注意**：不要觉得“万一以后业务要查呢”就提前建上。索引的添加应当由真实的慢查询日志、业务高频查询路径或明确的技术方案驱动，无依据的超前设计在数据库领域就是负债。

---

### 数据量极小的轻量级数据表

在数据量很小的表（例如全表记录数少于 1000 行）中，通常完全没有必要创建任何二级索引。这正是俗话说的“杀鸡焉用牛刀”。

#### 小表全表扫描与索引检索的成本倒挂

当一张表的行数只有几百条时，数据往往只需要一两个数据页（16 KB/页）就能全部容纳。此时数据库进行一次全表扫描，只需要将这极少数的数据页连续读入内存缓冲池（Buffer Pool），然后在内存中进行一次顺序遍历，耗时极短（通常在毫秒级以内甚至显示为 `0.00s`）。

如果我们非要给它建一个二级索引，查询引擎的检索路径反而变得更加冗长：

```text
【全表扫描路径（小表优势）】
直接顺序扫描数据页（1~2 个 Page） ---> 内存连续匹配 ---> 立即输出结果

【二级索引查找路径（小表劣化）】
检索二级索引根节点 Page ---> 二级索引叶子节点 Page ---> 拿到主键回表聚簇索引 Page
```

对于非聚簇索引，引擎先要在二级索引树上进行页寻址，拿到对应的主键值后，再回到主键聚簇索引树上进行一次“回表（Bookmark Lookup）”。这一来一回的页跳转和树查找，其指令开销和逻辑读次数甚至可能超过直接读两个数据页。在某些含有变长字符串的场景下，加了索引的小表查询耗时甚至可能比纯全表扫描还要高。

#### 真实测试案例剖析

为了验证这一现象，我们准备两个结构完全相同的小表，各存入 900 条记录进行性能比对：

```sql
-- 表 1：无二级索引
CREATE TABLE test_small_no_index (
    id INT PRIMARY KEY AUTO_INCREMENT,
    col_b INT
) ENGINE=InnoDB;

-- 表 2：在 col_b 上建立常规索引
CREATE TABLE test_small_with_index (
    id INT PRIMARY KEY AUTO_INCREMENT,
    col_b INT,
    KEY idx_col_b(col_b)
) ENGINE=InnoDB;
```

通过存储过程分别向两个表灌入 900 条离散数据后，执行等值条件查询：

```sql
SELECT * FROM test_small_no_index WHERE col_b = 9879;
SELECT * FROM test_small_with_index WHERE col_b = 9879;
```

在实际测试中，两者的执行时间均显示为 `0.00s`。在数据量小于 1000 行的量级下，索引的 B+ 树查找算法优势根本无法被感知，反而徒增了每次插入和更新时维护索引结构的额外开销。

> **结论**：当表记录数低于 1000 行时，应默认放弃除主键以外的多余索引设计，避免徒增存储开销与维护负担。

---

### 大量重复取值的低区分度字段

在区分度极低、包含大量重复值的列上，坚决不要建立索引。这一原则与我们在上一讲提到的“优先在高区分度字段上建索引”完全互为镜像。

#### 区分度过低导致索引退化

一个索引是否有效，关键在于它能否帮助优化器以极高的比例过滤掉不符合条件的数据。典型代表就是“性别”字段（通常只有“男”和“女”两种取值，各占约 50%）。

当你在一个包含数十万行记录的表中针对“性别”字段建立索引时，查询条件 `WHERE gender = '男'` 会命中整棵 B+ 树叶子节点中整整一半的数据。优化器一旦发现需要遍历二级索引树的一半叶子节点，并且对每一条命中记录都要进行一次回表操作，回表带来的离散随机 I/O 成本将极其惊人。在这种情况下，MySQL 优化器通常会直接放弃使用该索引，转而强制退化为全表扫描。

```text
B+ 树叶子节点分布示意（性别列）：
[ 男 | 男 | 男 | 男 | 男 ... (50%) ]   [ 女 | 女 | 女 | 女 ... (50%) ]
              ↓
  命中了 50 万条主键记录
              ↓
  引发 50 万次离散回表 I/O（性能暴跌，优化器直接弃用索引）
```

#### 极端倾斜分布下的特例分析

那么低区分度字段是不是在任何情况下都绝对不能建索引呢？并非如此。如果数据分布存在**极度不均衡（倾斜）**，并且业务高频查询命中那极小比例的极少数记录，索引就会产生奇效。

我们来看一个生动的真实场景：假设有一所历史悠久的师范类或外语类女子院校，其学生表总共有 100 万行记录。由于历史和学科特点，全校男生总共只有 10 个人，而女生有 999,990 人。

我当年本科读师范大学的时候就有类似的生活体验：传说学校的男女比例达到惊人的 7:1。走在校园的主干道上，放眼望去全是结伴而行的女生；男生如果结成一拨，那大概率只有两种可能——要么去篮球场打球，要么组队去网吧通宵。后来我到北航读研究生，大家都知道北航是工科院校，男女比例出现彻底的逆向失调，当时就格外怀念本科时那种校园氛围。

把这个极端的男女比例映射到数据库数据上：
- 男性比例为 $10 / 1,000,000 = 1/100,000$（十万分之一）；
- 如果业务需要频繁执行 `SELECT * FROM student WHERE gender = '男'`；
- 此时如果在 `gender` 上建立了索引，B+ 树检索能够精准定位并锁定这 10 条叶子节点数据，仅仅进行 10 次回表操作，查询耗时直接从全表扫描的 0.6 秒以上断崖式下降到 0.00 秒级别，性能提升达数十倍。

但如果业务要查的是那 999,990 个女生，索引就彻底失效了。

> **判定基准**：在常规业务场景下，当某一列中某个特定取值的重复率超过全部数据的 **10%** 时，该列通常就不再具备良好的索引筛选收益，应当坚决避免创建单列索引。

---

### 频繁变更的字段与高频写入的业务表

频繁被 `UPDATE` 的列，以及承担极高写入压力（高频 `INSERT`、`UPDATE`、`DELETE`）的业务表，必须极其克制地设计索引。

这一场景包含两个互相关联的维度：

#### 频繁更新的特定字段
当一个字段被频繁修改时，每次执行 `UPDATE`，InnoDB 不仅需要修改聚簇索引页中的记录本身，还必须同步在对应的二级索引 B+ 树上删除旧键值、计算新位置并插入新键值。如果修改引发了键值顺序的跨页变动，还会触发索引页的分裂与合并。因此，高频更新的字段挂载索引会严重拉低系统的写吞吐量。

#### 频繁写操作的业务表
对于电商下单流水、用户行为埋点日志等写多读少的事务表，如果一张表上设置了 5~6 个甚至更多的二级索引，那么每一次单行插入操作，后台都必须并发写入 1 个聚簇索引和 5~6 棵二级索引树：

```text
事务提交 INSERT INTO trade_order (...)
    ├── 1. 写入 Redo Log / Undo Log
    ├── 2. 插入聚簇索引（Clustered Index B+ Tree）
    ├── 3. 插入二级索引 idx_buyer_id B+ Tree
    ├── 4. 插入二级索引 idx_order_sn B+ Tree
    ├── 5. 插入二级索引 idx_create_time B+ Tree
    └── 6. 插入二级索引 idx_order_status B+ Tree
```

所有索引维护的成本将呈线性累加，不仅加剧了磁盘 I/O 竞争与缓冲池脏页刷新负担，还极易引发高并发事务之间的行锁和间隙锁冲突。

---

### 散列无序的非单调自增列作为索引键

坚决不建议使用散列、无序的值作为索引列，尤其是严禁作为表的主键聚簇索引。

常见的无序值包括通用唯一识别码（UUID）、MD5 散列值、随机字符串以及身份证号码等。虽然这些字段通常满足“非空且唯一”的约束条件，但它们在数值大小或字符字典序上呈现出完全离散、随机跳跃的物理分布。

#### 聚簇索引的物理特性与页分裂机理

InnoDB 的聚簇索引是严格按照主键大小在物理逻辑页内维护双向链表和有序槽位的，默认采取升序规则排列：

```text
【单调自增主键（AUTO_INCREMENT）插入】
Page 1: [1 -> 2 -> 3 -> 4] (满)
                        ↓
Page 2: [5 -> 6 -> 7 -> ...] (顺序追加在末尾，无需移动旧记录，零分裂开销)

【无序散列键（如 UUID）随机插入】
Page 1 已满: [10 -> 25 -> 40 -> 80]
此时插入 UUID 对应的值 32 ---> 必须强行插入 25 与 40 之间！
                        ↓
【触发页分裂（Page Split）】：
分配新页 Page 3，将 Page 1 后半部分数据搬迁至 Page 3，重新调整指针与槽位。
产生大量离散物理 I/O 与存储碎片！
```

当新写入的主键是一个随机生成的 UUID 时，它可能落在已经写满的任意一个中间数据页内。为了给新数据腾出插入空间，InnoDB 必须执行昂贵的数据页分裂操作（Page Split）：申请全新数据页、将原页内约一半的数据移动到新页、重构页内目录槽位并重新挂接前后指针。频繁的页分裂不仅会导致严重的磁盘写入放大，还会留下大量的页内物理碎片，导致表空间体积暴增而有效缓存命中率急剧下降。

> **最佳实践**：业务表的主键应当始终采用具备单调递增特性的整数类型并配置 `AUTO_INCREMENT`（或采用有序的分布式雪花算法 ID）。这样新数据总是顺序追加在 B+ 树最右侧叶子节点的最后位置，页写满后平滑开启新页，彻底消除中间页分裂。

---

### 业务废弃或几乎无调用的冷存索引

随着业务版本的快速迭代，很多早期的查询接口已经被重构或废弃，但留在数据库表结构里的索引往往由于开发人员“不敢动”的心理而被遗忘。

这些不再使用的冗余索引默默占据着珍贵的磁盘空间，并在每次写入数据时持续消耗 CPU 与 I/O 资源去维护树结构平衡。生产环境中应定期通过性能视图或工具梳理索引使用频率，对零访问的废弃索引果断执行 `DROP INDEX` 进行清理。

---

### 逻辑重复与覆盖冗余的索引结构

在数据库表设计中，许多开发者常因对索引底层机理缺乏透彻理解，无意中定义了大量重复或冗余的索引。

#### 联合索引前缀覆盖引起的冗余索引

假设我们在个人信息表 `person_info` 上创建了一个三列联合索引：

```sql
CREATE TABLE person_info (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(32),
    birthday DATE,
    phone_number VARCHAR(16),
    INDEX idx_name_birthday_phone(name, birthday, phone_number)
);
```

如果在该表上又额外单独创建了一个单列索引：

```sql
-- 错误设计：完全冗余的单列索引
CREATE INDEX idx_name ON person_info(name);
```

根据 B+ 树联合索引的最左前缀原则（Leftmost Prefix Principle），联合索引 `(name, birthday, phone_number)` 在物理上本身就是优先按照 `name` 严格排序构建的。当你执行如下单列查询时：

```sql
SELECT * FROM person_info WHERE name = '张三';
```

MySQL 查询优化器直接利用 `idx_name_birthday_phone` 联合索引即可完成高效率的二分查找，其执行路径与利用单列索引 `idx_name` 完全等价。此时单列索引 `idx_name` 在功能上完全被联合索引的前缀所覆盖，属于纯粹浪费存储与写性能的**冗余索引**。

#### 主键列重复挂载二级索引

更为荒谬但屡见不鲜的情况发生在对主键列的重复定义上：

```sql
CREATE TABLE test_duplicate (
    col1 INT PRIMARY KEY,
    UNIQUE KEY uk_col1(col1),
    INDEX idx_col1(col1)
);
```

在上述建表语句中，`col1` 已经被指定为主键，InnoDB 引擎会自动为其构建主键聚簇索引；如果开发者又显式添加了 `UNIQUE KEY` 和常规的 `INDEX`，相当于在同一个字段上重复构筑了三棵功能完全重叠的 B+ 树。这种**重复索引**在生产环境中应当坚决杜绝。

### 核心准则小结与面试应答框架

为了便于在日常架构评审或面试中快速调取，我们将不适合创建索引的场景及反模式整理对比如下：

| 不建索引的场景类型 | 典型场景示例 | 核心技术原因与危害 |
| :--- | :--- | :--- |
| **查询冷门列** | 从未出现在 `WHERE` / `GROUP BY` / `ORDER BY` 的列 | 无法参与定位与排序，白白增加存储与维护成本 |
| **小微数据表** | 表行数低于 1000 行的配置表、字典表 | 全表扫描仅需少量连续 I/O；二级索引需额外页跳转并引发回表，成本倒挂 |
| **低区分度列** | 性别、布尔标识位（重复率 > 10%） | 单个条件命中大量叶子节点，全量回表代价巨大，优化器倾向放弃索引 |
| **高频写字段/表** | 频繁 `UPDATE` 字段、高并发日志/流水表 | 每次写入均需同步维护多棵 B+ 树，引发锁竞争并降低写吞吐量 |
| **散列无序键** | UUID、MD5、随机字符串作为主键 | 无法按序追加，高频触发中间数据页分裂（Page Split），产生大量存储碎片 |
| **废弃冷索引** | 历史遗留、业务已不再调用的接口对应索引 | 纯粹占用磁盘并损耗写性能，需定期扫描清理 |
| **冗余与重复索引** | 联合索引前缀列再建单列索引；主键列再建唯一/普通索引 | 检索功能完全重叠，B+ 树重复构造，极大浪费存储与计算资源 |

> **提示**：建了合理的索引，并不代表 SQL 执行时就百分之百能吃到索引加速红利。在实际业务中，由于隐式类型转换、违背最左前缀原则、索引列参与运算或函数调用等不规范的 SQL 书写方式，都会导致优化器放弃索引，发生“索引失效”。这部分核心优化与避坑细节，将在后续章节中结合执行计划（`EXPLAIN`）进行深入专题拆解。

## 134-数据库优化步骤_查看系统性能参数
> 对应分集：P134 | 原始标题：《134-数据库优化步骤_查看系统性能参数》

在真实的线上生产环境当中，数据库服务运行着运行着突然变慢、接口响应延迟陡增，是每一位后端研发与 DBA 都必然会碰到的典型故障。一旦出现 SQL 执行缓慢，很多人往往像无头苍蝇一样盲目去改代码、加索引或者盲目重启服务。但数据库调优绝不是靠碰运气，它必须依托一套严密的排查逻辑与量化的诊断工具。

到底是因为索引设计不合理导致全表扫描？还是数据库连接池被耗尽、线程陷入长久等待？亦或是系统缓冲池配置过小引发了密集的磁盘物理 I/O？在正式深入钻研具体的优化工具之前，我们必须先建立宏观的调优全局观。数据库调优的核心目标永远是两个：**让响应时间（RT，Response Time）更快**，以及**让系统吞吐量（Throughput / QPS / TPS）更大**。本讲我们将完整拆解数据库调优的闭环诊断步骤，并深入掌握通过系统参数（`SHOW STATUS`）与查询成本（`last_query_cost`）度量性能的核心实战手法。

### 数据库性能调优的闭环排查步骤

调优的本质，是一个从宏观监控逐步聚焦到微观执行计划的诊断过程。在整个优化周期中，核心行为可以抽象为两个动作：**观察（Observation）**与**行动（Action）**。我们必须先通过监控与系统状态观察到瓶颈现象，再针对性地实施优化措施。

#### 全链路故障定位与调优流程图

下图展示了从业务表现异常到最终架构级落地的完整排查决策链条：


该流程图的决策推进逻辑如下：
1. **第一层：判断波动周期**。如果是周期性业务波峰（如电商的双十一、618 抢购促销），数据库瞬间面临数百倍流量冲击，此时仅靠优化单条 SQL 无法从根本上解决吞吐上限，必须依靠引入分布式缓存或优化缓存淘汰/预热机制，将读请求前置拦截。
2. **第二层：捕获慢查询**。对于非周期性的日常卡顿，应开启 MySQL 慢查询日志（Slow Query Log），合理设定 `long_query_time`，精准抓取执行耗时超出预期的慢 SQL。
3. **第三层：微观工具剖析**。利用 `EXPLAIN` 查看执行计划，结合 `SHOW PROFILES` 查看 SQL 在生命周期中每个阶段（语法解析、锁等待、发送数据等）的精确时间切片。
4. **第四层：区分等待耗时与执行耗时**。
   - 如果耗时长在“等待”（如等待锁释放、等待磁盘 I/O 把数据页换入内存），重点应调整 MySQL 服务端参数，例如增大 `innodb_buffer_pool_size` 减少换页颠簸；
   - 如果耗时长在“执行”（如正在进行千万级扫描、大排序、散列关联），重点应放在 SQL 重构、索引补全与表结构字段选型上。
5. **第五层：架构级横向扩容**。当单机数据库在硬件与索引层面已被压榨至极限时，就需要考虑采用主从复制实现读写分离，或者推进垂直分库、水平分表架构改造。

#### 调优层次的成本与收益金字塔

在实际工程落地中，调优动作所付出的代价与其带来的收益往往呈现显著的倒挂反差：

```text
               ▲                   成本维度              收益与见效维度
              / \             ===================     ===================
             / 4 \            硬件升级与架构重构 (高)    边际收益递减 (低)
            /-----\           -------------------     -------------------
           /   3   \          服务器系统参数微调 (中高)   局部性能改善 (中低)
          /---------\         -------------------     -------------------
         /     2     \        表结构设计与字段重构 (中)   中等全局收益 (中)
        /-------------\       -------------------     -------------------
       /       1       \      SQL 重写与索引优化 (极低)   性能飞跃提升 (极高)
      +-----------------+
```

从成本角度看，改动一行 SQL 或增加一个联合索引的成本几乎为零；重构表结构需要处理历史数据迁移，成本中等；修改系统参数需要充分灰度验证；而采购高性能服务器、改造分布式分库分表的架构成本最高。

然而从最终的优化效果来看，**越靠近底层的 SQL 重写与索引调优，其提速效果越立竿见影**（往往能让查询耗时直接降低数个数量级）；越往上的硬件升级，如果在烂 SQL 面前也只是杯水车薪，收益极为有限。因此，调优永远遵循“由下至上、由轻至重”的原则。

### 查看服务器系统性能参数（SHOW STATUS）

要想知道数据库服务器当前的健康状况，最直接的方法就是查看其内部维护的系统运行时计数器。我们可以通过 `SHOW STATUS` 指令调取参数。

#### 语法结构与作用域界定

`SHOW STATUS` 命令支持针对全局级别或会话级别进行过滤：

```sql
SHOW [GLOBAL | SESSION] STATUS LIKE '参数通配符';
```

- `GLOBAL`：统计自 MySQL 服务器启动以来的全局累计状态值；
- `SESSION`（默认）：仅统计当前客户端会话连接范围内的状态值。

在生产排查时，如果我们想要了解服务器整体的负载与运行瓶颈，务必加上 `GLOBAL` 关键字以获取真实的全局宏观数据。

#### 核心监控参数与实战演示

在 CentOS 终端通过 Xshell 登录运行在服务端的 MySQL 8.0 实例，我们可以针对几组关键指标进行实操观察：

##### 连接与运行时间指标：Connections 与 Uptime

```sql
-- 查看自启动以来累计建立的连接总次数
SHOW GLOBAL STATUS LIKE 'Connections';

-- 查看服务器已连续运行的秒数
SHOW GLOBAL STATUS LIKE 'Uptime';
```

以排查服务器异常重启为例：通过 `systemctl restart mysqld` 重启数据库服务后，在终端再次执行 `SHOW GLOBAL STATUS LIKE 'Uptime';`，可以看到其返回值立刻归零，随后从 5 秒、7 秒、8 秒逐步累加。通过监控 `Uptime`，运维系统可以灵敏捕获到数据库是否因内存溢出（OOM）发生过意外崩溃重启。

##### 慢查询频次指标：Slow_queries

```sql
-- 查看慢查询累计触发次数
SHOW GLOBAL STATUS LIKE 'Slow_queries';
```

该参数记录了执行耗时严格大于 `long_query_time` 的 SQL 执行总次数。在刚启动的洁净实例中，由于尚无慢请求，该值为 0。MySQL 默认的 `long_query_time` 设定为 10 秒；而在生产环境中，我们通常会将其下调至 1 秒甚至更低，以灵敏捕获所有隐患 SQL。

##### 存储引擎行级吞吐指标：Innodb_rows_%

InnoDB 存储引擎提供了一组精细反映 DML 与查询吞吐量的行计数器：

```sql
SHOW STATUS LIKE 'Innodb_rows_%';
```

常见的输出项包括：
- `Innodb_rows_read`：通过 InnoDB 引擎实际读取的数据行总数；
- `Innodb_rows_inserted`：向 InnoDB 表中累计插入的行数；
- `Innodb_rows_updated`：累计更新的行数；
- `Innodb_rows_deleted`：累计删除的行数。

为了直观验证其统计机理，我们在包含 107 条员工记录的 `employees` 表上进行两次全表扫描测试：

```sql
USE atguigudb;

-- 第一次全量查询，返回 107 条数据
SELECT * FROM employees;

-- 第二次全量查询，再次返回 107 条数据
SELECT * FROM employees;

-- 检查读取行数指标
SHOW STATUS LIKE 'Innodb_rows_read';
```

执行后可以清晰看到，`Innodb_rows_read` 的计数值精确增加了 $107 \times 2 = 214$。这一指标能够非常客观地反映出某些 SQL 是否在底层产生了惊人的无效数据扫描量。

### 度量 SQL 执行成本：last_query_cost

在 MySQL 优化器的成本模型（Cost Model）中，每执行一条 SQL，优化器在解析执行后都会计算出一个量化的代价数值。我们可以通过 `last_query_cost` 状态变量直接调取刚刚执行完成的那条查询的真实开销。

#### last_query_cost 的物理内涵

`last_query_cost` 衡量的是优化器执行最近一次查询所耗费的综合代价。而在所有的计算成本中，**数据页（Data Page）的读取数量与 I/O 方式是决定成本高低的绝对主导因素**。

> **核心定律**：位置决定效率，批量决定效率。
> - **位置决定效率**：从 InnoDB 缓冲池（Buffer Pool）读取内存数据页的延迟在纳秒到微秒级；而如果内存未命中，必须从物理磁盘（哪怕是 NVMe SSD）加载，延迟将成倍上升。
> - **批量决定效率**：从传统机械硬盘或固态介质随机读取一个孤立的数据页，寻道与寻址开销通常在 **10 毫秒**左右；但如果采用**顺序 I/O（Sequential I/O）**方式批量读取连续的数据页（例如以“区（Extent）”为单位连续读 64 个页），平均分摊到每一个数据页的读取时间将被极度压缩。

#### 百万级数据下的成本实操对比

我们在具备 100 万条模拟数据的学生信息表 `student_info`（位于 `atguigudb1` 库）中开展对照实验。

##### 实验一：主键单点精确等值查询

```sql
USE atguigudb1;

-- 针对聚簇索引主键执行单行点查
SELECT * FROM student_info WHERE id = 900001;

-- 检查最近一次查询成本
SHOW STATUS LIKE 'last_query_cost';
```

执行结果显示：`Value = 1.000000`。
这是因为主键是聚簇索引，通过 B+ 树根节点逐层向下查找，由于整棵树高度只有 3 层左右且非叶子节点通常常驻内存，引擎仅需精确定位并加载**1 个数据页**即可获取整行数据，因此其成本基准值记为 1。

##### 实验二：主键连续小范围查询

```sql
-- 检索连续的 100 行记录
SELECT * FROM student_info WHERE id BETWEEN 900001 AND 900100;

-- 检查查询成本
SHOW STATUS LIKE 'last_query_cost';
```

此时返回的成本约为 `21.000000` 左右，耗时依然极短（显示为 `0.00s`）。这表明为了连续提取这 100 条记录及其相关行，InnoDB 实际寻址并加载了约 21 个物理数据页。

##### 实验三：非聚集范围查询与“批量顺序 I/O”验证

当查询耗时都在 `0.00s` 时，我们无法直观对比耗时差异。为了放大 I/O 表现，我们针对普通字段 `student_id` 进行大范围过滤对比：

```sql
-- 测试用例 A：检索 student_id > 199000 的记录（数据量较大）
SELECT * FROM student_info WHERE student_id > 199000;
-- 实际执行耗时约：0.05 秒

SHOW STATUS LIKE 'last_query_cost';
-- 结果显示 cost 约为 2000+（涉及 2000 多个数据页）

-- 测试用例 B：检索 student_id > 199900 的记录（缩小范围）
SELECT * FROM student_info WHERE student_id > 199900;
-- 实际执行耗时约：0.01 秒

SHOW STATUS LIKE 'last_query_cost';
-- 结果显示 cost 明显降低，约为用例 A 的十分之一
```

对比两个用例的测试数据会发现一个非常奇妙的现象：
用例 A 涉及的数据页数量（2000+ 页）几乎是用例 B 的 **10 倍**，但在执行耗时上，用例 A（0.05 秒）仅仅比用例 B（0.01 秒）慢了 0.04 秒，两者的实际耗时差距只有 5 倍，根本没有出现跨数量级的耗时膨胀。

这背后的根本原因正是**顺序 I/O 与预读机制**的加持：在进行大范围连续数据扫描时，InnoDB 充分利用了底层的区（Extent）连续存储结构，以批量顺序读代替了昂贵的随机读，使得平摊到每个数据页上的绝对耗时急剧衰减。

### 本讲核心命令与指标速查表

| 指令 / 状态变量 | 核心作用说明 | 生产实战价值与关注点 |
| :--- | :--- | :--- |
| `SHOW STATUS LIKE 'Connections'` | 统计自服务启动以来的客户端累计连接数 | 评估服务并发峰值，辅助设定最大连接数参数 |
| `SHOW STATUS LIKE 'Uptime'` | 统计 MySQL 服务累计在线运行时长（秒） | 监测服务器是否发生过异常宕机或 OOM 重启 |
| `SHOW STATUS LIKE 'Slow_queries'` | 统计累计慢查询触发总次数 | 评估线上 SQL 健康度，决定是否介入慢 SQL 治理 |
| `SHOW STATUS LIKE 'Innodb_rows_%'` | 统计 InnoDB 引擎增删改查的物理行数 | 评估全表扫描带来的无效数据吞吐与 I/O 压力 |
| `SHOW STATUS LIKE 'last_query_cost'`| 查看最近一次 SQL 优化的物理代价（页数） | 定量度量 SQL 开销，评估是否需要优化范围或引入缓存 |

> **提示**：通过 `SHOW STATUS` 与 `last_query_cost`，我们已经能够在宏观上量化 SQL 的数据吞吐与页级开销。但要想精确捕获到底是哪一条 SQL 导致了系统瘫痪，以及该 SQL 在微观上究竟是如何被优化器执行的，我们就必须开启真正的“听诊器”——**慢查询日志（Slow Query Log）**与**执行计划（EXPLAIN）**。这正是我们下一讲将要深度攻坚的核心武器。

## 135-慢查询日志分析、SHOW PROFILE查看SQL执行成本
> 对应分集：P135 | 原始标题：《135-慢查询日志分析、SHOW PROFILE查看SQL执行成本》

在数据库性能排查的实战中，我们经常遇到这样的尴尬局面：业务研发反馈“系统偶尔变卡、部分接口响应极慢”，但你登录服务器后，如果漫无目的地盲抓 SQL，无异于大海捞针。到底系统里哪些 SQL 在拖后腿？这些慢 SQL 到底慢在哪里？是等待锁资源耗费了青春，还是由于缺少索引在疯狂扫描磁盘？

要回答这些问题，我们必须依赖 MySQL 提供的两套“微观听诊器”：第一套是**慢查询日志（Slow Query Log）**及其配套的统计分析工具 `mysqldumpslow`，用来从海量请求中精准“捞出”超时罪魁祸首；第二套是**SQL 执行剖析工具（SHOW PROFILE）**，用来把特定慢 SQL 的生命周期像慢动作回放一样逐帧切片，精确定量每一个执行阶段的 CPU 与 I/O 耗时。本讲我们将从零开始搭建 400 万级实战数据，完整走通慢 SQL 定位、日志归约分析与剖析拆解的整套排查链路。

### 慢查询日志的核心工作原理与判定阈值

慢查询日志是 MySQL 内部专用于记录所有运行时间超出预设容忍极限的 SQL 语句的物理日志。

#### 慢查询的两个核心判定变量

MySQL 并不会无差别地把所有执行的 SQL 都记入日志，而是基于两项系统变量作为过滤门槛：

```text
客户端发起 SQL 请求
        ↓
服务端执行并统计执行耗时（Query Time）与扫描行数（Examined Rows）
        ↓
【判定条件】：
Query Time > long_query_time  AND  Examined Rows >= min_examined_row_limit
        ↓
    [符合条件]  ------------------------->  写入慢查询日志文件 (*-slow.log)
```

1. **`long_query_time`（慢查询时间阈值）**：
   - 默认值为 **10 秒**。
   - **易错判定规则**：必须是**严格大于**该阈值（`>`），等于该阈值不计入。例如执行耗时恰好为 10.00 秒的语句不会被捕获，必须大于 10 秒（如 10.01 秒）才被判定为慢查询。
   - 在生产调优或压测场景下，10 秒的标准过于宽松，通常应当将其下调至 1 秒甚至 0.5 秒。
2. **`min_examined_row_limit`（最小扫描行数阈值）**：
   - 默认值为 **0**。
   - 含义为查询扫描过的最少记录数。当保留默认值 0 时，只要 SQL 执行耗时超过 `long_query_time`，哪怕实际扫描了 0 行数据，也会被强制写入慢日志；若将其设为 100，则即使耗时超时，扫描记录数不足 100 行时也不会被记入。日常排查通常保持默认值 0 即可。

#### 为什么慢查询日志默认处于关闭状态

在安装完 MySQL 后，慢查询日志默认是处于 `OFF` 关闭状态的。

> **注意**：慢查询日志的写入本身需要消耗磁盘物理 I/O，每次捕获到慢查询都需要进行文件句柄操作与落盘刷写。如果在高并发的生产环境中常态化全量开启，尤其当慢 SQL 密集爆发时，日志写入本身会形成严重的“次生 I/O 灾难”。因此，推荐的运维准则是在需要进行系统体检或性能调优时动态开启，调优排查完毕并归档分析后，及时将其关闭。

### 慢查询日志的动态启停与永久配置

#### 临时动态开启与作用域避坑

在排查现场，我们通常希望在不重启 MySQL 服务的前提下立即开启慢查询日志。在终端中查看当前状态：

```sql
SHOW VARIABLES LIKE '%slow_query_log%';
```

此时会输出两项关键配置：
- `slow_query_log`：开启状态（`ON` / `OFF`）；
- `slow_query_log_file`：日志文件的物理绝对路径，默认位于数据目录下，命名格式为 `主机名-slow.log`（例如在主机名为 `atguigu05` 的测试节点上，路径为 `/var/lib/mysql/atguigu05-slow.log`）。

##### 动态开启命令
如果直接执行 `SET slow_query_log = 'ON';`，MySQL 会明确抛出报错，因为该参数属于全局变量，必须显式附加 `GLOBAL`：

```sql
-- 正确开启方式：设置全局系统变量
SET GLOBAL slow_query_log = 'ON';
```

##### 修改超时阈值 long_query_time
查看当前的阈值：

```sql
SHOW VARIABLES LIKE 'long_query_time';
```

若将其从默认的 10 秒修改为 1 秒，**这里存在一个极其经典的变量作用域陷阱**：
如果我们仅仅执行了 `SET GLOBAL long_query_time = 1;`，随后在当前窗口执行 `SHOW VARIABLES LIKE 'long_query_time';`，会发现返回值依然顽固地显示为 10 秒！

这是因为 `long_query_time` 同时具备 `GLOBAL` 和 `SESSION` 两种作用域：
- `SET GLOBAL` 仅对执行该命令之后**新建立的客户端会话连接**生效；
- 对于当前已经建立的会话，必须同步修改会话级别参数才能立刻生效。

```sql
-- 生产标准推荐：会话与全局同步调整
SET GLOBAL long_query_time = 1;
SET SESSION long_query_time = 1;

-- 再次核验
SHOW VARIABLES LIKE 'long_query_time'; -- 成功变为 1 秒
```

#### 配置文件永久化（my.cnf）

若需要长期稳定监控数据库性能，应将配置固化到 Linux 的 `/etc/my.cnf`（Windows 为 `my.ini`）配置文件中的 `[mysqld]` 节点下：

```ini
[mysqld]
# 开启慢查询日志
slow_query_log = ON

# 指定慢查询日志的绝对路径与文件名
slow_query_log_file = /var/lib/mysql/atguigu05-slow.log

# 设置慢查询阈值（超过 3 秒则记录）
long_query_time = 3

# 指定日志输出形式为文件存储
log_output = FILE
```

保存配置文件后，执行 `systemctl restart mysqld` 重启服务。由于此时已固化至底层，重启后参数依然永久保持。

### 万级测试数据构建与慢查询实战捕获

为了真实还原生产中未命中索引导致的慢查询，我们在 `atguigudb1` 库中构建一张包含 400 万条记录的 `student` 表。

#### 准备数据表结构与批量造数

```sql
USE atguigudb1;

-- 创建无二级索引的基准表
CREATE TABLE `student` (
    `id` INT(11) NOT NULL AUTO_INCREMENT,
    `stuno` INT(11) NOT NULL,
    `name` VARCHAR(20) DEFAULT NULL,
    `age` INT(11) DEFAULT NULL,
    `classId` INT(11) DEFAULT NULL,
    PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

利用自定义的随机字符串与随机数值生成函数，编写存储过程批量循环写入 400 万条数据：

```sql
DELIMITER //
CREATE PROCEDURE insert_student_data(IN start_num INT, IN max_num INT)
BEGIN
    DECLARE i INT DEFAULT 0;
    SET autocommit = 0; -- 显式关闭自动提交，批量事务写入提速
    REPEAT
        SET i = i + 1;
        INSERT INTO student (stuno, name, age, classId)
        VALUES ((start_num + i), rand_string(6), rand_num(10, 30), rand_num(1, 1000));
        UNTIL i = max_num
    END REPEAT;
    COMMIT; -- 统一提交
    SET autocommit = 1;
END //
DELIMITER ;

-- 调用存储过程灌入 400 万条记录（耗时约数分钟）
CALL insert_student_data(100001, 4000000);
```

#### 全表记录数统计：InnoDB 与 MyISAM 的底层机制辨析

在 400 万记录灌入完毕后，我们执行全表计数：

```sql
SELECT COUNT(*) FROM student;
```

控制台耗时约 `0.82s`，能明显感知到短暂停顿。

> **提示**：为什么在 InnoDB 引擎下查 `COUNT(*)` 会慢，而在 MyISAM 下却能瞬时返回？
> - **MyISAM 引擎**：在磁盘表元数据头中维护了专门的物理计数器变量，不加 `WHERE` 条件的 `SELECT COUNT(*)` 直接读取该变量返回，时间复杂度为 $O(1)$；
> - **InnoDB 引擎**：由于支持多版本并发控制（MVCC），不同事务在同一瞬间能看到的有效版本行数并不一致，无法用一个全局静态计数器搞定，必须通过读取聚簇或二级索引树逐行遍历统计，因此数据量大时会产生肉眼可见的耗时。

#### 慢 SQL 触发与慢查询计数器验证

当前会话的 `long_query_time` 已设为 1 秒。我们针对未加索引的字段执行两次全表条件检索：

```sql
-- 检索用例 1：针对非索引整型字段 stuno 执行过滤
SELECT * FROM student WHERE stuno = 3453451;
-- 实际执行耗时：1.19 秒（> 1秒，被判定为慢查询）

-- 检索用例 2：针对非索引字符串字段 name 执行过滤
SELECT * FROM student WHERE name = 'aBcDef';
-- 实际执行耗时：1.25 秒（> 1秒，被判定为慢查询）
```

随后通过系统性能计数器检查慢查询是否成功被系统捕获：

```sql
SHOW STATUS LIKE 'slow_queries';
```

结果精准显示 `Value = 2`。这表明系统内部的慢查询监听器已准确感知并完整记录了刚才这两次超标操作。

### 慢查询日志分析工具：mysqldumpslow

生产环境如果运行了数周，慢查询日志文件动辄达到数百兆甚至几个 G，直接用 `cat`、`less` 或 `vim` 打开不仅极其低效，更容易把服务器内存撑爆。官方提供了专门用于聚合、排序与归类慢日志的命令行脚本——`mysqldumpslow`。

#### 工具工作环境与核心参数

`mysqldumpslow` 是一个独立的 Perl 脚本，**必须在 Linux 操作系统的终端命令行执行，严禁在 MySQL 的 SQL 命令行内输入**。

```bash
# 查看帮助与参数手册
mysqldumpslow --help
```

常用的核心参数如下表所示：

| 参数选项 | 全称 / 含义 | 详细功能说明 |
| :--- | :--- | :--- |
| `-s ORDER` | 排序维度 | 排序规则：<br>· `at`：平均查询时间（Average query Time，**默认**）<br>· `t`：总查询时间（Time）<br>· `al`：平均锁等待时间（Average Lock time）<br>· `l`：总锁定时间（Lock time）<br>· `ar`：平均返回行数（Average Row count）<br>· `r`：总返回行数（Row count）<br>· `c`：执行总次数（Count） |
| `-t NUM` | Top N 截取 | 仅返回排序后的前 `NUM` 条慢查询（例如 `-t 5` 返回前 5 条） |
| `-a` | 不抽象化参数 | **核心关键**：默认会将 SQL 中的具体数字抽象为 `N`、字符抽象为 `'S'`。<br>加上 `-a` 则保留原始具体字面值，方便复现 |
| `-g REGEX`| 正则模式过滤 | 仅匹配包含特定关键词或表名的 SQL（类似于 grep） |

#### 实战归约统计与输出解读

我们进入日志存放目录并使用该工具对 `/var/lib/mysql/atguigu05-slow.log` 进行提炼：

```bash
# 案例 1：按照总耗时降序排列，输出耗时最高的 Top 5 条慢查询
mysqldumpslow -s t -t 5 /var/lib/mysql/atguigu05-slow.log
```

在终端中，工具会对语法结构相同的慢查询进行自动归一化聚合，并输出如下关键性能块：

```text
Count: 1  Time=1.25s (1.25s)  Lock=0.00s (0.00s)  Rows=1.0 (1), root[root]@localhost
  SELECT * FROM student WHERE name = 'S'

Count: 1  Time=1.19s (1.19s)  Lock=0.00s (0.00s)  Rows=1.0 (1), root[root]@localhost
  SELECT * FROM student WHERE stuno = N
```

注意到输出里的 `'S'` 和 `N`：默认情况下参数已被抽象化归拢。如果我们希望看到当时执行的真实参数以供现场还原，加上 `-a` 参数即可：

```bash
# 案例 2：保留真实字面参数，按单次耗时提取 Top 5
mysqldumpslow -a -s t -t 5 /var/lib/mysql/atguigu05-slow.log
```

此时终端将原汁原味地还原出 `stuno = 3453451` 与 `name = 'aBcDef'` 的具体 SQL，为下一步使用 `EXPLAIN` 分析执行计划提供了精准的目标输入。

### 慢查询日志的清理、轮转与重置

当故障排查完毕，为了释放服务器磁盘空间，我们需要对庞大的历史慢日志文件进行物理清理与生命周期重置。

#### 物理删除与失效场景

在 Linux 终端可以直接使用 `rm` 命令删除旧的日志文件：

```bash
rm -f /var/lib/mysql/atguigu05-slow.log
```

但删除文件后，如果不通知 MySQL 重新初始化句柄，MySQL 进程依然持有已删除文件的失效文件描述符（inode），后续的慢查询将无法正常落盘写入。

#### 使用 mysqladmin 重置与刷新日志

我们需要通知 MySQL 重新生成全新的空日志文件：

```bash
# 刷新并重置慢查询日志文件
mysqladmin -u root -p flush-logs slow
```

> **易错点**：执行 `flush-logs slow` 后，检查数据目录发现新的 `-slow.log` 并没有生成，这是为什么？
> - 根本原因：如果此时数据库中的 `slow_query_log` 系统变量已被手动置为 `OFF` 状态，MySQL 认为无需记录日志，自然不会主动创建新文件；
> - 只有当 `slow_query_log` 处于 `ON` 开启状态时，执行 `flush-logs slow` 才会立刻在磁盘上生成一个初始化大小约 900 字节的新日志文件。

### 微观阶段耗时剖析：SHOW PROFILE 实战

慢查询日志只能告诉我们“哪一条 SQL 执行花费了超过 1 秒”，但这条 SQL 究竟把时间消耗在了哪个具体环节（词法语法分析？表锁竞争？还是真正的数据读取？），慢日志无法给出更细粒度的答案。这时就轮到 `SHOW PROFILE` 登场了。

#### 功能开启与会话生命周期管理

`SHOW PROFILE` 能够追踪当前客户端会话中最近执行的多条 SQL 在各个执行步骤（Execution Stages）中的微秒级资源开销。

```sql
-- 1. 查看 Profiling 功能是否开启（默认 OFF）
SHOW VARIABLES LIKE 'profiling';

-- 2. 开启当前会话的分析功能
SET profiling = 'ON';
```

开启后，我们在该连接中再次执行刚才的测试慢 SQL：

```sql
SELECT * FROM student WHERE stuno = 3453451;
SELECT * FROM student WHERE name = 'aBcDef';
```

#### 查询概要查看：SHOW PROFILES

通过 `SHOW PROFILES`，我们可以获取当前会话最近执行过的全部查询清单及其全局执行时长：

```sql
SHOW PROFILES;
```

典型输出格式如下：

| Query_ID | Duration | Query |
| :---: | :---: | :--- |
| 1 | 0.00018500 | `SHOW VARIABLES LIKE 'profiling'` |
| 2 | 1.19234800 | `SELECT * FROM student WHERE stuno = 3453451` |
| 3 | 1.25140200 | `SELECT * FROM student WHERE name = 'aBcDef'` |

#### 阶段明细剖析：SHOW PROFILE FOR QUERY

选定耗时最高的 `Query_ID = 3`，深入剖析其生命周期的完整执行切片：

```sql
SHOW PROFILE CPU, BLOCK IO FOR QUERY 3;
```

其控制台将逐行打印出整条语句历经的全部细分子状态：

```text
+----------------------+-----------+----------+------------+--------------+---------------+
| Status               | Duration  | CPU_user | CPU_system | Block_ops_in | Block_ops_out |
+----------------------+-----------+----------+------------+--------------+---------------+
| starting             | 0.000085  | 0.000060 | 0.000020   | 0            | 0             |
| checking permissions | 0.000012  | 0.000010 | 0.000002   | 0            | 0             |
| Opening tables       | 0.000025  | 0.000020 | 0.000005   | 0            | 0             |
| init                 | 0.000018  | 0.000015 | 0.000003   | 0            | 0             |
| System lock          | 0.000011  | 0.000008 | 0.000003   | 0            | 0             |
| optimizing           | 0.000015  | 0.000012 | 0.000003   | 0            | 0             |
| statistics           | 0.000020  | 0.000016 | 0.000004   | 0            | 0             |
| preparing            | 0.000018  | 0.000015 | 0.000003   | 0            | 0             |
| executing            | 1.250850  | 1.150000 | 0.100000   | 3240         | 0             |
| end                  | 0.000015  | 0.000010 | 0.000005   | 0            | 0             |
| query end            | 0.000010  | 0.000008 | 0.000002   | 0            | 0             |
| closing tables       | 0.000012  | 0.000010 | 0.000002   | 0            | 0             |
| freeing items        | 0.000309  | 0.000250 | 0.000050   | 0            | 0             |
| cleaning up          | 0.000020  | 0.000015 | 0.000005   | 0            | 0             |
+----------------------+-----------+----------+------------+--------------+---------------+
```

仔细审查上述表格数据会发现：
从 `starting` 到 `preparing`，前端鉴权、语法优化和锁检查仅消耗了微秒级时间；然而在 **`executing`（执行）阶段直接飙升到了 1.25 秒，伴随着极高的 `CPU_user` 与 `Block_ops_in`（物理块读入）**。

> **结论与诊断**：这直接印证了当前 SQL 的延迟完全不是因为锁等待或网络握手引起的，而是引擎在底层进行 400 万行的全表数据块逐页扫描。解决方案极其明确——立即在 `name` 字段上建立高效索引。

#### SHOW PROFILE 中必须警惕的四类高危状态

在利用 `SHOW PROFILE` 诊断复杂查询时，如果结果集中出现了以下四个状态之一，往往意味着底层执行机制发生了严重的性能退化，必须作为重点治理对象：

1. **`converting HEAP to MyISAM`（或 converting HEAP to ondisk）**：
   - **成因**：查询产生的内存临时表（MEMORY/HEAP 引擎存储）体积超过了 `tmp_table_size` 或 `max_heap_table_size` 的阈值，MySQL 被迫将内存表结构在磁盘上重建为基于磁盘的临时表。
   - **危害**：引发性能断崖式下跌，必须优化过滤条件或适当调大内存临时表阈值。
2. **`Creating tmp table`**：
   - **成因**：执行 `DISTINCT`、`GROUP BY` 或复杂关联排序时，引擎无法利用现有索引消除分组，被迫在内部显式开辟临时表。
3. **`Copying to tmp table on disk`**：
   - **成因**：临时表在磁盘上创建完毕后，正将海量行记录不断从内存拷贝写入磁盘。伴随大量的磁盘写 I/O。
4. **`locked`**：
   - **成因**：正在处于锁等待状态（表锁排队或行锁死锁争用），说明存在并发事务冲突，需排查长事务与未提交事务。

#### 工具演进说明与 Performance Schema 替代路线

需要特别说明的是，在 MySQL 5.7 后期及 MySQL 8.0 中，官方已将 `SHOW PROFILE` 与 `SHOW PROFILES` 语法标记为废弃（Deprecated）。官方推荐使用更强大、更细粒度的 `performance_schema` 和 `sys` 视图（如 `sys.x$statement_analysis`）来获取线程级性能剖析。

但由于 `SHOW PROFILE` 具有零学习成本、语法极其简练、开箱即用的特点，在日常应急排查现场，它依然是绝大多数工程师最顺手、最常用的快速诊断手段之一。

| :--- | :--- | :--- | :--- |

## 136-EXPLAIN的概述与table、id字段剖析
> 对应分集：P136 | 原始标题：《136-EXPLAIN的概述与table、id字段剖析》

在前面两讲中，我们通过系统状态监控感知到了数据库的性能瓶颈，并通过慢查询日志（Slow Query Log）以及 `mysqldumpslow` 工具，从成千上万条业务请求中精准定位出了超时的瓶颈 SQL。但将这些慢 SQL 抓出来之后，排查工作才刚刚进入深水区。面对一条复杂的 SQL，我们怎么知道数据库底层到底是怎么执行它的？它为什么没有走我们精心设计的索引？它关联多张表时到底先查哪张、后查哪张？

要透视这一切，就必须依靠 MySQL 中最核心、最权威的性能分析重武器——**执行计划（EXPLAIN）**。`EXPLAIN` 就像是一张数据库内部的“CT 扫描图”，能够把查询优化器在暗箱中制定的每一个执行决策巨细靡遗地呈现在我们面前。本讲我们将从 `EXPLAIN` 的核心架构与版本演进切入，构建万级基准测试环境，并深入攻坚执行计划中最基础却最容易被忽视的两个灵魂字段：**`table`（目标表）**与 **`id`（执行顺序标识符）**。

### EXPLAIN 的核心定位与优化器机制

#### 优化器与执行计划的逻辑关系

在回顾 MySQL 的逻辑架构时我们讲过，客户端发送一条 SQL 语句到服务端，历经连接池、SQL 接口、解析器（词法语法分析）之后，就会进入**查询优化器（Optimizer）**。

```text
客户端发送 SQL 请求
        ↓
词法与语法解析器（生成语法解析树）
        ↓
【查询优化器 (Optimizer)】
依据成本模型（Cost Model），评估全表扫描与各索引分支开销
最终生成一份预估成本最低的方案 ——【执行计划 (Execution Plan)】
        ↓
【存储引擎与执行器 (Executor)】
按照执行计划调用存储引擎 API 物理提取数据并返回
```

优化器本身并不真正去读取表里的具体数据行，而是根据系统的统计信息（如 Cardinality 区分度、数据页数量、索引深度等），通过内部精密的成本计算公式，在所有可能的执行路径中挑选出一条综合成本（Cost）最低的路线，生成最终的“执行计划”。随后，执行器才严格按照这份执行计划去调用存储引擎的 API 完成数据检索。

我们使用 `EXPLAIN`（或其完全等价的别名关键字 `DESCRIBE`），就是让优化器提前将它敲定的这份“执行计划”以二维表格的形式展示给我们看：
- 评估单表访问到底采用全表扫描（ALL）还是精确索引定位（const / ref）；
- 评估多表关联时的先后驱动顺序（谁是驱动表，谁是被驱动表）；
- 预测哪些候选索引可能被使用（`possible_keys`），以及最终敲定了哪个索引（`key`）；
- 预估需要物理读取与检查的记录行数（`rows`）。

> **注意**：优化器基于统计成本计算出来的“最优方案”，属于一种自动化的数学估算。在实际生产中，由于统计信息延迟未刷新、数据分布严重倾斜或复杂关联场景，优化器选出的执行方案**并不一定等同于研发或 DBA 眼中实际运行最快的方案**。这也是为什么我们需要通过 `EXPLAIN` 人工介入审查，甚至利用 `FORCE INDEX` 或 SQL 重写来纠偏。

#### 官方技术文档的阅读与学习方法论

针对 `EXPLAIN`，MySQL 官方在 5.7 与 8.0 的参考手册（Reference Manual）中都设立了极为详尽的专章进行技术规范描述。

很多初学者在刚接触一门新技术时，总觉得应该第一时间去啃官方英文文档，但实际操作中往往会被其晦涩严密的术语和庞杂的篇幅劝退。在实际的技术成长路径上，最高效的方法应当是：
1. **第一阶段：以通俗优质的中文技术资料与生动案例打底**，快速在头脑中建立知识框架，理解运行原理与核心套路；
2. **第二阶段：必须亲自动手在终端与管理工具中进行大量极限实操**，通过制造各种边界条件与反常案例发现问题；
3. **第三阶段：把官方文档作为最具权威性的“字典”与终极仲裁工具**。当在实操中遇到各种教程观点冲突、新旧版本行为不一致或未知 Bug 时，回过头精读官方文档的标准定义，定分止争。

#### EXPLAIN 的历史演进与只读安全性

在不同 MySQL 版本演进中，`EXPLAIN` 经历了几次关键的功能迭代：

```text
MySQL 5.6.3 之前       MySQL 5.6.3 之后            MySQL 5.7 / 8.0+
-----------------    -----------------------     -------------------------
仅支持 SELECT 查询     支持 SELECT / INSERT /     无需额外参数，默认展示
                     UPDATE / DELETE 等 DML      partitions 与 filtered 列
```

1. **支持的语句范围拓展**：在 MySQL 5.6.3 之前，`EXPLAIN` 仅仅支持对 `SELECT` 检索语句进行执行计划分析；从 5.6.3 版本开始，官方将其正式扩展到了 `INSERT`、`UPDATE`、`DELETE` 等全量 DML 语句上。
2. **扩展参数的内置集成**：在 5.7 之前的低版本中，若想查看分区信息，必须输入 `EXPLAIN PARTITIONS`；若想查看过滤度，必须输入 `EXPLAIN EXTENDED`。而在 5.7 及现在的 8.0 主流版本中，直接运行 `EXPLAIN` 就会默认输出全部扩展字段。
3. **只读安全性**：当我们执行类似 `EXPLAIN DELETE FROM student WHERE id = 2;` 时，**MySQL 仅仅是在模拟评估删除该行记录所需的索引查找成本，底层的物理数据绝对不会被真正删除**。这一特性保证了我们在生产环境中审查高危写语句执行计划时的绝对安全。

### EXPLAIN 输出字段一览与认知顺序调整

执行一条 `EXPLAIN` 语句，控制台将标准输出包含 12 个属性字段的二维表格：

| 字段名称 | 核心技术含义 | 调优关注级别 |
| :--- | :--- | :---: |
| `id` | 查询标识符（代表每个 SELECT 语句的执行顺序） | ★★★☆☆ |
| `select_type` | 查询的具体类型（如 SIMPLE / PRIMARY / SUBQUERY / UNION） | ★★★☆☆ |
| `table` | 当前行执行计划所对应的具体物理表名或临时表名 | ★★★☆☆ |
| `partitions` | 命中的物理分区信息（无分区表则为 NULL） | ★☆☆☆☆ |
| **`type`** | **单表的物理访问方法（如 const / ref / range / index / ALL）** | ★★★★★ |
| `possible_keys` | 当前查询中可能被优化器选用的候选索引列表 | ★★★★☆ |
| `key` | 优化器最终决策实际使用的索引名称 | ★★★★☆ |
| **`key_len`** | **实际使用到的索引字节长度（判断联合索引命中列数的关键）** | ★★★★★ |
| `ref` | 与索引列进行等值匹配的具体字段或常量来源 | ★★★☆☆ |
| **`rows`** | **优化器预估完成查询必须扫描检查的物理记录行数** | ★★★★★ |
| `filtered` | 存储引擎返回的数据经过 Server 层条件过滤后剩余的百分比 | ★★★☆☆ |
| **`extra`** | **极为重要的额外辅助诊断信息（如 Using filesort / Using temporary）** | ★★★★★ |

在实际排查中，标有五颗星的四大金刚——`type`、`key_len`、`rows` 和 `extra` 是衡量一条 SQL 优劣的核心生命线。

但为了彻底降低理解门槛，我们**不按照官方的列排列顺序死记硬背**，而是重构为契合人类大脑认知逻辑的最佳顺序：**先搞懂目标表 `table`，再搞懂执行顺序 `id`，接着搞懂查询类型 `select_type`，最后再攻坚深度的访问类型 `type` 与 `extra`**。

### 基准测试环境搭建（s1 与 s2 双表）

为了让每一个 `EXPLAIN` 字段的输出都能被肉眼捕捉，我们必须拒绝在空表上测试。**空表在优化器眼中是没有成本差异的，许多真实的索引下推、全表扫描与临时表行为只有在真实数据量下才会触发**。

我们在 `atguigudb1` 库中构建结构完全对称的两张基准表 `s1` 与 `s2`，并各灌入 10,000 条数据。

#### 创建包含多类型索引的基准表

```sql
USE atguigudb1;

CREATE TABLE `s1` (
    `id` INT NOT NULL AUTO_INCREMENT,
    `key1` VARCHAR(100),
    `key2` INT,
    `key3` VARCHAR(100),
    `key_part1` VARCHAR(100),
    `key_part2` VARCHAR(100),
    `key_part3` VARCHAR(100),
    `common_field` VARCHAR(100),
    PRIMARY KEY (`id`),
    INDEX `idx_key1` (`key1`),
    UNIQUE INDEX `uk_key2` (`key2`),
    INDEX `idx_key3` (`key3`),
    INDEX `idx_part` (`key_part1`, `key_part2`, `key_part3`)
) ENGINE=InnoDB CHARSET=utf8mb4;

-- 表 s2 结构与 s1 完全一致，专用于多表 JOIN 与子查询
CREATE TABLE `s2` LIKE `s1`;
```

分析表结构设计背后的深意：
- `id`：聚簇索引（主键 B+ 树）；
- `key1` 与 `key3`：常规非唯一二级索引；
- `key2`：唯一二级索引（`UNIQUE KEY`）；
- `(key_part1, key_part2, key_part3)`：三列联合复合索引；
- `common_field`：无任何索引的普通字段；
- 存储引擎显式指定为 `InnoDB`。

#### 批量灌入 10,000 条真实测试数据

编写随机函数与存储过程，分别向 `s1` 和 `s2` 插入 10,000 行包含离散字符串的数据：

```sql
-- 开启函数创建信任

-- 创建数据灌入存储过程
DELIMITER //

        VALUES (rand_string1(10), i, rand_string1(10), rand_string1(10), rand_string1(10), rand_string1(10), rand_string1(20));

-- 分别调用灌入
CALL insert_s1_data();
-- 类似地调用过程向 s2 表写入 10,000 条数据
```

数据写入完成后，通过 `SELECT COUNT(*) FROM s1;` 与 `SELECT COUNT(*) FROM s2;` 核验，确保底层各具备 10,000 条记录。

### 字段剖析之一：table（目标单表映射）

#### 核心定义与单表映射法则

在 `EXPLAIN` 的输出结果集中，`table` 字段表示当前行执行计划所访问的具体数据源名称。

> **核心黄金法则**：无论你的 SQL 语句写得多么复杂、嵌套了多少层子查询，**`EXPLAIN` 结果集中的每一行记录，都严格对应着一个具体的单表（或派生表、内存临时表）**！

如果你执行一个单表查询，结果集中必然只有 1 行记录，`table` 显示该表表名：

```sql
EXPLAIN SELECT * FROM s1 WHERE key1 = 'a';
```

输出中 `table` 列即为 `s1`。

#### 多表连接中的驱动表与被驱动表

当查询涉及到多表关联时，结果集中就会对应出现多行记录：

```sql
EXPLAIN SELECT * FROM s1 INNER JOIN s2 ON s1.key1 = s2.key1;
```

控制台将输出两行记录：
- 第一行记录的 `table` 为 `s1`；
- 第二行记录的 `table` 为 `s2`。

```text
+----+-------------+-------+------------+------+---------------+----------+---------+------+------+----------+-------+
| id | select_type | table | partitions | type | possible_keys | key      | key_len | ref  | rows | filtered | Extra |
+----+-------------+-------+------------+------+---------------+----------+---------+------+------+----------+-------+
|  1 | SIMPLE      | s1    | NULL       | ALL  | idx_key1      | NULL     | NULL    | NULL | 9895 |   100.00 | ...   |
|  1 | SIMPLE      | s2    | NULL       | ref  | idx_key1      | idx_key1 | 403     | ...  |    1 |   100.00 | ...   |
+----+-------------+-------+------------+------+---------------+----------+---------+------+------+----------+-------+
```

在执行计划中，**排在上面的表被称为驱动表（Driving Table），排在下方的表被称为被驱动表（Driven Table）**。查询引擎会先扫描驱动表 `s1`，每拿到一条记录，再拿着连接键去检索被驱动表 `s2`。

> **提示**：你在 SQL 中写 `FROM s1 INNER JOIN s2`，优化器**并不一定会机械地按照你书写的先后顺序执行**！优化器会评估两张表的大小与索引情况，自动选择成本更低的表作为驱动表。在上面的例子中，如果调整字段条件，优化器完全可能把 `s2` 放在第一行作为驱动表。

### 字段剖析之二：id（查询标识符与执行顺序）

`id` 是很多开发者最容易想当然的字段，常有人误以为 `id` 只是无意义的行号（1、2、3……自增）。其实不然，`id` 蕴含着整个查询的结构层次与执行时序。

#### id 的分配机理

> **核心黄金法则**：在一条大的 SQL 查询语句中，**每一个 `SELECT` 关键字，原则上都会被分配一个唯一的 `id` 值**。

- 整个 SQL 只有一个 `SELECT` 关键字，无论关联多少张表，所有行的 `id` 全都是 1；
- 出现子查询、嵌套查询或 `UNION` 时，存在多个独立的 `SELECT` 关键字，就会依次分配不同的 `id`（1, 2, 3……）。

#### 规律一：id 相同，从上至下顺序执行

当进行多表内连接时：

```sql
EXPLAIN SELECT * FROM s1 INNER JOIN s2 ON s1.id = s2.id;
```

结果集包含两行（因为有 `s1` 和 `s2` 两张表），但由于整个语句只有一个 `SELECT`，因此两行的 `id` **全部都是 1**。

```text
[id=1, table=s1] ---> 优先级相同，排在第一行，首先被读取（驱动表）
        ↓
[id=1, table=s2] ---> 优先级相同，排在第二行，嵌套循环匹配（被驱动表）
```

此时两张表的优先级完全一致，优化器按照从上往下的顺序流式执行。

#### 规律二：id 不同，值越大优先级越高

当编写包含子查询的 SQL 时：

```sql
EXPLAIN SELECT * FROM s1 WHERE key1 = (SELECT key1 FROM s2 WHERE id = 1);
```

执行计划将输出两行：
- 第一行：`table = s1`，`id = 1`；
- 第二行：`table = s2`，`id = 2`。

由于子查询内部包含独立的 `SELECT` 关键字，其被分配了 `id = 2`。根据数据库执行规律，**`id` 值越大，执行优先级越高，越先被执行**。执行引擎必须先执行 `id = 2` 的子查询，把 `s2` 表中 `id = 1` 对应的 `key1` 值计算出来，然后再交给外层 `id = 1` 的主查询去检索 `s1` 表。

#### 现象反转：查询优化器的子查询重写机理

下面看一个极具迷惑性、让无数初学者抓狂的经典案例：

```sql
EXPLAIN SELECT * FROM s1 
WHERE key1 IN (SELECT key2 FROM s2 WHERE common_field = 'abc');
```

乍一看，这条语句外层一个 `SELECT`，内层子查询一个 `SELECT`，按照理论，控制台应该输出 `id = 1` 和 `id = 2`。但当我们把该语句送入 MySQL 运行 `EXPLAIN` 后，令人震惊的结果出现了：
结果集确实输出了 `s1` 和 `s2` 对应的两行记录，但**两行记录的 `id` 居然全部变成了 1**！

```text
+----+-------------+-------+------------+------+---------------+----------+---------+------+------+----------+-------------+
| id | select_type | table | partitions | type | possible_keys | key      | key_len | ref  | rows | filtered | Extra       |
+----+-------------+-------+------------+------+---------------+----------+---------+------+------+----------+-------------+
|  1 | SIMPLE      | s2    | NULL       | ALL  | uk_key2       | NULL     | NULL    | NULL | 9895 |    10.00 | Using where |
|  1 | SIMPLE      | s1    | NULL       | ref  | idx_key1      | idx_key1 | 403     | ...  |    1 |   100.00 | NULL        |
+----+-------------+-------+------------+------+---------------+----------+---------+------+------+----------+-------------+
```

为什么子查询的 `id` 会消失？这正是 MySQL 查询优化器的**查询重写（Query Rewrite）**机制在发挥威力：
- 原生非相关子查询如果机械执行，逻辑类似于程序中的双层嵌套循环：外层扫描 $N$ 次，内层针对每一次都要扫描 $M$ 次，时间复杂度高达 $O(N \times M)$；
- 优化器在语法分析后敏锐发现：该 `IN` 子查询在语义上**完全等价于一个多表半连接（Semi-Join）或内连接**！
- 优化器直接在内存中将子查询重写为类似 `SELECT s1.* FROM s1 INNER JOIN s2 ON s1.key1 = s2.key2 WHERE s2.common_field = 'abc'` 的连接查询；
- 重写之后的实际执行 SQL 只有一个主 `SELECT`，多表连接并行推进，因此 `id` 自动归一为了一个并列的 `1`！

#### 规律三：临时表与 NULL 值的特殊含义（UNION 剖析）

除了数字之外，`id` 字段还有可能出现特殊的 `NULL` 值。典型代表就是 `UNION` 去重操作。

对比观察以下两个联合查询语句：

##### 场景 A：使用 UNION 进行求并集与去重

```sql
EXPLAIN SELECT * FROM s1 UNION SELECT * FROM s2;
```

执行计划控制台输出了 **3 行**记录：

```text
+----+--------------+--------------+------------+------+---------------+------+---------+------+-------+----------+-----------------+
| id | select_type  | table        | partitions | type | possible_keys | key  | key_len | ref  | rows  | filtered | Extra           |
+----+--------------+--------------+------------+------+---------------+------+---------+------+-------+----------+-----------------+
|  1 | PRIMARY      | s1           | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 10000 |   100.00 | NULL            |
|  2 | UNION        | s2           | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 10000 |   100.00 | NULL            |
|NULL| UNION RESULT | <union1,2>   | NULL       | ALL  | NULL          | NULL | NULL    | NULL |  NULL |     NULL | Using temporary |
+----+--------------+--------------+------------+------+---------------+------+---------+------+-------+----------+-----------------+
```

我们来深度拆解这 3 行数据：
1. 第 1 行对应第一个 `SELECT`，访问 `s1` 表，`id = 1`；
2. 第 2 行对应第二个 `SELECT`，访问 `s2` 表，`id = 2`；
3. **第 3 行记录**：
   - 它的 `table` 显示为 **`<union1,2>`**，明确表示它是将 `id = 1` 与 `id = 2` 两趟查询的结果合并后的临时数据集；
   - 它的 `Extra` 显示为 **`Using temporary`**，印证了 MySQL 在底层显式开辟了一张内存临时表来执行去重计算；
   - **它的 `id` 值为 `NULL`**：因为这行记录代表的是对前面两趟查询结果的后置聚合处理，它不是由任何一个独立的 `SELECT` 关键字产生的，因此不具备独立的查询标识符，必须置为 `NULL`。

##### 场景 B：使用 UNION ALL 进行纯拼接

如果我们换成不进行去重的 `UNION ALL`：

```sql
EXPLAIN SELECT * FROM s1 UNION ALL SELECT * FROM s2;
```

此时控制台只输出了两行（`s1` 和 `s2`，对应的 `id` 分别为 1 和 2），那个令人头疼的 `<union1,2>` 临时表与 `id = NULL` 行彻底消失了！
因为 `UNION ALL` 不需要剔除重复记录，引擎只需要将 `s1` 的数据发给客户端，紧接着把 `s2` 的数据发给客户端即可，完全无需建立临时表暂存数据。

### id 字段背后的系统性能哲学

通过对 `id` 字段的深入剖析，我们可以总结出数据库优化中最朴素的性能公理：

> **性能核心公理**：每个不同的 `id` 号码，都代表数据库需要发起一趟独立的查询检索。**一条 SQL 语句在执行计划中的查询趟数（不同 id 的数量）越少越好**！

```text
【低效的多层嵌套模式】
id = 3 (最底层子查询，先跑一趟)
    ↓
id = 2 (中间层子查询，再跑一趟)
    ↓
id = 1 (外层主查询，最后跑一趟)  ===> 依赖链条深，产生多趟往返与中间物化，效率低下

【高效的同级扁平模式】
id = 1 (table = s1, 驱动表)
id = 1 (table = s2, 被驱动表)   ===> 单趟多表关联，基于流式或块嵌套循环，吞吐极高
```

当看到一条复杂的业务 SQL 经 `EXPLAIN` 后输出了 4~5 个不同的 `id`，甚至出现了大量的内部派生表（Derived Table）时，就应当立即警惕：这说明查询引擎陷入了极深的多层嵌套依赖，应当尽可能通过改写为连接查询或利用临时物化表对其进行扁平化降维。

### 本讲核心要点快速复盘

1. **EXPLAIN 的角色本质**：它是优化器在执行前输出的成本预测蓝图，不执行真正读写，安全且权威；
2. **table 映射规律**：结果集一行严格对应一个物理表或临时表；在多表连接中，先打印出的表为驱动表，后打印出的为被驱动表；
3. **id 的基本法则**：一个 `SELECT` 原则上对应一个 `id`；`id` 相同从上往下执行，`id` 不同值越大越先执行；
4. **子查询重写**：原本写成子查询的语句，若在执行计划中看到所有表的 `id` 都是 1，说明优化器自动实施了优化重写，将其降维成了高效的连接查询；
5. **UNION 临时表机制**：`UNION` 去重必引入临时表（`Using temporary`），并在结果集中生成 `table` 为 `<union1,2>`、`id` 为 `NULL` 的聚合行；而 `UNION ALL` 则无此额外开销。

> **提示**：掌握了 `table` 与 `id`，我们已经能够清晰读懂 SQL 执行的骨架与时序。但这仅仅是读懂执行计划的第一步。在下一讲中，我们将全面攻克决定执行计划生死命脉的硬核字段——`select_type` 查询类型、`type` 单表访问方法（从最高效的 `system`、`const` 到最危险的 `ALL` 全表扫描），以及决定联合索引利用率的 `key_len` 字节深度计算。

## 137-EXPLAIN中select_type、partitions、type、possible_keys、key、key_len剖析
> 对应分集：P137 | 原始标题：《137-EXPLAIN中select_type、partitions、type、possible_keys、key、key_len剖析》

在上一讲中，我们拆解了 `EXPLAIN` 输出中的 `id` 与 `table`。我们知道了一个原则：查询语句中每出现一个 `SELECT` 关键字，通常就会对应分配一个独立的 `id`（除非被优化器重写合并）；而最终结果集里的每一行记录，本质上都对应着一张参与查询的物理表或临时派生表。

但随之而来的疑问是：在一个包含子查询、多表连接或 `UNION` 联合的大查询里，各个由 `SELECT` 关键字代表的小查询，究竟在整个宏大的查询架构中扮演着什么样的角色？是作为最外层的主干，还是作为内层的条件过滤，亦或是联合运算的后续分支？更关键的是，MySQL 到底是以怎样的方式去访问每一张表的数据？它到底是全表一条条硬扫，还是走主键精准命中，亦或是通过二级索引做区间检索？

这就是本讲要解决的核心议题。我们将按顺序深入剖析 `EXPLAIN` 输出中至关重要的六个字段：`select_type`、`partitions`、`type`、`possible_keys`、`key` 以及 `key_len`。其中，`type` 和 `key_len` 是衡量 SQL 执行性能高低与索引利用率的试金石。

---

### select_type 字段：小查询在大查询中的角色定位

MySQL 为每个 `SELECT` 关键字代表的小查询都定义了一个属性，叫做 `select_type`（查询类型）。有了这个属性，我们就能一目了然地看清该小查询在整个大查询语句中扮演的具体角色。

```text
+----+-------------+-------+------------+-------+---------------+
| id | select_type | table | partitions | type  | possible_keys |
+----+-------------+-------+------------+-------+---------------+
```

#### SIMPLE：简单查询

如果一个查询语句中既不包含 `UNION`，也不包含子查询，那么无论它是单表查询还是多表连接查询，其每一个小查询的 `select_type` 都会被标记为 `SIMPLE`。

```sql
-- 1. 最极其普通的单表查询
EXPLAIN SELECT * FROM s1;

-- 2. 两个表进行连接查询
EXPLAIN SELECT * FROM s1 INNER JOIN s2;
```

在执行连接查询时，虽然由于涉及两张表而在结果集中输出了两行记录（驱动表与被驱动表各一行），但因为整个 SQL 中只有一个 `SELECT` 关键字，所以两行的 `id` 均为 1，且两行的 `select_type` 全都是 `SIMPLE`。

> **结论**：只要查询语句中不存在 `UNION` 和子查询，不管是单表还是内连接、左外连接，各表的 `select_type` 均为 `SIMPLE`。

#### PRIMARY、UNION 与 UNION RESULT

当查询语句中出现了 `UNION`、`UNION ALL` 或者子查询等复合结构时，大查询就会由若干个小查询组合而成。此时各个小查询的角色便开始分化：

- `PRIMARY`：对于包含 `UNION`、`UNION ALL` 或者子查询的大查询，最左边（最外层）的那个主查询，其 `select_type` 就是 `PRIMARY`。
- `UNION`：在包含 `UNION` 或 `UNION ALL` 的语句中，除了最左边的主查询之外，其后连接的所有小查询，其 `select_type` 均为 `UNION`。
- `UNION RESULT`：因为 `UNION` 操作需要对两个数据集进行去重，MySQL 会使用内部临时表来汇聚并剔除重复记录。专门用于展现该临时表去重结果的小查询，其 `select_type` 就是 `UNION RESULT`。

```sql
-- UNION 查询案例
EXPLAIN 
SELECT * FROM s1 
UNION 
SELECT * FROM s2;
```

执行后的输出结构如下：

```text
+----+--------------+------------+
| id | select_type  | table      |
+----+--------------+------------+
|  1 | PRIMARY      | s1         |
|  2 | UNION        | s2         |
|NULL| UNION RESULT | <union1,2> |
+----+--------------+------------+
```

读图说明：最左侧的 `s1` 查询被视为主体，其 `select_type` 是 `PRIMARY`；通过 `UNION` 连接在后面的 `s2`，其 `select_type` 是 `UNION`；而最后一行 `table` 为 `<union1,2>` 的记录，代表将 `id=1` 和 `id=2` 的结果集放入临时表进行去重，该行的 `id` 为 NULL，其 `select_type` 即为 `UNION RESULT`。

如果换成 `UNION ALL`，因为不需要去重，MySQL 直接将两部分数据流式返回，不需要创建去重临时表，所以结果中就只有 `PRIMARY` 和 `UNION` 两行，不会出现 `UNION RESULT`。

#### SUBQUERY 与 DEPENDENT SUBQUERY

对于子查询，最外层的查询类型同样是 `PRIMARY`，而内层的子查询则取决于它是否与外层存在依赖关系（是否为相关子查询）：

- `SUBQUERY`：如果包含子查询的语句不能被优化器改写为多表连接，且该子查询是非相关子查询（内层查询独立运行，不依赖外层表的字段），内层子查询的 `select_type` 就是 `SUBQUERY`。
- `DEPENDENT SUBQUERY`：如果子查询无法转为连接查询，且内层查询的过滤条件中引用了外层查询的字段（即相关子查询），此时内层子查询的 `select_type` 就是 `DEPENDENT SUBQUERY`。

```sql
-- 1. 非相关子查询：内层为 SUBQUERY
EXPLAIN 
SELECT * FROM s1 
WHERE key1 IN (SELECT key1 FROM s2);

-- 2. 相关子查询：内层为 DEPENDENT SUBQUERY
EXPLAIN 
SELECT * FROM s1 
WHERE key1 IN (SELECT key1 FROM s2 WHERE s1.key2 = s2.key2);
```

> **易错点**：标记为 `DEPENDENT SUBQUERY` 的子查询可能会被执行多次。执行机制是外层主查询每扫描出一条记录，就将其字段值传给内层子查询执行一次，外层扫出多少条，内层就可能重复执行多少次，性能开销极大。

#### DEPENDENT UNION

当一个大查询内部包含子查询，而子查询内部又由 `UNION` 或 `UNION ALL` 构成，并且子查询中的各个小查询都依赖于外层查询时，除了最左侧的小查询之外，其余后续的 `UNION` 小查询的 `select_type` 就会被标记为 `DEPENDENT UNION`。

```sql
EXPLAIN 
SELECT * FROM s1 
WHERE key1 IN (
    SELECT key1 FROM s2 
    UNION 
    SELECT key1 FROM s1
);
```

执行该语句时，你会发现内层查询并没有显式引用 `s1` 的字段，为什么依然出现了 `DEPENDENT UNION`？
这是因为 MySQL 查询优化器在处理 `IN` 子查询时，往往会自动将其重构改写为 `EXISTS` 相关子查询。在重写之后，外层的参数被渗透进了内层的每个分支中，使得内层的小查询变成了依赖外层的查询，因此右侧分支被打上了 `DEPENDENT UNION` 标记。

#### DERIVED 与 MATERIALIZED

- `DERIVED`（派生表）：如果子查询出现在 `FROM` 子句中，且无法被优化器折叠合并到外层，MySQL 就会把该子查询的执行结果物化为一个派生表。该子查询的 `select_type` 就是 `DERIVED`，而外层查询的 `table` 字段会显示为 `<derived2>`（由 `id=2` 的查询派生而来）。
- `MATERIALIZED`（物化表）：当优化器在处理包含子查询的语句时，如果决定不将子查询转为连接，也不采用相关子查询的多次循环迭代方式，而是选择将非相关子查询的结果直接物化为一个带索引的内部临时表，然后再与外层表进行连接，此时内层子查询的 `select_type` 就是 `MATERIALIZED`。外层的 `table` 可能会显示为 `<subquery2>`。

```sql
-- 包含派生表的查询
EXPLAIN 
SELECT * FROM (
    SELECT key1, count(*) AS cnt 
    FROM s1 
    GROUP BY key1
) AS derived_s1;
```

### partitions 字段：分区表命中分析

`partitions` 字段用于反映查询在分区表（Partition Table）中的分区命中情况。

- 如果当前查询涉及的表不是分区表，该字段的值始终为 `NULL`；
- 如果表在建表时通过 `PARTITION BY RANGE/LIST/HASH` 划分了不同的分区，当查询带有分区键过滤时，`partitions` 字段就会明确列出本次查询命中了哪些具体分区（例如 `p0`、`p1`）。

> **提示**：在绝大多数没有配置物理分区的单表场景下，该字段均为 `NULL`，在日常调优中了解即可，无需过度关注。

### type 字段：单表访问方法全景详解

从 `type` 字段开始，我们正式触碰到执行计划中最核心、与索引关联最紧密的指标。

> **定义**：`type` 字段刻画的是 MySQL 在执行查询时对某个表采取的具体“访问方法”（Access Method）。

访问方法的优劣直接决定了查询耗时。各访问方法的性能排序从最优到最差大致如下：

```text
system > const > eq_ref > ref > fulltext > ref_or_null > index_merge > unique_subquery > index_subquery > range > index > ALL
```

《阿里巴巴 Java 开发手册》中明确给出过数据库 SQL 调优规范：**SQL 性能优化的目标，至少要达到 `range` 级别，要求是 `ref` 级别，如果能达到 `const` 则是最理想的。** 绝不能放任核心业务接口长期运行在 `index` 尤其是 `ALL` 级别。

#### system：精确统计引擎的极速单行访问

`system` 是性能最高的理论极限级别。它必须满足两个严苛条件：
1. 表中只有一条物理记录；
2. 该表所使用的存储引擎具有精确的统计数据（例如 `MyISAM` 或 `Memory` 引擎）。

为什么必须具备“精确统计数据”？因为像 `MyISAM` 这类引擎，其内部维护了一个元数据变量精确记录了当前表的总行数，执行 `SELECT COUNT(*)` 时根本不用翻阅数据页，直接读取变量返回常数。因此面对单行表，优化器能直接把整行记录当成固定常数提取出来。

```sql
-- 验证 system 级别（MyISAM 引擎）
CREATE TABLE t (a INT) ENGINE = MyISAM;
INSERT INTO t VALUES (1);

EXPLAIN SELECT * FROM t; -- 此时 type 为 system

INSERT INTO t VALUES (2);
EXPLAIN SELECT * FROM t; -- 记录变为两条，退化为 ALL
```

**对比思考**：如果我们在 `InnoDB` 引擎下建一张单行记录表 `tt`，执行同样的查询，它的 `type` 会是 `system` 吗？
答案是：**不会，它是 `ALL`！**
因为 `InnoDB` 引擎采用 MVCC 多版本并发控制，由于并发事务与版本链的存在，表中到底能看到多少条记录必须结合当前事务的 ReadView 去实际扫描判断，它没有一个全局精确记录行数的物理变量。在没有索引辅助的情况下，即使物理上只有一条数据，也必须老老实实做全表扫描。

#### const：主键或唯一索引的常量等值匹配

当我们通过主键（`PRIMARY KEY`）或者非空的唯一二级索引（`UNIQUE KEY`）与一个常量进行等值比较时，该表的访问方法就是 `const`（常数级）。

```sql
-- 1. 根据主键等值匹配
EXPLAIN SELECT * FROM s1 WHERE id = 10005;

-- 2. 根据唯一二级索引等值匹配（假设 key2 字段有 UNIQUE 约束）
EXPLAIN SELECT * FROM s1 WHERE key2 = 100;
```

其底层机理在于：主键与唯一索引的根基就是“唯一性”。在聚簇索引或唯一二级索引的 B+ 树上进行二分查找，一路下潜到叶子节点，只要找到匹配的值（如 10005），就能彻底断定整张表里绝不可能再有第二条相同的记录。优化器甚至可以在查询准备阶段直接算出该记录并将其视作一个常量，故称为 `const`。

#### eq_ref：连接查询中被驱动表的主键/唯一索引匹配

在多表连接查询中，如果被驱动表是通过主键或者非空的唯一二级索引列，与驱动表的某列进行等值匹配连接，那么被驱动表的访问方法就是 `eq_ref`。

```sql
EXPLAIN SELECT * FROM s1 INNER JOIN s2 ON s1.id = s2.id;
```

分析该查询的执行过程：
1. 优化器选择 `s1` 作为驱动表，对 `s1` 进行全表扫描（`type = ALL`）；
2. 对于从 `s1` 检索出来的每一条记录，将其 `id` 值作为确定输入，去被驱动表 `s2` 的主键索引树上做等值匹配；
3. 因为 `s2.id` 是主键，对于驱动表传来的每一个特定值，在 `s2` 中最多只能找到一条匹配记录；
4. 这种被驱动表的访问效率极高，其 `type` 呈现为 `eq_ref`。

> **提示**：如果主键或唯一索引是联合索引，必须对该索引包含的每一个列都进行等值匹配，才能达到 `eq_ref`。

#### ref：普通二级索引的常量等值匹配

当通过普通的（非唯一的）单列二级索引与常量进行等值匹配检索时，访问方法即为 `ref`。

```sql
-- key1 为普通单列二级索引
EXPLAIN SELECT * FROM s1 WHERE key1 = 'a';
```

因为是普通二级索引，B+ 树叶子节点中键值为 `'a'` 的记录可能不止一条，它们在叶子节点单向链表中是连续排列的。优化器通过索引树快速定位到第一条 `'a'`，然后沿着链表向后顺序扫描，直到遇到第一个不是 `'a'` 的值为止。由于返回的可能是一个连续区间而不是唯一一条，其性能略低于 `const`，但在业务查询中已属非常理想的级别。

> **易错点（隐式类型转换）**：如果 `key3` 是 `VARCHAR` 字符类型，但在写 SQL 时写成了 `WHERE key3 = 123`（没有加单引号）。此时 MySQL 会自动调用类型转换函数将列值转为数值再做比对。一旦在索引列上触发隐式函数运算，索引将彻底失效，访问方法会直接从预期的 `ref` 骤降为 `ALL`！写 SQL 时必须保证常量类型与字段定义完全一致。

#### ref_or_null：支持 NULL 值的普通索引等值扫描

如果在普通二级索引等值匹配的基础上，查询条件还允许索引列为 `NULL`，此时对应的访问方法就是 `ref_or_null`。

```sql
EXPLAIN SELECT * FROM s1 WHERE key1 = 'a' OR key1 IS NULL;
```

二级索引树的叶子节点把所有的 `NULL` 值集中存放在了链表的最左端。MySQL 既要扫描 `'a'` 对应的连续记录，又要去扫描最左侧为 `NULL` 的记录，因此访问方法记作 `ref_or_null`。

#### index_merge：多索引合并扫描

通常情况下，一条单表查询语句只能使用一个索引。但某些特殊场景下，优化器可以同时利用多个单列索引检索出各自匹配的主键集，然后将结果集进行并集（Union）或交集（Intersection）合并，这种访问方法称为 `index_merge`。

```sql
-- key1 和 key3 均为各自独立的单列二级索引
EXPLAIN SELECT * FROM s1 WHERE key1 = 'a' OR key3 = 'a';
```

此时 `type` 为 `index_merge`，同时在 `key` 字段中会显示 `idx_key1,idx_key3`。优化器分别利用两个索引定位出主键列表，做内存并集运算后再统一回表取整行数据。

> **注意**：如果把这里的 `OR` 改成 `AND`（`WHERE key1 = 'a' AND key3 = 'a'`），优化器绝大多数情况下不会走 index_merge，而是会在 `key1` 与 `key3` 之间精算成本，挑出一个过滤效果更好、成本更低的单个索引去执行，另一个条件则在回表后进行内存过滤。

#### unique_subquery：子查询中主键等值匹配

在包含 `IN` 的子查询中，当优化器将 `IN` 结构转换为 `EXISTS` 相关子查询，且子查询内部的关联条件可以使用主键进行等值匹配时，该子查询对应表的 `type` 就是 `unique_subquery`。它本质上就是子查询内部对主键做的类似 `eq_ref` 的查找。

#### range：索引范围扫描

当利用二级索引或聚簇索引获取某个连续范围或离散点集区间的记录时，访问方法就是 `range`。

```sql
-- 1. IN 离散集合范围扫描
EXPLAIN SELECT * FROM s1 WHERE key1 IN ('a', 'b', 'c');

-- 2. 连续区间范围扫描
EXPLAIN SELECT * FROM s1 WHERE key1 > 'a' AND key1 < 'b';
```

`range` 级别通常对应 SQL 中的 `<`, `>`, `<=`, `>=`, `BETWEEN`, `IN` 等操作符。利用 B+ 树索引的有序性，优化器只需要确定扫描的起始边界与终止边界，并在叶子节点链表中做一段局部遍历即可。这是日常业务调优所必须坚守的底线级别。

#### index：覆盖索引全扫描

很多初学者容易将 `index` 与走索引高效检索混淆。**`index` 本质上也是一种全表扫描，只不过它扫描的是整棵二级索引树，而不是聚簇索引树。**

当查询所需要返回的全部列（包括 `SELECT` 列表、`WHERE` 条件列）恰好被某个二级索引（尤其是联合索引）完全覆盖，不需要进行任何回表操作时，即使查询条件不符合最左前缀原则、无法利用索引树做二分快速定位，优化器依然会选择把整棵二级索引树的所有叶子节点从头到尾扫一遍。

```sql
-- 假设存在联合索引 idx_part(key_part1, key_part2, key_part3)
EXPLAIN SELECT key_part2 FROM s1 WHERE key_part3 = 'a';
```

在这个查询中：
1. 条件直接使用了 `key_part3`，违背了最左前缀原则，无法通过 B+ 树层级索引快速跳跃定位；
2. 但查询的字段只有 `key_part2`，条件字段是 `key_part3`，它们全都包含在 `idx_part` 联合索引树里；
3. 二级索引树的一个数据页往往能塞下几百上千条紧凑的索引条目，而聚簇索引树包含整行全部列数据，页面非常膨胀。扫描整棵二级索引树所消耗的磁盘 I/O 成本，远远小于扫描整棵聚簇索引树；
4. 因此优化器决定做**全二级索引扫描**，此时 `type` 显示为 `index`，`Extra` 常常伴随 `Using index`。

> **易错点**：如果在上面的 `SELECT` 列表中额外加入一个不在联合索引中的普通列 `common_field`，因为二级索引无法覆盖它、必须全表回表，优化器就会果断放弃扫描二级索引，`type` 会立刻跌入万劫不复的 `ALL` 全表扫描。

#### ALL：全表扫描

最糟糕的访问方法。没有利用任何索引辅助定位，直接从头到尾遍历聚簇索引的所有数据页和所有数据行，磁盘 I/O 开销与 CPU 比对开销达到峰值。在线上大表环境中，必须通过建立合理索引将其彻底消灭。

### possible_keys 与 key：可能选用的索引与最终裁定的索引

这两个字段用来展现优化器在索引决策过程中的心智模型：

- `possible_keys`：展示在当前查询的 `WHERE` 条件中，涉及到的列上建立的、理论上可能被用到的索引清单；
- `key`：展示优化器通过精细的成本估算后，最终决定真正采用的索引名称。

```sql
EXPLAIN SELECT * FROM s1 WHERE key1 > 'z' AND key3 = 'a';
```

在该查询中，`key1` 和 `key3` 上分别建有独立的单列二级索引。在 `possible_keys` 栏目中，MySQL 会同时把 `idx_key1` 和 `idx_key3` 列出来；但在最终的 `key` 字段中，优化器选定了 `idx_key3`。

为什么选 `key3` 而不选 `key1`？
因为 `key1 > 'z'` 是一个范围查询，扫描的数据量和回表开销不确定且可能较大；而 `key3 = 'a'` 是一个单列常量的等值精准匹配（`type = ref`），评估得出的 I/O 与 CPU 成本明显更低。优化器最终遵循“成本最低”原则裁定了 `idx_key3`。

> **优化器思考题：候选索引越多越好吗？**
> 有些开发者认为：在表上建的索引越多，`possible_keys` 候选项越多，查询越灵活，就越好。
> 这种想法就像是在生活中幻想：“追我的女生越多越好，有三四个女生追我多风光。”但现实中选择越多，你筛选甄别、沟通权衡的决策成本就急剧飙升。
> MySQL 查询优化器也是一样。`possible_keys` 里的候选索引越多，优化器在编译期计算排列组合、估算读取页面成本的耗时就越长，反而极大地拉高了 SQL 解析和执行计划生成的代价。因此表上的索引绝非多多益善，必须克制精简。

> **特殊现象**：`possible_keys` 为 `NULL`，但 `key` 却有值。
> 这绝非矛盾。典型场景就是上一节讲到的 `type = index` 覆盖索引扫描。因为查询条件不符合索引树的查找过滤逻辑，所以优化器在初始阶段认为没有可用于精准定位的 `possible_keys`；但在后续评估返回列时，发现整个查询可以由某个二级索引全覆盖免于回表，于是最终在 `key` 中选用了该联合索引。

### key_len 字段：索引使用的有效字节长度深度解析

`key_len` 记录的是 MySQL 在执行查询时，**实际使用到的索引部分的字节长度**，单位是字节（Byte）。

```text
+----+-------------+-------+-------+---------------+----------+---------+
| id | select_type | table | type  | key           | key_len  | ref     |
+----+-------------+-------+-------+---------------+----------+---------+
|  1 | SIMPLE      | s1    | ref   | idx_key_part  | 303      | const   |
+----+-------------+-------+-------+---------------+----------+---------+
```

#### key_len 的核心意义：联合索引充分利用度的体检表

很多人听到一条调优口诀叫“`key_len` 越大越好”，便容易陷入误区：拿表 A 的 `key_len = 20` 去跟表 B 的 `key_len = 303` 比，毫无意义，因为不同表字段类型和字符集本身就完全不同。

> **核心原则**：`key_len` 只能**跟自己的不同查询语句比**，它最核心的应用场景是：**检查复合索引（联合索引）是否被充分利用**。

假设存在一个三列联合索引 `idx_part(key_part1, key_part2, key_part3)`：
- 当查询条件只用到了 `key_part1` 时，`key_len` 算出的是 303 字节；
- 当查询条件同时用到了 `key_part1` 和 `key_part2` 时，`key_len` 跃升为 606 字节；
- 当三列全部充分用在过滤条件上时，`key_len` 达到 909 字节。

此时 909 字节明显远胜于 303 字节。`key_len` 越长，意味着联合索引中参与过滤的列越多，在 B+ 树中下潜定位的范围越精准，最后需要扫描的数据页和需要回表的数据行就越少。

#### 字段字节长度计算规则

`key_len` 的数值是由字段数据类型、字符集编码、是否允许为 NULL 以及是否为变长字段四项规则严格相加推导出来的：

```text
+--------------------------------------------------------------------------------+
| 单列 key_len = 基础类型字节数                                                   |
|              + (字符类型需乘以字符集单字最大字节数)                                 |
|              + (若允许为 NULL，额外加 1 字节记录 NULL 标志位)                      |
|              + (若为 VARCHAR 等变长字段，额外加 2 字节记录数据实际长度)               |
+--------------------------------------------------------------------------------+
```

1. **基础数值类型**：
   - `TINYINT`：1 字节；
   - `SMALLINT`：2 字节；
   - `MEDIUMINT`：3 字节；
   - `INT`：4 字节；
   - `BIGINT`：8 字节；
   - `DATETIME`（MySQL 5.6.4+）：5 字节；`TIMESTAMP`：4 字节。
2. **字符集倍率**：
   - `latin1`：每个字符占 1 字节；
   - `gbk`：每个字符最多占 2 字节；
   - `utf8`（utf8mb3）：每个字符最多占 3 字节；
   - `utf8mb4`：每个字符最多占 4 字节。
3. **NULL 标志位开销**：
   - 如果列定义中允许为 `NULL`（即没有显式声明 `NOT NULL`），MySQL 内部需要额外耗费 **1 个字节** 存储 NULL 标志位。
4. **变长长度列表开销**：
   - 对于 `VARCHAR` 等变长类型，MySQL 在底层紧凑行格式中必须记录该字段的真实数据长度，额外耗费 **2 个字节**。如果是定长类型（如 `CHAR(n)`、`INT`），则无此 2 字节开销。

#### 案例实战拆解

我们以演示库 `s1` 中的字段定义（基于 `utf8` 字符集，单字符最多 3 字节）来逐个核算：

##### 案例 1：主键 INT NOT NULL
```sql
EXPLAIN SELECT * FROM s1 WHERE id = 10005;
```
- 字段类型：`INT`，固定 4 字节；
- 约束：主键自带 `NOT NULL`，无需 NULL 标志位；定长无长度列表。
- **最终 key_len**：$4$ 字节。

##### 案例 2：唯一索引 INT NULL
```sql
-- key2 为 INT 类型，UNIQUE 索引，建表未声明 NOT NULL
EXPLAIN SELECT * FROM s1 WHERE key2 = 100;
```
- 基础长度：`INT` 为 4 字节；
- NULL 标志：允许为 NULL，增加 1 字节；
- **最终 key_len**：$4 + 1 = 5$ 字节。

##### 案例 3：普通单列 VARCHAR(100) NULL
```sql
-- key1 为 VARCHAR(100)，utf8 字符集，允许为 NULL
EXPLAIN SELECT * FROM s1 WHERE key1 = 'a';
```
- 字符内容最大占用：$100 \times 3 = 300$ 字节；
- NULL 标志：允许为 NULL，增加 1 字节；
- 变长长度记录：`VARCHAR` 变长类型，增加 2 字节；
- **最终 key_len**：$300 + 1 + 2 = 303$ 字节。

##### 案例 4：联合索引 idx_part(key_part1, key_part2, key_part3)
表中三列均为 `VARCHAR(100)`，`utf8` 字符集，允许为 NULL。单列完全利用的长度为 303 字节。

```sql
-- 1. 仅命中第一列
EXPLAIN SELECT * FROM s1 WHERE key_part1 = 'a';
-- 输出 key_len: 303

-- 2. 命中前两列
EXPLAIN SELECT * FROM s1 WHERE key_part1 = 'a' AND key_part2 = 'b';
-- 输出 key_len: 606 (303 + 303)

-- 3. 命中全部三列
EXPLAIN SELECT * FROM s1 WHERE key_part1 = 'a' AND key_part2 = 'b' AND key_part3 = 'c';
-- 输出 key_len: 909 (303 + 303 + 303)

-- 4. 违背最左前缀
EXPLAIN SELECT * FROM s1 WHERE key_part2 = 'b';
-- 输出 key: NULL, key_len: NULL (无法使用索引)
```

通过 `key_len` 的数值演变，我们能精准辨析出当前查询到底吸纳了联合索引中的几个字段。如果看到预期应该全部走索引的语句其 `key_len` 只有 303，就必须立刻排查是不是后续字段在 SQL 中触发了范围查询或者隐式类型转换，导致联合索引发生截断失效。

### 本讲提到的练习：key_len 计算规则自测

本讲中，我们通过几个常见的字段声明模式来巩固 `key_len` 的底层推导。请结合给出的定义，推算其作为单列索引时的 `key_len`：

#### 题目 1
- **字段定义**：`col1 VARCHAR(10)`，字符集 `utf8`，允许为 NULL。
- **推导解析**：
  1. `VARCHAR(10)` 在 `utf8` 下基础字符长度：$10 \times 3 = 30$ 字节；
  2. 允许为 NULL，增加 1 字节；
  3. 属于变长类型，增加 2 字节。
- **计算答案**：$30 + 1 + 2 = 33$ 字节。

#### 题目 2
- **字段定义**：`col2 VARCHAR(10)`，字符集 `utf8`，明确声明 `NOT NULL`。
- **推导解析**：
  1. 基础字符长度：$10 \times 3 = 30$ 字节；
  2. 声明了 `NOT NULL`，省去 NULL 标志位（+0）；
  3. 变长类型增加 2 字节。
- **计算答案**：$30 + 0 + 2 = 32$ 字节。

#### 题目 3
- **字段定义**：`col3 CHAR(10)`，字符集 `utf8`，允许为 NULL。
- **推导解析**：
  1. `CHAR(10)` 在 `utf8` 下基础字符长度：$10 \times 3 = 30$ 字节；
  2. 允许为 NULL，增加 1 字节；
  3. 因为是定长字符类型 `CHAR`，不需要长度列表（+0）。
- **计算答案**：$30 + 1 + 0 = 31$ 字节。

## 138-EXPLAIN中ref、rows、filtered、extra剖析
> 对应分集：P138 | 原始标题：《138-EXPLAIN中ref、rows、filtered、extra剖析》

在前两讲中，我们详细探讨了 `id`、`table`、`select_type`、`type`、`key` 以及 `key_len`。通过这些字段，我们已经能够摸清一个小查询在大查询中的角色、单表的数据访问方法以及复合索引的具体利用深度。

然而，仅仅知道索引被用上了还不够。我们在做 SQL 性能体检时，经常要面对几个更加尖锐的工程问题：
- 我们用索引去匹配的到底是一个死常数、另一张表的某个具体字段，还是一个运行期的函数？
- 优化器为了查出我们想要的结果，预估需要扫描多少行数据？在这些被扫描的数据中，真正满足条件的有效数据占了多大百分比？这个百分比在多表关联中又是如何成倍放大系统开销的？
- 为什么明明走了索引，SQL 还是慢如蜗牛？到底有没有发生隐蔽而昂贵的回表？有没有在内存甚至磁盘里打临时表？有没有触发底层的全表重排序（filesort）？

这些关键细节，全部隐藏在 `EXPLAIN` 的后半段字段中：`ref`、`rows`、`filtered` 以及信息量最为庞大的 `Extra`。本讲我们将逐一拆解这四个字段的底层机理，并在文末客观厘清 `EXPLAIN` 工具的适用边界与局限性。

### ref 字段：索引等值匹配的对象识别

`ref` 字段的含义非常直观：**当使用索引列进行等值查询时，用来展示与该索引列进行等值匹配的对象或表达式信息**。

它与前面讲到的 `type` 字段（尤其是 `const`、`eq_ref`、`ref` 级别）紧密呼应，主要有以下三种典型呈现形式：

#### 常量匹配（const）

当索引列直接与 SQL 中写死的常量值进行等值比较时，`ref` 字段会显示为 `const`。

```sql
-- key1 上建有普通的二级索引
EXPLAIN SELECT * FROM s1 WHERE key1 = 'a';
```

在该查询中，`type` 为 `ref`，而 `ref` 字段明确输出为 `const`，表明优化器使用普通二级索引去检索时，匹配的目标是一个确定的静态常量 `'a'`。

#### 多表关联的具体列匹配（库名.表名.列名）

在多表连接查询中，如果被驱动表是通过索引列与驱动表的某列进行等值连接，`ref` 会完整打印出驱动表提供数值的具体列全称（格式为：`库名.表名.列名`）。

```sql
EXPLAIN SELECT * FROM s1 INNER JOIN s2 ON s1.id = s2.id;
```

执行后，被驱动表 `s2` 的 `type` 显示为 `eq_ref`，其 `ref` 字段显示为：
```text
atguigudb1.s1.id
```
这清晰地告诉我们：`s2` 在主键索引树上每次查找的键值输入，来自于 `atguigudb1` 数据库中 `s1` 表的 `id` 字段值。

#### 函数与动态表达式匹配（func）

如果关联条件中驱动表的列被函数或复杂表达式包裹，此时传递给被驱动表索引的就不是一个原始列，而是一个运行期计算结果。

```sql
EXPLAIN SELECT * FROM s1 INNER JOIN s2 ON s2.key1 = UPPER(s1.key1);
```

此时被驱动表 `s2` 虽然使用了 `key1` 上的二级索引，但其 `ref` 字段不再输出列名，而是输出 `func`，代表其等值匹配依赖某个函数的返回值。

---

### rows 与 filtered 字段：行数预估与过滤效率的联合分析

在进行 SQL 性能调优时，`rows` 和 `filtered` 通常是一对必须联合查看的“黄金搭档”。

```text
+----+-------------+-------+-------+------+---------+------+------+----------+
| id | select_type | table | type  | key  | key_len | ref  | rows | filtered |
+----+-------------+-------+-------+------+---------+------+------+----------+
|  1 | SIMPLE      | s1    | range | idx1 | 303     | NULL |  382 |   100.00 |
+----+-------------+-------+-------+------+---------+------+------+----------+
```

#### rows 字段：预估扫描记录数

> **定义**：`rows` 字段表示查询优化器根据统计信息，**预估为了获取目标结果集所需要读取的物理记录条数**。

- **核心原则**：`rows` 数值**越小越好**。
- **底层物理逻辑**：预估读取的记录数越少，这些记录被收拢在同一个数据页中的概率就越高；记录越发散、行数越多，所需加载的数据页就越多，引发的磁盘 I/O（甚至随机 I/O）次数就会急剧膨胀。

例如执行范围查询：
```sql
EXPLAIN SELECT * FROM s1 WHERE key1 > 'z';
```
输出中 `rows` 显示为 382，表示优化器根据 B+ 树叶子节点的采样统计，估算出大约需要沿着索引链表扫描 382 条记录。

#### filtered 字段：条件过滤保留率

> **定义**：`filtered` 字段是一个百分比（0.00% ~ 100.00%），表示经过当前表的 `WHERE` 条件搜索过滤后，**剩余满足条件的有效记录占预估扫描总行数（`rows`）的比例**。

**思考设问：这个百分比是越高越好，还是越低越好？**
答案是：**越高越好！**

我们可以通过一个具体的数学对比来理解：
假设两个不同执行方案的最终结果集都需要返回 40 条数据：
- **方案 A**：优化器估算 `rows = 40`，`filtered = 100%`。意味着系统扫了 40 行，40 行全是目标有效数据，过滤精准度 100%，没有浪费半点 I/O；
- **方案 B**：优化器估算 `rows = 400`，`filtered = 10%`。最终算出的有效条数同样是 $400 \times 10\% = 40$ 条。但方案 B 为了这 40 条数据，白白多扫描了 360 条毫无价值的脏数据，占用了更多的缓冲区与内存。

因此，`filtered` 百分比越接近 100%，说明索引下潜过滤越精准，被无效加载的数据越少。

#### filtered 在多表连接中的连锁放大效应

在单表查询中，`filtered` 更多只是衡量当前条件过滤的充分度；但在**多表连接查询**中，驱动表的 `filtered` 拥有决定整个查询生死的重大意义！

> **核心结论**：在连接查询中，**驱动表预估扫描行数与过滤比例的乘积（$\text{rows} \times \text{filtered}$），直接决定了被驱动表被驱动循环调用的总次数**。

```sql
EXPLAIN SELECT * FROM s1 INNER JOIN s2 ON s1.key1 = s2.key1 WHERE s1.common_field = 'a';
```

假设该查询的执行计划输出如下：

```text
+----+-------------+-------+------+------+------+---------+------+----------+
| id | select_type | table | type | key  | ref  | rows    | ...  | filtered |
+----+-------------+-------+------+------+------+---------+------+----------+
|  1 | SIMPLE      | s1    | ALL  | NULL | NULL | 9895    | ...  |    10.00 |
|  1 | SIMPLE      | s2    | ref  | idx1 | ...  |   10    | ...  |   100.00 |
+----+-------------+-------+------+------+------+---------+------+----------+
```

分析该执行过程：
1. `s1` 作为驱动表，全表扫描预估行数为 9895 行；
2. 其 `WHERE` 条件 `common_field = 'a'` 上没有索引，经过过滤后的比例仅为 10.00%；
3. 驱动表实际向后传递的记录条数约为：
   $$9895 \times 10.00\% \approx 989 \text{ 条}$$
4. 这意味着被驱动表 `s2` 必须被外部循环连续调用 **989 次**！
5. 如果驱动表的 `filtered` 更低或者 `rows` 更大，被驱动表的执行频率就会以数量级为单位飙升。优化驱动表的过滤精准度，是治理慢连接查询的首要突破口。

### Extra 字段：深层执行机制诊断报告

`Extra` 字段虽然名字叫“额外的”，甚至像编程语言里的 `default` 或备用备注项，但它在实际调优中的地位举足轻重。

MySQL 提供的 `Extra` 描述信息多达几十种。它用简短但极具技术分量的提示语，直接揭示了 MySQL 到底是如何在内存、磁盘与存储引擎之间搬运和处理数据的。

#### No tables used 与 Impossible WHERE

- `No tables used`：查询语句中根本没有 `FROM` 子句。
  ```sql
  EXPLAIN SELECT 1;
  ```
- `Impossible WHERE`：查询语句中的 `WHERE` 条件在静态分析期即可判定永远为 `false`，根本不可能命中任何数据。
  ```sql
  EXPLAIN SELECT * FROM s1 WHERE 1 != 1;
  ```
  此时优化器甚至连 `table` 都不需要读取，直接返回空结果集。

#### Using where：条件过滤发生的层面

`Using where` 经常被误解为“只要写了 WHERE 条件就会出现”，其实不然。

`Using where` 的真正含义是：**存储引擎层无法单靠索引树把所有过滤条件处理完毕，必须将数据行读取出来，在 Server 层使用额外的条件进行逐行过滤**。

常见于以下两种场景：
1. 全表扫描时使用过滤条件（没有任何索引可用）：
   ```sql
   EXPLAIN SELECT * FROM s1 WHERE common_field = 'a';
   ```
2. 虽然使用了索引，但 `WHERE` 中还并列存在着无法走索引的其他普通列条件：
   ```sql
   EXPLAIN SELECT * FROM s1 WHERE key1 = 'a' AND common_field = 'b';
   ```
   优化器先利用 `key1` 索引定位到主键并回表取出行数据，随后在 Server 层对 `common_field = 'b'` 进行比对过滤，因此出现 `Using where`。

#### No matching min/max row 与 Select tables optimized away

在包含 `MIN()` 或 `MAX()` 聚合函数的查询中，优化器会专门做极端优化：

- `No matching min/max row`：当 `WHERE` 中的等值条件在索引树中根本找不到任何匹配记录时直接输出。
  ```sql
  EXPLAIN SELECT MIN(key1) FROM s1 WHERE key1 = '不存在的常量';
  ```
- `Select tables optimized away`：如果针对建立索引的列执行 `MIN()` 或 `MAX()`，因为 B+ 树天然是有序的，极小值必然在最左叶子节点，极大值必然在最右叶子节点。优化器在执行前读取索引根节点和边界就能直接秒得常数结果，执行阶段直接将该表操作“优化掉”（Optimized Away）。

#### Using index：覆盖索引（最高优状态）

> **定义**：当查询列表（`SELECT` 列）以及搜索条件中的所有字段，**全部包含在所使用的二级索引树中（包含隐藏的主键列），无需进行任何回表操作**即可返回数据时，`Extra` 会明确显示 `Using index`。

```sql
-- 1. 覆盖索引：查询字段仅包含索引列和主键
EXPLAIN SELECT key1, id FROM s1 WHERE key1 = 'a';
-- 输出 Extra: Using index

-- 2. 破坏覆盖索引：加入了非索引列 common_field
EXPLAIN SELECT key1, common_field FROM s1 WHERE key1 = 'a';
-- 输出 Extra 为空或 Using where，必须触发回表
```

在 B+ 树存储模型中：
```text
+-------------------------------------------------------------+
| 二级索引叶子节点: [ key1 键值 | 主键 ID ]                      |
| (无需回表，直接从二级索引页读取内存数据流式返回) -> Using index    |
+-------------------------------------------------------------+
                              |
                              v 需要查询其他列
+-------------------------------------------------------------+
| 聚簇索引叶子节点: [ 主键 ID | 事务ID | 回滚指针 | 完整行字段数据... ]|
| (必须根据主键 ID 进行磁盘随机 I/O 回表)                         |
+-------------------------------------------------------------+
```

`Using index` 是高并发系统中最推崇的优化状态，避免了昂贵的聚簇索引随机回表 I/O。

#### Using index condition：索引条件下推（ICP）

这是 MySQL 5.6 引入的划时代的重磅优化特性——**索引条件下推（Index Condition Pushdown，ICP）**。

```sql
EXPLAIN SELECT * FROM s1 WHERE key1 > 'z' AND key1 LIKE '%a';
```

在这个 SQL 中，`key1 > 'z'` 可以利用 B+ 树做范围检索，但随后的 `key1 LIKE '%a'` 因为以通配符 `%` 开头，无法走索引树层级快速查找。优化器在 `Extra` 中会标注：`Using index condition`。

我们对比 ICP 开启前后的底层机理差异：

```text
没有 ICP (传统做法):
[二级索引] 找出满足 key1 > 'z' 的 382 个主键 
    --> 立即逐一回表 (触发 382 次聚簇索引查找) 
    --> [Server 层] 过滤 key1 LIKE '%a' 
    --> 最终只剩 3 行 (白白浪费 379 次回表 I/O!)

开启 ICP (现代做法):
[二级索引] 找出满足 key1 > 'z' 的候选条目
    --> [存储引擎内部] 直接利用索引条目里的 key1 过滤 key1 LIKE '%a'
    --> 淘汰 379 条不符合项，只剩下 3 个有效主键
    --> 仅对这 3 个主键进行回表取全列 (回表次数骤降到 3 次!)
```

读图说明：ICP 将原本属于 Server 层负责的过滤条件，直接“下推”到了存储引擎层。凡是索引中已经包含的列，即使无法利用树形做二分快速定位，也先在引擎层做一遍内存过滤，筛掉绝大多数不合格行之后再去回表，极大地节省了磁盘 I/O。

#### Using join buffer (Block Nested Loop)

当进行多表连接时，如果被驱动表的关联条件上没有索引，MySQL 无法走索引等值查找，只能采用基于块的嵌套循环连接算法（Block Nested Loop）。

此时 MySQL 会在内存中专门划拨一块名为 `join buffer` 的连接缓冲区，用来暂存驱动表的数据行，然后整块与被驱动表进行批量比对。

> **提示**：看到 `Using join buffer`，说明连接条件由于缺失索引已经退化为低效的内存穷举匹配。调优手段只有一个：**立刻在被驱动表的连接字段上建立合适的索引**。

#### Not exists：外连接反连接优化

在使用左外连接（`LEFT JOIN`）且 `WHERE` 子句中包含“要求被驱动表的非空列为 NULL”的条件时（常用于求差集反选），优化器会利用该主键不为 NULL 的物理特性进行反向剪枝：一旦在被驱动表中找到第一条匹配记录，就立即停止对被驱动表的继续扫描，此时 `Extra` 显示为 `Not exists`。

#### Using union(...)：索引合并并集

对应上一讲提到的 `type = index_merge`。当单表查询中使用 `OR` 运算符连接两个独立的单列索引时：

```sql
EXPLAIN SELECT * FROM s1 WHERE key1 = 'a' OR key3 = 'a';
```

`Extra` 会显示：`Using union(idx_key1,idx_key3); Using where`。说明优化器分别通过两个单列索引树查出主键集，在内存中完成主键并集去重后，再统一执行回表。

#### Zero limit

当 SQL 末尾显式写了 `LIMIT 0` 时出现：
```sql
EXPLAIN SELECT * FROM s1 LIMIT 0;
```
优化器识别到业务调用方压根不需要任何数据行，直接做短路跳过处理。

#### Using filesort：内存/磁盘文件排序（危险警报！）

当 SQL 包含 `ORDER BY` 操作，而排序字段无法借由现有索引的既有顺序直接输出时，MySQL 就会被迫在内存（Sort Buffer）或者超出内存限制后借用磁盘临时文件进行额外的排序计算。这种排序方式统称为**文件排序（filesort）**。

```sql
-- 1. 能直接利用索引的天然有序性
EXPLAIN SELECT * FROM s1 ORDER BY key1 LIMIT 10;
-- 输出 Extra: 空 (索引本身在叶子节点链表中就是单调递增的，无需额外排序)

-- 2. 无法利用索引，被迫进行文件排序
EXPLAIN SELECT * FROM s1 ORDER BY common_field LIMIT 10;
-- 输出 Extra: Using filesort
```

> **易错点**：`Using filesort` 并不一定意味着“生成了磁盘文件”。如果待排序数据量小于系统参数 `sort_buffer_size`，排序完全在内存中进行；只有当数据量超过缓冲区上限时，才会切片落盘到临时文件做归并排序。但无论哪种，其 CPU 和内存消耗都远高于直接读取索引。
> **调优准则**：线上核心高频查询一旦出现 `Using filesort`，必须优先考虑通过建立联合索引或单列索引来承接 `ORDER BY` 的排序需求。

#### Using temporary：内部临时表（严重性能杀手！）

当查询中包含 `DISTINCT`、`GROUP BY`、`UNION` 等操作，且相关列无法利用索引维护好的有序分组状态时，MySQL 必须在底层隐式创建内部临时表来累加、暂存和比对数据。

```sql
-- 1. 无索引字段分组：被迫创建临时表并触发文件排序
EXPLAIN SELECT DISTINCT common_field FROM s1;
-- 输出 Extra: Using temporary; Using filesort

-- 2. 利用索引直接完成分组与去重
EXPLAIN SELECT DISTINCT key1 FROM s1;
-- 输出 Extra: Using index (直接从索引树走覆盖去重，开销极小)
```

> **结论**：建立与维护内部临时表涉及大量的内存分配，当数据量膨胀超出限制时还会转为磁盘临时表，其 I/O 成本极为高昂。在生产环境中，看到 `Using temporary; Using filesort` 组合出现，通常意味着该接口存在巨大的慢查询风险，应立即针对分组字段补充索引。

### EXPLAIN 工具的局限性与认知边界

`EXPLAIN` 是我们排查和治理慢 SQL 最常用的利器，但工具皆有其边界。我们在使用执行计划时，必须清醒认知到它的四个固有局限：

1. **不感知任何数据缓存状态**：
   `EXPLAIN` 评估的是一条 SQL 在理论物理架构下的访问方法与成本估算，它完全不考虑当前数据页是已经缓存在 InnoDB 的 Buffer Pool 中，还是需要从物理固态硬盘里冷读。
2. **不展现优化器的决策推导过程**：
   `EXPLAIN` 呈现给我们的是优化器最终选定的“既定事实”。如果优化器在三个索引中挑了索引 A，为什么不选索引 B 和 C？内部的 I/O 成本与 CPU 成本到底各算出了几点几？这些决策心智模型无法通过普通的 `EXPLAIN` 获知（需要借助后续的 `Optimizer Trace` 工具）。
3. **无法获知触发器、存储过程与 UDF 的动态影响**：
   如果 SQL 触发了底层存储过程、触发器或用户自定义函数（UDF），这些程序性构件在运行期产生的隐式开销与锁竞争，在 `EXPLAIN` 静态分析中是完全失真的。
4. **统计信息均为采样估算，非精确物理数字**：
   `rows` 和 `filtered` 是基于系统数据字典采样得出的概率分布估算值，并非实际运行时的真实条目数。不能将 `rows` 的数值直接等同于实际执行返回的记录数。

### JSON 格式与执行计划成本（Cost）模型拆解

#### 为什么必须掌握 JSON 格式？

在传统表格格式中，最大的痛点在于**缺失了衡量执行计划好坏的最核心属性——成本（Cost）**。

MySQL 的优化器本质上是一个“基于成本的优化器（Cost-Based Optimizer, CBO）”。面对同一条复杂 SQL，优化器内部可能会推演很多种执行方案（例如方案 1 走索引 A、方案 2 走索引 B、方案 3 走多表连接、方案 4 走物化表）。优化器最终之所以挑中某一个方案，是因为经过精密数学模型计算后，判定该方案的综合成本值最低。

但在传统格式中，我们只能看到被选中的既定事实，完全看不到具体的成本数字。而通过指定 `FORMAT=JSON`，MySQL 会将所有内部估算的 I/O 成本、CPU 评估成本完整倾泻出来。

#### 语法与字段映射对应关系

使用 JSON 格式非常简单，只需在 `EXPLAIN` 与待分析的 SQL 语句之间插入 `FORMAT=JSON`：

```sql
EXPLAIN FORMAT=JSON 
SELECT * FROM s1 INNER JOIN s2 ON s1.key1 = s2.key1 
WHERE s1.common_field = 'a';
```

JSON 格式中的键值与传统表格字段存在着一一映射关系：

```text
传统表格字段                JSON 键名 (Key)
--------------------------------------------------------------
id                          -->  select_id
table                       -->  table_name
type                        -->  access_type
possible_keys               -->  possible_keys
key                         -->  key
key_len                     -->  key_length
ref                         -->  ref
rows                        -->  rows_examined_per_scan
rows * filtered 派生值       -->  rows_produced_per_join
filtered                    -->  filtered
Extra 中的 Using where 等   -->  attached_condition
```

#### 成本信息 cost_info 深度剖析

在 JSON 输出中，每一个表以及顶层节点下都会出现一个极其核心的结构体：`cost_info`。我们以上述连接查询的 JSON 输出为例，拆解其内部的成本核算：

```json
{
  "query_block": {
    "select_id": 1,
    "cost_info": {
      "query_cost": "1360.08"
    },
    "nested_loop": [
      {
        "table": {
          "table_name": "s1",
          "access_type": "ALL",
          "rows_examined_per_scan": 9895,
          "rows_produced_per_join": 989,
          "filtered": "10.00",
          "cost_info": {
            "read_cost": "914.85",
            "eval_cost": "98.90",
            "prefix_cost": "1013.75",
            "data_read_per_join": "1M"
          },
          "attached_condition": "((`atguigudb1`.`s1`.`common_field` = 'a') and (`atguigudb1`.`s1`.`key1` is not null))"
        }
      },
      {
        "table": {
          "table_name": "s2",
          "access_type": "ref",
          "possible_keys": ["idx_key1"],
          "key": "idx_key1",
          "key_length": "303",
          "ref": ["atguigudb1.s1.key1"],
          "rows_examined_per_scan": 1,
          "rows_produced_per_join": 989,
          "filtered": "100.00",
          "cost_info": {
            "read_cost": "247.43",
            "eval_cost": "98.90",
            "prefix_cost": "1360.08",
            "data_read_per_join": "1M"
          }
        }
      }
    ]
  }
}
```

我们要重点理解 `cost_info` 里的三个核心指标：

1. **`read_cost`（读取成本）**：
   对于驱动表 `s1`，`read_cost` 主要由两部分累加而成：
   - 扫描聚簇索引数据页产生的 **物理 I/O 成本**；
   - 扫描出来之后，由于不满足过滤条件而被剔除的废弃数据行所消耗的 **CPU 比较成本**，即：
     $$\text{rows} \times (1 - \text{filtered}) \times \text{单行比较 CPU 权重}$$
2. **`eval_cost`（求值评估成本）**：
   代表经过条件筛选后，满足过滤条件的有效数据行在准备输出或向下一阶段传递时所消耗的 CPU 评估成本：
   $$\text{eval_cost} = \text{rows} \times \text{filtered} \times \text{单行评估 CPU 权重}$$
   在上述案例中，$9895 \times 10\% = 989.5$ 行，对应 CPU 成本为 98.90。
3. **`prefix_cost` 与 `query_cost`（累积前缀成本与总成本）**：
   - 驱动表 `s1` 自身单表处理的总成本为：
     $$\text{prefix_cost} = \text{read_cost} + \text{eval_cost} = 914.85 + 98.90 = 1013.75$$
   - 进入被驱动表 `s2` 后，`s2` 处理自身的 `read_cost`（247.43）和 `eval_cost`（98.90）总和约为 346.33；
   - 整个多表连接的全局总成本 `query_cost`，就是将驱动表的前缀成本与被驱动表自身成本彻底累加：
     $$\text{query_cost} = 1013.75 + 346.33 = 1360.08$$

此外，`data_read_per_join` 指明了在当前关联步骤下单次连接预估读取的原始数据体量（例如 1M），为内存缓冲区的配置提供了直观参考。

### TREE 格式与可视化图表输出

#### TREE 格式（树状层次结构）

在 MySQL 8.0 及以上版本中，引入了 `FORMAT=TREE` 输出选项：

```sql
EXPLAIN FORMAT=TREE 
SELECT * FROM s1 INNER JOIN s2 ON s1.key1 = s2.key1 
WHERE s1.common_field = 'a';
```

执行后的输出效果如下：

```text
-> Nested loop inner join  (cost=1360.08 rows=989)
    -> Filter: ((s1.common_field = 'a') and (s1.key1 is not null))  (cost=1013.75 rows=989)
        -> Table scan on s1  (cost=1013.75 rows=9895)
    -> Index lookup on s2 using idx_key1 (key1=s1.key1)  (cost=0.25 rows=1)
```

读图说明：TREE 格式以清晰的缩进树表达了自底向上的算子调用链条：
1. 底层首先对 `s1` 进行全表扫描（`Table scan on s1`），成本 1013.75；
2. 上层对全表扫描的结果应用过滤条件（`Filter`），将 9895 行筛至 989 行；
3. 最外层执行嵌套循环连接（`Nested loop inner join`），内部驱动对 `s2` 的索引查找（`Index lookup on s2`），最终汇总总成本为 1360.08。

相比复杂的 JSON 嵌套，TREE 格式在保留算子成本和数据流向的同时，大大提升了在终端阅读的可读性。

### SHOW WARNINGS：探查查询优化器的 SQL 重写实录

很多工程师在做 SQL 调优时，常常会遇到“执行计划的结果与我手写的 SQL 语义完全对不上”的困惑。这往往是因为 MySQL 查询优化器在生成执行计划之前，对原始 SQL 进行了一轮深度的**等价改写与规范化重构**。

我们要想亲眼目睹优化器真正执行的“重写 SQL”，必须借助 `SHOW WARNINGS`。

#### 使用规则与返回规范

> **操作铁律**：`SHOW WARNINGS` **必须紧跟在 `EXPLAIN` 语句之后立刻执行**！如果中间执行了任何其他 SQL 语句，上一次执行计划的上下文就会被立即冲刷覆盖。

```sql
-- 步骤 1：执行 EXPLAIN
EXPLAIN SELECT ...;

-- 步骤 2：紧跟执行 SHOW WARNINGS（在命令行终端建议追加 \G 纵向展示）
SHOW WARNINGS\G;
```

执行后将输出三列信息：
- `Level`：通常为 `Note`（提示级别）；
- `Code`：状态码，最常见的是 `1003`；
- `Message`：**优化器经过词法解析、规则改写、常量折叠与半连接扁平化后，最终实际采用的 SQL 结构**。

#### 经典实战一：外连接消除与驱动表逆转

看下面这个左外连接案例：

```sql
EXPLAIN 
SELECT * FROM s1 
LEFT JOIN s2 ON s1.key1 = s2.key1 
WHERE s2.common_field IS NOT NULL;
```

按照我们的书写认知，`s1 LEFT JOIN s2` 说明 `s1` 必须作为主表保留全部数据，`s1` 理应是驱动表。但执行 `EXPLAIN` 后，第一行赫然出现的竟然是 `s2`，第二行才是 `s1`！

此时立刻执行 `SHOW WARNINGS\G`，观察返回的 `Message`：

```sql
/* select#1 */ 
select `atguigudb1`.`s1`.`id` AS `id`,
       `atguigudb1`.`s1`.`key1` AS `key1`,
       ...
from `atguigudb1`.`s2` 
join `atguigudb1`.`s1` 
where ((`atguigudb1`.`s1`.`key1` = `atguigudb1`.`s2`.`key1`) 
  and (`atguigudb1`.`s2`.`common_field` is not null))
```

真相瞬间大白：
因为我们在 `WHERE` 条件中显式约束了 `s2.common_field IS NOT NULL`，这导致原本左外连接中“当 `s2` 无法匹配时补 NULL 保留”的语义彻底失效——哪怕补了 NULL，也会被 `WHERE` 条件无情过滤掉！
优化器敏锐地识别到了这一点，判定该查询在数学语义上与内连接（`INNER JOIN`）严格等价，直接把 `LEFT JOIN` 改写成了 `JOIN`。而一旦变成了内连接，优化器就拥有了自由调换驱动表顺序的权力；评估发现以数据量更小的 `s2` 作为驱动表综合成本更低，于是果断逆转了表的执行顺序。

#### 经典实战二：IN 子查询扁平化为多表连接

再来看一个典型的子查询场景：

```sql
EXPLAIN 
SELECT * FROM s1 
WHERE key1 IN (
    SELECT key1 FROM s2 WHERE key2 = 'a'
);
```

直觉上，外层一个 `SELECT`，内层一个 `SELECT`，执行计划应该分配 `id=1` 和 `id=2`。但实际运行后，控制台显示两行记录的 `id` **全部都是 1**！

紧接着执行 `SHOW WARNINGS\G` 查看 `Message`：

```sql
/* select#1 */ 
select `atguigudb1`.`s1`.`id` AS `id`,
       `atguigudb1`.`s1`.`key1` AS `key1`,
       ...
from `atguigudb1`.`s2` 
join `atguigudb1`.`s1` 
where ((`atguigudb1`.`s1`.`key1` = `atguigudb1`.`s2`.`key1`) 
  and (`atguigudb1`.`s2`.`key2` = 'a'))
```

从 `Message` 可以清晰看到：原本嵌套在 `IN` 内部的子查询，被优化器彻底“压平（Flattening）”，直接重构成了一个等价的由 `s2` 和 `s1` 组成的多表内连接！既然在执行期已经被拉平成了一个单层连接，整个大查询中就只剩下一个统一的逻辑主体，因此两张表的 `id` 均为 1。

> **注意**：`SHOW WARNINGS` 输出的 `Message` 只是优化器内部推演重构的抽象语法逻辑表示，里面夹杂着数据库前缀、内部函数修饰及别名映射，**严禁直接将其复制粘贴到生产代码中执行**。它的核心价值在于帮助我们看清优化器的真实执行意图，验证自己的 SQL 改写假设是否与优化器的实际决策同频。

## 140-trace分析优化器执行计划与Sys schema视图的使用
> 对应分集：P140 | 原始标题：《140-trace分析优化器执行计划与Sys schema视图的使用》

在前面的章节中，我们系统搭建了一套慢查询定位与性能分析的工具链：先通过慢查询日志（Slow Query Log）抓出拖垮性能的低效 SQL，再借助 `SHOW PROFILE` 洞察查询在生命周期各阶段的毫秒级耗时分布，接着用 `EXPLAIN` 详细解读单表访问路径与联合索引利用率，并用 `SHOW WARNINGS` 验证优化器内部的改写逻辑。

但在讲到 `EXPLAIN` 的局限性时，我们留下了一个悬而未决的“黑匣子”难题：
- `EXPLAIN` 只能告诉我们优化器最终挑选了哪个方案，却从未解释它**为什么选它、为什么淘汰其他候选索引**；
- 当表上存在两个以上的索引时，优化器在内部对每种方案到底估算了多少 I/O 成本与 CPU 成本？它是基于怎样的演算路径做出取舍的？
- 除此之外，面对日常系统巡检，难道我们只能在 `performance_schema` 和 `information_schema` 那些动辄上百张、结构生僻、没有单位换算的底层元数据表里“盲人摸象”吗？

为了解决这两个痛点，MySQL 分别推出了两大杀器：一个是 MySQL 5.6 引入的优化器黑匣子记录仪——`optimizer_trace`；另一个则是官方精心封装的开箱即用性能监控库——`sys` 模式视图。本讲我们将深入实战这两个工具，补齐性能分析知识拼图的最后一块。

---

### optimizer_trace：追踪优化器的决策链路

> **定义**：`optimizer_trace` 是 MySQL 5.6 引入的深度追踪功能。它能将优化器在解析、重写、代价估算以及方案比对过程中的完整心智决策，全程记录为结构化的 JSON 文档，并暂存在 `information_schema.OPTIMIZER_TRACE` 系统表中。

通过 `optimizer_trace`，我们不仅能看到优化器重写 SQL 的每一个中间步骤，更能看清它对不同索引的估算行数、数据页成本以及最终决策的裁决依据。

#### 开启追踪与参数调优机制

由于生成追踪信息会消耗额外的内存与 CPU 开销，MySQL 默认将该功能置于关闭状态。我们必须在当前会话（Session）中显式开启：

```sql
-- 1. 开启优化器追踪，并开启 JSON 末尾标记以提升可读性
SET optimizer_trace = 'enabled=on,end_markers_in_json=on';

-- 2. 调大追踪信息的最大内存配额（默认通常较小，极易被截断）
SET optimizer_trace_max_mem_size = 1048576; -- 设置为 1MB (根据查询复杂度可设 10MB)
```

> **易错点**：为什么要调大 `optimizer_trace_max_mem_size`？
> 即使是一条看似普通的单表范围查询，优化器内部推演产生的 JSON 追踪信息也往往长达数百行。如果内存上限维持默认偏小的值，超出部分就会被底层直接截断丢弃，导致最关键的代价比对信息丢失。因此在开启追踪前，务必先将该内存参数适当调大。

#### 标准操作工作流（四步闭环）

在生产排查时，必须严格遵循四步闭环操作，避免产生全局性能副作用：

```sql
-- 步骤 1：在当前会话开启 trace 并设置内存
SET optimizer_trace = 'enabled=on,end_markers_in_json=on';
SET optimizer_trace_max_mem_size = 1048576;

-- 步骤 2：执行需要深度分析的目标 SQL
SELECT * FROM student WHERE id < 10;

-- 步骤 3：立即从系统表中提取最新一条追踪记录
SELECT * FROM information_schema.OPTIMIZER_TRACE\G;

-- 步骤 4：排查完毕后，立即关闭 trace 释放资源
SET optimizer_trace = 'enabled=off';
```

#### 追踪结果集的四大组成部分拆解

执行查询后，`OPTIMIZER_TRACE` 表将输出包含四列的关键记录：

```text
*************************** 1. row ***************************
                            QUERY: SELECT * FROM student WHERE id < 10
                            TRACE: { ... JSON 核心追踪报文 ... }
MISSING_BYTES_BEYOND_MAX_MEM_SIZE: 0
          INSUFFICIENT_PRIVILEGES: 0
```

1. **`QUERY`**：记录本次追踪所针对的目标原始 SQL 文本。
2. **`TRACE`**：全量 JSON 报文，也是最核心的数据体。它自顶向下严格对应了优化器的三大执行生命周期：
   - `join_preparation`（准备阶段）：包含常量折叠、派生表展开、初步语法树重构；
   - `join_optimization`（优化核心阶段）：包含 `condition_processing`（条件规范化）、`table_dependencies`（分析表依赖关系）、`rows_estimation`（单表各候选索引扫描行数与成本精算，记录 `considered_execution_plans`）、`attaching_conditions_to_tables`（确定条件下推）；
   - `join_execution`（执行阶段）：记录最终确定的调用算子执行计划。
3. **`MISSING_BYTES_BEYOND_MAX_MEM_SIZE`**：因超出内存阈值而被截断丢弃的字节数。如果该数值为 0，说明整份追踪报文完整无缺；若大于 0，说明末尾已被截断，必须进一步调大 `optimizer_trace_max_mem_size` 后重试。
4. **`INSUFFICIENT_PRIVILEGES`**：权限不足指示位。取值为 0 表示当前用户拥有完整查看权限；若取值为 1，则表示由于权限不足（例如执行了以 `SQL SECURITY DEFINER` 创建的视图或存储过程），系统自动隐匿了 `TRACE` 内容。

### sys schema：开箱即用的官方性能诊断视图

在日常维护中，我们不可能遇到任何性能波动都去翻底层源码或手撕 trace JSON。为了实现高效的数据库日常体检，官方在底层构建了一套极具实战价值的运维框架。

#### 架构演进与设计定位

长期以来，MySQL 的运行时状态主要分散在两大系统库中：
- `information_schema`：提供数据字典、表结构与静态元数据；
- `performance_schema`：提供锁等待、事件消耗、I/O 吞吐等底层动态插桩数据。

然而，`performance_schema` 的原始表结构极其生僻，存储的数字往往以微秒甚至皮秒（Picoseconds）为单位，且缺乏多表关联逻辑。

为了让普通开发者和 DBA 从繁重的报表拼接中解脱出来，MySQL 从 5.7 开始官方内置了 **`sys schema`**。它通过封装一组预定义的视图、存储过程与函数，将底层的原始遥测指标归纳为直观易懂、自带人类可读单位（如秒、MB）的诊断报表。

```text
+-------------------------------------------------------------+
|                     sys schema 业务级诊断视图                |
|           (提供人类可读单位、自动关联汇总、即查即用)            |
+-------------------------------------------------------------+
                              |
        +---------------------+---------------------+
        v                                           v
+-------------------------------+   +-------------------------------+
|     performance_schema        |   |      information_schema       |
|   (底层动态运行时性能埋点数据)  |   |    (静态数据字典与元数据定义)   |
+-------------------------------+   +-------------------------------+
```

#### 核心实战场景与常用诊断查询

`sys` 库中的视图非常丰富，在实际生产中我们完全无需死记硬背，只需针对高频场景挑出对应的利器直接调用即可：

##### 场景一：索引健康度治理（冗余索引与未利用索引）

表上索引绝非越多越好。无用和重复的索引不仅霸占宝贵的内存，更会在每次 `INSERT/UPDATE/DELETE` 时引发繁重的 B+ 树维护分裂与磁盘 I/O。

1. **排查冗余索引**：
   ```sql
   SELECT * FROM sys.schema_redundant_indexes;
   ```
   **经典实战案例**：
   假设在表 `student_info` 上，我们之前定义了一个单列索引 `idx_create_time (create_time)`；后续为了满足联合查询，又定义了一个联合索引 `idx_ct_sid (create_time, student_id)`。
   通过 `sys.schema_redundant_indexes` 查询，系统会立即报警提示 `idx_create_time` 属于冗余索引。
   原因非常清晰：因为联合索引天然遵循最左前缀原则，所有能使用 `idx_create_time` 单列过滤的查询，完全可以无缝被 `idx_ct_sid` 承接。保留旧的单列索引除了徒增维护开销外毫无益处，应立即执行 `DROP INDEX` 删除。

2. **排查从未被业务使用过的索引**：
   ```sql
   SELECT * FROM sys.schema_unused_indexes;
   ```
   在系统上线稳定运行数周后，执行该查询。如果发现某些非主键、非唯一约束的索引其命中使用计数始终为 0，说明业务查询根本没有用到该索引，可以将其列入清理清单。

##### 场景二：表物理访问与 Buffer Pool 内存排查

1. **全表物理 I/O 访问热度统计**：
   ```sql
   SELECT * FROM sys.schema_table_statistics;
   ```
   直观呈现各个业务表的读写行数总和及总耗时排行。排在最前列的高频访问表，就是我们重点需要通过缓存（如 Redis）或建立覆盖索引进行架构减负的目标。

2. **排查哪些大表吃光了 InnoDB Buffer Pool 内存**：
   ```sql
   SELECT * FROM sys.innodb_buffer_stats_by_table;
   ```
   直接展示缓冲池中各表数据页的占用比例与容量（自带 `MB/GB` 单位），快速定位是否存在突发大表全表扫描将热点业务数据“冲刷”出内存的恶性事件。

##### 场景三：低效高危 SQL 模式监控

1. **全系统 SQL 执行耗时与频率全局排行**：
   ```sql
   SELECT * FROM sys.statement_analysis;
   ```
   将参数参数化归一化后，列出执行频次最高、平均耗时最长、甚至返回全表扫描行数最大的 SQL 模板，是日常架构巡检的首要看板。

2. **监控频繁触发全表排序与临时表的 SQL**：
   结合 `sys.statements_with_sorting` 和 `sys.statements_with_temp_tables`，秒级抓出哪些线上接口正在后台频繁引发 `Using filesort` 和 `Using temporary`。

##### 场景四：行锁阻塞与死锁定点排查

当线上并发事务突然卡顿、接口响应时间暴增时，往往发生了严重的行级行锁阻塞：

```sql
SELECT * FROM sys.innodb_lock_waits;
```

该视图会将“谁持有锁（Blocking 事务及 SQL）”与“谁在苦苦等待锁（Blocked 事务及 SQL）”直接配对列出，DBA 可以直接拿到对应的线程 ID 执行 `KILL` 终止源头阻塞事务，迅速恢复业务可用性。

#### 生产环境调用戒律与注意事项

`sys` 模式下的视图功能极其强悍，但在实际生产环境中必须严格遵守一条铁律：

> **警示戒律**：**严禁在生产环境高并发业务高峰期，以高频轮询（如每秒一次）的方式自动化扫描 `sys` 视图！**
> `sys` 视图底层基于复杂的嵌套查询和跨内存表汇聚统计。频繁调用它自身就会消耗不可忽视的 CPU 和内存资源，甚至在底层数据字典表上引发锁竞争。正确的姿势是将相关巡检脚本安排在夜间低峰期运行，或者在排查突发故障时由工程师手动定点触发。

```text
       |
       v

       v
```
