### 数据库调优的四个维度

先泛泛地看一遍：到底有哪些维度可以支撑我们去做数据库调优。这里只做一个整体交代，后面还有一章专门做汇总。

```text
数据库调优的四个方向
├── 索引与 SQL 编写    索引失效、没建索引、没充分利用索引 → 建索引 + 遵守编写准则（本讲重点）
├── 关联查询           JOIN 的表一般不超过三张；反范式化设计减少 JOIN（下一章）
├── 服务器与参数       my.cnf / my.ini：缓存大小、线程数（下下章细讲）
└── 数据量与高并发     分库分表、主从复制、读写分离，分散服务器压力（后面的篇章）
```

第一个维度是索引失效。索引一旦失效，查询效率一般情况下就会差一些。失效了、或者没有充分利用到索引，怎么办？如果没有利用索引、或者压根没建索引，那就去建立索引；如果是索引失效，那多半是我们 SQL 的编写方式有问题，去注意相应的编写准则就可以了——这是本讲后面几节的主要内容。

第二个维度是关联查询，也就是 JOIN 太多。多表查询免不了要用 JOIN，但一般最好不要超过三张表，超过以后性能会受到影响；一旦发现 JOIN 的表过多，就要适当地做 SQL 优化。下一章讲范式的时候还会提到一条路：做反范式化的设计，增加必要的冗余，把过多的 JOIN 行为消掉。

第三个维度是服务器调优和各项参数的设置，比如缓存区域的大小、线程数的多少，通过调整 my.cnf 或者 my.ini 来改；具体改哪个文件，看我们的 MySQL 服务器搭在什么平台上。这一章只会涉及一部分参数，更多的参数留到后面那章去讲。

第四个维度是数据过多。如果 SQL 调优已经做到极限、实在优化不动了，但高并发的访问压力还在，怎么办？那就上更多的服务器：分库分表、主从复制、读写分离，用这些办法把服务器压力分散开。这一块放在后面的篇章里讲。

关于数据库调优的知识点，应该说非常分散。不同的数据库管理系统，比如 MySQL、Oracle、SQL Server，底层设计的原理不一样，具体的调优方式也会不同；不同的公司、不同的职位、不同的项目里遇到的问题也不尽相同。所以我们把范围收在 MySQL 上，分成三章来讲：本章讲索引优化和查询优化，下一章讲范式、E-R 模型以及反范式，再往后关注其他调优策略。

### 物理查询优化与逻辑查询优化

SQL 查询优化的技术有很多。面试的时候也可以先把一个大观点抛出去：大处着眼，小处着手。大处着眼是说，从大方向上讲，查询优化主要有两大方向——一个是物理查询优化，一个是逻辑查询优化，这两个词前面讲某一章的时候提到过。

物理查询优化，可以理解为实打实的物理磁盘层面：我们创建一个索引，对应的 ibd 文件当中就会多出索引占用的空间。它主要靠索引和表连接方式来做优化，这一块是重点要掌握的，尤其是索引。

逻辑查询优化就仁者见仁、智者见智了。不同的人 SQL 开发经验不同，写出来的 SQL 质量也不一样——就像用编程语言实现同一个算法，不同的人写出来差别很大。好的 SQL 查询效率高，差一些的查询效率就低。我们可以通过 SQL 等价变换的方式提升 SQL 的质量；另外 MySQL 的查询优化器也会对我们的 SQL 做优化和重写，上一章就提到过：我们写的是一个子查询，优化器有可能给我们转换成内连接的方式。

```text
SQL 查询优化
├── 物理查询优化   索引、表连接方式          ← 重点掌握，尤其是索引
└── 逻辑查询优化   SQL 等价变换、优化器重写   ← 靠 SQL 开发经验积累
```

这就是一个泛泛的概述。下面开始动手。

### 索引的作用与各存储引擎的索引结构

这一部分以「索引在表里起不起作用」为突破口来讲。

想提高查询效率，最有效的方式就是设置合理的索引。通过索引，我们能够快速地定位到表中的某条记录：这条记录存在叶子节点的页面当中，我们直接把那个页面加载到内存里就可以了，从磁盘做一次加载即可。反过来，如果没有使用索引，就需要扫描表中的所有记录——所有记录存放在不同的页当中，这些页要是还没有在内存里加载，我们还得把它们全都加载到内存中才可以，这是极其崩溃的一件事情。所以在大多数情况下，尤其是表的数据量非常庞大的时候，查询一定要考虑用索引。

这一讲的讲解主要以 B+ 树来进行。InnoDB、MyISAM 默认用的都是 B+ 树；空间类型用的是 R 树；Memory 默认支持的是以哈希算法为主的哈希索引。另外，MyISAM 里面数据和索引是分离的，不存在聚簇索引这个概念，所以这一讲的讲解还是以 InnoDB 为主。

### 优化器的成本开销与索引选择

用不用索引，最终还是优化器说了算。SQL 写完了，字段上确实也有索引，但优化器一算，发现不用索引的成本可能更低，它还真就可能不用。

> **提示**：遇到「明明建了索引，结果还不如不建」的情况，要反过来想一想：是不是索引设置本身有问题，才让优化器把它放弃了。

我们讲这么多案例，目的就是从案例里发现优化器的一些规则。那优化器是基于什么做选择的？基于成本开销（cost），它不是基于规则式的，也不是基于语义式的。

这里的开销不是时间长度的意思。上一章讲 explain 的时候说过，explain 有好几种格式，其中 JSON 格式主要呈现给我们的就是成本开销：外层查询算出一个数值，内层查询算出一个数值，两者相加就是总成本——外层那个数值加上内层那两个数值，一共得到最外层上面写的那个数值。里面涉及 read_cost 和 eval_cost，这两个值有具体的计算公式（上一章提过），公式里用到表中的行数以及 filtered 百分比。这个数值的单位不是时间，你可以理解成 1。

```text
查询的成本开销（explain 的 JSON 格式中呈现）
├── 外层查询
│   ├── read_cost   读取记录的成本
│   └── eval_cost   评估过滤条件的成本（涉及表行数、filtered 百分比）
└── 内层查询
    ├── read_cost
    └── eval_cost

总成本 = 外层(read_cost + eval_cost) + 内层(read_cost + eval_cost)   ← 单位不是秒，可理解成 1
```

另外，SQL 语句是否使用索引，跟数据库的版本、数据量、数据的选择度都有关系。

先说选择度。比如 `select *`，我们一直强调要尽量避免在业务场景中使用它。

> **提示**：`select *` 会把整行的所有列都要回来。哪怕二级索引帮你定位到了记录，也得回表把别的列补齐；如果只 select 索引里已经有的字段，就不用再回表查整张表的数据了。索引会不会被选中，跟这种代价算得清楚与否直接相关。

再说数据量。同样是查一张表：一种选择是把整张表的数据都查出来，另一种是加上 `limit 10` 只查十条。你会发现，在不加 limit 的时候，某个字段上虽然建了索引，优化器最后可能并没有选这个索引，而是让 explain 的 type 字段变成了 all——也就是全表扫描。它的判断是：我用了你那个索引，前面还写着 `select *`，用了索引还得回表做全表查询，那还不如干脆直接全表查一遍效率更高，于是反而不走索引了。但要是加上 `limit 10`，优化器一核算：全表扫描可能要翻一千条、一万条，而你只要十条，行，那我就用一下你这个索引，成本可能更低。

这也解释了我在造表的时候为什么把数据量造得不小，一整就是十万级别以上：数据量的多少对优化器的选择是有影响的；另一方面，下面演示用索引和不用索引的时候，也想看出查询时间的差距，数据量稍微大一点，效果能明显一些。

### 全值匹配规则与联合索引

下面看具体规则。我一共列了 11 条，相应的一些规则做了合并，大方向上就是这 11 条，我们一条一条来。第一条：全值匹配我最爱。

演示针对的都是 student 表。先看一眼这张表：id 是主键，除此之外的其他字段只有 not null、null 这类约束，没有别的索引。

在还没有创建新索引的情况下，用 explain 看针对 age 的查询：没有任何索引可用，type 是 all，key 也是 null；另外两条语句同样道理，都没有索引可用，也没有 using index 之类的字样。

接着执行一条带三个条件的查询，条件是三个字段的等值比较：

```sql
-- select 的列从略，这一条是三个字段的等值条件
select ... from student where age = 30 and class_id = 4 and name = 'abcd';
```

执行完没有查出数据，耗时也有记录。然后给表添加必要的索引，一个一个来说：

```sql
-- 第一步：只在 age 上建索引（这个索引就叫 idx_age）
create index idx_age on student(age);

-- 第二步：把 age 和 class_id 都算进来
create index idx_age_class_id on student(age, class_id);

-- 第三步：把 age、class_id 和 name 全都算进来
create index idx_age_class_id_name on student(age, class_id, name);
```

建索引的过程本身是要花时间的，底层对应的 ibd 文件也会变大——索引数据要存在里面。

第一步建完再 explain，这条语句就用上索引了，用上的恰好是刚创建的 idx_age，因为 where 里面出现了 age。key_len 是 5，因为 age 本身是 int 类型（4 字节），又允许为 null（再加 1 字节）。这时候执行那条 select，时间确实变少了：0.022 秒。

第二步把 age 和 class_id 都算进来。建完再 explain，此时表上有两个索引，优化器选了稍微长一点的那个，把 age 和 class_id 都算上了。理论上来讲，执行 select 会更快点，实测是 0.001 秒，效果确实出来了。

为什么两个索引之间它选了长的那个？因为联合索引构建的 B+ 树是先按照 age 排序、再按照 class_id 排序的。如果只用 age 那个索引，找到 age=30 之后，非叶子节点当中没有 class_id，那剩下的条件怎么办？只能回表去找主键了，花的时间就要更多一些。而用 (age, class_id) 这个索引，在 age 相同的情况下，直接看非叶子节点里的 class_id 是不是 4 就可以了，简单一些。

第三步再把 name 也算上，建了一个更长的联合索引，然后执行 select：时间好像反而更长一点，0.002 秒；explain 也是 0.001、0.002 这个量级。这已经非常小了，0.001 和 0.002 相当于没有本质区别。主要原因是：用前两个字段筛选完之后，剩下的数据量已经极小，刚才这条查询甚至根本没查到数据，所以区分不出来；如果表里有几百万条甚至几千万条数据，并且确实有这样的记录，应该能看到这条还是要更小一点。

这里也能发现，优化器帮我们选了最长的这个索引，原理和前面在两个索引里选长的那个是一样的：基于第三个索引去查，可以直接在这个索引的 B+ 树里把 name 是不是 abcd 也比出来，显然更好。

| 索引情况 | explain 里的 key | key_len | 实测查询耗时 |
| --- | --- | --- | --- |
| 不建索引 | null，type=all | — | 全表扫描 |
| 只建 age 单列索引 | age 上的索引 | 5 | 0.022 秒 |
| 再建 (age, class_id) 联合索引 | 优化器选中更长的这条 | — | 0.001 秒 |
| 再建 (age, class_id, name) 联合索引 | 优化器选中最长的那条 | — | 0.002 秒 |

> **结论**：当 where 条件都是等值比较时，把这几个字段建成一个联合索引，效率要比只建其中部分字段的索引更好；数据量越大，越能看出这个差别。

### 最佳左前缀法则

第二条叫最佳左前缀的规则。这个概念在前面讲索引的时候其实说过，这里再明确一下。

先交代一点：下面这条语句里明确不使用查询缓存，目的是实打实地看耗时——讲逻辑架构、讲查询缓存的时候说过这一点。

此时表上有几个索引（再加上主键）。看第一条语句：

```sql
-- select 的列从略，where 里是 age 和 name
explain select ... from student where age = 30 and name = 'abcd';
```

它只用上了 age 那部分索引，因为 name 上我们并没有单独建索引。再看第二条，where 里换成 class_id 或者 name，就完全用不上索引了。

这里容易有疑问：明明索引里有 class_id 和 name 啊？注意，我们联合索引当中是先写的 age，后有的 class_id，这就意味着 B+ 树里是先按 age 排序的。索引里虽然存了 class_id 和 name，但实际上是用不上的。这个数据结构是先考虑 age，age 相同了才看 class_id——你上来就 class_id，这棵树当然用不了。

```text
联合索引 (age, class_id, name)：B+ 树里的比较顺序

        先比 age        再比 class_id        最后比 name
       +---------+      +------------+      +------------+
记录 1 |  age=30 | ---> | class_id=4 | ---> | name=abcd  |
记录 2 |  age=30 | ---> | class_id=4 | ---> | name=abce  |
记录 3 |  age=30 | ---> | class_id=7 | ---> | name=aaaa  |
记录 4 |  age=31 | ---> | class_id=2 | ---> | name=bbbb  |
       +---------+      +------------+      +------------+

只有先给出 age，才能进入下一层；跳过了 class_id 直接找 name，这一层就对不上了。
```

接着看下面这一条，where 里给了 class_id、age、name 三个条件。看着是不是挺好？执行一下，用上了这个索引，跟上面那条的区别就在于我们加上了 age：它的访问方法变成了 ref，而上面用不上索引的那条是 all，效率差别比较大。

这就是所谓的最佳左前缀法则。在联合索引当中，先写谁后写谁是有严格区别的；查询里要想用上这个联合索引，必须先把左边这个字段考虑上，然后才能考虑下一个字段、再下一个字段。反过来说也成立：如果最左边的字段没有出现，而直接出现了后面某个字段，这个索引也有可能被考虑使用，但你只能用上它最前面的那一部分。必须得有左边的情况下，你再写右边的，才能整体上考虑上这个索引更多的部分。

演示到这里，我顺手把干扰的索引 drop 掉，并且用 show 看一眼剩下的索引：

```sql
drop index idx_age on student;

show index from student;
```

清掉之后，我们自己创建的索引就只剩第三个 (age, class_id, name) 了。这时候再执行一条 where 里给了 age 和 name、但没有 class_id 的语句：explain 里选的就是最后这个索引，但 key_len 只写了 5。

为什么只有 5？因为只考虑了 age——age 本身是 int 类型，4 个字节加上 1 个 null 标志，就是 5。后面明明写了 name，为什么没考虑进去？因为在这棵 B+ 树当中，age 相同的情况下，要先看 class_id，再去考虑 name；你现在都略过 class_id 了，直接去找 name，那就不合适了。所以我们只能够用到这个联合索引的一部分。

> **易错点**：使用索引的过滤条件，必须按照建立索引的顺序依次满足。一旦跳过了某个字段，它后面的字段就都无法使用了。

> **提示**：一个索引最多可以有 16 个字段，默认情况下就是 16 个。

### 主键插入顺序与页分裂

第三条叫主键的插入顺序。这一点给我们一个启示：设置主键的时候，通常都让它依次递增，而不会是一个混乱的顺序。

主要原因是在 InnoDB 当中，数据存储都要按照聚簇索引的方式去做添加。如果主键值是从小到大递增的，我们就始终在页面当中的右边做添加就可以了；右边不足的时候，再新开辟一个数据页继续添加。

但如果主键值中间有空隙——比如 8 后面空了个 9，直接就到了 10，而用户后来又把 9 插入进来：由于索引默认是升序排列的，9 就必须插到 8 和 10 之间。要是这个页恰好数据也满了，这些数据就要考虑移到下面一个页当中去，这就出现了页分裂；然后我们再把这个 9 添加到那个位置。这样一来，肯定会影响性能。

```text
页分裂（主键值中间有空隙，后插的记录要落进已满的页）

数据页 P1（已满）
+------+------+------+------+
|  6   |  7   |  8   |  10  |     ← 主键 9 缺失
+------+------+------+------+

用户后插主键 9：索引按升序排列，9 必须落在 8 与 10 之间
                |
                v
+------+------+------+------+
|  6   |  7   |  8   |  9   |     P1：9 插进来了
+------+------+------+------+
+------+------+------+
|  10  | ...  | ...  |              P2：从 P1 挪过来的记录
+------+------+------+
                          ↑ 一部分记录被移到新页，页与页之间的指针也要一并维护
```

> **定义**：页分裂，是指插入的记录需要落在已经写满的数据页上时，把该页的一部分记录挪到新分配的页里，再完成这次插入。它带来额外的写入以及页指针维护开销。

所以实际开发当中的建议是：一定要让主键是依次递增的顺序，比较好的选择就是给主键加上 auto_increment。而且 auto_increment 本身还要求你对应的这个字段得是主键或者唯一约束的字段，这一点前面也讲过了。

> **提示**：这里先肯定 auto_increment，后面讲到第 13 节的时候我还要推翻它——非核心业务的表可以考虑用 auto_increment，但如果是核心业务的表，比如淘宝当中的订单表，针对主键用 auto_increment 就不是一个很好的选择了。为什么，到时候再说。这叫否定之否定。

### 字段上的运算与函数导致索引失效

第四条：where 当中的字段上出现了运算、出现了函数。这类场景会导致索引失效，在实际开发当中是一定要小心、谨慎的点。

#### 模糊查询：like 前缀匹配与 left 函数

我写了两个 explain 来比较：两条语句作用是一样的，都是找 name 以 abc 开头的记录，区别是一个用 like 做模糊查询，另一个是在字段上用函数。最简单的想法是这两条没什么区别，都可以——从运行结果上来讲确实没区别，但从效率上来讲就有区别了。

课堂上有人会说「这个函数我不认识、不熟，那我就觉得它不好」，于是指了另一条；要是因为这个原因去选，反而还更 low。也有同学说两条没区别——好歹人家还认识 left 这个函数。

结论当然是上面这条好，原因是它能用上索引。前提是得先有一个索引，所以我们先创建：

```sql
create index idx_name on student(name);

-- 写法一：前缀模糊匹配
explain select ... from student where name like 'abc%';

-- 写法二：字段上作用函数
explain select ... from student where left(name, 3) = 'abc';
```

在有索引的情况下执行：写法一的 explain 里 key 这个位置有值，type 是 range，还算是一个不错的访问方法；写法二执行出来就很糟糕了，全表访问，key 这个位置也没有值。

为什么会出现这样的原因？name 字段上构建了一棵 B+ 树，这棵树是按 name 排好序的。`like 'abc%'` 的操作就可以从这棵树里去找：先定位到以 a 开头的那一波，接着看第二个字符是 b 的、第三个字符是 c 的，然后从这一段里开始找——这就相当于用上索引了。

而 `left(name, 3)` 不一样，它是在字段上作用了一个函数，再把结果跟另一个字符串去比。函数作用的是什么，优化器并不知道——千奇百怪的函数多了去了。它能做的，就是老老实实把这个字段的值一个一个取出来：每取出来一个，就作用一次函数取它的前三个字符，然后看看是不是等于 abc。这样一来，一开始就根本没有办法锁定 B+ 树里 abc 开头的那一段，只能一行一行地取值，B+ 树自然用不上。

```text
where name like 'abc%'
  -> 在按 name 排好序的 B+ 树里，直接定位到 a->b->c 这一段区间去取   （type=range，key 有值）

where left(name, 3) = 'abc'
  -> 优化器不知道 left() 到底做了什么
  -> 只能逐行取出 name 的值 -> 作用函数 -> 再和 'abc' 比较
  -> 事先无法锁定 'abc' 开头的区间，只能一行行验              （type=all，key=null）
```

下面还有具体的举例，运行效率上的区别就不一一演示了。

#### 字段参与算术运算

再看第二种情况。这一次出现在 student_number 字段上，得先确保它上面有索引：

```sql
create index idx_student_number on student(student_number);

-- 字段上带着运算：用不上索引
explain select ... from student where student_number + 1 = 900001;

-- 把运算挪到等号右边：能用上索引
explain select ... from student where student_number = 900000;
```

第一条执行下来，key 上也没有值，走的也是全表扫描。第二条是把加 1 挪过去——左边减个 1，右边也减个 1，小学都学过，它跟上面那条表达的其实是一个意思——执行下来明显就用上索引了。这里 student_number 还是非空的限制，4 个字节。

实测这条 select 是 0.042 秒，另一条就要更多一些。

道理跟前面一样：在现有的字段上加了个值，相当于要做一次运算；一做运算，优化器就没办法直接拿着你后面那个值去 B+ 树里找了。像 `student_number = 900000` 这种就可以直接在索引的 B+ 树里定位到那个值；而你做了运算，我就得把字段的值一个一个都取出来，再去做运算。所以就用不上索引。

#### name 字段上的函数与 key_len 计算

再一次举例，这次还是针对 name 字段：在字段上作用一个函数，然后等于 abc。name 上面刚才已经建过索引了，那这个显然也就用不上了——执行下来 type 是 all，key 是 null，不行。建议的写法还是把前三个字符是 abc 表达成前缀匹配，显然就能用上这个索引。

顺便看一下这个索引的 key_len 是怎么算出来的。name 是 20 个字符，可以为 NULL，本身又是可变的，需要额外的字节去记录长度，所以 $20 \times 3 + 1 + 2 = 63$，一共 63 字节：每个字符最多 3 字节，加 1 字节的 NULL 标志，再加 2 字节记录变长字段的长度。

在字段上用了函数，就不是一个好的选择。

### 隐式类型转换导致的索引失效

第五条：类型转换导致的索引失效。name 上已经有索引了，看这条语句：

```sql
-- name 是字符串类型，右边却写了数字
explain select ... from student where name = 123;
```

explain 出来还是 all，key 也是 null，不行。那怎么才能用上索引？把 123 加上单引号：

```sql
explain select ... from student where name = '123';
```

name 本身就是字符串类型，右边也给字符串，就不会出现类型转换的问题，再执行就用上索引了，没有问题。而前者相当于先把这个字段上的值做了一个隐式的函数——做了一次转换，再拿去跟 123 做对比。既然一旦用上函数索引就失效，那么这里也是同一个道理。

> **提示**：想让索引持续有效，「字段上不加运算、字段上不加函数、比较时两边类型保持一致」这几条一定要考虑在内。

到这里就是索引失效的第一波情况。回头看这三件事：`left(name, 3) = 'abc'`、`student_number + 1 = 900001`、`name = 123`，写法上各不相同，根子上是同一件事——字段没有以自己的原始值去参与 B+ 树的定位，而是先被算过一遍再拿去比较，有序结构也就没法用了，索引自然失效。

## 142-索引失效的11种情况2
> 对应分集：P142 | 原始标题：《142-索引失效的11种情况2》

接着往下走，该说失效清单的后半段了。前面那些场景——字段上套函数、类型转换、最左前缀断掉——我们已经一条条看过；从这里开始是第 6 条到第 11 条：范围条件右侧的列、不等于、`IS NOT NULL`、以通配符开头的 `LIKE`、`OR` 两侧的非索引列，最后补一条特别容易被忽略的字符集不统一。

这几条规则本身都不难理解，难的是把每一种失效都真真切切地跑出效果来。每一个案例都得让优化器按预期把索引丢掉，否则讲出来就是空口说白话——看着讲的时间不算长，准备工作其实花了不少功夫。

所以每演示一条，我们先把环境弄干净。演示库是 `atguigudb2`，表是 `student`：不把残留的索引清掉，后面看到的执行计划说不定就是别的索引造成的，效果全被干扰。

> **提示**：判断索引失效这件事，脑子里有一棵 B+ 树就够了。这些案例基本都能自己推出来——能不能在树上找到一条可以连续下探的路径，找得到就走索引，找不到就退化成全表扫描。我们一条条做实验，主要目的是验证事实确实如此。

### 范围条件右侧的列索引失效

先看看这张表上到底有多少索引：

```sql
SHOW INDEX FROM student;
```

一执行就是一大片。这些都是前几讲为了演示陆陆续续建起来的，留着只会干扰判断。把之前写好的那个删索引的存储过程调一遍——库 `atguigudb2`，表 `student`——执行完再看一次：

```sql
SHOW INDEX FROM student;
```

这回只剩一个主键索引了，很干净，没有别的索引来干扰我们分析。

这一节要演示的是范围条件，用到的字段是 `age`、`class_id`、`name`，先建一个三列的联合索引：

```sql
CREATE INDEX idx_age_classid_name ON student(age, class_id, name);
```

索引里的列序完全照创建语句来：`age` 在前，`class_id` 居中，`name` 最后。这一点后面要反复用到。

拿三个条件去查：`age` 走等值、`class_id` 走范围、`name` 走等值。结果应该说毫不意外，索引肯定用上了；关键看 `key_len`（索引使用长度），它是 `10`。

`10` 是怎么来的？`key_len` 统计的是本次查询真正用到的索引列字节数之和，逐列算一遍：

- `age` 是 `int` 类型、允许为 `NULL`：$4 + 1 = 5$ 字节；
- `class_id` 也是 `int`、也允许为 `NULL`：同样是 $5$ 字节；
- 两列相加，正好 $5 + 5 = 10$。

那 `name` 呢？`name` 这列如果也参与进来，`key_len` 还要再加上 `63`——这个 `63` 就是它的完整字节开销：字符内容按字符集的最大宽度算，变长类型再多记 2 字节长度，允许为 `NULL` 再加 1 字节。现在这个 `63` 根本没被加上。

> **结论**：`key_len = 10` 说明这个三列联合索引，我们只用了其中两列，第三列 `name` 没参与。

为什么没用上？索引是按 `(age, class_id, name)` 建的，最左前缀原则保证了"先用上 `age`，才轮到考虑 `class_id`"，这两列确实都用上了。可按同样的道理，紧挨着的 `name` 也该能用上，偏偏它没有。卡住它的不是最左前缀，而是 `class_id` 上的范围条件：**范围一旦出现，它在索引里右边的那些列就都用不上了。**

往树里再追一层，这个结论就更清楚了。联合索引的叶子节点是分层排序的：先按 `age` 排，`age` 相同的再按 `class_id` 排，`class_id` 也相同的才按 `name` 排。给定 `age = 常量`，我们拿到的是 `age` 那一段连续区间；再要求 `class_id > 常量`，就是从这段区间里取出 `class_id` 更大的一截。问题出在这一截内部：`name` 只在同一个 `class_id` 之内有序，一旦跨过 `class_id` 的边界就重新从头排起，于是它在整个结果区间里并非全局有序——树上根本没有一段连续的区间对应"`name = 常量`"，索引也就没法拿它去定位。

```text
联合索引叶子节点排序 (age, class_id, name)
    age=20, class_id=3, name='aaa'
    age=20, class_id=3, name='bbb'
    age=20, class_id=5, name='aaa'   <-- 跨过 class_id 边界，name 重新排起
    age=20, class_id=5, name='ccc'
    age=20, class_id=9, name='bbb'

age = 20 且 class_id > 3 的命中区间：从第 3 行往下全部
    -> 该区间内 name 并非全局有序，无法据此定位
    -> 索引只负责 age、class_id；name 留到回表之后逐行过滤
```

读图说明：联合索引的排序是"逐列递进"的，前一列一旦不是等值而是范围，后一列在这个区间里就失去了全局有序性，只能退化成回表后的过滤条件。

> **易错点**：这里的"右边"指的是**索引里的右边**，不是 WHERE 语句里的右边。看索引，不要看 SQL。

那能不能靠调整 WHERE 里条件的书写顺序把它救回来？有同学问：把 `class_id` 挪到后面、把 `name` 提到前面，行不行？答案很干脆：没有任何意义。对优化器来说，这几个条件谁先写谁后写无所谓，它自己会去颠倒顺序。真正颠倒不了的是索引里的列顺序——索引里你先写了 `class_id`、先把范围写在前面，那范围右边的列就注定失效。

```text
WHERE 的书写顺序     age = 20  AND  class_id > 5  AND  name = 'abc'
                        |             |                 |
优化器重写条件顺序   重新排序 -> age = 20  AND  name = 'abc'  AND  class_id > 5
                       （等值条件在前，范围条件放到最后）
                        |
索引里的列序         idx_age_name_cid (age, name, class_id)   <-- 这一层改不了
                        |
结果                 三个条件全部落在索引上，key_len = 73
```

读图说明：优化器能自由重排的是 SQL 里条件的先后，重排不了的是索引里列的先后；所以"换 WHERE 顺序"救不了失效，"换索引列序"才能。

办法在建索引这一步就能解决：把确定的等值字段列在前面，范围字段放到最后。于是重新建一个索引：

```sql
CREATE INDEX idx_age_name_cid ON student(age, name, class_id);
```

索引叫什么名字随意，决定顺序的是括号里列的排列。再执行同样的查询，`key` 换成了这个新索引，`key_len` 从 `10` 变成 `73`：$5 + 63 + 5 = 73$。三列全用上了。

```text
联合索引 idx_age_classid_name   (age, class_id, name)
    age      = 常量    -> 用上
    class_id > 常量    -> 用上（范围列自己能用）
    name     = 常量    -> 用不上          <-- 被范围截断

联合索引 idx_age_name_cid       (age, name, class_id)
    age      = 常量    -> 用上
    name     = 常量    -> 用上
    class_id > 常量    -> 用上            <-- 范围在最右，前面全保留
```

读图说明：同一组 WHERE 条件，索引列序不同，能利用到的列就不同；判断依据始终是范围条件落在索引的第几列，落在越后面，被截掉的列越少。

| 索引列序 | WHERE 条件形态 | `key_len` | 实际用上的列 |
| --- | --- | --- | --- |
| `(age, class_id, name)` | age 等值、class_id 范围、name 等值 | `10` | age、class_id |
| `(age, name, class_id)` | 同上 | `73` | age、name、class_id |

这里还有一个细节要澄清。有人会接着追问：如果把范围条件写在 WHERE 的中间，也就是 `AND class_id > 常量` 夹在等值条件之间，还能用上新索引吗？还能，`key_len` 依旧是 `73`。因为条件之间是 `AND`，优化器会自动把它们交换一下：先考虑等值，最后才考虑范围。所以顺序这件事，我们只管索引里的，不用管 WHERE 里的。

把它说全就是：只要出现 `<`、`<=`、`>`、`>=`、`BETWEEN ... AND ...` 这一类范围条件，范围列自己能用上索引，它右边（索引里的右边）的列就用不上。

这条规则在实际开发里几乎躲不开——查金额、查日期往往都是范围。有人习惯把范围条件写到 WHERE 的最后，这个习惯本身没问题，但它只是给自己一个暗示：这个条件是最后才考虑的那个。真正要落到索引上的动作只有一句：创建联合索引时，务必把范围字段写在最后。

### 不等于运算符导致的索引失效

第 7 条，`!=`。先在 `name` 上建好索引，然后跑一次等值匹配：

```sql
SELECT * FROM student WHERE name = 'abc';
```

这个肯定能用上索引，没有任何问题。把 `=` 换成 `!=`：

```sql
SELECT * FROM student WHERE name != 'abc';
```

索引就用不上了，`type`（访问方法）退化成 `ALL`，也就是全表扫描。换成另一个写法 `<>`，结果一样：

```sql
SELECT * FROM student WHERE name <> 'abc';
```

同样不行。两个符号是一个意思，都不能用索引。

| WHERE 写法 | 执行计划 |
| --- | --- |
| `name = 'abc'` | 走 `name` 上的索引 |
| `name != 'abc'` | `type = ALL`，全表扫描 |
| `name <> 'abc'` | `type = ALL`，全表扫描 |

道理想一想就通：在 B+ 树里要"等于 `abc`"，直接顺着树找到等于 `abc` 的那些项就完了；可"不等于 `abc`"呢，你从哪儿下嘴？树上并没有哪一个连续区间正好对应"不等于 `abc`"，只能一条一条记录去比。既然要一条条比，那还不如干脆全表扫描。

### IS NULL 可用索引与 IS NOT NULL 失效

第 8 条。`age` 上我们并没有单独建索引，但前面建的那个以 `age` 打头的联合索引正好可以用来验证：

```sql
SELECT * FROM student WHERE age IS NULL;
```

用上了：走的就是那个联合索引，而且只用到它的第一个字段 `age`，`key_len` 是 `5`——正好是 `int` 加上允许为 `NULL` 的那 1 个字节。换成 `IS NOT NULL`：

```sql
SELECT * FROM student WHERE age IS NOT NULL;
```

索引就没了，还是 `ALL`，全表扫描。

机理和第 7 条是一路的：`IS NULL` 相当于"等于某个值"，在 B+ 树里直接去找 `NULL` 所在的位置就行；`IS NOT NULL` 相当于"不等于某个值"，树上同样没有对应的连续区间，只能一个一个看过去，看谁不是 `NULL`。

> **定义**：可以把 `IS NULL` 当成一次等值匹配，把 `IS NOT NULL` 当成一次不等值匹配。第 7 条和第 8 条失效的根子是同一个——不等值在 B+ 树上没有可下探的连续区间。

由此带出一条很实用的建表经验：设计数据表时，通常给字段都加上 `NOT NULL` 约束。既然所有数据都满足非空，查询时就不必再写 `IS NOT NULL` 这个条件，直接写其他过滤条件，该建索引建索引，索引就能用上。

那确实需要"没有值"这个语义怎么办？用等价的替代值：数值类型设成 `0`，字符串类型设成一对单引号里什么都不放的空串。用这种写法去替换原来 `NULL` 的场景，索引照样能用。

同样的道理，`NOT LIKE` 也一样——凡是带 `NOT` 的、非的，都只能全表扫描。

### 以通配符 % 开头的 LIKE 导致的索引失效

第 9 条。前面讲 `LIKE` 与函数调用的时候出现过一次：`LIKE 'abc%'` 前面确定、后面不确定，这种写法是可以走索引的。这一条要说的是另一头——以通配符 `%` 开头的写法。

`name` 上有索引。`LIKE 'abc%'` 走索引，`type` 是 `range`（范围扫描）；一旦在最前面加上一个百分号，不管是 `'%abc'` 还是 `'%abc%'`，索引就用不上了，退化成全表扫描。后面加不加百分号都无所谓，关键是开头是不是通配符。

```sql
-- 能走索引：前缀确定
SELECT * FROM student WHERE name LIKE 'abc%';

-- 走不了，全表扫描
SELECT * FROM student WHERE name LIKE '%abc';
SELECT * FROM student WHERE name LIKE '%abc%';
```

原因还在 B+ 树的查找方式上：树上逐层比较键值——比 A 大、比 A 小、还是等于 A，每一步都要有一个确定的起点。`'abc%'` 的开头是确定的，所以能一路下探；`'%abc'` 一上来就不确定，你让我去树上找哪一支？第一个该不该走都判断不了，那还不如把数据一条条取出来过一遍，看谁以 `ab` 结尾、谁里面包含 `ab`。

```text
LIKE 'abc%'   前缀确定
    根节点 -> 逐层比较 'ab' / 'abc' / 'abd' -> 沿确定路径下探
    结果：命中一段连续的索引区间        -> 走索引 (range)

LIKE '%abc'   前缀不确定
    起点无法确定 -> 树上没有可下探的分支
    结果：只能逐行取出做字符串匹配      -> 全表扫描 (ALL)
```

读图说明：能不能走索引，取决于字符串匹配有没有一个可以下探的确定前缀；有前缀就有连续的索引区间，没有前缀就只剩逐行比对。

阿里巴巴开发手册里对这条是强制要求：页面搜索严禁左模糊或者全模糊。如果业务上非要用这种匹配，那就别在 SQL 上硬扛，交给搜索引擎去做。

说到底，只要脑子里有一棵 B+ 树，这些失效案例基本上都能自己平推过去。一条条地讲，主要是让大家看到事实确实如此——很多结论，理论上我们自己都能分析出来。

### OR 两侧存在非索引列导致的索引失效

第 10 条。演示之前把环境再清一遍：还是调那个存储过程删掉 `student` 上的索引，再用 `SHOW INDEX FROM student;` 确认只剩主键。这次只针对 `age`、`class_id` 里的一个字段建索引：

```sql
CREATE INDEX idx_age ON student(age);
```

建 `age` 还是建 `class_id` 都无所谓，效果一样。然后用 `OR` 去查：

```sql
SELECT * FROM student WHERE age = 20 OR class_id = 3;
```

用不上索引，`type` 是 `ALL`。

为什么？`OR` 取的是并集——两边的数据全都要。现在一侧有索引、一侧没有：有索引的那侧先把结果捞出来，没索引的那侧照样得全表扫描；两段开销加在一起，还不如直接来一遍全表扫描快。既然怎么算都不划算，优化器干脆不碰索引了。把那个索引删掉也是同样的结果，反正都是 `ALL`。

那什么时候 `OR` 能用上索引？让 `OR` 两边的字段都有索引：

```sql
CREATE INDEX idx_class_id ON student(class_id);
```

两个索引都在了，再看同一条 SQL，`type` 就变成讲 EXPLAIN 时见过的 `index_merge`（索引合并）——相当于把这两个索引合并在一起用，`Extra`（额外信息）里会出现 `using union`。这时候索引真正起作用了，查询效率比全表扫描高，不用再扫全表。

```text
WHERE age = 20 OR class_id = 3
            |
            +--> idx_age         --\
            |                      >-- index_merge (using union) --> 结果并集
            +--> idx_class_id    --/
```

读图说明：`OR` 的每一侧各走自己的索引，各自取出一部分结果集，再由 `index_merge` 做并集合并；只有两侧都有索引可取，这条路径才成立，只要有一侧没索引，整条 SQL 就退回全表扫描。

### 字符集不统一导致的索引失效

最后一条，第 11 条，也是最容易被忽略的一条：数据库和表的字符集要统一，统一使用 `utf8mb4`，用 `utf8mb3` 也行，重点是**一定要统一**。这条主要针对 MySQL 8.0，它的默认字符集就是 `utf8mb4`，所以我们这里也用它。

为什么必须统一？不同字符集的字段在比较之前，一定会先做一次字符集转换；一旦涉及转换，就相当于在比较的时候用上了一个转换函数。而字段上套了函数，索引就失效了。

> **提示**：这条没有专门的演示案例，但它是隐含在每一条 SQL 里的坑：库与表、表与表、字段与字段的字符集只要不一致，等值比较和连接条件都可能因为这个隐式转换把索引丢掉。

到这里，索引失效这一串场景就讲完了：从范围条件右侧，到不等于、`IS NULL` 家族、左模糊 `LIKE`、`OR` 两侧的非索引列，再到字符集不统一。

### 索引选择与联合索引列序的经验建议

收尾之前，把散落在上面的规则收成几条可以直接照做的建议。先看一眼这一路讲下来的失效形态，以及它们各自的根因与处置：

| 失效形态 | 根因 | 处置 |
| --- | --- | --- |
| 范围条件右侧的列用不上 | 范围列右边的列在命中区间里失去全局有序性 | 建联合索引时把范围字段放到最后 |
| `!=`、`<>` | 不等值在 B+ 树上没有可连续下探的区间 | 尽量改写成等值匹配 |
| `IS NOT NULL`、`NOT LIKE` | 等价于一次不等值匹配 | 字段加 `NOT NULL`；用 `0` 或空串替代 `NULL` |
| 以 `%` 开头的 `LIKE` | 匹配没有确定前缀，树上无法选择分支 | 改成右模糊 `'abc%'`，或交给搜索引擎 |
| `OR` 两侧存在非索引列 | 无索引那侧仍要全表扫描，总代价反而更高 | 两侧字段都建索引，走 `index_merge` |
| 库表字符集不一致 | 比较前发生字符集转换，相当于在列上套了函数 | 库、表、字段统一用 `utf8mb4` |

这几条建议本身就是从上面这些形态里长出来的，下面逐条说。

#### 单列索引：挑过滤性最好的那个字段

如果表上只有单列索引，而 WHERE 里写了一串条件，那就尽量选择针对当前 query 过滤性最好的那个索引。这件事优化器自己也会做：假设四个字段上各有一个单列索引，它会把成本最低的那个挑出来用。

我们自己建索引时同理，但不能全都建上——表上的索引一多，维护成本就跟着上去。只允许挑一个的时候，就挑过滤性最好的那个：同样两个字段，一个过滤完只剩 10% 的数据，另一个能过滤掉 99%，那当然选后者。

#### 联合索引：过滤性最好的字段靠前

建联合索引时，当前 query 中过滤性最好的字段，在索引里的位置越靠前越好。道理是连锁的：过滤性越好，经过它筛完剩下的数据越少；剩下的数据越少，后面那些列的比对压力就越小。

反例也很直观：把性别这种字段放在索引第一位，过滤完还剩一半数据，后边还有 50% 等着你，效果就稍差一些。

#### 联合索引：尽量覆盖 WHERE 里更多的字段

联合索引要尽量选择包含当前 query 中 WHERE 子句里更多字段的那一个，优化器在做选择时也是这个倾向。字段越多，索引就被用得越充分。

#### 联合索引中的范围字段放到最后

这就是第 1 节那条规则的正写：组合索引里如果某个字段会出现范围条件，尽量把这个字段放到后面。总之一句话——书写 SQL 语句时，尽量避免索引失效的情况。绕了这么大一圈，讲的不就是这一句吗。

### 本讲提到的题目：联合索引 (a, b, c) 的可用性判断

规则讲完，还有一道小练习：表上有一个联合索引 `(a, b, c)`，判断给出的各种 WHERE 写法里，哪些能用上索引、哪些用不上。练习左侧罗列了一串写法，右侧就是要自己填的结论——把右侧遮住，一条条推，再看填出来的答案对不对得上。

最容易错的是这两类：

- `a`、`b` 同时出现的那些等值写法，是能用上索引的；
- 有一类写法看着把条件都写了，实际上只能用到 `a` 这一段，`b` 那一段就用不上了。

推法就两条，依据全在上面几节里：

1. **最左前缀**：从索引最左列开始，连续命中等值条件，命中到哪一列就用到哪一列；中间跳掉一列，后面的列就都不参与。
2. **范围截断**：某一列上出现范围条件（`>`、`<`、`BETWEEN ... AND ...` 等），这一列自己能用上，它在索引里右边的列全部用不上。

判断任何一条写法之前，先排除那些会让索引直接失效的形态：字段上套函数或做运算、类型或字符集不一致引起的隐式转换、否定条件（`!=`、`<>`、`IS NOT NULL`、`NOT LIKE`）、以 `%` 开头的 `LIKE`，以及 `OR` 两侧存在没有索引的列。

## 143-外连接与内连接的查询优化
> 对应分集：P143 | 原始标题：《143-外连接与内连接的查询优化》

实际写 SQL 的时候，只要语句一复杂起来——多表查询、子查询——几乎都要面对关联查询的优化问题。所以这一讲把多表查询和子查询的优化专门拎出来说：先解决多表查询这一块，看它在**外连接**和**内连接**这两种写法下，执行计划到底有什么不同、索引该往哪儿加。

### 多表连接的分类与本讲范围

多表连接可以从不同角度分类，这里只看其中一个角度：分成内连接和外连接。

外连接再往下分，是左外连接、右外连接和满外连接。MySQL 里没有一条直接的满外连接语法，得用 `UNION` 把两侧的结果拼起来，它本质上是"组合"，而且拼起来的两半本身各自就是外连接。既然是组合出来的东西，就没有必要单独讨论它。

左外连接和右外连接，一个是 `LEFT JOIN`，一个是 `RIGHT JOIN`。右外连接把两个表的位置交换一下，就可以改写成左外连接——两者的能力是等价的。所以外连接这一支，只拿左外连接当代表来讲就够。

于是本讲要覆盖的场景就收敛成两种情况：

- 情况一：外连接，以左外连接为代表；
- 情况二：内连接。

这两种情况，把实际开发里连接查询的执行计划问题基本概括全了。

### 演示环境：type 表与 book 表

为了讲清楚，准备两张表，各 20 条数据，直接用 `INSERT` 写进去。

数据量故意做得小，是因为这里要对比的不是"用索引和不用索引性能差多少"，而是**谁做驱动表、谁做被驱动表**。行数一大，执行计划反而不好读，成本差异也容易被掩盖。

| 表名 | 主键 | 参与连接的字段 | 索引情况 | 初始行数 |
| --- | --- | --- | --- | --- |
| `type` | `id` | `card` | 无任何索引 | 20 |
| `book` | `book_id` | `card` | 无任何索引 | 20 |

连接条件就是把两张表的 `card` 字段等值连起来。

两张表的主键在这次连接里帮不上忙：连接条件用的是 `card`，不是 `type.id`，也不是 `book.book_id`。所以主键索引对这次连接没有任何贡献，能不能用上索引全看 `card` 上有没有——这也是为什么初始状态下两边的访问方法都是 `ALL`。

> **提示**：两张表的主键名字不一样（`id` 与 `book_id`），但连接字段同名，都叫 `card`——字段名同不同名其实无关紧要，第 5 节会说到真正有约束的地方。

### 无索引时的左外连接执行过程

先看左外连接，语句很直白：从 `type` 表出发，左连接 `book` 表，连接条件是两张表的普通字段 `card` 相等。

```sql
SELECT *
FROM `type` LEFT JOIN book
     ON `type`.card = book.card;
```

因为两张表的 `card` 上都没有索引，`EXPLAIN` 里两张表的访问方法都是 `ALL`——全表扫描。

看 `EXPLAIN` 的结果主要盯三处：访问方法那一列是 `ALL` 还是 `ref`，`key` 列显示实际用上了哪个索引，`Extra` 列给出额外提示。这三处也就是本讲后面反复用来做判断的依据。

#### 嵌套循环的匹配过程

`EXPLAIN` 输出里靠上的那一行是**驱动表**（外层循环），靠下的那一行是**被驱动表**（内层循环）。整个匹配过程跟编程里学过的嵌套循环是一回事——不管写的是 Java、C、Python 还是 Go，双层 `for` 的结构都是这个形状。

为了算账方便，假设 `type` 有 20 行、`book` 有 30 行：先从 `type` 里取一条记录，拿它的 `card` 值到 `book` 里按连接条件找匹配的记录；而 `book.card` 上没有索引，这一趟只能把 `book` 整表遍历一遍，也就是 30 行。匹配上的记录放进结果集。接着从 `type` 取第二条，`book` 那边又是一次整表遍历……

```text
   驱动表 type（外层循环，访问方法 ALL）
        |
        |  取第 1 条记录  ->  按 type.card = book.card 去被驱动表匹配
        |  取第 2 条记录  ->  按 type.card = book.card 去被驱动表匹配
        |  ...
        |  取第 20 条记录 ->  按 type.card = book.card 去被驱动表匹配
        v
   被驱动表 book（内层循环，card 上无索引 -> 每次匹配整表扫 30 行）
        |
        v
   被驱动表累计被访问 20 x 30 = 600 行
```

图里的 600 就是没有索引时这条语句要付出的代价量级：驱动表只扫一遍（20 行），被驱动表却要被扫 20 遍。

值得留意的是，两张表都没有索引时，"谁做驱动表"这件事还看不出区别：让 `type` 驱动，总访问量是 $20 \times 30$；让 `book` 驱动，总访问量是 $30 \times 20$——同一个数。真正让驱动表位置变得值钱的，是被驱动表上有了索引之后：内层不再整表扫，而是一次查找，总代价由外层的行数乘上一个 $\log$ 级别的查找成本决定。后面"索引要加给被驱动表""小表驱动大表"两个结论，都是从这个变化里长出来的。

> **易错点**：内层循环的代价会被驱动表的行数放大。所以被驱动表上有没有可用的索引，比驱动表本身怎么扫重要得多。

#### join buffer 与哈希连接

被驱动表要被反复遍历，查询优化器不会干看着，它在这里做了一个优化处理：用 join buffer 把数据缓存起来，配合哈希连接（Hash Join）的方式，让每次探测不必再从表头扫起，检索速度能提上去。

哈希连接的做法是：把参与连接的数据按连接字段整理成一张哈希表，再让另一侧的记录直接拿 `card` 的值去哈希表里探测，平均一次探测就能定位到匹配的记录，不必再逐行比对。join buffer 就是给这类批量匹配留出来的内存缓冲。

> **提示**：join buffer 是优化器在内存里划出来的一块缓冲，哈希连接是使用这块缓冲的算法——在被驱动表的等值连接字段上没有可用索引时，用哈希表代替反复扫表。

要留意的是，这个优化并不会改变"两张表的访问方法都是 `ALL`"这个观察结果：`EXPLAIN` 里看到的仍然全是 `ALL`。判断一条没有索引的连接语句，主要就是看 `ALL` 出现在哪张表上。

### 在被驱动表上添加索引

给 `book` 的 `card` 加上索引：

```sql
CREATE INDEX Y ON book(card);
-- 等价写法
ALTER TABLE book ADD INDEX Y(card);
```

这里索引名取 `Y`、后面给 `type` 加的取 `X`，只是为了区分两张表上的索引，方便看执行计划时对上号。

执行完再跑一次 `EXPLAIN`，变化很明显：

| 位置 | 表 | 访问方法 | key | 说明 |
| --- | --- | --- | --- | --- |
| 驱动表 | `type` | `ALL` | 无 | 仍然是全表扫描 |
| 被驱动表 | `book` | `ref` | `Y` | 走索引做等值匹配，性能相当不错 |

被驱动表的访问方法从 `ALL` 变成 `ref`，而且用上了 `key = Y`。此时执行会快很多：从驱动表取一条记录，去被驱动表找的时候就能用索引了——`book.card` 上的 B+ 树直接定位到那条想要的记录，查找次数是 $\log n$ 量级，也就是 $\log_2 30$ 这个水平，比整表 30 行好得多。

这笔账还能再算细一点：索引没加之前，被驱动表每次探测读 30 行，20 次探测总共 600 行；加索引之后，每次探测退化成 B+ 树上的一次查找，$\log_2 30$ 大约是 5 次比较，20 次探测总共 100 次左右——同样的结果集，代价掉到了原来的六分之一量级。而且驱动表行数越多、被驱动表越大，这个差距还会继续拉开。

驱动表那一侧，`card` 上的索引也能被利用，`Extra` 里会出现 `Using index` 这样的提示：查询需要的列可以直接从索引里拿到，不必回表。

> **提示**：能否形成覆盖索引，取决于查询到底用到哪些列。只要有一列不在索引里，就还得回表取数据，`Using index` 也就不会出现。

驱动表毕竟是走 `ALL` 全表扫描的，但这里头有个讲究：左外连接本来就要求左表的数据全部保留——除了两张表都匹配上的记录，左表里没匹配上的记录也要留下来，那驱动表走 `ALL`、把数据一条条过一遍，被驱动表用上索引，其实是一个比较好的选择。

> **结论**：如果两个连接字段上只能加一个索引，那这个索引一定要加给**被驱动表**。

### 连接字段的类型一致性要求

既然被驱动表能加索引，驱动表这边也可以加一个，看看两张表都有索引会怎样：

```sql
CREATE INDEX X ON `type`(card);
```

> **易错点**：`type` 是 MySQL 的关键字，表名不加反引号分隔符会直接报"表不存在"。实际开发中要么给表起名时避开关键字，要么老老实实把反引号加上——这不是可选项，是准确性问题。

建好之后再 `EXPLAIN`，两张表就都用上索引了。

这里有个细节必须点出来：两个字段上都有索引、也都应用上了，背后还有一个隐含条件——**两张表连接字段的名字可以不一样，但类型一定要相同**。

> **易错点**：如果两侧字段类型不一致，连接时就要做隐式类型转换，相当于给字段套了一层函数，直接掉进前面讲过的索引失效场景里。

举个具体的例子：一边的连接字段是字符串类型、另一边是数值类型，MySQL 在比较之前必须把字符串转成数值，这个转换落在字段值上，也就等于给字段套了一层函数，`card` 上的索引自然用不上了。所以设计多表连接时，只要有连接关系，就让连接字段的类型保持一致；字段名不同没有关系。

### 左外连接中驱动表的固定角色

现在把 `book` 上的索引删掉：

```sql
DROP INDEX Y ON book;
```

再执行 `EXPLAIN`，被驱动表那一位又变回 `ALL`——索引一没，被驱动表只能退回 join buffer 加哈希连接那条路。

```text
   左外连接：两个表的位置由写法决定，不由优化器决定
       type（左表，驱动表，访问方法 ALL）
            |
            |  左表的每一行都必须留在结果集里
            v
       book（右表，被驱动表）
            |
            +-- 有索引   -> ref
            +-- 无索引   -> join buffer + 哈希连接
```

图里要表达的是：左外连接里两边的角色被写法钉住了，能变的只有被驱动表用什么方式访问。

这个来回删、加的演示，是为了跟内连接做对比。没有对比就直接下结论会显得有点牵强，但外连接的结论可以先摆出来：

> **结论**：在左外连接里，左边的表就是驱动表，右边的表就是被驱动表——角色是定死的。

定死的原因是语义：左外连接要求左表的数据全部出现在结果集中，左表就必须先被完整地读出来当外层，优化器没有把左表塞进内层的自由。

而内连接里，驱动表和被驱动表是由查询优化器决定的。差别就在这里。

### 内连接中优化器的驱动表决策

内连接先把两张表上的索引都删干净，再把语句从 `LEFT JOIN` 改成内连接：

```sql
SELECT *
FROM `type` INNER JOIN book
     ON `type`.card = book.card;
```

两张表的 `card` 上都没有索引时，`EXPLAIN` 里两张表都是 `ALL`，`type` 在上面、`book` 在下面——跟前面左外连接最初的样子几乎一样，没什么可说的。

接着把 `book` 的索引加回来，被驱动表那一位就出现 `ref`、`key = Y`。

再给 `type` 加上索引，两张表的连接字段就都有索引了。这时候跑出来的执行计划，两张表的先后顺序可能跟别人那儿不一样，甚至同一份脚本、同一台机器上再跑一次也可能互换。

> **提示**：顺序有变化不代表它是随机的。优化器是把两种方案的成本都算过一遍才决定谁上谁下的，变的只是成本估算的输入。

#### 内连接中两张表的对等地位

左外连接里两张表有角色区别，左表的数据必须全要；内连接只取两张表共同匹配的那部分，左右两边地位一样。地位一样，优化器就有决策权了：让谁做驱动表、让谁做被驱动表，两种方案都列出来算一算成本，选成本较低的那一个。

```text
   内连接：两张表连接字段上的索引情况
        |
        +-- 只有一个字段有索引 ----> 有索引的那张表做被驱动表
        |
        +-- 两个字段都有索引 ------> 按成本计算，小表做驱动表
        |
        +-- 两个字段都没有索引 ----> 两张表访问方法都是 ALL，
                                    被驱动表靠 join buffer + 哈希连接兜底
```

图里最后一条路径是与外连接共有的，前两条才是内连接独有的决策空间。

#### 连接字段上只有一个索引时的选择

把 `book` 上的索引删掉、`type` 上的留着，再执行一次：两张表的位置换了——原本 `book` 在下面，删掉它的索引之后，`type` 跑到了下面，也就是 `type` 成了被驱动表。

```text
   场景 A：只有 book.card 上有索引
       type（驱动表，ALL 全表扫描）
            |
            v
       book（被驱动表，ref，用上 key = Y）

   场景 B：只有 type.card 上有索引
       book（驱动表，ALL 全表扫描）
            |
            v
       type（被驱动表，ref，用上 key = X）

   索引装在哪张表上，哪张表就落到被驱动的位置
```

> **结论**：内连接的连接条件里，如果只能有一个字段有索引，那么**有索引的那个字段所在的表会被当作被驱动表**出现。

这不是随机结果，而是成本算出来的。驱动表只会被完整读一遍，在它身上装索引，收益仅是把那一次全表扫描换成一次索引扫描；而被驱动表要被探测 N 遍（N 就是驱动表的行数），索引装在它身上，收益要乘以 N。同样一个索引，装在会被反复探测的那一侧，收益才被放大。

再把索引加回 `book`，`book` 又回到下面（被驱动）的位置。

#### 两个连接字段都有索引：小表驱动大表

到这一步，两张表都还是 20 行。往 `type` 里再插 20 条数据，把数据量拉开——注意要插的是位置在上面那张表（这里 `type` 在上面，所以往 `type` 里插；如果你那边两张表的顺序不一样，就往上面那张表里插），插完 `type` 40 行、`book` 20 行。

再执行 `EXPLAIN`：`type` 跑到下面去了。也就是说，数据量变了之后，谁做驱动表、谁做被驱动表也跟着变了。

> **结论**：内连接中，两个连接字段上都有索引时，优化器会选择**小表作为驱动表**——这就是常听到的那句"小表驱动大表"。

这里的"小"说的是数据量（行数）小。优化器最终比较的是成本，行数只是其中最直观的一个输入。

至于为什么小表该放在外层，把账算一下就清楚了：驱动表每取出一条记录，被驱动表就要按索引探测一次，所以探测次数约等于驱动表的行数；而每次探测的代价是 $\log(\text{被驱动表行数})$ 量级。

- 小表（20 行）在外层：$20 \times \log_2 40 \approx 20 \times 5.32 \approx 106$
- 大表（40 行）在外层：$40 \times \log_2 20 \approx 40 \times 4.32 \approx 173$

驱动表的行数在成本里充当乘数，所以把行数少的那张放在外层，总代价更小。

### 两类连接的驱动表决策对照

把这一讲验证过的结论并到一张表里：

| 对比项 | 左外连接 | 内连接 |
| --- | --- | --- |
| 结果集 | 左表全部记录，加上右表能匹配上的记录 | 两张表都能匹配上的记录 |
| 两张表的地位 | 不同，左表数据必须全部保留 | 相同，只取共同匹配的部分 |
| 驱动表由谁决定 | 固定是左表 | 查询优化器按成本决定 |
| 被驱动表由谁决定 | 固定是右表 | 查询优化器按成本决定 |
| 连接字段只有一个有索引 | 索引要加在被驱动表上 | 有索引的那张表做被驱动表 |
| 连接字段都有索引 | 驱动表仍走 `ALL`，被驱动表走 `ref` | 小表做驱动表（小表驱动大表） |
| 连接字段都没有索引 | 驱动表 `ALL`，被驱动表靠 join buffer 加哈希连接 | 两张表都是 `ALL`，被驱动表同样靠 join buffer 加哈希连接 |

最后一行里两种连接的表现是一样的；真正分道扬镳的地方在于**谁能决定谁是驱动表**：左外连接的左表被语义钉死，内连接则交给优化器按成本挑。

到这里，外连接和内连接在实际执行计划里的表现就都验证完了。上面这些结论都是从实验里看出来的，那底层支撑它们的成本模型到底是什么样子？那就是 JOIN 语句原理要展开的内容了，下一节从那里接着讲。

## 144-JOIN语句的底层原理
> 对应分集：P144 | 原始标题：《144-JOIN语句的底层原理》

前面我们已经拿一堆 SQL 跑过现象，也把结论攒出来了：`a` 表连 `b` 表，连接条件是 `a.a = b.b`；两个字段都没索引，结论是**小表驱动大表**；如果 `b` 表的 `b` 字段有索引，那 `b` 一定作为被驱动表出现；反过来两个都没索引、只有 `a` 字段有索引，那就是 `a` 当被驱动表；如果 `b` 有索引、`a` 也有索引，又回到小表驱动大表。

这些结论是从现象里"看"出来的，可现象到结论中间站着一个人——**查询优化器（Query Optimizer）**。它为什么这么干？对现在的我们来说它还是个黑盒子。这一讲就把它剥开，看看里面支撑的数理逻辑到底是什么。

我拿中学化学打个比方。我们现在学的化学，是好几代化学人积累下来的成熟学科；可几个世纪以前，欧洲那些有钱的贵族买一堆瓶瓶罐罐的试剂在家里来回捣腾，今天看看这个现象、明天得个那个结论——这么推下去，化学很难有长足发展。真正让它变成一门固定学科的，是理论层面的突破，一个历史性事件就是俄国的门捷列夫发现了**元素周期表**。有了元素周期表的支撑，中学里那些试剂、固态物之间的关系才变成了"谁加谁等于谁""酸加碱等于盐"这样的公式，化学才能作为一门科学不断往前推。

放在我们这儿，道理一样：现象背后的**物理与数理逻辑**是什么，就是这一讲要讲的 JOIN 原理。而这条线索的入口，是一个算法——**嵌套循环连接（Nested-Loop Join，NLJ）**。

### 驱动表与被驱动表的判定

#### 从 EXPLAIN 输出顺序定义驱动表

讲算法之前，得先把"驱动表"和"被驱动表"这两个概念说透彻——上一讲只是提过，没说透。

> **定义**：在执行计划里排在**上面**的那张表是驱动表，排在**下面**的那张表是被驱动表。这个上下，看的是连接字段在 `EXPLAIN` 里的输出顺序。

也就是说，所谓驱动表、被驱动表，本质上是"查询优化器优化完以后"的结果，是 `EXPLAIN` 呈现给我们的，不是我们写在 SQL 里的书写顺序。

#### 内连接与 `STRAIGHT_JOIN`

于是问题就来了：内连接写 `a JOIN b`，那么 `a` 一定是驱动表吗？

不一定。我们的结论是"小表驱动大表"——如果 `b` 才是小表，那 `b` 就成为驱动表。

那如果我就是想指定顺序、不让优化器插手呢？用 `STRAIGHT_JOIN`：

```sql
SELECT ... FROM t1 STRAIGHT_JOIN t2 ON t1.b = t2.b ...
```

它明确要求优化器不要破坏书写的前后顺序。写成 `t1 STRAIGHT_JOIN t2`，就是让 `t1` 充当驱动表、`t2` 充当被驱动表；反过来写 `t2 STRAIGHT_JOIN t1`，那就倒过来。

> **提示**：`STRAIGHT_JOIN` 在这里的价值不是"提速"，而是**固定顺序**——你怀疑优化器选错了驱动表的时候，用它把顺序钉死，再去看成本差异。

#### 外连接会不会被改写

外连接要分左右来看。`a LEFT JOIN b` 跟 `b RIGHT JOIN a`，仅从字面上看，如果优化器**没有**帮我们改顺序，那可以说 `a` 相当于驱动表的位置、`b` 相当于被驱动表的位置。

关键问题：内连接优化器会改顺序，外连接也会吗？

也会。我为了验证这件事专门写了个例子：在 `atguigudb2` 这个库下建 `a`、`b` 两张表，插一批数据，然后做三组测试，全部用 `EXPLAIN` 看输出。

| 测试 | SQL 写法 | `EXPLAIN` 里看到的顺序 | 说明 |
| --- | --- | --- | --- |
| 1 | 外连接 + 关联字段 + 过滤条件 | 先 `b` 后 `a` | 明明写的是 `a LEFT JOIN b`，结果显示先 `b` 后 `a`，`b` 成了驱动表 |
| 2 | 同一个外连接，换一组过滤条件 | 先 `a` 后 `b` | `a` 成了驱动表，说明外连接里写在前面那张也不一定是驱动表 |
| 3 | 内连接 `a JOIN b` | 先 `b` 后 `a` | 顺序同样被颠倒，印证内连接由优化器说了算 |

测试 1 那个结果最能说明问题：SQL 里明明写着 `a LEFT JOIN b`，结果里却是先 `b` 后 `a`。那真实情况是什么？我去翻了优化器改写之后的 SQL——**它把这个外连接改造成了一个内连接**。既然已经变成内连接，那谁当驱动、谁当被驱动，就是优化器自己说了算。

> **结论**：外连接里写在前面那张表，不一定是驱动表。知道这一点就够用了。

### 三类连接算法

#### Simple NLJ（简单嵌套循环连接）

JOIN 操作本质上就是一次**循环匹配**。`a` 表连 `b` 表，连接字段分别是 `a.a` 和 `b.b`，从驱动表里取出一条数据，拿去和被驱动表里每一条记录一条一条地做连接——此时 `a` 和 `b` 都没有任何索引，非常干净的纯粹的两个普通表，这就是全表遍历：来一条数据，全表遍历一遍；再来一条，再遍历一遍。

```text
Simple NLJ（a、b 均无索引）

驱动表 a                         被驱动表 b
+---------+                      +---------+
|  a = 1  |--- 逐条比对 --------->|  b = 1  |
|  a = 2  |--- 逐条比对 --------->|  b = 2  |
|   ...   |--- 逐条比对 --------->|   ...   |
| a = 100 |--- 逐条比对 --------->| b = 1000|
+---------+                      +---------+
     |                                 ^
     +---- 每取出一条驱动表记录 -------+
           就把 b 全表扫描一遍（无索引可用）
```

读图：外层循环走驱动表 `a`，每走一行，内层循环把被驱动表 `b` 整表扫一遍，一次索引都用不上。

**成本账**：前提是 `SELECT ... FROM ... JOIN ... ON ... WHERE ...` 都过滤完之后，`a` 有 100 条、`b` 有 1000 条，那么

- 外表扫描次数：$1$（整体扫一遍表 `a`）
- 内表扫描次数：$a$，也就是 100
- 读取记录数：$a + a \times b$，也就是 $100 + 100 \times 1000$
- JOIN 比较次数：$a \times b$，也就是 $100 \times 1000 = 100000$ 次
- 回表次数：$0$——不涉及索引，也就没有回表这回事

> **结论**：这是最简单直接的算法，性能也最差。

既然有成本账，就能推出一个虽然浅薄但很有用的结论。看读取记录数 $a + a \times b$：$a$ 和 $b$ 在这个式子里权重并不一样，$a$ 出现在两层里，是**影响因子更大**的那一个。那自然 `a` 越小越好——`a` 相对 `b` 越小，整体成本越低。这就是"小表驱动大表"在数理上的出处。

#### Index NLJ（索引嵌套循环连接）

引入 Index NLJ 的目的很直接：**减少内层表数据的匹配次数**。Simple 场景里 `a` 每来一条数据就要全表遍历一遍 `b`，这个成本太高了。怎么办？给要当被驱动表的那张表的连接字段加索引——这里就是给 `b` 字段加。

加上索引之后就简单了：从 `a` 表取一条记录，直接拿 `b.b` 去索引里找，走 **B+ 树**定位，很快就能命中那条记录，而不是一条一条做遍历，性能显然就上来了。

这里有个细节必须分清：

> **易错点**：如果 `b` 字段上建的是**非主键索引**（也叫非聚簇索引、二级索引、辅助索引），最终要 `SELECT` 的信息可能还得**回表**一次；如果 `b` 字段恰好就是**主键**，那就完全不用回表，性能更高。

**成本账**：

- 外表扫描次数：仍然是 $1$
- 内表扫描次数：$0$——不用再扫全表，直接找索引走 B+ 树
- 读取记录数：$a + b_{match}$，前半是 `a` 的每条都读一遍，后半看索引总共匹配到多少条
- JOIN 比较次数：$a \times \text{index\_height}$——B+ 树有几层，来一条记录就往下走几层，三层就乘 3
- 回表次数：主键索引为 $0$；二级索引则等于匹配到的条数

这显然是我们追求的方向。但往往事与愿违，有两种情况会把它打回原形：

1. **没加索引**。经验少、不懂，就没建索引，那直接崩回 Simple。
2. **加了索引但索引失效**。SQL 写法有误导致索引失效，同样退回 Simple，这是最崩溃的。

#### Block NLJ（块嵌套循环连接）

为了兜住上面这两种情况，MySQL 又设计了一个更好的算法——**Block NLJ**。这里的 Block 是"块"的意思，不是"阻塞"。

先看它针对的是什么场景。回到 Simple：从 `a` 表取一条数据，把 `b` 表的数据加载到内存里，让这一条 `a` 走一遍比对；比完之后，加载进来的这份 `b` 数据就**被清掉**了。第二条 `a` 来了，再加载一遍 `b`，再比一遍，结束又清掉。这样下去 I/O 次数非常高。

我们希望的是**减少非驱动表加载到内存中的次数**。可这个次数直接关联的是 `a` 表的条目数——你想查的就是 100 条，条目数不是你能控制的。那就换个思路：控制**一次加载进内存的条目数**。原来是一条一条加，现在**一块一块地加**。一共 100 条，一次来 60 条，那还剩 40 条，分两次加载；比较温和一点的切法是 40、40、20，那就是三次。极端一点一次把 100 条全加载进来，那这 100 条就被完整缓存住，被驱动表 `b` 拿进内存，一次就把比较做完，不用销毁再加载。能不能一次装完，就看缓冲池大小——也就是 **join buffer**。

```text
Block NLJ：驱动表分块装入 join buffer，被驱动表整表加载一次

驱动表 a（100 条）
+----+----+----+ ... +----+   +----+----+ ... +----+
| a1 | a2 | a3 |     | a40|   | a41| a42|     | a100|
+----+----+----+ ... +----+   +----+----+ ... +----+
        |                              |
        v  第 1 块（40 条）             v  第 2 块（40 条）     第 3 块（20 条）
  +---------------------+        +---------------------+   +-------------+
  |     join buffer     |        |     join buffer     |   | join buffer |
  +---------------------+        +---------------------+   +-------------+
        |                              |                        |
        v  整表加载一次                 v  整表加载一次             v  整表加载一次
  +-------------------------------------------------------------+
  |              被驱动表 b（1000 条）—— 共加载 3 次              |
  +-------------------------------------------------------------+
```

读图：驱动表的数据按块进入 join buffer，每一块都把被驱动表整体加载一次做匹配；加载次数就是分块数 $k$。

**成本账**：

- 外表扫描次数：$1$
- 内表扫描次数：$\dfrac{a \times \text{used\_column\_size}}{\text{join\_buffer\_size}} + 1$——前半是分了几块，后半那个 $1$ 是被驱动表本身也要扫一次
- 读取记录数：$a + b \times \text{分块数}$
- JOIN 比较次数：$b \times a$（和 Simple 一样）
- 回表次数：$0$

Block NLJ 比 Simple 好很多，这是没有疑问的。

> **注意**：join buffer 里放的不只是驱动表的连接字段。除了 `a` 本身，`SELECT` 里涉及驱动表的那些字段也要放进去。所以没用的字段就别多写，上来一个 `SELECT *` 是很崩溃的——它把 join buffer 占满，一次能装的条目数就变少了。

> **注意**：如果有 $n$ 个 JOIN，也就是 $n$ 张表做连接，那就会有 $n - 1$ 个 join buffer。

#### 两个相关参数

既然希望驱动表装进 join buffer 的次数越少越好，就要看受哪些参数影响。

第一个参数决定你是否使用 Block NLJ。查系统变量可以看到它是 `on` 的，也就是 Block NLJ 处于启用状态，启用之后才能用这套算法。第二个参数是 **join buffer 的大小**，默认 **256K**，可以用 `SET` 调大（课上没演示调整过程）。

```sql
-- 查看 Block NLJ 是否启用
SHOW VARIABLES LIKE 'block_nested_loop';

-- 查看 join buffer 大小（默认 256K）
SHOW VARIABLES LIKE 'join_buffer_size';
```

> **注意**：join buffer 的上限在 32 位系统上是 4 个 G；64 位系统下可以申请大于 4 个 G，但 Windows 下比较特别——即便是 64 位，也还是 4 个 G 的上限，多出来的部分会被截断。

### 三类算法的成本对照

| 成本项 | Simple NLJ | Index NLJ | Block NLJ |
| --- | --- | --- | --- |
| 外表扫描次数 | $1$ | $1$ | $1$ |
| 内表扫描次数 | $a$ | $0$ | $\dfrac{a \times \text{used\_column\_size}}{\text{join\_buffer\_size}} + 1$ |
| 读取记录数 | $a + a \times b$ | $a + b_{match}$ | $a + b \times \text{分块数}$ |
| JOIN 比较次数 | $a \times b$ | $a \times \text{index\_height}$ | $b \times a$ |
| 回表次数 | $0$ | 二级索引为 $b_{match}$，主键为 $0$ | $0$ |

> **结论**：整体效率上，**Index NLJ 好于 Block NLJ，Block NLJ 好于 Simple NLJ**，这是没有问题的。

至此，底层介绍和数理支撑就把上一讲那些结论解释清楚了：为什么优化器会这么选，账是这么算的。

### "小表驱动大表"的精确化

#### 从表行数到结果集大小

严格来讲，"小表驱动大表"这句话是**不精确**的。什么叫小表，什么叫大表？更精确的说法是：**小的结果集驱动大的结果集**。

举个例子。`a` 表 100 行，`b` 表 1000 行，两表做关联——谁是小表谁是大表？大家可能异口同声：`a` 是小表，`b` 是大表。现在我再补一个条件：连接之后加了个 WHERE，对 `b` 的某个字段做了限制，比如小于某个数，过滤完以后 `b` 只查出 50 行，然后拿这 50 行去跟 `a` 关联。这时候谁小谁大？

> **结论**：要看**过滤之后**的数据。所以不该说哪个表大哪个表小，而要说**结果集**——过滤完得到的小结果集，才是那个"小"。

#### 行数乘以行大小

光看行数也不够。真正意义上的谁小谁大，应该是**表的行数乘以每行的大小**。

为什么？因为往 join buffer 里放的时候，每一条数据越小越好。每条越小，其实就是每一行的大小越小。行大小决定同样 buffer 里能塞进多少条目，条目越多，攒满 buffer 所需的分块数就越少。

> **提示**：行的"大小"要按实际用到的字段算——连接字段加上 `SELECT` 里涉及的驱动表字段，这两部分才是真正要放进 join buffer 的内容。

#### `STRAIGHT_JOIN` 的对照实验

为了把这件事说清楚，我写了个例子。两张表乍一看一模一样，眼睛都看酸了，猛一看没区别，实际上有区别——区别在书写顺序上：一个是 `t1` 去连接 `t2`，另一个是 `t2` 连接 `t1`。

后面跟的条件是**完全一样**的，也就是说表的行数被固定住了。那接下来谁算小结果集、谁算大结果集，主要区别点就在 `SELECT` 那块：

| 写法 | 驱动表 | 被驱动表 | `SELECT` 查出来的字段 | 谁当驱动表更合适 |
| --- | --- | --- | --- | --- |
| `t1 STRAIGHT_JOIN t2` | `t1` | `t2` | `t1` 只查 `b` 这个字段 | 推荐这一种 |
| `t2 STRAIGHT_JOIN t1` | `t2` | `t1` | `t2` 查了它所有字段（字段很多） | 不推荐 |

推荐第一种。原因很直白：把 `t1` 当驱动表，往 join buffer 里放的时候只需要放 `b` 这一个字段（关联条件也正好是 `b`），那在**相同 buffer 大小**的情况下，能放的条目数就更多；反过来用 `t2` 当驱动表，它涉及字段很多，一行数据占的空间大，能放的条目数就变少。一个显而易见的道理。

> **结论**：小表驱动大表的本质，是**减少外层循环的数据数量**。

#### 三条优化原则

把上面的账合起来，就是三条可以直接落地的原则：

1. **小的结果集驱动大的结果集**——减少外层循环的数据量。
2. **给被驱动表的匹配条件加索引**——上面那些结论都是在两个表都没有索引的前提下谈的；一旦给被驱动表的匹配字段加上索引，就进入了 Index NLJ 场景，内层循环次数大幅减少。
3. **减少驱动表不必要的字段查询**——只查必要的字段，每行占的空间就小，一次能装的条目数就多；再配合加大 join buffer 的 size，一次缓存的数据更多，分摊下来成本更低。

### MySQL 8.0 的 Hash Join 与版本差异

#### Hash Join 的原理与限制

讲到这儿本来就算完事了，但有个新特性必须提：**Hash Join**。因为咱们讲的这版 MySQL 里，情况已经变了。

刚才做测试的时候，有同学早就发现不对劲了：`EXPLAIN` 里看到的不是 `using join buffer (Block Nested Loop)`，而是 `hash join`——这又是什么鬼？这是版本差异导致的：我用的 MySQL 是 8.0.25、8.0.26 这样的 8.0 版本。换到 5.7（比如在 160 这台机器上重建一遍库、重加一遍数据，再跑同样的测试），`EXPLAIN` 里呈现的就是我们上面说的 Block NLJ 了。

> **结论**：如果你面试时只讲到这里（三类 NLJ 加成本公式），大概能打 80 来分——至少都懂，说得也还算清晰透彻，"小结"也能表达清楚。想上 90 分、95 分以上，就得把 Hash Join 这个新特性讲出来。

Hash Join 与 Nested-Loop 方式的区别在哪？

> **结论**：数据集比较小的时候，NLJ 那套还可以；一旦数据集比较大，推荐的就是 Hash Join。

原理是：优化器把两个表中**较小的那个表**，利用 **join key** 在内存中建立一个**散列表（哈希表）**，然后扫描较大的那个表，并**探测**这个散列表，找出与哈希表匹配的行。

Hash Join 的限制也很明确：

> **易错点**：Hash Join **只能做等值连接**。

另外，数据量大的时候因为它就是针对大表场景适用的，所以可能会占用临时空间，比如使用不同的区域、临时段这类机制。这部分细节课上就不展开了——整体时长已经比较长，高级部分会有一本教材对 Hash Join 做深入讲解。

#### 版本与参数的对应关系

把版本这条线索理一下：

| MySQL 版本 | 大表连接默认走什么 | 说明 |
| --- | --- | --- |
| 5.7 | Block NLJ | `EXPLAIN` 显示 `using join buffer`，即我们上面讲的块嵌套循环 |
| 8.0.18 及以后 | Hash Join | 明确开始使用 Hash Join |
| 8.0.20 及以后 | Hash Join | 废弃了 Block NLJ 这种方式，主要用 Hash Join（8.0.25 / 8.0.26 实测可见） |

## 145-子查询优化与排序优化
> 对应分集：P145 | 原始标题：《145-子查询优化与排序优化》

多表连接查询这一段先告一段落。前面收尾的时候提到过一个算法叫块嵌套循环（Blocked Nested-Loop），那是针对 5.7 场景的做法；到了 8.0，这个算法又被优化了，改成了哈希连接（Hash Join）。有兴趣的可以下来查一查 Hash Join 底层的具体情况，这里不展开。

接着来看 SQL 编写当中同样重要的一块内容：子查询。

### 子查询的开销与改写为多表连接

子查询这个东西，在它的定义被人提出来之后，好处是明摆着的：它可以一次性完成我们以前需要多个查询才能完成的工作，也能实现一个比较复杂的查询结构。但通常情况下，子查询的执行效率一般都不是特别高。原因我这儿列了几条，真正起作用的主要是两点。

#### 内层查询带来的临时表开销

第一点，执行子查询的时候，针对内层查询通常需要建立一张临时表。

- 建表要开销，用完之后还得把它销毁，整个过程中我们要消耗过多的 CPU 资源和 I/O 资源，这往往就是我们产生慢查询的主要源头；
- 同一时间它还占着内存空间。

第二点，针对这张临时表，我们是没办法给它建立索引的。没有索引可用，一旦这张临时表比较大——也就是我们所谓的结果集比较大——对我们性能的影响是非常大的。

#### 用 JOIN 替代子查询

这一节主要想抛一个结论：在实际开发当中，大家可以考虑把子查询再拆解成多个查询，拆解的过程中使用 JOIN 操作，也就是用多表连接的方式去替代子查询；一个搞不定，那就拆成多个。

然后在多表连接里，把前面讲过的那些规则用上：小表驱动大表、被驱动表上有索引，等等。

用 JOIN 替代子查询，最直接的好处是不用再建临时表了，而且速度比子查询要快——因为连接里还能创建索引。下面用两个例子来体会。

#### IN 子查询的物化过程

第一个例子在 8.0 里演示。先在 class 表的 monitor 字段上建一个索引，monitor 存的是每个班的班长。

```sql
-- 班级表的班长字段上建索引
create index idx_monitor on class(monitor);

-- 查询所有担任班长的学生的信息
select *
from student
where number in (
    select monitor
    from class
    where monitor is not null
);
```

这条查询的意思：先从班级当中找到班长，前提是这个班有班长（`is not null`）；找到班长以后，再看哪些学生就是这个班长，把班长本人的信息输出出来。

explain 的结果里有两处值得看。一处是 `select_type` 出现了 `materialized`——前面讲 explain 的 `select_type` 字段时提到过它，意思是执行子查询时会对内层查询做一次物化（materialize），物化之后的结果再和外层查询做连接。另一处是 `using where` 和 `using index`，说明相应的索引是用上了。

```text
外层查询(student)
      |
      | (1) 先执行内层查询
      v
内层查询(class: monitor is not null)
      |
      | (2) 结果物化(materialized)成临时表 --- 无法建索引
      v
   临时表  ---- (3) 与外层查询做连接 ---->  结果集
```

读图说明：`materialized` 把内层结果固化成一个临时表，再拿去和外层连接；这张临时表既吃 CPU、内存与 I/O，又不能建索引，代价就出在这里。

把它跑一下：花了 0.2 秒，而且没查出结果。正常来讲肯定是有结果的——只不过我们学生表里的 number 和 class 里的 monitor 都是随机生成的，两边没匹配上，是个挺尴尬的情况。实际场景里，每个班的班长一定是个学生，一定能匹配过来。

这个子查询可以改造成多表查询：

```sql
select *
from student s
join class c on s.number = c.monitor
where c.monitor is not null;
```

explain 的结果全是 simple 状态，索引也用得上。真跑起来，执行时间看着还长了一点，不过跟上面那个没差出数量级，还算同一个档次，效果不明显。

#### NOT IN 子查询与左外连接改写

第二个例子：取所有不是班长的同学的信息。还是先用子查询：

```sql
select *
from student
where number not in (
    select monitor
    from class
    where monitor is not null
);
```

explain 显示的是子查询的方式。执行一下，效率还挺高，0.007 秒。

改造成多表连接：

```sql
select *
from student s
left join class c on s.number = c.monitor
where c.monitor is null;
```

写法就是在左外连接的基数之上，把公共的那部分砍掉不要——让 `c.monitor is null` 就可以了（这里的 c 就是 class 表）。执行效率也很高，秒数很低，同样没拉出明显的差距。

但是从规律和结论上讲，我们还是推荐把子查询改造成多表查询，尤其当子查询比较复杂的时候，一定要考虑把它变成多表查询。

这里边其实蕴含了一个小公式，`not in` 或者 `not exists` 都可以替换成这样的格式：

```text
A left join B on <A 与 B 的关联条件>
where B.<关联字段> is null
```

原理是：`not in` 表示"不在这里边"。我们把两张表按关联字段相等连在一起，同时去掉 B 表里非 null 的那些数据，只留下 null 的，相当于把公共数据切掉了，剩下的就只有 A 表（左表）里独有的数据。这是个套路，可以直接拿去用。

子查询的优化比较简单直接，就过掉了，接下来看排序优化——这块涉及的内容还不少。

### ORDER BY 排序的两种方式与三条优化方向

先抛一个问题：在 where 条件的字段上加索引，性能会好一点，这个我们知道。那为什么还要考虑在 order by 的字段上加索引？

因为 order by 上如果能用上索引，排序这一步就省时间了——索引本身就是排好序的。

#### FileSort 与 Index 两种排序方式

MySQL 支持两种排序方式：FileSort（文件排序）和 Index（索引排序）。前面举例子的时候，大家已经见过 FileSort 了。

> **结论**：以后要养成一个概念——只要看到 FileSort，潜意识里就认为它是比较耗时的；能用 Index 的方式那是最好的。

两者的差别很实在：

- Index：索引本身就有序，你还按它排序，直接操作就行，效率比较高。
- FileSort：相当于要做一次文件排序，一般得把数据加载到内存当中再排，这时候要占用 CPU 资源。如果要排序的数据量很大，内存（缓冲区）里可能都放不下，那就得排一部分写出去、再排一部分再写出去，产生很多临时的 I/O 场景，效率是很低的。

#### 三条优化方向

实际开发中的建议有这么三条。

1. where 子句中、order by 子句中，都可以考虑使用索引。where 里使用是为了避免出现全表扫描；order by 里使用索引，主要目的是为了避免出现 FileSort。
2. 尽量使用 Index 方式完成 order by。如果 where 和 order by 后面是相同的列，那太完美了——按它过滤完，还用它排序，这就是最好的情况；如果两者不同，就可以考虑建一个联合索引，因为我们一般是先执行 where，所以 where 用的字段放前面、order by 用的字段放后面，比如 where 用 A、order by 用 B，就建成 `(A, B)`。
3. 如果实在没有办法使用 Index 这种方式，那就只能对文件排序方式尽可能地进行调优了。

> **提示**：也有极端情况——出现了 FileSort，性能反而比 Index 还要高。这不是理论上的空话，后面的案例实战里就有这样的例子。

### 排序索引的生效与失效案例

在看例子之前，先把 student 和 class 表里已经创建的索引删掉。造的索引多的话，就都要干掉。这里可以复用本章最开始创建的那个"删除表中所有索引"的存储过程。

```sql
-- 删完确认一下：两张表各自只剩主键索引
show index from student;
show index from class;
```

删完再 `show index` 一下，两张表各自就只剩一个主键索引了。

#### 无索引可用时的 FileSort

此时 student 表里只剩主键索引，来一条最朴素的排序：

```sql
select *
from student
order by age, class_id;
```

这就别想了，肯定没有索引可用，explain 结果是 `using filesort`——把数据加载到内存中排序。在这个结构的基础上再加一个 `limit`（也就是分页），也还是没有任何索引可用。

#### 覆盖索引与 select 列数对索引选择的影响

接着创建一个三字段的联合索引，注意字段顺序：

```sql
create index idx_age_cid_name on student(age, class_id, name);

select *
from student
order by age, class_id;      -- 用上索引了吗？
```

这条会不会用上索引？不好说，跟表里的数据量、跟字段都有关系。实测结果是：**没有用上索引，还是 `using filesort`**。

为什么一个以 age、class_id 打头的联合索引，它就是不用呢？这是查询优化器的优化策略在起作用。假如它用上这个索引，那就是一条二级索引；用完之后因为这里是 `select *`，要查所有字段，每一条数据还得回表——到主表的聚簇索引里逐条找到叶子节点。而我们这张表里有几百万条数据。查询优化器一算：算了，我还是别让几百万条数据都回表了，干脆把表里的所有数据都加载进来，在内存级别重新排个序，花的时间比回表还少。原因就是这个。

那把这颗星改掉，只查排序用到的两列：

```sql
select age, class_id
from student
order by age, class_id;
```

这时候竟然用上了索引，不再走 filesort 了。原因是没有回表。

> **定义**：覆盖索引（covering index）——查询需要的字段全部包含在二级索引里，不用再回到主表（聚簇索引）去取数据，也就是"没有回表"。

这里的二级索引中包含的字段完全能够支撑 select 要查的字段，都覆盖得了，不用再去找那个聚簇索引。既然不用回表了，走索引当然更好；如果这时候还用上面的 filesort，那确实太费事了。

#### limit 对索引选择的影响

再看在刚才那条 `select *` 的基础上加一个 limit：

```sql
select *
from student
order by age, class_id
limit 10;
```

一执行，发现用上了索引。有同学可能就迷惑了：难道 limit 跟索引也有关系？

原因还是上面讲的那件事。这张表数据量挺大，走二级索引之后每一条数据都要回表，再在聚簇索引里一条条找叶子节点，还不如直接针对内存当中的数据排序快；而现在不一样了——只要 10 条数据，那就干脆排好序以后取前 10 个，只对这 10 条回表，这个成本优化器认为很低。毕竟在内存中把所有数据的这两个字段重新排一遍，反而更慢。所以它就用上索引了。

经验是怎么增加的？有一些是理论上的规则，另外一些就是靠多见——见多了，见识和经验就有了。这一段的例子就是让大家大量地去见这些实际情况，知道是怎么回事。

#### 排序字段顺序错误导致的索引失效

再看下面一种情况：order by 的顺序写错了，索引也会失效。先创建一个新的联合索引：

```sql
create index idx_age_cid_num on student(age, class_id, student_number);
```

现在表上有两个大的联合索引：`(age, class_id, name)` 和 `(age, class_id, student_number)`。

判定规则其实前面讲过：

> **易错点**：联合索引的第 1 个字段都不考虑，那就肯定用不上——上来就写 `order by class_id`，或者 `order by class_id, name`，连最左前缀原则这一关都过不去，只能走 filesort。

顺序必须和索引里字段的先后一致：索引是 age 在前、class_id 在后，order by 也得先 age 后 class_id。更细的逐条判定，我放在文末的《本讲提到的题目》里，那里还有 `key_len` 给出的证据。

> **提示**：`key_len` 显示的字节数可以用来看索引实际用了几个字段。本表里 `age` 允许为 null，整数本身 4 字节再加上 1 个 null 标志位，占 5 字节；`class_id` 同样允许为 null，占 5 字节；`student_number` 是 not null 的，占 4 字节。三个字段全用上就是 $5+5+4=14$ 字节。

#### 排序方向与反向索引扫描

这一波数据只考虑 order by，不提 where：

| order by 写法 | 是否用上索引 |
| --- | --- |
| `order by age desc, class_id asc` | 用不上，走 filesort |
| 不带 age、直接从后面的字段开始 | 用不上 |
| `order by age asc, class_id desc` | 用不上 |
| `order by age desc, class_id desc` | 用上了，提示 `backward index scan` |

`order by age desc, class_id asc` 为什么不行？age 是一个降序，这就玩不了了。

`order by age asc, class_id desc` 也不行，原因是 age 是升序、class_id 是降序。假设索引里这两列都是升序的，当 age 相等的时候，找 class_id 还得逆着来；这么玩下来，还不如在内存中重新排序（filesort）来得快，于是干脆不用。

而 `order by age desc, class_id desc` 反而能用上索引，而且 explain 里有提示 `backward index scan`——倒着遍历就可以了。索引里 age 是升序、class_id 也是升序，那我们干脆整体倒着来，age 也好、class_id 也好，都相当于从大到小。

> **结论**：顺序错了不行，方向反了也不行；要反就全反，但顺序必须一样——先 age 后 class_id。

#### 过滤后的数据量对排序字段取舍的影响

这一波是 where 与 order by 一起出现的情况，体会一下"过滤"这件事的分量。

第一条查询在 where 里给出 age 的条件，再按 age 排序。大家可能会想：那是不是能用上索引了？确实用上了，而且是优化器综合判断之后挑的那个以 student_number 结尾的联合索引。但你会发现它的 `key_len` 只有 5——**难点不在于用没用索引，而在于为什么是 5**。

说白了，这时候它只考虑了 age 这一段，order by 的那个字段根本没管。所有的排序都是先基于过滤数据的：如果过滤完以后能把大部分数据都干掉，只剩几百条、几千条，甚至上万条，那优化器有可能就不再让另外一个字段进入索引了。几千条我们觉得挺多，对 CPU 来讲，在内存当中排几千条数据其实是 so easy 的事。这条查询的 rows 是 18000 多行，按我们的标准一万多条并不少，但 CPU 觉得这个数据其实不多，它就直接回表了，没有考虑 order by。这是优化器的选择，跟数据量有关系。

下一条把 order by 的字段换成 class_id、name，执行结果还是这样——同样没有考虑 order by，同样是一万多条数据。两条查询的过滤条件一样，rows 的数值自然也应该一样，只是都只用了 age 这一段。

再往下这一条，where 里除了 age 还加上了 class_id 的条件，同时保留 order by：优化器并不走那两个联合索引去排序。没有 limit 限制，意味着符合条件的数据全都要，数据量又很大，它觉得还不如直接做一次全表扫描加 filesort——何况本来也没有以 class_id 开头的索引。

而在这条查询的基础上只加一个 `limit 10`，同学反而会觉得：这跟上面不是一样吗？可一执行发现，还真用上了，而且两个字段全用上了。怎么理解？它是先按 age 用这个二级索引做了排序，在这个有序的基础上再去找 class_id 是 45 的记录，找到以后只取前 10 个，直接从这儿取走，所以性能会更高一些。这一条也正是前面说的那种"范围条件与排序字段二选一"的场景。

那把索引补上试试：

```sql
create index idx_cid on student(class_id);
```

再执行刚才那条带 class_id 条件的查询，毫无疑问，它一定会用上这个 cid 索引。也就是说，一开始如果没有 class_id 开头的索引，优化器就认为直接全表 filesort 更好；有了这个索引，它的选择就变了。

> **结论**：order by 与 where 一起出现时，可以考虑构建联合索引；但能不能用、值不值得用，还得经过查询优化器的分析——并不是我们看到"它应该能用"就一定用得上。

#### 联合索引 (a, b, c) 与 where/order by 的组合清单

最后做一个小结。假设表上有一个联合索引 `(a, b, c)`：

| 查询形态 | 能否用上 `(a, b, c)` 排序 |
| --- | --- |
| `order by a` / `order by a, b` / `order by a, b, c` | 可以 |
| 上述写法整体逆序（方向一致地倒着扫） | 可以，但 a、b、c 之间必须保持有序 |
| where a 为常量，`order by b` 或 `order by b, c` | 可以 |
| where a 为常量且 b 也为常量，`order by c` | 可以 |
| 排序字段乱序 | 不行 |
| order by 里出现索引之外的字段 | 不行 |
| order by 里不带首个字段 a | 不行 |
| where a 为常量，`order by c`（缺 b） | 不行 |
| where a 为常量，`order by a, d`（多了 d） | 不行，多了个 d 就不能按它排序了 |
| `where a in (...)` | 不行，in 相当于还是一个范围，范围就不行 |

> **注意**：上面只是泛泛地说一些规则。真正用没用上，还得结合具体表里的数据来看——优化器要核算一下成本，至少它会把索引作为一个选项来考虑，但选不选是另一回事。

### FileSort 与 Index 排序的性能对比实战

这个实战专门测一下 FileSort 和 Index 两种排序方式的差距。先把 student 表里的索引都干掉，然后看这样一个查询需求：where 里对 age 给出一个范围条件，order by 一个 name。

#### 无索引基线

```sql
select *
from student
where age < ?
order by name;
```

explain 的结果：`type` 是 ALL，并且有 `using filesort`。真跑起来其实速度还挺快，跑两遍也差不多，稳定在这个数值范围。

#### (age, name) 联合索引对 FileSort 的消除

为了去掉 filesort，我们建一个索引。这条语句里 age 上带着范围条件，name 是排序字段——先直接建一个由 age 和 name 构成的联合索引：

```sql
create index idx_age_name on student(age, name);

explain select *
from student
where age < ?
order by name;
```

用上索引了，后面也没有 `using filesort`，filesort 被去掉了。但 `key_len` 写的是 5，相当于只考虑到了 age 这一段，它还没给 name 面子——优化器觉得过滤完以后剩下的数据直接回表，性能就挺高。执行一下，效率确实比什么都不用的时候要快一些。

#### (age, student_number, name) 索引下的 FileSort

那去掉 FileSort 就一定比不删掉它性能高吗？再来一个方案：再建一个索引，顺序是先 age、再 student_number、最后 name。

```sql
create index idx_age_num_name on student(age, student_number, name);

explain select *
from student
where age < ?
order by name;
```

这次又出现 `using filesort` 了，而且前面的 `key_len` 写的是 9——用到了 age 和 student_number 这哥俩（$5+4=9$），没有考虑 order by，所以排序的时候还得 filesort。

按说出现 filesort，性能应该差一些吧？可真执行起来，**这条反而更快，是 0.002 秒**，比上面那个 `(age, name)` 方案的时间明显要短，都差出一个数量级了。

怎么解释这件事？因为 where 经过它过滤以后，结果数量本身就已经很少了。上面那个方案只考虑了 age、没考虑 name；而现在多了一个索引（注意前一个索引我还没删掉，是在多了一个索引的情况下），优化器毫不犹豫地就奔向了新索引的怀抱。言外之意，查询优化器认为：这两个条件合在一起构成的索引，结果数量已经很少了，`key_len` 是 9 说明 name 在不在索引里都无所谓——跟你那个 name 一点关系也没有。过滤完就这么点数据，order by 也不用考虑了，直接在内存当中针对这十条数据排序，效率当然高。

> **结论**：并不是看到 filesort 就要紧张、非得把它改成没有 filesort 不可。两个索引同时存在时，MySQL 会自动选择最优的方案，而且随着数据量的变化，它的选择也会跟着改变。如果经过前面这两个字段过滤之后数据量仍然极其庞大，那也不排除它会把 name 字段也用上。

#### 范围条件与排序字段二选一时的取舍

把结论提炼成一条可以照着用的规则：

> **结论**：当范围条件和 group by、order by 的字段出现二选一的时候，优先观察条件字段过滤的数量。如果过滤掉的数据量足够多、而需要排序的数据并不多，那就把索引放在范围字段上。

还有一点可以验证：如果不用 `(age, student_number, name)` 这个三字段索引，只建一个两字段的联合索引行不行？当然可以。drop 掉刚才那个三字段索引，再建一个两字段的，跑一遍同样的语句，效果是一样的。

### FileSort 的两种算法与参数调优

filesort 在实现上用的算法，我们也来熟悉一下。FileSort 有两种算法，主要是 MySQL 版本不同造成的：一个叫双路排序，一个叫单路排序。

#### 双路排序

双路排序指的是需要进行两次加载、两次磁盘扫描。以 `order by age` 为例：

1. 先找到 order by 的这个字段 age，把这一列所有的值加载到内存当中；
2. 在内存中针对 age 排一遍序；
3. 排好序以后，再拿着这些 age 回磁盘，找到表中对应的那一条完整数据，把完整的那条数据再取到内存里来。

整个过程需要两次磁盘扫描，比较耗时，因为 I/O 的次数比较多。MySQL 4.1 之前用的就是它。

```text
双路排序(two-pass, 4.1 之前)
  第 1 次扫描: 只读 order by 列(age) --------> 内存中排序
  第 2 次扫描: 按排好的 age 逐条回表取整行 ----> 内存
  结果: 2 次磁盘扫描, 大量随机 I/O
```

#### 单路排序

4.1 之后用的是单路排序，言外之意就是只扫描一次。做法是：不再先把 order by 那一列单独拿过来，而是上来就把磁盘中查询需要的所有列一次性读进来，在 sort buffer 里针对 order by 的 age 字段排序。既然要读所有列，它对内存的要求就更高一些。

好处是速度快了，而且把随机 I/O 变成了顺序 I/O。因为从磁盘读的时候，数据页都放在相应的区里边，一次性全读过来了，这就是顺序 I/O；而双路排序是先排好 age 这个字段，再拿着每一个 age 回去找表中具体的数据，这一条跟下一条有可能就在不同的页当中，那就是随机 I/O，性能肯定要慢一些。

```text
单路排序(single-pass, 4.1 之后)
  第 1 次扫描: 一次读入查询所需的所有列 ---------> sort_buffer
  在 sort_buffer 内按 order by 列(age)排序 ------> 结果
  结果: 1 次扫描, 顺序 I/O, 但占用内存更大
```

单路排序大体上是对双路排序的替换，但也不算严格的替换关系——双路排序也有它的好处，就是对内存的占用要小一点。

#### sort_buffer_size

单路排序占用的空间比较多，这时候就要担心容量够不够，于是提到了 `sort_buffer_size` 这个参数。

> **易错点**：容量不够的时候很恶心——排一部分就得写出去，然后再排下一部分、再写出去，来来回回反而造成大量的 I/O 操作，得不偿失。

所以我们要考虑增加这个容量的大小。`sort_buffer_size` 默认是 1 MB。既然开发当中我们尽量用 Index 方式完成排序，万一避不开、只能用 filesort，那就要对它调优，第一步就是把这块空间调大，让单路排序尽量别反复往磁盘里写。

#### max_length_for_sort_data

第二个可以调的变量是 `max_length_for_sort_data`，它影响的是我们到底选单路还是双路：拿要查询的字段长度跟这个变量做对比。

- 字段长度比较短（小于这个变量）：可以用单路排序；
- 字段长度比较长，已经大于这个变量：就走双路排序，性能相应地要稍微差一些。

所以 order by 的时候尽量**不要 `select *`**——那意味着你要查的字段是最多的，就有可能超出这个量，一超就开始用双路了。

### 本讲提到的题目

student 表上除了主键索引，只有两个联合索引：`(age, class_id, name)` 和 `(age, class_id, student_number)`。下面这几条排序，哪些用得上索引、哪些会失效？

1. `order by class_id`
2. `order by class_id, name`
3. `order by age, class_id, student_number limit 10`
4. `order by age, class_id`
5. `order by age`

解析：

- 第 1 条用不上。表里除了主键就是那两个联合索引，上来就是 class_id，联合索引的第 1 个字段都不考虑，最左前缀原则这一关就过不去，走 filesort。
- 第 2 条也用不上。同样没有 age，还是一样的问题。
- 第 3 条匹配得上，用上了索引，而且三个字段全用上了。`key_len` 是 14：age 允许为 null 占 5 字节，class_id 允许为 null 占 5 字节，student_number 非空占 4 字节，$5+5+4=14$。
- 第 4 条用上了，两个联合索引的前两个字段一样，优化器会从中挑一个。实测 `key_len` 是 73，说明连 name 也被算进去了——排完序以后，name 也处在有序状态。
- 第 5 条也能用上，而且选的是带 name 的那个索引，`key_len` 同样是 73。排完之后不光 age 有序，后面跟着的字段也都各有顺序了。

> **注意**：这几条判定都是在这张表当时的数据量下得出的。数据量不一样了，例子的结果也可能不同。

## 146-GROUP BY优化、分页查询优化
> 对应分集：P146 | 原始标题：《146-GROUP BY优化、分页查询优化》

`WHERE` 条件过滤的优化讲完了，`ORDER BY` 的排序优化也讲完了。剩下的两块拼图，一块是 `GROUP BY`，一块是 `LIMIT`——它们各自都有一个绕不开的坑：分组要么吃掉一次额外的排序，要么把 CPU 耗在明明可以省掉的操作上；而分页，尤其是那种翻到很后面才取十条数据的分页，看起来只是一句 `LIMIT`，执行起来却能把整张表往内存里搬一遍。

打个比方，你站在路口，远远看见一个卖糖葫芦的，你冲人家招手，人家背着那一大串糖葫芦大老远走过来，到了跟前你只说了一句“你这糖葫芦看着挺好的”，然后拿了十根就走了。这一趟人家的工夫，跟你拿到的十根糖葫芦，完全不成比例。深分页干的就是这件事：数据库辛辛苦苦扫过前面二百万行，只为把最后的十条交给你。

下面把这两件事讲清楚。

---

### GROUP BY 的两种执行路径

#### 使用索引时的排序消除

`GROUP BY` 使用索引的情况，跟我们前面讲的 `ORDER BY` 几乎是一致的。它不仅可以在有 `WHERE` 的情况下配合索引使用，在没有 `WHERE` 的情况下，也可以直接使用索引来做分组——这一点是没问题的。

当然，具体能不能用上，仍然要交给查询优化器去判断和选择：它会把不同方案的执行成本放在一起对比，再决定选哪一条路。我们写好语句，剩下的是成本说了算。

这里有一条原理性的推断必须记住：**`GROUP BY` 是先排序、再分组**。所以只要索引已经替我们把数据排好序了，分组这一步就可以直接做，排序被完全省掉。反过来，如果索引的顺序帮不上忙，这一次排序就躲不过去。

`ORDER BY` 与 `GROUP BY` 在这种“索引本身是否有序”的判断逻辑上是一套的，因此它们遵守同一条法则——最佳左前缀法则。索引的前缀列顺序对不对得上分组列的顺序，决定了这次分组能不能借上索引的力。

> **结论**：`GROUP BY` 与 `ORDER BY` 可以共用同一条优化思路——先看索引能不能提供有序性，能用就不要额外的排序；用不上，就得为排序付出代价。

#### 无法使用索引列时的参数调整

当无法使用到索引列的时候，情况就跟 `ORDER BY` 里那个 `filesort` 一样了。此时我们要做的，就是把下面两个参数的值调大：

| 参数名 | 作用 | 调整方向 |
| :--- | :--- | :--- |
| `sort_buffer_size` | 排序缓冲区大小，决定排序能否在内存中完成 | 适当调大 |
| `max_length_for_sort_data` | 参与排序的单行数据长度阈值，决定走全字段排序还是回表排序 | 适当调大 |

这两个参数在讲 `ORDER BY` 的时候出现过，这里原样适用，因为底层要解决的问题是同一个：排序数据放不下时，排序过程就会往磁盘上溢出，性能会明显掉下来。

---

### 分组与排序场景的编写规范

#### 过滤条件写在 WHERE 而不是 HAVING

`WHERE` 的效率高于 `HAVING`，所以能写在 `WHERE` 里的条件，就不要写到 `HAVING` 里。标准很简单：**针对非组函数（也就是非聚合函数）的条件，一律建议写在 `WHERE` 中**。

原因在执行的先后顺序上：`WHERE` 在分组之前就把不合要求的行筛掉了，参与分组的数据量从源头就变小；而 `HAVING` 是对分组结果做的过滤，它要等分组和聚合都算完才生效，前面那些本该被排除的行已经陪着算过一遍了。

> **易错点**：把聚合函数写在 `WHERE` 里，或者把普通列条件写在 `HAVING` 里，是最常见的两种写法错误。前者语法上就会报错，后者语法通过但白白多算了一遍聚合。

#### 少用 ORDER BY 并控制结果集行数

`ORDER BY` 要尽量少用。这件事最好去跟业务沟通：能不排序的就不排序，能在程序端做的排序就放到程序端去执行，不要全压在数据库上。

理由很直接：`ORDER BY`、`GROUP BY` 以及 `DISTINCT`，都是比较耗费 CPU 资源的操作。前面看 `ORDER BY` 的例子时已经见过走不到索引的情况——语句里带着 `WHERE` 又带着 `ORDER BY`，如果没能用上排序字段的索引，就直接进入 `filesort`；即便用上了字段索引，也可能一路回表，最后还是在内存里做一次排序。CPU 就这样被吃掉，这个一定要留意。

> **提示**：这里不是让你把所有排序都从 SQL 里删掉。数据库的排序是在数据落地的位置完成，不经过网络传输；程序端排序则要先取回更大的结果集。所以判断的依据是“这份数据最终要用到什么程度”——只为取前十行而在数据库里给整表排序，才是不划算的那一种。

还有一个具体标准要记：**包含 `ORDER BY`、`GROUP BY`、`DISTINCT` 的查询语句，`WHERE` 条件过滤出来的结果请保持在 1000 行以内**，否则这条 SQL 会很慢。

> **定义**：“`WHERE` 过滤出来的结果”指的是过滤之后、排序与分组动手之前的那份行数。这个 1000 行是判断“这条语句该不该换个写法”的一条实操线，而不是允许排序开销无限放大的上限。

### LIMIT 深分页的问题与优化

#### 案例：从 200 万位置取 10 条

分页查询这块，一般情况下的优化手段是创建覆盖索引，它能比较好地提高性能——覆盖索引是什么，后面单独讲。这里先看一个让人比较头疼的具体案例。

我们从这个 `student` 表中，查询从第 200 万这个位置开始的 10 条记录。语句的思路就是跳过 200 万行，只要后面的 10 条。

这条语句为什么崩溃？三个原因叠在一起：它没有提供任何可用于过滤的字段，用的是 `SELECT *`，并且 `SELECT *` 决定了它没有办法用上主键索引之类的索引来做覆盖。于是执行的时候，只能把数据都往内存里加载，等到数到那个位置了，才取出十条数据。

```text
分页偏移的扫描代价
──────────────────────────────────────────────
offset 2000000, size 10

读取起点 ──► 逐行扫描 ──────────────────────────► 第 2000000 行 ──► 取 10 行返回
             └──────── 读出来，然后全部丢弃 ────────┘              └─ 真正需要的部分 ─┘

扫描量 = 2000000 + 10 行
```

读图说明：真正需要交付的只有末尾 10 行，前面 200 万行被读进内存之后就直接丢弃了，扫描量与实际产出完全不成比例——这就是卖糖葫芦那趟路白跑的地方。

#### 优化方向：往主键索引（聚簇索引）上靠

优化的思路是：尽量用上主键索引，也就是聚簇索引，因为走它就不涉及回表的问题。回到具体语句上，判断分两个分支：

- 如果查的不是 `SELECT *`，字段都能被某条索引覆盖，那就考虑用覆盖索引；
- 如果查的就是 `SELECT *`，那就尽量使用主键索引。

那么用主键索引具体怎么做？关键前提是主键本身是不是自增的。

如果主键 `id` 本身就是自增的，那么构建出来的整个索引天然就是升序排列的。这时候不需要“跳过 200 万行”，直接按 `id` 的范围去定位就行：让 `id` 大于 200 万，再 `LIMIT 10`。这样等于直接定位到索引上的那一段，取十条数据出来即可，也不需要回表。

#### 主键非自增时的排序处理

有的同学会想到一个问题：如果这个 `id` 在赋值的时候不是自增的呢？比如先给 1、3、7，再给 2、5、6，最后给 10。主键不是自增的情况下，按“大于某个值”去取那一段，取出来的数据跟自增的情况下取出来的那一截就不一样了。

这个问题确实存在。但放到实际开发里想一想：无论是去百度、去淘宝，还是查我们自己系统的第 100 页数据，后台的数据量其实很大，而我们真正要保证的是什么？

> **结论**：分页只要保证**不重不漏**——第 100 页的数据不要跟第 99 页查重了（第 99 页已经出现过的又跑到第 100 页，这不合适），也不要漏掉一些数据，让每条数据都能出现一次，就够了。

正因为“绝对连续的行号”不是分页的业务要求，“跳过 N 行”这种性能很差的方式才被替换掉。

那么主键确实不是自增的时候怎么办？按 `id` 做一个排序，排序之后就可以直接使用聚簇索引了——思路始终是尽量往聚簇索引、主键索引上靠。排完序以后仍然用主键索引取出这十条数据，再通过一个 `WHERE` 条件去定位到目标行的 `id` 值上，把这十条数据取出来。两条路径的性能都比“读 200 万行丢 200 万行”要好得多。

```text
深分页的两条优化路径
──────────────────────────────────────────────
方案一：主键自增，逻辑顺序与自增顺序一致
    范围条件（id > 起始值） ──► 主键索引定位 ──► LIMIT 10 ──► 返回

方案二：主键非自增，逻辑顺序与自增顺序不一致
    按 id 排序 ──► 主键索引有序 ──► 取出 10 行 ──► WHERE 定位目标 id ──► 返回

共同点：都不再逐行扫描并丢弃，起点是“定位”出来的，不是“数”出来的
```

读图说明：两条路径的差别只在起点怎么来——自增主键直接用范围条件定位，非自增主键先按 `id` 排序再用条件定位目标行；共同点是都终止了“把前面所有行读出来再丢掉”这个动作。

这套做法在开发中是必须有的意识：**深分页的起点要靠条件定位，而不是靠逐行数过去。**

> **易错点**：用“前一页最后一条记录的 `id`”作为下一页的起点，前提是排序规则稳定且没有并发写入造成的位置漂移。翻页过程中有数据插入或删除时，相邻页之间仍可能出现重复或遗漏——这也是为什么要把“不重不漏”当作分页的验收标准，而不是“第 N 页恰好是第 N 段行”。

### 下一讲的接口

分页这一块，前面其实已经有好几个地方都提到过覆盖索引了：一般分页性能的提升、`SELECT *` 之外的字段选择，都指向同一个东西。这一讲把它当成“下一讲要展开的概念”用了两次，也该把它本身讲清楚——接下来我们就来看一看，什么叫覆盖索引。

> **本讲要点回顾**：`GROUP BY` 先排序再分组，所以它与 `ORDER BY` 共享同一套索引判断逻辑；用不上索引时靠 `sort_buffer_size` 与 `max_length_for_sort_data` 扛排序开销；过滤条件优先写在 `WHERE`；带排序类操作的语句把过滤结果压到 1000 行以内；`LIMIT` 深分页把“逐行跳过”换成“条件定位”，主键自增直接用范围条件，主键非自增先按 `id` 排序再定位。

## 147-覆盖索引的使用
> 对应分集：P147 | 原始标题：《147-覆盖索引的使用》

同一个索引，同一条语句，`SELECT` 后面只多写一个字段，`EXPLAIN` 的结果就能从“用上索引”翻成“全表扫描”。

这件事我们其实已经碰见过一次，只是当时在讲排序优化，顾不上展开。那会儿 `student` 表上建着 `(age, class_id, name)` 这条索引，我们把查询字段一个一个往里加，索引的可用性就跟着一起变脸。先把这一段完整走一遍，覆盖索引也就有了由头。

### 字段增删与索引可用性的变化

实验的底子是排序优化里用过的那条语句：`SELECT *` 查 `student` 表，`EXPLAIN` 出来 `type` 是 `ALL`，索引一点没用上。然后我们在这条语句上把 `SELECT *` 换成具体字段，一次加一个：

| 查询列表 | 与索引 `(age, class_id, name)` 及主键 `id` 的对应关系 | 是否覆盖 | `EXPLAIN` 的表现 |
| :--- | :--- | :--- | :--- |
| `age, class_id` | 两个字段都落在索引列之内 | 是 | 用上索引 |
| `age, class_id, name` | 恰好等于索引的三列 | 是 | 用上索引 |
| `age, class_id, name, id` | 索引三列再加主键 | 是 | 用上索引 |
| `age, class_id, name, id, student_number` | 多出一个 `student_number` | 否 | 用不上索引，退回 `ALL` |

读表说明：能不能用上索引，与这几个字段写在语句里的位置、顺序都无关，只看它们是否落在“索引列 ＋ 主键”这个集合里；只要有一个字段掉在集合外面，结论就翻转。

一路看下来确实蹊跷：一会儿能用上，一会儿又不能用上，加字段这里到底有什么讲究？讲究就在优化器的判断依据上——它发现走这条索引的成本确实更低，才会选它。而这种“用上索引”的场景，我们给它起个名字，就叫覆盖索引（Covering Index）。

> **结论**：字段能不能加、能加到几个，本质上是同一个问题——这条索引还能不能把查询要用的列全部提供出来。

那么，主键 `id` 明明不在索引的定义里，加进去为什么也还算覆盖？换成 `student_number` 为什么就不算了？答案要到二级索引的 B+ 树结构里去找。

### 覆盖索引的判定条件

#### 二级索引结构与回表

回想第 6 章我们一步步搭出来的那棵 B+ 树：从简易到复杂，迭代着把结构丰富起来，最后引出了聚簇索引和二级索引这对概念。这里以二级索引为例。

```text
表 t(c1, c2, c3)：c1 为主键，在 c2 上建一条普通二级索引

  二级索引（c2）                            聚簇索引（主键 c1）
      非叶子节点                                 非叶子节点
      [c2 | c1 | 页号]                           [c1 | 页号]
           |                                         |
           v                                         v
      叶子节点 [c2 | c1]   ---- 回表 ---->      叶子节点 [c1 | c2 | c3]
      按 c2 有序                                 整行数据
```

读图说明：二级索引的非叶子节点上放的是 `c2` 的值、与它对应的 `c1` 值，以及往下的页号；到了叶子节点，除了索引列 `c2` 本身，还留着主键 `c1` 的值——留着它，就是为了回表。

拿语句来说，`select * from t where c2 = 2`：走 `c2` 的二级索引 B+ 树往下判断，命中 `c2 = 2` 的那一项，从它身上取出对应的主键值（假设这个 `c1` 就是 3）；再拿着 `c1 = 3` 回到聚簇索引最后一级的叶子节点，把这一行的 `c1`、`c2`、`c3` 三个字段完整取出来。取 `c3` 的这一趟，就是回表。

现在把语句改掉，不查 `c3`，只查 `c1` 和 `c2`：`WHERE` 条件里的 `c2` 是索引列，`SELECT` 里的 `c2` 和 `c1` 在二级索引的叶子节点上本来就有。既然压根没打算查 `c3`，这一趟回表就完全没有必要。

> **定义**：一条查询所需要的列全部由某条索引直接提供，不必再回表取整行，这种情况就叫覆盖索引。

为什么边界恰好停在“索引列 ＋ 主键”？看图就清楚了：二级索引的叶子节点上只放了两类东西——索引列本身，以及主键值，除此之外它没有地方容纳查询要用的别的字段。所以一条索引能覆盖多少列，不取决于语句怎么写，而取决于它的叶子上到底存了什么。

#### 可覆盖字段的范围与超界后果

单列索引的场面比较窄，实际写语句时更常见的是多列联合索引。假设索引由三个字段构成，那么能覆盖的字段集合就是“这三个索引列 ＋ 主键”，一共四个：查这四个字段是覆盖，少写几个、只用到其中两三个，仍然是覆盖，**只多不得**。

讲到这里顺便落一条硬标准：一个索引包含了满足查询结果的数据，就叫覆盖索引，它包含查询里 `SELECT`、`JOIN` 和 `WHERE` 中用到的所有列——相当于把查询用到的所有列加上主键全部包进来。落到 §1 那个实验上，索引是 `(age, class_id, name)`，加上主键 `id` 一共四个字段，那就是上限；这四个字段之间没有顺序要求，写满可以，写少也可以，多一个就不行。

这里还有一点容易漏：`SELECT`、`JOIN`、`WHERE` 三处出现的列，算的是同一个集合，没有谁比谁特殊——`WHERE` 里拿来过滤的列，和 `SELECT` 里查出来的列，都要从这个额度里扣。所以判定覆盖与否不能只盯着查询列表看，条件里用到的列同样占地方。

多出来的 `student_number` 为什么致命？它既不在索引列里，也不是主键，二级索引的叶子节点上找不到它，想拿到就只能回表。而一旦确定要回表，优化器的算盘就变了：既然横竖要回表，那还不如直接对完整的一张表做扫描过滤（在排序优化那个场景里，就是干脆针对整表做一次排序），成本反倒更低——于是索引被彻底放弃。

> **易错点**：把“主键也算在覆盖范围里”当成可有可无的细节，是判断失误的主要来源。同一条索引，写不写主键，能覆盖的字段数差一个，判定结果可能正好相反。

### 举例一：不等值条件下的覆盖索引

先把 `student` 表上的索引清一清：删掉原有的索引，重新建一条 `(age, name)` 的联合索引，然后跑这条语句：

```sql
SELECT * FROM student WHERE age != 20;
```

`EXPLAIN` 一看，`key` 是空的，索引没用上。这跟我们前面讲索引失效时的结论一致：出现不等于，索引确实可能失效。

#### 失效规则与成本判断的关系

但“不等于就一定用不上索引”这句话，你们千万别记死。前面列的那些规则，是拿来帮我们做分析、做判断的，让我们写 SQL 的时候心里有个数；它们本身就是查询优化器从成本出发总结出来的近似规律，**成本的账一重算，规则立刻就能被打破**。

> **结论**：写 `age = 20` 这种等值条件，索引基本上一定会用上，这一点不用胆战心惊地猜；写 `age != 20` 这种不等值条件，只是“有可能”被放弃——是有可能，不是一定。

这件事我用一个比喻说透：查询优化器跟资本家一样，就是逐利的。你别指望它出于人道主义，也别指望它跟你讲理性，它只看哪条路更省钱，就往哪条路走。华尔街的资本早就不一定归属于美国了：中国发展得好，热钱就涌向中国；美国发展得好，热钱又涌回美国。它没有“我爱国”这一说，逐利才是它最根本的目的，查询优化器追的就是成本。

经济学也是同一个道理：我们建了一堆模型，而每个模型都建立在“人是理性的”这个大前提上，可现实里的人偏偏常常是非理性的。一个人在路上被人指使“你去把那个人打一顿”，你八成是不敢的；但要是周围有上百号人，其中有人喊一句“我们打他”，可能轰的一下就全上去了——因为在群体里你会觉得，真把人打伤了也未必轮到自己负责，“反正大家都打了”。单独一个人的时候，你可能反而胆怯一些。人性就是这么复杂，所以规则立起来是给人用的，不是用来把自己框死的。

#### 覆盖索引下的成本重算

把 `SELECT *` 换成具体字段：

```sql
SELECT age, name FROM student WHERE age != 20;
```

再执行一次，索引用上了。刚刚才说不等于会让索引失效，这里怎么又不失效了？——不是前面讲错了，是成本重新算了一遍。

走索引的成本一共两块：一块是针对二级索引 B+ 树本身的运算，另一块是回表。这两块加起来要跟“不用索引、直接全表扫描再逐行过滤”比一比，谁便宜听谁的。

- 写 `SELECT *` 的时候：`age`、`name` 能从索引里拿到，其余字段拿不到，必须回表补齐。两块成本加在一起，比全表扫描还高，优化器自然放弃索引。
- 改成 `SELECT age, name` 之后：要查的两列索引里都有，回表这一整块成本被砍掉，只剩一块成本，比全表扫描便宜，优化器就大胆地用上了这条索引。

把这两笔账并排放，差别只在“回表”那一栏：

| 写法 | 二级索引运算 | 回表 | 与全表扫描相比 | 优化器的选择 |
| :--- | :--- | :--- | :--- | :--- |
| `SELECT *` | 需要 | 需要（补齐索引里没有的列） | 更贵 | 放弃索引，走全表扫描 |
| `SELECT age, name` | 需要 | 不需要，索引已覆盖 | 更便宜 | 用上索引 |

读表说明：条件 `age != 20` 一个字没改，成本结构却从“两块”变成“一块”，这就是同一类写法在两次执行里给出相反结论的全部原因。

> **易错点**：不要把这些失效规则当成铁律去背。语句一改、字段一换、回表成本一省，结论就可能翻转——判据始终是成本，不是规则本身。

### 举例二：前导通配符条件下的覆盖索引

规则得先立起来，再一个一个打破，顺序不能反。就像教小孩：你得先告诉他世界是有爱的、好人多、善有善报恶有恶报，先把最基本的规则立住；等他长大了，发现世界上也有坏人、人有时候也会说谎，他再回过头来说，世界上不全是好人，但好人还是多一些，还是要乐观地看这个世界。一上来就跟他说世界很复杂、没有规则，他是接不住的。

第二个例子用的还是这条 `(age, name)` 索引，语句是前导通配符的模糊查询：

```sql
SELECT * FROM student WHERE name LIKE '%...';
```

`%` 写在最前面，而索引是按 `name` 排好序的，前缀不定就没法用它来定位，所以用不上索引——而且这里还有另一半原因：`SELECT *`。

把 `SELECT *` 具化成三个字段：

```sql
SELECT id, age, name FROM student WHERE name LIKE '%...';
```

索引又用上了，原因跟举例一完全是同一个：要查的 `age`、`name` 是索引列，`id` 是主键，三个字段在二级索引的叶子节点上凑齐了，不用回表，优化器就会考虑用它。甚至连 `name` 都可以从查询列表里删掉，只查 `age` 照样能用上。

> **结论**：判定标准可以压成一句话——只要这次查询不需要回表，优化器就会考虑把索引用起来。前导通配符本身并不单独判死刑，真正决定结果的是“要不要回表”。

### 覆盖索引的收益与代价

先说一段备课的实话。我一开始写这一节，只写了覆盖索引的好处，列了一条、两条就收工，写完自己觉得不对：任何事物出现，都应该是有利有弊的，这是最基本的一条事实和原则。所以我一定要给它补一个弊端出来，也确实补得出来。

你们将来判断一个新技术也是同一套路数。框架层出不穷，SSH、SSM、微服务，一波接一波，每一个新东西都是对旧东西的迭代，好处当然有；但你同时得问一句它的弊端在哪。就像商场里拉着你办信用卡，送一套厨具，或者送一个行李箱，质量看着还不错，还说办了不开卡也行、没有年费——这种好事，是做慈善的吗？肯定不是。那你就要想它图什么，想清楚了才不至于在那里踩坑。

也总有同学问我：“老师，你学一个技术是怎么学的？”我的回答是：先看它实际用在什么地方，然后不断地问为什么。这个“为什么”当然也要适可而止，人的精力有限，探到一定程度就没必要再往下探了——开发里用得到那个程度，面试的时候人家可能再往下“恶心”你一下，讲课的时候我会讲得更多一点，但总不至于一路退到 $1+1=2$ 这种最原始的程度去比。把深度控制好，比一味往下钻更有用。

#### 收益一：避免索引的二次查询

第一条好处，是它避免了 InnoDB 的表做索引的二次查询，说白了就是避免回表。回表省掉，成本就降下来，优化器在挑执行方案时会优先考虑它，不用像原来那样直接走全表扫描——那样性能是很差的。手上多了一个更优的选择，整条语句的执行时间更短，效率也就上来了。

#### 收益二：随机 I/O 转为顺序 I/O

第二条好处，是把随机 I/O（Random I/O）变成了顺序 I/O（Sequential I/O）。这句话值得展开，我们还是用那棵树来解释。

假设做的是范围查询，让 `c2` 从 2 查到 20，命中的是一批数据，它们都落在 `c2` 二级索引的叶子节点上，而且在索引里彼此挨着。

```text
范围查询 c2 ∈ [2, 20]

  二级索引叶子节点（按 c2 有序）
      [2] [3] [4] [5] ... [20]        <- 数据挨着，顺序 I/O
       |   |   |   |        |
       |   |   |   |        |  回表
       v   v   v   v        v
  聚簇索引叶子节点（按主键定位）
      页A(区1)   页K(区3)   页B(区1)   <- 位置散落，随机 I/O

  一个区 = 64 个连续页 × 16 KB = 1 MB
```

读图说明：在索引这一侧，这批准数据是连续的；一旦回表，它们会按主键落到聚簇索引的各个位置上，相邻的两条记录可能落在不同的页，不同的页又可能落在不同的区，这一趟读下来就是随机 I/O。不回表时只读索引页本身，数据天然有序，挨着的数据可能就在一个页里；即使不在一个页，那些页也通常落在同一个区里，本身还是连续的，一路顺序读下去即可——这就是顺序 I/O。

回表这一侧为什么会散？因为聚簇索引是按主键排的，同一个 `c2` 区间里的记录，主键可能相差很远，命中的行数越多，要回表的次数就越多，而每一次落点在哪个页、哪个区，事先并不知道。索引这一侧刚好相反：数据在叶子节点上已经按 `c2` 排好序，一页装不下就顺延到下一页，页与页之间本来就是接着的。两边一对比，差别不是“要不要多读一次”，而是“读的时候要不要来回跳”。

这里补一个我们前面算过的数：一个区有 64 个连续的页，每页 16 KB，所以 $64 \times 16\ \text{KB} = 1\ \text{MB}$。

> **结论**：覆盖索引砍掉的看似只是一个回表动作，其实砍掉的是一次随机 I/O，剩下的只要顺序 I/O 就够了，性能提升相当明显。也正因为覆盖索引可以减少树的搜索次数、显著提高性能，它才成为一种常用的性能优化手段。

#### 代价：索引变长与空间占用

再说弊端。前提是一条大家都认可的事实：索引字段的维护是要付出代价的，所以我们前面反复讲，不要无缘无故地多建索引。

那么为了用上覆盖索引，会发生什么？本来 `WHERE` 里只涉及两个字段，针对这两个字段建一条联合索引就够了，占用也小。可你现在 `SELECT` 里列了四个字段，一看用不上覆盖索引了怎么办——把索引建长一点，在那两个字段之外再补两个进来，目的只有一个：往覆盖索引上靠。

```text
优化前：WHERE 只涉及 (a, b)
    索引 (a, b)          -> 只服务过滤条件，占用小

优化后：为了覆盖 SELECT 出来的 (a, b, c, d)
    索引 (a, b, c, d)    -> c、d 不进过滤，只为免回表而存在，占用更大
```

读图说明：`c`、`d` 根本不参与条件过滤，它们进索引的唯一作用是让查询不用回表，代价是索引更长、更占空间、维护成本更高——这部分多少有点冗余了。

多出来的列是要真金白银养着的：索引更长，占用的空间就更多，写数据时要维护的索引项也更多，整体成本随之抬高。所以这笔账不能只看查询这一侧——查询是快了，代价转移到了存储和写入上。

到底加合适还是不加合适，这是业务的 DBA 或者数据架构师要衡量、要拍板的问题。这也算覆盖索引的一个弊端。

> **本讲要点回顾**：覆盖索引 = 查询所需的列全部由一条索引（索引列 ＋ 主键）提供，不必回表；`SELECT` 列表的字段落在这个集合里就是覆盖，可少不可多、没有顺序要求；能否用上索引始终由查询优化器按成本决定，所以 `!=`、前导通配符这类“通常失效”的写法在变成覆盖索引之后仍可能用上；它的收益是免去二次查询、把随机 I/O 变成顺序 I/O，代价是可能为了凑覆盖而把索引建长，带来冗余、空间占用与维护成本。

## 148-索引条件下推(ICP)
> 对应分集：P148 | 原始标题：《148-索引条件下推(ICP)》

### 索引下推是什么

接着往下看一个内容，叫**索引下推**。它的全称是**索引条件下推（Index Condition Pushdown，ICP）**，平时口语里就叫索引下推。

它是 **MySQL 5.6** 引入的一个新特性，是一种**在存储引擎层使用索引过滤数据的优化方式**。猛一看这句话不太好懂，但它的原理其实并不难——它和我们前面讲的**覆盖索引**是同一类东西：不了解的时候总觉得很高大上，了解之后发现也就那么回事。

索引下推是**查询优化器在优化过程中的一个具体策略**。这个概念对你们也并不完全陌生：上一章讲**性能分析工具**、讲 `EXPLAIN` 的时候，`Extra` 字段里有一个值叫 `Using index condition`，它代表的就是索引条件下推。当时只是简单提了一句，有同学没有理解透彻，所以这里再把它讲一遍——而把这个过程讲清楚，实际上就是在讲索引条件下推的原理。

> **提示**：这个知识点在面试里也常被问到——索引下推是怎么回事、它的原理是什么、好处是什么，让你刻画一遍。前段时间就有个同学面试被问到，没有说清楚，回来问我，我给他讲了讲，发现其实也不是特别难。所以这一讲值得你彻底弄明白。

### 原理：从「以为的过程」到真实的过程

#### 一个直观的例子

先看第一个场景。前提是 `key1` 这个字段上**有索引**——这是前提，得有索引。查询的写法是 `key1` 上既有范围条件、又有一个以 `%` 开头的模糊匹配条件。

`%` 开头的 `LIKE` 用不上索引，这一点前面已经反复说过，所以这里真正能驱动索引的只有前面的范围条件。我们**以为**的过程是这样的：

- 通过 `key1` 上的索引去查数据，假设满足范围条件的有 100 条；
- 这是二级索引，那这 100 条**每一条都要回表**——回表到聚簇索引上，逐条找到它对应的整行记录；
- 拿到聚簇索引里的数据之后，再判断 `key1` 字段是否满足后面那个模糊条件，满足就留下，不满足就丢掉；
- 假设过滤完只剩 10 条，最终结果就是这 10 条。

也就是说：**100 次回表 + 100 次条件过滤**，最后留下 10 条。

#### 真实的过程：条件被下推

查询优化器实际做的不是这样。它同样先查出那 100 条记录，但**并不急着对这 100 条都做回表**，而是先做后一个条件的判别——**条件下推（pushdown）**，推到哪儿？推到后面那个条件所在的位置。先不要着急回表，把条件推到那里去。

关键点在于：`key1` 所用的这个索引当中，**本身也包含后面那个字段**（这个例子我是刻意设计成前后都是 `key1` 的，先说这种场景）。既然索引里有这个字段，那这 100 条记录在索引里就能直接判断是否满足后面的条件——先在索引层把这 100 条过滤一遍，假设过滤完只剩 10 条，**再拿着这 10 条去回表**。

于是回表次数从 100 次降到 10 次。这就是 ICP。

这里要抓住一个认识上的分界：**回表这件事本身没有被取消，它只是变少了**。查询该回表还是要回表，最后那 10 条仍然要去聚簇索引里把整行取出来；ICP 改变的是「拿多少条去回表」——从「满足范围条件的全部候选」变成「在索引层先过滤过一轮的候选」。相应地，服务器层拿到的也不再是 100 条待判断的记录，而是 10 条已经过了后置条件的记录。

```text
【没有 ICP】服务器层驱动，索引层只负责范围扫描
                索引层（二级索引）        服务器层
  范围条件  ──►  取出 100 条索引记录  ──►  回表 100 次（聚簇索引）
                                              │
                                              ▼
                                    逐条判断后置条件 → 留下 10 条
                                    随机 I/O 次数：100 次

【有 ICP】条件被下推到索引层
                索引层（二级索引）        服务器层
  范围条件  ──►  取出 100 条索引记录
                      │
                      ▼
              在索引层用后置条件过滤（该字段就在索引里）
                      │
                      ▼
                  留下 10 条  ──────►  回表 10 次（聚簇索引）
                                    随机 I/O 次数：10 次
```

读图要点：两种走法的**范围扫描工作量完全相同**，差别全部发生在候选记录产生之后——ICP 把只能靠整行数据判断的条件，提前到索引层就能判断的位置，于是回表次数与随机 I/O 次数一起被压下去了。

> **定义**：索引条件下推（ICP）是指，当 `WHERE` 中的某个条件所在的列**包含在所使用的索引中**、但这个条件本身**用不上索引的有序性**时，把这个条件下推到存储引擎层，在索引记录上先做一次过滤，只把过滤后剩下的记录回表取整行。

#### 它省下的不只是回表次数

回表次数减少，同时减少的是**随机 I/O**。原来那 100 条数据，每一条在聚簇索引里所在的数据页**可能并不连续**；要把一条记录加载进内存，它所在的那个页就得一并载入，这就是随机 I/O。

把这个数字放大一点感受一下：假设范围条件查到的是 **10,000 条**，而第二个条件过滤完以后只剩 **1 条**，甚至一条都没有——写得夸张一点，就是为了让你看清楚：

- 不用 ICP：10,000 条全部回表，再做 10,000 次随机 I/O 把数据页加载进来；
- 用 ICP：先在索引里过滤到 1 条，只回表一次，只把那一条记录所在的数据页加载一次。

两者的性能差别有多大？是不是很大。这就是索引下推省下来的东西：**回表次数**和**随机 I/O 次数**。

为什么随机 I/O 这一项必须单独拎出来说？因为随机 I/O 的次数并不等于「读到的记录条数」，而等于**这些记录散落在多少个数据页上**。100 条记录如果分散在几十上百个不同的页里，就得把这几十上百个页分别从磁盘随机读进内存；哪怕某一条记录我们最终不要，它所在的那个页也已经付出了加载成本。ICP 把候选集从 100 条压到 10 条，压下去的不只是 90 次回表，还有这 90 条所牵连的那些数据页的随机加载——**越往后过滤性越强，省得越多**。

> **结论**：ICP 的收益来源只有一句话——把原本必须回表之后才能判断的条件，提前到索引层判断，从而减少回表次数与随机 I/O 次数。数据量越大、后置条件过滤性越强，收益越明显。

### 联合索引场景：更一般的情形

上面那个例子其实**不够典型**，因为前后都是 `key1`，展示不出更一般的场景。所以再举第二个例子，这个例子更具备普遍性——**索引条件下推更多时候针对的是联合索引**。

#### 表结构与索引

这个表上建了一个联合索引，三个字段：`zip_code`、`last_name`、`first_name`。

查询里用到了 `zip_code`，**对上了**；`last_name` 也对上了，但它用的是 `%` 开头的 `LIKE`，所以**用不上**；后面还有一个条件，对应的字段**不在索引里**——这是我刻意这样设计的，就是为了体现更一般的场景。

结论是：这个索引**只被用上了前面一部分**，`key_len` 上也能看得出来。

> **提示**：`key_len` 是 `EXPLAIN` 里判断「联合索引到底用上几个字段」的现成工具。它显示的是本次实际用到的索引键长度，用上的字段越多、长度越大；一旦某个字段因为条件失效（比如 `%` 开头的 `LIKE`）而没能参与定位，`key_len` 就停在前一个字段上，不会继续往后走。看到 `key_len` 只覆盖 `zip_code` 这一段，就说明索引的有效范围到此为止——**注意，有效范围到此为止，不等于这个索引里没有 `last_name`，这两件事要分开看**，ICP 能利用的正是后者。
>
> 反过来说，**字段不在索引里，条件就下推不了**。所以例子里我把最后一个条件的字段刻意选在联合索引之外：它不是用来展示 ICP 的，而是用来划出 ICP 的边界——能下推的只有索引里有的字段。

#### 两种走法的对比

没有 ICP 时的过程，就是前面说的「我以为什么」：索引只能有效到 `zip_code` 这一段，从索引里找到一波满足该条件的记录，假设有 1,000 条，那这 1,000 条**每一条都要回表**——回表找主键索引（聚簇索引）。而且这 1,000 个数据项，**每一项都要以数据页的方式加载进内存**，然后才在里面判断第二个条件、第三个条件，过滤完可能只剩 10 条。

有 ICP 时：索引里除了 `zip_code`，**还包含 `last_name`**。虽然 `last_name LIKE '%张%'` 用不上索引的有序性，但**这个字段就在索引里**，所以可以在索引层就判断一下 `last_name` 是不是「有张的」。`zip_code` 过滤完之后，再在索引里过滤到只剩「有张的」，假设剩下 100 条。至于再往后那个条件——**用不了了，因为联合索引里根本没有这个字段**。

于是拿这 100 条去回表，加载进来之后再看这 100 条里哪些满足最后那个条件，再过滤一次，只剩 10 条。这就是 ICP：回表次数减少了，回表之后把数据加载进内存的**随机 I/O 次数也减少了**。

```text
索引：idx(zip_code, last_name, first_name)   PK(id)

查询条件：  zip_code  范围条件        ← 能用索引定位
            last_name LIKE '%张%'    ← 用不上索引有序性，但字段在索引里
            另一条件                   ← 字段不在索引里

没有 ICP：
  索引层 ── 按 zip_code 扫描 ──► 1,000 条候选
                                  └─► 1,000 次回表 → 1,000 次随机 I/O
                                        └─► 再判断后两个条件 → 10 条

有 ICP：
  索引层 ── 按 zip_code 扫描 ──► 1,000 条候选
            └─► 在索引层判断 last_name LIKE '%张%' ──► 100 条
                                                       └─► 100 次回表
                                                             └─► 判断最后一个条件 → 10 条
```

读图要点：能下推的只有「字段在索引里」的那一个条件；字段不在索引里的条件，无论有没有 ICP，都只能在回表之后由服务器层判断。

#### 什么时候体现不出 ICP 的好处

再设想一种写法：`last_name LIKE '张%'`（张开头，不是 `%` 开头），再加一个 `first_name LIKE '三%'`。

这时候虽然也写了 `Using index condition`，但**真正意义上还没有起到多大作用**。为什么？因为这两个条件对应的列都在联合索引里，而且它们是**确定的**（非 `%` 开头），使用索引的时候，第一个字段、第二个字段、第三个字段**本来就会一起考虑上**，然后再回表。既然索引本身就能用上这些字段，那就体现不出索引条件下推的好处到底在哪。

> **结论**：ICP 真正发挥作用的场景是——**字段在索引里，但这个字段对应的条件失效了、用不上索引的这部分能力**，此时在回表之前用它在索引层做一次数据过滤。这才是它的价值所在。

---

### 执行计划里的 Using where 与默认开启状态

执行这个查询的时候，除了 `Using index condition`，还会看到 **`Using where`**。这后面那个条件的字段不在索引当中，所以它会在 `Extra` 里留下 `Using where`。

如果你不想看到 `Using where`，只需要把那个不在索引里的条件去掉，再执行一次，`Extra` 里就只剩索引条件下推了。

同时也会发现：**默认行为下 ICP 就是开启的**。既然默认开启，下一个问题就是它如何开启和关闭。

---

### 开启与关闭：optimizer_switch 与 NO_ICP

默认情况下这个参数处于**开启**状态。要关闭它，就用 `SET` 把优化器开关里的 `index_condition_pushdown` 改成 `off`：

```sql
-- 关闭索引条件下推
SET optimizer_switch = 'index_condition_pushdown=off';

-- 重新打开索引条件下推
SET optimizer_switch = 'index_condition_pushdown=on';
```

关掉之后再 `EXPLAIN` 执行一遍，会发现**索引条件下推没有了**（`Extra` 里不再出现 `Using index condition`），性能随之下降；改回 `on` 再执行，它又回来了。这就是索引条件下推的开启与关闭。

关闭还有**第二种方式**：不改变量，直接在写 SQL 的时候加上 **`NO_ICP`** 这个优化器提示，表示这条语句不使用索引条件下推。这种写法不需要「一会儿想用还得再打开」，作用范围只在这一条语句上。

> **易错点**：两种关闭方式的作用域不同——改 `optimizer_switch` 是**会话级/全局级**的开关，会影响之后的语句，用完还得自己改回来；写 `NO_ICP` 只影响**当前这一条 SQL**。做对照实验时后者更省事。

---

### 性能对比实验：100 万条数据下的实测

理论说清楚之后，从一个实际例子看看开启和关闭到底有多大区别。

#### 造数据

向 `people` 表里**批量添加 100 万条数据**做一个前后对比。造数据这件事通过**存储过程**来完成：写一个向 `people` 表中添加 100 万条数据、用来测试 ICP 开启与关闭状态下性能的存储过程，选中执行，然后 **`CALL`** 调用它即可。

```sql
-- 调用存储过程，批量写入 100 万条测试数据
CALL insert_people(1000000);
```

调用之后**执行时间会相对久一些**，这中间要等它把 100 万条写完。跑完之后，先确认一下数据是否到位：

```sql
SELECT COUNT(*) FROM people;
```

先把 `profiling` 打开——它**默认是关闭的**：

```sql
SET profiling = 1;
```

#### 两次执行与耗时对照

在同一台机器、同一份数据上，用同一张查询做两组对照：

| 对照组 | 索引下推状态 | 执行耗时 |
| --- | --- | --- |
| 第 1 组 | 开启（`on`） | 明显更短 |
| 第 2 组 | 关闭（`optimizer_switch` 改 `off`，或 SQL 里加 `NO_ICP`） | 明显更长 |

第 1 组在 ICP 恢复成 `on` 的状态下执行，查完之后记录耗时；第 2 组把 ICP 关掉再执行同一条语句，光是等它跑完就能**明显感觉到时间长了不少**。两组一对照，用时上的差别非常明显，高下立判。

#### 用 profiler 排除「其他原因」

想把细节也看清楚、想确认会不会是**其他原因**造成的差别，可以继续看：

```sql
SHOW PROFILES;
SHOW PROFILE FOR QUERY 1;
SHOW PROFILE FOR QUERY 2;
```

`SHOW PROFILES` 里能看到刚才两次执行各自的耗时；再分别 `FOR QUERY 1`、`FOR QUERY 2` 看具体细节，会发现**主要的耗时区别就落在这个执行过程当中，跟其他环节没有关系**。也就是说，执行过程上的差别主要就是 ICP 用与不用造成的。

> **结论**：数据量大起来之后，ICP 开启与关闭的耗时差距很大。这也是为什么它值得单独拿出来讲——它不是纸面上的优化，是能实测出来的优化。

---

### 使用条件与限制

最后看 ICP 的适用条件，这几条了解一下即可，但每一条背后都有明确的原因。

#### 针对的访问类型

针对访问表的类型（也就是讲 `type` 时的那套分类），只有 **`range`、`ref`、`eq_ref`、`ref_or_null`** 才适用于 ICP。

同时，ICP 对 **InnoDB 和 MyISAM 两种存储引擎都生效**。

#### 只适用于二级索引：前提是「会发生回表」

这里要强调 ICP 的一个前提——**它一定得回表**。回表之前，我们多做了一个比较、多做了一个条件的判断，因为那个字段出现在索引当中了。

如果本身**没有回表这个行为**，那 ICP **就没有意义了**。什么时候没有回表行为？

- 一种是查询用的就是**聚簇索引**——聚簇索引里直接就有整行数据，不存在回表，所以 ICP 不能用于聚簇索引。
- 另一种是**二级索引 + 覆盖索引**——覆盖索引不需要回表，所以 ICP 也就用不上了，不支持。

> **定义**：覆盖索引（covering index）指查询所需要的全部字段都能从索引里取到，因此不需要回表。

这个「水火不容」的关系，很像 Java 里的 `final` 和 `abstract` 两个关键字——**它们不能同时修饰一个类**，有点势不两立的意思。记住这个类比，这两条限制就不会混。

#### 相关子查询的条件不能使用 ICP

**相关子查询**的条件不能使用 ICP，因为涉及到**内外条件之间的相关性**问题。这一条注意一下就行。

---

### 小结：三条要点

把这一讲压成三句话：

1. ICP 是 MySQL 5.6 的新特性，属于查询优化器的一个具体优化策略，`EXPLAIN` 的 `Extra` 里显示为 `Using index condition`；
2. 它的原理是把「字段在索引里、但条件用不上索引能力」的那个条件**下推到存储引擎层**，在回表之前先过滤，从而减少回表次数与随机 I/O 次数；更多时候针对的是**联合索引**；
3. 它默认开启，靠 `optimizer_switch` 里的 `index_condition_pushdown` 开关或 SQL 里的 `NO_ICP` 提示关闭；只适用于 `range`、`ref`、`eq_ref`、`ref_or_null`，且必须**会发生回表**（二级索引、非覆盖索引），相关子查询的条件不适用。

判断一次查询能不能吃到 ICP 的收益，顺序就是这样：先看 `Extra` 里有没有 `Using index condition`，再看所用的索引里**有没有那个失效字段**，最后看这条语句**会不会回表**。三者都对得上，性能的差别才是实打实的。

关于索引条件下推，我们就说到这。

### EXISTS 与 IN 的性能取舍

写 SQL 的时候大家经常发现，同一个需求既能用 `IN` 写，也能用 `EXISTS` 写。到底选哪个更好？从性能优化上讲该怎么看？

判断的主要依据是**表的大小**，理解的标准可以概括成一句话：**小表驱动大表**。谁的效率更高，要放到这个标准下去比。

#### 两种写法的对应关系

先举一个例子。第一个场景用 `IN`：

```sql
SELECT *
FROM employee
WHERE manager_id IN (SELECT manager_id FROM department);
```

这里是员工表和部门表两张表。先从部门表里把管理者（`manager_id`）找出来，再看员工表里哪些人是这些管理者，把员工的信息列出来。需求就是这个。

同一个需求改写成 `EXISTS`：

```sql
SELECT *
FROM employee e
WHERE EXISTS (
    SELECT 1
    FROM department d
    WHERE d.manager_id = e.manager_id
);
```

> **提示**：`EXISTS` 只是判断"存不存在"，并不关心子查询里查出什么值，所以子查询的 `SELECT` 列表写 `1`、写 `*` 都不影响语义，写 `1` 最直观地表达了这一点。

两种写法语法上都能跑，区别藏在执行方式里：`IN` 的子查询和外层表之间没有引用关系，是不相关子查询；`EXISTS` 的子查询里引用了外层的 `e.manager_id`，是**相关子查询**。

#### 相关子查询的执行方式与选择规则

相关子查询的执行过程，其实就类似于我们说的嵌套循环：外面是 `A`，里面是 `B`。外层每送一条数据进去，内层查完出来，再送下一条进去。所以**外层这个表的大小会影响整个查询的性能**，它小一点会更好。

按这个道理往下推，结论很清楚：

| 表的大小关系 | 建议写法 | 原因 |
| --- | --- | --- |
| `A` 表小、`B` 表大 | `EXISTS` | 相关子查询，外层 `A` 逐行驱动内层 `B`，小表在外层，循环次数少 |
| `A` 表大、`B` 表小 | `IN` | 不相关子查询，先把小表 `B` 的 `cc` 查出来，外层只需按这几个值做匹配 |

也就是说，`A` 表小、`B` 表大，我们建议用 `EXISTS`；`A` 表大、`B` 表小，就不妨用第一种写法 `IN`。原因在于 `IN` 这种场景是不相关子查询：它先把小表里的 `cc` 取出来，然后让 `cc` 直接等于这里面这几个值就可以了，性能会更高一些。

> **结论**：`EXISTS` 走的是相关子查询那条路，外层驱动表越小越好；`IN` 走的是不相关子查询那条路，内层被先算出来的那个表越小越好。两种写法各自把"小表"放在了不同的位置上，所以选法的本质是看哪张表小、小表能不能被放到该放的位置上。

#### 两条执行链路对照

把两条链路并排画出来，差别就很直观了：

```text
不相关子查询 (IN)                          相关子查询 (EXISTS)
外层大表 A                                 外层小表 A
   |                                          |
   |  1. 内层 B 先整体算一次                  |  1. 从 A 取一行
   v                                          v
内层小表 B  -->  得到一个值的集合          送到 B 去查是否存在
   |             (只有几个值)                  |
   |  2. A 按集合做值匹配                      |  2. 结果返回，再取 A 的下一行
   v                                          v
输出匹配行                                  循环往复，逐行判定
```

读图说明：左侧 `IN` 的小表只被算一次，外层表拿到一个很小的值集合后做匹配；右侧 `EXISTS` 的判定必须由外层逐行触发，外层有多少行就要驱动多少次内层查询。

也正因为如此，两者的 NULL 处理不一样：`IN` 是在值集合里比对，碰到 NULL 会污染比较结果；`EXISTS` 只做存在性判断，不产生值集合，因而不受 NULL 影响。写法选择时，这一点也要一并考虑。

### COUNT 三种写法的效率

我不知道大家在面试里有没有被问过这个场景。很早以前我了解到，面试当中是经常会被问的；网络上有大量关于 `COUNT(*)`、`COUNT(1)`、`COUNT(具体字段)` 的探讨，具体字段里又分成主键字段和非主键字段，讨论得特别热闹。那我们就来讲一讲，查询表中有多少条记录，到底哪个性能更高。

#### 讨论的两个前提

先注意两件事，不然后面的结论会被误用。

第一，我现在讲的是 **MySQL**，不是所有数据库的通用情况。Oracle 有它自己存储引擎的机制和特征，别的数据库我们不去谈，先立足到 MySQL 上。

第二，我们讨论的前提是**查询表中有多少条记录**，不是统计某个字段的非空行数。两者的意义完全不同——你要找某个字段非空的行数，用 `COUNT(*)` 本身可能都是错的。我们要确保 `COUNT(*)`、`COUNT(1)`、`COUNT(具体字段)` 这三者查出来的结果首先是同一个东西，然后再去比谁的性能更好。

> **易错点**：把"表有多少行"和"某个字段有多少个非空值"混成一件事，是这一节最常见的误用。前者是三者的共同目标，后者只有 `COUNT(字段)` 才成立的语义，拿它跟 `COUNT(*)` 比性能没有意义。

#### COUNT 星与 COUNT 1 的等价性

先看 `COUNT(*)` 和 `COUNT(1)` 这一对。它们是对所有结果进行 `COUNT`，两者**没有本质上的区别**，可以理解成性能效率是一样的。既然一样，很多同学习惯上用 `COUNT(*)` 就完全没有问题。

这里还要补一句筛选的影响：如果你有 `WHERE` 子句，那自然要按条件做筛选，该筛选就筛选；如果没有 `WHERE` 子句，那就是对这个表里所有的数据行做一次统计。

#### 存储引擎决定的复杂度差异

`COUNT(*)` 与 `COUNT(1)` 两者的耗时基本上是一致的，或许会略有差别，但基本一致。那这个"基本一致"的复杂度是多少？答案是：**取决于你用哪个存储引擎**。

- 用 **MyISAM**：统计表行数是 $O(1)$ 的复杂度，相当于常量级别。
- 用 **InnoDB**：需要做一次全表扫描，相当于 $O(n)$ 级别的复杂度。

> **结论**：在"表里有多少条记录"这个语义下，`COUNT(*)` 与 `COUNT(1)` 等价，耗时的差别不在函数写法上，而在存储引擎上——MyISAM 是 $O(1)$，InnoDB 是 $O(n)$。

这里我们肯定要问：为什么两者会有这样的区别？

主要原因在于 MyISAM 的数据表有一个 **meta 信息**，其中记录了这个表的记录数，叫做 `row_count`。因为它有这么个记录，查询的时候直接把值取出来就行了。它的一致性由**表级锁**来保证，锁的粒度其实比较粗；也正是因为你访问这个表走的是表级锁的方式，它才有机会用这种方式去做记录。

InnoDB 不一样。它支持事务，支持**行级锁**和 **MVCC**，所以没有办法像 MyISAM 一样维护这样一个变量——这是出于数据一致性的考虑。InnoDB 的粒度更小，并发性更好，但代价就是不能用这样一个现成的变量，只能是扫描全表，复杂度就是 $O(n)$，通过循环累加计数的方式把结果统计出来。

> **提示**：MyISAM 的 $O(1)$ 只对"不带 `WHERE` 的全表行数"成立，因为 `row_count` 记的是整表记录数。一旦加了筛选条件，得实际数一遍，这个捷径就用不上了。（行级锁与 MVCC 的具体机制后面还会讲。）

#### InnoDB 下 COUNT 具体字段与索引选择

接下来是在 InnoDB 这个引擎里，用 `COUNT(具体字段)` 统计行数靠不靠谱的问题。

如果你用 `COUNT(具体字段)`，**尽量采用二级索引**。言外之意就是：不建议用主键索引（聚簇索引）。为什么呢？

用聚簇索引统计，要把这棵 B+ 树整体加载到内存里。聚簇索引的叶子节点放的就是一条条真实的记录，字段肯定更多，加载到内存中占用的内存就会更大。而二级索引的叶子节点放的是索引列和主键，数据量更小，加载的成本也就更低。所以我们会选用二级索引。

那 `COUNT(*)` 和 `COUNT(1)` 在这一点上是什么行为？**如果我们没有写明具体用哪个字段，它们会自动去选一个空间比较小的二级索引。**

顺着这个"自动选一个比较小的"再往下问一层：如果表里有多个二级索引，它到底选哪一个？答案是——选择**占用空间最小的那个二级索引**。可以这样理解：它不会选择聚簇索引，而是在二级索引里选占用空间最小的。

那二级索引之间又怎么比大小？靠的是 `key_len` 这个字段——我们在讲 `EXPLAIN` 的时候见过它。优化器会选 `key_len` 比较小的那个二级索引来做扫描，因为成本更低。你像有的时候 `key_len` 是 5，有的是 10，有的来个 63，那加载的量显然就不一样；带有字符串列的索引会更大。二级索引之间也有谁更少的问题，我们选那个比较小的。

| 统计写法（InnoDB） | 走哪个索引 | 开销来源 |
| --- | --- | --- |
| `COUNT(具体字段)` | 用该字段所在索引，尽量选二级索引 | 二级索引叶子节点只有索引列与主键，比聚簇索引整行数据小而轻 |
| `COUNT(*)` / `COUNT(1)` | 优化器自动挑 `key_len` 最小的二级索引 | 不读聚簇索引；在多个二级索引里选占用空间最小的那个 |

> **结论**：在 InnoDB 里统计表行数，无论你写 `COUNT(*)`、`COUNT(1)` 还是 `COUNT(字段)`，都尽量落到二级索引上；写具体字段时靠你来选（选二级索引），不写字段时由优化器按 `key_len` 自动挑最小的那个二级索引。

### SELECT 星的两项代价

我们直观上都有这个感觉：编写查询语句时尽量不要去写 `SELECT *`。一方面凭直觉就知道——你也不知道这个表到底有哪些字段，你想要哪个就写哪个，不要用星号。那往深了究，为什么不建议用？这里有两个原因。

#### 解析阶段查询数据字典

第一个原因在解析过程里。你写的是一个星号，感觉挺省事，但底层的查询过程首先要把这个星号转换成表中具体的字段。这个转换需要**查询数据字典**，也就是系统内部的那些表，把星号展开成具体的列名。

我们在前面讲章节的时候提到过系统内部的表，那里面储存的就是用户定义的表，以及表里那些具体字段的信息。查这个数据字典肯定要花时间，而且花的时间还挺多。

#### 覆盖索引无法生效

第二个原因跟我们之前讲 `ORDER BY` 时的那个例子是同一件事。很多时候我们写了 `ORDER BY`，对应的索引也在，但它就是不用。原因就在于你用了星号，我们根本没有办法使用**覆盖索引**。

> **易错点**：覆盖索引的前提是"查询要的列全都在索引里"。`SELECT *` 要的是整行的所有列，索引里几乎不可能全有，所以覆盖索引直接失效——`ORDER BY` 那个例子里的索引明明存在却用不上，根子就在这里。

你要是列出具体的字段，反而能用上覆盖索引，效果更好一点；用星号就用不上了。

| 写法 | 解析阶段 | 覆盖索引 |
| --- | --- | --- |
| `SELECT *` | 需要查数据字典，把 `*` 展开成具体列名，耗时较多 | 几乎无法命中，需要回表取整行 |
| `SELECT 具体字段` | 列名已经写明，无需展开 | 字段被索引覆盖时可命中，避免回表 |

### LIMIT 1 的生效条件

再说一个点，关于 `LIMIT 1` 对优化的影响。`LIMIT 1` 对优化到底有没有影响？这得看怎么讲。

如果针对的是**全表扫描**：这时候我们加上 `LIMIT 1`，就是你已经确定了结果集当中只有这一条记录。那就意味着找到一条记录之后就不再继续扫描了，速度确实会加快。

但如果这个字段**已经建立了唯一索引**，那就没必要了。因为你已经有了唯一索引，找到一条记录之后，索引本身的查找就不再往后进行了，这时候你加 `LIMIT 1` 的意义也就不大了。

> **结论**：`LIMIT 1` 的价值在于"提前终止扫描"。全表扫描时它能让你在第一条命中处停下，收益明显；已经有唯一索引时，唯一性本身就保证了查到即止，再加 `LIMIT 1` 属于多余。

我要是面试官，可能就会问这么几个问题：一个是 `EXISTS` 与 `IN`，一个是 `COUNT`，一个是 `SELECT *`，一个是 `LIMIT 1`，看看你对数据库的理解到底有多深刻。答案我都罗列在上面了。

### 事务的尽早提交

下面这个点大家可能都能想得到：写程序的时候，差不多觉得能够构成一个事务了，我们就可以把这个数据做一个提交，这样能提高性能。

为什么提交会提高性能？这也可以当成一个面试问题去问。原因是 **`COMMIT` 会释放相关的资源**：

- **回滚段**上用于恢复数据的信息，它对应在 **UNDO 日志**当中；
- 被程序语句获得的**锁**。在提交事务之前，你相应地会有一些锁的获取；提交之后，这些锁资源就释放了；
- **REDO、UNDO 日志空间**的释放（UNDO 同时也涉及回滚）；
- 以及**管理上述三种资源**的内部花费。

```text
未提交的事务持有                          COMMIT 之后
  UNDO 日志（回滚段恢复信息）  --------->  释放
  事务期间获得的锁              --------->  释放
  REDO / UNDO 日志空间          --------->  释放
  三类资源的管理开销            --------->  随之减少
```

读图说明：事务提交是这四类资源的统一释放点，事务开得越久、持有得越多，这部分开销就累计得越大。

> **易错点**：前提是你**该提交的时候**才提交。提交了跟不提交是有区别的，但有时候你要是不该提交，那就别乱提交——一旦提交，这个事务就结束了。

到这里，这几个零散的点就说完了，相对来说对大家在面试当中会有一些帮助。

### 本讲提到的题目

这几道都是我在讲的过程中当场提出来的，也是我做面试官时会拿去问的。

**1. 同一个需求既能写 `IN` 也能写 `EXISTS`，该选哪个？**

看两张表谁大谁小，标准是小表驱动大表。`EXISTS` 是相关子查询、相当于嵌套循环，外层表逐行驱动内层表，所以外层表越小越好：`A` 表小、`B` 表大就用 `EXISTS`。`IN` 是不相关子查询，先把内层小表的 `cc` 查出来，外层表按这几个值做匹配，所以内层表越小越好：`A` 表大、`B` 表小就用 `IN`。

**2. `COUNT(*)`、`COUNT(1)`、`COUNT(具体字段)` 统计表行数，哪个性能更高？**

前提是 MySQL，且统计的是表中有多少条记录（不是某字段的非空行数），三者结果必须一致。`COUNT(*)` 与 `COUNT(1)` 没有本质区别，效率一样。复杂度取决于存储引擎：MyISAM 的表 meta 信息里记了 `row_count`，靠表级锁保证一致性，所以是 $O(1)$；InnoDB 支持事务、行级锁与 MVCC，出于一致性考虑无法维护这样一个变量，只能全表扫描，是 $O(n)$。在 InnoDB 里统计行数时用 `COUNT(具体字段)` 要尽量选二级索引，因为二级索引叶子节点只有索引列和主键，比聚簇索引整行数据更轻；不写字段时，`COUNT(*)` 与 `COUNT(1)` 会自动选一个 `key_len` 最小的二级索引。

**3. `SELECT *` 为什么不建议写？**

两个代价：解析时要把 `*` 转换成具体的列名，需要查询数据字典（系统内部的表），这个时间花得还挺多；以及用星号时无法使用覆盖索引——`ORDER BY` 那个例子里索引明明存在却用不上，就是因为它要的是整行所有列。

**4. `LIMIT 1` 对优化有没有影响？**

看场景。全表扫描时，加上 `LIMIT 1` 意味着找到一条记录后不再继续扫描，速度确实会加快。如果该字段已经建立了唯一索引，就没必要了——唯一索引本身查到一条就不再往后查，再加 `LIMIT 1` 意义不大。

**5. 为什么事务经常提交能提高性能？**

因为 `COMMIT` 会释放相关资源：回滚段上用于恢复数据的信息（在 UNDO 日志中）、被程序语句获得的锁、REDO 与 UNDO 的日志空间，以及管理这三类资源的内部花费。前提是这次提交本身是该提交的——不该提交时别乱提交，一旦提交事务就结束了。

## 150-淘宝数据库的主键如何设计
> 对应分集：P150 | 原始标题：《150-淘宝数据库的主键如何设计》

### 主键设计问题的提出

这是这一章的最后一个问题：淘宝数据库的主键是如何设计的。

这个问题对大家来讲应该是非常有意义的，因为我们在创建表的时候都要考虑主键的设置。尤其是当表的数据量比较大，甚至你面对的是一个分布式系统的时候，主键的设计就非常讲究了。

如果你是面试官，我觉得你也可以去问一下被面试者：在业务当中，表结构里的主键是如何设计的，看看他怎么说。通过这个问题，你可以考察他实际的技术水平——他的理解、他的思考都在里边。这相当于给大家提供了一个去考别人的非常好的题目。

### 案例为什么选择淘宝

为什么拿淘宝的数据库举例，大家应该也心知肚明。淘宝数据库在国内乃至全球范围内，核心业务涉及的数据量都非常庞大。它的主键设置得好，对我们就更有参考价值。

网上流传了很多淘宝、阿里相关的规范，所谓形成的一些"军规"。但其中有一些是网络博主自己编的，并不是真正的阿里体系里在用的规范。比如就有这样一个说法：淘宝的数据库用 8 个字节的 `bigint` 做主键，为了确保空间够用而没有选 `int`。

> **结论**：这个说法听着很有道理，但实际情况是错误的，淘宝不会这样做。

一方面我们可以自己推理；另一方面，淘宝自己也会出相应的规范，比如《Java 开发手册》，用来让内部体系的人统一标准，对其他非阿里体系的业务场景也可以作为借鉴。

用 8 个字节的 `bigint` 做主键，本质上只是站在数据库这一层去考虑问题，没有从业务的角度去思考主键。

> **易错点**：以为主键就只是一个自增 ID 吗？站在架构设计上看，这个答案连及格都拿不到。

### 自增 ID 的问题

自增 ID 除了简单易懂、设置方便之外，几乎其他方面全是缺点。下面这几点就是它的问题所在。

#### 可靠性不高

自增 ID 存在 ID 可以被回溯的问题。这个问题一直到 MySQL 8.0 才被修复——在它之前，重启之后自增计数器可能回退到当前表内已有记录的最大值加一，删掉的记录腾出来的号会被重新分配出去。

> **提示**：MySQL 8.0 把自增计数器的最大值持久化了下来，实例重启后不会再把已经分配出去的 ID 重新发一遍；8.0 之前没有这个保证。

#### 安全性不高

自增 ID 对外暴露的接口很容易被猜测到对应的信息。比如我们暴露的接口是 `/user/1` 这样的形式，那很容易就能猜出用户的 ID 值是多少，也很容易推断出这个系统的用户量有多少，从而很方便地被爬虫工具去爬取数据。

> **易错点**：不要以为 ID 只是一个内部编号。它一旦出现在 URL、接口参数或对外单号里，就是一个信息泄露面。

#### 性能较差

自增 ID 需要在数据库服务端生成，所以它在性能上要稍差一点。

#### 交互次数多

如果想看一看当前自增 ID 的值是多少，还得用一个专门的函数去查询。在海量并发的系统里，每多一条 SQL，就多一份开销。交互比较多。

#### 只有局部唯一性

这一条在实际业务场景中比较糟糕。自增 ID 是局部唯一的。如果我们在分布式场景下，这就很麻烦了。

举一个实际中的例子：假设你是一个连锁超市。在单个分店的表里，自增 ID 能保证数据在"这家分店"当中是唯一的。但如果这个连锁超市要把数据在总部做汇总，这时就出问题了——ID 值可能就不再具有全局唯一性了。对于主键值相同的数据该怎么办？很麻烦，这就不能行。

> **结论**：局部唯一性是我们不能接受的点，而它恰恰是自增 ID 的固有属性。

### 业务字段能否充当主键

前面说的 ID，仅仅是为了表示一个主键、满足唯一性和非空这两个特征，它不是业务字段。那换一个思路：用业务字段做主键可不可以？

以会员信息表为例，表里有这些信息：卡号、名称、电话、身份证号、地址、性别、生日。

性别、生日、姓名就别想了，不靠谱。地址也不行——北京、上海写得这么泛泛，很容易出现不唯一的特征。真正能考虑的，也就是卡号、身份证号、电话号码这几个字段。下面逐个看。

#### 会员卡号的复用隐患

卡号看似比较靠谱。我们创建一张会员表，把卡号定义成主键，每个会员的卡号都不一样，卡号和会员之间有一个一一对应关系，感觉没什么问题。

但实际情况中，可能出现卡号重复使用。比如张三因为工作变动，不再在这个门店消费了；门店为了复用，把张三那张卡又给了王五去使用。这时表里就要把张三的信息改成王五的信息。

单看这张表，问题不大；可其他表还关联着它——比如消费记录表。真正出事的地方在流水表上。

销售流水表里有一个会员卡号字段，记的是张三那张卡号。张三还在的时候有过一次消费，比如买一本书，发生在某个时间，金额是 89 块钱。当你把这个卡号给了王五，会员表里张三的信息就被抹掉、改成王五了，而流水表里的卡号没有变。这时候去做多表连接查询，查出来的结果就成了：**王五在这一天买了一本书，89 块钱**。

> **结论**：从业务场景上讲这就是一个错误。卡号不能用来做主键。

#### 电话号码与身份证号

会员电话做主键也不行。实际中手机号可能被会员弃用，运营商把号重新分配给另一个人，主体这个人又变了，所以不太靠谱。

那身份证号呢？身份证号是国家给每个人分配的唯一标识，每个人也不会去变更它。有一个新闻，说一位孩子的母亲觉得给孩子分配的身份证号寓意不好，算卦算过觉得不行，就去找公安局要求改一个——这是改不了的。身份证号一旦确定下来就不能修改。

看似这个号挺好，不会像卡号、手机号那样被换掉。但是它毕竟属于个人隐私。登记的时候，用户可能根本不愿意把这个号报给你；不愿报就是 `null`，而主键不能是 `null`，那不行。如果你跟用户为这个事吵起来，用户可能连会员都不办了。所以实际情况中，这张表里的身份证号甚至电话都有可能是空的。

> **提示**：`null` 与主键互斥，这一条就足以把身份证号从主键候选人里排除，不需要再讨论它的唯一性和稳定性有多好。

#### 业务字段做主键的结论

卡号、身份证号、电话号都不太靠谱，也就是说用业务字段作为主键值不太合适。因为我们谁也无法预测，在项目的整个生命周期当中，哪一个业务字段会因为业务需求而出现重复或者重用。一旦有重复，你把它用成了主键，就等于不允许人家重复，这不行。

这里说一个实际的经验：刚开始使用 MySQL 的时候，很多人容易犯的错误就是喜欢用业务字段做主键，想当然地认为自己了解业务需求，但实际情况往往出乎意料。而更改主键的成本是非常高的——想想你的索引，想想底层存储数据的情况，表数据量大的时候改一下你试试，简直就崩溃了。

| 候选主键字段 | 唯一性 | 稳定性 | 可行性 | 否决原因 |
| :--- | :--- | :--- | :--- | :--- |
| 姓名、性别、生日 | 差 | — | 不可行 | 大量重复，无法唯一标识会员 |
| 地址 | 差 | 差 | 不可行 | 取值过于泛泛（如"北京""上海"），不唯一 |
| 会员卡号 | 好 | 差 | 不可行 | 卡号会被回收复用，改卡主会污染历史流水 |
| 会员电话 | 好 | 差 | 不可行 | 手机号会被运营商回收再分配，主体会变 |
| 身份证号 | 好 | 好 | 不可行 | 属个人隐私，用户可能拒填，主键不允许为 `null` |

### 淘宝订单号的结构观察

回到一开始的问题：淘宝数据库的主键是怎么设置的。看它的订单表。

订单表里罗列了近期若干条消费订单记录，其中的订单号在订单表里相当于唯一的，我们可以理解成它就是主键。那这个主键是怎么设计的？

把这几条数据抽取出来，一共发现它是有 19 位。再细节一观察，发现后 5 位都是一样的，就是 `08113`；而前 14 位还是一个单调递增的场景。

那我们就大胆地猜测，淘宝的订单 ID 可能是这样设计的：

```text
订单号（19 位）
┌────────────────────────┬──────────────┬────────────────────┐
│  时间段（前 14 位）      │  去重字段     │  用户 ID（后 5 位）  │
│  单调递增                │              │  取尾数若干位        │
└────────────────────────┴──────────────┴────────────────────┘
        ↑                                        ↑
   保证时间上递增                            同一用户的订单后缀相同
```

读图说明：把订单号切成"时间段 + 去重字段 + 用户 ID 尾数"三段，前段单调递增、后段按用户区分，整体就能既唯一又有序。

为什么这样能保证唯一？因为一个用户的后几位一样，就是他的用户 ID，所以后缀都相同。而时间是可能极其一致的——比如双十一的场景，时间点高度重合，又有多个用户同时消费。但**对同一个用户来讲**，一个订单跟下一个订单的时间完全一样，这不太可能。所以首先要把用户这一块考虑在内。

当然用户 ID 我们也不是完全取完整的 ID，取它的尾数这样几位，已经能够起到很好的区分、去重作用了。

在考虑 ID 的情况下，把时间字段加上，再考虑一个去重字段。这个设计能做到全局唯一，对分布式系统比较友好。大家设计自己的表主键时，可以考虑用这样的方式。

> **提示**：这里关于去重字段，大家还需要自己去考虑考虑，里边是有讲究的。

### 自增 ID 与有序 UUID 的取舍

除去上面猜测出来的淘宝方案，我们还能不能自己再做一种设置？这里仁者见仁、智者见智。下面给大家一种方案，应该是不错的。

> **定义**：对**非核心业务**，表主键选择自增 ID 是可以的。比如告警、日志、监控这些，放在本地，跟分布式关系不大，表数据量也没那么大，只需要做一个不同条目的区分就可以了。

> **结论**：对**核心业务**，主键需要保证两点——第一是**全局唯一性**，这是主键最基本的特征；第二是**单调递增**。

单调递增主要是为了在插入数据的时候，直接在 B+ 树右边插入，不要触发页分裂，从而保证插入的性能。而全局唯一是要应对分布式场景：涉及多个不同数据源、需要合并的时候，一定要保证全局唯一。

### UUID 的特点与分析

这里边最简单的一种设计主键的方案，叫做 UUID（Universally Unique Identifier，通用唯一识别码）。

大家一想到 UUID 就很头疼，说不是都说了不要用 UUID 吗？我们先从 UUID 入手，然后再去改造它。

UUID 的特点是：全局唯一、占用 36 个字节、数据无序、插入性能比较差。看起来好像没什么好处。那我们逐个分析：为什么它是全局唯一的？为什么它要占用 36 个字节？它是无序的吗？

#### 个字节的构成

先说 36 个字节是怎么来的。网上搜索"UUID 占用多少个字节"，很多同学搜出来是 16 个字节，那是因为它是用二进制的方式存储的。而 MySQL 当中的 UUID 是用**字符串**的方式存储的。

看一个典型的 UUID：

```text
xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
   8       4    4    4       12      →  32 个十六进制字符
   └── 4 个短横线 ──┘                     →   4 个字符
────────────────────────────────────────────────────
字符总数 32 + 短横线 4 = 36，字符串存储下每个字符占 1 字节 → 36 字节
```

读图说明：去掉 4 个短横线后剩 32 个字符，加回短横线是 36 个字符；按字符串存储，一个字符占一个字节，所以是 36 字节。

#### 全局唯一性的来源

再看 UUID 的格式：它由几个部分构成——有**时间**，时间又分成时间低位、时间中位和时间高位（比如小时、分钟、秒）；接下来有 UUID 的**版本**、**时钟序列**，以及 **MAC 地址**。

光从时间上来考虑，它就占用了 60 个位，类似于 `timestamp` 这样的时间戳。再加上后面的版本、时钟序列和 MAC 地址这些结构，合在一起，就能够保证它的唯一性。

#### 随机无序的原因

那它为什么是随机无序的？因为在 UUID 的设计当中，把**时间低位放在了前边**。

举例来说，几点几分几秒里的"秒"是老是变的：一会儿是 10 秒，一会儿变成 50 秒，一会儿又变成 10 秒。它不是严格递增的。只要不是递增，就相当于我们把它理解成一个像随机的过程——一直在变化。

### 有序 UUID 的改造

理解了 UUID 之后，首先明确一点：我们不会选择原生的 UUID 作为主键，因为我们希望它是单调递增的。全局唯一这一点它能保证，但无序就不理想。

那怎么办？对它进行改造。改造的目标就是让它变成单调递增。

办法是**把时间的低位和高位互换**，也就是先考虑时、分，再考虑秒。还有年月日的说法，这里只简单一说。你在考虑时间的时候把高位放在前边——某年某月某日，然后某时某分某秒，再接着往下走，那这个数据不就始终是一个递增的顺序了吗？这样就变成单调递增了。

用它做主键，就可以避免**页分裂**。MySQL 8.0 可以更换时间低位和高位的存取方式，8.0 在这一点上做得非常及时。

### MySQL 8.0 的二进制存储与函数支持

接着，MySQL 8.0 还解决了 UUID 的存储空间问题：不再使用字符串保存，而是使用**二进制**方式保存，这样存储空间就降低为 16 个字节。

原来 36 个字节，现在改成 16 个字节，降得还挺多的。那这个 16 是怎么算的？

- 光数字符（不数短横线）一共 32 个，$36 - 4 = 32$；
- 每一个位置是一个十六进制字符，一个十六进制位要用 4 个 bit 来存：$2^4 - 1 = 15$，15 对应十六进制就是 `F`；
- 所以 $32 \times 4 = 128$ 个 bit；
- 一个字节占 8 个 bit，$128 \div 8 = 16$ 个字节，短横线就不要了。

$$32 \times 4 = 128\ \text{bit},\qquad 128 \div 8 = 16\ \text{字节}$$

那 MySQL 8.0 是如何支持的呢？靠 `UUID_TO_BIN()` 这个函数。

演示的过程是这样的：先把一个 UUID 赋给一个用户定义的变量，再用 `UUID_TO_BIN()` 把它转成二进制，并且在这个函数后面加一个参数 `true`：

```sql
-- 生成一个 UUID 并保存到用户定义变量中
SET @uuid = UUID();

-- 原始 UUID（字符串形式，36 字节）
SELECT @uuid;

-- 转成二进制：16 字节，但仍按原来的时间位顺序存放
SELECT UUID_TO_BIN(@uuid);

-- 转成二进制，并把时间低位与高位互换
SELECT UUID_TO_BIN(@uuid, true);
```

`UUID_TO_BIN()` 是 MySQL 8.0 提供的转换函数，它的第二个参数就是"是否交换时间字段顺序"的开关。

执行之后可以观察到：原始的 UUID 里那些短横线被去掉了，这时候它已经是 16 个字节，而原来那个是 36 个字节——存储空间上就变了。

写 `true` 的时候，相当于在位数上做了一个调整。具体看这个调整：中间这一段位置不变，把三段时间的顺序交换了位置，改成先高位、后中位、后低位。

```text
原生 UUID 的字段顺序（时间低位在前 → 生成值不递增）
┌──────────┬──────────┬──────────┬────────┬──────────┬─────────┐
│ time_low │ time_mid │ time_hi  │ 版本   │ 时钟序列 │ MAC 地址 │
│  (低位)  │  (中位)  │  (高位)  │        │          │         │
└──────────┴──────────┴──────────┴────────┴──────────┴─────────┘
     ↑ 秒级字段在最前，变化最快，所以 UUID 看起来是随机的

UUID_TO_BIN(uuid, true) 之后（时间高位在前 → 生成值单调递增）
┌──────────┬──────────┬──────────┬────────┬──────────┬─────────┐
│ time_hi  │ time_mid │ time_low │ 版本   │ 时钟序列 │ MAC 地址 │
│  (高位)  │  (中位)  │  (低位)  │        │          │         │
└──────────┴──────────┴──────────┴────────┴──────────┴─────────┘
     ↑ 年月日时分在最前，先生成的值一定小于后生成的，顺序自然递增
```

读图说明：交换的三段就是时间的高位、中位、低位，其余字段位置不动；交换后时间的高位排在最前面，因此新生成的 UUID 一定是递增的。

对比原始值和转换后的值可以直接看出来：某一段不变，后面那些段落的顺序被调换了。这个操作就是把高位、中位、低位调整一下格式。调整完之后再去随机生成 UUID，因为前边这段是时间的高位、中位、低位，所以能够保证它就是有序的。

> **易错点**：`UUID_TO_BIN()` 只做二进制转换时，UUID 依然是无序的——它省的是空间，不是顺序。单调递增要靠第二个参数打开的时间位交换。

言外之意，我们后面就可以把得到的结果直接充当主键：既可以保证全局唯一性，又可以保证单调递增，而且占用的空间还小了。

### 有序 UUID 的实测数据

拿 16 个字节的有序 UUID，和之前用来自增的主键类型做一个对比测试：添加 1 亿条数据，每条数据占用 500 个字节，表上有 3 个二级索引。

整个测试的结果会发现：**有序 UUID 比自增 ID 花的时间要短一些。**

表大小方面，有序 UUID 相较于自增主键多了 3 个 GB，在 240 GB 这个基数上多了 3 个 GB，其实也就增加了不到 1.5%。

| 对比项 | 自增主键 | 有序 UUID（16 字节二进制） |
| :--- | :--- | :--- |
| 主键占用空间 | 8 字节 | 16 字节 |
| 写入 1 亿条数据的耗时 | 较长 | 较短 |
| 表空间大小 | 基准 240 GB | 多 3 GB（增幅不到 1.5%） |
| 全局唯一性 | 仅局部唯一 | 全局唯一 |
| 生成位置 | 只能数据库服务端生成 | 可在业务端生成 |

> **结论**：增加的空间其实比较有限，整体来讲用有序 UUID 还是比较不错的，也能保证全局唯一性。

而且在实际业务当中，有序 UUID 还可以**在业务端生成**，不用像自增 ID 那样必须在服务器端生成，这可以进一步减少 SQL 的交互次数。

在当今的互联网环境当中，不推荐用自增 ID 作为主键来设计，大家可以类似地用这种有序 UUID 去设计。

另外，在真实业务当中，主键还可以考虑用业务和系统的属性去设计，比如**用户的尾号**、**机房的信息**，没有必要非得用有序 UUID。

### 非 8.0 场景下的自定义主键方案

上面提到的是 8.0 当中提供的函数。那如果不是 8.0 怎么办？就需要手动去设置主键了。

这时候可以参考像淘宝那样的方式去做设置，但你要记得保证全局唯一性。

再回到前面提到的那一点：用户可以自己创建一个字段。如果涉及多个主体，比如连锁超市，每个超市里边都有自己的具体 ID，那要合在一起，这个数据可能就不能保证全局唯一性了。

怎么办？方案是**在总部维护一张用户信息表**，其中有一个字段专门记录当前主键 ID 的当前最大值。

```text
              ┌──────────────────────────────┐
              │   总部：用户信息表             │
              │   字段：当前主键 ID 的最大值    │
              └──────────────────────────────┘
                    ↑            │
        ③ 更新最大值 │            │ ① 取走当前最大值
                    │            ↓
              ┌──────────────────────────────┐
              │   分店 / 部门                 │
              │   ② 在取到的最大值上自增       │
              └──────────────────────────────┘
                    │
                    └── ④ 用完把最新最大值还回来，再记录、更新
```

读图说明：总部只保存"当前最大值"这一个数，分店取走 → 本地自增 → 用完归还最新值，形成一个循环，从而在多个主体之间不重号。

哪个部门、哪个分店要用的时候，把这个最大值取过来，然后它做自增。自增完以后，把你得到的这个当前最大值再上传到总部的这个字段上，把它作为更新。然后其他分店再用的时候，拿过来以后再用，接着再去增长。用到最后再还回来，记录一下、更新一下最新的最大值。这样也能够保证全局唯一性。

主键的设置其实有很多思路。我们主要的思考点就是：**保证全局唯一性，然后单调递增**，大家可以根据实际情况去做一个思考。
