## 第 1 章：121-InnoDB数据存储结构概述
> 对应分集：P121 | 原始标题：《121-InnoDB数据存储结构概述》

在上一章中，我们花了大量精力拆解索引底层的核心数据结构——B+ 树。无论是 InnoDB 还是 MyISAM，底层索引骨架采用的都是 B+ 树。在当时的推演中，我们把 B+ 树上的每一个节点统称为“数据页”；非叶子节点因为存放的是目录项，我们也常形象地叫它“目录页”，但从物理本质上讲，它们在引擎底层都是同一种结构：数据页。

然而，上一章我们是在逻辑数据结构层面俯瞰整棵树。到了本章，我们必须真正下潜到磁盘与文件的物理微观世界：这些索引信息和实际的数据行记录，到底是以什么样的文件格式落盘的？一页内部到底塞了什么东西？一行记录除了我们建表声明的字段，底层还藏着哪些管理信息？这就是我们要系统拆解的 InnoDB 数据存储结构。

### 1. 存储引擎与底层存储结构的定位

#### 1.1 磁盘文件与 B+ 树节点的物理映射

索引结构为我们提供了极高的查询效率，但大家心里必须时刻清楚：索引和数据最终都是持久化在磁盘文件中的，它们不是凭空飘在内存里的抽象符号。

对于不同的存储引擎，底层的物理落盘形态截然不同：
- **InnoDB 存储引擎**：索引与数据是浑然一体的，这就是所谓的聚簇索引，它们统一存放在以 `.ibd` 为扩展名的表空间文件中。
- **MyISAM 存储引擎**：索引与数据是明确拆开存放的，数据记录落在 `.myd`（MyData）文件中，索引结构则独立落在 `.myi`（MyIndex）文件中。
- **Memory 存储引擎**：它是一个完全基于内存的引擎，服务重启数据即清空，连磁盘文件都没有，更谈不上操作系统文件系统层面的落盘结构，其默认索引结构也是哈希索引。

> **结论**：只要脱离了具体的存储引擎，空谈“底层物理存储结构”就没有任何技术意义。存储引擎直接负责表内数据的读取、写入与落盘管理，引擎不同，数据在磁盘上的编排格式就完全不同。

#### 1.2 为什么聚焦于 InnoDB 存储引擎

既然各个引擎千差万别，我们为什么把全篇的核心火力全部集中在 InnoDB 上？

这里给大家做一个类比。许多同学学习 Java 体系时接触过 JVM（Java Virtual Machine）规范。JVM 只是一个抽象规范，市面上有非常多的具体虚拟机实现，随着 JDK 版本更迭各家引擎层出不穷。我们在学习 JVM 内部内存结构与垃圾回收机制时，必须抓住一条绝对的主线——那就是 Oracle（早期的 Sun 公司）官方发布的 HotSpot 虚拟机；讲垃圾回收器也是以官方主推的 G1 为核心主线。抓住了 HotSpot 和 G1，你就抓住了整个生态绝大多数的生产基准。

MySQL 同样如此。自 MySQL 5.5 版本起，InnoDB 便取代 MyISAM 成为了官方默认的存储引擎。在当今互联网与企业级开发的实际生产场景中，绝大多数业务表都在使用 InnoDB；高并发、事务 ACID 保障、行级锁控制、海量数据吞吐调优，面对的全部是 InnoDB。我们学习底层原理的目标不是去各大厂应聘编写一款全新的数据库存储引擎，而是为了摸清机制、给业务架构和 SQL 执行调优打下不可动摇的地基。把 InnoDB 的底层细节吃透，应付任何技术深访和生产故障排查都已经绰绰有余。

### 2. 磁盘与内存交互的基本单位：页（Page）

#### 2.1 页的默认规格与跨数据库对比

在 InnoDB 体系中，数据划分为若干个“页”，**页是磁盘与内存交互的基本单位**。

InnoDB 默认的页大小是 16KB。这是一个硬核参数，也是后续大量计算的基准。我们可以在登录 MySQL 服务器后，通过系统变量进行实测检验：

```sql
mysql> SHOW VARIABLES LIKE 'innodb_page_size';
+------------------+-------+
| Variable_name    | Value |
+------------------+-------+
| innodb_page_size | 16384 |
+------------------+-------+
1 row in set (0.01 sec)
```

查询结果显示的 `16384` 字节，换算后恰好是 $16384 / 1024 = 16\text{ KB}$。

在其他主流数据库产品中，也有对应的数据页概念，但默认规格有所差异：
- **SQL Server**：页的默认大小为 8KB，恰好是 MySQL InnoDB 的一半。
- **Oracle 数据库**：Oracle 体系中通常使用“块（Block）”这一术语来指代页的概念，本质完全相通。Oracle 的块大小更为灵活，支持 2KB、4KB、8KB、16KB、32KB 乃至 64KB，均为 2 的整数倍阶梯，允许在创建表空间时根据业务特征灵活指定。

#### 2.2 基本单位的严格内涵：基本单位与最小单位的辨析

很多初学者容易把“基本单位”和“最小单位”混为一谈。这两者在计算机与自然科学逻辑上存在本质差异。

我们以中学生物和化学举例：
- 生物体的基本结构单位是**细胞**。但细胞是生物的最小单位吗？显然不是。细胞内部还有细胞核、细胞壁、线粒体、高尔基体等极其复杂的微观细胞器。然而，我们在统计一个有机体的构成时，它必须由整数个细胞组成，你绝不可能说“这里有 3.5 个细胞”——细胞砍成一半，生命机能就不成立了。
- 构成物质化学性质的基本单位是**原子**（或分子）。原子并不是最小单位，它里面还包含原子核、质子、中子与核外电子。但是从化学反应的原子计量来看，原子必须按整数颗来参与反应，不能劈开半个原子去参加配平。

> **定义**：所谓“基本单位”，意味着系统在执行特定维度的操作时，每一次进出的度量颗粒度必须是该单位的整数倍，绝不允许出现半个单位或小数个单位的操作。

将这个原理映射到 InnoDB 存储引擎：
1. **从磁盘读入内存（数据加载）**：当 SQL 需要读取磁盘上的数据记录时，InnoDB 绝不会单单从磁盘挑出那几十个字节的字段，而是哪怕只读一条数据，也必须把整整 16KB 的数据页作为一个完整单位全部装载进内存缓冲区（Buffer Pool）。
2. **从内存写回磁盘（数据刷盘）**：当内存中的某条记录被修改成为脏页后，后台线程将其写回磁盘持久化时，同样必须以页为单位成批刷新，刷盘写入量必须是 16KB 的整数倍。

```text
+-------------------+                          +-------------------+
|                   |   Disk Read: N * 16KB    |                   |
|                   | -----------------------> |                   |
|    磁盘 (Disk)    |                          |    内存 (Buffer)  |
|   .ibd 表空间文件  |   Disk Flush: N * 16KB   |    Buffer Pool    |
|                   | <----------------------- |                   |
+-------------------+                          +-------------------+
```
*图 1：磁盘与内存间以 16KB 整数倍页为单位的双向 I/O 交互示意图*

#### 2.3 页级刷盘机制的必要性与 I/O 考量

这里经常有同学产生疑问：
“老师，如果在内存中一个 16KB 的数据页里，我用 `UPDATE` 语句仅仅改动了一个整型字段（4 个字节），为了这 4 个字节，刷盘时为什么非得把整整 16KB、一万多字节的数据全盘推出去？只把改动的那 4 个字节写回磁盘文件难道不是更轻量、更省流量吗？”

这恰恰是缺乏系统 I/O 认知导致的误解。在计算机存储体系中，**磁盘 I/O（尤其是传统的机械硬盘磁头寻道与旋转延迟，或是固态硬盘的块擦除机制）是整机系统最大的性能瓶颈**。

如果按单条记录的修改去微观写盘，表面上每次写入的网络与总线传输量很小，但现实业务中，数据库每秒可能在各个数据行发生上万次细碎变动。若每一次变动都触发一次独立的磁盘寻道写操作，磁盘磁头将会被极高频次的随机 I/O 彻底拖垮，系统吞吐量会暴跌几个数量级。

InnoDB 采用页作为基本交互单位，正是利用了**空间局部性原理**：
1. **批量平摊 I/O 成本**：将一段时间内落在同一个页内的所有细碎修改在内存中合并，待时机成熟时，只需发起一次 16KB 的顺序或集中写盘操作，就能一次性持久化数十甚至上百条改动，大幅削减实际的 I/O 次数。
2. **故障容灾保障机制**：有些同学会担心，既然一页是 16KB，万一在执行这 16KB 写盘的过程中操作系统突发断电、服务器宕机，导致只刷了 4KB 进去就中断了（即所谓的“页断裂”或部分写失效），岂不是会损坏数据？MySQL 对此设计了极其严密的 doublewrite buffer（双写缓冲区）以及 Redo Log、Undo Log 机制，在底层彻底兜底了奔溃恢复与事务原子性，确保数据绝不丢失和变形。

### 3. 页内与页间的逻辑拓扑关联

#### 3.1 物理离散与页间双向链表

当一张表的数据量达到数十万、数百万甚至上千万条时，需要容纳的数据页数量也会攀升到数万甚至数十万个。

那么问题来了：这数万个 16KB 的数据页，在物理磁盘文件的存储空间上，必须是严格紧挨着连续存放的吗？

答案是：**不一定，在物理上它们往往是离散的**。

在操作系统的文件分配机制中，很难在磁盘上随叫随到地划拨出大片绝对物理连续的空闲空间。随着数据的频繁插入、更新与删除，页与页之间的空隙往往是碎片的。为了在这种离散物理环境下维持数据的全局有序性，InnoDB 在每个数据页的头部（File Header）中开辟了专属字段，记录了该页的**前驱页指针（FIL_PAGE_PREV）**和**后继页指针（FIL_PAGE_NEXT）**。

通过这两个指针，所有在逻辑上相邻的数据页被串成了一条**双向链表**。

```text
+-----------------------+      FIL_PAGE_NEXT      +-----------------------+
|        Page A         | ----------------------> |        Page B         |
|      (Page No: 3)     |                         |      (Page No: 7)     |
|                       | <---------------------- |                       |
+-----------------------+      FIL_PAGE_PREV      +-----------------------+
```
*图 2：基于前驱与后继指针连接的页间双向链表拓扑*

页 A 的物理位置可能在磁盘文件的前端，页 B 的物理位置可能在磁盘文件的末尾，但凭借页头中的指针，逻辑扫描能够顺畅无阻地从前一页跨越到后一页，这构成了 B+ 树叶子节点之间横向遍历的物理基础。

#### 3.2 记录级单向链表与聚簇索引排列

把视角从页外部拉入到一个 16KB 页的内部。在这个页里，实际存放着一条条真实的业务数据行。

页内部的各条数据记录之间，又是如何组织连接的？
- **连接方式**：记录与记录之间并不是紧密无缝死板压在一起的数组结构，而是通过每条记录自带的**记录头信息（Record Header）**里的 `next_record` 指针，串联成一个**单向链表**。
- **排序依据**：
  - 如果当前页属于**聚簇索引**，页内的记录链表是严格按照**主键值从小到大**的顺序递增排列的。
  - 如果当前页属于**二级索引（辅助索引）**，记录链表则是先按照**索引列值**递增排列；当索引列值相同时，再按照包含的**主键值**递增排列。
- **虚实边界**：在页内除了我们自己插入的真实业务数据记录，InnoDB 还硬性预装了两个虚拟边界记录：**最小记录（Infimum）**和**最大记录（Supremum）**。链表的起点固定始于 Infimum，终点固定指向 Supremum。

#### 3.3 链表遍历瓶颈与页目录的二分查找

单向链表这种数据结构，在计算机算法里具有非常鲜明的优缺点：
- **优点**：数据插入与删除极为高效。若需要在两行之间新插入一条记录，只需修改前驱结点的 `next_record` 指针让其指向新节点，再让新节点指向后继即可，不需要像定长数组那样把后面的成百上千条记录在内存中全部平移一位。
- **致命缺点**：检索极其低效。单向链表不支持下标随机寻址，要寻找链表中的某一个特定值，只能从头节点顺着指针逐个向下比对，其时间复杂度为标准的线性阶 $O(n)$。

设想一下：如果一个 16KB 的数据页中塞入了 1000 条业务数据，现在上层引擎经过 B+ 树路由，已经精确定位到我们要找的主键记录就在这个页内。如果 InnoDB 只能在页内沿着单向链表从第 1 条硬生生比对到第 1000 条，那么即便 B+ 树在外部找到了页，页内部的开销也会把整体查询效率拖垮。

为了解决单向链表的检索瓶颈，InnoDB 在页的尾部专门引入了一个硬件加速结构——**页目录（Page Directory）**：
1. **分组抽取**：InnoDB 将页内所有紧密相连的记录划分成若干个“组”（Group）。
2. **提取槽位**：将每个组内最大的那条记录的物理地址偏移量提取出来，逆序存放在页尾部的页目录中，每一个提取出来的地址偏移量被称为一个**槽（Slot）**。
3. **二分查找定位**：页目录在内存中是连续排列的紧凑数组结构，且各个槽位所代表的主键值呈现严格升序。当我们在页内查找目标主键时，不再遍历单向链表，而是直接在页目录的各个槽之间执行**二分查找（Binary Search）**。

通过二分法，比对范围每一次直接腰斩一半，槽定位的时间复杂度直接从 $O(n)$ 骤降到对数阶 $O(\log_2 n)$。一旦通过二分法锁定了目标记录所在的具体槽位（即锁定到某一个小组内），再进入该小组内部，在仅包含 4~8 条记录的微型微单向链表里进行线性扫描，瞬时即可精准捕获目标行。

### 4. InnoDB 的多层级存储架构：行、页、区、段、表空间

很多同学在初学时，容易把页当成数据库存储体系的全部。但事实上，页只是最关键的“原子交互单位”，在页之上存在着庞大且分工严密的高级逻辑架构。

一个活生生的生物体，除了由细胞构成，细胞还会组织成组织，组织形成器官，器官构成系统，系统最终集成个体。InnoDB 为了兼顾局部快速读写与海量空间的统一调配，也设计了一套层层嵌套的五层存储架构。

#### 4.1 五层存储架构拓扑图解

```text
+-----------------------------------------------------------------------+
|                           表空间 (Tablespace)                          |
|    (.ibd 独立表空间文件 或 ibdata1 系统表空间物理文件，最高逻辑存储容器)    |
|                                                                       |
|  +-----------------------------------------------------------------+  |
|  |                           段 (Segment)                          |  |
|  |    (分配管理单位：叶子节点段、非叶子节点段、回滚段等数据库对象形态)    |  |
|  |                                                                 |  |
|  |  +-----------------------------------------------------------+  |  |
|  |  |                        区 (Extent)                        |  |  |
|  |  |         (物理连续空间分配单位：固定 64 个连续页，容量 1MB)         |  |  |
|  |  |                                                           |  |  |
|  |  |  +---------+  +---------+  +---------+         +---------+|  |  |
|  |  |  |  页 0   |  |  页 1   |  |  页 2   |   ...   |  页 63  ||  |  |
|  |  |  | (16KB)  |  | (16KB)  |  | (16KB)  |         | (16KB)  ||  |  |
|  |  |  +---------+  +---------+  +---------+         +---------+|  |  |
|  |  |       |                                                   |  |  |
|  |  |       v                                                   |  |  |
|  |  |  +-----------------------------------------------------+  |  |  |
|  |  |  |                      页内行记录 (Rows)               |  |  |  |
|  |  |  |  [Row 1] -> [Row 2] -> [Row 3] ... (单向链表)       |  |  |  |
|  |  |  +-----------------------------------------------------+  |  |  |
|  |  +-----------------------------------------------------------+  |  |
|  +-----------------------------------------------------------------+  |
+-----------------------------------------------------------------------+
```
*图 3：InnoDB 存储体系从 Row 到 Tablespace 的五层嵌套架构图*

#### 4.2 存储单位逐级解析（行、页、区、段）

自底向上梳理各层级的核心职能与参数规范：

##### 1. 行（Row）
业务真实数据的载体。用户在表中声明的一行数据，落到物理层面不仅包含我们自定义的各个业务列（`id`, `name`, `age` 等），还包含 InnoDB 底层强行注入的内部系统列（如事务 ID 列 `DB_TRX_ID`、回滚指针列 `DB_ROLL_PTR`、隐式主键列 `DB_ROW_ID`）以及行记录头信息（如变长字段长度列表、NULL 值列表、删除标记、记录下潜指针等）。行内部的具体组织方式就是所谓的“行格式（Row Format）”。

##### 2. 页（Page）
磁盘与内存进行数据交换的最基础单位。默认尺寸恒定为 16KB。一个页内可以容纳多条甚至数百条行记录。

##### 3. 区（Extent）
在庞大的表空间中，如果单纯以 16KB 的页为单位东申请一个、西申请一个，当表膨胀到千万行时，磁盘上将会产生铺天盖地的碎片页，导致哪怕做一次顺序全表扫描，磁头都必须不断发生漫长的随机寻道。

为了解决大范围扫描的性能退化，InnoDB 引入了“区”的概念：
- **容量规则**：**在默认 16KB 页大小的配置下，1 个区在物理磁盘上强行连续占据 64 个页**。
- **空间大小**：
  $$64 \times 16\text{ KB} = 1024\text{ KB} = 1\text{ MB}$$
- **核心价值**：区是连续物理空间分配的基础。当表数据量非常庞大时，InnoDB 不再零敲碎打地申请单页，而是直接以 1MB 大小的整“区”为单位向操作系统申请连续空间。64 个页在磁盘物理柱面上是连续排列的，顺序 I/O 读取速度比随机寻道快数十倍。

##### 4. 段（Segment）
很多初学者看到“段”这个词会感到困惑，为什么有了区还要搞出一个段？段被称为**数据库对象的空间分配单位**。

“段”并不是一个在物理磁盘上死板连续切出来的空间区域，而是一个逻辑管理单位。不同性质的数据库对象拥有不同的段：
- **数据段（叶子节点段）**：专门用来挂载 B+ 树底部的所有叶子节点（即实际存放行数据的页与区）。
- **索引段（非叶子节点段）**：专门用来挂载 B+ 树非叶子节点的目录项页与区。
- **回滚段（Rollback Segment）**：专门管理事务撤销日志（Undo Log）所占用的存储空间。

为什么要把叶子节点和非叶子节点划分进不同的段来管理？
> **提示**：如果叶子节点和非叶子节点的页混在一起胡乱分配，当我们在进行大范围的范围扫描（`WHERE id BETWEEN 100 AND 100000`）时，磁盘磁头在读取叶子节点区时就会冷不防撞上夹杂在中间的目录项页，造成连续物理顺序的断裂与震荡。将它们隔绝成独立的“段”，就能保证叶子节点段内尽可能以连续的区推进，最大化顺序读写优势。

#### 4.3 表空间的演进：系统表空间与独立表空间

表空间（Tablespace）是整个存储结构的最顶层抽象，也是直接映射到操作系统文件层面的最高级别物理文件容器。每一个表空间内部由若干个段、区、页组成。

回顾 MySQL 的架构演进历史，表空间的落盘模式经历过非常关键的技术更迭：

| 表空间形态 | 代表物理文件 | 历史默认版本 | 存储管理特征与优缺点 |
| :--- | :--- | :--- | :--- |
| **系统表空间 (System Tablespace)** | `ibdata1`（位于 `/var/lib/mysql` 数据目录） | MySQL 5.5.7 至 5.6.6 之前默认开启 | 全局所有数据库的所有表数据、索引、系统元数据统统混合塞入单一的 `ibdata1` 文件。**致命痛点**：单文件极度膨胀，即便 `DROP TABLE` 删掉几百张表，由于操作系统文件空洞机制，`ibdata1` 磁盘物理体积也无法自动回缩收缩，极易把磁盘撑爆，难以维护。 |
| **独立表空间 (File-Per-Table Tablespace)** | 独立的 `表名.ibd`（位于各数据库子目录下） | MySQL 5.6.6 及以上版本（包括主流 5.7 与 8.0）默认开启 | 每一张独立的数据表都在其对应的数据库文件夹下，拥有一份以其表名命名的专属 `.ibd` 磁盘文件。**核心优势**：单表数据完全物理隔离。当执行 `DROP TABLE` 或 `TRUNCATE TABLE` 时，对应的 `.ibd` 文件直接被操作系统从磁盘删除，瞬时彻底释放物理空间，备份、迁移与排查极为便捷。 |

我们可以验证独立表空间的参数设置：

```sql
mysql> SHOW VARIABLES LIKE 'innodb_file_per_table';
+-----------------------+-------+
| Variable_name         | Value |
+-----------------------+-------+
| innodb_file_per_table | ON    |
+-----------------------+-------+
1 row in set (0.00 sec)
```

只要该变量维持默认的 `ON`，我们在业务中创建的任何表，都会以独立的 `.ibd` 文件存在于磁盘上，这就是我们能直接用 `ls -l` 看到的终极存储载体。

### 1. 页的类型划分与七大内部组成区域

#### 1.1 页的功能类型划分

在深入页的微观布局前，必须先明确一个概念：在 InnoDB 中，“页”是一个通用的空间规格，并非只有存放数据行的一种。

根据所承载系统职责的不同，InnoDB 的页被划分为多种类型：
- **索引页 / 数据页（FIL_PAGE_INDEX）**：存放 B+ 树节点的页面。在聚簇索引中叶子节点存放完整的用户数据行，非叶子节点存放目录项；在二级索引中叶子节点存放索引列和主键。虽然逻辑上我们常区分“目录页”和“数据页”，但在物理类型上它们统称为索引页。
- **Undo 日志页（FIL_PAGE_UNDO_LOG）**：专门用来存放事务撤销日志（Undo Log），用于支持事务原子性回滚以及多版本并发控制（MVCC）的数据版本快照链。
- **系统页（FIL_PAGE_TYPE_SYS）**：存放系统管理信息与数据字典元数据。
- **事务数据页（FIL_PAGE_TRX_SYS）**：存放事务系统的全局状态与控制信息。

无论页承担何种上层业务，只要它是 InnoDB 管理的页，其底层物理尺寸默认一律为 16KB，且基础框架遵循高度标准化的结构布局。

#### 1.2 数据页的七大内部组成部分

一个标准的 16KB 数据页被严格划分为 7 个功能区：

```text
+-------------------------------------------------------------------+
| 1. File Header (文件头部, 38 字节)                                  |
|    通用信息：页号、上一页、下一页、页类型、校验和、LSN                     |
+-------------------------------------------------------------------+
| 2. Page Header (页头部, 56 字节)                                   |
|    数据页专有状态：槽数量、记录数、空闲空间偏移量、最大事务ID等         |
+-------------------------------------------------------------------+
| 3. Infimum + Supremum (最小与最大虚拟记录, 26 字节)                 |
|    页内记录的逻辑边界哨兵：Infimum (下界) 与 Supremum (上界)           |
+-------------------------------------------------------------------+
| 4. User Records (用户记录, 动态大小)                                |
|    实际插入的业务数据行 (行格式 Compact/Dynamic 等，单向链表串联)       |
+-------------------------------------------------------------------+
| 5. Free Space (空闲空间, 动态大小)                                 |
|    页内尚未分配的剩余存储空间                                      |
+-------------------------------------------------------------------+
| 6. Page Directory (页目录, 动态大小)                               |
|    基于槽 (Slot) 的稀疏索引结构，为页内主键查找提供二分查找加速       |
+-------------------------------------------------------------------+
| 7. File Trailer (文件尾部, 8 字节)                                 |
|    校验和与 LSN 副本，用于校验从内存刷盘到磁盘时的页面物理完整性       |
+-------------------------------------------------------------------+
```
*图 1：InnoDB 16KB 数据页内部七大功能区域物理排布示意图*

这 7 大区域的具体职能与尺寸规范如下表所示：

| 序号 | 区域名称 | 英文标识 | 占用空间 | 核心职能说明 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | **文件头部** | `File Header` | 38 字节 | 记录该页的通用元数据，包括当前页号、双向链表前后指针、校验和、最后修改 LSN 等，所有类型页均包含。 |
| 2 | **页头部** | `Page Header` | 56 字节 | 数据页（索引页）专有的状态信息，用于记录页内记录数量、槽位数量、空闲链表偏移量等统计属性。 |
| 3 | **虚拟边界记录** | `Infimum + Supremum` | 26 字节 | 数据库系统自动生成的虚拟哨兵记录，Infimum 代表比本页内任何主键都小的下界，Supremum 代表比本页内任何主键都大的上界。 |
| 4 | **用户记录** | `User Records` | 动态大小 | 存放业务实际插入的数据行记录，记录之间通过单向链表串联。 |
| 5 | **空闲空间** | `Free Space` | 动态大小 | 页内未被使用的连续物理空洞。新插入记录时从该区域切取空间；随着记录不断写入，空闲空间逐渐被蚕食殆尽。 |
| 6 | **页目录** | `Page Directory` | 动态大小 | 将页内记录分组后提取各个组内最大记录的偏移量，逆序存放构成的槽数组，用于支持 $O(\log_2 n)$ 的折半查找。 |
| 7 | **文件尾部** | `File Trailer` | 8 字节 | 存放前 4 字节的校验和与后 4 字节的 LSN 镜像，配合文件头部检测刷盘过程中是否发生部分写断裂。 |

#### 1.3 教学认知的结构三段重组法

很多同学初看这 7 个部分会感到信息过载，甚至担心“这 7 个结构面试时是不是全得一字不差地背下来”。死记硬背毫无意义，我们必须顺着系统设计的内在逻辑去拆解。

为了彻底消除混乱，我们将这 7 个部分重组成**三大逻辑模块**进行分步突破：
1. **第一模块：首尾协同与物理安全（File Header + File Trailer）**
   文件头部负责定义这个页“是谁、属于哪种类型、前后的邻居是谁”，而文件尾部只有 8 个字节，其设计目的完全是作为文件头部的“影子”来检测刷盘是否成功。把头和尾放在一起讲，逻辑天然闭环。
2. **第二模块：记录存储与空间流转（Infimum/Supremum + User Records + Free Space）**
   最小最大记录、用户记录与空闲空间，本质上全部围绕着“数据如何在页内安置”展开。新数据插入时，空闲空间被压缩，用户记录链表被加长，首尾始终卡在 Infimum 和 Supremum 两个哨兵之间。三者具有强烈的动态转化关系。
3. **第三模块：页内状态与高速检索（Page Header + Page Directory）**
   Page Header 是整个数据页的运行状态仪表盘，而 Page Directory 则是基于这个仪表盘构建的二分检索加速引擎。两者共同支撑了 B+ 树叶子节点单页内部的高速定位。

本讲我们集中攻克第一模块：**文件头部与文件尾部的协同校验机制**。

### 2. 文件头部（File Header）的核心结构与字段解析

文件头部（File Header）固定占据 **38 个字节**，它的核心定位是：**为 InnoDB 中所有类型的页面提供跨类型的通用描述信息**。

无论当前页是存储用户数据的索引页，还是存放事务状态的系统页，其最前方的 38 个字节格式完全统一。

```text
+---------------------------------------------------------------------------------------+
|                                File Header (共 38 字节)                                |
+---------------------------+----------+------------------------------------------------+
| 字段名称                  | 字节大小 | 核心用途与职能                                 |
+---------------------------+----------+------------------------------------------------+
| FIL_PAGE_SPACE_OR_CHKSUM  | 4 字节   | 页的校验和 (Checksum)                          |
| FIL_PAGE_OFFSET           | 4 字节   | 当前页的唯一页号 (Page Number)                  |
| FIL_PAGE_PREV             | 4 字节   | 上一个数据页的页号 (双向链表前驱指针)           |
| FIL_PAGE_NEXT             | 4 字节   | 下一个数据页的页号 (双向链表后继指针)           |
| FIL_PAGE_LSN              | 8 字节   | 页面最后被修改时对应的日志序列号 (LSN)          |
| FIL_PAGE_TYPE             | 2 字节   | 当前页面的具体功能类型 (如索引页、Undo页等)     |
| FIL_PAGE_FILE_FLUSH_LSN   | 8 字节   | 仅在系统表空间首页中使用，记录独立刷盘检验点   |
| FIL_PAGE_ARCH_LOG_NO_OR_SPACE_ID | 4 字节 | 当前页所属的表空间 ID (Space ID)            |
+---------------------------+----------+------------------------------------------------+
```
*图 2：File Header 内部 38 字节字段全景结构表*

我们逐项拆解其中最核心的五个字段：

#### 2.1 页的物理标识：FIL_PAGE_OFFSET

`FIL_PAGE_OFFSET` 占用 4 个字节。它记录的是当前页在整个表空间内的**唯一页号（Page Number）**。

正如数据行依靠主键唯一标识一样，数据页依靠 `FIL_PAGE_OFFSET` 唯一标识自身。当 InnoDB 需要在包含几万个页的表空间文件中精确寻址某一个页时，只需将页号乘以 16KB，就能算出该页在物理磁盘文件中的绝对字节偏移量：
$$\text{Physical File Offset} = \text{FIL\_PAGE\_OFFSET} \times 16384$$

#### 2.2 页的功能定义：FIL_PAGE_TYPE

`FIL_PAGE_TYPE` 占用 2 个字节，用于指明当前页面到底扮演什么角色。

常见的重要取值包括：
- `FIL_PAGE_INDEX`：数值通常为 `0x45BF`，代表 B+ 树的索引页（存放真实数据行或非叶子节点的目录项）。
- `FIL_PAGE_UNDO_LOG`：代表存放 Undo 日志的页面。
- `FIL_PAGE_TYPE_SYS`：代表系统管理页。
- `FIL_PAGE_INODE`：用于管理段（Segment）分配的索引节点页。

引擎在从磁盘读入一个 16KB 内存块后，首先读取这 2 个字节，立刻就能判定后续的 16KB 内容应当按照哪种内部协议去解析。

#### 2.3 物理离散与逻辑串联：FIL_PAGE_PREV 与 FIL_PAGE_NEXT

我们在上一讲曾着重强调：在海量数据持续插入与删除的物理磁盘环境中，操作系统很难随时分配出大片连续无间隙的页。

`FIL_PAGE_PREV` 和 `FIL_PAGE_NEXT` 各占 4 个字节，分别存储**前一个数据页的页号**与**后一个数据页的页号**。

> **结论**：正是依赖这两个 4 字节的页号指针，原本在物理磁盘空间上零散分布的数据页，被串联成了一条严密有序的**双向链表**。

这也是 B+ 树能够进行高效区间范围查找（如 `WHERE id >= 100 AND id <= 500`）的底层支撑：当 B+ 树从根节点自顶向下定位到主键为 100 的叶子节点页后，后续的扫描不再需要反复回退根节点重新寻道，只需顺着当前页 File Header 中的 `FIL_PAGE_NEXT` 顺藤摸瓜，一路沿着双向链表向右推进即可。

### 3. 文件尾部（File Trailer）与页面完整性校验

在 File Header 的最后，我们留下了两个极其核心的字段：`FIL_PAGE_SPACE_OR_CHKSUM`（校验和，4 字节）与 `FIL_PAGE_LSN`（日志序列号，8 字节）。

要彻底弄懂这两个字段的玄机，就必须将它与位于页面最底部的 **File Trailer（文件尾部）** 联立分析。

#### 3.1 什么是校验和（Checksum）

在深入数据库机制之前，我们先通俗拆解一个基础计算机设计思想：**什么是校验和？**

假设现在网络上有两个极其庞大的字节串（或者存放在磁盘上的两个巨型数据块），长度高达数十万个字节。如果我们要判定这两个长串内容是否完全相同，最朴素的做法是一个字节一个字节逐一比对。但这在超高频并发场景下开销极大、耗时极长。

更高效的做法是：设计一套数学算法（如 CRC32、Adler32 或哈希函数），输入这串极其庞大的字节序列，输出一个非常短小紧凑的固定长度数值（例如一个 4 字节的整型数值）。这个经过计算生成的紧凑数值，就称为**校验和（Checksum）**。

```text
[ 16KB 庞大数据块: 16384 个字节 ... ] 
                  |
                  v  (Checksum 算法)
           [ 0x8A4F3C12 ] (4 字节校验和)
```

**校验和的核心特性**：
1. 若两个数据块计算出来的校验和不相等，则这两个数据块必然不相同；
2. 若数据块内部哪怕仅仅发生了一个 bit 位的篡改或丢包，计算出来的校验和都会发生显著剧变。

#### 3.2 刷盘的部分写失效（Partial Page Write）灾难

有了校验和的概念，我们再回到数据库与操作系统的交互现场。

我们再次强调：**页是磁盘与内存交互的基本单位，每次刷盘必须是完整的 16KB**。

然而，操作系统的底层 I/O 调度以及物理磁盘驱动器（HDD 的扇区通常是 512 字节或 4KB，现代 SSD 的 Page 通常是 4KB/8KB），并不能保证对整整 16KB 的写入操作具有原子性硬件保障。

这就带来了一个极为凶险的故障场景：
1. 内存 Buffer Pool 中，某个 16KB 数据页经过多次更新变成了脏页。
2. 后台刷盘线程发起 I/O 操作，开始向磁盘的 `.ibd` 文件顺序写入这 16KB 的数据。
3. 刷盘是从页头开始顺序向后推进的。当文件头部刚写完，数据部分才刷了 4KB 时，**服务器突发意外断电，或者操作系统内核崩溃死机**！
4. 此时，写操作在物理中途被腰斩。

这一灾难在数据库内核中被称为**部分写失效（Partial Page Write）**，也常被称为“页断裂”。此时磁盘上的这个 16KB 页面，前半段是更新后的新数据，后半段是历史上的老数据，整个页处于物理破损和逻辑混乱的致命状态。

#### 3.3 File Trailer 的 8 字节物理结构

为了在数据库重启恢复的第一时间精确识别出“页断裂”，InnoDB 在每个 16KB 边界的最底端，规划了固定占用 **8 个字节**的 `File Trailer`：

```text
+-----------------------------------+-----------------------------------+
| 前 4 字节: 校验和 (Checksum)      | 后 4 字节: 日志序列号 (LSN) 副本   |
+-----------------------------------+-----------------------------------+
```
*图 3：File Trailer 内部 8 字节字段结构图*

- **前 4 字节**：存储当前页计算得出的校验和。它与 `File Header` 中的 `FIL_PAGE_SPACE_OR_CHKSUM` 形成前后呼应。
- **后 4 字节**：存储当前页最后修改时的 `LSN` 的低 4 位。它与 `File Header` 中的 `FIL_PAGE_LSN` 形成版本映射。

### 4. 首尾协同工作流与崩溃容灾推演

文件头部的 Checksum 与文件尾部的 Checksum，究竟是如何协同防范页面损坏的？我们通过一个完整的状态演进周期进行全局推演。

#### 4.1 正常刷盘流程的状态流转

```text
1. 磁盘原始稳定态 (初始校验和 = 123):
   +-----------------------------------------------------------+
   | Header Checksum: 123 | ... 原始数据 ... | Trailer Checksum: 123 |
   +-----------------------------------------------------------+
                              |
                              v  (读入内存进行修改)
2. 内存缓冲区脏页计算态 (重新计算校验和 = 256):
   +-----------------------------------------------------------+
   | Header Checksum: 256 | ... 新数据 ...   | Trailer Checksum: 256 |
   +-----------------------------------------------------------+
                              |
                              v  (发起顺序刷盘 I/O，从头部向尾部写)
3. 磁盘写入完成态 (刷盘顺利结束):
   +-----------------------------------------------------------+
   | Header Checksum: 256 | ... 新数据 ...   | Trailer Checksum: 256 |
   +-----------------------------------------------------------+
```
*图 4：正常刷盘状态下 File Header 与 File Trailer 的 Checksum 协同流转图*

1. **初始稳态**：原本位于磁盘上的数据页，其头部 Checksum 是 `123`，尾部 Checksum 也是 `123`。两者完全相等，说明该页是一个物理结构完整的数据页。
2. **内存修改与重算**：当该页被加载到内存后，经过事务更新，数据发生改变。在准备将该脏页同步回磁盘前，InnoDB 会使用内部算法对内存中这个全新的 16KB 数据页重新计算校验和，假设计算结果为 `256`。
3. **首尾同时置换**：InnoDB 将内存页中 File Header 的 Checksum 更新为 `256`，同时把 File Trailer 的 Checksum 也更新为 `256`。
4. **顺序刷盘**：I/O 调度启动，将整整 16KB 数据按物理顺序推入磁盘。
5. **落盘确认**：若刷盘过程顺畅无阻，磁盘文件上该页的头部被写为 `256`，尾部也被顺利更新为 `256`。首尾相同，代表此次 16KB 写入是一次完整、成功的原子性落盘。

#### 4.2 遭遇异常中断的断裂捕获与修复

如果刷盘中途突发宕机，状态又是如何被捕获的？

```text
发起刷盘 (从头向尾写入) ---> 刚刷入头部与部分数据 (Header 变成 256)
                                   |
                                   X 【突发断电 / 宕机崩溃】
                                   |
磁盘残留态 (出现页断裂):
+-----------------------------------------------------------+
| Header Checksum: 256 | ... 半新半旧数据 ... | Trailer Checksum: 123 |
+-----------------------------------------------------------+
                                   |
                                   v
             重启校验: Header(256) != Trailer(123) --> 报警: 页断裂！
```
*图 5：刷盘中断导致 Checksum 首尾不一致的页断裂捕获时序*

1. **断裂产生**：当数据刚写入前几千字节（此时磁盘上的 Header Checksum 已经被覆盖改写成了 `256`），主机断电死机。而处于页面最底部的 File Trailer 根本还没来得及被磁头触碰，其值依然停留在历史版本的 `123`。
2. **重启探测**：数据库实例重启启动恢复机制。InnoDB 扫描磁盘数据页，比对 File Header 的 Checksum（`256`）与 File Trailer 的 Checksum（`123`）。
3. **精确识别**：`256 != 123`，系统立刻断定：**该数据页在最后一次落盘时遭遇了非正常中断，属于半生不熟的破损页，绝不能直接投入生产运行！**
4. **容灾修复**：
   - **方案一（Redo Log 重做前滚）**：如果该事务在提交时，其 Redo Log 已经完整写入磁盘日志（WAL 机制），且通过 Doublewrite Buffer 找回了该页在刷盘前的完整镜像，系统可以先将干净的旧页还原出来，再通过 Redo Log 中的日志记录重新执行物理前滚，最终把尾部的 Checksum 也刷新为 `256`，完成数据的一致性重建。
   - **方案二（Undo Log 事务回滚）**：如果该断裂页涉及的事务尚未提交，或者系统判定数据无法安全重做，系统则利用 Undo Log 记录的逆向逻辑，将已经部分写入的修改彻底撤销，使页面回滚恢复到最初一致的状态（回到首尾均为 `123` 的状态）。

> **结论**：File Trailer 设立的核心意义，就是在物理架构的最末端安插一个哨兵。通过首尾两个 Checksum 以及首尾两处 LSN 的精确印证，为高并发与断电灾难下的存储一致性提供了最坚固的物理自愈判定依据。

## 第 3 章：123-页结构之最小最大记录_行格式之记录头信息
> 对应分集：P123 | 原始标题：《123-页结构之最小最大记录_行格式之记录头信息》

在解析了文件头部（File Header）与文件尾部（File Trailer）的首尾协同校验机制之后，我们正式进入数据页内部最核心的资产区域——实际存放业务数据的空间。

按照上一讲梳理的三大模块，本讲我们将聚焦第二模块：**空闲空间（Free Space）、用户记录（User Records）以及最小最大虚拟记录（Infimum & Supremum）**。

在讲解这一模块时，我们会遇到一个绕不开的底层矛盾：用户记录在页内是一行一行紧密存储的物理字节，但在逻辑检索上，它又必须维护成一条按主键递增排列的单向链表。这个单向链表的指针到底长在什么地方？记录被删除后到底去了哪里？为什么新插入记录的位置编号不从 0 开始？要彻底把这些底层细节讲透，我们必须在剖析页结构的同时，穿插下潜到 Compact 行格式中的“记录头信息（Record Header）”。

---

### 1. 记录存储区域与空间动态流转

#### 1.1 存储区域的三大构成要素

在 16KB 的数据页中，除去固定占用的文件头（38 字节）、页头（56 字节）、虚拟记录（26 字节）和文件尾（8 字节），剩下绝大部分空间都处于动态流转状态。这部分空间主要由三个角色瓜分：

```text
+-------------------------------------------------------------------+
| Infimum + Supremum 虚拟记录 (固定 26 字节，作为页内记录链表头尾哨兵) |
+-------------------------------------------------------------------+
| User Records 用户记录 (动态增长，存放实际业务数据行)               |
| [Row 1] -> [Row 2] -> [Row 3] ... (单向链表逻辑连接)              |
|                               |                                   |
|                               v  (空间向下蚕食)                   |
+-------------------------------------------------------------------+
| Free Space 空闲空间 (动态收缩，尚未分配的纯物理空白区域)          |
+-------------------------------------------------------------------+
| Page Directory 页目录 (由下往上生长，槽位数组)                    |
+-------------------------------------------------------------------+
```
*图 1：页内用户记录、空闲空间与页目录的动态空间博弈示意图*

1. **User Records（用户记录）**：我们通过业务 SQL 显式插入的数据行。如果是聚簇索引叶子节点，存放完整的数据行；如果是非叶子节点，存放目录项记录。
2. **Free Space（空闲空间）**：页内尚未被开辟的物理空白区域。在一张新表刚分配的干净数据页中，除了少量的管理元数据，几乎全都是空闲空间。
3. **Infimum + Supremum（最小与最大记录）**：由存储引擎自动初始化的两个系统虚拟记录，分别充当页内所有数据行的逻辑下确界与上确界。

#### 1.2 空间的生长、极限与页分裂

数据写入页内的物理过程，本质上是用户记录对空闲空间的“蚕食”：
- **初始状态**：用户记录区域大小为 0，空闲空间最大。
- **持续写入**：每次执行 `INSERT` 操作，InnoDB 便按照预设的行格式，从空闲空间中切分出一块对应尺寸的内存区域追加到用户记录区，空闲空间随之按字节缩减。
- **极限状态（页填满）**：随着写入推进，空闲空间被压缩至极限，无法再容纳哪怕一条新记录。
- **边界处理（页分裂）**：当现有页无法写入新记录时，存储引擎必须向操作系统申请开辟一个新的 16KB 数据页，并根据 B+ 树的平衡算法，将原页中的部分记录挪移到新页中，同时调整双向链表的前后指针。这一过程就是数据库内核中经典的**页分裂（Page Split）**。

### 2. 行格式之记录头信息（Record Header）微观拆解

用户记录在物理上是依次排列的，但我们在上一讲提到，它们在逻辑上必须构成一条**有序的单向链表**。

既然是链表，节点就必须携带指针；既然数据行可能被更新或删除，系统就必须维持状态位。这些底层的控制元数据，全部被封装在每条记录最前端的 **5 个字节（40 个 bit）** 的**记录头信息（Record Header）**中。

#### 2.1 实验环境准备与数据样本

为了直观观察 5 字节记录头信息的运作机制，我们构建一个极简的标准测试表，并插入 4 条测试数据：

```sql
CREATE TABLE page_demo(
    c1 INT,
    c2 INT,
    c3 VARCHAR(10000),
    PRIMARY KEY (c1)
) CHARSET=ascii ROW_FORMAT=Compact;

INSERT INTO page_demo VALUES
(1, 100, 'aaaa'),
(2, 200, 'bbbb'),
(3, 300, 'cccc'),
(4, 400, 'dddd');
```

> **设计说明**：
> 1. 表的字符集指定为 `ascii`。在 ASCII 编码下，一个英文字符严格对应 1 个字节，便于我们精确推算各字段的物理开销。
> 2. 行格式显式指定为最经典的 `Compact` 格式。
> 3. 列 `c1` 作为整型主键，聚簇索引将强制按照 `c1` 的升序组织存储。

#### 2.2 记录头信息的 5 字节微观结构

一条完整的 Compact 行格式记录由两大部分构成：**额外信息** 与 **真实数据**。

```text
+-----------------------------------------------------------------------+
|                              Compact 行格式                           |
+---------------------------------------+-------------------------------+
|               额外信息                |            真实数据           |
+-------------------+---------+---------+------+------+------+----------+
| 变长字段长度列表  | NULL 列表| 记录头  |  c1  |  c2  |  c3  |  隐藏列   |
|   (逆序排列)      |  位图   | (5 字节)| (INT)| (INT)|(VAR) |(Trx,Roll)|
+-------------------+---------+---------+------+------+------+----------+
```
*图 2：Compact 行格式物理构成全貌*

我们拿放大镜将这 **5 个字节（40 bit）** 的记录头信息展开，其内部严格划分如下：

```text
+-------+-------+-------------+--------------+---------+---------+-------------+-------------+
| 预留1 | 预留2 | delete_mask | min_rec_mask | n_owned | heap_no | record_type | next_record |
| 1 bit | 1 bit |    1 bit    |    1 bit     |  4 bit  | 13 bit  |    3 bit    |   16 bit    |
+-------+-------+-------------+--------------+---------+---------+-------------+-------------+
```
*图 3：5 字节（40 bit）记录头信息内部位域切分图*

下表详细汇总了各个位域的定义与功能规范：

| 字段名称 | 占用空间 | 取值含义与技术规范 |
| :--- | :---: | :--- |
| **预留位 1 & 2** | 各 1 bit | 预留标志位，当前版本暂未使用，固定置为 0。 |
| **`delete_mask`** | 1 bit | **逻辑删除标记**。`0` 表示记录处于有效状态；`1` 表示记录已被逻辑删除。 |
| **`min_rec_mask`** | 1 bit | **B+ 树非叶子节点最小目录项标记**。若为 `1`，表示该记录是 B+ 树某层非叶子节点中主键最小的目录项记录；普通数据行一律为 `0`。 |
| **`n_owned`** | 4 bit | **当前记录拥有的记录数**。专门服务于页目录（Page Directory）。每个槽所对应的组长记录在此记录当前组内的记录总数；非组长记录固定为 `0`。 |
| **`heap_no`** | 13 bit | **堆编号**。表示当前记录在当前数据页的堆（Heap）存储空间中的相对物理排布顺序编号。 |
| **`record_type`** | 3 bit | **记录类型**。`0`：普通用户记录；`1`：B+ 树非叶子节点目录项记录；`2`：Infimum 虚拟最小记录；`3`：Supremum 虚拟最大记录。 |
| **`next_record`** | 16 bit | **下条记录相对偏移量**。表示从当前记录的真实数据起始地址，到下一条记录的真实数据起始地址的字节相对偏移量。 |

### 3. 记录头关键属性深度剖析

#### 3.1 逻辑删除标记：delete_mask 与垃圾链表

在执行 `DELETE FROM page_demo WHERE c1 = 2;` 时，底层到底发生了什么？

很多初学者的直觉认知是：既然删除了 `c1 = 2` 这一行，InnoDB 就应该立刻把磁盘上这几十个字节的内容直接清空抹除，然后把后面 `c1 = 3` 和 `c1 = 4` 的记录在内存和磁盘物理地址上整体往前平移挪动，把空洞填满。

**这种设想完全违背了高性能存储引擎的设计准则。**

如果每删除一行就执行物理紧凑平移，对于一个包含数百条记录的数据页而言，将会触发极其昂贵的内存数据块批量搬运，导致 CPU 缓存频繁失效、磁盘碎片化重组，系统性能将发生雪崩。

InnoDB 的真实处理方案极其轻量：
1. **就地标记**：将目标记录记录头中的 `delete_mask` 从 `0` 修改为 `1`。
2. **指针脱轨**：将正常的用户数据单向链表绕过该记录。
3. **加入垃圾链表**：被删除的记录并不会消失，它的 `next_record` 会被重新指向页内的“垃圾链表（Garbage List / Free Record List）”表头。被标记删除的记录所占用的物理存储空间变成了“可重用空间”。
4. **空间重用**：未来若有新的数据插入且尺寸匹配，InnoDB 可以直接覆盖写这一块废弃的旧空间，避免了频繁申请新空间的开销。

#### 3.2 堆编号：heap_no 与神秘消失的 0 和 1

在上面插入 4 条测试记录后，如果我们通过底层的页面查看工具打印出各条记录的 `heap_no`，会发现一个极具颠覆性的现象：

```text
c1 = 1 的记录: heap_no = 2
c1 = 2 的记录: heap_no = 3
c1 = 3 的记录: heap_no = 4
c1 = 4 的记录: heap_no = 5
```

我们明明向表中新插入了 4 条记录，计算机系统的索引编号通常从 0 开始计数，为什么这 4 条记录的 `heap_no` 竟然是从 `2` 开始排布？编号 `0` 和 `1` 去了哪里？

> **结论**：编号 `0` 和 `1` 并没有丢失，而是被 MySQL 强制分派给了由引擎内部维护的两条**虚拟伪记录（Pseudo Records）**——`Infimum` 和 `Supremum`。

#### 3.3 下条记录指针：next_record 与相对偏移量本质

`next_record` 是串联单向链表的最核心支柱。它占用 16 个 bit（2 个字节），采用有符号整数表示。

很多同学初次分析行格式十六进制转储时，看到连续多条记录的 `next_record` 字段都写着相同的正数值（例如都显示为 `32`），常常会感到费解：“为什么多条记录的指针数值一模一样？难道它们都死板地指向了内存中同一个绝对地址？”

必须明确：**`next_record` 存储的绝不是物理内存的绝对指针地址，而是相对位置偏移量（Relative Offset）**。

```text
[Record N 的记录头] [Record N 真实数据起点] --(向前推进 32 字节)--> [Record N+1 真实数据起点]
                             ^                                      ^
                             |                                      |
                             +----------- next_record = 32 ---------+
```
*图 4：next_record 相对偏移量寻址示意图*

- **相对寻址机制**：`next_record` 的基准点是当前记录的“真实数据起始位置”（即记录头与真实数据列的交界处）。`next_record = 32` 意味着：从当前记录的真实数据第一个字节开始，向后顺序数 32 个字节，恰好就能精准定位到下一条记录的真实数据起始位置。
- **正负指向规则**：
  - 如果下一条逻辑上有序的记录在物理位置上排在当前记录的后面，`next_record` 为**正数**；
  - 如果经过多次插入与删除后，下一条逻辑有序的记录在物理位置上被分配到了当前记录的前面，`next_record` 就会成为一个**负数**。

这种精巧的相对偏移量设计，使得数据记录无论被加载到内存缓冲区的哪一个物理地址段，都不需要逐一重定位和修改指针，极大地提升了页在内存与磁盘间置换的性能。

### 4. 虚拟边界记录：Infimum 与 Supremum

既然记录是以单向链表维系的，任何严谨的数据结构实现中，链表都必须具备清晰稳定的“头哨兵”与“尾哨兵”。

在 InnoDB 的数据页中，担任这一重任的正是 **Infimum（最小虚拟记录）** 与 **Supremum（最大虚拟记录）**。

#### 4.1 概念定位与数学内涵

在高等数学中，`Infimum` 表示集合的**下确界**（即小于等于集合中一切元素的最大下界）；`Supremum` 表示集合的**上确界**（即大于等于集合中一切元素的最紧上界）。

InnoDB 借用了这两个数学概念：
- **Infimum 记录**：代表当前数据页中在逻辑上比任何用户自定义主键都小的绝对最小值；
- **Supremum 记录**：代表当前数据页中在逻辑上比任何用户自定义主键都大的绝对最大值。

无论用户在表中插入了多小的主键（哪怕是整型极小值或负数），或者多大的主键，它们在逻辑大小上都必须严格夹在 Infimum 与 Supremum 之间。

#### 4.2 虚拟记录的 13 字节物理规格

最小与最大记录属于系统固定分配的边界结构，位于 `Page Header` 之后、`User Records` 之前，合计固定占用 **26 个字节**。每条虚拟记录各占 **13 个字节**：

```text
+---------------------------------------+---------------------------------------+
|        Infimum 记录 (13 字节)          |        Supremum 记录 (13 字节)        |
+-------------------+-------------------+-------------------+-------------------+
| 记录头信息 (5 字节)| 真实内容 (8 字节) | 记录头信息 (5 字节)| 真实内容 (8 字节) |
| record_type = 2   | "infimum\0"       | record_type = 3   | "supremum"        |
| heap_no = 0       | (ASCII 字节流)    | heap_no = 1       | (ASCII 字节流)    |
+-------------------+-------------------+-------------------+-------------------+
```
*图 5：Infimum 与 Supremum 虚拟记录的内部 13 字节布局*

- **前 5 个字节**：标准的记录头信息。
  - 对于 Infimum：`record_type = 2`，`heap_no = 0`；
  - 对于 Supremum：`record_type = 3`，`heap_no = 1`。
- **后 8 个字节**：固定的字符常量。
  - Infimum 的数据部分直接填充字符串 `"infimum\0"`；
  - Supremum 的数据部分直接填充字符串 `"supremum"`。

### 5. 记录链表的全生命周期流转实例

我们将前面拆解的所有概念统揽起来，通过“初始插入 $\rightarrow$ 执行删除 $\rightarrow$ 重新插入”三个阶段，全流程追踪页内记录链表与状态标志位的微观流转。

#### 5.1 阶段一：初始稳态链路

当我们的测试表刚插入 4 条数据（主键分别为 1, 2, 3, 4）时，页内的完整逻辑链表拓扑如下：

```text
[Infimum (heap_no=0)]
         | next_record > 0
         v
[Row 1: id=1 (heap_no=2, delete_mask=0)]
         | next_record > 0
         v
[Row 2: id=2 (heap_no=3, delete_mask=0)]
         | next_record > 0
         v
[Row 3: id=3 (heap_no=4, delete_mask=0)]
         | next_record > 0
         v
[Row 4: id=4 (heap_no=5, delete_mask=0)]
         | next_record > 0
         v
[Supremum (heap_no=1)] (next_record = 0，链表终点)
```
*图 6：4 条用户记录与 Infimum/Supremum 构成的完整有序链表*

- 逻辑链表始终从 `Infimum` 出发；
- `Infimum` 的 `next_record` 精准指向页内主键最小的真实记录（`Row 1`）；
- 用户记录内部顺次向后指引，呈现严格的物理与逻辑双重递增；
- 最大的用户记录（`Row 4`）的 `next_record` 指向 `Supremum`；
- `Supremum` 作为终点哨兵，其 `next_record` 为 0，终止遍历。

#### 5.2 阶段二：删除记录的指针脱轨与状态演变

此时我们执行删除操作，移除主键为 2 的记录：
```sql
DELETE FROM page_demo WHERE c1 = 2;
```

底层的微观结构瞬时发生如下剧变：

```text
[Infimum] 
    |
    v
[Row 1: id=1] ------------+ (next_record 直接跨越指向 Row 3)
                          |
[Row 2: id=2] <-----------+ (delete_mask 从 0 置为 1，脱离正常检索链表)
  (挂入垃圾链表)            |
                          v
                    [Row 3: id=3]
                          |
                          v
                    [Row 4: id=4]
                          |
                          v
                    [Supremum] (所在组的 n_owned 从 5 递减为 4)
```
*图 7：删除主键为 2 的记录后页内链表与状态位变更时序图*

1. **删除标记置位**：`Row 2` 的记录头中，`delete_mask` 由 `0` 翻转为 `1`。物理数据原封不动停留在原处。
2. **正常链表绕路**：前驱节点 `Row 1` 的 `next_record` 被重新计算并改写，直接跳过 `Row 2`，精准指向 `Row 3` 的起始位置。
3. **检索隔离**：后续任何正常的 SQL 查询沿着 `Infimum` 顺藤摸瓜时，根本不会再访问到 `Row 2`，它在逻辑上已经“死亡”。
4. **组内计数调减**：负责监控该记录所在槽的组长记录（即 `Supremum`），其记录头中的 `n_owned` 计数自动由 `5` 调减为 `4`。

#### 5.3 阶段三：重新插入与物理空间复用

随后，我们再次执行插入操作，把主键为 2 的数据重新插回：
```sql
INSERT INTO page_demo VALUES (2, 200, 'bbbb');
```

存储引擎并不需要去开辟新的空闲空间，而是执行空间重用复活流程：
1. **垃圾空间捕获**：InnoDB 在页内垃圾链表中检索到了原先释放出来的空闲槽位（原 `Row 2` 所在区域），其容量完全吻合。
2. **数据就地覆写**：直接将新的列值写入该物理区域，并将记录头中的 `delete_mask` 重新清零（由 `1` 恢复为 `0`）。
3. **链表指针重挂**：修改 `Row 1` 的 `next_record` 指向复活后的 `Row 2`，同时设置 `Row 2` 的 `next_record` 指向 `Row 3`。
4. **状态与计数复原**：`Supremum` 的 `n_owned` 计数重新由 `4` 递增恢复为 `5`。

> **核心结论**：
> 无论我们在一个数据页内执行何种剧烈的增删改操作，InnoDB 始终依托 **5 字节记录头** 维护着一条坚不可摧的、按主键升序排列的单向逻辑链表。这条链表始于 `Infimum`，终于 `Supremum`，为上层索引扫描提供了绝对有序的底层保证。

## 第 4 章：124-页结构之页目录与页头
> 对应分集：P124 | 原始标题：《124-页结构之页目录与页头》

在前面的章节中，我们系统拆解了文件头尾的安全校验机制，并深入分析了用户记录通过 5 字节记录头串联成单向链表的过程。但在上一讲的推演中，我们留下了一个关键悬念：记录头信息里的 `n_owned` 字段到底承担什么职责？为什么它在组长记录中记录着数值，在普通记录中却全部归零？

这一切的底层答案，全部指向数据页内部的第三大核心模块：**页目录（Page Directory）** 与 **页头部（Page Header）**。

单向链表虽然带来了极低的插入与删除开销，却在检索层面存在着天然的致命缺陷：无法随机访问，查找复杂度高达 $O(n)$。如果一个页容纳了上千条数据，我们好不容易通过 B+ 树各层目录页定位到了该数据页，若在页内只能靠单向链表逐行硬扫，整体检索效率依然会崩溃。本讲我们将彻底揭晓 InnoDB 如何利用精巧的“页目录稀疏索引”与“折半二分法”打破这一性能瓶颈，并全景剖析控制整个数据页状态的“仪表盘”——Page Header。

---

### 1. 页目录（Page Directory）的设计初衷与稀疏索引权衡

#### 1.1 链表检索困境与二分查找诉求

当 SQL 查询的主键通过上层 B+ 树索引路由，精准降落到某个具体的叶子节点数据页时，面临的第一道考题就是：**如何在当前 16KB 页内的数百甚至上千条记录中，以最短的时间锁定目标行？**

- **方案一：顺序扫描（Sequential Scan）**
  顺着 `Infimum` 哨兵记录的 `next_record` 指针，沿着单向链表一条一条向后比对主键值。这种方式的时间复杂度是线性的 $O(n)$。当单页记录繁多时，CPU 周期将被大量无意义的指针跳转和缓存未命中消耗殆尽。
- **方案二：折半二分查找（Binary Search）**
  在计算机算法中，对于有序序列，最理想的高速定位方式无疑是二分查找，其时间复杂度为极为优异的对数阶 $O(\log_2 n)$。

#### 1.2 为什么不建立“全量稠密目录”

既然要用二分查找，二分查找的前提是数据必须具备**类似连续数组的随机下标寻址能力**。

很多初学者会自然产生一种设想：既然要二分，为什么不在页尾建立一个全量数组，把页内 1000 条记录的主键和指针按顺序全抄一遍？

**这种稠密索引设计的代价是存储引擎完全无法承受的。**

尤其是在非聚簇索引（二级索引）的场景下，叶子节点页内只存放索引列与主键，单条记录的物理体积可能只有十几个字节，一个 16KB 的页内轻松容纳一两千条记录。如果对每一条记录都硬性抽取主键建立目录项，目录本身就会吃掉数百甚至数千字节的宝贵空间，相当于在页内近乎完整复制了一份用户记录，引发严重的存储膨胀。

InnoDB 给出的工程解法极其优雅：**不搞全量稠密索引，而是搞分组稀疏索引（Sparse Index）**。

```text
[全部有序记录] 划分为若干组 (每组 4~8 条)
      |
      v
只提取各组最大记录的地址偏移量
      |
      v
紧凑存入页底部的槽数组 (Page Directory Slots)
```
*图 1：页目录从全量单向链表向稀疏分组槽位抽取的逻辑抽象*

将页内所有记录切分为若干个小组，每组只挑选出主键最大的那条“组长记录”，把组长的相对地址偏移量提取出来，按顺序存入页底部的数组中。这个数组就是**页目录**，数组中的每一个元素被称为一个**槽（Slot）**。

---

### 2. 页目录的分组规则与槽位（Slot）机制

#### 2.1 记录分组的核心规则

页目录对记录的分组并非随意切分，而是受到底层极其严密的数学边界约束：

1. **成员纳管边界**：
   - 必须纳入分组：包含系统虚拟记录 `Infimum` 和 `Supremum`；
   - **绝对排除在外**：已经被打上删除标记（`delete_mask = 1`）的失效记录，绝不允许计入任何分组。
2. **第一组的绝对特殊性**：
   - 第一组固定且唯一归属于虚拟最小记录 `Infimum`；
   - **该组有且仅有 1 条记录**，即 `Infimum` 自成一组。
3. **最后一组的动态边界**：
   - 最后一组必定包含虚拟最大记录 `Supremum`；
   - 该组允许容纳的记录条数范围为 **1 到 8 条**。
4. **中间其余各组的标准规格**：
   - 处于中间的正常数据分组，记录条数严格限定在 **4 到 8 条** 之间。

#### 2.2 组长特权与 n_owned 的真相

现在，我们可以彻底揭开上一讲留下的 `n_owned` 字段的谜底：

> **定义**：在一个分组中，主键最大的那条记录被称为“组长”。**只有组长记录的 5 字节记录头中，`n_owned` 字段才会记录当前组内实际拥有的记录总数；该组内其余所有普通成员的 `n_owned` 统统强制置为 0。**

```text
+-----------------------------------------------------------------------+
| 槽位 (Slot) | 对应分组形态                    | 组长记录 (最大主键) | n_owned |
+-------------+---------------------------------+---------------------+---------+
| Slot 0      | 第一组 (固定仅 Infimum)         | Infimum 记录        |    1    |
| Slot 1      | 中间组 (如包含记录 1, 2, 3, 4)   | 记录 4              |    4    |
| Slot 2      | 中间组 (如包含记录 5, 6, 7, 8)   | 记录 8              |    4    |
| Slot 3      | 最后一组 (包含记录 9 及 Supremum)| Supremum 记录       |    5    |
+-------------+---------------------------------+---------------------+---------+
```
*图 2：各槽位对应的分组边界与组长记录 n_owned 取值对照表*

页目录中的每一个槽（Slot）固定占用 **2 个字节**，里面存放的就是该组组长记录在页内的相对地址偏移量。槽与槽在物理上是逆序从页底向上紧挨着存放的，因此在内存中可以直接视为一个支持下标随机访问的连续数组。

### 3. 分组分裂机制与槽位动态演进

数据页中的记录条数是随着业务 `INSERT` 动态增加的，页目录中的槽位数量又是如何伴随分组裂变而增加的？

我们通过一组连续的插入推演来追踪这一过程：

#### 3.1 初始状态：两极双槽

在一个刚刚完成初始化的全新空数据页中，只有 `Infimum` 和 `Supremum` 两条虚拟记录。

此时系统只有 2 个槽：
- **Slot 0**：指向 `Infimum`，其 `n_owned = 1`；
- **Slot 1**：指向 `Supremum`，其 `n_owned = 1`。

```text
Slot 0 (偏移量) ----> [ Infimum (n_owned=1) ]
                            | next_record
                            v
Slot 1 (偏移量) ----> [ Supremum (n_owned=1) ]
```

#### 3.2 持续插入：最后一组的膨胀

当业务开始写入主键递增的用户数据时（如依次插入主键为 1, 2, 3, 4 的记录）：
- `Infimum` 组规格被锁死为 1，不可扩张；
- 新插入的记录全部被顺延划分进包含 `Supremum` 的最后一组；
- `Supremum` 依然是该组的主键最大记录（因为任何主键都不可能超过上确界）；
- `Supremum` 的 `n_owned` 随着每条新记录的加入而单调递增：从 1 变成 2、3、4，直到插入第 4 条真实记录后，`Supremum` 的 `n_owned = 5`（包含 4 条真实记录 + 1 条 Supremum）。

#### 3.3 触达阈值：分组裂变与新槽诞生

当业务持续向最后一组插入数据，直到该组的总记录数达到 **8 条** 时，最后一组的容量达到法定上限。

如果此时再次写入第 9 条记录：
1. **超限触发**：当前组记录数达到 9 条，突破了“组内最多容纳 8 条”的铁律；
2. **分组裂变**：InnoDB 强制将原本的 9 条记录拆分成两个独立小组：
   - 提取前半段较小的 **4 条记录**，独立切为一个全新的中间组；
   - 让第 4 条记录担任新组的组长，其记录头中的 `n_owned` 置为 `4`；
   - 剩下的 **5 条记录**（后 4 条较大记录 + Supremum）保留在原最后一组，`Supremum` 的 `n_owned` 调整为 `5`；
3. **分配新槽**：在页目录中开辟一个新的 Slot 槽位，写入新中间组组长（第 4 条记录）的相对偏移量。

```text
分裂前 (达到 9 条超限):
[Record 1..8] + [Supremum] (全塞在 Slot 1 中，n_owned = 9 违规！)
                      |
                      v  (裂变为 4 + 5 结构)
分裂后 (生成新槽位):
Slot 1: 指向 Record 4 (新组长, n_owned = 4)
Slot 2: 指向 Supremum (最后一组组长, n_owned = 5)
```
*图 3：组内达到 9 条记录时触发 4+5 裂变并追加槽位示意图*

正是凭借这一动态分裂机制，随着数据规模膨胀，页内的小组通常呈现出规整的 `1（Infimum组）, 4, 4, 4, ..., 5~8（Supremum组）` 的分布格局。

### 4. 基于页目录的折半查找（二分法）全流程

当上层引擎确定目标主键位于当前数据页后，基于页目录的二分定位是如何执行的？

我们以一个包含 18 条记录、划分为 5 个槽位（Slot 0 至 Slot 4）的成熟数据页为例，推导检索主键为 `target` 的完整闭环。

```text
页目录 (连续槽数组):
Slot 0 (Infimum, n_owned=1)
Slot 1 (组长 PK=4, n_owned=4)
Slot 2 (组长 PK=8, n_owned=4)
Slot 3 (组长 PK=12, n_owned=4)
Slot 4 (Supremum, n_owned=5)
```

#### 4.1 第一阶段：槽位数组的二分折半

设初始查找区间指针：`low = 0`, `high = 4`。

1. **计算中点槽位**：
   $$\text{mid} = \frac{\text{low} + \text{high}}{2} = \frac{0 + 4}{2} = 2$$
2. **抓取中点组长**：通过 `Slot 2` 中记录的偏移量，瞬间寻址到该组组长记录，取出其主键值（假设为 `8`）。
3. **比对区间收缩**：
   - 假设目标主键 `target = 6`；
   - 因为 `6 < 8`，说明目标行不可能在 `Slot 2` 之后的小组中，收缩高端边界：`high = mid = 2`；
   - 重新计算 `mid = (0 + 2) / 2 = 1`，读取 `Slot 1` 组长的主键（假设为 `4`）；
   - 因为 `6 > 4`，说明目标行必定不在 `Slot 1` 及其之前的小组中，收缩低端边界：`low = mid = 1`。
4. **区间锁定**：此时 `high - low = 1`，二分法顺利将目标范围锁定在 **Slot 1 组长与 Slot 2 组长之间**！
   > **结论**：目标主键必定归属于 **Slot 2** 所管辖的小组。

#### 4.2 第二阶段：逆向单链表的切入技巧

此时面临一个极度考验算法细节的难题：
- 我们确定目标在 `Slot 2` 的组内；
- 但是 `Slot 2` 存取的偏移量是指向该组的**最大记录（组长）**；
- 页内的记录链表是**单向链表**，指针只能从小到大向后单向遍历，根本无法从组长向前回溯！

InnoDB 如何从组内的最小记录开始向后比对？

**核心绝技：借道上一个槽（Slot 1）的组长记录！**

```text
Slot 1 组长 (PK=4) 
       |
       | next_record (精准跨入 Slot 2 组内的第一条记录！)
       v
[PK=5] -> [PK=6 (目标命中！)] -> [PK=7] -> [PK=8 (Slot 2 组长)]
```
*图 4：利用上一槽位组长 next_record 指针切入目标组遍历图*

1. 系统直接通过 `Slot 1` 找到上一组的组长（主键为 4 的记录）；
2. 顺着该组长的 `next_record` 指针向前踏出一步，直接精准切入到 `Slot 2` 组内的第一条记录（主键为 5 的行）；
3. 沿着单向链表向后比对。因为组内受到规则约束，最多只有 4 到 8 条记录，线性比对仅需执行极少几次；
4. 当比对到主键为 6 的记录时，数据精准命中返回。

整套组合拳下来，二分查找耗时极短，组内扫描至多不超过 8 次遍历，单页内的检索瓶颈被彻底粉碎。

### 5. 页头部（Page Header）的 56 字节状态仪表盘

如果说页目录是负责单页加速检索的发动机，那么位于文件头之后的 **Page Header（页头部）** 就是整个数据页的运行状态仪表盘。

Page Header 固定占据 **56 个字节**，专门用于记录数据页（索引页）内部独有的运行状态与统计信息。

```text
+---------------------------------------------------------------------------------------+
|                                Page Header (共 56 字节)                               |
+----------------------+----------+-----------------------------------------------------+
| 字段名称             | 字节大小 | 核心用途与职能说明                                  |
+----------------------+----------+-----------------------------------------------------+
| PAGE_N_DIR_SLOTS     | 2 字节   | 页目录中当前的槽 (Slot) 总数量                       |
| PAGE_HEAP_TOP        | 2 字节   | 空闲空间 (Free Space) 的最小物理地址偏移量           |
| PAGE_N_HEAP          | 2 字节   | 当前页内分配的所有记录总数 (含虚拟记录与已删除记录)  |
| PAGE_FREE            | 2 字节   | 垃圾链表 (已标记删除记录链表) 的头节点物理地址偏移量|
| PAGE_GARBAGE         | 2 字节   | 当前页内所有已标记删除记录累计占用的总字节数        |
| PAGE_LAST_INSERT     | 2 字节   | 最后一次插入记录的物理位置偏移量                    |
| PAGE_DIRECTION       | 2 字节   | 最后一次插入的方向 (向左/向右)                      |
| PAGE_N_DIRECTION     | 2 字节   | 连续向同一个方向插入记录的累计次数                  |
| PAGE_N_RECS          | 2 字节   | 当前页内实际有效的用户记录条数 (不含虚拟与删除记录) |
| PAGE_MAX_TRX_ID      | 8 字节   | 修改当前页面的最大事务 ID                           |
| PAGE_LEVEL           | 2 字节   | 当前页在 B+ 树中所处的层级 (叶子节点恒为 0)          |
| PAGE_INDEX_ID        | 8 字节   | 当前页面所属的索引唯一 ID                           |
| PAGE_BTR_SEG_LEAF    | 10 字节  | B+ 树叶子节点段的段头信息 (仅在根页面有效)          |
| PAGE_BTR_SEG_TOP     | 10 字节  | B+ 树非叶子节点段的段头信息 (仅在根页面有效)        |
+----------------------+----------+-----------------------------------------------------+
```
*图 5：Page Header 内部 56 字节各状态字段全貌表*

我们重点剖析其中最关键的系统状态指标：

#### 5.1 空间与记录统计指标

- **`PAGE_N_DIR_SLOTS`**：页目录中的槽数。在执行二分查找初始化时，二分查找的高端指针直接由此字段赋值：`high = PAGE_N_DIR_SLOTS - 1`。
- **`PAGE_HEAP_TOP`**：物理未分配空间的起始指针。每当有全新记录插入且无法从垃圾链表重用时，引擎直接从 `PAGE_HEAP_TOP` 处划拨内存，并将其指针向后推移对应字节数。
- **`PAGE_N_RECS` 与 `PAGE_N_HEAP` 的精细辨析**：
  - `PAGE_N_RECS`（2 字节）：记录该页内**真实有效**的用户数据行数。不包含 `Infimum`、`Supremum`，也不包含被 `delete_mask = 1` 标记删除的行。
  - `PAGE_N_HEAP`（2 字节）：记录当前数据页堆内已分配的**全部物理记录总数**。不仅包含了真实的有效数据，还把 `Infimum`、`Supremum` 两个哨兵以及垃圾链表中的所有废弃记录统统算在内。

#### 5.2 垃圾回收与空间复用指标

- **`PAGE_FREE`**：这是我们在前两讲多次强调的**垃圾链表头指针**。所有被执行 `DELETE` 标记删除的记录，通过自身的 `next_record` 彼此链接成单向链表，而这个链表的入口地址就存放在 `PAGE_FREE` 中。当有新记录插入时，引擎会优先顺着 `PAGE_FREE` 检索是否有大小匹配的废弃槽位可供覆写。
- **`PAGE_GARBAGE`**：统计垃圾链表累计吞噬的碎片字节数。当该数值累积过大且页内空闲空间告急时，InnoDB 会触发页内物理重组（Defragmentation），将有效数据集中紧凑重排，彻底回收碎片。

#### 5.3 插入方向感知与自增优化

在 Page Header 中，有一组极为精巧的自适应优化参数：`PAGE_DIRECTION` 与 `PAGE_N_DIRECTION`。

- **`PAGE_DIRECTION`**：表示最后一次插入的方向。若新插入记录的主键比上一条插入记录的主键大，标记为向右插入（递增）；反之标记为向左插入。
- **`PAGE_N_DIRECTION`**：记录连续同向插入的次数。

> **底层优化机理**：
> 如果业务表使用了 `AUTO_INCREMENT` 自增主键，几乎所有的插入都是单调递增的向右插入。此时 `PAGE_N_DIRECTION` 会持续飙升。InnoDB 监测到这一特征后，在后续插入新记录时，不再做多余的槽位折半比对，而是直接假定新记录应当追加在上一条记录之后，从而省去了大量二分检索开销。这就是官方为什么强烈建议业务表必须采用自增单调递增主键的微观底层原因之一。

## 第 5 章：125-设置行格式与ibd文件剖析Compact行格式
> 对应分集：P125 | 原始标题：《125-设置行格式与ibd文件剖析Compact行格式》

在探讨具体的行格式之前，我们先从宏观的 B+ 树数据页检索谈起。在前面讲解数据页内部结构时，我们把 B+ 树抽象为由一个个数据页通过双向链表相连的层级结构。当我们在日常开发或面试中遇到这样一个问题：**在同一个表中，普通索引和唯一索引在查询性能上到底有多大差异？**

很多人直觉上会认为唯一索引一定比普通索引快得多。其实从物理存储机制来看，两者性能几乎没有可感知的差别。假设我们查找字段 `c2 = 10` 的记录：对于唯一索引，由于有 `UNIQUE` 约束保证数据唯一，当在数据页的单向链表中找到 `c2 = 10` 的记录时，任务便宣告完成，CPU 不需要再往后读指针；而对于普通索引，由于该字段允许重复，定位到第一条 `10` 之后，必须顺着 `next_record` 指针再读下一条，直到遇到大于 `10` 的值为止。

> **结论**：数据库读写磁盘的最小单位是页（Page，默认 16KB）。在查询发生时，整座包含目标数据的数据页已经被完整加载到了内存的缓冲池（Buffer Pool）中。在内存中，CPU 顺着单向链表多遍历一条甚至几条记录的开销仅在纳秒级别，相对于磁盘 I/O 而言完全可以忽略不计。

理解了数据在“页”层面的交互，接下来必须进一步深入到物理存储的核心微观单元——**行格式（Row Format，亦称记录格式）**。数据页内部存储的一行行数据，到底在二进制字节流中是以怎样的格式排布的？

---

### 1. InnoDB 的四种行格式与设置语法

InnoDB 存储引擎演进至今，主要支持四种行格式：
1. **Compact**：紧凑行格式。自 MySQL 5.1 引入，核心设计目标是消除物理存储中的冗余字段，使数据页能容纳更多记录，提高内存与缓存的利用效率。
2. **Dynamic**：动态行格式。MySQL 5.7 与 MySQL 8.0 的默认行格式，针对行溢出（Off-page）机制做了进一步优化。
3. **Compressed**：压缩行格式。在 Dynamic 的基础上，对存放在物理页上的数据和行溢出数据进行 zlib 压缩存储。
4. **Redundant**：冗余行格式。MySQL 5.0 之前使用的古老格式，不具备 Compact 的紧凑特性，保留了大量冗余元数据。

#### 1.1 查看与配置默认行格式

在 MySQL 中，全局或会话级别的默认行格式由系统变量 `innodb_default_row_format` 控制。可以通过以下 SQL 语句查看：

```sql
SHOW VARIABLES LIKE 'innodb_default_row_format';
```

在 MySQL 5.7 和 MySQL 8.0 环境下，该变量的默认查询结果均为 `dynamic`。

#### 1.2 指定与修改表的行格式

在建表或维护已有表时，我们可以显式指定行格式，语法如下：

```sql
-- 1. 创建表时指定行格式为 Compact
CREATE TABLE emp3 (
    id INT,
    name VARCHAR(15)
) ROW_FORMAT = COMPACT;

-- 2. 修改已有表的行格式
ALTER TABLE emp2 ROW_FORMAT = COMPACT;

-- 3. 查看指定表的行格式状态
SHOW TABLE STATUS LIKE 'emp3'\G
```

执行 `SHOW TABLE STATUS` 后，结果集中的 `Row_format` 字段会明确显示当前表采用的实际行格式（如 `Compact` 或 `Dynamic`）。

---

### 2. Compact 行格式的物理排布模型

Compact 行格式之所以被称为“紧凑型”，是因为它在二进制层面剔除了所有可以由元数据计算得出的占位空间。一条完整的 Compact 记录在物理存储上严格划分为两大部分：**记录的额外信息**与**记录的真实数据**。

```text
+-----------------------------------------------------------------------------------+
|                                 记录的额外信息                                     |
+--------------------------------+-----------------+--------------------------------+
|     变长字段长度列表 (逆序)    |   NULL 值列表   |     记录头信息 (固定 5 字节)    |
+--------------------------------+-----------------+--------------------------------+

+-----------------------------------------------------------------------------------+
|                                 记录的真实数据                                     |
+-------------------+--------------------+--------------------+---------------------+
| DB_ROW_ID (6 字节)| DB_TRX_ID (6 字节) | DB_ROLL_PTR (7 字节)| 列 1 值 | 列 2 值 ...|
+-------------------+--------------------+--------------------+---------------------+
```

> **读图说明**：一条记录由左至右连续存储。前三个部分为额外信息，紧接着是三个系统保留隐藏列（视建表条件可能省略 `DB_ROW_ID`），随后按字段顺序排列用户实际插入的列数据。

---

### 3. 记录的额外信息核心组成

#### 3.1 变长字段长度列表

在 MySQL 中，`VARCHAR(M)`、`VARBINARY(M)`、`TEXT`、`BLOB` 等类型属于变长数据类型。这意味着字段占用的实际物理字节数取决于具体存入的内容，而不是定义时的最大长度 $M$。

例如，定义 `col VARCHAR(8)`，但实际插入 `'songhk'`。在单字节字符集（如 ASCII、latin1）下，实际仅占用 6 个字节。如果底层存储引擎只把 6 个字节写入文件，而在读取时不知道该字段的具体长度，就无法确定该字段在何处截断。因此，Compact 行格式必须显式记录每个非空变长字段的实际占用字节数。

变长字段长度列表具有以下三大关键特征：
1. **仅记录变长字段**：定长类型（如 `INT`、单字节字符集下的 `CHAR(10)`）占用字节固定，不记录在该列表中。
2. **仅记录非 NULL 字段**：若某个变长字段的值为 `NULL`，其实际长度为 0，该字段的长度信息直接省略，不在该列表中占位（其 NULL 状态完全由 NULL 值列表管理）。
3. **逆序排列**：若表中变长字段按定义顺序为 `col1`、`col2`、`col4`，其实际占用字节数分别为 1 字节、2 字节、3 字节，则长度列表中记录的顺序为 `03 02 01`。

> **提示（为什么必须逆序存储）**：
> 记录头信息中的 `next_record` 记录指针指向的位置并不是整行记录的最前端，而是**记录头信息与真实列数据之间的分界点**。
> 当读取指针定位在分界点时：
> - 向右读是用户真实列数据：第 1 列、第 2 列、第 3 列……
> - 向左读是元数据额外信息：第 1 个字节对应第 1 列的长度，第 2 个字节对应第 2 列的长度……
> 这样元数据与实际数据的排布在逻辑上构成了“对称展开”，最大化提升了 CPU 缓存读取连续内存时的局部性。

#### 3.2 NULL 值列表

在数据表中，许多列允许为 `NULL`。如果将 `NULL` 作为特定字符或者直接用定长空字节填充在真实数据区中，会浪费大量宝贵的物理存储空间；而如果直接略过，解析引擎又无法判断哪一列被跳过。

Compact 行格式的做法是：把所有允许为 `NULL` 的列统一提取到前置的 **NULL 值列表（NULL Value List）** 中，用紧凑的二进制位（bit）进行标记。

NULL 值列表的生成算法遵循如下严格步骤：
1. **统计可为 NULL 的列**：遍历表结构中所有列，排除声明了 `NOT NULL` 的列以及主键列（主键天然不允许为 NULL）。如果一张表所有列都定义为 `NOT NULL`，则该记录中的 NULL 值列表完全不生成，节省整段开销。
2. **用 bit 位映射状态**：每一个允许为 NULL 的列对应一个二进制位：
   - 二进制位为 `1`：代表该列的值为 `NULL`；
   - 二进制位为 `0`：代表该列的值非 `NULL`。
3. **逆序排列**：按照字段定义的相反顺序依次填充 bit 位。即定义靠前的列存放在二进制的低位，定义靠后的列存放在高位。
4. **按字节高位补齐**：NULL 值列表的存储单位是整字节（Byte，8 bit）。如果可为 NULL 的列数为 $N$ 个，所占用的字节数为 $\lceil N / 8 \rceil$ 个。不足 8 位的高位全部用 `0` 补齐。

#### 3.3 记录头信息（Record Header）

Compact 格式的记录头信息固定占用 **5 个字节（40 个 bit）**，包含行记录在数据页内部运行与组织所需的各类标记：

| 标记名称 | 位数（bit）| 技术含义与功能 |
| :--- | :--- | :--- |
| `delete_mask` | 1 | 逻辑删除标记：`0` 表示未删除，`1` 表示已执行 `DELETE`（进入垃圾链表） |
| `min_rec_mask` | 1 | B+ 树每层非叶子节点目录项记录中的最小记录标记 |
| `n_owned` | 4 | 当前记录所在分组拥有的记录条数（配合页目录 Page Directory） |
| `heap_no` | 13 | 当前记录在页面堆中的相对位置序号（0 为 Infimum，1 为 Supremum） |
| `record_type` | 3 | 记录类型：`000` 普通用户记录，`001` B+ 树非叶子节点目录项，`010` 最小记录，`011` 最大记录 |
| `next_record` | 16 | 核心偏移量指针：当前记录与下一条记录之间的相对地址差值（构成页内单向链表） |

---

### 4. 记录的真实数据与系统隐藏列

在用户自定义的业务数据列之前，InnoDB 会自动追加若干系统保留的隐藏列：

1. **`DB_ROW_ID`（row_id，6 字节）**：
   - 当用户建表时显式指定了主键（`PRIMARY KEY`），或者定义了非空的唯一索引（`UNIQUE NOT NULL`）时，InnoDB 会直接复用该列构建聚簇索引，此时记录中**不会**生成 `DB_ROW_ID`。
   - 只有当表中既没有主键也没有非空唯一键时，InnoDB 才会强制生成一个 6 字节的全局自增隐藏行 ID，以此维系“索引即数据、数据即索引”的聚簇索引底层骨架。
2. **`DB_TRX_ID`（transaction_id，6 字节）**：
   - 事务 ID。记录最新插入或修改该行记录的事务唯一标识，用于支撑 MVCC 多版本并发控制与事务一致性读。
3. **`DB_ROLL_PTR`（roll_pointer，7 字节）**：
   - 回滚指针。指向该行在 undo log 历史版本链中的最新物理存储地址，用于事务回滚与历史版本快照重构。

---

### 5. 基于十六进制编辑器的 .ibd 文件底层逐字节剖析

为了彻底穿透理论，验证 Compact 格式在磁盘上的字节排布，我们通过 MySQL 实际建表，并使用十六进制编辑器对数据表对应的独立表空间文件（`.ibd`）进行实战剖析。

#### 5.1 实验环境与数据构建

执行以下 SQL 语句建立测试环境，设置字符集为单字节的 `latin1`，行格式显式指定为 `COMPACT`：

```sql
CREATE TABLE mytest (
    col1 VARCHAR(10),
    col2 VARCHAR(10),
    col3 CHAR(10),
    col4 VARCHAR(10)
) ENGINE=InnoDB CHARACTER SET=latin1 ROW_FORMAT=COMPACT;

-- 插入三条具有对照意义的典型测试数据
INSERT INTO mytest VALUES('a', 'bb', 'bb', 'ccc');
INSERT INTO mytest VALUES('d', 'ee', 'ee', 'fff');
INSERT INTO mytest VALUES('d', NULL, NULL, 'fff');
```

数据写入后，在 MySQL 数据存储目录（例如 Windows 平台下的 `C:\ProgramData\MySQL\MySQL Server 8.0\Data\atguigudb\mytest.ibd`）定位到该文件。在 MySQL 8.0 中，表的元数据与物理数据统一整合在该独立表空间内。使用具备 Hex-Editor 插件的文本编辑器打开该二进制文件。

#### 5.2 第一条记录物理字节流解构

在十六进制视窗中定位到第一条用户记录的物理偏移位置，截获的连续十六进制数据串如下：

```text
03 02 01 00 00 00 10 00 2c [ROW_ID: 6字节] [TRX_ID: 6字节] [ROLL_PTR: 7字节] 61 62 62 62 62 20 20 20 20 20 20 20 20 63 63 63
```

我们对这串字节流进行逐段解构：

1. **变长字段长度列表（`03 02 01`）**：
   - 表中变长字段为 `col1`、`col2`、`col4`；`col3` 是定长 `CHAR(10)`，不进入该列表。
   - 各字段实际长度：`col1` 存 `'a'`（1 字节），`col2` 存 `'bb'`（2 字节），`col4` 存 `'ccc'`（3 字节）。
   - 逆序记录后，字节流严格体现为：`03 02 01`。
2. **NULL 值列表（`00`）**：
   - 第一条记录中所有列均有明确赋值，不存在任何 `NULL` 值。
   - 所有 bit 位均为 0，高位补齐一个字节后表现为十六进制 `0x00`。
3. **记录头信息（5 字节）**：
   - 占据接下来的 5 个字节，其中末尾的两个字节 `00 2c` 代表 `next_record`，表示从当前记录分界点向后偏移 44 个字节即到达下一条用户记录。
4. **系统隐藏列**：
   - 因建表未指定主键，紧随其后的是 6 字节的 `DB_ROW_ID`、6 字节的 `DB_TRX_ID` 以及 7 字节的 `DB_ROLL_PTR`。
5. **真实列数据物理存储**：
   - `col1`（`VARCHAR`）：存入 ASCII 码 `0x61`（即字符 `'a'`）。
   - `col2`（`VARCHAR`）：存入 `0x62 0x62`（即字符 `'bb'`），实际占用 2 字节。
   - `col3`（`CHAR(10)`）：定长字段。存入 `'bb'`（`0x62 0x62`）后，剩余未占满的 8 个字符由空格填充。在 `latin1` 字符集中，ASCII 空格的值为 `0x20`。因此底层连续占用整整 10 字节：`62 62 20 20 20 20 20 20 20 20`。
   - `col4`（`VARCHAR`）：存入 `0x63 0x63 0x63`（即字符 `'ccc'`）。

#### 5.3 第三条记录物理字节流解构（含 NULL 值的精妙紧凑设计）

第三条记录插入的数据为 `('d', NULL, NULL, 'fff')`，其在物理二进制流中的表现截然不同：

```text
03 01 06 00 00 18 00 2c [ROW_ID: 6字节] [TRX_ID: 6字节] [ROLL_PTR: 7字节] 64 66 66 66
```

我们重点分析其在存储优化上的两大核心体现：

##### 1. 变长字段长度列表的变化：`03 01`
- `col4` 为 `'fff'`，占用 3 字节，对应 `0x03`；
- `col2` 虽然是 `VARCHAR` 变长字段，但其当前值为 `NULL`，**直接被移出变长字段长度列表**；
- `col1` 为 `'d'`，占用 1 字节，对应 `0x01`；
- 逆序存储后，该区域仅占用 2 字节：`03 01`。

##### 2. NULL 值列表的计算推演：`06`
表 `mytest` 中 4 个列均未显式声明 `NOT NULL`，因此 4 个列全部归入 NULL 值监控范围：
- 按照字段定义的正序状态检查：
  - `col1` = `'d'`（非 NULL，标记为 `0`）
  - `col2` = `NULL`（为 NULL，标记为 `1`）
  - `col3` = `NULL`（为 NULL，标记为 `1`）
  - `col4` = `'fff'`（非 NULL，标记为 `0`）
- 按照规则进行**逆序排列**（高位为后定义的列，低位为先定义的列）：
  - 倒序位排布为：`col4` `col3` `col2` `col1` $\rightarrow$ `0 1 1 0`
- 高位补齐为一个完整的 8 bit 字节：
  - 最终二进制为：`00000110`
  - 转换为十六进制：$0 \times 2^3 + 1 \times 2^2 + 1 \times 2^1 + 0 \times 2^0 = 4 + 2 = 6$，即十六进制的 `0x06`！

##### 3. 真实数据区的极致压缩
观察后续的真实数据区：
- `col1` 写入 `0x64`（字符 `'d'`）；
- `col2` 和 `col3` 均为 `NULL`：**在真实数据区中连 1 个字节的物理空间都没有分配，直接跳过**；
- 紧接着直接写入 `col4` 的数据 `0x66 0x66 0x66`（字符 `'fff'`）。

> **核心结论**：
> 通过直接翻阅 `.ibd` 磁盘底层二进制，我们确凿印证了 Compact 行格式的紧凑逻辑：
> 1. 值为 `NULL` 的列不仅在变长长度列表中不留痕迹，更在真实数据区实现零空间开销；
> 2. 整个表的所有空值状态仅依靠前置的几个 bit 位以极高密度集中管理。这正是 Compact 格式大幅缩减行存储体积、提升 I/O 吞吐能力的核心奥秘。

## 第 6 章：126-行溢出与Dynamic、Compressed、Redundant行格式
> 对应分集：P126 | 原始标题：《126-行溢出与Dynamic、Compressed、Redundant行格式》

在彻底剖析了 Compact 行格式的物理布局之后，我们接下来审视其余三种行格式：Dynamic、Compressed 以及 MySQL 5.0 之前广泛使用的 Redundant。

在 MySQL 5.7 与 MySQL 8.0 中，系统默认的行格式均为 `dynamic`。从整体架构来看，Dynamic 与 Compressed 和 Compact 高度相似，记录的基本额外信息与真实数据排布大同小异。然而，它们之所以独立成为新的行格式规范，核心分歧点在于对**行溢出（Row Overflow）**这一极端物理存储边界的处理策略不同。

要透彻理解现代 InnoDB 为何默认采用 Dynamic 格式，首先必须厘清行溢出的物理成因与底层边界。

---

### 1. 行溢出机制与物理极限推导

#### 1.1 页容量与行尺寸的天然矛盾

InnoDB 存储引擎在磁盘与内存之间交互的最小物理单元是**数据页（Page）**，其默认大小为 **16KB（即 $16 \times 1024 = 16384$ 字节）**。

而在 MySQL 的语法规范中，一个 `VARCHAR(M)` 变长字段理论上所能声明的最大存储容量可以达到 **65535 个字节**。这就产生了一个根本性的物理矛盾：**一个物理数据页满打满算只有 16384 字节，而单行中的单个大字段却能够申请超过 65000 字节的存储空间**。即使一个数据页中不存任何索引目录、页头元数据，也无法塞下这样的一行记录。

当一行记录中的数据量过大，单个数据页无法完整容纳时，InnoDB 就会触发**行溢出机制**，将超出的数据转移至物理页外部进行存储。

#### 1.2 VARCHAR(M) 边界极值演算与建表验证

很多开发者在学习 `VARCHAR` 时，常误以为直接声明 `VARCHAR(65535)` 即可创建成功。但在实际操作中，无论字符集如何配置，该语句均会触发报错。我们通过实战推导其精确边界。

##### 1. 多字节字符集下的字符数换算
在 `CREATE TABLE` 语句中，`VARCHAR(M)` 里的参数 $M$ 代表的是**字符数**而非字节数：

```sql
-- 在默认 utf8mb3（每个字符最多占 3 字节）环境下执行：
CREATE TABLE varchar_size_demo0 (
    c VARCHAR(65535)
);
-- 报错：Column length too big for column 'c' (max = 21845); use BLOB or TEXT instead
```

因为 $21845 \times 3 = 65535$ 字节，所以当字符集为 `utf8mb3` 时，允许声明的最大字符数极限直接被限制在 21845。

##### 2. 单字节字符集（ASCII）下的元数据开销计算
为了消除字符与字节之间的倍率干扰，我们采用单字节的 `ASCII` 或 `latin1` 字符集（此时 1 字符 = 1 字节），再次验证 65535 字节的极限：

```sql
CREATE TABLE varchar_size_demo1 (
    c VARCHAR(65535)
) CHARSET=ascii;
-- 仍然报错：Row size too large. The maximum row size for the used table type, not counting BLOBs, is 65535.
-- This includes storage overhead, check the manual. You have to change some columns to TEXT or BLOBs.
```

错误信息明确指出：65535 是**包含存储开销（Storage Overhead）在内的一整行记录的最大字节上限**。变长字段为了维系物理存储，必须扣除以下两笔额外开销：

1. **变长字段长度列表占位（2 字节）**：
   当变长字段的最大长度超过 255 字节（$2^8 - 1$）时，1 个字节已经无法记录其真实长度，存储引擎必须分配 **2 个字节**来记录该字段的实际字节数。
2. **NULL 值列表占位（1 字节）**：
   若该列允许为 `NULL`，必须至少预留 1 个字节（8 个 bit）的 NULL 值列表来记录该列是否为空。

因此，在字段允许为 `NULL` 的前提下，单个 `VARCHAR` 字段所能分配的最大有效数据长度为：
$$65535 - 2 - 1 = 65532 \text{ 字节}$$

我们用 SQL 验证这一极限边界：

```sql
-- 尝试 65533：失败，报错超出行尺寸上限
CREATE TABLE varchar_size_demo2 (
    c VARCHAR(65533)
) CHARSET=ascii;

-- 设为 65532：成功创建！
CREATE TABLE varchar_size_demo3 (
    c VARCHAR(65532)
) CHARSET=ascii;
```

##### 3. NOT NULL 约束对极限容量的释放
如果在建表时对字段显式追加 `NOT NULL` 约束，由于整张表中已不存在任何允许为 NULL 的列，Compact 及其衍生格式会**直接略去 NULL 值列表的 1 字节开销**。此时最大可用容量即可扩充 1 字节：

$$65535 - 2 = 65533 \text{ 字节}$$

```sql
-- 显式声明 NOT NULL，验证 65533 字节极限：成功创建！
CREATE TABLE varchar_size_demo4 (
    c VARCHAR(65533) NOT NULL
) CHARSET=ascii;

-- 尝试 65534：失败，再次触碰 65535 绝对行上限
CREATE TABLE varchar_size_demo5 (
    c VARCHAR(65534) NOT NULL
) CHARSET=ascii;
```

> **结论**：
> MySQL 单行数据的最大物理长度为 65535 字节。对于单个 `VARCHAR` 字段：
> - 允许为 `NULL` 时，单字节字符集下的最大声明长度为 `65532`；
> - 声明为 `NOT NULL` 时，单字节字符集下的最大声明长度为 `65533`。

### 2. Compact 与 Dynamic/Compressed 行溢出存储对比

当单行字段的物理尺寸达到数万字节，远超单一数据页 16384 字节的承载极限时，不同的行格式采取了截然不同的物理布局方案。

#### 2.1 Compact 行格式的“部分行溢出”机制

在 Compact（以及早期的 Redundant）行格式中，对于产生行溢出的大字段（如长 `VARCHAR`、`TEXT`、`BLOB`）：
1. **本页保留前缀数据**：InnoDB 会在该记录的真实数据区保留该字段的**前 768 个字节**；
2. **溢出页分页存储**：将其余未能容纳的超长数据，分散写入一个或多个专门的**溢出页（Off-page / Overflow Page）**中，溢出页之间通过双向链表相连；
3. **20 字节外部指针**：在原数据页的 768 字节数据之后，追加一段 **20 个字节**的指针信息，详细记录存放剩余数据的溢出页所在表空间 ID（Space ID）、页号（Page Number）以及在溢出页中的有效字节长度。

```text
Compact 行格式行溢出物理分布：

[ 数据页内部真实数据区 ]
+------------------------------------+---------------------------------------+
|  该超长列的前 768 字节数据         |  指向溢出页的 20 字节指针 (Space/Page) |
+------------------------------------+-------------------+-------------------+
                                                         |
                                                         v
                                              [ 溢出页 1 (Overflow Page) ]
                                              +----------------------------+
                                              | 存放该列后续超出部分数据   |
                                              +--------------+-------------+
                                                             | (链表相连)
                                                             v
                                              [ 溢出页 2 (Overflow Page) ]
                                              +----------------------------+
                                              | 存放该列最终剩余数据       |
                                              +----------------------------+
```

> **读图说明**：原数据页必须被动划分出 768 字节的庞大物理空间来存放前缀字符，仅将尾部数据丢入溢出页，20 字节的外部指针负责维系原页面与外部溢出页的物理寻址。

#### 2.2 Dynamic 与 Compressed 的“完全行溢出”机制

MySQL 5.7 与 8.0 默认选用的 Dynamic 行格式，以及经过压缩的 Compressed 行格式，对这一机制进行了关键重构。它们采用了**完全行溢出（Fully Off-page）**模型：
1. **数据页内零前缀**：在原数据页的真实数据区，**完全不存储这 768 个字节的前缀数据**；
2. **纯指针引用**：在原数据页内，仅保留一个 **20 字节**的溢出指针；
3. **全量数据外放**：该超长大字段的所有真实数据，全量转移到外部溢出页中存储。

```text
Dynamic / Compressed 行格式完全行溢出物理分布：

[ 数据页内部真实数据区 ]
+----------------------------------------------------------------------------+
|  指向溢出页的 20 字节指针 (包含表空间 ID、起始溢出页号、实际字节长度)      |
+-------------------------------------+--------------------------------------+
                                      |
                                      v
                           [ 溢出页 1 (Overflow Page) ]
                           +----------------------------+
                           | 存放该字段从头开始的全部数据|
                           +--------------+-------------+
                                          | (链表相连)
                                          v
                           [ 溢出页 2 (Overflow Page) ]
                           +----------------------------+
                           | 存放该字段剩余数据         |
                           +----------------------------+
```

> **读图说明**：原数据页内不再为大字段分配任何前缀存储空间，仅以 20 字节的轻量指针占位，整段超长数据全部由外部连续溢出页承担。

#### 2.3 为什么 Dynamic 机制在性能上更胜一筹？

Compact 在主页保留 768 字节的设计初衷，是为了让包含前缀索引或极短文本的查询不必产生跨页二次 I/O。但在实际生产中，这种设计带来了显著的负面效应：
- 768 字节在 16KB 的数据页中占比过大。如果一行中有两个超长字段，单行记录在页内就要强行吃掉 $768 \times 2 = 1536$ 字节。
- 数据页能容纳的行记录数断崖式下跌，导致 B+ 树的聚簇索引叶子节点急剧膨胀，树的高度被迫增加，进而引发更多次的磁盘随机 I/O 与缓冲池争用。
- Dynamic 彻底摆脱了 768 字节的束缚，仅用 20 字节占位，使得**单个数据页能够容纳更多的行记录，极大提高了 B+ 树的扇出能力（Fan-out）与 Buffer Pool 的缓存命中率**。

#### 2.4 Compressed 行格式的特殊压缩能力

Compressed 格式与 Dynamic 共享完全相同的完全行溢出机制，其独特性在于存储编码层面：
- 页面级 zlib 压缩：在将物理页刷盘存储时，采用 `zlib` 算法对常规数据页与外部溢出页进行整页物理压缩；
- 适用场景：针对存储大量文本（`TEXT`）、二进制流（`BLOB`）且存储成本敏感的归档数据库表，Compressed 能提供极高的数据压缩比。但在高并发高写入场景下，页面解压与压缩会带来不小的 CPU 计算开销。

### 3. Redundant 行格式的物理结构与冗余机理

Redundant 是 MySQL 5.0 之前版本的古老行格式。虽然在现代系统设计中极少主动使用，但了解其物理结构，有助于从架构演进的角度透彻理解 Compact 与 Dynamic 为何如此设计。

#### 3.1 Redundant 与 Compact 结构对照

```text
Compact 行格式结构：
+-------------------------+-------------+----------------+--------------------------+
| 变长字段长度列表 (逆序) | NULL 值列表 | 记录头 (5字节) | 系统隐藏列 + 真实列数据  |
+-------------------------+-------------+----------------+--------------------------+

Redundant 行格式结构：
+-------------------------+----------------+----------------------------------------+
| 字段长度偏移列表 (逆序) | 记录头 (6字节) | 系统隐藏列 + 真实列数据                |
+-------------------------+----------------+----------------------------------------+
```

> **读图说明**：相比 Compact，Redundant 的元数据区发生了三大核心变化：
> 1. 原“变长字段长度列表”变成了“字段长度偏移列表”；
> 2. 原有的“NULL 值列表”彻底消失；
> 3. “记录头信息”从 5 字节扩充到了 6 字节。

#### 3.2 为什么被称为“冗余（Redundant）”？

许多初学者容易产生一种直觉误判：Compact 的元数据有 3 个部分，而 Redundant 只有 2 个部分，少了一项，为什么反而叫“冗余”？

其根本原因在于列表记录的内容范畴不同：

##### 1. 全字段强制记录（丧失“变长”针对性）
Compact 格式只对非空变长字段（如 `VARCHAR`）记录长度，对于定长列（如 `INT`、单字节字符集下的 `CHAR(10)`）直接略过，由元数据字典硬编码推导；
而 Redundant 的“字段长度偏移列表”，**会将记录中所有列（包括系统隐藏列 `DB_ROW_ID`、定长列、变长列、为 NULL 的列）全部无一遗漏地记录一遍**。对于固定占用 6 字节的隐藏列或确定占用 4 字节的 `INT` 列，这种每个数据行重复记录物理尺寸的做法存在严重的元数据冗余。

##### 2. 累积偏移量计算（计算间接复杂）
Compact 格式直接存入各字段占用的真实字节数（例如 `06 04 08`，直观反映各字段占用 6、4、8 字节）。
而 Redundant 存储的是**累积偏移量（Offset）**。
例如某记录中：
- 第 1 个隐藏列占用 6 字节，偏移列表中记录 `0x06`；
- 第 2 个列紧接着占用 6 字节，偏移列表中记录的不是 `0x06`，而是累加后的 `0x0C`（十进制 12）；
- 在反解析第二列时，必须用当前偏移量减去前一个字段的偏移量：$0x0C - 0x06 = 6$ 字节，才能得出该列的物理长度。

##### 3. NULL 值的内嵌标记机制
Redundant 之所以能够省略单独的 NULL 值列表，是因为它把 NULL 标记偷渡进了字段长度偏移列表中。在偏移列表记录的每个 1 字节或 2 字节偏移量中，其最高有效位（第 1 位）被用作 NULL 标志位：若最高位为 1，则表示该列的值为 NULL。这种将元数据杂糅在偏移列表中的设计，进一步增加了行记录反序列化解析的复杂度。

#### 3.3 记录头信息差异

Redundant 的记录头固定占用 **6 个字节（48 bit）**，相较于 Compact 的 5 字节结构，存在以下两点本质差异：
1. **新增管理字段**：
   - `n_fields`：记录该条记录中总共包含多少个列（包括隐藏列）；
   - `1byte_offs_flag`：标记字段长度偏移列表是以 1 字节还是 2 字节为单位进行寻址；
2. **缺失关键属性**：
   - Redundant 记录头中没有 `record_type` 属性，无法像 Compact 那样直接从头信息区分最小/最大记录（Infimum/Supremum）与 B+ 树目录项记录。

### 4. 四种行格式特性综合对比

为了便于在技术选型与底层性能调优中快速决策，我们将 InnoDB 四种行格式的核心机制归纳如下：

| 行格式（Row Format） | 默认版本 | 变长/偏移元数据 | NULL 值管理 | 记录头尺寸 | 行溢出处理策略 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Compact** | MySQL 5.1 / 5.5 / 5.6 | 仅记录变长列实际长度（逆序） | 独立 bit 位列表（逆序，高位补齐） | 5 字节 | 部分溢出：页内保留前 768 字节数据 + 20 字节溢出指针 |
| **Dynamic** | MySQL 5.7 / 8.0（当前默认） | 仅记录变长列实际长度（逆序） | 独立 bit 位列表（逆序，高位补齐） | 5 字节 | 完全溢出：页内仅保留 20 字节溢出指针，数据全外放 |
| **Compressed** | 可选指定 | 仅记录变长列实际长度（逆序） | 独立 bit 位列表（逆序，高位补齐） | 5 字节 | 完全溢出：20 字节指针 + zlib 算法整页与溢出页物理压缩 |
| **Redundant** | MySQL 5.0 之前（遗留兼容） | 全列累积偏移量列表（逆序，含定长） | 无独立列表（嵌入偏移量最高位标记） | 6 字节 | 部分溢出：页内保留前 768 字节数据 + 20 字节溢出指针 |

> **核心结论**：
> 从 Redundant 的全列偏移冗余，到 Compact 的变长提纯与独立 NULL 位图，再到 Dynamic 的完全行溢出轻量化，InnoDB 行格式的演进清晰地展示了数据库底层对“提升单页记录密度、降低 B+ 树高度、削减随机 I/O 开销”这一终极性能目标的持续优化。

## 第 7 章：127-区、段、碎片区与表空间结构
> 对应分集：P127 | 原始标题：《127-区、段、碎片区与表空间结构》

在微观层面剖析完行格式与数据页内部结构后，我们必须把视角向上拉升。在 InnoDB 存储引擎中，数据存储并不是直接由数据页无序堆叠而成的。如果仅仅依赖数据页（Page，16KB）以及由页头指针维系的双向链表，随着数据量的急剧膨胀，底层 I/O 将面临毁灭性的性能灾难。

为了解决大规模物理存储的高效分配与顺序扫描问题，InnoDB 在“页”之上设计了一套严密的高级存储层级架构：**行（Row） $\rightarrow$ 页（Page） $\rightarrow$ 区（Extent） $\rightarrow$ 段（Segment） $\rightarrow$ 表空间（Tablespace）**。

---

### 1. 物理层设计的核心驱动：为什么需要“区（Extent）”？

我们知道，InnoDB 与磁盘进行 I/O 交互的最小基本单位是页（Page），每一次磁盘读写必定传输整数个连续的页面。但这并不意味着只要以页为单位就能保证高效。

#### 1.1 随机 I/O 与顺序 I/O 的性能鸿沟

假设我们需要执行一个范围查询：`SELECT * FROM t WHERE c1 BETWEEN 5 AND 300;`。这个查询涉及的数据记录由于数据量较多，分散在 3 个不同的数据页中。如果当前内存缓冲池（Buffer Pool）中未缓存这些页面，数据库必须向磁盘发起 I/O 请求。

数据页与数据页之间虽然在逻辑上通过 `File Header` 中的前后指针构成了双向链表，但在物理磁盘的扇区上，这 3 个页面可能分布在相距极远的物理磁道上。

在传统机械硬盘（HDD）甚至现代固态硬盘（SSD）的底层调度中，物理位置分散意味着将产生大量的**随机 I/O（Random I/O）**：
- **随机读取单个页的耗时模型**：
  平均读取一个物理不相邻的数据页大约需要 **10 毫秒（ms）**。解构这 10 毫秒的内部开销：
  - 约 6 毫秒耗费在机械磁头的物理**寻道时间（Seek Time）**与盘片的**半圈旋转延迟（Rotational Latency）**；
  - 约 3 毫秒耗费在操作系统与磁盘控制器的**队列等待时间**；
  - 真正将 16KB 数据页从磁盘传输到数据库缓冲池的传输时间，仅仅占用 **1 毫秒**。
  也就是说，随机 I/O 下 90% 的宝贵时间全被空耗在定位物理扇区的物理机械动作上。

- **顺序读取（Sequential I/O）的极致吞吐**：
  如果这批数据页在物理磁盘扇区上是绝对连续存放的，磁头只需一次寻道即可顺次读取连续数据块，直接消除后续页面的寻道与旋转延迟。
  假设普通磁盘的顺序吞吐能力为 $40\text{ MB/s}$：
  - 1 秒内可顺序读取的 16KB 页面数量为：
    $$\frac{40 \times 1024 \text{ KB}}{16 \text{ KB}} = 2560 \text{ 个页面}$$
  - 读取单个连续页面的平均耗时仅为：
    $$\frac{1000 \text{ ms}}{2560} \approx 0.39 \text{ ms} \approx 0.4 \text{ ms}$$

> **结论**：
> 随机 I/O 读取一个页需 10ms，而顺序 I/O 平均读取一个页仅需 0.4ms，两者的性能差距高达 **25 倍**。因此，底层的核心优化诉求就是：**尽可能让逻辑上相邻的数据页在物理磁盘空间中也是连续存储的**。

#### 1.2 区的物理规范与范围查询优化

为了让页面连续，我们不可能指望磁盘控制器动态为成千上万个离散的数据页随时腾挪出一大片连续地址。折中且高效的工程实践是：**划定一个标准尺寸的物理连续块，一次性分配给表使用**。这个标准块就是**区（Extent）**。

- **区的规格**：在默认 16KB 页面大小下，InnoDB 规定**连续的 64 个物理页组成一个区**。
- **区的大小**：
  $$64 \times 16 \text{ KB} = 1024 \text{ KB} = 1 \text{ MB}$$

当发生范围查找时，由于同一个区内的 64 个页面在物理地址上绝对连续，读取这些页面时存储引擎可以直接使用高性能的顺序 I/O。即使遇到海量数据，InnoDB 也会尽可能按“区”为单位向操作系统申请相邻的连续物理空间，极大降低磁头寻道损耗。

---

### 2. 逻辑层隔离机制：为什么在区之上还要引入“段（Segment）”？

引入“区”确保了页面在物理上的局部连续，但这引发了另一个致命的架构冲突。

#### 2.1 叶子节点与非叶子节点的“混杂灾难”

我们回顾 B+ 树索引的底层构成：
- **叶子节点（Leaf Node）**：真实存放用户业务数据记录的数据页；
- **非叶子节点（Non-leaf Node）**：存放主键/索引键与下级子节点指针的目录项页。

如果仅仅按“区”为单位向 B+ 树分配存储空间，一个区内的 64 个页面就不可避免地会**混杂存放**叶子节点页和目录项页。

```text
混杂存放的区 (未引入段管理)：
+----+----+----+----+----+----+----+----+---------------------+
|目录|数据|数据|目录|数据|目录|数据|数据| ... 共 64 个页面    |
+----+----+----+----+----+----+----+----+---------------------+
  ^    |    |    ^    |    ^    |    |
  +----+----+----+----+----+----+----+-- 扫描时必须频繁跳跃，打断物理连续性
```

当执行范围查询（如遍历叶子节点链表）时，我们只需要连续读取数据页。如果这 64 个页面里夹杂着大量非叶子目录页：
1. 真正的数据页被稀释，单个区能容纳的有效数据行急剧减少；
2. 扫描数据链表时无法一次性按顺序块流式拉取，必须在物理扇区上不断跳过中间的目录页，顺序 I/O 被硬生生打断回退为局部随机 I/O；
3. 本区的数据页过早读完，引擎被迫频繁跨区寻找下一个数据页，彻底丧失了区设计的初衷。

#### 2.2 段的本质与分类

为了让物理扫描保持绝对“纯粹”，InnoDB 引入了逻辑管理单元——**段（Segment）**。

> **定义**：
> 段并不是一个物理上连续的磁盘空间，而是一个**具有特定存储业务属性的“逻辑集合”**。段负责统筹并专有占有一组区，确保不同业务性质的页面绝不混杂在同一个物理区中。

InnoDB 中最核心的段包括：
1. **数据段（Leaf Node Segment，叶子节点段）**：专门管理 B+ 树叶子节点的区集合。当数据页写满需要扩容时，只从数据段专属的区中分配新页；
2. **索引段（Non-leaf Node Segment，非叶子节点段）**：专门管理 B+ 树非叶子节点目录页的区集合；
3. **回滚段（Rollback Segment）**：专门管理事务撤销日志（Undo Log）页面的段结构。

> **生活类比**：
> 我们可以把底层存储做一个生动的现实类比：
> - 每一栋住宅楼好比一个**页（Page）**；
> - 由多栋楼整齐规划在一起的一个封闭小区，好比一个物理上紧密连续的**区（Extent）**；
> - 而像“龙泽苑街道”这样的行政街道，本身不代表具体的建筑砖石，而是一个管理管辖多片小区的**行政逻辑单元**，这就是**段（Segment）**。街道按需对辖区内的小区进行统筹规划与职能分配。

### 3. 碎片区（Fragment Extent）与阶梯式空间分配策略

区的最小分配单位是 1MB。而一个普通的 B+ 树索引为了隔离叶子和非叶子节点，必须同时建立数据段和索引段两个段。如果一个段每次扩容都直接分配一个完整的区（1MB），就会产生严重的“大材小用”问题。

#### 3.1 碎片区的引入由头

如果一张表刚创建，里面只插入了几条或者几十条记录，甚至整张表的数据加起来都塞不满一个 16KB 的页面。若按照整区分配原则：
- 数据段分配 1 个区（1MB，64 页），实际只用 1 个页，闲置 63 个页；
- 索引段分配 1 个区（1MB，64 页），实际只用 1 个根节点页，闲置 63 个页。
建一张空表就要平白吞噬 **2MB** 的物理磁盘空间！如果一个系统有数百张轻量级字典表，这种资源浪费是不可接受的。

为了解决微量数据下的空间闲置问题，InnoDB 提出了**碎片区（Fragment Extent）**机制：
- 碎片区在物理尺寸上依然是一个完整的区（64 个页，1MB）；
- 但碎片区内的页面**不再专属于某一个特定的段**，而是充当公共资源池。段 A 可以从中申请 1 个页面放数据，段 B 也可以从中申请 1 个页面放目录项，实现多个段“拼单”共享存储空间。

> **管理归属判断**：
> 碎片区里的各个页面既然同时服务于不同的段，那么碎片区本身算哪一个段的？
> 答案是：**碎片区不属于任何段，它直接隶属于顶层的“表空间（Tablespace）”统一调度管辖**！

#### 3.2 阶梯式存储分配算法

InnoDB 针对每个段的生命周期，制定了一套动态演进的阶梯式分配策略：

```text
段的空间分配演进流向：

初始插入阶段 (数据量极小):
[ 段 (Segment) ] 
       | (以单个页面为单位索取)
       v
[ 表空间管理的公共碎片区 (Fragment Extent) ] 
       |
       +---> 累计分配页面数 < 32 页 (空间占用 <= 512KB)

规模壮大阶段 (突破 32 页阈值):
[ 段 (Segment) ] 
       | (停止零散拼单，改为申请整区)
       v
[ 独占分配专属区 (Dedicated Extent) ]
       |
       +---> 每次以 1MB (64个连续页) 为单位独占分配
```

1. **零散拼单阶段**：刚向表中插入数据时，段不会申请整区，而是由表空间在碎片区中划拨**单个零散页面（Free Page）**供该段使用。
2. **专属独立阶段**：当一个段在碎片区中累计占用的零散页面达到 **32 个页面（即 512KB）** 时，InnoDB 判定该段的数据已具备规模化特征。此后该段将不再使用碎片区，而是直接向表空间申请**专属区（Dedicated Extent）**，每次独占申请 1 个或多个完整的 1MB 物理连续区。

> **定义修正**：
> 因此在物理本质上，**一个段是由“若干零散的碎片页面”加上“若干专属完整的物理区”共同构建而成的**。

### 4. 区的四种物理状态与表空间组织

在表空间内部，所有的区根据其当前的使用情况与隶属关系，被严格划分为四种状态：

| 区的状态类型 | 状态名称标识 | 归属管理主体 | 物理状态与功能定位 |
| :--- | :--- | :--- | :--- |
| **空闲区** | `FREE` | 表空间直接管理 | 该区内的 64 个页面均处于完全未分配状态 |
| **有空闲页的碎片区** | `FREE_FRAG` | 表空间直接管理 | 碎片区，部分页面已被某些段借用，尚有剩余页面可供分配 |
| **满载的碎片区** | `FULL_FRAG` | 表空间直接管理 | 碎片区，区内的 64 个页面已被各个段瓜分借用完毕，无可用余量 |
| **附属于段的专属区**| `FSEG` | 专属的段直接管理 | 该区的所有 64 个页面全量专属于某一个特定的段（如专属数据段） |

> **军事编制类比**：
> 我们可以用军队体系理解四种区的管理关系：
> - **表空间**好比“集团军”；
> - **段**好比“师”；
> - **区**好比“团”。
> 正常情况下是军管师、师管团（即附属于段的专属区 `FSEG` 隶属于段）。但集团军往往保留有直属特种力量——`FREE`、`FREE_FRAG`、`FULL_FRAG` 这三种状态的碎片区，好比集团军直属的“独立团”，不划归任何单一师级编制，直接由集团军司令部（表空间）统筹调配。

### 5. 表空间（Tablespace）结构与物理文件解构

表空间是 InnoDB 存储引擎逻辑存储体系的最高层容器，所有段、区、页最终都安放在表空间之中。

#### 5.1 独立表空间与空间回收优势

在 MySQL 早期版本（如 5.5 及 5.6 早期小版本），所有表的数据和索引默认混杂在全局共享的**系统表空间（System Tablespace，即 `ibdata1` 文件）**中。

自 MySQL 5.6.6 起，系统变量 `innodb_file_per_table` 默认设为 `ON`，全面推行**独立表空间（File-per-table Tablespace）**，即每一张表对应一个独立的物理磁盘文件——`表名.ibd`。

独立表空间带来了巨大的运维与架构优势：
1. **便捷的数据迁移**：单表数据与索引完全收敛在一个 `.ibd` 文件内，可以通过冷拷贝或传输表空间（Transportable Tablespaces）实现跨实例快速迁移；
2. **高效的空间回收**：在共享表空间中，执行 `DROP TABLE` 删表后，物理文件 `ibdata1` 并不会缩减体积（磁盘空间无法直接还给操作系统）；而在独立表空间下，执行 `DROP TABLE` 会直接在操作系统层面删除对应的 `.ibd` 文件，磁盘空间瞬间物理释放；
3. **低侵入的碎片重组**：对于频繁增删改产生大量页内碎片的业务大表，运维人员可以直接执行：
   ```sql
   ALTER TABLE t ENGINE = InnoDB;
   ```
   该操作会通过重建表（Rebuild Table）生成一个全新的、紧凑的 `.ibd` 文件并原子替换旧文件，快速将碎片空间回退给操作系统，且整个过程对其他业务表毫无干扰。

#### 5.2 初始空表的物理尺寸差异剖析（MySQL 5.7 vs 8.0）

新建一张不包含任何数据的空白表，观察其物理磁盘上的 `.ibd` 文件大小，能清晰反映出不同版本在表空间元数据管理上的演进。

##### 1. MySQL 5.7 环境测试
在 MySQL 5.7 中创建空表 `temp`：

```sql
CREATE TABLE temp (
    id INT,
    name VARCHAR(15)
);
```

在底层数据目录（`/var/lib/mysql/dbtest1/`）查看文件属性，`temp.ibd` 的初始物理大小为 **98304 字节**。
我们进行数学推导：
$$\frac{98304 \text{ 字节}}{1024} = 96 \text{ KB}, \quad \frac{96 \text{ KB}}{16 \text{ KB}} = 6 \text{ 个页面}$$

这 6 个页面就是 InnoDB 独立表空间初始预留的管理页面（包括 FSP_HDR 表空间头部信息页、IBUF_BITMAP 插入缓冲位图页、INODE 节点管理页等）。

##### 2. MySQL 8.0 环境测试
在 MySQL 8.0 中执行完全相同的建表语句，观察 `temp.ibd`，其初始物理大小变为了 **114688 字节**。
再次演算页面数量：
$$\frac{114688 \text{ 字节}}{1024} = 112 \text{ KB}, \quad \frac{112 \text{ KB}}{16 \text{ KB}} = 7 \text{ 个页面}$$

> **深度提示（为什么 8.0 默认多出 1 个页面）**：
> 在 MySQL 5.7 及更早版本中，表的结构元数据是单独保存在磁盘上的 `.frm` 文件中的（`temp.frm`）；
> 而在 MySQL 8.0 中，官方彻底废弃了 `.frm` 机制，引入了统一的**数据字典（Data Dictionary）**，将序列化的表结构字典信息（SDI，Serialized Dictionary Information）直接内嵌到了表本身的 `.ibd` 内部。多出的这 1 个页面（16KB），正是用于存储该表自身的字典元数据定义。

### 6. 系统表空间与内部核心数据字典

虽然独立表空间承载了具体表的用户数据，但整个 MySQL 实例仍然必须维系一个全局唯一的**系统表空间（System Tablespace）**。

#### 6.1 数据插入背后的元数据校验链路

当我们执行一条看似极为简单的 `INSERT INTO t VALUES (1, 'abc');` 时，数据库底层绝非直接无脑落盘，而是需要驱动系统表空间完成一整套严密的校验闭环：
1. 检查目标表 `t` 是否真实存在于数据字典中；
2. 校验传入的字段值（列数、类型、长度、非空约束）是否与元数据定义严格吻合；
3. **定位目标根页面**：查询目标表的聚簇索引以及所有二级索引的根节点页面位于哪个表空间（Space ID）的哪一个物理页（Page Number）；
4. 将记录插入聚簇索引的 B+ 树对应页面，并同步维护各个二级索引的树状结构。

上述流程中所依赖的“表空间编号、列定义、索引根页面”等支撑数据库正常运转的核心基础数据，统称为**元数据（Metadata）**。

#### 6.2 四大核心系统内部表

元数据在系统表空间内部，由四张最核心的系统内部表进行持久化维护：

| 系统内部表名 | 存储的核心元数据信息 |
| :--- | :--- |
| `SYS_TABLES` | 记录实例中所有表的元数据：表 ID、表名、所属表空间的 Space ID、列数量等 |
| `SYS_COLUMNS`| 记录每个表中每一列的元数据：列所属表 ID、列物理排布序号、列名、数据类型等 |
| `SYS_INDEXES`| 记录每个索引的元数据：索引 ID、所属表 ID、索引名称、索引类型、**B+ 树根节点页号** |
| `SYS_FIELDS` | 记录每个索引所涵盖的字段定义及字段在索引内的前缀长度与排序规则 |

> **提示**：
> 普通数据库用户与开发人员无法直接通过 SQL 语句读写上述四张底层 `SYS_*` 内部表（底层具备极高权限保护且不对外暴露直接访问入口）。
> 为了满足运维排查与性能分析需求，MySQL 在 `information_schema` 库中封装了一批以 `INNODB_SYS_*`（或 8.0 中的系统视图）为前缀的只读视图（如 `INNODB_SYS_TABLES`、`INNODB_SYS_INDEXES`）。这些视图是内部系统表的数据镜像与对外透出接口，供开发者在无害环境下观测表空间的底层运行状态。
