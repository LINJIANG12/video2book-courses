欢迎回到 CS231n 第 11 讲。今天咱们聊聊大规模分布式训练。这话题挺让人兴奋，因为现在训练神经网络基本都靠它。你看初创公司、工业界乃至学术界的大模型，大规模如今基本成了深度学习的新常态。自打咱们开这门课以来，过去十年间这情况变化挺大的。10 年前在单个 GPU 或设备上训练模型其实挺常见的，以前多设备训练很少见。但现在在几十、几百、几千甚至几万台设备上同时训练成了新常态，所以咱们得搞出新算法和新思路。

今天咱们会拿 Llama 3-405B 当例子多聊聊。不是因为它最好或最有趣，而是因为它接近顶尖水平，而且公开了训练细节和架构。过去几年 Google、OpenAI、Anthropic 等公司训练出许多强大模型，但他们基本不再公开任何细节。2023 年 GPT-4 论文里的一句名言让我觉得整个行业发生了根本性转变。发布 GPT-4 时，他们说出于竞争格局和 GPT-4 这类大模型的安全考虑，这份报告不再提供架构方面的细节，包括模型规模、硬件、训练算力、数据集构建、训练方法等等。这基本就是现状，也是此后三年大模型的最高水平。他们什么都不透露，能告诉你的就是 Transformer 就算走运了。Llama 3 挺特别，不是因为它最好，而是因为它是最开源的模型之一。这是 Meta 训练的大语言模型，2024 年 4 月开源发布。跟 OpenAI 不同，这篇论文公开了大量训练细节。数据集讲得不多，但系统基础设施讲得很多，藉此咱们能一窥如今大模型到底是怎么训练的。另外 Meta 上个月（2025 年 4 月）刚出了个新模型 Llama 4。开源界已有烧好的模型，不过 Llama 4 还没论文，希望几个月后论文出来咱们能学到新一代 Llama 的训练经验。所以今天咱们就主要拿 Llama 3-405B 来举例。

今天主要聊两件事：一是 GPU 硬件，二是怎么用多 GPU 训练。我想让大家了解两方面：运行这些模型的硬件，以及大规模训练用的算法。先聊聊 GPU 硬件。GPU 就是图形处理单元，他们本是专为图形设计的协处理器，结果成了非常通用的并行处理器。在这间黄氏礼堂讲课很应景，因为这里就是黄氏礼堂。黄仁勋是英伟达的创始人兼 CEO。这家公司是近 20 年最大的 GPU 厂商，既做游戏，也做机器学习。他们最初主要面向图形，因为做图形需要生成大量像素，你得处理大量基本几何图元才能生成这些像素。所以做图形处理时并行算大量东西是很自然的事。大家很快发现这原本为图形造的硬件其实也能干更通用的并行计算。所以 2000 年代初，研究人员琢磨出怎么把显卡改造通用并行编程工具。到了 2010 年代，英伟达真正抓住了这个方向，专门把它开发、推广做成了通用并行处理器。当时他们可能还不清楚具体用来干什么，但他们大致意识到并行处理会很重要。并在 2010 年代初深度学习兴起时抓住了机遇。英伟达值得称赞的是他们很早就看出这个研究领域的潜力，早在 2010 年代初就投入大量资源，确保自家硬件真正适合深度学习训练。如今十多年过去了，这基本上仍是大家训练大规模深度学习模型的主要方式。情况开始有点变了，不过现在大家主要用的还是他们的芯片。

我特别喜欢研究这些硬件的内部构造。这是 NVIDIA H100，现在深度学习训练的主力就是它。下一代刚出，但还没普及，我还没在上面跑过训练。这是现在的顶尖水平。在这块 H100 GPU 内部，中间是计算核心，周围环绕着 80GB 的高带宽内存（HBM）。你看哪，内存和计算核心是分开的，数据得靠总线在 GPU 内存和核心间来回传，速度大概每秒 3TB，数据量非常大。咱们往 GPU 核心里看，计算部分有个约 50MB 的 L2 缓存，比 80GB HBM 小得多，但离计算单元很近，核心能更快访问它。核心里的关键部件是 132 个流式多处理器（SM）。它们像独立的并行核心，并行能力比典型 CPU 核心强，但时钟频率低。指令分支预测也不如 CPU，两者很难直接比。我通常把 SM 看作大致相当于 CPU 核心。我知道有人回家会去数屏幕上的小方块，你会发现其实有 144 个，为什么说是 132 个？因为 GPU 硬件有个叫分选（binning）的工艺，造的时候不可能所有单元都完美，所以他们在开发产品时通常会提前把这种情况考虑进去。他们说我们要造一块芯片，理论上整芯有 144 个单元，但没一个是完美的。不过我们能挑出不少至少有 132 个单元能用的芯片，所以他们常用分选这套工艺。只要承诺 132 个单元能用，就能卖出更多芯片。

咱们还能再往一个流式多处理器里头钻，看看 GPU 内部到底怎么回事。这是 H100 里 132 个活跃流式多处理器之一，里面有几个点值得看看。首先这里有 256KB 的 L1 缓存和寄存器文件，这延续了 GPU 内存层级的趋势。你以为在学深度学习，其实是在学计算机体系结构。抱歉，这算是个惊喜。事实证明内存层级结构对深度学习和高性能计算都很关键。一般规律是离计算核心越远内存容量越大；离计算核心越近内存越小，但速度快得多。如果你写的是跑在这些硬件上的底层算法，那一定要清楚这个内存层级结构，还要非常用心地在内存层级各阶段之间传递数据。写高性能 GPU 内核时，你会花大量时间优化这一点。这就感受一下，在 H100 里就能看到三层内存结构：它有 256KB 的 L1 缓存、50MB 的 L2 缓存，还有 80GB 的 HBM 内存。以上就是 H100 的三级存储层级。

另外还有 128 个 FP32 核心。这些是小型算术单元，能处理各种浮点运算。具体来说，这 128 个 FP32 核心都能计算 a * x + b，a、x 和 b 都是标量。它一个时钟周期就能算完 a * x + b，算一次乘加。128 个核心让每个 SM 每周期能算 256 次浮点，每个 SM 每时钟周期。红色部分则是真正的魔法所在。除了 FP32 核心，还有 4 个张量核心（Tensor Cores）。这名字有点误导，它们其实是矩阵核心。这些张量核心是专用电路，只干一件事：矩阵乘法。每个小张量核心都能做一次矩阵乘法。比如 H100，出矩阵 A 是 16x4，B 是 4x8，再加个 16x8 的偏置矩阵，也就是算 A * X + B，其中 A、X、B 都是固定大小的小矩阵块。每个核心每周期能算一块。算下来这个大小的 A * X + B 就是 1024 次浮点运算，乘和加各算一次。再乘以 SM 里的 4 个张量核心，可以看到整个 SM 每周期能跑 4096 次浮点运算。得拿它跟 FP32 核心的 256 次比一下。你看，这就是张量核心真正出活的地方，设备的主要吞吐量也来自这里。想最大程度用好 GPU，代码就得充分利用这些张量核心。

张量核心还有个特点：它们实际是用混合精度来算的，不像传统 32 位浮点数。张量核心用混合精度，输入通常是 16 位，它们能用好几种不同的 16 位格式，今天咱们就不细说了。乘法在 16 位低精度下做，加法累加则在 32 位高精度下完成。咱们说说这些张量核心，这看着挺细碎，但你在 PyTorch 代码里把数据类型搞错时，影响就很实在了。

GPU 真的快。过去十来年速度提升之大简直离谱。我刚读博搞深度学习那会儿，大家用的最强 GPU 是 2013 年出的 K40。这设备整机也就 5 TFLOPS 的 FP32 算力。咱们来解读一下这张图：横轴是时间，从 2013 年到现在；纵轴看的是峰值吞吐量，单位是每秒每设备多少 TFLOPS。你看这图长得很猛。有关键点：从 K40 到 P100（2016），2017 年左右发布的 V100 带来了惊人突破。V100 是第一款带张量核心的设备。后来的设备张量核心更多更大，占的芯片面积也更大，这让吞吐量有了巨大的提升。过去 10 到 15 年，这些设备的吞吐量大幅提升，最新的就是刚正式官宣的 B200。现在正慢慢铺开，理论上这块芯片有 5000 FP32 算力约 83.3 TFLOPS，张量核心的混合精度算力理论值达 5000 TFLOPS。退一步看，过去 12 年计算能力实际上增长了 1000 倍，这还是单机层面的数据。这也解释了为什么过去 10 年 AI 进步神速，发生了什么？答案就在这里：我们用上了一种新的算力来源，过去 10 年涨了 1000 倍。任何事物要是翻了 1000 倍，你都得重视，因为这会彻底改变我们的技术能力。我觉得这 1000 倍的提升正是过去 10 年深度学习进步的核心动力。它并没有 5000 个张量核心，那是 5000 万亿次浮点运算的张量核心算力。对，咱们得把张量核心算力和 FP32 核心算力区分开，这是惯例。对吧？这已经够疯狂了，你手里拿个设备算力就翻了 1000 倍。我摸过 K40，可惜没机会上手 B100，他们外形相似，但如今的设备快 12 年前的 1000 倍，太疯狂了。

但我们训练时不只用一块 GPU。2013 年 K40 刚出时单卡训练挺普遍的，现在不只一块，而是成千上万甚至几十万块 GPU 一起训练一个模型，再叠加单设备千倍的吞吐提升。过去 10 年的变化真叫人惊掉下巴。咱们刚才看了 GPU 内部，我想把视角拉远，把 GPU 放到现代集群里看，不只看单设备，而看我们拼起来的整套集群。我们已经看过单块 H100 GPU 了，现在可以把它看作内存层级的又一层。H100 内部有三层内存结构，越靠近计算单元越快，离计算单元越远内存带宽越低，数据传输速度越慢。一旦跳出单块设备放到整个数据中心来看，这个趋势依然存在。单块 H100 GPU 的内存带宽约为 3TB/s，也就是 HBM 显存和它的计算单元之间每秒传输 3TB 数据。这些设备通常装在 GPU 服务器里，几乎所有 GPU 服务器都是一个机箱装八张卡，GPU 之间可以互相通信。

服务器内任意两张卡之间的速率通常约为 900GB/s。你看，这带宽只有设备内部 GPU 通信的 1/3。咱们再看 Llama 3。大厂通常不公开集群细节，但 Llama 3 技术报告给了不少信息。细节可能略有不同，但这些数据来自训练模型用的 Llama 3 集群。拿到一个 GPU 机箱，他们会把两个叠进一个服务器机架里。服务器机架高约 6 英尺，跟人差不多大，方便大家有个直观印象。一个机架里有两台服务器，总共 16 个 GPU。接着把多个机架连成一个 GPU Pod。Llama 3 集群的每个 Pod 由 192 个机架组成，共 3072 个 GPU。这些机架之间用的是高带宽连接器，因此这个 Pod 内任意两块 GPU 之间的通信速率约为每秒 50GB。现在你看，单机服务器通信和整个机柜 GPU 间通信相比，显存流量又降了大约 20 倍。所以 3072 块 GPU 看着算力不少，但远远不够用。我们把这些 GPU Pod 叠在一起，就成了完整的 GPU 集群。这就是 Meta 用来训练 Llama 3 模型的那个集群。这东西把 8 个 GPU Pod 拼在一起，总共 24576 块 GPU。我没找到这些设备间显存流量的确切数字，但肯定不到每秒 50GB。顺便说一句，这远不是全球最大的 GPU 集群，这只是我能快速查到精确数据里最大的。但世界上确实有 5 万、10 万块 GPU 的集群，它们确实存在，大家就在上面训练模型。

这种方式能自然扩展，所以你会把更多 Pod 聚在一起，打出一个更大的集群。或者还有更高层级，比如用超级 Pod 连接其他超级 Pod。再往上一层，用这个 GPU 集群训多久？Llama 3 我一时记不清，但近十年有个经验法则：最长的训练通常是数月量级。我觉得这跟技术关系不大，更多跟人有关。要推进工作、制定计划、安排人手，超长的训练周期很难管理。所以最长的训练、最大最先进的模型通常都以月计。要是最大的那些模型，像 GPT-4.5、GPT-5，现在快奔着一年去了，我也不会意外。不过在这些超大集群上训练各把月是很常见的。

问题是：为什么要加服务器装进机架，而不是集群里总得有地方放他们吧？毕竟有物理限制嘛。服务器机架这种标准单元在数据中心里已经用了几十年了。所以等 GPU 这些新设备出现，服务器的形态就变得不一样了。他们个头大得多，功耗也高得多，但你没法一夜间就把整个数据中心推倒重建。所以服务器机架就成了标准单元，硬件尺寸都是标准的，数据中心通常也围着它来建。一个集群通常占多大地方？这问题问得好。单个机架嘛，你可以想象成大概 6 到 8 英尺高，差不多就这么大。一个机架大概就像这个讲台那么大，高度跟我差不多。一个 Pod 有 192 个机柜，想象 200 个这样的讲台规模多大？再乘 8，但这低估了，因为要排成行让人走动。其间集群还需要更多硬件，不只是计算机柜，除了放 GPU 服务器的计算机柜，还有放网络硬件的机柜。这么多设备间要传输大量数据，有专放网络硬件的机柜，也有专放存储硬件的机柜。训练数据得存起来并传入设备，这些很占地方。

大型集群里小计算单元能保持更高吞吐量吗？没错，这正是设计这类系统的核心秘密与挑战。我们想利用快速通信，但在扩展时也要能优雅地回退到大单元较慢的通信。很热！如果你家电脑有 4090 或 5090 显卡，单张卡玩游戏就能让房间热到想开窗，单张游戏显卡就能让普通房间变热。那在数据中心堆叠数万张卡，冷却需求有多严峻！还有个有趣的事：冷却需求变得很夸张，对吧？游戏台式机通常风冷或水冷，你可以设计不同冷却系统。在硬件上大做文章来优化这一切，我觉得很酷。想象这些 GPU 不是漂浮在云端的神秘生物，而是真实存在的，他们是被人们建造并堆叠在某处的实体。想象他们的样子很有趣。

所以转向大型 GPU 集群时，一个思维转变是：别在盯着单个设备、单个服务器看扁了，我把整个数据中心当成一台巨型计算机。它有 2.4 万个 GPU、1.8PB 的 HBM 显存、4.15 亿个 FP32 核心和 1300 万个 Tensor 核心，算力达到每秒 24 ExaFLOPS，也就是 24 * 10^18 次方。这算力很猛，但 5 年后这数字就不算大了，这才是更疯狂的地方。我们的目标是把这 2.4 万个 GPU 当成一台巨型超级计算机。关键问题是怎么在这台超级计算机上连续训练好几个月，训出一个能吞下海量数据、超级强大的神经网络？这就是我们转向深度学习时的核心问题和范式。谢谢。

顺便说，我老提 GPU 和英伟达，因为他们是当今最主流的训练架构和硬件，但也有其他新花样冒出来。现在英伟达训练硬件最大的对手是 Google。Google 有自己的硬件叫 TPU，性能真的很强，他们已经出了六代，这是 v5p 的数据。现在 Google Cloud 就能租到 TPU，规格跟 H100 差不多。TPU 的设计跟 GPU 不一样，挺有意思，但今天没时间细说。有人问这东西多大？这是实拍图，TPU 和 GPU 一样组成集群，v5p TPU 可以组成集群。这是 v2 TPU 集群的实拍图，只有 256 个芯片，这样你对规模有了概念。你看这里并排放着 4 个机架，这些机架比我略高一点，4 个并排容纳 256 个 TPU 芯片。我估计在更新的 Pod 里会大得多，最多能装进 9000 个芯片。Google 的 Gemini 模型几乎肯定是在 TPU 上训练的。他们当然不会说，但要不是我会非常震惊。TPU 其实非常好，我猜大多数 Google 大规模模型都在上面训练，而且都很有竞争力。这是非常好的训练硬件，和英伟达的区别在于它买不到。想用 TPU 只能去 Google 上班，或者在 Google Cloud 上租。硬件很好，很多人在用，但今天它还是不如 H100，不如 NVIDIA GPU 那么流行。其他公司显然也看中这点，都在努力开发有竞争力的训练硬件。我觉得目前主要是英伟达和 TPU 这两大巨头，他们在易用性、性能和市场份额上都遥遥领先。但很多公司正试图追赶，其中两家值得关注的就是 AMD。几十年来 AMD 一直是主要的 GPU 厂商之一，他们还推出了名为 MI325X 的训练加速器。纸面数据看它跟 H100 差不多，但现在的实际影响力还比不上 H100。AWS 也搞出了自己的训练芯片叫 Trainium，我对这个不太熟，自己没用过，但 Anthropic 训练时确实用了它。我不太清楚他们的训练到底有多少是纯 Trainium，多少是 GPU。未来会有更多，但当下 NVIDIA GPU 还是老大，Google TPU 紧随其后，他们也很强，只是没 NVIDIA GPU 用的那么广。

好，第一部分讲完了。GPU 到底啥样，怎么组集群？咱们先看看这些机器的物理构造。第二点：咱们怎么写算法，才能用好那几万个 GPU 组成的大集群？这需要新算法、新计算思路，还有把神经网络并行拆分的新法则。核心策略就是拆分计算。毕竟这些都是巨型并行设备，他们有大量能独立工作、彼此少交流的 GPU 和 CPU 核心。咱们看计算机高层做的事，主要是计算，也就是处理输入比特；二是通信，把比特从一个内存位置移到另一个位置。咱们得利用集群的多层内存，让通信和计算重叠，并拆分计算。这样训练大模型时，数万 GPU 和百万计算单元都能派上用场，让他们并行干活，互相通信，靠这个大集群完成大模型训练。

我觉得现在训大模型主要用到五种并行方式。这跟 Transformer 有关，毕竟它是大规模训练的主流架构。咱们看 Transformer，它主要由 L 层堆叠，每层处理三维张量。其中一维是 mini-batch 维度，我们有一批序列在 mini-batch 中并行处理；还有序列维度，也就是处理 token 序列或集合；每个 token 本身就是一个向量。所以 Transformer 在这些三维张量上操作，并通过层堆叠来实现。这给了我们四个可并行化的轴：我们可以对层轴并行化，这叫流水线并行；我们可以对 batch 维度并行化，这叫数据并行；我们还可以拆分序列维度。这些名字有点怪，但本质上他们都是在计算内部的四个轴上拆分计算的不同方式。你的 Transformer，接下来我们会逐一详细介绍。因为这些分布式训练机制有很多有趣的细节。

首先是数据并行（DP）。基本思路很简单。记住，训练神经网络时我们总是对一小批样本进行操作，对吧？我们总是取一个批量，并根据训练任务为其中的每个样本计算损失，接着计算梯度。它通常是小批量中各样本损失梯度的平均值。在大多数神经网络架构中，小批量内每个样本的损失和梯度计算是相互独立的。这显然可以并行。思路是：如果单个 GPU 能容纳 N 个样本，而你有 M 个 GPU，就用 M * N 的大批量来训练模型。我们把这个大批量拆分成一个个 N 个样本的小批量，分别放到每个 GPU 上。从数学上看这为什么合理呢？因为梯度具有线性特性。实际上如果你计算一个标量损失 L，它是各样本损失的平均值，这些 x_j 就是整个宏观批量里的所有样本，W 代表整个网络的权重矩阵。前向传播结束时的损失通常是各 mini-batch 元素损失的均值。对网络权重求损失的梯度正是更新权重所计算的量，而这个计算实际上会被拆分，因为梯度是线性的。我们可以自由选择先求和、先求梯度还是先求平均。将梯度整理成这种形式很方便：蓝色高亮的内部项本质上就是对 N 个元素做一次正常的反向传播，这些可以在不同的 GPU 上并行计算；接着是外部求和，我们需要对所操作的 M 个不同设备上的梯度取平均。这就是数学层面的原理。可见这在数学上完全成立，数学上这和在单设备上训练完全一样。我们只是巧用代数技巧调换了求平均和求和的顺序。这并不是近似值，算出来跟单块大 GPU 完全一致。

只放得下这么多，实际规模大得多。每个 GPU 都独立维护一份权重、优化器状态和梯度副本。每个 GPU 并行加载不同的 mini-batch 数据。图中每个 GPU 加载三个元素。关键在于各 GPU 的批次必须不同。我和学生的代码都出过 bug：所有 GPU 误加载了同一批次。这么用别犯这错。关键是不同 GPU 要加载不同的小批量数据。接着每个 GPU 独立处理自己的小批量数据，完成前向传播并计算局部损失。它们能完全独立运行，GPU 之间不需要任何通信，每个网络都会执行。这也能独立进行，因为每个 GPU 都持有模型权重的独立副本。它可以独立执行前向和反向传播。但反向传播结束后情况就复杂了。我们要计算所有参与训练设备的梯度平均值，这时需要通信。我们执行 All-Reduce 操作，每个 GPU 都要把梯度发给其他 GPU。这里其实同时发生着两件事：第一，每个 GPU 向所有 GPU 广播梯度；第二，收集所有参与训练设备的梯度。这就是全规约操作，通常耗时随 GPU 数量呈对数级增长。全规约结束后，每个 GPU 都拿到了所有设备梯度的平均值。通信完成，每个 GPU 现在都拿到了全规约后完全相同的梯度副本。训练迭代开始时我们假设每个 GPU 都有独立的一模型权重副本，此时每个 GPU 都拥有整个宏观批次数据的相同独立梯度副本。现在每个 GPU 都能在本地权重副本上做权重更新。因为起点权重相同，应用的梯度也相同，只要计算确定更新后的权重也相同。

顺便说一句，这很关键：第四步和第五步其实可以并行执行。我们说过这里有两件事可以并行发生：一是反向传播，每个 GPU 各自计算梯度；二是跨 GPU 的梯度通信。实践中这些操作通常同时发生，也就是说每个模型会先对网络最后一层做反向传播，算出本地梯度；接着模型转而计算倒数第二层的反向传播。当计算单元忙于计算倒数第二层的反向传播时，GPU 会同时对最后一层的梯度执行 All-Reduce 操作。这意味着操作会交错进行：第 l+1 层的通信与第 l 层的反向传播并行推进。这样等反向传播结束时，梯度已在所有设备上完成规约，我们就能一次性更新权重无需等待。这很重要，因为正如前面所说，通信相对较慢，窍门就在于设法隐藏通信开销，让它和计算同时进行。

瓶颈是第四步还是第五步？答案是肯定的，这完全取决于设备速度、模型大小、小批量大小以及设备间互联速度。到了这个规模的分布式训练，答案通常取决于你的具体情况，你得针对自身情况做基准测试。比如为何不在各模型上分别取 M 个梯度步长？这主意真不错。以前流行过异步 SGD（Asynchronous SGD），让多个副本独立更新，偶尔取平均。这曾经很流行，Google 在推出 TPU Pods 前就这么干，2010 年代初的网络也这么训。但它更不稳定，且难调试、难复现，效果往往稍差。这看似更可扩展，但若能同步，算法就更好调、更好懂、更好推理。只要能用同步梯度更新，效果通常更好。不过我不意外异步 SGD 未来几年可能复兴，毕竟它对分布式训练更友好。没有任何一台计算机能统筹全局，这些设备都是独立的，没有任何驱动能俯瞰全局并自动执行这些操作，计算必须在某处进行。

好问题：当通信与计算重叠时，你需要写代码还是硬件自动搞定？必须写代码。硬件没那么聪明不懂你的意图，它只认是那些基础的矩阵乘法块，它只懂底层逻辑。至于如何调度通信，都得靠软件来处理。不过好在 PyTorch 已经为许多常见场景内置了支持。比如 PyTorch 有个分布式数据并行类（DistributedDataParallel, DDP），它能帮你搞定在写的常规代码之上透明地实现这一过程。这跟单设备编程很有趣，比如用 NVIDIA 的 CUDA 编程 GPU 时，硬件会自动处理大部分异步传输。不过集群层面通常不这么做，得靠软件。设备级并行硬件自动搞定，集群级得软件协调，这不对称挺有意思。这些系统通常是异构的，各部分用不同语言写。底层设备内核就是 GPU 里实际跑的那些代码，一般用 CUDA 写，这是英伟达给自家 GPU 用的类 C 语言。这些内核会被封装，你就能在 Python 里调用它们。PyTorch 就是这么工作的：一堆 GPU 内核加上封装，他们的 Python 和 C++ 代码让编程更顺手。图中每个 GPU 都在自己算自己的梯度，红色梯度由所有 GPU 并行进行 All-Reduce 操作计算得出。你看底层的反向传播得靠上一层的梯度，关键是每个 GPU 只在自己本地的 mini-batch 上做反向传播。所以现在每层都得考虑两种不同的梯度，比如局部梯度，就是我 mini-batch 损失对权重的梯度；还有全局梯度，就是宏观批次总损失对权重的导数。所以每个 GPU 算反向传播，只要尚有梯度的本地版。但算尚有梯度的全局版，就得靠通信了。这就是数据并行。

不过这里有个问题：虽然它是并行化 GPU 计算的好方法，这是大家最初在神经网络训练中并行化 GPU 计算的方式。但我们很快在模型规模上遇到了瓶颈。大家还记得每个 GPU 都存着模型参数的独立副本。模型越大这问题越明显。比如每个网络权重基本得记四个数：权重本身、它的梯度，还有优化器状态。如果用 Adam，每个参数通常都有 beta 值，也就是 beta1 和 beta2，有时还算模型参数的指数移动平均。所以你通常得盯着四到五个标量针对网络里的每个权重。现在常用 16 位精度训练，虽然有些数精度更高，但以 16 位为底线，每个数占两字节，也就是说每个标量有四个数，每个两字节，共八字节要记录。那十亿参数就要占很大的空间。所以在这种配置下，你能训练的最大模型也就 100 亿参数左右，这还不够大。我们要的是真正的大模型，不该被 GPU 显存大小限制住，所以得想办法解决。

其实这瓶颈简单的，得把模型权重分到不同 GPU。除了分数据，权重也得这么分。这就引出了完全分片数据并行（Fully Sharded Data Parallel, FSDP）。这很简单。简单来说，网络里的每个权重 W_i 都分给一个 GPU 拥有。所以每个权重都归我们训练用的 M 个 GPU 里某一个专属拥有。持有该权重的 GPU 还需要负责管理它的全局梯度和优化器状态。一般是按层来切分，毕竟你不是去管单个标量。这个 W 你可以把它当成整个网络层的权重矩阵。所以右边的图就稍微有点不一样了。这只画了两个 GPU，因为剧透一下待会儿会有大量数据来回传。这里有个四层网络，分在两个 GPU 上。前两层的权重 W1、W2 归 GPU 1 管，算 W3 和 W4 则归 GPU 2 管。所以这意味着，你看，在同一时间里它们也在各自工作。所以这里得加点额外通信。做完全分片数据并行时，前向传播开始前持有第一层权重的 GPU，得把这个权重矩阵广播给其他所有 GPU。你正在训练的 GPU，此时 GPU 1 持有 W1，就把它广播给 GPU 2。这样 GPU 2 也拿到了 W1 的副本。现在所有 GPU 都有 W1 副本了，就能对网络第一层做前向传播，算出第一层的激活值。前向传播跑完后，不持有 W1 的 GPU 会删掉本地的 W1 副本以此节省内存。第一层前向传播结束后，模型权重依然分散在各个 GPU 上。但此时所有 GPU 的显存里也都存好了第一层的激活值。接下来处理第二层，操作完全一样：持有第二层权重的 GPU 会把它广播给所有参与训练的 GPU。现在大家都有了 W2 的本地副本，可以继续往下跑。另外这里我们也能把计算和通信交错起来，在算第一层前向传播时顺便预取下一层的权重。实际上这在 FSDP 的前向传播期间是并行发生的。所以我们在取第三层权重时会并行计算第二层。到了第三层，注意此时第三层归 GPU 1 所有，于是 GPU 1 会把权重广播给所有参与训练的 GPU。这一过程会重复，直到网络末尾。此时每个模型都已完成完整的前向传播，在本地小批量上算出了局部损失，且所有层的激活值已驻留内存随时可进行反向传播。

现在我们需要反向执行同样的操作。所以在最后一层反向传播开始时，持有该层权重的设备会把它广播给所有设备。设备拿到权重后即可执行反向传播。整个反向过程都遵循类似的流程。这里可以对网络最后一层做个优化：不让 GPU 释放最后一层权重，而是保留在内存中。所以实践中通常这么做，对吧？因为此时所有 GPU 都已在前向传播中存有最后一层权重的副本，反正反向传播还要用，干脆先留在内存里。所以最后一层的权重先别删。

反向传播主要得搞定三件事：第一，GPU 算完最后一层后手里有了权重副本，就能算出各自的局部梯度；接着要把这些梯度传回去。之前说过谁拥有权重矩阵，谁就负责管理对应的梯度。所以不像数据并行那样全规约，这次只让拥有权重的单个 GPU 处理。比如 GPU 1 把局部梯度发给 GPU 2，后者就能拿到整个批次的完整梯度。那空挡期怎么办？得并行搞。所以反向传播主要得搞定三件事：反向传播阶段需要交换权重，谁持有某层的权重谁就得负责广播；其次所有 GPU 拿到权重后，都要对该层做一次反向传播计算；第三步每个 GPU 算完反向传播，得把梯度结果发回给持有者；最后权重持有者拿到完整梯度后，只有他能更新这个权重矩阵。其实不用传更新后的权重，因为下一轮前向传播会重新广播。这点跟数据并行 DP 的情况不太一样。这些步骤其实都能并行跑，网络里的每一层都会重复这个过程。对于深层网络，进入稳态后这三件事就会同时发生。

所以算第 l 层反向传播时，咱们得聚合梯度并更新权重。刚才我提过得做三件事：拿权重、跑反向传播、更新权重。在聚合梯度并更新，这些都能并行做。简单来说反向传播时，咱们同时处理三个连续层，并行搞定这三步。对，咱们往回遍历网络时，要是通信和计算重叠得好，等你跑完反向传播，梯度早就传完了，所有 GPU 早就更新完所有权重，咱们准备好了。另外希望数据加载器也到位了，这些操作基本上这就是并行化。咱们得在单卡内和跨卡间处理大量任务，尽量重叠这些步骤，好让 GPU 一直有数据，为了让张量核心满负荷跑。

搞完这批，咱们基本就能跑下一批数据了。这招很管用，这就是完全分片数据并行，能帮你搞定不少事。其实数据并行还有个更高级的变体叫混合分片数据并行，简称 HSDP。这种情况下我们可以从概念上把 GPU 分成一个二维网格。之前的例子里我们假设有 N 个 GPU 并行计算的方式也大致相同，在之前的数据并行变体里我们只有一个并行维度。到了混合分片数据并行，我们就同时有了两个独立的并行维度。第一个维度是跑标准的 FSDP，也就是完全分片数据并行。我们把 GPU 分成每 k 个一组，每组都跑刚才说的完全分片数据并行。每组 k 个 GPU 里，模型权重被拆分到这些 GPU 上。前向和反向传播时交错地相互传输权重和梯度。现在我们会有那 k 个组的 M 个副本并行运行。比如这儿两组各四个 GPU，每组里权重都拆分到这四个 GPU 上。不过这整套配置被完整复制了一份，跑在第二组的两个 GPU 上。这么做的话组之间就会做典型的数据并行。组内做前向和反向传播，反向结束时各组算出各自的本地梯度，然后组间对梯度做 All-Reduce，凑齐整个宏观批次的完整梯度。各组拿到这个宏观批次的完整梯度后，就能各自独立地更新梯度了。这叫多维并行。因为我们同时在两个不同维度用两种不同策略来并行计算。这为什么有用？因为这两种并行方式所需的通信量并不一样。咱们想想完全分片并行 FSDP 期间到底要通信哪些数据：前向传播时咱们会复制权重，通信量相当于一个完整的权重副本；反向传播时得重新传权重还要传梯度。用 FSDP 的话，单次前向反向传播要通信三倍的权重。普通数据并行里各组独立存权重，只需 Reduce 梯度，这意味着跨多个数据并行组单次前向反向传播只需传一次权重。这体现了 GPU 集群内部的多层级结构。比如用单机内八张 GPU 通过高速互联组成的服务器，这些可能构成一个 FSDP 组。因为 FSDP 组内需要更多通信，换个维度看你可以有多台服务器，每台都存一份完整的模型权重。记住跨服务器通信比服务器内部通信要慢，咱们第一个例子就是利用已知的设备网络拓扑来设计算法。

一旦搞懂数据并行 FSDP 和 HSDP，这套方法能让你走得很远。比如 1000 亿参数的模型得占 800GB 内存才能存下，要是分到 80 块 GPU 上，每块卡只要 10GB 内存就够了。有了 FSDP，你就能运行相当大的模型。但模型激活值本身会占满显存，以 Llama 3-405B 为例，它是 126 层的 Transformer，维度 16000，序列长 4096。你想想光存隐藏状态就要多少 GPU 显存。前向传播时这量很大，模型和序列一大，GPU 显存就会迅速溢出。这就引出了激活检查点技术（Activation Checkpointing）。咱们不把所有激活值都存内存里，反向传播时咱们再算一遍。理解这招可以把神经网络看成两层，每层做两件事：前向传播算下一层的激活值；反向传播结合上游梯度和激活值算梯度。假设这些常数不变，典型的正反向传播，前向阶段大概要四步。前向传播时你会记住这些激活值，接着是反向传播的四步。在常规的正反向传播中，n 层网络大约占用 O(n) 的计算量和 O(n) 的显存。但正如刚才所说这会导致显存溢出，我们可以选择在反向传播时重新计算激活值。看起来是这样：从激活值开始运行第一层前向传播，随机丢弃这些激活值，如此重复四次。现在网络遍历完毕得到最后一层的激活值，此时可计算最后一层的反向传播。但此时我们遇到了麻烦：没有 a3 的激活值来计算下一次反向传播，我们可以重新计算它们。现在可以执行反向传播了：重新计算、执行反向传播，再重新计算、再执行反向传播。加起来看，n 层网络的单层计算量是 n，内存占用是常数级。因为是从 n 加到 n-1、n-2、n-3 一直这样下去直到 1，这叫二次时间复杂度，咱们可以拆分。O(n^2) 的计算量对深层网络来说太糟糕了，所以咱们别重算所有东西，试着每 c 层存个激活值检查点。这样咱们只在小块网络内部重算。这时候如果你设 c 个检查点，网络跑的时候就会记 c 次激活值。计算量变 O(n*c)，内存 O(n/c)。通常设 c = sqrt(n)，这样计算量 O(n)，内存 O(sqrt(n))。这是平衡算力和内存的常用招，能训练更大的模型。有了这些技术，我们就能高效训练大型模型了。咱们可以开始训练超大模型了。

具体推荐如下：咱们先试试原始数据并行，用到 128 个 GPU 左右，模型参数约 10 亿。这种规模的模型直接用普通数据并行就行，效果通常不错。咱们尽量把每个 GPU 的批次大小调到显存满载，这几乎总是对的。模型变大后会吃掉大量 GPU 显存，这就会带来问题。具体看 GPU 显存多大、互联速度多快，模型超 10 亿参数时就该考虑从数据并行切换到 FSDP 了。这时能扩不少，但激活值会撞上显存瓶颈，这时得开激活检查点。这招虽慢，但能练更大的模型。这能撑到几百张 GPU。看集群结构大概在 256 或 512 张 GPU 时，设备到几百个时 FSDP 太贵，得换 HSDP。这能在千张 GPU 上练几百亿参数的模型。这适合长序列，但要是 GPU 过千，参数超 500 亿，序列超 1 万，就得用更高级的策略，比如上下文并行、流水线并行或张量并行。

接下来有个大问题：感觉参数多的让人头大，该怎么优化？得定全局和局部批次大小、HSDP 和 FSDP 维度，还得算重计算量。我彻底懵了，该咋办？参数太多完全不知道从哪下手。答案是优化一个叫模型 FLOP 利用率（MFU）的关键指标。当你被 GPU 并行搞晕时，模型 FLOP 利用率就是你的指路明灯。跟着它走，它会指导你优化训练栈。不过聊 MFU 前得先说说硬件 FLOP 利用率（HFU）。记得吗？理论上 H100 的张量核心每秒能跑 989.4 万亿次浮点运算，但那是理论值。实际上能有多少？关键在于实践中到底能跑多少。这就是硬件 FLOP 利用率。你在设备上跑计算任务，理论算力上限你实际能跑满多少？这很简单，比如写几行 PyTorch 代码跑个基准测试就行。这是我昨天在 H100 上跑的。简单来说横轴就是循环里做的密集矩阵乘法，接着看看矩阵乘法花了多久。我们算出矩阵乘法的浮点运算量。横轴是矩阵大小，从 512 到 32000；纵轴是硬件浮点运算利用率，即实际跑出的理论峰值占比。用这个简单的 PyTorch 循环，8000x8000 的大矩阵在 H100 上能跑到 80% 利用率，这不错。但问题是硬件浮点运算利用率没算模型需要的其他活。我们可能在做激活值重计算，或者同时还跑着别的模型，比如数据加载、数据增强。GPU 除了干正事还在忙一堆别的活，在原始模型上做前向和后向传播。这时我们就从硬件算力利用率转向了模型算力利用率。

所以模型算力利用率说白了就是 GPU 理论峰值算力里有多少真正用在了模型的前向后向传播上。具体来说，你根据模型架构、层数和每层大小，算出在一个 mini-batch 上跑完一次完整前向后向传播要多少 FLOPs；然后查到设备的理论峰值吞吐量，两者一除就得出若达到理论最大吞吐量，一次完整前向后向传播该花多久。这就是模型前向后向传播能达到的理论最快基线。然后你实际测一次模型前向后向传播的时间。而训练循环里还在跑所有这些别的操作：它在做数据加载、做数据增强、做通信，可能还有激活检查点，反向传播时还要重算。训练循环里做了很多事，测一下实际耗时。把这两个数相除得到一个 0 到 1 的数值，也就是训练循环实际达到理论峰值的比例。这就是模型算力利用率 MFU。同样我们可以用一段简单的 PyTorch 代码来测一下。这个例子是在一个带 ReLU 激活函数的多层感知机上做前向和反向传播。在单张 H100 上用极宽的 MLP 层和超大批量，MFU 大约能到 50%。一般来，说调分布式训练的各种参数时，要尽量调高 MFU，因为这是优化训练，吞吐量是我们最看重的指标。如今 MFU 一般超过 30% 就算不错了。要是远低于 30%，多半是哪里有大瓶颈出问题了。超过 40% 就非常棒了，基本上是顶尖水平。我们看几个数据：

主要来自前面提到的 Llama 3-405B 论文。最后的训练阶段他们分几种方案，同时在 8000 到 16000 张 GPU 上训练，他们的 MFU 大概在 30% 多到 40% 出头，这挺不错的。在 H100 上基本很难再高了。矛盾的是较新的设备 MFU 有时反而更低。上一代的 A100 MFU 有时能超过 50%，这是因为 GPU 算力的增速超过了通信带宽的增速。从 A100 升级到 H100，理论算力提升约 3 倍，但显存带宽仅提升 2 倍。GPU 算力飙升，但 GPU 间通信的扩展更难导致差距越来越大。所以新款设备上的 MFU 有时反而会更低。

我特意重点讲这些，因为这是你们在实践中最可能用到的。我觉得在座各位应该都没机会用上万张 GPU 的集群，真有的话课后找我聊聊。实践中大家遇到的通常是几百张 GPU。还有几页幻灯片做得挺好，但咱们不用细抠所有细节，可以离线验证。前面说过上下文并行主要是沿着序列维度切分。我们说过 Transformer 处理的是序列，思路很简单，就是面对一个长序列，让不同 GPU 处理序列的不同片段。回想一下 Transformer 模块，这对大部分组件很容易，因为层归一化、前馈网络 MLP 和残差连接都是独立运行的，反正这些操作在序列维度上是独立的。所以把计算切分到序列维度上很直接，不过会复杂一些。MLP 内部确实有点棘手，因为里面有权重，所以你得像数据并行那样做一下梯度的 All-Reduce。序列并行的难点在于注意力机制，因为注意力要算序列里每对元素之间的交互。Q K V 投影很简单，因为他沿序列天然就能并行。核心的注意力矩阵其实很难并行。最早的方案叫环形注意力（Ring Attention），就是把矩阵分块，让 GPU 并行处理这些块，按顺序并行处理这些块确保结果正确。细节很多，建议看论文。第二种叫 Ulysses 注意力，概念更简单，是在注意力头上做并行。大家知道 Transformer 常用多头注意力，也就是并行算多个注意力矩阵。Ulysses 注意力把核心注意力算子并行化，分散到各个头上，其余部分也都并行处理。Transformer 其他部分沿序列维度并行。比如序列很长时，上下文并行就很重要了。以 Llama 3 预训练为例，它分两个阶段训练：第一阶段序列长 8000，不用上下文并行；第二阶段升到 13 万，用 16 路上下文并行。也就是说每个 13.1 万长度的序列都有 16 块 GPU 在并行运算。这就像批次大小是 1/16，因为现在每块 GPU 处理的元素不到一个。好，这就是上下文并行。

接下来讲流水线并行。我们在层维度上进行划分。直观来看你有一个包含许多层的网络，我们只需把层分给不同的 GPU，这确实很直观。但问题在于存在顺序依赖，对吧？因为每块 GPU 都需要前一块 GPU 的激活值，才能继续执行前向传播。而在反向传播时，我需要上有层的梯度才能计算反向传播。所以我们可以画个图：纵轴代表 GPU 1 到 4，横轴代表时间流逝。你看 GPU 1 先开始前向计算，接着把激活值传给 GPU 2，再传给 GPU 3，最后传给 GPU 4。GPU 4 比较幸运，能一口气做完前向和后向传播，再把梯度传回给 GPU 3、2 和 1。你看这显然很糟糕，因为 GPU 大部分时间都在闲着。事实上如果你有 N 个 GPU，他们只有 1/N 的时间在做有用功，也就是说如果是八路流水线并行最大 MFU 就 12%，这太糟糕了。对了，这有个可爱的名字有时叫气泡（bubble），就是 GPU 在那儿干等等着通信完成的那段时间。流水线并行的关键在于缩小气泡，也就是减少气泡。具体做法是同时运行更多微批次（micro-batches）。现在我们不再让单个批次数据串行经过所有 GPU，而是让多个批次数据同时并行地在 GPU 间流转。虽然有很多有趣的模式可以尝试，但这里展示的是一个相对简单的四路流水线并行模式：四个 GPU 并行工作，同时处理四个批次的数据。批次用颜色区分，GPU 1 依次对蓝、黄、绿、红批次进行前向传播。当 GPU 1 处理黄色批次时，蓝色批次的激活值已传给 GPU 2；GPU 2 随即开始对蓝色批次进行前向传播。这些操作可以级联并行，反向传播阶段也遵循相同的模式。数据流经不同 GPU 时，我们可以把这几个微批次交错着处理。比如用四路流水线并行和四个微批次，最大理论 MFU 就等于图中非白色区域的比例，这提升到了 57%，相当不错。所以用流水线并行时，如果微批次足够多，MFU 就会很高，因为能并行做更多事。但微批次越多，内存里要存的激活值也就越多，所以得用激活检查点技术。接着你会想：哎呀这咋整，参数要调吗？并行度要加吗？微批次要少点吗？检查点要更积极吗？还得在上面叠加数据并行吗？我也不知道，目标就是最大化 MFU。你得把那些参数都调好让训练效率最高。

最后是张量并行（Tensor Parallelism），也就是沿着模型维度把数据切分。简单来说我们的模型有很多权重矩阵，这些矩阵都在执行 X * W = Y 的计算。我们在 Transformer 里就这么反复操作的。思路是把每个权重矩阵拆分到不同 GPU 上，差不多吧。这和 FSDP 不一样，我们是把单个权重矩阵跨 GPU 拆开的。这时候不用通信，每个 GPU 做一次块矩阵乘法就行。每个 GPU 现在都在全量输入上计算这个矩阵乘法的一个切片。比如把权重矩阵拆成 W1 到 W4，每个 GPU 算一下矩阵乘法的切片，得出输出的切片。问题是前向传播之后，你得把各 GPU 上的激活值汇总起来，才能做下一次前向传播。有个小窍门：要是这两层是连着的，其实中间不做汇总也能搞定。有两层的话，你可以静下心来一步步推导，把主矩阵切成列块，再处理其他部分。借助分块矩阵乘法的特性，一切都能完美衔接。你会发现最终输出就像 Y 和 U 这些块矩阵乘法形成的内积结构，可以直接算出来。所以两层矩阵乘法可以跨多个 GPU 拆分，每两层只需要通信一次。这招很管用，别忘了 Transformer 的 FFN 里就有两层 MLP。这招很妙，正好用上了 Transformer 一直有的那两层 MLP。大型 Transformer 常在 MLP 里用张量并行，也就是这种双层张量并行技巧。

这基本就是我们跨 GPU 拆分计算的全部办法了。哪个最好？其实答案是全都要。实际中我们会用 ND 并行。前面咱们看了 HSDP 二维并行的例子，实际上现在最前沿的就是四维并行了。拿 Llama 来说，他们最大规模的训练用了 1.6 万块 GPU，采用 8 路张量并行、16 路上 border 并行和 16 路流水线并行。大家要注意：不同的并行机制对通信的要求是不一样的。所以如果你能巧妙安排这些并行维度在集群里的布局，就能利用整个集群里不同的通信速度。以上就是大规模分布式训练的快速概览。今天要记住的核心是：单块 GPU 本质上就是一台通用的并行计算机器；GPU 集群则是由几万甚至几十万块独立 GPU 组成的巨型并行机器。我们要把它当做一个整体来编程，我们还聊了这些。所以下次当你去用数万块 GPU 做训练，记住这点，记得告诉我。好，让我借你的 GPU 用用。
