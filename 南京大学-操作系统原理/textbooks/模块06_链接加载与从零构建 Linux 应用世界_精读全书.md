## 链接和加载：可执行文件是一份描述
> 对应块：BLK21 | 覆盖分集：P11上 | 块标题（分集名）：《链接和加载（上）》

我们前面一直都在讲系统调用这样一个接口，讲怎么在它上面一层一层地构建出各种各样的应用程序：从 libc，到一个正常的程序。最早我们写过一个最小的 `minimal.s`，直接写一段指令序列，通过调用系统调用来访问操作系统；然后讲了 fork、execve、mmap 这些系统调用，你们一边做实验，一边知道怎么用系统调用去实现自己在用户空间想要的功能。

今天要讲的东西有一点点不一样，但它其实还是基于系统调用、也完全可以基于系统调用实现——链接和加载。

### 可执行文件到底是什么

讲链接和加载，第一个要正面对讲的对象就是可执行文件。

`file /bin/ls`，或者你们自己编译出来的 `a.out`，它会告诉你这是一个 ELF 64-bit 的 executable，一个可执行文件；当然你们多半是 x86，我这里是一台 ARM 的机器。

在学操作系统之前，你们对"可执行文件"的理解是什么？就是那个双击能弹出窗口的东西——双击 Steam，或者"原神启动"的那一下双击。学完操作系统之后，对这个概念应该有一点变化，或者说有了更深的理解。

首先，可执行文件就是操作系统里的一个对象，它就是一个普通的文件。

既然可以用 `file` 去查看 `/bin/ls`，当然也可以 `cat /bin/ls`，把它的内容直接打印到终端上。如果觉得读起来比较困难，还可以把它管道给 hexdump 这样的程序，它会把整个二进制序列打印出来。你会在头部看到 `7f 45 4c 46`，也就是 0x7f，后面跟着 `E`、`L`、`F` 三个字符的 ASCII 编码。它就是一个普通文件，所以你甚至可以用任何一个文本编辑器去编辑它——确实能看到那三个字母，只不过编辑起来比较困难。对大语言模型来说，这件事好像也是可以办到的。

但当你说到"可执行文件"的时候，更多应该想到的是：它其实是描述进程初始内存布局的一个数据结构。这才是更精确的定义。

为什么可执行文件可执行？什么东西是可以执行的？是程序，是进程。第一个进程是 init，它可以通过 fork 创建子进程，通过 execve 执行另外一个程序。那什么叫执行？谈执行，谈的就是 execve 这个系统调用，execute。execve 的手册名字就叫 execute program。它的第一个参数是一个 `const char *` 的 pathname，指向一个可执行文件，而这个文件描述了一个进程的初始状态。

进程的初始状态里，有一部分是操作系统给的：System V ABI 里的 initial process stack，sp 指向某个位置，那上面有参数的数量、参数的向量等等一整个数据结构。剩下的部分就在可执行文件里——它描述了进程的初始内存布局，比如哪里是代码，哪里是数据。

```text
        高地址
        +-------------------------------------------+
        |  initial process stack（操作系统负责布置）  |
        |    argc / argv[] / envp[] / auxv            |
        |    sp 指向这里                              |
        +-------------------------------------------+
        |  ...                                       |
        |  可执行文件描述的段（可执行文件负责）        |
        |    .text   可读 可执行   代码                |
        |    .data   可读 可写     已初始化的数据       |
        |    .bss    可读 可写     未初始化的数据       |
        +-------------------------------------------+
        低地址
```

进程刚被 execve 创建出来时，地址空间里只有两部分东西：栈顶那一块由内核按 ABI 摆好，其余那些一段一段的代码和数据，全部照着可执行文件里的描述搬进来。

### a.out：简单到连 offset 都没有

真正的可执行文件，比如刚才那个 `/bin/ls`，格式是 ELF。不过你们学计算机系统基础的时候，第一个接触的往往是 Unix 的 a.out：它既可以用来链接，也可以用来执行，有点像 ELF。a.out 这个 a 不是随便取的 abcd 的 a，是 assembler，assembler output。

它的格式定义简单到你可以让 AI 帮你读一遍手册：把网页下载下来，让它做一份 summary，然后跟它对话。比如你可以问：这是一个链接的格式吗？答案应该是支持链接的，因为里面确实有 relocation（重定位）和符号表。有手册在手，大语言模型就不太会出幻觉——手册和代码尤其如此——所以有任何疑问都可以快速得到回答。你甚至可以继续追问链接是怎么完成的，让它给你写一个 a.out 的链接器和加载器。

所有复杂的东西，比如 ELF，都是从简单演变过来的。`struct exec` 就那么多字段，它甚至连 offset 都没有。

作为描述进程初始状态的数据结构，它本来必须说清楚：我的代码、数据和 bss 要加载到内存的哪个位置。你用 readelf 看 ELF 的时候会看到很多 `PT_LOAD` 的 program header，它们会告诉你那一段要加载到内存的什么位置；而在 a.out 里没有这些信息——加载位置直接由平台和 ABI 相关的常数决定。也就是说，操作系统写好的时候，就已经把"加载到哪一个地址"硬编码在自己的代码里了。所以这个结构才显得非常简单。

代价也很明显：a.out 不支持动态链接，不支持调试信息，不支持内存对齐、thread-local 等等后面还会再讲的东西。有这么多功能要往一个新的格式里加，于是就有了今天的 ELF。

### ELF：为机器效率而设计，所以人读着痛苦

讲到 ELF 就会想起被计算机系统基础课支配的恐惧。System V ABI 手册里有一部分专门规定了进程的初始状态，包括 process initialization 那一节里的初始进程栈；除此之外还有 Object Files 那一节。这份手册非常难读：信息量极大，每一个东西你都看不懂，你很快就会想把它关掉。

而且这门课要考试。我做过一个调研，问过几个同学：期末复习计算机系统基础的时候吐血了吗？同学们都说吐了。他们甚至觉得 CS:APP 连这一章讲得都比较枯燥——细节很多，你必须要非常专注才能理解这些细节。

其实不只你们，上这门课的老师也在吐血。有两位老师反馈：第一位老师说，第一次打开 PPT 的时候真的有点吐血；第二位说得更直接，这根本讲不完，我估计听得懂的人也不多。

我现在不上那门课了，这件事跟我就没有关系了。但你们在吐血的时候，有没有反过来问自己一个问题：为什么会这么难？就没有办法了吗？

先问为什么。因为 ELF 是为了机器的效率设计的。

它是一个数据结构，它要描述进程的初始状态：内存里有很多很多的段，我需要从某一个地址到某一个地址加载到某个位置；它还有权限，什么读、写、执行；再往后还有链接、调试信息、符号表，各种各样的东西。为了效率，它做了这样一些设计：

**字符串和符号是身首异处的。** 当我要引用一个符号，比如说 `_start`，这个字符串并不在引用的地方，它在符号表里。引用它的地方只存一个 offset：这个符号的字符串在文件的第 4587 个字节，也就是文件头加上 4587 个字节，你得通过这个类似指针的东西去索引到这里，才知道它是 `_start`。这对人就非常非常不好读了。你跑一下 `readelf -a`，会看到大量的 offset——如果我说要定位到文件里的某一个地方，全部都是用 offset 在算，人脑是不可能算这些 offset 的。所以讲 ELF 的时候，讲到"这里有一个 program header，它叫 LOAD，它的 offset 是多少多少"的时候，你的注意力就已经开始涣散了。

**权限这类信息是 bit field 编码的。** 我要加载一段代码，这段代码就是可读、可执行、不可写的；我要加载一段数据，那就是可读、可写、不可执行的。这些东西全部以 bit field 的方式编码，你必须经过一层翻译，把它翻译成一个平坦的结构，人类才能够理解。

对机器来说这些都不是问题：加一个 offset，或者干脆想办法把它 patch 成一个指针，它就能读到了。而人不像机器那样适合处理这么复杂的结构。

> **结论**：ELF 不过是一个描述——进程初始状态的描述。它主要说清楚两件事：把什么东西搬到哪，以及哪些地方需要重定位。它包含的信息无非是基本信息（版本、机器结构）、内存布局（哪些部分是什么数据、访问权限是什么），以及重定位、调试信息、符号表。而这些信息，总是可以用另一种等价的描述形式表达出来。

### 我们总可以在等价的描述形式之间转换

"我们总可以在等价的描述形式之间转换"，这是我上这门课的时候一直在用的一个非常基本的原理。最早讲汉诺塔，无论是递归还是非递归，我都可以直接把它画出来——无非是把程序的状态变成另外一种等价的形式。我也一直在做可视化：把程序运行过程中隐藏的东西，用你肉眼容易阅读的方式表达出来。比如前面讲管道的时候，我去读 `/proc` 下某个 pid 的 fd，就知道那个进程打开了哪些文件描述符，然后把这个文本形式转换成一个图形的形式，读起来相对来说就容易多了。

而现在，intelligence is cheap。你只要知道这件事可以做，AI 就可以帮你生成代码去做。我那个汉诺塔的可视化完全就是 AI 帮我 vibe coding 出来的。

所以理论上说，我们完全可以把 ELF 转成一个容易阅读的、人肉眼容易阅读的格式，甚至还可以自己实现一个加载器去实现它。想到这两点，你马上就可以做这件事了。

#### funny little executable：用 JSON 描述一个二进制

我每年的这个时候都会讲一个 funny little executable，这几年也一直在改进它。想法就是刚才说的：我们自己定义一个用来描述二进制文件的数据结构。数据结构用什么表示？用字符串、指针、字段。那我们完全可以把它变成一个 JSON 格式——一个 serialized 的、借用 key-value 的 dictionary 或者数组来表达的东西。

这个二进制文件长这样：文件里直接说"这是一个可执行文件"，你不需要像 ELF 那样在文件头上放一个 `\x7fELF`。然后里面有一些 symbol，比如 `_start` 在第 15 个位置；再往上就是那些指令，头上有一个标志说明"这是指令"。我实现了完整的编译器工具链：有一个 libc，可以把 C 语言编译成我自己定义的这种 fle 格式，然后可以链接，可以加载。有兴趣的同学完全可以在 AI 的指导下读一读这份代码。

它是为 x86 设计的，我现在这台 ARM 机器上跑不起来，但你可以看到，我就是在 JSON 里引入了几个符号——我要导出的符号是什么，我要改写的符号是什么——然后把所有东西写在一块，读起来在视觉上是 OK、很 OK 的。

比较有意思的是：如果我要改一个设计，比如我对 funny little executable 有了一个新的想法，我马上就能把它实现出来，因为我只要把设计说出来，它就可以帮我实现。这意味着什么呢？我这些年所有"聪明"的努力——每年上课我都会想，这个地方同学们理解起来会有困难，所以我应该加一层可视化，或者应该做一件什么样的事情让这件事情变得更简单——后来发现其实都可以归结成一句话：我们总是在等价的描述形式之间转换，接下来设计一个合适的描述形式，剩下的交给 AI 就可以了。

任何一种你觉得合适的描述形式都行：你可能喜欢命令行里面的日志，也可能喜欢那种可视化的、用方框和箭头做出来的 diagram。AI 都可以给你，甚至它可以直接读一个 ELF 文件，帮你画成你想要的框图——你说"你给我生成一个 SVG，帮我把它的内容正确地展示出来"，它就去做了。

#### 用 Markdown（或者 SVG）重写一遍 ELF

准备这一讲 slides 的时候我在想：如果让我再做一次，JSON 其实不算一个很坏的设计，它就像一个小的 DSL 语言，我把 ELF 里面那种 offset 指针的结构全部去掉了，我需要任何信息的时候，可以以浪费空间的方式来换你好理解。那我为什么不用 Markdown 来做一个 ELF 呢？

我昨天就跟 AI 对话了一下，它给了我一个这样的设计：

- 开头就说 ELF，把所有属性用中括号写在后面：64 位的 ELF、小端序、System V 的 ABI、x86-64，等等；
- 一段要加载到内存里面的东西，那它就是一个 `PT_LOAD`，注明它可读、可执行；
- 里面是节，比如 `.text` 节，`.text` 节里面有 `_start` 这个符号，符号里面就是那些代码；
- 里面也可以有重定位。

当你这样写的时候，你马上就知道了：`48 8d 35` 后面要跟一个 4 字节的整数，这个 4 字节整数是小端的，叫 PC-relative 32。你不需要知道它到底是什么意思，你需要知道的是：这里要填一个数字，这个数字是 `message` 减点——`message` 的地址算出来，点（当前位置）的地址算出来，因为它们现在都在同一个二进制文件里，就都有相对于文件头的地址了，所以这个差可以直接算出来。

> **提示**：重定位最朴素的样子就是这样。指令里留出的那个空位，等所有符号都安排到位置上去之后，填进去的是一个"目标地址减参考地址"的差值；名字叫 PC-relative 32，只是说它从当前位置往前算、占 32 位。

你也可以既不喜欢 JSON 也不喜欢 Markdown，就是喜欢图形，那没问题，你就用 SVG 来构建二进制文件。你可以 vibe code 一个程序，把一个 `.o`——一个 ELF 文件——翻译成 SVG 的图形；你甚至可以把 SVG 图形链接起来：把两个画布拼起来，那不就是两个图吗？用 SVG 来实现链接和加载，也是完全可以的，只要你能开脑洞。

代价是，我以前花了很多时间给大家构造的那些 demo，现在可能都不那么必要了。真正要紧的，是把一个知识的网络交到你们手上——比如我一定要告诉你们去读 ELF 的手册，要告诉你们有 `readelf -a` 这个命令。

### 链接就是填一个数

在编译的时候，如果我们在一个 a.c 里写一条 call 指令——x86 里面的 call 有很多种，有很短的跳转，也有更长的跳转——一般来说，如果这个 call 是在你自己的 .c 文件里面，你在编译的时候就可以在外面有一个地方有 foo。这个 foo 有没有，其实你都不知道，但你可以在 main 里面调 foo，你可以声称外面有一个 foo。

那这个时候 foo 到底有没有定义，谁都不知道。如果这个 foo 从头到尾都没有被定义过，链接器就会告诉你：对不起，我找不到这个 symbol，它没有办法链接。

#### 编译器先留出四个字节的零

关键在于，只要它存在，编译的时候就可以编译成二进制的指令序列：它会编译成一条 call 指令，然后留四个字节的 0。这四个 0 就是空出来的一个 32 位整数。

```text
  x86 里一条 call foo 编译出来的样子：
        e8  ?? ?? ?? ??
        ^   ^
        |   +---- 四个字节，留给 foo 的地址差，编译时先填 0
        +-------- 操作码：这是一条 call
```

那四个字节里要填的，其实是一个表达式——在这个例子里是 `message_end` 减点再减 4。就这么简单。

#### 链接时才算得出来的表达式

再比如一条 mov：我需要一个 4 个字节的常数，是那个字符串的长度，写出来就是 `message_end` 减 `message`。等到链接的时候，所有符号都已经安排上位置了，它就可以把这个值算出来，填到这个 32 位的常数里。

| 场合 | 留出的空位 | 链接时要填的表达式 |
| :--- | :--- | :--- |
| 一条 `call foo` | 4 字节 | `message_end - 点 - 4` |
| `48 8d 35`（PC-relative 32） | 4 字节 | `message - 点` |
| mov 里填字符串长度 | 4 字节 | `message_end - message` |

> **结论**：这就是链接。把所有东西都以平坦的方式写到指令序列里面之后，这个问题就彻底解决了。你可以像我那样用 JSON、用一点 emoji，让你的注意力能够回来；你也完全可以用 Markdown 来写，把代码内联在里面。

### 加载就是照着字面把东西搬进内存

所谓加载，就是你看到上面字面意义上是什么，我就应该把什么东西搬到内存里。我要把一个 `PT_LOAD` 的东西以可读、可执行的方式搬到内存里，用一个 mmap 系统调用，这件事就全都解决掉了。

所以链接和加载的基本原理就是这两句话：**链接**，是把空出来的空位填上一个只有等符号都排好位置才算得出来的数；**加载**，是照着描述把该搬的东西搬进内存，附带它该有的权限。

当然这是一个复习，我并不是真的来讲 ELF。你们现在也不需要知道 ELF 里面那么多非常琐碎的细节了——所以我在准备这部分的时候，甚至都不想烧这个 token，因为你们每个人都可以有一个自己的设计。

### 一定要知道的那点事：readelf -a 与 .text 的重定位

你可以 propose 任何你喜欢的形式，但有一张知识网络是我一定要交给你的。

比如我在 a.c 里定义一个 `int foo`，再写上 `extern int x;`，然后在里面写一句 `x = 1;`——这是一段合法的代码。`gcc -c a.c` 能成功编译它。然后你去看 `readelf -a a.o`，这里有很多重要的信息：你可以看到 a.o 里面有一个 `.text` 节的重定位（relocation）信息。

再用 objdump 去看那条指令：取地址的时候，那里是一个 0；在 ARM 的指令里面，那是一个立即数位域，编译器先把它填成 0，这个 0 最后会在链接的时候被重新填进去。

你只要知道这一点，就可以用任何你想要的方式去学它，甚至可以预先准备一些 prompt，只要把这些 token 烧掉，你就可以学会它。

我自己的上学经历——从读本科到读完博士——很大程度上就是在人肉做这件事。但现在 AI 也可以做这件事了。前提是：你能够提出正确的问题，能够把握解决问题的方向，有一个够好的模型，并且你有质疑的能力，有 critical thinking 去质疑并且确认结论。

而在这个领域里，有一件事非常关键：**程序的运行不会骗你**。

当你生成了一段指令序列，你确定这个指令序列是调用系统调用、往终端上打印一个 hello，然后你把它链接、加载、运行起来，真的看到 hello 打印出来了，你就真正确认了这个结论——你的链接器和加载器等等，都正确地生效了。

所以某种程度上，我看到了一个还是有一点可怕的未来。你们可以这样想：拿出一本字典，从长度为 1 的单词开始枚举，1、2、3、4、5……一直枚举到一个上限，比如 20 或者 50，然后把字典里所有能枚举出来的句子都拿去做 research。就像今天我说的，第一个疯狂的句子是"我们总可以在等价的描述形式之间转换"，很小的一句话；下一句话是"我能不能用 SVG 来实现链接和加载""我能不能用 Markdown 来写一个链接和加载的格式""我能不能用一个 emoji-based 的方式来写一个链接和加载的形式"。

剩下的就是普通智能了。有创意的那一句话，AI 可能暂时还想不到；但 do research 这件事情对于 agent 来说是完全 OK 的：它有手有脚，可以自己尝试、自己反思，最后自己写代码验证。那这不就可以产生出人类几乎所有知识了吗？我们还要学什么？这个问题我到现在都还没有想清楚。

### 加载器在内核里长什么样

回到加载。刚才我们说，只要有这个概念就行了：所谓的二进制文件，一个 a.out，它就是进程初始状态的一个描述。你的进程里面需要有内存，需要有一个 initial process stack——这是操作系统帮你做好的；而 a.out 里面则是：你需要把什么代码加载到哪一个位置、什么权限，数据加载到什么位置、什么权限。甚至不止代码和数据，还有 BSS，你自己想要在里面塞上任何东西都可以。

我们也知道，加载是通过 execve 这个系统调用实现的：execve 有一个参数是 pathname，它就会对应到这个 a.out。

那这个加载器到底长什么样？我准备好了 Linux 的源代码——非常大的源码，九万个文件，没有编译。我可以直接问：有一个叫 `binfmt_elf.c` 的文件，里面有加载器的代码。你对这个 codebase 没有任何知识，九万个文件，点开它的下一秒就是劝退。但你只需要一个 prompt。

它开始读代码了：这个文件一共 2185 行，它是 400 行 400 行地读的——很聪明，它在控制大语言模型的能力边界。只要烧掉一些 token，你就可以知道关于这个 ELF 文件里面所有的细节。关键流程是：先检验这个数据结构的合法性，然后加载 program headers，然后映射 load 段，然后创建 ELF tables。里面有一个 `create_elf_tables`，它在栈上布置 argc、argv、envp 和 auxv——这就是我们上课讲过的 initial process stack 的东西。

### 初始进程栈里的 auxv 与 vDSO

顺着这个问题马上就可以接着问下去。你会看到 initial process stack 有一个 sp，上面是 argc、argv[0]、env[0]，还有一个 auxv，也就是 auxiliary vector。auxv 对大家来说一直都很神秘，我上课的时候也就是一带而过。

还记得我调 vDSO 的时候吗？vDSO 是一个不进入内核的系统调用：操作系统内核会映射一段内存在你的地址空间里，然后你可以直接跳过去执行。而 vDSO 的地址就在 auxv 里。

```text
  初始进程栈（内核在 execve 里布置好）
        高地址
        +-----------------------------+
        |  ...                        |
        |  auxiliary vector (auxv)    |  vDSO 入口等架构特定的信息在这里
        |  NULL                       |
        |  envp[] ... NULL            |
        |  argv[] ... NULL            |
        |  argc                       |
        +-----------------------------+  <-- sp 指向这里
        低地址
```

它还会告诉你：在 `arch_dl_info` 这个宏中，架构特定的 auxv 也会被插入，比如 `SYSINFO_EHDR`——这个 SYSINFO_EHDR 就是我们说的 vDSO 的那个入口地址。它甚至可以去其他的地方找：在其他的文件里找 `AT_SYSINFO_EHDR`，会再去读整个 Linux 内核里面的文件，而你只是从九万个文件里问了它一句话。它直接找到了 x86 上这个 `arch_dl_info` 下的宏是怎么定义的——当前进程 mm 的 `context.vdso` 这个代码全都写在这里。它会告诉你 vDSO 是什么，也会告诉你到底是哪一行代码设置的。

这是"一年以前还做不到"的事情。一年以前 coding agent 还各种不听指令的时候，我还得把网页打开，跟大家解释一下这个代码。而我这么多的努力，现在好像全都没有了——在 AI 面前，你只需要能问出这个问题，它就能帮你找到，你不需要对这个 codebase 有任何的熟悉。

我自己上学、像你们这么大的时候，大概是从 Linux 2.6.30 左右开始看 Linux 内核的代码，所以对这些东西还算比较熟悉。但在今天，它知道的比我多，知道的比我好，解释的也比我好，还能给你提供情绪价值。刚才这一段用了 63k 的上下文。如果你有一个 100 万上下文的模型，或者 200 万上下文的模型，它真的非常强：像 Linux 内核这样的项目，因为人类把它管理得很好，它只要能加载相关的代码，直接对着那些代码做 in-context learning，一边看着那个代码，一边根据它自己的感觉就可以做出正确的判断——你让它在 Linux 内核里面下刀动刀子，又快又好。所以这也是一个非常可怕的事情。

### shebang：加载器里的隐藏彩蛋

加载器做的事情就是把那个数据结构搬到内存里，给进程一个初始状态：包括 argc、argv、envp 和辅助向量的整个布局，还有一段一段的映射。而在这个加载器里面，还有一个非常有趣的隐藏特性，叫 shebang——一个 shell 的 bang。

#### 文本文件为什么能执行

你们都用过这个特性。如果你想写一个脚本，第一行写 `#!`，后面可以跟 bash，可以跟 python，反正可以是一个可执行文件，然后你这个脚本就会当做可执行文件来执行。

我这里有一个 `a`，把它改成 `a.sh`，因为用了 `chmod +x`，它就变成可执行的，然后我可以直接执行它，得到 hi。可它不是一个文本文件吗？文本文件为什么可以执行呢？

你们都用过这个特性，但有没有同学想过试着 strace 一下它？它能 strace 吗？如果我有一个 a.txt，里面就是 `echo hello`，我用 `bash a.txt` 是可以打印出 hello 的，后缀名是无所谓的；但是 `./a.txt` 会失败，告诉你 permission denied——我不能是 `./a.txt`，我只能 `bash a.txt`。而我可以 `strace ./a.sh`，然后看到整个 strace 的日志：我是可以用 execve 去执行一个脚本的。

换句话说，你直接写一个 C 程序，让它 execve 一个 a.sh，或者 execve 一个 a.py，都是完全可行的。

这个行为 100% 也在 Linux 内核的加载器里。所以同样的，你也可以去 Linux 内核里面，像我刚才那样直接问：`fs` 下的 `binfmt_script.c`，这也是加载器的一部分。刚才那个文件叫 `binfmt_elf`，也就是说我们的 Linux 内核支持加载 ELF 格式的二进制文件，加载器在那儿；它也支持 script 格式的二进制文件，在这儿。

里面有一段代码，这是 Linux 世界里面硬编码的：它会先把那个文件的头读出来。这个动作是必须的——你只有把文件头读出来，才知道这是 ELF、是 a.out，还是 `#!`。Linux 现在默认应该已经不支持 a.out 格式了，但比如说 BSD 还可以加载 a.out 的二进制文件。只有读到的 buff[0] 和 buff[1] 等于井号和叹号的时候，它才会继续执行，把它当成一个 script 来加载。

#### 参数是怎么拼起来的，以及 Linux 与 Mac 的分歧

先看一个打印所有参数的 a.c，编译出来是 `a`。

我写 `./a 1 2 3 4 5`，argv[0] 就是命令行里的这个参数，也就是 `./a`；剩下的 1、2、3、4、5 才是我传给它的。它也可以接收 hello world，也可以接收一串数字。如果你用引号把一串东西括起来，它就还是一个参数；如果没有引号，它就会被拆成几个分开的参数——比如 argv[1] 是 hello，argv[2] 是 world，argv[3] 是 `1 2 3 4 5 6`。

然后我写一个脚本 `s`，就是你们熟悉的 `#!/bin/bash` 那种井号叹号的写法，只不过这里 `#!` 后面的二进制文件不是 bash，是 `a`，并且我还给 `a` 带上参数 b 和 c。那如果我执行 `./s` 会发生什么呢？它就会像 `/bin/bash` 一样，去调动我自己的 `a`——任何一个可执行文件都可以。

如果我再给它传参数，比如 `./s 1 2 3`，你会看到 `./s` 最终调用到了 `a`，也就是 a.c 编译出来的那个 a，因为我的 `./s` 里面写的解释器就是 a。它调用 a 的时候，argv[0] 就是 a；它还会把 s 里面写的剩下的东西（b c）当作参数跟上去；并且它还会把这个脚本本身、这个 s 的路径原封不动地写进去；然后才是 `1 2 3`。

```text
  ./s 1 2 3
    |
    |  s 的第一行：#!  解释器 a  参数 b c
    v
  内核 execve 之后实际摆出来的 argv[]：

    argv[0] = "a"        #! 后面的解释器路径
    argv[1] = "b c"      Linux：剩下的整段算作一个参数
    argv[2] = "./s"      脚本本身的路径，原封不动插入
    argv[3] = "1"        调用时给的参数
    argv[4] = "2"
    argv[5] = "3"
```

所以这就等价于 `a b c ./s 1 2 3`，也就是 `bash a.sh 1 2 3` 那种形式。bash 或者 python 才能正确地知道哪一个是脚本文件，然后去执行那个脚本文件。

不过 POSIX 在这里也不干好事：它没有规定第一行里 b 和 c 中间那个空格，应该作为两个分开的参数，还是作为一个单独的参数。在 Linux 里，剩下的东西全部作为一个参数传进去；而我在 Mac 里昨天特意试了一下，同样的代码会把 bc 作为两个分开的参数——在 Mac 里你会看到 argv[0] 是 a，argv[1] 是 b，argv[2] 是 c，然后才是剩下的那些。这是跨系统不一致的地方，是 Unix 给我们留下的一个小彩蛋：一段在 Unix 和 Linux 里面都硬编码的小代码，给了我们一个很有趣的机制，让我们能实现脚本的自由。

如果有一个不合法的文件，但它以 `#!` 开头，它依然会被试图执行。加载器会把它当成一个路径——路径当然是可能不存在、也可能存在，但不是合法的可执行文件。比如我把解释器写成 `.`，执行的时候就会失败，说指定的解释器是一个目录，而目录是不能执行的；我也可以把它改成一个不存在的名字，它就会说这不是一个可执行文件；再比如没有执行的权限，也都会导致错误。

### 静态链接留下的麻烦

到这里，静态链接的部分就讲完了：它就是 execve 的时候对一个数据结构的一次加载。

最早的时候，所有的程序——像 a.out，它不支持动态链接——都是静态链接的。但静态链接的二进制文件有一个问题：所有的库函数在文件里面都会多保存一份。比如 libc，一开始它可能很小，就只有一点点，那每一个二进制文件都链接一份，可能还是 OK 的；但如果 libc 越来越大，比如现在可能有几兆，而你 Unix 世界里面有 1000 个文件——我们来看一下，`/usr/bin` 底下就有 2100 个文件——如果这几千个、几万个可执行文件，每一个文件都带着一份 libc，这份重复就再也不是能忽略不计的了。

```text
  静态链接：每个可执行文件都自带一份库
    a.out #1   [ 自己的代码 | libc 的一份拷贝 ]
    a.out #2   [ 自己的代码 | libc 的一份拷贝 ]
    a.out #3   [ 自己的代码 | libc 的一份拷贝 ]
    ...
    /usr/bin 下 2100 个文件，每个都是一份拷贝
```

## 动态链接与加载：第一条指令在哪里
> 对应块：BLK22 | 覆盖分集：P11下 | 块标题（分集名）：《链接和加载（下）》

上一节我们把静态链接的账算清楚了，但算出来的结果很难看：如果每个程序都把 libc 完整地拷一份到自己身上，系统里就白白浪费了大量存储空间。想让这件事不浪费，唯一的出路是把应用程序掰碎——掰成好多小的部分，需要什么就共享什么。这一讲就从"掰碎"开始，一直走到一个真正的 Linux a.out 在它执行第一条指令时的完整状态。

### 为什么要把应用程序掰碎

把一个大程序拆成若干小块，最典型的例子就是 `libc.so`，再往下还有 `libm.so`，以及你用到的各种各样第三方库——`readline` 之类，能想到的各种东西。我们的系统里就有：去 `/usr/lib` 看，甚至还有 `/lib`，里面躺着大量能叫得上名字的库，`libdbus`、用来做渲染的 `libXrender`、`libmenu`，等等。

这样一来，一个大的应用程序就可以被掰成好几块。其中有一部分是它自己的代码，这部分没办法，必须自己带一份；但共享的库在整个系统里只需要一份拷贝，磁盘上的存储空间就省下来了。

> **结论**：动态链接的第一层收益是磁盘上的共享——同一个库，全系统一份。

省磁盘只是开始。第二个好处更重要：只要接口保持不变，就可以独立升级。你的 libc 是有版本的。假如今天 libc 里出了一个严重的安全漏洞，明天你要发一个安全补丁——请想一想，如果你的系统里有一万个可执行文件全都静态链接了 libc，你今天要发这个补丁，是不是非常难受？

库里面真的会有这种安全问题，而且正因为人人都链接它，它就必须有一套好机制来完成更新。把库从静态链接里隔离出来，本身就是一个极强的动机。所以动态链接显然是需要的。

它还不仅是用来做系统库，还可以实现大型项目的分解，比如你会见到的 `libjvm.so`、`libart.so`。我一直建议把 NEMU 也这么干：可以把 NEMU 编译成一个 `nemu.so`，这个 `nemu.so` 就是你们的 CPU。CPU 往 uncore 上一插，就相当于动态链接库一加载，它们之间通过函数调用去调用你模拟的 CPU 逻辑，就真的像是插进来的——外围的外设等部分由框架代码提供，你把自己的 CPU 插进去，就能跑出你跑的结果；把一份参考的 CPU 插进去，就得到标准的结果，应用程序运行是正常的。更进一步，还可以做 differential testing 这样的机制。

> **提示**：`ld.so` 之所以能承担这么多角色，是因为"共享"这件事在它这里只是一种文件映射关系，跟具体是系统库还是你自己切出来的模块无关。

所以动态链接绝对是一个有用、非常有效的功能。早先我们看进程的地址空间时其实已经见过它的痕迹：比如我现在有一个 fish 作 shell，进程号 17644，`pmap 17644` 一看，里面确实有 `libc.so`。里面可读可执行的那段是什么？是代码。可能还有一些可读可写的，是它的数据，数据相对来说不算多。不仅有 libc，还有 `libm`、`libgcc_s`，还有 `libpcre2`——那是正则表达式匹配的库，还有若干类似的文件。

### 内存里也只有一份：一个 40 兆 nop 的实验

我们的虚拟内存、我们的 `mmap` 机制，还给动态链接带来了一个额外的好处：不仅在磁盘上 `libc.so` 只有一份副本，在内存里，无论你启动多少个进程，那些只读的数据也都只有一份副本。

这个功能就非常有用了。我可以在系统里启动 1000 个进程，每个进程都动态链接一份 libc，这个 libc 有两兆的代码，但这两兆在系统内存里只有一个副本。

这句话听起来太舒服了，但它是真的吗？我在课上提到这一点的时候，就会说：你可以让 AI 帮你写一个程序来验证这是真的。我给大家准备了这样一个程序，它有两个部分，一个叫 bloat，一个叫 sample。

- `bloat` 是一段内联汇编，这段内联汇编会生成 10 兆个 `nop`。所以编译一下——你看，光这个编译本身就花去了比较长的时间，比你们预期的要长一些。
- 在 ARM 上一个 `nop` 是 4 个字节，在 x86 上一个 `nop` 是 `0x90`，只有一个字节。所以同样是 10 兆个 `nop`，在 ARM 上生成出来的 `libbloat.so` 有 40 兆，里面全是 `nop` 指令序列。
- `sample.c` 干的事情是：先用 `dlopen` 加载这个 `libbloat.so`（这段代码是我让 Claude 写的），加载之后调用 `bloat` 这个函数，让它把那 40 兆的 `nop` 执行一遍；执行完再把 `bloat` 的地址用 `%p` 打印出来。

先运行一个 sample，放后台。然后再运行很多次，你会发现它打印出来的地址落在地址空间的不同位置。这是因为地址空间随机化：`mmap` 的时候，如果我不指定一定要映射到某个位置，`mmap` 会根据整个地址空间的布局找一个有随机性的地址——虽然都在 `7fff` 那个范围里，但具体位置是随机的。

那么在整个操作系统里面，`bloat` 是不是只有一份内存副本？

验证的办法很简单：`libbloat.so` 一个是 40 兆，那我就创建 1000 个不就行了。我直接开一个 agent，连脚本都不用让它写，就跟它说 "run 1000 个 sample in background"，它就帮我写了个脚本，在后台启动了 1000 次 sample。

然后看结果：确实有 1000 个 sample，而我的系统没有卡死。`free` 一看，8G 内存现在用了 4.7 个 G——这很正常，我现在有 VS Code、有 Claude Code，还有前台各种东西，其中还有一部分是 buffer/cache。反过来算一笔账：如果有 1000 个进程、每个 40 兆，那就是大约 40G 内存。如果每一个后台运行的 sample 都持有一份独立的拷贝，我的系统早就挂掉了。但系统运行得非常丝滑。

> **结论**：这证明了不仅在存储设备上、磁盘上，在内存里，一个很长的二进制库函数也只有一个副本。动态链接库是真的在进程之间共享的。

还可以继续问下去。你们还记得 `/proc` 下的 pid 目录里有 `fd` 吗？我们在做管道可视化的时候用过好多次了——它能看到一个进程打开的所有文件。在 `mmap` 的情况下也可以看：比如看 20142 这个进程，你能看到它打开的文件描述符，也能看它的 `maps`，确实这个 sample 映射了 `libbloat.so`。

### 数一数谁引用了它：lsof 与 procfs

顺着上面这个发现，你马上就会想：是不是有一个命令行工具，可以查看我刚才那个 `libbloat` 二进制到底被多少人引用了？它在系统里到底被打开了多少次？

你如果问 AI，AI 会告诉你可以用 `lsof`——list open file。它能列出系统上所有打开的文件。用它来看 `libbloat.so`，你会看到所有打开了 `libbloat.so` 的进程都在里面，一共是 1001 个。多出来的那一个应该是 `lsof` 进程自己打开的——我猜测它启动时也会去打开一下 `libbloat.so`。

下一个问题：`lsof` 是怎么找到这个文件的全部引用的？

你只要 `strace` 一下就行了，比如把 `open` 相关的系统调用 grep 出来，就知道它是怎么找到的：它遍历了 `/proc`，就像你们 pstree 实验里遍历 procfs 一样。它把整个 procfs 全扫了一遍，而且不只是 `fd`，还包括 `maps`，然后统计出有多少人引用了 `libbloat.so`。

有意思吧。所以你们看，我们的每一个实验背后都是有精心设计的。你看起来觉得"pstree 很简单啊，不就是去遍历一下 procfs 吗，给 AI 一句话 vibe coding 就完了"。但如果你在 pstree 那个实验上面真的投入了时间，然后上课时再来听我讲这一段，你会发现知识联系起来了。因为我禁止你们直接用 AI vibe code 掉所有东西，所以你会自己写一些代码，会自己到 procfs 里面多花点时间去看。然后每次我讲这部分内容、又说了一个神奇的命令行工具在 procfs 里干了什么事的时候，你的印象就加深一点。慢慢你就能像我一样：我在准备这堂课的时候就会想，`/proc/pid` 下面有 `fd`，那理论上我们应该可以找到系统里有多少个进程引用了 `libbloat.so`——这件事就真的做到了。

把 sample 全部杀掉之后，我们就证实了前面那个结论：动态链接库在进程之间是共享的。这不仅省了磁盘，也省了内存。

### 一个先有鸡还是先有蛋的问题

接下来看一个动态链接的 a.out 到底是怎么加载的。我先用 `musl-gcc` 编译刚才的 a.c，它同样给我编译出了一个动态链接的 ELF 文件，但它的 interpreter 和 `gcc` 得到的不太一样——`gcc` 编译出来的东西和 `musl-gcc` 编译出来的东西不太一样，一会儿我来揭晓这是什么、以及为什么。

在继续调试之前，先想一想静态链接和动态链接的区别，你会发现里面有一个"先有鸡还是先有蛋"的、想不清楚的问题。

我们说过所有的文件都有一个 `_start`。不管是静态链接还是动态链接的二进制文件，它都有 ELF；如果这个 ELF 里面有一个 entry，那这个 entry 会指向一个 `_start` 符号，而这个 `_start` 是在 `crt1.o` 里的。

好，那下一个问题：这个 `crt1.o` 是静态链接的还是动态链接的？

`crt1.o` 里面当然还会调用一个 `__libc_start_main`。那你们觉得这个 `__libc_start_main` 又应该是静态链接还是动态链接的？

如果它是代码——你看，它已经是库函数的代码了，它应该是库函数的一部分。而这个库函数的一部分，是不是应该在整个系统里面只有一份副本，好节省空间？这是对的，所以它是动态链接的。

那么问题就来了：我这个 ELF 文件、一个动态链接的 a.out 被映射到内存以后，它动态链接的那个 libc 里的 `__libc_start_main`，到底是谁加载的？

你仔细想的话，会发现这里面有非常非常多的细节。

### interpreter：动态链接 ELF 的第一条指令

这些细节其实就藏在一个地方。`file` 一下这个 a.out，或者干脆 `readelf -a`，你会看到动态链接的二进制文件里面有一个域叫 **interpreter**，叫解释器。就是这个 interpreter 域，决定了你在加载的时候、初始的时候要干什么。

> **定义**：ELF 的 program header 里有一段 `PT_INTERP`，内容就是形如 `requesting program interpreter: /lib/ld-musl-x86_64.so.1` 的一串字符串。动态链接的二进制文件，它执行的第一条指令不是它自己的 `_start`，而是这个字符串所指定的那个文件的 `_start`。

如果我期末考试考这个题，我觉得至少有一半的同学要做错。

对一个静态链接的 a.out，你用 `starti` 停下来的就是那个程序的 `_start`。但如果是一个动态链接的 a.out，它的第一条指令**不在这儿**，第一条指令在 interpreter 里，在 interpreter 的 `_start` 里。

那这个 interpreter 是什么呢？我现在用 musl 编译的 a.out，它的 interpreter 是一个符号链接 `ld-musl-x86_64.so.1`，直接链接到 musl libc 的 so。但如果我直接用 `gcc` 编译 a.c，编译出来的 interpreter 就是 GNU glibc 里面的 `ld-linux-x86-64.so.2`——这就是所有动态链接程序统一的加载器入口。

回到 musl 那个 a.out，用 `starti` 调试它：你看到这里不是 a.out 的 `_start`，而是一个 `_dl_start`，由 entry 指定的 `_dl_start`。切到汇编看，它前面还有一段很小的汇编跳板代码，然后进到 `dlstart_c`，这时候就能看到它的源码了——这是 musl libc 里面的加载器。

这个时候进程的初始栈还是一样的：`SP` 指向 `argc`、`argv`、`envp` 和辅助向量。只不过现在执行的是动态加载器的代码。加载器会把这些参数都妥善安顿好，然后做动态加载：它负责加载所有需要的动态链接库，不仅是 libc，而是这个程序所需要的所有动态链接库。不过在 musl 里面，它不需要再加载任何额外的库函数——因为 musl 的 `ld.so` 和整个 libc 是链接在一起的，那个符号链接直接指向 libc，所以它没有别的额外库要加载。

只有在所有需要的动态链接库都加载完成以后，加载器才会调用程序的 `_start`。这个 `_start` 就是之前给大家调试过的 `crt1.o` 里面的那一小段代码，它还会再跳到 libc 里的 `__libc_start_main`，然后 `__libc_start_main` 再跳转回 `main`。这部分代码在 libc 里，不在 `crt1.o` 里，而此刻它已经在动态加载的时候被加载进内存了。

稍微有点绕，但把一个真正的 Linux 里的加载过程完整梳理出来就是这个样子：

```text
execve("a.out")
  │
  ├─ 内核读 ELF program header，发现 PT_INTERP
  │      内容是一串字符串：
  │      requesting program interpreter: /lib/ld-musl-x86_64.so.1
  │
  ├─ 把 a.out 需要加载的段映射进地址空间
  ├─ 映射内核自己塞进来的 vvar / vdso
  ├─ 把这个字符串所指的文件（它也是 ELF）映射进来 —— 也就是 ld.so
  └─ 建立初始栈：SP -> argc / argv / envp / auxv
        │
        ▼
   第一条指令：PC 指向 ld.so 的 entry，不是 a.out 的 _start
        │
        ├─ ld.so 解析 auxv，找到 a.out
        ├─ 递归加载 a.out 依赖的所有 .so（libc、libm、……）
        └─ 全部就位后才跳到 a.out 的 _start
              │
              ├─ _start（来自 crt1.o）
              └─ __libc_start_main ──► main
```

读图的方式是自上而下看两次跳转：第一次是内核根据那串字符串去加载解释器，第二次是解释器把所有依赖就位后把控制权交还给程序的 `_start`。

#### 那串字符串是真的可以改

我现在可以强行把它改掉。interpreter 就是一个字符串，我可以把这个 `64` 改成 `65`，完全可以——做一个非法操作。这时候我再执行这个 a.out，它就告诉我失败了，因为它找不到那个 interpreter 了。再 `readelf -a`，它就说需要一个 `/lib` 下的 `ld-musl-aarch65.so.1`。

不要紧，我现在把这个文件创建出来：把 `aarch64.1` 做一个链接指向 `ld-musl-64.1`，于是我就有了一个 `ld-musl-aarch65.so.1`。这个文件存在以后，这个 a.out 就可以执行了。

所以你要注意到，这里的文件完全是 program header 里面的一段字符串。这个字符串上写的是什么，内核里的那个 ELF 加载器就会去把这个文件当成一个 ELF 文件映射、加载到内存里。你回头可以在我和 AI 的帮助下再去读那段内核加载器代码。

> **结论**：所谓"解释器"没有任何神秘的地方，它就是 program header 里的这一串字符串。因此你实际上可以把加载器换成任何一个你自己的加载器——你可以自己实现一个动态加载器，回去 write code 一个，它是真的可以工作的。

#### 用地址空间验证"第一条指令"

现在用 `info proc mappings` 看：musl 的情况下，在我 `starti`、只执行第一条指令的时候，这个 musl 的 libc 已经在我的地址空间里了——我的 `ld.so`，也就是那个文件，已经被映射进了进程地址空间。除此之外其他的库都还没有被映射进来。

glibc 的情况也一样。`starti` 之后看地址空间：a.out 被加载了，这是应该的；`vvar`、`vdso` 也被加载了，这是内核干的；以及 `ld-linux`，也就是那个 interpreter，也被加载了。除此之外，libc 是**不在**的——glibc 的 `libc.so` 不在地址空间里。

然后我在 `_start` 上面打一个断点，`continue`，再查看这时候的地址空间：libc 就被加载进来了。

所以我们可以非常确信地描述进程第一条指令执行时的那一刻状态：

> **结论**：进程第一条指令执行时，它的状态是——由 `SP` 指向的初始栈（`argc`、`argv`、`envp`、`auxv`），a.out 需要加载的部分，以及 program header 里那个 interpreter 所指的二进制文件（它本身也是一个 ELF）。就这些，没有别的了。

到这里，我已经把一个真实的 Linux 里面的全部过程清楚地解释给大家了。之后就是指令开始执行——此刻 PC 实际上是指向 interpreter 的 entry 的，a.out 自己的 `_start` 还没有开始执行。

### ld.so(8)：一座金矿

上课的时候我还想告诉大家：这里有一座金矿，这座金矿就是 `ld.so` 的手册。Dynamic Linker 和 Loader。

我肯定没有办法事无巨细地把这些底层细节全部交代给你们——甚至可以毫不犹豫地说，其实我对这些细节了解得也不是特别清楚，我只是在需要的时候会去查阅这个手册。所以我更重要的任务是告诉你们**存在这样一个手册**：`ld.so(8)`。它记录了动态链接和加载器的行为，尤其是 glibc 里那个加载器的大量有趣行为。

我们可以把手册以文本形式打印出来，然后让大模型给我做一个总结。手册里面有非常非常多的宝藏，你们可能听都没有听说过。

#### LD_LIBRARY_PATH 与 LD_DEBUG

你们在计算机系统基础课里学过 `LD_LIBRARY_PATH` 吧？上课的时候应该让你们自己编译过一个动态链接库。编译出来之后你会发现，默认它是没有办法运行的，没有办法加载；只有把它所在的位置放进 `LD_LIBRARY_PATH` 这个环境变量里，它才能跑起来。

这背后的机制毫无魔法：`ld-linux.so`——就是我们前面说的那个 interpreter——能看到这个环境变量。因为它能看到这个环境变量，所以它就知道去哪里找动态链接库。你把它改了，libc 你就可以加载另外一个。这是一个非常确定的行为。

手册里还有更多的宝藏：`LD_PRELOAD`、`BIND_NOW`（启动时解析所有符号，也就是关闭延迟绑定），还可以输出调试信息。调试信息这个非常有用：

```bash
LD_DEBUG=libs ls
```

我可以看任意一个程序到底加载了哪些二进制文件。结果比你想象的要多一点。比如你试着打开 VS Code，它会加载很多很多库，整个加载的过程都在输出里了。这个真正的程序也可以被它打开。

#### ldd 与 LD_BIND_NOW

手册里还有很多 SEE ALSO，那些都是宝藏，有兴趣的同学可以花点时间去读一读。

它还告诉你有一个命令叫 `ldd`。`ld` 你知道，是链接；`ldd` 是什么？`ldd` 可以查看一个程序要加载哪些文件——它是假装启动一个加载器 `ld.so` 去加载，假装加载之后就知道真实加载时到底会是哪几个文件。它会**递归地解析**依赖的库。

比如 `ldd /bin/ls` 要加载这些东西。`code` 不行——它是一个脚本。那就看 `gcc`：你看 `gcc` 的依赖非常少、非常干净，甚至比 `ls` 还要干净，是一个非常干净的动态链接二进制文件。

`LD_BIND_NOW=1` 也可以用来调试：你可以确保所有的符号都被加载。万一有什么测试时没遇到的情况，用这个可以覆盖你的预期行为，把那些潜伏的分支逼出来。

#### LD_SHOW_AUXV：看一眼辅助向量

还有一个有意思的：`LD_SHOW_AUXV`，打印 auxiliary vector。

刚才我们说进程初始栈上有一个 auxv。一方面，我们在 Linux 内核里那段加载器的代码——我们让 AI 帮我们读了，它能告诉你内核往这个进程里放了什么。另一方面，`LD_SHOW_AUXV=1` 这个环境变量可以让 `ld-linux.so` 帮你把实际的 auxv 打印出来：

```bash
LD_SHOW_AUXV=1 ./a.out
```

你看，每次打印的时候 `AT_SYSINFO_EHDR` 那个 VDSO 映射的位置都变了，每次运行都变；program header 加载的位置也变了；还有 random，那个随机数也变了。

我可以直接让 agent 帮我读一下，解析每一个辅助向量到底意味着什么。它有足够的知识：比如它知道 `AT_SYSINFO_EHDR` 是 VDSO 的地址，用于快速系统调用；还有 `AT_RANDOM` 是栈上的随机数地址，用于 ASLR 和 Canary——Canary 后面我们还会再讲到。

一句话总结就是：内核加载 ELF 程序后，通过栈把这些元数据传递给运行时。glibc 和 `ld.so` 由此知道你的内存布局、CPU 能力、链接器在哪等关键信息。有 AI 的辅助，我觉得学习变得前所未有的容易。

### LD_PRELOAD：先到先得的占坑机制

还有一个彩蛋：`LD_PRELOAD`。

我们知道，动态链接和加载的时候有一个"先到先得"。比如说 `printf`：你的 a.out 里引用了 `printf` 这个符号，你在 a.out 里调用 `printf`，它就会调用到 `printf`。在加载器加载的时候有一个先到先得的机制——谁先定义了这个符号，这个坑就被占了，以后就会调用到它。当然你可以通过传一些参数、跟 AI 对话让它教你怎么改变这个行为，但默认的时候它就是一个先到先得的占坑机制：谁先被加载并首次满足未定义的符号，谁就生效。

所以，如果我们用 `LD_PRELOAD` 预加载一个库，就可以覆盖掉任何我们想要覆盖的符号。

比如 `malloc`：我可以覆盖 `malloc`，把 `malloc` 变成我的 `malloc`；我也可以覆盖 `malloc`，但还是去调用原来的 `malloc`，只是在调用之前和之后都打印一些消息。这就叫一个钩子，hook——我把它钩住了。我可以通过覆盖一个符号保持它原来的行为，`malloc` 还是 `malloc`，但我可以在它前后插入自己的代码。

这样玩的话，花活就多了。

#### 变速齿轮

你马上就会想到，可以用它来改变任何 API 的调用。比如我前面说过：程序对时间的感知是怎么来的？是通过系统调用。如果我要 sleep 1 秒，那就是 sleep 1 秒；如果我调用 `gettimeofday`，我就知道现在是多少。

那么，我可以让 AI 帮我覆盖所有和时间相关的函数，用 `LD_PRELOAD` 的方式帮我实现一个**变速齿轮**。它真的给我实现了。看看它 hook 了哪些代码，它 hook 了不少：`gettimeofday`（时间）、`clock_gettime`、`usleep`、`alarm`（睡眠、设闹钟，这些都是和时间相关的），还有很多像 `select` 这样的。为什么要 hook `select`？因为我要和别的进程——比如窗口管理器——通信的时候会设置一个 timeout，比如希望 30 毫秒以后就 timeout，然后我就活了；如果没有收到任何按键信息我也要更新一下图形界面。所以像 `select`、`poll` 这些也都会被替换成我修改过的时间。

看一下 Makefile 怎么编译的：它有一系列的 CFLAGS，最终把它编译成了一个 `libwheel.so`。这是当前体系结构下的一个动态链接库，一个 shared object——你们在计算机系统基础课上做过这件事。

然后我的系统里有很多和时间相关的程序，比如 `cmatrix`，打印一个黑客帝国片头风格的掉落字幕，看起来还不错；以及一个贪吃蛇游戏 `nsnake`。我觉得这个 nsnake 实在太慢了，确实有点慢，我可以按上下左右来控制它，但就是慢。那我现在就：

```bash
LD_PRELOAD=./libwheel.so nsnake
```

你已经感觉到它变快了，快了很多，它真的变快了。

再对比一下 `cmatrix`：正常速度下是正常的掉落效果。现在看 10 倍快的 cmatrix——它都快把我的 VS Code 弄卡了，其实是 terminal emulator 卡了，它打得太快太多，字符刷得太猛，发生了卡顿。

然后是 `sleep`：

```bash
LD_PRELOAD=./libwheel.so sleep 1
```

正常的 `sleep 1` 就是老老实实睡了一秒钟；但在这里，0.1 秒它就返回了。

所以，只要覆盖和时间相关的系统调用，我就真的实现了改变应用对时间的感知。你现在只需要知道这件事情是可以的。

#### 还能玩出什么花活

甚至你都不需要线索。你可以和 AI 讨论：我想实现一个这样的外挂，有什么样的实现途径？它会告诉你 LD_PRELOAD。因为很多人都用这个机制来改变程序的行为——我可以改变一个库函数的行为，就可以做很多事。

比如我可以监控一个程序的 `malloc`，拿到 malloc 的日志，这样我就知道有没有 use-after-free 这样的错误。

除了变速齿轮，你还可以让 AI 再想各种各样有意思的花活。比如 AI 还知道用 `LD_PRELOAD` 覆盖 `glXSwapBuffers` 可以实现透视外挂。再比如，我可以截持 `random`，实现可控的随机：有个程序随机扔骰子，你们在迎新晚会上看到过那种跳动的程序吧？你会发现那些东西理论上说都是不可信的——即便你看了它的代码，代码是随机的，你也可以用 `LD_PRELOAD` 改变它随机数的返回值、随机种子等等，来实现你控制的随机。以及，我可以用非侵入式的方式来实现 `malloc` 和 `free` 的日志，就像 strace 那样的日志。

> **提示**：`LD_PRELOAD` 威力这么大，是因为符号解析是"先到先得"，而它恰好能让你插到所有依赖之前。

### 动态链接是怎么实现的

还有一点点时间，简单提一下动态链接是怎么实现的。当然这部分大家也不需要知道，也不需要掌握，看一下就好。

我以你们比较熟悉的 x86 指令集来讲。假设在 `main` 里面，你调用一个 `foo`，也调用一个 `printf`。`foo` 可能也在 a.out 里——`main.c` 和 `foo.c` 都在 a.out 这个二进制文件里。但 `printf` 不一样：`printf` 是动态链接的，在链接的时候是不知道它的地址在哪里的。

不管怎么样，编译器对 `foo` 和 `printf` 是一视同仁的。编译器现在要给 `main` 生成代码，它会生成一条 `call` 指令。不管是 x86 的 32 位还是 64 位，`call` 指令有一个立即数，这个立即数有多大？4 个字节、两个字节、一个字节都可以。对 `printf`，编译器会生成一个 `call 00 00 00 00`，然后给你一个 PC relative 32 的 relocation。

大家还记得这个细节吗？不管是 `call foo` 还是 `call printf`，它都会生成这样的指令序列。好，那这就麻烦了。

在链接的时候，这是 `main.o`、`foo.o`，把它们链接成 a.out，我是不是要给这些地址填上数字？链接就必须要给这些 relocation 全部填上正确的数字。这在 `foo` 身上是好办的：`foo` 现在在 a.out 里已经有了，我就可以算出一个合适的数字，使得我的跳转可以跳到 `foo` 这个位置。

但 `printf` 不行。`printf` 在地址空间的任何地方。我们有 64 位的地址空间，现在一般是 48 位有效，而这个地址空间根本就不在我的 4 个字节可以跳转到的位置——我用 4 个字节写一个位移，根本就跳不到 `printf` 那里；更何况现在 `printf` 的地址还不知道。

#### PLT：一次长跳转变成两次短跳转

那动态链接是怎么实现的呢？我们的编译器会在这里生成一小段代码：`printf@plt`。这个大家好像有印象。

这个 `printf@plt` 是放在 a.out 里的，所以我的 `call printf` 不是 `call printf`，而是 `call printf@plt`——**procedure linkage table**，简称 PLT。这时候我就知道，我只要跳过来就行了。而在 `printf@plt` 这一段代码里面，可以找到 `printf` 的实际地址：我们把它叫做 global offset table，`printf` 的表项。然后再 `call` 这个查表得到的 `printf`。

```text
main:
    call printf@plt        ; 位移很短，链接时就能确定
        │
        ▼
a.out 里的 printf@plt:
    jmp *printf@GOT(%rip)  ; 查表：表项里存的是运行时才填好的真实地址
        │
        ▼
libc.so 里的 printf          ; 真正的实现，地址在运行时才知道
```

读图的方式是：`call` 的目标始终是 a.out 内部的 PLT 桩，PLT 桩再通过 GOT 表项做一次间接跳转，跳到运行时才确定的真实函数体。

所以编译器做了一个非常聪明的 trick：不管我是调用同一个链接单元里的 `foo`，还是调用一个动态链接库里的函数，它都会变成一个相对跳转。在 ARM 里面它用那个 26 位的立即数，128 兆的空间；在 x86 里面有 32 位的立即数，可以寻址 2G 的空间。但两者都必须在链接出 a.out 的时候就把地址确定好。所以，如果这个函数是动态链接的、在静态的时候无法确定地址，它就在代码里面再加上 PLT 这一段。

因此你在 a.out 里面是可以看到 PLT 的。而在 PLT 里面会有一个查表的过程——一般来说现在都是直接就加载好了，这个表两条指令就查完，然后一个 `call` 指令跳转过去就可以了。这就是动态链接实现的基本方法。

#### 数据访问的无奈：GOT 与 PIC

但是 PLT 没能解决数据的问题。我们来写一小段代码：

```c
x = 1;
```

这就比较复杂了。这个 `x` 到底是在另一个动态链接库里，还是在当前这个二进制文件里呢？你不知道。

所以你会看到，用不同的编译选项来编译，结果不一样。比如用 `-fno-pic -c a.c`，再加一个 `-O2`——`-fno-pic` 就是不做位置无关代码，意思是我知道它就在这个地方了。这样编译出来，`x = 1` 只有一条 store 指令：先把地址算出来，直接 store 进去。

但如果换成 `-fpic`，也就是要做位置无关代码，它就会做一次间接访问：从 global offset table 这张表里面查一个地址出来，查出来以后再把它写进去，这才完成 `x = 1`。

> **易错点**：`-fpic` 下，所有 `extern` 的外部数据——比如 `extern int x`——不管它是不是在同一个库里面、不管你其实能不能用一个短地址访问到它，编译器都会给你增加一层间接访问。

所以这是现在系统设计的一个非常无奈的地方。这一层间接会带来一定的性能损耗，你也需要一些 hack 去告诉编译器、控制这个行为。这是比较复杂的地方。

### 虚拟化这一路，其实一直在讲 execve

我们花了好几节课讲虚拟化，那就先复习一下，这几节课到底讲了什么。我们从程序和进程开始讲，讲进程的地址空间——里面有一个游戏修改器；然后讲到文件描述符，我们怎么去打开操作系统里面的各种各样的对象。你们做了实验，做了 `pstree`，做了 `s-perf`，然后也知道了 C 的标准库是怎么一层一层实现起来的。

上一次课，我合上了整个 virtualization 部分的最后一片拼图：链接和加载。但仔细想想，这个学期到现在的所有实践，我讲的一直都是系统调用，也就是操作系统给应用程序提供的各种各样的 API。所以上节课我讲的其实是 `execve` 系统调用的行为——你们当时可能没有反应过来，今天这样一讲，再回头想一想我调过的那些东西，感觉就不一样了。

所谓 `execve`：我们说，任何一个程序执行一条指令的时候，它都有一个确定的行为。如果它执行的是一条 `execve`，那它执行的行为就是——把 `execve` 那个 `path` 对应的二进制文件所描述的可执行文件的初始状态，搬到这个进程的内存里。这里面就包含了一个初始的进程栈：不管是 x86、ARM 还是任何一个体系结构，都有一个 stack pointer，它指着的就是初始的栈，栈上面还有 auxiliary vector（辅助向量）。我们甚至看过 Linux 内核里加载器的代码，你们知道这里面每一项都是有代码写进去的，没有任何魔法。

除此之外还有"加载"。静态的加载、静态链接和加载、动态的链接和加载——`execve` 的行为就是把这个 `a.out` 的所有东西搬进来：你用 `readelf` 看到的那些 `PT_LOAD` 的段，代码、数据、未初始化的数据，全都要加载到进程的地址空间里，这就是 `a.out` 内存映像的来源。

然后还有 interpreter。一个动态链接的 `a.out`，你用调试器停在它第一条指令上的时候，进程的地址空间里只有这两部分内容；像 `libc` 这些东西甚至根本不在进程的地址空间里。如果你用 `ldd` 查一下，会发现它可能用到很多动态链接库，但在第一条指令执行的时候它们都不在，而是由加载器再用系统调用、再用 `mmap`，把那些 ELF 的 `.so` 文件里一段一段的内存搬进地址空间。等所有这些东西都准备完毕，还有一个 PC——这条 PC 对应的是 interpreter 里面的第一条指令。这个程序就从这里开始往后执行，被放到 CPU 上往后跑。

整个这个过程，就是你在 `strace` 里能看到的东西：

```text
高地址
  初始的栈                     ← stack pointer 指向这里
  auxiliary vector（auxv）
  interpreter（比如 ld.so）的 .text / .data
                               ← 第一条指令的 PC 指向这里
  a.out 的 PT_LOAD 段
    .text（代码）/ .data（已初始化数据）/ .bss（未初始化数据）
  libc.so 等动态链接库
    第一条指令执行时还不在这里，
    由 interpreter 后面再用 mmap 一段段映射进来
低地址
```

读图时抓住两个关键：第一条指令执行的那一刻，地址空间里只有 interpreter 和 `a.out` 自身；剩下的动态库是"后续动作"，由加载器一条条系统调用搬进来。

所以你看，这么复杂的东西，其实在概念上操作起来没什么困难。你在任何时候想要知道任何程度的细节，就去跟 AI 交互；你建立了正确的概念，就能知道里面每一个字节是怎么来的——你提出那个正确的问题，AI 会帮你找到。

### 从一篇论文讲起：最早的 Unix 连 fork 都没有

这个故事的第一个东西，是一篇论文，叫 *The Evolution of the Unix Time-Sharing System*。我强烈推荐每一个同学都去读一下。

它有点长，我也知道同学们一定不会愿意在课后去读这样的阅读材料——尤其是我如果在一节课上给出十来个链接，每个链接都那么长，你们马上就麻了。不用着急，我们一会儿再回到这篇文档。

它很经典，它传递的 message 是：Unix 是怎么从零开始一点一点实现成现在这个样子的。最早的 Unix 甚至连 `fork` 都没有。它创建进程的方式不是 `fork`、`execve`，也不是我们今天觉得更合理的那个直接 spawn 一个程序的做法。早期 Unix 的 shell，如果你要运行一个外部程序，比如 `ls`——那个时候还没有管道——它会做这么几件事：把所有打开的文件都关闭，把 0、1 这两个文件描述符打开到终端，然后把自己退出，于是这个 shell 就被从内存里面卸载了。

卸载以后它用 `execve`——当然这是我们今天的叫法——他们的 `execve` 用加载器把一份代码加载到内存里，然后执行。程序退出以后，shell 再被重新加载回来。也就是说，在最早的 Unix 上，一台终端里最多最多只有两个程序：一个是 shell，一个是可执行文件，然后来回切换。

```text
一台终端里的早期 Unix
  shell 在内存里
      │ 关掉所有文件、把 0/1 打开到终端、自己退出（从内存卸载）
      ▼
  用 execve 把可执行文件加载进内存并执行
      │ 可执行文件退出
      ▼
  shell 重新被加载回来
  → shell、可执行文件、shell、可执行文件……来回循环
```

这有点像你们大一大二做小练习：想跑一个稍微复杂点的程序，可能还得写汇编。

后面还有很多有意思的故事。比如他们脑洞大开，Ken Thompson 用 27 行汇编实现了一个 `fork`。为什么能这么少？因为在早期那个简单的进程模型底下，所有的内存可能就是几个指针就描述完了——我的代码从哪开始到哪结束、数据从哪开始到哪结束——这就是 `struct proc`，就像我们写的那个小的 CrazyOS 一样。在这样的模型下，实现一个进程的复制就非常非常简单，27 行汇编就够。

这给了我们一个启发：**所有复杂的东西，在刚开始的时候都是很简单的。** 今天大语言模型已经很可怕了，但如果你不停地往前溯源——我们讲到并发的时候专门有一个实验，你们会真的看到一份代码，它就可以推理 GPT-2 的模型。早期的时候它们其实都没有那么复杂。现在为了把这么大的模型高效地 serve 出来，有各种 PD 分离、KV cache 之类的技术，但最早的时候都不是这样的，都是你们能理解的最简单的样子。

### Minix：一台如假包换的 UNIX V7

论文之后，是 Minix。这也牵扯到一个非常有名叫 Andrew S. Tanenbaum 的人，他写了一个操作系统叫 Minix。

Minix 3 是一个非常成熟的操作系统，成熟到什么程度呢？它有一个模仿 Windows XP 的界面，真的能把这个用户界面完整地起起来。而且它一度是世界上最流行的操作系统。为什么呢？因为 Intel 的许可证比较宽容——Minix 3 的许可证很宽容，它就在 Intel 自己的 firmware 里，在那个芯片组上：每一台电脑里面有一个主要的 CPU，CPU reset 以后执行 firmware，而在 CPU 之外，芯片组上还有一颗小 CPU，那颗 CPU 上运行着一个操作系统，运行的就是 Minix 3。没有人知道，后来被人发现了，有个帖子说："哦，我们发现了，原来 Minix 3 才是世界上最流行的操作系统。"因为那个时候 Intel 如日中天，每一台 Intel 芯片组的计算机上，都有一颗 CPU 运行着 Minix 3。所以不管你的主 CPU 上运行的是 Windows 还是 Linux 还是别的系统，它里面都有一个 Minix。

Minix 最早是 1987 年。1987 年的时候它走了一条非常有趣的路线：要走 UNIX 的**完全兼容**。Unix 早期火了以后一直没法广泛流转，因为他们是贝尔实验室的，Dennis Ritchie 和 Ken Thompson 受到"他们要挣钱"这个约束。于是 Andy 做了一件事：写了一本书，叫 Minix Book，书名叫 *Operating Systems: Design and Implementation*。这本书算是我梦开始的地方。

我像你们这么大的时候，就拿一本操作系统教材，书的前一半教你操作系统，后一半是代码。我们那个时候有惊人的注意力，可以一边看书，然后放个书签在前面——你读一下操作系统这个部分是怎么实现的，就翻到后面去找代码，一行一行代码人肉解释、人肉"解释执行"它。这算是我操作系统的启蒙老师。这本书写得非常非常好，虽然今天来看，它的阅读价值已经越来越低了，但在那个时候就是如获至宝。

- 1987 年的 Minix 1：到 UNIX V7 兼容。
- 1997 年做了 Minix 2.0：POSIX 兼容，就完整地对着一个 POSIX UNIX 标准。
- 2006 年发布 Minix 3：因为它的兼容性，一直和标准对齐。

就靠这份兼容性，这还是一个非常了不起的项目：

| 版本 | 时间 | 兼容目标 |
| :--- | :--- | :--- |
| Minix 1 | 1987 年 | UNIX V7 完全兼容 |
| Minix 2.0 | 1997 年 | POSIX 兼容 |
| Minix 3 | 2006 年 | 完整的现代系统，至今仍在维护 |

我今天还给大家准备了一个 Minix。怎么准备呢？因为有爱好者已经把 Minix 这个项目完整地存档下来了。你们每个同学把这份代码下载下来以后，直接 `make minix2`，它就可以从 GitHub 上把 Minix 的源代码下载下来，包括 Minix 1，包括 Minix 2。这里面有一个编译的脚本，如果你的环境配置正确，里面的 `make all` 可以正确执行，执行完以后你会生成很多 images——包括 Minix 1.7 的一个 64 兆镜像，还有一个 Minix 2.0 的 64 兆镜像。非常小，在今天看非常小，但在那个时候其实已经是非常大的镜像了。

生成镜像以后——感谢软件世界里面有很多随手可得而且开源免费的工具——我们这次又用到模拟器了，可以直接 `make run`。

```bash
make minix2     # 从 GitHub 拉取 Minix 1 / Minix 2 的源码
make all        # 编译并生成镜像：Minix 1.7 与 Minix 2.0 各一个 64MB 镜像
make run        # 用模拟器把镜像跑起来
```

我这是一台 ARM 的树莓派，就是像小霸王一样的一台设备，整个计算机系统都在这个键盘里。它一点也不吃力，可以运行一个 Minix 1.7.5——那是随书送代码，每一个买那本《Operating Systems: Design and Implementation》教科书的人都会得到、都可以使用这份代码。所以这个 Minix 系统也是 Linus 实现 Linux 系统的原点。

启动的时候有一些日志信息：它找到了 `hd0`，那是一个 QEMU 的硬盘，它在 QEMU 上找到了一个磁盘，也报了一些 memory 的信息，然后有一条日志写着 `MINIX executing in 16 bit protected mode`。16 位意味着什么？你们没有用过 16 位机，没有真正在 16 位机上写过程序。但这是一个如假包换的、UNIX V7 兼容的 Minix 1.7；如果是 Minix 2.0 的话，它甚至是 POSIX 兼容的。

这和你们在一个 Linux 里面的体验几乎是一样的。你可以把时间回到 1987 年，得到一个这样的系统，里面有几乎所有的 UNIX 体验：

- 我可以用一个 `vi` 编辑器。`vi` 不是现在才有的，它是从 `ex` 来的——一个基于命令的编辑器，你每一条指令都说"我要把光标移到哪里""把这行换成什么"，一行一行输命令；后来它变成了一个 visualized 编辑器，就是 `vi`。我可以编辑一个 C 文件。
- 为了证明机器确实是 16 位的，我只要写这样一段代码，打印 `sizeof(int)`，编译运行一看是 `2`——16 位机器上 `int` 就只有两个字节。
- 上下键不能用，这个 shell 不支持我重复上一条命令。
- 我可以 `cat a.c`，然后把它管道给 `wc`。你看，我们今天上课的时候、你们日常在 zsh、在 fish 这些现代 shell 里用的管道命令，我现在经常管道给 `color-p`，但这就是从那个时代就有的应用思想。
- 我可以用 `cc` 来编译它，它就真的编译，生成了一个 `a.out`。`file a.out` 一看，它的格式是 `MINIX-PC 16-bit executable`。然后我真的可以运行它，`a.out` 打印出来 `2`。

UNIX 体验有多完整呢？我们甚至可以用 `man` 来查看手册，竟然还是有颜色的。今天 Linux 的手册也长这样：`man 1` 是 USER COMMANDS，`man 2` 是 SYS CALLS，`man 3` 是 LIBRARY ROUTINES。我们还可以 `man -k`。只是没有 `less`，只有 `more`。

这个系统里面有非常非常全的工具、系统调用、库函数。它甚至还有完整的源代码：在 `/usr/src` 里面，你可以找到所有的源代码，包括内核的源代码实现，也包括所有工具的源代码实现——比如刚才我用的 `vi`、`cc`，它们的实现都在。一个完整的、非常非常可用的操作系统。

我们说它是 UNIX V7 兼容的，这不是开玩笑的。这意味着在 1987 年，你找一台它能够支持的体系结构的机器，拿一个终端接上去，你在终端上看到的就是这个东西——不像今天我们已经没有那些设备了，必须在模拟器里运行它。而且它是可以自己编译自己的：你可以在 Minix 里面修改 Minix 整颗的内核，或者修改操作系统的功能。比如你想给它加一个功能、加一个系统调用，这都是 OK 的；然后你可以在 Minix 里面编译它，编译完了以后把这个内核镜像烧录到磁盘上——磁盘里面有加载器、有启动加载器，firmware 可以把这个东西加载上去，这个系统就真的可以运行了。而且你可以改它，改完以后的系统它也可以运行。

你可以用它来做任何事：打印、生成文档，生成文档以后连接一个打印机，把文档从打印机里打印出来，这都是可以做到的。

所以最早的时候，Linux 就是从这儿诞生的——因为它已经非常完整了。

### 微内核：一个只想要两个系统调用的疯狂想法

但是 Minix 有一个致命的缺点：慢。

Tanenbaum 是一个大学教授，是个像我这样的人。大学教授的想法总是比较疯狂和超前——有的时候我觉得我上课时的一些想法也比较疯狂，对吧，我们要做一个 Crazy OS。他那个时候的想法也很疯狂：在 1987 年、计算机处理器还很慢的时候，他就要做微内核。他的理想是想要做一个只有一个系统调用的操作系统，这个系统调用就叫 `send_receive`：我可以发一条消息，然后等一条消息回来。当然，Minix 实际上是有 `send` 和 `receive` 两个系统调用的。

只要有两个系统调用，它的操作系统内部就有一些线程，或者叫这些"服务"。你跟操作系统里的那些服务去交换消息，而这些服务甚至可以运行在用户态，只是会被赋予特别的权限。打个比方，就相当于我们有三个同学：A 同学负责文件系统，B 同学负责管 CPU，C 同学负责管内存。那我作为一个进程，我要内存，就跟负责内存的同学发个消息，他做好了给我；我要 CPU，就跟负责 CPU 的那个同学发个消息。他们都以普通进程的方式运行在用户态。

这确实是当时非常超前的想法。我觉得在今天这个想法其实挺好的，微内核很可能就要复活了——我记得前两年 OSDI 有一篇文章，就是讲鸿蒙的微内核是怎么实现的。但在那个时候，这是一个非常超前、而且不被大家看好的想法。

为什么呢？因为那个时候计算机很慢。计算机很慢的时候，你每执行一条系统调用——像 Linux，我一条 `syscall` 指令到内核里，内核代码没过几个时钟周期就开始执行了。但如果要发消息，那就不行：你先要把那个消息准备好。比如说你 `read`、`write` 的那些参数，你 `read`、`write` 那个字符串，都要先写到一个消息里；写完了以后，你要通过系统调用的方式把这个消息发给另外一个进程；另外一个进程运行了，执行完以后再返一个消息给你。它的性能很低。

```text
Linux（宏内核）的路子
  进程 ──syscall 指令──▶ 进入内核，内核代码马上开始执行

Minix（微内核）的路子
  进程 ──send(消息)──▶ 内核 ──转发──▶ 文件系统 / CPU / 内存服务
     ▲                                  （以用户态进程的形式运行）
     └────────── receive(回复消息) ──────┘

  read/write 的参数（比如那个字符串）必须先拷进消息里
```

所以这个操作系统对 Andy 来说，他一直说："我做这个操作系统、这个 crazy OS——当然包括 Minix——是为了上课的。我是为了教学生什么是操作系统、怎么设计和实现一个操作系统，性能不是我要管的。未来有一天，性能会是问题的。"

|  | 宏内核（Linux/Unix 一脉） | 微内核（Minix 的路线） |
| :--- | :--- | :--- |
| 系统调用入口 | 一条 `syscall` 指令直接进内核 | 发一条消息、等一条消息 |
| 服务的位置 | 内核代码在同一地址空间里执行 | 内核里的服务可以是用户态进程，被赋予特别权限 |
| 代价 | 代码全写在一起，改起来容易一团乱 | 参数要先拷进消息，进程切换加往返通信 |
| 当年的结论 | 性能好，但结构上难维护 | 结构干净，但在当年的机器上太慢 |

### 1991 年 8 月 25 日：just a hobby

于是就有了 1991 年 8 月 25 日的一个里程碑式的事件。

在那个时候，有一个来自芬兰的年轻人，时年 21 岁，跟你们差不多大。芬兰是一个非常冷的地方，一年四季有相当长的时间都是冬天。然后大雪封门，你可能会去滑雪、参与这种冬季运动，但更多的时候你可能只能宅在家里取暖，那你就只能在家里从事一些脑力活动。

在那个时间点，有一个天才少年——你们知道这个名字的，Linus。Linux 就是从他这儿来的。你看 Minix 那个 "x" 就是 Unix，Linux 那个 "x" 也是 Unix，然后把自己的名字放进来。（所以从这个意义上讲，我觉得 Tanenbaum 起名字的时候更像一个老师起的名字。Anyway，这个不重要。）

他在 Minix 的邮件列表里发了这样一个帖子，这个列表叫 `comp.os.minix`——今天可以理解为就是百度贴吧，叫"Minix 吧"，你们这么理解就行了。帖子的意思是：同志们好，你们这些用 Minix 的人，我现在在做一个 free 的 operating system，`just a hobby, won't be big and professional like GNU`。

> **提示**：这句 **just a hobby, won't be big and professional like GNU** 是 Linux 史上最有名的一句话。它出现在 1991 年 8 月 25 日那封发往 `comp.os.minix` 的帖子里。

那个时候 GNU 也在开发自己的内核，结果 GNU 的内核到现在都还是难产的状态，而 Linux 已经成为事实标准了。他还说，我这个 Linux 从来没有想过要支持另外一个机器结构，RISC-V 这些从来没想过——像今天，我的小霸王上是 ARM64，我在这里还可以用 QEMU 跑一个 32 位或 16 位的 x86 系统，这从来没想过。他说，因为就因为他手上有台 386，所以他说好，我现在就想做一个 386 上面能够取代 Minix 的操作系统；我从四月份就开始搞了，现在马上这个东西就可以给你们用了。然后很快，他就把最早的一批源代码发了上来。

很有意思，发在"百度贴吧"上——一会儿我还要继续讲这个"百度贴吧"里面发生的故事。

早期的 Linux 还会依赖 Minix，它不像现在所有东西都是 GNU 系、可以 self-contained。因为它还没有自己的文件系统的时候，你为了运行 Linux，需要把你的磁盘格式化成 Minix 文件系统——就是我刚才给大家看的那个终端里的 Minix 文件系统——格式化成 Minix 文件系统，然后 Linux 才能用。而它上面运行的软件包括了 GNU 的 GCC、bash，当然都是非常早期的版本。

所以有的时候觉得是这样：在一个合适的时间、合适的地方有一个合适的人，然后就做成了一件事。

### 对的时间、对的地点、对的人

我觉得更有意思的是，这个世界上有更多可能合适的人在不合适的时间做了合适的事，然后这个事情就可能会被雪藏几十年。

比如 Frank Rosenblatt 的 Perceptron paper，他提出了一种叫感知机的东西。这个东西你们看，是不是有点熟悉？他说人类——他受到人类神经元的启发——说：我们能不能把这个机器里面也做出一个像人类神经元一样的东西，一个 neuron，它能够接收来自其他神经元的输入，然后再输出一些输出，送给其他的神经元；当然这些权重是学出来的。这不就是我们今天的深度神经网络吗？

当然，后来到 2012 年的时候才有 AlexNet。这就是"有合适的人想做合适的东西，但是在不合适的时间"：因为那个时候没有算力，也没有一个氛围可以让大家都愿意去做。虽然这个东西火过，但后来又被一些人泼了冷水——他们试图证明，比如两层的、就一个 hidden layer 的感知机，它的计算能力很弱；多层的、多层的能力是强，但是大家又不会训练。然后就走进了人工智能的寒冬，现在又是人工智能的热潮。

所以我们需要正确的时间、正确的地点、合适的人，把一件事情给做成了。做成了，就是你知道的我们今天上课讲的 Linux：你们的每一个服务器——不管是你今天打开抖音还是淘宝，他们背后给你提供服务、生成那个页面的服务器——或者你们的安卓手机，背后都是 Linux。这是一件很了不起的事情。

在这个过程里也诞生了很多名场面。2012 年我那个时候在读 PhD。2012 年的时候 AlexNet——这三个人，Alex、Ilya，这两个非常有名，还有一个是 Geoffrey Hinton——他们还在搞 AlexNet。而 NVIDIA 在 2006 年推出了 CUDA，就是那个现在消耗全球最多电力的编程框架。它是一个非常反人类的编程框架，那个时候我还在读 PhD，还在跟我的同学们抱怨：你看 NVIDIA 野心很大，但是它做了一个烂东西出来。当然到今天大家还是在抱怨 CUDA 反人类，所以你看现在有什么 Megatron、有什么 Triton，这些抽象层把它按到下面去。

就在那个时候，2012 年又是一个正确的时间，他们在搞 AlexNet。Linus 说了一句："NVIDIA is the single worst company we have ever dealt with." 然后配上一个手势，和某个 colorful word。现在 NVIDIA 已经是地球上市值最高的公司了。

但 Linus 就是这样一个非常有性格的人。他有很多名言，包括他很自负地说：这个世界上没有人能写出完美的代码，除了我。后来还有人写论文的时候还会 diss 他——因为 Linux kernel 的那个邮件列表是永久保存的，你可以翻出历史上所有的那些邮件，所以他在里面那些口出狂言、大放厥词，也都被记录下来了。我觉得在那个时代的背景下，这些话还是有一定的道理的，虽然你现在从现在的意义上会觉有点看笑话。

### 一个偶然的革命

那他是怎么成功的呢？Just for fun。

我刚才说到，他是来自芬兰的一个天才男孩，在冰天雪地里什么事也干不了，只能窝在温暖的家里边写代码。有一本回忆录，David Diamond 参与写的，书的名字就叫《The Story of an Accidental Revolutionary》——一次偶然的革命。没有人想到，那个和你们一样大的 21 岁少年，在 1991 年 8 月 25 日说"我就是一个 hobby"，在贴吧上发了个帖子，没想到诞生了今天整个计算机世界的基座。

所以这本书里说：革命不是被"生"出来的，它可以被计划、可以被管理，但它归根到底是自己"发生"的——they happen, just happen。

### 交叉路口：今天的土壤与今天的约束

所以我们处在一个很有意思的交叉路口上。

第一个：这是我梦开始的地方，2009 年。在那个时候，其实这本书已经出来很多很多年了，已经是一个过时的教科书了。也就是说，我在 2009 年的时候，是在用一本过时的教科书来学"操作系统是什么"。而等到今天，你们坐在这儿，手上已经有最好的大语言模型——中国也有——所有东西都是最好的，课程也是最好的；你们可以在计算机系统基础课上写 NEMU，这就是世界上最好的学计算机系统的方式。

也就是说，我们现在已经有一个土壤了。如果你们有一个同学 just for fun，今天想去百度贴吧做一个 CrazyOS，你们也可以做成。

但与此同时，我们又很奇怪：最近也有一些有意思的帖子，包括那个很火的、已经被广泛流传的公众号帖子——"我的博导也是干摩托车发动机的，为什么他没干出来？"。以及，在 2023 年 12 月，全国高校科技创新工作会议暨基础学科拔尖创新学科突破计划启动部署会召开，要求高校老师提高政治站位、勇担国家使命、精心谋划一批重大战略任务、重大政策举措和重大工程项目。

从国家的背景上看，我觉得这无可厚非，他们也只能用这个手段——因为他没有办法说"你们每个人都躺平吧，去做 CrazyOS 去，国家有钱"，所以他必须要求高校来做这件事情。但是从另外一个角度，如果我们被迫要做这件事情的时候，我就什么也做不出来了：因为我必须写一个非常长的计划，论证这件事情是可以的；等把这个东西写出来的时候，我要做的事情可能已经过时了。

而 Linus 那个少年，是在一个好的、无所谓的土壤里，经历了很长一段时间的发展。

### 贴吧论战：大学教授、毛头小伙子与院士

随着关注 Linux 的人越来越多，`comp.os.minix` 上关于 Linux 的讨论也越来越多。这里面甚至出现了一件有意思的事：刚才我提到的 Minix 的作者 Andy Tanenbaum，以一种官方的方式在"百度贴吧"里回复了，开始和 Linux 这个小伙子论战。

在 1992 年 1 月 29 日，他说——因为有一种什么感觉呢，Minix 很好，我们刚才看了，Minix 真的很好，它能用，就是性能不行，它做得很超前——所以他站在道德的制高点上来批判 Linux，说：你看你这个小伙子——一个大学教授，在百度贴吧上跟人论战——`To me writing a monolithic system is a truly poor idea`。monolithic 就是说 Linux 内核像 Unix 一样，所有的代码都写在一起；在 1991 年的时候说这话，攻击性非常强。

还有一些防御性的话，我觉得就有阴阳怪气的感觉了：`Don't get me wrong. I am not unhappy with Linux.` 我还是很开心啊，吧啦吧啦吧啦…… `But in all honesty, I would suggest that people who want a modern free OS look around.` ——就是"来看我的，我这个才是"。

然后这个论战就……Linus 这个人大家都知道，嘴臭，那你肯定是是要喷回去的，他就喷回去了。

有意思的是，这个帖子里还有一个人回了，是 Ken Thompson。Ken Thompson 相当于什么呢？那个时候大家已经在 10 年前——1983 年，因为 Unix 获得了图灵奖——就相当于他在中国的地位，比中国科学院院士还要再顶一层，至少是中国科学院院士级的人物。也就是说，一个院士，在一个大学教授和一个毛头小伙子的论战之间，实名在贴吧上发表自己的言论。

当然这个言论也是他自己的工程经验。他说：`Generally agree that microkernels are probably the wave of the future.`——我觉得真的，你看到今天，我们开始有鸿蒙微内核了——`However, it is in my opinion easier to implement a monolithic kernel, easier for it to turn into a mess in a hurry as it is modified.` 结果就是，这几句话都成真了。

### Linux 自己的弯路

院士说"monolithic 容易很快变成一团乱"，这句话在 Linux 身上确实应验过。Linux 在有一段时间里面，其实经历了一个非常大的 mess。

从那张图上你能看到：Linux 最早的时候是一个 hobby project，还很小；然后随着越来越多的厂商开始入场——IBM 那些开始入场——Linux 开始成为一个服务器上可以严肃运行的东西。

- 内核 2.0 引入了多处理器支持；到 2.4，内核代码才真正能多处理器并行，否则只有用户态的程序能并行执行。
- 2003 年 Linux 2.6 发布，大概在那个时候正好是大家开始做云计算基础设施的时候——Google 开始在那个时候做云计算的基础设施——它开始起飞，源码经历了一个巨大的膨胀，2003 年的时候经历一个巨大的膨胀。
- 之后基本上是稳定了，但好几个 subsystem 经历了巨大的重构，包括 USB 子系统等等，就是它已经陷入了一个泥潭。那段时间图上也有断崖式的下跌。

```text
1987   Minix 1，UNIX V7 兼容，随书发行
1991   Linux 0.01：Linus 在 comp.os.minix 发帖；
       四月份开始写，手上是一台 386；
       早期还要把磁盘格式化成 Minix 文件系统，靠 Minix 的工具链和 GCC、bash
       │
       ▼  越来越多的厂商（IBM 等）入场
           Linux 成为服务器上可以严肃运行的系统
 2.0   引入多处理器支持
 2.4   内核代码才真正能多处理器并行（此前只有用户态程序能并行）
       │
2003   Linux 2.6 发布，恰逢云计算基础设施起步，源码规模巨大膨胀
       │
       ▼  多个 subsystem 大规模重构（USB 子系统等），一度陷入泥潭
今天   既像微内核、又像宏内核的一个现代的、非常先进的操作系统
```

所以 Linux 早期说的那些"不所谓不重要的话"，最后也都被打脸了。它逐渐变成了一个现代的、非常先进的操作系统——有点像微内核，又有点像宏内核，我也不知道应该怎么叫它。

### 为什么还需要上了年纪的人来教你们

我再回到刚才那件事：院士竟然可以下场到贴吧来回复。在我们这里，这是一件政治不太正确的事情。你想嘛，你们校长突然到百度贴吧来回你的帖子，你会觉得 not likely to happen。

但如果我们有一天真的可以变成这样——我就去贴吧跟你们论战，你们有同学说你们写了一个 CrazyOS，然后我就去跟你们互喷，喷完了以后这个系统最后越变越好——那我觉得这绝对是值得的。这样的故事其实一直都在发生，它不是个例。

所以为什么我觉得需要老一点的人、像我上了年纪的人来教你们，而不是同学和同学之间学习？同学和同学之间学习，我觉得有一点好：你们年轻人有热情，有荷尔蒙。我到我这个年纪，没什么荷尔蒙了，所以我看什么事情都比较平常，兴奋不起来了。

但你们不一样。你们像 Linus 那时候，一看到 Andy 竟然要抱怨我的系统，那我一定要喷回去；而我现在看你们要喷我，我也不会喷回去，我是平常心。就是这种热血——因为你们年轻人之间有热血，所以你们可以把一件事义无反顾地做下去。可能很多人都失败了，但最后有一个人成功了，就彻底改变了世界。

所以这些伟大的东西，其实都是从零开始的。*Fire in the Valley* 讲个人电脑的故事，从最早的时候那台 Altair 8800，Bill Gates 要带着一卷纸去运行他的 Basic；然后到 *The Evolution of the Unix Time-Sharing System*——这些伟大的东西都是从零开始的。

### 从 0 到 0.1 前所未有的容易

你看这些故事，它们都是从零开始的。而且今天，在现在这个时代，从 0 到 0.1——从完全没有，你只有一个想法，像 Linus 当时说"我就要在一台 486、在微机上复刻一个 Unix 操作系统，然后它性能很好"——这样的一个想法，在那个时候必须要一个天才才能实现，但今天不需要了。

只要你有这个想法、它足够偏门，但是实现起来对一个领域的专家没有显著的门槛，那么从 0 到 0.1 就前所未有的容易：你马上咔咔地烧点 token，就给你做一个原型出来，界面还做得漂漂亮亮的。然后甚至我觉得可能在短时间、不会太长的时间里面，从 0.1 到 0.95 可能都变得容易了，然后这个世界上创新的模式就变了。

我其实有一些例子。比如我今天上课说 CrazyOS，我一直在想，CrazyOS 可以把它变成什么？我想到的是：我们可以在硬件上面通过增加指令集的方式，让硬件能够高效地运行 CrazyOS。那这就可能真的可以做一种新型的计算机，然后我可以做这个 hardware-software co-design，彻底重新做一种操作系统。至少可以从头再做一遍——可能以前有人做过类似的事情，但至少可以从头再做一遍。而从 0 到 0.1 非常容易。

最近也有一个大新闻：Anthropic 发了新的模型，已经变成 3.5 了，然后它说 `Finding bugs is easy`。当然马上大家就揪出来它是过度营销——它找的那个 FFmpeg 的 bug 是一条根本就不可能走得进去的路径，就是一条地球上都不会有人去走的路径上面的一个遗留 bug。

但我觉得确实是从 0 到 0.1 变得前所未有的容易。比如我们自己的工作：我们也做测试。你们的编译器是有 bug 的，你们的 GCC、你们的 LLVM 在编译程序的时候都有可能会编译错。我们是真的在实际的项目当中遇到过它给编译错的，那真的很离谱。因为编译器给你编译错了，你为了把这个 bug 找到——一般来讲，你程序出错了，第一个怀疑的都是我自己、我的逻辑写错了，你不会去怀疑编译器给你代码翻译错了；但编译器真的会翻译错。

在 GPT-4 的时代，我们通过非常好的 prompt engineering，我们用一个 prompt 给 GCC、LLVM 就找了 150 个 bug——而且还是在那个 prompt 写得很差的情况下：第一个，prompt 写得很差，因为那是学生写的；第二个，是因为 GPT-4 的能力其实比现在差很多。你看现在各种榜单，一个 20B 的小的开源模型都会吊打 GPT-4，但 GPT-4 是那个时候最大的模型。也就是说，我如果现在重新去做这份工作，我觉得我找到个一两千个 bug 绝对不是一件困难的事情。

但是，又怎么样呢？从 0 到 0.1 会变得前所未有的容易。

再比如这两天有一个很有意思的项目，叫 Caveman，它去用极致的 prompt 去压缩你的输出。你看大语言模型，它被微调，被微调成一个舔狗——我一直说大语言模型就被微调成了一个舔狗，它每次说任何话的时候，都是要把你的主人伺候得好好的。但这对调用者来说是一种浪费。

门槛塌到这么低之后，稀缺的东西其实就换了：不再是"我能不能把它做出来"，而是那个足够偏门的想法，以及愿不愿意像那些少年一样，一无反顾地做下去。

## 从第一个进程到应用生态

### 从 Caveman 说起

我最近看到一个很有意思的做法，叫 Caveman。它让 AI 把所有没必要的废话全砍掉：能用文言文讲就用文言文讲，语法不正确也不要紧，能写多短就写多短——反正大语言模型看得懂。

它省 token 省得极狠，但精妙的地方不在这儿，而在于它利用了 agent 的容错性。你马上就会想：prompt 被缩减了，信息必然丢；信息丢了，准确率必然下降；以前说一堆废话的时候能做对的，现在说得少了，就做不对了。这个推理一点没错，但是不要紧。任务描述没变，程序的输出也没变，agent 发现做不对，它会自己再试一次；再试一次，往往就做对了。它用 agent 的自主性去弥补那一点点下降的准确率——只要下降得不太大，从 overall 上看，token 还是省下来了。Caveman 背后就是这个道理。

我自己的 Claude.md 里也有一条类似的规则：答得简单一点，用中文。我上课的时候所有的问答都是用英文问的，但你看我的 Claude Code，输出全是中文，而且确实比较短。想法跟 Caveman 一样，只是他做得更极致。

顺着这件事，我还发现了另外一点。我最近在审稿，审了一些论文，其中不少论文做了好多好多东西，A、B、C、D、E 加在一起，可我觉得它们的效果可能都不如 Caveman。我不明白为什么会这样：为什么一定要为了一篇论文去写一篇论文，浪费每一个读者的时间？明明在这个时代，从 0 到 0.1 已经变得前所未有的容易。

说了这么多，其实我就是要说一件事：你们可能在高中已经坐牢坐了三年，已经 burn out 了，但你们现在还有机会把自己解脱出来。你们可以像 Linus 那样，想一想自己还可以做什么，然后在 AI 的帮助下做一点了不起的事情，找到一个状态。现在的版本答案，也许并不是拿一个南大的学位、回老家找个公务员的工作、躺到退休——因为当所有岗位都面临被取代的时候，我自己也一样，我在这儿能走多远我都还不知道。你们可能更要往前走得更远一点。

好，回到操作系统。前面讲的是历史上我们的系统调用、我们的操作系统是怎么从最早的 Unix 一点一点变成今天的 Linux 的。接下来要看的是另一件事：一个真正的 Linux，我们能不能从零开始，真正掌控它。

### 谁是世界上的第一个进程

先回顾一下进程的初始状态，也就是 execve 的那一刻：有 `argc`、`argv[0]`、`envp`、`auxv`，有 `path` 和 `interpreter` 被加载到内存里，然后设置好正确的 PC。我们的硬件也有一个 CPU reset 状态：一上电，寄存器和内存里就是确定的值，PC 指向 firmware。我们还讲过能感染 firmware 的病毒——它在 4 月 26 号把你的 firmware 改写掉，你的电脑就真的成砖了。

firmware 会执行，它里面有一个启动加载器，也就是 bootloader；启动加载器会加载操作系统。操作系统可能也是一个 ELF，比如 `os.elf`，它是静态链接的；PC 指向里面的一条指令，操作系统就开始运行了。

操作系统运行起来以后，它会加载世界上的第一个进程。那么第一个进程是什么呢？你在 pstree 里看进程树，会发现所有的进程都有一个共同的根，叫 systemd。Linux 从硬件、固件被加载起来、运行之后，跑的第一个进程就是 systemd 吗？还是别的什么？

这就是今天技术部分要讲的东西：操作系统上的第一个进程。因为内核加载了第一个进程之后，它自己就变成了一个系统调用的提供者——你的 system call 调进来会调到它；它会响应中断；它还会在后台处理一些还没完成的事情，比如把缓存写到磁盘里去。那么，掌管了你看到的整个操作系统世界的全部进程，它到底在哪里？它做了什么？我们能不能控制它？

> **结论**：只要你问出这个问题——我们能不能把操作系统加载的第一个进程换成我们自己的进程？——那么合理的事情就一定能做到。你马上就可以让 AI 帮你把这件事搞定。

```text
上电
  │  CPU reset：寄存器和内存被置为确定状态，PC 指向 firmware
  ▼
firmware（固件，可能被病毒改写）
  │  内含 bootloader
  ▼
bootloader 加载操作系统镜像
  │  os.elf（静态链接的 ELF）
  ▼
内核开始运行
  │  在 initramfs 里按硬编码路径依次尝试：/sbin/init → /etc/init → /bin/init
  ▼
第一个进程（本例中是 initramfs 里的 /init）
  │  做完了该做的事，执行 pivot_root 系统调用
  ▼
换成真实根文件系统上的 init（例如 systemd）
  │  systemd 才成为进程树的根
  ▼
整个进程世界
```

这张图就是这一讲要走的路：从 CPU reset 那个绝对确定的初始状态出发，一路走到第一个进程，再走到今天看到的整棵进程树；中间那个 pivot_root，是往后才会揭晓的答案。

### 一个最小的 Linux：initramfs

#### 一个最小的二进制文件

我在课上讲过一个最小的 x86_64 二进制文件：它先做一个 syscall 打印一句话——这里打印的是 `This is a minimal binary`——它不需要任何额外的库函数，就用系统调用打印，然后再调用一个 exit，程序就退出了。这是一个 64 位的、静态链接（static linked）的 minimal 二进制文件。

我把它编译出来，就能在我的电脑上运行。等等，这不是一个 x86 的二进制文件吗？为什么能在我的电脑上跑？因为我的加载器知道我的系统里面有 QEMU。如果我运行一个别的体系结构的二进制文件，它默认会进入模拟器的状态执行：所有的用户态指令——mov 这些做计算和访存的指令——都被模拟执行；而当它调用系统调用的时候，它会直接调用我这个操作系统上面的系统调用。这是一个很有意思的特点。

#### 为什么要有一个内存里的文件系统

如果你问 AI：我想控制第一个运行的进程，需要准备什么？它大概会告诉你，你首先需要准备一个东西，叫 initramfs。

这个词是这样断的：init-ram-fs，初始的时候、内存里面的文件系统。

为什么必须先有它？还记得 execve 的参数吗？`man 2 execve`，execve 的第一个参数是一个 pathname，它指向系统里面的一个文件。你可以 execve 一个 `a.out`，可以 execve `/bin/ls`，可以 execve `/bin/bash`，但总之你必须有一个文件。而内核刚开始的时候，它还根本不知道你的文件是存在 U 盘上、存在磁盘上，还是在哪里——那么最早的那个文件在哪里？就在 initramfs 里。它是一个你可以控制、可以自己构建的东西。

> **提示**：你用 apt 更新软件包的时候，有时候会看到一个耗时特别长的操作，叫 `update-initramfs`。别的操作都很快，唯独它最慢。原因就是有些软件更新以后，新版本的软件要被打回这个最初始的文件系统里去，而这个文件系统里必须放着你要加载的第一个程序。

知道了这一点，你就可以让 AI 帮你构建一个 initramfs，它也可以给你一个打包脚本。因为 initramfs 是一个文件系统，所以我们可以做一棵目录树：树里有 `/bin`，有任何一个你想要的东西，`bin` 里面可以有 bash……

至于第一个进程到底是谁在管，Linux 操作系统的代码里硬编码了一系列路径，它会从 initramfs 里一个一个去尝试：`/sbin/init` 不存在，就试 `/etc/init`，再试 `/bin/init`。总之试到最后一个有的，execve 成功，这个第一个进程就被加载到 Linux 的世界上了。

#### 打包、加载，与 init 退出之后

这个 initramfs 是这么造出来的：把一棵目录树用 `cpio` 归档，再用 `gzip` 压缩，生成一个 `initramfs.cpio.gz`。QEMU 启动的时候，用 `-kernel` 加载内核，用 `-initrd` 加载这个打包好的 initramfs。

我还可以再加一个参数 `rdinit=/init`：它硬编码的那些路径是一个默认行为，但我可以在内核的命令行参数里把它 override 掉，直接指定第一个进程是谁。

```text
目录树（/bin、/init、驱动模块……）
  │  cpio 归档，再 gzip 压缩
  ▼
initramfs.cpio.gz
  │  QEMU 用 -initrd 交给内核（内核镜像由 -kernel 加载）
  ▼
内核把它解开，当成初始的内存文件系统
  │  按硬编码路径逐个尝试；被 rdinit 覆盖时直接用指定的那个
  ▼
第一个进程被 execve 加载，成为 1 号进程
```

从目录树到第一个进程，中间只隔着一个压缩包：谁来把包交给内核（`-initrd`），以及内核从包里挑哪一个文件来执行（硬编码路径，或 `rdinit` 指定），就是全部可以动手脚的地方。

`make run`，我就在 QEMU 的模拟器里跑起来了。我用了 `-nographic` 的选项，所以没有那个图形界面的 QEMU；启动比你们的 Linux 慢很多，因为这是模拟出来的，我在 ARM 上模拟了一个 x86。日志里能看到 `Linux version 6.1.0-amd64`——这是我从另外一台电脑上拷出来的一个 Linux 内核镜像，运行的是一台 QEMU Standard PC。

你们有没有见过 Linux 开机？屏幕上不断地滚消息，滚到某一个时刻，屏幕会突然闪一下，然后字体、分辨率就都正常了。它的启动其实是分好几级的。

在 minimal 这个例子里，内核运行了 4.4 秒以后，Linux 说：`Run /init as init process`——正确，这就是我刚才指定的行为。然后它打印出 `This is a minimal binary`，跟我刚才直接运行那个 minimal 时打出来的一模一样的红字。

接着有意思的事情来了：执行了几条指令以后，它执行了一个 exit，一个 syscall exit。在我的操作系统上这没有任何问题，这个进程退出了，因为系统里面还有别的进程。但如果退出的是 init 进程，内核就直接罢工了：

```text
Kernel panic - not syncing: Attempted to kill init!
```

它后面还给了一个 call stack，整个操作系统就挂掉了。

> **结论**：我们确实控制了 Linux 加载的第一个进程；同时也能看出 init 是一个特殊进程——别的进程退出无所谓，init 一退出，整个系统就完了。

### 让 AI 解包一个真实的 initrd

既然已经知道 initramfs 是一个打好包的目录树，那真实的系统里面应该也有一个一模一样的包，只不过那是别人打好的、目录树是固定的。于是我可以直接对 AI 说：你可以把这个 initramfs 解开吗？我告诉它我是一台树莓派，想把它解出来。它找到了 `/boot/initrd.img`。

你甚至都不需要知道它内部运行了什么，你只要有这么一个概念：这个世界上有一个打好包的目录树。

#### 大小对不上：识破一次错误的解包

这一次 AI 翻车了。它把包解开，然后说：这是一个 minimal 的 initrd，仅包含内核模块，没有 init 脚本。

我为什么知道它翻车了？因为我今天准备这个的时候自己走过一遍这个流程。证据是：解开以后所有文件加起来总共只有 7.3 兆，可这个 initrd 本身足足有 23 兆。这件事情不对。你只要发现这个不一致，就可以跟它说：肯定有一些东西没有解出来。

> **提示**：你们需要的是一种敏感性——随时随地，AI 都可能会犯错，都可能会做错。就像这次，它开始干各种骚操作，甚至直接去读那个二进制文件，因为它觉得后面还有没解压出来的数据。

于是它开始写脚本来解。这就是 coding agent 像人的地方：它找到了在 trailer 后面还有 19 兆的额外数据，然后发现后面还有一段 zstd 压缩的 cpio。这也是 Linux 内核复杂的地方——initrd 概念上是一个目录树，但这个压缩文件可以分成几段来压缩。它这次解到了一个叫 `initrd4` 的目录里。

顺便说一句：在刚刚整个过程中，我对具体的流程、它使用的工具、文件的结构一无所知，应该用什么样的命令行工具我也一无所知——我可能有概念，但我是故意假装自己没有这些概念。我有的只是一些最基本的观察：我解出来一个 7 兆的东西，但那个文件有 23 兆，那 23 兆里面一定还有东西没解出来。如果你能有敏锐的观察——我也相信有一天 AI 会自然而然地产生这种敏锐的观察——那它就真的可以把要做的事情给搞定。

#### 一个真实 initrd 里装着什么

`initrd4` 的目录结构长得非常像你的 `/`：有 `lib`、有 `usr`、有 `bin`，看起来就像一个完整的小系统。我当时做的任务，就是让它解释一下一个真实系统里面、初始的那个文件系统的目录树。

里面有什么呢？有核心的启动脚本，它还告诉你按照什么样的顺序来启动；甚至有 `ntfs-3g`，也就是 NTFS 支持，你可以从一个 NTFS 驱动器里面读到数据；有各种各样的配置文件，甚至有键盘布局、字体配置；还有用户空间工具——`/usr/bin` 和 `/usr/sbin` 下面有大量的工具，都是 BusyBox 提供的经典版。这有点像前面看到的 MINIX：你有一套全套的命令行工具，这里一个 BusyBox 也有全套的命令行工具，还有一些库。

`init` 其实可以是动态链接的，因为在这个时候已经有文件系统了。前面我那个 initramfs 里只有一个 minimal，所以它是静态链接的；但如果文件系统里面有动态链接库，我的操作系统完全是可以支持 ELF 的动态加载的，这里也就有必要的动态链接库。此外还有内核模块的信息，还有固件——一些固件的二进制，也就是驱动。它需要加载必要的驱动才能访问某些设备，这些都在 initramfs 里。它也知道，这是树莓派上 Debian 的 initrd，主要职责是加载内核模块、检测并把实际的文件系统挂载起来，然后显示一个启动画面。

> **提示**：如果你的磁盘发生了损坏、文件系统挂不上，你有可能会进入 initrd 的模式。这时候只要这个初始的文件系统没有损坏，你依然可以得到一个命令行的体验：Linux 内核已经加载了，所有的系统调用都正常工作，虽然磁盘上的那些二进制文件都取不到，但你的系统其实已经可以工作了。

#### switch_root：那个从没见过的文件系统去哪了

在这个 init 的最后，有一句话引起了你的注意：`switch_root`，切换到真实根文件系统。

你回头想一想：这个 initramfs 你从来没有见过。我用 tree 打印这个点，你们从来没有在自己的 Linux 系统上见过一个长成这样的文件系统；但你又非常确信它就是系统的——因为系统里面可能只有这一个文件，而且如果你看 Linux 内核启动的日志，它也确实指向这个文件是 initramfs。那这个东西到哪去了呢？

答案是一个新知识。Linux 系统在启动的时候，虽然看起来 systemd 是你整个进程树的根、是你的 1 号进程，但其实不是这样的。在整个系统的启动和加载过程当中，initramfs 阶段的最后——这个阶段你甚至可以弹出一个命令行 shell 跟它交互，告诉它你要干什么、重新配置，比如找不到启动盘的时候，你在 `/etc/fstab` 里写了启动盘，它找不到的时候你甚至可以在那里说"我要换一块盘来启动"——当所有事情都完工以后，它会执行一个 syscall，叫 `pivot_root`。`man 2 pivot_root` 上面写着：change the root mount。它重新创造了以 systemd 为根的那个世界。这当然也是可以指定的：你系统的根、你的 init 是 systemd，然后这个 systemd 再创建出你在进程树里看到的那整个操作系统的进程世界。

> **易错点**：systemd 是 1 号进程，但它是 pivot_root 之后才成为 1 号进程的；在 initramfs 那个阶段，这个世界上的 1 号进程是 initramfs 里的 `/init`。系统启动并不是"内核直接拉起 systemd"，中间还隔着一整个阶段的初始文件系统。

### 亲手点亮一个真实的 Linux

理论说完了，我们来真实地看一个 Linux。我也准备了这样一份脚本。这份脚本里面有两个部分的 init，它们都叫 init，名字有一点点容易混淆，但这两份脚本是不一样的：一份在 initramfs 阶段，一份在真实的根文件系统上。

#### initramfs 阶段：只有 BusyBox 的世界

在 initramfs 阶段，我的世界上就只有 BusyBox。我在这里加了一个 shell。这个例子里我打包了这样一个初始文件系统：一个 `/init`、一个 `/bin/busybox`，除此之外还有一些驱动程序——我今天发现我的 QEMU 必须要这些驱动才能正确运行。这个世界里面就再没有任何别的东西了。

根据我们知道的信息，Linux 加载以后会把这个 initramfs 解开、当成一个文件系统，然后执行这里的 init。这个 init 是什么？它的解释器是 `/bin/busybox sh`，我用 shell 来解释它；解释以后，先把 `/init` 删掉，然后执行一个 shell。

编译、运行——这次是有图形的。因为我是树莓派，用它做全系统模拟稍微有点慢，x86_64 的 QEMU 启动需要那么几秒钟。几秒钟以后 Linux 正常启动了，它加载了我这个 initramfs，刚才那个脚本就跑起来了。

这时候系统里面其实什么也没有。`find /` 一下：只有 `/bin/busybox`，还有我加的那一大堆驱动（没有这些驱动我就没有办法做下一件事，所以我被迫要烤上一大堆驱动）。`/root` 是 shell 创建的，最开始的时候是没有的；还有一个 `/dev/console`。你今天见到的那些东西都不存在：什么 `/bin/ls`、`/bin/sh`，都没有，只有一个 `/bin/busybox`。

我的脚本还没有完，它跑到 13 行，然后我要从这个 shell 里退出。shell 退出以后，脚本会打一条 message，然后执行一段非常神奇的脚本：

```sh
for cmd in $(/bin/busybox --list); do
    /bin/busybox ln -s /bin/busybox "/bin/$cmd"
done
```

`/bin/busybox --list` 的功能是把 BusyBox 里面所有支持的命令都列出来——你看有这么多的命令，全都被集成在这一个 busybox 二进制文件里。然后为每一个命令创建一个符号链接：如果里面有一个命令叫 `ls`，我就创建一个符号链接 `/bin/ls`，指向 busybox。用这样的三行脚本，我就创建出了 `/bin` 里面的一大堆二进制文件。

接下来，脚本用 `mkdir`、`mount` 这些命令开始创建操作系统里面的对象：创建一个 `/proc`（procfs），创建一个 `/sys`；再用 `insmod` 往内核里面安装一大堆驱动；用 `mknod` 创建一大堆设备；最后打一句 `init ok, launch a shell. initramfs busybox sh`。

于是我退出这个 shell，它就开始做剩下的事情。日志都打印出来了，`insmod` 成功了，那行红字 `init ok, launch a shell` 也出来了。这时候你就可以运行 `ps` 了——procfs 里面有东西了；可以用 `ls /bin/*` 看看现在有的功能：这些文件都存在了，每一个都是符号链接，像 word count、`wget`，都指向 `/bin/busybox`。

这个系统其实已经有一点能用了。`ps` 显示 1 号进程是 init，是 busybox sh 那个 `/init`——这是最早的、操作系统加载的那个二进制文件，是所有进程的祖先，此外还有一些操作系统自己的线程。系统里面现在就只有我的 busybox sh，还有刚起的那个 ps。

计算机系统里面没有任何的魔法。还有一点我要强调：在那个 shell 被加载以后，我看起来在用的是命令行的工具，但它们的背后全部都是系统调用。

- 执行那行 `ln -s` 的时候，我当前的 shell 会 fork 一份，fork 完以后 execve 运行 busybox，busybox 完成解析后执行一个做符号链接的系统调用，这个系统调用就在文件系统里面创建一个符号链接。
- 看起来是一个 `mkdir` 命令，背后也是一个 mkdir 的系统调用，它就在这个文件系统里——当然是最初始的内存里的文件系统——创建一个目录。
- `mount -t proc /proc` 是把整个 procfs 里面所有的对象都在 `/proc` 这个目录里面创建出来：一条 mount 命令背后是 mount 系统调用，在我的操作系统里面又创建出了很多对象。
- 每一个命令都对应一个系统调用，包括 `mknod`。比如我要创建一个叫 `/dev/vda` 的磁盘，`vda` 是一个虚拟磁盘，是一个 virtio 的 QEMU 磁盘——如果你在阿里云上租一台机器，你也能看到 `/dev/vda`。这里需要指定一个主设备号、指定一个从设备号，这个设备文件才能被创建出来。

你 `/dev` 里面的每一个文件都是以这种方式创建的。列一下就能看到它们都是设备：

| 设备文件 | 类型 | 主设备号 : 从设备号 |
| :--- | :--- | :--- |
| `/dev/random` | 字符设备 | 1 : 8 |
| `/dev/urandom` | 字符设备 | 1 : 9 |
| `/dev/null` | 字符设备 | 1 : 3 |
| `/dev/tty1` | 字符设备 | 4 : 1 |

它们现在是可以正常工作的，你看操作系统的日志就知道。

有了 procfs，`ps` 才能工作。在最开始那个阶段你是没有办法 `ps` 的，因为 ps 会发现 `/proc` 里面没有文件；现在 `/proc` 里面有文件，所以 ps 可以正确执行。我还可以 `vi a.txt`、`cat a.txt`，也可以用管道，这都是标准的。

#### 第二段 init：挂上真正的磁盘

如果我的 shell 退出，真正神奇的事情才开始。这一次我会倒数三秒钟：3、2、1。倒数完，我就可以把 `/dev/vda` 挂上了——创建一个叫 `/mnt` 的目录，然后 `mount -t ext4 /dev/vda /mnt`。它成功了。

到这个时候，一个 `/dev/vda` 对应一块磁盘，磁盘也是一个操作系统的对象；但磁盘里面有一个文件系统的目录树，这棵目录树就被放到了系统里面的 `/mnt` 下面。这是我准备的另外一个目录：`fs-root` 里面有一个 `e1000.ko`，是网卡的驱动；还有一个 init——另外一个 init，它会打印一句 `jyy 的 Minimal Linux`。

先把这个文件系统 umount 掉，`/mnt` 下面就空了。然后退出 shell，倒数 3、2、1，它又花了一些时间——你看它启动了网卡。这时候有一条日志叫 `goodbye QEMU console`：我的 console 不能用了，但是另外一样东西可以用了。

我们回到了最早的时候和 MINIX 一样的处境。这是 QEMU 模拟出来的一个 VGA 设备，一个显示设备。刚才我们一直是在跟一个串口对话——像那个调试串口，`/dev/console` 就是它——而那个 VGA 屏幕一直是黑的（如果你们留意到，我有几次不小心切到了中间，那里一直处于什么输出也没有的状态）。但是现在有了 `/dev/tty1`。如果我 `echo hello` 到 `/dev/tty1`，就会显示在这个屏幕上。

所以这是 Linux 用驱动程序画出来的，每一个像素都是画出来的。屏幕上有我打印的 `jyy 的 Minimal Linux`，这个 Linux 就是一个真正可用的 Linux。

这个 init 是操作系统在 initramfs 的最后阶段执行 `pivot_root` 系统调用之后换过来的：换一个 init，换一个文件系统。因为这个文件系统现在是空的，所以我还是需要把 BusyBox 里面的那些 `ls`、`grep` 全部都再创建一遍，再把 procfs、sysfs 这些东西再创建一遍，`/dev` 里面也要重新创建一遍。

然后我在这里配置了网络：安装一个 e1000 的模拟网卡驱动，设置一个 IP 地址。于是我可以干这样一件事——在这个 Linux 里，这是一个虚拟机，但理论上说它在一个真实的计算机上运行也没有任何问题——我在这里启动一个 httpd，在 8080 端口。

你明显会发现这个终端打印的速度变慢了：因为它是一个图形设备，是一个一个像素点画出来的，它不再是刚才那个硬件模拟出来的字符接口，它真的模拟了一个图形的设备。这时候网络应该也能正常工作了，因为网卡 `link becomes ready` 了。

我的 Makefile 里还留了一个彩蛋：我用 QEMU 做了一个端口映射，把虚拟机里面的 8080 映射到外面的 8080。这也意味着，理论上说我在外面访问 `localhost:8080`，就能访问到虚拟机里面的网页。

先看到一个 404，这是对的，因为我没有 `index.html`。那么我的虚拟机里面有什么呢？它的文件系统里面有一个 `init`。所以理论上说，如果我实现得正确，访问 `localhost:8080/init` 就应该能看到这个 init 脚本——我看到了。这证明我的这个 Linux 真正点亮了。

### 应用视角的操作系统

我们经历了一个非常漫长的过程，所有脚本你都看到了：从最早的 initramfs 里面只有那点东西，到可以在 initramfs 里面加载驱动、做 Linux 允许的系统调用的事情——都是系统调用；从第一步，到 pivot_root，最终到可以在里面启动一个 httpd，甚至从外面访问到里面的网络服务。我真的在浏览器里看到了那个网页。

> **结论**：从第一个进程开始，之后所有的事情都是用系统调用实现的。这就是系统调用这个抽象真正厉害的地方。

这就是应用视角的操作系统。绕了这么久，回到基本原理上：操作系统一定会到达一个确定的初始状态，这个绝对确定的初始状态是由 CPU reset 决定的；然后 firmware 会把操作系统加载好，操作系统会把第一个程序加载好；从第一个程序的初始状态开始，剩下的整个世界就只有一个东西——操作系统对象和 API。这就是操作系统给应用世界提供的一切。

你可以想象这件事还是挺惊叹的：你拿起一个 Android 手机，下意识地打开抖音的时候，再想到操作系统课上我说过的——它从 initramfs 开始，之后你在抖音上看到的每一个像素点，都是系统调用实现的。这么想一下，还是有一点点惊叹的。

从 Unix 到 MINIX 到 Linux，我们看到了这个历史是怎么走过来的：从最早的一个 27 行汇编代码的 fork，到 MINIX，到论战，到 Linux，到今天一个成熟稳定的状态。一个很精彩的故事。但它其实没有结束，因为精彩的故事在系统调用的对象和 API 之上还在延续，没有停止。在 Linux API 上没有什么是不能做的：大语言模型、Agent、抖音、淘宝，这些东西全部都是在 Linux API 上做出来的。

### 操作系统自己什么都不是

我最后要稍微讲一点的，是应用生态。

光有操作系统的 API 是不够的。这个操作系统的 API，很大程度上是和使用这个操作系统的应用程序一起演化的：应用程序发现操作系统里面的性能不够，操作系统就会给它一个新的 API、性能够的 API，或者一个新的文件、一个新的对象；它们就这样共同进步，最后变成了今天操作系统的样子。所以其实是应用生态成就了操作系统的繁荣。操作系统自己本身什么都不是，它就是一个 API。但因为厂商、个人开发者，每一个人在 GitHub 上每天都在发布新的应用，所以操作系统其实不仅仅需要实现这一套 API，还需要一套核心的工具集来支撑这些厂商和个人开发者——这些也是操作系统的一部分。

```text
┌────────────────────────────────────────────────────┐
│ 应用生态：厂商与个人开发者每天发布的新应用          │
├────────────────────────────────────────────────────┤
│ 核心工具集：shell、基本工具、3D 库、图形库……        │
├────────────────────────────────────────────────────┤
│ 运行库：libc                                        │
├────────────────────────────────────────────────────┤
│ 内核 API：系统调用与操作系统对象（最小的一层）      │
└────────────────────────────────────────────────────┘
```

从下往上看：内核 API 是最小的一层，往上依次是运行库、核心工具集和整个应用生态，每一层都长在下面一层之上。

#### 狭义的操作系统与广义的操作系统

所以操作系统有狭义和广义之分。我们讲操作系统原理，最主要的还是讲操作系统 API。但当我们谈论操作系统的时候——比如问"为什么中国没有国产的操作系统呢"——我们很多时候谈论的是这个生态。它需要一套核心的工具集：基本的运行库 `libc`，然后什么 3D 的库、图形库，这就麻烦死了。这个核心工具集里面一个安全漏洞都不能有，一个安全漏洞就把你整个系统都拖垮。除此之外还有各种辅助工具要安装、版本管理、系统管理，这都是代码。

Linux 内核看起来好像一两千万行代码，已经是个庞然大物了，但相比于这个应用生态来说根本就是一点点：一个复杂的业务代码很有可能就是上千万行的，一个应用程序就是上千万行。然后它们之间还要互相协作。

#### 软件是怎么发到用户手里的

这个应用生态也不是一下就变成今天这个样子的。在早期 DOS 的时代，我们还是用软盘和光盘发布软件，那个光盘的 CD Key 就写在光盘上，或者一张纸条贴在那个光盘里面，所以很容易破解。进入互联网时代以后，我们有了更好的应用生态分发方法：App Store、APT、RPM，Python 的 packaging index、NPM、Hugging Face、Ollama，都是这种内容分发的生态。

| 时期 | 分发方式 |
| :--- | :--- |
| 早期 DOS 时代 | 软盘、光盘；CD Key 印在盘上或贴在盘里的纸条上，很容易破解 |
| 互联网时代 | App Store、APT、RPM、Python packaging index、NPM、Hugging Face、Ollama |

我举个我自己的例子：现在我树莓派上跑的这个 Debian 系统。Debian 说，Our mission is creating a free operating system. When we use the word free, we're not talking about money.——不是钱的事情，不是免费的操作系统，是自由的操作系统，是 software freedom：所有的软件都是可见的，每一行源代码你都能看到、你都能理解，你也可以为它做出贡献。所以我觉得 Computer Science 能够发展得这么好，也有很大一个原因是有 Linus 这样的人：那个天才少年不藏着掖着，他说我有一个好东西，我就迫不及待地想要和别人分享；每一个人看了别人分享的好东西，自己做出好东西以后，也自然而然愿意和别人分享。

1998 年的时候 APT 被发明出来——注意这是 1998 年。如果你想装 Firefox，你只要 `apt-get install firefox` 就装好了。你看苹果的 App Store 是什么时候才出来的？200 几年的时候才有 App Store。而 1998 年就有跨越时代的 Advanced Packaging Tool 了。

APT 有一整套开源供应链的管理流程：你的包从不稳定的 unstable 分支——就是 GitHub 上那些每天你都往上面提交的代码——一点一点被合进 testing 的分支，然后有一些志愿者就愿意尝试；愿意尝鲜、愿意获得更新的版本和功能的人可以先用，然后慢慢一点一点进入稳定的状态。

后面还有一些细节，比如说软件的生态到底是怎么构建的：一个软件包——你随便找一个，你的系统里面可能也有好多 deb 包，不管是 RPM 还是 deb——你都可以让 AI 直接把这个包解开，然后问它：安装这个软件包到底意味着什么？你就能知道这个应用生态是怎么完整地构建起来的。我觉得这是一个很有意思的话题：它是操作系统上面的对象和系统调用，但它从上面长出了完整的应用生态的世界。
