## 从块设备到目录树：文件系统 API 的第一层抽象
> 对应块：BLK47 | 覆盖分集：P24上 | 块标题（分集名）：《文件系统 API (1)（上）》

存储设备的抽象其实非常非常简单。虽然一个 bit 的存储本身可以很复杂——它可以是一块 SSD，可以是一块 HDD，它们上面甚至各自都有一台完整的计算机系统：我上次拆硬盘的时候你们也看到了，板子上真的躺着一颗芯片；拿显微镜去看 SSD，也能看到芯片；连那张小小的 TF 卡里面，都有一颗 ARM 芯片在跑。

但整个 I/O 设备最后被抽象成了极其简单的接口：块设备（block device），一个 `read`，一个 `write`。实际上还留了另一个口子，用来等数据真正落盘——你可以去查一个数据到底有没有被正确地写进磁盘，而不是停在缓存里、或者停在 SSD 自己的 RAM 上。不过只要不考虑数据一致性，主要就是读和写这两个动作。

### 一个 bit 的存储有多复杂，接口就有多简单

因为它是 block device，按块来访问，为了省空间、省电路，我们一般会把比较多的 bit 打包在一起，比如 512 个字节，或者 4K。设备一次就 `read` 一个 block、`write` 一个 block，剩下的复杂性你就不用操心了。

设备终究要通过总线接入计算机系统，然后操作系统里有一份驱动，就可以 read block、write block。那我们能不能让进程直接去用这个驱动？先看看系统里到底有哪些块设备，`lsblk` 一敲，能看到一堆 `mmcblk*`：

```text
mmcblk0      整张卡（TF 卡完整的字节序列）
├─ mmcblk0p1 第 1 个分区，本身也是一个 block device
└─ mmcblk0p2 第 2 个分区，本身也是一个 block device
```

一个驱动器可以有好几个分区，分区信息写在最前面的 metadata 里：第一个分区有多大、第二个分区有多大。最左边那一列标明，它们每一个都是块设备。而块设备是可以 `mmap` 到进程地址空间里的，映射完之后就能直接当内存来访问。

但显然，让进程自己去 `open`、`mmap`、`lseek` 一个存储设备，不是一个好想法，会乱套——访问的时候就会冲突。如果你把一个很大的字节序列或者一个块设备看成一个数据结构，那你们做 `malloc` / `free` 的实验就已经告诉过你们：要在多个进程之间共享一个数据结构，是一件非常麻烦的事情。所以我们要再加一层抽象，把这些存储设备管起来，这一层就是大家其实很熟悉的**文件系统**。

> **提示**：这一讲谈的是人类使用的文件系统 API，也就是 Unix 早期发明出来、给我们用的那一套。程序和 AI agent 用的文件系统 API 放到下一次课——那套东西更少见，但同样是构建现代计算机系统非常重要的基础。

### 内存已经做过一遍：从虚拟地址空间到虚拟磁盘

接下来从数据结构的角度讲"怎么从块设备走到文件系统"。因为在我们的计算机系统里，把存储设备做抽象这件事，其实**已经做过一次了**，那就是内存。

DRAM 就是内存条，上面有好多个内存颗粒。它的模型你可以理解成一个 byte array：两张 8G 的内存条插到主板上，你就得到了 16G 内存，也就是从 0 到 16G 的一个物理地址空间。不过内存挂在总线上传输的时候，一般来说都是 burst 传输——一次可以连续送好几个字节，可以不停地往总线上送数据，所以内存本质上也有一点像一个 block device。虽然细节和 SSD 一个 16KB 的 page 不太一样，但访问特性有点像。

再往后就是我们学过的 memory hierarchy：在 CPU 里，你一般不会直接访问这样的物理内存，中间要经过缓存、虚拟内存一层层才能到物理内存。而 DRAM 之上，CPU 里有 MMU，所以每一个进程、每一个线程看到的都是一个虚拟的地址空间。这个虚拟地址空间就像一副 VR 眼镜：戴上由 MMU 配置好的这副眼镜以后，你看到的就是一个可以任意摆布的地址空间——可以把任何一个物理页映射到某个虚拟页上，甚至可以在两个进程之间共享同一个虚拟页面的映射。在这之上，我们得到的是一个平坦的地址空间；在平坦的地址空间之上，我们构建了 `malloc` 和 `free`，那是你们做的实验；在 `malloc` / `free` 之上，又可以构建很多数据结构——在 Python 里实现一个 list、set、dictionary，基本上都是基于 `malloc` / `free`。所以内存这一侧的抽象阶梯，已经走完了。

存储这一侧呢？存储设备和内存一样，都是 byte array，所以做抽象的时候，很自然想到的就是一个**虚拟的磁盘**。也就是说，如果我们要在进程之间共享和管理存储设备，字节序列就是非常自然的底层，最起码要做的一层抽象是"磁盘到虚拟磁盘"。转了一圈你会发现：虽然在讲 persistence，但其实又回到了 virtualization 里做过的事情——虚拟内存对应虚拟磁盘，而这个虚拟磁盘就是**文件**。

现实世界里的文件大家更熟悉：一个活页文件夹，里面夹纸，它的定义就是"文字符号固定于纸张等载体上的信息记录"。它就是一个数据，那么在计算机世界里自然表示成一个字节序列，一个 vector of characters，一个 byte sequence。

文件和自己脚下的磁盘不一样：磁盘买来多大就是多大，128GB、1TB 定死在那里；虚拟的磁盘却可以变长——有的文件很小，有的很大。你存一个代码文件，绝大多数时候就是几 KB 到几十 KB；存一部电影，它就很大。所以文件是一个**变长**的抽象，还可以改变它中间的值，像擦掉以后重写。这个抽象支持 `read`、`write`、`lseek`、`ftruncate` 这些系统调用，通过文件描述符来访问它。不管是 `hello.c` 还是 `a.out`，都用同一组 API 来访问。

| 层次 | 内存世界 | 存储世界 |
| :--- | :--- | :--- |
| 物理介质 | 主板上的 DRAM 颗粒、内存条 | HDD / SSD / TF 卡这类块设备 |
| 访问特性 | 是 byte array，但总线上按 burst 连续传送 | 一次读或写一整个块，512 B 或 4 KB |
| 中间的硬件 | MMU 与页表 | 设备驱动 |
| 虚拟化的结果 | 每个进程一份平坦的虚拟地址空间 | 每个文件一份"虚拟磁盘" |
| 之上的容器 | `malloc` / `free` | 文件系统（目录树） |
| 再之上 | list / set / dict 等数据结构 | 你放进去的任何信息 |

> **结论**：块设备接口被刻意做得很薄——读一块、写一块，外加一个等落盘的口子。剩下的复杂性全部上移：先把它抽象成变长的虚拟磁盘（文件），再解决"这么多文件怎么管"的问题。

### 从 PID 到图书馆：为什么要一棵目录树

今天真正要讲的，是我们怎么样管理整个系统里面各种各样的文件。

先看一个例子。有一个进程，它就有一个虚拟的地址空间；如果我要入侵另外一个进程的地址空间——还记得我上课讲过的那个游戏修改器吗——那我怎么确定那个进程的地址空间？我打开的是 `/proc` 下那个 PID 目录里的 `mem`。这就是文件系统里的一个文件，或者说操作系统里的一个对象：访问进程、访问线程、访问这些对象的时候，总得有一个命名机制。

进程用的命名机制是 PID，你们实现 `pstree` 那个实验的时候，跟 PID 打过很大的交道。但 PID 并不是一个非常好的抽象，因为它就是一个数字。对程序来说可能没问题——`/proc/<PID>/mem` 这样用挺好；但对人类来说就非常不友好：你看到的就是一个随机的、几百万几十万的很大的数字，你根本不知道它是什么意思。所以写那个游戏修改器的时候，其实是我在命令行工具里跟一个名字，比如 `DOSBox`：程序去 `/proc` 里遍历所有的进程，找到名字是这个的，再拿到它的 PID（用了一个 `pidof` 的能力）。

> **易错点**：PID 只是"最小可用"的唯一索引，不是给人用的命名。如果文件系统里所有的文件也都只给一个 FID，理论上也能跑起来——但你想想，以后所有的 `open`，第一个参数不再是 `a.txt` 这样的路径，而是一个 `176358`，那对人是没法用的。

所以很自然地，文件系统要参考我们在现实生活中怎么管文件：建一个图书馆。图书馆用的是中图法分类，A、B、C、D 一路排下来，比如计算机类的书在 TP 那个区，你找到对应的书架就行了。而且哪怕你没有明确目标，只是今天逛图书馆想找本小说，你也可以顺着这个分类一层一层往下找：先进文学区，再进文学区里的某个子区，最后找到那本书。这背后是**信息的局部性**：相关的东西放在一起，同一个书架上那些书的关联相对比较紧密，于是就形成了一个层次性的索引结构。

映射到计算机里，就是你非常熟悉的那个动作：点开 C 盘，点开一层，再点开一层。这就是目录树。而在任何一个目录里，你都会看到一个叫 `.` 的目录和一个叫 `..` 的目录——`. ` 代表当前目录，`..` 代表上一级目录。

### 目录树的数据结构：点、点点与隐藏文件

所以本质上，图书馆那套索引在文件系统里实现出来，不只是一个索引，而是一棵树状的数据结构。来看 `/` 下面的 `home`：

```text
          /
          │  "home"
          ▼
      [ home ]
          ├─ .       指向自己   ──▶ [ home ]
          ├─ ..      指向上一级 ──▶ /
          ├─ a.txt   普通文件
          └─ .hello  以点开头，默认看不见
        （. 和 .. 只在 ls -a 时才列出来）
```

`ls -al` 的输出看起来是一组普通的条目，但 `.` 会悄悄地指向当前这个目录，`..` 会悄悄地指向上一级目录。所以更准确的写法是：`/` 有一条叫 `home` 的边指向一个真实的目录，这个目录里又有一个叫 `.` 的条目指向它自己、一个叫 `..` 的条目指向它的上级，另外还挂着 `a.txt` 这样的文件。这就是 Unix 的目录模型，把它理解成数据结构，后面就很好办了。而刚接触 PC 的时候你会觉得它就是"目录下面有一堆文件"——因为你看不到 `.` 和 `..`，但实际的数据结构是这样的，也没有问题。

早期大家不停往这个小设计上扩展功能，比如它为什么要有 `.` 和 `..`？因为它把几个功能融合在了一起。Unix 认为所有以 `.` 开头的文件都是一种**隐藏文件**：`ls` 的时候你是看不到的，只有 `ls -a` 才能看到 `.`、`..`；同理你创建任何一个文件，比如 `.hello`，列表里也看不到它，但它完全存在于文件系统里。

操作系统看到的是一个包含 `.`、`..`、`hello`、`.hello`、`a.txt` 的目录结构，忽略这些条目只是命令行工具在偷懒。BusyBox 里 `coreutils` 下的 `list.c`（也就是 BusyBox 的 `ls`）非常粗暴：它用 `readdir` 遍历目录，每读出一个条目就判断 `d_name[0]` 是不是 `.`；是 `.` 的话，再看有没有 `-a` 这个选项，如果没有 `-a` 就直接 `continue`。一行代码就实现了隐藏文件的机制。

```c
/* 示意：BusyBox ls 中隐藏文件的判定逻辑 */
if (entry->d_name[0] == '.') {
    if (!(opt & OPT_A))   /* 没有 -a 就跳过 */
        continue;
}
```

> **提示**：隐藏文件不是文件系统给的权限或属性，只是"以点开头"这条约定加上 `ls` 的一行过滤。这也是为什么 `.`、`..` 能顺带把"引用自己和上级"和"隐藏"两件事合并在一起。

文件系统看起来简单——因为你们一直在用它——实际上是一个极其强大的抽象。我可以把我所有的数据都文本化：我是谁，我最近干了什么，和我相关的所有文档、specification 都放进来；你们还可以把学生手册放进来，把每天上课的轨迹放进来，然后每天晚上打开 Claude，或者干脆设一个 cron job，每天问一句"我今天会被开除吗"——因为学生手册上写着旷课到一定程度就会被开除。用文件系统以分层的方式把这一切存起来，它就能管理世界上一切的信息，而且很容易找到。这就是图书馆级别的能力。

### 世界上到处都是目录树

再往后想一步：任何一个存储设备都对应了一个文件系统，或者说对应了一棵目录树。刚才 `lsblk` 里那个 `mount points` 就说明了这一点——`mmcblk0p1` 和 `mmcblk0p2` 各自对应一棵目录树，而且它们都在这台机器的系统里。任何一个块设备，比如 `/dev/nvme0n1p2`，都对应着从根一直到 `a.txt` 的这样一棵很大的树。

于是操作系统设计者立刻要面对一个问题：这世界上有这么多的目录树，怎么管理？不只是本地的设备——你的 U 盘本质上也是一棵目录树；任何一个网络网盘也是一棵目录树。我办公室的机器挂的是 WebDAV 上的 Nextcloud，那台机器一直录像，跟同学开完组会，录像就自动同步到 WebDAV 网盘里。虽然还没把这一部分接进我的 agent，但我觉得这是一个很好的方向，它可以自动管好我生活和工作的方方面面。

而你们其实已经很习惯了：U 盘插进去，文件管理器里就多一个盘符，点开 E 盘就是一棵新的目录树。Linux 里更简单，插上 U 盘，桌面上的目录列表里就多一个目录，双击进去正好是 U 盘的内容——那个目录通常就在 `home` 下某个 `Desktop` 文件夹里，U 盘对应的目录树一下子就被放到了这个位置上。这些其实都是操作系统搞出来的。

以 Windows 为例，它有很多你看不见的特征。Windows 其实有一个所有操作系统对象的根，就叫 `\`：

```text
\                                  所有操作系统对象的根（cd \ 进不去）
├─ \Device\HarddiskVolume1         设备对象
├─ \Driver\NTFS                    驱动对象
└─ \\                              网络入口
   └─ \\server\share  →  \Device\LanmanRedirector\server\share
```

但这个 `\` 你是 `cd` 不进去的：在 PowerShell 里 `cd \`，你得到的是 C 盘的根目录，或者当前工作盘符的根目录。可是如果你用 API 来访问，`\` 就是所有操作系统对象的根，可以一级一级引用 Windows 里的一切对象，比如 `\Device\HarddiskVolume1`、`\Driver\NTFS`。这里面有很多神奇的东西，比如 `\\`：通过 `\\192.168.3.1` 可以访问网络上的另一台计算机，`\\server` 下的 `share` 会被转义成 `\Device\LanmanRedirector` 下的 `server` 下的 `share`。你可以用 `CreateFile` 这样的 API 去创建或打开这样的设备文件，拿到一个 device 的 handle——你可以把它理解成一个文件描述符。这套机制是从最早 DOS 时代的历史遗留延续下来的。

那为什么你们的系统盘是 C 盘？因为 A 盘和 B 盘就是之前给大家展示过的软盘：第一个软盘驱动器是 A 盘，第二个是 B 盘。在没有硬盘的时代这就已经定下来了，所以等硬盘出现的时候，只能往后放，成了 C 盘。而且你看到的 C 盘只是 Windows 让你看到的：从整个操作系统的对象根来看，你的 C 盘是 `\??\` 下的 C 盘。`\??\` 是 per-user 命名空间——两个不同的用户可以各自有一个 `\\server\share`，他们的 `server` 可以不是同一台，也就是同一个路径可以解析成两个不同的东西。Windows 在演化过程中，为了向前兼容不停地打补丁，这些东西普通用户都看不到；只有当你要写 Windows 上的内核代码时，才需要去折腾这些。普通用户很开心，他只看到 C 盘下面有一堆东西。

### mount：把一棵目录树贴到文件系统里

无论 Windows 还是 Linux，都需要一个 API：我 U 盘上有一棵目录树，我的网络上有一棵目录树，我希望把这棵目录树放进我的文件系统里，让它可以被一级一级索引找到。这个过程你们都经历过——插上 U 盘，桌面上就多了一个U盘目录。

回想最小的 Linux 启动：我可以构建一个最小的 Linux，里面甚至只有一个 `minimal.s`，一段我自己写的汇编代码。直接编译运行它可能要几秒钟，因为在 ARM 上模拟 x86，性能损失比较大。Linux 启动之后只有一个 initramfs，它不认识任何文件系统，里面就只有 initramfs 自带的东西；`minimal` 执行完，系统直接 panic 了。那时候文件系统里什么都没有，只有那个 `minimal` 和一个 `/dev/console`。

这就需要执行一个操作系统的 API，把某个真实磁盘上的目录树挂载到文件系统的某个位置上，这就是 `mount`：

```text
   块设备 /dev/sr0 里的目录树             进程看到的目录树
     /（设备自己的根）                     /（系统根）
      ├─ autorun.inf                        ├─ home
      ├─ README                             │   └─ Desktop
      └─ SETUP.EXE                          │        └─ cdrom
                                            └─ ...
             │                                        ▲
             └───────────  mount  ───────────────────┘
        把设备上的整棵树贴到目标目录；
        贴好之后读写该目录，都真实作用于那个设备
```

`mount` 的行为就是把一个块设备上面的目录树，完整地贴到文件系统的某一个位置。贴过来以后你就可以正常访问：比如贴到 `/home/.../Desktop/U盘`，那你就能在这个路径下面读 `a.txt`；你对文件的写入，也会真实地反映到那个设备上。

> **提示**：`mount` 在系统调用层面要求一个块设备。记住这一条，后面讲"挂载一个文件"时，它正是那个必须被绕开的约束。

### 现场：Win98 光盘、sr0 与 ioctl

我这次带了一个很有意思的东西：一个光盘驱动器，和上次展示过的那张 Win98 光盘。把它插到电脑上，这时再查看系统里的块设备，就多出来一个 `sr0`。

遇到一个未知的东西，总是先让它给你补一些背景，这是好习惯。而我现在觉得，只要你问问题，AI 就可以给你惊喜，因为这个世界上的新知识实在太多了。在以前读手册的时代，这真的是不可能的事情。它说：当前槽中插入了一张 Win98 的光盘，ISO 9660。这是一种文件系统的格式，相当于按照某一个特殊的结构体来排布——比如有一个 `struct iso9660_primary_descriptor`，它要求在某一个地方有一个 `CD001`。你确实能看到它在 8000 这个偏移上有 `CD001`，这就是这个数据结构的标示。

这和内存里的树是一个道理：内存里要有一个数据结构，总归要有一个根节点，根节点可能带 left、right 两个指针；同样地，在这个字节序列里，我们知道一个设备就是一个 byte array，而这个 CD-ROM 的 byte array 里有一个 `CD001` 字符串，通过它就能定位到"在正确的位置上有一个正确的数值"，从而认定这是一棵什么样的树结构，然后调用相应的代码来解析它，把它变成一个目录树放到文件系统中间。想使用这个驱动器，就要用 `mount`。

第一次 `mount /dev/cdrom` 失败了，再试一次才成功，而且给了一个 warning：`write-protected, mounting read-only`。这是因为光盘没办法写入——它不是一个可写的块设备，所以只能只读挂载。挂上以后进目录一看：有 `autorun.inf`。这个文件意味着 Windows 看到它就知道你的光盘是可以自动播放的；这也是当年发售游戏的方式——把游戏光盘插进光驱、合上光驱，系统读到 `autorun.inf` 就自动运行 `autorun.exe`。再 `cat` 一下 `README`：全是乱码，因为这是中文版 Windows，Win98 那时用的是中文编码，而当前系统是 UTF-8；做个 `iconv`，从 GBK 转到 UTF-8，就能读到 Win98 的自述文件了。

看那棵目录树还挺有意思：那时候人们对计算机系统的概念，一直到今天都还在延续。

完整的写法要带上 `-t`，同时 `/dev/cdrom` 是一个符号链接，指向 `sr0`。更关键的是 `strace` 一下——这是我们操作系统课上告诉大家最重要的事情之一：任何东西你都是可以打得开的。你知道它有一个行为，比如 `mount` 确实把设备挂到了某个位置，然后你就能知道它是用什么样的系统调用来实现的。答案现在其实也知道，就是 `mount` 那个系统调用。但有意思的是一次失败的 `mount` 给了更多惊喜：

```text
strace mount ...
  ├─ ioctl(...)  先确定它是一个块设备
  ├─ ioctl(...)  再确定它的大小是 306 MB（这张 1998 年买的光盘）
  ├─ ioctl(...)  发现 CD-ROM drive status 是"无盘"
  ├─ 反复尝试去读 ──▶ 读不到
  └─ close(...)
```

设备除了读写以外，所有和设备控制相关的 API 全部塞进了 `ioctl` 里。这张光盘确实放了很多年——Win98 就是 1998 年，光盘也买于 1998 年——所以它读不出来。再 try again，还是无盘。

最后还有一个有意思的命令：`eject`。它把光盘推出来，就相当于你按一下光驱上那个键。合上以后，在命令行里运行 `eject`，它也自动推出来了；甚至可以用它做一个往复推拉的小玩具。而 `eject` 用的系统调用，答案也是 `ioctl`：

```text
strace eject ...
  ├─ open("/dev/sr0", ...)                  打开设备
  └─ ioctl(fd, CDROMEJECT)                  弹出光盘
```

所以你在操作系统里其实看不到任何魔法。某种意义上，它做的所有事情都是简单的：都是有一些 well-defined 的 API，要么像 `eject` 这样由驱动帮你 take care，要么就是块设备读写这类基本动作。这些东西加起来，就变成了你在操作系统里看到的一切——从无到有的一棵目录树，以及一个 `mount` 系统调用。

### 挂载一个文件：loopback device

`mount` 不只可以挂载一个块设备。实际上 `mount` 还可以挂载**一个文件**。想想看，我们是可以有虚拟磁盘的：下一个实验里，你们会从网上下载一个这样的文件镜像，然后把它挂载起来，挂完你会发现里面有好多图片。那个实验模拟的就是这样一件事：你有一个磁盘，里面存了好多图片，就好像你相机的 SD 卡，而这张 SD 卡被格式化过了，你要把里面的图片重新捞回来。这完全办得到，具体怎么办我在后面讲文件系统实现的时候会细说。

但这里有一个矛盾：`mount` 系统调用必须要求一个块设备，它只能把一个块设备里面的文件系统挂到某个位置；而一个文件就是一个文件，它不是块设备。最早的 Linux 肯定不支持挂载一个 `.image` 文件，后来支持了，靠的是 **loopback device**：

```text
   fs.img（一个普通的文件）
      │
      │ ① open(fs.img, 只读) → 探测出这是 vfat 文件系统
      │ ② open(/dev/loop-control, 读写)
      │ ③ ioctl(LOOP_CTL_GET_FREE) ──▶ 0
      │       （再要一次给 1、2、3、4…；失败返回 -1，所以可以建很多个）
      ▼
   /dev/loop0  —— 一个块设备，
      │           它对块设备的读写全部委托给 fs.img 的读写
      │           （调用那个文件的 struct file_operations）
      │ ④ mount("/dev/loop0", 目标目录, "vfat", ...)
      ▼
   目标目录下出现整棵目录树
```

也就是说，我们先让操作系统创建一个对象叫 loopback device：它是一个 device，表现出块设备的样子，但它所有对块设备的读写都会 delegate 到某个文件的读写。文件在操作系统里有自己的 `struct file_operations` 实现，loopback device 的读写就直接调用这个文件 `struct file_operations` 里面的读写；而这部分本身是文件系统代码，最后可能再转到真实的块设备上。正是因为有了 loopback device，你就可以把这个东西挂到文件系统的任何一个地方。挂载完成之后，`lsblk` 里会多出一个 `loop0`。

> **提示**：文件系统的探测发生在应用侧。"操作系统会创建一个 loopback device"这句话是对的，但它到底意味着什么，写在 `strace` 里——创建这个对象本身，就是一个 `ioctl` 调用。

如果想让 AI 帮你真实地分析一遍，就让它读完整的 `strace`。第一次演示时我忘了 `unmount`，所以再 `mount` 一次时它发现已经挂载过了，直接结束，看不到正确的过程；`unmount` 掉、再来一次，就能看到完整的流程：

1. `mount` 命令先以只读的方式打开这个文件，探测它是什么文件系统。这是应用侧做的事——在系统调用层面你必须告诉它是什么文件系统，操作系统不负责探测，如果它认为这个文件系统不合法，会直接拒绝这次 `mount`。这里探测出来是 vfat。
2. 接下来分配 loopback device：打开 `/dev/loop-control`，以读写的方式打开。
3. 对它做 `ioctl`，用 `LOOP_CTL_GET_FREE`：第一次拿到的编号是 0，再要就是 1、2、3、4，失败会得到 -1。拿到编号以后，就可以访问 `/dev/loop0` 了。
4. 把镜像文件绑定进来，然后执行一次真正的 `mount`——这时候它已经是一个块设备了，就可以被挂到文件系统上。

这就是整个系统调用的流程，没有什么理解不了的，你问 AI 就可以了。顺便说，那次 AI 读了完整的 `strace`，连命令行里为什么能显示彩色的字都解释了；它的知识真的很丰富，如果你在 prompt 里让它稍微发散一些、更多地让它变成一个老师来教你，你真的可以从它那里学到很多东西。我每一次跟它交流都在学到新的东西，所以我也愿意在上课的时候稍微停下来，花那么两分钟看一眼。系统里如果装了 snap 之类的包管理，`lsblk` 里同样能看到很多 loop device。

### 根目录长什么样：FHS 是大家的共同语言

Linux 有一个标准叫 FHS，Filesystem Hierarchy Standard：`/usr` 是什么、`/home` 是什么、`/mnt` 是什么，都是标准里规定的。虽然这个标准现在显得有点过时了，尤其是当你的设备越来越多的时候，但依然有这样的标准会让你感到比较安心、比较舒适。

举个例子，macOS 的内核实际上也是 Unix，但它就不遵循 Linux 的 FHS。如果你遵循它，你会得到一个统一的体验。目录树相当于图书馆，FHS 就相当于图书馆里中图法的那套编号规定：里面具体放什么——比如你的 Desktop 里存什么——那是你自己决定的，但整个文件系统的根最好长成这样。这是大家的共同语言。

### 从 initramfs 到增删改查的 API

那这棵目录树到底是怎么来的？Linux 启动的时候一定有一个 initramfs，它会去找一个启动设备，然后把这个设备的根挂载上去；挂载完之后再执行一个叫 `pivot_root` 的系统调用，或者 `switch_root` 那个命令，就得到了这样一棵目录树：

```text
   内核启动
     │
     ▼
   initramfs —— 内存里的最小根：只有一个 minimal 程序和 /dev/console
     │  找到启动设备
     ▼
   mount 启动设备 ──▶ 得到真实的根目录树
     │
     ▼
   pivot_root / switch_root —— 把真实根搬到 /，丢掉 initramfs
```

有了这棵目录树，很自然地就有各种各样的 API，那就是增删改查的 API。既然我有一个目录树，那我一定会提供：创建一个新的目录、删除一个目录、遍历一个目录。这些系统调用大家其实也都用过，比如 `strace mkdir 1`，你马上就能找到它对应的系统调用：

```text
mkdirat(AT_FDCWD, "1", 0777) = 0
```

它就是在当前目录下创建目录 `1`，返回 0 表示成功。

除了这些系统调用，命令层面还有一些语法糖，比如通配符：用 `**/*` 这样的写法，就可以一次匹配一批符合模式的路径。

## 文件是带名字的指针：链接、属性与文件系统的幻觉
> 对应块：BLK48 | 覆盖分集：P24下 | 块标题（分集名）：《文件系统 API (1)（下）》

### 把目录翻个底朝天：globbing 与它背后的系统调用

「把任意一个目录、不管下面套了几层，里面的某个文件给我找出来」——比如把藏在各处的 `.config` 统统翻出来——这类 API 是非常有用的。

今天 AI 的几大工具就是 read、write、bash、grep，再加上一个 glob。你经常看它用 glob 在文件系统里按关键字去找它认为相关的文件。

但 globbing 这件事本身是 bash 的功能，不是系统调用。所以如果你直接去

```bash
strace echo /etc/*/*
```

是看不到任何 globbing 过程的：bash 早在把命令交出去之前，就已经把 pattern 展开成了一串具体的参数贴进去，`echo` 收到的本来就是展开后的路径列表。想看清楚 globbing 到底用了哪些系统调用，得把它包进 `bash -c`：

```bash
strace bash -c 'echo /etc/*/*'
```

这时候你会看到大量的 `open`（准确说是 `openat`）和 `getdents64`。`getdents64` 就是 `readdir` 背后的那个系统调用——把目录里的条目一条条读出来。所以整件事说到底，还是文件系统上的增删改查。

所有基于文件系统的工具都是同一个原理。比如你们喜欢的 fuzzy finder，`fzf`：它和几个命令联合使用，你交互式地选一个文件，比如选中了 `cloud.md`，它就神奇地把这个文件打开了。这个「Shell 上的小技巧」背后，仍然是那一套增删改查的 API 在支撑。

### 硬链接：同一份数据挂上两个名字

既然文件系统就是这么一个数据结构，那回头再看一个事实：**每一个文件，实际上就是一个带名字的指针**。没有人阻止我们做这样的事——我现在有一个叫 `a.txt` 的东西，我可以再创建 `b.txt`，让 `b.txt` 也指向同一个对象。

这件事我们其实早就见过了，只是没往这个方向想：`.` 和 `..` 就是这么实现的。同一个对象，可以有指针指向它自己（`.`），它的每一个孩子里又都有一个指针指向它（`..`）。你有多少个子目录，就有多少个「指向你」的指针。既然我允许这么干，就没有道理不允许我们在同一个文件系统里，让两个普通的文件名也指向同一个文件。

于是就有了硬链接。演示是这样的：

```bash
ln a.txt b.txt      # 背后是 link / linkat 系统调用

echo hello world > a.txt
ls -l a.txt b.txt   # 两个名字的大小都变了
cat b.txt           # 输出 hello world
ls -li              # 带上 -i，两个名字的编号一模一样
```

改成 `hello world` 以后两个名字的大小一起变大，打印 `b.txt` 也是 `hello world`；用 `ls -li` 看，它们后面跟着的那个编号完全相同——说明它们就是同一个文件。而如果这时另建一个 `c.txt`，它的编号就换了，是另一个数。

> **定义**：文件是有 ID 的。我们说进程有 PID，实际上文件也有属于自己的编号（每个文件系统内部唯一），这个编号就是 inode 号。`ls -i` 打印出来的那一列，就是它。

于是「链接」的用途也清楚了。比如系统里可能有同一个运行时库的好多个版本（比如一堆 libc 版本并存，另外还需要一个「当前」的 libc）：你可以复制一份，也可以链接一份。链接一份，立省 100% 的空间。

```text
   dir/
    |-- a.txt ----+
    |-- b.txt ----+---->  inode #191  [hello world]   引用计数 = 2
    `-- c.txt ---------->  inode #264  [c]            引用计数 = 1

   同一个 inode 有 2 个名字，数据只有一份；
   加一个名字，引用计数加一。
```

#### 删除为什么叫 unlink

正因为一个文件可以有多个名字，删除文件时用的系统调用根本不是 `remove`，而是 `unlink`。

一个文件身上要记一个引用计数。你敲的命令看起来是 `rm c.txt`，实际发生的是一次 `unlink`（或 `unlinkat`）：它把这条「名字 → 对象」的链接指针拿掉，然后把引用计数减一。只要还有别的名字指着它，这个文件的数据就不能回收；**只有当引用计数减到 0，也就是没有任何人指向它了，文件系统才真正把这个对象回收掉**。

这就是链接的全部意义所在。

#### 为什么不能给目录做硬链接

硬链接有两个明确的限制：**不能指向目录**（`.` 和 `..` 是例外），**不能跨文件系统**（因为它是文件系统内部的实现机制）。

后一条好理解，前一条值得多想一步：如果允许给目录建硬链接，很容易形成一个环。一旦成环，引用计数这套机制就失效了——环里的每个对象都被别的对象指着，引用计数永远不为 0；可这个环已经从整个目录树上 detach 下来了，你再也不可能通过任何一个路径走到它。理论上它该被回收，但引用计数做不到这件事。

### 符号链接：一个把路径写进内容的文件

硬链接能做的地方，做硬链接当然不错，但它确实不支持目录、确实不支持跨文件系统。这时候我们还想要一个能跨文件系统的、像快捷方式一样的东西。Windows 里就有快捷方式，而且它比你想的要复杂一些。

比如你可以给 U 盘上的一个文件建一个快捷方式。今天这个 U 盘插进去可能是 E 盘，明天插进去就可能是 F 盘了——你电脑上随时可能插入新设备，比如光盘驱动器一插上来就被分配一个盘符。所以每一次插入，U 盘的盘符都可能不一样。而快捷方式可以智能地识别这个文件，即便文件被移动了，它在一定程度上也能帮你找回来。这是一个非常方便人使用的特性，也是一个非常复杂的特性。

Unix 里的对应物是符号链接（symbolic link）。一个符号链接**本身就是一个文件**，你可以把它理解成一个文本文件，里面存了一段话：去哪里找。

```text
   符号链接的处理方式：路径解析时替换

   /home/jyy/symlink  ---内容(一段路径字符串)--->  ./t/a.txt
                                                      |
                                                      v
                                         拼进当前路径，继续往后解析

   和硬链接不同：它不指向 inode，它指向一个"路径"
```

**注意**：操作系统在处理路径的时候，一旦碰到符号链接，就会自动把这个字符串拼到你的路径上，然后继续往后找、往后找。所以内容里写什么都行，写 `../t/a.txt` 也行。

演示一下：

```bash
ln -s a.txt symlink     # 创建一个指向 a.txt 的符号链接
ls -l                   # symlink -> a.txt
rm a.txt                # 注意：执行的是 unlink
cat symlink             # 找不到：路径解析失败
cp a.txt.back a.txt     # 把 a.txt 拷回来
cat symlink             # 又回来了
```

删掉 `a.txt` 的时候，执行的是 `unlink`，它的引用计数减一，但**符号链接这个对象本身还在**，内容还是那句话。所以此时 `symlink` 仍然指向那个已经不存在的路径，`cat` 它会失败——相当于路径解析到头来没找到东西。可只要把 `a.txt` 拷回来，它立刻又能用了。

符号链接没有任何限制：可以指目录，可以指自己，甚至可以指来指去形成一个环。

> **提示**：`ls -l` 里能一眼看出 `l` 类型的符号链接，但硬链接是看不出来的——因为在这个模型里，**每一个普通文件本来就是一个 link**，硬链接并不比别的文件更特别。

硬链接和符号链接的差别，可以放在一张表里对照：

| | 硬链接 | 符号链接 |
|:---|:---|:---|
| 本质 | 同一个 inode 的另一个名字 | 一个内容为路径字符串的文件 |
| 能否指向目录 | 不能（`.` 和 `..` 除外） | 能 |
| 能否跨文件系统 | 不能 | 能 |
| 原文件被删掉之后 | 计数减一，数据仍在 | 链接对象仍在，但解析失败 |
| 能否成环 | 不能 | 能 |

### 用符号链接做一台文字冒险机器

符号链接既然这么随便，理论上你就可以用它来**伪造一个文件系统**。我拿它做过一件更离谱的事：做一个文字冒险游戏，甚至可以说是图形冒险游戏。

游戏脚本是这么个结构：它有一个 `title`（游戏名），然后是一个状态机——每个状态下，你做 1 就走到某个状态，做 2 又走到另一个状态，而这个状态图里是**允许有环**的。文本是让 AI 随便生成的，我也看不懂日文，不重要。

`make` 一下之后，每个状态变成了一个目录，目录里的每个选项就是一个文本文件，告诉你选它会发生什么。而 `状态机` 这个符号链接，指向的是上一级的目录。

于是玩起来就成了这样：

```text
   每个状态 = 一个目录
   每个选项 = 目录里的一个符号链接，指向下一个状态的目录

   ask_milk/          <- 我此刻在这个状态
     |-- 1  --> .../another_state/
     |-- 2  --> ...
     `-- 状态机 --> ../            （指回上一级）

   cd 2  ==>  路径解析把这一跳替换掉，直接落进 2 号状态
   cd .. ==>  退回上一个状态
```

`cd 2` 之所以能当「选 2」用，是因为路径解析会替换——它实际把这一跳换到了别的地方。而 `cd ..` 就是**时光回溯**：退回上一个状态；连按几次 `cd ../../../` 就回到了第一幕。一路 `cd` 进去之后，`pwd` 里会记着你走过的全部历史，因为你就是一级一级 `cd` 进来的。

这个游戏里还有一个 `start.sh`，是我让 AI 写的一个 galgame 引擎，它有动画效果、打字机效果，还 hook 了 `cd` 命令，Tab 键能帮你补全选项。完整效果我放在附录里了。有意思的是「结局」：走到某个状态，路径看着还是那个路径，但目录里已经没有文件了——没有选项可选，它就是结局。演示里按三下就到了结局。

> **注意**：这套东西没有任何神秘的运行时，它就是一个 bash，加上一堆目录和符号链接。

顺带一提，演示里的那些图片是我的一个学生在做的项目生成的。一年前这种效果的连贯性还比较差，现在用一个不那么强的模型也能做到完全 consistency——你能看到图里的草莓酸奶之类的东西前后完全一致。这是一个 generative workflow，也可以拿它来生成 PPT，有台电脑在手，能做的事可能超过你的想象。

### nix：用符号链接伪造整个文件系统

符号链接既然什么都能指，那就可以伪造一个完整的「虚拟目录结构」——看起来是一棵目录树，实体却全都在另一个地方。这是真正有用的设计，`nix` 就是这么干的。

它的做法是：把所有文件都放在 `/nix/store` 下面，命名成 1、2、3、4、5 这种——当然实际上存的不是数字，而是**文件的 hash 指纹**，hash 地址代表了这份文件的身份，再配上名字。于是好处极其直接：

```text
   /nix/store/<hash>-python-3.11.1/
   /nix/store/<hash>-python-3.14.9/
   /nix/store/<hash>-python-3.15-preview/
   ...
              |
              |  用符号链接（理论上硬链接也行）
              v
   /usr/bin/python  ->  指向你这次选中的那个版本
   各种 library      ->  也各自选版本，"凑"出一个环境
```

同一个文件系统里可以同时存着同一个软件的很多个版本：Python 3.11.1、Python 3.14.9，最近还发布了 15 的 preview。你想构造一个环境，甚至在系统启动的时候在启动界面里直接选——我要这几个这几个，它就把这些东西用符号链接拼起来。`/usr/bin/python` 不只可以指向某个 Python 三进制，库也可以各自选版本，凑出一个环境。

这背后是一个很重要的概念差别：

> **定义**：`nix` 是一个 functional 的包管理器，它**只增不减**。而我们现在用的 `apt` 之类，所有修改都是 in place 的：你 install 一个新版本，就得把旧版本卸掉，中间还要跑一个 post-install 脚本。

「只增不减」这件事我们前面讲数据结构的时候见过：当你手里有 random read 加 append-only 的 write，你就可以实现任意的 persistent data structure。想修改一棵二叉树，不是去改它，而是**创建一个新的根节点，只把这条路径上的东西拷一份，其他指针统统指回原来的节点**。append-only 加上这种「路径复制」，就能实现任意数据结构，而且是只增不减的。

映射到包管理上，推论就很舒服了：你可以不断地往上加，而**增加的时候不会对已有的软件产生任何影响**，已有的所有环境都还在。哪天想把它捞出来，你随时可以回滚到一个过去的版本——`nix` 里有一个 listed generations 的概念，一代一代地记着。系统挂了，直接回滚到上一个 generation，**没有任何代价**，因为实际的文件就在那里。新版本也可以随时构建。

现场看它拉一个环境：比如你没有 node，正常得用 apt 装、或者去下载一个什么东西来装。但在 nix 里，它是**从一个已经装好的东西里把环境拉出来**——创建一大堆链接，然后你的世界就有了。而且这个世界随时可以摧毁，因为它不改变 store 的部分。它还有很多语法糖。

不过今天是「版本答案」：你甚至不需要知道 nix 的官网长什么样、不需要知道怎么安装。直接打开一个 AI agent，说「帮我 create shell」，你不需要知道任何概念，就能拿到一个隔离的 Python latest 环境。如果这件事你要重复很多次，就让它存成一个脚本、做成一个 skill，有一万种方法。演示里它给我写了个 `shell.nix`，我没允许它执行完——但你在自己机器上可以完整地得到一次 nix 体验。

所以重要的不是记住创建 symlink 的是哪个系统调用，而是知道**什么事情是能做的**，以及它背后的运行机制大概是什么。将来想起两个印象深刻的例子——一个是 nix，一个是那个 galgame——就够了：符号链接是一个非常有力量的工具，你可以随时构造出一个虚拟的目录结构，而实体放在别的地方。

### 隐藏文件与文件属性

除了目录树的增删改查和链接机制，文件系统里还有一类东西：属性。

还记得最初画目录树的时候，`.` 和 `..` 是怎么出现的吗——虽然它们是指针，但我们实际上给这些目录加了一个属性，叫**隐藏文件**。

在 Windows 里你们都试过：把一个文件或目录点右键、属性、隐藏、确定——它就从资源管理器里消失了。本质上这就是给一个目录加属性的操作。但 Unix 和 Windows 的设计哲学不太一样。

> **提示**：Unix 是 quick and dirty 的：操作系统根本不管这件事。它只是知道 `.` 和 `..` 是当前目录和上一级目录；剩下所有你想隐藏的文件，自己在名字前面加个点，然后 `ls` 这个工具帮你过滤掉，就这样。操作系统其实不区分隐藏与不隐藏。理论上你完全可以改几行 Unix 的代码，让 `$` 和 `$$` 来当隐藏标记，也是 OK 的——只不过现在 Java 开了个坏头，它编译出来的 class 里全是 `$`，于是很多人也开始在文件名里用 `$`。

#### 属性里到底有什么

隐藏当然不是文件唯一的属性。Windows 的属性对话框里还有只读、系统等等好几个 checkbox；Unix 其实也有不少，`ls -l` 就能看到一堆对象属性：

- **inode 编号**：`ls -li` 时那一列。在 `/tmp` 下看到的编号很小，因为那是个临时的文件系统（tmpfs），`tmp-y`，随手创建随手销毁，编号从小的开始发；而我今天新下载的那个文件编号就去到了 264095 这样一个比较大的数，看得出是一个接近于**顺序分配**的 inode 编号。编号本身就是文件的一个属性。
- **设备类型**：`/dev` 下面的设备，可能是字符设备（`c`），也可能是块设备（`b`）。
- **读写权限**：`rwx` 那几组位。
- **类型位**：`ls -l` 第一列的字母，`d` 是目录，`l` 是符号链接，`p` 是 pipe，`c` 是字符设备，`b` 是块设备。

> **易错点**：硬链接在这里是看不到的。因为每个文件本来就是一个 link，硬链接就是一个普通文件，你没法从 `ls -l` 上把它认出来；符号链接才显示为 `l`。

#### 权限位：user、group、other

权限位分成三组，每组三个 bit：

```text
   r w x  r w x  r w x
   |      |      `-------- other  其他所有人
   |      `--------------- group  同一个用户组
   `---------------------- user   文件的所有者

   111 = 可读可写可执行
   101 = 可读、可执行，但没有写权限（中间那位是 0）
```

我们实际改一遍就清楚了：

```bash
whoami                    # 切到 root
touch a.txt               # 文件属主和属组都成了 root
chmod 777 a.txt           # 所有人都可以读写执行
echo hello > a.txt
chmod 000 a.txt           # 权限位清零
```

**root 创建的文件的 owner 和 group 就是 root**，这两个本身也是文件的属性——所以文件属性一下子变多了。改成 `777` 以后，连 other 都能读写执行它；改成 `000` 以后权限被清得干干净净。

在这里你能看到权限位是怎么决定操作系统行为的：root 可以绕过这些检查，所以它照样能访问所有文件，能把可执行位加回去并执行它；而普通用户就完全不行了——不但改不动它的 metadata（因为那属于 root），连**打开它都会拿到 `permission denied`**。

```bash
strace open a.txt         # 直接死在 open 这个系统调用上
```

`strace` 看得很清楚：失败发生在 `open`，返回的是 `EACCES`，就是 permission denied。所以权限也是文件属性的一部分，属性又会直接影响操作系统的行为——你能不能执行它，决定了你能不能用 `execve` 去处理它；你有没有访问它的权限，取决于用户、组和这几组 mode bit。

往回看，这些属性从 Unix 演化过来一直在增长。更早的 DOS、FAT 文件系统里根本没有 user、group、permission 这个概念，文件就那么几种属性：你把 U 盘格式化成 FAT，插到任何设备上，任何人都可以读它写它，软盘是更典型的例子——文件系统里没有权限，就谈不上保护。是 Unix 引入了这样的权限，于是这些 metadata、这些属性就被加到了文件上。

### 给文件一个人格：还没被实现的 policy

但反过来想：我们费劲加这些属性，到底是为了什么？

我们其实是希望文件——或者说这些虚拟的磁盘、这些存储数据的对象——有一些自己的**personality**。打个比方：当你把「学习资料」这个目录设置成隐藏的时候（我知道你们想干什么），你真正想要的不是一个 `ls` 不显示；对操作系统设计者来说，把「点开头的就不显示」当成一个合理行为是可以的，但你**真正想要的**是：只有我自己用这台电脑的时候能看见它，旁边只要有别人，它就得藏起来。

只是我们现在的文件系统是一个抽象层，它是人写的，既要给人用、也要给机器用。它会觉得这件事太复杂了——我还得判定这个 policy 的执行条件，比如「有没有人正在你电脑旁边」，再决定要不要隐藏。所以我们现在的操作系统不支持这样的 policy，它只支持「这个文件是隐藏的」这样一个简单的、由程序实现的语义。

但这其实是一个革命性的机会。**每一个文件，你都想给它一个自己的 personality。**在 Windows 里点右键、属性，里面就有一个框叫它的 personality，你说这是我的学习资料，但只能在没有别人的时候我才学习——然后它正确地执行你的 policy。这会是一个很好的 feature，一个非常好的产品。

这种「奇怪的隐藏 policy」其实在操作系统里已经实现过了，你们做进程树的时候应该已经撞见过：`pstree` 里有一大堆线程，随便挑一个比如 1695——

```bash
ls 1695/                 # 可以，目录在
cat 1695/status          # 可以，看到它的信息，name 是 FooToRender2
cd 1695                  # 也可以进去
ls | grep 1695           # 咦，看不到它
```

也就是说，**文件系统是可以欺骗你的**。

### procfs：对象从未真正存在过的文件系统

`/proc` 这样的欺骗，来自 Linux 实现的一个特殊文件系统。挂载的时候（前面讲最小 Linux 时见过那条 mount 命令）类型写的是 `procfs`：`mount -t proc`。所以**这整个文件系统，包括 `getdents64` 的实现，全部由 procfs 的代码自己决定**。理论上它想做什么就能做什么。

那些看起来像目录树的东西，其实根本没有在操作系统里创建成对象，全是临时构建出来的。你 `tree /proc` 会看到一个非常庞大的文件系统，但这些对象从来没有真正被构建出来——因为操作系统内部有另外一套数据结构：

```text
   内核里真实存在的                  应用看见的
   ------------------------          --------------------------
   struct task（可调度实体）    ->    /proc/1695/status
   每 CPU 的 runqueue 链着它们   ->    /proc/1695/memory
   pid、线程的那一大堆信息       ->    /proc/1695/...

   打开目录时：对象还没造
   调用 getdents64 时：一边遍历系统里的 struct task，一边现编结果
```

以 Linux 为例，每一个可以调度的实体都是一个 `struct task`（你自己写操作系统时大概会叫 `struct thread`），里面有巨多关于线程的信息，比如 `pid_t pid`；每个 CPU 上有一个 runqueue，runqueue 里链着一大堆这样的 task。这些数据结构都在内核里连得好好的。

而 procfs 的代码，只有在你**真的 open 了那个目录**（总会有个 `openat` 打开 `/proc/...`）之后才开始工作；而且**打开目录的时候那些对象都还没创建**——只有在你真正调用 `getdents64` 的那一刻，它才去遍历系统里现存的 `struct task`，一边遍历一边动态地把结果生成出来。所以那些对象根本不存在，它看起来是一棵树、一个文件系统，其实全是代码给你造出来的幻觉。

> **结论**：只要你的 API 返回的值是你想要的那个值，这件事就是成立的。`/proc/<pid>/memory` 这种东西也不是一个实在的文件，但文件系统帮你把它实现了。文件本来就不存在，那么让你看见、不让你看见、让你看见什么，完全由它决定。

### 扩展属性：给每个文件配一个 key-value

那么问题就回到：我们希望能在文件系统上面，给文件增加**任意的**属性。这个想法不错，而你不是唯一一个这么想的人——操作系统真的有这样的 API，叫 **extended attribute**（扩展属性）。想了解这个机制，`man` 的手册页就有（`man 7` 的 extended attribute 那一页）。

它是什么？就是**为每一个文件维护的一组 key-value**。有点像刚才说的那个「personality」的框：

```text
   a.txt
     |- user.author      = "jyy"
     |- user.description = "..."
     |- user.version     = "1"
     `- ...               任意你想加的 key（可以想成挂在文件上的一个小 JSON）
```

比如文件的真实 type 是什么、想给这个文件加一个 icon，都可以；反正就是 key-value。

下面是现场的一段真实过程，很值得看：我在完全不知道这个机制的情况下，让 AI 去处理 extended attributes 这件事，它就告诉我该用什么命令，用了 `setfattr` 之类——当然它一开始也**幻觉**了一些 key 出来，比如 `user.author`、`user.description`，随后它自己把这些验证了一遍。

接着我做了一次拷贝。因为整个操作系统的设计需要做到**向前兼容**，你会发现目标文件在这个 list 里完全看不到任何 extended attribute。所以你有时候会好奇：macOS 里一个下载到一半的文件，图标上会显示「下载了多少」那种小图示，这东西到底存在哪？它就在 extended attribute 里。下完之后的一些签名之类，也可以存在 extended attribute 里。

**但它对拷贝不友好。** AI 在这里表现得比我聪明：我会想当然地假设这是 Linux，而 Linux 的 `cp` 是可以 preserve xattr 的；但你的 `cp` 未必支持这个特性——如果是个 toybox 的 `cp`，它可能就不支持。所以它非常谨慎，**先把 `cp` 的帮助打出来、先读一下文档**，然后才用一个 preserve extended attribute 的写法，把 `user.version`、`user.description`、`user.author` 全都带了过去。`tar --xattrs` 同理，也能保留这些扩展属性。

老实说，我不知道、或者说我即使知道也记不住所有这些细节。**我的大脑里显然装不下这些信息，尤其是一段时间不用之后，突然要用的时候是真的想不起来。**所以对你来说重要的不是背下来，而是建立起正确的概念体系：

1. 我可以在文件上**加**这个东西；
2. 在**拷贝**的时候，它是有危险会丢的；
3. 这个东西**可以拿来干很多有趣的事**。

有了这三条，你就可以在任何时候借助 AI 去借用这些机制，构建有意义的系统。比如去年我看到一个很有意思的项目叫 VectorFS：我想要在所有的照片里搜索某种东西，甚至让 Claude 帮我生成一个相册，把几个命令行工具结合起来就能做到。

这样的「智能的 extended attribute 搜索」也很适合做成 agent 的原生工具。现在的 agent 可以用 `grep`、用 `glob` 找文件，也可以用 language server 去找一个 identifier 定义在哪里——都很有用。而**在文件系统里按扩展属性搜索**肯定也会是一个非常实用的工具。

当然它有一个致命的缺陷：**知道的人太少**。一般操作系统课都不太讲，讲完也是一笔带过。这意味着不是所有的文件系统都支持它——当把一个带 extended attribute 的文件拷到 FAT 上时，这东西就**悄悄地消失了**。操作系统和拷贝工具都不想每次都打断你的流程、问你一句「extended attribute 要丢了，你确认吗」，那太崩溃了；于是只能 silently 丢掉，因为你的文件系统不支持 FAT 上根本没有这个概念。

后果是：你一来一回拷两趟，文件就变了。你看起来只是把文件拷到 U 盘、拿到另一台电脑上编辑了一下、再拷回来——**元数据丢掉了**，这显然不是你想要的。这会带来一些比较复杂的系统实现上的麻烦。但这是一个非常好的机制，我觉得它迟早有一天要火，我先立个 flag，只是现在不知道为什么还没火。

### ACL：比三组权限更细的控制

除了扩展属性，还有更复杂的机制。前面展示的 access control 是 user / group / other 三档读写执行——这已经比较粗了。你马上会想要干一些更细的事，比如：**让所有用户都能访问一个文件，除了某一个用户**。你甚至可以想「除了我爸不能看」。这种事用用户和组来做就比较麻烦，你得专门创建一个组。

Linux 对此的扩展叫 **Access Control List**，它可以做这种 fine-grained 的访问控制。

现场我追问的一个问题是：能不能让一个文件对某一个用户不可访问，而这个用户是 **root**？

> **提示**：从操作系统设计者的角度看，root 是绝对的，0 号用户拥有绝对的权限。如果 root 都不能访问、不能删除某个文件，那会是一个很糟糕的操作——我就可以把整个系统的存储空间占满，而即便有最高权限的人也删不掉它。这件事显然是不对的。

AI 也知道这一点：**root 会 bypass 掉这些检查**。后面它真的做了一个属于 jyy 的文件，并把 jyy 自己的访问 deny 掉——而 owner 把自己 disable 掉，同样是一种不应该被允许的操作。它在这个过程里探索了各种各样的可能性、做了一堆实验，虽然不是每次都符合我的预期（毕竟是现场），但可以确认的是：拿到这样一个工具之后，你可以无限地和它对话、去了解它的真实行为。

同样地，你要记住的只是**这个世界上有一个东西叫 Access Control List**，然后在有需要的时候能用它、并且能启发 AI 把它用到你的产品里去。

到这儿可以把整讲的意思收一下：这就是**在没有直接经验的领域、技术、语言、框架里，做有质量保证的编程工作**。你会知道每一个机制的存在，搞清楚它的 API——它给你什么样的保证——然后你就可以工作在这个抽象层上，把它集成到你自己的系统里。所以这件事对你们来说，其实并没有那么困难。

## 监控、快照与 Git：把文件系统当数据结构来用
> 对应块：BLK49 | 覆盖分集：P25上 | 块标题（分集名）：《文件系统 API (2)（上）》

### 从增删改查看出去：文件系统是数据结构

上一节课讲的是文件系统增删改查那一部分 API。这些 API 你们其实非常熟练了：在 Windows 的资源管理器里右键、新建一个目录、编辑一个文本文件，背后就是同一批操作。我们由此认识了 `mkdir`、`link`、`unlink`、`symlink` 这些机制——不仅可以创建普通文件，还能创建两份指针指向完全相同的文件，两个名字不同，但一份改了另一份会跟着同步修改；可以做出像快捷方式一样的符号链接；还可以在文件上标注属性：Unix 默认的 `mode`，也就是读、写、执行权限，FAT 里没有这套读写执行权限，但它有自己的一套文件 metadata，再往上还有 extended attributes，允许你把任意的 key-value 写到一个文件里，并带着这个值一起跑。

这些都是对文件的一小步操作，增、删、改、查。拿它们去写一个管理很多文件的应用程序当然没问题，但操作系统上面能干的事情远远不止于此。上节课里就出现了很有趣的一个 API 叫 `mount`，挂载——它就是一个文件系统级的 API：把一个块设备、一个字节序列的抽象，甚至文件系统里的一个文件（通过回环设备）挂到目录树当中，一次调用就在目录树里长出一棵新的树，里面还有好多好多东西。

所以今天要回到一个更根本的问题上：文件系统是一个数据结构，是一个 abstract data type。既然它是数据结构，理论上说，我们就可以在这个数据结构上定义各种各样的操作。

比如你们学数据结构时见过的 persistent data structure：用 append-only 加 random read 就能实现任何一个数据结构，于是我可以回到历史上的任何一个时间点，把所有历史版本都记下来，退回到过去的一个快照。再比如学算法时解决过的一类问题：维护一个集合，比如 3、5、10，那是一个 set of int；但如果这个数据结构上还允许全局操作——比如对所有元素都加 10——就有两种实现。一种是老老实实遍历一遍，3、5、10 变成 13、15、20；另一种是把"加 10"这个动作悄悄地写到数据结构的边上：我现在取一个元素 5，加上那个 10 再返回 15。这时候如果要插入 9 怎么办？不能去动那个永远带着的 +10，而应该插入一个 `-1`——所有元素都永远带着 +10，取出来正好就是 9。数据结构里有很多这种有意思的 trick，能让你对一个数组的某个区间整体加一个值，同时还保持良好的时间复杂度。

> **结论**：数据结构上能玩的这些花样，文件系统凭什么不能玩？

所以今天就是干这几件事：第一件是监控，就像刚才维护一个 flag 的例子；第二件是快照，对文件系统整体做快照；第三件是文件系统的覆盖，overlay 或者 union，有了 Docker 之后这个东西很好玩；最后还有一个终极的虚拟化——既然文件系统是数据结构，凭什么我不能实现一个数据结构来充当文件系统？也是可以的。

### 监控文件系统

文件系统改变以后希望被通知，最好是通知你的时候还告诉你哪一个文件变了——这是一个非常正常的需求。什么地方会用到？

写 Web server 的时候。你们做过 `httpd` 实验，就知道那种"请求 `/hello` 就调用某个 function 返回结果"的结构。用 Flask 这样的框架，debug mode 一打开，你的 Python 代码被修改以后就要 reload：比如 `A.py` 已经运行起来了，文件的内容已经在内存里、在进程的地址空间里，这时候你去改这个文件，进程里的东西还是旧的，你就得重新加载这个文件、重新创建一个进程、把旧的进程杀掉。项目里有几百几千个文件时，这件事就需要文件系统监控。Next.js 的 reload 做得更彻底：改一个 CSS，你一按保存，网页瞬间就变了——如果浏览器就在旁边，你会看到保存的那一瞬间界面就变了。最神奇的是让 coding agent 去改前端，比如让它改 style，你就能看着它一步一步地改，界面一点一点地变，最后变出你想要的界面。这是一个非常实用的需求。

#### 用 stat 和 diff 硬拼一个监控

原则上这个需求不需要操作系统的帮助也能实现。比如一段 shell 脚本：用尖括号把一条命令伪装成一个文件（进程替换），这个"文件"就能喂给像 `diff` 这样需要两个文件输入的命令。脚本里 `stat` 可以输出文件的各种元数据——上节课讲过的 `mode`、modification time 这些 attributes——后面跟一个通配符，就可以遍历出目录下所有文件的信息。我让它输出修改时间；当前目录下用 `**` 可以匹配目录和子目录里所有的东西（这个 feature 需要在 bash 里配置一下），也可以用 `*/*` 表示某个目录下所有的文件。

流程就是：先立刻拿到当前所有文件的修改时间，睡两秒钟，把 `a.txt` 改掉，再 `stat` 一次，然后 `diff` 两边——它就会告诉你变了。如果不改，只睡觉，`diff` 什么都不返回，因为没有检测到任何区别。一行脚本就能得到一个 last modified 的列表。

> **提示**：这个办法的代价在文件数量上。如果目录里有几百万个文件，效率就很低，每次遍历都是几百万次文件元数据查询。当然现在操作系统即便这样查，性能也不会差到不能忍受，因为热数据会被放进内核的缓存里——文件的元数据和数据本来都在存储设备上，可能是很慢的光盘（上节课大家看到访问它可能有秒级的延迟，盘要转），也可能是 U 盘——但几百万个文件时，你仍然会觉得不该用这么暴力的方式去查。

#### inotify：把查询换成事件

更好的办法是：文件系统改了，就收到一个事件，收到事件直接处理就行，不需要一遍一遍地把整个文件系统的时间查一遍。这是操作系统给你的机制。`man 7 inotify` 会看到两个重要的系统调用：`inotify_init` 和 `inotify_add_watch`，用完之后还可以 `inotify_rm_watch`。

`inotify_init` 返回一个文件描述符。注意 Linux 的设计——所有东西都是用文件描述符实现的，这意味着你可以用 `epoll`、`select` 这些系统调用去监听它，也可以同时持有好多个 inotify 的文件描述符，只要任何一个有更新你都能知道。你关心的那些事件来了以后，会得到一个事件的数据结构。

> **注意**：inotify 是不递归的。想覆盖一整棵目录树，得自己逐层登记。

使用场景一抓一大把：文件管理器的自动刷新（文件管理器不是唯一修改文件的入口，别人 ssh 到你的机器、在一个终端里 `touch` 一个文件，你打开的 desktop 目录也应该正确地把变化反映出来）；编辑器的自动重载，VS Code 也用这个特性；systemd 监控 unit 文件的变化；还有 `tail -f`，等待文件被写入。

#### 一次演示暴露的细节

有一段现成的 Python watchdog 脚本，就是一个 low-level 的系统调用加上好用的封装（比如 `EventHandler`），能正常跑起来。开一个 tmux，右边 watch，左边动手：创建一个目录，创建的那一刻右边就收到事件了；在另一个终端里执行别的命令时，什么都没有发生。接着 `touch a.txt`，这时候文件系统的变化比你想的要多一点——

```text
touch a.txt 之后收到的 inotify 事件（示意）

  [created ]  a.txt                      ← 新文件被创建
  [modified]  t/                         ← 它所在的目录也被 modified
  [open    ]  t/1/2/a.txt
  [modify  ]  t/1/2/a.txt
  [close   ]  t/1/2/a.txt
                 ↑
        文件修改/关闭之后，它的 modification time 随之改变
```

创建文件的时候，它的目录本身也会跟着 modified——这是一个以前可能没有留意过的细节：你改一个文件的 modification time，它上一级目录的 modification time 也会改。

那如果目录有好几层呢？比如 `t/1/2` 这样的结构，在 `t/1/2` 里 `touch a.txt`，`t/1/2` 的修改时间改了，它的再上一级会不会改、会不会一层一层向上传递？

> **易错点**：不会逐级向上传递。只有直接容纳这个文件的目录（`t/1/2`）会变，`t/1` 不会跟着变。目录的修改时间记录的是"这个目录里有什么发生了变化"，而不是"这棵子树里有什么发生了变化"。

监听文件系统的变化没有什么困难的，它就是非常切实的需求，操作系统于是提供一个 API 来帮你实现它。

### 从监控到 eBPF

回过头再想一下。前几次课展示过一个还有点小酷的例子：在终端里看到系统里所有进程执行块设备 I/O 的操作——我现在不知道是哪个进程读了、写了或者同步了，但如果我写一个很大的文件，写的那个条就上来了；如果我读，就看到读的条；如果做一个文件系统的同步，也就是落盘操作，就能看到那个粉红色的落盘。这很有启发性。

刚才我们实现的是文件系统的监控，监控的是目录里文件的变化。但真正想要监控的不只是目录里的文件——而是整个操作系统这个程序在运行时各种状态的变化。本质上操作系统也是代码，又回到那句话说过的 everything is a state machine：你写过 NEMU 的模拟器之后就可以永远这样想象，我们的操作系统直接跑在你写的模拟器上，所有的东西都是代码；代码执行时会有函数调用，会有结构体的修改。所以理论上说，用 inotify 这个机制去拿到文件系统目录树的事件，理论上说也能拿到操作系统里任何东西改变的事件。

我们已经反复用过很多 trace：有东西搞不懂它是怎么工作的时候，就去 trace 它。`strace` 把应用程序打开，就知道这个功能到底是用什么系统调用实现的；`ltrace` 告诉你它调用了哪些 library call；inotify 告诉你什么时候调用了文件系统的那个 system call。可以把 inotify 理解成一种全局的 `strace`，只不过它只 trace `open`、`close`、`modify` 这些。包括那个追踪内核 block I/O 生命周期的 `bpftrace` 程序（一个 `.bt` 文件），本质上都是从操作系统的状态执行上提取信息。

于是有一个很自然的问题：既然它们本质上都是从内核执行上提取信息，那我们能不能在操作系统里面插入一段由你的代码生成的 probe？比如，操作系统调用每一个函数的时候都要经过你的代码，你的代码能知道函数的名字或者 ID，还能知道它的 arguments——相当于对它做一个 hooking。我们之前讲过 hooking，可以用 `LD_PRELOAD` 把 `malloc`、`free`、`printf` 任何一个库函数调用截住，知道调用的是哪个函数、参数是什么，还可以假装这个函数的行为，像给它装了个"变速齿轮"，调整这个进程对时间的感知。那么为什么不能手写一段代码插进内核里，让内核的每一个函数在执行时都跑一下这段代码？那样你甚至不需要 inotify 这个系统调用，只要这段代码追踪的是文件系统里和修改相关的函数，在函数到来时往一个队列里放个信息就行。

恭喜你，你发明了现在非常火热的一个机制：eBPF，Extended Berkeley Packet Filter。

#### 名字里的出身

听名字就知道它是干什么用的——它是在网络子系统上用的。网络是世界上速度最快的设备之一。而且很有意思：Linux 里讲 I/O，块设备是 block read、block write，应用层可以用 `read`、`write` 系统调用，也可以用 `mmap` 去访问 I/O；但这些操作对网卡通通不适用。你们不会用 `read`、`write`、`mmap` 去访问网卡，因为网卡来包的速度实在太快了。到数据中心的网卡上看一眼 packet count，你甚至会觉得 64 位整数快要溢出了；一个几百 GB/s、带宽一般能用满的服务器，不停地在向内核发中断，需要几十个 CPU 一起响应才响应得过来。最终所有 I/O 设备都活成了网卡的样子，于是 Linux 现在有 `io_uring` 这样的机制，用的就是网卡的 ring buffer 设计。这些不是上课要讲的，有兴趣的同学可以回去了解。

真正催生这个想法的例子是防火墙。一个防火墙想把来自某一个 IP 地址、或者某一段 IP 地址的所有请求都扔掉。有一种办法是等这个包到了用户空间，在那里执行一段代码，再返回去告诉内核——但这样的 context switch 开销太大了。于是就有了一个非常自然的想法：我能不能写一小段代码？一段很简单的代码，一般就是判断一个 IP 地址而已。把这段代码写到内核里，内核每次收到一个 packet 都去执行它，由它决定这个包是留下还是扔掉。再扩展一下，让它能在一些 hook point 上运行，至少可以做一些信息收集——这就是 eBPF。

#### 这台虚拟机的构造和它的紧箍咒

eBPF 也是一个虚拟机。当然它最终还是编译成本地体系结构的机器码来执行。它是一个 RISC-like 的指令集，有 11 个寄存器，`R0` 是返回值；在每一次函数调用、也就是每一个 probe 的入口，`R1` 都会指向一个 context 结构体，里面包含函数参数、function name 这些东西。这个虚拟机和你们写 NEMU 时那个小的指令集是一样的性质，但它有一条非常特殊的指令：`bpf_call_helper`，用来调用内核给你实现好的函数。比如 `bpf_get_current_pid_tgid` 可以去询问当前的 PID、TGID，还可以做 buffer 的、BPF map 的 lookup element。

如果你的代码能够随意修改内核内存，那就很危险，所以最好是只读的。BPF 有一个非常严格的验证器，它只允许 bounded execution：不能有那种 unbounded 循环，有的话直接拒绝。这就导致一个后果——你没有办法在 BPF 里面实现自己的数据结构。想记录、想统计某个函数调用了多少次，就必须借用它的 map 机制，那相当于它给你预实现好的数据结构。有了这些，就可以读懂那个 biotrace 了：它就是一个 tracepoint，挂在 block request 的 insert 上，比较简单，直接打印；打印也相当于打印到一个 buffer 里，最终用户态可以看到。

完整流程是：

```text
        写一段 C 代码
             │
             ▼
     编译成 eBPF 字节码
             │
             ▼
   调用 BPF system call  ──  这一步很重要：需要一个系统调用把代码注入内核
             │
             ▼
     内核中的 verifier 静态检查  ──  不允许 unbounded 循环，代码只读
             │
             ▼
   优化的编译器编译成目标指令集上的指令
             │
             ▼
     变成 hook，勾住一些关键的 hook point
```

内核里暴露了各种各样的 tracepoint，可以让 AI 帮你把全部列出来。至于拿它干什么，答案是任何事。

#### 一个被优化掉的 printf

这种东西也是有 bug 的，我们在生产环境里遇见过。有兴趣的同学可以去看我学生写的一篇 blog：我们写了一个 eBPF 的 probe，里面有一个 `printf`，我在它前面加了一个循环，然后那个 `printf` 就不执行了。根据语义，你可以 100% 确信这个 `printf` 是要执行的——但它被优化的编译器不知道出于什么原因 optimize out 掉了。当时的情况是它的分析有错，它认为那是死代码，可它显然不是死代码。

#### 用几百行代码复原自己的一天

这个机制非常 powerful：代码是我写的，而内核里暴露了各种各样的 tracepoint。可以用几百行 eBPF 的程序去捕获你所有键盘的按键和鼠标的移动——这不是一个开玩笑的功能。把它和别的 trace 结合起来，比如 `execve` 这类关键系统调用的 trace，就能基本完整地复原出你在这台 Linux 电脑上干过的所有事情，至少在这台机器上。

这也是一个很好的学习辅助。比如你想让自己用 shell 更熟练、用 Vim 更熟练——其实我也很想练，但有时候没有足够强的动机去做这种自虐的事情——但你可以把每一个带时间戳的按键 trace 从内核里用 BPF 拉出来，再结合 Vim buffer 随时间演化的快照，去问大语言模型：我做这件事的时候是不是可以做得更好？它会不断地告诉你，这个编辑你应该这样做，那个编辑你应该那样做。功能很容易实现，但只有也非常有自虐倾向的人才会这样干，因为它给你的心智带来了巨大的负担。这些东西都可以做，天马行空——你可能从来没有想过这件事也能做，但就是从 inotify 开始想，想到 `strace`、`ltrace`，想到本质上这是一个内核执行的 tracing 机制，最后就收敛到一个非常有名也有用的机制上。

#### 会提问就够了：specification is all you need

回头再看最开始那个引入：先在某一个时间点把所有文件的 modification time 打印出来，一秒钟以后再打印一遍，做一次 `diff`，如果发生了改变就知道文件变了、也知道是哪一个文件变了，然后做下一步动作。如果我是 Web 服务器 debug mode 的实现者，就可以借用这个机制。

但以前，作为一个软件开发者，你需要知道很多的库、各种各样的机制才能实现它；今天其实不需要。你今天需要的只是一个 AI——我现场就用一个 Flash 小号模型，假装自己不知道，因为这件事是 trivial 的：你知道文件系统可以增删改查，所以这件事一定办得到。你想要高效地实现它，直接问就行了，因为模型比你有更多的 knowledge，甚至比我的 knowledge 还多。它很快就能收敛到不止一种方案。我问了这些方案：

| 方案 | 机制 | 代价 | 什么时候合适 |
| :--- | :--- | :--- | :--- |
| 轮询 + `diff` | 定期 `stat` 全部文件并比较结果 | 每次都要全量遍历文件元数据，文件一多就不可接受 | 文件很少，或者只是临时脚本 |
| inotify | 在内核登记 watch，事件到达时监听的那个文件描述符就可读 | 不递归，得多层目录逐个登记 | 目录级监控的常规解法 |
| fanotify | 可以监控整个文件系统，而无需逐个添加目录 | — | 需要覆盖整个文件系统时 |
| eBPF | 在内核的 hook point 上跑自己写的代码 | 要写 C、编译成字节码、过 verifier | 通用的内核行为追踪 |

模型先是讲了 polling，然后讲到 inotify——既然它知道 inotify，这个问题其实就已经解决了，可以继续让它去实现。它还知道别的，比如 fanotify，可以监控整个文件系统而无需添加目录。再用大杀器——给它一点启发，提到 eBPF，或者让它 think harder、不停地 push 它想更多方案，它总有一天会想到 eBPF。当然对于这个需求来说，inotify 就是最好的方案，但 eBPF 肯定也是可以的。

> **结论**：这就带出一个很重要的结论。DeepSeek 的招聘须知里说过，你要有一种能力——在你并不熟悉的东西上面，仍然能把事情搞定。现在有一个前所未有的机会：你需要做到的是对这些事情是 knowledgeable 的，对"这个系统能做到最底层的事情"非常 knowledgeable，并且能够组合这些最底层的事情，清楚地知道你想要什么。至于它到底怎么高效实现，你不用 care，模型能给你搞定。这就是 specification is all you need。

你甚至可以先在文件系统上面搭一个性能奇烂无比、但是正确的 prototype——它能工作——然后把它丢给 AI：这是我写的一个功能性的描述，中间有很多性能很差的实现，但这正是我想要完成的功能，你能不能帮我尽可能地借用操作系统里面的机制，做一个高效的实现？剩下的事情你就不用管了。当然，你还是得会一些软件工程的知识：怎么做质量保障，怎么确保 AI 不要出太大的幻觉，以及出了幻觉以后你还能救回来。一旦有了这样的能力，你会发现自己的编程能力突然暴涨。

昨天我看到 Ion Stoica 的一篇 paper，叫 *The Time is Here for Just-in-Time Systems*。他说，现在有了 LLM agent 以后，也许我们可以让整个系统都是 synthesized from scratch，从零开始做，而它的性能就是特别特别好的，specialized to the environment, workload and required system properties——依然是那句话，specification is all you need。未来我要做软件，或者说这个软件要在你的机器上运行，我就描述"我的软件行为是这个，我想监控文件系统的变化"，它就可以从零开始，不停地根据你的运行环境去优化它的系统。

操作系统的设计者花了十几年的时间，设计了各种各样的机制：`strace`、inotify，然后到更本质的 eBPF。而有一天可能发生的事是：你对现在的操作系统有点不满意，就直接说"我想要在应用层做这件事，请你帮我把这个操作系统内核改一下吧"，它就 just-in-time、on-the-fly 地把这个内核改一改，加入你要的功能，然后你要的那个功能就能被高效地实现。在大语言模型有 100 万上下文的时候，让它自己去 propose 测试、自己把事情弄对，这完全是可能的。我真的觉得这件事情很快就会发生。

从监控这一个需求出发，我们能想到这么多有趣的东西。而这一切的起点，只是"文件系统是一个树形的数据结构"。

### 快照：append-only 加 random read

监控之外，还有一个很常见的需求是快照。前面已经说过：random read 加上 append-only write，等于持久化的数据结构。

如果有一棵这样的二叉树，我现在想在其中插入一个节点，做法是：先在这里标记一下，这个叫 v0，也就是旧版本；然后把从根到那个节点的整条路径都拷贝一份出来，这个叫 v1。

```text
       v0（旧版本）                            v1（新版本）
            root                                  root'
           /    \                                /    \
         A        B     ── B 及其子树没变 ──>    A'      B
        / \      / \      （指针原样复用）       / \
       C   D    E   F                          C'  D
                                               |
                                               N   ← 这次新插入的节点

  root → A → C 这条路径被复制成 root' → A' → C'；
  没有改动的 B、E、F 仍由新版本直接指过去，不复制。
```

只有那些发生了改变的节点需要拷贝一份，没变的子树因为是指针指过来的，直接复用即可。这样旧版本和新版本就都保存下来了，所有的历史版本也都保存下来了。

有一个你们非常熟悉的工具就是这么干的，从你们上课的第一次课开始就在用它——Git。Git 说：这个题我懂，它自己就是一个 persistent data structure。

> **提示**：今年研究生复试的时候，我问了每一个到我这里来的同学"什么是 Git"。有摇头说不知道的，有说是"从网上下载代码的"，然后没有一个同学能答出 `git rebase` 是干什么的；答得最多的也就是"这是一个管理代码的（工具）"，连快照有没有说出来我都不确定。我当时被雷倒了，所以今天很有必要讲讲 Git。

### Git 是一个依托文件系统实现的持久化数据结构

先新建一个干净的 repository：`git init` 之后会看到里面有一些 hooks 的 sample，可以删掉。Git 就是这样——所有东西都在文件系统里，它都是文件；如果你把这个 `.git` 删了，就相当于你所有的历史也都没有了。

现在是一个空的 Git repository。创建一个文件，`git add a.txt`，提交，就得到一个 commit，`git log` 能看到它。这时候再 `find .`，就多了些东西：多了 `.git` 下的 objects，每一个 object 其实是个目录，名字像 `196507…` 这样。文档或教科书会告诉你，Git 有三大对象，都存储在 `.git/objects` 下面，一个叫 blob，一个叫 tree，一个叫 commit。

再做一个实验：把 `a.txt` 从 `Hello` 改成 `Hello World`，再走一遍 add、commit 的流程，于是有了两个提交。因为它是 persistent data structure，老版的 `a.txt` 和新版的 `a.txt` 是同时存在于这个文件系统里的，也都在刚才 `find` 看到的 objects 里。

#### 亲手拆开 .git：三种对象

要验证这一点，可以让 AI 现写一个叫 `git-cat` 的小工具（这个名字和 `cat` 重名了）。这些对象都是压缩存储的，我再让它改成能从命令行接收文件路径，把内容打印出来。然后用通配符匹配出当前 Git 里所有的 objects，直接打印内容——你会看到两个 object：一个是 `Hello`，一个是 `Hello World`。一个旧版本，一个新版本，真的都在 objects 里。

三种对象分别是什么：

- **blob**：就是 `a.txt` 的内容。不管你写的是 C++ 还是别的什么，都是以这种压缩的方式直接存进去的。
- **tree**：就是这样的文件系统的树。例如 `100644` 开头，那是文件的 mode——这个文件是可执行还是不可执行，都记在 Git 的 tree object 里；后面是这个数据结构的描述，是一段 binary，得再写点程序才能把它解开。
- **commit**：也是一段文本。里面有 commit message（一个叫 add a.txt，一个叫 modify a.txt）、author 信息、时间戳，还有 tree 和 parent。每一个 commit 都有一个 tree object、一个 parent object。看到 tree 的那个哈希（比如 `25086…`），就能在 objects 里找到对应的那个 tree object。

> **结论**：Git 是一个非常非常干净、极为干净的设计。它是一个 persistent data structure，依托文件系统实现。所谓 append-only，就是直接往 `.git/objects` 这个对象池子里丢一个文件——和上节课讲的那个一大堆 nix store 的机制完全一样，就是往里面丢文件；丢完之后把 tree 和 commit 这样的 object 也丢进去。丢完这些，就说完了 Git 的全部。

#### 剩下的全是指针

`.git` 里还有什么？比如 `HEAD`，它是一个指针，指向 `refs/heads/master`，而这个文件又指向一个 commit object。我可以依葫芦画瓢在 `.git` 里也创建一个文件叫 `tail`，里面同样放一个 ref、一个指针，然后就可以 `git diff HEAD tail`——diff 的就是那两个东西。所以 Git 这个东西没有任何神秘的，所有东西都是刚才那三种 object 之一，剩下的一切都是指针，以文本方式存储的指针。

一个分支是什么？分支就是一个指针，指向某一个 commit object。你再 commit 的时候，这个指针会往后移，不停地往后移；`HEAD` 也是这样一个往后移的 ref。`checkout`、`commit`，都是非常平常的文件系统操作，就是一个数据结构。

上面展示的都是在一个分支上的操作。现在创建分支：`git checkout` 出一个叫 `new` 的分支，再来一个叫 `new-new` 的分支。这时候会发现 objects 其实没有变化，只是多了一些东西——`refs/heads/new` 和 `refs/heads/new-new`，它们和刚才看的 `master` 是一样的，就是一个哈希，指向那个 commit object。看 `new-new`，它也是同一个 commit object。而如果我现在在 `new-new` 这个分支上提交，`refs/heads/new-new` 就会变，变成新的哈希——因为我人现在站在这里。

一个 repo 的对象图和指针关系，可以画成这样：

```text
  HEAD ──> refs/heads/master ──> commit (add a.txt) ──> tree ──┬──> blob "Hello World"  (a.txt)
             │                        │                       └──> blob …             (其他文件)
             │                        └── parent ──> commit (Hello) ──> tree ──> blob "Hello"
             │
             └──> refs/heads/new、refs/heads/new-new
                     （只是多了两个装着同一个哈希的文本文件，objects 一个没多）

  分支切换后再提交时，被切到的那个 ref 文件里的哈希就换成了新的 commit。
```

就是这么简单，它所有东西都是以文本明文的形式存储在文件系统里的。

## 数据结构视角下的文件系统：Git、快照、OverlayFS 与 FUSE

### 从一个漂亮得不像话的设计说起

Git 的设计者是谁？Linus，也就是 Linux 的发明人。你如果真去看过它内部的对象模型，会觉得这是一个非常、非常、非常漂亮的设计。

在它之前大家用的是 SVN。你们没有经历过那个时代，我经历过——`check in`、`check out`，SVN 难用得像什么什么一样。直到 Git 来了，这个世界就完全变了。GitHub 现在就是事实标准。它有一个非常干净的设计，而这个干净的设计又能承载未来更多的需求：Git LFS 解决大文件问题，worktree 解决多任务问题。这些其实都是小问题，真正关键的是——这个模型对于代码来说简直太合适了，代码本身就是一堆小的、细碎的对象。

### Git 的对象模型：一切都是对象，一切都只是指针

先看分支和提交，再看一个不起眼但很好用的东西：**stash**。

你手头可能有一些 ongoing 的修改，做到一半，还不对，你不想把它 commit 到分支上。那这时候就可以 `git stash push`，把这些改动暂存起来；然后你可以看到 stash 列表，并且不断地往里 push。

关键在于：**stash 其实也是一个 commit object**。

我可以用 `echo` 往工作区里造一点改动，随手 push 一个 stash；然后翻一下 stash 列表，找到一条，比如消息是 "working in progress on niuniu" 的。把它打开看——它有一个 tree，然后它有两个 parent。

```text
   栈顶  stash@{0}   ← 最近 push 进来的工作区改动
         |            parent[0] = HEAD
         |            parent[1] = stash@{1}
   中间  stash@{1}
         |            parent[0] = HEAD
         |            parent[1] = stash@{2}
   栈底  stash@{2}
```

每个 stash 都是一个 commit，两个 parent 一个指向 HEAD、一个指向上一个 stash，于是所有 stash 就被串成了一个栈——所以它能 push，也能 pop。就这么简单。

> **结论**：所谓版本管理，说到底就是数据结构。你平时写 `tree`、写二叉搜索树的时候，指针是 `struct node *left`、`*right`；而在 Git 里，所有的指针都是**一个 hash**。一模一样的玩意儿。数据结构有不同的节点类型，节点上挂你自己想放进去的 data，仅此而已。

既然对象都是可以读出来的，那也很适合交给 AI：任何一份 commit history，你都可以让 AI 直接把里面的 objects 全部读出来——它会自己找到正确的工具。然后你可以让它画代码图，比如画成 Mermaid，也可以直接生成 SVG。总之你能得到一张还不错的流程图或者原理图，帮你看清楚自己的 project 到底发生了什么。

### 合并的几种形态

要把话说明白，Git 的定义还是该给：它是一个**分布式的版本管理系统**，管理的是很多棵目录树的快照。

前面说了，commit 对应一个 tree。既然有分支，就可能在同一个 tree 上分叉：一台机器上长出了 A 和 B，另一台机器上由 C 和 D 两个人开发。这时候历史就不再是线性的了——所以 Git 要做合并。基本上，用这个模型就能理解合并的全部了。

#### merge 与 fast-forward

最基础的 merge，就是**添加一个 E 节点**。

这个场景你们一定会遇到：你们本地的 main 已经往前走很远了，而我这边还停在一个非常早的提交上。我会在这上面做 M1、M2。

```text
   公共祖先
      |
      +--> ... --> B ----+
      |                  |
      |                  E   (merge commit，parent 是 B 和 D)
      |                  |
      +--> ... --> D ----+
```

你从远端拉取分支的时候，就会创建一个 E，它有两个 parent：B 和 D。这时候做的是一次**三方合并**：有一个公共祖先 tree、一个 B 的 tree、一个 D 的 tree。中间那些提交，不管是一万个还是十万个，通通被展平——它只看 common ancestor、B 和 D，然后合出一个 E 来。这是比较直观的情况。

如果你的本地压根没有 A 和 B，远端有 C 和 D，那你直接把 C 和 D 拉过来就同步了，本地也变成那样。这个叫 **fast-forward**。你去别的 Git repo 拉东西时有时会看到一条 message 说这是 fast-forward，意思就是"我这边什么都没看见，就把你的东西放过来"。

那如果这边有 A 和 B，你又不想创建 E，有办法吗？标准做法当然是打一个 merge，肯定要创建一个新的提交对象来代表它。你可以特意要求 no-fast-forward，比如合一个 niuniu 分支，它就要求你创建一个新的 commit。打开这个新提交看，它就有两个 parent 了——一个是本地的 `531`，另一个是远端的那个提交。

#### cherry-pick：只要那一个补丁

想不要 E，也有办法，用到的功能叫 `git cherry-pick`。这是个非常好用的功能，它可以 cherry-pick 任何提交。

打个比方：你在本地复制了一份 Linux 内核，可能是 10 年前复制的。10 年里 Linux 内核已经发生了翻天覆地的变化，你已经不可能跟它合并了——你也改了，它也改了，要解决所有冲突是不可能的。但是，比如内核里某个地方给一段很老的代码打了个安全补丁，这个补丁跟你没有冲突，你就想把它拉过来，这时候就可以 `git cherry-pick`。

本质上你可以这样理解：**任何一个提交，比如从 A 到 B 的那个提交，它就是一个 diff**。A 是一棵树，B 是一棵树，你只要记录 A 和 B 之间的 diff，就可以把这个 diff 抄过来。

#### rebase：把别人的工作插到你前面

rebase 是怎么做的呢？

```text
   改前：
   main --- A --- B            (我本地，Δ1 = main→A，Δ2 = A→B)
            \
             +--- C --- D      (远端)

   改后（先把 C、D 复制过来，再在它们之上 replay Δ1、Δ2）：
   main --- C --- D --- A' --- B'
```

rebase 做的事情是：先把 C 和 D 复制过来，然后在那个状态上，试图 cherry-pick 从 main 到 A 的 Δ diff，得到一个 A'。就好像"这里有一个补丁"——如果你修的 feature 跟别人不冲突（比如 C、D 改的文件和 main、A 之间改的文件根本不是同一个），那这个 Δ 就可以直接 patch 过来。接着 replay Δ1 得到 A'，再 replay Δ2 得到 B'。原来的 A、B 就没了。

它给你制造出一个假象：你本地写的是 A 和 B，也就是 Δ1 和 Δ2；远端的 C 和 D 被插到了你的前面。你们本来是并行开发的，但看起来像是**别人先做完，你在他那个基础上接着做的**。这样你就省掉了那个 merge commit。

> **易错点**：rebase 是要慎用的。如果我本地的提交和对面没冲突，比如改的是不同的文件，那基本上没问题，一般来讲我会把 rebase 设成 merge 的默认行为。但一旦 cherry-pick 发生冲突，基本上你就该放弃 rebase，老老实实 merge。因为它是**逐个 replay delta**，你可能 resolve 了这个冲突，下一个又冲突了；如果两条线 diverge 的时间比较长，你会变得非常非常痛苦，极度痛苦。而且即便 auto-rebase 成功了，它也可能隐藏逻辑上的冲突——你还是得回过头来，把这个 diff、那个 diff、再一个 diff 都 review 一遍，确保自动合并的过程没有做你不想要的事。所以说，rebase 是一个非常危险的操作。

| 操作 | 是否产生新提交 | 特点 | 风险 |
| :--- | :--- | :--- | :--- |
| merge | 产生一个 E（两个 parent） | 三方合并，历史保留分叉 | 历史里多出 merge commit |
| fast-forward | 不产生 | 直接把 HEAD 移到远端提交 | 没有分叉时才可用 |
| no-fast-forward | 产生一个 merge commit | 强制保留"这里合过"的痕迹 | — |
| cherry-pick | 产生被挑选提交的副本 | 只搬一个 diff，不管历史 | 冲突需逐个解决 |
| rebase | 产生一串重写后的提交 | 把别人的工作插到自己前面 | 冲突连环、可能隐藏逻辑冲突 |

到这里，你掌握的东西已经超过 90% 的 Git 用户了。

### 历史总在重演：单线程假设与 worktree

我在准备幻灯片的时候惊人地发现，历史总是在重演。

Git 是一个 **persistent data structure**，它是为**单线程**设计的——也就是说，它假设你的开发者一次只做一件事。

还记得 Unix 吗？最开始它就是进程模型，没有线程。那时候只有操作系统内部有共享状态，一个进程里就一条执行流。当我们把一个进程变成线程、引入 pthread 的时候，就打开了一个魔鬼的盒子——我花了好几节课讲并发、讲并发 bug、讲并发 bug 该怎么应对，就是为了把进程模型变成线程模型。

Git 很像 Unix 那个单进程的模型：它只有一个工作区、一个 HEAD。你在本地工作时是一条线性的 commit——你们自己不自知，做实验的时候每一次 `make` 提交都在往性地往后加一个、往后加一个，直到你需要跟别人同步时才会 merge 一下。大部分时候这个模型工作得很好。但一旦你从单线程变成多线程，事情就麻烦了。

设想一下这个场景：我正在一个分支上工作，修到一半，老板打电话来说手头的事情别干了，切到另一个 feature 分支上去修一个高危漏洞。我该怎么做？我应该 stash——做到一半的东西不能 commit，得 stash 起来；然后做一个上下文切换，checkout 到那个分支上。

你有没有感觉到开始并发了？我做了一半的东西被保存下来了，我切到另一个地方工作。然后我又做了一半，老板又打电话来，说有个更高优先级的 bug 要修，那我就没办法，再 stash 一次。

而 stash 是一个**线性的 stack**。你会发现它的设计之初就没有让你多线程工作，所以当你一定要多线程工作时，就会出现 **stash hell**。还好，从人道主义的角度考虑，老板一般不会这么过分，所以一般有个两三个 stash、同时 multitask 两三个事情，你可能还能管得过来。我觉得 Linus 当年设计这些的时候应该就是这么想的。

但是在 Agentic AI 的时代又变了。当我可以一下放一大堆 Agent 在同一个项目上、同一台机器上，又变麻烦了。当然总有办法：我可以以进程的方式把 Git repository 复制好多份，你们分别工作，再去 GitHub 上同步。这肯定是可以的。

不过早在 2015 年，为了解决 multitasking 的需求，Git 做了一个很有趣的机制，叫 **worktree**。

还记得 persistent data structure 的性质吗？所有历史都是留着的。比如 `git reflog`——如果你 `git reset --hard`，那些没 add 的东西就丢了；但其他所有东西，因为它是 persistent data structure，对象都留在文件系统里。哪怕有一个 commit 变成了没有任何引用的孤儿提交，只要你不做 `git gc`，你的 tree object、blob object 实际上都还在文件系统里，你都能捞回来，也能在 `git reflog` 里找到全部历史。

既然这是一个 persistent data structure，我们为什么不能把树直接复制一份呢？没有道理不能。因为复制是没有代价的——我永远不修改，所以"复制"一个指针、让它指在这个位置就可以了。于是就有了 `git worktree`。

```text
   repo/.git/                     ← 真实仓库（目录）
       objects/                   ← 所有对象只存这一份
       worktrees/
           hotfix/               ← worktree 的元数据
               HEAD
               gitdir

   repo-hotfix/.git               ← 这是一个文件，不是目录
       内容：gitdir: /path/to/repo/.git/worktrees/hotfix
```

我在当前目录下执行 `git worktree add`，得再换一个目录，还要起一个分支名，比如说 hotfix——老板要求我 hotfix。于是我就有了一个 hotfix 工作区。

这时候你会发现有点不对劲：那个 `.git` 它不是一个目录。刚才原始仓库的 `.git` 是目录，里面有 objects，那个 persistent data structure 就存在那里。但 worktree 的 `.git` 我可以直接 `cat` 它——又是一样的设计，跟 HEAD 一样：HEAD 是一个 reference，指向某个东西；这个 `.git` 说的是"Git 目录实际在这里"。

我可以 cd 进去，会看到它在真正的 `.git/worktrees/hotfix` 下面。里面一堆指针，**没有 object**——它不需要存 object，因为是 persistent data structure，所有东西都是指针就可以了。我只要有一个 HEAD 指向一个合法的 HEAD，HEAD 再指向一个合法的 commit，这件事就搞定了。这就是 persistent data structure 带来的一个完全免费的 feature。

当时是为了解决"老板不停地给我打电话"的需求，但今天，worktree 已经成了 Agent 时代一个非常标准的特性。这时候你会发现，学 SICP 里面那些 functional programming 的含金量还在上升。历史总在重演。

### 把持久化数据结构搬到块设备：Btrfs

Git 这部分就讲完了。你们用得到的 feature 基本都有个基本概念了，用不到的也可以在基本概念之上再去问 AI。

接着往下想：如果 Git 是一个 persistent data structure，persistent data structure 这么好，我们能不能把文件系统整个也搞成 persistent data structure 呢？没有道理不能。

这个文件系统叫 **Btrfs**。它是有十来年历史的东西——大概十几年前你基本上就可以在 production 里开始用了，当然它有 bug。那时候我们尝鲜用，各种 bug 会把你整个文件系统搞挂。但这个 idea 是一样的。

名字里的 B-tree，就是数结课上学的那个 B-tree：每个节点装在一个大块里（块大小 4096 字节），所以它是一棵非常宽的多叉树，而不是二叉树。多叉的索引结构可以把整个索引的层数压得非常浅。它就是"everything is a B-tree"。

它和 Git 有一点不同：Git 因为有文件系统的抽象，可以直接把东西往 `.git` 下面的 objects 里丢；而 Btrfs 不行，它要在**块设备**上从零开始实现一个 persistent data structure。它的 volume、它的文件系统目录树，所有东西都是以 append-only、copy-on-write 的方式做持久的。

于是这个文件系统和 Git 一样，**支持免费的快照**。你只要持有了一个文件描述符，对它做一个 `ioctl`，叫 `BTRFS_IOC_SNAP_CREATE`，就可以创建一个 snapshot。而对持久化的数据结构来说，创建快照根本不是什么困难的事——它只是把这个指针给一个名字记下来。就像在 Git 里你创建一个新的 tree object，让它指向好多 blob object 一样。恭喜你，又发明了一项改变世界的技术。

我不讲操作系统内核，我向大家承诺我们只讲操作系统应用层的东西。但你们依然可以看到：即使只是讨论操作系统的 API，哪怕只是增删改查的 API，你都可以实现像 Git 这样非常有趣的应用。

### UnionFS：把两棵目录树叠起来

Git 之后，还有一个更让人意想不到的操作。这个 idea 最早可以追溯到一篇 UnionFS 的论文。

既然文件系统是数据结构，那它当然是一棵目录树——我们还是尊重 Unix 的那一套，`/bin`、`/home`，一棵一棵这样的树。那么除了最普通的增删改查，你还能不能为它设计和实现一个更不一样的机制？

这个很神奇的 idea 是这样的：允许你在任何一个地方，比如刚才 `tmp` 里面有两个目录，一个叫 `upper`，一个叫 `lower`。每个里面既可以是目录也可以是文件，简单起见，`upper` 里放一个 `a`，`lower` 里放一个 `a.txt` 和一个 `b.txt`。

```text
   +-------------------+        +-------------------+
   |   upper（可写）    |        |   lower（只读）    |
   |   a.txt            |        |   a.txt（原样）    |
   |                    |        |   b.txt            |
   +-------------------+        +-------------------+
              \                        /
               \                      /
                v                    v
             +---------------------------+
             |   merged（虚拟目录）       |
             |   a.txt  ← 来自 upper      |
             |   b.txt  ← 来自 lower      |
             +---------------------------+
```

UnionFS 想干的事情是创建一个**虚拟的目录**，这个名字随便起，比如叫 `merged`。这个虚拟目录在访问上、在增删改查的意义上就是一个普通的文件系统对象，就是一个目录。但是我可以**通过一个系统调用**——在 Linux 里就是 `mount`——把 `upper` 和 `lower` 拼起来，拼成一个 `merged`。

从名字就能看出来：一个叫 upper，一个叫 lower，所以 upper 拼在上面、lower 拼在下面。而 merged 是假的、是虚拟的。

```text
   merged 上的查询
        |
        v
   upper 里有？ --有--> 返回 upper 的那份
        |
        没有
        v
   lower 里有？ --有--> 返回 lower 的那份
        |
        没有
        v
   不存在
```

每当你要问 merged 里面要文件的时候，它先去 upper 里看：有就直接返回给 merged；upper 里没有，就去 lower 里找，再返回给 merged；lower 里也没有，那 merged 里就没有。相当于它把这两个目录**叠起来**了。

叠起来以后有什么效果？我的 lower 里可以放好多文件，比如当成一个系统盘。而 upper 里可以对 lower 做修改——改完以后，lower 本身可以**不变**。这样我就可以创建好多好多个 merged 目录，于是就有有趣的应用了。

### 叠起来能干什么：并行刻盘与系统回滚

哪怕只能叠一层 lower、一层 upper，也有两个 killer application。

#### 一个 lower，十六个 upper

假设你有一个刻盘工具，一次性可以 burn 一个目录，比如一个 600M 的目录，写到一张光盘里。现在你的电脑上有 16 个光驱——16 个光驱就意味着 16 倍的带宽，因为假设内存和 CPU 的带宽是足够的，写光盘相对比较慢。

但你必须在用这个刻盘工具的同时，为每一张光盘写入一个**不同的 CDKey**。你会生成好多 CDKey，打印出来贴在光盘上一起卖。

于是就有了这样的局面：lower 上有 600M 文件，这 600M 对每张盘都一样；upper 上是一个 1M 的文件，每张盘都不同。有了 OverlayFS，我就可以创建好多个 upper：upper1、upper2、upper3……upper1 + lower 就是第一张光盘，upper2 + lower 就是第二张光盘。空间就省下来了。

> **提示**：注意刻盘工具的要求是"burn 一个目录和一个驱动器"。如果没有 UnionFS 这套机制，我又想并行，就必须把这个目录拷 16 份，再为每一份写入不同的 `CDKey`，然后并行去做。操作系统在拷贝的时候也许内部做了优化，但那终究是 16 份。

#### 把整个根当成 lower

另一个 killer application 今天大家都在用。

现在好多了，尤其是我用回 Debian 以后系统稳定很多。我以前用 Ubuntu 的时候，如果有一段时间没升级，然后做一次 `apt dist-upgrade`，基本上电脑就一定要成砖——它有一个很大的概率会成砖。那怎么应对电脑成砖？

你可以把**整个文件系统的根**当成一个 lower。听起来刚才那个机制很不起眼——"我可以把两个目录拼成一个目录"——但当我说"我把整个文件系统的根变成一个 lower"以后，就完全不一样了。然后我再在另外一个地方，比如另外一个设备上、另外一个驱动器上，做一个空的 upper，它也挂在 `/` 上。相当于我的文件系统根就变成了：旧的根是 lower，新建的目录放在另一块盘上作为 upper。

然后我做一次 `apt dist-upgrade`。这就意味着：**所有的 lower 是不变的**。apt 没什么神奇的，你去看它的 `strace`，它本质上就是写文件、写文件系统。所以因为这是根，所有写入都会落到 upper 里——它可能往 `usr/share` 里改点东西，可能在 `etc` 下改配置文件，还会有好多好多东西；在 systemd 里面它会有很多 triggers，往 systemd 里加东西。**你对系统持久状态的所有修改都是反映在文件系统上的**，这就是 persistence。

结果就是：你的旧系统还在，从来没有变过。下次系统重启、挂载的时候，你把 lower 和 upper 都挂上。如果它成砖了，不要紧——回到 initramfs 那个模式下做一个配置，把整个拿掉，你的系统又回来了。

这个机制看起来不起眼，但能力非常大。现在我们有 `overlayroot` 这个工具就可以做这件事，它真的做到了。你想对系统做任何潜在摧毁性的操作，都可以用它。试完了如果觉得 OK、没问题，你直接用一个 `rsync`，把里面的所有数据同步搬回到 lower 那一层——因为它是两个目录拼起来的，你总有办法访问 lower——相当于把这些修改 **commit 到磁盘上**了。

### OverlayFS 的实测行为：copy-up 与 whiteout

Linux 也给了这样的机制，叫 **OverlayFS**，而且做得更彻底：它可以挂载不止一个 lower。这正是 **Docker** 实现的一个非常关键的地方——Docker 里面本身就有 layer 的概念，它会不停地创建 layer，可以挂好多层 lower overlay 成一个。

但是只能挂一个 upper，同时还要给它一个临时目录叫 `workdir`。

```text
   mount -t overlay overlay \
       -o lowerdir=./lower \
       -o upperdir=./upper \
       -o workdir=./workdir \
       ./merged
```

`workdir` 是给操作系统用的临时目录，**必须是空的**，不空它会报错。只允许一个 upper，可以有多个 lower。

现在来干活，边做边看行为。

往 upper 里放一个文件，比如 `a.txt`。你会看到它在 upper 里是在的，同时对 upper 的修改会反映到 overlay 里——`echo` 一下，upper 和 overlay 会同时更新。

然后进 overlay，在 overlay 里修改 `a.txt`，把它改成 `456`。你会看到**在 overlay 里的修改同样会反映到 upper 里**。

再试着修改一个 `lower.txt`。你看，overlay 的变了，但 **lower 的没有变**；同时在 upper 里面多了一个 `lower.txt`——是我改过的那一份。再改一次，改成 `new lower`，upper 里会有新的副本。

最有意思的是**删除**。

```text
   lower/lower.txt        (永远不变，无论叠多少层 lower)
   overlay 里 rm lower.txt
        |
        v
   upper 里出现一个字符设备文件（whiteout）
   overlay 里 lookup lower.txt → 命中 whiteout → Permission denied
```

删除的时候我怎样才能让这个文件"找不到"呢？你在 hash table 里删除的时候，需要一个 **tombstone**。这里类似：lower 里的 `lower.txt` 永远不变，你 overlay 多少层它都不会变；但是在 upper 这一层里，会产生一个很有意思的对象——**一个字符设备文件**。这个字符设备文件你当然没有办法访问，你试着看，它会说 `Permission denied`。这是一个假装出来的、不存在的文件，叫 **whiteout** 文件。你删除，它就在 upper 里创建这个文件。

这样一来，你就可以实现一个网吧管理器：网吧里的用户会任意破坏你的电脑，你甚至愿意给他 grant 一个高的权限，但不要紧——你把系统做在 lower 里，给它一个 upper；等他下机，你直接把 upper 删掉就可以了。

### 从网吧、考场到 Docker 的镜像分层

#### 网吧、考场与考试管理

就像刚才说的那种更新模式一样，把系统做在 lower 里，给它一个 upper，下机就把 upper 删掉。

我们在做大规模的考试、竞赛管理的时候也是这么做的：把考试机器的 `/home` 做成一个 overlay，然后把这个 overlay 实际上的 upper 放在一个**用户访问不到的地方**。上午场考试的同学来了，他就在上午场那个 upper 里面工作；然后我直接给它 mount 一个别的 upper，下午场的考试又开始了。下午场的同学看不到上午的人的工作目录，但实际上的工作目录还是存在我的系统里的——当我最后把 U 盘回收的时候，我还是可以看到所有的东西。

当然，用它来解决网吧的问题就实在太是大材小用了。

#### Docker 的 layer 就是一层层叠上去的 upper

你们知道的 Docker。这份 Dockerfile 是我的 Online Judge 的 Dockerfile，里面就是一行一行的命令，它的设计也非常 Unix。比如它从一个已有的镜像开始，我们可以假设它是 Ubuntu 22.04——在 Docker 里面这叫一个 layer。

接下来我会配置一些东西，比如设置环境变量，以及这里有一个 `RUN`。每当我运行一个 `RUN`，就相当于启动一个虚拟机（当然这是容器），然后它会创建一个 upper，挂载上去，底下是上面那层的 Ubuntu 22.04。它把这批两层的文件系统放进虚拟机里，让虚拟机执行 `apt update`——`apt update` 不就写到这个 upper 里了吗？写到 upper 里面，等虚拟机运行结束，它就不再是 upper 了，它就是第一层。

```text
        ↑ 依次追加
   +------------------------------+
   |  RUN apt-get install -y ...   |  ← 新挂的 upper，执行完固化成 layer
   +------------------------------+
   |  RUN apt-get update           |  ← 上一层，已固化，之后只当 lower
   +------------------------------+
   |  FROM ubuntu:22.04            |  ← 最底下的 layer
   +------------------------------+
```

接下来再运行下一个，比如装软件 `apt-get install -y`。它会在这里再放一个 upper；刚才执行 `apt-get update` 的结果就变成了 lower 层，这层不再变化，而当前这层是 upper，它去执行 `apt install`。install 完了以后，你要再执行下一个命令，它又变成一个新的 layer。就这样一层一层一层堆上去。

所以如果你发现漏装了一个软件，该怎么办？一旦这个地方改了，比如我这条命令改了，我就需要**退到上一条命令创建出来的那个 layer，重新 replay 执行这条命令**。我如果改了这个，就要从这里开始执行后面所有的东西；如果我改了 `FROM ubuntu:22.04`，上面所有的东西都不对了，全都要从这里开始 replay 所有操作。

> **提示**：想要再装一个包，正确的方式是在最上面再加一个 `RUN`，比如再加一条 `apt install`，而不是回头去改中间那条命令。这样底下所有层都是 lower，只有新加的这一层是可变层，它挂上去执行完，又变成 append-only。

这又是 persistent data structure：append only，只有正在动的那一层是可变的，可变完了它又 append only。

好处是：你的任何一个 layer——实际创建出来的是一个镜像——比如这个安装完了以后，这个 layer 加上底下所有的东西，就变成了一个文件系统的快照。你就可以在这个基础上，把底下所有东西全部当成 lower，再创建一个新目录作为 upper，你就得到了一个虚拟机。你可以创建好多好多个 upper 目录同时运行，而它们**共享一个 lower**。这就是**容器**。

没有什么神奇的，确实没有什么神奇的。你的动机就是"我希望看到的目录可以是拼凑出来的"，而它能做到的事情远超你的预期。

### 跨过 CRUD 的边界

到这里你应该已经明显感觉到，我们开始做一些非常规的操作了。

前面不管是用 inotify，还是做快照，这些都是可以用 CRUD 实现的——本质上都能用增删改查实现：快照你就把它拷贝一份，inotify 你可以用遍历的方式来实现。

但是 overlay **不能**用增删改查来实现，它其实**改变了文件系统的语义**。你把两个目录合并，"合并"是一个新的语义操作。

所以再往后想一步：文件系统就是一个数据结构。我们早就学过数据结构了，数据结构你是可以随便实现的，没有人规定数据结构一定要按照某个方式实现。那**为什么我不能直接写一个 `fs.c`，自己来实现一个文件系统**？

`/proc` 就是内核里面的一个文件系统。它的 `getdents64` 系统调用是它自己提供的，所以它就可以有一些目录：你能 `cd` 进去，但你 `ls` 看不到。这个行为是由**文件系统的实现**确定的。

所以我就应该能够直接写一个 `fs.c` 来实现文件系统。而你能想到的事情，你就一定能做到。

### FUSE：把文件系统搬进用户态

#### struct fuse_operations 就是全部

最简单的做法是在内核里实现一个内核模块，装到内核里，让内核支持这个文件系统。但实际上还有更通用的办法，叫 **File System in User Space**，也就是 FUSE。

```text
   open / read / write / readdir / getdents64 ...
              |
              v
       +-------------------+
       |  VFS（内核通用层）  |
       +-------------------+
              |
              v
        FUSE 驱动（内核）
              |
              |  转发
              v
   +-----------------------------+
   |  我的用户态进程              |
   |  struct fuse_operations {   |
   |     open, read, readdir,    |
   |     write, setxattr, ...    |
   |  }                          |
   +-----------------------------+
              |
              v
       我自己虚构出来的数据
```

你的操作系统内核会把 lookup、read、write 这些操作**转发到 fuse driver**。你所要做的所有事情，就是实现一个这样的结构体。你去看手册，一个 `struct fuse_operations`，比如读、写、打开目录、遍历目录，甚至这个结构体里面还有一个 `setxattr`——FUSE 是支持 extended attribute 的，它是一个 Unix 兼容的文件系统。

从此以后，这个文件系统就再也不是一个 CRUD 了。你可以用它来实现 overlay 的语义，也可以实现任何一个文件系统：它背后**没有任何文件**，但你可以虚构出一棵目录树来，每一个目录和文件的读写都由你自己决定。

你甚至可以直接在 Windows 上面实现一个 `/proc`。理论上说，没有任何问题。

#### galgame 文件系统：一个能玩的例子

还记得那个 galgame 吗？galgame 是一个比较令人印象深刻的例子。我做了一个 galgame 文件系统，叫 **ggfs**，就是用 FUSE 做的。

我在开头声明了 `FUSE_USE_VERSION 26`，然后找到 `fuse_operations`。我只要实现这个结构体——`open` 是什么、`read` 是什么、`readdir` 是什么。我只要实现这个 `readdir`，我想给它什么文件就给它什么文件；它问我要文件数据的时候，我想给它什么数据就给什么数据，完全由我的文件系统实现来提供。**代码是 Turing-complete 的**，所以理论上说你可以做任何事。

```bash
make fuse
ls /tmp/ggfs
mount | grep galgamefs
```

效果是：这次不再是我建了一大堆虚拟链接了。一开始 `/tmp/ggfs` 是空的。我 `make fuse`，就进入了 galgame 模式。这时候进 `/tmp/ggfs`，如果我查看 mount，可以看到有一个 `galgamefs` 挂载到了 `/tmp/ggfs`。

于是这个目录里面已经有文件了。这些文件完全是我虚构出来的，**没有一个对应磁盘上的真实文件数据**。我可以 `cat` 这个文件——我打开什么，它就返回原样的数据，这是由程序生成的。所以理论上说，它完全可以返回一个随机数给我。

还有一个行为：我往一个文件里面写入任何数据，**我的文件系统内部的状态就会感知到这一点**，然后这个 galgame 就启动了。你看目录就变了。只要往任何一个文件里写入数据——而写数据也就是回调了我 FUSE 实现里面的一个 API——它就可以做任何计算，于是它可以驱动整个 galgame 的运行。

这就是 FUSE。

#### 疯狂的人类已经用它干了什么

用 FUSE 可以做几乎任何事情，而且疯狂的事情人类已经干了很多。

**把远端的东西搬到本地。** 你可以把一个远端的 ssh 目录变成一个本地目录，映射到本地。因为你是 FUSE，只要把所有的目录操作**代理**到那个地方的目录操作就行了。你还可以把一个远端的 git 仓库变成一个本地目录。

**用数据库来存文件系统。** 有一个 dbfs：有些文件系统，比如 FAT，是不安全的，崩溃的时候可能会不一致；而数据库可能确实做到了一致，因为它是 append-only 方式实现的。那我就可以在这个基础上用 FUSE 实现一个数据库文件系统，比如 `filesystem.db`，用一个像 SQLite 这样的数据库引擎把你的文件系统保存在数据库里，你的文件系统操作全部改成 SQL 查询。这都是可以的。

**反过来：把不是文件系统的东西变成文件系统。** 这马上就能想到——就像 galgame 一样，一个不是文件系统的东西，也可以挂载到文件系统里。

比如说一个 JSON 文件，一个 key-value：我可以把 key 变成目录，把 value 变成目录里的一个 `value.txt`；我往那个 `value.txt` 里写入，它就去更新那个 JSON；你每次读那个 JSON，读到的就是最新的、up to date 的那个 serialized version。

再比如，你可以把一份什么样的学习资料真正隐藏起来：你让 `getdents64`、`readdir` 系统调用看不到这个文件，但是你**可以 `cd` 进去**——这时候只有你知道那个名字，你才能 `cd` 进去，没有任何人能进去。

```text
   ls /mnt/xxx          → 看不到（readdir 不报告）
   cd /mnt/xxx/秘密名字  → 能进去（lookup 命中）
```

所以这是一个 **everything is a file 的终极实现**。

### 回到那句话：文件系统就是一个数据结构

我们说了，文件系统是一个树结构。就这一句话。

然后你从增删改查开始，只要你**有想象力**，借助操作系统机制，你就可以做任何的事情。Git 是这样，Btrfs 的免费快照是这样，OverlayFS 是这样，FUSE 也是这样——它们全都是同一句话在不同层次上的展开。

## 在块设备上实现文件系统：从 superblock 到 FAT
> 对应块：BLK51 | 覆盖分集：P26上 | 块标题（分集名）：《文件系统实现和崩溃一致性（上）》

### 文件系统就是提供一棵目录树的任何东西

上节课我们讲了文件系统。什么是文件系统？文件系统就是给你提供一个目录树状结构的任何东西。

这话听起来有点不讲道理，但我们其实从最开始就反复在用这样的东西：`procfs`、`sysfs`，它们都是虚拟出来的文件系统，本没有一个真实的存储设备在后面撑着。甚至你在用户态也能实现它——文件系统 in userspace，FUSE，你只要实现得够遍历目录、能创建目录、删除目录、`get attributes`、`open`、`read`、`write` 这一套基本功能，再加一个目录树的结构和文件的读写，它就是文件系统。

例子可以荒诞到什么程度？我上次甚至做了一个 `galgame-fs`，它维护自己的一套内部状态——虽然我说它是文件系统，它其实不是一个文件系统，它是一个 galgame，它能在屏幕上给你把一个游戏显示出来。同时它对外暴露一棵目录树，你读写那棵目录树就能操作这个游戏。所以理论上，只要你做出来的东西符合我们反复使用的那套 Unix 目录树结构，它就是文件系统。

今天要讲的是文件系统的实现：我们要在 block device 上，把一棵目录树做成一个真正的数据结构，并且做到 persistence——持久化。持久化一直是操作系统里非常重要的主题。

先看一下我们要把它建在什么东西上。`mount` 这个系统调用你们见过，它要求一个 block device。这个 block device 对外其实就三个接口：一块一块地读、一块一块地写，以及等待正在途中的写落盘。真实的设备会比这复杂一点，比如它有一个队列，你往队列里提交请求，还要能知道这个请求什么时候完成；但简单起见，你可以把它类比成并发程序里的共享内存。

```text
   shared memory (concurrent program)        block device
   +--------------------------------+   +----------------------------------+
   | byte array, byte addressed     |   | block array, block addressed     |
   | load / store                   |   | read(#blk) / write(#blk)         |
   | barrier / mutex                |   | block sync (wait in-flight write)|
   +--------------------------------+   +----------------------------------+
```

内存是一个字节序列，按字节寻址，L1/L2/L3 到内存那一整条 memory hierarchy 帮你把存储栈藏了起来，你用 load 和 store 就能按字节读写；block device 类似，它是一个 block array，一个数组，元素大小可能是 4KB，软盘上则是 512 个字节，你以块为单位整体读出来、写进去。并发程序里我们说 data race 很危险，两个线程同时读写一个内存位置会出事，于是要用互斥锁做互斥；block device 也有对应的东西，就是那个 sync 指令，它可以把并行变成串行，等所有在途的写都落盘了再返回。

有了这三个操作，你就能实现任何数据结构，就像你可以只用 load 和 store 实现内存里的一切数据结构一样。

但我一打这个并发的比方，你们大概马上就有感觉了：我又一次打开了魔鬼的盒子。我们说多处理器编程是从入门到放弃，那时候打开过一次魔鬼的盒子；今天我会再打开一次。文件系统的实现本身相对简单，但你要实现一个 crash safe 的文件系统，就会发现你撞上的问题和并发编程里一模一样。这很有意思。

### 从 lsblk 到 LVM：块设备也能一层层虚拟出来

刚才那个「能读一块、能写一块、能等落盘」是过度简化后的存储设备模型。真实的设备比这个稍微复杂一点。

你在终端里执行 `lsblk`，确实能看到一些设备，包括 block device 和它的分区：比如 MMC 是我的 SD 卡，`mmcblk0` 下面的 `p1`、`p2` 就是它的第一个和第二个分区；你可能还会看到一个 NVMe 的分区。

一个 block device，比如一块磁盘、一个 SSD 或者 HDD，本质上也是一个数据结构，而这个数据结构也是有 specification 的。我们今天主要用到的是 GPT——注意不是那个 ChatGPT 的 GPT，是 GUID partition table，GUID 分区表，它是 UEFI specification 的一部分。UEFI 就是那个固件的 specification。

#### 为什么分区表由固件厂商来定

你们想，为什么磁盘的数据结构布局要由固件的标准来规定？因为系统一启动的时候，就是 firmware 要去看这个磁盘：如果它解析不了这个分区，它就不知道操作系统到底装在哪、数据盘在哪、该怎么挂载。所以所有可以被启动的磁盘都遵从这套标准。

有一系列工具可以去读它、写它。比如你想做一个可以启动的 U 盘，就要把它格式化成这样的 GUID partition table。它就是一个数据结构，它告诉你头在哪、数据结构在哪、怎么识别这个文件系统是什么、怎么识别这个分区有多大、每个分区落在什么位置。你读存储设备最前面的那一段字节，就能知道第一个 partition 在哪、第二个 partition 在哪。

反过来也一样：如果我把一个完全被我写成全 0 的存储设备插上来，它是识别不出 `p1`、`p2` 的，只能看到一个光秃秃的 `mmcblk0`。我确实可以干这么一件事——把 `/dev/zero` 直接重定向到 `/dev/mmcblk0`，这台机器马上就等于重装了：全刷成 0 之后，你就再也看不到 `p1`、`p2`，只剩一个 block。

GPT 这个数据结构也不是只存在一处：

```text
  block 0              : 兼容用的 MBR
  block 1              : GPT header（整个磁盘数据结构的 root）
                         -> 指向分区表项
  ...
  partition 1 .. pN    : 各个分区的区间
  ...
  最后一个 block        : GPT header 的备份
```

读图的方式是：根不在设备的第一个 block 上，第一个 block 留给兼容用的 MBR，GPT 真正的头部在第 1 个 block；而且它会在磁盘尾部再存一份备份，这样头部一旦损坏，顺着尾巴往前找还能找回来。

#### 八个磁盘虚拟出一个磁盘

设备也可以是虚拟的，而且能一层一层叠很多层。

如果你想挂载一个文件系统里面的文件——像我前面给大家展示的那样，把一个 `.image` 镜像，一个 FAT32，挂载到我自己的文件系统目录里——背后靠的就是这一整套虚拟化层。Linux 里这套东西叫 LVM，logical volume manager。它可以一对多，也可以多对一，也可以多对多。

所以理论上我可以创建好多个 image，`1.image`、`2.image`……通过 loopback device（回环设备）把它们变成 `/dev/loop0`、`/dev/loop1`，每一个看起来都像是一个 block device；再把这些虚拟出来的设备做成一个 volume group，然后在上面又创建好多个 logical volume。因为本质上所谓块设备就是一个 block array，原则上我甚至可以用多块磁盘虚拟出一块更大的磁盘。你们如果读教科书看到 RAID 那一章，我们也可以用多块磁盘去虚拟出一块更快同时更可靠的磁盘——虽然今年课时可能来不及讲 RAID 了，课后可以去读一下 OSTEP 教科书上讲 RAID 的那一章，也很精彩。

我就做了这样一个脚本，而且完全是 vibe coding 的，我几乎没管中间的过程，就是让 AI 帮我实现了两个脚本，`lvm-demo` 和 `lvm-cleanup`。`lvm-demo` 跑起来干了这么多事：

```text
  disk1 .. disk8            8 个 32 MB 的普通文件
        |
        v
  /dev/loop0 .. /dev/loop7  回环设备（看起来就是块设备）
        |
        v
  physical volumes          一个个"物理卷"
        |
        v
  vg-demo                   合成一个 224 MB 的虚拟磁盘
        |
        v
  GUID partition table      格式化，切成 p1 和 p2
        |
        v
  p1 = FAT, p2 = ext4       两个不同文件系统的分区
```

它先创建 8 个 32 兆的磁盘，再创建好多回环设备，于是我就有很多块设备了；这些块设备就是一个个 physical volume，看起来就是一个一个的磁盘；然后把它们虚拟成一个虚拟磁盘，叫 `vg-demo`，创建出来一看有 224 兆；再把它格式化成 GUID partition table，切成 `p1` 和 `p2`，一个是 FAT，一个是 ext4。全部完成。

也就是说，你们现在需要的只是有概念。里面用到的很多 LVM 工具，以前都是要哎呀先查手册、先把概念弄清楚，再自己去执行那些命令；现在不需要了，你只要知道有这个概念、知道这件事能做成就可以了。我现在就有 `p1` 和 `p2` 两个目录，然后我在 `p1` 下面写 hello 到 `a.txt`，在 `p2` 下面写 world 到 `b.txt`。注意这些东西都是虚拟的，最后都会走到回环设备背后的 `1.image`、`2.image` 这些文件上。

写完之后我做一次 `sync`，确保系统真的把这些写入落进磁盘、落进文件里。然后我们看一件有意思的事：hello 和 world 会在哪？我在 `p1` 里写了 hello，在 `p2` 里写了 world，它们分别落在 `a.txt` 和 `b.txt` 里——而这些数据真的被正确地路由到了那两个虚拟磁盘的文件里。原因就是我做了前一半和后一半的分区：有一个 GUID partition table，前一半是一个文件系统 `p1`，后一半是另一个文件系统 `p2`，数据就真的躺在那两个磁盘镜像文件对应的字节上了。

#### 全是 ioctl：为什么复制一份 Linux 这么难

我还特意让它把所有的 strace log 都打印出来。我只跟 AI 说了一句话：你能不能帮我把每一个 LVM 相关命令里面的 system call 挖出来？它就把整份 strace log 用管道送给大语言模型，让模型思考两秒钟，然后告诉我：第一步建立 loopback device——它在 `/dev/loop-control` 这个文件上做 `ioctl`，用 loop control get free 拿到一个空的 loop device，于是创建出好多回环设备，主要用的就是 ioctl。到 `pvcreate` 初始化物理卷的时候，LVM 开始起作用了，它用的是 `/dev` 下 mapper 里的 control，一个映射器，也是 ioctl；它确实找到了 block device 的大小，然后各种写入标签。再往后是创建组、创建逻辑卷，和回环设备那一套 API 是一样的：先用 ioctl 查询 device mapper 的能力，再创建 device mapper 的设备，这是关键的步骤，通过 ioctl 把 name、UUID 这些东西写进去，用的是 `DM_DEV_CREATE`；分区的映射，也是为每一个分区创建对应的 DM 设备。

总结下来，全都是用 ioctl 实现的。

这就是为什么你想再复制一份 Linux 非常困难。你看着好像只要实现 `read`、`write`、`open` 就可以了，不是这样的：一旦你碰到 ioctl，你会发现内核里几乎每一个子系统，它的 API 都是用 ioctl 这种东西暴露出来的，甚至有些是通过文件系统、通过 sysfs 暴露出来的。这些复杂性你都得实现，所以想实现一个兼容的 Linux 就非常困难。

现在的 NVMe 硬件上有 NameSpace 支持的时候，它有点像一个硬件级的 LVM，但那是真实的块设备。不管怎么样，块设备你还是可以这样理解：虽然有很多有趣的功能，可以层层虚拟化，但最终一个 block device 就是 read、write 和 sync 这几个操作。

### 在块设备上写文件系统，麻烦在哪

在这样的东西上面实现一个文件系统，面临的困难是什么？

文件系统本质上就是一个数据结构，直接实现它就可以了。真正的困难在于：如果你想实现得高效，那还是很有挑战性的，因为你读写数据都会造成读放大和写放大。

#### 写一个字节的代价

你很多时候真的只想要一个字节。比如你只想要这个文件的大小，或者只想要这个文件的 stat——什么时候修改的这些信息。但为了读到这个信息，你就得把一整块数据全部读进来。所以你的数据在磁盘上的排布就变得很重要。

再往下看写：你想更新文件里面的一个字节，你不仅要更新这一个字节，你还会更新它的 modification time，也就是它的元数据，这就涉及到多个块的写入。而哪怕只是一个块的写入，你也得先把这个块读出来，把中间的部分改掉，再写回去。

写一个块的时候，又会牵涉到 SSD FTL 里面的 map table 的修改。SSD 里面有一个像页表一样的东西做地址翻译：你看到的「我要写第一块」，实际上你写的不是第一块，而是第一块经过映射之后的那一块，因为那是一个虚拟地址。你要维护这个虚拟地址，就又多了一个数据结构，而这个数据结构又是 copy-on-write 的；它要拷贝，就会先拷贝根节点，然后一层层往下拷贝。所以在理论上，你写一个字节，可能会有几万倍甚至几十万倍的写放大。当然这个例子比较极端，你真的是只写一个字节；退一步，写一块依然会有若干倍的读写放大，甚至到十倍都是有可能的。

#### buffer cache：缓存和局部性一个都不能少

所以你们也知道，在文件系统这一层要做缓存，和 memory hierarchy 一样。内存那套有一级、二级、三级缓存，文件系统也需要在内存里留一份数据。

于是 block read 和 block write 看起来就是 read disk——我可以对它做 `bread` 或者 `bwrite`。但操作系统内核会统一分配一份缓存，Linux 内核里这个东西叫 buffer cache。这是个很糟糕的名字，因为「buffer」和「cache」这两个词连起来其实说不通，这是历史原因，不应该这么叫——它就是一个 cache，文件系统的 cache。

有了它，`bread` 就可以类比成共享内存里的 load，`bwrite` 就是 store，很好理解：你 load 就从 cache 里 load，cache miss 说明 cache 里没有，它就去设备里找；而设备如果本身是一个虚拟设备，它又会往下走，走到 loopback device，再走到文件里，经历一层层的转化。写的时候和 memory hierarchy 不太一样：因为我已经是一个块的写了，所以这个块可以直接写进 cache，把旧的覆盖掉，这就相当于 cache hit，下一次 read 就直接从 cache 里读走。这就是你要做的一个优化。

其实你会发现，操作系统里很多事情和另外的系统——存储系统、内存系统——做的事情是一样的，它也在用 locality 的原理。如果你想让文件系统高效，你就希望尽可能把经常会一起访问的数据结构放到一个块里，这是很自然的想法：这一次读到了这个数据结构，下一次读它临近的那个数据结构时，cache 就 hit 了，访问速度就降下来了，一定程度上减少了读写放大。当然有些读写放大还是不可避免的，比如我就是要写一个字节，那确实会造成比较显著的读写放大。

### 文件系统要实现什么

回到正题：在 block device 上我们要实现的是一个目录树。反正任何东西都是根，比如 `/bin`、`/home`，下面可以有目录，可以有文件，也可能有链接——在链接的意义上那个图其实画得不是特别好，不过这不重要。比如 `ls` 就是一个 byte array。你要用 block read、block write 把它做出来。

为了做出这个数据结构，有好几样东西要一起实现：

- data：文件真正的字节内容；
- 每一个目录或文件的 metadata：它的大小、它的名字（名字也是 metadata 的一部分）、访问它的权限 mode、它的时间戳。上次我给大家展示过，文件系统里每次修改你都感知得到，尤其是在 inotify 的时候；而且它的上层目录的 modify time 也会被一起改掉；
- 目录树状的结构：你们实现一棵树的时候，可以定义一个 struct，里面放一个 vector of children；磁盘上同样需要这样一个树结构。

#### 先看看真实文件系统里都装了什么

如果你想实现一个高效的文件系统，最好的做法是先去观察现有文件系统里的统计。这就意味着你得先做一个 study，然后厚着脸皮去找各种人说：你的文件系统能不能借我遍历一下？我不窃取你的隐私，我只是想看一下文件的分布。然后到各种场景里去取数据——数据中心里、个人用户的 PC 上、不同的人手里——把数据拿出来之后，就能得到一些结论。这些结论稍微有点过时了，但基本上还符合我们今天 Unix 系统里的文件分布，尤其是个人电脑；数据中心会非常不一样，因为数据中心里大部分是管理用的数据块。

- 绝大部分文件都比较小，这符合预期。我们生产的源代码不可能塞在一个巨大无比的文件里，那样维护会变得很困难，一定会拆开；文档性的内容也都不会很大；图片这类 binary 也不算特别大。
- 少数大文件用掉了绝大部分空间（a few big files use most space）。一个数据库、一部电影，确实会占掉磁盘的绝大部分。
- 一个目录里面的 entries 不会太多。如果你把项目组织成几千个文件放在一个目录里，浏览起来会相当困难；当然现在都是 AI 在浏览，好像也没有那么大的关系了。
- 文件系统大致是半满的（file systems are roughly half-full）：不管你留了多大的门限，人总会想办法把它填得比较满。

这些 findings 就能指导你设计一个高效的文件系统。

#### 由此要回答的几个问题

你要回答的其实就是几个问题。

第一个：metadata 怎么存？是直接跟数据存在这儿，还是存在别的什么地方？

第二个：data 怎么存？一个文件是一个 byte array，它由好多块组成——那就有第一块、第二块、第三块，这里需要一个数据结构。

第三个：一个大文件，你怎么知道它的每一个 offset 对应的块在哪？文件可能很小，比如 2KB、4KB；也可能很大，几十个 GB。这是一个非常现实的现实问题，你需要一个数据结构来存这个映射。

理论上你甚至可以这样干：写一个爬虫，把这个世界上所有跟数据结构相关的论文全部爬下来，然后拼一个 prompt 给大语言模型：「对于这个数据结构，我要在磁盘的特性上实现文件系统，优化什么样的 workload，这是不是一个好 idea？」把所有不好的 idea 都删掉，你就得到了一个新的文件系统实现。这基本上就是我们今天的标准答案——如果你要做文件系统的话。

所以这事其实就这么简单，我就可以下课了。我剩下的内容，都是相当于把人类已经沉淀下来的知识跟大家 overview 一下。

### 所有的数据结构都要有一个入口

你要在一个 block device 上实现一个数据结构，它一般来说是一个 partition，就像我们前面看到的 `/dev` 下 `mmcblk0p1` 那样的第一个 partition。它也是一个字节序列，一个 block 一个 block 的序列。

而所有的数据结构都要有一个入口。你们的链表一般会有一个 head；一棵二叉树会有一个 root 指针指着它。你看各种各样的文件，它们其实也是数据结构，比如 bitmap；比如我做 Mandelbrot set 的时候为了输出一个图像，用 `printf` 直接输出一个 `.ppm`——就一个 `printf`，最后你真的能在浏览器里看到那张图片，这对我这种想在上课做 demo 的用途非常友好。这些都是数据结构。ELF 也是，它有一个头，头里有 magic number，帮助 `file` 命令和加载器识别这是不是一个 ELF；头里还有一个结构体，结构体里有 ELF 的 entry、文件的大小、program header 的数量这些东西。

所以，第一件事是：数据结构都有一个 root，指向某一个 block，一般来说就放在最头上。

GUID partition table 也是数据结构，所以它也有一个 root，放在整个分区表的位置上。它不是从整个设备的第一个 block 开始的——第一个 block 一般还是兼容的 MBR，后面才是 GPT 的数据结构，这是分区表的 root，相当于整个磁盘的数据结构的 root。另外它会在磁盘的尾巴上再存一份，备份两份：分区信息丢了之后要恢复这块磁盘会比较麻烦，虽然也不是做不到，备份一份，损坏了顺着尾巴往前找还能找到它。

### superblock

在这个分区里面，头上也有一个数据结构，它的名字就叫 superblock。这是对整个数据结构来说最关键的一个 block。如果你只被允许损坏一个 block，并且想给文件系统的使用者造成最大的麻烦，那你就应该把 superblock 抹掉。当然这些信息还是可以恢复出来的，但会给他造成一些麻烦。

superblock 里通常有一个 magic number，然后有文件系统意义上的信息，比如 block 的 size。这里有个容易忽略的细节：你的磁盘可能是 512 个字节一块，但文件系统可以说，好，这个东西它按 512 字节给所有块编号 1、2、3、4——如果磁盘比较大，这个编号的位数就会很大。比如 FAT32 用 32 位的 block number，如果每个 block 只有 512 字节，那么最多也就是 512 乘以 $2^{32}$ 这么大，最大文件就只能这么大；但如果它不按 512 字节，而是按 4KB 作为逻辑块，虽然磁盘还是 512 字节访问，我的文件就可以更大一点。

superblock 里还有别的文件系统关键信息：这个文件系统还有多满、还有多少空间、还能剩下多少个文件可以分配、数据结构的起始位置和大小。`mkfs` 的时候如果你去 strace 它，就会看到它在前面写上这个数据结构；而 `mount` 命令其实也是根据 superblock 去确定文件系统的类型。

> **提示**：superblock 是「文件系统自己的 block 大小」，和「设备物理上的扇区大小」是两件事。物理 512 字节的设备上，文件系统完全可以按 4KB 一个逻辑块来编号——这决定了它能寻址到多大的空间，也决定了 FAT 这类「用块号当指针」的设计能撑多大。

### File Allocation Table：拿一个 next 数组当文件系统

既然知道这是一个数据结构，就可以开始设计了。第一个比较容易理解、非常简单的设计是 File Allocation Table。它可以在硬盘上用，也可以在软盘上用：比如 5.25 英寸的软盘，单面是 160KB。160KB 意味着，如果块是 512 个字节，它总共只有 320 个 block，320 个 sector。

你想想，只有 320 个块，你要在它上面构建文件系统，设计思想应该是什么？肯定不能是花哨的数据结构——你在数据结构里增加的每一分复杂性都浪费了空间。为了换来更高的查询效率而多牺牲一点空间，这种事你不想做，你想要的是极致的空间节约。

顺便说一句：曾经我觉得我自己的操作系统课能给大家带来一个很重要的 takeaway，就是你们可以去读手册。因为我们有个文件系统 recovery 的实验，你必须对 FAT 里面的各种东西非常清楚——以前你不知道，因为从来没做过这事。然后你会发现读手册其实没有你们想象的那么困难，因为它总是一点点来的；如果上来就给你一份 PCIe 的 specification，你直接崩溃。FAT 这个 specification 长度适中，你可以对着它写代码，最终把代码调对的时候，你会得到一些比较宝贵的经验。当然今天好像也不需要了——直接让 AI 读 specification 就行，而且 AI 确实非常擅长处理这种手册。

#### BPB：FAT 的 superblock

FAT 的 specification 里，3.1 节有一个叫 BPB 的结构，叫作 common to FAT12、FAT16 和 FAT32——先不管 12、16、32 是什么意思。这就是它的 superblock，里面有很多字段：

- OEM name：可以存一些字符串信息；
- bytes per sector：这个存储设备每个扇区有多少个字节，所以它可以兼容 512、1024 等各种各样的设备——FAT 不只兼容一种磁盘；
- cluster：这就是前面说的那件事。物理上你访问磁盘是按 512 个字节访问的，但你可以把任意 $2^k$ 个 512 字节绑成一个 cluster。比如 $k=2$ 就是 4 个 512 字节，也就是 2KB，这叫一个 cluster，然后有 cluster number 1、number 2、number 3……这是它的核心概念。

为什么它叫 FAT 文件系统？就因为它核心的数据结构叫 File Allocation Table，文件分配表。它是一张「cluster ID 到某个值」的表。

在 FAT12 里，一个表项是 12 个 bit，12 个 bit 只能存 0 到 4096，是一个很小的文件系统；FAT16 就到 65536；FAT32 就是 $2^{32}$。

| 变体 | 表项位数 | 能编号的 cluster 数 |
| :--- | :--- | :--- |
| FAT12 | 12 bit | $2^{12}=4096$（实际可用还要更少一点） |
| FAT16 | 16 bit | $2^{16}=65536$ |
| FAT32 | 32 bit | $2^{32}$ |

你可以把它理解成一个 next 数组。磁盘在 FAT 里已经被编成好多 cluster，也就是好多块；前面有一些区域是不用的（对应那棵树结构图上的一些其他区域），从某处开始是 cluster number 1、2、3……

于是什么是 next？next 就是一条链表。三种取值把整件事说完了：

| next 的值 | 含义 |
| :--- | :--- |
| 另一个 cluster 号 | 这个文件的下一个 cluster 在哪 |
| 0 | 这一块空闲，可以分配 |
| 结束标记 | 文件到此结束（约定成全 1 的保留值，可以理解成 -1） |

假设 cluster 大小是 4KB，`next[1] = 3`，意思就是 cluster 1 里装的是文件的第一段数据，接下来第二段在 cluster 3，第一个 4KB 在这儿，第二个 4KB 在那儿。如果 `next[2] = 0`，那这一块是 free 的，可以分配，说明它没用过。如果 `next[3]` 是结束标记，那就说明这个文件到这块就结束了，它最多只有两块、最大 8KB；你只要再存一个文件 size，就能知道这最后一块里到底有多少字节是真正属于这个文件的。

```text
  cluster 里的数据 :  [ 第一段 4KB ]      [ 第二段 4KB ]
                          |                    ^
                          |  next[1] = 3       |
                          +--------------------+

  next 数组（每项一个 cluster 的"下一跳"）：

     index:   1      2      3      4      5
     value:   3      0     EOF     -      -
                \     \      \
                 \     \      `- 文件到此结束
                  \     `- 空闲，可以分配
                   `- 下一块在 cluster 3
```

#### 个 bit 怎么压进 3 个字节

这样的数据结构，对于只有 320 个 sector 这么小的磁盘，肯定是最合适的，因为它非常紧凑：FAT12 里一个指针就是 12 个 bit，而 12 不是 8 的整数倍，所以它把两个 12 bit 打包成 3 个字节按位紧压——3 个 byte 正好是 24 bit，一个 12 bit 属于上一个指针，另一个 12 bit 属于下一个指针，非常非常省空间。

```text
      byte 0            byte 1            byte 2
   +-----------+    +-----------+    +-----------+
   | ptr[n]    |    | hi4 | lo4 |    | ptr[n+1]  |
   | low 8 bit |    | of[n]|[n+1]|    | high 8bit |
   +-----------+    +-----------+    +-----------+
        \_______________/    \_______________/
             ptr[n]                 ptr[n+1]
             12 bit                 12 bit
```

而且在一个 320 个扇区的文件系统里，绝大部分都应该是很小的文件。小文件配这样一条线性链表，你觉得性能可能比较低，其实完全没有问题：因为整个 FAT 是可以一起读出来的，一旦读进内存，就相当于你一下子把好多 next 指针都加载到了内存里，你几乎就是在内存里遍历这个数据结构，性能不是大问题。

#### 大文件与碎片：FAT 的死穴

但如果是一个很大的文件系统，情况就不一样了。FAT 在小的存储设备上完全没有问题；可到了几十个 GB 的文件系统，里面可能有几 GB 的电影这样的大文件。

这时候 next 有两种情况。一种是最理想的：next 都是连续的，`next[3] = 4`、`next[4] = 5`、`next[5] = 6`，你访问一个文件的时候，它在 cluster 里存的一大张也是连续的。

但分配的时候并不是这么回事。你的文件会不停地创建、删除、再创建、再删除，这跟 memory allocation 一样：这有一个空的块，可能被分配走了，过会儿它又被回收了；时间长了就会产生碎片。一旦产生碎片，FAT 就不连续了，它可能指向一个很远的地方，再指回来，又指到一个很远的地方，来回跳。

```text
  连续（理想）：  464 -> 465 -> 466 -> ... -> 546

  碎片化：        2407 -> 2408 -> ... -> 2431
                        |
                        `-- FAT 里跳到很远的地方 --.
                                                  v
                  2511 -> 2512 -> ... -> 2587
```

如果是一个很大的文件、碎片又很多，就会造成很大的读放大。因为 FAT 本身也很大——FAT32 在很大的磁盘上 entries 非常多，于是你这段的 next 读出来了，它的下一个 next 在另一个 block 里，你就得把那个 block 也读出来；再下一个 next 又在别的 block 里……反复地读块，读放大就非常严重。

#### 用 mmap 把镜像当成数据结构来解析

我们其实给大家准备了一个实现去检查 FAT 文件系统的小工具，一个 `.c`。这个代码对大家很有用，因为你们要做实验，实验就是解析 FAT 文件系统，而你们的起点就是这个示例代码。你会看到它是真的把文件系统当成数据结构来处理的：我们直接用 `mmap` 把一整个磁盘镜像映射到进程的地址空间里。

一旦把整个磁盘映射完，FAT32 的 header 也就是它的 superblock，我直接就变成了一个指针，它就是一个数据结构。然后我可以从这个指针里读出各种各样的信息：bytes per sector、total sectors、volume number、serial number，等等。

有了这些，我就可以用遍历数据结构的方式去遍历它——一个 DFS scan，用深度优先搜索把整个目录树扫一遍。拿它去读实验要求里的那个镜像，目录结构是可以正确显示的，跟你们的实验一样。那是一个 64 兆的 FAT32 文件系统，`FS type` 就是 FAT32，你能看到好多文件：有一个叫 `DCIM` 的，假装是相机拍摄的目录，里面有很多 `.bmp`。

有些图片，比如用了 83 个 cluster，从 464 到 546，它就是连续的，next 一路 464、465、466……连下去。也有一些文件是不连续的。这些不连续是我特意造出来的：我会不停地往里面写文件，然后删掉，写文件、删掉、写文件、删掉，相当于不停地 allocate 一些随机大小的内存，时间长了 allocation 和 free 之后就会产生碎片。产生碎片以后，一个文件就可能分散在连续的几部分里：从 2407 到 2431，然后 2511 到 2587。

这些都可以用程序把它当成数据结构来解析，所以没有什么神秘的。

### 目录在 FAT 里也是一个文件

文件的数据讲完了，接下来是目录。目录怎么弄，手册里也有。

最早的 FAT 里，存储一个文件名用的是固定的 11 个字节——从 0 到 11，今天管它叫 short file name，11 个字节，8.3 的格式。比如 `AUTOEXEC.BAT`：在 DOS 里，如果它看到这个名字的文件，它就会自动运行它。如果你的 C 盘、A 盘，比如软盘的根目录下有一个 `AUTOEXEC.BAT`，系统启动时就会自动去执行它，跟你们的 `.bashrc` 差不多。

它总共只存 11 个字节，其中默认有 3 个字节是扩展名，所以文件名最多只有 8 个字符。这个非常有历史感——今天你根本不能想象这件事，你随便就可以起一个很长很长的文件名。

这也解释了为什么我们那个工具里会看到波浪线 1、波浪线 2、波浪线 3：如果文件系统是在今天创建的，为了保持向前兼容（比如在 DOS 里你依然可以访问这个目录），一个很长的文件名如果前缀又都相同，它就会把前缀截断，用 `~1`、`~2` 去区分这些文件。这是 FAT 的一个很有意思的特性。

#### dentry 里有什么

我们的目录实现，其实也是一个文件：它也是一个数据，也靠 next 串起来。比如你的目录里有好多好多项，一万个文件，这一万个文件就是不停地 next、next、next，所以它也是一个线性表。这个线性表里是一堆 directory entry，我们叫它 dentry，就是目录项。

```text
  +----------------+--------+  ...  +-------------------+-----------+
  | name           | attr   |       | first cluster     | file size |
  | 11 bytes (8.3) |        |       | high(2B) + low(2B)|           |
  +----------------+--------+  ...  +-------------------+-----------+
          ^             ^                     ^                ^
       文件名      属性位：read-only /      第一块在哪      文件多大
                  hidden / system /           |
                  volume ID / 目录(0x10)      v
                                       顺着 next 一路找下一块
```

dentry 里有一个名字，有一个 attribute：这里的位告诉你它是不是 read-only、是不是 hidden、是不是 system、是不是 volume ID、是不是目录，比如 `0x10` 就说明这是一个目录。这些都是文件的 metadata，还有名字、attributes，以及别的字段，其中 file size 是非常重要的。每个目录里就存了它目录下所有的文件。

也正因为目录项里存的就是这些东西，你会看到这个文件系统是不支持链接的——它就是一个最简单的实现。

#### 遍历目录，就是把目录当成普通文件读出来

那么作为一个文件系统的实现者，你怎么遍历目录？你就把这个目录文件当普通的文件读出来。读完之后它变成好多好多个数据结构的拼接，你去遍历这个数据结构，就知道这个目录里面有哪些文件。

还有一个非常重要的字段，叫 first cluster，也就是这个文件的第一个 cluster 在哪，它有 high 和 low 两个两字节。相当于这个 dentry 里有一个指针，指向这个文件的第一块（我那个图画得不是特别好，但意思就是这样）；然后这一块的 next 就是它的第二块，再 next 就是它的第三块，继续 next 下去，就能把整个文件的所有内容都遍历出来。

好，这就是 File Allocation Table，没有任何神秘，它就是一个数据结构。

### Unix 想得更远：它要装得下一张图

如果换成 Unix 呢？Unix 的设计者在设计文件系统的时候，想得比 FAT 要远一些。他会问：如果我们的文件很大怎么办？如果我们的文件系统也很大怎么办？以及，他想要支持链接——所以在 Unix 的文件系统里面，它和 FAT 不一样，它是一个图，而不是一棵目录树。

Unix 实际上是什么呢？比如我的 `/`，它是一个图状的结构。

```text
                 /
               / | \
            bin  home  ...        <- 目录
             ^
             |   bin/..  ->  /      （点、点，指向上级）
             |   bin/.   ->  bin    （点，指向自己）
             |
             +-- 目录里的"边"指向别的节点，图就闭合起来了
```

比如这里有一个 bin 目录，它有一个点是指向它自己的，有一个点点是指向它上级的，这就是一个图的结构。

如果你要存储一个 graph，而这个图上的每一个点都有它的 metadata：比如是一个 bin 目录，我首先要知道它的修改时间，知道它的 inode 编号，还有一些别的 metadata，同时我还要知道这些边——你们会怎么存这个数据结构？

最自然的想法，是你定义一个 struct node，节点；然后把这个节点所有重要的信息——就是在 `stat` 里能看到的那些东西，`st_mode`、`st_size`，各种东西——全部都放进去，这就是一个节点所有的 metadata。

那边怎么存呢？边在这个目录文件里。因为图中的每一个节点，要么是一个普通的数据文件，要么是一个目录文件；不管它是目录还是数据文件，它都有一个 byte array，除此之外它还拥有一个 index，这个 index 就相当于是一个指向它自己数据块的入口。

## 从 inode 到日志：文件系统怎么扛住崩溃
> 对应块：BLK52 | 覆盖分集：P26下 | 块标题（分集名）：《文件系统实现和崩溃一致性（下）》

### 目录、inode 与索引块

#### 目录文件里存的是文件名到 inode 编号的映射

一个文件之所以找得到，靠的不是它叫什么名字，而是它被记在哪儿。普通文件在磁盘上有一个叫 inode 的结构，每个 inode 都有一个编号。目录靠什么把"文件名"和"文件"对上？答案朴素得有点出乎意料：在目录文件自己的数据里，存一个从文件名到 inode 编号的映射就够了。

完全不需要什么 fancy 的数据结构，顺序存就是了：一个文件名、一个 inode 编号、一个 `\0`；再来一个文件名、一个 inode 编号、一个 `\0`……一个目录文件就这么一路排下去。

这其实就是你们在数据结构或算法课 OJ 上写过的那个东西——要表示一张图，而且边上还得挂 label，你会怎么存？把目标节点的位置和边上的名字写在一块儿。目录就是那张图的一个具体实例："边上的 label"是文件名，目标节点就是 inode。

#### 索引块：把文件头几块直接塞进 inode

Unix 文件系统里真正有趣的设计在索引上。

先记住一个经验事实：**大部分文件都是小文件，而且绝大部分时候你只读一个头**。你要看一个东西是不是 binary、是个什么 binary，扫一眼开头就够了，后面的内容你根本不在意。既然如此，文件系统当然希望访问文件头部时越快越好；可它同时还得能装下很大的文件。

于是 Unix 做了一个联合的数据结构：**把文件最前面的那几块，直接写在 inode 里**。具体是 9 块、10 块，还是 12、13 个指针，记不准也不重要，反正先用 inode 里的几个槽位把文件的开头几块兜住。这样你读文件头，读 inode 就拿到了，中间一个步骤都不用绕。

文件要是超大了呢？再拿一个块来做**一层间接索引**，概念上就是一个一级页表：那个块里排的不是数据，而是指向数据块的指针。一级还不够，就在这个指针之外再挂一个二级表；二级还不够，再上三级。这样一路铺下去，多大的文件都索引得住。

算一下账：4KB 的块，里面能放下 1024 个指针。所以一级间接覆盖 $1024$ 块，二级 $1024 \times 1024$，三级 $1024 \times 1024 \times 1024$。三级表已经大得离谱了。

> **结论**：这是一个非常漂亮的、多个数据结构的联合。它把 locality 用到了极致——小文件读头，直接从 inode 里拿；只有要往后读的大文件，才逐级展开那张"页表"。

#### inode 聚成一片，符号链接还能偷索引区

还有第二个设计：**把所有的 inode 放在一起**。

放在一起带来的也是 locality。一个目录里写了 10 个文件，分配的时候它们就是连续分配的，所以在 inode 区域里存得也近乎连续。于是你把这一片 inode 一次性读出来，相邻的、彼此相关的那些文件就一起进了内存。在有 cache 配合的前提下，inode 聚集是一个非常合理的、站得住脚的实现。

这个设计还有一个更有意思的副作用：**符号链接可以直接偷这块内存**。

如果符号链接的目标不超过 60 字节，它还需要索引块吗？不需要。它不必为数据单独分配任何一块，直接借用 inode 里那块本该放索引的内存，把 `../a` 这样的字符串塞进去就行——`../a` 一共才 4 个字节。这块本来就冗余的空间，让你能玩出很多花样来。

#### 亲手看一眼：debugfs 剖开的 ext4

上面这些都不是纸上谈兵，在真实的文件系统里能直接看到。

Unix 世界里有专门的工具做这件事，核心用的那个叫 `debugfs`。你甚至不需要先懂它的代码——让 AI 看一眼代码结构就行，它对 Unix 世界里的工具熟得很。但更重要的其实是先有一个观念：操作系统**应该**有办法把文件系统底层的信息暴露出来，不必事事都绕上层的 API。

拿它去解剖一个 ext4 文件系统，你能看到整个目录树的结构：`cd` 进去，建一个目录、写一个文件、做一个链接，然后再把结构打出来看一眼。你能看到链接计数（link count），能看到 `a.txt` 和 `b.txt` 这些节点，能看到每个文件占的 block ID。`README` 的 block ID 是多少、`dump_ext4.py` 这个文件一共 16.1KB、占用了 5 个 block，而那 5 个 block 在磁盘上还是**连续**的——前面讲的连续分配，这里活生生地摆在你眼前。还能看到一个符号链接，它的目标（如果是短的）就 **inline 在 `i_block` 里面**，压根没另外占块。

> **提示**：这些事情都是可以做到的。你只要有兴趣自己动手构造一个工具，就能得到很不一样的、更深入的理解。

所以回到根上：**本质上文件系统就是一个数据结构**，数据结构课其实完全可以把这些内容都讲好。但操作系统里的文件系统还背着一项数据结构课没有的职责——应对崩溃。

### 崩溃一致性：磁盘上的写会乱序，而崩溃随时到来

#### 一次 append 背后是三个 bwrite

你们的系统随时随地都可能 crash。可能是 power loss：设备没电池，一断电，内存里的数据瞬间全没。你们对"崩溃、掉电、内存数据丢失"这件事早就习以为常了。可对 persistent storage 来说，它必须小心翼翼地保证：即便发生掉电，文件系统里的数据也不能丢。

这就引出了 **crash consistency**（崩溃一致性）：文件系统必须从一个 consistent 的 state，稳稳地挪到下一个 consistent state。

为什么这件事难？因为它终究还是个数据结构。哪怕你只是写个链表，要把 y 插到 x 后面，你也不是写一个指针就完事：

```text
n = x.next;        // 先记住原来的后继
x.next = y;        // 让 x 指向 y
y.prev = x;        // y 指回 x
n.prev = y;        // 原来的后继改指 y
y.next = n;        // y 接上原来的后继
```

在并发语境下，为了防止 data race，你会在这里加个 lock、那里加个 unlock——这都没问题。但你从来没想过：**如果这时候这个线程突然被杀掉，会怎么样？**

crash consistency 就有点像"线程随时随地都可能突然消失"。设想你刚做完 `x.next = y`、`y.prev = x`、`n.prev = y`，正打算写 `y.next`，线程消失了。此时 `y.next` 是空的，飘到 0 去了，你去遍历这个数据结构，它就崩了。**必须把所有操作都执行完，这个数据结构才是一致的**。

把这个抽象落到真实的文件操作上。假设最简单的情形：往文件尾部 append 恰好一个 block。你需要做三件事：

1. **allocate 一个新的 block**——比如分配第 40 块，那就要把 bitmap 里第 40 块的位置置成占用（不再是 free）；
2. **写 data**——把内容写进第 40 块；
3. **更新元数据**——把这"第 40 块"记进 inode。

这三件事各自都是一次 `bwrite`。而麻烦在于，`bwrite` 执行之后，请求只是进了一个队列，这个队列通向**存储设备自己内部的那套计算机系统**。想想一块旋转硬盘：它有一个读写头，读写头怎么处理请求？当然是"离我近的先进"。如果盘片转过来时第 2 号请求正好在我底下，我就先做它。反正 1、2、3 落在不同 block 上，顺序做 1-2-3 还是 3-2-1，最终结果都一样——**正是这个"最终一样"，意味着实际顺序可以任意**。

> **结论**：既然顺序任意，一次崩溃就意味着这三个 `bwrite` 的**任意一个子集**都可能落盘，其余的没来得及。三个写，$2^3 = 8$ 种可能。

#### 任意子集都可能落盘

八种结局里有的安全，有的危险。挑三种说说，你就能感觉到味道：

| 实际落盘的写 | 后果 |
| :--- | :--- |
| 三个都落盘 | 一致，正常 |
| 只落了 data（bitmap、inode 都没动） | 相当于往一块仍然标为 free 的块里写了几个值，文件系统毫发无伤，安全 |
| data 与 inode 落盘了，bitmap 没落 | 文件当场读得出来，内容是对的；但第 40 块在文件系统眼里**还是 free**。将来它被分配给别的文件、别人又写了一遍，第 40 块里的内容就被覆盖了。于是这份文件好好地放在那儿，隔天打开，内容自己变了 |

最后一种是最阴险的：你运行程序没有问题，`hello` 是在的；损失不发生在当下，而是潜伏到未来某次分配才爆发。这就等于打开了一个魔鬼的盒子，和并发里那个 reorder 是同一套思考方式——**它会乱序，你必须非常小心地处理所有情况**。

#### 裸奔的几十年：从 fsck 到 lost+found

crash 会导致文件系统不一致，后果是什么？人类其实在几十年里一直处于一种"裸奔"状态。

文件系统的实现者多半是知道 crash consistency 问题的，但在 1970 年代，要做出 crash-safe 的数据结构显得太过复杂，于是干脆不管了。**做 systems 的人都是这样：先挣钱，后还债**——系统能用、好用，这种小问题先放着。

债终究要还：系统会 crash，crash 之后数据可能丢、目录可能损坏。极端一点，如果你正在写 inode 区域，读写头已经开始写了，这时候 RAM 掉电，哗一下就把那个 block 抹掉了，你完全有可能得到一个 **corrupted file system**。

这不是猜测。当时在美国的 lab 里做过一个很有意思的小面包板：从 VGA 送一个信号出来（能编程），用这个信号**物理性地把 SSD 的电源切断**。结果发现很多 SSD 内部那套计算机系统有严重问题——crash 之后整块盘可能就死了，再也读不出任何数据。SSD 的修复还极其复杂，它和 HDD 不一样：HDD 坏了你还能拆盘，SSD 基本上没法修。这个工作后来促成厂商修了一大批固件，再后来就再也找不到这类问题了。

而做 systems 的人的思路很简单粗暴：我的文件系统好用，这种小问题先不管；真出了问题怎么办？送去做一次 **file system check**（文件系统检查）——你在老一点的 Windows 机房机器上见过，开机时"正在扫描文件系统，找到多少坏簇并修复"。快速格式化的文件系统，数据其实捞得回来；当年那起照片外泄事件里，替人修电脑的最后被判了八个月。当然，那大概是在你们出生以前的事了。

这套检查的思路是把不一致的状态搜出来再修：还是刚才的例子，第 40 块在 bitmap 里是 free，但某个 inode 指向了 40。那你就扫描这条磁道上所有的 inode，遍历出所有**已被使用**的存储空间；既然 40 已经有人用了，它就不该是 free 的，去把 bitmap 里这一位置修回来。很长一段时间里大家做的都是这种 **rule-based file system checking**。

它也有猜不出来的时候。比如目录被人移动以后，你可能得到一个看不懂的结构：第 1 个指向第 4，第 2 个也指向第 4，第 3 的父亲是第 1，第 4 的父亲是第 2。这时候没办法了，只能**猜**一个"之前到底发生了什么"才变成现在这样。Unix 默认的 `fsck` 对某些孤儿会很客气：如果一个文件已经没有任何目录指向它（可能是它所在的目录文件损坏了），但它的 inode 还在，那就把它捞回来，丢进一个叫 `lost+found` 的目录里。你偶尔在文件系统里看到 `lost+found`，就是这么来的。

> **易错点**：`lost+found` 不是垃圾箱，它是"检查器只能救回 inode、救不回名字"的那些文件的收容所。文件内容还在，但原来的路径没了，只能靠编号去认。

但这**不是我们想要的**。我们真正想要的，是一个 crash-safe 的文件系统：它任何时候崩溃都可以，崩溃不影响一致性。怎么做？答案还是要回到数据结构上。

### 日志：把任意数据结构变成崩溃安全的

#### 两种视角：数据结构本身，与它的操作序列

先看一棵二叉树的例子。一开始是空的；`insert 3`，3 落在根上；再 `insert 6`，6 到右边；再 `insert 5`，5 挂在 6 的左边。

如果这棵树的节点带 parent 指针，你就和刚才的链表一样，要面对**多处写更新**的问题：`5.parent = 6` 和 `6.left = 5` 是两次写。只要分两次写，它就是 crash unsafe 的——对数据结构的写本身就不安全。

那什么东西容易做到 crash-consistent？**append-only**。

所以数据结构其实有两种视角：

- **第一种**，看数据结构本身：这是一棵有 `left`、`right`、`parent` 的树，查询 $O(\log n)$，我很喜欢它；
- **第二种**，看记录这个数据结构的**操作序列**：只要你把所有的操作都记下来，哪怕这棵树当场不一致了，甚至整棵树丢了都没关系——只要 replay 这条插入序列，树就重建回来了。

再往前推一步：我可以做一个 **memory trace**。对共享内存的每一次修改和分配，全都记下来，比如 `mem[6.left] = 5`、`mem[5.parent] = 6`。因为数据结构的本质，归根到底都是通过 memory write 实现的——**你只要把所有的 memory write 按顺序记下来，replay 它，就能得到一个一模一样的数据结构**。就这么简单。

#### write-ahead log 与 redo log

于是实现 crash consistency 真正做的事，是个"$1 + 1 > 2$"的组合：我们一边在 block 上存那个正常的数据结构（inode bitmap、inode 数组等等），一边在磁盘上**单独划出一块区域做 journaling**。

```text
                         磁盘
┌──────────────────┬────────────────┬──────────────────┬──────────────┐
│    journal       │  inode bitmap  │    inode 表      │   数据块      │
│   （只追加）      │  哪些 inode 用了│  struct inode[]  │              │
└──────────────────┴────────────────┴──────────────────┴──────────────┘
        ▲                                     ▲
        │  每次 bwrite 先追加到这里            │  确认落盘之后，
        └─────────────────────────────────────┘  才去改这里的数据结构
```

每当我执行一次 `bwrite`，先以 **append-only** 的方式把它写进 journal；等这次写确确实实进了 journal，才再去把这个写落到真正的数据结构上。数据结构写进去了，journal 里那条记录就可以丢掉了。可只要数据结构那边还没写完，这条记录就始终**在磁盘上待着**。

于是行为很清楚了：这时候如果 crash，磁盘上的数据结构是不一致的；但 reboot 以后，我可以把这些 `bwrite` 重新 replay 一遍，把它补完。

这个机制叫 **write-ahead log**（写前日志），也叫 **redo log**（重做日志）——你是在写之前先记一笔日志，而这笔日志是为了"重做"用的。有了它，**任意数据结构都能做到 crash consistency**。

#### 顺带一提：LSM-Tree

把"只追加 + 内存缓冲"这条路走到极致的经典数据结构，叫 **LSM-Tree**（Log-Structured Merge-tree）。现在的 key-value 系统甚至数据库，很多都以它为根基。它的原理大致是这样：

- 先在内存里放比较热的数据。要写一个数据，直接写内存；内存里用一个对并发比较友好的结构（比如 skip list）承载。
- 对所有这个结构的更新，都以 write-ahead log 的形式写进日志——所以哪怕随时 crash，内存里那份结构也能靠日志重建回来。
- 等 memtable 写满，触发一次 flush，往磁盘持久化。
- 磁盘上存的是一棵一棵**不可变**的树，靠均摊分析撑着：整个结构一层一层，下面那层总比上面那层大，最上面是小小的内存层。写满就往下层合并——插进这一层，发现这层太大了，继续往下一层并，一层层落下去，最终得到接近 $O(1)$ 的时间复杂度。

核心就是"内存的层次化存储 + 一个 write-ahead log"。这里不展开，你可以自己回去在 AI 的帮助下学一遍。

#### transaction begin/end 与 happens-before

在文件系统里做 journaling，其实**不需要做成对任意数据结构都成立的那套通用日志**。你只需要在真正要写的时候，把要写的东西直接往里写，然后加两个标记。

```text
时间 ────────────────────────────────────────────────────────────────▶
   │ 写数据 / 写 inode / 写 bitmap │  flush   │ 写 transaction end │ flush │
   │      （真正要落盘的东西）      │（等落盘）│      （结束标记）   │       │
                                  └── 此刻崩溃 ──▶ 整笔事务当作没发生过
                                               └── 此刻崩溃 ──▶ 重放即可恢复
```

顺序是：把数据写下去，标一个 **transaction begin**（事务开始）；接着发起一次 flush，告诉磁盘"我要等这些数据全都落盘"；等它落盘完成，再写一个特殊标记 **transaction end**（事务结束）；完了可以再 flush 一次。

这就建立了一条 **happens-before** 关系：这些数据 happens-before 那次 flush，那次 flush 又 happens-before 写 transaction end。

> **结论**：反过来看，当我在磁盘上**看到了** transaction end 这个标记，说明 transaction end 已经发生；它发生了，就说明 flush 一定发生并且完成了；flush 完成了，就说明那些数据一定已经落盘。于是这笔操作算数，只要 replay 它就行。这一步就是 **checkpointing**：把 journal 里的操作重放到真实的数据结构上，重放完 journal 就可以清掉。

于是崩溃点的位置决定了一切：

- 崩溃发生在 flush **之前**：就像这笔事务从来没做过，因为不能保证所有数据都落盘；
- 崩溃发生在 transaction end **之后**：只要重启时看到这个标记，这些操作就一定会在重启后被正确地反映到文件系统上。

这就实现了 crash consistency。

#### ext4 的两处改良：checksum 与 metadata journaling

为了实现高效的 journal，trick 还有不少。

哪怕小到 xv6 这种教学用的操作系统，也会**把多次系统调用的 transaction 合并成一个**。比如有好多个 ongoing 的写——写了这个文件、写了那个文件——把它们合成一笔事务，那样只要 flush 一次。代价是 crash 时可能多丢一点东西，换来的是**减少等待磁盘同步的次数**。

Linux 里则有 **Journaling Block Device**（JBD，第二版叫 JBD2）。你会看到每个设备都有一个这样的 journaling daemon 在后台跑：它隔一段时间（比如 30 秒）才把东西做一次 snapshot，而不是你写完一个文件就立刻落盘——所以在系统里会显得稍微慢一点。

ext4 干了一件非常高明的事。既然核心是那条 happens-before（要靠 flush 才能保证先数据、后标记），那我**干脆不要 transaction end，也不必真的等那次 flush**——当然你仍然可以把日志推落盘，那样更安全——改为在日志**头部直接写一个 checksum 加一个长度**。crash 之后我不再傻傻地扫遍整个 journal 区域，而是看这里有个 checksum、有个长度，按长度读出这一段，算一下 checksum 对不对：

- 对，就说明它正确落盘了，replay 它；
- 不对，就把后面的全扔掉。

就这么简单。它用 checksum 这套机制，省掉了落盘的 synchronization。

第二处改良是 ext4 **默认采用 metadata journaling**。数据占了磁盘写入的绝大部分——你绝大部分时间其实是在写数据，而数据丢不丢通常对你**不太要紧**，应用程序在一定程度上有义务保证自己不丢数据。所以 ext4 把 inode、bitmap 这些**元数据**的更新全写进日志，而对文件内容的修改不写进日志。crash consistency 的含义本来就是你崩溃时会丢一小段时间内的内容，所以它更看重的是**目录树的完整性**：不能因为目录节点出了问题，把你的目录整个搬进 `lost+found`，那对你就很糟糕了。它要保证目录结构一致，数据可能丢，以此换性能。

### 用户空间的崩溃一致性

#### 编辑器保存文件：O_TRUNC 是个陷阱

但真的是这样就够了吗？答案是不是。实现 crash consistency 比想象中麻烦一点。

假设你写了一个文本编辑器——就像数据结构课里做过的那个 Vim 的 clone。现在你在自己的 buffer（内存）里有一个 `a.txt`。你要怎么保存它？

第一件绝对不能做的事，是直接 `open` 这个 `a.txt` 并带上 `O_TRUNC`。`open` 的那一瞬间，文件内容就没了；要是这时候你的进程被别人杀掉，这个文件就彻底没了。所以不能用 `O_TRUNC` 去打开一个正要被保存的文件。

那自然会想到这样的流程：

```text
open  a.txt.tmp   ──▶ 写入新数据 ──▶ close
                                      │
unlink a.txt      ◀───────────────────┘
rename a.txt.tmp ──▶ a.txt
```

先把新数据写进 `a.txt.tmp`，`close` 之后你会觉得"临时数据已经写进去了、我安全了"；接着 `unlink a.txt`，再 `rename a.txt.tmp` 到 `a.txt`。

**但这个流程是不行的。** 因为我们的操作系统做的是 metadata journaling，它对这个"数据"不负责。redo log 里记下的只有元数据操作：第一步，"创建一个空的 `a.txt.tmp`"（`O_CREAT` 本身是目录里的元数据操作）；第二步，"把 `a.txt` 删掉"（`unlink` 也是目录里的操作，同样要 journal）。然后 system crash 了——而 data 是不 journal 的。

重启之后，重启的日志里看到的就只有这两条：创建空的 `a.txt.tmp`、删掉 `a.txt`。于是 `a.txt` 没了，`a.txt.tmp` 是个空的。你回来一看，文件就这么不见了。

> **提示**：这就是 metadata journaling 的边界——它保证的是目录结构一致，不是你的文件内容一定在。

#### Git 为什么敢不管

顺带说一个现象：**Git 是不管文件系统一致性的**。

因为 Git 本身是 append-only 的数据结构，它只要能确保所有东西——所有的 object——都在就行。理论上，即便文件系统留下了一致性问题，你依然可以把 Git 回到一个过去的一致状态，因为所有的 commit object、tree object 都不会丢，它们都在文件系统里；你扫一遍，总能把该恢复的恢复回来，不会有东西真的丢掉。所以 Git 就干脆为了性能不管 crash consistency。

#### 把落盘的控制权交回用户：sync 家族

Git 的这个决定带来了一个很有意思的后果。我们很长时间的 OS lab 都是在虚拟机里做的，于是同学们编完程、编译通过、`make submit` 交上去，一看 OJ 过了，**马上就点关闭虚拟机**。关虚拟机时有几种选项，其中一种是安全关闭，一种是快速关闭——对同学们来说，一定是选最快的方式。而快速关闭意味着直接给虚拟机一个 power off，相当于把线拔了。

线一拔，问题就来了：我们的文件系统是有日志的，那个 journaling block device 的日志——哪怕只是 metadata——可能都还没 replay，日志只写了一部分。这时候 Git 就进入了一个不一致的状态，因为有些 data 没了，你需要重新扫描它。

所以在用户空间，这个行为是**可控的**。那一组用来实现用户态 crash consistency 的系统调用就是 **sync 家族**，还有一个 `sync` 命令。你去看我们的 Makefile 就会发现，在 `git commit` 之后我加了一个 `sync`：做一次全局的文件系统同步，确保数据都落盘。所以那个 `make` 会比较慢；尤其是如果你的存储设备也像我一样是个树莓派这种慢家伙，你会明显感到一个肉眼可见的延时。这就是我为了 crash consistency，告诉操作系统"请你把所有东西都落盘"的代价。

sync 家族细看是这样的：

| 调用 | 同步的范围 |
| :--- | :--- |
| `sync` | 全局的文件系统同步，把所有东西落盘 |
| `syncfs` | 同步这个文件描述符所在的**整个文件系统** |
| `fsync(fd)` | 同步**这一个文件**的 data 和 metadata |
| `fdatasync(fd)` | 同步文件的 data，并且只有当 metadata **真的变了**，那份 metadata 才一起同步 |

`fdatasync` 特别有用。如果你要在磁盘上实现一个数据库，你很可能会先分配一个固定大小的文件，比如一个 4GB 的 database。那这 4GB 的空间**已经被分配出去了**，任何一个 block 都已经映射到磁盘上的某个 block，此后你对它的任何修改都不会改变这个数据结构的映射关系，变的只有数据和那个 modification time。

这时候 `fdatasync` 会更新数据（比如你在某处写了 `1 2 3`，它确保这 `1 2 3` 落盘），但**不去动 inode**——因为 size 和索引都没变，动 inode 反而要多涉及一个块的写入，白白多一份 inode 上的落盘开销。所以在应用程序里实现 redo log 这类东西，用 `fdatasync` 的性能是最好的。

#### 只留一个 rename 就够了

那到底怎样保存文件才是安全的？

正确的方式其实简单到只有一句：**只留一个 rename 就够了**。`rename` 能保证 atomicity——它要么就换过去了，要么就完全没有换，没有中间态。这是 Linux 给出的保证。

> **结论**：把新内容写进临时文件、确保数据落盘之后，**不做 unlink，直接用一次 `rename` 换过去**。崩溃发生在 `rename` 之前，你手里的还是旧文件；发生在之后，你拿到的是新文件。中间不存在"两个都没有"的时刻。

可开发者怎么可能知道这一点呢？当年读 PhD 的时候我就想：除了真正优秀的 systems programmer 写的软件，**所有业余程序员写的软件应该都有 crash consistency 的问题**。然后我们去验证，答案是 yes。

#### 谁真的踩了坑

我们找到的软件名单很长，而且很多是 legacy——它们设计的时候根本没有 crash consistency 这个概念：

- **GNU 的 make**：可能给你留下一个不正确的 build；
- **sort**：如果你做 in-place 的排序，那个文件可能会被整个丢掉；
- **Perl**：它本身支持像 sed 那样做正则替换，专门有个 `-i` 的就地修改选项，那个也会把你的文件整个丢掉；
- 还有更夸张的：2016 年 VS Code 刚起步那会儿，整个 JS、Node.js 的世界**根本不存在一个可以安全保存文件的 API**。也就是说，所有 Node.js、Electron 的应用全都有 crash consistency 问题。那时候 GitHub 家的还是 Atom，有人在 issue 里说：我要保存一个很大的文件，这时候磁盘空间满了，然后我的文件就消失了——非常沮丧。

顺带说一句 `sort`：它是支持 in-place 的（有些程序不支持，因为用 `O_TRUNC` 打开就直接挂了），但它支持 in-place 的同时，**并不支持 crash consistency**。

### 这门课真正教我的东西

讲完日志、讲完 crash consistency，你们有了一个概念，也学到了一组 API——`fsync`、`fdatasync`，下次处理数据的时候知道要非常小心。但比起这些，我真正想教的东西是：**所有的东西都是可以做的**。

就在讲课的前一天，我把十年前那篇 2016 年的论文直接丢给大语言模型，让它帮我实现一个 crash consistency 的 checker——一个简化版的、用户态的版本。你看，将近 1000 行代码，修了几轮基本上就对了。

拿它去检查 `sort`：`sort a.txt`，而 `sort` 又支持 in-place。它于是能观测 `sort` 保存文件的过程——所有和文件相关的系统调用——然后生成大量模拟出来的、可能的 crash 现场。再让大模型直接去解读那份 `result.json`，它就能把结论复现出来。换句话说，**我让大语言模型直接复现了当年那篇论文里的研究结果**，那篇 paper 是可复现的。

这里还藏着一个"洗 paper 的流量密码"：你可以找一个还不错的 paper，用你的 token 和超能力把实验规模扩大 100 倍——因为现在有 LLM 了，你理论上可以去世界上所有的开源软件里都做一遍这个实验；而当年我没有 LLM，很多时候只能依赖 heuristics 来判断"这里到底有没有 crash consistency 问题"，如今完全可以用 LLM 替代掉所有 heuristics。

它确实找出来了：AI 知道 `sort` 会在截断之后发生一次崩溃，也知道它在写入中断的时候会发生部分数据丢失，能正确地定位这个 bug。当然，coreutils 出于可移植性的考虑不打算修它；而 **Perl 最后把这个 bug 修掉了**。所以我们完全可以用 LLM 去做一个非常好的实验。

但是——**不要这样做**。学操作系统，你要去干地球上没有人做过的事情。因为现在你有知识了，也有模型了，你就可以去做世界上没有人做过的事。
