### 期中测验复盘：从文件描述符说起

#### 文件描述符为什么是「一张表加一个整数」

第一道题讲基本概念：什么是文件描述符。

如果让你来设计，进程总是需要去指代一个已经打开的文件。这里有一个硬约束：操作系统把进程的地址空间隔离了，所以进程不能直接访问别人（或者内核里的对象）。于是——不能用指针，也不能用名字。指针不好，用名字也不好。

Unix 的选择就是一张表加一个整数。我这个进程持有的、编号为 0 的文件（对象）是 stdin，编号为 1 的对象是 stdout，以此类推。`fd = 3` 只是一个数组下标，它背后是操作系统里的一个对象。因为 everything is a file，所以这个下标就叫文件描述符。

这题大家应该都非常清楚，因为它一定会考。

#### fork 之后文件描述符怎么办

第二题就比较麻烦了：fork 以后，子进程还要不要访问、还要不要持有同一个文件？肯定是要的。因为我们的 `fork` + `execve` 正是拿它来实现管道、重定向这类功能的。

这里有两个设计选择：

- 父子进程各自独立有一个偏移量；
- 父子进程共享同一个「打开的文件」，也就共享偏移量。

实际的答案是第二个。但更有意思的是站在操作系统设计者的角度去推：如果父子进程都要写文件，那第二个选项才是正常的——不然两个进程同时写日志，日志就会被覆盖掉。

AI 在这里还给了一个更漂亮的论证，有点出乎我的意料：我们确实可以干这件事。shell 里可以用分号把两个命令连起来，或者用 `&&` 连起来，于是「先运行一个、再运行一个、再运行一个」被打包成**一个**命令；而这个动作里面就有两个进程。让它们共享同一个打开的文件，我的行为才是把第一个命令的输出和第二个命令的输出**合并**起来，而不是让它们交叉错乱。因为有这样的实际需求，你才会知道该选哪一个。

> **结论**：共享状态是协作的前提。

fork 之后，两个 fd 指向的是同一个打开的文件对象：

```text
  父进程 fd 3 ──┐
                ├──►  打开的文件对象 { offset, inode }
  子进程 fd 3 ──┘

  两个 fd 指向同一个对象，所以 offset 是共享的：
  父进程写掉 100 字节之后，子进程接着从第 100 字节往后写。
```

#### execve 只换掉代码、数据和栈

第三题相对简单：`execve` 的函数原型是什么？

有的同学居然不知道什么是函数原型——函数原型（function prototype）就是一个函数签名一样的东西。`execve` 做的事情是换掉代码、数据和栈，但保持 fd 和 pid 不变。这个大家应该都会。

#### 终端界面靠什么画出来

第四题很有意思，大家答得比我预想的要更不好一些。原因主要有几个方面。

如果想在终端里做一个 UI，不管是 Vim 还是 Claude Code 这样的程序，第一件事是能画界面。而画界面里，Unicode 只是其中一部分——比如那个奇怪的小 logo 是用 Unicode 画出来的。真正实现终端主要功能的是 Escape code：因为有 Escape code，你才能控制光标的位置，才能擦除屏幕的一部分。有了这些，你才能绘制一个动态的界面：你看那个框框一直在那儿不变，但里面的字不断地往后吐。

要实现这个功能，就需要 Escape code。当然还有 PTY 这个机制，以及信号的机制——大语言模型在吐 token 的时候你要能 Ctrl+C，我不知道为什么大家都把这个概念忘记了。你们有没有让 AI 帮你们写过一点终端里的程序？你会看到好多好多这样的 Escape code，讲义里面也是频繁出现的。

### 期中测验复盘：那些细碎的第二题

#### 判断一个二进制运行时要不要加载 .so

给你一个二进制文件，如何判断它运行时是否需要加载 `.so`？你只要去看那个 ELF 文件就行：在 gdb 里可以看，也可以直接读 ELF 的 `.interp` section，它记录了动态链接器的路径；命令行工具像 `ldd` 也能干这件事。看那个 ELF 文件，就知道它是不是动态链接的。

#### 谁修改了环境变量

谁修改了 environment？哪一个变量是被哪一条指令改的？那就用 watchpoint。AI 的直觉真的非常好：你有一个需求的时候，它真的知道你该做什么——你只要说出「gdb 提供了一个机制，可以在某一个地址被修改的时候让你停下来」，你就知道该怎么做了。

#### 环境变量存在哪里

环境变量存在哪里，和栈有什么关系？你不需要记得这些具体的东西，但有了概念就能答对：先 `print environ[0]` 拿到地址，然后去这个地址所在的 mapping 里查它在地址空间中的位置，问题就回答了。

这也是这一类题的共同特点：你不需要记住细节，你有概念的时候就能答对。

#### 定位 mmap 的 syscall 指令

要定位执行 `mmap` 的那条 system call 指令，你可以 trace 所有的指令，甚至可以单步：写一个 hook，每一次停下来的时候单步执行，并且在每个 hook 停下时都检查一下。理论上，这个问题和「从 `_start` 到 `main` 都执行了哪些东西」可以用同样的方式处理。

AI 还知道 gdb 有一个 reverse execution 的机制。它的代价是要记录每条指令；而正因为它的代价是记录每条指令，当你想知道一共执行了多少条指令时，正好可以借用这个机制。

它还反问了一句：动态链接每次要多执行几万条指令，这就是 `ld-linux` 动态加载的代价，这个到底值不值？当然值得。我说过，在整个系统里面，你都只有一份 `libc` 代码的拷贝，所以花这一点时间相当值得。

#### struct FILE 到底叫什么

第三题是找不到 `struct FILE` 的定义。搜了 `struct FILE`，什么都没找到。这其实是个很有意思的问题：你知道 `struct FILE` 在，但你就是看不到一个像 C 里面那样定义的 `struct FILE`——大括号，然后在里面写字段。它实际上是 `_IO_FILE`，是 typedef 出来的。所以你真正要找的是 `_IO_FILE`。

如果假装没有这个知识，也依然有办法：用 `gcc -E` 看预处理的结果。你甚至不需要事先知道 `gcc -E`——只要你知道 C 是经过预编译的，这件事很重要——你希望让编译器帮你把预编译展开，你就可以拿到答案。

> **提示**：编译器看到的和你看到的不一样。写一个 `.c` 文件引用这个结构体，再让预处理器展开，定义就露出来了。

#### fork 之后 buffer 和 lock 会怎样

fork 对 buffer 和 lock 有什么影响？这也可以用纯逻辑推理推出来：一个锁的实现，比如一个互斥锁，如果它要用 futex 机制，那它在用户空间一定有一个 `int lock`——就是一把钥匙。我们打比方的时候说桌上放着一把钥匙，放没放，那一定是用一个变量表示的，这个变量可能是 0 也可能是 1。而这个变量位于进程自己的地址空间里；正因为它位于进程的地址空间里，所以它会被复制。

于是 buffer 会复制，lock 的整数值也会复制。所以有时候：如果 fork 的时候锁正被别的线程持有，子进程就会死锁，不能正常运行。

#### 多线程下的 fork

多线程的 fork 同样要站在操作系统设计者的角度去看，它是一件非常麻烦的事。因为每一个线程都是异步的，默认情况下相互不同步。我执行 `fork` 的时候，每一个线程都可能在执行任何一条指令，它就在 CPU 上跑，你是没有办法把它直接停下来的。

所以 POSIX 对 fork 的选择是：只有调用 `fork` 的那个线程存活，其他线程好像不存在一样。

> **易错点**：这是一个很麻烦的机制。当你同时有线程又有 fork 的时候，你其实要花一些时间去想：如果我是操作系统的设计者，我该怎么办。

基本上推荐的、也是唯一安全的选择，就是 fork 之后就做 `exec`。fork 和线程本身是有失配的，这也是大家诟病 fork 的一个原因。

#### 自己实现 popen

实现 `popen`/读，这就是课上的内容：管道，你们做过的那个实验。如果你们当初是按要求自己把系统调用写出来的，而不是让 AI 说「帮我把这段代码搞定吧」，你们应该会有一些印象。有了印象，你就应该记得文件描述符在父子进程之间是会复制的；然后你只需要关掉合适的文件描述符、腾挪合适的文件描述符，就可以了。

### 回到 sum++：锁给了正确性，却给不了扩展性

`sum++` 在并发编程里是一个非常常见的 pattern。虽然这是一个过度简化的例子：我创建一个 Tsum，在 Tsum 里面获得一把互斥锁，在持有这把锁的时候做 `sum++`——无论有多少个线程，比如一共加了 1 万次，我最后一定会得到 `sum` 等于 1 万。互斥保证了正确性。

这个过度简化的模型在实际中的意义是什么呢？实际中被锁保护的部分，很可能是**一个数据结构的操作**：

- `printf` 的时候，两个线程共享进程的一个 buffer，这个 buffer 有一把锁，锁上之后才能往里面写东西，于是两个线程可以并发地写，`stdout` 就能看到不被打乱的、正确的数据；
- 你有一个 key-value 的 dictionary，只要这把锁保护住了整个数据结构，在它上面做更新就是安全的。

这是一种非常常见的 pattern。

我们之前对比过好几个做 `sum++` 的实现，实验是在我那台树莓派上跑的：

| 实现 | 单次 sum++ 的开销随线程数增长的变化 | 备注 |
| :--- | :--- | :--- |
| 汇编写的原子 sum++ | 最快 | 连获取锁、释放锁的过程都没有 |
| 互斥锁（mutex） | 基本保持不变，但也不会变好 | 串行化，阻止了并行 |
| 手写的自旋锁（spin lock） | 随线程数增加而变慢 | 不断地试图去桌上拿那把钥匙 |
| 使用 futex 系统调用进内核 | 随线程数增加而变慢 | 每次操作都要进操作系统内核 |

随着线程数量的增长，进入操作系统内核或者自旋的每一次 `sum++` 所花的时间都在增长。这显然是一件很糟糕的事：线程越多，性能反而越差。而 mutex 和 atomic 基本上性能保持不变——至少它不下降了。

但不下降同样是很糟糕的事。理论上说，如果你的算法设计得非常好，那么当我多一个 CPU 的时候：如果原来要花 1 秒钟，两个 CPU 就应该花 0.5 秒，4 个 CPU 就应该花 0.25 秒——因为我给它分配了更多的算力。每一个 CPU 都是独立的，它可以独立执行指令、独立响应中断。一个真正好的实现，就应该能够把 CPU 的计算力 100% 用起来。

而这里看到的是：一个操作在一个 CPU 的时候最快，两个 CPU 的时候变慢，4 个 CPU 变得更慢，然后 8 个、16 个开始饱和就不再变了。这根本不能说是性能好，可以说是性能非常非常差的实现。你真正想要的是：随着 CPU 数量增加，每秒钟能完成的操作数**增加**。mutex lock 最好的情况也就是到某个地方到顶，再加也不会有性能损失——但它是串行的，它阻止了并行，所以这不是我们想要的东西。

反过来说，锁也确确实实给了我们两样硬货：

- **完整的 serializability**：第一个线程的 lock/unlock、第二个线程的 lock/unlock，我们可以清楚地排出每一次上锁和解锁之间的顺序；
- **acquire/release 之间的数据可见性**：如果写了 `x = 1`，然后 `unlock`，那么在另一个线程里 `lock` 之后，一定能看到 `x = 1`；`x = 1` happens-before 这次 lock。锁的实现会使用特别的指令（或者一堆指令）去告诉 CPU，读 `x` 的时候必须读到 `x = 1`，而不能读到一个更旧的值。

> **结论**：这些保证都要付出代价，代价就是 scalability——性能没有办法随着 CPU（线程或者机器）的增长而增长。

### scale up 与 scale out

今天主要的问题就是：我们怎么去设计一个合适的并发算法和并发的数据结构，来实现 scale up 和 scale out。

这两个概念稍微有点不一样：

- **scale up**：你可以想象一台计算机，随着线程数增长，它的性能不断增长；
- **scale out**：你可以再来一台计算机、再来一台、再来一台，随着计算机数量的增加，性能依然可以增加。

怎么样做到 scale up 和 scale out，其实是这些年——尤其是大数据和 AI 时代——最核心的引擎。正因为我们的各种信息系统可以 scale up、可以 scale out，你才能支撑起全国人民都在发抖音这么大的数据量，才能支撑起全国人民都在调大语言模型的 API。所以 AI 超算是现在最热门的事情之一。

我们从并行的算法讲起，因为并行算法会比并行的数据结构简单一点，后面再讲并行的数据结构和你们的 `malloc`。

### 并行计算问题就是一张计算图

任何一个并行计算的问题，它的本质都是一张**计算图**：每一个节点是一次计算，每一条边是一个依赖关系。

比如在矩阵上做动态规划，`dp[i][j]` 是 `dp[i-1][j]`、`dp[i-1][j-1]`、`dp[i][j-1]` 这几个值的函数，于是就得到一张这样的依赖关系图：

```text
   dp[i-1][j-1] ──┐
                  ├──► dp[i][j]
   dp[i-1][j]   ──┤
                  │
   dp[i][j-1]   ──┘
```

只要每一个节点上面的计算量很大，而这段计算又不需要上锁（本身不涉及共享变量），那么这个算法就可以让「上锁和解锁之间」被串行化的区域变得很小。一旦它变得很小，我们的系统就可以 scale up，也可以 scale out。

### 在计算图上切分，而不是一格一格地同步

还拿上面这个例子说：如果你让每一个 `dp[i][j]` 都作为一个节点，那这张计算图其实设计得**很糟糕**。

因为你需要上锁、需要同步来确保自己能运行。不管你用条件变量去 wait，还是用信号量：我有三个前驱，那我就在执行前 P 三次，算完之后再对后继各 V 一次，然后才能继续。而这些同步操作、互斥锁都是有代价的。你付出了这么多代价以后，只做了一个 `dp[i][j] = dp[i-1][j] + 1`——一两步算术运算，然后又要花很大的代价去做同步运算。即便这张计算图到一定程度时并行度足够高，它依然可能不是一个你认为特别好的算法。

那要解决 LCS 这样的问题该怎么办？你可以在计算图上做很多文章，也就是**切分**：

- 在最开始，把整个上面的小三角形都变成一个节点，串行地算——它本身算得很快，就几百个东西，不值得为它付同步的代价；
- 直到并行度上来以后，按这条对角线来切：把这一层切成两份，再切成三份（1、2、3），随着并行度继续提高切得越来越细；
- 本质上，你只要算完这一层，就可以算下一层。

所以你不是非得按照原来那个问题的写法（`dp[i][j] = dp[i-1][j] + …` 或者一个 `max` 加 1）去一格一格地算。切分问题是灵活的：你可以切成一块一块，块和块之间有依赖关系。

```text
   +-----------------------+
   |           A           |
   +-----------+-----------+
   |     B     |     C     |
   +-----+-----+-----+-----+
   |  D  |  E  |  F  |  G  |
   +-----+-----+-----+-----+

   最上面的 A 就是那个小三角形，整块串行算；
   越往下切得越细，块与块之间只剩边界上的依赖。
```

这时候我们就满足了可以 scale up、甚至可以 scale out 的模式：同步、上锁的时间很小，而绝大部分时间都在做自己的本地运算。

### 高性能计算：为 massive computation 而生

由此引出了一个领域，一整个领域，叫**高性能计算**。按定义：高性能计算是一门利用超级计算机或计算机集群的算力（a technology that harnesses the power of supercomputers or computer clusters），去解决需要 massive computation 的复杂问题的技术。

它源于各种各样的**数值密集型科学计算任务**。大到宇宙、小到量子，只要你有模型，你就能模拟：有了牛顿力学，你就可以模拟任何粒子系统，只要把它拆得足够小、足够细。只要你有那个物理系统的公理，不管你是天上的气流、核武器的爆炸，还是流水，你都可以模拟。所以你再也不需要真的去做地下核试验了，你只要建模——因为原子的模型我们已经搞得很清楚，而且我们做过很多实验，确实可以验证我们建的物理模型是比较准确的。

我以前和做化学的人合作过，他们模拟有机物的反应时，会考虑量子化学的特性。这无非就是：你投入多少计算量，就可以获得多大的精度；算得越慢，最后的结果离真实结果就越准。这是一个非常典型的 require massive computation 的任务。

所以你可以理解，科学计算这种大规模的高性能计算，在天气预报、航天、制造、能源、制药这些领域都是毁灭性的战斗力。这是在 AI 之前——在 AI 之前我们只能硬模拟；有了 AI 之后，在硬模拟的基础上又出现了一些像 AlphaFold 这样很有趣的东西。它一直是给高性能计算买单的最大的客户。

随着高性能计算继续往前走，又有了两个比较近的新力量。

第一个是**矿场**。本质上的 blockchain（比特币）就是一条 append-only 的 list——对计算机系来说它就是一个数据结构，一条只能往后追加的链表。但这条 list 是分布式的，由地球上的所有参与者共同维护。

问题在于：如果这个账本落到一个恶意的玩家手里，他就可以随意篡改账本，或者故意不把该记的账记进去，这个账本就不再可信了。怎么做一个可信的账本？我们让所有同学都来做期末考试、都来做这道题，每一个人都是随机的，谁先做出来，这一次就让他记账。这样就能实现一种强制的分布：所有参与的玩家都有机会记账，于是一个分布式的账本就被建立起来了。

这就催生了一件事：如果你想记账，你就需要 proof-of-work，你要证明自己有这么多的算力；要证明自己有这么多算力，你就需要很多 GPU 矿卡——也就有了矿场。

第二个新力量就是现在最热门的 AI 算力。比如最近的消息是 xAI 被解散，把算力都交给 Anthropic 去跑 Claude 系列的模型。我后面会有两节课专门讲 GPU 相关的内容——这就是经典的高性能计算。

### 从 Cray-1 到 Cerebras

我们来看看高性能计算是怎么一路走来的。

1976 年，出现了「世界上最贵的沙发」（the world's most expensive love seat）。为什么是沙发？因为它这个系统在设计的时候有一个底座，底座里面应该是走线的，而那个地方是真的可以坐人的——论文里有一张图，图上就是 Cray 本人坐在上面。138 MFLOPS（$138 \times 10^6$ FLOPS），功耗 115 千瓦——注意，是千瓦。

对比一下：今天你如果有一台 M4 的 iPad Pro，它的峰值算力是 3.8 TFLOPS——注意是 TFLOPS。M 是 $10^6$，G 是 $10^9$，T 是 $10^{12}$，中间隔了三个数量级。没有到 100 万倍，但这个数量级已经来到了一百万倍的差距，而对手就是一台 Apple M4 的 iPad Pro。

再比如很火的 Chat Cerebras：它是一个能跑每秒 15000 token 的 ASIC。它把一个 8B 的模型烧到一个电路上——真的以门电路的形式烧进电路里。你们在用 AI 的时候应该从来没有过这种速度的体验：网好的时候你试一下，按一下回车，token 就啪叽一下全出来了。哪怕它只是一个 8-bit 的模型——8-bit 的模型智力其实已经相当可以，做一些翻译之类的任务没问题；它因为经过了过度量化，质量不能说非常好，但这依然是一件非常离谱的事。

大概估算一下，这块芯片基本上得有 300 TFLOPS，那就真的相当于两百万台 Cray-1 的计算能力；而这个芯片大概只有二十几瓦。也就是说，在 20 几瓦的功耗上，我们拿到了相当于 Cray-1 用 115000 瓦换来的两百万倍的算力。

再看今天的超级计算机。中国超算 TOP100 每年都会有一个排名，不过这个榜单也很久没有动过了——很久没有人再建一个更大的超算，或者没有公开的超级计算机，你看，有些安装地点甚至都不公开。2016 年拿到世界第一的是神威太湖之光，在江南计算所，它有那么多个 CPU，数都数不过来。而你看到现在的超级计算机是用 PFLOPS 来算的，不是 TFLOPS——又多了一个 $10^3$。这是一个多么可怕的算力。正是因为有了这些算力、有了 AI，AI 才能走到今天这样的时代。

我强烈建议大家花一点时间去读一下那篇讲「世界上最贵的沙发」的论文，里面有整个 Cray-1 的设计图：从指令集到整个系统的硬件物理设计，非常推荐。

### 什么样的程序能跑在百万个核上

那么到底什么样的程序，可以跑在一个有那么多 CPU 的计算机上，甚至跑在一个计算机集群上？

你们到现在为止，绝大多数同学摸过的都只是一台 16 核、32 核的计算机。对这样的机器来说，用课上的线程库（`thread.h`、`thread-sync.h`）就非常够用了：你起 32 个线程，做一个生产者–消费者，把任务分解开就行了。但如果真的给你 100 万个核，你到底该怎么用它？

最早驱动高性能计算的这些科学计算问题，恰好利用了一个特点：**我们总是可以把物理的世界切分成网格**。

只要你要模拟的那个物理系统足够大就行。比如我不是想模拟南京大学顶上的天气，而是想模拟全世界顶上的天气——那你想切出 100 万份、1000 万份，就轻轻松松。切完之后，每一份都可以独立计算。

当然，每两份之间会有边界上的值，因为边界上的值既受我左边影响，也受我右边影响。你可以不切成方块网格，而是切成六边形的网格：这样每一个格子有六个相邻格子，会更科学一些。那么我只需要在算这条边上少量的点时做同步——他们也研究了很多算法来解决这个同步问题。而每一个块内部的计算基本上就是可以并行的。

可以并行就意味着，像我们最开始提到的那样：只有很少的一部分需要上锁、需要同步，绝大部分都是我在本地计算的。于是我这台高性能计算的机器、这个集群，就可以借助这样的计算任务既 scale up，又 scale out。

```text
   +-------+-------+-------+
   |  b1   |  b2   |  b3   |
   +-------+-------+-------+
   |  b4   |  b5   |  b6   |
   +-------+-------+-------+

   块内独立计算；只有相邻块之间的那层边界值要同步。
```

### Linpack 与线性方程组

如果你留意到一个细节：评估 HPC 用的是 Linpack。

Linpack 是一个基准程序，简单来讲就是求解一个稠密矩阵的线性方程组 $Ax = b$。当然，这个矩阵可以非常大。它也是一个可以分块计算的任务，所以它可以跑在超级计算机上。

为什么线性方程组这么重要？因为所有的非线性系统，比如用微分方程来定义的系统，你都可以用牛顿法把它变成一个线性的系统——就像有限元那样。我不是这方面的专家，但总体来说，你几乎总是可以用求解线性方程组的方式来求解非线性的问题。

好，那这个问题就解决了：你只需要做一个巨大无比的线性方程组，然后去求解它就行。哪怕是稀疏的矩阵，它的局部最后也会分解成很多稠密的线性方程组，稠密的解完再拼起来，就可以了。这是科学计算里绝大部分问题所满足的特性。

### embarrassingly parallel：令人尴尬的并行

除了上面这类比较复杂的超算程序，还有一类问题，有一个词叫 **embarrassingly parallel**（令人尴尬的并行）——这个名字不是特别好，但很形象：它意味着你的整个计算图几乎不需要什么同步和通信。

对比一下就清楚了。物理系统的时间步模拟：我有 $t=0$，然后有 $t=1$，$t=1$ 的网格里每个点的计算可能和相邻的网格有依赖关系，所以它是一层一层的——先算 $t=0$，再算 $t=1$，再算 $t=2$。这样的依赖图本身已经足够并行化了。而所谓的 embarrassingly parallel，计算图大概长成这个样子：一件东西我可以放出无穷多个——几百万、几千万个计算任务，算完以后最后收一个结果就行。

```text
  分层依赖（时间步推进）              令人尴尬的并行

   t=0   A  A  A  A                    ┌──► 任务 1 ──┐
         |  |  |  |                    ├──► 任务 2 ──┤
   t=1   A  A  A  A                    ├──► 任务 3 ──┼──► 汇总
         |  |  |  |                    ├──►  ...      │
   t=2   A  A  A  A                    └──► 任务 N ──┘
```

这样的任务天生就很容易并行：你只需要先把任务切好，切好以后放到第一个计算机（或者第一个线程）上，再放到第二个、第三个上，于是你就 scale up、scale out 了。

这类例子很多，课上都展示过不少。

**tree search。** 你要下围棋：第一步可能有十种下法，第二步又有十种，那你就有了 100 种、1000 种、10000 种。你只需要在一个线程里，或者哪怕就用几个线程，先搜索十层，你就有好多好多搜索的子树——可能几百棵，可以找到几百万、几千万棵。然后你再把这百万、千万棵搜索子树分配到机器上。前面是段比较复杂、比较小的计算图，后面就是一个 embarrassingly parallel 的过程。

我们实现过 fork-based DFS，你们其实可以直接抄答案：现在你用 AI，只要你有这个概念——你知道搜索的子树是可以并行的——你不要求它，直接说「帮我写一个 Python 程序搜索什么什么什么」，它就会给你一个顺序的 Python 程序；但如果你告诉它可以用 fork-based DFS，它就会给你一个并行化的版本。这样你能用好自己 CPU 上的十几个线程，真的可以快十几倍。

十几倍不是一个小数目。如果你的 CPU 有 20 个核，能快十倍，那就意味着本来要一分钟的任务，只要六秒钟。一分钟到六秒钟，这个差别很大：一分钟你要是等了五六秒没有结果，肯定就去摸鱼了。就像你打开 Claude 让它干活的时候，你一定会去干另一件事，因为不想等它——我自己就做了一个 hook（在办公室那台机器上），每当 Claude 需要用户输入时，它都会「叮」地放一个声音，我就知道它干完了，再回过头去看；现在 Code Interpreter 也有 pet 了，你可以选一个 pet，它跑完会告诉你。但是如果这个任务能从一分钟降到五秒钟，它就不会打断你的思路，你可以在这五秒里再做下一件事。所以哪怕是十几倍的加速，都是非常值得的。

**Monte Carlo 算法。** 如果你要去逼近、拟合一个概率分布，你就不停地在这个概率分布里面采样，采完之后大概就知道，比如这个分布的均值是多少。打个比方：你有一个未知的概率分布，要知道这个随机变量的均值，那你就去采样一千万份，把它们加起来，再除一下。这就是一个 embarrassingly parallel 的任务，因为每一次采样都是独立的——你在第一台计算机上采样 100 万次，第二台采样 100 万次，第三台采样 100 万次，就 scale up、scale out 了。

**视频编解码。** 如果你把关键帧切好了，那么关键帧和关键帧之间的一段视频就完全是独立的，你可以分给两个线程或者两台机器去处理。

这些都是高性能计算里面常见的模式。

### 一个例子：从实数轴到 Julia 集

今天给大家准备了一个例子，叫 **Mandelbrot set**。虽然看起来这不是操作系统课上的内容，但我依然非常想介绍一下，它有一个 walkthrough，是一个分形。

先从最简单的递归公式说起：

$$x_n = x_{n-1}^2$$

它不断地迭代下去，把它画在数轴上，只改变 $x_0$ 的取值。

如果 $x_0 = \frac{1}{2}$，那序列就是 $\frac{1}{2}, \frac{1}{4}, \frac{1}{16}, \dots, \frac{1}{256}$，越来越小、越来越小。所以你看到的是它不停地往左跳，越跳越小。

如果 $x_0$ 靠近 $-1$ 也是类似的：它第一次会跳到一个接近 $+1$ 的地方，然后才往 0 的方向跳。但如果 $x_0$ 往其它地方走，它就是发散的。

于是结论很清楚：$x_0 > 1$ 时序列发散，$x_0$ 在 $-1$ 和 $1$ 之间时收敛，$x_0 < -1$ 时也是发散的。把它们合起来，就是 $|x_0| \le 1$ 收敛（$x_0 = \pm 1$ 对应 1 这个不动点），$|x_0| > 1$ 发散。

```text
   发散       收敛        发散
   ◄──────────┤ ● ├──────────►
   x0 < -1     -1  1      x0 > 1
```

这样就定义了一个神奇的东西，叫做 **Julia set**。

现在把完全一样的序列放到复平面上——注意，还是 $x_n = x_{n-1}^2$，$x_0 = 0$ 平方还是 0，$x_0 = 1$ 平方还是 1，来回跳。区别在于，复数的乘法是带旋转的：它一部分是标量计算，一部分是旋转。

在复平面上你也可以画出它的轨迹：走到某一个地方以后，它就会回来。那你们猜，什么时候它会收敛，什么时候它会发散？这其实已经非常明显了：只要 $x_0$ 位于**单位圆**里，也就是半径为 1 的圆里面，这个序列就是收敛的。

但是如果我们再给它加一个常数 $c$：

$$x_n = x_{n-1}^2 + c$$

你认为还会收敛吗？我干脆把收敛的区域画出来，这就好玩了。每当我改变这个 $c$——在复平面上换一个位置放 $c$——我就看到了很不一样的图形，非常非常不一样的图形。

### 本讲提到的题目

这一次期中测验考到的题目，我按当时讲到的信息重新列在这里，方便你自测；上面各节里已经把每道题的推理过程讲完了，答案里只留最关键的结论。

1. **什么是文件描述符？为什么用「一张表加一个整数」？** 进程需要指代一个已经打开的文件，但地址空间是隔离的，所以不能用指针也不能用名字；Unix 的选择是一张表加一个整数，`fd = 3` 只是数组下标，背后是操作系统里的对象。
2. **fork 之后文件描述符该怎么处理？** 有两种设计：各自独立一个偏移量，或者共享同一个打开的文件、共享偏移量。选后者——否则父子进程同时写日志会互相覆盖；而且只有共享，shell 里用分号或 `&&` 连起来的两个命令，输出才会合并而不是交叉。
3. **`execve` 的函数原型是什么，它做了什么？** 换掉代码、数据和栈，但保持 fd 和 pid。
4. **要用终端做出一个 UI（Vim、Claude Code 这类），需要哪些机制？** 要能画界面：Unicode 只是一部分，主要靠 Escape code 控制光标位置和擦除屏幕；再加上 PTY，以及信号机制（大语言模型吐 token 时要能 Ctrl+C）。
5. **给你一个二进制文件，怎么判断它运行时是否需要加载 `.so`？** 看 ELF 的 `.interp` section（记录动态链接器路径），在 gdb 里看，或者用 `ldd` 之类的命令行工具。
6. **怎么知道哪个变量是被哪条指令修改的？** 用 watchpoint：gdb 提供了在某个地址被修改时停下来的机制。
7. **环境变量存在哪里？和栈有什么关系？** `print environ[0]` 拿到地址，再去这个地址所在的 mapping 里查它在地址空间中的位置。
8. **怎么定位执行 `mmap` 的 syscall 指令？从 `_start` 到 `main` 执行了多少条指令？** trace 所有指令并单步，写一个 hook，每次停下来都检查一遍；同样的方式可以处理 `_start` 到 `main`。数指令条数还可以借用 gdb 的 reverse execution——它本来就要记录每条指令。
9. **为什么搜 `struct FILE` 找不到定义？** 它是 typedef 出来的 `_IO_FILE`；也可以写一个引用它的 `.c` 文件，用 `gcc -E` 展开预处理结果来看。
10. **fork 对 buffer 和 lock 有什么影响？** 互斥锁（比如用 futex 实现）在用户空间一定有一个 `int lock`，它位于进程自己的地址空间里，所以会被复制；buffer 会复制，锁的整数值也会复制。fork 时锁若被别的线程持有，子进程就会死锁。
11. **多线程的程序里怎么 fork？** 线程默认异步，fork 时每个线程都可能在执行任何一条指令，没法直接停下来；POSIX 的选择是只有调用 fork 的线程存活。唯一安全的选择是 fork 之后立刻 `exec`。
12. **实现 `popen`（读）该怎么做？** 用管道；记住文件描述符在父子进程之间会复制，关掉该关的、腾挪好该腾挪的 fd 即可。

## 从 Mandelbrot 到松散计数器：并行算法与并发数据结构
> 对应块：BLK36 | 覆盖分集：P18下 | 块标题（分集名）：《并行算法和数据结构（下）》

### 从 Julia 集到 Mandelbrot 集

接着上一讲，我们把参数换一换：迭代的规则不动，只把迭代的起点固定下来，改一改参数 $c$，就得到了另一个图形——而且是完全不一样的图形。

这一张图很有味道：它有一大块是收敛的，另有一些地方发散，而在收敛与发散的边界上，情况非常复杂。这种图形就叫 Mandelbrot 集。

它对并行这件事的态度和 embarrassingly parallel 是一样的。要画一张 Mandelbrot 图，我可以把整张网格切开——甚至不用切成网格，直接切到每个像素：每一个像素都是一次独立的计算，我甚至可以把每个像素分配给某一个线程去算。当然没必要这么极端，分成一块一块、每个线程负责其中一部分像素就够了。

```text
   +---------+---------+---------+
   |   T0    |   T1    |   T2    |
   +---------+---------+---------+
   |   T3    |   T4    |   T5    |
   +---------+---------+---------+
```

读图：整张待渲染的图被切成互不重叠的小块，每块交给一个线程；块与块之间没有任何共享状态，所以谁算哪一块都行，谁先算完也不影响别人。

它还有一个很好看的性质：把边界上的任意一小块无限放大，图案依然精细，放大非常非常多倍之后里面还是无穷精细的图案。而这种"每个像素都完全独立"的计算，正是后面所有讨论的起点。

### 一段插话：AI 先让数学概念有了直观

这里我花了一点时间讲了些不该在操作系统课上讲的内容——而且很糟糕的是，我把这些不该讲的内容讲得比操作系统课本身还好，照这个逻辑，大学要完蛋了。

### 这种任务怎么并行：切成小块，但别把自由全给开发者

对于这种 embarrassingly parallel 的问题，第一反应当然是拿线程库自己写：把它变成生产者消费者。把图像切成一百万个、一千万个甚至更多的任务，每个任务块里装几万或者几十万个像素；消费者每次从队列里取出一个任务，把那些像素填进一个巨大的数组。这就行了——用我们之前学过的信号量、条件变量这些机制，完全可以实现。

但对很多同学来说，这条路的成本太高了。比如学物理、学化学的那些理科专业的同学，编程经验很少，也没写过并发程序、没吃过那个苦；真要让他自己写 synchronization，他一定会错到怀疑人生，而且手里没有工具去 debug，data race 那种 bug 是查不出来的。

所以对于这种 embarrassingly parallel 的任务，包括科学计算里的大量类似程序，我们不愿意把太多自由交给开发者，而是提供一套尽可能简单的编程机制，同步也受限——比如你只能传消息。于是有了 MPI、OpenMP 这些东西。你们写 system 程序会发现它们并不是特别好用；但如果你写的是数值计算模拟的程序，OpenMP 简直好用：比如你要创建 128 个线程，你手上有一个 for 循环，就可以直接让这个 for 循环跑在 128 个线程上。

### 求 Mandelbrot 集：自己写线程，还是加一行 pragma

我要画的是一张 6400 × 6400 的 Mandelbrot 集，这还挺大的。每个像素 $(x, y)$ 都要执行一段计算；`TWorker` 就相当于遍历整个图像空间，如果某些像素是属于我自己的，我就把它求解出来，写进 `picture(x, y) = Mandelbrot(x, y)`。这个任务就这么简单。程序里还有一个现成的 `monitor`，它会实时追踪渲染进度，所以你能看着它一点一点画出来。

#### 用线程库：spawn 与 join

按常理，用线程库就是：

```c
for (int i = 0; i < nthread; i++)
    spawn TWorker;
```

创建 `nthread` 个 `TWorker`，再做一次 join，事情就搞定了。

这其实也就是在定义一个计算图：程序第 74 行到 77 行定义的就是"有若干个 `TWorker`，做完以后把它们 join 起来"这样一个图。

#### 加一行 pragma：让编译器去干脏活

同一个计算图，我也可以用另一种方式定义：我说我要 `nthread` 个线程并行，把这个循环并行化。注意，这个循环本身只是一个顺序的循环；我写下这段代码的时候，既不知道我的系统里有多少个 CPU，也完全不懂并发编程，但只要加上那一句话，就像魔法一样，我的程序自动并行化了。

先 `make try`，链接时加了 `-fopenmp`。跑一下：一个线程的时候，它能看出是从左到右一点一点算出来的（画的是刚才那种局部放大过的 Mandelbrot），大概花了 18 秒；创建 16 个线程之后，速度非常明显地变快，3 秒。

```text
   1 个线程    :  ~18 s   一条一条扫描像素
   16 个线程   :  ~3 s    同样的代码，只多了一行 pragma
```

最后的结果是一张 6400 × 6400、形状非常精细的 Mandelbrot 集。所以你看，一门好的编程语言、一套好的编程机制，对人类来说有多有用。

### 一个物理系同学的魔法，和 AI 的默认选择

一个物理系的同学，学过 C、会写一点做计算的 C 程序，他不需要知道任何线程概念，不需要来上我的操作系统课，只需要记得师兄告诉他的一句"魔法咒语"，或者翻一翻文档和手册看到那句话，就能把超级计算机里的 128 个线程都利用起来，快上 128 倍。

顺便说一个很实际的技巧。你们现在写了一个 C 程序，需要把它并行化，可以让 AI 帮你改。它会倾向于怎么改？我认为 AI 大概率给你一个 Pthreads 的实现——它默认你的机器上不一定装了 OpenMP。而 Pthreads 版本会往你的代码里加入各种同步，改完之后代码可能变得你自己都看不懂。

但如果你在 prompt 里多加一句"你可以用 OpenMP"，结果就不一样了：它可能在尽可能少改动你代码的前提下完成并行化，你的代码依然保持干净整洁，那些 dirty work 交给编译器去做。

当然，实际当中不管是 OpenMP 还是 MPI，都有比这里讲的好得多的编程机制，它们还有同步机制、可以给你做共享等等。你们可以去试一试；更简单的是，往自己的武器库里多放一条 prompt。

### 高性能计算真正难的地方

上面这个程序有一个隐含的假设：我假设每一个 SRAM 访问的代价都差不多。只有这样才能让每个线程跑得差不多快、差不多时候结束。但实际上是做不到这一点的。

你们的 CPU 之间，访问内存的速度是不一样的。放到多个计算机的集群里，计算机和计算机之间的通信速度与带宽也不一样：同一个机柜内带宽大；机柜和机柜之间总带宽就没那么大，延迟也增加了；更远的机柜还要经过更多交换机，延迟更大。你怎么解决网络通信的问题？网络通信甚至会不可靠。此外还有怎么管理功耗、怎么管理散热、怎么管理稳定性、存储、容错、软件、工具链。

这些都当然没法在这门课上讲。但我觉得到今天你们完全可以去试一试：如果有同学对超级计算机特别感兴趣，可以自己去找一些 HPC 上的 workload，在自己的电脑上跑一跑找找感觉，甚至做一些优化，在 AI 的帮助下都可以试。你可能就此入门了高性能计算和并行编程。

### 实验 gpt.c：那一处可并行的循环，自己找

实验里我们发布了那个 `gpt.c`。我希望大家不要去偷看答案——因为这个实验是我"抄来"的（不能叫抄，我给了它 credits）：我裁剪自 Andrej Karpathy 的 `llm.c`，它有一个 GPT-2 的版本，那就是原本的代码。

### 从"写串行程序"到 harness engineering

#### OpenMP：写给非专业人士的魔法

OpenMP 这样的机制，对非专业人士是非常友好的：我只需要写串行的程序，只要里面有一两个可以并行的 for 循环——不管它是一层的还是两层的——系统都可以自动利用好多处理器系统里的 CPU。

#### 没有人再读代码了，但你要能验收

而现在我觉得这件事又变了。现在你已经不需要人类友好的编程机制了，因为反正没有人会去读代码了：我们所有人都在做 harness engineering——你只要给我那个东西最终是对的，我根本不 care 你是怎么实现的，也不 care 我能不能维护它，因为我们谁也不写代码了。

所以你可以轻易把这些交给 AI agent。但你要把 harness engineering 做好，要确保最后 AI 交给你的那个东西是你要的，而不是它幻觉出来的一个什么很有意思、很 fancy 的东西——那不是你要的。

#### 先自己摸一遍工具，再交给 AI

我们安排了很多实验，帮大家去构建 computer systems 里面那些重要的概念。比如我们有一个 `sperf`，这是一个 profiler；在 `gpt.c` 这个实验里你会再次体验它，用它去找并行计算里面最 intensive 的那部分。你可以用 trace，可以用 profiler。你自己用过之后，就会对这个工具有印象，下一次你会告诉 AI"你也用一下"，而不是让它直接帮你逃课。

因为 AI 对大语言模型非常清楚，你如果直接让它并行化 `llm.c`、并行化 `gpt.c`，它马上就给你搞定——所有作业你都可以直接把要求告诉 AI，它马上就能帮你搞定。但这样做的后果是：期中考试、期末考试的时候，你不知道该说什么，因为你没有建立正确的概念。你需要清楚地知道发生了什么，至少要清楚地知道为什么 AI 能知道，你才有可能驾驭它。

至少我们目前是这么想的。未来是不是也可能完全不需要这样，我也不知道。

### 并行数据结构：当程序就是一串 sum++

并行算法讲完了，我们再回到另外一个问题——比并行算法更难一点的：并行的数据结构。还是回到 `sum++`。

刚才高性能计算里的那些任务，不管是可划分的任务还是 embarrassingly parallel 的任务，回到 `sum++` 这个例子上，它们的应用场景都是：问题规模很大，而需要串行的那点 `sum++` 足够少、它不是瓶颈。可能每个计算节点里都有一个 `sum++`，但相比于一个计算图节点里的海量计算来说，那只是非常少的一部分，所以它天生就是可以并行的。

但如果程序里就是有很多并行的数据结构操作呢？如果这个程序就长成"很多线程一起 `sum++`"的样子，你不就没办法了吗？

现实中这样的程序肯定有：

- **操作系统内核**：内核里有大量的数据结构。你的每一个进程、每一次访问文件，不管访问的是进程相关的数据结构还是文件相关的数据结构，我都要上锁——两个不同 CPU 上的两个线程同时访问同一个数据结构里的 field，那就是 data race，不上锁内核就错了。内核里有无穷多的这种并发 bug，所以我们有 ThreadSanitizer，操作系统里面也有。操作系统内核就是一个需要非常频繁地做并行数据结构操作的东西。
- **数据库与点赞**：你们人人都去刷热搜、给同一个帖子点赞。虽然现在有些办法可以用更巧妙的方式实现、不必去上同一把锁，但如果它的实现就是一个"点赞数加一、要上锁、然后所有读者都要去读那个点赞数"，那它就相当于一个 `sum++` 的问题。热点一来，所有人都在刷，这就是一个并行的 `sum++`。
- **网络游戏的服务器**：很多人挤到同一个位置，你要移动、他也要移动，两个人想移到同一个位置的时候，就必须有锁的保护——或者至少要有一些同步，才能决定到底由谁走到那个位置。
- **量化交易**：那里也会有各种各样这类代码。

### 让 sum++ 变快：放松可见性

`sum++` 你已经觉得不可能更快了，因为这就是 sum，`sum++` 就是我要的。它怎么还可能更快？答案是真的有可能：我们可以放松其他线程看到 `sum++` 的及时性。

先看现在这把互斥锁给了我们什么。它有 release 和 acquire 的语义：一次 `sum++` 里有 load sum（比如读到 100），然后 store sum 等于 101。这意味着在写者 release 完之后，只要有人 acquire，他就一定百分之百能看到这个 101。但是这个可见性——我看到自己的修改及时地反映给所有人——是要付出代价的。

代价从电路上看很清楚：每一个 CPU 都是独立的，每个 CPU 都有自己独立的 L1 cache。缓存不是可有可无的东西：如果让每一条指令都去访问内存，那个内存非常非常慢，你的 CPU 就不可能运行在 3 GHz、5 GHz 上，它根本办不到。所以所有的指令和数据都是从离自己很近的 L1 SRAM 缓存里走的，之后可能有共享的 L2 cache，再往后才是 RAM。

```text
      CPU0                      CPU1
  +-----------+             +-----------+
  |  L1 SRAM  |             |  L1 SRAM  |
  +-----+-----+             +-----+-----+
        |                         |
        +------------+------------+
                     |
              +------+------+
              | shared L2   |
              +------+------+
                     |
              +------+------+
              |     RAM     |
              +-------------+
```

读图：每个 CPU 有自己的 L1，指令和数据都走最近的缓存，这就是 CPU 能跑到几 GHz 的前提；一次 store 要让别的 CPU 看见，就必须沿着总线把新值传播出去（不同 CPU 实现不同，可能是一个环，也可能是一个目录），而且大家改的是同一个地址上的同一个变量，还要有额外的协议让别人知道我改过这个内存地址。

这些都是开销。所以还有另一条路线：不要着急让别人看到这个 101。

做法是：我为每一个线程创建一个本地的 sum（`sum_local`），所有的 `++` 都打在自己的 `sum_local` 上；每当本地的 sum 加到 100，我就上锁，把这个 100 加回全局的 sum，然后把我本地的 sum 变成 0。

```text
   +-----------------+                    +----------------------+
   | local = local+1 |   flush a batch    | lock; global += n    |
   | 99 of 100 times | -----------------> | local = 0; unlock    |
   +-----------------+                    +----------------------+
```

读图：一百次自增里有九十九次只碰线程自己的本地变量，不产生任何跨 CPU 的传播；只有攒够一批才去抢一次锁，把这批增量一次性并进全局。

这意味着什么呢？我确实想要一个全局的 sum，但对所有人来说，没有人能够看到一个真实准确的 sum。你 load 到 sum 的那一刻，不管你上没上锁，你看到的是 100 还是 101；等你执行下一条指令的时候，你已经不知道 sum 是多少了——你看到的 sum 永远是旧的值。除非你持锁做 `sum = sum + 1`。

所以如果场景允许"点赞数稍微有一点出入、晚一点不要紧"，那我完全可以用线程本地 `++`、隔一段时间再把它加回去：这样绝大部分计算又变成了本地的，只有少部分需要上锁。这就是一个 sloppy 的、比较松散的 counter。你们现在看到的点赞数其实就是这么实现的——它不代表那个真实精确的点赞，它可能需要延迟一会儿才会变精确。

刚才这个实现也是 overly simplified 的。回写的触发条件可以是"攒够一个值"，也可以是按时间：比如每过一毫秒，或者设一个一毫秒的 timeout，只要超时了、哪怕没攒够也把本地 sum 加回去。这样我可以保证：任何人读这个 sum，读到的都是 1 毫秒之内的值。这么一来你就会觉得这个 sum 还是可以用的，完全可以用。

> **结论**：牺牲可见性、牺牲强的 serializability，可以换来一个更高效的并发数据结构；而"把尽可能多的计算留在本地"，是并发数据结构优化的一个非常关键的地方，也是你们实现 `malloc` 时非常关键的一点。

### thread_local：每个线程一份的变量

既然都讲到 `sum_local` 了，你们是不是也不喜欢它？很难看：每次都要写 `sum_local[tid]`，还要 `sum += sum_local[tid]`、`sum_local[tid] = 0`。

我不喜欢它，你也不喜欢它，操作系统的设计者不喜欢它，编程语言的设计者也不喜欢它——没有人喜欢它。所以我们有了一个叫 `thread_local` 的 keyword。

- 这个关键字从 C++11 开始有，C23 也正式引入，所以 C 语言里面也有 `thread_local` 了；以前你只能用 `__thread`，现在可以直接写 `thread_local`。
- `thread_local` 类型的变量会自动在**线程创建的时候**得到一份拷贝。
- 它可以是任何类型：可以是一个 struct，可以是一个指针，你也可以给它赋初值。
- 所以只要定义一个 `thread_local int sum_local;`，在 `Tsum` 里用它，每个线程就都有自己的 `sum_local`。

> **易错点**：如果你在函数的作用域里——在一个大括号的作用域里、非全局作用域里——定义一个 `thread_local int`，编译器会直接报错。因为它不准许：`thread_local` 的含义是每一个线程一份，而定义在函数里意味着每一个栈帧、每次函数调用都有一份，这两个含义本身是冲突的。

做个小实验：`thread_local int x = 100;` 然后在 `Tworker` 里 `x++`。

如果这里写成普通的 `int x = 100;`，那当然就是 data race，你可能看到 101、102、103、104。但写成 `thread_local int` 的话，你应该看到四个 101。程序里还会把 `x` 的地址取出来，所以你应该认为每一个 `Tworker` 看到的 `x` 地址是不一样的——你可以相信编译器，它确实打印出不一样的地址：线程 1、2、3、4 各自的 `x` 地址不同，而加 1 之后的值都是 101。`thread_local` 确实在起作用。

### thread_local 落在哪儿：RIP、RSP 与 FS

那它是怎么实现的？编译器清楚地知道每一个变量定义成什么样，包括你定义的 `const`、`volatile` 这些 modifier。于是访问不同存储位置的变量，用的寻址方式也不同。

| 变量 | 存放位置 | 访问方式 |
| :--- | :--- | :--- |
| 全局 `int x` | 全局数据区 | RIP（PC）相对的寻址 |
| 函数里的局部 `int y` | 当前栈帧 | RSP 相对的寻址 |
| `thread_local int x` | 线程自己的局部存储 | 相对于线程局部存储的一个 offset |

对 `thread_local` 来说，我要的就是一个"相对于当前线程"的基准。寄存器不够用了，x86 里面就"偷用"了 FS 寄存器。所以你在自己的机器上编译我这段演示代码、并且用 `objdump` 去看，就会看到它会把这个访问翻译成一个 `FS + 一个常数偏移量` 的 load 或者 store。

顺手还能做件事：把 `gcc` 换成 `musl-gcc`，再加上 `-static`，用 musl 的 gcc 和静态链接可以编译出更干净的代码。它能运行，而且地址不太一样，但是行为还是一样的。

### `thread_local int x = 42` 的 42 是谁写的

`thread_local` 是支持初值的。既然你可以写：

```c
thread_local int x = 42;
```

那问题来了：这个 42 是谁赋的值？

它和数据区不一样。如果数据区里有一个 `.data` 的 `x = 42`，你的 ELF 文件里就有一处存着 42；loader 在 load 的时候把 ELF 文件整个搬到内存里——不管是 mmap 还是你一个字节一个字节拷贝都可以——这个 42 就被搬进去了。它只要搬一次就够了，这是全局的 `int x = 42`。

局部变量里的 `int y = 42` 呢？编译器会在这个函数的头部编译出一个 mov 之类的指令，把 42 写进 `y` 里。这个行为你们都知道，在计算机系统基础课上都看过汇编。

那 `thread_local int x = 42` 呢？它应该要在 ELF 里——至少这个 42 得存在于某个地方。但是内存里等于 42 的那个 `x`，必须在**每一次线程创建的时候**都被执行一遍：你每创建一个新线程，就要有一个 42 的拷贝。这其实带来了相当大的麻烦。

### 让 AI 去读 ELF：TLS 是怎么建起来的

这些问题你完全可以直接问 AI。它会去读整个 ELF 文件，也包括反汇编出来的代码；读完它就知道整个线程的内存布局：有一个 `struct pthread`，有一个指向 TLS 数据的指针，还有一个 `.tdata`——一个 TLS 的段。

它给出的答案是：

> **答案**：子线程的 TLS 是先执行 `pthread_create`，然后 mmap 分配一个线程栈，同时分配 TLS 的区域；而且它是在主线程里、而不是在创建出来的子线程里初始化这个 TLS 的。也就是说，在 spawn 的时候它会调用一个叫 `copy_tls` 的函数，把 `.tdata`（它也在 ELF 里）复制到这个线程的 TLS 区域里去。

```text
   struct pthread (one per thread)          TLS area (one per thread)
   +--------------------------+             +------------------+
   |  ...                     |             |  x = 42  (copy)  |
   |  pointer to TLS data ----+-----------> |  ...             |
   |  ...                     |             +------------------+
   +--------------------------+

   pthread_create: mmap thread stack
                 + allocate TLS area
                 + copy_tls: copy .tdata (from the ELF) into the TLS area
```

读图：每个线程有一套自己的 `struct pthread`，里面有一个指向 TLS 数据的指针；真正给这个线程准备 TLS 的不是子线程自己，而是创建它的那个线程——`pthread_create` 分配完线程栈和 TLS 区域之后，直接把 ELF 里的 `.tdata` 拷过去，`thread_local int x = 42` 的初值就是这么来的。

所以操作系统的实际实现，会比你们想象的复杂一点。我讲线程那一节的时候忽略了这一点——如果我第一节课讲线程时就讲这些细节，你们马上就会不知道我在说什么。但你们已经玩过线程库以后，我就可以再说一句：我们的系统里面还有一个叫 thread-local 的机制，你定义 `thread_local int x = 100`，它会存在 ELF 的 `.tdata` 里，然后在每次线程创建的时候被 `copy_tls` 复制一份。这就有了。

### 并行数据结构：把锁拆开

并行数据结构，当然是为了维护一个状态：一个数据结构。它可以是一个线性表，可以是一个最简单的数组，也可以是一棵二叉树，或者一个图——这些都是 abstract data type。所谓 ADT，就是"我有一个 data structure，它有一个接口"，比如这个接口可以 push、可以 pop；然后你就把这个东西想象成一个可以 push、可以 pop、而且高效的东西，剩下的各种应用程序都建立在这个抽象之上。

所有的数据结构都有一个共同特点：它们在内存里是分散存储的。不管是一个很大的数组还是一棵二叉树，它要么描述一个集合——比如 `1, 2, 5, 7` 这样一个 sorted set，你可以用平衡二叉搜索树、红黑树去维护一个 ordered set；要么描述一棵有根有孩子的 tree，或者一个 graph。而且它们越大，越是一个有局部性的结构：讲树的时候，我们一般关心的是这个节点周围的节点有什么性质，或者全局地关心这棵树有多大；讲集合的时候，我们关心的是某个元素在不在这个集合里——5 在不在、8 在不在；再进一步，基于 set 还能实现 map 或者 dictionary，知道对某个 key 可以找到和它对应的 value。**所有这些数据结构天生都是有局部性的。**

这就意味着：两个线程要同时访问这个数据结构，你当然可以在这个数据结构上直接上一把大锁，那就变成所有线程排队访问整个数据结构。但很有可能，我的两个线程访问的是两个**不同的元素**，它们之间根本没有冲突。一个线程想把 7 删掉、另一个线程想询问 7，那我一定得有一把锁把它保护起来；但一个线程问 5、一个线程问 7，或者一个线程删 2、一个线程读 7，这些都是可以并行执行的。

也就是说，读写数据结构的一部分，其实不需要锁住整个数据结构。前面那个 sloppy counter 其实就已经用了这个性质：你可以把那个 sum 想象成一个 list 的 append——每加 1 就是往 list 上 append 一个节点，问 sum 是多少就等于问这个 list 的 size。我在本地攒了一个 list，每次直接往本地那个 list 里加；等到本地加到 100，我就对全局的 list 上一把锁，把这 100 个节点一并拼到上面去。sum 和数据结构之间的关系，就是这样。

> **定义**：锁的拆分，就是为数据结构的**不同部分分别上锁**，而不是用一把大锁盖住整体。最好情况下，绝大部分时候线程都是并行的，只有在确实要访问同一个元素的时候，才会去争抢同一把锁。

### 三种常见做法

| 做法 | 用的东西 | 划算在哪里 |
| :--- | :--- | :--- |
| 用原子指令 | 一条原子指令，比如原子的 `sum++` | 临界区小到只剩一次计数、一次 slot 分配 |
| 区分读锁和写锁 | `pthread_rwlock_t` | 读多写少：读与读之间本来就不冲突 |
| 把锁做划分 | 为数据结构的不同部分分别加锁 | 数据结构各部分的访问本来就互不相关 |

**如果你能用一条原子的指令，就尽可能用原子指令。** 比如你们可能会好奇我的 Online Judge 是怎么检查的——你们各种过不去、有 bug，有 bug 就会被它逮住。我的做法是：Online Judge 里分配了一块非常大的内存，然后我有 T1、T2、T3、T4 这些线程；任何一个线程执行了一次 `malloc`，我就在这个数组里面放一条日志，记下"malloc 返回了多少"。也就是说，每个线程都产生日志，但是我不上锁；我只有一个原子的计数器 `n`，我只要原子地把 `n` 加一，就得到了一个空的 slot，拿到空 slot 之后再把数据写进去。相当于有两个指针：一个不停地往后跑（分配），一个从前往后跑（回收）。当然我用了一些 trick——实际上我的程序是有 data race 的，但这个 data race 在实际中是正确、安全的。所以我是一边往前跑一边分配、一边让回收的指针往前挪。这样的话，我会在一个线程里回收另一个线程分配的单元，而这是你们非常常见的一个 bug 来源。原子指令非常好用，但它不在我这门课的范围里；有兴趣的同学可以去选梁辉民老师那门并发编程的课，它会讲怎么用各种各样的花活儿去实现并发算法。

**然后，我们可以区分读和写的锁。** 线程库里有一个 `pthread_rwlock_t`。什么意思呢？读是可以不止一个线程同时做的：比如集合是 `1, 3, 7`，两个线程都想去找 3、去读这个 3，只要你不去改它，完全 OK。但是读和写是冲突的：如果你拿到一把写锁去写 3，那别人也不能读了。所以这种不对称的锁允许同时有多个线程持有读锁，但只有一个线程能持有写锁，并且一旦有人持有写锁，读锁也不能获得。这样也能提升性能——至少读全部都可以并行了。不过这两种技术都比较难用，你们使用的时候要谨慎：读写锁没问题，原子指令你们现在的知识还不够。

**最后一件你们至少可以做的事，就是把锁做划分。** 我举的例子是哈希表。哈希表是一种非常高效的 key-value 数据结构，大家都知道：一个元素来了，比如 `x` 来了，我会先为它算一个哈希函数，再把它放到这个函数算出来的位置上。既然每个元素落在哪里由哈希函数决定，一张表天然就被分成了若干互不相干的部分，那把覆盖整张表的大锁，也就可以拆成覆盖各个部分的锁。

```text
   one lock for everything                one lock per part
   +------------------------+             +--------+ +--------+ +--------+
   |   the whole structure  |             | part A | | part B | | part C |
   +------------------------+             +--------+ +--------+ +--------+
        every thread queues                  only same-part access waits
```

读图：左边是一把大锁盖住整个数据结构，所有线程依次排队；右边是每个部分各自一把锁，只有访问同一部分的线程才需要互相等待——这就是锁划分，也正是前面那个 sloppy counter 思路的一般形式。

### 本讲提到的题目

**思考题**：`thread_local int x = 42;` 里的这个 42，是谁、在什么时候写到每个线程自己的那个 `x` 里的？

**解析与答案**：

- 42 本身必须存在于 ELF 里，它落在 ELF 的 `.tdata` 段（TLS 数据段）中。
- 但"把 42 写进 `x`"这件事不能只做一次——每个新线程都有自己的一份 `x`，所以每创建一个线程就要重新进行一次。
- 真正做这件事的是**创建线程的那个线程**：`pthread_create` 在 mmap 出一个线程栈、并分配好这个线程的 TLS 区域之后，调用 `copy_tls`，把 ELF 里的 `.tdata` 复制到这个线程的 TLS 区域里。也就是说，初值不是子线程自己去赋的，而是创建者在 spawn 阶段拷贝过去的。
- 对照另外两种情况就更容易记住：`.data` 里的全局初值由 loader 搬一次就够了；函数里的局部 `int y = 42` 由编译器在函数头部生成一条 mov 写进去；而 `thread_local` 的初值由 `copy_tls` 在每次线程创建时拷一份。

前几节课我们一直在写各种各样的并发程序，也在对付并发的 bug。做这件事的过程里，其实反复出现了一个概念——计算图。每次课我都会提一下：我们在这里会有一个计算图，它长什么样。这是一个非常核心的概念。

今天，前面这些铺垫会一次性兑现：你们会看到之前几节课学的东西，怎么一下子解释清楚今天在各种地方——不管是数据中心里，还是浏览器的网络栈里——它们的并发编程到底是怎么实现的。我的并发其实已经上了很长时间了，但终于在这一刻，你们可以体会到自己学到的东西真正有一点用处。

### 先把上节课的尾巴收掉：malloc、free 与"你需要什么性能"

上节课我讲了并行的算法，尤其是 embarrassingly parallel 的那几类问题，还有很酷的 Mandelbrot set 的演示；也讲了一些并行的数据结构，比如哈希表并行实现起来会很困难，你们可以做一个 sloppy counter，牺牲掉一定的、会带来延迟的精度，把计算留在本地，从而让程序能够 scale up。

上节课还有一个收尾的部分和你们的作业直接相关：malloc 和 free。做任何性能调优的时候，一把大锁保平安是能过几个 easy test case 的，但那个 hard test case 你过不了。这时候，在正确的基础上，请始终记得这句话：premature optimization is the root of all evil。如果你总是想当然地、脑热地去做优化，那结果很可能不符合你的预期。

我确实看到同学在群里说："我让 GPT-5 帮我修，然后这个 GPT-5 也还是过不了。"问题往往出在你给它的 prompt 上。大语言模型已经被调教成彻头彻尾的舔狗了：你的指令如果不正确，它也会强行跟随你的指令，你说什么它一定做什么，这是它强化学习出来的 reward。

#### 性能必须和 workload 绑在一起看

我们在算法与数据结构课上的习惯是死盯 worst case：这个 worst case 要尽可能特别特别地好，你才能通过那道算法题。所以你们脑子里拿到任何一个问题，第一反应都是"这个 worst case 是 $O(1)$、$O(n)$ 还是 $n\log n$"，因为你们总是被问这样的问题。

但真实的系统要的不是这个。对实际的系统来说，你需要的是在真实的一个分布下的表现——比如你考虑排序的时候总会说"已经排好序的顺序是最差的"，或者"某个精心构造的数据是最差的"；可在实际当中，你的业务系统收到的内存分配序列、你的集合收到的 insertion/deletion 序列，是符合现实物理世界中的概率分布的。你要做的，是在这个现实分布下尽可能好。

> **结论**：实用的性能指标 = 真实分布下的表现 + 一个可以接受的 worst case 上界。两边都要，缺一个都不行。

worst case 也不能太坏，还有一个安全上的理由：如果你的算法有一个指数级的 worst case，那别有用心的攻击者就可以通过给你发那种特别差的请求，让你的系统变得非常非常慢。

Apache 的 httpd 在很长一段时间里都是整个互联网的核心支撑。你们都知道 HTTP 请求可以带查询参数：请求里有一个问号，后面可以写 `a=b&c=d` 这样的请求字符串，而这个字符串会被插入到一张哈希表里。只要你精心构造这些字符串，让它们所有的 key 都映射到哈希表的同一个桶里，你就可以让那个 Apache 的 server 变得很慢。

> **提示**：这是一个针对哈希表的复杂性攻击（algorithmic complexity attack）漏洞。它打的不是加密，而是"你的数据结构在构造出来的输入下会退化成什么复杂度"。这也解释了为什么实用系统里的哈希表实现要考虑防碰撞，甚至要随机化哈希种子。

#### malloc 有大有小，越小的对象越频繁

考虑 malloc 的时候，很多人的第一反应是："所有的 malloc 都是一样的，因为它们都是一个整数。"其实 malloc 是不一样的。

大对象不是凭空出现的：哈希表 resize 以后装不下了，要乘 1.5 倍大小，你就得分配一块很大的新内存，或者回收一块很大的内存；或者你需要一个非常大的缓冲区块，要映射一块很大的内存，比如磁盘上的一个大文件。这就意味着：你一旦分配了一个很大的对象，之后一定会读写它很多次。

反过来说——分配一个比如 100 兆的对象，只读写里面几个字节，然后把它 free 掉，这是什么？这是一个 performance bug。你不该申请那么多内存，也不该使用那样的数据结构。你开一个能装 100 万的哈希表，只用三个元素就 free 了，那就应该用一个更紧凑的 set 或者 map，而不是去分配那块很大的内存。

> **结论**：实际 malloc/free 的 workload 有一条很清晰的推论——对象越小，创建和分配越频繁、生命周期越短；对象越大，越倾向于稳定地长期停留在内存里。

- 小对象：临时的字符串，它可能在这一次请求里被贴到最终的文本里，然后这个字符串就再也不会用了。这类对象很多、很琐碎，生命周期也很短。
- 中等大小对象：比如你要生成一个 HTML 请求，这个请求最终会变成一个字符串，那它的生存期一定比那些零散的小对象要再长一些。
- 大对象：几兆到几百兆，通常是一个用来维护整个系统全局状态的大数据结构。越大，这个数据结构就越倾向于稳定，会在内存里停留更长的时间。

所以如果想通过这个实验，你几乎只要管好小对象就可以了。小对象的分配回收的 scalability 是主要瓶颈——这和我们讲过的 `sum++` 其实是一样的。把 `sum++` 想象成一个数据结构，就是 list 的 append：我可以在本地持有一个别的线程看不到的 list，每次加加都往里面 append 一个元素，隔一段时间再把这个 list 放回全局那个主的 list 上。

#### slab 与 segregated free list：把快路径留在本地

大块内存直接用 mmap 分配就好，这样你在整个内存里可以得到很多块 slab。slab 的大小定得比较随意：理论上，尤其对现在的系统、对你们的 lab 来说，浪费一点内存并不是很糟糕的事。比如 slab 定 1 兆，你就认为大于 1 兆的对象是非常非常大的对象；定小一点，4 KB、8 KB，也都是 OK 的。

核心目标是：让小对象的分配和回收都能直接在本地完成。现在我有 T1、T2、T3 几个线程——真正实现 malloc 和 free 的时候，一般还会做成 per-CPU 的池子，每个 CPU 一个——每个线程都可以持有一些 slab，要分配就直接从自己的 slab 里拿。slab 内部是哪种小数据结构都行：你想做二叉树也好，做空闲链表也好，任何一个传统经典的算法都可以。

```text
        T1                    T2                    T3
   +-----------+         +-----------+         +-----------+
   |  slab #1  |         |  slab #1  |         |  slab #1  |
   |  [lock]   |         |  [lock]   |         |  [lock]   |
   | free list |         |   btree   |         | free list |
   +-----------+         +-----------+         +-----------+
        |                     |                      |
        | 本线程的分配/回收都走这里                    |
        +---------------------+----------------------+
                              |
                              v   自己的 slab 用完了，才去找系统要
                    +--------------------+
                    | mmap 一块新的 slab |   <-- 只有这一步上大锁
                    +--------------------+
```

读图：绝大部分分配与回收都在本线程自己的 slab 里完成，只有"向系统申请新 slab"这条慢路径才需要一把全局的大锁。

分配的时候，只需要获得这个 slab 的锁就可以了。而这个上锁其实非常快，因为绝大部分对象都是线程自己分配、自己回收的——比如为了贴进 response object 里的那个临时字符串就是如此。只有别的线程试图 free 这个 slab 里分配出来的对象，也就是我 T1 把这个对象交给了别的线程的时候，别的线程才会来碰这把锁；其他时候都只有我 T1 会持有它。

这就是一个非常安全、也非常典型的设计：就像一张属于我自己的桌子，钥匙就摆在桌上，一般别人都不会拿；我作为 T1 随时伸手去拿，拿了立即完成这个 slab 里的分配或者 free，再把钥匙放回去。绝大部分时候，这件事都是 $O(1)$ 的。

更快的一种做法，是浪费空间换极简。你希望把这个 slab 切成等大的小块：如果按 16 字节算，就 16 字节一块、16 字节一块地切下去，把所有空闲小块串成一条空闲链表；再准备 32 字节的切块，同样用一条 free list 串起来，以此类推。这样每一个线程就持有各种不同大小的 slab。

```text
  size class 16B :  [free] -> [free] -> [free] -> ...   pop / push 都是 O(1)
  size class 32B :  [free] -> [free] -> ...             malloc(17) 落到这一档
  size class 64B :  [free] -> ...
        ...
  每个线程持有若干种 size class，每一种一条 free list
```

读图：`malloc(17)` 会落到 32 字节那一档，直接从对应链表里 pop 一个空闲块，就得到了空闲空间；要归还，就往对应链表里插入。找到大小对应的那个桶，再做一次链表操作，所有操作都是 $O(1)$，这是一个非常非常高效的 fast path。

只有走到 slow path 时才不一样：当某一档的所有内存都被分配完了，你才需要去问系统要一个新的 1 兆 slab——这时候上一把大锁——然后再返回来切分使用。当然实际会比这复杂一些，比如 free 之后你还要把空闲链表维护好。但在这个 idea 底下，你就能得到一个非常高效的 malloc 和 free。这种 segregated free list 的做法，1964 年就提出来了。

> **提示**：我非常推荐你们去看那篇 malloc 的 survey paper。它很长，非常长，可以在 AI 的帮助下读。上课的时候我们会讲"malloc 怎么做、free 怎么做"，讲 A 算法、B 算法、C 算法，看教科书会误以为世界就是这样的。OSTEP 其实算是写得比较好的一本，但如果你看别的教科书，就更容易误认为世界就是这个样子。世界不是这样，世界比你们想象的内卷得多。

任何一个问题，只要它有实际的价值、只要它是一个重要的问题，就会被卷到极致——对 computer systems 来说，malloc 变快了就意味着你的程序变快了；你省下一些内存，就意味着可用的内存空间变多了。而这些最终都意味着是**钱**。

systems 最有意思的地方就在这里。我今天讲并发编程，其实和钱有很大的关系。当你能把一个系统的性能提升 10%，10% 已经是一个不小的提升了：如果你有 100 万台服务器、100 万个 CPU，这 10% 就是一个非常可观的绝对数，你可能要裁掉很多人才能省下这笔机器的钱。

> **注意**：不要低估 performance 这个系统问题的难度。现在在 AI 的时代，你学起来会很快——可以把这篇文章丢给豆包，让它帮你一点一点地梳理出来。

### 线程不是免费的

性能非常重要，这就意味着两件事。

第一，我们依然需要并发、需要并行，想要利用好多处理器的性能。第二，你回过头来要想清楚：你的每一个线程都是有代价的。虽然我们说"我们做一个线程库吧，`thread.h`，include 进来就可以 spawn 一个线程，就能用好 CPU 里的资源"——这是对的——但你的每一个线程都会占用相当多你看不到的资源。

#### 看不见的开销：栈、`/proc/PID` 与内核里的全局结构

线程是需要内存的，线程的栈是需要内存的，这一点毫无疑问：它就在地址空间里，你用 `pmap` 去看一个多线程的程序，能看到一块一块的线程栈。

不仅如此。你们做进程树的时候，有没有发现 `/proc/PID` 下有一些目录你是可以 `cd` 进去的，但在里面却看不到？如果你没看系统的 pstree，你会看到一些更多的数字。这当然也是文件系统实现里的一个 trick：你问操作系统"请告诉我这个目录里有哪些文件"，它返回的就是那份文件列表；但当你 `cd` 到比如说一个不存在的 PID 的时候，它可能会成功，说"你已经进来了"——操作系统可以不保证这两者一致。有些线程就被藏在这后面。

不管里面是什么样子，每一个进程其实也是一个线程。你在那里看到的每一条信息，都是操作系统给它维护的某一份数据：比如 command line，那个字符串我能够打印出来，是通过 `read` 系统调用得到的，而这个数值是操作系统帮我写进去的；再比如 environment，也在操作系统里。各种各样的信息，每一条都需要内存。

> **结论**：`/proc/PID` 下的所有文件，都是操作系统内核为这个线程或者进程维护的数据结构的一次反射。

此外，操作系统里面还有很多全局的数据结构。你的系统里如果有 1 万个进程、1 万个线程，甚至 100 万个线程，那每一个线程都有一个 PID、都有一个线程号；为了维护这些数据结构，操作系统也需要付出代价。

#### 一个问题：Linux 下的一个线程到底占多少资源？

顺着上一节，你下一句话就可以问：Linux 里面的一个线程到底要占用多少资源？

比如我就启动一个最简单最小的线程，它默认有 8 兆的栈。但这个栈是按需分配的，所以你实际上只使用了栈顶上的一小部分；如果每创建一个线程就立马把 8 兆全部分配给你，内存很快就爆炸了。

我上了这么多年课，甚至都没有在课上提出过这个问题，也没有同学跟我反映过我们其实可以问这个问题：Linux 底下的一个线程到底要占用多少资源？

回答它有很多办法。可以让 AI 去阅读 Linux 源代码，然后告诉我们；也可以直接做一个实验：如果我想知道创建一个线程到底会在系统里面引入多大的开销，那么我只要一个最简单的程序就行了——这个程序几乎不占用任何额外的内存，那个函数调用完以后它就几乎不留东西了。然后我创建若干个、$n$ 个线程，$n$ 从命令行里面读取。

有了这个程序，我就让 AI 帮我写了一个脚本，我根本就没有看，看都没看；我给它一些 prompt，让它小心地 cross-check、让它不要出错，让它帮我估算每一个线程一共用了多少资源。它做的事情很简单：

- 在这个进程启动之前，先看一下操作系统里面各种资源的状态；
- 然后启动 1 万个线程（100 万个可能有点多）；
- 再看一遍系统的可用资源发生了什么样的变化；
- 变化量除以线程数量，就是每一个线程的资源使用量。

> **注意**：1 万个内核线程已经不是小数目了，别一上来就试 100 万个。

我创建 1000 个线程的时候，它算出来每一个线程大约要 16.9 KB 的资源。这个资源包括了操作系统内核里面各种数据结构增长所需要的开销。你创建 1 个的时候，你看不到那一点增长；但如果你创建足够多，就一定程度上能够看到这些数据结构的增长。之后你还可以再跟 agent 去求证：系统里还有哪些资源、这些资源发生了怎么样的变化，等等。

以前我们不这样做的原因是，我们自己有一个本能："做这件事情很麻烦。"觉得麻烦之后，又会觉得收益可能没那么大——因为大家都知道了线程一定会有代价，把它搞明白你要付出很大的代价，而这个代价和收益相比可能不那么值得。但在今天，所有你想搞清楚的东西，它的收益都是值得的，所以你可以去做这件事。这是我在操作系统课上最想告诉大家的一件事。

> **结论**：创建一个最简单的线程，都会给系统带来十几 KB 级别的内存开销。线程是会占用操作系统里面资源的。

#### 切换的代价：每次都要进内核走一圈

除了创建的开销，每一次线程切换也会引起额外的、进入操作系统的开销。

比如我现在有两个线程，但只有一个 CPU。这个线程在执行指令，如果它要切换到另外一个线程去执行，就会发生一次中断；或者我执行 `read`，`read` 以后我发现系统里面没有数据，这时才会切换到另外一个线程。这些切换都要去操作系统里面走一圈。

走这一圈会涉及保存寄存器、恢复寄存器，也就是线程的状态。因为我们的 CPU 只有一组寄存器，你必须先把当前线程的寄存器保存下来，再把另一个线程的寄存器放到当前的 CPU 上，另一个线程才能继续执行。而这些都是需要指令的，都是需要时间开销的。

> **结论**：线程不是免费的，线程是有代价的。我们一开始讲原理的时候会弱化这一点，会告诉大家"至少你以前多个 CPU 用不起来，现在你能用起来了"；但它确实有开销。

### 我们真正想要的：计算图想怎么写就怎么写

我们真正想要的东西是：计算图想怎么写就怎么写，写完以后几乎没有任何额外的开销；无论计算图的每一个节点上面做多少事情，系统都能帮我们很好地调度它们。

上节课我讲过，如果要做一个并行的 RCS，我需要把计算图切成 1、2、3 若干块，每一个节点里面都有足够多的计算，性能才会好。再比如我要画一个 Mandelbrot set，我按 $X$ 轴把它分成若干个区域，变成线程 1、线程 2、线程 3、线程 4。虽然这是 embarrassingly parallel 的，但计算图并不只有那四条并行的边：

```text
   main（初始化）
        |
        |  happens-before
        v
   +----+----+----+----+
   | T1  | T2  | T3  | T4 |      按 X 分区并行计算 Mandelbrot
   +----+----+----+----+
        |
        |  join / happens-before
        v
   把结果写入图像文件
```

读图：并行的部分只是计算图中间那一层，两头各有一个必须等待的节点。这个例子里并行度是 4，所以开 4 个线程非常划算。

但如果在这个例子里你要创建 100 万个线程，线程的开销就会显得比较大，使得你必须人工去做一个合适的切分——比如算一算到底该开多少个线程。

理论上说，任何一个并行任务，你用人的智慧去想、去写一段代码把它切分好，都是可以做到的。但人对所有的事情都是不满意的，我们总要把这件事情做得更好。

而这里的本质是：计算图的一个节点就是一次计算，而我们在编程语言里面对计算的抽象就是函数——我要去算一个 Mandelbrot 的值，那我就调一个 `Mandelbrot(x, y)`。计算节点的开销却远远大于一个函数调用的开销，这件事就有点疯狂了：你们在写线程库的时候从来没有想过"创建线程是有开销的，我接受了"，但就是有些人他不接受，他偏偏要问——我有没有可能创建一个线程，它的开销和函数调用一样小？

当然不可能和函数调用完全一样小，因为在机器上，函数调用是**指令集**支持的一条 `call` 指令。但谁说未来不能在 CPU 上做 100 万个上下文、在 CPU 上用一条指令去创建一个线程呢？还真的有人做。不过我今天不会讲得那么远，我今天讲两个非常常用、在真实世界里写并发程序时真的会用到的方向。

| 路线 | 做法 | 代表 |
| :--- | :--- | :--- |
| 把线程做轻 | 保留多线程编程模型，把 spawn/join 的代价压到接近函数调用 | 协程 coroutine、goroutine |
| 改变执行模型 | 让语言本身能描述计算图，在程序里直接写并行与依赖 | promise、future、async/await |

第一条路是：把线程做得非常非常轻量，让 spawn 和 join 接近于函数调用的代价——于是我们有了协程（coroutine）和 goroutine。你写代码的时候还是像写多线程程序一样：我去 spawn 一个函数（当然是一套别的 API），函数放出去它就开始执行了，然后我可以 join 这些函数，多线程编程的模型完全没有变。唯一的区别是同步机制：这里不能用互斥锁那些东西，要用别的同步机制，我今天会讲。但你在操作系统课上学到的所有和多线程编程相关的理解，全都是作数的。

第二条路是：改变程序的执行模型，让我们能在程序里面用代码直接描述这个计算图。我们现在的编程语言里没有计算图的概念，因为语言在设计的时候就没有这种东西——C 语言设计的时候沿袭的是更早的 B、Fortran、Pascal，它是为了描述一个顺序的程序执行而设计的，那个时候的 CPU 是顺序的，它本真不带写计算图的功能。那我们可以改变编程语言、改变程序的执行模型，于是就有了 promise、future、async/await。你们经常会在 AI 写出来的代码里看到它定义了一个什么 `async` 的函数，然后你可能不知道它是什么；今天我就会用操作系统课前几次的知识，很清楚地告诉你它到底做了一件什么事。在这个编程模型下，用法会稍微有点不一样，但和线程其实还挺像的：相当于把一个 job、一个带了代码的函数丢到队列里，然后我可以等待它们完成。

### 没有 pthread，也能实现 spawn 和 join

现在进入第一个比较疯狂的事情：我们能不能让线程变得非常轻量化？

> **问题**：在操作系统没有任何线程库的时候——没有 `pthread_create`，没有 `mutex_lock`，这些函数全都没有——你有没有可能依然实现 spawn 和 join？

你会发现有些编程语言里面还真的可以做这件事。比如 Python，它就支持在一个线程里，在没有创建多个线程的同时，维护好多条用户程序的执行流。这个语法特性就叫 generator。

#### Python 的 generator：一个线程里的许多个栈

先看它在做什么（这里用最简单的形式把结构写出来）：

```python
def TWorker(name):
    i = 0
    while True:                  # 无穷无尽的死循环：它真的是一个"线程"
        i = i + 1
        yield name, i            # 交还控制权，同时把执行状态留在这里

threads = [TWorker(k) for k in range(1000000)]   # 创建 100 万个"线程"，此时它们还没运行
for _ in range(10000000):                        # 做 1000 万次调度
    current = random.choice(threads)             # 随机挑一个线程对象
    print(current.send(None))                    # 让它跑
```

这段代码里有两件事要看清楚。

第一，`[TWorker(k) for k in range(1000000)]` 只是把 100 万个 generator 对象创建出来，它们还没有运行。

第二，`current.send(None)` 相当于一次"函数调用"：控制流进入那个 generator，从上次 `yield` 的地方继续往下执行，直到再一次遇到 `yield`，又把控制权交还给调用者。

`TWorker` 真的是一个线程，因为它是一个死循环：`i = 0`，然后 `i = i + 1`，无穷无尽。如果这是一个顺序程序，`TWorker` 一旦开始调用就永远不会出来了，一次只能有一个 `TWorker` 在执行。但这里有一个神奇的 Python 关键字 `yield`：它每次都会报出"我是哪个线程、我的 `i` 等于几"，并且把当前函数的执行状态暂存下来，然后直接返回到调用者。下一次我再 `send` 同一个 `TWorker`，它就会从这个状态继续往下执行。

运行起来很有意思：我是先创建完 100 万个，然后才开始打印的；在我按下回车的时候，只等了一小会儿——非常短的一会儿——所有的线程就都开始运行了，而且你会看到它确实是并发的：每一个 `TWorker` 都有自己的线程号、自己的名字，有的线程名字回显出来是 `i = 1`，有的已经到 `i = 2`，有的已经到 `i = 3`。看起来就好像是线程一样。唯一的区别是：线程的切换不是由操作系统强迫的，而是我主动 `yield` 的。

> **提示**：顺带说一句，用 `sleep.c` 那套代码去创建 1 万个线程的时候反而失败了，我猜是内存不够，理论上应该不会失败——你们可以跟 AI 再去确认一下。

要理解这件事，请回想 Simple C 的模型。我们说 C 语言里每一个函数有一个栈帧：比如 `hanoi(3)` 里面会调 `hanoi(2)`，一层一层压下去；每个栈帧里面都有一个 P-program counter（PC），另外还有一份 globals。Simple C 的每一次执行，就是从 top-most frame 的 PC 上取一条语句来执行。

```text
   单线程的 Simple C                多线程的 Simple C = 有好多个栈
   +------------------+           +-------+  +-------+  +-------+
   |  frame:  PC      |           |  PC   |  |  PC   |  |  PC   |
   |  frame:  PC      |           |  PC   |  |  PC   |  |  PC   |
   |  frame:  PC      |           |  PC   |  |  PC   |  |  PC   |
   +------------------+           +-------+  +-------+  +-------+
        globals                       globals（外加数据竞争的困扰）
```

读图：多线程在 Simple C 这个层面上的全部含义，就是"同时存在好几条栈"，每条栈都有自己的 PC。

Python 的 generator 机制和这个模型很像：它就是一个独立的栈。程序在一条栈上执行的时候，我可以退出来；而退出来的时候，这个栈不销毁。如果你是一个单线程的程序、没有这种东西，一个栈帧要么往上 push，要么 pop；但如果有多个栈，我就多了一个像 `yield` 这样的动作——可以在正在运行的栈之间切换。`yield` 的语义是："我现在正运行在这个栈上，这个栈我留着，我返回到调用我的人那里去"，也就是回到 `main` 继续执行。

这个东西你可以叫它一个线程，也可以叫它一个协程：如果它是操作系统实现的，我们一般叫它线程；如果是我自己模拟出来的，我可以叫它一个协程；而在 Python 里面，它是一个 generator。（Python 里面也有协程，语义上稍微有点不一样，等讲到异步编程的时候我们再回来。）注意在这个程序里面只有一个线程——我们再没有创建过第二个线程。

#### 把栈换掉就行：汇编与 setjmp/longjmp

同样的机制，我们可以在汇编里面实现，在 Python 里面实现，甚至还可以直接在 C 和 C++ 里面实现。这曾经是一道操作系统课的作业，后来我们觉得太难了，就把它从实验集里拿掉了：那道作业是希望大家在 C 里面用 `setjmp` 和 `longjmp` 去实现栈的切换。

原理简单得有点过分：C 语言的程序编译成汇编以后，每一次函数调用就是一条 `call`，每次函数返回就是一条 `return`，它根本不管你这条栈是在哪儿的。所以你完全可以用 `malloc` 去分配一段栈的空间，然后用一段汇编——x86-64 和 ARM64 都可以工作——用一条 `move` 指令把栈顶指针 `rsp` 挪到另外一个地方。没有人能阻止你。

```text
   切换前                              切换后
   rsp ---> [ 栈 A 的栈顶 ]            rsp ---> [ 栈 B 的栈顶 ]
            ...                                  ...
            栈 A 原封不动留在那里                栈 A 原封不动留在那里，等下次切回
```

读图：所谓"切换到另一个线程"，在这个层面就是一条移动指令把 `rsp` 指向另一段栈，然后程序继续执行，就这么简单。用 `setjmp` 保存寄存器现场，用 `longjmp` 跳回去，再配上一次栈切换，我就可以实现和刚才那个 Python 版本完全一样的功能。

在 C 里面我们会写一个 `coroutine_create`，它创建一个协程；创建好以后调用这个协程的 entry。这个 entry 和刚才那段代码是完全一样的：可以 `i++`，甚至可以给协程分配一个 buffer；本地计算做完以后，就做一个 `yield`，而 `yield` 调用 `longjmp` 跳转到另外一个协程去工作。

> **提示**：这个地方比较复杂，如果你没有跟上，不要紧，有兴趣可以回去看；但我考试肯定是不考这么深的内容的。你要有的感觉是：我们确实可以在用户空间里面实现线程。

#### 无栈实现：能写闭包就够了

C++20 专门引入了一个关键字 `co_yield`，用来实现完全一样的功能。理论上说，任何一个现代的编程语言，只要它能实现闭包——也就是说它可以捕获作用域里面的变量、生成一个函数对象——就都有能力去实现这样的堆栈切换。

原因还是那个：本质上这就是一个函数。假设一个函数要做 `x = 1, y = 2`，`x` 和 `y` 都是本地的。任何能做闭包的编程语言，都可以在这个函数执行到这个时间点的时候，创建一份这个函数状态的快照——因为闭包本来就要捕获当前作用域里面的变量，所以它天生就可以把 `x` 和 `y` 放到内存里。

一旦 `x`、`y` 放到内存里，我只要把这个函数的 PC 记下来，这个函数的运行状态就封存了。封存以后，我就可以做一次栈切换，或者甚至不做栈切换，只做一个跳转，跳到别的地方去执行。C++ 的 coroutine 和 Python 的 generator 就是这样"无栈"的实现。

> **易错点**：无栈协程并不是没有状态，而是不持有独立的栈——状态被搬到了堆上的对象里。而我刚才那个 C 版本是模拟出来的栈：我真的为每一个自己实现的线程分配了一段栈，所以它是有栈的协程。

到这一步我们成功了：我们在用户空间里实现了 100 万个线程，而且它们是可以并发执行的。但也要记住它的代价——这时线程的切换不是被动的、不是由中断驱动的，而是我主动的。如果我的程序在 `while (1)` 里死循环、不做 yield，那就再也不会切换，其他所有的"线程"都会饿死。

### 用户态线程的两个麻烦

虽然我好像模拟出了 T1、T2、T3，每个人可能都有一段栈，但操作系统本质上只有一个线程。所以只有 T1 在 `yield` 的时候，我才会切换到 T2。这一个事实带来两个还没解决的问题。

#### 麻烦一：一个人 `read` 阻塞，所有人都跟着等

第一个麻烦是 I/O。假设 T1 现在不是 `yield`，而是执行 `read`。`read` 是一个系统调用，它会执行一条 `syscall`（ARM 上是 `ecall`）指令，进入操作系统内核；内核发现你要读的那个文件、那个管道里面还没有数据，你这个线程就要等待——`read` 是要等待的，这是你们非常熟悉的行为。

好，要等待。那对不起，我在操作系统里面等待的时候，T1 就没有办法执行 `yield` 了。也就是说，哪怕 T2 是可以继续执行计算的，T2 也得跟着一起等。

> **易错点**：并发的价值恰恰体现在这里。如果我创建的是两个真正的操作系统线程，T1 进入 `read` 等待的同时，T2 的计算依然可以继续。但当这个"线程"是我在用户态模拟出来的、整个进程只有一个真线程时，一旦 `read` 进入内核睡眠，别人就都算不了了。这不是我们想要的。

#### 麻烦二：互斥锁一用就死锁

第二个麻烦是：你依然会有同步和互斥的需求，但你不能用锁，不能用条件变量。

为什么呢？假设你想实现一个互斥，于是你在"线程"里 `lock`。还记得那张桌子、那把钥匙的比喻吗？线程里有一张桌子，桌上有一把钥匙。注意，桌子是在**这个线程**里——而你现在只有一个线程，虽然你模拟出了好几个栈。`lock` 把这把钥匙拿走了。然后 `lock` 之后会 `yield`，控制流到另外一个"线程"去执行。那个线程也执行 `lock`，它也试图去拿这把钥匙，但钥匙刚才已经被 T1 这个协程拿走了。于是它说："`lock` 我得不到。"得不到的时候，它就会进入操作系统去等待——`mutex` 拿不到就是进入操作系统等待。而进入操作系统等待的后果是：整个进程只有一个真线程，T1、T2、T3 全是模拟出来的，于是这个真线程正在等一把它自己已经拿在手里的锁，程序永远停在那里。

> **结论**：互斥锁是操作系统为线程设计的同步原语；在操作系统眼里，用户态模拟出来的这几个协程全都属于同一个线程。所以在协程里面，你不能用互斥锁来实现同步。

事情也不是完全没办法：你只要隔一段时间就加一个 `yield`，就能真正模拟出线程轮转的行为——只要 `yield` 得足够频繁，你就能构造出一个"它们都在均匀并发、雨露均沾地执行"的假象。但互斥锁依然不能用。

> **提示**：其实编程语言、操作系统和人类世界的需求是同步演化的。人类的野心永远不会停止——就像现在有了 AI，人类的野心也不会停止一样。

#### 出路：`O_NONBLOCK` 的 `read` 与 epoll

为了支持我们在用户空间直接实现这样的线程，第一个麻烦是可以绕开的：我现在只有一个操作系统线程，但我依然想要 T1 计算完就 `yield` 到 T2，然后 T2 要去 `read`——如果这个 `read` 想阻塞的话，我们可以把它变成不阻塞的。办法是用 `O_NONBLOCK` 来打开文件。

手册是权威。你们可能看过 `open` 的手册，然后说："哦，操作系统考试会考，`open` 会返回一个文件描述符。"然后你们就认为，知道 `open` 会返回一个文件描述符、知道文件描述符是什么，期中考试就能得满分，就觉得自己理解了。但实际上，操作系统为了支持这些东西演化了很长时间，手册里写着的东西远不止那一条。

一旦你用 nonblock 的方式打开了一个文件，之后所有的 `read` 系统调用的行为就变了。比如我要 `read` 一个管道，而这个管道是用 nonblock 方式打开的：

| 打开方式 | 管道里没有数据时的 `read` |
| :--- | :--- |
| 默认（阻塞、同步） | 一直等到有数据来为止 |
| `O_NONBLOCK` | 立即返回，返回值为 `-EAGAIN` |

如果你读到了数据，它照样返回你读到了多少个字节。而如果返回值是 `EAGAIN`，你就可以 `yield` 了；`yield` 出去以后，你应该再跳转回来，重新 `read` 一次。这时因为你做的是一个 non-blocking 的 `read`，你可以切到另一个可以计算的协程上去。

```text
   T1 计算 ---> read 管道 ---> 返回 -EAGAIN ---> yield 出去
                                                   |
                                                   v
                                        T2 继续计算（不再被 T1 拖住）
                                                   |
                                                   v
                              再次轮到 T1 ---> 重新 read 一次
```

读图：把"阻塞等待"换成"立刻返回 `EAGAIN` 再重试"，模拟出来的多个执行流就都能往前推进；而这张图里自始至终只有一个操作系统线程。

这种 non-blocking I/O 和你模拟出来的线程组合在一起，你就几乎可以得到——至少在一个线程里面几乎得到——任意多个线程的效果和行为。

> **提示**：这个水面底下有一座巨大的冰山。我今天不花时间去让 AI 帮我读了，但我也非常推荐大家去读一下 `epoll` 的手册。这个 API 支持的功能是：让你的手上拿一大把文件描述符……

## 把线程做轻，把计算图写进语言
> 对应块：BLK38 | 覆盖分集：P19下 | 块标题（分集名）：《协程、Goroutine、异步编程（下）》

只要任何一个文件描述符上有数据了，它就会返回。

这是后面所有推理的起点。它意味着我手上多了一个能同时和一整批并发活动打交道的东西：可以同时监听多个文件描述符，谁来数据，谁就放我继续往下走。这个机制本来是用来做 I/O 等待的，但换个角度看，它其实就是一种同步。

### 让文件描述符变成同步原语

同步就好像信号量：我可以一口气 P 好几个信号量，任何一个来了，我都可以继续。文件描述符给的是同一种能力——同时监听一大批 fd，谁先准备好，谁就把我唤醒。而它比信号量还多一层好处：文件描述符不是「每个线程一个」的东西，它是操作系统里一个实实在在的对象。不管是我在一个线程里模拟出来的那一堆协程，还是别的进程里的某个线程，都可以访问同一个 fd。

> **结论**：`mutex_lock` 是绑在线程上的，文件描述符不是。正因为 fd 是一个能被多方共同引用的对象，它才有资格充当协程之间、甚至跨进程的同步手段。

多路复用机制会在操作系统里维护一份数据结构，用一份结构同时盯着上百万个文件描述符也没有问题。操作系统还提供了 `eventfd`、`timerfd` 这类更专门的机制，它们无一例外都建立在 fd 之上。于是可以这样用：一个线程准备好之后往自己的 `eventfd` 上写一下——这相当于对这个文件描述符做一次 V 操作；另一边的主线程用 `epoll` 等着这个 fd，就收到了这个信号。

站在操作系统设计者的视角看，你在博客里读到的 asynchronous I/O、non-blocking I/O 一下子就会变得自然：它们不是凭空发明的时髦 API，而是沿着「我要在用户态做线程」这条线走下去必然要有的东西。这条线在讲到文件系统的时候还会再回来一次——在今天这讲里，它只是被借来当工具用的。

### 不想学新 API：让编译器替我改写

刚才一口气冒出来这么多新名词，第一反应大概是：期末考试会不会考这个异步 I/O？不会考。所有的编程机制，出发点都是让人用得更好；如果一套 API 反而给你增加了心智负担，那我就该改语言、改操作系统、改系统的设计，把它变成不难用的样子。

假设语言由我自己设计，我会让你写的代码和原来一模一样：还是 `spawn(Tworker)`，`Tworker` 里该怎么写就怎么写，该 `sleep` 就 `sleep`，该 `read` 就 `read`，而且这个 `read` 就是阻塞语义的 `read`。区别在于编译器在我的控制之下：

- 遇到 `sleep`，编译器把它改写成「把我放进一个队列，并且标记我：至少一秒钟之内不要再调度我」，然后 `yield`，让别人去跑；
- 遇到 `read`，编译器把它改写成一段循环——循环里做的是非阻塞读，一旦返回 `EAGAIN` 就 `yield`。

> **结论**：我写的是彻彻底底的多线程代码，但它在运行时变成了一个高性能的轻量级线程。同步的写法，异步的执行。恭喜你，你发明了 goroutine。

### Goroutine 怎么跑起来：worker 线程与可运行队列

> **易错点**：前面几处「线程」是在两个意思上用的。一种是我用 `spawn` 从操作系统那里要来的真线程；另一种是我自己在用户态模拟出来的轻量级线程。上下文里它们都被叫做「线程」，读的时候要小心区分。

现在可以干一件更疯狂的事。借助操作系统的 `spawn`，我们仍然可以为一个共享内存的进程创建多个线程——这些是真正的 worker。同时在它们之上，再创建很多个用上面那种「编译器帮你改写」的写法写出来的执行体，这就是 goroutine。

每一个 worker 线程上跑的都是一个死循环，循环里只做一件事：不断从队列里取出当前可以运行的 goroutine 来执行。具体来说：

- 一个 goroutine 执行到「把自己标记为睡眠」这一步时，它会被从可运行队列里摘掉，一秒之后再放回去；
- 一个 goroutine 执行到异步的 `read` 而暂时没有数据时，同样被移出队列，只是会额外记下它在等哪个 fd；调度程序用 `epoll` 盯着这些 fd，哪个 fd 上有数据了，就把对应的 goroutine 重新放回队列。

```text
   goroutine 在某个 worker 线程上执行
              │
              ├── 遇到 sleep ────────────► 移出可运行队列
              │                                  │
              ├── 遇到 async read ───────► 移出可运行队列
              │      (记下它等的 fd)             │
              │                                  │
              │        ┌─────────────────────────┘
              │        │
              │   条件满足（sleep 到期 / epoll 发现 fd 有数据）
              │        │
              │        ▼
              └──► 重新入队 ──► 等一个空闲的 worker 取走
```

读图说明：worker 只有少数几个，goroutine 可以成千上万；谁被挂起就从队列里摘出去，谁的条件满足就重新入队，任何一个空闲的 worker 都能接着把它跑起来。

这样得到的轻量级线程，和我前面用 C/C++ 模拟出来的协程一样轻，同时又真的能像线程一样在多个 CPU 上并行。这是模拟协程做不到的：那个版本只有一个进程、一个线程，靠 `yield` 在多个协程之间切换，天然用不上多核。而 goroutine 完全可以吃满 CPU 的并行资源，用起来和线程完全一样。

前提是用标准库。如果你偏偏自己用汇编写一个阻塞的 `read`，或者在库里硬塞一个阻塞实现，那个在它上面跑的 goroutine 就真的会把底下的线程占住。用标准库里那一套，同步写法会被自动改写成异步的写法，拿不到资源的时候会被移出调度队列。

于是，一个进程里就出现了一个「小操作系统」：内存是共享的，成千上万个执行体被送到少数几个真正的 worker 线程上去运行。

### 用通信来共享内存，而不是用共享内存来通信

Effective Go 里有这样一句话：**Do not communicate by sharing memory; instead, share memory by communication.**

回想前面讲的那些并发控制：互斥锁、信号量确实实现了同步，但数据的交换依然是通过共享内存完成的。生产者消费者里我要有一个 buffer，还得手工维护它：生产者产生一个东西、P 一下，然后再上一把互斥锁，把这个数据放进 buffer。同步和通信是分开的两件事，这其实带来很大的问题。

而 Unix 时代早就有一个非常好的并发编程机制，甚至在多处理器时代也能并行，它描述的就是一个计算图——管道。

```text
   cat *.txt          cat *.cpp           wc
   ┌────────┐         ┌────────┐       ┌────────┐
   │ 逐行产出 │──管道──►│ 逐行产出 │──管道─►│ 逐行读入 │
   └────────┘         └────────┘       └────────┘
        │                  │                │
        └─ 一行数据出来了，下游节点才能工作 ─┘
```

读图说明：`cat *.txt | cat *.cpp | wc` 这一串管道本质上是一个并发计算图，上游的数据出来一行，下游节点才动一下；生产者和消费者之间的同步由管道自带，不需要再手工加锁。

Go 把这个抽象搬了进来：可以在任意 goroutine 之间建立 channel，channel 就是管道。可以建很多很多个管道，就像 Unix 里进程可以随意创建管道一样；命名管道还能让两个进程往里写、一个进程从里面读，用管道来管理进程之间的同步。这样既同步、又传数据，不是很好吗？

> **结论**：Golang 是真正继承了 Unix philosophy 的语言——在共享内存的时代，把 Unix 里那些好东西重新做了一遍。

这条路走得很自然，因为它的发明人是 Rob Pike、Ken Thompson 和 Russ Cox。Thompson 是 Unix 的核心设计者之一；Rob Pike 也是 Bell Labs 的核心成员，写过 Unix 编程方面的东西。

### Mandelbrot：把计算节点随便开出来

有一份 Mandelbrot set 的实现，是 AI 帮我写的。里面的 `worker` 和我前面那个 C 版本完全一样：它有一个 `low`、一个 `high`，负责算图像里被切出来的一条竖带——计算图的切分方式和前面讲的一致，把图像切成若干竖条，每条竖条各自开算。

Go 里有个关键字 `go`，它干的就是 `spawn` 的事。因为创建计算图节点非常轻量、你根本不用考虑开销，想创建新节点就直接 `go` 一份：

```text
   for i := 0; i < nthreads; i++ { go worker(...) }
   go monitor(...)
```

就这么简单。goroutine 之间通过管道通信，注意主线程本身也是一个 goroutine：它从管道里收到的消息，要么是时间的 tick，要么是 done；等到最后一个线程也结束、收到 done，就把 `mandelbrot.png` 写出来。

演示时开 4 个 goroutine，可以看到它在 CPU 利用率上、在线程利用率上确实是并行的。开到 4000 个的时候出了一点小问题——是同步出了问题，AI 给我写的这份代码确实有 bug。

> **提示**：出问题的不是 goroutine 的数量。计算图的节点创建起来就是可以这么随便开，这一点依然成立；坏在同步没写对上。

> **结论**：这就是「把线程做轻」这条路的答案——线程的创建代价、管理代价、切换代价都可以变得非常低，全部在用户态实现，甚至还可以借助操作系统的线程机制来跑。

### 另一条世界线：十天写出的 JavaScript

1995 年，Brendan 加入 Netscape，被委以重任：设计一门嵌入在网页里的脚本语言。他花了 10 天，把 C、Java、Scheme、Self 的各种语言特性融合进去。主要目的是设计一门像 Java 的语言，因为那时候 Java 已经有点起来了，他要靠这个吸引人。然后，人类命运的齿轮就转起来了。

有意思的是，他的主要兴趣是函数式编程，对这些事情其实不上心。他做了一些很糟糕的设计；但也正因为他的兴趣在函数式编程，他把「函数是一等公民」放进了 JavaScript 里。

于是有了那张很有名的梗图：左边《JavaScript: The Guide》很厚，右边《JavaScript: The Good Parts》很薄——意思是这门语言的好部分很少。这门语言里有无数多的坑，比如 `this` 是动态绑定的，语义和 C++、Python、Java 完全不一样；用过早期 React 的人会记得要一个个 `bind this`，还经常用错。

还有那个「三位一体」的调侃：圣父是神，圣子是神，圣灵是神，但他们彼此之间又都不是神。JavaScript 里打开 F12 的控制台就能复现同款行为，因为 ECMAScript 标准就是规定这么做的：`0` 可以等于空的 list，可以等于字符串 `'0'`，可以等于空白字符串，而这些值彼此之间又是不等的。它是弱类型的，动态写起来很好用，但你一不留神写了一个「看起来对」的东西，下一次它就不对了。这些糟糕的特性后来也都慢慢补起来了，但这条时间线上人类的命运确实发生了非常大的变化。

### HTTP 原来这么简单

有兴趣的话可以去看一下 HTTP 的演化。最早的 HTTP 协议就是一个非常简单的纯文本：客户端发一段文本给服务器，说请你给我一个 `/mypage.html`；服务器不管用什么办法把这个文本文件找出来，返回一段 HTML；客户端就收到了这个网页。没有 WebSocket 这些花哨的东西。

那个时候的网页就长那样，雅虎的首页就是那样；AI 还帮我复刻了一个 199X 年风格的网站，很有那个时代的味道，包括那种神奇的浮动小窗——前两年你还能在教务系统里见到。

HTTP 协议比想象中简单得多，甚至可以拿真正的网页去试探一下：给课程主页发一段文本的 HTTP 请求，它就真的返回一段文本，就是你平时看到的那个页面。返回里会写 `HTTP/1.1`，会告诉你服务器是 nginx，状态码是 200——200 代表 OK，后面还有一些其他信息。

在这样的网页框架下，诞生了很多有趣的网站，中国互联网的初代三巨头新浪、搜狐、网易都是那个时代的产物。那时候的前端还没有 CSS，最早甚至连 CSS 都没有，大家只能拿 `table` 把网页划分成很多个二维网格。本质上就是精细地控制每一个像素的位置：在这块二维平面上放一个 banner，在这里切出多少像素、放一张图片，在那里再放一张，中间放文字。今天一个 CSS 就能做出的圆角矩形包围，那时候必须切出非常精细的表格，再往那些地方塞图片。于是诞生了「切图工程师」：先用 PS 或者别的设计软件设计出页面，精准算出每一个部分的像素数值，最后把它变成网页。这就是那个时代的 Web。

### 1999 年的 XMLHttpRequest 与 jQuery

1999 年，一个跨时代的 API 诞生了，叫 `XMLHttpRequest`。JavaScript 是网页的语言，而它允许你在 JavaScript 代码里随时随地请求任何一个其他的网页。这打开了一扇全新的大门。

这项技术后来被称为 AJAX，Asynchronous JavaScript and XML。你没有看错，是 XML：今天网页上传输的数据都是 JSON，连大模型给你的 API 回来的也是 JSON，但那时候 Java 的后端应用里广泛使用 XML，所以从远程 HTTP 服务器上拉回来的就是 XML。正是这个机制帮我们实现了网页的后台刷新。

在 HTTP/1.0 的时代，一个网页就是一个完全静态的页面，HTML 写完就长那样；想访问另一个网页就得点一个超链接，然后从零开始重新加载一个页面。有了 `XMLHttpRequest` 这种异步 API，网页终于可以后台刷新。

再加上 JavaScript 能任意改变文档里的元素——就像刚才那个浮动小窗，改一改它的绝对位置 `x`、`y`，你就能看到一个东西一路走。那么理论上我也可以在网页上加上一个东西、删掉一个东西，任何改动都能实现。于是两件事凑齐了：第一，我可以向后端请求数据，可以不停地向后端查询整个应用程序后台的状态；第二，我可以改变图形界面。任何一个应用程序能做的事，网页也都能做了。

后来还出现过一些非常好的 API，比如 jQuery 的那个 `$`。`$` 本质上是一门 DOM 查询语言；现在浏览器里也内置了等价的东西，就是 `document.querySelector`。

- `$(document).ready(...)` 可以注册「文档加载结束以后执行这段代码」；
- `$(...)` 可以按 id、按元素类型选中某一个或某一类元素——你的界面本来是一棵树，DOM tree 就是这棵树，而你可以像写查询字符串一样，选中树里的任意一个或一批节点；
- 选中之后可以改样式、改文本，甚至直接往里塞新的 HTML，浏览器会帮你把它渲染好，界面就更新了。

理论上这样就能做任何事了。比如一个土味页面，想把它变成现代页面，只要在浏览器里调用一些 `querySelector`，往网页里注入样式、任意添加元素；复制，打开控制台，粘贴，回车——天就亮了：内容一点都没有变，但出现了圆角的输入框、有按下动画的按钮。这就是前端。

### 把 Office 搬进浏览器

有了 jQuery 这类技术，就可以真的在浏览器里做任何事。那个时期 Google 试图把 Excel、Word、PowerPoint 全都搬到云上、搬进浏览器里，而且这是一个很成功的尝试，到今天还有很多人在用，只是因为它在墙外面，我们用起来不太方便。

原因很清楚：HTML、jQuery、CSS 用起来的方便程度远远超过传统的图形界面。黏一段脚本进去，整个界面就改头换面了。用 Qt 写过大作业的人会有体会，那有多麻烦。这种「一行就能改变整个界面」的能力，一定会成功。

Google 甚至试图发布 ChromeOS：底层是 Linux，但暴露给你的就是一个浏览器，所有东西都由浏览器和 JavaScript、DOM 渲染出来。为此 Google 投入了大量资源去做高性能的浏览器。后来被微软摘了桃子——微软放弃了 IE，实现了基于 Chrome 内核的 Edge 浏览器，重新拿回了很多市场份额。这是八卦。

### JavaScript 为什么选了事件模型

网页的请求天生会消耗很多时间；JavaScript 又是一个被鼠标点击驱动、被框的移动驱动的东西，所有事件都是动态的。事件就意味着你不知道它什么时候会到达——鼠标不知道什么时候会点击，网页的请求不知道什么时候能结束。所以 JavaScript 天生就应该对并发有很好的支持。

那它选了什么？线程，还是前面说的那种协程？都不是。

想想 JavaScript 是一门什么样的语言：任何人都能快速入门，一个 HTML 里直接写一行代码就能工作，零门槛，连编译过程都没有，任何工具都不需要，任何一个操作系统开箱就能用。而写线程、写协程这件事——并发讲了这么多次课，你现在才刚刚有概念什么是 data race、什么是 atomicity violation；对于一个没有这些知识的人，怎么让他把并发用好？

> **结论**：需要一个非常简单的、描述计算图的模型——它既并发，又不并发。JavaScript 做了这个决定：基于事件的并发模型。

网页加载的时候创建一个事件，鼠标点击的时候创建一个事件，发起网络请求的时候创建一个事件，请求回来的时候又创建一个事件。而这个模型选择永远不要和任何人并行，而且永远不能在中间被切换出去——不像线程随时都会被打断切换，也不像协程可以 `yield` 到别的协程。一个事件一旦开始执行，就必须等到它返回。

> **易错点**：这就是为什么 JavaScript 里一个不小心写出的死循环，或者一个真的有性能问题的长计算，会让整个网页失去响应、点什么都点不动——一个事件开始执行，就一定要等它把所有代码都执行完，才能轮到下一个事件。

在事件里当然可以请求后端：`$.ajax` 会立即返回，剩下的部分继续执行；等请求真的回来了，浏览器再创建一个新的事件去调用你的回调函数。因为跑在浏览器里，这门语言才可以做这样的设计：禁止并行，而且没有任何阻塞式 I/O——你在操作系统课上学到的那些 `read` 系统调用，在 JavaScript 里统统是不存在的。

要请求一个网页，就给它一个 callback，比如在 success 的时候调用哪个函数。callback 本质上就是一个函数，这就要感谢 JavaScript 把函数作为一等公民的设计。浏览器实现自己在那儿等，其间可能还有别的事件插进来，比如某一个东西被 click 了；等到它发现网页已经返回了，再创建一个事件去调用那个函数，而这个函数同样运行到完成，不与任何东西并行。

> **结论**：每一个 JavaScript 事件都是原子的。你永远不用担心它会和别人并行执行，也就从根上避开了 data race 和 atomicity violation 这类问题。

这其实就是在描述一个计算图：不是「先做这件事，等它完成了再创建下一个节点」，而是事件完成之后动态地创建新节点。这张图有意思的地方还在于它有两条分支——success 一条、fail 一条，success 执行一个函数、fail 执行另一个，实际只会走其中一条。

```text
   网页加载 ──► 事件 ──► 事件 ──► …
                    ▲
   鼠标 click ───────┤
                    │
   $.ajax 发起 ──────┤  立即返回，代码继续往下跑
                    │
           ┌────────┴─────────┐
     请求返回 success     请求返回 fail
           │                  │
      调用 success 回调    调用 fail 回调
           └────────┬─────────┘
                    ▼
      新事件：run-to-complete，独占执行完
```

读图说明：事件由外界（加载、点击、网络返回）驱动着被创建出来，每个事件从开始到结束独占执行，绝不与他人并行；success 与 fail 是同一张动态计算图上互斥的两条分支。

把这几套模型摆在一起看，差别就很清楚了：

| 模型 | 是否并行 | 是否会被中途切换 | 共享内存与数据竞争 | 阻塞式 I/O |
| :--- | :--- | :--- | :--- | :--- |
| 操作系统线程 | 是 | 是，随时被打断 | 共享内存，有 data race | 有 |
| 用户态模拟的协程 | 否，单线程靠 `yield` 切换 | 是，自己 `yield` | 共享内存，有 data race | 有 |
| goroutine | 是，多个 worker 线程并行 | 是 | 共享内存，有 data race | 有，但标准库会把同步写法改写成异步 |
| JavaScript 事件 | 否，事件串行 | 否，run-to-complete | 事件原子，不会并行 | 不存在 |

### 回调地狱

这种「事件完成以后再创建一个新事件、调用我的函数」的回调机制，带来了一个非常著名的词：callback hell，回调地狱。

假设要做三件事：先登录，登录之后拉 friend list，第三步拉某个 friend 的 feeds，也就是你好友的动态。这三件事之间是有依赖关系的，计算图天生如此，所以写的时候只能先请求登录；登录会有成功和失败，失败了就处理，成功了再去做下一件事，而每一件都是一个函数。一个顺序的 A、B、C 流程，必须被拆成三个函数，而且写起来往往是一层套一层：在 ajax 的 success 里创建下一个函数，再调用下一个 API，再来一个函数。

结果是：每要做下一件事，就多出两级缩进。很快这段代码就没有办法维护了，你也不知道这些回调最后到底长什么样，调试的时候会花掉非常多的时间。一个非常经典的顺序逻辑、一张顺序的计算图，硬生生被拆成了几个部分——它不能用编程语言里的顺序结构来描述「先 A 再 B 再 C」。

> **提示**：能忍着这么难用的 Ajax API，用这么多年在 JavaScript 的世界里建起那么多东西，地球上的人类确实很厉害。

### Promise：在代码里画计算图

这个过程里诞生了很多库，今天的版本答案是 Promise API（严格来说还有 Promise 和 Future 之分，这里简化成 Promise）。它给了我们一种能力：直接在代码里画计算图。

举个例子，这是我 Online Judge 里的代码。写一句 `fetch`，给它任意一个 URL，它会返回一个 Promise 给我。注意 `fetch` 在执行的时候是立即返回的——JavaScript 里没有同步的 I/O 调用，我永远不能等一件很长的事情结束再执行下一个，所以它必须立即返回。它返回一个 Promise（更严格地说是一个 Future），告诉你：未来会有一件事情完成。

刚拿到的时候，这个 Promise 还是 pending；过一会儿再看，它已经 fulfilled，这时就可以去读它的 response。

再加上一些别的 API，计算图就出来了：

- `Promise.all` 可以一次收进去好几个 Promise，它本身就是一个现成的 join；
- Promise 还可以写 `.then` 和 `.catch`；
- `Promise.all(...).then(...)` 里 `.then` 这个节点，happen after 前面那几件事；而它们各自也有可能出错。

```text
   fetch A ──┐
             ├──► Promise.all ──► .then（后续节点）
   fetch B ──┘          │
                        └──► .catch（出错分支）
```

读图说明：`Promise.all` 把若干条并行分支汇到一个汇合点，`.then` 挂在汇合之后，`.catch` 兜住任意一条分支的失败。

写这些的时候，每一句都是立即返回的；计算图一旦被构建出来，里面的 HTTP 请求其实就已经开始工作了。理论上我只要等到最后一个 Promise（比如那个 `.then` 或 `.catch` 返回的）完成，就能确保整张计算图里的节点都完成了。

### async/await：把计算图写回顺序结构

但这还不够好用：就算我写了一个很长的 Promise，它还是立即返回的。我还是想在编程语言里有顺序结构、选择结构、循环结构——最符合程序员直觉的那种写法。于是就有了 `async` 和 `await`。

这又是一个编译器替我干活的地方，和 goroutine 是同一套道理：如果编译器在我的控制之下，我写的代码就能被改写成任何一种我想要的形式。

一个 `async` 函数，编译器会把它包装一下：它不再是普通的函数，而是会 `return` 一个 Promise，所以像 `fetchData` 这样的异步函数一般不再直接使用，而是被 `await`。而 `await` 是「什么东西都能 await」的：在网页里直接 `await 1`，它就等于 1；`await "hello"` 就返回 `"hello"`；`await Promise.all(...)` 可以，`await fetchData` 也可以。

在我自己的 Wiki 上试一下就很直观：先定义 `fetchData`，然后 `await Promise.all(...)`。`Promise.all` 本身也返回一个 Promise，所以直接看它是一个 pending；但我一 `await`，编译器就会把它变成链式的调用——也就是刚才回调地狱里那种一层一层的函数调用。

具体来说，如果我写：

```js
a = await f;
b = await g;
```

编译器会把它翻译成一个一个执行的 Promise：先是 `a`，`f` 执行完了以后 `Promise.resolve(f)`，然后 `.then`，把后面所有的东西都塞进这个 `.then` 里面；接着对 `b` 再递归地做同一件事——`resolve(g)`、再 `.then`、把后面的部分继续填进去。它生成的代码会非常难看，一层一层缩进就像回调地狱一样，但这件事是编译器做的，而我写的时候保持住了计算图的顺序逻辑。

所以当我把 `fetchData` 写成 `await Promise.all(...)` 的时候，其实是为了这两个动态的计算图节点在这里做一次汇合，我会等这两个节点都完成——这次它就真的花了一点时间，不再是立即返回；然后看到两个 `fetchData` 都返回了 `not a valid token`。

这段检查是真实存在的：我的网页代码会记住你在网页左上角粘贴的那串 Online Judge token，然后用一句 `await` 去请求后端的 `/api/submission`，检查这个 token 是否合法。演示里两次都返回 `not a valid token`，正说明这条路径真的跑通了。这就是 `async/await` 语法糖。

### JavaScript 长出了什么

JavaScript 就是这么一门十天内设计出来的语言。因为它确实很糟糕，很多语法特性都成问题，一度出现过各种第三方库军阀混战的局面。但也因为它支持函数作为一等公民，编程模型非常灵活，想在上面做什么都可以。甚至新标准的 JavaScript 是用 JavaScript 自己写的一个 transpiler 实现的：把带 `async/await` 的新版本 JavaScript 编译成老版本的 JavaScript，这样就能在所有浏览器里兼容运行。

在它之上生长出了一个完整的应用生态：从早期的 Angular、Bootstrap，到现在的 Express、Next、Nest。

后来大家发现网页好用，就想：凭什么不能用网页、不能用 JavaScript 来构建桌面应用？于是有了 Electron——一个把网页变成应用程序的框架，VS Code 就是这么来的。再后来又想，为什么不能用写网页、写 React 的方式来写命令行程序？于是有了 Ink 这个库。还有更疯狂的人在琢磨：浏览器运行的性能既然这么好，我能不能在浏览器里解释执行汇编代码？如果能在浏览器里解释执行机器指令，那不就可以在浏览器里跑 C 和 C++ 了吗？JavaScript 也就可以和任何 C/C++ 程序互相调用。

这很像操作系统自己的演化：从 Linux 的系统调用 API，到 LibC，到高级语言 C++，一层一层往上；浏览器和 JavaScript 又是一个抽象层，在它上面长出了巨大无比的应用生态。不只是能和 C、C++ 互相链接，还有像 Mermaid 这样用来画图的，有 TensorFlow.js，有 Three.js——AI 用 Three.js 用得很溜，你可以让它直接给你构建 3D 应用。

### 两条路线：把线程做轻，或在语言里画计算图

刚开始学 JavaScript、在 `async/await` 这些地方遇到困难的时候，不妨回头把「并发被发明，然后被治理好」的这条过程重走一遍：从线程，到 data race，到互斥，到同步，再到「怎么在编程语言设计者和使用者的角度都舒适地描述一张计算图」这一连串问题。

这正好就是今天看到的两条不同路线。Go 走的是线程的轻量化：写法一点不变，代价压到极低，让编译器把同步的写法改写成异步的执行。JavaScript 走的是在语言里描述计算图：用事件模型禁止并行、消灭阻塞式 I/O，再用回调、Promise、`async/await` 一层层把计算图写顺。

## 撞上功耗墙：从动态流水线到 SIMD
> 对应块：BLK39 | 覆盖分集：P20上 | 块标题（分集名）：《CPU、SIMD 和 GPU（上）》

### 我们一直在 CPU 上画那张计算图

先把之前学过的东西过一遍。我们有一个线程库，有 `spawn`；在 `spawn` 的基础上，可以加上互斥锁、信号量、条件变量这些互斥与同步的操作，于是就能控制一个并发程序怎么执行。

但我们控制并发执行的本质，其实是我们脑子里有一张**计算图**：有些部分可以并行，有些部分不能并行。不能并行的就得按顺序执行，能并行的就应该尽可能放出去一起执行。前面讲的一大堆机制，都是在"线程"这个抽象上面，实现各种各样的计算图。

要让一张计算图跑得好，并不是一件简单的事。所以我们走了两条路。

一条思路是把线程做得尽可能轻量：从 Python 的 generators，到协程，再到 Go 语言里那种"用起来和线程完全一样、但又像协程一样轻"的 goroutines。

另一条思路是让编程语言本身受我控制——原则上，我甚至可以允许自己在编程语言里嵌一段自然语言，让它帮我把这些东西并行执行掉。在编程语言发展的那个年代，答案就是 JavaScript 里 event-based concurrency 加上 Promise 的 API，用去描述一张计算图：我创建几个 HTTP 请求，然后用 `Promise.all` 等它们都结束。

到这里为止，所有讨论都还是在 CPU 上面谈并行和并发。**今天，是时候推翻 CPU 在计算这件事上的统治了**——我们来看看这件事意味着什么。

### 顺序执行只是 CPU 精心维护的一个假象

先回顾什么是 CPU。回到第一次 introduction 课讲的那个计算模型：一个单文件就能装下的计算器，比如 `mini-rv32ima.h`。它有一个状态 `state`，我们每一次都可以执行一个 `rv32ima_step`，往前走一小步。这就是 CPU。

但当时我也讲过：**顺序执行只是 CPU 精心维护的一个假象**。你写的每一段程序，虽然看起来是 `x = 1; y = 2` 这样一条接一条，等它们被编译成指令、真的在 CPU 里面执行的时候，其实就是并行的。

为什么能这样？因为**逻辑门天生就是可以并行的**。

你们在数字逻辑电路课里用 Logisim 连过非常非常大的电路。我那天跟大一的同学聊了一会儿，听他们抱怨这门课——你要用鼠标一条一条线连，这没有任何意义；而用编程语言写的时候，一个 `for` 循环就能创建 100 个、1000 个、10000 个门，对你来说都一样。同学说，连电路图极大提升了他的鼠标操作精准度。但 Logisim 的电路图给了你们一个非常直观的感受：信号从左边过来一路走到右边的时候，**所有的逻辑门是同时执行的**。逻辑门天生就是一个并行的系统。

所以没有人能阻止我：

- 我可以放很多很多个逻辑门；我可以一次从内存里取出 32 个 bit，那就没有任何道理能阻止我一次取 64 个 bit 或者 128 个 bit —— 一条 load 指令就能做到，至少我可以在电路上这么设计；
- 如果我能同时取出两条指令，我就可以把它们送到两份复制的电路上去译码，译完就知道"这是一条 `mov 1, %rax`，那是一条 `mov 2, %rbx`"；
- 也没有任何理由不让我再加一块电路，去判断这两条指令能不能并行执行、它们之间有没有互相等待的数据依赖；
- 如果它们真的可以并行，也没有人能阻止我用电路把两个值同时写到两个寄存器里——你们都实现过那个叫双口 register file 的东西，可以选两个寄存器同时写两个值。

原理上，没有任何本质困难挡着我们去同时执行两条指令。

**所以现在的 CPU，每一个都是一个编译器**。而且不止两条指令：CPU 里面有一条非常非常长的队列，每个时钟周期它都会固定地往队列里塞进三条、四条或者更多的指令。指令进了队列之后，CPU 里有一个很大的"编译器"——讲它是编译器不算特别合适，但至少是一个**数据流分析器**——它知道"我这条指令要等到那条指令算出来的结果才能继续执行"，或者"这条指令可能会有什么后果"。它必须把很多信息都存在队列里。

只要你的分支预测一直正确、指令执行的速度又能跟得上（有的指令快，有的指令慢，比如 cache miss 就会特别慢），你就可以始终保持一个非常非常高的执行速度。

> **结论**：CPU 早就不是"一条一条顺序执行"的东西了。它在硬件里维护队列、做依赖分析、同时发射多条指令——顺序执行只是它为你维护出来的假象。

### 怎么证明一个时钟周期执行了不止一条指令

我喜欢期末考试出这种比较 open 的题目：**如果你希望证明你的处理器在一个时钟周期里确实可以执行超过一条指令，你应该怎么办？**

这是一个综合性问题，得从好几个概念拼出来。首先，你可以从 Linux 系统里知道你 CPU 的一些特点，比如 `/proc` 下面有一个 `cpuinfo`：它会告诉你这是一颗什么样的 CPU、主频（frequency）是多少。再查一下手册，你就知道这个时钟周期到底有多长。

然后你可以写程序——用汇编写，写那种没有冲突的指令，尝试各种各样的指令组合。

接下来，你还要有一个意识：计算机系统里应该存在一个工具可以帮你**数指令**。如果你们做过 RISC-V 的处理器实现，里面就有各种各样的 counter，甚至连时钟中断都是用 counter 做的——每个时钟周期它减 1、减 1、减 1，减到 0 的时候就发生一次时钟中断，行为非常确定。

把这些概念凑起来，你就知道这件事能做到；然后让 AI 帮你写，你就能知道你的 CPU 到底能不能一个时钟周期执行超过一条指令。

### BogoMIPS：没有精确计时器时怎么 delay 20 毫秒

真实的系统里确实有这个概念留下的痕迹。`cpuinfo` 里有一个值叫 **BogoMIPS**。我手上这台机器上是 108；你们的电脑上大概是 5000 甚至更大——因为这是一颗非常低功耗的 CPU，而且它测算的时间比较早。

> **定义**：BogoMIPS 里的 Bogo 就是 bogus（假的、估出来的），它是估出来的百万条指令每秒（million instructions per second）。

今天我们的 CPU 基本都有非常完善的计时机制：你可以从一个寄存器里读到一个非常精确的时间戳，精度是纳秒级的，至少记录了"从 CPU 启动到此刻"经历了多少。但在早期，或者 CPU 刚启动、这些处理器特性还用不了的时候，你要大致估算时间，就麻烦了。

比如写操作系统内核或者固件代码的时候，我要发出一个信号，并且确信 20 毫秒以后能收到它的反馈，或者要等 20 毫秒让电路状态稳定下来——那我就得实现一个 `delay 20ms`。

在没有任何精确计时器的情况下，怎么实现 delay 20 毫秒？Linux 的答案是：**假设你的 CPU 频率是固定的**，然后用一个循环来计数——比如一个 `while` 循环，里面调用 `cpu_relax`（一条确定的指令，比如 `nop`）。只要我能算出一秒钟有多长，我就能算出执行一次 `cpu_relax` 循环大概需要多少时间，进而估出这个 BogoMIPS 值。

我这边是 108 million per second，说明这颗处理器在测算 BogoMIPS 的时候跑在一个非常低的频率上。而你们的 Intel 处理器上至少能看到几千，三四千、五千都可能。

有意思的是：**这个数值往往是大于你处理器的主频的**。你的处理器可能是 2 GHz，但你测出来的 BogoMIPS 比它更大。这某种程度上就说明了，我们的处理器在一个时钟周期里是可以执行多条指令的。当然，真要把它证死，你得让 AI 帮你写一个脚本来实测。

### ILP benchmark：一个周期到底能执行几条指令

这里我想多说一句今天的变化：以前这样的脚本，我在课上大概都会拿出来给大家讲一讲我到底做了什么，因为有一天你们可能会自己去写它。但今天我们发现，**你再也不用写代码了**。你更需要知道的是：这个世界上存在一种方式可以写出这样的代码，以及怎么确认你写出来的东西是对的还是不对的。剩下的就交给 AI。

所以我让它做了一个 **ILP benchmark**，ILP 就是 Instruction-Level Parallelism，指令级并行。既然译码一次可以译出超过一条指令，那到底能出多少条？

它的办法是写各种各样的程序：

- 一种是不断地给 `W0` 这个寄存器加 1。因为下一条指令一定要等上一条的结果，下一条又要等下一条，**没有任何办法并行**。理论上，如果 CPU 实现得非常好，这种程序的 IPC 可以接近 1；如果实现得不好，比如你们写的五段流水线，可能还到不了 1。
- 另一种是不写同一个寄存器，而是 `R0`、`R1`、`R2`、`R3` 各写各的。这就应该能触发指令级并行了——同时发射四条指令，同时执行。

> **定义**：IPC 是 instructions per cycle，每个时钟周期完成的指令条数。

我让它统计 IPC。它就帮我写了个脚本，调用一个正确的工具。你甚至不需要事先知道 Linux 里有一个工具叫 `perf`——虽然我在 lecture notes 里给大家讲过，`perf` 非常有用，可以度量程序各种各样的行为，包括 cache miss 的数量，能帮你诊断性能问题。

编译运行之后看结果：那个有依赖、最头上不断 `W0 = W0 + 1` 的程序，居然也能跑到 1.5 的 IPC；而在我这样一台树莓派上，混合了一些指令之后，甚至可以一个时钟周期执行三条指令。它就是靠 `perf` 拿到了程序执行的 instruction counter（指令数量）、cycles（总时钟周期数）这些数据。

> **提示**：你们在自己机器上会看到不同的结果，这和你们 CPU 的实现有关系。有兴趣的同学可以开一个 AI coding agent（比如 Claude Code），让它解释整个程序里到底发生了什么。

**但我要讲的不是体系结构**。我要讲的是：指令级并行到底意味着什么——CPU 的设计者在这里做了一个非常艰难的决定。

### 动态流水的账单

你想，如果要做一次加法，需要多少电路？无非是一个超前进位加法器。乘法、加法都是 ALU 里的固定电路。做位运算就更省电路了，与或非而已。浮点会稍微大一点。

但如果你要在 CPU 里面塞一个编译器呢？

你要塞一个 1024 项的队列，这个队列支持 push 和 pop——那么队列的每个格子都得有 bit 去维护"这里面有没有东西"，你还需要知道队列头在哪里，而且它实际上是循环的：你只能用一个类似数组的东西，但队列不停地往后长，长到头又回到前面。

要维护这样的 FIFO 队列，还要维护一个编译器、一个数据流分析器，而数据流分析器要分析**队列里任意两条指令之间存不存在数据关系**。理论上这是 $O(n^2)$ 的，当然有聪明的办法把复杂度降下来，但你可以想象，塞编译器、塞队列、塞这些东西要占用多少电路——**这些电路就不能用来放运算部件了**。

还有更直接的代价：功耗。如果一块电路不动，比如时钟信号没来，或者 enable 信号不在，它就没有功耗；可只要**任何一个逻辑门从 0 变成 1、或者从 1 变成 0，它就要发热**。所以整个编译器和动态流水线部分的功耗，比你真正去算这条指令（比如把一个 1 写进寄存器）要大得多。

你写程序的时候觉得"先执行 1，1 执行完了再执行 2"；为了让 1 和 2 能同时执行，硬件付出了巨大的功耗。而**这些能量其实是被浪费掉的**——它没有参与到实际的计算里，只是为了让计算在时间域上更快。

```text
      取指 ──► 译码 ──► ┌───────────────────────────┐
                        │   很长的指令队列（1024 项） │  每周期塞 3~4 条
                        └─────────────┬─────────────┘
                                      │
                            数据流分析 / 依赖判断
                            （队列里任意两条指令，O(n²)）
                                      │
                                      ▼
                        执行单元：ALU / 浮点 / 访存
                                      ▲
                    分支预测正确 ─────┘  （预测错了就前功尽弃）

     结论：芯片面积与功耗的一大块，没有用来算数，而是用来"调度"。
```

图里最重要的一行就是最后那句：芯片面积和功耗的一大块没有用来算数，而是用来调度。后面我们反复要跟这个"调度开销"打交道。

### 从 1995 到 2005：队列越来越大，制程越来越好

我还挺幸运，生活过 1995 到 2005 这个时代。不能说每天，但你隔一小段时间就能看到处理器又快了多少，每一代都比上一代快。

那这个快是怎么来的？非常粗暴。比如今天队列是 1024 项，发布下一代处理器的时候，因为制程更先进，就把它变成 2048 项——就是这么离谱。队列大了，动态流水线就能更快，代价是这个"编译器"又变得更复杂，FIFO 也占更大的电路。

但那十年里我们的工艺制程从 100 多纳米一直变到十几纳米，一直在有先进工艺接上。Intel 那时候有个叫 **Tick-Tock** 的节奏：隔一年发布一个更先进的动态流水线，再隔一年发布一个更先进的制程。制程进步意味着集成电路做得更小，于是单位面积上能塞更多晶体管，而且**每个晶体管的耗能也减少**。1995 到 2005 年的单处理器性能增长，就靠这个方式在维持。

**但这件事总有一天会撞墙。**

### 功耗墙，以及系统里各种各样的墙

整个计算机芯片的热功耗有三个因素。

第一个是**电容**，这个基本上没有办法，它跟你的制程有关：制程变好了，这个系数就下降。第二个是**频率**，也很好理解——你不让它动它就没有功耗，只要 CPU 跑起来就要耗功。第三个是**电压的平方** $V^2$，依靠更先进的制程可以用更小的电压把功耗压下去。

$$P \;\propto\; C \cdot f \cdot V^{2}$$

可一旦制程不能变得更先进了，$C$ 和 $V^2$ 基本上就定下来了。那你就没有办法继续加大 buffer size，没有办法让这个编译器变得更复杂——因为你要撞墙了：**你的封装散热能力是有限的，也就 100 多瓦**。你就算能把电路做得更大、在里面塞一个更复杂的处理器，散热也已经跟不上了。

> **结论**：这就是**功耗墙**。撞上它以后，单处理器性能的无限增长就结束了。

其实系统里有很多很多这样的墙，墙就意味着极限：

| 墙 | 卡在什么地方 |
| :--- | :--- |
| 功耗墙 | 封装散热就只有 100 多瓦，再多的电路也散不出去 |
| 频率墙 | 频率不能再往上提了 |
| 内存墙 | 内存带宽有限，缓存与内存之间的带宽成了瓶颈 |
| I/O 墙 | 输入输出的能力到顶 |

内存墙的例子最直观：有的程序写得非常好，几乎每一条都是 load，而且每条 load 之间互相独立、可以并行执行——那很快缓存和内存之间的带宽就成为瓶颈，指令再也发不出去，只能等，就是撞墙。频率的、内存的、I/O 的，你都会碰到。

### 系统里的黑话：交税

在这些墙旁边，你还会在 systems 这个圈子里听到一些黑话，比如"**交税**"。有各种各样的税：你收到一份好处，就必须额外付出一些东西。

你在淘宝上下一个单，要发一个 HTTP 请求。**那个 HTTP 请求才是你真正要的东西**；可为了把它从我这台机器发到那台机器，你会一层一层经过 TCP/IP，经过本地以太网或者是无线的以太网协议。每一层协议都要在头上和尾巴上加一些东西——HTTP 本身只是个字符串（应用层的协议），但你为了把它发出去，只能不停地在上面加头、加头、加头。

```text
你要发的东西：
  HTTP 请求（真正的载荷）
      │  + TCP 头
      ▼
      │  + IP 头
      ▼
      │  + 以太网帧头 …… 帧尾
      ▼
  网线上的比特流  ←── 一路加出来的这些头，就是你交的税
```

所以要做一个性能极致的系统，要考虑的因素非常非常多。

### 两条路径：把核做复杂，或者把核做多

回过头看，前面讲的都是 facts：我们现在的 CPU 是什么样、我们总想要更好的性能、我们撞上了功耗墙、而且那种做法虽然确实提升了性能，却浪费了很多能源。

那么一个很自然的问题就来了：**我们有没有可能在有限的能源上，做出一个更快的处理器？**

对芯片设计者来说，答案很直接：跑得更快就能挣更多的钱，就这么简单。

所以面对功耗墙，我们有一个非常重要的观察：**有没有可能压榨出更多的 performance per watt**——让每一个逻辑门的翻转都有意义，都参与到实际的计算当中，而不是像刚才那样，逻辑门的翻转是用来在"编译器"里算有没有数据依赖、在队列里做 bookkeeping。这些功耗最终都没有反映到程序的实际执行上。这就是交的税。

于是有了两条非常重要的途径：一条是**处理器内部的并行执行**；另一条是**用更多、更简单的处理器**。

同样大小的电路、同样的功耗，我可以选择放两个大的，也可以放四个小的，或者 8 个、16 个更小的。

```text
同一份面积 / 同一份功耗，两种选择：

   [   大核   ] [   大核   ]        [小][小][小][小][小]
   复杂的动态流水线，编译器复杂        核很简单，编译器很小
   单核性能强，但浪费的功耗多          单核性能弱，但核多
```

放两个大的，就意味着编译器更复杂、单核性能更强，但有更多功耗被浪费掉；放小的，同样的功耗下就能多塞几个 CPU，单核性能下降——你会看到 Word、Excel 这类单核应用变卡——但好处是：完成同样的工作，功耗降低了；如果是并行任务，就能在更短的时间里完成。

Intel 基本上是在 2005 年左右推出了第一款双核处理器：它发现靠"让编译器更复杂"这条路已经要到头了，只能在 CPU 数量上扩展，来维持摩尔定律。

后来又发现，没法让芯片里每一个核都一样大。2011 年左右——正好是手机、移动互联网兴起来的时候——ARM 有了 **big.LITTLE** 架构：一块芯片上既塞大的，也塞几个小的，甚至还可以塞一些超小的。这样当系统处于不活动状态的时候，就在能效比非常高的核心上启动。

道理是一致的：**同样的面积上，处理器越简单，能放的数量就越多**，理论上就能把更多的逻辑门翻转投入到实际的计算上。

### SIMD：让一条指令干更多的事

然后还有一条路径，你们可能没想到：**让一条指令能够处理更多的数据**。

注意，动态流水线调度的单位是**指令**。说到指令你会想到什么？一条 `mov %eax` 是一条指令。所以我们谈指令的时候，尤其是讲 RISC-V 指令的时候，一条指令就只能做非常非常小的一件事。

**这时候指令做的事情非常小，但 bookkeep 这条指令的代价非常大——你交税了，而且交得巨多无比**。相当于你收入 100 块，有 99 块都交了税，这谁想干。

那能做什么？我可以让一条指令里面操纵更多的寄存器。比如，我能不能引入一条指令把所有的寄存器都加一？实际的 CPU 设计者当然不会这样设计——这会彻底改变 CPU 的微架构，我们总还是有一些物理上的规则必须遵守。但假设有这么一条指令：它可以执行很长时间，原来要 32 条指令才能做完的事，现在一条指令放在队列里就做完了。

这就意味着**税被分摊成了三十二分之一**。而且它依然只占队列里的一个格子，对整个动态流水线的复杂性几乎没有显著增加——这笔账非常划算。

> **定义**：single instruction multiple data，**SIMD**——让一条指令做更多的事。

### MMX：一条指令里的四个数

SIMD 当然不会去做"把所有寄存器都加一"这种看起来很傻的事。它的办法是这样的——

1997 年，32 位机上有了一组扩展，叫 **MMX**，MultiMedia Extension。这是一个非常有年代感的名字，"多媒体"就是说把图像、声音放在一起，给人一个真实的体验。这个词你们听说过吗？在今天它已经完全成为计算机系统的一部分了——你打开智能手机、打开抖音，那默认就自带了这样的功能。

它做的事情是：为 32 位机增加**一组 64 位的寄存器**，这个 64 位寄存器可以当成**四个 16-bit 的整数**来用，然后增加一组指令集。当然需要 load、需要 store，它本质上还是一个寄存器。关键在于，它允许你**同时对这四个数字做某一个操作**：比如我给两个 MM 寄存器做加法，它的第一个通道加第一个通道、第二个通道加第二个通道……四个通道各自相加。

这和 64 位整数加法完全不同。64 位整数相加的时候，低位相加产生的进位会溢出到高位去；而 MMX 这一组指令在设计时是**不会跨通道溢出**的——两个通道里的数加溢出了，它会保留一个最大值，有点像浮点数的那种 overflow 和 underflow 的感觉。

> **提示**：这一点是这一节最容易混的地方。用 SIMD 寄存器做四个 16-bit 加法，是四条互不干扰的通道；用 64 位整数做加法，是有一条进位链把它们串起来的。前者不会把累加"串味"到相邻通道。

```text
一条 64 位 MM 寄存器（四个 16-bit 通道）

  +----------------+----------------+----------------+----------------+
  |   16-bit #3    |   16-bit #2    |   16-bit #1    |   16-bit #0    |
  +----------------+----------------+----------------+----------------+
          +                +                +                +
  +----------------+----------------+----------------+----------------+
  |   16-bit #3    |   16-bit #2    |   16-bit #1    |   16-bit #0    |
  +----------------+----------------+----------------+----------------+

  四条通道各自相加；溢出被截在本通道内（饱和到最大值），不会进位到隔壁通道
```

为了展示技术的先进，他们在随处理器发售的每一台机器里都附了一张光盘，上面放着 MMX 指令集的 killer application。那是 1997 年，画面看起来已经非常高清：一个三维渲染的场景，而且**有光照**——你留意的话，子弹射出去的时候是带光照的。这在之前很难实现。虽然今天看它连手机游戏都不如，但在当时，这个图形效果是非常惊艳的。

### 你其实早就用过 SIMD 的思路

你们在编程的时候，不经意之间已经用过这样的思想了。

指令集里说"我引入一种新寄存器，它可以当成四个 16-bit 整数来用"；而你们实现 bitset 这类数据结构的时候，用的是同一招：**把一个 32 位整数当成 32 个 1-bit 来用**。

比如要维护一个集合，集合刚好只存 0 到 31 的元素，比如 {0, 1, 2, 6, 7}。你可以写一个 `set of int`，也可以直接用一个 `uint32_t`：从右往左数，这是第 0 位；某元素在集合里，就把对应的那一位写成 1，得到 `1100 0111` 这样一个 32 位整数。

当然你还可以更进一步：用 32 位整数建一个数组，`array[0]`、`array[1]`……就能做一个很大的 **bit vector**。要查询 `x` 在不在集合里，就先把它除以 8 找到那个格子，再找出格子里对应的那一位。

你们还见过一些很神奇的位运算，比如 `lowbit`：`x & (-x)`，我上计算机系统基础课的习题课时会讲它的原理。还有一些**骚操作的代码，一看就两眼一黑**。

### popcount：分治，还是查表

你们知道 popcount 吗？就是数一个二进制串里有多少个 1。把 32 位整数当成 32 个 1-bit——这本身就是 single instruction multiple data。

那个"骚操作"是这样的：`0x55` 是 `0101`，`0xAA` 是 `1010`。于是

- `x & 0x55555555` 取出的是从第 0 位开始的**偶数位**；
- `x & 0xAAAAAAAA` 取出的是**奇数位**。

把偶数位取出来、奇数位也取出来，再把后者右移一位——这就对齐了：右移之后低位补 0，"错开"的那一位就没了。两个数一加，相当于每两位一组地把它加在一起，就得到了**每两个 bit 里有几个 1**。

然后再对这个结果做同样的操作：取它的奇数位、偶数位，对齐，再加。加着加着，就形成了 divide-and-conquer 的过程，最后剩下的就是整个 32 位的 popcount。指令数远比一个 `while` 循环要少。

> **提示**：这种 clever 的位运算实现在现代处理器上**性能很差**，因为它对动态流水线非常不友好——里面有大量计算依赖，每个下一步都要等上一步的结果。它不是好的实现。

那现在要写一个比较快的 popcount 应该怎么办？**查表**。

把这个 32 位整数分成四个 8-bit 整数，预先处理好每一个 8-bit 整数对应的 popcount 值。这样你只需要四次 load，虽然它们 load 的是不同地址，但只要缓存足够大，这些常用的值在缓存里是热的，四个 load 几乎是并行完成的，或者几个周期内就能拿到，再做几个加法就得到了结果。

**所以不要试图去做那种比较 clever 的优化**。当然，我这里要告诉大家的是：我们确实也要写这种 SIMD 的低级程序。

### 寄存器越来越宽，名字越来越难起

SIMD 引入了 **packed register**，还有一组指令去操作它们——光 MMX 就有 57 条。如果你们有兴趣，我可以把手册直接附给你们，你在 AI 的帮助下可以直接读它；甚至你都不需要让 AI 去读手册，因为它对 SIMD 指令集已经有很好的了解了。里面有很多各种各样的指令，甚至有 PACK 指令、Shuffle 指令，加减等等。

这确实是一个**平摊每条指令开销**的好办法：不管怎么样它都是一条指令，只占队列里的一个格子；而这一个格子，可以实现原来要 4 条、8 条甚至更多指令才能完成的数据操作。性能就这么提上来了。

于是 Intel 就走上了不断增加寄存器长度的道路：从 MMX 到 SSE，到 AVX，再到 AVX-512。你要是看 `/proc/cpuinfo`，会看到这些字样——`sse`、`avx`，你们有印象的话，它们确实都在那里。

寄存器名字的来历是一段历史：

| 名字 | 宽度 | 含义 |
| :--- | :--- | :--- |
| `mm` | 64 bit | multimedia，多媒体的时代引入的——这是一个历史上的错误，今天已经没有人提多媒体了，但寄存器的名字被永远保留了下来 |
| `xmm` | 128 bit | extended mm |
| `ymm` | 256 bit | 128 变 256 的时候，他们发现没有名字可用了 |
| `zmm` | 512 bit | AVX-512 |

AVX-512 在短期内基本就是极限了。512 个 bit 这么宽的一个寄存器，已经足够分摊掉指令的开销。而且实际上，Intel 第十代前后那些支持 AVX-512 的处理器就已经撞上功耗墙、碰到了热密度的极限：**只要你开启 AVX-512，整个封装的功耗就扛不住，处理器会被迫降频**。

这里面还有很多故事：

- **指令集支持了更多的数据类型**。早期只有整数，后来支持 `float32`、`float64`，完整的 IEEE 754 浮点都装进来了。这很大程度上得益于先进的制程——能在有限的面积上塞下更多晶体管，才做得到完整的指令支持。
- **支持了更多的运算**，像 shuffle 类的运算；一条指令还可以做很多次内存 load。
- 还有 **FMA（fused multiply-add）**：用一条指令实现 $A \times B + C$，这在矩阵乘法里是非常常用的操作。

> **结论**：SIMD 有一点特别好——它**不改变你的编程模型**。你依然写一个单线程的程序，但用 AVX-512 就可以用一条指令完成很多数据的写，**就好像有好多个线程在同时给你工作一样**。这就是 CPU 内部的并行。

### SIMD 没能解决的问题

但 SIMD 并没有把所有问题都解决，它和 CPU 设计者的设计理念其实是有一点点违背的。

因为它还是会参与到 CPU 微架构里的每一样东西：SIMD 寄存器的 load 和 store 依然要经过缓存，而且是和别的指令同一个缓存；它也要参与动态流水线的调度——虽然一条指令分摊下来的计算代价降低了，但这依然占着那个 buffer 里的一个格子，**动态流水线本身没有改变，那部分功耗还在**。

最终的结果就是：SIMD 指令会和你的其他指令**抢缓存、抢功耗**。它可能不是我们真正想要的那个终极方案——我们想要的是大规模并行。

人在做优化这件事上，永远是不满足的。我们真正想要的是：**让指令调度的代价接近于 0**。只有所有交的税都降到 0（或者近似为 0），人类才满意。

### VLIW：把调度全部交给编译器

历史上人类还有过一次非常激进的尝试，叫 **VLIW**，Very Long Instruction Word。这个技术其实没有完全死掉，在今天一些特殊的加速器上你还能看到它的影子。

它的想法是这样：我们随便找一个程序，它都是五花八门的汇编序列——这是 mov，那是 jump。所以我们才要在处理器上面做**动态**的指令调度。VLIW 说：好，你不要在处理器上做动态指令调度，我们**把指令打包**。

激进一点的做法是：每一条指令有 256 个 byte，在这 256 个 byte 里面 pack 8 条、16 条指令，甚至可以是可变数量的。这时候，**一个指令 pack 里面的所有指令都是可以并行执行的**，由编译器保证它们之间不存在"我这条指令要依赖它"的情况。

于是译码器就可以做得非常简单：我看到这里面是什么指令，直接执行就行，**不做任何依赖判断**。整个指令序列也都是由编译器生成的；如果某处有个跳转，编译器要保证跳过去之后不会导致动态流水线的问题，一旦会导致问题，它就要插入一些 `nop` 之类的指令。所有事情都交给编译器。

这个尝试失败了。Intel 花很大的代价做了一个叫 **IA-64** 的指令集，那就是一个 VLIW，结果失败了，没有市场。为什么？因为那个时候，指令级并行带来的收益和先进制程带来的收益都很大，而且没有迁移成本——所以它就没有市场。

**但我觉得在大语言模型的时代，这种方式又复活了**。因为它是一个真正能够让指令调度的代价接近于 0 的方案；只是在它诞生的时候，编译器技术还有点跟不上。今天，我觉得真的有可能要复活。

### 活下来的方案：让每个核简单到不留一点浪费

活下来的方案，就是我刚才说的那条路：如果一个大的、复杂的 CPU 可以做一个复杂的动态流水线让指令执行得很快，那我就能够把这个 CPU 不断地变简单、变简单、变简单，然后**塞进更多的 CPU**。

那指令调度的代价不就近乎为零了吗？如果我的每一个 CPU 都是一个**单周期**的 CPU——就是你们做实验时实现的那个最简单的 CPU——那我就不浪费电路。每一个 CPU 都运行得很慢，确实很慢，但我真的没有浪费任何电路：每一次逻辑门的翻转，几乎都用在有意义的事情上——指令的译码、指令的执行、load、store。

今天要讲的那个 CUDA，就是显卡里面的技术，比这个还要再激进：**它让 CPU 里面的一部分是共享的**。只有绝对需要的东西——比如执行单元——才会由多个副本，ALU 必须每个 CPU 有一份；但甚至连译码器也可以让多个 CPU 共享同一个，因为指令集越复杂，译码器越占电路。这是一个非常有意思的想法。

```text
             +--------------------------------------+
             |       共享的译码器 / 调度电路          |
             +---+--------------+--------------+----+
                 |              |              |
            +----v----+    +----v----+    +----v----+
            |  ALU 0  |    |  ALU 1  |    |  ALU 2  |   ← 每个核只保留
            | 寄存器  |    | 寄存器  |    | 寄存器  |     最必要的执行单元
            +---------+    +---------+    +---------+

   核越简单，同一块面积上能放的核越多；被共享的部分，开销只交一次。
```

这个想法直接引出了今天人工智能时代的明星。

### 另一条时间线：从乒乓球到 NES

要讲 GPU，我得先讲人类改变命运的另外一条时间线。把时间倒回去一点。

1972 年，有一台 Magnavox 的 **Odyssey**。这是人类世界上第一台发售的游戏主机，一个极为大胆的尝试。它已经颇有今天游戏主机的雏形——如果你有 Xbox 或者 PS5，你看还真的有点相似。你有像手柄一样的设备可以操纵它。它没有声音，画面甚至只是光点。

光点能玩什么游戏？就那种乒乓球，ping-pong：你控制一个挡板，上下上下上下，然后乒乓。但这台主机卖得还可以，这个产业就起来了。

到了 1983 年，出现了一个跨时代的产品：**Nintendo Entertainment System（NES）**，也是我这个年代的人的童年回忆。1986 年有一款游戏发售，就是塞尔达传说的第一代——它已经拥有非常精美的图形、平滑的动画，还有一个交互的界面。

我今天不是来玩塞尔达的。我说的是：**你看到一个非常漂亮的界面，它背后其实隐藏了一个计算危机。**

我自己学编程的时候，最最让我印象深刻的时刻，是学了循环之后——我可以用打印一个星号来画任何想画的图形，哪怕只是一个三角形、一个圆形、一个正方形，我都感到很开心。

本质上画图就是这样的：一个二重循环，`for` 每一行、每一列，然后计算一个函数 $f(x, y)$ 算出这个点上面到底要不要有一个像素、或者它的像素是什么颜色，然后把它画出来。

**这是一个 embarrassingly parallel 的程序。** 又回到我前面课上讲过的 Mandelbrot set：你想画一个 6400×6400 的 Mandelbrot set，那不要紧，我创建一大堆线程——如果我真有足够轻量的线程，我甚至可以为每一个像素点创建一个线程，你去画吧，画完再回来。这是一个 embarrassingly parallel 的任务。

**但那个时候所有的 CPU 都没有多处理器，多处理器的理论、实践根本就不存在。**

1983 年的 NES 用的是一颗 **MOS 6502**。它的 IPC 是 **0.43**，小于 1：它没有任何动态流水线。它要去 load，就得等内存控制器、内存总线里那个值回来，所以它必须等；它可能连流水线都没有，或者只有一个两级的、非常简单的流水线。一次 load、store 可能就要花三个周期。

**但它却有一块非常漂亮的屏幕**：那块屏幕非常精细、效果非常好，上面有六万一千个像素、几百种颜色，而且所有的 NES 游戏都跑在 60 FPS 上，非常丝滑。

一颗 IPC 只有 0.43 的 CPU，撑起了 60 FPS 的漂亮画面——这就是那个隐藏的计算危机。怎么在"没有多处理器、连流水线都没有"的机器上，把这种 embarrassingly parallel 的图形计算做出来，就是接下来要讲的东西的起点。

### 本讲提到的题目

**题目一**：如果希望证明你的处理器在一个时钟周期里面确实可以执行超过一条指令，你应该怎么办？

**解析**：这是一道综合性很强的题目，答案要把好几个已学概念拼起来。

1. 先弄清你的硬件是什么：从 Linux 的 `/proc/cpuinfo` 里读出 CPU 型号与主频（frequency）。
2. 再查手册，知道这颗 CPU 的时钟周期到底有多长。
3. 写一段汇编去实测：使用没有冲突的指令，尝试各种不同的指令组合（例如反复给同一个寄存器加 1 制造依赖，改成几个不同寄存器各写各的制造并行）。
4. 需要有"数指令"的意识：计算机系统里存在这样的工具，比如 Linux 的 `perf`，可以拿到程序执行的指令数量和时钟周期数；也可以参照你自己实现 RISC-V 处理器时的那种 counter——它每个时钟周期减 1，减到 0 触发一次时钟中断。
5. 用指令数除以时钟周期数得到 IPC，若大于 1，就说明一个时钟周期确实执行了超过一条指令。前面的 BogoMIPS 是这条结论的旁证：它常常大于处理器主频，正说明一个周期不止一条指令。

**题目二**：如果现在要实现一个比较快的 popcount，应该怎么做？

**解析**：不要走那种"聪明"的分治位运算路线。虽然 `x & 0x55555555` 取偶数位、`x & 0xAAAAAAAA` 取奇数位、右移一位对齐相加，再递归地做下去，用很少的指令就能算出结果，但那条链上全是计算依赖，对动态流水线非常不友好，在现代处理器上性能很差。快的做法是**查表**：把 32 位整数切成四个 8-bit 整数，预先准备好每个 8-bit 值的 popcount，然后做四次 load——地址虽然不同，但常用的表项在缓存里是热的，四次 load 几乎可以并行完成——最后做几个加法即可。

> **承前启后**：上一节讲完「撞上功耗墙：从动态流水线到 SIMD」，下一节接着讲「从 NES 的贴块到 CUDA 的线程束」。

## 从 NES 的贴块到 CUDA 的线程束
> 对应块：BLK40 | 覆盖分集：P20下 | 块标题（分集名）：《CPU、SIMD 和 GPU（下）》

### 一万条指令，六万个像素

先摆一笔账，这笔账在当年看起来是根本还不起的。

一台机器要跑 60 FPS，也就是把 1 秒钟切成 60 份，每一份里要把屏幕上六万个像素全部渲染出来。而同时期 CPU 能拿出来的预算是多少？差不多 10,000 条指令。用 10,000 条指令去完成 60,000 个像素的渲染，摊下来每画一个像素连四分之一条指令都分不到，IPC 小得可怜——连 1 都不到。

这笔账怎么算都还不上。可游戏就是跑起来了，跑得还挺好。唯一能解释这件事的，是图形绘制本身的性质：它是一个 embarrassingly parallel 的计算。每个像素要算什么，跟旁边那个像素几乎没关系，你把它们全都轰到并行单元上去做，谁也不用等谁。

于是整个体系结构上最重要的一句话就出来了：**把"要画什么"和"到底怎么画"分开**。CPU 只负责产出一个叫场景描述的数据结构，这个数据结构里写清楚"这个画面里有些什么东西"。剩下的"怎么把它变成像素"，交给一块专门为此设计的硬件。

这句话说完，后面的所有东西都只是它的推论。

### 把「画什么」和「怎么画」分开

#### 8×8 的贴块与四种颜色

我们拿 NES 的 PPU 当样品。它的场景描述极其节俭，节俭到有点可爱。

所有图元都存在 ROM 里，每一个图元就是一个 $8 \times 8$ 的小贴块。注意，不是你们现在电脑里那种高清彩色贴图，每一种颜色都占好几个字节；这里一个小贴块只允许有 4 种颜色。4 种颜色意味着每个像素只要 2 bit，于是一个 $8 \times 8 \times 2\,\text{bit}$ 的图元，几个字节就装下了。

省到这个地步，是因为那 4 种颜色里只有两种是自定义颜色，另外还有一个前景色、一个背景色，甚至还可以留一个是透明色。

而更省的一招是**调色板**。贴块本身只存 2 bit 的索引，真正决定它长什么颜色的是给它配的那张调色板。你们都见过 Super Mario 里那两个角色——一个红衣服的，一个绿衣服的，绿衣服那个就是 P2 路易吉。他和红衣服那位用的是**完全相同的贴块**，只是配了不同的调色板，所以他就变绿了。在那个年代，这一点点存储空间是值得这样去省的。

#### 一个背景加 64 个精灵

NES 描述一个画面，只需要两样东西。

**一个背景。** 背景是一大块由规则排列的贴块拼成的东西，一块一块一块一块，而且它比实际显示的区域要大一些。然后我们告诉这块硬件："这一次真正要显示的是这一块。"于是你把显示窗口从左往右移，移到最右边的时候，把左边这几列贴块换成新的，屏幕上就出现了卷轴效果——Super Mario Brothers 里那种经典的横向卷动就是这么来的。

> **提示**：这也是为什么那个年代的游戏基本只能往右走、不能回头。往回卷需要额外换一批贴块，得靠很多编程上的 trick 才能在后来实现。

**一堆精灵。** 在背景之上，我们还可以把很多个 $8 \times 8$ 的小块摆到画面上的任意位置，这时候位置就不再受"规则排列"的约束了。这种 $8 \times 8$ 的小东西叫 sprite，精灵。一个卷轴的背景加上一层动态的前景，就是你在《塞尔达传说》里看到的那幅画面。

所以整个屏幕上"能变的东西"其实非常少，但恰恰是这些用贴块拼出来的东西在变。

#### 属性字节里的翻转把戏

每个精灵要交代的信息是：它是哪一个 tile、用哪张调色板、摆在屏幕的哪个 $x$、$y$ 上。此外还有**一个 8 bit 的属性**，这 8 位里的分配是这样的：有两位选调色板，有几位没有实现，有一位是优先级——相当于 Z 轴的顺序，还有两位是水平翻转和垂直翻转。

```text
    ROM 里的贴块表 (每个 8x8, 每像素 2 bit -> 4 色)
                    |
                    |  取 tile 号 + 调色板号
                    v
    +-----------------------------------------------+
    |  背景: 规则排列的贴块图, 比显示屏更大           |
    |        视野窗口在图上滑动 -> 卷轴               |
    +-----------------------------------------------+
                    |
                    |  叠上位置任意的前景
                    v
    +-----------------------------------------------+
    |  精灵: 最多 64 个 8x8, 每个带一个 8 bit 属性   |
    |        [调色板 2b][未实现][优先级 1b][H/V 翻转 2b]
    +-----------------------------------------------+
                    |
                    v
       line 计数器逐行扫过, 每行切成若干 chunk 并行处理
```

就是这两个翻转位，让他们玩出了很多很有意思的东西。

想画一个圆，你不用准备 4 个 tile：一个 tile 做一个垂直翻转，再各做一次水平翻转，四个象限就凑出来了，一个圆就有了。还有你们在 Super Mario Brothers 里见到的那种碰到就会死的蘑菇：它明明在往前走，但那个"走路"的动画并不是真的让它走起来。蘑菇有两只脚，一只脚画得短一点，一只脚画得长一点，两只脚分别在两个贴块上；程序只要交换这两只脚的位置，再顺手做个镜像翻转，就得到了一个只有两帧的动画，然后让它缓慢地向前移动——看上去它就在走了。

用这种极简的描述模型能做出很多神奇的编程，很早年的游戏开发里到处是这种 trick，值得专门去找来读。

#### 换一张调色板就是一整屏动画

前面说过屏幕上能变的东西不多。那你们猜猜，当年那种**全屏动画**是怎么做出来的？

答案还是调色板。屏幕上的东西一个都没动，变的是颜色。你把调色板整张换成一张全黑的，画面就全黑了，而显示的内容本身完全没有变化。再加上那个区域足够大，能容下 4 帧动画，一个非常简单的描述模型就能做出各种花活。

### 图形渲染的本质：一个描述，一台翻译机

#### struct GPU state

回到本质上来。图形渲染就是：**我们有一个描述，由另一块硬件专门负责把这个描述变成图形**。

描述的形式有很多种。可以用寄存器，比如一对 XY 寄存器；也可以把一部分东西放进内存，比如一个 sprite buffer，CPU 直接读写那块内存，也就是内存映射。怎么放都行。

而所谓的数据结构，说到底就是内存里平铺的一堆数据。你在做 NEMU 的时候写过一个 `struct CPU state`——这次不是 CPU 了，这是 `struct GPU state`。这个 GPU state 里面有 XY 或者别的什么。**GPU 是什么呢？GPU 就是一个程序，它负责把这个 state 翻译成像素。**

只不过它是一个 embarrassingly parallel 的程序。

#### line 与 chunk：逐行扫描的并行

一台 NES 的 PPU 工作原理大概就是这样，它真的是逐行扫描的。

硬件内部有一个寄存器叫 `line`，它从 0 开始一直往上扫；0 的事情做完了才做 1，1 做完了才做 2——从抽象角度看就是一个设计好的时序逻辑电路。我照抄一份 OpenMP 的说法：这些事好像是并行做的。

```text
        line = 0, 1, 2, ... 逐行推进
                |
                |  对当前这一行
                v
   +------------------------------------------+
   | 先算背景: 在贴块图上做加法, 取出该点的  |
   | 背景色                                   |
   +------------------------------------------+
                |
                v
   +------------------------------------------+
   | 再遍历 64 个精灵, 看这个像素被几个精灵   |
   | 覆盖, 谁的优先级最高就取谁的颜色         |
   +------------------------------------------+
                |
                v
   若没有任何精灵覆盖这个像素 -> 用背景色
```

扫到某一个像素时，先确定它在背景上是什么颜色——这个只要做一个加法就取出来了。取完背景色，再对每一个 sprite 去匹配：这个像素上到底叠了几个精灵、谁的优先级最高，我就取谁的颜色。这有点像今天的 Z-buffer：一层一层一层，你永远只能看到最上面那一个，上面的会盖住下面的。如果一个都没盖住，那就显示背景色。

图形组合就这么实现了。

而既然逻辑门在电路上本来就是并行的，这里就可以并行地处理多个像素。它也未必一次就处理完一整行像素，可以另外有个寄存器叫 `chunk`。你们都实现过计数器的电路，用计数器就能做出类似循环的效果：行从 0、1、2 往后扫，同时把每一行切成 10 个 chunk，0 到 9；每进一个 chunk，就知道这个 chunk 要算比如 20 个或者 32 个像素，然后并行地算。

#### 固定逻辑固化进电路

这里的关键在于：**如果逻辑是完全确定的、写死的**——因为数据结构就这么规定，处理逻辑也就这么写死——那理论上完全可以把这部分计算固化到电路里去。

> **结论**：你能用固定的电路实现并行化，就能把画图这件事从 CPU 里彻底解脱出来。

这个想法会一直反复出现。最典型的例子是矿卡。如果你在 1983 年见过 NES 干这件事，等到比特币热潮的时候你自然会想：我们应该把 Hash 的那部分固化到电路里。想明白了，你可能就发大财了。

### 图形引擎长大了：从贴块到贴图

NES 火了以后挣了大把的钱，挣了钱就能去雇世界上最好的工程师——软件的、硬件的——去开发下一代产品。因为对图形处理器来说，它干的活只是"把一个数据结构变成一幅图像"，**没有人规定这个数据结构一定要长成"一块紧密排列的背景加 64 个前景小块"**。任何描述方式都行，只要满足两个条件：CPU 有足够算力在一帧时间里生成这样一个描述，硬件能把描述变成真正的图片。

#### 黏纸一样的线性变换

于是第一件事自然就是：不再用固定大小的块块，改用真正的贴图。

一张贴图有四个点。我可以对它做线性变换。想象这张贴图是一张黏黏的、有弹性的纸，你揪着一个角往外拉，纸被拉大了，上面的像素不就跟着一起被拉大了吗？于是我可以把任意一张贴图放大、缩小、裁剪，然后拼到画布上。

描述也随之改变：不再是"一块一块的贴块"，而是"我有一个 bitmap，我要把它移到屏幕上的 $(x_1,y_1)$ 到 $(x_4,y_4)$ 这四个角去"。真实设计当然不是这样，这只是为了理解方便。

```text
   ROM 里的 bitmap 1  -->  贴到屏幕 (x1,y1)..(x4,y4)
   ROM 里的 bitmap 2  -->  贴到屏幕 (x1,y1)..(x4,y4)
   ...
   对每个像素遍历所有 bitmap, 取最上面那个的颜色
```

这同样是一个 massive parallel 的问题：对每一个像素去迭代过每一个 bitmap，找到对应位置上最上面那层的颜色，图形就画出来了。

即便是这样一台"完全二阶"的 2D 图形引擎，他们也能玩出各种花样。它本来是为卷轴、马里奥、金币这些东西设计的，但你看那个 logo 放大的特效，就是把一块 logo 拉伸出来的；它还有一些其他的处理流程，可以实现模糊的效果。

#### 用二维挤压出三维

然后你会看到一个 3D 游戏——但它的 3D 实际上是用二维模拟出来的。

做法是把一个矩形往某个方向挤压，就用 2D 贴图模拟出了 3D 的观感。你细看会发现那个 3D 贴图有点不对，因为它根本没有深度信息，只是被强行挤压成了那个样子，所以它不能转得再大一点，再大一点就要穿帮。但真跑起来的时候，效果确实还是很酷的：它把画面旋转了，背景随着镜头移动变小一些，前景随着镜头移动变大一些。Game Boy Advance 上有很多这样的代表作。

> **易错点**：那个梯形看起来是"挤压"出来的，但真实的透视效果其实是深度造成的——你把纸往后放了，于是有了近大远小，才看到梯形。**如果没有深度信息，你就无法区分"我是把它挤进去的"还是"因为深度把它放下去的"。**这正是后来必须引入真正的三维管线的原因。

#### 差一个平移，就加一个维度

从 2D 到 3D 其实很自然。拉伸、旋转都是线性变换，但平移不是。平移不是也不要紧——你给它加一个维度，变成齐次坐标。

在二维平面上，你没办法用一个 $2 \times 2$ 矩阵让一个点集整体平移，你只能旋转、拉伸。但把它放进三维空间里，给每个点补一个 1 的坐标，就可以：

$$
\begin{pmatrix}
x' \\ y' \\ z' \\ 1
\end{pmatrix}
=
\begin{pmatrix}
\cdot & \cdot & \cdot & t_x \\
\cdot & \cdot & \cdot & t_y \\
\cdot & \cdot & \cdot & t_z \\
0 & 0 & 0 & 1
\end{pmatrix}
\begin{pmatrix}
x \\ y \\ z \\ 1
\end{pmatrix}
$$

最后一行是 $0,0,0$，平移量写在最后一列。乘的时候这一行和最后一列这一项就把前三个分量消掉，只剩下那个 $t$；其余的变换照常写在这个矩阵里。于是三维世界里的一切变换，都变成了"乘一个 $4 \times 4$ 矩阵"。

你要做的只是在三维空间里用 $x,y,z$ 描述顶点、描述面，用前面那种方式描述贴图，再描述光照和各种东西——**总之都是描述**。描述完之后有一个定义好的过程把描述变成你看到的三维世界，比如一个相机的投影，在齐次坐标底下它就是线性的。

甚至可以更极端一点：哪怕没有贴图，你照样能做出 3D 效果。只要做那个 $4 \times 4$ 矩阵的运算就行。我觉得你们上高中的时候自己就能实现一个这样的三维引擎，因为这就是线性代数里的基本知识——什么叫摄像头平移、什么叫摄像头旋转、往哪里平移、往哪里旋转。手上再有几个坦克模型、飞机模型，你真的就能做出一个 3D 游戏。

### 让图形处理器开始编程：shader

最重要的一步在于观念上的转变。

NES 的 PPU 处理的是一个很小的数据结构：一个 `struct Sprite`，64 个，就是一个 `struct`。然后 PPU 执行一段固定的渲染流程，把图形画出来。

但你要画的东西越来越复杂的时候，就会想一件事：**我们能不能不再提供数据结构，而是直接有一个编程语言？**反正都是描述，我用数据结构来描述，和我写一段程序来描述，它帮我编译完之后在我的 GPU 上并行执行——有什么本质上做不到的呢？何况那时候的图形处理器已经越来越复杂，要做矩阵乘法、要处理贴图、要干很多事，它已经非常接近一个通用处理器了，只是并行度比通用处理器更高。

于是就有了着色器，**shader**。这个名字也起得非常有时代特点——它是在图形渲染管线当中被发明出来的东西。

#### 顶点着色器：先改顶点

所谓 vertex shader，是这样的：

一个 Sprite 本来是 `x, y` 加上一些别的信息。vertex shader 就是一个程序 $P$，你可以把它理解成一个 `TVertex`，它接收所有的 vertex——当然有一个匹配过程决定哪些 vertex 归它——然后**允许你修改**这些顶点。程序里就是几条指令，比如给 `this.x` 赋值、给 `this.y` 赋值，也可以改别的信息，比如顶点的颜色。

先用 CPU 构造出一个基础场景，把这个程序（一般是事先写好、经过编译的）烧到 GPU 里。然后显卡每看到一个顶点，就执行一遍这段固定的程序，把这个顶点改掉。

它的 killer application 是什么？因为你可以改顶点的坐标，就能实现顶点非常轻微的扭动。这个轻微的改动可以实现水面的波纹，可以实现毛发的摆动。这些东西本来是要在 CPU 里算的，但你的头发很多、要算的波纹很多，而每个顶点做的又是**完全相同的事情**——那就跟 Mandelbrot set 一模一样了：有一个机器，根据当前这个点在整片水面里的位置，可能再加上上一时刻水面的状态，用波的方程算一算，就跟算 Mandelbrot set 一样。你用 vertex shader 就能改掉这个点的坐标，在**完全不占用 CPU** 的情况下实现水波纹。

#### 像素着色器：给每个像素做后处理

光改顶点可以，那能不能再给每一个像素做一个后处理？于是有了 pixel shader，或者叫 fragment shader。

喜欢摄影的同学应该会立刻理解这件事。你们用相机的专业模式拍出来的那种 raw 格式照片，在屏幕上看是灰蒙蒙的——因为 raw 格式基本上记录的只是传感器上收到的原始光子信息。它有红、绿、蓝三色滤光片，滤完之后你拿到的是三种光子的数量。要把它变成人眼看着舒服的样子，就要做处理。

比如我现在对着你们拍一张，然后编辑这张照片：调整曝光，让整个画面变亮或者变暗——这本质上是**对每一个像素**做同一件事。

顶点处理完之后得到的是像素：$x, y, r, g, b$。注意时序上肯定要等 vertex shader 执行完、顶点都算好了，才会去着色。而在着色之上，我还可以再挂一个程序，它的输入就是 $x, y, r, g, b$。我能做的事比如：

$$r \leftarrow r \times 0.9,\qquad g \leftarrow g \times 0.9,\qquad \ldots$$

会用 Lightroom 调色的同学更熟：你可以做一个蒙版（mask），然后只对蒙版里面对应的像素做调整，写成一段 `if` 判断——在 mask 里就调亮调暗。**你对照片的所有操作都是这样的数值型运算**，不管是拉高亮部还是压暗部，背后都有一个数值公式。这就是 fragment shader 干的事：为每一个像素修改它的颜色值。

#### 法线贴图：不打磨几何体，只骗光

看起来这不就是在做 PS 处理吗？其实不是，它可以干很疯狂的事情。比如**法线贴图**。

设想这里有一面墙——外面那种瓷砖砌的墙。瓷砖是一块一块的，中间有缝，缝是凹下去的，砖是凸出来的。你要精确描述这个几何特征，需要非常非常多的三角形，显卡显然扛不住。

但是你可以骗它。骗法是：给每一个像素一个光反射的**法线**，也就是光打过来之后反射的情况应该是什么样。然后在这个 pixel shader 里，根据这个法线和光照方向的夹角做一次内积（inner product），算出这个点上的光照应该变强还是变弱。

```text
   入射光方向  ----\
                    \  theta
                     \|
   表面法线 n  --------^  亮度 ∝ <光方向, 法线 n>
```

效果差别很大。没有法线贴图的时候，就像把砖墙拍成一张照片、印成一张纸贴在那里，再给这张纸打光，得到的是一张很平面的效果。有了法线之后，**在不增加任何多边形的情况下**，就能有非常真实的打光感：缝和面的法线不一样，受到的光也就不一样，于是有了立体感。

> **易错点**：法线贴图只能骗光。你远看基本不穿帮，凑近了还是穿帮——真凑到瓷砖跟前，你会看到凸出来的部分能遮挡凹进去的部分，而这件事法线反映不出来。所以它适合用在中远景上，帮你省多边形。

#### shader 是一段受限的程序

本质上，你真的可以写一个这样的程序，而且这个程序**甚至就是一个字符串**。你把这个字符串交给一个图形库，说"请你帮我把它编译了，然后作用到每一个 pixel 上"，于是每一个像素的颜色就能被你改一遍。

你们看 OpenGL 的教程，一般第一个教程就是教你画一个三角形，并且让这个三角形上面带渐变的色彩——那个渐变，本质上就是这么呈现出来的。

当然这是一个受限的编程语言。你肯定不能在里面去做操作系统的 system call，那会直接给你一个编译错误，做不到。但你可以做计算、做分支、做条件判断，这些都可以；你甚至可以 load 和 store，去访问贴图上的法线向量这类数据。

### 把科学计算塞进图片里

既然这个程序是我可以控制的，那我是不是可以用它来做通用计算？

大概在 2001 年的时候就有这样一篇论文，我非常建议大家去读一读。他们当时的概念是：用 general-purpose 的 GPU、用可编程的 shader，**把科学计算的问题变成图片处理的问题**。

今天作为计算机科学家去看会觉得这很怪——你直接编程不就完了吗？但他们的做法是：把一个矩阵乘法变成一张图片。如果这个矩阵来自比如天气预报的计算，那张图片看上去就是很随机的、奇奇怪怪的、在图像意义上毫无意义的图片，但它一旦变成了图片，就可以用渲染管线里的 vertex shader、pixel shader 去做计算。

具体怎么变？把矩阵乘法分解成**行列向量外积的和**。内积我们用得多，外积用得少。因为外积对你们来说是很奇怪的操作，它很浪费：我有一行、有一列，做一次外积就得到一个完整的矩阵，而这个矩阵的 rank 是 1——它里面只有这两个向量的信息，我却要为它付出整整一个矩阵的存储和计算。

```text
   矩阵乘法  =  若干"行向量 x 列向量"外积之和
                 |
                 v
       每个外积 -> 一张 .bmp 图片 (rank = 1)
                 |
                 v
       送到显卡上, 图片的叠加用 pixel shader 完成
       (对每个像素做一次加法)
```

但只要能把它变成 .bmp 送到显卡上运行，而显卡又比 CPU 快很多，这件事就可能是有收益的。这篇文章讲的就是怎么把矩阵乘法分解成外积的和：一旦变成外积，所有东西都是图片了，矩阵就是图片，图片显卡就能处理；最后再把几张图片叠加起来，而图片叠加本身也是一个 for each pixel 的相加操作，也能用 pixel shader 做。

于是它真的能实现矩阵乘法。那时候就已经预示了今天我们用显卡这个模型做高性能计算的路子。

### CUDA：两百万个线程怎么养得起

再回顾一下什么是 shader program：**为一大堆同样的东西，执行同一段代码**。

这不就又回到了操作系统课讲并发的第一节课吗？

#### kernel 就是那个 pixel shader

我想干的事是这样的：在 device 上、在我们的显卡上分配一块内存，比如一块 screen。我要画一张 1920×1080 的图，那就分配一个 1920×1080 这么大的数组，为显卡分配这么一块内存。然后我想要显卡帮我干的这件事，就是一个 kernel——它就是一个 pixel shader 程序。

我希望为每一个像素 spawn 一个线程，给这个线程一个参数是 row 和 column，它用 row 和 column 算出一个 f(color)，得到一个颜色，再把这个颜色写到它对应的那个像素上。

```text
   device 内存:  screen[1920 * 1080]
                    ^
                    |  写回
   kernel(pixel shader):
        row, column  --f-->  color  --store--> screen[row*1920+column]
                    ^
                    |  每个像素 spawn 一个线程
   device 上同时活着 1920*1080 ≈ 200 万个线程
```

这当然就是画图。但它当然也是科学计算。如果显卡能给我启动 200 万个足够轻量的线程，那这不就是我想要的并行计算效果吗？我用的是操作系统课第一节课就学过的线程方式，只是我希望这些东西跑在显卡上，内存也在显卡上——**仅此而已**。

于是就有了 CUDA 的 programming model。CUDA 没有什么神奇的。

你们第一次打开一个 CUDA 的 sample、第一次换到 GPU 编程的时候，大概会觉得有点害怕：`__device__` 这种在 C 语言里从没见过的东西，还有那种没见过的语法——一个 `mandelbrot` kernel 后面跟着三个尖括号（C 和 C++ 里都是这样），看起来莫名其妙。但其实一点都不可怕。**你看到的这些东西，就是操作系统课上讲的那个东西**：你只是想创建一大堆线程，这些线程都运行同样的代码。

> **提示**：这里有一个硬性要求——这些线程必须运行同样的代码。所以"每个像素运行同样的代码"这件事，在图形上成立，在 CUDA 里也成立。这就是 CUDA 的 programming model。

#### 能省的只有 PC 和译码器

但如果真的按上一节课讲的轻量化线程去做，代价依然是不能接受的。一个线程就算只花 1KB 的开销，乘以 200 万，这事根本不可能。

所以 CUDA 做了一件事：**它允许你创建非常非常多的线程，但会非常小心地把它们调度到实际的硬件上。**

回想一下一个执行单元里什么东西是省不掉的。ALU 肯定得有，寄存器也必须有——没有寄存器就没办法计算、没办法执行指令。所以当大量 T-worker 被送到执行单元上时，每个 T-worker 都有自己的寄存器。比如我有一堆 T-worker，编号 30、31、32，那么一个执行单元的寄存器里放的是 30 和别的一些东西，另一个放 31，再一个放 32；如果每个像素都要算一个 Mandelbrot set 的颜色，那还会有一个寄存器放最终算出来的 color，也还可以有循环变量 $i$ 之类的。

到这里为止，和 CPU 上把三个线程加载到三个 CPU 上没有区别。但 CPU 的做法是：放出去就各走各的，没有同步，执行完 `T-spawn` 就不管了，要等它结束就去 join。**GPU 不是这样。**

GPU 引入了一个概念叫**线程束，thread warp**。它要把这些线程捆起来。

捆起来之前先想一下：现在只有 ALU 和寄存器，这个程序还是不能执行。还缺一个非常重要的寄存器——**program counter**。只有有了 PC，程序才知道下一条指令执行什么。而对 CPU 来说，PC 在自己的核心里面，这也意味着**每一个 CPU 里都有一个取指令和译码的部件**。译码是要浪费电路的：你们写过 NEMU 的译码逻辑，指令就那 32 个字节，译码完了以后就是一大堆 if-else——这是不是 jump 指令？是不是 load、store？load 的是一个 bit、两个 bit、一个 byte、两个 byte 还是四个 byte？这些信息全部都是一根线，每一根线都要占逻辑门、占触发器。

CUDA 把它们捆起来的意思就是：**这一捆线程不各自拥有 PC，它们共享一个 PC。**

```text
      单个 CPU 上的三个线程            一个 thread warp
   +--------+--------+--------+    +-------------------------+
   |   PC   |   PC   |   PC   |    |   共享的 1 个 PC        |
   +--------+--------+--------+    +-------------------------+
   | 译码器 | 译码器 | 译码器 |    |   共享的 1 份取指/译码  |
   +--------+--------+--------+    +-------------------------+
   |  寄存器|  寄存器|  寄存器|    |  寄存器  寄存器  寄存器   |  <- 省不掉
   +--------+--------+--------+    +-------------------------+
   |  ALU   |  ALU   |  ALU   |    |   ALU    ALU    ALU      |  <- 省不掉
   +--------+--------+--------+    +-------------------------+
```

在现代 NVIDIA 的实现里，一个 thread warp 里是 32 个线程。这 32 个 T-worker 执行一样的代码，共享一个 PC；只有一个 PC，就只需要一个译码单元，电路就省下来了。

> **结论**：绝对省不掉的电路（寄存器、ALU）留着，能省的 PC 和译码器只放一份，这样"交的税"相对于真正参与计算的部分就变得非常非常小。

这就是 CUDA 基本的编程模型，叫**单指令多线程**，single instruction multiple threads：只有一个 PC，但我一次把很多个 T-worker 一起往前执行一步。

#### 单指令多线程：一条指令，32 个线程

神奇的事就在这里发生。

假设把参数是 30、31、32 的这几个 T-worker 放进同一个线程束，然后我假装自己是 CUDA runtime，往前 single step 一步。执行的是最后写入像素的那一步，也就是 `screen[row * 1920 + column]`。

所有线程 PC 相同，执行的动作自然也相同。先把 `row` 载入一个寄存器，或者直接算出 `row * 1920` 写到一个寄存器里。对这几个线程来说 `row` 都是 3，所以 `3 * 1920` 这个临时寄存器的值是一样的。下一步加上 `column`，寄存器的值就不一样了：

```text
   T-worker 30:  temp = 3*1920 + 0
   T-worker 31:  temp = 3*1920 + 1
   T-worker 32:  temp = 3*1920 + 2
        |
        |  下一步依然是完全相同的操作:
        |      store screen[temp], color
        v
   一条 add 之类的指令: 只是寄存器内部的操作, 无所谓
   一条 load/store 指令: 变成了一条非常长、非常连续的访问
```

add 或者 move 这种指令是寄存器内部的操作，没什么。但 load 和 store 变成了一条**非常非常长的、连续的**指令。

而计算机科学家最喜欢的就是"连续"。连续意味着我们可以用好内存控制器的带宽——这不就回到前面讲的 SIMD 了吗？AVX-512 可以一次 load 512 字节的内存到同一个 ZMM 寄存器里，也可以把一个 ZMM 寄存器 store 到 512 字节的内存里。在 SIMT 里，这个效果是**自然而然**就实现了的：32 个线程，每个 4 字节，那就是 $32 \times 4 = 128$ bit 的一次 store；如果存的是 64 位浮点数，那就乘 8，一次 256 bit 的 store。这对内存控制器来说非常友好。

这个计算模型的强大之处在于：**在内存访问连续的时候，它就能获得最佳性能**。哪怕内存不连续，它一样能照做——只是这时候内存要等内存了，没法连续地写，它会先写一部分、再写一部分、再写一部分。每一个 stream processor 都相当于有一个内存控制单元，它和内存控制器交互，一次最多写 32 个地址和对应的数据，然后负责把这件事办完。

#### 一个 SM 手里不止一束线程

实际在 NVIDIA 做的时候，一个 stream multiprocessor 可以管理不止一组 32 个线程的线程束，并且可以在多个线程束之间切换。

为什么需要切换？因为有可能这次 store 打到的是一块全局内存，这次访问不在 cache 里，要等很长时间。为了降低延时，它不是用动态流水线的方式去调度，而是——我手上还有另外 32 个线程，那就把这另外 32 个线程拿来做。它们执行的可能就是从 `4 * 1920 + 0`、`4 * 1920 + 1` 开始算的那一批。

GPU 上的编程模型就是这样，用海量的线程，鼓励你创建 200 万个线程，然后靠 GPU 内部高效的调度把这些线程塞满执行单元。这里面有一点点编译器调度的味道，也有一点 VLIW 那种感觉——这些机制之间是有内在联系的，非常有意思。

### 天下没有免费的并行

当然，这也不是没有代价的。这意味着 **CUDA 程序非常难写**：一旦写得有一点点不好，性能就会爆炸。

就说刚才那个 `row * 1920 + col`。如果是连续的，这一次就能生成一条连续的 store，你拿到最佳性能；稍微改写一下，性能立刻就变得非常差，因为内存访问全部不连续了，内存控制器只能一个字一个字地写，要花非常非常多的时间。

以及，**CUDA 程序里的分支非常讨厌**。

你会立刻有一个疑问：SIMT 怎么实现分支呢？我只有一个 program counter，怎么写 `if A else B`？

答案是：CUDA 的 C 编译出来的所有东西，都是没有这种二选一分支的。它要么用无条件的跳转，要么用循环那种指令。如果你写了 `if A else B`，它会先为这个 if 算一个条件，把条件放到一个寄存器里；然后根据这个寄存器的值，把条件不满足的线程 **disable** 掉。

```text
   if A:  ...     编译后 ->  算 condition, 放进寄存器
                              disable 掉所有 condition 不满足的线程
   else:  ...                -> 线性逻辑
                              enable 回 condition 满足的那些线程
```

所以 `if/else` 就没有了，它变成了一段线性的逻辑。**SIMT 不是没有代价的**，你没有办法随意地去写任何程序。

我甚至给大家准备了一个 Mandelbrot set 的程序，有兴趣的同学可以回去在有 GPU 的地方跑一跑，你会发现它比 CPU 版本快得多。你甚至可以让 AI 直接阅读它为我们生成的、运行在 GPU 上的汇编——你会看到里面完全没有那种 if-else 的 branch。真的可以让 AI 帮你解释一遍这个 SIMT 模型里到底发生了什么。
