### 实验更新，与这个时代的学习方式

#### 让 coding agent 先把框架克隆好

实验须知一上来就是一串不知道在说什么的话，然后告诉你去获取实验框架代码。以前的做法是照着文档一条一条敲命令，而现在你可以直接把实验要求粘贴给一个 coding agent，看它怎么反应。毫无疑问，今天的 AI 是能把这件事搞定的。

有意思的是它的思考过程：它知道要在命令行里执行正确的命令；如果它真的去执行，它不只是把该做的事情做了，还会真的看一眼目录里的文件，检查是不是和实验手册上写的一样。一样的话，它就会给你一个相对肯定的答复——比如说「框架代码已经克隆到了 os2026 的目录」。它甚至会给你额外的提示，说它确实检查了目录结构，并且是正确的；还会问你需不需要查看具体的实验指南来获取实验代码。你可以不停地追问，一直把它追问到帮你完成整个作业。

但我不是很建议大家这么做。我想强调的是另一件事：**在这个时代，更重要的是你能提出一个好问题，或者说你知道自己下一步可以做什么。**

#### 顺手学会的几条 git 命令

举个例子。假设你只知道「老师在某一天更新了代码，我要把这个更新同步到我本地」，但你对 git 一无所知——这其实就够了，你只要知道这件事应该做得到。

我先假装自己有一点知识：我在 oslab 目录里能看到我推送过几次代码，21 号发布之前有几个提交，22 号中午有一个 update test kit 的提交。于是我可以做一件不太常规的事情：我现在有一个叫 main 的分支，我能不能让它往回退一个 commit？即便你有 git 经验，也未必记得精确的命令是哪一个，这时候大语言模型的能力就非常重要——你只要知道这件事是可以做的。

它先查看当前的提交历史，用 git log 看了一眼，确实看到有个分支需要回退，于是给出了正确的命令：git reset --hard。这条命令会把我当前的东西摧毁掉，但没关系，因为这是我新克隆下来的 repo，不会伤到我自己真正的代码，所以我回答 yes。执行完它还会再确认一句「main 分支已经回退一个 commit」，甚至告诉你：如果之后想恢复那个 commit，可以用 git reflog 找到它，再用 git cherry-pick 或者 git reset 恢复。

现在我手上就得到了一个「12 点钟之前的第一天」的 repo。这时我再来模拟你的处境：你不知道该怎么做，你只知道要把更新同步到本地。而日志里已经写着 `your branch is behind origin main by 1 commit`，你看到过这行字。于是当我问它「我该怎么办」的时候，它会耐心解释该做什么——当然我直接让它做了。结果 test kit 确实更新了，远程更新合并到了本地仓库。

就这么短短一点时间，你学会了 git reset、git fetch、git log、git merge 这几条命令。**你脑子里先有一个「这件事能做」的概念，下一次随着用得越来越多，自然就能更好地使用这些现代工具。** 以前操作系统课一直是一门体验很差的课：你是个新手小白，却要完成很多很多事情，被迫看很多文档，而今天文档可以在你需要的那一刻自动出现在你面前，而且是被 AI 消化过的。所以你们更多需要的是拥抱世界的变化，让 AI 放大你们的 self-motivation——你愿意去做点什么的时候，只要往前走一小步，就可以真的做成很多事。

### 上节课留下的缺口：两个进程怎么共享数据

#### 进程、地址空间，以及能对它做的几件事

上节课我们讲了程序和进程，也讲了一组系统调用：fork、execve 和 exit。一个程序运行起来就是一个进程，它有自己的状态，状态里面装着内存和寄存器，它可以**通过系统调用去请求操作系统**。如果我希望我的程序本身能创造出这样的进程，我可以用 fork 做一份状态的完整复制；可以用 execve 把它重置到另一个二进制文件所指定的进程状态上；也可以用 exit 摧毁一个进程。

在进程内部，状态就是内存加寄存器。这里有一个很基础的问题：**如果让一个指针从 0 开始扫过一整个进程的地址空间，哪些东西是可读的？哪些是可写的？我能不能读它、能不能写它？** 我们甚至用游戏修改器演示过——我真的可以读写别的进程的内存。那么对一个进程来说，我就有了 mmap、munmap、mprotect 三个系统调用可以用，还有一个 msync，它可以把一段内存里写进去的数据同步到被映射的文件上，这个等你们用到的时候自然会知道。

其中最重要的是 mmap，因为你可以通过它分配内存：我可以 map 一个十几 GB 的很大内存，而且几乎立刻就可用，不需要等很久。mmap 还可以映射文件，比如把一整个磁盘或者 GPIO 端口映射进我的地址空间。

到这里，其实你已经可以创建一整个应用程序的世界了：fork 能创建一整棵进程树，mmap 能调动系统里各种各样的资源。那么下一个问题来了——如果你要真正写出一个应用程序，比如终端模拟器、浏览器，你免不了要和操作系统里更多的对象打交道，其中第一个就是文件。

> **注意**：我们今天才正式讲文件，尽管你们早就熟悉它了。

#### 个进程算出来的数字，怎么加起来

真正的问题出在进程之间。用 fork、execve 创建出来的两个进程是完全分离的，各管各的——上节课那个能打印出好多好多 hello 的例子就是证据。那它们之间想交换数据怎么办？

设想一个科学计算程序：为了用满机器上的 128 个核，我创建了 128 个进程，每个进程算出一个数字，比如某个区间里的某个值。现在我想把这些数字加起来，怎么加？光靠 fork、execve、exit 这一套是做不到的。你需要在操作系统里**创建出一个新的对象，让父子进程都能访问它**，才可能实现这种共享。

```text
  fork 之后：两个彻底分离的进程

        parent                    child
      [regs|mem]                [regs|mem]
          |                          |
          +--- 谁也看不见谁的数据 ---+

  要交换数据，必须在内核里造一个双方都能访问的对象：

        parent ---+               +--- child
                  |               |
                  v               v
            [ 内核中的共享对象 ]
```

读图：上面是 fork 出来的两个进程各自持有独立的寄存器和内存，中间没有通路；下面是解法——由操作系统在内核里新建一个对象，父子进程都持有对它的访问权，数据才能流动起来。

这就是今天的主题：**操作系统中的对象，以及管理这些对象的 API。**

### 程序员想要什么，操作系统就给什么

我们一直说，操作系统是给开发者提供服务的。你们写过大作业：写算法，把一个数据结构变成另一个数据结构，把一种数字、图这样的结构变成结论性的东西；做 AI 可能要算棋盘、做状态空间搜索。但除此之外，你还希望**调用一个库函数，去完成一个不是计算类型的任务**——而这些任务大部分背后都有一个操作系统。

你想发一个网络请求。我有一次让 coding agent 去读 POSIX 手册，问它命令行参数的规范是什么样的；你要读一个网络上的东西，这件事确实是要交给别人——一个库函数和操作系统一起做的。你想写入一个文件。你想和别的进程通信。这些事情的本质都是**去访问操作系统里面的对象**。

关键在于，程序员脑袋里想的和系统调用长得完全不一样。如果我要实现一个游戏修改器，我想的**不是** `fd = open(...)` 这一套，虽然你们在计算机系统基础课上已经见过 `fd = open`。我想的是一个更面向对象、更抽象的界面：用 Python 的 pathlib 把 `/proc/1234/maps` 当文本读出来，这是我想做的事情。甚至我想的是一个更舒服的接口，叫 `get_memory_map(pid)`——它返回一个数据结构给我，我就知道每一段内存从哪开始、到哪结束、访问权限是什么；我想要 `read_process_memory`，给我一个 pid、一个地址、一个 buffer、一个 size，你把那段内存读给我。

而操作系统设计者脑袋里想的是：**任何应用程序开发者想做的事情都是对的。** 操作系统是一个通用机制，它存在的意义是让应用生态繁荣发展起来。最早的 Unix 里甚至没有网络功能，直到后来有了套接字；一开始没有这些功能的时候，操作系统的设计者会一点一点把这些 API 加进去。他脑子里想的就是提供一套简单、稳定、通用的 API，也就是一个抽象层。

> **结论**：操作系统设计者设计什么样的 API，就是为了满足程序员脑子里想做的事——这是一个非常重要的 first principle。

#### 复用文件和目录的 API：/proc 这条路

这套 API 可以是完全迎合程序员的，比如我真的提供一个叫 `get_memory_map` 的系统调用。也可以是另一套不太一样的机制：在 Unix/Linux 世界里，我有一个 `/proc`，把进程相关的信息**以文件的形式**放在里面，这样我就不需要专门提供额外的系统调用 API，而是复用文件和目录的 API——我有 open、read、write；目录也是 open 打开，然后用 read directory entry 扫出目录项。**复用本来已经实现好的 API**，开发者就能访问操作系统对象，从而做出 `get_memory_map`、`read_process_memory` 这类东西。在 Linux 里，这三件事用的就是同一套 API。

但这不代表别的操作系统也这么实现。`pmap 7583` 可以打印出进程地址空间映射的样子，可它背后是以文本文件的形式打开 `/proc/7583/maps`，把这个 maps 文本解析一遍，再加工成输出的样子。这其实很浪费：这些信息在内核里本来就是一个数据结构，为了实现成 procfs，它要先把这个数据结构序列化成文本；pmap 读出来之后又要做一次文本解析。数据结构就在内核里，如果能直接搬出来，就可以用更少的时间、浪费更少的计算，操作系统的性能不就更高了吗？

#### Windows 走的另一条路

Windows 是一个在软件工程意义上设计得非常好的产品。它的理念是**开发者要什么我就给什么**：要创建文件，有 CreateFile；要写，有 WriteFile；要移动文件指针，有 SetFilePointer。要访问另一个进程，Windows 也有一个 API 叫 OpenProcess。这些 API 调用直接把参数传递给 Windows 内核，所以像 OpenProcess、ReadProcessMemory，以及查询进程地址空间的 VirtualQueryEx，都能非常高效地实现——比从 procfs 里以文本形式读出来再解析要高效。

```text
  Linux /proc 路线                     Windows 路线

  kernel 数据结构                      kernel 数据结构
        |                                    |
   [序列化成文本]                        [直接把参数
        v                                 /数据交给内核]
  /proc/<pid>/maps                             |
        |                                      v
   pmap 读入并解析文本                     用户态拿到结构体
        |                                      |
        v                                      v
     人类可读输出                        直接就是可用字段

  代价：两次表示转换 + 一次文本解析        代价：接口由设计者预先定义
```

读图：左边是为了「一切皆文件」付出的转换成本——内核数据结构先序列化成文本，用户态工具再解析回信息；右边是 Windows 的做法，内核按 API 契约直接填充用户态要的结构体，中间没有文本这一层。

不过 Linux 选了这条路之后，带来了今天要讲的 Unix Philosophy 这一系列很有意思的化学反应。而且在大语言模型的时代，到底谁好谁坏又不好说了——所以我觉得世界很有意思，它一直在变化。

#### O_CREAT：为一个字节留下的历史

看 Unix 的做法会更明白它的气质。Linux 把各种 flags 都塞在 open 里面：可以以 append 的方式打开、以追加写入的方式打开，可以以 asynchronous 的方式打开，还有好多好多。如果你想要文件不存在的时候创建文件，还要用 `O_CREAT`——这名字看着就奇怪，因为它是 create 的拼写错误。

> **提示**：这是 Unix 的历史遗留。当年 Ken Thompson 设计时为了省一个字符、一个字节，觉得「没关系，就省了吧」。等后来字节不值钱了，他发现自己犯了个很大的错误，可这个错误已经改不掉了——最早的系统这么定下，后面的实现为了兼容就一直沿用了这个错误的拼写。做系统的人会经常遇到这种事：接口一旦发出去，就再也收不回来了。

### 一切皆文件

#### 文件是有名字的数据对象

Unix 做了一件大事，叫 **everything is a file**。那先想清楚：什么是文件？

你对文件的第一次认识来自小学的电脑课——桌面上有个东西，双击鼠标打开它，那就是文件。现在你接触过很多文件了，能接受的、归纳出来的定义是：**文件是一个有名字的数据对象。** 你日常电脑里的那些东西——README.md、lab.c、.png——都是这个意思。你可以用 API 打开它，用 fwrite、fread，或者用 cin、cout、fin、fout 去读写。它的模型就是**一个字节序列**。

#### 字节序列为什么足够普适

字节序列在计算机世界里是一个极其普适的抽象。计算机无非就是代码和数据——冯·诺依曼结构里最重要的两个东西——而数据用一个字节序列几乎可以表示任何东西：

- 它可以表示一个数据流。你在键盘上每按下一个键就产生新数据，这就是一个 append-only 的 list；
- 它可以表示一个数组。图片、一个 JSON 数据结构，都可以变成一个数组；
- 它可以是网络上传来的东西。浏览器下载任何一个页面时，页面都是一个字节一个字节发给你的。当然前面会有一段你看不见的头部信息，浏览器帮你藏起来了；头部会告诉你这是哪个 URL、内容有多长，然后跟一个空行，空行之后开始送正文——整套流程完全符合字节序列这个抽象。

再比如你连到系统的打印机、你的终端、你的显卡，为什么这些也是字节序列？我会到讲设备驱动的时候再回答。甚至一把锁、一个可以互相传递数据的管道，它们都可以假装自己是文件。

> **结论**：如果所有东西都是文件，那我们就能用同一套工具处理它们。Unix 世界里有 cat、wc 这些工具，我只要有一套处理文件的工具，就能处理世界上的任何对象。这就是 Unix 的设计选择：**把操作系统里的对象直接暴露出来，再给你一组工具，让你用工具组合的方式去管理这些对象。**

#### 谁在用它：黑客与软件开发者

Windows 的设计不是给黑客用的，是给软件开发者用的。你清楚地看到，Windows 的用户不直接操作系统里各种各样的对象——他不会打开一个 terminal，说「把某个东西删掉」，也不会说「我要看一下我的 CLAUDE.md 有多少行」。顺便解释一件你们可能好奇的事：我的 agent 输出总是中文，是因为我这里有一个 CLAUDE.md；但 Windows 并不预期它的用户会做这件事。

所以在 Windows 那里，所有用户都被当成程序员，于是它提供一套非常符合软件工程规范、而且高效的接口。而 Unix 的用户是黑客，黑客会写前面那种命令，所以它需要一个好办法，把操作系统对象以简单舒服的方式暴露给所有用户，并且能够复用那些小的命令行工具。

Unix 最后再把文件放进目录里，一层一层套起来，于是**每一个操作系统对象都有一个名字**。前几年我带着大家极限速通操作系统实验的时候，要自己实现文件系统，我就直接用一个「从路径名到字节序列的映射」来实现——这完全可以。整个文件系统就是一个文件的集合，每个文件有它带路径的名字，我再从这里面模拟出当前目录是什么、路径怎么解析。本质上每个文件就是一个带名字的对象。Windows 让你看见的带名字对象，基本只有你实际看到的那些；Unix 选择把操作系统内部的所有信息也以某种文件的形式暴露给你，区别就这么大。

### 文件系统能装下任何信息系统

#### 一个没有数据库的在线评测系统

**文件系统是一个非常好用的抽象，它可以用来构建任何信息系统。** 拿我们的课程网站举个例子。现在提交还没开，你 make submit 会看到 `not open yet`——顺便说，有 hacking 精神的同学去看那个脚本会发现我直接复用了去年的脚本，里面就是 echo 打印一句 not open yet 然后 exit，真正的提交代码还在下面，理论上你直接执行下面那段就能交上来，但我不确定服务器上的配置做对了没有。

看我后台：有一个叫 file received 的目录，里面有 OS2025，每个同学的提交就以目录的形式放在正确的目录里，比如 M1，里面有很多同学，包括蹭课的。提交是这样工作的：你的代码在本地打包成一个压缩包，送到我网页的后端，后端代码执行一个类似 pathlib 的操作，往某个目录里的某个地方写一个文件。**我写的文件名就是日期**——2025 年 4 月 24 号提交的，就放一个这个名字。我假设你一秒钟内不会交两次，实际上我确实有个检查：交得太多可能被拒；就算真的一秒交两次且都成功了，也就是把上一次覆盖掉，无非是历史提交记录少了一条。

```text
  同学本地打包
        |
        v
  网页后端：把压缩包写到提交目录
        |
        v
  file_received/OS2025/M1/<日期>        <-- 文件名就是提交时间戳
        |
   online judge 不断 watch 这个目录
        |
        v
  <日期>.result                          <-- 评测完把结果写回来
        |
        v
  想 rejudge：find 出来把 result 删掉，judge 就会重新扫到它
```

读图：整条流水线没有数据库，只有目录和文件——提交是文件，结果是文件，而「谁还没评测」这件事根本不需要额外记录，因为**没有 result 的提交就是要重评的提交**。

后台的 online judge 会不断 watch 这个目录，直到把你的程序评测完，然后生成一个这样的 result 文件贴上去。

#### 它的弱点，以及接下来可以怎么玩

你们肯定要问：为什么不用数据库？作为一个码农，要构建这样的信息系统，第一反应就是建一个数据库。我不建数据库的原因是：**一旦用了数据库，想 hack 它就变得前所未有的困难。**

每一个 hack 我都要么为它实现一个工具——比如在网页上再做一个管理端。你们看教务系统是怎么膨胀的：你们在一号上面申请各种东西，用得很烦躁，我用得也很烦躁，因为它把数据强行做了一层封装，你必须用它封装好的接口才能访问。而对我来说，想删掉一份提交，直接把它删掉就行了，一秒钟的事，提交就没了。

想 rejudge 呢？比如我想 rejudge 所有的 M1。我可以直接用 Unix 里的所有工具，因为这就是文件——我不需要去写一个 online judge 后台的 rejudge 功能。我不知道你们有没有同学开发过或者搭过开源 online judge，那种后台有一堆功能：rejudge 这道题、rejudge 某一段时间内的提交。我不需要，我只要一个 find，把这些文件全部删掉（2025 年的我已经备份过了），删完就只剩提交、没有 result 了；后台扫到没有 result 的提交就会拿过去评，过一段时间又有一个 result 贴上来。

甚至我想给每个人的提交记录写一段 AI 点评：如果这东西存在数据库里，我就又要额外做一层信息；虽然做到是能做到，数据库性能也确实比我这个高得多，但如果只是想在每个结果文件里填一个域，那对我来说太容易了——开一个 Claude Code 让它自己把它评完，这事就解决了。所以**只要蹭课的人没有多到我的服务器扛不住，用文件系统就是一个完全 OK 的选择，因为我随时可以 hack 它。**

当然它有代价：

> **易错点**：文件系统没有很强的一致性保证。如果你要写三个文件，写到第二个的时候程序 crash 了，系统就进入了一个不一致的、不正确的状态，文件系统本身不提供这个保证。我这里是拿人力在赌——赌 99.9999999% 的情况下服务器运行过程中不会出现这种事；真出现了，也就一两条命令把那个提交删掉。我用它换来的是方便。在开发软件的时候，用文件系统是绝对正确的选择。

更有意思的是这条路接下来可以怎么走。现在有大模型、有 coding agent 了，我先用文件系统实现这个 online judge 或者任何一个信息系统——比如一个社交网络——再让大模型帮我把它翻译成带数据库的实现，或者翻译成云上 serverless 的实现。这样我就有了一个性能很低但正确的参考实现：我可以不断地测试它，两个版本互相交叉检查，就像你们在 PA 里做 differential testing 一样。用我的「笨」实现和一个很好的实现做 cross checking，然后我就可以无缝地从一个几千行的新系统，一路做到 planet-scale。我觉得这件事完全可以做成。

所以虽然数据库、serverless 这些技术看起来很 fancy，但当你要回头思考「我到底要构建什么、解决什么问题」的时候，回到文件系统上，Unix 会给你很多启发。

### 文件系统里到底有什么

#### 标准目录结构

文件系统里有哪些东西，是有标准规定的，叫 **FHS（Filesystem Hierarchy Standard）**，有兴趣的同学可以让 AI 帮你读一读。你看到的每一个 Linux，`ls /` 出来的内容都差不多：有 home、dev、boot、usr、sys……

```text
  /
  ├── home      用户的家目录
  ├── dev       设备
  ├── boot      启动相关
  ├── usr       用户程序与数据（user）
  ├── sys       虚拟文件系统：设备与内核信息
  ├── proc      虚拟文件系统：进程与内核的信息
  └── srv       服务数据
```

读图：这是一棵标准的 Linux 根目录树，几乎每个 Linux 都遵循这套布局，所以你在一台机器上学到的知识可以直接搬到另一台上用。

大部分系统遵循它，但也不是全部，甚至有的非常不遵循，比如 macOS。有统一标准的好处是：你在一个系统上获得的知识，在另一个系统上也找得到对应的文件。

#### 隔离知识这件事变了

以前我们刚开始教计算机系统基础的时候，你们第一次接触 Linux，这个文件系统的结构让我们教得很头疼，因为很细碎。我说你去看手册吧，又不太好；我说你去读本书吧，就有一本《鸟哥的 Linux 私房菜》之类的——你去图书馆一借，发现那么厚，直接就崩溃了。它没办法像 AI 那样，精准地从海量知识里隔离出你真正需要的那一点。以前**隔离知识是你们自己要做的事情**，你只能从图书馆借到书、在搜索引擎里找到博客，这是你唯一能做的。

现在你不用自己隔离了：你不知道 proc 是什么，它会告诉你这是一个虚拟文件系统，里面是进程和内核的信息；srv 是服务数据；sys 也是一个虚拟文件系统；你有没有好奇过 usr 是什么？它是 user，用户程序和数据。反正你对哪个感兴趣就问哪个。

### Unix philosophy：小工具、组合、文本

#### 三条准则

在这样一个很大的文件系统上，everything is a file，我们可以在文件系统里构建任何东西，之后 Unix philosophy 的真正力量就体现出来了。它叫 **KISS principle——keep it simple, stupid**，主要有三个要点：

1. **每一个工具只做一件事，而且把它做好**。像 grep、sed、awk 这些命令行工具。
2. **让这些工具能够 work together**，组合起来用。
3. **把文本流当作通用接口**（handle text stream as a universal interface）。

第三条是非常具有前瞻性的设计。

#### 文本接口：机器读得懂，人也读得懂

文本接口的好处是什么？**人类可以理解，机器也可以理解。** 就拿 `/proc/10718/maps` 来说：你作为一个对 Unix 有理解的 power user，看到这段文本就知道「哦，这里有这个，这里有那个」。而不像 Windows 那样返回一个数据结构给你——结构体里有些是字符串、有些是指针、有些是十六进制数，你还得再找别的东西去解析它。

> **定义**：文本接口，就是操作系统对象以文本流的形式暴露出来，所有工具都读写文本流，于是**任何一个工具的输出都能成为另一个工具的输入**。

所有的文本接口都意味着它既是机器可读的，也是人类可读的，代价是不要那么高的性能。在 1970 年代敢于做这样的 trade-off 是个非常勇敢的决定，因为那个时候计算机的每一个时钟周期都还是很贵的。当然你永远可以在 Windows 的 API 上再接一个工具翻译成文本接口，也有这样的实现——以前我们想在 Windows 上得到一个 Unix 世界，有个工具叫 Cygwin，不过现在它已经死掉了。

更进一步：在 Unix 里，你可以用文本接口访问所有工具的输出，以及访问几乎所有文件——除了确实有些设备本来就是二进制的。

而且它甚至撞上了今天这个时代。当年设计者当然没想到有一天会有大语言模型，而**文本恰好是大语言模型最适合处理的东西**。像 Claude Code 这样的 coding agent，就是在一个自然语言预训练得到的模型基础上微调成的 coding agent：它能理解命令行工具的输出，也能写出很多命令行工具。你看它在运行的时候不停地 bash、bash、bash，每一个 bash 里面都组合了好几个命令行小工具。**当它学会写命令行工具的时候，命令行工具本身也像是一种自然语言。**

#### 一条像自然语言的命令

我课上有一个例子。在 shell 里用通配符，就能找到 `/proc` 下所有进程的状态文件，在这些文件里找 VmRSS 这个 field，我就可以用非常 quick and dirty 的方式拿到进程占用的物理内存；再把这个命令的输出管道给另一个命令，就能求出所有进程 VmRSS 的和。

```text
  /proc/*/status      --通配符展开-->   所有进程的状态文本
        |
     grep VmRSS
        |
        v
  一串 "VmRSS: 12345 kB"
        |
      管道 | 交给下一个命令求和
        |
        v
  整个系统所有进程占用的物理内存总和
```

读图：一条命令里只有「找一个字段」和「求和」两件小事，是通配符、grep 和管道把它们拼成了一个自然语言式的句子。这个命令我是用 bash 写的，fish 不支持这种语法。

执行之后，我找到了系统里所有进程物理内存的总和，是两千多 GB。我甚至可以让它继续和其他命令组合，比如用 free 看系统里剩余的内存——以前我们会花很多时间讲 free 的格式是什么、每一项是什么意思，现在不需要了，AI 能帮你理解系统里有多少内存。它还调用了一个让我有点出乎意料的命令：直接读 `/proc/meminfo`。**这就是文本接口的好处——原来 free 的数据就是从这里来的。**

我觉得这套东西理想的形态是一个脑机接口：你在脑袋里自动产生「我想干什么」，下一秒它就替你执行完，结果再用脑机接口送进你脑子——想想也是有点可怕的事。

总结一下：我们的系统里有很多很多对象，不管是进程的状态、进程的内存，还是整个系统的状态，它们都变成了文件；而你平时接触的 .c、.md 这些东西也都是文件。于是 everything is a file，你可以通过一套统一的命令行工具来处理它们。其中**最神奇的是管道**——把一个程序的输出粘贴给另一个程序作为输入。这实现了命令行工具与数据的组合和复用，所以它找到了一个非常好的自然语言和编程语言之间的平衡点。

### 文本接口的代价

#### 空格、Makefile，以及 quick and dirty

有一本小册子很有意思，叫 **The UNIX-HATERS Handbook**——讨厌 Unix 的人吐槽 Unix 的地方。它的吐槽都是真的：Windows 给你的接口非常结构化、非常规整，在软件工程意义上就是设计得好；而 Unix 给你的是文本接口，文本接口就意味着你需要解析它，解析的时候就会有各种各样的问题。

最典型的是空格。用 Windows 的时候，文件名里有空格不是很大的问题；但凡是使用过 Unix/Linux 的人都有一种非常强烈的倾向：**不在文件名里引入任何空格**，要分隔就用减号。因为空格会给很多命令行工具带来麻烦：字符串里有空格，你就必须用引号括起来，否则粘贴到 shell 里就会被拆成两个参数，再传给命令行工具就不对了。Makefile 至今都不能很好地处理空格，GNU 的 make、legacy 的 make 都不行，你还得在上面再叠一层别的东西去解决它。

> **提示**：The UNIX-HATERS Handbook 里吐槽的那些诡异行为，都是因为它是一个 quick and dirty 的 hack——它要的是让 hacker 快速写出一个「大致正确」的命令，在自己的工作流里把事情办完，而不是让每一处细节都规整漂亮。

我试着打开那本 Handbook 的页面时还被拒绝了访问。总之你可以自己去找来看。

#### 脚本语言会走向历史吗

我觉得这套设计今天也多多少少已经完成了它的历史使命——它成了大语言模型的语料。GitHub 上写的那么多代码也都成了语料，然后码农们就把自己给干掉了。

在生成式 AI 时代，**脚本语言肯定会成为历史**。因为 UNIX-HATERS Handbook 里吐槽的很多 Unix 诡异行为，都是因为它是一个 quick and dirty 的 hack。如果我们的大语言模型可以写 strongly typed 的 Python 或者 Rust 代码，它就完全不需要用这种方式：它生成 token 如果够快、够好、够准，完全可以写一个真正好的 parser 把内容解析出来，甚至可以**直接调用一个 API，从内核里拿到绝对准确的数据，再翻译成我想要的任何形态**。

但工具的组合和数据的复用，对我们来说是很有启发性的。而且在大语言模型流行的时代，这是一个更友好的方向：**everything is a text，everything is a file，对语言模型来说更亲切。**

### 回到内核：一次 putchar 就是一次文件写入

现在我们来看操作系统到底给了我们什么样的 API 去访问它里面的对象。先看一眼我的 CrazyOS。CrazyOS 是一个操作系统，它有两个进程，进程可以执行一个叫 putchar 的系统调用。这个 putchar 在操作系统里实现出来，就是一段很平常的代码：它把字符放进每一个进程的一个 buffer 里——这个进程有一个缓冲区，缓冲区有一个长度。

这不就是一个**打开的文件**吗？你们想想 everything is a file：如果我们的应用程序可以执行 putchar，这个 putchar 是不是就是向一个 default file 里面写了一个字符？所以这其实就是操作系统内部对文件的实现。文件如果在操作系统内部有一段内存或者一个缓存，它就是一个 buffer；这个 buffer 有一个长度，甚至有一个指针指向它现在写到哪儿了。

```text
  struct file {            /* 内核里一个“被打开”的文件 */
      char  *buf;          /* 缓冲区 */
      size_t length;       /* 这个文件有多长 */
      size_t pos;          /* 现在写到哪儿了 */
  };

  进程执行 putchar(c)：
      f->buf[f->pos] = c;      /* 把字符写进当前位置 */
      f->pos  = f->pos + 1;    /* 指针往后挪一格 */
      f->length = f->pos;      /* 长度跟着更新 */
```

读图：所谓「写一个字符到文件」，在内核看来就是往一块 buffer 的当前位置填一个字节，然后把写指针往后推、把长度更新——CrazyOS 里 putchar 的实现和操作系统里文件对象的表示，其实是同一件事。

在 CrazyOS 里就是这样实现的，而这就是操作系统实现文件的方式。你好比是看 libc 里面的 `struct FILE`，你们都见过。

## 文件描述符：进程伸向操作系统对象的那只手
> 对应块：BLK14 | 覆盖分集：P07下 | 块标题（分集名）：《访问操作系统对象；文件描述符（下）》

内核里要表示一个「打开的文件」，其实没什么花哨的东西：C 标准库里有 `struct FILE`，你把这个 `struct FILE` 直接嵌进进程的 `struct proc`，文件这件事就实现了一大半。

站在用户这一侧看，everything is a file 说的无非是这么一件事：`/home` 底下某个目录里的 `a.md`、某个 `README`，乃至 `/proc/1/maps` 这种看上去完全不像文件的东西，全都是操作系统里的对象，每一个对象都映射到一段字节序列，或者一段可以访问的字节。它们是同一类东西。既然它们是同一类东西，而 C 里打开一个文件用的是 `fopen`、拿到的是 `struct FILE`，那么让进程访问其中某一个，做法就顺理成章了：

```text
  进程 P1（struct proc）           内核里打开的文件
  +------------------+
  | ...              |
  | ofiles[0] ------ |----> struct FILE ---> /dev/pts/4
  | ofiles[1] ------ |----> struct FILE ---> /dev/pts/4
  | ofiles[2] ------ |----> struct FILE ---> /dev/pts/4
  | ofiles[3] ------ |----> struct FILE ---> log.txt
  +------------------+
       （offset 记在 FILE 里，表示"我写到哪了"）
```

每个 `struct FILE` 里放一个指针指向真正的文件对象，再放一个 offset 记住自己写到哪个位置了——这和我实现 CrazyOS 时的做法完全一致。注意这张图里进程一侧是「编号」，内核一侧是「结构体」，这个错位正是后面所有麻烦和所有设计的源头。

### 先有系统调用，才有 C 的那套 API

在这套结构之上，操作系统自然会往外提供一组 API：`open`、`close`、`read`、`write`、`lseek`，还有 duplicate。

- `open` 相当于在进程里新分配一个 `struct FILE`（或者说 `FILE *`）。这个结构体在内核里是要占内存的：open 哪一个文件，就有一个指针指向那个文件对象。
- `close` 就是把这个结构体丢掉，我不再需要指向这个文件了。
- `read` / `write` 就是我前面 `putchar` 那套动作：手里有一个指针或者一个 offset 指向当前位置，写一个字节，offset 往后挪一格，再写一个，再挪一格。
- `lseek` 的全名是 reposition read/write file offset，就是重新摆放读写位置。既然 offset 代表的是「在字节序列里的第几个字节」，那我当然可以给它加多少、减多少，可以设成 0，也可以设成 -1（你们在 Python 里本来就习惯用负数下标）。C 里给了三个宏选起点：`SEEK_SET` 从头算、`SEEK_CUR` 从当前位置算、`SEEK_END` 从尾巴算。
- duplicate 是再创建一个新的 `FILE`，指向同一个文件。这些动作全都发生在操作系统内部。

这里有个先有鸡还是先有蛋的问题值得点破：`fopen`、`fread` 这些，实际上是对 Unix 最早那套设计的封装——先有了系统调用，才有 C 标准库的那一层 API。你们是先学的 C 的 API，所以反过来讲也完全没问题，但别把这层包装当成本体。

> **提示**：`struct FILE`、`fopen` 属于用户态 libc 的抽象，是后来加的一层；底层真正干活的是那几个系统调用。后面讲到 libc 时会回来细说这层封装做了什么。

### 应用程序拿不到那个指针，于是有了文件描述符

但这些都是发生在操作系统内部的事。我们在应用程序里——在 C 的世界里，甚至在汇编的世界里——怎么去访问内核里那个 `struct proc`、那 64 个 `struct FILE` 呢？

在内核代码里，我可以直接拿一个指针指向 `ofiles` 数组的第 0 个、第 1 个、第 2 个。**你在应用程序里是获得不了这个指针的。**

这就是 Unix 里文件描述符的由来。想清楚这一点，先看一个程序到底是什么：一个 C 程序只有内存和寄存器，也就是你们的 `int main` 里能干的那些事——定义一个 `int x` 或者全局变量 `int g`，用 load / store 指令去读写，甚至可以取 `main` 的地址把那个地址读出来（上节讲地址空间的时候我们干过这件事）。但它还有另外一种「地址空间」，里面是 0、1、2 这样的编号，每个编号指向一个已经打开的文件。它不能通过 pointer dereference 去访问，必须通过系统调用才能访问。这就是文件描述符。

```text
  应用程序看得见的"编号"                内核里打开的文件
  fd 0  -----------------------------> 标准输入
  fd 1  -----------------------------> 标准输出
  fd 2  -----------------------------> 标准错误输出
  fd 3  -----------------------------> open("log.txt") 新建的 FILE
  （只能靠系统调用指定，不能解引用）
```

其实你们早就用过它了。最早讲 minimal 的时候，那个最小的二进制文件向终端输出字符，用的是 `write` 系统调用，而 `write` 的第一个参数就是文件描述符：

```text
write(1, buf, size);
```

往「编号为 1 的地方」写一段 buf。这个 1 指的就是上面那个空间里的 1。它让你想到 x86 里做 I/O 的做法：你得先指定一个 I/O 端口，再往端口里写数据，数据才能从计算机送到外部设备上。进程同样不能直接解引用这个 1，但它可以在系统调用里指定它。你 `read` 0，操作系统就知道你是要从 0 号对应的那个文件读。

也可以完全不把它想成地址空间，就把它想成一个整数：

> **定义**：文件描述符（file descriptor）是应用程序用来访问操作系统对象的编号。它是一个指向操作系统对象的间接指针，以 0、1、2 这样的整数编号；编号究竟指向哪一个文件对象，由操作系统负责解读。

因为 Unix 的设计是 everything is a file，所以所谓的 file descriptor 其实是 everything descriptor——file 等于 everything，那它就是 everything descriptor。这个名字在我看来有一点点 misleading，但没办法，这是历史的沿革。你记住 everything is a file，它是 everything descriptor，是一个指向操作系统对象的指针，就够了。

### 编号从 3 开始，而且永远挑最小的空位

`open` 会怎样分配编号？假设 0、1、2 已经分配掉了，我现在拿 `open` 打开一个 `a.txt`，内核就会**从 3 开始**，也就是挑一个最小的、还没有被分配过的编号，让它指向你打开的那个文件。所以 `open` 实际改变的是这个编号空间里 3 号指向的对象。

这个空间有多大？大部分时候你只会用到 0、1、2，甚至一个 `wc`、一个 `grep` 在命令行里组合起来的时候你压根不会再打开文件。但只要你提出这个问题，它就是可以解答的——而且答案马上就能验证。我写了一个 `try_open` 做示范：

```c
int try_open(const char *path) {
    int fd = open(path, O_RDWR);   /* 以可读可写的方式打开 */
    if (fd < 0) {
        perror(path);              /* 打开失败，打印原因 */
    }
    return fd;
}
```

可读可写地打开文件，然后检查返回值。因为这个编号空间是从 0 开始的，返回 `-1` 就说明打开失败了（小于 0 都不正常），这时候用 `perror` 把失败原因打出来。全部打开都失败、一个文件都没有，也是常见的结果：比如去开 `/dev/sda` 会失败，因为我这台是树莓派，它上面是一张 SD 卡，设备名是 `mmcblk`；你们机器上可能是 `sda`，也可能是 NVMe 那种更快的闪存，把文件名换一下就行。

试图打开一个不存在的文件，它会返回 -1，并告诉你 No such file or directory——这条信息你们会经常见到。甚至你把系统的语言设置改一下，能看到这句话变成中文的。

> **提示**：`perror` 会按当前的语言设置输出错误信息，所以系统调用或库函数失败时，它能把原因用人话打出来。这个功能后面讲 libc 的时候会回来讲。

关于分配规则，有一点要记牢：**关掉以后，它总是从最小的编号开始重新分配。**你 0、1、2 分别给了标准输入、标准输出、标准错误，再打开文件就是 3、4、5；关掉 3 再打开，拿回来的还是 3。写几行示例代码就能证明。

### 换个名字：Windows 的 handle，也就是「把柄」

Windows 里这个东西有另外一个名字，叫 handle。

门上面那个把手叫 handle，锅的把手也叫 handle，你们有谁见过特斯拉那个车门？第一次见到那车门的时候人是崩溃的——你看到一个 handle，而 handle 是干什么用的？是给你一个权限、赋予你控制那个东西的：我拽上那个门的 handle，我就控制了这个门；我抓上车的把手，我就控制了车门。所以我觉得更合适的词是把柄：**我抓到你的把柄，我就可以让你做任何事。**文件描述符也是这个意思，我持有一个编号为 1 的句柄，我就能对 1 号文件做 `read`、`write`。

在 Windows 里面按 `Ctrl+Shift+Esc` 进任务管理器，切到「详细」那一版，里面有一列就叫句柄。Windows 里也有一个 handle 类型，你调 `OpenProcess`，它返回的就是一个 handle。

「句柄」这个中文词是怎么来的？它和 handle 好像完全扯不上关系。这是沿用下来的一次错误翻译：以前有一本讲编译的书，里面讲一个 sentence handle，一个句子的柄、一个句子的把柄，被误译并且一直沿用了下来，后来又被 Windows 的官方翻译采用，就变成了奇怪的「句柄」。知道这段来历，你反而更容易记住：文件描述符、句柄，说的都是指向操作系统对象的指针。

两者的差别在于信息放在哪：

| 维度 | Unix 的文件描述符 | Windows 的 handle |
| :--- | :--- | :--- |
| 形态 | 从 0 开始的整数编号 | 一个 handle 值 |
| 对象编号 | 编号本身 | 包含在 handle 里 |
| 权限信息 | 主要留在操作系统内部，要用额外系统调用去查（比如查这个 fd 到底可读还是可写） | 权限等信息一起放在 handle 里 |
| 更像什么 | 指向对象的一个编号 | 一个带权限的指针 |

Windows 的设计更像一个「指向操作系统的指针」，你拿到的这个 handle 里不只是对象编号，还带着权限等等信息。

### fork 之后，这个 offset 到底归谁

到这里的内容，你们在计算机系统基础课上其实都比较熟悉了。但在操作系统课上要告诉大家的是：**看起来简单的设计，放到真实的操作系统里，会带来不小的麻烦。**

比如文件就是一个字节数组，我打开 `log.txt`，它拿到 3 号描述符：

```c
write(3, "1", 1);
write(3, "2", 1);
```

会先写下一个 1，再写下一个 2，文件里得到 `12`。要写 `hello`、`world`，就得到 `helloworld`。这就是顺序写，谁都清楚。内核里也真的就是一块内存：`struct FILE` 里有一个 buff 指向它，有一个 offset 记着位置；`write` 的时候按 3 号找到那个打开的文件，写一个字节，offset 往后加一，下次就写在后一个位置。

麻烦出在 `fork`。

`fork` 是把整个进程完整拷贝一份：内存和寄存器完全相同，唯一不同的是那个返回值寄存器——父进程拿到子进程的 PID，子进程拿到 0。除此之外，在用户态、在进程自己看来没有任何区别。

那么在操作系统里就有两个进程了。现在假设我程序是这样：先写一个 1，然后 `fork`，然后两个进程都要写 2。这看起来是一个顺序的程序，先做这个再做 fork，可 fork 完了以后世界上就有两个一模一样的进程，我甚至不区分谁是父亲谁是孩子，它们都要往这个文件里写一个字符。**它们应该覆盖，还是应该写两个 2？程序跑完，你应该看到一个 2 还是两个 2？**

这件事其实是操作系统设计者的自由：

- 复制进程的时候把这个 `struct FILE` 也拷一份，offset 也拷一份，两个 offset 各写各的——那你只看到一个 2；
- 只做一次浅拷贝：让第二个进程的 3 号指向同一个 `struct FILE`，两个指针指向同一个 offset。第一个进程写 2、offset 往后移一格，第二个进程再写时又往后移一格——那你就看到两个 2。

```text
  fork 之后：两个进程，一个 offset

  P1.fd3 --\
            +--> 同一个 struct FILE { offset } --> log.txt
  P2.fd3 --/

  （若如上浅拷贝，两次写 2 会各占一个位置，文件里出现两个 2）
```

Unix 的设计者选的是后一条路，让 P1 和 P2 写出两个 2。为什么？他期望的是：当父子进程共享一个文件、并且以追加的方式写入时，不要再丢掉数据，也不要让两份数据随意互相覆盖——**覆盖一般来说都不是你想要的。**程序员不希望父子进程在写的时候把对方的结果盖掉，甚至我先写的被别人盖掉。那在程序员的意义上就是非预期的结果。

所以 Unix 把 offset 做成浅拷贝，两个指针指向同一个 offset。这也是为什么在 Unix 里，你想要一个深度独立、互不干扰的 offset，唯一的办法是**把这个文件再打开一次**——`open` 一次就得到一个新的 `struct FILE`、一个新的 offset。

### 默认全继承带来的祸：从最小权限到 O_CLOEXEC

`fork` 的这种默认行为——父子进程所有东西都继承——本身也带来很大的麻烦。每一个 `fork` 都会和几乎每一个系统调用、每一种操作系统对象产生关联：你一旦有了「复制」这个动作，任何被进程持有的资源，都要重新考虑复制之后的语义是什么。

有人一直在吐槽操作系统课里不该再教 fork 了，为此写过一篇文章，叫 *A Fork in the Road*，作者里有不少很有名的大佬，挺有意思，值得一读。它的意思是：软件系统的每一处设计，都要非常小心地考虑它和其他部分的交互。

Windows 的 handle 在这件事上设计得更好一点：**handle 默认不继承**，和 Unix 正好相反。你可以在创建 handle 的时候设置 inherit（继承），也可以在程序执行到某一点时再决定这个 handle 在将来派生新进程时要不要被继承。这是一个最小权限原则，从软件工程上看是更好的设计。

为什么说更好？你想这个场景：你的父进程持有着一个非常敏感的文件描述符，然后创建了一个子进程，再用 `execve` 去执行另外一个程序。如果你不小心忘了把那个敏感的文件描述符关掉，那个子进程就拥有了这个文件的访问权限。这就很危险——我把本来不该让另一个人访问的东西给了另一个人。它可能连安全漏洞都算不上，只是一个 bug，但足以让别人的程序误写掉系统里的一个文件。

所以后来 Linux 也引入了一个 `O_CLOEXEC`，让一个文件描述符在子进程创建（exec）的时候不被继承。你看，操作系统演化到今天，它的 API 实际上也是千疮百孔的。

> **提示**：好消息是 AI 对这些行为理解得都非常好。你们真正需要的能力是：在遇到真实问题时能意识到「这里有一个潜在的复杂性」，然后能 reason about 这些程序的执行。有这个能力就 OK 了。

### 到 /proc 里去看每个进程打开了什么

文件描述符相关的 API 基本讲清楚了，剩下的你们会在做实验的过程中真正去体会。接下来看看操作系统里到底有什么对象——我们已经学了 FHS（Filesystem Hierarchy Standard），知道文件目录树长什么样，也知道能用 `open`、`read`、`write` 去访问它，那就可以看看操作系统里到底有哪些文件了。

打开一个 `/proc/<pid>/fd` 目录，列出里面所有的东西：

```bash
ls -l /proc/*/fd/
```

有意思的就来了：**每个进程都打开了一些文件，而且因为 everything is a file，你可以在文件系统里看到每个进程打开的文件，看到每一个文件描述符究竟指向哪一个文件。**你能看到有些进程打开着 `tty7`，有些进程打开着 pipe。

既然看得到，就可以照 Unix philosophy 再往前走一步：把输出处理干净，把不想要的前缀去掉，然后直接把它管道给 claude-code，让它 explain it。去年我做这件事用的是自己写的命令行工具，今年就全部让 claude-code 来做了，甚至可以在 prompt 里让它调用工具。我做的事就是先打印出所有程序打开的文件，把格式稍微处理一下，然后让它解释。

在 everything is a file 的加持下，理解操作系统的任何一个部分都变得前所未有的简单。你们现在需要的是想象力——你可能没想到还能干这件事。但当你看得越来越多，你会发现计算机世界里没有任何魔法，你想知道任何事，都会有一个很干净的解释。

它显示的是系统中各种进程打开的文件描述符。在我们的系统里、就在此时此刻，你就能看到我们的程序打开了什么：一些 `/dev/pts/*`，这是伪终端，也就是终端模拟器。比如我现在这个终端是 `/dev/pts/5`，那我只要往它写数据，就能在那个终端上打印出东西来：

```bash
echo hello > /dev/pts/5
```

这条命令背后相当于 `open` 了 `/dev/pts/5`，然后执行一次 `write`，把 hello 打进去。打完你就看到那个终端上出现了一个 hello。也就是说，**只要我有权限，我就可以打开别人的终端，往里面写数据，别人的终端上就会出现我写进去的内容。**

顺着这条线你还能看到：真正的控制台 `/dev/tty7`、一个空设备、一个 GPU 渲染设备、`/dev/input` 下新挂上来的输入设备、随机数、还有套接字和管道。所有这些，都是可以用 `open`、`read`、`write` 去访问的对象。

### 管道：一个有容量、会互相等待的文件

刚才那个列表里有很多特殊文件的类型：有些是套接字，有些是管道。今天要讲的一个很重要的系统调用就是管道。

管道你可以理解成它就是一个文件——它就是一个文件，我甚至可以真的创建一个管道文件。它有一个写口、一个读口（画在左在右无所谓）：

```text
                 内核里的管道对象（一段有容量限制的缓冲）
                 +--------------------------------------+
  写口 <---------- | [ ...  数据 ... ]                    |
                 +--------------------------------------+
                                     ------------> 读口
```

你用 `write` 往写口里写，用 `read` 从读口里读。它的特点在于**阻塞**：

- 如果这个管道是空的、没有数据，那我的 `read` 就会等，等到有数据为止；
- 管道的容量是有限的（平时使用你基本可以当成容量无限，这件事交给 AI 帮你判断就行），如果写不下，我的 `write` 就会等，等到里面空出足够多的位置，我才能继续写。

这个「等」就是它最有价值的地方。打个比方：你想用 128 个进程并行算出数据来，每个进程把自己算出来的东西通过管道的写口写进去，最后主管的那个进程从管道里把 128 份数据读出来，加起来、打印。这不就实现了「等待进程把事情做完，再做下一件事」吗？

更具体一点，我让每个写完的进程往管道里写一句 `OK`，比如 `number 1 OK`、`number 2 OK`，那么主管进程只要读到 `number 1 OK`、`number 2 OK`，就知道谁已经 OK 了。管道就这样提供了一个进程间通信的机制。

### 命名管道与匿名管道

#### 命名管道：mkfifo 造出一个能 ls 到的文件

第一份示例用的是命名管道。我可以用 `mkfifo` 在 `/tmp` 下创建一个 `/tmp/mypipe`：

```c
if (mkfifo("/tmp/mypipe", 0666) < 0) {
    perror("mkfifo");
}
```

程序里也是同一件事：make FIFO 出 `/tmp/mypipe`，然后看命令行参数——如果参数是 `pipe_read` 就调用 `pipe_read`，否则就调用 `pipe_write` 往管道里写数据。

编译执行之后的行为很能说明问题。先跑读的那一头 `named_pipe_read`：什么都不会发生，**它就等在那儿**。这时候我从另一边 `write` 一个 hello，我的 `write` 马上就返回了，读的那边就读到了 hello。

反过来也一样：如果没有人在读，我往管道里写 hello，它也不会返回——它不是把数据丢完就走的，而是**要等到我 pipe read 那边真的读到一个 hello，这个 write 才会结束**。这就是一个互相等待的机制，它能在进程之间传递数据。

命名管道的好处是它在文件系统里有名字：`ls` 列出来的时候你会看到它带一个 `p` 的标记，清清楚楚是一个管道。

#### 匿名管道：int pipe 和那个很丑的 pipefd[2]

但如果你想做 `ls | wc` 这种事，是不需要创建一个命名管道的。管道运算符用的是匿名管道，系统调用是 `int pipe`，它会返回两个文件描述符。

这个 API 在 C 里用起来其实挺丑的。你得先定义一个长度是 2 的数组：

```c
int pipefd[2];
pipe(pipefd);
```

`pipe` 系统调用做的是：在内核里创建一个管道对象（这个管道没有任何名字，是匿名的），然后打开两个文件。比如 0、1、2、3 都已经被占用了，它就找到两个最小的空闲编号，假设是 4 和 5，一个指向管道的读口、一个指向管道的写口。其中 `pipefd[0]` 是读口，`pipefd[1]` 是写口。

```text
  pipe() 之后，进程里多出两个描述符

  fd 3 ---> /dev/pts/4
  fd 4 ---> 管道读口  <==== 内核里的管道对象 ====>  管道写口  <--- fd 5
```

高级语言在这里确实更舒服：你现代用什么语言都好，C++、Python、JavaScript 都能给你 `read_port, write_port = ...` 这种语法糖，而 C 里你就得弄一个长度 2 的数组、再记住 0 是读、1 是写。

这个管道一旦遇上 `fork`，行为更复杂：**fork 会把所有文件描述符都继承**。所以再创建一个进程，父子进程各有一份完全一样的描述符表，读口写口都一样。接下来要实现 `ls | wc`，就需要把 `ls` 的输出接到 `wc` 的输入上：保留管道的写口、把读口关掉，另一侧保留读口、把写口关掉，再做一点文件描述符的「腾挪」——那要用到 duplicate 那个系统调用，下一节课再详细讲。

在这个更简单的例子里，父子进程各自关掉自己不用的那一头，最后得到的就是一个相对干净的视图：

```text
  父进程关掉读口、子进程关掉写口之后

  父进程 fd 4 ---写---> [ 管道 ] ---读---> fd 3 子进程
```

父进程往 4 号写，子进程从 3 号读，数据就从父进程流到了子进程。

我对 `pipe` 这个系统调用设计的看法是：从使用者的角度它很讨厌，因为它是 `pipefd[2]`，你每次都要写 `pipefd[1]`——更好的做法是给它一个有意义的名字：

```c
int write_end = pipefd[1];
int read_end  = pipefd[0];
```

这样代码读起来才顺畅。但它的行为本身还是可以理解的。

### 不用再手画图：让调试器把 fd 状态打印出来

这里有一个更有意思的变化。

以前讲管道，我要在课堂上手画这些父子进程的描述符图，而且经常画得一塌糊涂。今天的做法是：想理解一个 pipe 程序怎么用，你不需要读文档，直接调试这个示例代码。因为**程序的状态我们随时随地都可以拿到**——刚才我们已经能做到查看进程已经打开的文件了。既然能查看每个进程打开了哪些文件，那我当然也能知道父进程、子进程各自打开了哪些管道、哪一个是读口哪一个是写口，这不就把那张图直接画出来了吗？

所以我不需要再在课堂上画了。我昨天晚上花了一点时间，直接让 AI 帮我写了一个工具：用 GDB 调试任何管道程序，把每一步的文件描述符状态导出来，生成一份 fd-state 的 markdown，里面是一张用 mermaid 语法描述的关系图，然后用 markdown preview 打开看。

匿名管道的那个例子是这样的：子进程执行 `do_child`，从管道里读；父进程执行 `do_parent`，往管道里写。效果就是父进程写一个 `Hello World`，子进程读到这个 `Hello World`，然后结束。

我们来看调试出来的状态。一开始进程是 22454，它有 fd 0、1、2，都是**以读写方式**打开的 `/dev/pts/4`。如果你不知道 `/dev/pts/4` 是什么，可以直接往上面打一点字符：

```bash
echo hello > /dev/pts/4
```

你看，这个 hello 就出现在 `/dev/pts/4` 那个终端上了。计算机世界里面每一个东西都是对的，严丝合缝的：图告诉我这个进程连着的终端是 `/dev/pts/4`，我真的往 `/dev/pts/4` 写数据，就真的在那个终端看到了 hello。

接着执行 `pipe` 系统调用，成功了。打印 `pipefd`，确实是 3 和 4——**从小到大返回**。这时候内核里多了一个管道对象，我的进程里多了两个文件描述符：3 连着管道的读口，4 连着管道的写口。

再往下走到 `fork` 那一行（示例里是 48 行的 `fork`）。fork 完状态更新：父子进程的 0、1、2 都指向 `/dev/pts/4`，管道的读口写口也都各自有了一份。这正是我刚才那张「手画图」想表达的内容，只是这个工具的 layout 能力比我强一点。

```text
  fork 之后（父子各有一份描述符表）

  父进程 fd 0,1,2 ---> /dev/pts/4      子进程 fd 0,1,2 ---> /dev/pts/4
  父进程 fd 3 ------> 管道读口          子进程 fd 3 ------> 管道读口
  父进程 fd 4 ------> 管道写口          子进程 fd 4 ------> 管道写口
```

继续看程序。现在是父进程，它做的事是**把管道的读口关掉**（fd 3），只保留写口 fd 4。调一步，视图就变了：读口没了，父进程的 fd 4 指向写口，还在。再切到第二个进程，`fork` 在子进程里返回，`child` 会把 `pipefd[1]`——也就是管道的写口——关掉。两边各关一头之后，就得到一个干净得多的视图：

```text
  各关一头之后的最终状态

  父进程 fd 4 ---写---> [ 管道 ] ---读---> fd 3 子进程
```

父进程用 4 号描述符往管道里写，子进程用 3 号描述符从管道里读出来。所以这个程序的本质就是：父进程往 4 号写，子进程往 3 号读。

要把它变成 `ls | wc`，你只需要再做一次指针腾挪：把 `ls` 的标准输出指向管道写口、把 `wc` 的标准输入指向管道读口，用 duplicate 那个系统调用就可以实现，这个下一节课再详细讲。

### testkit：assert 把程序打崩了，测试为什么还能继续

最后还有一点时间，讲一下我们的测试框架 testkit，这个也挺有意思。

首先表态：今天再也不要用古法去读代码了，AI 在这件事上真的能做得非常好。

再看 testkit 的用法，想想就觉得有趣。比如我现在写一个 simple，实现两个测试用例：一个运行 `test_pass`，我 assert 它的 exit status 等于 0；另一个运行 `test_fail`，这个一定会失败，我 assert 它的 exit status 不等于 0。

注意这里的 assert 会把**整个程序**给 crash 掉——你们写程序的时候写个 `assert(0)`，那这个程序就没有了，后面所有东西都不会再执行。那么问题来了：为什么我的 testkit 在 `verbose = 1` 的时候，`test_fail` 之后程序还在继续执行，而且还能告诉你两个 test case pass 了？

答案藏在实现里：**这里创建了子进程。**对每一个注册的测试用例，先用 `mmap` 创建一块共享的 buffer，这块 buffer 相当于既能给它喂输入、又能收集子进程的输出，于是子进程的输出就可以被拿来 assert；然后创建一个子进程去跑这个用例，子进程会给自己设一个闹钟当 timeout，超时就被杀掉——所以你们要是写了个死循环，也会被我的 testkit 逮住。最后父进程等它执行完，检查它的输出。

```text
  testkit 跑一个用例的时序

  父进程 ----mmap 共享 buffer----> 子进程（跑用例，设 alarm 做 timeout）
     |                                    |
     |<----- 等子进程结束、读 buffer 检查输出 -------
     |
     +--> 用例崩溃/超时都不影响父进程继续跑下一个用例
```

因为每个用例都在自己的子进程里跑，把 `assert` 打崩的只是那个孩子，父进程毫发无伤，可以接着跑下一个用例、最后统一汇报。有兴趣的同学可以把它当成一个进程管理加 `mmap` 的综合例子来读。

## 从打字机到伪终端：终端设备的前世今生
> 对应块：BLK15 | 覆盖分集：P08上 | 块标题（分集名）：《(Aside) 终端和 UNIX Shell（上）》

我们每天都从终端里走进计算机的世界。但我想先把时间倒回去——回到 1970 年代，那时候还没有高像素的图形显示器。没有图形界面、没有鼠标、没有彩色屏幕，人们却照样完成了今天你能做的所有事情。他们是怎么做到的？答案就藏在那个我们最熟悉、也最不理解的设备里：终端。而要讲清楚终端，得先从一个更古老的物件讲起——键盘。

### 键盘的老祖宗不是电脑

提到 keyboard，你们脑子里第一个跳出来的肯定是笔记本上那个键盘。但最早的 keyboard 完全不是用来打字给计算机的。

它最早可以追到公元前 3 世纪的水风琴（water organ），后来是管风琴——管风琴的声音很好听。到 1500 年左右，出现了最早的钢琴原型：一根一根的琴弦，你按下一个键，就有一个小锤子打到某根琴弦上，于是你听到了悦耳的声音。这就是"击奏弦鸣乐器"这个说法背后的机构。你看那个小视频的时候会有一种感觉：我们今天看到的一切有趣的东西，回头看，可能都是必然的。

这个机构距今已经五百多年，再往前的水风琴时代就已经有"按下按键、发出对应声音"这件事了。然后你一定会想到另一种机构——擒纵机构。按下键的时候，你用弹簧给它蓄力；松开键的时候，弹簧蓄的力可以去做一件额外的事：把机械结构向右推动固定的一小段。

把这两件事拼起来，打字机就诞生了。按键按下，不是让锤子去打琴弦发声，而是让它打到一个带墨水的色带上（现在大概是橡胶一类材料做的），色带再把字母印到纸上。只要所有按键打下去都落在同一个位置，色带上就会在纸上留下一个字符；而松开键的时候，擒纵机构把字车向右移动一格。于是你就实现了打字——不再需要手写，想到什么就打什么。

```text
      按下按键
         │  压缩弹簧蓄力，字锤被抬起
         ▼
     [字锤] ──► [色带] ──► [纸面]        留下一个字符
         ▲
         │  松开按键
         └──► 擒纵机构释放弹簧，把字车向右推固定的一格
                                            光标等待下一个字符
```

读图说明：一个按键的动作被拆成两半——按下时"印出一个字符"，松开时"往右走一格"，而这一格的距离是机械上固定死的。

这套机械结构也带来一个副作用：如果两个按键同时按下（或者几乎同时按下），两根字锤要抢同一个击打位置，机械结构很容易卡住。所以在 1860 年代，我们现在熟悉的 QWERTY 键盘被发明出来了。你们刚开始学键盘的时候一定觉得很奇怪——为什么要强行记住这套布局，从 `A S D F` 开始，一只手一只手地熟悉第一排按键，直到整个键盘变成肌肉记忆？原因就在这里：这个键盘的设计目的，本来就是降低你的打字速度，让字锤不容易撞在一起。

我自己在 2000 年的时候还真的玩过那种打字机。它能看到色带，而且色带其实支持两种颜色，你可以把色带调到上面或下面，一般是黑色和红色。它按起来很累——因为你打一个字母，不只是要把字锤推到色带上、还要击中它，同时还要有足够的能量把字车推到下一个位置。手指需要相当大的力量才能按下去，不像现在的键盘这么轻松。

#### 打字机留在键盘上的遗产：换挡

我们键盘上那些说不清来历的键，几乎都能在打字机上找到出处。

先看 `Shift` 和 `Caps Lock`。按 `Shift` 再按 `A` 得到大写 `A`，直接按得到小写 `a`；`Caps Lock` 则是把大写锁定。这两个键在机械结构上都有对应物：打字机的字锤上通常上下排着两个字符，下面是小写，上面是大写。按下 `Shift`，整排字锤的档位就被向上抬一格——原来这个按键打到的位置就"打空"了，落到了上面那个字符上，于是打出大写字母。`Caps Lock` 无非是把档位锁定在上面那个位置。就这么一个非常简单的机械结构，解释了每一个键的由来。

#### 打字机留在键盘上的遗产：回车与换行

我们在 `printf` 里写的两个特殊字符 `\r` 和 `
`，一个叫 carriage return，一个叫 line feed，也都是从打字机来的。`\r` 是回车：把打印头移回行首。打字机每按一个键都会往右走，你也可以用手直接把它推回左边；而把打印头推回去的过程同时也在给弹簧蓄力——推动的力一部分来自你的手，另一部分被弹簧存起来，留给后面走格用。

于是就有了一道题：我要打印 `hello`，但在中间插一个 `\r`，会发生什么？打前三个字符 `h`、`e`、`l` 之后，光标回到了这一行的头部；回到头部以后再打，就会把原来的字符覆盖掉。所以后面那两个字符会盖在前两个位置上，第三个位置还留着原来的 `l`——这一行最后显示出来是 `lol`。

> **提示**：在打字机上这个覆盖是物理的：色带把新字符直接印在旧字符上面，没有橡皮擦这回事。所以你写错了就是写错了，擦不掉。

那么打字机上打错了怎么办？这就是下面几个键的用处。

#### 打字机留在键盘上的遗产：space 与 backspace

你有没有想过，退格键为什么叫 `backspace`，而不是叫 delete？现在苹果键盘上那个位置甚至印的就是 delete。原因很简单：它和 `space` 是一对互逆的操作。`space` 把当前位置向右移一格，`backspace` 把当前位置向左移一格。

既然可以往回走，改错就有办法了：不停地 `backspace` 退回去，然后打若干个减号、斜杠，把原来那些字划掉，接着再往下打。你去看那些老照片，打字机打出来的稿子上真的有一道道划掉的横杠；甚至你可以换一个颜色的色带，用红色把它划掉，这都是可以的。

#### 打字机留在键盘上的遗产：Tab

键盘上的 `Tab` 是制表符。打字机上有一些可以设定的 tab stop（制表位）：你按下 `Tab`，字车就一直往右走，直到碰到一个 tab stop 才停下——我猜大约是用了棘轮一类的结构。所以它能很容易地实现对齐。

怎么对齐？比如我要排一个表格，一列 name、一列 ID。如果我靠打空格来 padding，名字长短一变，列就歪了；而按 `Tab`，它会跳到下一个 tab stop，于是无论名字多长，对齐都是自动的。这样即使在一台打字机上，你也能方便地做出排版工整的表格。今天我们按 `Ctrl+Tab`、`Alt+Tab`、`Win+Tab` 切换窗口，用的还是这个键。

#### 打字机留在键盘上的遗产：等宽字体

打字机还带来了 monospace，也就是等宽字体：因为每打一个字符，字车向右移动的距离完全确定。这个习惯一直延续到今天——我们在终端里用的依然是等宽字体。

> **提示**：那如果做一个不是等宽字体的终端呢？也许是可以的，也许会有非常有趣的效果。这值得你去做个小的 project，live coding 一下试试。

到这里，你们看到的键盘的雏形基本就齐了，绝大部分按键都已经出现在打字机上。

### 电传打字机：把字符送到导线的另一端

从机械时代走到电气化时代，我们有了另一种 typewriter。打字机叫 typewriter，就是 type 加 write：按一下 `A`，就打出一个 `A`。而 Teletypewriter，也就是电传打字机，功能其实是一样的，但有一个关键区别：当我按下 `A`，我不是在本地打出字来，而是在**导线的另外一端**打出字来——这根导线可以非常非常远，甚至在大陆的另一端。

这是一个跨时代的设计。用打字机，我要打出一张 A4 纸，然后请邮差把它送到欧洲去；有了电传打字机，我只要有一根维护良好的导线，它当然会有很多中继站来保证正常运转，我只需要给每一个字符编一个码、编一个号就行。

1920 年用的是 5-bit 的编码。5 位当然装不下打字机那么花哨的全部字符，但也够用：`a`、`b`、`c`、`d` 这些字母编进去，数字编进去，再加上一些特殊符号。大小写怎么办？只要保留一些特殊的编码字符——"进入大写模式""进入小写模式"——就可以切换。你去看那张编码表会发现里面居然没有美元符号，所以这台机器一看就不是美国人设计的。

```text
  [电传打字机 A]                     [线路 + 中继站]                  [电传打字机 B]
      键盘输入  ────►  每个字符编成 5-bit 码  ────►   在远端把字符打印出来
    （本地不产生输出）                                           （距离可以横跨大陆）
```

读图说明：字符被压成编码后放进导线，输入点和输出点从此可以隔着几千公里——这已经非常接近后来计算机的样子了。

顺便说一句，有兴趣的同学可以找 Teletype Model 28 的资料读一读，那是 1951 年前后的产品，技术数据手册写得很扎实。这种文档很值得读，尤其在 AI 的帮助下读：它把整个系统怎么构建、由哪些零件和部件组成、坏了怎么照着手册维修、工作原理是什么，全都写得清清楚楚——中间那些机械结构，包括电路的波形特性和内部电路，一个细节都不含糊。读这些东西的时候你可能会有一点小小的震撼：1950 年代，人类的科技就已经发展到这个程度了。

### 从戳孔到人能读的输出

经过这些演进，终于有一天轮到计算机登场了。还记得最初的时候，程序是以机器码的方式直接在计算机上运行的，运行完了输出就不停地戳孔——寄存器或者内存里的值本来就是一个 bit string，把 0 和 1 送到一个机械部件上真的戳出孔来，输出就有了。但那对人类实在太不友好了。第一次课上给大家看过的那张 Fortran 打孔卡片就是这个样子：你要写一行语句，就要在一张卡片上戳戳戳戳戳。

当计算机变得更快以后，我们很想要两件事：让计算机的输出以人眼可读的方式直接呈现出来，并且人类再也不要像弄 Fortran 打孔纸带那样干活。所以在很长一段时间里，计算机系统上用的就是这种类似电传打字机的东西——它不再戳二进制的 0 和 1，而是把数据编码成二进制，输出到一台打印机上打印出来。

### TTY 这个名字的由来

真正的跨时代产品是 Video Teletypewriter。TTY 这个名字就是 Teletypewriter 的缩写，而 Teletypewriter 又是从 typewriter（最早那台打字机）继承下来的——它保留了"打字机"最重要的那个功能，它还是一台能执行的打字机。

从计算机硬件、或者说从操作系统的角度看，这个设备给我们的接口就是 `putchar`：计算机生成一个字符，把字符送进去。你可以把它想象成一个 memory-mapped 的 I/O 端口——往那个内存地址里写一个字符，打字机就收到它、把它打出来。你送一个 `\r`，它就回到行首；送一个 `\t`，它就跳到下一个 tab stop；打字机能接受的任何字符，你都可以送。

那个时代制定了很多标准，你们学计算机的时候一定学过 ASCII：需要一个国际标准来确定一个数字（二进制也好、十进制也好）到底对应哪一个字符。

但你们有没有为 ASCII 困惑过？大写 `A` 是 65 号，这个数字相当大；小写 `a` 更大，是 97。为什么这么大？前面那些编号又是些什么东西？

> **结论**：ASCII 的设计就是和电传打字机共同完成的。那些看起来莫名其妙的编码，正是终端设备真实需要的动作——这一点接下来会一个个解开。

### VT100：一个事实上的行业标准

到 1978 年，VT100 出现了。它是里程碑式的产品，后来成了事实上的行业标准。它支持完整的 ANSI escape sequence（escape code）：可以有颜色，可以做屏幕控制、屏幕滚动这些功能。

它还是像打字机：打字机可以滚纸，Video Teletypewriter 也可以滚纸——你就想象成一张无限长的纸，可以往上滚往下滚。今天的终端里也一样能上下滚。

也就是从那个时候起，80×24 个字符的显示成了今天终端布局的标准。你们最早在 Windows 里写代码时看到的那个黑黢黢的窗口，默认大小就是这么大。

### Unicode 时代的终端

从电传打字机一路走到现在这种高清晰度的显示器，TTY 并没有消失，尤其有了 Unicode 之后，能玩的花活更多了。

你在我终端里看到的那个三角形是怎么画出来的？我当然没有画一个三角形，我是把很多 Unicode 字符叠加起来的。Unicode 规定了大量字符，包括你们见过的 emoji——我上课的时候偶尔也会用一两个表情符号表达情绪。

表情符号很有意思：它就像一个词，我们给它赋予一个含义；在 token space 里它也有自己的 embedding，代表那个意思。但你很难把它念出来——中文念不出来。以后表情符号是不是要收进新华字典？收进去以后怎么给它标拼音？这是个挺有意思的问题。

Unicode 里还有很多不同高度的矩形块、不同高度的线条，有中间空的，也有实心的。当这些组合足够多的时候，我就可以用 Unicode 字符拼出任何一个形状来。比如 Code 的那个小人，我们最后还 3D 打印了一些放在 lab 里。

回头看整条演化路线，其实非常平滑：最早是一个像钢琴一样的击弦机构，然后一点一点往前走，每一步都是一个非常小的改动，积少成多，就成了今天这么好用的东西。比如大家都喜欢给 `zsh` 做的那个 powerline status bar——用 Unicode 配合前景色和背景色，调出一个分成好几段的状态栏。有兴趣的同学都可以试一试，也可以直接让现在的模型给你 vibe code 一个 Unicode 的图形出来。

### 终端同时也是输入设备

作为输出设备，终端和操作系统的接口就是一个 `putchar`：它收到字符就打印出来，就像打字机一样。

但我们的 typewriter 是有键盘的，所以它和那种纯机械的、按什么打什么的手动打字机不一样——它还可以作为电脑的**输入**设备。

当我按下一个 `A`，实际发生的事情是：video teletypewriter 把 `A` 这个字符送进了计算机，操作系统的进程看到这个 `A`。至于要不要把这个 `A` 打印出来、是打印 `A` 还是打印一个 `*` 给你，全都是由操作系统决定的，也就是由软件决定的。它只是一个比较傻的设备：当你按下一个键，它就给你一个字符。

按 `ESC` 也一样：它真的给你一个 ESC 字符，ESC 是有 ASCII 码的，就是 033——你写 escape sequence 的时候用的那个 ESC。操作系统看到它，爱怎么处理就怎么处理，可以原样把它打印出来（所以你会看到在某些环境里按 ESC，屏幕上真的显示出东西），也可以什么都不显示——这由操作系统和应用程序共同决定。

`Shift` 就更有意思了。在你现在的电脑上，哪怕是终端模拟出来的终端（或者你真的有一台 VT100），当你按下 `Shift` 的时候，这个键虽然被按下了，但其实没有任何数据被送进计算机。`Shift` 的状态留在终端上面——就像在打字机上按下 `Shift` 只是把字锤整排换挡、并没有敲下去；只有真正敲下去，才相当于把字符送进计算机。换到上档以后，你再按一个 `A`，送进去的是一个大写的 `A`。

> **易错点**：`Shift` 从来不会作为一个按键被送到计算机里。它只改变"下一个真正敲下去的键送什么字符"。

### 真的把按键码读出来看一遍

我让 AI 写了一个程序，目标是：直接读到终端上所有按键的编码，相当于假设有一台 VT100 接在我的电脑上，所有送过来的字符原封不动地打印出来、不做任何处理。答案是可以做到的。

- 程序提示 `press q to exit`，我按 `q`，确实退出了。
- 按 `a b c d e f`，得到的就是正常的 ASCII 码。
- 按 `Shift`：虽然我已经按下了，但什么也没收到；等我按下 `A`，它才真正发生。
- 按 `Ctrl+C`：它没有被当成"Ctrl 这个键 + 一个 C"，也不是把程序杀掉——我得到的是一个编号为 **03** 的 ASCII 码。按 `Ctrl+D`，得到 **04**。（`Ctrl+D` 就是你告诉程序"输入到此为止"的那个键。）
- 回车给我的是 `\r`，不是 `
`——和打字机上那个行为是一样的。
- 退格键送出的其实是 **0x7F（DEL）**，所以它常被程序解释成 delete，这也解释了苹果键盘上那个位置为什么印着 delete。
- `Tab` 得到 `\t`，空格得到 space。
- 方向键呢？ASCII 里面**根本没有**上下左右。所以它被迫编码成了一串 escape code。反过来也一样：ASCII 里没有编码"颜色是什么"，我就需要用 escape code 告诉终端颜色。按方向键收到的末字节是 0x41、0x42、0x43、0x44，分别对应上、下、右、左。

| 按键 | 终端送给操作系统的字节 | 说明 |
| :--- | :--- | :--- |
| `Ctrl+C` | `0x03` | 不是"Ctrl+C"两个字符，就是一个 03 |
| `Ctrl+D` | `0x04` | 表示输入结束 |
| 回车 | `0x0D`（`\r`） | 是回车，不是换行 |
| `Tab` | `0x09`（`\t`） | 制表符 |
| 空格 | `0x20` | 空格本身 |
| 退格 | `0x7F`（DEL） | 因此常被当作 delete |
| 方向键 | ESC 序列，末字节 0x41/0x42/0x43/0x44 | ASCII 里没有方向键，只能靠 escape code |

于是你就可以完全清楚地知道终端和操作系统之间的关系了：它就是一个非常傻的东西，像打字机一样。ASCII 里那些你不知道是干什么、也从来没有人给你解释过的编码，其实就是这么来的。

```text
                 ┌──────── 终端设备（或终端模拟器）────────┐
                 │  键盘：按下一个键 → 送出一个字符        │
                 │  显示：收到一个字符 → 在屏幕上画出来    │
                 └────────────────────────────────────────┘
                        ▲  字符流（读）            │  字符流（写）
                        │                          ▼
                        └──── 操作系统 / 应用程序 ────
                             read() 拿到什么、putchar()/write() 送什么
```

读图说明：终端与计算机之间只有这一条双向的字符流，别的约定一概没有——所谓"终端"，就是一台按字符收发的打字机。

这里还有一个很有意思的意外。在这个程序里，`Ctrl+C` 已经退不出去了，`Ctrl+Z` 也退不出去，`Ctrl+反斜杠` 同样结束不了它——我只能再开一个终端把这个进程 kill 掉才能退出。幸好我写代码的时候留了一个后门：按 `q` 可以退出。如果我把那行代码注释掉，你就真的没有任何办法从程序里出来。

> **提示**：`Ctrl+C` 能终止程序，不是因为终端有什么特别的能力，而是操作系统在收到那个 03 之后**额外模拟**出来的行为。这件事后面会专门讲。

### 伪终端：想要多少就有多少

VT100 是一台真正的终端：你可以向它写字符、写 escape code，也可以从它读字符、读 escape code。

但在我们现在的计算机系统里，终端想要多少就有多少——每按一下就有个新终端，而且每一个都不一样，每一个都有自己的 `/dev/pts/N`；用完把它销毁掉，这个名字还能被下一个人复用。

操作系统有一个非常有趣的能力：它可以无限制地分配像 VT100 那样的**虚拟终端**。你要一个，就向操作系统要一个，它就给你变一个出来，结束的时候再把这个终端销毁。这叫 pseudo-terminal，伪终端，或者说是模拟出来的终端。

你们都用过 `tmux` 吧？在 `tmux` 里可以分屏，分出很多个终端，每一个都是不一样的。那有没有好奇过：如果让你实现一个 `tmux`，你能做到吗？我直接 vibe code 了一个 mini-tty——这不就是 tmux 吗。

它的行为是这样的：我在自己当前的终端里，再创建了一个 `/dev/pts` 下的终端。先执行 `tty` 看看，外层这个终端是 `/dev/pts/3`；运行它之后再执行 `tty`，里面的程序就认为自己是 `/dev/pts/4`。也就是说，我相当于向操作系统要了一个新的 VT100，把它的窗口大小配置得比我的屏幕小一点，然后把它画出来。在里面我可以正常地干任何事情。

```text
   外层终端 /dev/pts/3                     新申请的伪终端 /dev/pts/4
  ┌────────────────────┐                  ┌──────────────────────────┐
  │   mini-tty（画窗口） │  open /dev/ptmx  │  运行在 pts/4 上的程序     │
  │                    │  grantpt         │  （它以为自己在一台真终端上）│
  │   键盘输入 ─────────┼──► master fd ───►│──► 里面的程序读到按键       │
  │   屏幕输出 ◄────────┼───  master fd ◄─│◄── 里面的程序写出的字符     │
  └────────────────────┘  unlockpt        └──────────────────────────┘
```

读图说明：mini-tty 站在中间当二传手——把 pts/3 上的输入转发到 pts/4，再把 pts/4 的输出搬回 pts/3，于是就在一个终端里长出了另一个终端。

这是怎么办到的？这其实涉及操作系统的 API——说到底我还是在讲操作系统课。我们的操作系统里有一个特殊的设备叫 `/dev/ptmx`。上一次课我讲过，Unix 世界里 everything is a file，所有东西都是文件，终端也是一个文件。那你要创建一个终端，也是要创建一个"新文件"；但你不能像创建普通文本文件那样去创建它，你得向 `/dev/ptmx` 这个特殊文件请求，问操作系统：能不能给我分配一个新的终端？

分配的过程写在 `pty_master_open` 里：先用 `open` 打开 `/dev/ptmx` 这个 master 设备，然后调用一个叫 `grantpt` 的操作，再 `unlockpt`，最后拿到对应的路径和文件描述符等。一旦你作为 master 持有了这个 PTY，你就可以去读写里面的数据了——它就是一个完整的终端设备，你在上面可以做任何事情。这里面还有很多细节，你们可以一点一点地和 AI 交流。

正是因为能随意申请一个 pseudo terminal，才能做"终端中的终端"这种事，也才能干很多有趣的事。

### ttyrec：把一次终端会话原样录下来

比如有一个命令行工具叫 `ttyrec`。我用它的方式是这样的：先 `ttyrec` 开始录制，然后直接开一个 claude，问它一句 `hi`，它可能会很快给我结果，也可能没有，这不重要。

运行 `ttyrec` 之后好像什么都没发生，但其实它已经"偷梁换柱"了——它偷偷创建了一个新的 pseudo terminal，把我所有终端的输入和输出都劫持了。劫持之后就可以用 `ttyplay` 回放：你会看到刚才那条消息，以及我做的每一个操作。

它靠什么做到的？就是靠记录时间戳。因为前面说过，终端是一个非常简单的设备，它和操作系统之间的接口就是字符进、字符出。既然是这样，我只要知道每个字符是什么、以及它出现的时间戳，就能完整地恢复一次终端的运行。所以网上有很多工具可以把终端的 trace 甚至渲染成一个 HTML 里的 SVG，嵌到你的网页上——你点开那个网页，就能看到终端里整件事情是怎么发生的。

我一直觉得这件事很了不起：人类从一架钢琴开始，构建了很多有趣的基础设施，然后这些基础设施一点一点演化，最终构成了一个非常好的、可以"替代老师"的基础设施——也就是能把我干掉的东西。因为我可以让 AI 帮我生成演示的脚本、想好演示的剧本，然后让它在真实环境里执行；执行的时候你们看到的是真正的程序怎么运行，同时 AI 老师一边在讲解。而最终留下来的，就是一个 ttyrec 格式的文件——里面记录着我问的那句 `hi`，也记录着它打印出来的各种 color code。

### 在终端里显示图片：Sixel

如果我们不满足于一个只能打印字符的终端呢？你看我的终端模拟器是可以显示图片的，而且是货真价实的彩色图片。为什么一个终端模拟器能显示彩色图片？

这也是一个很自然、很合理的需求——大家都想在终端里显示图片。随着集成电路技术的发展，终端本来是只能显示 24×80 个字符的；它想做得更先进，那就把字符做得更大，做个 48×160 的大号终端，四倍大。但你再大也还是字符终端，而且你的脖子很快就不够用了。

那如果芯片进步了、能显示更细粒度的图像了，我们能不能真的在终端上显示图片？可以——在 escape code 上做一个小小的扩展就好。这个扩展 DEC 早在 VT200 的时候就已经做了，叫 Sixel 编码。

它的思路是：我可以在终端上显示一个高度为 6 的单色块。6 这个数字是有讲究的——$2^6 = 64$，正好能被所有可显示的 ASCII 字符覆盖住。于是做一个映射：`?` 表示这一列六个像素全都不亮（全白），`@` 表示最上面一个像素亮起来，后面的字符依次表示六位的各种组合。有了这个，我就能在终端上输出图形了——很多这样的"六像素高的块"拼在一起，就是一张图。

```text
   一个字符 = 一列 6 个像素       若干列并排 = 一条 6 像素高的色带
   ┌───┐                            ┌───┬───┬───┬───┬───┐
   │ ● │  ← 最上面一个像素亮          │ ● │   │ ● │   │   │
   │   │                            │   │   │ ● │ ● │   │
   │   │                            │   │   │   │ ● │   │
   │   │                            │   │   │   │   │   │
   │   │                            │   │   │   │   │   │
   │   │                            │   │   │   │   │   │
   └───┘                            └───┴───┴───┴───┴───┘
     '@'                                 逐列送字符即可拼出图形
```

读图说明：把"一列六个像素"当成一个字符来编码送出，终端只要能显示字符，就顺带能显示这种粗粒度的位图。

后来这个标准还被扩展了：可以加一个调色板，指定第 1 块、第 2 块……第 6 块分别是什么颜色；没有指定颜色的那些位置就变成一个 mask。

今天很多现代终端都支持它：我平时用的 kitty，现在用的 foot，包括你们更新以后的 Windows Terminal（我不记得从哪个版本开始）也支持在终端里显示 Sixel 图像。所以理论上我这一系列代码在 Windows 环境下也能正常运行。

> **提示**：在不支持 Sixel 的终端上，你什么也看不见；把那段输出丢到一个 `a.txt` 里，就是一堆看不懂的字符。把这段文本贴到支持 Sixel 的终端里，你确实能看到一小块 image——虽然可能只是一个 patch，但它真的是像素。

随着历史发展，终端变得几乎无所不能，尤其在今天有 Unicode 帮忙、给我们编码了各种各样的奇怪东西之后，能画出各种有趣的图形。这就是我们今天看到的终端世界。

### 你平时感受到的终端：canonical mode

但是，无论你在终端上按 `Ctrl+C`、`Ctrl+D`，还是在终端里看到图像，它背后的接口都是那个非常原始的接口：我送一个字节流给终端，终端把字节流送回给操作系统、送回给应用程序。**这不是**你平时感受到的那个终端。

你平时感受到的终端是这样的：你在终端里运行 `./a.out`，或者运行 `cat`。`cat` 会执行一个 system call，大概是 `read`——从 stdin 读一个 buffer，带一个 size。按上面那个模型，`read` 读到字符就应该直接 `write` 出来，这也确实是 `cat` 的实现。那为什么我按 `aaaaaa` 的时候它没反应？因为 `read` 还没有返回。

现在用 `strace cat` 看：`read` 确实没有返回。我打 `aaaaaa`（打错了可以退格退掉，再打 `bbbbb`），只有当我按下回车键的时候，`read` 才返回、才读到数据。

这跟前面的模型矛盾吗？不矛盾。因为你的终端是把字符送给**操作系统**，而不是直接送给应用程序——虽然在前面的示例程序里，我可以选择直接从终端读、请操作系统不要帮我处理。

除了这种"不处理"的方式，操作系统还会给你提供一个**行编辑**模式。你用的 foot、kitty、iTerm，都叫 terminal emulator，它模拟了一个终端设备；它的功能和你操作系统里的那部分配合在一起，才完成了你看到的这种带编辑的模式——这叫作 canonical mode（规范模式）。

```text
   按键 ──► 终端 / 终端模拟器 ──► 操作系统的行规程（canonical mode） ──► 应用程序
            只负责收发字符          缓存整行、处理退格与删除            read() 返回
                                              │
                                              └──► 回显（echo）──► 屏幕
```

读图说明：按键并不是一个字符一个字符地交给 `read`，而是先被行规程攒成一行、顺手处理掉退格，等回车才一次性交出去；顺带把整行回显到屏幕上。

为什么这件事要做得这么认真？因为终端是人机交互的第一个设备。从 1970 年代 VT100 的时代起，它就是最重要的、和人打交道的 I/O 设备——那个设备坏了，你就别想用电脑了。

### 系统启动时，终端是被谁照顾的

正因为终端这么要紧，它在系统启动的时候就必须被照看好。

系统启动最先是 firmware 在运行（固件），然后是操作系统的代码开始运行。等操作系统代码完成了一定的初始化以后，它就会把终端设备扫描好、初始化好。接下来，`init` 进程会调用一个叫 `getty` 的程序：它 opens a tty port（打开一个终端），prompt for login name（提示输入登录名），并调用 `login` 命令。

"打开一个终端"这句话需要展开一下。整个系统刚启动的时候，第一个进程刚被加载时，文件描述符 0、1、2 是什么都没有的。而 `init` 其实也不知道自己处在哪一个终端上——因为系统上可能有五六个终端。

```text
   firmware ──► 操作系统初始化（扫描并初始化终端设备） ──► init
                                                            │
                                        ┌───────────────────┼───────────────────┐
                                        ▼                   ▼                   ▼
                                     getty               getty               getty
                                  (/dev/tty1)         (/dev/tty2)         (/dev/tty3)
                                        │                   │                   │
                          打开终端、把 0/1/2 指向它、配置初始化、提示登录
                                        │
                                        ▼
                                      login
```

读图说明：`getty` 由 `init` 在每个终端上各起一个，它的职责就是把那一台终端打开、把标准输入输出接上去，然后请人登录。

所以 `getty` 是要带参数的：`init` 说"我要在第一个终端上启动这个程序"，又"要在第二个终端、第三个终端上也启动它"。这就是为什么在 Linux 里按 `Ctrl+Alt+F1`，你会看到打印日志的控制台；`Ctrl+Alt+F2`、`F3` 每一个都能看到一个提示用户登录的程序。而我切到 `Ctrl+F7` 的时候，就到了第七个屏幕上——`tty7`，我的图形用户界面就跑在 `tty7` 上面。

`getty` 之后做的就是真正打开对应的终端设备（比如 `/dev/tty1`），然后把 0、1、2 这三个文件描述符都指向这个终端，并做一些配置和初始化。这里有一个很有意思的配置项叫 baud rate，波特率，也就是接口真实传输的速率。如果你面对的真的是一台 VT100，你必须给它一个有意义的数值，操作系统才能正确地跟终端握手；现在终端是模拟出来的，这个数值其实不那么重要了——但你查看当前 pseudo-terminal 的时候，它依然会模拟出一个 38400 的波特率来。

到这一步，终端才和操作系统里的进程真正联系起来，然后 `login` 被创建出来。如果你走的是远程登录，情况稍有不同：`sshd` 会去分配一个 pseudo-terminal，然后 fork 一个自己的程序，创建伪终端并完成初始化，再执行 `login`——或者更准确地说，是一次权限切换，因为 `sshd` 本身运行在高权限上，它可以把自己变成另外一个程序。

所谓 `login`：login program is used to establish a new session with the system。这个终端就是你最开始坐下来、坐在它面前的那个终端；一个会话（session）里都有一个 controlling terminal（控制终端）。`login` 的手册里说它要 begin session on the system——它要启动一个 session。所以这里的"session"一词有点混乱：`login` 里说的 session 和 login 手册里说的 session 混在一起。但我们知道的是……这个话题后面还会回到。

### 本讲提到的题目

**题目一**：我要打印 `hello`，但在这个 `hello` 中间加一个 `\r`，会得到什么？

**解析**：`\r` 是 carriage return，在打字机上就是"把打印头移回行首"。把它插在 `hello` 中间，字符序列就变成了 `h`、`e`、`l`、`\r`、`l`、`o`。打完前三个字符后光标回到行首，后面两个字符就会盖在前两个位置上，第三个位置还留着原来的 `l`。

**答案**：这一行显示为 `lol`。

**题目二**：在那个直接读原始按键码的程序里按下 `Ctrl+C`，会发生什么？是程序被杀掉，还是收到"代表 Ctrl 的编码 + 一个 `C`"，还是收到一个编号为 03 的字符？

**解析**：终端只是一个傻设备，它会把 `Ctrl+C` 解释成一个字符送出去；而 ASCII 的设计本来就是和电传打字机共同完成的，所以这个字符有现成的编码。`Ctrl+D` 同理。

**答案**：得到编号为 03 的 ASCII 码（`Ctrl+D` 得到 04）。程序不会被杀掉——正因为如此，那个程序里 `Ctrl+C`、`Ctrl+Z`、`Ctrl+反斜杠` 都退不出去，只能再开一个终端把进程 kill 掉；它能退出，靠的是作者自己留的"按 `q` 退出"的后门。

**题目三**：如果让你实现一个 `tmux`，你能做到吗？

**解析**：靠伪终端（pseudo-terminal）。向 `/dev/ptmx` 请求操作系统分配一个新的终端，在 `pty_master_open` 里先用 `open` 打开 `/dev/ptmx`，再 `grantpt`、`unlockpt`，拿到路径和文件描述符；作为 master 持有这个 PTY 之后，就可以读写它里面的数据。接下来把外层终端（比如 `/dev/pts/3`）的输入转发进新终端（`/dev/pts/4`），再把新终端的输出搬回外层终端，并在外层屏幕上把那个窗口画出来——正文里的 mini-tty 就是这么做的。

**练习四**：做一个不是等宽字体的终端。等宽字体的习惯是从打字机来的（每个字符右移的距离完全确定），所以不按这个规矩来会得到什么效果，值得 live coding 一下试试。

### 按下 Ctrl+C 到底发生了什么

但是你们头上始终有一朵乌云：在操作系统课刚开始的时候我抛出的那个问题——你按下 Ctrl+C 的时候，到底发生了什么？而且在我讲完终端以后，这个问题只会更费解。因为你可以像我一开始展示 mini-tty 时那样，向操作系统提出要求：请你把终端里收到的所有字符全都直接给我。这时候你按 Ctrl+C 就没有任何反应了——它不再是一个"取消"的指令，它变成了一个字符，被从终端设备送到了应用程序里，应用程序看到了这个字符，只是没有把它解读成你们熟悉的那个"应该退出"的 Ctrl+C。

你们可能听说过：按下 Ctrl+C，操作系统会给程序发送一个信号。这个模型是对的。至于每一个字符应该怎么解读——比如 Ctrl+C——那是因为操作系统里有一个驱动。不管是真的 VT100 那样的驱动，还是我模拟出来的一个终端（那本身就是一段软件驱动），行为都一样。

键盘这一侧：我按下 Ctrl+C，设备的行为就是送出一个 Ctrl+C 对应的字符；我按 Shift，设备不会给驱动、给操作系统发任何数据，直到我接着按下 `a`，它才把大写的 `A` 送出去。收到字符之后，驱动再根据应用程序对终端的配置来决定行为。

默认情况下，就像刚才 `cat` 的时候那样，终端处在 canonical mode。在这个模式下，操作系统的驱动会模拟出一个行编辑状态，内部有一个 buffer：

```text
 keyboard/pty
      |
      |  每个按键 = 一个字符
      v
 +-----------------------------+
 |  terminal driver            |
 |    line buffer: a b _       |
 |    backspace -> 删掉上一个  |
 |    echo on/off -> 回显屏幕  |
 |    INTR/QUIT/EOF -> 特殊    |
 +-----------------------------+
      |
      |  一整行（raw 模式下则原样放行）
      v
   process: read(fd)
```

进程可以 `read` 那个终端设备；而当你按下 `a`、再按下 `b` 的时候，`a`、`b` 只是进了驱动的缓冲区，还没有到进程手里，再按一下退格，是驱动把这个 `b` 去掉的——整个行编辑是驱动模拟出来的。驱动还会把字符送回去做回显，而回显本身是可以开也可以关的：你们都知道用 `sudo` 输密码的时候按下的字符不显示，这时候行编辑照旧在驱动里正常工作，只是回显关掉了。

**本质上这一切都是操作系统搞的鬼。** 当你按下 Ctrl+C 或者 Ctrl+D——也就是 end of text、end of transmission——那个字符会被操作系统解读成另一个含义再送给进程；具体变成什么行为，取决于你怎样配置这个终端驱动。如果你配置成"驱动什么都别管，所有字符直接送到我的程序里"，那就会出现刚才那样：无论按什么键都退不出来。

比较有意思的是，你可以用 `stty -a` 看当前终端支持哪些配置：

| 配置项 | 默认按键 | 含义 |
| --- | --- | --- |
| `interrupt` | Ctrl+C | 中断，送 SIGINT |
| `quit` | Ctrl+\\ | 退出，送 SIGQUIT |
| `eof` | Ctrl+D | 文件结束（end of transmission） |

`stty -a` 里没有 end of line 之类的项。这里有一个你们可能不知道的救命技巧：**在 Ctrl+C 退不出来的时候，试试 Ctrl+\\**。你会看到它给出的提示不一样——`yes` 按 Ctrl+C 是一个正常的中断退出，按 Ctrl+\\ 得到的是 `terminated by SIGQUIT`，是一个异常退出。这个映射也不是写死的，interrupt 配在 Ctrl+C 上，你完全可以把它改到别的按键上。

> **结论**：只有处在 canonical mode、走行编辑这条路的时候，Ctrl+C 才会被操作系统识别并按终端配置转成一个 interrupt；整个终端驱动的行为都是可配置的。

### Ctrl+C 究竟杀谁：进程组

这个问题解决之后，更麻烦的问题来了。操作系统里的进程是一棵很大的进程树（`pstree` 打出来那么大一棵），那么我按下 Ctrl+C 的时候，**到底哪些进程要被杀掉**？

你越想越可怕。我在这里按下 Ctrl+C，为什么旁边那个 VS Code 安然无恙？我这儿开着一个 `yes` 在刷屏，我按 Ctrl+C，我想杀的当然是这个 `yes`，可为什么不是别的程序？如果这个 `yes` 又创建了子进程呢？

答案是一个从进程树上看不出来的东西：进程组。在 Shell、Bash 里启动一个新程序的时候，我会为它分配一个新的进程组——就像你在 Windows 里双击一个应用，我会给它一个新的窗口。这是 Shell 干的事情。默认情况下，你创建出来的进程会继承父进程的进程组；当然操作系统也提供了系统调用去修改自己的进程组。

```text
 session S  (leader: 你的登录 shell)
   |  controlling terminal: /dev/pts/N
   |
   +-- process group 1 (PGID=1)   <- 前台（由 tcsetpgrp 标记）
   |     +-- bash
   |     +-- ls
   |
   +-- process group 2 (PGID=2)   <- 后台
         +-- yes

 Ctrl+C --> 给前台的进程组里的每一个进程发 SIGINT
 Ctrl+Z --> 给前台的进程组发 SIGSTOP（之后可以用 fg/bg 恢复）
```

正因为有了这个隐藏的 process group ID（PGID），到底是哪一个应用程序才被分开了；分开之后，Ctrl+C 的行为终于清楚了：**操作系统会给前台的进程组里的所有进程发送 SIGINT**。这个设计是正确的——只要进程不忽略 SIGINT，前台那一组里的每一个进程都会收到。所以它是一个非常粗暴的解决方法。而且后面还有更粗暴、更让你不舒服的地方。

### 作业控制：终端里的窗口管理器

那些更不舒服的地方，先从一套熟悉的东西说起。你在编辑一个文件，按下 Ctrl+Z——哎？没了。但是程序没有终止，我还可以再去编辑另外一个文件。这时候可以用 `jobs` 命令看手头的任务。

`jobs` 就相当于你们在 Windows 上按 Alt+Tab：Alt+Tab 会轮换窗口，Windows+Tab 也是；轮换的时候你就知道，哦，我现在已经打开了两个窗口。同样地，我可以开一个 `yes`，把它切到后台——切后台之后，程序默认都暂停在那里。但我也可以让它在后台继续跑：用 `bg` 把 3 号任务放到后台继续运行，再把它挪回前台，然后 Ctrl+C 杀掉。

这不就和 Windows 里启动一个应用程序、有了一个窗口、再双击启动另一个、然后在几个程序之间切换完全一样吗？我在这里可以开无数个窗口——我刚才按 Ctrl+Z 就是把它最小化，然后 `fg %2` 或者 `fg %1` 把它放到前台来，它又回来了，再 Ctrl+Z 又回去了。唯一的区别是终端里一次只能显示一个应用，而背后就是刚才说的那套很讨厌的 session、process group 概念。

> **结论**：`job control` 是为了实现"像 Windows 那样用 Alt+Tab 切换程序"而做的一整套机制，它顺带让我们知道了 Ctrl+C 可以发给谁。

具体到操作层面：最小化的时候发的是 `SIGSTOP`；做进程切换的时候，用 `tcsetpgrp` 这个系统调用去标记哪一个进程是前台、哪一个是后台。只有前台的那个进程才会收到 Ctrl+C 带来的 SIGINT，后台的不会——后台进程可以继续运行，但我按 Ctrl+C 永远只能影响前台。如果当前没有前台进程，我按 Ctrl+C 谁都影响不到，后台的 `yes` 照样在输出。

这是一个非常难受的历史遗留问题，而且它甚至成为了 POSIX 标准的一部分。一旦成为标准的一部分就没有办法了：任何声称 POSIX 兼容的实现都必须实现这套机制，才能和 Bash 这类已经依赖这个标准接口的软件保持兼容。你可以说它不好，但你不实现，就用不上整个开源生态。

### 会话与控制终端：SSH 断线为什么杀掉你的训练任务

回到那类更粗暴的地方。你们有没有租过云主机？如果有，考虑这么一件事：你在云主机上跑 `vi`，或者跑一个 long-running program，比如以极低的价格——你们有学生身份可以薅个羊毛——租到 GPU，在上面训练一个东西，不用自己买卡。跑一个要很长时间的程序很正常，你平时在自己终端里就是这么跑的。但是网络连接一断，**你的程序也终止了**，你必须从头再跑一遍。

这叫 hang up。原因就在登入这一侧：SSH 登陆（或者真正的 TTY 登陆）的时候，会引入一个叫 session 的最大分组，子进程会继承父进程的 session ID；每一个 session 又会关联一个控制终端。当这个 session 的 leader 退出的时候，整个 session 里的所有进程都会收到一个叫 `SIGHUP` 的信号，而这个信号的默认行为就是退出。

所以你们知道有个命令叫 `nohup`——它的意思就是"请忽略掉那个 hang up 的信号"，忽略之后才能继续执行。你们也用过的 `tmux` 是另一条路：它不会收到那个 SIGHUP，所以可以继续在后台运行。而在 session 内部又有进程组，那是为了做 Ctrl+C。

相应的也有一系列操作系统 API：`setsid`、`getsid`、`setpgid`、`tcsetpgrp`。`setsid` 在 2 号手册的 syscall 页里，描述是 "creates a session and sets process group ID"。

到这里可以停一下，看看我们为了这些功能往操作系统里加了多少东西。因为我们有 CrazyOS，最早讲的时候操作系统简单到就是一个 `struct proc`，你把东西写进去就行了；后来进程里多了 uid、effective uid、saved uid。随着 UNIX 系统长大，为了解决各种各样的问题，它打了无穷多的补丁。等到 2025 年、2026 年再看，会发现这些补丁可能其实并不是那么需要。

### 换一套设计会怎样：Android、容器，以及重新设计的机会

刚才我们展示的这一切麻烦，都是为了实现一个类似 Windows 窗口管理器的 job control：最大化、最小化、关闭那个叉叉按钮，全都能用系统调用做出来。但如果回过头想，你**并不绝对需要把进程绑定到设备上**。

Android 就有一个很有意思的设计：每一个 app 都是一个不同的用户。它借用了 Linux 的权限隔离——我作为一个用户，不能随便访问另一个用户的任何东西，除非另一个用户以某种方式允许我。所以 Android 有一个功能叫"强行终止"：很多流氓应用一直驻留在后台，除非你强行终止；而这个强行终止，就是在操作系统里直接遍历属于这个 uid 的所有进程，全部杀一遍，给一个 `SIGKILL`，它就没了。完全 OK，你根本不需要什么 controlling terminal，因为 Android 本身是面向图形界面的。

另一些程序，比如 snap，是在完全隔离的沙箱里运行。还可以这样想：我不需要 process group，我们今天有容器、有虚拟机，有 namespace、有 cgroups。当一个程序启动的时候，它就处在一个虚拟机里；你想把它杀掉，就把这个虚拟机关掉。在虚拟机里创建的程序仍然属于同一个虚拟机、继承了 PGID，所以这套逻辑也解释得通。关键在于：**当年设计进程组、session 的时候，还没有想到未来会有容器、Docker 这种东西**，所以它被迫做了一个 workaround，而 workaround 一直活到了现在。

> **提示**：如果给你一次重新设计系统的机会，你可以做得更好。这也是我觉得 AI 时代所有同学都可以去突围的一个地方——大厂、要维护老代码的人必须遵守旧标准，但如果你有胆量把旧世界整个破坏掉，建一套新的世界、新的秩序，那里面可能会有机会，尤其是 AI coding。

这就是终端和 job control。最后把你们的第一性原理放回来：**终端只是在和计算机操作系统交换字符**，其他所有的行为都是可以定义的——或者说，是你作为一个操作系统设计者可以定义的；最终操作系统设计者收敛到了这样一个方案，仅此而已。

### Shell 是一门只有字符串的编程语言

那个命令行不只是一个"敲命令的地方"，它是 Unix philosophy 的载体，是 Unix philosophy 背后的编程语言。还记得 Unix philosophy 说的是 keep it simple, stupid：希望每一个工具都能做好一件事，然后把工具用文本的接口连起来，用管道把一个程序的输出交给另一个程序当输入。而背后这件事，相当大的程度是靠 Unix shell 的编程语言支撑的。

> **提示**：你们想过吗？Shell 其实是一门编程语言。有个挺有意思的程序员笑话：当你坐在 Linux 面前、坐在 VT100 面前的时候，你按下的每一个字符都是在编程。哪怕你看起来只是在整理自己的文件，你输出的每一条命令在 Shell 看来都是一个表达式或者一个程序，它把这个程序解释执行了。

而且它是一门基于**文本替换**的极简编程语言，设计跟 C 这些语言完全不一样——它甚至连整数都没有。你可以想象一门没有数据类型的编程语言。

那在早期的 Unix 里要算 1+2 怎么办呢？你得把两个要加的数字变成字符串，然后调用一个外部命令——也就是说，起一个进程。这个命令叫 `expr`，你可以给它 `expr 1 + 2`，它会告诉你 3。但如果你写成 `1+2`，它算不出来，因为那只是一个字符串。注意，`expr` 并不是一门语言的解释器——虽然可以在几十行、一百行代码里就实现一个 `expr`，那正是非常典型的 Unix philosophy。**必须用空格**，因为只有当 1、`+`、2 被空格分开时，Shell 才会把它们切成三个字符串放进 `argv`；而 `expr` 匹配的是 `argv` 的第二个字符串，看它是不是加号。`expr 1 '<=' 2` 这样写也同样能得到正确结果。

> **易错点**：`expr 1+2` 不是算术，它只是一段字符串传给了一个程序；Shell 这一层没有整数，没有算术类型。

这门语言干的事情，是把你敲的任何一条命令翻译成一组系统调用的序列——从命令到操作系统。因为操作系统无非就是启动进程、打开文件这些东西；而你最终需要 `fork`、`execve`、`waitpid`、`pipe`，还有文件描述符的腾挪。Shell 的语法成分也是围绕这个思路设计的。

### 它把一条命令翻译成一组系统调用

#### 预处理与文本替换

Shell 和 C 是一脉相承的，都在做字面意义上的文本替换。你们在 C 里可以用 `#define` 定义一个字面意义上的常量，甚至定义一个单看并不合法的东西（比如一个括号逗号括号），再拼出一个 `(X)` 这样合法的表达式——预处理器做的就是纯文本替换。Shell 也一样。

它可以把**一个程序的输出**以字符串的形式直接贴进来。甚至可以把一个程序的结果包装成一个文件描述符，把这个文件描述符的**路径**贴进来。这个非常有用：比如你有一些数据是动态生成的，从网络上拉回来的，你没法容易地把它保存成文件——除非你再执行一个命令。用这个语法就可以生成一个路径，比如 `/dev/fd/63`，然后你用 `cat` 去读这个路径，就把它里面所有的输出读出来了。这能干什么？你可以去两个网页上爬两份数据，然后直接做 `diff`，它会给你一个 diff。因为有些工具必须输入文件——`diff` 就需要两个文件，它没有办法把两个文件都放到标准输入里，这也是 Unix 设计的一个缺陷；但各种各样的 workaround 把它解决掉了。

#### 重定向

所谓重定向，就是把文件描述符换一个位置。因为 `execve` 的时候，新程序会继承父进程的文件描述符，所以父进程先 `fork` 一份自己，把编号为 1 的文件描述符替换成指向 `a.txt` 的文件描述符，然后 `execve`：

```text
 shell: read line "ls > a.txt"
   fork()
     child:
       fd = open("a.txt", O_WRONLY|O_CREAT|O_TRUNC)
       dup2(fd, 1)            # fd 1 现在指向 a.txt
       execve("/bin/ls")      # ls 往 fd 1 写，就写进了 a.txt
     parent:
       waitpid()              # 前台任务，等一下它
```

`execve` 执行的是什么命令都无所谓，可以是很长很长的一条命令；**但凡它往编号为 1 的文件描述符里写数据，就会写到 `a.txt`**。这就是把一条命令翻译成系统调用的结果。用一个大于号重定向标准输出，用一个小于号重定向标准输入，把标准错误用一个很丑的语法重定向到 `/dev/null`，都是同一个套路。

#### 控制流

Shell 也支持控制流：命令一运行完就运行命令二，还有**短路求值**。这和 C 语言里的 `&&` 是一样的道理：左边是 false（或者 0）的时候右边就不算了，因为 0 和任何东西与起来都是 0；`||` 类似，左边已经是真，就不用算右边。

于是你们经常能看到这样的写法：`ls` 如果左边成功，我就执行右边的；左边失败，我就不执行。这就是"如果左边成功了我就执行右边"。反过来的用法也常见：**如果我想在失败的时候做另一件事**——我想试一试某个工具能不能用，能用就结束，不能用就再试下一个工具，一个接一个，直到有一个能用为止。

> **结论**：这也是为什么你写脚本、看别人的脚本时，脚本头上那个解释器一般写 `/bin/bash` 或者 `/bin/sh`，而不会用 fish——fish 不标准，它虽然好用，但会让你翻车。

#### 管道

管道是上一节课讲过的：用 `pipe` 系统调用创建出两个文件描述符，一个指向管道的读口，一个指向写口；这两个文件描述符在 `fork` 之后同样被继承。于是我把一个进程的写口留下、读口关掉，把另一个进程的读口留下、写口关掉，再腾挪一下文件描述符，就实现了把一个程序的输出接给另一个程序当输入。

你会觉得这段代码确实写得不优雅：有一个输入的 fd、一个输出的 fd，你要 `fork`，然后到处腾挪。可这已经是写得比较好的一份代码了，看起来还是有点难受。

### 读 `man sh`：知道什么能办到

虽然 AI 时代好像学什么都容易了，学什么反而成了一个老大难问题——你们会进入一种虚无的状态：什么都能学，那好像什么都不用学了。但我每年在操作系统课上都会给大家推荐 `man sh`，它的标题是 command-line interpreter。

我讲得很快，很多细节你可能没跟上，而这里面还有我根本想不到的宝藏。比如刚才讲到重定向，我可以把一个程序的输出重定向到另一个文件；那如果我想要**追加写入**呢？手册里有——它叫 append the standard output to file。你还可以把编号为 2 的、也就是 stderr，追加到一个文件里。这里有无穷多的宝藏。

在 AI 时代为什么还要去遍历这个文档？我建议你们这样做：把这本手册**非交互地直接打印出来**，而不是在命令行里用分屏的方式交互着看；打印出来以后，比如给它一个管道传给 `vim`，你就能看到手册确实长这样。我更强烈建议把它管道给一个 AI agent——Unix philosophy 在这个时候竟然还在发挥余热，让它 make a summary，让 AI 帮你总结。你读了这本手册，或者在 AI 的帮助下读了，就知道什么事情是能干的、什么事情是不能干的。

> **提示**：这个时代你们最需要的是一个清晰的概念：什么事情是能办到的。因为你没有办法做自己想象不到的东西，而扩大想象力的方式就是去看别人想到了什么。这本手册里有很多你没想到过的东西——原来操作系统设计者、shell 设计者在这一套系统调用之上还能做这些功能。

手册里有控制流和循环，有变量和参数，还有 special parameters。你可以直接跟 AI 说 "special parameters"，让它展开给你介绍；对其中任何一个部分感兴趣，都可以让它讲。很短的时间里，你就能对整个世界有一个更好的概念和理解——这就是你想象力的来源。

### 这套设计的裂缝

当然，Unix 的 Shell 也不是绝对好。它是一次无奈的取舍：为了 1970 年代的算力、算法和工程能力，当时只能实现几百行的系统，后人就只好将错就错了。

有意思的例子：`ls` 重定向给 `a.txt` 之后输出已经没了，再管道给 `cat`——这不就是未定义行为吗？不同的 shell 实现不一样。在 fish 和 bash 里你什么也看不到；而在 zsh 里，它会变得像 `tee` 一样，既把文件写进去，也在标准输出里让你看到。设计者自己大概也没想清楚，反正他觉得这样对你更好，就这样做了。

还有一个非常有意思的例子：`sudo` 在这种情况下是不起作用的。为什么？你们回去可以想一想，如果一时想不通，让 AI 帮你想。

最后给大家准备了一个彩蛋：一个没有任何依赖的、free-standing 的 shell——所有的东西，包括系统调用，都是用汇编写的。

这堂课讲的其实是教科书上往往没有的东西：终端、job control、Unix shell。希望你们记住的那一条仍然是——终端只是交换字符，Shell 是把你的命令行翻译成系统调用序列的一门只有字符串的语言。
