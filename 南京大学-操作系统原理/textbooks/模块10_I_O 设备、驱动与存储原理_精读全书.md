## 一个 Token 的旅程：从一次 curl 到数据中心的并发

### 并发这一路，我们从哪儿出发

回顾一下并发编程里我们到底学了什么。我们学了"多处理器编程从入门到放弃"：入门的时候就是 spawn 的 API，它相当于打开了一个魔鬼的盒子。你能 spawn、能 join，理论上你就可以实现任何的计算图。你可以放一个线程出去，当然你还有可能需要和别的线程同步，于是有互斥锁、条件变量、信号量这些机制。有了这些，你就能创建计算图，理论上你就能并行化任何程序。我们甚至还有一个实验——gpt2.c，你去那堆代码里找到它的热点，然后把它做线程的并行化。这个实验可以早一点开始，虽然 malloc 应该是整个实验体系里面最难的一个。

然后我们讲了很多种"如果对 spawn 和 join 不满意，我们还能怎么办"。比如实现更轻量级的线程，像 coroutine，配上 non-blocking 的 I/O；再比如 goroutine，它既能像协程一样轻量级切换，又能在多处理器上并行执行，所以特别适合拿来写后端的业务代码。还有 JavaScript 里的 Promise 和 async/await，它也是用来描述一个计算图。

```text
spawn / join  (原语)
   |
   +-- 互斥锁 / 条件变量 / 信号量        显式同步
   +-- coroutine + non-blocking I/O     更轻的切换，但要自己处理 I/O 语义
   +-- goroutine                        轻量切换 + 多处理器并行
   +-- Promise / async、await            把计算图写成数据流
        |
        +-- 共同点：都是某种 spawn 与 join
```

关键在于最后一行：这些并发编程模型，本质上你都可以把它们想象成某种 spawn 和 join，只不过"怎么并行"这件事不在你的编程语言之中，而是由整个运行的框架帮你搞定了。

### 连 CPU 也在并发

上节课我们讲了一个很有意思的故事：我们自己的 CPU，它本身就是并行的。你看起来它执行的是 1、2、3、4、5 这样顺序的指令，但实际上它内部还有一个"编译器"在工作。这是从 1990 年代到 2000 年代一件非常关键的技术，它撑起了摩尔定律的持续增长。这个技术大概到 2005、2006 年前后就开始失效——大家发现，单处理器性能继续做大，收益反而在变小，必须在硅片上放更多的处理器，才能把能效比救回来、把摩尔定律维持住。

#### 处理器内部的重排：从 1990 年代到 2005 年

这段历史的走向值得记住：处理器内部重排指令，是为了在单核上榨出更多的并行度；等到榨不动了，架构就从"把一颗核做快"转向"在一颗硅片上放很多核"。后一条路要真正走到极限，就要最大化计算的密度与能效比——最理想的情况是，处理器里负责译码的部件、以及它占用的电路，消耗的能耗能降到零。

#### SIMD 与 SIMT：把译码电路的开销压到最低

顺着这个思路，就有两种技术。

一是 SIMD：在一条指令里操纵一个 512 bit 的很大数据，把这个数据分成好多块，同时做同一个操作。

二是更有意思的编程模型：CUDA，也就是 SIMT。我们有很多份 ALU 执行单元、很多份寄存器，但只有一个共享的 program counter。它的样子是这样的：

```text
                共享的 program counter
                        |
        +---------------+---------------+---------------+
        |               |               |               |
     ALU#0           ALU#1           ALU#2    ...    ALU#n
        |               |               |               |
   regs#0          regs#1          regs#2          regs#n
   index.x=0       index.x=1       index.x=2       index.x=n
   (线程 ID 存在各自的寄存器里，可以算出坐标 / 数组下标)
```

这个模型之所以聪明，就在于"寄存器各自独立"。即便这一组线程——CUDA 里的术语叫一个 thread warp，一个线程束——执行的是完全相同的指令，甚至遇到 `if (a) ... else ...` 这样的分支，它也会把两个分支顺序执行一遍，只是在执行某一支的时候只激活满足条件的那些线程，其余线程相当于什么都不做。

CUDA 靠什么实现高性能并行计算？靠的就是每个寄存器里的值不同：每个线程的 ID 就在寄存器里（比如 `index.x`，再加上 `x`、`y`），它可以根据这个 ID 算出屏幕上的坐标，或者一个数组的下标。于是这个线程算出 0、那个线程算出 1、第三个算出 2……如果下一条指令是一条 store，那么从整个线程束来看，这次 store 读写的是一段非常长的、最好是连续的内存，内存控制器上就能发出一个 burst 的 read 或者 write，速度非常快。

> **提示**：这一节只是开了个头。即便这样聪明的模型也还不够高效，怎么再压榨出最后一点点性能，是我今天还要接着讲的内容。

### 把程序打开，看它到底做了什么

顺着这份 strace，它给了我一个流程，第一幕是 DNS 解析。

> **提示**：你们网络课会不会考 DNS 用哪一个端口？53。你反复观察这些程序的执行，就会对这些事情留下印象。考试的时候你未必能立刻想起来 53，但你看多了以后，如果这是一道 ABCD 选择题，你会明显地感觉到"53 这个东西我见过"。

第二幕是 TCP 连接的建立。这里有一些建立 TCP 连接的系统调用，其中比较重要的就是 `connect`：它用 `connect` 去连接另一个 IP 地址的端口，`inet_addr` 那个地址，端口 443。然后 TCP 和对方做一个三次握手。都正确，都正确。

但你还可以做得更多一点。如果你愿意再和 AI 对话一小会儿，你在自己的机器上就可以真正看到这个过程里更多的信息。比如我让它用 `dig` 去看一下这个 DNS 到底发生了什么。

```bash

traceroute api.deepseek.com
curl -i https://api.deepseek.com
```

随着你在本机上把这些行为一点一点展开，就会有越来越多有趣的问题，指向今天真实的计算机系统里会发生的事情。

#### 一个域名，不止一个 IP

我们都知道，用 curl 也好、看刚才的 strace 也好，远端的服务器就是"一个 IP 一个端口"，而 443 是 https 的端口，所以理应如此——对我的课程主页也是这样。但换成 DeepSeek 就非常有趣了：`api.deepseek.com` 如果去查它的 IP，你会发现它不止一个 IP。

为什么会有不止一个 IP？因为这是一个很大的服务提供商，而这个服务提供商又用了别家的服务去做分布式的 DNS。它告诉你这两个 IP 都可以用：`58.49.197.113`、`218.92.146.107`。而且如果你在地球的另外一个地方执行同样的命令，你很可能会看到不同的 IP。

> **结论**：一个真正严肃的、向全球提供服务的网站，它背后比你想像的要复杂。DNS 会有很多个可能的 IP；你甚至能查出这是腾讯云的 CDN 域名——这个 API 请求并非直连 DeepSeek 的源站，而是走的 CDN 节点。

#### 一跳一跳地走过去

同样，如果你想知道这个包是怎么到达彼端的，可以用 `traceroute`。这个命令在网络课上讲过，它的原理是操纵 time-to-live 的值：一点一点让它的寿命长一点、再长一点，因为 TTL 长一跳，你就可以往更远的一个节点走一跳。它就用这个方式探查这条网络链路上经过的那些路由器。

不管怎么样，这些网络课上讲的内容我们先跳过。刚才那个请求，终究会到达数据中心的另一台计算机。

### 转发比处理便宜

那台计算机大概率也不是真正给你提供服务的服务器，而是一个 load balancer。它同样只是个代理：它一秒钟可能会收到很多个请求，然后它不会实际处理这些请求，而是把它转发出去——它手上可能有 16 个或者 32 个 worker，于是它把这个请求随机地、或者按照某一个方式映射到某一个 worker 上，转发过去。

```text
                    全世界的大量请求
                          |
                          v
                    load balancer
                  (不处理，只做映射)
          +--------+--------+--------+
          |        |        |        |
       worker   worker   worker  ... worker     16 或 32 个
          |        |        |        |
          +--------+--------+--------+
                          |
                    真正的业务逻辑
```

这里的关键是：**转发的代价远远小于处理的代价**。这样一层一层地转发，最终我就可以扛住一个非常非常大的业务量。

到了另一台机器，假设所有业务逻辑都处理完了，你就真正能看到它的 response。这一步很有意思，我试过：

如果你去访问 `api.deepseek.com`，当然它会给你 401，因为我这里没有一个正确的 key。它告诉你，HTTP 的 header 里有一个 server 字段，叫 OpenResty——这很可能是另一个 API 的网关。但如果你是去访问 `deepseek.com`，DeepSeek 的 server 给你的又是 Cloudflare 的一个东西，也是一个类似代理的角色；而且它还给了我一个 error request blocked，它禁止了我这次 curl 的访问——因为我每一个 HTTP 请求都带着一个 User-Agent。

你慢慢跟 AI 对话，就能了解这个应用层协议里到底发生了什么。但从操作系统的意义上，我还得回到操作系统课：这一切都是由那几个系统调用实现的。刚才那份 strace 里，你看到的是 send、recv（receive），是 connect，是你对这个文件描述符做一个 read。你做这些操作，看到的就是文本形式的数据——我的命令行用的是 `curl -i`。

```text
应用数据
  + 应用层头   (HTTP header: Authorization / User-Agent / ...)
  + 传输层头   (TCP)
  + 网络层头   (IP)
  + 链路层头尾
----------------------------------------
每一层包裹都会加上头、加上尾——你要交"网络税"
回来之后，应用程序收到的仍然是一段文本形式的信息
```

### 到了业务节点，麻烦才刚开始

不知道的部分我们就不知道了——后面发生了什么，我们其实看不到。但可以告诉大家的是，请求最终会打到一个实际的业务节点上。业务节点收到的、来自本机的这个请求里，包含了 header 里我刚才写的那个 DeepSeek API key（我是从环境变量里读出来的），以及 body 里的那段 JSON。

这已经很复杂了。但真正复杂的麻烦才真正刚刚开始。

你们觉得，我向 DeepSeek 请求——我给你一段 JSON，你去算一个东西回来，比如给我 complete 一个 token——背后真的就这么简单吗？

在社交网络的时代，或者更早的 Web 1.0 时代，HTTP 后端基本上就是干这件事：查一个数据库。你想，如果我们是在刷淘宝，或者用 QQ、微信，那么当你的请求到达服务后端的时候，一般来说要么是我问微信要聊天记录，要么是我要一个图片。像图片这种，它已经在 CDN 上做好了分发，你基本上就是根据一个 URL、一个很长的 hash，把那个文件取走。所以这基本上就是一次数据库查询——不论是淘宝、抖音还是微信。

但对于大语言模型来说，它背后干的事情还真不少。首先它和微信、淘宝是一样的：它要做 authorization，要判断你的 API key 是不是合法。如果你的 API key 合法，它给你提供服务，它还要计费。计了费之后还要审计——你们经常看着 DeepSeek，你问它一个比较敏感的问题，或者一个可能不合适的问题，并且你成功让它"破甲"，让它开始输出那些不能输出的东西的时候，你会看到它输出了一部分，然后突然间那些内容就消失了。这些都是后端需要干的事情。

> **提示**：所以，我们学过的这些操作系统的 API、并发编程的知识，默默支撑了你们看到的这一切。把我们做过的所有实验拼起来，你就得到了一个相对来说还是比较完整的计算机科学的 big picture。比如刚发布的那个 httpd 实验：你真的要实现一个 HTTP 后端，而且它真的可以支持 CGI。在 BBS 的时代，一个实验作业就可以支撑起一个网站——真的可以支撑起一个创业公司做得足够好、能挣不少钱的网站。虽然在今天看来，AI 一秒就能把这个东西给你解决掉。

今天我分两部分来讲数据中心里到底发生了什么，主要从并发编程的视角讲故事：一个是数据中心里面的并发编程，另一个是从 token 到 tensor——你的一个 token 到底是怎么产生的。

### 数据中心的上下半场

先说数据中心。刚才我们说，全世界的人都可能访问你的同一个 API、同一个 endpoint：`api.deepseek.com`。这些东西都是在数据中心里处理的。

> **定义**：数据中心是 *a network of computing and storage resources that can enable delivery of shared applications and data*——它是一套算力与存储资源的网络，用来交付**共享**的应用与数据。关键词是"共享"，因为它是由全世界的人一起用的。

数据中心有上半场，也有下半场。上半场就是我刚才说的那个后端应用：从 1990 年代的雅虎、新浪，到 Facebook、微信、淘宝，再走到移动互联网，其实都属于上半场，只是规模在不断地增长。你所有的数据都在云端，云端的好处是你的手机、你的电脑，它们的消息是完全同步的，你的 personality 也是同步的——云端有你的完整 personality。同时，这也意味着我们其实没有任何隐私：理论上说，腾讯有你所有的 QQ 和微信聊天记录，他就知道你是一个什么样的人。只是现在法律不允许他拿这些信息去做某些事，但他到底有没有做，谁知道呢？当然也有在法律授权下被允许做的事情，比如你真的涉及刑事案件，双方的聊天记录在本地都删掉了，他还是可以给你恢复回来。

这是上半场，数据库都还在。下半场是从 2022 年到现在，也就是 AI 的推理。

你看到 DeepSeek 的 flash 版本是 284 billion 参数，但它每一次的 activation 是 13 个 billion——那也是很大的数字。Pro 是 1.6T 参数，activation 是 49B 参数。而且这只是 per token 的计算量，**不包括 attention**，算 attention 的成本我一会儿会说。大家应该都在 DeepSeek 发布的那个微信里看到过一行红色的小字——大概是说，等昇腾 950 的计算节点上线以后，它还会再降价一次。它本身卖得也不贵，虽然不能算特别便宜，但现在价格是特别便宜的；等有了新的算力，它声称可以卖得更便宜。

| 维度 | 上半场（1990s ~ 2022 前） | 下半场（2022 ~ 现在） |
| :--- | :--- | :--- |
| 核心负载 | 后端应用、数据库的增删改查 | AI 推理，per token 的参数计算 |
| 数据形态 | 消息、图片、订单、聊天记录 | 上下文、token、attention 的中间量 |
| 规模驱动力 | 用户规模与移动互联网 | 参数规模与外推的算力成本 |
| 典型指标 | 吞吐、延时、可靠性 | 单 token 成本、推理延时、可弹性 |

这也意味着，数据中心其实是一个产业链。当你谈一个需要服务全世界人民的应用时，你就知道它不是一个"我们做一个 online judge 的题目，这个题目给你一个 accept 就结束了"的事情。你要建数据中心，建数据中心需要土地、需要水、需要电、需要人、还需要保洁——这是一个很复杂很复杂的问题，我们每一个人都不可能完全知道这里面所有的细节。

我觉得我们在学校里面挺有意思的：大家都在做题，比如操作系统课，我一直都在讲这个系统怎么用、那个系统怎么用，我们却很少讲这些题目是怎么来的。我有时会说，操作系统经历了某一个历史时期的发展，所以它里面多了这个、多了那个。但实际上我们可能反过来了：操作系统可能不是那么重要——当然在这门课上它很重要，因为我们被设计成要在这门课上学操作系统的知识。真正重要的是 drive 这个操作系统发展的那个市场。市场的供需关系是永远存在的：如果有一天计算机不存在了，那整个市场就不存在了，我们每个人还是得找工作。所以朝阳产业永远需要更多的人，就像数据中心上半场到今天下半场的变化。

你们都很在意毕业能不能找到工作、薪资怎么样，然后你们听到的永远是"字节系又拿到了一个让人无法拒绝的年薪"，于是你就想，如果我也能有那个年薪就好了——每个同学都是这样想的。你们每天刷公众号，制造这样的焦虑。而焦虑的背后，其实是你们不太知道这个世界还有一个别人不教你的、我们上课也不太教你们的世界模型，因为上课更多的是关注技术。我们的技术总有一天会过时，我们操作系统一直都在，但这些技术都是和产业的结构、市场的环境息息相关的。你们作为做题家都很不容易，进入社会以后还会经历一次重新学习：一个产业链、一个数据中心、一个公司的本质到底是什么？它的供应链是什么？它是怎么运转的？什么叫股权？我相信你们这一代同学现在都应该知道这些概念了。

所以你们在课堂上学的，其实是去体会：当我讲一个技术的时候，它发展的那段历史是什么？在什么时间点这个技术被需要了？这个技术是怎么被设计出来的？然后你要有设计出这些技术的能力，并且能看到未来会发生什么。每个同学现在就可以想一想：等你毕业的时候，这个世界会发生什么样的变化？你应该成为一个什么样的人，才能适应这样的变化？

> **结论**：所有的这一切都指向一个回答——你们每一个人都必须成为一个超级个体。如果你不是的话，你在毕业的时候一瞬间就被淘汰了。我在上课的时候不断教大家 AI agent 应该怎么用，因为我不断有一种感觉：我的 PhD 学生可能还不如我的 agent 好用。那就意味着他们有一天可能会被淘汰掉。这是一个你们可能需要想一想的事情。

### 一个请求背后那些"小"事

说回来。一个请求到达 `api.deepseek.com`。在大语言模型火起来之前，其实我们已经有很多应用和它非常接近了：很多实时的小数据的增删改查，也就是 CRUD。所以现在 CRUD 工程师已经被淘汰了，已经彻底被 AI 取代了。

这些小的数据处理包括：你在淘宝上要下一个订单；你发一个帖子，就要把这个帖子写到数据库里；有人要查聊天记录，你就要从数据库里把聊天记录取出来。这就是增删改查。它还包括用户的鉴权——你的 API key 合不合法；我发一条弹幕，这个弹幕在第几分第几秒显示；还有计费信息——一次 API call 我要收你多少钱，它的缓存是不是命中，应该用哪一种 pricing，是峰还是谷。这些各种各样的、相对比较小的处理，全都属于这个范畴。

再比如 DeepSeek 本身还是一个完整地向外提供功能的网页，有一个 `deepseek.com` 的网页，它刚才我们看到的后台和那个 API 是不太一样的。那个网页会保存你所有的完整聊天记录，所以你今天跟它聊完，明天还可以回到那个网页上，点开昨天的聊天记录继续追问。这些都是传统上非常经典的数据中心里的海量分布式数据处理要干的事情。

除了这些增删改查以外，数据中心里还有很多别的东西。哪怕只是一个公司自己的业务，它都有一些**半离线**的数据处理。打个比方，一些周期性的记账：我们前面说过，并发数据结构想设计得好很难，你光做一个 `sum++`，想实现一个 scalable 的 `sum++` 都很困难。而记账很可能是在一个分布式数据库上记的，它会有一些延时；要反映到一份精准的账本上，比如日账单、月账单，真的要给你计费的时候，它可能还需要一次半离线的数据处理。再比如备份，它隔一段时间就会备份；还有数据大看板。

然后再到**离线**的那种非常非常大的数据处理，包括神经网络的训练——每一轮训练都要几百万美元；还有内容的索引。分布式数据处理的诞生，就是因为 Google 那个时候可以用分布式的机器把整个互联网给存下来了；但存下来以后，它还需要运行一个程序，把它变成一个搜索的索引。

> **提示**：我现在真的用搜索越来越少了，因为我的大语言模型可以搜索，我还可以给它一个更难的问题，让它帮我解决。但在可能十年以前，你学会搜索、掌握 Google 搜索的能力，你就是超级个体，你和别人就有 10 倍的生产力差距。今天你会用 GenAI，你跟别人就有 100 倍、1000 倍的生产力差距。就是这么来的，所有的应用都无一例外——Google、Meta、通义千问、DeepSeek，各种各样的应用。

### 从 C10K 到 C10M

在数据中心里面，有一个 1999 年由 Dan Kegel 提出的问题，叫 C10K problem：concurrent 1 万个 client 的问题。也就是说，在 1999 年，Web server 或者说那个时候应用的规模，已经增长到可能会有 1 万个 client 同时访问你的应用。那个时候的机器，一个服务器多多少少其实是可以扛住这个计算量的——那时候多处理器系统还不流行，但在服务器领域已经有一些了——所以你基本上还是能扛住这 10,000。但是你的编程语言的机制、你的软件写得不好，你是扛不住这相当于每秒 1 万个请求的并发的。

你想，今天上课一开始我就说，所有并发编程都可以用 spawn、join 的模型来理解。那你就会去创建一个 request：每次就像我在 strace 里看到的那样，你用系统调用去建立一个连接，建立完连接以后你就 `pthread_create` 创建一个线程，然后这个线程去跑。如果软件写得不好，你就没有办法支撑这个 C10K。

```text
C10K (1999, Dan Kegel)                        C10M (随后)
  1 万并发 client                                1000 万并发 client
       |                                              |
  机器勉强扛得住                                  摩尔定律以年（18 个月）为单位慢慢走
  软件机制扛不住                                  10K -> 10M 的跨度不是同一个问题
       |                                              |
  催生:                                         要求:
    select -> epoll                              高吞吐 + 低延时 + 高可靠
    Nginx / 事件驱动架构                          光有协程、异步事件编程不够
    goroutine
```

正是这个动机——99 年大家提出的这个问题，催生了很多操作系统的进步，包括 `epoll` 这个系统调用。在 `epoll` 之前，我们还有一个系统调用叫 `select`：`select` 和 `epoll` 的功能基本上是差不多的，都是我可以监听多个文件描述符，等到任何一个文件描述符里面有数据，我就可以继续。但是 `select` 的 API 设计并不是为这个 C10K 准备的，所以它在解决这个问题的时候会有严重的性能问题。随后又催生了一系列的东西：Nginx、事件驱动的架构，包括 goroutine 这样的并发模型，都是在这个历史背景下产生的。

等 C10K 问题解决以后，很快我们就发现：如果我能够服务 1 万个 client，我就可以服务 1 亿个 client。所以就有了 C10M 这样的问题——当然这是 1000 万，有 1000 万个并发。在这个意义上，因为摩尔定律还是相对缓慢地发展，它以年、以 18 个月为单位，如果你一下子要从 10K 变到 10M，而且还有各种各样的负载要求，那事情就完全变了。

所以数据中心的并发编程，光有我们前面说的协程、或者这种异步事件编程，其实还是不够的。因为对数据中心来说，**产品的体验就是一切的生命**。他们要的是真正高吞吐、低延时的事件处理，虽然绝大部分也都只是增删改查。

但这个问题比你们想象的要困难。因为处理一个事件，比如说淘宝要下一个单，它不仅仅是那一个业务系统里面的事情：淘宝会涉及到支付宝，支付宝还要涉及到银行，它有好多的业务逻辑，可能会有 1000 多个模块都被拉起来。在这种意义下，你依然要保持整个系统的性能，就变得非常有挑战性。很多程序的性能至今都没有解决，比如一个微信小程序：你会很明显地发现，如果你用一个 app，你的体验对网络延时的容忍、对网络故障的容忍就会好很多；但如果你是一个微信小程序，它的体验相对来说要差很多。

我举一个例子。你们在做 malloc 和 free 的时候已经觉得很痛苦了，然后你会想：实际系统里我就用一个简单的方法，一把大锁保平安。那会导致什么呢？比如说一个并发的 hash table，它已经有几十兆大了，这个时候你要对这个 hash table 做 resize。resize 的时候，你旧的那个 hash table、那个数组就不能要了，你会重新 allocate 一个——又是一个几十兆的——然后你会做一个几十兆的 memory copy，把旧内存拷到新内存上；甚至是一个遍历，它的代价比 memory copy 还要再高一点。拷完了以后，你再把旧的那块释放掉，把整个 hash table 迁移到新版本。

那如果你要做一次几十兆的 memory copy，这个延时可能就是接近几十毫秒、上百毫秒——就算它 100 毫秒。而这 100 毫秒就意味着：在这段时间里，所有可能几万个或者十几万个并发的 client 都要等待 100 毫秒。这对你的 P99 latency 就是毁灭性的伤害。

> **注意**：这里有一个非常有名的调研结论——每当你的延时增加 100 毫秒，你的用户就会有成倍的流失。因为他觉得你比较卡。你最好是及时得按下一个键它就立即有返回；如果你让他觉得慢了，他就会觉得你的服务做得并不好。

而在这种海量请求到达系统的时候，理论上说其实世界上没有东西能扛得住。比如说前两年雷总在小米汽车的发布会上展示小爱同学的功能，他叫了一声"小爱同学"。一般来说，关注小米汽车的人都是米粉，所以他们家里至少都有一个小米设备，比如小米音箱；而当时在看直播的人，家里电视上也有。于是雷总叫出小爱同学的时候，全国的小爱同学都被唤醒了，就形成了一种有点像 denial-of-service attack 的效果——海量请求突然到达数据中心，它也没有办法服务得过来，就在那一刻，全国的小爱音箱都在小米汽车发布会上同步瘫痪了。

我们其实想要解决的就是这样的问题。数据中心里的并发编程真正想解决的是：**在一个很大的弹性范围内，当你的用户突然增长的时候，你的系统能接得住；当这个峰值过去以后，你的系统又可以把资源给还出来。** 当然不能说无论多少 client 都能扛住，但至少要有这样一个弹性范围。并且，真正麻烦的事情是，你还需要保证一个超高的可靠性——谁也不希望自己的 QQ 和微信聊天记录发生丢失。

所以这就是分布式系统里你遇到的一个最大的难题。

### CAP：不可能定理

上上次课我们说过，有功耗墙、内存墙，这些各种各样的墙。当你撞到瓶颈以后，你的系统想要表现得更好就更困难了。而在分布式系统里，我们面临一个更糟糕的问题，叫不可能定理，叫 CAP theorem。

> **定义**：CAP theorem 说的是，在一个分布式系统里面，consistency（一致性）、availability（可用性）和 partition tolerance（分区容错性）这三者不可兼得。

先解释这三个词。

availability 很容易理解：如果给你一个请求，你最好是马上给我返回，你不能无限地延时我的请求，因为延对我来说是一件很不开心的事情。

partition tolerance 也很好理解：我们是数据中心，数据中心是由网络连接的；甚至我的数据中心是由两个地理上隔离的数据中心组成的，比如南京、北京、杭州。你们如果租过阿里云、腾讯云的服务器，都可以选择一个区。这就意味着区和区之间是有线缆物理连接的。而这条线，没有人能保证它在施工当中不会被挖断，或者因为某些物理原因被挖断，或者因为算法、延时等等问题被延时。

consistency 就是：我做一件事，不管在哪个地方做——我在这儿做 1、在这儿做 2、在这儿做 3——从全局意义上看起来，就是一个先 1 后 2 后 3 的、按顺序完成的结果。

#### 一个必须让妈妈看不见的朋友圈

举个例子你们就能理解为什么 CAP 是不可能的。

今天你想发个朋友圈，说"哎呀我又和女朋友出去玩了"，但你不想让你妈知道。这是一个很常见的需求。所以你会干一件什么事呢？你首先会把你妈拉黑，也就是先设置屏蔽，这是第 1 步。作为计算机专业的同学，你们应该反应过来了：所谓"拉黑"，背后就是我刚才那个 curl 里的一个 HTTPS 请求，也许是一个 `api.wechat.com` 的拉黑——这是一个 CRUD，一次增删改查，它会去数据库里把你妈和你之间"朋友圈可见"的这个数据给抹掉。这个没问题。

接下来你会发这个朋友圈，这是第 2 步。在你的本机上，这两件事有一个先后发生的故事：你等到拉黑请求进去以后，它给你返回了。注意——如果你要 consistency，那你最好是等到这个拉黑真正生效，比如等到这个拉黑在整个全域的数据中心上都同步了，它再给你返回。但那样延时就很大。所以拉黑它肯定先告诉你"我已经拉黑了"，实际上它在后台再去悄悄地拉黑。

然后会发生什么呢？

```text
时间线：

  你的手机 (南京大学校园网)          数据中心 A
     1. 拉黑妈妈  ------------------>  记下"屏蔽"
        立即返回"已拉黑"（后台慢慢同步）
                                        |
                                        |  同步有延时
                                        v
  你的手机 (下一秒切到 5G)           数据中心 B (杭州)
     2. 发朋友圈  ------------------>  写入"朋友圈"
         走不同路由，5G 觉得杭州更快

  妈妈的两部手机：
     南京的一部  -> 数据中心 A  刷不到（拉黑已生效）
     杭州的一部  -> 数据中心 B  刷得到（拉黑还没同步到）
```

你的手机刚才是在校园网上拉黑的，拉黑完以后，下一秒钟你就切换到了 5G 无线网，然后在 5G 上发出了这个朋友圈；你的朋友圈实际上到达了另外一个数据中心。这是完全有可能的，因为它们走的是不同的路由——5G 可能觉得到杭州那个数据中心更快，它就把你的朋友圈发到了杭州。

那这个时候问题来了。如果你要在随时随地都能提供服务，比如你妈想要在这个数据中心上也能看到你的朋友圈、在那个数据中心上也能看到你的朋友圈（假想你妈有两部手机，一部在南京、一部在杭州，同时都在刷朋友圈），那么南京那部手机应该在一个地方刷到朋友圈，杭州那部手机在另一个地方刷到朋友圈。

所以，实际上有可能发生的是：我的拉黑请求进了这台服务器，它会慢慢地再去告诉杭州那个数据中心"这个人被拉黑了"；但是在杭州的那个手机发新的时候，如果这个请求还没到，妈妈就会看到你的朋友圈。虽然你先拉黑了你妈，然后才发了朋友圈，但她还是看见了。这就是因为你有两个数据中心，它们之间是有延时的。

> **易错点**：如果你一定要 availability——刷完朋友圈立即就要能返回；同时你又要 partition tolerance——这就意味着你要容忍"两边的数据暂时不一致"。一旦网络发生分区，你又要求立即返回，那你就永远不可能等到那边的事情被同步过来。它们对同一个共享数据结构的操作一定是同时发生的，所以 consistency 一定会被牺牲掉。

#### 三种取舍

| 你想要的 | 你放弃的 | 结果 |
| :--- | :--- | :--- |
| consistency + availability | partition tolerance | 单机。你假设它可信，一台机器，就既 consistent 又 available |
| availability + partition tolerance | consistency（某种程度上） | 可以做超大规模的分布式系统，但要接受短时间的不一致 |
| consistency + partition tolerance | availability 的一部分 | 请求要等到"拉黑被确认"之后，后一个请求才能完成 |

#### 同一堵墙上的 API key

但是，实际系统的设计者花了大概十年左右的时间——从最早的 Google 那几个分布式系统开始，做到今天——你完全感受不到 CAP 的存在。你完全感受不到这个不可能三角。你就感觉你的数据放在微信非常安全，从来不会丢，并且它给你的服务又非常稳定，几乎感受不到特别卡顿的延时。这都是系统设计：CAP 虽然是存在的，但它用了很多方法来让你感受到一个好的服务体验。

刚才那个拉黑的例子只是其中之一，DeepSeek 的 API key 也有同样的问题。因为我们需要用 key 去做 authentication，然后你要计费。你们到 dashboard 里能看到花了多少 token、要花多少钱，而这个计费是有延时的：你今天的 API 哗一下吐了很多、给了很大的 context input，response 已经返回了，但你刷新的话，可能要等几秒钟或者一分钟，才能看到计费的数据回来。

同样，你的 API key 可以被多个机器使用，你也可以随时 disable 这个 API key。这不就是刚才"先拉黑、再发朋友圈"的那个例子吗？你一边要请求大语言模型 inference 的 API，一边又可以随时把这个 API 给下线。这个时候就会撞到 CAP theorem 的墙——而这就是一个真实的业务系统每天要面对的处境。

回头看这一路：从一个环境变量里的 key，到一次 curl；从 DNS 的 53 端口到 443 端口上的三次握手；从 CDN 节点到负载均衡器背后的 worker；从业务节点上的鉴权、计费与审计，到数据中心里海量的增删改查、半离线记账与离线训练；再从 C10K 到 C10M，一直走到 CAP 这堵绕不过去的墙。这些全部由我们学过的那几个系统调用、那些同步原语、那些并发模型默默支撑着。

而一个 token 到底是怎么被算出来的——从 token 到 tensor 的那另一半旅程——是后面的事了。

## 从 Serverless 到 Tensor Core
> 对应块：BLK42 | 覆盖分集：P21下 | 块标题（分集名）：《一个 Token 的旅程（下）》

一个 DeepSeek API 系统，如果放在数据中心的意义上去看，牵扯到的东西多到吓人。比如在一台机器上可能跑着好多 TWorker，这些 TWorker 是共享内存的；而机器和机器之间都是通过网络连接的，网络上的包甚至可能跨数据中心。你们写 `malloc`/`free` 的时候已经够痛苦了，对吧？但如果要写的程序不但有共享内存、还有网络，而且随时随地机器都可能会 crash、网络会 delay，那就完全是另一个难度。

分布式系统最糟糕的一点是：一台机器从机架上断开，可能是电源断了，也可能是网络断了，那根线就断了。如果机器真的很多很多，这些都是不可避免的。为这样的系统编程，你就必须把这一点考虑进去。

想想你们的并发模型变成了什么样子：你有一个多线程的程序，你的每一个线程不仅不知道别的线程会不会随时访问我的共享内存，它自己还随时随地会消失——在执行到任何一个时刻都会消失。而你依然要保证这个系统能够正常运转。这个事情做起来有多难，可想而知。

### 机器会消失

```text
          一台机器                             另一台机器
  ┌───────────────────────────┐     ┌───────────────────────────┐
  │  TWorker  TWorker  TWorker│     │  TWorker  TWorker  TWorker│
  │      └────────┴────────┘  │     │      └────────┴────────┘  │
  │            共享内存        │     │            共享内存        │
  │                │          │     │                │          │
  │            网络接口        │     │            网络接口        │
  └────────────────┼──────────┘     └────────────────┼──────────┘
                   └─────────────┬───────────────────┘
                          数据中心内部网络
                                 │
                      ┌──────────┴──────────┐
                另一个数据中心          另一个数据中心
```

读图说明：机器内部多个 TWorker 共享内存，机器与机器之间只能靠网络通信，包还可能跨数据中心——任何一台机器、任何一条连线上都随时可能出故障，这正是分布式编程比单机并发难得多的地方。

### 把计算带到数据

为了在这样的数据中心上面编程，我们还是要再走一遍 Unix 走过的路线。每当一个新的需求出现，你需要的其实是构建一个全新的、好用的编程抽象。Unix 赢就赢在它的编程抽象上——管道、组合和复用这些机制。

对单机来说，`open`、`read`、`write` 这些系统调用（包括最开始 `chat.py` 里用到的那些）已经工作得非常好了，一个多处理器的单台计算机其实已经很好了。但是对于分布式应用，如果你还是让程序去 `open`、`read`、`write`，那就等于把容错这种非常难做的事情交给用户，这件事不行。

所以做分布式系统时有一个核心的 mindset change。在 Unix 的模型里，program 才是带了主要语义的东西：像 `grep`、`cat` 这些，还有你自己写的各种各样的业务逻辑；你用管道把 program 连起来，你大部分时候想的是这个 program 怎么处理数据——你的想法在程序上，所以是**把数据带到程序**。但在分布式计算的意义上，程序随时都有可能会消失，这时我们就要换一个 mindset：**把计算带到数据**，而不是把数据带到计算。

一旦你想通了这一点，你会发现分布式系统的设计其实没有那么困难。去看一看 Google 是怎么从 Google File System、Bigtable 一路做到 MapReduce、建立起它的帝国的，它做的就是这件事。`everything is a file` 这件事在 Unix 时代成功了，在分布式计算的时代依然可以。

它只需要做好一个文件系统的抽象。文件是什么？是一个 byte array。假设我有好多好多台电脑，在分布式存储上构建一个可靠的分布式文件系统：一个文件可能有 1 PB，没有任何一台 PC 机存得下一个 PB 的数据，那时候也没有任何单台服务器可以——但它可以把这个文件分片以后存到不同的机器上，比如这一部分存到这两台机器上，那一部分存到那三台机器上。它把文件切开存到不同的机器上，却完全不让你看到这些机器。你编程的时候看不到机器，你只能看到这个文件。

```text
Unix 的模型：数据被搬到程序这里
   cat a.txt │ grep x │ sort        ← program 是中心，数据在管道里流动

分布式的模型：程序被送到数据那里
   for each chunk in 分布式文件:
       把 program 送到存放这个 chunk 的那台机器上执行
       结果写回分布式文件
```

读图说明：两种模型的差别只在于"谁动"，程序带着算法去找数据，而不是把海量数据搬到程序所在的那台机器上。

所以你还是在做操作，还是有 program，这个 program 依然可以非常复杂、有非常复杂的算法；但它不再是"我把 program 运行起来、然后把数据塞进去"，而是以文件系统里的文件为中心：把程序跟文件里的一部分联系起来，再把程序写到新的文件里。你看到的永远是"我要启动一个程序，这个程序做了一次数据的处理"。这里面就有"把数据带到计算"和"把计算带到数据"的区别。

在这个基础上，他们又在文件之上构建了一个数据库——key-value database，解决增删改查的问题。因为如果你有一个 key-value database，你就可以做 API key 的鉴权、做 API key 的删除，就像 DeepSeek 那个例子里的做法。有了 database，C10M（一千万并发连接）的问题一定程度上就已经解决了：我只要查询这个 database 就可以了，而它背后是分布在很多很多数据中心的分布式数据库，读取很快，写入相对来说也比较高效。

他们还为这种超大的文件上的计算开发了一个大数据处理系统，叫 MapReduce。这三篇论文开启了分布式计算的一个新时代，解决了分布式计算里的编程问题，把实现细节留给了分布式系统。最终每台机器上跑着的还是一个 Linux，但它对外暴露的接口，就不再是 Linux 那种非常底层的 `open`、`read`、`write` 了。

### Serverless：不要服务器

那么今天我们怎么样为这样一个复杂的分布式系统编程呢？还是回到前面说过的：所有的并发编程任务本质上都是计算图。所以你最好的编程方式就是去描述这个计算图长什么样。至于这个计算图到底怎么执行、分发到哪一台机器上，最好都由底下那个 system implementation 去管，我作为程序员不需要管。

所以你应该知道：只要有一个足够好的分布式数据库系统，再有一门足够好的、可以让我描述计算图的编程语言，所有的问题就都解决了。这就是今天的 serverless computing，无服务器的计算。

以前我们说我们要建一个网站：哪怕就是课程网站，我在阿里云租一个服务器，租完这个服务器我就有一个固定的 IP，有了固定 IP 我再去域名厂商那里买一个域名（我觉得每个同学都可以去实验一下，买一个 `.xyz` 的域名，那个比较便宜），然后搭一个自己的个人网站。在这个模式下，你一切都是以服务器为中心的：你会 ssh 连到那台服务器上，服务器上跑一个 Nginx，然后你去配置它。这就是非常典型的把数据带到计算、以计算为中心的一个思路。

serverless 告诉你不要有 server 这个概念，你应该以数据为中心。因为本质上数据就是状态：你有多少用户，哪些用户是 active 的，哪些 API key 是 inactive 的，每个 API 用了多少量。而你所有的业务——至少是增删改查那部分业务逻辑——都是事件、都是事件驱动的：比如有人要 disable 一个 API key，有人要查看他的 dashboard、你要汇集哪些数据。这不就是 JavaScript 面向事件编程最容易写的那种东西吗？所以我们真的可以用 JavaScript 来写数据中心里面的程序。

比如我让它假装写了一个基于 Amazon S3 数据存储的 serverless 程序。它就是一个 event handler：从 HTTP 的头上（`event.headers`）找到 authorization 那个 header，找到它的 value，把 API key 找出来；拿到这个请求的 API key 以后，就去问另外一个数据库，这个 API key 还是不是 valid。如果它不 valid，就返回一个 401——就像今天最开始看到的那个请求，因为 key 是不合法的，所以它给了我一个 401，请求到此结束。如果这个检查能通过，我就再去做一个 LLM inference。我这样写完函数，把它部署到云服务厂商上，剩下所有的问题就都不是我的了，都是那个 infrastructure 的问题了。

```text
HTTP 请求
   │
   ▼
┌──────────────────────────────────────────────────┐
│ event handler（一个 serverless function）         │
│                                                  │
│  1. event.headers["authorization"] → 取出 API key │
│  2. 问数据库：这个 key 还 valid 吗？               │
│        不 valid ─────────────────► 返回 401，结束  │
│        valid                                     │
│  3. do LLM inference                             │
└──────────────────────────────────────────────────┘
   │
   ▼
返回给用户
```

读图说明：整个业务就是一个事件处理函数——鉴权、失效就直接 401 结束，通过就去做推理，函数之外的服务器、扩容、容错全部交给基础设施。

这样写程序你就可以 write once, planet-scale。也就是说，只要那个云服务的厂商能扛得住，短时间内涌入大量请求，云厂商会给你动态地分配更多的服务器；它也会不断地预测你的业务量大概在多少，然后给你预留服务器，并且跟你谈好一个价格：每一次 function call 收一个非常低的价钱，相当于按需租用他的服务器。我只需要写出计算图是什么，至于那个 C10 million 的问题，你就让厂商去头疼，那不是你的事情了。

### 幂等

当然，Function-as-a-Service 也不是就这么简单的。因为你的这段代码意味着它随时随地都有可能会消失，这个程序可能运行到一半以后就不正确了，而 serverless 会重启你的代码、让它从头再运行一次。所以绝大部分 serverless function 都应该是 idempotent 的——你们在离散数学课里学过这个概念，叫"幂等性"，也就是说这个操作你做几次结果都应该是一样的。

比如你想做一个计费。你可以像我们写共享内存那样写成读—改—写：

```text
sum = load(key)
T   = sum
T   = T + 1
store(key, T)
```

但如果这个函数 `store` 已经完成了，机器 crash 了再跑一遍，那个账就会被记两次。所以你的函数写的时候就要非常小心，最好不要是这样的写法，而是往集合里加：产生一个 random key，把它加入一个 set，你的 sum 就变成了取这个 set 的大小。

```text
key = random()          # function 刚开始被调用时生成
set.add(key)
sum = size(set)
```

这个 random key 是在 serverless function 刚刚开始调用的时候就生成的——进入系统之后它会给你 assign 一个 idempotent key，一个唯一的 key——然后你往那个集合里面加。这样我就实现了一个幂等的 counting。所以编程方式上会有这样一些小的改变。

| 写法 | 核心操作 | 崩溃重跑一次的结果 | 是否幂等 |
| :--- | :--- | :--- | :--- |
| 读—改—写计数 | `load` → `T = T + 1` → `store` | 账被记两次 | 否 |
| 集合计数 | 生成唯一 key → 加入 set → 取集合大小 | 结果完全不变 | 是 |

只要你的程序是幂等的，你就可以放心大胆地把它交到一个分布式的环境上，它可以帮你容错，可以帮你自动地做副本、存储来抵抗故障，你可以得到一个非常非常可靠的系统，不用担心你租用的那个服务器 crash 了或者怎么样了。

### 存储和计算是分开的

当然，我们现在租用的那些在数据中心里面的服务器也非常地可靠。你们有没有人在云厂商上租过服务器？你的存储和你的计算是分开计费的。在实际的数据中心当中，比如说一个计算节点，一个带 CPU 和内存的计算节点，它实际上是通过超高性能的网络连到一个像 SSD 的集群里的。

比如你在云上租了一台 Linux，你在里面写了一个 `a.txt`。看上去你是往文件系统里面连续的一段写，实际上它是往这个 SSD cluster 里写。写的时候它会自动给你写两份或者三份的副本。也就是说，你的数据其实是非常非常可靠的：你在云厂商那里虽然只写了一份，但因为底下的 SSD 存储集群是有副本的，所以你的数据非常安全。

```text
        计算节点（CPU + 内存）
              │
              │  超高性能网络
              ▼
    ┌──────────────────────────────┐
    │         SSD 集群             │
    │    a.txt ──┬── 副本 1        │
    │            ├── 副本 2        │
    │            └── 副本 3        │
    │                              │
    │    libc（版本完全相同）        │
    │        → 只存一份 + 引用计数+1 │
    └──────────────────────────────┘
```

读图说明：计算与存储分开计费，计算节点只通过高速网络碰存储；你写的一份数据在下面被复制成两三份，而内容相同的数据靠引用计数共享，不必真的存好几遍。

而且这正是云厂商像阿里云这种挣钱的独门秘笈。因为你的数据比如 `a.txt` 是进他的存储 cluster 的，所以他随时随地都可以给你压缩——假设你的文件系统不加密的话。你如果给文件系统加密，他其实就会比较难受；但他赌的就是你正常的文件系统都是不加密的。不仅不加密，而且他还可以 deduplicate：比如你们每一个人租的虚拟机里都有一份 libc，都是同一个版本，这个 libc 的文件就是一模一样的；当他的 SSD cluster 发现这个 libc 是一模一样的时候，他存都不存，只是给引用计数加一。实际的数据他可能有三份副本，但引用计数只加一。

所以他甚至可以做到在有三个副本的情况下，存储的写放大比例甚至小于一。小于一意味着：他向你收 1 GB 存储的钱，他实际在 SSD cluster 里面占用的总存储是小于 1 GB 的。这是个我不知道是谁赚了谁亏了的事情——反正他挣钱了，但我们得到了服务，所以某种程度上我觉得这也是理所应当的。

这就是你在数据中心里面看到的、发生的非常非常多复杂的事情。我们当然没有办法在操作系统课上把这么多年 systems 领域里那些让人激动的工作都讲完，但我觉得我们开了一个头。所有这些背后的东西，都是你看到的那些系统调用：`read`、`write`、`send`。他一层一层一层地，把这个系统给你实现出来了。

### 一个 forward pass

现在我们知道刚才那个 API 里面相关的增删改查是怎么实现的了。那么剩下的就只有一件事：do LLM inference。也就是要回到从 token 到 tensor。

本质上，大语言模型你们应该大部分同学都做了那个 `gpt2.c` 的实验了——它就是从一个学到的函数、一个很大的数学函数上采样。如果去看 `gpt2.c` 的源代码，我这里就不运行它了，整个代码的核心就在 GPT-2 的 forward：一个 forward pass、一个正向的推导。它是一个循环，循环的每一层都是一层 Transformer。Transformer 说起来很高大上，其实就是一大堆数学计算：所谓的一层，就是一大堆数字。里面有很多参数，为了算出这一大堆数字在数组里面的位置，是一长串的乘加运算。说白了，每一层就是一个函数：输入好多好多个数字，算出下面的一堆数字。GPT-2 里面要加载一个 124 million 的参数；算完以后又得到一堆数，这个数再写到内存里，再去算下一次。所有的函数干的就是这样一件事。

```text
        输入 token
            │
            ▼
   ┌────────────────────────────────┐
   │  for each layer in Transformer │
   │      ┌──────────────────────┐  │
   │      │ matrix multiplication│  │ ← 最耗时的两个函数
   │      │ attention            │  │ ← 最耗时的两个函数
   │      └──────────────────────┘  │
   │      结果写回内存，进入下一层    │
   └────────────────────────────────┘
            │
            ▼
        下一个 token
```

读图说明：整个推理就是一个循环，每一层都用矩阵乘法与 attention 这两类函数对一大片数字做变换，算完写回内存再进下一层。

比如这里有一个 matrix multiplication forward，还有一个 attention forward——实际上这两个函数是耗时间最大的，所以理论上说你们去优化它们就可以了，我就把实验的答案已经告诉大家了。而这些函数的实现都特别特别地工整，都是一个巨大的循环：`for (int b = 0; b < B; b++)`、`for (int t = 0; t < T; t++)`、`for (int h = 0; h < NH; h++)`。这不就是 SIMD 最喜欢的编程方式吗？我们前面用 CUDA 加速那个 Mandelbrot set，或者你们哪怕用多线程去加速 Mandelbrot set，那个代码的样子就是 `for x = 0..W`、`for y = 0..H`，for each pixel on the screen，我要去渲染一个点。这里也是一样，无非是对某一个东西去算一个 inner product。

代码看起来都不长，里面蕴含的道理却非常深刻。我们人类花了很长的时间、做了非常多的实验，一直到那篇非常著名的 scaling law 的论文，才去证明了 Transformer 架构确实是比 LSTM 更适合在这种长上下文的模型上面训练。

### 从标量到 tensor

什么叫 tensor？一个数字叫一个 scalar，标量；一个数组叫一个 vector；一个二维数组叫一个 matrix；更高维的数组就叫 tensor。tensor 这个词很 fancy，而且有些系统叫 TensorFlow，PyTorch 里面也有很多 tensor。那为什么需要 tensor 呢？

哪怕是最早的时候，在深度学习刚刚火起来的时候，大家还知道那个应用吗？第一个深度学习爆火的应用是 AlexNet。它揭开了深度学习的序幕，在 ImageNet 上面得到了一个非常好的分数。那个时候所有的人都觉得那种手工特征已经到头了、做不下去了，而 Geoffrey Hinton 他们带的团队刷新了这个比赛的历史记录。

那图像是什么？图像是一个数组。一个图像是一个矩阵，是一个二维数组。上上节课我也讲到，有一些聪明的人试图用 pixel shader 把这个矩阵当成是一张图像，然后他就可以用 shader 来做图像的加法、做向量的外积这样的操作，来实现矩阵的运算。

但如果我们用深度神经网络去处理图像，它不仅仅是一个矩阵进、另外一个矩阵出，而是通常来说会有好多张这样的矩阵。首先，每一个矩阵它都有 RGB 三个 channel（黑白图像就不说了）：你们都知道像 HTML 里面你要写一个颜色，就需要三个十六进制数来标记它的颜色，它是由红、绿、蓝三个整数表示的。然后对应那个神经网络做了池化以后，这个还会越来越多、越来越多。所以这就变成了一个高维的、非常高维的东西：它有好多好多大小一样的矩阵。而这一整个东西又可能会有好多好多份，比如在一个 batch 里面又有好多份数据，如果你要做一个 batch，这一整个东西又会被复制好多好多份。所以这就是一个 100 × 100 × 3 × 6 这样的东西：这是宽，这是高，这是 channel 数量，这是 batch 数。

```text
              宽 W ───────────────►
        ┌──────────────────────────┐
   高   │                          │     一个矩阵：W × H
   H    │                          │
        └──────────────────────────┘
        叠加 3 个 channel（R / G / B，每个是一个整数）
        池化之后 channel 越来越多
        再叠加 batch 里的多份数据
                    │
                    ▼
            W × H × C × B  →  tensor
```

读图说明：从二维数组往上叠 channel、再叠 batch，维度越来越高，这个高维数组就是 tensor。

所以这个东西就是 tensor。没有什么神秘的，这是你在实现这个系统的时候很自然而然地就会用到的概念。

### Self-Attention 就是查一本书

深度学习继续往后发展，到了 Transformer 的时候，又有一个跨时代的发明，叫 Self-Attention。每层的 Transformer 我打算给大家打一个比方：每层的 Transformer 都是一本书。

大语言模型做的事情是 next-token prediction：比如"my……"或者"answer my question……"，它要 predict 的是 next token。这个要补全的东西就叫 Q，叫 Query，它是动态的，每一次都不一样，至少每一次这个都不一样。然后还有一个东西叫 K，还有一个东西叫 V。Q 就是要补全的句子，K 就是这本书的一个目录，V 就是书里面具体的内容。

所以它先做的是：把 Q 和 K 放在一起，去把 V 里面的一部分以比较高的权重取出来。相当于书里面有很多东西是不重要的，或者说对于我这句话、这个补全任务来说是不重要的；不重要的我就把其他的这些东西都给删掉，但是我可以把书里面一些有用的东西给取出来。完了以后我会做一个运算——做一个 SoftMax，然后再乘以 V 的运算。运算完了以后，我就会形成一个很大的向量，这个向量就是我的瞬时记忆、我的短时记忆。

每过一层 Transformer，就像是你的"人"去思考了一层。思考一层以后，你就会得到一个短时的记忆，大概是"我已经把这里面所有的东西都消化了，并且是就着这本书去消化的"。消化完了以后，它再去重新生成一个这样的结构，长得像这样的结构，传给下一层的 Transformer。

```text
      Q（要补全的句子，动态的）
            │
            ▼
     ┌─────────────┐
     │   Q  ×  K   │   K = 书的目录
     └──────┬──────┘
            │ 权重（不重要的部分权重低，相当于删掉）
            ▼
     ┌─────────────┐
     │   SoftMax   │
     └──────┬──────┘
            │ 再乘以 V（书的具体内容）
            ▼
      一个很大的向量 = 短时记忆
            │
            ▼
   过几层 dense 的计算 → 重写 Q → 传给下一层的 Transformer
```

读图说明：Q 去查 K 这本目录，按权重从 V 里取出有用的内容，压成一个"短时记忆"向量；再用几层稠密计算把它重写成新的 Q，交给下一层继续读同一本书。

换成人的动作就是：我根据我现在的这个问题先去查书；查完书以后，我在自己的大脑空间里面会产生一个想法；这个想法会过几层这种 dense 的神经网络，做几次相对比较复杂的计算；完了以后我再把这本书、把我的问题重写一遍；重写一遍以后再过，每往上一层，我的信息的密度就会越接近于我要输出的那个最后的 next token。

有意思的地方是：刚开始的时候你看到的还是你的每一个 token，但等到越后面的层，你越来越不知道你看到的是什么了。而且书里面的每一个部分也都是你学出来的——一个非常有意思的架构。我们甚至觉得这个架构它的潜力还没有到头；我们普遍觉得这个架构可能不是最好的。

### 把 kernel 拼起来

`gpt2.c` 是从 `llm.c` 里面裁出来的。如果去看那个 `llm.c`，它有一份 CUDA 的代码，就跟我们那个 `mandelbrot.cu` 比较类似。你会发现在这里，Attention forward、matrix multiplication forward，这些代码都和 mandelbrot 是很像的。所以我们可以毫无疑问地用任何一种方式并行化它，比如用 spawn，比如用 SIMD。

那 137 行的运算，也就是最内层的循环，就是在这个 Attention forward 里面执行得最多的运算：它就是一个 inner product。而这个 inner product 完全是可以用 SIMD 的 FMA 指令来实现的——本质上就是两个很大的向量，把它们乘起来然后再加起来、乘起来再加起来。SIMD 是可以的，SIMT 当然也是可以的。

在那份 CUDA 版本的代码里，当你写了带尖括号的代码，这段代码就会运行在 GPU 上：它会立即把这次矩阵乘法所需的所有参数（`out`、`input`、`weight` 这些）都发到 GPU 上，然后 GPU 立即开始执行。但是 GPU 会把所有对 kernel 的调用全部都排队：它会等到第一个 kernel 执行完，再执行第二个 kernel，再执行第三个、第四个。

所以这相当于 CPU 把一个计算图发给了 GPU。比如 Kernel 4，它本身可能是一个 SIMT 的 kernel，是一个非常高度、极度并行的程序；但最终要所有 SIMT 的线程都执行完了，这个 kernel 才结束，等这个 kernel 结束以后，才会有下一个 kernel。

```text
现在：kernel 一个一个排队
   K1 ───►│ K2 ───►│ K3 ───►│ K4 ───►
   每个 kernel 结束时，都要等最慢的那几个线程

想要：把计算图拼起来
   ┌────────────────────────────────────┐
   │  K1 + K2 + K3 + K4 融合成一个 kernel │
   └────────────────────────────────────┘
   中间结果不出显存，GPU 一直被喂饱 → FlashAttention
```

读图说明：串行排队的 kernel 之间会留下等待尾巴，把相邻 kernel 的计算图拼成一个，就是把那些空转的时间找回来。

你会很明显地觉得这不是最好的。因为在一个多线程的程序里，尤其是像这种 SIMT 里面，当我可以创建 100 万个线程的时候，那总会有几个线程会运行得比较慢。也就是说刚开始并行度上去以后，GPU 可能运行得非常满；但是到最后只剩那几个因为各种随机的原因（比如调度的原因）运行得最慢的线程时，就只剩一两个线程了，它们会拖慢整个 GPU 的利用率。相当于 GPU 利用率一开始很高，到最后的时候就比较低了。

所以你会想：有没有可能把所有的这些 kernel 都打包成一个 kernel？因为下一个 kernel 本质上可能只是需要这里的几个计算结果，它也是一个计算图。所以你是不是可以把这个计算图给拼起来？拼起来以后，你不就可以更充分地利用 GPU 里面的这些算力吗？是的，你会希望把这些计算图打包在一起，所以你就发明了一个叫 FlashAttention 的东西。这是一个相对比较新的系统，但一旦有了这个想法，你可能会发明一些有趣的、真正在现实中用到的技术。

### 从 SIMD 到 Tensor Core

我今天上课的时候一开始留了一个问题：我们有没有可能真正地把这个并发做出来——我有一个 TSpawn，本质上我是想要 spawn 好多好多的 TWorker，但是任何一条指令的执行都会有一些代价，比如译码的代价。我们说 SIMD 单指令多数据，它一定程度上摊掉了译码代价；SIMT 也摊掉了译码的代价。那我们能不能在 SIMT 里面引入 SIMD 呢？答案也是可以的。

因为 `gpt2.c` 里面那些运算其实是非常固定的、非常 regular，就是矩阵的运算。所以你希望的是在 SIMT 的模式下，你是靠算一个位置：你有好多寄存器，寄存器里面有 index——比如这个是 0、这个是 1、这个是 2——你通过一条像 `base + row * stride + column` 的一条运算，所有的线程都同时执行这个事情，算出一个 index，然后再拿着这个 index 去 store 或者 load，来实现这个高带宽的内存访问。

但是你浪费了这条计算指令的代价。你需要电路，需要译码，而这些都是能源。如果你想要能效比足够高、尽可能绝对地高，你连这条指令都不想要，你想要一条矩阵乘法的指令、一条矩阵乘法的 FMA。所以恭喜你，你就发明了 Tensor Core。

```text
              k 列                         n 列
        ┌──────────────┐            ┌──────────────┐
     m  │      A       │      ×  k  │      B       │   =   D（m × n）
        └──────────────┘            └──────────────┘
                    Tensor Core 一条指令做掉
```

读图说明：Tensor Core 就是把两个矩阵的乘积累加压成一条指令，不再让线程一条条去算地址、再一条条去 load/store。

今天 NVIDIA 的 GPU 里面就有 Tensor Core。其实这个名字有一点 misleading，虽然它也不 misleading，我觉得还是对的——它本质上干的事情是把一个 A 矩阵（$m \times k$）乘一个 B 矩阵（$k \times n$），得到一个 D 矩阵（$m \times n$）：

$$A_{m \times k} \times B_{k \times n} = D_{m \times n}$$

所以这不是任何 Tensor，它就是矩阵。NVIDIA 完全可以在宣传的时候说这是什么 multi Matrix Multiplication Extension、MMX——这就是开玩笑了，那个是 Intel 的 Multimedia Extension。他显然觉得这个名字太土了：他不想说"我在指令集里面引入了这个东西"，而是吸取了 Intel 失败的教训，给了一个更现代、名字更响的名字，叫 Tensor Core。它最核心的功能、用得最多的功能就是做这个 FMA。它可以加，也可以不加。

### 分块与内存布局

但其实你并没有发明 PTX 里面的那个 SIMD。我们的 GPU 设计者真正面临的难题，实际上是内存的移动和布局的优化。

矩阵乘法最大的麻烦其实是：两个大矩阵在乘的时候，这是一行乘以一列的。所以这些矩阵无论你是用行优先来存，还是用列优先来存——还记得这两种存法吗——你总有一个矩阵是要牺牲访问的连续性的。因为你的内存是一个 linear addressing 的东西、线性编址的东西，你的内存就是一个线性的地址，它没有一个二维的结构（其实我觉得做二维的内存也 OK 啦，当然我们现在是用别的办法，用分块的办法让内存变得接近于二维）。所以如果你直接用这种方式来访问，总有一个矩阵不符合 cache friendly。那怎么办呢？

```text
行优先（row-major）                    列优先（column-major）
 ┌───┬───┬───┬───┐                     ┌───┬───┬───┬───┐
 │ 0 │ 1 │ 2 │ 3 │                     │ 0 │ 2 │ 4 │ 6 │
 ├───┼───┼───┼───┤                     ├───┼───┼───┼───┤
 │ 4 │ 5 │ 6 │ 7 │                     │ 1 │ 3 │ 5 │ 7 │
 └───┴───┴───┴───┘                     └───┴───┴───┴───┘
 一行的元素在内存里连续                  一列的元素在内存里连续

分块（tiling）：把大矩阵切成能装进缓存的小块
 ┌───────┬───────┬───────┐
 │  tile │  tile │  tile │     每次只算一小块，
 ├───────┼───────┼───────┤     小块正好待在缓存里，
 │  tile │  tile │  tile │     访问才是高效的
 └───────┴───────┴───────┘
```

读图说明：同一份数据只能按一种顺序摆在内存里，所以乘法的两个矩阵里总有一个访问不连续；用分块把每一小块控制到能装进缓存的大小，就能把它换回连续访问。

现在的办法实际上是把它们分成一个一个的小块。所以 tile 这个词，以及你们现在看到很多的 CuTile、TileLang 这些词——你们可能会在各种官方博客里面见到——都是因为我们的硬件本质上的一些限制、系统设计上的一些本质限制，它不得不做的一件事情：必须分成整块，而且每一块都要能够相当于进入缓存、正好在缓存里，那才能实现高效的计算。

所以 Tensor Core 真正解决的问题其实是像这类东西：多维寻址、稀疏数据的搬运，它甚至压缩解压缩；跨步的访问、异步同步、内存布局的转换。比如在比较新的 GPU 上有这个 `cp.async.bulk.tensor`，它支持稀疏数据的拷贝，还支持这种 zero-overhead 的转置——因为你取出这一块和取出那一块这两个矩阵的时候，其中一个矩阵需要转置以后才能改写成连续的 inner product。它做了很多这样的事情，最终只有一个目的：使我们刚才那种 CUDA 程序、CUDA 的 kernel 可以更高效地运行在 GPU 上。

这就是极致压榨性能的后果。我觉得这种东西都是新的，如果你直接去看手册或者直接跟 AI 对话的话，你会发现它一下子甩了海量的信息给你，让你很难接受，因为你真的需要很多概念。所以你需要的其实是把时间倒回到一点，比如倒回到 1997 年，去看看那个 Intel 是怎么做 MMX 的，以及做 MMX 的时候那些经验和教训是什么。然后你会发现历史就是惊人的相似。

### 第二个 Unix 生态

这两天有个很有意思的新闻：NVIDIA 的市值已经超过印度股票的总和了。也就是一个公司的产业体量已经超过一个世界大国了——我们不可否认印度是一个世界大国——然而这还只是十万亿美元的产业生态最底下的东西。

如果你回顾计算机硬件和计算机软件发展的历史，你会发现历史真的是惊人的相似。你们可以试着去把 Unix 做一个类比：从底层的那些系统调用、那些像分页一样的机制开始，你在 Linux 上能玩到的这些机制，我们的系统调用世界就一点一点长出了你今天看到的全部；而从这个加速器、GPU 的生态上，就长出了我们今天人工智能应用的一切，最底下的就是 GPU。

所以我觉得 DeepSeek 这次用昇腾的卡来做推理的 service，其实是一个很大的非常大的进步——传言中他们是因为适配国产卡导致了延期发布，但这也没有任何证据能证明这一点。

在 GPU 和 CUDA 上，中间还有一把非常非常重要的库函数，比如说 cuBLAS，这叫 Basic Linear Algebra、基础线性代数，就是比如矩阵乘法。这就好像你的新的处理器——比如说你的 Intel 的 MMX 的处理器——发布了，但如果没有人为这个处理器的扩展指令集写汇编，那不就没人能用好你这个处理器的性能吗？

同样的道理：你为了能够用好 Tensor Core 的这些性能、用好它的内存带宽，你的内存布局应该是什么样的？你的访问模式应该是什么样的？你的一个很大的矩阵、两个非常大的矩阵要乘，你这么分块、块分多大？这些事情都是和底层的硬件相关的，甚至你为不同的 GPU 都应该编译出不同的代码，它才是最优的——因为下一代的 GPU 它可能 Tensor Core 更大更多，那你分块的大小就要发生变化。所以就有 cuBLAS 这种库，它一直在更新，随着 CUDA 的更新；这很像操作系统里面紧密相关的像 libc 这样的库函数。

当硬件体系结构的功能更新以后，libc 上面相应的东西也会更新。比如 memory copy：你们今天如果试图用 C 写一个 memory copy，再用高级的优化去优化的话，你会发现你的编译器会使用 SIMD 指令里面的一些比如 XMM、YMM 寄存器去做这种很长的 load，做一个非常长的 load，然后一个非常长的 store，来降低你需要很多个 load 和很多个 store 的开销——他们认为这样会更快一点，也确实有可能会更快一点。同样的事情在这里会再发生一次。

cuBLAS 这一层还有 DeepSeek V3 发布的时候那个 DeepGEMM——General，它叫 General Matrix Multiplication，你看全部是矩阵乘法；然后 NCCL，Communication Library，通信的库。在这个库函数之上，又有了各种各样的应用系统工具的生态，就是 coreutils 那些。但对于人工智能应用来说，它的 coreutils 和我们在面向系统管理员的 coreutils 不太一样：它需要的是算子 kernel 的 fusion 这种技术，像 FlashAttention，它最好是能把几层的、多层的计算全部都打包在一起，变成一个计算图，然后发给 GPU。然后还有训练的框架、推理的框架，各种各样的框架，在这些框架的上面，还有和用户交互的、和 AI 用户交互的程序。

```text
     应用与界面        Ollama / Open WebUI / ComfyUI …
          ▲
     高层框架          PyTorch / TensorFlow（用高阶方式描述计算图）
          ▲
     算子融合          FlashAttention 之类（把多层计算拼成一个计算图）
          ▲
     基础库            cuBLAS / DeepGEMM / NCCL
          ▲
     指令与硬件        CUDA / PTX / Tensor Core / GPU

  对照 Unix 世界： 用户程序 → coreutils → libc → 系统调用 → 硬件
```

读图说明：GPU 这一侧的层次和 Unix 那一侧一一对应——库函数对着 libc，算子融合对着 coreutils，高层框架对着用户程序，往上的一切都有人在做。

当然，这里的"用户"不是指最终的用户，不是拿豆包聊天的那种用户，而是会去训练神经网络、会去研究神经网络的用户：那就是 PyTorch、TensorFlow 这种高层的编程语言，它可以用更高阶的方式来描述一个计算图，然后这个计算图最终会被用 FlashAttention 去编译，再调用 cuBLAS，最后变成一个复杂的程序到 kernel 上面去执行。再往上，就看到像 Ollama、Open WebUI、你们的 ComfyUI 这些。和 Linux 生态也是一样的：你能想到的一切都有人在做。

### 1.6T 的模型与 PD 分离

如果你的推理集群上运行的都是 GPT-2 的模型，1.5B 的模型——这是 extra large，GPT-2 1.5B，1K 的上下文——那问题几乎就解决了：相当于 HTTP 的请求会到达一个业务节点，然后这个业务节点会对数据库做一个增删改查，然后这个事情就完了。相当于直接起一个 kernel，把这个推理流程全部都完成。

但如果你今天的模型是一个 1.6T 的模型，1 兆的 context，这绝对是一个非常困难的事情。因为你的一张 GPU 卡上面没有 1.6T 的显存，所以你必须把这个计算分到好多张卡上去；而且里面有一些计算，比如如果你是一个 $n^2$ 的 full attention 的话，这个计算量是非常非常大的。

| | GPT-2 1.5B / 1K 上下文 | 1.6T / 1M 上下文 |
| :--- | :--- | :--- |
| 显存 | 一张卡装得下 | 一张卡绝对装不下 |
| 计算 | 起一个 kernel 跑完整个推理 | 必须切到多张卡，还要对付 $n^2$ 的 full attention |
| 类比 | HTTP 请求进业务节点做一次增删改查 | 需要整套推理基础设施：PD 分离、各种并行策略 |

所以我们今天的大语言模型的推理服务，这种像水和电一样的基础设施的推理服务，普遍做了一个叫 PD 分离的东西：prefill 和 decode 的分离。

我们刚才说 attention 机制就像是去看书。实际上是每一层，如果这个 Q 是以前用过的话，那所有的 K 和 V 就可以保存到一个叫 KV cache 里面去。所以你会看到像 DeepSeek 的 API 它会有一个 cache hit 的价格和一个 cache miss 的价格。cache hit 就意味着那个 KV cache 还没有被挤掉：prefill 之前已经为你做过了，它认为它还在显存里面、可能还是热的，还没有人过来把它挤掉。如果你隔得太久，它就会被挤掉，挤掉以后你就相当于 cache miss 了。

一次 KV cache 的 prefill 是需要相当多的开销的，decode 也需要另外一部分开销：它会读取完整的 KV cache，然后根据当前那个 Q——就像我刚才说的，好像是你去一遍一遍地看不同的书，每看完书以后你会得到一个自己的短时记忆，然后再去重写一个 Q——这样来生成下一个 token。

去年 DeepSeek 做 inference 的工程师在 Stanford 上面做过一个 talk，他上来的第一句话就是：你们在体系结构课、操作系统课上所有学过的所有概念，你们所有关于 memory hierarchy 的印象，在教科书上写的这些通信的延迟、速度，在这里都不一样。但是你们在这门课上学到的那些分析问题的方法——比如说你想要知道系统的每一个部分到底做了什么事，你会知道用一个 profiler 去看系统每一个部分的行为——你学到的这些肌肉记忆，最后在这些实际的生产当中都是有非常大的用处的。

然后就是这样一个非常复杂的过程，要在推理集群里面有 tensor parallelism，有 pipeline parallelism，有这个 expert——现在都是 MoE 的模型。然后最后终于返回了一个整数，就是你的那个 next token。

### token 回来之后

这个 next token 返回来了以后，就像刚才那个 serverless 的 code：他拿到那个 token 以后，又会做很多事——会做审计（就像刚才我说到那个拉黑朋友圈的例子）、会做记账，然后他会更新 dashboard，最后会生成一个 HTTP event stream 的 response。

这就是我实际打开 `chat.py` 之后、实际收到的那个数据的第一个 chunk：里面有一个 system fingerprint，他推理系统的指纹，还有一个 `FP8 KV Cache 2026 00402`，然后就开始吐 token 了。

而这个旅程其实没有终点。那个 token 就回来了，所以在数据中心里面就兜了一圈。

## 从一盏会闪的灯到 PCIe：I/O 设备的寄存器模型
> 对应块：BLK43 | 覆盖分集：P22上 | 块标题（分集名）：《输入输出设备和驱动（上）》

### 一盏 LED 灯，一台最标准的 I/O 设备

先看我手上这盏灯。电源按钮底下有个灯，它现在是常亮的。我在这里写了一段很普通的 C 代码，它在文件系统里有一个路径，叫 `/sys/class/leds/power`，我打开这个文件，拿到一个 fd，然后用一个 `write` 系统调用往里面写值，灯就开始闪了。

这件事在你们的 PC 上比较难实现，在我的树莓派上却很容易——因为它直接把 GPIO 引脚连出来，一根线串一个电阻，就接到发光二极管上。我把程序关掉，灯就不动了；我把频率调成 1000，它闪的速度就明显变慢。

值得琢磨的是：**这盏灯背后到底是什么**。我在用户态看到的是一个文件路径、一次 `write`，但这层文件系统只是门面，落到操作系统内核里，它就是一块**内存映射的地址**——往那个地址写 0 或 1，就是给引脚一个低电平或高电平。这就是最典型的 I/O 设备，它在底层实现上就是一个寄存器，完美地符合我们要建立的模型。

> **提示**：别把 `/sys/class/leds/...` 这类路径当成"特殊魔法"。它背后仍然是寄存器的读写，`sysfs` 只是内核给这组寄存器套的一层好用的外壳；你在内核里看到的就是一个地址，你在用户态看到的就是一个文件。

能把灯点亮，理论上你就能实现很多有用的东西。比如一个核弹发射器——电脑上做一个密码验证，验证通过了就给一个电平，这个电平去触发另一个东西。能驱动一颗 LED，就能驱动一个继电器，就能驱动任何一个马达或者任何一件东西，因为你能控制 GPIO 上的电压：是 0 还是 VCC，一般是 3.3 伏。既然能给出一个小小的电压，你就总有办法用电路去驱动物理世界里任何一个状态变化，去发射一枚导弹、去打开某一扇门。理论上说，这和控制树莓派上那盏灯没有本质区别。

### 串口：从寄存器到一台能用的计算机

在这个 canonical（标准）模型上往上走，就可以做越来越复杂的设备。串口就是一个。

我们的 `/dev/tty` 前面已经花很大篇幅讲过它是怎么来的——teletypewriter。在终端里可以发 ANSI escape code，终端也支持 Ctrl+C，支持 job control，这些都和操作系统联动。而在你们的 PC 上，其实都有一个叫 COM1 的东西，它是一个 UART，Universal Asynchronous Receiver-Transmitter；在我的树莓派上也有一个串口，我先找 `/dev/ttyS0` 没找到，实际上它叫 `ttyAMA0`。这个串口绑在 GPIO 上——就是那块很细的针脚板上的一两个引脚。

PC 上访问串口也是类似的方式，它有好几个 register。这里是 x86 的代码。x86 和 ARM、RISC-V 不一样，它有一个**独立的 I/O 地址空间**：在我的 ARM 上，所有寄存器都直接映射到某个内存地址，我读写那个内存地址就等于访问寄存器；而 x86 专门有一块 0、1、2 编号的 I/O 地址空间，得用 `in`、`out` 指令去访问。

```text
x86：两块并行的地址空间            ARM / RISC-V：只有一块
 +-------------------+          +-------------------+
 |   内存地址空间      |          |   内存地址空间      |
 |   RAM / MMIO       |          |  RAM + 所有设备寄存器 |
 +-------------------+          +-------------------+
 |  I/O 地址空间       |                ^
 |  0x0060 PS/2       |                |  mov / ld / st
 |  0x01F0 ATA        |                |
 |  0x03F8 COM1       |          （设备寄存器被"插进"内存地址里）
 +-------------------+
        ^
        |  in / out
```

*读图：x86 用一条独立的 I/O 通道，靠 `in`/`out` 指令进出；ARM、RISC-V 把设备寄存器直接摆进内存地址空间，用普通的访存指令就够了。*

COM1 的基础端口是 `0x3f8`。你需要给不同偏移的寄存器写正确的值来完成 UART 的配置：`COM1+2`、`COM1+3`、`COM1+0` 各有分工，就是刚才说的 status、command、data 那一套。配置完成以后，想写一个字符，实际上就是写一个寄存器——往 COM1 的 data 里丢一个字节，它就把这个字符送出去了；和刚才往寄存器里写 0 或 1 是同一回事。

从串口读数据也是一个道理：不断从 `+5` 那个寄存器里读，看有没有数据来；有数据，就从 COM1 的 data 里读一个出来；没有，就说明此刻没有数据。

```text
CPU 侧                         UART（串口）              终端
 ------ 写 data 寄存器 ------->  [data]  -----发送----->  显示字符
 ------ 读 status(+5) -------->  [status] <---接收-----  键入字符
 ------ 写命令寄存器 --------->  [cmd ]                    配置波特率等
```

*读图：串口在 CPU 眼里就是 status / command / data 三个寄存器，写 data 出去，读 status 判断有没有收到，读写之间就是一次完整的字节交换。*

一旦有了串口，计算机就变得可用了：你能实现一个终端，你的电脑就能真的用起来。所以你们在数字电路课、计算机系统基础课上做的那个"小东西"，可能觉得它太简单、甚至过度简单了，但它和真正的计算机非常非常接近——基本上就是一台真正的计算机，只要你给它足够的外设。

### 键盘与 PS/2：把功能下放到设备里

键盘、鼠标也是常用设备。我的鼠标是蓝牙的，那就更复杂一些，这门课不会覆盖它；这把键盘是 USB 的，前面那根线就是 USB。

在更早的 IBM PC 时代，还没有 USB 总线，键盘控制器是另一种接口——如果你拆过老机器，或者从家里翻出过一个老鼠标，你见过那种接口：它是 PS/2，一共有 6 根线。data（数据）、clock（时钟）、VCC 和 ground（高电平与低电平），再加上两根预留的、没有任何功能、厂商可以自定义的线。USB 接口里面同样排着一组引脚，只不过线数更多。

PS/2 会映射到 I/O 地址空间上的两个端口：`0x60` 和 `0x64`，其中 `0x60` 是 data，`0x64` 是 status 和 command。你可以往 command 里写一些特殊的字节来配置键盘和鼠标——比如让 caps lock 灯亮或灭，或者调按键重复的延迟高低。

这里有个很有意思的历史差异。以前键盘的行为是**和 tty 比较像**的：你按下 a，它就隔一小段时间不停地给你发送 a 按键，而这个间隔写在键盘控制器里。为什么放设备里做？因为当时 CPU 速度很慢，大家会希望尽可能把功能放到设备上去，这样能减轻 CPU 的负担。现在反过来了：键盘更多时候只把你按下的键和松开的键报给软件，由软件来决定发多少个按键序列，于是你可以在操作系统里改按键重复的延迟。

```text
以前：键按住 -> 键盘控制器自己按固定间隔重复发送 -> CPU 收到一串按键
现在：键按下/松开 -> 上报给软件 -> 软件（操作系统）决定重复节奏与延迟
```

*读图：同一件事——"按住键要重复"——从设备端的电路搬到了操作系统软件里，这是硬件变快之后责任重新划分的结果。*

所以你看，I/O 设备其实没什么了不起的：它就是寄存器，只要有寄存器，你就可以和另一个由电路做出来的东西收发数据，就能实现 input 和 output。

### 磁盘：ATA 控制器

除了键盘，还有 ATA 控制器，全称 Advanced Technology Attachment，它连到 IDE 磁盘接口。如果你以前装过电脑，可能用过那种非常胖的数据线，40-pin。

它映射到 x86 的两个端口区间：`0x1f0` 到 `0x1f7`，以及 `0x170` 到 `0x177`。想从磁盘读数据，步骤是：先等磁盘 ready——ready 也是从 status 寄存器里读出来的；ready 之后，往正确的寄存器里写上正确的值：我要读多少个 sector、这些块的编号是什么；最后把读的命令写到一个正确的寄存器里，然后就可以四个字节四个字节地把数据读出来。

到这里，其实已经构成了经典计算机世界的全部：你有键盘、有鼠标、有磁盘、有中断，还可以有一个显示器——那确实是一个完整的计算机体验。

| 设备 | 接口形态 | 在 x86 上的落点 |
| :--- | :--- | :--- |
| LED | 内核里的一块内存映射地址，用户态是一个文件 | 由 GPIO 寄存器承载 |
| 串口 | status / command / data 一组寄存器 | COM1 基础端口 `0x3f8` |
| 键盘、鼠标 | 6 根线，data / clock / 电源 / 预留 | PS/2 端口 `0x60`、`0x64` |
| 磁盘 | 命令、块号、块数、数据一组寄存器 | ATA 端口 `0x1f0`–`0x1f7`、`0x170`–`0x177` |
| 摄像头 | 标准化的数据流协议 | UVC 标准，见后文 |

### 打印机：一台会解释程序的机器

#### 打印机收什么数据，发什么数据

顺着上面的说法：任何 I/O 设备在 CPU 眼里都是一堆寄存器，那打印机应该也是一组寄存器。于是问题来了——打印机到底收什么数据、发什么数据？CPU 会给它发送什么，它又会把什么返回给 CPU？模型一定是这个模型。你去翻古，会发现里面有很多有意思的老文档和老手册，真的值得花点时间读一读，尤其是可以让 AI 帮你读。

我们今天的打印机，不管是激光还是喷墨，都是以一个个小点的方式成像：热转印把墨粉转上去，或者喷墨把小点喷到纸上，油墨干了就看到图形。但最早的打印机做不了那么精细，它就是一支笔，你甚至可以直接叫它**绘图仪**。

想清楚绘图仪要多简单就够了：在二维平面上画画，本质只需要一个打印头/笔，能抬起、能放下，能左右移、能上下移，甚至可以斜着同时移。只要有了 X 轴的移动、Y 轴的移动，加上提笔和落笔，理论上就能画出任何东西。

所以如果让你穿越回 1950 年设计一台打印机，你也会得到同样的设计：一个卷纸筒提供 Y 轴自由度——往上卷、往下卷；中间一个机械臂提供 X 轴自由度；然后你只需要告诉打印机，现在该落笔还是提笔；如果落笔，就说"向 X 以什么速度移动多少、向 Y 以什么速度移动多少"。任意直线都可以分解成 X 方向的位移和 Y 方向的位移，所以你能画线段；再靠提笔、落笔切换，理论上就能画出任何图形。恭喜你，你发明了这样的打印机。

#### 从笔到语言：PCL 与 PostScript

很难想象这样简单的模型真的能画出任何图形，但只要你能画线就够了，而且它还内置了一些字模，比如 A B C D 这些字母。**本质上，一台打印机其实是一个程序的解释器**：你需要在 CPU 上生成一个 program，这个 program 由具体指令组成——可以很底层，像机器代码，比如抬起、放下、移动；也可以更高级一点，比如 `line X1, Y1, X2, Y2`，或者 `string X, Y, ...`。

```text
   高级语言程序              编译器            低级控制序列
  （line X1,Y1,X2,Y2）  ------------->  （抬笔 / 落笔 / X 位移 / Y 位移）
        |                                        |
        |                                        v
        |                            +---------------------------+
        |                            |  data 寄存器（一个字节一个字节）|
        |                            +---------------------------+
        |                                        |
        |                                        v
        |                            +---------------------------+
        |                            | 打印机内部缓冲 + 一台小计算机   |
        |                            +---------------------------+
        v                                        |
   （再往上：PCL / PostScript）                    v
                                          纸面上的图形
```

*读图：计算机上有一个编译器，把高级语言翻成低级的控制序列；低级程序通过 data 寄存器送给打印机；打印机里有一块缓存、还有一台小小的计算机，它收到这段低级程序后执行指令序列，把图形打到纸上。*

这样一来，打印机就变复杂了，但它的功能也变大了：打印机是一个小的计算机，收到了低级的程序以后执行这个指令序列，就能打出真正的东西。非常简单的想法，但是非常 powerful。最开始打印机也好、绘图仪也好，都只画线、画字符；随着打印机越来越强、CPU 进步、计算机被发明之后能力一直在增长，打印机可以执行的程序也越来越复杂，于是就很自然地需要更强大的编程语言来描述"我到底要把什么东西打到纸上"——PCL 出现了，PostScript 也出现了。

我们实验室的打印机就是一个 PCL 6 兼容的打印机。在 PCL 6 之前，比如 PCL 5 或更早，打印命令长这样：每一次都是往 data 寄存器里送一个程序，程序里先是 escape，也就是一个 ESC，然后跟一个命令。打印机支持各种各样的命令——设置打印的 resolution、设置打印模式、设置打印宽度、各种配置，然后你可以把一个 binary 的图像送过去，它收到就可以接着打印。

为了方便交换这种可以打印的文件，就有了 PostScript。它和今天的 SVG 很像。顺便说个大模型时代的用法：终端里很好用，但你平时自己用的时候，其实可以让它生成 HTML 或者 SVG，这样你得到的东西更好读。比如你们用 AI 帮你们写文章，交上去总觉得 AI 味比较重，我教你们一个我自己的 prompt——因为我经常要改论文、给学生改论文，我希望它在输出的时候，给每一个重要的动词和名词一些额外的选项，比如 "This is a ..."，所有有多选的地方都用一种语法表示出来，这样你就能在一个 prompt 里得到多种风格去挑，而且这个结构是可以 nested 的。今天的 reasoning model 做这件事做得非常好，你甚至可以让它给你生成一张 HTML 卡片。这就是编程语言的力量。

回到 PostScript。它就是一个编程语言，甚至是一个**图灵完备**的编程语言：它可以循环，它有一个基于 stack 的 machine；但它的本质是用图形的状态机去构造路径，就像前面的 `line` 一样，每一个 PostScript 里都可以描述一条路径。这条路径不一定是直线，它可以是二次曲线；还可以给这条路径做填充；还可以设置字体、打印文字，这些都是这个语言里支持的东西。

#### 从 PostScript 到 PDF

我上课前让 DeepSeek 帮我生成一段 PostScript，就一个 prompt：我上课要给大家讲讲 PostScript，它和 SVG 很像，你能不能给我一个比较 fancy 的 PostScript 用来做演示。它就给了我一个 `page.ps`。

拿它干什么？用 `ps2pdf` 把这个 PS 变成 PDF，打开看：有文字，有图形，它精确地描述了一个矢量的、可以无限放大并且依然精确的图形，这样就能以极高的质量做印刷。你看它打印文字的时候有一些命令，指定一个字体，字号是 28 号，`setfont` 之后把打印头移到某个位置上，然后用某个字体去打印一个 title。

在很长时间里，PostScript 都是打印界的事实标准，直到 PDF 成为它的继任者。PDF 的兼容性更好，而且**去掉了 PostScript 里图灵完备的部分**，它是一个更安全的 container 格式，但留下了 PostScript 描述形状的那些功能。现在我们还有更多编译器：LaTeX、Markdown，都可以编译成 PDF，再送到打印机里；现在很多打印机也支持直接打印 PDF 文件。早期的时候，我们的系统里甚至有 `lp`、`lpr` 这样的命令，直接把文件送到打印机。所以在 Unix 时代，甚至还没有这么漂亮的图形界面的时候，我们就已经有这种东西了——一切都是用编程语言做的。你写一个 LaTeX，写的时候也没有图形界面，但就是这样一层一层的编译，最终编译成底层的打印机可以理解的语言，打印机就帮你生成高质量的打印稿件。你用一个命令就能打印东西，这是一件非常神奇的事情。

### 摄像头：标准化的力量

除了打印机，另一个有意思的设备是摄像头。今天你买到的所有这种 USB 摄像头都是**免驱**的，我手上这个虽然是个小型的放大显微镜，但它也是摄像头；刚才把它插上以后，应该就可以打开一个 `video0`。它们几乎全是 USB 的，这是因为 USB 底下有一个标准，叫 **UVC，USB Video Class**，它已经标准化了。

这个标准化的协议规定了你怎么枚举系统里的这类 USB 设备，所以在 Linux 里你会看到 `video0`、`video1` 这样的设备节点。你的摄像头会和操作系统、或者应用程序协商捕获图像的格式、分辨率、帧率、压缩方式等等。我这次视频流的颜色有点小问题，估计就是摄像头和树莓派之间某个参数协商弄错了——用了一个不那么标准的软件，没有完全实现符合标准的 UVC。协商完了之后传输就开始了，UVC 给我们一个逐帧读取数据的功能：一帧一帧、一张一张地读，可以是未压缩的图像，也可以是压缩的，比如 Motion JPEG 或者 H.264 的一帧。

但要注意：**它仍然是字节流的交换**。虽然经过了 USB，但它的数据交换和寄存器模式是一样的。

```text
  应用                     内核 UVC 驱动            摄像头
   |  枚举设备（video0）         |                     |
   |--------------------------->|                     |
   |  协商格式/分辨率/帧率/压缩   |<---- 描述符/能力 -----|
   |                            |                     |
   |<==== 逐帧字节流（裸数据 / MJPEG / H.264）=========|
```

*读图：UVC 把"怎么发现摄像头、怎么协商参数、怎么逐帧取数据"标准化了；应用只要买一个 UVC 兼容的摄像头，在 Windows 或 Linux 上写软件就能用。*

今天的行车记录仪、显微镜、内窥镜、平板扫描仪、眼球鼠标，本质上都是 UVC 设备，所以大家开发起来很容易。你看，理论上这些东西很简单，就是交换数据的寄存器，但因为我们可以有程序、可以有协议，所以能在上面交换非常有趣的数据，造出非常有趣的设备。

### DMA：一个只会 memcpy 的 CPU

光有趣是不够的。本质上 I/O 设备是 CPU 的手和脚，是 CPU 的延伸，它要做一些 CPU 完成不了的事情。除了和设备交换数据，我们还可以干一件非常有趣的事情：**让设备也和 CPU 接在同一块内存上，共享内存**。

这当然可以，这就成了协处理器。不过协处理器未必一定以共享内存的方式接入：早期 CPU 里是没有浮点指令的，比如 80386 就没有浮点指令，它配一颗 80387 浮点协处理器，那颗芯片上有一些寄存器，CPU 去访问它就行。今天绝大部分协处理器都更复杂，通常以共享内存的方式接到内存里。

最早的这类设备就是 DMA，Direct Memory Access。**你可以把 DMA 理解成一个 CPU——它就是一个 CPU**，只是它不像我们的 CPU 一样能执行任何指令，它的指令集非常受限，甚至可以说没有指令集，它只能做一件事。比如 Intel 的 8237 DMA，它一共有四个通道，每次都会挨个通道看过去：如果哪个通道待拷贝的字节数还大于零，就拷贝一个字节。

因为 DMA 和 CPU 共享内存，甚至可以共享 I/O 端口地址空间，所以它就能干活了。学过多线程、多处理器编程以后这就非常好理解：它就是一个 CPU，不停地执行 `memcpy`——可以是内存到内存，可以是内存到端口，也可以是端口到内存。

```text
   +--------+  配置：源/目的地址、端口、字节数   +-----------+
   |  CPU   | ------------------------------> |    DMA    |
   |        |  启动 / 取消                    |  控制器    |
   +--------+                                 +-----------+
        |                                          |
        |  算力即刻释放                              |  逐字节搬运
        v                                          v
   （回去干别的）                    +-----------------------------+
                                    |  内存  <--->  设备端口       |
                                    +-----------------------------+
```

*读图：CPU 只负责写 DMA 的寄存器——起始地址是什么、端口是什么、要搬多少字节、什么时候开始和停止；一旦启动，搬运就是 DMA 自己的事，CPU 的算力被释放出来。*

这样就把 CPU 从又麻烦、又耗时的 I/O 里解放了出来。回到刚才的 ATA：磁盘准备好以后会把数据送到自己的缓冲里，然后我们可以从端口里四个字节、四个字节地读。如果我要读 1 兆的数据，CPU 就得耗在一个很大的循环里等它读完。为了把 CPU 从这个繁重的任务里解脱出来，我们才有了这个"更小的 CPU"。而 DMA 在 CPU 眼里依然是一堆寄存器：CPU 读写这些寄存器，用来控制 memcpy 的地址是什么、端口是什么、要拷贝多少字节，还可以通过这些寄存器控制 DMA 的开始和结束，比如取消一个正在进行的 DMA 任务。

一旦你发现你的 I/O 设备不仅能是一组寄存器的协议，还能访问内存，你就可以实现很多更复杂的功能。

### 共享内存的加速器：GPU 与 NPU

最典型的就是异构加速器，比如 GPU 和 NPU。

前面一次课讲过 GPU 里的编程：你写 `cuda 1.cu`，可以理解成它就是一个 C 程序，但里面有一些 kernel，这些 kernel 是跑在 GPU 上的代码；你用那套语法启动一个 kernel，还有 `cudaMemcpy` 这样的命令。这时候 CPU 和 GPU 的关系就有意思了：GPU 里面有显存，它嫌 CPU 的内存太慢，觉得共享内存没有意义——虽然现在你确实可以在 CUDA 的 host 上做 memory allocation，分配一块和 GPU 共享的内存，但速度会慢一些。所以大部分时候 GPU 认为自己的显存——比金子还贵的显存——更快，它要用显存。

于是流程就变成这样：CPU 通过 GPU 的一些寄存器跟它通信，告诉它要做什么、做一些配置；然后把我们编译好的 GPU kernel，也就是代码，以及 `cudaMemcpy` 的那些数据，通过 DMA 送过去——因为这些数据一开始就在内存里，通过 DMA 送到显存里，这里相当于还有另外一个处理器就是 DMA，DMA 会完成 CUDA 的 memory copy 和 kernel 的 copy。等全部都拷贝好了，CPU 再跟 GPU 说：请你运行显存里面那个 address 上的程序。

```text
  CPU                          DMA                         GPU
   |  配置寄存器                  |                            |
   |---------------------------> |                            |
   |  把 kernel 代码 + 数据交给 DMA | ---- 搬进显存 -----------> | 显存
   |                            |                            |
   |  告诉 GPU 执行某个地址的程序    |                            |
   |-------------------------------------------------------> 启动 kernel
   |                            |                            |
   |                            |                    众多 GPU worker 线程跑起来
```

*读图：这确实有点像启动一个程序。GPU 就像另一台电脑，只不过它需要受 CPU 的控制来启动一个 kernel 的执行；拷贝由 DMA 完成，真正"按下启动键"的是 CPU 的寄存器写操作。*

其他的处理器和加速器也差不多。比如 NPU，你们手机里高通的处理器上就有一个 NPU 引擎；高通的 NPU 是共享内存的，不像 NVIDIA 的 GPU 有独立显存，你只需要告诉它要执行什么样的程序，它就会共享着内存开始执行。

### 总线：给无限多的设备留出地址空间

讲了这么多设备，有一个问题已经浮现出来了：每个设备都暴露一组寄存器的接口，而在 IBM PC 时代，每一个端口都是写死的——`3F8` 是什么、`60`、`64` 是什么，每一个端口都绑定到一个具体设备。那是因为当时要做标准化，当时也还没有那么多的设备，没人想到未来会有各式各样的设备出现。

那如果想要兼容无限的设备，有没有可能呢？你看，每个设备都是一组寄存器，那我们能不能做一个像虚拟地址空间一样的东西：不再是原来那个固定的 I/O 端口，而是有一个地址空间 0、1、2、3、4、5，一组寄存器可以 **memory map** 到进程/系统的地址空间里；我把一组寄存器插到一个设备上——比如插一台打印机——它就在 `2、3、4`；插到别的位置就是 `6、7、8`。有没有这个可能？当然有，这就是你们每天都用的**总线**。

总线其实也是一个特殊的 I/O 设备，你可以这样理解：它也是一组寄存器，但它的寄存器比一个具体设备（比如一个摄像头）要多一些，而且它的寄存器是可以动态分配的。它有一组协议：CPU 只要和总线说话，就可以问总线上有哪些设备，可以轮询总线、看设备有没有变化，总线也可以给 CPU 发中断，甚至总线上自带一个 DMA——CPU 只要跟总线上的 DMA 说好从哪一个端口开始、把哪些内存搬到内存的哪里，事情就完成了。

```text
没有总线（IBM PC 时代）            有总线之后
  端口号 <-> 设备 写死               CPU <-> 总线 <-> 设备
   0x3F8 -> COM1                    总线的寄存器负责：
   0x0060 -> 键盘数据                 · 枚举有哪些设备
   0x01F0 -> ATA                     · 设备变化时通知（中断）
                                     · 自带 DMA
                                     · 设备地址动态分配
```

*读图：总线就是一个 I/O 设备的管理器，它把"每个设备固定占哪个端口"变成"设备插进来再分配地址"，于是设备种类可以无限制地扩张。*

所以只有建设了这样的生态，硬件厂商才会不断地生产兼容的设备，这个生态就会越滚越大。现在最著名的几种总线之一，就是我插显卡用的 PCIe 总线——你们的 CPU 其实就有一些 PCIe 的 lanes，Intel 的 CPU 上就是这样。

## 总线、ioctl 与设备驱动
> 对应块：BLK44 | 覆盖分集：P22下 | 块标题（分集名）：《输入输出设备和驱动（下）》

### 总线：把设备接到 CPU 上

你有一块显卡，正对着 PCIe 总线的插槽，插进去，插到底。插到底以后，这件事其实就已经完成了——完成的是这块设备上的寄存器和总线上的一些寄存器的对齐。插进去以后，它当然还会和总线有一些通信，总线会把这个设备管好；管好以后，你就可以在 CPU 里面以 memory-mapped I/O 的方式去访问这个设备。所以不管你插进去的是一块显卡还是一块网卡，它都构建了一条 I/O 数据寄存器上的通路。这就是总线的功能：总线会把 CPU 上的数据转发到相应的设备上。

其实我们前面说过的 port I/O——port-based I/O，访问磁盘、访问 PS/2 的那个 I/O——它也是一个总线。总线是计算机非常非常重要的一个设计。

> **提示**：memory-mapped I/O 与 port-based I/O 是访问设备寄存器的两条路。前者把设备寄存器映射进 CPU 的内存地址空间，于是读写设备寄存器跟读写内存没有区别；后者走一套独立的 I/O 端口空间，要用专门的 I/O 指令去访问。名字里都带 I/O，但通路不同。

你们用得更多的是 USB 总线：有一个 USB 口，把 USB 接口插进去，插好了以后，同样完成了这个过程。然后 CPU 可以询问这个总线，总线上有什么样的设备。比如我们可以用 `lspci` 来 list pci，你们也可以在自己的系统上 list pci。在我的树莓派上，拓扑会和你们不太一样：在 x86 的系统上，我们的 USB 总线是挂在 PCI 总线上的，相当于 PCI 总线有一部分接了一个 USB 总线的控制器，然后 USB 还可以一层一层一层往后接。我们同样可以用 `lsusb -t` 得到一个树状的 USB 列表。

我把摄像头打开以后就能看到：我的 port 001 上，我确实插在最右边那个接口上，插了这个摄像头，并且我把它打开，打开以后就有了这样一个设备——Class 等于 Video，Driver 等于 uvcvideo，还有 480 兆的传输速率。

总线支持设备的发现，也可以有一些名字。比如你扫描 PCIe 总线的时候，可以从那个设备上面得到一个设备号；通过那个设备号，你可以知道它是哪一个厂商生产的，然后就可以加载相应的驱动，把这个设备正确地运行起来。

总线其实是一个非常复杂的东西，也留有了不少名场面。这是名场面：比尔·盖茨打了一个非常好的圆场，他说，这就是为什么我们现在还没有正式地发布它。总线就是很复杂。你看他展示的功能：插入这个设备以后，应用程序是不会看这个总线的；操作系统会收到一个中断，收到中断以后它就会去轮询这个总线，去找总线里面哪一个设备是新的。然后它会自动加载、自动安装一个驱动程序。而那个地方很有可能驱动程序里面有一个 bug，或者别的原因、时序上的问题，然后整个系统——因为是在内核态代码里面运行——它就 crash 了。所以一直到 Windows 7 的时候，整个 Windows 的 driver 子系统都重构了，经历了很大的变化。各种各样的总线，PCI、USB，都是这样。

### PCIe 为什么受优待

今天，实际上在你们的 PC 机上，包括其他设备上——比如说像一个能够做 AI 的盒子这样的设备上——PCIe 都是受到特殊优待的设备，因为它的速度很快。

CPU 的 specification 会告诉你，CPU 上面有多少条 PCIe lanes，比如 40 条。它会分成几个部分：比如有些可以给显卡——16 条可以给显卡，然后 4 条可以给你的 NVMe。这样分完了以后，你的每一个这样的高速设备都可以享受足够的带宽。

```text
                CPU（例如 40 条 PCIe lanes）
        ┌──────────────┬──────────────┬──────────────┐
        │   16 lanes   │   4 lanes    │     其余     │
        └──────┬───────┴──────┬───────┴──────┬───────┘
               ▼              ▼              ▼
              显卡           NVMe          其他设备
```

图里是同一条总线上的带宽怎么被切开：lane 是 PCIe 的通道单位，把 16 条划给显卡、4 条划给 NVMe，每一类高速设备就都能拿到足够的带宽。

由 CPU 负责这个总线和内存的连接。注意，总线是可以 DMA 的，总线是可以和内存直连的。这里面就涉及到内存的一致性——memory coherence。因为我的 CPU 也会访问内存，CPU 有 cache hierarchy，而我们的 PCIe 总线也可以访问内存。为了让整体变得很一致，我们的 PC 是直接把 PCIe lane 放在 CPU 里的。像 ARM 系统就不太一样：它们的内存和 PCIe 都挂在一个高速总线上，由这个高速总线来完成 coherence。这比较细节了，你们暂时应该用不到，不需要知道这些细节。

像现在这个 PCIe 6.0 ×16 的带宽可以到 128GB/s，也就是说你可以得到一个 800Gbps 的网卡。这是一个非常离谱的速度。

总线还自带 DMA。这样你就可以高速地搬运数据：比如游戏里面，你需要把那个场景的各种材质和贴图搬来搬去。你们看到那个游戏，有些游戏加载的时候那个读条很长；那个读条很长，其实并不是说 GPU 花了很大的代价在算那个初始的场景，而是你需要把那些高清的贴图——可能很大的数据——从硬盘上面读出来，读出来以后再通过 DMA 传送给这个游戏。所以如果你有一个高速的 SSD 的话，你的加载会快很多。它需要在显存和内存之间搬运比较多的数据，当然也会执行一些计算，可能也会花一些时间，但相比来说这个磁盘 I/O 的时间会是更多的。

总线还支持供电：它默认支持一个 75 瓦的供电。所以你如果有一个更高功率的显卡的话，就需要 6 pin 或者 8 pin 的供电口。

而我们现在这些真正高速的设备——FPGA、显卡、网卡、NVMe——都是连在 PCIe 总线上的。

### CXL：总线想要共享内存

基于 PCIe 总线的物理层，还诞生了一种更夸张的协议，叫 CXL，也就是 Compute Express Link。你可以认为它是下一代的、另一种数据中心里面常用的总线。它有三个 protocol：一个是 IO，一个是 cache，一个是 memory。

你从这里就能看到它的野心：它不再是把显卡或者我们说的打印机这样的设备——这种 canonical device 的 model——当作唯一形态。canonical device 就是说，好，我的设备本质上是一个比较慢的东西，或者是一个和物理世界交互的东西，然后它通过 register 和我的 host，也就是我的 CPU 交换数据。

但 CXL 的野心在于，它希望有一个总线可以直接在远端和我共享内存。首先，它可以在本地和一块显卡共享一个高带宽的内存；而它最夸张的 feature 是，它可以共享另外一台计算机上的内存。它们之间有一个高速网络互联来实现数据的传送。

这很离谱。你可以得到这个 disaggregated data center，也就是解聚的数据中心：你一台服务器、一个 CPU，本地当然肯定是有内存的，因为只有本地的内存访问才够快，但我本地不需要那么大内存；而在远端，我可能有一个 16T 的共享的大内存。这个 16T 的内存对我来说，每一个字节都是可以寻址的，都可以像内存一样访问。我甚至可以把这个 16T 的内存——比如说我 allocate 我要 4 个 T 的内存——然后这个 allocate 的 4 个 T 内存就在我的地址空间里。访问的时候，如果我的 memory hierarchy 命中了，可能就在我本地的内存里取走了；但如果它是一个远端内存，可能会有一次网络的 round trip，就可能会有几百纳秒的延时。但只要你的程序写得够好，你就可以实现这种数据中心里面的 disaggregated memory。

```text
   服务器 A（本地内存小）             服务器 B（远端大内存池）
   ┌──────────────────────┐          ┌──────────────────────┐
   │  CPU ── 本地内存     │          │      16T 共享内存    │
   └──────────┬───────────┘          └──────────┬───────────┘
              │       高速网络互联（round trip 几百 ns）
              └─────────────────────────────────┘
                    allocate 4T → 进入 A 的地址空间
                    命中 memory hierarchy → 本地取
                    未命中 → 一次网络往返去远端取
```

读图说明：本地内存负责快，远端内存池负责大；能不能把两者当成一块内存用，取决于程序的访存局部性写得好不好。

这也是我上节课说过的：你去了真正的系统里面以后，你就会知道教科书上学的所有东西都错了。你能够留下来的，就是你分析这些问题的基本原理——它们是什么，然后你应该怎么面对它们，出了问题以后你应该怎么诊断这些事情。

这就是总线。所以我们又讲了一些很有意思的 I/O 设备。到底来讲，它们都跟一个 LED 没有本质的区别，就是交换数据。但是你只要能交换数据，我们就可以实现很多更有趣的东西，比如打印机、摄像头、总线，各种各样。真正使我们计算机系统世界能够繁荣起来的，是各种各样的 I/O 设备。

### 应用程序不该直接碰寄存器

以上都是底层的，是我站在 CPU 看 I/O 设备是什么：它就一堆寄存器，我可以读，可以写。但是作为应用程序，应用程序不应该直接去访问这些寄存器，肯定不能。

为什么不能让应用程序直接访问总线或者设备的这些寄存器？答案就藏在下面这些例子里：设备是「懂某种语言」的，只有内核里面的驱动才知道怎么和设备对话。所以应用程序和设备之间那道门，是由设备驱动把守的；而设备功能的绝大部分，都要依赖 ioctl 这个系统调用来完成。

比如 CUDA memory copy。我已经把这段内存准备好了，然后你可以用 DMA 做一个 CUDA memory copy 了；于是它会做一个 ioctl——用一条 ioctl 把我当前需要拷贝的那个 buffer 的地址送给内核，然后内核里面那个驱动程序就会开始启动 DMA，把这个 buffer 拷到 GPU 上。为什么必须绕这一圈？因为只有内核里面的驱动才知道怎么样和 GPU 对话：GPU 应该拷到哪，应该用什么样的命令、和哪些控制寄存器通信，才能完成内存的复制。

我这里还有另外一个例子，不过这个例子没有——我写这个 code 的时候，它还没有来得及把所有的 bug 都修完；以前 x86 的时候是可以跑的。

> **结论**：ioctl 就默默地承担了操作系统里面所有的复杂性。

### 一个 ioctl 造一台虚拟机

前面那个例子就是 `/dev/kvm`。Linux 系统里面有一个非常特别的设备叫 `/dev/kvm`，Virtual Machine，虚拟机。

还记得我在开学的时候实现了一个叫 CrazyOS 的东西。CrazyOS 干了一件什么事呢？就是 `while(1)`，里面有一个 `rv32ima_step`。我相当于现在有一个进程，然后让这个进程往前执行一步；如果这个进程是 system call，我就把这个 system call 处理了。当然，这是模拟的。

`/dev/kvm` 是一个非常神奇的工具，它就是一个虚拟机。我 `open` 一个 `/dev/kvm`，如果打开成功，它就成功了；如果打开失败，这里就没有 `/dev/kvm`。然后你就看到，这个接口其实还挺恶心的——ioctl 就默默地承担了操作系统里面所有的复杂性。

我就用 ioctl 这样一个系统调用，对 KVM 这个文件描述符——KVM 是 `open` 返回的那个 fd——执行一个叫 `KVM_CREATE_VM` 的命令，它就会悄悄地在操作系统内核里面创建一个虚拟机。创建出来以后，我还可以分配内存：比如我在我的地址空间里面 mmap 分配一块内存，然后我可以用 ioctl 再告诉 KVM，说我要 `KVM_SET_USER_MEMORY_REGION`，我可以把这段内存给虚拟机。相当于我可以在我的进程里面分配一个 128M 的内存，然后把这个 128M 的内存送给内核里面的虚拟机。

然后我还可以在内核里面创建一个 vCPU，你看，我可以创建一个 vCPU，甚至还可以创建多个 vCPU，还可以做一大堆的配置。然后我可以把一段 code——code、data 这些东西，就类似于送给显卡那样——送到这段内存里，实际上就是进程的这段内存里。然后我会给这个 vCPU 做一个初始的寄存器。

真正神奇的是：这个虚拟机是在操作系统内核里面创建的，我用户程序不能直接访问、直接控制它，但是可以通过 ioctl 来控制它。比如我可以改它的寄存器；我的进程里面可以分配一段内存，这个内存是属于这个虚拟机的。

然后当我执行那个 ioctl——vCPU 的文件描述符上的 `KVM_RUN`——它执行的操作就好像在执行这个东西：它可以模拟执行，就相当于这是一个虚拟化的 CPU，而这个虚拟化的 CPU 里面可以执行特权指令。任何什么关中断这种，理论上说都可以执行。特权指令我是不干涉的：比如你说要关中断，就好像关了中断一样，你里面就能看到关中断的状态。但是它会一直往前执行——我一旦执行了 ioctl 的 vCPU `KVM_RUN` 以后，我当前的进程就变成了一个虚拟机，这个虚拟机就开始执行了，它一条一条指令连续地执行。

但是，如果我在里面执行触发了一些特殊的指令——它不是系统调用——比如说触发一些像 I/O，你看 `KVM_EXIT_MMIO`，然后 hypercall、VM-exit、shutdown，它有一些原因。比如说它要执行一个 I/O 操作，但是因为这是一个虚拟机，它没有任何的 I/O 设备，所以它就不能进行 I/O，这个时候它就会触发一个 VM-exit。VM-exit 就会使这个虚拟机又回到这个进程上去执行。然后你就会看到代码执行到这里，你可以看到它的 `exit_reason`；如果它是 memory I/O 的话，就可以模拟一个虚拟的 I/O 设备，给它送一个值。

```text
   宿主进程                            内核
   ─────────────                     ──────────────────────
   open("/dev/kvm")  ──────────────▶  拿到 kvm fd
   ioctl(kvm, KVM_CREATE_VM) ──────▶  内核里悄悄建出一台虚拟机
   mmap(128M)                         （进程自己的地址空间）
   ioctl(vm, SET_USER_MEMORY_REGION)▶ 把这段内存交给虚拟机
   ioctl(vm, KVM_CREATE_VCPU) ─────▶  建出 vCPU（可以建多个）
   送 code / data 进这段内存、设初始寄存器
   ioctl(vcpu, KVM_RUN) ───────────▶  当前进程变成虚拟机，开始连续执行
                                       │
                                       │ 遇到 I/O / hypercall / shutdown
                                       ▼
   ioctl 返回，读 exit_reason ◀────── VM-exit 回到进程
   （若是 MMIO，就模拟一个虚拟 I/O 设备送一个值）
```

读图说明：整条链路里，用户程序一次都没有碰到虚拟机内部——创建、交内存、建 vCPU、启动、拿退出原因，全部是同一套 ioctl 接口上的不同命令。

所有这一切，只用了 ioctl 这一个 API。

> **提示**：考试我不会考这个 KVM 的。但你可以知道的是 ioctl 有多么的复杂——一整个虚拟化的子系统都是基于这一个 API 完成的。它承载了访问操作系统内部对象和子系统的复杂性；一定程度上，所有同步的访问都可以通过 ioctl 来完成。

### UVC 摄像头：设备驱动到底做了什么

终于，今天我们花了很多的时间去理解操作系统里面的对象：我们的设备驱动程序是实现了 `struct file_operations` 的东西，最终应用程序会通过设备驱动程序再去访问实际设备的数据。

我这里也有一个展示的例子，还是我的这个 UVC 的摄像头。我有一个程序是这样的：我先随便抓，然后 snapshot。运行 snapshot 以后，我就会从这个摄像头里面取一帧，然后 save to `capture.jpeg`。确实，这个 jpeg 的数据有点问题，应该这是一个非标准的 UVC 设备；但你确实也看到它 capture 到了一些图形——那个 A，那个 A 是我大写字母 Caps Lock 锁定的那个灯上面的字符。所以我确实从这个摄像头里面抓取到了一帧，这个程序基本上是可以工作的。

然后我就可以问 AI 了：我可以让它帮我用 `strace` 去追踪这个程序。实际上这个程序不是我写的，这个程序就是我今天下午用五分钟写的，没有任何的知识——我只知道理论上说我有一个 UVC 的摄像头，我就可以写一个 C 程序来 capture 它。然后我就可以让 AI 帮我做。做完了以后，我反过来——不是说做完以后把作业交了就可以了。大家一定养成一个习惯：你在操作系统课里面学过很多工具。因为我们说了，I/O 设备的原理是很简单的，它就是通过设备驱动；那到底通过了什么？你只需要把系统调用的序列打开，让 AI 帮你解释一下，你就可以知道了。

```text
   open("/dev/video0")
        │
        ▼
   一长串 query / 配置：querycap、s_fmt ……   ← UVC 驱动代你和设备对话
        │
        ▼
   mmap 分配缓冲区（我这里分了四块）
        │
        ▼
   ioctl：告诉驱动「缓冲区准备好了，有数据就送到这个内存地址」
        │
        ▼
   stream on → 等一帧就绪（也是 ioctl）
        │
        ▼
   write capture.jpeg
```

读图说明：从打开设备到拿到一帧，中间所有的协商与等待都发生在 ioctl 上，真正「写数据」的动作只剩最后那一下。

它首先有一个 `open /dev/video0`——确实，这个东西就是 video0。然后它会有很长的一段序列去和这个摄像头交互，这是 UVC 驱动给我们提供的。因为相当于这是一个懂 UVC 语言的设备，理论上说它有一个 specification：这个设备如果给我放一个什么样的结构体，我就应该回一个什么样的结构体，然后每一个 field 是什么意思。比如我可以问这个设备，你支持的分辨率有哪些，你支持的刷新率有哪些，你支持的视频模式有哪些。所以在我们这里也是各种 query：querycap、s_fmt，等等。

接下来它会用 mmap 去分配一个缓冲区，然后用 ioctl 告诉设备驱动——我的 UVC 设备驱动——我的缓冲区已经准备好了，如果有数据就帮我送到这个内存地址里。然后我在等，相当于等这个 stream，所以你看我有四块缓冲区。

有时候我的程序处理得会比较慢，有时候我的程序处理比较快，我的摄像头速度会比较慢，这些都是由我们的摄像头的 subsystem 去处理的。

stream on 以后，就可以去 buffer 里面取一个，等待一帧就绪——等待一帧就绪也是通过 ioctl；最后用一个 write 把 `capture.jpeg` 写过来。所以 Linux 那个摄像头的 subsystem，V4L2，它不是用 read 和 write 实现的，而是用 ioctl。

| 接口 | 主要承担的事 | 说明 |
| :--- | :--- | :--- |
| `read` / `write` | 搬运数据 | 主要是数据的接口 |
| `ioctl` | 请设备完成某一项功能、访问子系统内部对象 | 设备功能的实现基本都走它 |

所以我说 read 和 write 主要是那个数据的接口；但是如果你想要直接请这个设备完成某一项功能、完成某一项任务的话，一般而言我们都是用 ioctl 的。这里面有一个生产者消费者。

### GPU：同样的套路，一层层封装

其它的例子也是非常类似的，比如说 GPU。GPU 是一个有自己内存的协处理器，它同样地，你也是用 mmap 把内存——把我进程的内存——交给设备驱动或者设备，甚至我可以直接把我自己进程的指针就送给设备驱动程序；然后我可以通过 ioctl 去提交命令，比如说一个 doorbell，然后让 kernel 就从我的 GPU 里面开始启动。

本质上 GPU 也是一个处理器。处理器在空闲的时候它是什么也不做的，它必须要接受 CPU 的一个指令，然后它才会加载一个程序。然后一层一层，这个东西就会一层一层经过封装：有 Linux 的这个 Direct Rendering Manager，有 libdrm 用户态的库封装这个 ioctl，或者是 Mesa 封装了 OpenGL、Vulkan 的实现，再去提交这些渲染的命令。

```text
   应用程序 / 游戏
        │   OpenGL / Vulkan 调用
        ▼
   Mesa（用户态图形库，封装 OpenGL / Vulkan）
        │
        ▼
   libdrm（用户态库，封装 ioctl）
        │   ioctl（提交命令 / doorbell）
        ▼
   DRM（Direct Rendering Manager，内核态）
        │
        ▼
   GPU（自带内存的协处理器：空闲时什么都不做，
        必须收到 CPU 的指令才加载程序）
```

读图说明：从游戏到 GPU 隔着好几层，但越往下越薄，最后落到内核 DRM 上的还是那一条 ioctl。

本质上它和这个 UVC 的摄像头，你会看到类似的东西。

### 一切最终都落回寄存器

所以这就是关于 I/O 设备的全部，这就是全部。

我们程序的每一个系统调用，不管是 read、write 也好，在操作系统里面兜了一大圈，最终都要变成总线上面的、总线上连着的设备上面的寄存器上面的一个值：你写进去，或者读出来。这就是计算机的本质，没有什么神秘的。你们可以从最简单的那个 LED 灯开始，一点一点往后想，然后你就可以做出很多有趣的东西了。

比如说树莓派的这个 USB。树莓派的 USB 可以做普通的 USB 接口，也就是说你可以连一个 U 盘或者连一个鼠标到上面，然后它就可以当鼠标和键盘来用。

同时，这个 USB 设备还可以把自己假装成是一个 USB 设备：你可以用 CPU 去控制它，给另外一头——比如说我可以连一根线，然后把这个 USB 线连到我的这台电脑上，然后我的这个电脑就可以把这个东西模拟成一个键盘或者鼠标。我可以假装这是一个 USB 的键盘，然后把按键的信息送给这台电脑。所以我是没有键盘的，但是我可以写一个程序，不停地——本质上是寄存器，只要我假装自己是一个 USB 的键盘，对吧，OTG 的模式——它就可以把数据伪装成一个设备送给计算机。

```text
   树莓派（CPU 写寄存器）                另一台电脑
   ─────────────────────               ──────────────
   把自己伪装成 USB 键盘  ═══USB 线═══▶  识别为一个键盘设备
   按键信息 → 寄存器 → USB 报文          收到按键事件
```

读图说明：方向反过来也一样成立——同一套寄存器通路，谁在写、谁在读，决定了谁是「设备」、谁是「主机」。

所以这里面有很多很多可以玩的东西，比如你真的可以实现一个游戏外挂。

## 用磁和光存下一个 bit
> 对应块：BLK45 | 覆盖分集：P23上 | 块标题（分集名）：《存储设备原理（上）》

我小的时候，家里还在用磁带存数据。当时没觉得这有什么特别，今天回头看，一盒磁带到底能装下多少东西、它是怎么被读出来的，反而很值得琢磨。有一条经验一直成立：如果一件事确实有意义，人类一定会把它做到极限。

### 磁带：把一维介质卷到极限

一眼看上去，磁带不像一个好的存储介质。第一，它存不了太多数据；第二，它是一维的——所有的 bit 排成一条线，要读哪个位置都得让带子卷过去，没法跳。这么想下去，磁带应该很弱。但事实正好相反：磁带的密度可以高到离谱。

现代磁带不再是一根可以转动的"磁针"。它直接结晶成一个完全固化的固体，写入时给它一个非常强的磁场，把里面磁畴的自旋方向改变。这里改变的是磁化方向，晶体的物理结构并不动，所以它是一个非常硬、非常坚固的东西，而单元却非常小——以纳米计，比如几十纳米。单元足够多，就能产生足够大的磁场，把一个个 bit 清楚地表示出来。

这个密度能到什么量级？**300 GB 每平方英寸**，一卷磁带做到 **30 TB** 是很现实的。

磁带的好处不止密度。价格低——它本质上只需要结晶，比集成电路那种要一层一层做结构的制程容易得多；容量高；可靠性高——里面全是固体，放上几十年、几百年可能都不会坏；顺序读写性能也不错——每个 bit 这么小、密度这么高，读写头只要在感应电流方向这件事上跟得上，我就能用不算太慢的转速把数据连续地读出来、写进去。

> **提示**：磁带的高密度不是"把 bit 硬做小"换来的，而是靠把每个单元做成完全固化的晶体、只用磁场改它的自旋方向。单元小到几十纳米仍然足够稳定，这才是它敢往 300 GB/平方英寸走的原因。

> **结论**：磁带的所有优势都指向同一个方向——它适合一次写完、顺着读完，越少回头越好。

### 致命缺陷：随机访问

有一个进程可以 `mmap` 一个很大的文件，甚至可以 `mmap` 一块设备：比如 `/dev/sda`。我在树莓派上直接 map 过 `/dev/mmcblk` 或者 nvme 的盘，把一个 256 GB 甚至 1 TB 的存储设备映射进内存。映射之后，我手上就有一个指针指向整块盘的全部内容——如果它是 1 TB，那它在我的地址空间里就是 1 TB。我任意地给这个指针加一个数字，就得到另一个指针，可以直接读、也可以直接写。

这件事在 SSD 上、甚至在我们的机械硬盘上都是可行的：只要访问不是太散，随机访问的性能基本可以接受。可如果底下是磁带，读的延迟会非常非常非常高。

原因就在"一维"这个先天结构上。磁带为了容量必须尽量长，于是盘成一大卷；读写头固定在一处。要读某个位置的 bit，我就得让带子卷、卷、卷，把那个位置转到读写头下面才能读；下一次如果访问的是靠近带尾的数据，我还得倒、倒、倒，把它再转回来。一读一倒，整段很长的带子都要走过一遍，时间就消耗在这里。这不是我们想要的。

> **提示**：能把 `/dev/sda` 直接映射进地址空间，前提是设备支持随机访问。一维、需要长距离卷带的介质一旦被这样映射，指针随手挪一下，就是一次巨大的延迟。

> **结论**：磁带是一个很好的存储设备，也很稳定，但它只适合几乎不需要随机读写、所有读写都是顺序的场景。

那什么样的场景满足这个条件？

**冷数据的存档和备份**。大批档案可能要存几十年；金融的交易数据要终身追责，有一天真得把八十年前的数据拿出来抓人，这种冷得不能再冷的数据，放在磁带上就是不错的选择。

**音频和视频**。听音乐、看电视都是顺着看的，跳着看并不是一个常见的操作；在录像带还很稀缺的年代，每一盘带子都很珍贵，谁也不愿意跳过其中的细节。磁带正好利用了这个特点——读写头读取的速度和数据的密度差不多匹配，那就一边慢慢转、一边慢慢读，把内容顺着放出来。

> **提示**：磁带分单面和双面，这里有不少精巧的设计。单面磁带要把内容再听一遍，得从头到尾听完，然后倒带、倒回开头，再放一遍；双面磁带听完第一面可以直接开始往后倒，而倒的过程里，你听到的是另一面的内容。

### 磁鼓：把一维绕成一个圈

能不能让磁带变得可以随机访问？思路是两条：避免长时间卷带，并且让卷带的速度尽可能快。这两条都指向同一个结论——不能再做成"卷起来的带子"这种结构，得放弃磁带那点容量优势。

于是出现了一个很有意思的设备：**磁鼓**。一维的存储介质如果绕成一个圈，而且可以绕好多好多圈，中间放一根转轴让它旋转，同时在每一个位置都配一个读写头，速度就上来了。介质用比较硬的，做得大一些，用 16 个或者 32 个读写头并行去读；这样的机械装置每分钟转上千转是现实的，而 1000 转其实已经是一个不错的速度了。定位被压住了：读写延迟不会超过旋转周期——任何时刻想读某个位置，等它转到读写头下面就行；最坏的情况是数据刚刚错过读写头，那就再等它转整整一圈。

这是从一个"一维内卷的材料"，变成了一个"1.5 维内卷的材料"：好多根"磁带"排在同一个盘上一起转。

```text
              读写头（16 或 32 个，并行读）
        ┌──┬──┬──┬──┬──┬──┬──┬──┐
        │  │  │  │  │  │  │  │  │
        │  │  │  │  │  │  │  │  │   ← 一维介质绕轴缠成很多圈
        │  │  │  │  │  │  │  │  │
        └──┴──┴──┴──┴──┴──┴──┴──┘
                     │
                转轴（每分钟约 1000 转）
```

读图说明：一维介质缠在转轴上绕成多圈，每个位置各配一个读写头并行读；整鼓持续旋转，所以最坏情况只需要等它转过一整圈，而不是像磁带那样卷完一整段。

### 磁盘：把磁带铺成一个平面

磁鼓再往前走一步，就是今天的主力机械存储设备——磁盘。磁鼓是把一维介质绕成"一维多圈"；磁盘换了一种卷法：在二维平面上铺上一圈一圈的"磁带"，同心圆地铺满整个盘面。转轴还在，盘片照常旋转。

如果只有一个位置固定的读写头，它还是不够灵活。磁盘的读写头有**两个自由度**：一个是盘片的旋转——每个 bit 都跟着盘片一起转，转到读写头下面时就被读到；另一个是读写头自己可以稍微径向挪一点，切换它对着哪一圈。可以把每一圈想成一条被卷成圆的"磁带"：读出 `1 2 3 4` 之后，读写头稍微偏一点，就换到下一圈去读 `5 6 7 8`——相当于读写头能切换"磁带编号"。

```text
              ┌─────────────────────────────┐
              │   ╭───────────────────────╮ │
              │   │  ╭─────────────────╮  │ │
              │   │  │    ╭───────╮    │  │ │
              │   │  │    │ 转轴  │    │  │ │
              │   │  │    ╰───────╯    │  │ │
              │   │  ╰─────────────────╯  │ │
              │   ╰───────────────────────╯ │
              └──────────────▲──────────────┘
                             │
                          读写头

   第 1 圈： 1 2 3 4
   第 2 圈： 5 6 7 8
   读完 4 ──▶ 读写头径向挪一点 ──▶ 换到第 2 圈接着读 5
```

读图说明：盘面上的圆圈就是一圈圈"卷起来的磁带"，读写头靠两个自由度定位——靠整盘旋转把目标 bit 送到自己下面，靠径向移动换到另一圈；同样是数据刚错过读写头就再等一整圈。

这个结构非常高效，原因在于整个盘片是**硬封装**的：盘片非常硬，每个盘片的上下表面都配读写头，还可以好几个盘片并排叠放，全部装在一个基本密封、几乎没有灰尘的环境里工作，所以盘片能转得非常快——市面上很常见的就是 5400 转和 7200 转的机械硬盘，每分钟 7200 转。背后是一个很大的产业，厂商一直在想办法往一个盘片里塞下更多的 bit：磁畴不是横着排，而是竖着排，读写头的磁场方向也随之改过来，同样的面积就能装更多；材料也在不断改进，把每个 bit 的尺寸继续缩小；再加上双面、多盘片，机械硬盘的容量可以做得很大。

把这条技术线连起来看，一路上变的就是"读写头怎么找到数据"这一件事：

| 设备 | 介质排布 | 读写头怎么定位 | 随机访问的代价 |
| :--- | :--- | :--- | :--- |
| 磁带 | 一维排成一条线 | 卷带，把目标位置送到读写头下 | 可能要卷或倒很长一段带子 |
| 磁鼓 | 一维介质绕轴缠成多圈 | 轴转，多个读写头并行读 | 最多等它转一整圈 |
| 磁盘 | 同心圆铺满二维盘面 | 盘片旋转 + 读写头径向寻道 | 寻道 + 最多等它转一整圈 |
| 软盘 | 与磁盘相同，但盘片裸露 | 同上，机械结构更松散 | 同上，而且整体更慢 |

### 磁盘的脾气：便宜、稳定、怕摔

总结一下机械硬盘作为存储设备的特点。它和磁带一样便宜——存储用的晶体一旦制作工艺成熟，成本比电路还要低一些；密度高，所以每字节的成本低；容量也很高，因为它把"磁带"一圈一圈卷满整个二维平面，还要双面、多盘片继续扩展；可靠性也很高。

它唯一的缺点是对振动敏感。读写头需要给出很强的磁场，尖端又非常尖。平时我们能拿到的那种磁力很强、甚至可能伤人的磁铁，直接在磁头表面划，对它都没有任何影响——它并不怕"磁"，它怕的是机械位移。一旦发生很大的机械振动，尖端的微小位移就可能划伤盘片，晶体结构被破坏，那部分数据就读不出来了。这种情况一般发生在笔记本电脑跌落的时候。反过来，放在机柜里的服务器只有非常轻微的振动，机械硬盘在那里就非常稳定。

读写性能上，顺序读写肯定没有问题：转速快、密度高。随机读写就没那么好了：最坏情况是数据刚从我读写头下面转过去，那就必须再等它转一圈，比如等上**八毫秒**。八毫秒对现在的计算机来说已经是很长的时间，所以随机读写会有明显的延时。但这个延时不是不可接受——只要绝大部分读写都是顺序的，这八毫秒就会相对平摊在很多次数据读写上，几乎消失，也可以通过改写程序来规避。所以它到今天仍然是计算机系统的主力存储之一。

> **易错点**：把机械硬盘怕磁、怕摔这两件事混为一谈，就会得出错误的结论。磁铁划在磁头上没事，摔一下才会出事——致命的是尖锐读写头的机械位移划伤盘面，不是磁场。

它还有一个很好的特性：**坏了可以修**。如果只是控制器坏了，这块盘读不出来，但磁介质本身是一个非常稳定、化学性质也很稳定的结构，可以把盘拆开，用别的方式把数据恢复出来——被划坏的那部分可能丢了，绝大部分还是能救回来。SSD 就不一样：所有东西都封装在存储颗粒上，其中一部分发生不可逆的损坏，会连带导致其他部分也读不出来，数据损坏了就损坏了。

| | 机械硬盘 | SSD |
| :--- | :--- | :--- |
| 存储结构 | 磁介质盘片，机械读写头 | 存储颗粒，全部封装在一起 |
| 部分损坏后 | 介质稳定，可拆盘用别的方式恢复大部分数据 | 可能连带损坏，基本无法恢复 |

> **提示**：现在越来越多的数据放在云上，而云可以始终保持你的数据有三个副本，一块盘坏了再补一个副本就行——正因为如此，性能好得多的 SSD 才能用来存海量数据。也正因为 SSD 的性能实在太好，消费级的手机、电脑里已经越来越难看到机械硬盘；服务器上因为它便宜，还在继续用。

### 寻道、旋转与盘里的那台电脑

机械硬盘读写时最糟糕的部分，就是随机访问的那两段等待。第一段：读写头得先找到对应的磁道，如果目标数据不在当前磁道上，就要先移动过去，这叫**寻道**；第二段：移到磁道之后，还要等数据转到读写头下面，才能把它读出来。

早期有些操作系统书上会讲怎么调度读写头：软件可能同时要读盘上好几个分散的部分，那应该按什么顺序去读？最经典的类比是电梯——最里圈就是第 1 层、第 2 层、第 3 层、第 4 层、第 5 层，我要读写某个地方的数据，就等于在那个楼层按了一下呼梯按钮；读写头先走到有请求的最内圈，再走到有请求的最外圈，然后再回来、再过去，上下上下，像电梯一样往返。这样一趟走下来，比在盘面上随意乱窜省得多。

> **定义**：寻道（seek）是把读写头移动到目标磁道的那段时间。它与等待数据旋转到位的时间合在一起，构成了机械硬盘随机访问的主要延时。

现在这些算法已经全部集成到磁盘的控制器里了。因为磁盘上面其实也有一台电脑，只有厂商最清楚这块盘的各种特性：转一圈需要多少时间，有几个读写头，读完这份数据之后读写头还来不来得及再去读另一个磁道上的另一份数据。这些参数只有生产厂商掌握，所以调度就交给盘自己去做。

于是从我们这一侧看过去，磁盘就是一个很大的字节序列。我们只要告诉它我要读哪些数据，盘就负责把数据读出来。

### 软盘：装在口袋里的磁盘

#### 一张软盘长什么样

软盘（floppy disk）和硬盘的原理完全相同，只是形态不同。硬盘的读写头、驱动器、控制电路全部封装在盘体里面，所以卖得挺贵；软盘的盘体本身只有塑料、铁片、弹簧和盘片，几乎没有什么复杂的电路——驱动器在机器里面，盘本身成本很低。

5.25 英寸的软盘能直接看到里面的盘片，它和硬盘的盘片是一个道理。普通磁铁贴着这片盘片划，也不会改变里面的数据，比想象中要稳定。它同样也怕划伤：盘套上开着一个小窗口，驱动器里有一个突出的、有点像盖子的东西，插进去以后它会顶住盘片、带着盘片旋转，读写头就从那个小窗口的位置开始读写数据。

3.5 英寸软盘设计得紧凑得多，外面有一个保护盖，只有把它插进驱动器之后，保护盖才会被一个机械装置打开，平时盖着，不容易被划伤。它还有一个很精巧的设计叫**写保护**（Write Protect）：盘角上有一个小孔，用手把那片小塑料拨过去，这个孔就通了；驱动器只要用一个灯加一个光电传感器，就能知道这个孔是空的还是被挡住的，从而判断这张盘是不是写保护。写保护的盘不能写入，防止意外的覆盖。今天我们是用软件把文件标成只读，那时候是把一个孔堵上或者放开。

> **提示**：3.5 英寸软盘其实并不软。"软盘"这个名字来自最早引入的 8 寸和 5.25 英寸盘，那两代盘片确实是软的；3.5 英寸只是继承了软盘这个名字，它本身是一块硬塑料。

#### 软盘为什么能统治那么久

把软盘当成存储设备分析一遍。它的介质密度低，因为盘片裸露在外面，没法像硬盘那样放在受控环境里；但密度低也有好处——它反而不那么容易损坏，可靠性还可以，当然不能和硬盘比，用力掰一下、折一下还是有可能会坏。读写性能也不高，顺序读写和随机读写都低，因为它的机械结构本身就不精密：盘片是松的，甚至能轻轻挪动。

可是回到 20 世纪 80 年代、90 年代，情况完全不同：如果不谈互联网，软盘就是整个计算机世界里传递数据最主力的介质。那时候要把一个文件送给别人，一般不会把硬盘抽出来送过去，而是把软盘插进驱动器，把想分享的文件拷进去，再带着这张盘走到对方那里。传递数据在人类世界是一个非常重要的需求，而这件事长期由软盘承担。

几个很具体的画面。一整套 DOS 操作系统，就在一张 1.44 兆的软盘上。我们小学机房的 PC 机是没有硬盘的，全被拔掉了，所以我写的程序、写的文档全部都在我自己那张软盘上：插进去、系统启动，就可以上课；上完课把盘带走，就等于被带回家了——那时候家里并没有电脑。1.44 兆在当时其实是一个很大的容量：一个几十 KB 的 BASIC 程序就非常复杂了，解释器能帮你执行它，游戏、应用软件，理论上都能放在这样一张软盘上。

90 年代的游戏软件甚至通过软盘发行。要发一个 Windows 更新，甚至会给你邮寄一张软盘，里面放一个要运行的应用程序——那时候没有互联网，或者说互联网还没有普及，普及了的网速也非常慢。像《仙剑奇侠传》就有软盘发行版：跑起来玩到某个点，游戏会说"对不起，请你插入下一张软盘"，你就得把这张盘抽出来，再插下一张进去。你去看它的目录，会发现有很多分块的数据文件；理论上游戏数据只要一份就够了，但为了把不同部分放在不同的盘上，它必须拆成一个一个的文件，前一张盘的数据用完了，就到下一张盘上去取——当然也有一部分程序会常驻在内存里。

软盘今天当然已经没有用了，但它并没有消失。打开 Word、Excel 或者任何一个软件，那个保存按钮上的图案，就是它的实物——作为一个时代的吉祥物，它留存到了今天。

### 挖坑也是一种存储：光盘

用磁来存下一个 bit，这是一条一直走到今天的存储介质技术线。在历史发展的过程中，还有别的方法来存一个 bit，比如**挖坑**。罗塞塔石碑（Rosetta Stone）就是跨越千年的持久存储：在一个稳定的介质上挖一个坑，就创建出一个 bit——不挖是 0，挖一个就是 1，持久性（persistence）也就实现了。挖坑容易，填坑困难；古代留下的碑文，记一件当时发生过的事情，用的也是挖坑。而随着现代工业的进步，我们总能挖出越来越精密的坑。

现代工业的坑精密到什么程度？拿一张光盘来看：盘里有非常非常多的小坑，肉眼根本看不到。用一台小显微镜，我能看清手机屏幕上的像素排列，也能看清从硬盘上面拆下来的那颗芯片的型号——存储设备上面其实自带一整套计算机系统，它负责处理我提交上去的所有读写请求，并尽可能把这些请求服务好——但即便这样的显微镜，也依然没有办法看清光盘上那一个个挖出来的坑的结构。要想看清，需要足够的分辨率。光盘的坑已经挖得非常非常小；而机械硬盘盘片上一个 bit 的尺寸还要更小，那是纳米级的存储单元。

挖出了更精细的坑，该怎么把它读出来？思路其实和磁盘很像，只是换了一个"读"的物理量：磁盘用磁来存一个 bit，光盘是一圈一圈的坑。要判断某处到底挖没挖坑，就得用光——拿一个激光器，把一束光打到坑上；坑的深度在一定的范围内会产生干涉，光射到坑里和没射到坑里，接收器收到的信号不同，0 和 1 就被区分出来了。

```text
        激光器
          │
          ▼
      ┌───────┐     ┌────┬────┬────┬────┐
      │ 光束  │────▶│    │ ▄  │    │ ▄  │   ← ▄ 是挖出来的坑
      └───────┘     └────┴────┴────┴────┘
                        │
                        ▼
                   ┌─────────┐
                   │  接收器 │ ◀── 射到坑里 / 没射到坑里，信号不同
                   └─────────┘
```

读图说明：激光打在坑面与坑上，反射回来的光因干涉而呈现不同状态，接收器据此把一圈圈坑读成 bit；光盘和硬盘一样要旋转——盘心里有一个孔，卡在驱动器上转起来，转动中把内容读出来。

到这里，"用磁"和"用坑"这两条线就接上了：坑挖得越密，一片介质能装的东西越多，而要把它读出来，手段也得越来越精妙。

## 存储设备原理：从挖坑到闪存
> 对应块：BLK46 | 覆盖分集：P23下 | 块标题（分集名）：《存储设备原理（下）》

手上这张盘的容量，最初不是为计算机定的。最早发明光盘的是索尼和飞利浦，目的很单纯——存储数字音频、发唱片。所以容量就定在了「正好能装下一部贝多芬第九交响曲」：74 分钟，大约 700 兆。数字音频唱片长成了今天的数据盘，这个尺寸的来历听起来有点荒诞，但它恰好说明了存储介质这件事：物理上怎么把一个 bit 放进去，先于逻辑上我们要拿它装什么。

顺着这个由头往下看，我们要回答的问题其实只有一个——**一个 bit 的持久化（persistence），到底可以用多少种办法做**。挖坑、用磁、用电，一路走到今天你手里的 U 盘、SD 卡和 NVMe SSD。而这一路的每一步，都会回到同一个老问题上：要把它读出来，你得付出多少定位的代价。

### 光盘：把坑压进透明塑料片

#### 从黑胶的凹槽到 CD 的坑

更早的时候，人们用挖坑的方式存数据，那就是黑胶唱片机。它和 CD 的区别不在「挖不挖坑」，而在挖出来的是什么。

黑胶刻的是连续的凹槽——声音本质上是震动，那就在一条槽里刻出声波震动的形状，读写头跟着走，后面接一个杠杆把震动放大，声音就被原样还原出来。这是一个纯模拟的过程，留声机也就是这么把声音录下来的。

CD 是数字时代的东西：有坑和没坑，直接对应 0 和 1。但事情没有这么糙——它把 8 个 bit 的数据编码到 14 个坑位上，多出来的余量用来做纠错。单看「一个坑一个 bit」是数字存储，实际上落到介质上的坑序列是编码过的，这样才能在坑的尺寸、间距上留出工艺余量，也才能在读错的时候纠回来。

#### 压盘：为什么复制几乎不要钱

那这种存储设备最大的优点是什么？**复制极其容易。**

你在光盘表面看到的漂亮彩虹，其实是衍射出来的效果，跟数据没关系。数据真正所在的那些坑，是在一层透明塑料片上。而你要在塑料片上有坑，得先做一个母盘：需要挖坑的地方留凸起，用母盘做出钢模；钢模一旦做好，每复制一份只要压一下。

这个过程叫**压盘**。塑料片被母盘压一下，几秒钟之内几百兆的数据就进去了，之后在这层透明塑料膜上再镀一层反射膜，才有你看到的成品效果。放到那个年代看这件事的分量：你可以把大量资源砸在母盘上，一旦母盘做好，每一张盘的复制速度和成本都变得很低。三秒钟能压出一张 100 GB 的蓝光盘，折算下来写入带宽约 33 GB/s——这个数字放在工厂里是相当夸张的。

我还听过一个很有意思的故事：如果要在两个数据中心之间传数据，用什么方式最好？网络带宽可能不够，那你可以并行地把整个数据中心的数据全部写进磁盘，然后用一辆卡车把磁盘拖过去。这带宽很可能比你在网络上传更快，因为写盘是并行的，而做母盘也是可以同时做不止一张的。同一个道理。

所以光盘普及以后，发布软件、发布电影、发布音频，CD 都是首选材料。我在实验室里翻出来一堆这样的光盘：装系统的盘、显示器驱动盘、随书附赠的《精通 Visual C++ 图像处理编程》示例代码盘，还有《Windows 游戏编程大师技巧》。复制成本这么低，信息才可能在人类世界里广泛传递。

#### 赢在哪、输在哪

它的特点非常鲜明。

优点是三条。第一，**价格极低**——本质就是一片塑料。第二，**容量其实不低**——坑可以挖得非常细，虽然比不上磁盘和 SSD，但容量相当可观。第三，**可靠性很高**：数据刻在另一面，你这一面随便划，划的全是塑料划痕，一点关系都没有，因为激光强度很大，照样能清楚读出另一面那些精巧的坑。

缺点集中在性能和写入上。顺序读还可以，一旦随机读就露出和软盘一样的毛病：它不像硬盘封在一个密闭空间里，它是**开放的**，需要一个驱动器带着它旋转；在空气里旋转就不可能转太快，为了机械稳定性，这类介质的速度都上不去，随机读性能就下来了。写入也很难——我小时候很长一段时间里都有可写的 CD-RW、DVD-RW，有各种不同技术，有用相变材料（phase-transition material）做的，也有不是相变材料、只能顺序往后写的；这些今天你已经见不到了。

今天光盘甚至不再是一个好的数字内容分发媒介。你现在买个游戏，发售之前就预下载好了，首发那一刻它才变得可以运行。而一旦母盘压好，你就**再也不能改**了；现在的软件随时随地都在更新，一个不能改、还要靠快递送到你手上的介质，显然没有网络方便——网络的延迟实在太低了，一百兆的网络下个游戏，大家觉得等得起。

### 追加写加随机读，可以造出任何数据结构

挖坑不只用来做光盘。这里要岔开一下，讲一件计算机科学里经常做的事——看起来像在上一节数据结构课。

设想你有这样一个存储介质：它是**随机读**的，你可以像访问一个巨大数组那样直接访问任何一个 `A[i]`；但它是 **append-only** 的，你唯一能做的写入是往后追加，只有一个 buffer 位置不停 `position++`，不能回头改过去的 `A[i]`。

> **结论**：只要有 random read 加 append-only write，理论上就能实现任何随机读写的数据结构——list、set，随便什么。因为这个地方是可以有指针的。

而且这类结构正好有个名字重合：**persistent data structure**，持久化数据结构。拿一棵二叉树来试。二叉树查找是 $O(\log n)$，从根往下走最多 $\log n$ 层就到叶子；如果每个节点能存更多数据，树的分叉更宽、深度更浅，但道理一样。现在我要往里插入一个节点 $n$，也就是想执行 `x.left = n`——可介质不允许我改它已经写下去的部分：$x$ 的 left、right 早就定死在那里了，树就长成这样，改不动。

怎么办？**把从根到 $x$ 的这一整条路径复制一份，新建节点。** 所有没被碰到的子树原封不动，旧树上指过来的指针照旧指过去，无论子树里有多少个节点都不用动。

```text
插入前                        插入后
  root                          root'          ← 复制
   │                             │
   ├── 左子树 L ──────────────── ├── 左子树 L    （整棵复用，一个节点都不用动）
   │                             │
   └── x                         └── x'         ← 复制
        ├── 旧右子树 ─────────────── ├── 旧右子树   （复用）
        └── null                     └── n        （新增节点）
```

代价是路径上每一个节点各复制一份，总共 $O(\log n)$ 个节点——**花 $\log n$ 的空间，插入了一个节点**。而且旧树的指针还在，历史全留着：我拿到某个指针，就知道那是上一次的这棵树；换一个指针，就是这一次的这棵树。

### Project Silica：把数据写进玻璃

既然 random read 加 append-only write 等于任何数据结构，那能不能有一个设备，就是不停地往后挖坑：我有很长很长的一条介质，往后挖、往后挖，挖下去的地方我不能再改，但我可以一直往后写。

这件事真的有人做，而且做得非常大胆，叫 **Project Silica**。一句话概括：如果我要 persist data，我就应该用玻璃。

它用激光聚焦到玻璃内部——因为我们能聚焦——去改变那里的晶体结构，这样写入一个 bit。它不像压盘那样先做母盘再一次性封上去，而是一个 bit 一个 bit 地写；但本质还是挖坑，坑挖完就不能动了，这就是 persist，然后继续往前挖，等价于 append-only 写。

一整块玻璃写满以后，就必须永久地放回架子上存档。而存档之后，这个东西是 **random read** 的：它做了一套图书馆式的机器人设备来实现随机访问。因为它本质上是三维结构，机器人要定位到某个架子的某一块上的某个位置，把这块玻璃取出来，把那个 bit 读出来，再放回去；这些动作甚至可以并行。

第一反应会觉得这个想法非常疯狂，但仔细一想，所有的配方都是你熟悉的配方，只是换了一种形式。这个东西最后能不能用、成本能不能降到足够低，我不知道。但它的意义在于：有时候你觉得世界上能想到的事都被人做尽了，还是会有人做出特别有意思的新东西。

### 磁和坑都有硬伤，所以轮到电

今天真正的主角是电。因为用磁和用坑来存一个 bit，都有本质缺陷。

磁盘——不管是哪种磁盘——都有一个旋转的机械部件，你要等它转一圈，这本质上就带来毫秒级的延时，这显然不是我们想要的。挖坑也有问题：挖坑的效率低，填坑很困难；虽然我前面说它有 random read，但随机读也是要付代价的，你得付出**定位**的代价。

那么，什么东西对于今天的高性能电子计算机来说是一个完美的存储系统？我们希望它有电子的密度、电路的速度，这样才能和跑在 5 GHz 的 CPU 匹配上。能满足这个的只有一样东西——**电路**。

### 闪存：往浮栅里塞电子

于是有了 flash memory，闪存。想法本身并不惊天动地：在一个电路里挖一个坑，把电子填进去是一个状态，把电子放跑是另一个状态。就像磁针朝这边、朝那边可以区分 0 和 1，一个坑挖下去和填起来也像 0 和 1 一样，能区分两种状态。

为了尽可能压榨一个坑里能存的数据，还可以精确控制放进去多少电子，让它产生一个可测量的电势差，靠测量电势差来决定这个 bit 到底是几——于是一个单元里能塞进多个 bit：一个单元存两个 bit、三个 bit（TLC）、四个 bit（QLC）。

这个器件和 MOSFET 非常像，只是在它上面多了一层 **floating gate（浮栅）**。往浮栅上充电、放电，就是把电子塞进去、放出来，用充放电表示 0 和 1。

```text
        ┌─────────────────┐
        │  Control Gate   │   控制栅
        ├─────────────────┤
        │  Floating Gate  │   浮栅：电子被塞进这里
        ├─────────────────┤
        │   隧穿氧化层     │
        ├─────────────────┤
        │     Channel     │
        └─────────────────┘

   充电 → 电子被困在浮栅里 → 读出来是一个状态
   放电 → 电子被放走       → 读出来是另一个状态
```

#### 便宜

本质上它和制作集成电路没有区别，它就是一个大规模集成电路。只要集成电路能把成本打下来，闪存也可以。磁盘的价格确实低，但集成电路因为量大，相对也没有那么高。

#### 容量和可靠性

容量可以很高，因为它本质上就是集成电路，可以做得非常小。可靠性也非常高：它是集成电路的封装，一层一层封下去，最后封得非常死。这个东西不怕水、不怕摔、不怕晒，什么都不怕——我的 U 盘进洗衣机洗过好多次，不小心，拿出来晒干了继续用。集成电路完全封死了，物理上灰尘进不去，水也进不去。

#### 读写性能与可扩展性

它最不讲道理的特点是读写性能。Project Silica 读取时是并行的，而**整个电路都是并行的**——电路的每一个逻辑门都是并行的。所以它能做到很好的读写性能，而且有非常高的可扩展性。

这一点同样不讲道理：你去买 MacBook 看评测会发现，512 G 机型比 256 G 机型的磁盘性能好接近一倍，1 T 又比 512 G 好一倍。原因就是闪存是有颗粒（die）的，颗粒和颗粒之间并行工作，你多一份颗粒，就多一倍的带宽。这就像你往电脑里插两块盘，就得到两倍的读速度和两倍的写速度——两个颗粒就是两倍的读写速度。

#### Jim Gray 的那句预言

2006 年，SSD 还没普及，Jim Gray 就说：

> **Tape is dead, disk is tape, flash is disk, ram locality is king.**

磁带已死，磁盘就是新的磁带，闪存就是新的磁盘，而 RAM 的局部性才是王道。他预见到了 flash 终有一天会彻底取代市面上这些存储设备。确实如此：今天数据中心里的存储在成本还可以接受的前提下，基本都换成了 flash，因为它全身都是优点。

### U盘：真正让闪存普及的东西

有意思的是，让 flash memory 真正普及的并不是高速 SSD，而是你手上的 U 盘。这是朗科的专利，名字很朴素：「用于数据处理系统的快闪电子式外存储方法」。它甚至算不上一个很技术的专利——核心就是把 USB 接口和芯片封装在同一块电路板上，这样就使得闪存不需要通过一个深入计算机的接口，而是直接通过 USB 接进来。

大约 2000 年前后，U 盘开始替代软盘，成为人与人之间交换数据最重要的媒介。它的容量还可以，我的第一个 U 盘是 128 兆——相比 1.44 兆的软盘大了一百倍，我可以在里面放视频、放图片，分享给另一个人，软盘做不到这些。速度也还不错，USB 2.0 有 480 Mbps 的带宽，拷些图像、视频是可以接受的。当然现在用得也少了，因为有网络。

### 写一千次就该坏的闪存，为什么你的文件没坏

往浮栅里充电、放电来实现一个 bit，有一个致命缺点：**放电放不干净**。每一次放电，总会有一些电子留在里面，没办法完全放掉。而且放电需要 20 伏左右这么高的电压，即便这么高的电压，也做不到彻底放干净。

于是放电几千次、几十万次以后，这个 cell 看起来就像一直处于充电状态，不能再用了——它进入 **erase saturation（擦除饱和）**，这个 cell 就死了，也就是 wear out 了、挂了。今天的 QLC flash cell，大概只有 1000 次左右的写入寿命。

这里要停一下。**如果放电 1000 次这个 cell 就挂了，那我现在在机器上跑这样一段程序，把 `a.txt` 写成 1000 个不同的值，这个文件是不是就该损坏了？** 如果你今天是第一次听说闪存放电 1000 次就报废，是不是有点害怕？

但你们从来没遇到过这个问题。你的很多文件已经被反复修改过很多次了，像日志文件、系统文件，绝对写了不止 1000 次——那为什么它没坏？

物理的限制是不可能突破的：一个 cell 放电 1000 次，它就放坏了。这是物理。**但物理的限制有一个办法弥补，那就是用软件。**

### FTL：每块闪存里都藏着一台计算机

拆开一块闪存颗粒的芯片看，你会发现 SSD 的封装上不只有闪存颗粒，还有别的芯片——那是一个 system-on-chip，我不知道具体型号，但在这个图上能看到：NAND 是闪存，还有 control（主控，是一个 CPU），还有 DRAM。**它是一台完整的计算机系统。**

你的 NVMe SSD、你的 U 盘，甚至树莓派上那张小得可怜的 TF 卡，里面都藏着一台完整的计算机系统。这台计算机上跑的软件叫 **FTL，Flash Translation Layer，闪存翻译层**。

FTL 里维护了一张很大的表，是一个 **logical to physical** 的映射数据结构，映射编号 1、2、3 的对应关系。也就是说，在操作系统这一侧、或在设备驱动这一侧看，它还是一个大字节数组，被切成一块一块的，比如 16 KB 一个 page。这张表要维护的是：我逻辑上的第一块，到底对应物理闪存颗粒上的哪一块。

第二块可能就不对应第二块，第三块可能搬到了第四块。比如我这次往逻辑 1 号块里写 16 KB，可能就写到物理 1 号；下一次还往逻辑 1 号写，这次我就不再覆盖写同一个物理块了——因为这个块只有 1000 次寿命——而是分配一个新块。比如我发现物理第 2 块写得比较少，就在映射表里把「逻辑 1 → 物理 1」改成「逻辑 1 → 物理 2」。这有点像 MMU 里面的 page table：我可以改这个映射，本质上就是一个数据结构。

改完、写过之后，物理 2 号块的写入次数加一。每个物理块都维护自己的写入次数，这样就能把所有写均匀分摊到颗粒的每一块上。这个机制叫 **wear leveling（磨损均衡）**。

```text
        逻辑块号              物理块号             写入计数
          L1 ────────────────▶ P1                      8
          L2 ────────────────▶ P4                      3
          L3 ────────────────▶ P3                      7

   再写一次 L1 时，不回写 P1（它已经写了 8 次），
   而是挑一块写得少的，只改映射表：

          L1 ────────────────▶ P2                      4   ← 只改了这张表
```

这里有一个漂亮的呼应：**FTL 这张映射表本身也必须是 persistent 的数据结构**，因为它也放在闪存里，也要服从 append-only。你可能会想，那就是个 hash table 嘛——但如果我不停地写 L1 的映射，往这一项上写 100 万次，`hash(1)` 指向的那个表项就被写坏了。所以这张表也必须用 append-only 的持久化结构来实现。

也就是说，FTL 和 wear leveling 又一次印证了前面那条结论：用 random read 加 append-only write，可以实现任何数据结构。

### 便宜到不正常的 U 盘是怎么骗你的

U 盘、SD 卡、SSD，从特别小的到性能比较高的 NVMe SSD，存储原理完全一样，**但软件、硬件的系统复杂程度完全不一样**。哪怕是一张 SD 卡，上面也会有一台计算机系统、有一个 ARM 的 CPU。但你要知道，这个计算机系统的 RAM 大小、缓存大小、CPU 算力，肯定是远远不如一块 SSD 的。所以在不同系统上，同样的原理给出的是不一样的性能。

所以千万不要买过度便宜的 U 盘。颗粒本身其实没什么办法偷工——就这么多的颗粒，有便宜有贵，但颗粒终究是颗粒；**颗粒之外的所有东西都是可以偷工减料的。**

一个设备连接到计算机上，设备驱动会问它：你是什么型号？你支持什么协议？你的容量有多少？上一讲讲设备和驱动时说过，canonical device 是一组寄存器——相当于我的计算机可以给它送一个特殊的数据结构或者 packet，含义是询问容量，而闪存盘会回一个 packet 说我的容量是多少。**这一切都是可以伪造的。**

所以在拼多多上买那种便宜到绝对不正常的 SSD，很有可能买回来的是一个伪装成 1 TB SSD 的 64 GB U 盘：主控被改过，对外宣称 1 TB，实际只能存 64 GB，超过 64 GB 的部分直接扔掉。刚拿到手的时候它看起来是好的——你拷一个文件进去，把盘拔下来换到另一台电脑上，文件还在。但这只是一个伪造出来的假象；等你继续往后写，后面的东西就开始丢了。这就是不要买过度便宜 U 盘的原因。

### 从字节数组到块数组

所有这些存储设备，在计算机系统看起来实际上是一个 **byte array**。操作系统需要对这样的 byte array 再做一层抽象。于是要回到那个反复出现的问题：**怎么把这个 bit 找出来？**

因为你有好多好多 bit，本质上是一个 byte array 的逻辑结构，要把其中一个 bit 找出来，就需要一个定位、一个寻址的操作。而寻址是在你设计硬件的时候就要付出代价的。

#### 定位的代价

对于电路来说，需要额外的寻址电路——行选通信号、列选通信号这些东西；对于磁盘来说，你需要读写头、需要转轴。所以定位的代价是很大的。只有一种设备例外：SSD 本来就靠电路实现，再加些寻址电路不算特别困难。而磁盘、Project Silica 这类介质上定位，都要额外的物理器件配合。

| 介质 | 定位靠什么 | 代价 |
| :--- | :--- | :--- |
| 电路（闪存） | 额外的行选通、列选通电路 | 最低 |
| 磁盘、软盘 | 读写头 + 转轴，等它转到位 | 毫秒级延时 |
| Project Silica | 机器人到架子上把玻璃取出来 | 更慢，但可并行 |

#### 让一块数据共享一个定位组件

为了减少这部分代价，所有这类存储设备虽然逻辑上是一个 byte array，但都希望**让尽可能多的 byte 共享一个定位组件**。

在 SSD 里，它组织成 page。内部从 die 到 plane 到 block，一层一层地组织下去，直到一个 16 KB 的 page——当然这不是固定尺寸，一般讲是 16 KB。这 16 KB 要读就一起同步、并行地读出来；要写也是一次写 16 KB；要擦除甚至是更大的单位，可能 4 MB 一起擦掉。

```text
  Flash 封装
    └── die
         └── plane
              └── block        ← 擦除单位，约 4 MB
                   └── page    ← 读 / 写单位，约 16 KB
```

这样就减少了寻址开销——不必为里面的每一个 bit 单独做一根行选通线和列选通线，一路省掉了这部分电路。

磁盘、软盘也一样，它以 512 字节为单位存储：盘片上连续的一段 512 字节叫一个**扇区（sector）**，一旦开始读，就把这 512 字节连续读出来，而不是转到任意一个位置只读一个字节。

这两件事是互相成就的：因为在写程序时，我们有办法写出具有**访存局部性（memory access locality）**的代码，硬件才敢以块为单位收放数据；反过来，硬件按块读写，也要求你把程序写得有局部性。

#### 于是设备层看到的是块数组

所以虽然理论上这是一个 byte array，我们希望在软件上看到一个 byte array，但在设备层你看到的是 `struct block` 的数组，每一块是一个 block，可能是 16 KB，也可能更大、或者 4 KB。计算机系统要用这个存储设备，就指定一个编号：「请把三号块读出来」「请把这 16 KB 数据写到第八号块」。这就是操作系统里存储设备的抽象——**读一块，写一块**。

```text
 文件系统看到的：   byte array   →  映射进进程地址空间，按字节寻址
                         │
 设备层看到的：     block array  →  [块1][块2][块3]…  每块 4 KB / 16 KB
                         │
 硬件层看到的：     page / sector / 坑串 —— 共享同一套定位机构
```

在这之上，文件系统、虚拟文件系统还会再做一层抽象，使得我可以把这个 byte array 映射到进程的地址空间里，作为一个可以按字节寻址的设备。但这一层里面操作系统做了很多工作。

#### 读放大与写放大

打比方：你把整个磁盘映射到进程地址空间里，然后写一个字节。哪怕只写一个字节，也需要把这一整块先读出来，读出以后把这个字节改掉，再把整块写回去。所以如果你映射了一大块内存，或者打开一个文件直接写里面的一个字节，就会带来严重的**读放大**和**写放大**：读放大是你想读一个数据，实际读了更多；写放大是你想写一个数据，实际写了更多。我本来可能根本不想看那 16 KB，结果被拖着读了 16 KB。

现在的接口也开始解决这个问题。比如 NVMe 2.0 允许我们不再用 block array 的方式访问设备，而是允许直接去操作闪存里面那种 append-only 的数据结构，这样就能避免读写放大的开销。有兴趣可以课后看一看。

### 存储设备的驱动接口

在操作系统里，你的存储设备也是有设备驱动的。理论上说，因为模型就是「读一个 block、写一个 block」，非常简单，只要为你的存储设备实现一个 `struct block_device_operations` 就够了。

它有点像 `file_operations`，但有一个关键差别：`file_operations` 是对任意 offset 读写的，你可以用 `lseek` 把游标跳到文件的任意位置，然后读数据、写数据；而 block device 不支持这个操作——它要么读一块，要么连续读多少块，要么连续写多少块。

你只要实现读写块的操作，知道怎么在设备上读块写块，剩下的像 `read`、`write`、`mmap` 这些系统调用，全都是 Linux 帮你实现的。

### 用 AI 把块读写抓出来看一眼

开头我给大家放过一页幻灯片：DeepSeek 在招人，招的是能够在**没有直接经验的领域**做有质量保障编程工作的人。那节课后我就想实践一下——假装我对这件事一点都不了解。

今天我上了操作系统课，听老师说 Linux 里有这么一些东西：这个世界上有一个东西叫读块和写块，这个设备是按块访问的，这非常好理解，所有人都知道。那能不能真的在操作系统里看到它呢？我作为一个没有任何知识的人，写了几行 prompt。我当然在一定程度上让它遵循了我的一些设计习惯，比如分成几个组件、让组件之间互相通信；我心里其实知道 Linux 内核里发生了什么，但我故意假装不知道。

结果 AI 很好地完成了。它帮我实现了好几个工具，其中一个是：当系统里发生任何磁盘或存储系统的 block 读、写时，把这个读和写直接打印出来。你不知道这是怎么实现的？这里面用了 eBPF，你可能不知道 eBPF 是什么，你也不需要知道。你只需要知道一条 **first principle**：操作系统也是一个程序；既然是个程序，我就没有任何道理不能 debug 它，没有任何道理不能在它执行关键操作的时候，把这个关键操作拉出来。因为我知道「读一个 block 或者写一个 block」这件事，一定是由代码实现的。所以这件事就是能做到的。

既然拿到了整个系统里所有 block read 和 write 的序列，就可以做一个命令行工具，展示当前系统里发生的磁盘读写。比如我执行 `find /`，就会有大量的文件读取，屏幕上就是一连串的读；我写 100 兆数据到 `a.txt`，马上就看到写入被标出来。它还给出各个进程 IO 延迟的分布、哪一些进程花去了最多的 IO、以及 IO 的类型——蓝色是读，黄色是写，橙色是同步。刚才那次 `find` 花去了绝大部分 IO 操作。

这是我在对操作系统没有知识的情况下写出来的程序，而它正确工作了。以前我上课要写这个 demo，可能得花好几天；今天就完全变了。你可以从 first principle 出发，清楚知道你想要什么，然后你真的可以把任何东西做出来。

我这门课讲的所有操作系统知识，其实都可能不重要了。重要的是，你们通过我讲的这些案例，可以外推到做任何一件事的时候：**老师也许还教过你，一些疯狂的事情是可以去想的——而只要你去想，就有一个非常强的 AI 帮你实现。但如果你都不去想，你可能这辈子就不会有机会去实现它了。**
