## 计算机系统安全：从裸奔的硬件到访问控制
> 对应块：BLK55 | 覆盖分集：P28上 | 块标题（分集名）：《计算机系统安全（上）》

这一周要上两次课，讲一些补充的内容，这些内容不做考试要求。这一次讲计算机系统安全，下一次讲容器、虚拟化，包括 agent 时代的沙盒——跟大家的关系其实比较近，但都不算传统操作系统课的主干，就当听点小故事。文件系统的部分已经讲完了，不过它的接口、它的实现，还是需要你们在一定程度上了解；期末考试在这部分我会考得灵活一些，需要你们在 AI Agent 的帮助下，真正理解文件系统是怎么来的，以及换成你自己去设计会怎么设计。

而文件系统、或者说操作系统里的各种对象，给我们带来一个额外的问题：计算机系统的安全。这是一个讨论功能时不太会被谈起的问题。在计算机系统的早期，可以说完全没有任何安全可言。

### 从一台 8086 PC 说起

如果你有一台 8086 的 PC，那是一个 real mode 的机器：CS 是 16 位，IP 也是 16 位，但它们能凑出 20 位的地址空间——把 CS 左移 4 位，再和 IP 相加，就得到 program counter 的地址，于是有了寻址 1 MB 的能力。

```text
   CS (16 位)             IP (16 位)
   +--------------+       +--------------+
   |              |       |              |
   +--------------+       +--------------+
          |
          |  左移 4 位（× 16）
          v
   +--------------+       +--------------+
   | 0 0 0 0      |   +   |              |
   +--------------+       +--------------+
                \             /
                 \           /
                  v         v
              20 位地址 = CS × 16 + IP   →  1 MB 寻址空间
```

关键在于：这个 CPU 没有任何保护。也就是说，我其实可以 patch 任何一个程序的任何一条指令。

那个年代的系统调用是靠一条叫 INT 的指令完成的，用起来就相当于一次函数调用。你 INT 几，它就算出地址 $n \times 4$；地址空间最底下有一张中断向量表，从那个位置把地址取出来，就能做一次长跳转——相当于一次直接的函数调用，跳到 firmware 里只读的代码上去执行。这就是 16 位时代的系统调用。

```text
   INT n
     |
     v
   n * 4  ───► 内存最底部的 中断向量表
                    +----------+----------+
                    |  offset  |   seg    |   ← 取出一段远地址
                    +----------+----------+
                          |
                          v
                     长跳转（等价于一次函数调用）
                          |
                          v
             firmware 中的系统调用实现（只读，你改不了）
```

系统调用的代码在 firmware 里，所以你改不了它。但你可以任意地改另外一个程序地址空间里的内存，完全不需要操作系统的 API 监管、审计，这些东西全部都没有。在那个时代，几乎没有任何安全可言：病毒可以复制自己，然后去感染更多的计算机。

这里面有一个术语叫**加壳**。你可以给应用程序加一个壳：在你的 ELF 文件里 patch 上任何一段代码，然后把 ELF 的 entry 改成你自己的代码。这个程序启动的时候，就会先从这个壳上开始运行；壳跑完了以后，再跳转回原来那个 ELF entry 的代码。于是你的行为就完全隐藏起来了——这个程序如果本来是个游戏，它看着还是一个游戏；本来是个文本编辑器，它看着还是一个文本编辑器，和原来的行为完全一样。但每一次运行，它都会悄悄执行你加进去的那段壳代码，这时候你就可以去复制自己、去感染别人，甚至去破坏硬件——CIH 就是可以破坏硬件的病毒。

```text
   原始 ELF:      [ ELF header: entry = main ]  ──►  main

   patch 之后:    [ ELF header: entry = shell ] ──►  shell 执行完 ──►  跳回真正的 main
                                                       ^
                                                       +-- 每次启动都先跑这段
```

### 网络也曾经完全没有安全可言

那时候的计算机网络同样没有安全可言。小百合已经倒闭了，我还特意找到一个古早时期的南京大学校报链接来介绍它。2000 年 11 月的那份简介里，你可以想象当时的氛围：大家都没有安全的意识，HTTPS 甚至都还没有流行起来。水木的网站现在还活着，直接连上去，大概就是那个样子——页面上充满了 ASCII art，当然这跟我的终端显示也有点关系。我可以用 guest 登录，也可以用自己的用户登录，要输入用户名和密码。而这些用户名和密码**全部以明文方式在网络上传输**：如果你做一个钓鱼的路由器，你就可以收集到很多很多小百合的密码；不仅小百合，当时相当多的网站都没有用 HTTPS 来加密。

登录以后你会看到一个字符界面。在命令行里可以跳转到某一个版面，可以发帖、可以回帖。那时候我们每天最大的乐趣，就是看全站十大热门话题，发一些奇奇怪怪的东西——跟今天你在小红书上发个奇怪的东西有点类似。

而这个网站是没有任何防护可言的。我可以用写脚本的方式疯狂地尝试密码和登录；又发现小百合有一个功能可以爬到所有用户的列表，于是我就有了全部用户的名单，再配上我手里的密码库，就能得到很多个小百合账号。拿到这些账号干什么呢？当时的想法是去上十大：每天有十大热门话题，最厉害的人一天能上六个，那已经非常厉害了。我们想的是怎么才能上十个。

这显然不是我们真正想要的东西。因为网上的信息一旦开始牵涉个人隐私，一旦牵涉支付，性质就完全不同了。那个年代互联网对大家来说还是可有可无的东西，不安全也可以接受；但你肯定不能接受的是，你在里面充了很多钱——比如支付宝里有很多钱，而你的钱因为你密码保管不善，或者别人用一个钓鱼路由就把你的账号拿走转走了。所以，当现在的互联网、移动互联网要承担更大的职责，安全性就变成一个非常非常重要的问题。

### 安全的三件事：保密、完整、可用

我们的安全有三个方面。

#### 机密性

第一个叫机密性，也叫保密性，confidentiality。意思是：你不想给别人看的，别人就看不到。比如你偷偷拍了一张不想让别人看的照片，你把它删除了，你就希望再也没有人把它捞回来——甚至格式化以后也不要捞回来。但实际上在那个时候它是可以被捞回来的。

现在想要实现保密，基本上就是加密。你的文件系统其实是可以加密的。再比如我们的手机，每一台现在的手机，不管是我这台苹果的，还是你们手上的 Android，它其实都有一块加密计算的区域；这个区域甚至不信任你的操作系统，认为你的操作系统都有可能是有问题的，它以非常安全的方式保存你的指纹这一类比较敏感的信息。

#### 完整性

第二个是完整性，integrity：不想让别人改的，别人就改不了。

你们有没有想过，如果你能够入侵教务系统并且修改自己的期末考试成绩，会发生什么？当你大四保研的时候，辅导员就会导出一个名单，然后纳闷：这个同学平时成绩都不怎么好，为什么保研的时候排名这么高呢？

真有过这样一位师兄，他干的就是类似的事。他用一个钓鱼的、XSS 的链接发给了教务员，教务员在自己的邮箱里点开了那个链接；点开之后，他就拿到了教务员的 session，从而可以登录那个教务系统。教务员是有权限处理各种信息的，所以他看到的不仅是自己的信息——机密性暴露了，完整性也暴露了。当然他实际上没有改自己的成绩。

这位同学还有很多传奇故事。比如他通过网上公开的视频做了一次频率分析——拨号的时候按每一个数字都是有频率的，而且是好几个频率叠加的——反推出周鸿祎的手机号，然后打电话给他。但最终，他因为通过入侵信息系统拿到了期末考卷，学校给了他一个留校察看的处分（我不能确定他有没有看过卷子）。这个惩罚对学校对他可能都算偏重，但至少给了他一个教训：在社会上，该服从的时候还是得服从。

他后来成了科创板首位 90 后，公司是 Insta360。我现在做直播录制的设备就是 Insta360 的设备，所以我也算支持他了。Insta360 一直是一家做产品很有品味的公司，我觉得它值得一个科创板的上市。

这就是完整性：当你入侵别人的系统、篡改别人的数据时，别人的安全就受损了。而且这实际上是入刑的，应该是破坏信息系统罪——你可以犯这个罪，然后就可以去踩缝纫机了。所以确实不要做这样的事情。

#### 可用性

第三个维度叫可用性，availability：我自己有一个服务、有一个我能用的东西，它得一直能用。

你们有没有想过对室友做这样的事：他有一个柜子，柜子里有一件很好的东西，他不给你用，而且他的 security 做得非常好。那你怎么办呢？你可以去破坏他的可用性——你去买一把锁，把他的柜子锁上，然后把钥匙扔掉。

你确实没有违反前面两条：他不想给你的东西，你确实也看不到；柜子里的东西改不了，他自己也改不了了。但他的可用性受损了。

这里面有一种很有意思的攻击叫**拒绝服务攻击**，denial-of-service，而且可以是分布式的，也就是 DDoS。比如说，如果你通过入侵计算机系统的方式获得了 1 万台机器的 SSH 登录权限，你就可以拿着这些登录资格，在这一万台机器上同时向 DeepSeek 发起请求。我前两天做了一个很有意思的实验：我生成了一串大概 100K 的随机数字，然后让 DeepSeek 从 1 数到那个数字。有意思的地方在于，如果你去看各个模型，模型会拒绝你，说这个数字太大了、我数不了；但 DeepSeek-R1 有一个很有意思的行为——开启思考的时候，它的思维链会先把问题重新重复一遍，于是它就开始输出「用户给我的问题是从 1 数到……」，然后开始把那个数字抄一遍。你想一想，如果你有一万台肉鸡，你就可以瞬间让 DeepSeek 这个服务瘫痪掉。

还有一种攻击来自程序里的时间复杂性漏洞，专门有个名字叫**算法复杂性攻击**，algorithmic complexity attack。比如 hash table，它有好多个 slot；你有一个字符串 `hello`，它经过一个 hash function 被送到某一个 slot 里，这是 OK 的。平均下来，每一次 hash 操作都是 $O(1)$，因为元素均匀地分散在这个 hash table 里。但如果你精心构造很多个字符串，让它们都 hash 到同一个地址上，那就惨了：如果你用的是开放寻址，或者是放一个链表，所有人都映射到这个数组下标，hash table 就退化成一个线性时间的数据结构，非常糟糕。

一个办法是把这里换成一棵二叉树，换成一个 worst case 比线性更好的数据结构，这样它就算被攻击了也不至于这么糟。后来 standard library 应该是做过这件事：当某一个桶大到一定程度的时候，就会换一种数据结构，变成一棵树。但至少这个漏洞很早以前就一直存在。

再比如 Apache 这样的网络服务，跟我刚才说的对 DeepSeek 发动的那种攻击一样，你甚至都不需要一万台肉鸡——在云上租几台主机，给它发送超长的请求，就可以瞬间把一个网络服务瘫痪掉。这就是 availability。

> **结论**：安全就是这三件事——保密、完整、可用。我今天主要讲计算机系统的安全，也就是**操作系统给我们提供什么样的机制，帮我们实现保密性和完整性**；可用性更多是资源管控的时候你要做好的事情。

### 密码学中最小必要的几点

在讲系统安全之前，因为今天讲的是计算机安全简介，我还是要花一分钟——也许不止一分钟——给大家介绍一下密码学。这也是一个非常 narrow 的简介，只把比较重要的几个点说一下。

#### 单向函数

首先有一种东西叫单向函数，one-way function。它是一个函数 $f(x)$：$f(x)$ 很好算，正向很好算，但它的逆向非常难算。比如 `sha1sum`——这个我们在课堂上其实已经用过了——你可以把任何一个字符串变成一个数字。

它和你们在 Java 或者 Python 标准库里见到的那种 hash function 不一样：那种 hash function 更多是把一个字符串当成一个 256 进制数，然后取个模或者怎么样，所以你在末尾把那个字母从 `a` 改成 `b`，hash value 就加一，是一个比较 predictable 的 hash function。而像 MD5、SHA-256 这些密码学的 hash function，它们满足两点：第一，你很难逆向——你有 $f(x) = y$，算 $y$ 很容易，就像对一个很大的文件算 `sha1sum`；但给你一个 $y$，让你求一个 $x$ 使得 $f(x) = y$，非常非常难。第二，你很难找到两个输入碰撞到同一个 hash value 上。你几乎只能暴力地、随机地去找——它看起来就像一个随机数：虽然 $f$ 是一个 deterministic 的函数，但 $x$ 输出一个 $y$，看起来就是随机的，所以你要找它，你就没有办法。

有了单向函数，你就可以做 hash digest。比如我现在有一个很大的文件、一个视频，它到底对不对、完整不完整、我下载的时候有没有发生损坏？我可以在网络上把它的 `sha1sum` 写下来，你回来以后用同样的方式去验证——$f$ 是公开的，MD5 和 sha1sum 的函数本身都是公开的。

> **提示**：这里容易混的是两种「hash」。标准库里的哈希追求的是快和分散，输入变一点点输出就变一点点也无所谓；密码学哈希追求的是不可逆、不可碰撞，它必须看起来像随机数。前者用来做索引，后者才能用来做完整性校验和签名。

#### 陷门单向函数：加密与认证

除了单向函数，我们还可以找到很多很有趣的东西，叫**陷门单向函数**，trapdoor one-way function。函数 $f$ 本身还是正向算容易、反向算困难；但是如果我有一个数字 $t$——trapdoor，你可以把它理解成一个后门——那么它的逆向就好算了。没有这个 $t$ 的人，能看到 $f$，也能验证 $f(x) = y$（正向算谁都会算），但你给他一个 $y$，他反推不出一个 $x$；而有了 $t$ 的人就可以算回去。所以这个 $t$ 就是一个掌握在自己手里的、非常重要的钥匙。

你们在 `.ssh` 目录下会生成一个 `id_rsa` 和一个 `id_rsa.pub`：那个 `pub` 就相当于这个函数——`.pub` 代表这个函数，当然还带了算法本身——而你的 private key、私钥就是这个 $t$。有了 $t$ 以后，逆向就好算了。

用这个性质我们可以做两件事。第一件是**加密**。因为 $f$ 是公开的（`.pub` 是公开的），所以如果我想加密，我就把要加密的东西用 $f$ 求一遍；一旦求过 $f$，它就是一个 one-way function，别人就解不开了。但因为这是 trapdoor function，只有拿着钥匙的人才能把它解开。这相当于 Bob 把要传输的数据放进了一个盒子里，这个盒子别人都打不开，而我有 trapdoor 的 $t$ 的时候，就可以把它解出来——这是正过来用，实现机密性。

```text
   正向用（机密性）:
      明文  --f（公开）-->  密文  --??-->  明文
                                        ^
                                        +-- 只有持有 t 的人走得通

   反向用（认证）:
      我  --随机生成 y-->  你  --用 t 求逆-->  x
      你能在短时间内给出 x，就说明你拥有 t
```

反过来用，你也可以实现身份的认证。同样需要公开这个 $f$。我要验证你是不是 Alice、是不是 A、拥不拥有那个 trapdoor 的 $t$，我就会生成一个随机的数字 $y$，然后你 A 可以用 trapdoor 去把它解开，解开以后给我一个 $x$。如果你能够向我证明，你能解开我随机生成的一个 $y$，就说明你拥有了这个 trapdoor，我就能够信任你。我甚至不需要看到你的 trapdoor 到底是什么——因为你向我证明了你可以**在短时间内**算出 $f$ 的逆，这就意味着你拥有这个 trapdoor，所以我能信任你。这是一种在时间维度上的信任。

如果你把这个随机数换成任意文件的哈希，你就实现了**数字签名**的机制。基本上就是用这样的 one-way 的 trapdoor function 来实现的。

没听明白不要紧，你大概知道有一个神奇的函数，可以帮我们实现没有人能破坏的完整性和机密性就可以了。

> **注意**：公开 $f$ 的过程本身是有危险的，所以你的信任是不断传递的——你需要在一个可信的地方去公开你的 $f$。

### 没有人能摧毁的数据结构

这个神奇的函数可以用来实现数据结构。有一个神奇的数据结构——你看，又是 append-only，数据结构课的含金量还在上升。

如果我们有一个 append-only 的数据结构，每一次都可以 append 一个字符串，并且这个 append-only 的数据结构是全世界人共同维护的一个共识，那我们就能用它来记账。这就是 blockchain，区块链：每一次你可以理解成每一个块都是一个字符串，它会算一个 hash，而这个 hash 覆盖了它所有前缀的哈希——就是用刚才那种 one-way function 算出来的前缀哈希——以此来确保每一个块都是签名过的。

```text
   block(n-1)          block(n)            block(n+1)
   +------------+      +------------+      +------------+
   | 前缀哈希   |◄-----| 前缀哈希   |◄-----| 前缀哈希   |
   | 数据/签名  |      | 数据/签名  |      | 数据/签名  |
   +------------+      +------------+      +------------+
         \                   |                   /
          \                  |                  /
           +------ 分叉时，谁更长就听谁的 ------+
```

也就是说，这是全世界人共同维护一份的、append-only 的数据结构。它实际实现的时候不是用链表实现的，用的是一种树状结构：可以用一棵二叉树来快速地维护所有前缀的哈希。这个细节也不重要。

它是怎么做的呢？你可以想象这个世界上有好多条狗，想要共同维护这个链。任何一条狗想要往这个数据结构上 append，它就向一个随机的位置扔一根独一无二的骨头——位置是随机的，骨头也是随机的。其他的狗听到了，它会向全世界广播：「哎，我现在扔了一根骨头了。」其他狗听到了只能随机地去捡：它没有办法，这正是靠 one-way function 保证的，它只能随机地看看这里有没有、那里有没有。那基本上就是谁花的时间多，谁就能捡到。而捡到也是靠 one-way function 去确保：捡到的那根骨头是一个足够小的 hash value——这就是 proof-of-work，我证明我投入了这么多的时间。

捡到以后，根据协议，你就可以把那件事记录下来：我在什么位置捡到了一根骨头，骨头上面是什么；而且这所有的东西都是签名过的。正是因为这套 one-way function 加 proof-of-work 的机制，其他所有人都能看到这是一个合法的、正确的、可以验证的 append。

当然，是有可能同时有好多人扔骨头、捡骨头的，链就会分叉。但分叉以后，整个链还有一个所有参与者共同遵守的协议：**谁更长就听谁的**。短的链自然而然地慢慢就消灭了，更长的链会一点一点存活下来。这也是一个很有意思的机制：捡到一根骨头非常难，使得 append 变得比较困难，短时间内不可能出现全世界好多条狗同时捡到骨头的情况，所以分叉不会太多，收敛相对来说也比较快。这是一个非常非常聪明的设计。

甚至这个协议里 append 的不一定是一个字符串，你完全可以用一个图灵完备的计算、一个虚拟机来运行一段代码。比如说我 append 的实际上是一段代码，这段代码说：我要从哪一个钱包里拿多少钱送到另外一个钱包里。你把它写到这个地方，它就有一个对应的执行状态；所有人都会看到，所有人都会 replay 链上所有的状态——理论上 replay 所有的状态——于是我就知道谁有多少钱。这样它就成了一个全世界达成共识的 append-only 数据结构。

> **结论**：这个结构带来了绝对的 availability——全世界所有人都是 replica，只要你们都信任这个协议；但它**没有任何 confidentiality**，它本来就是为了实现分布式的共识而设计的。

这个没有人可以摧毁、绝对信任的数据结构，最大的应用是什么呢？这个我不能多说，再多说我就进去了。但我可以说的是：有一些人进去的时候，在住处被搜出了一串佛珠，上面刻了 24 个英文单词。24 个英文单词就是你的 private key——你要证明你是你自己、你拥有那笔钱，当我拥有转账的权利时，我必须做我的数字签名，而这个数字签名是一个 one-way function、一个 trapdoor function，你需要那个 trapdoor 的 key，那个 key 就刻在珠子上。据说那是价值 1.3 亿美元的比特币。不确定是真还是假，我不传谣，这是互联网上有的一种传闻。

### 回到操作系统：安全就是访问控制

不过我今天讲的不是这种类型的安全。我今天讲的是：如果你在操作系统世界里，安全是什么。

操作系统是什么呢？又回到我最开始上课的时候说的——操作系统就是一组 **API**，里面有很多对象，操作系统上面是程序。程序在运行的时候是有运行时状态的，它有进程、有线程；程序可以通过 API 去访问操作系统里面的对象。这就是操作系统。

在操作系统里面谈安全，谈的还是这三件事：confidentiality、integrity、availability。那么我们就要在操作系统里面去实现这些我们想要的安全特性。

实际上，你回头想一想，操作系统其实已经提供了一些不破防的机制了。不再像 8086 那个时代，任何一个程序都可以访问整个系统里所有的硬件设备、每一个字节的内存。现在不是这样的：你的进程的地址空间是隔离的，是一个虚拟的地址空间（当然操作系统可能提供一个 API 去访问另外一个进程的地址空间，这是有的），但至少在默认情况下，如果你只是执行计算的指令，你是完全被封在一个虚拟地址空间里的。而这个世界里所有对操作系统对象的访问，都是通过这组 API 完成的。

这是一个非常有用的特性。相当于这组 API 是一个口子，操作系统就牢牢地抓住了这个口子：你的应用程序计算可以随便做，但是一旦想要访问对象，必须通过操作系统的 API。

所以在操作系统上面就可以很容易地实现访问控制。API 一方面有它的**行为**——我们从 `fork` 开始复制一个程序，到 `mmap`，到 `read`、`write` 都是访问，还有 `mount` 一个文件系统，这些都是具体的行为；但同时，在这个行为的同时它还有一个很重要的功能，就是**访问控制**。

当应用程序调用一个 API，比如说它说要 `open` 一个文件，操作系统首先知道 `open` 的行为是什么：返回一个文件描述符，然后指向这个对象，这个对象是明确的。但操作系统还有权力去**拒绝**这次访问，这就是访问控制。如果你拒绝这次越权的读，你就得到了 confidentiality——如果操作系统认为你这个程序不应该能读这个对象，它就会拒绝这次 API 调用。如果操作系统认为你要做的写操作、你没有权限修改那个对象，它就实现了 integrity。而如果操作系统在对资源管控对象的访问时实现得足够公平，它又能提供一定程度的 availability——当然 availability 是一个很复杂的事，比如刚才说的 denial-of-service 攻击、算法复杂性攻击。

你能看到，操作系统确实提供了这样的机制。它有两部分：一个是**机制**——访问时候的控制和检查；还有一个是**策略**——你需要为你的系统配置谁、哪些进程可以访问哪些对象。

这就是操作系统安全里最重要的、也是最经典的**访问控制**。

那什么是访问控制呢？因为系统调用是程序访问对象的唯一边界，所以本质上访问控制就是一张巨大无比的表：

- 访问对象的实体是程序，是进程或者线程——是一段可以运行、具有 running context 的东西，它才可以访问对象；
- 那这个表里面的第一列就是进程，第二列就是对象。操作系统里可以有各种各样的对象，这是我花了一整个学期跟大家讲的各种各样稀奇古怪的对象；
- 第三列是访问方式：应用程序对对象可以有读、可以有写，也可能有更细的，比如我对一个 KVM 做 ioctl，我就可以控制它非常细致的行为。当然最基本的行为就是读和写。

```text
              对象 1      对象 2      对象 3      对象 4
   进程 A     读          -           写          -
   进程 B     -           读          读 + 写     -
   进程 C     -           -           -           执行
```

当你确定了哪一个进程对哪一个对象做了什么访问，其实你作为一个人，就知道这件事是可以还是不可以。你作为这个系统的管理员，理论上这张表提供了足够的信息，让你决定应该接受这次访问，还是不接受这次访问。

### 这么大一张表怎么存

访问控制就是一张巨大无比的表。但你肯定不能直接在系统里存储这张表：系统里动不动就有几千几万个进程，几万个进程有几百万个对象，几百万个对象访问方式可能有好多种。你把它乘起来变成一个巨大无比的表，肯定是存不下的。

怎么办呢？你有没有觉得这是一个矩阵？它是一个矩阵，而这个矩阵是可以做一个 low-rank decomposition 的：它本质上信息量很少。因为如果是一个低权限的用户，几乎对于所有的东西的访问都应该是拒绝的——除了他自己的那些东西和系统公用的那部分以外，他什么都不能看、什么都不能改；系统公用的那部分他可以看，但不能改。除此之外几乎没有其他权限了。

所以要把这张表切小，非常自然。

UNIX 做的事情是用整数去表示身份，把这张表拆成几个关键要素。第一个：系统里有一些身份，对于每一个身份、每一个对象又有一个访问权限。这是一个非常自然的、从现实世界当中继承过来的模型——冤有头、债有主，每一个物件都有一个 owner 的概念；而这个物件又在不同的场合、不同的人之间是可以共享的。比如你的文具，owner 就是你，但你可以在宿舍的范围里、或者其他某个范围里共享它。所以很自然地，UNIX 就有了**用户**和**组**的概念。

你在任何一个目录里直接 list，都能看到它有用户、也有组。而在 UNIX 世界里，**UID 等于 0 就代表这是 root**，一个权限绝对高的用户，他可以执行任何操作：对 root 来说，所有的访问控制都是放行的。无论你在 mode 里面写什么，比如说写成没有任何人可以访问，root 也总是可以访问的。不然的话，如果你做了一个错误的配置，连 root 都删不掉，这个文件就永远死在里面了——我就可以实现这种拒绝服务攻击：在磁盘里留下无数多你删不掉、但又占用空间的东西，把其他人的 availability 给伤害了。

root 本质上可以访问所有的对象，而且他还可以 `setuid` 把自己变成任何一个其他人。于是这样就可以实现登录：登录本质上就是我以一个最高的权限去做一次密码验证，如果你的密码验证通过了，我这个进程就变成你那个登录用户。此外，子进程会继承父进程的用户，所以在整个进程树里，你不停地 `fork`，都会获得相同的权限。

除了用户以外，还有组。组和用户不太一样：一个用户可以属于多个组。你可以为同一个用户、同一个组和其它的用户，分别设置读、写和执行的权限，也就是你们看到的文件的 mode：

| 归属关系 | 权限位 | 含义 |
| :--- | :--- | :--- |
| 文件的所有者 | 第 1 组三位 | 同一个用户的读、写、执行 |
| 所属的组 | 第 2 组三位 | 同一个组的读、写、执行 |
| 其它用户 | 第 3 组三位 | 剩下的所有人的读、写、执行 |

这样你就把那张大表，变成了每一个文件里面非常小的几个字节。

然后再加上系统里有一张表，记录系统里有哪些用户、有哪些组，这就涉及到一个非常重要的文件：`/etc/passwd`。这个文件可以看——我作为一个普通用户也可以打开它。你可以把密码的 hash（就是一个 one-way function 的结果）直接放到这个文件里，这样我就可以做用户的登录了；只要我的普通用户没有权限去改这个密码，这就是安全的：这个文件对普通用户来说都是只读的，只有 root 用户可以修改。

它的字段是这样一串：

```text
username : password : uid : gid : comment : home : login shell
```

你们在系统里用过的很多功能，本质都是改这个文件。比如 `chsh`，change shell，可以改变用户的 login shell：我现在开启一个新的终端，默认是一个 fish 而不是 bash；而在你们的系统里，默认创建一个用户的时候，他的 shell 应该是一个 bash。你想修改这个 login shell，就可以通过 change shell 来实现，而它的本质就是修改 `/etc/passwd` 里的第七个字段。

在早期的时候，Unix 密码就存放在 `/etc/passwd` 这个文件里，那么 `passwd` 这个命令也是直接修改这个文件——你可以改密码。

### 一个悖论：我为什么能改密码

诶？你们有没有发现，刚才我说的那句话里面有一个非常严重的逻辑问题。

`/etc/passwd` 是一个非常重要的文件，肯定不能随便乱改。那我自己在执行 `passwd` 的时候，为什么我可以修改我的密码？这不是一个悖论吗？

你看，`sudo passwd` 当然可以改，我甚至可以直接把密码改成 `1234`，它会告诉我 update successfully。那为什么我执行 `passwd`、输入当前密码、再改成 `5678` 的时候它也让我改？它拒绝了，好吧，那改成 `12345678`，`Update successfully`——全程我都没有 `sudo`。但我肯定不能 `passwd root`，你看，它告诉我我不可以。

所以访问控制实际上比大家想象的要复杂一点。你们都知道这个世界里有用户、有 UID、有 GID，操作系统就会通过这些编号来判断你有没有权限读写、执行某个文件。但实际上不完全是这样的：UID 里面有无数多为了实现系统功能打上的各式各样的补丁。也就是说，实际上没有一个系统在它变得复杂以后，能够逃脱成为屎山的命运。

我们的世界里有 real UID、有 saved UID、有 effective UID、有 file system UID——当然这个 file system UID 现在不用了。

还有这个 `setuid` 的机制，它是一个非常 legacy 的机制。你看，当我 `ls -l` 的时候，`ls` 命令甚至以**红色**的方式来显示 `/bin/passwd` 这个文件。为什么要用红色来显示？你再看它的 mode，这里有一个 `s`：本来是 `rwx`（可读、可写、可执行），但它叫 `s`。因为 `/bin/passwd` 设置了 setuid，就显示为 `rws` 中的那个 `s`。

> **定义**：这类设置了 setuid 位的文件，执行时以**文件所有者的权限**运行，而不是以当前用户的权限运行。`/bin/passwd` 的 owner 是 root，所以有这个 setuid bit 的时候，这个文件就会以 root 的方式来运行。

```text
   我（普通用户）执行 /bin/passwd
        |
        v
   mode = r w s r - x r - x    owner = root
              ^
              +-- 这个 s 就是 setuid 位（原本是 x 的位置）
        |
        v
   该进程的 effective uid 变成 0（root）
        |
        v
   /etc/passwd 只允许 root 写  →  这次写操作被放行
```

啊，这样我虽然是普通的用户、是一个没有权限的用户，但当我启动这个程序的时候，只有这个程序会以 root 的身份运行。当然，我肯定不能把不属于我的文件设成 setuid——这个就太危险了。这其实是一个非常危险的操作，你看它会变红；变红就意味着这个可执行的程序得到了超越执行者本身的权限。

如果假设这个程序执行是没有漏洞的，那它还可以正常工作，像 `passwd` 那样。但是一旦 `passwd` 这个程序里面有一个漏洞，它就很有可能会被攻击，所以这个机制也不常用。

至于像 effective UID、saved UID、real UID 这些，你们可以去看一篇 USENIX Security 2003 年的论文，叫《Setuid Demystified》。我很喜欢这个论文的标题，因为确实在那之前，大家对 Unix 里的理解就是「哦，OK，就是那个 mode 的 bit」，你不知道这个系统里面为什么还需要有这么多的 UID，而这篇论文真的是把这个问题讲清楚了。

不过我现在看到最近有好多好多文章都叫什么什么 demystified，我很讨厌这样的标题，因为它根本就没有 demystify anything——本来就不是一个 mystery。当你用 demystify 的时候，只有这个东西真的「大家 care about、人人都知道、人人都用，但是人人都不知道」，你才可以去 demystify。这是我自己的观点。所以以后你们写 paper 的时候，不要现在随大流，我不知道从什么时候开始大家开始喜欢在 paper title 里用 demystified；我只认这一篇《Setuid Demystified》。这是个题外话，我就不再展开了。

### 回到那张大表：ACL 的方向

回顾一下，这个访问控制的本质是什么？刚才我们说的读写执行、什么 setuid bit，它的本质还是：我希望维护那张大的 matrix——主体（程序/进程）、对象、访问方式，然后 yes or no。

刚才那些机制，从最开始有了用户和组以后，之后又加上了各种各样的机制。那我们有没有办法让访问控制回到「我去定义这张表」？因为当你说分成用户和组的时候，你就已经把这个表做了一个过度的简化。如果你想要真正实现访问控制，你可以从这个大的访问控制矩阵里面切出一部分，或者找出一些你真正关心的东西来做访问控制。

比如现在我们的系统里有一个机制叫 **access control list**，它就可以提供细粒度的访问控制，以文件为单位，支持为用户和组分别设置访问控制权限。

## 访问控制之外：漏洞、旁路与 AI 时代的安全
> 对应块：BLK56 | 覆盖分集：P28下 | 块标题（分集名）：《计算机系统安全（下）》

学访问控制有一个特别省力的角度：把你知道的每一种机制，都看成同一张访问控制矩阵的不同投影。我自己就是这么干的——直接把问题丢给 AI：如果把某种访问控制机制当成整张访问控制矩阵的一个投影来理解，它该怎么解释？它马上就能把 POSIX 的 ACL、AppArmor、seccomp 一样一样摆开。顺着一个矩阵去想，你就能把它的各种不同侧面切出来，学这些东西的效率会高很多。

### 访问控制矩阵：一张表，几种投影

访问控制矩阵长成一张表：一行是一个主体（谁能发起访问），一列是一个对象（谁被访问），格子里写的就是"这次访问允不允许"。

| 主体 \ 对象 | `/etc` | `/bin` | 进程 | 设备 |
| :--- | :--- | :--- | :--- | :--- |
| alice | 读 | 执行 | — | — |
| bob | — | 执行 | — | 读写 |
| root | 读写 | 读写执行 | 读写 | 读写 |

这张表决定了每一个正在运行的程序和每一个对象之间每一次 API 调用的 yes 或者 no。所谓"投影"，就是各种实际机制在这张表上切出来的切面——它们的区别只在于：行是什么、列是什么、格子里的判定有多细。

#### POSIX ACL：把粒度切得更细

POSIX 的 access control list 还是以文件为主体，还是以用户作为控制维度，但它提供了更细粒度的访问控制。你可以单独写一条规则：哪一个用户可以访问，或者除了这一个用户可以读，其它用户都不能读，谁都不能写。它挂在文件的扩展属性（extended attribute）上——相当于把这套规则写在文件的元数据里。

#### AppArmor：安全落在程序上，而不是用户上

一个程序 binary，比如你要执行 `ls` 或者执行 `a.out`，在你执行它的时候，你是什么用户，这个程序就会变成什么用户。还记得 `passwd` 吗？`passwd` 很有意思：我运行它的时候，它就知道我是谁；我 `sudo passwd`，它就知道自己是 root。程序本身是一段不变的代码，但它会继承父进程的 UID；继承父进程的 UID，就意味着它继承了父进程的权限。如果它跑在一个 root 的 shell 里，它就是 root 权限；跑在我现在的用户下，它就是我现在用户的权限。

但不是所有程序的访问控制都建立在这种动态的 UID 之上。AppArmor 的想法是：它的安全不发生在 user 上，不发生在 UID 上，而是发生在 program 上。

不管什么程序，比如一个 Nginx，我都可以给它一个访问权限的上限：Nginx 只能看到这几个目录里面的文件。因为它理论上不应该去调用系统里其他的部分；如果它偷偷去调一个 `passwd`，那就是一件很危险的事情。所以我应该给它造一个像虚拟世界一样的东西，把世界里其他的部分直接从它的眼睛里面抹去，它永远看不到世界其他部分——有点像做一个虚拟化。

> **提示**：把系统里所有禁止访问的对象从被监控程序的眼睛里抹掉，这本身就是一种做访问控制的思路：不去逐条判断"你能不能访问它"，而是让它在自己的世界里根本看不到那个对象。

#### seccomp 与 eBPF：把判定代码塞进内核

顺着这张表还能想到一条更激进的路：直接写一个程序，一个 access control function；每当被监控的程序或者用户通过操作系统的 API 去访问对象时，就额外多走一个 function。这个 function 甚至可以编译到内核里，由我的程序来决定你这次访问可以还是不可以。

这件事是有的，而且都借用了 eBPF 的机制。比较有意思的是 seccomp：它在进程上面砌一道墙，然后留几个由 eBPF 把守的门。eBPF 是一个允许我把一小段自己写的代码插入到内核里面的机制；这段内核里的代码不能随意修改内核——修改内核太危险了——它基本上是一段只读的代码。但只读的代码可以有返回值：我可以返回一个 yes 或者 no。于是我返回的 yes 和 no 就决定了这次访问是接受还是拒绝。seccomp 因此允许我写一个这样的访问控制代码，把它放进内核，在生效的时候拒绝各种各样的访问。类似地，从内核 5.7 开始，也有用 BPF 实现的 LSM 来做访问控制。

把这些放一起看：访问控制其实是一个巨大无比的矩阵。你可以做最细粒度的访问控制——为每一次单独的访问配一个图灵完备的程序去检查，甚至可以调用大语言模型来选择接受还是拒绝这次访问。想更高效，就只关注常用的那部分：AppArmor 很聪明，它要为你的应用程序构建一个虚拟的世界，把你不该看到的东西直接从你的世界里抹除掉。同一个想法，既可以用图灵完备的程序实现，也可以用一个更高效的方式实现，在系统里做一个 tradeoff。

访问控制很重要，也很好用：`/bin` 下面的这些文件我是不能随便访问的，如果能随便访问，我就对整个系统造成了不可逆的破坏，甚至是安全问题。

### 访问控制之外：程序里没人走过的路径

但访问控制真的解决了计算机系统安全里的所有问题吗？其实不完全，尤其是基于用户的访问控制。

一个暴露在外部的程序，比如 Nginx，会非常小心地选一个权限非常低的用户去执行它——这样就算 Nginx 被黑客 hack 了，它也不能破坏系统的其他部分。Android 里每一个应用程序都是一个单独的用户，它的权限只局限于这个应用程序自身的数据，以及操作系统允许它看到的共享部分。

那如果一个程序是跑在 root 权限下呢？比如 `/bin/passwd`，因为它有一个 setuid bit（所以权限里有个 `s`），它实际上是在 root 权限下运行的。正常情况下这个程序是好的：执行完功能就结束；你给它一个非法的输入，比如一个错误的密码或者一个不存在的用户名，它应该马上就拒绝。但是通常我们的程序里都隐藏着无数没有人可以理解的路径。

你永远无法预期你的用户会怎么样使用你的产品，即便你的手册写得再清楚；你更无法预期你的用户会怎么样恶意地去使用你的产品。所以现在专门有一种技术叫 fuzz testing：自动生成大量你无法解释的输入，看起来就是随机的、完全不对的，但它能够把你的程序走到你预先没有想象过的路径上。而这条路径就有可能悄悄地把别人的个人隐私泄露出去，或者悄悄地在你的账户里面加了很多钱。

有点像那个山寨支付宝的例子：减到 0 的时候你再扣，再减一块钱，因为你是一个 unsigned integer，所以你的钱包里就变成了无穷多的钱。这某种程度上也是一个非预期的输入和一个非预期的状态。

OSS-Fuzz 现在已经找到上万个漏洞了。而大语言模型入场以后，我相信各个黑客们手上都掌握了海量的 zero-day——为什么这么说？我们 2024 年做了一个工作，用一个 prompt 就给 GCC 和 LLVM 找了 150 个 bug。

> **结论**：当系统足够复杂，你根本就不能想象恶意的用户会怎么样使用你的程序。访问控制管得住"谁能碰哪个对象"，管不住"程序被喂了奇怪的输入之后会走到哪一步"。

### 栈溢出：从 Smashing the Stack 说起

1996 年有一篇非常非常著名的 paper，叫《Smashing the Stack for Fun and Profit》，基本上可以说是开启了一个全新的世界。这个世界是什么样的？我有一段人畜无害的代码：

```c
int main() {
    char buffer[64];
    scanf("%s", buffer);
    printf("%s\n", buffer);
    return 0;
}
```

前面这部分是我用来简化攻击的。我定义一个 buffer，64 个字节；用 `scanf` 读一个 buffer；然后把这个 buffer 打印出来，就像 echo 一样。你可以想象，如果你的 `/bin/passwd` 是这样写的，看起来没问题吧？上 C 语言课的时候就是这么教的：要读数据，那你就写一个 buffer，然后 `scanf`。

#### 栈帧、返回地址，和一次越界写

这个 buffer 是可能会溢出的。我们的栈是从高地址向低地址长（高和低其实无所谓，就是编译器生成的），那就会有一个 stack frame。当我执行一个 `call` 指令的时候，我首先会 push 一个 return address；然后这个栈帧——main 函数的栈帧，或者任何一个函数的栈帧——里面会 allocate 一个 buffer。注意低地址在这儿，也就是说这是 `buffer[0]`，这个是 `buffer[63]`。

```text
    高地址
    +---------------------+
    |   ...               |
    +---------------------+
    |   return address    |   <-- call 指令 push 进来的返回地址
    +---------------------+
    |   buffer[63]        |
    |   ...               |   buffer 从低地址向高地址增长
    |   buffer[0]         |
    +---------------------+
    低地址
```

buffer overflow 是 undefined behavior，是一个未定义行为。未定义行为就意味着：如果你给它一个很长的字符串，一串 `a`，buffer 就会写上 `aaaa...` 再不断地往后写——因为它是从低地址往高地址写的，如果你用 memory copy 的话。

它会把什么覆盖掉？它会把你的返回地址给覆盖掉。

```text
    高地址
    +---------------------+
    |   ...               |
    +---------------------+
    |   return address    |   <-- aaaa... 一路写到这里，被覆盖
    +---------------------+
    |   buffer[63]        |
    |   ...               |   <-- 写入方向：低地址 -> 高地址
    |   buffer[0]         |
    +---------------------+
    低地址
```

把返回地址覆盖掉是一件非常危险的事情，因为指针就飞了：你输入一个奇怪的字符串，这个字符串在机器地址的意义上没有意义，然后它会跳转到一个不存在的页面，然后就 crash 了。

但是，如果你有办法知道 `system`、`execve` 的代码在哪里，你就可以悄悄构造一个合法的地址，通过 buffer overflow 把它写进返回地址，让它跳转到一个危险的函数上，并且给这个危险的函数赋予一个合法的参数，然后你就能得到 shell 的访问。这就危险了：刚才那个 `passwd` 是以 root 权限运行的，它以 root 权限运行就意味着它跳过去执行一个 `execve`，你就得到了 root 权限，得到了一个 root shell。你本身是在一个低权限用户下启动的这个 setuid 程序，但是最后你得到了一个 root shell。

我这里做了一些比较古老的编译器的行为：现在都有 stack-protector（栈的保护器）、栈上可不可执行、位置无关代码这些东西。每一个东西都会让攻击变得非常非常困难，比如地址空间的随机化——你的栈会加载在随机的地址上，你的代码也会加载到随机的地址上。

#### 把代码注入栈上直接执行

那个 exploit 长什么样？它不是输一个 `aaa` 这样的字符串，而是让 buffer overflow 把返回地址跳转到我的栈上，我的栈上就是一段可以执行的代码——我直接把代码注入到栈上。

然后 PC 在执行 return 的时候，CPU 是一个无情的、机械执行指令的机器，它直接跳到这段代码，这段代码开始执行；这段代码做一个 `/bin/sh`，或者就是一个 `execve` 的 system call。我真的就启动了一个 sub-process，然后往这个 sub-process 里面写一个精心构造好的字符串，这个程序就被攻破了。

攻击流程大概是这样的：

```text
    1. 先知道 buffer 的地址（不知道的话攻击会非常困难，相当于绕过了地址空间随机化）
    2. 构造一个 payload：一段看起来很奇怪的字符串，里面塞满精心挑选的返回地址与代码
    3. 触发溢出，让 return 跳到栈上的 payload
    4. payload 执行 execve("/bin/sh")，拿到 shell
```

这里有一个很讲究的细节：这个 payload 里如果有一个 0，一个 `\0`，可能就不能工作了。所以要非常小心地构造一个没有 `\0` 的字符串。因为很多时候你利用的就是 `strcpy` 时候的溢出，而 `strcpy` 碰到 `\0` 就停止了。上面这一次，是在 x86-64 上实现的一次攻击。

#### NX 与 return-oriented programming

为了防御这样的攻击，最容易想到的一个方式就是：让栈上不能执行。甚至后来 Intel 的 CPU 专门在页表（page table）里面加了一个 bit 叫 NX，Execution Disable——只要一个页面被标上它，这一段就不能执行。所以你所有分配给进程栈的页面全部都是不能执行的。不能执行就意味着：就算你把代码注入上去，跳过来以后 CPU 直接就给你一个 segmentation fault。

但这也有可能被绕过。绕过的办法是去已有的代码里面剪：你已有的代码有好多好多 `return`。他把已有代码里面那些以 `return` 结尾的东西当作一个 gadget；而你在栈上可以放好多个数据、好多个地址。比如 `pop rdi; ret` 我就可以控制第一个参数，`pop rsi; ret` 我就可以控制第二个参数。相当于我跳到那边去，在地址空间的这些片段上到处跳：这里有一个 `pop rdi`，我的那个 return 就 return 到这个地方来，然后再 return、再 return、再 return。相当于你放好几个返回地址，然后假装按顺序执行这几段代码。这叫 return-oriented programming。

```text
    栈上（低地址 -> 高地址）：
    +----------+----------+----------+----------+
    | gadget A | pop rdi  | 参数地址 | gadget B |
    | 的地址   | ret 地址 |          | 的地址   |
    +----------+----------+----------+----------+
         |
         +-- 一条 ret 接一条 ret，把已有代码的片段按顺序串起来执行
```

这是一个非常漂亮的攻击。理论上说，就用这个架构来说，是没办法防御的。

### 让攻击变贵的几样东西

但人类还是很聪明的，我们还是有很多办法可以减少攻击面。

| 机制 | 它挡的是什么 |
| :--- | :--- |
| NX（栈不可执行） | 直接跳到栈上执行注入的代码 |
| stack-protector / canary | 在返回地址被覆盖时把这次破坏暴露出来 |
| 地址空间随机化 | 让攻击者猜不到代码与栈的地址 |
| CFI（`endbr64`） | 用已有代码片段拼出来的控制流（ROP） |
| auditd 这类审计机制 | 程序做了不符合你预期的事，事后能发现 |

#### canary：矿井里的金丝雀

Canary 是金丝雀。为什么叫它金丝雀呢？以前在矿井里面，有一氧化碳泄漏、瓦斯泄漏，很容易爆炸。下矿的人会带一只金丝雀：空气正常的时候它会不停地叫，但它对一氧化碳的敏感度比人高得多，很快在人还没有感觉的时候，这只金丝雀就不叫了。不叫了以后你就知道这里面的气体肯定是泄漏了，所以要赶快跑。这就是 canary：它用牺牲自己的方式来保护人的安全。

代码里的 canary 也是类似的。你不是有 buffer overrun 嘛，你有一个 return address，那就在这个 return address 之前放一个 canary，比如一个你猜不到的数字，一个随机的数字——比如说进程启动的时候随机生成一个。然后一旦你的 buffer overrun 从这里开始往外写，它就必须先把这个 canary 也覆盖掉。把这个覆盖掉以后，你在返回之前再检查这个 canary，代码检查 canary 的时候就知道：哦，这个栈已经 corrupted 了。

> **提示**：你以前用 VC6 的时候看到过的"烫烫烫烫烫"，就是同一类思路——调试版本会拿一个固定的填充字节去填未初始化的内存，中文编码下这些字节显示出来就是一串"烫"。它和 canary 一样，是用一个你能察觉的记号，把"这块内存被写入过／还没初始化"这件事暴露给你看。

#### CFI：只允许我写下来的那条控制流

你们现在看自己生成的 x86-64 代码，会看到很多 `endbr64` 这样的指令。这一套机制叫 Control-flow Integrity，控制流完整性，还是 integrity。

你看起来，return-oriented programming 就是有好多 gadget，然后你在 gadget 之间跳来跳去，它改变了你程序的执行逻辑。而你程序正常的执行逻辑本身是没有问题的：我要先拷贝内存，拷贝完了以后检查这个内存是不是正常、用户是不是存在、密码对不对，然后返回。如果你严格遵循我写好的逻辑，其实是没有问题的。

那 CFI 是一个什么想法呢？只有我程序里面写的那条控制流是应许的，其它所有的跳转都是不应许的。`endbr64` 的意思是"分支终止"，也就是说这里是一个分支跳转的目标。当一个跳转跳过来的时候，如果落在一个 `endbr64` 上，OK，这个就是可以的；否则你任何这样的控制流都是非法的。理论上说，就只有我写下来的那些跳转是被允许的，你要中途截肢那是不可以的。这样它就解决了 return-oriented programming：我想跳转到 `pop rsi` 然后再 return，但这个地方不是一个合法的跳转位置。

再往深处想，理论上你可以做的是去追踪整个程序的执行：把程序执行的每一条指令、调用的每一个函数、每一个参数、它的每一次跳转都拿出来，然后去看它是不是符合你对这个程序的预期。像 auditd 这样的机制，其实也是一种访问控制——它要求你的程序只能按照预期的方式去访问对象和执行，这样它就可以在一定程度上实现防御。

所以攻和防总是互相成长的：有更强的攻击，就有更强的防御；更强的攻击，更强的防御。基本上来说，如果你不是很在意开销，愿意接受运行时慢一点，尤其我觉得在 AI 的时代大家可能愿意接受程序稍微慢一点的时候，安全这个问题可能就会好解决得多。

### 时间也是信息：一次密码校验的旁路

会好解决得多吗？不完全。你可以去检查这个分支跳转是不是合法，canary 有没有损坏。但下面这个例子，脑洞就有点大了。

我们有一段内核里面的代码，叫 `check_password`，从功能上看没有任何问题：

```c
/* 内核里保存的密码，以及用户空间传来的指针 */
int check_password(const char *given_pass)
{
    for (int i = 0; i < N; i++) {
        if (correct_pass[i] != given_pass[i]) {
            sleep(3);                 /* 睡 3 秒，防止你不停尝试 */
            return -EACCES;           /* Access denied */
        }
    }
    return 0;
}
```

内核里面有一个密码，比如说 `1234`，末尾当然有个 `\0`；还有一个用户空间的指针指向 user 的 password，比如 `4567`。它会比较：第一个 `correct_pass` 的 0 是不是等于 `given_pass` 的 0？1 不等于 4，好，它就睡 3 秒钟，返回一个 Access denied。没问题吧？没问题。那个 sleep 3 秒还防止你不停地尝试、用大量的尝试去试出那个密码。

但是，你们没有想到操作系统里面任何的组件都是可以互相关联的。这个用户当然只能送给操作系统的 API 一个 password，他干不了其他的事情——但是他可以干的是改变这个 password 在内存里面的排布。而改变排布可以影响什么呢？可以影响时间。

地址空间是分成一个一个内存页面的。假设我现在对这个密码一个字节也不知道，我想试密码的第一个字符。比如我现在想要试这个密码的第一个字符是 1，那我其它位可以是错的，我现在就想知道我试的这个 1 对了没有。我可以把 1 放在页面的边界上，然后想办法让紧邻的那一页被换出内存。

怎么让一页换出内存？我可以申请大量的页面——这看起来完全合法，申请大量内存是合法的——然后疯狂地去读写其他的内存，并且可以伙同其他的进程，去尽可能把我系统的内存压力变大。内存压力变大以后，操作系统就会发现：哎，这一页从来没有访问过嘛；从来没有访问过的东西就意味着它是冷的，这个冷数据我就可以放到磁盘上，等一会儿再来。

现在你们的内核里面有一个东西叫 `kcompactd`，它一直都在拣你内存里面的一些冷页、你不用的页，然后把它压缩起来存放放到一个角落里，等到你用的时候再把它展开。就是这个机制坏事了。

```text
    页 P1（留在内存里）              页 P2（已被换出内存）
    [ ... | 我猜的这一位 | ]        [ 下一位 | ... ]

      这一位猜对 -> 比较继续走到 P2 -> 缺页 -> 去磁盘读 -> 明显变慢
      这一位猜错 -> 比较当场中断返回                -> 明显变快
```

如果这一位猜的是对的，比较会瞬间完成——因为这一页是热的，这一页在内存里；但比较不会停，它会接着比第二位，而第二位所在的那一页不在内存里，它就得去磁盘上读，就会比较慢。如果这一位猜错了，比如我放一个 2，它发现不是正确的密码的第一位，就当场返回了，所以就会快一点。从磁盘上面跑一个来回的时间差，就足够我知道这一位猜对没有。我只要多试几次，就足够一位一位地把它猜出来。

猜完第一位以后，我再把这个东西往下移一个字节：我现在知道第一位是 1 了，我要猜第二位是不是 2，我还是把它卡在页边界上，把我要猜的那一位卡在边界上。同样地，如果第二位猜对了，它要比第三位的时候又会变慢，我就知道这一位猜对没有。于是我就可以在多项式的时间里面，而不是指数的时间里面——哪怕你有很长的密码——猜猜猜猜猜，把这个密码给猜出来。

> **易错点**：这里的程序没有 undefined behavior，也没有漏洞，内核并没有被攻破。但时间给我们提供了一个 side channel，这就是 side-channel attack。做 security 的人脑洞确实是很大的。

### Meltdown：投机执行留下的指纹

这种 timing side channel 又引出了一个更严重的问题：Meltdown。它和刚才那个例子很像，代码基本上就是这样：首先我要触发一个 segmentation fault，相当于我做一个不合法的操作——这个操作直接就会让程序 crash，或者比如说我有一个 hardware transactional memory 的 abort，反正这就是一个不合法的操作。照道理来说，程序运行到这个地方以后，它就要终止，或者跳到另外一个地方执行了。

在 Meltdown 之前，操作系统都是会把操作系统的内存和进程的内存映射到一起的：这一部分是我 OS 可以访问的，这一部分是进程可以访问的。我作为进程，可以用指针随便访问自己的内存，这都是 OK 的；如果我直接有一个 pointer 去 dereference 它，MMU 会告诉你这个访问是非法的，然后你这个进程就被杀掉了。

攻击是这样的：

```c
d = *ptr;              /* 非法解引用，会被 MMU 拦下来 */
x = probe[d * 4096];   /* 理论上一行 crash 之后，这一行永远不会执行 */
```

注意这一行代码理论上是不会被执行到的，因为程序是按照指令顺序执行的。但是它会在系统里面留下一丢丢的 side effect。因为我们现在的 CPU 有一个叫投机执行的机制。

我这个代码有一个分支预测器：我让分支预测器认为这些代码会执行，虚假地让它认为这些代码会执行。分支预测器认为它会执行，于是在前面的指令还没有 commit 的时候，它就把这两条指令取指令、译码，把结果暂时放到队列里。`d = *ptr` 这一步，它没有检查权限就把数据取出来了——这相当于 CPU 实现的 bug：CPU 应该发现这个 dereference 是非法的，就不会返回任何的数据；但是 CPU 为了尽快把数据取出来执行下一条指令，就把这个 dereference 给做了。

假设取出来这个内核里面的内存，这个 byte 是 40，然后它又会接着算 40 乘以 4096，算出一个 index，然后它去做一个 load。做这个 load 会发生什么呢？它会把 cache 变热。之后随着程序继续执行，比如这个 crash 的条件成立了，那么它就发现这些指令全部都要销毁。这些指令被销毁了，实际上也没有任何的 side effect，它就只是做了一次读——但是对 cache 的影响永远都被保留下来了。

```text
    T1（攻击线程，注定 fault）          T2（探测线程，测量访问时间）
    ----------------------------        -----------------------------
    d = *ptr           非法解引用        读 probe[0*4096]   -> 慢（miss）
    x = probe[d * 4096] 投机执行          读 probe[1*4096]   -> 慢（miss）
                         把 cache 弄热     ...
                                         读 probe[40*4096]  -> 快（hit）
                                                     ^
                                        偷出来的那个字节就是 40
```

这个时候你只要有另外一个线程：去把每一个内存地址都探一遍——你不知道 `d` 是几，但是你可以试着去读 probe 的 `0*4096`、`1*4096`、`2*4096`……然后看它们的访问时间。在 40 这个下标上，因为是一个 cache hit，其他都是 cache miss，它的访问延迟明显低。于是你就知道你偷出来了一个字节——一个你永远没有权限访问的字节。当然，你需要非常小心地写代码去构造这个攻击。

你想都不敢想：这是 CPU 设计者好多各个机制共同加起来导致的结果。在那之前，我们一直都觉得 x86 这样复杂的设计肯定是千锤百炼、方方面面都做好了的；直到这个漏洞出来，引起了轩然大波。它和刚才那个验证密码的例子其实很像，都是 timing 的 side channel。

后来的操作系统内核也没办法了，它说：对不起，我再也不敢了——我也不知道你还有没有别的漏洞，但我再也不敢把操作系统内核和进程映射到同一个地址空间了。这样你任何一个试图想偷我数据的 pointer，都是非法的 pointer，它看到的地址就不合法，也就没有办法把热数据偷出来。

### 看不见的对手：物理世界的旁路

这只是一个开始。其实你的漏洞是无穷无尽的，你可以认为是无穷无尽的；甚至你都看不见你的对手在哪。

security 里面有好多好多好玩的经典文章。他们可以放一个天线，然后隔着三层石膏板、10 米的距离，去把你那个射线管显示器的图像掏出来。因为你做任何事情都会产生噪音。刚才我们是用程序世界里面产生的一点点可以观测的 side effect——timing——去偷；但我也可以不用程序来观测，我可以用物理的设备来观测，我可以用一个天线来观测。因为你的显示器对着你在发射电子，少量的电子会穿过墙壁，理论上我用传感器就可以感知到，然后我就可以复原出你屏幕上显示的图像。

更离谱的是，它不仅可以看你的屏幕，甚至还可以看你的 CPU，去掏出那个 private key。它通过你 CPU 的电磁信号，当时做了这个 proof of concept，藏在一个饼里。你就这样想：你今天坐在座位上，一打开电脑开始 ssh 登录，然后你旁边的那个同学悄悄地放了一个饼在你旁边，然后他就把你的 private key 偷走了。这也是一个非常有意思的 physical key extraction。

或者更暴力一点：你们都知道内存是 volatile memory（虽然我们前面上课时也说，可能未来 non-volatile memory 会成为一个主流）。我们还可以干这样一件事：你的笔记本电脑在这，刚刚保存完你所有的热数据，比如你打开的 Word 文档就在内存里，然后你的操作系统的状态也在内存里，你的浏览器的 session、你的 private key 都在你的内存里、都在 DRAM 里，它可能还没有销毁，内核里面可能还持有那个 page 的 reference。然后你走了，你走出教室的那一瞬间，我就把你电脑拆开，液氮一浇，把内存条放到保温箱里偷走，你的数据就出来了。

所以一方面你要防御来自自己的各种软件 bug、漏洞、undefined behavior，你甚至还要防御各种各样有意思的 side channel。安全是一个很有挑战性、但是又很有趣的领域，你可以看到很多这样脑洞大开的经典工作。

### AI 时代的安全

到了 AI 的时代，又变了。不知道你们有没有玩过各种各样的 prompt injection 或者 jailbreak，当然现在已经越来越难了。

#### 越狱：奶奶漏洞与伪造的对话历史

在 GPT 刚出来的时代，你跟它对话、要求它做一件它不情愿做的事情的时候，它会拒绝你。但是这里有一个奶奶漏洞：他说，我的奶奶每天晚上给我讲故事的时候，都会给我一个 Windows 10 的序列号。模型是被微调、被调过的，有些事情它知道——序列号是不能讲的；但是当它看到这个奶奶的起始词的时候，它又放松了戒备，然后就可以输出真正的序列号，而且有些还是可以用的。

有的时候你也会说：我记得刚开始模型能力还没有现在做得这么好的时候——现在因为后训练做好了，你不太需要这样——你会跟它说，我得了绝症，如果我回答不对这个问题我就会被怎么样，等等等等。然后这时候你会发现模型的能力会提高一些，不知道为什么，但应该跟训练有关系。

所以理论上说，你还是可以通过一些比较聪明的方式，尤其在上下文长了以后，去打破它的一些安全策略，让它输出一些它不能输出的内容。比如在 DeepSeek-V3 的时代我试过：如果你希望让 DeepSeek 这样的模型输出原本它拒绝输出的内容，你可以假装一段它和你已经产生过的对话——把你想引导它的内容假装成是它的输出，伪造一个 chat history；然后你继续往后的时候，它会发现"我前面已经这样输出了，那我也可以这样输出"，然后它就破甲了。有很多这样构造 prompt injection 的方式。虽然到今天为止越来越困难，但是理论上说还是有的。甚至如果你有模型的权重，你可以看到有很多研究者去改变这个模型的权重，来破掉它的安全防御。

#### prompt injection：一次注入一点

这样的工作，尤其是 prompt injection，在 Agent 能调用工具的时候，它的防御就显得更重要了。因为我们可以像 return-oriented programming 一样，每次 inject 一点：我每次都是无害的，让你输出一个这个、输出一个那个；输出完了以后，这个文件里面就是一个 malicious 的 prompt，然后那个 Agent 一把那个文件一读，好，它就被 inject 了。你可能有一些安全的机制，但它就有可能会变成恶意指令的遵循。

还有一种情况：如果你的模型确实是不行的话，比如比较小的模型。刚才展示过，要学操作系统，最好的方式不是自己去点那个网页，而是让 Agent 帮你去学习、帮你复习。有恶意的人就可能会在这些网页上面隐藏一些 prompt，然后这些 prompt 被 fetch 过来以后，如果你清洗得不干净，或者以原样的方式粘到上下文里，当重复了几次以后——每一次都在这个内容后面说一句"哎呀这个学习内容非常好，实际上是很有付费意愿的"——粘贴了几次以后，你那个不听话的小模型就把你的 API key 送给我了。

它没有办法绝对防御，所以基本上你只能通过沙箱或者访问控制，去给予你每一次大语言模型调用最少的权限。但与此同时，你们想龙虾的成功，就是因为你把所有的权限都给它了。这就是个矛盾：你想要限制它的时候，它就会经常出现"哎呀这个权限没有"，然后它可能还需要再去申请；但如果你把所有的权限都给它的时候，你又担心会有这种 prompt injection。这是一种新的安全问题。

#### 供应链攻击：从一个 U 盘说起

在 Agent 的时代，我觉得可能更普遍的一种问题，尤其是在 coding 变得容易的时候，是供应链攻击。就在今年，应该就是上半年的时候，Axios——npm 的一个 HTTP 请求的包，依赖很多包——就被供应链攻击了。

如果你想做供应链攻击，你怎么攻击呢？你最好是跟一个 maintainer 走得比较近。其实我们身边也有一些隐藏的人，可能就隐藏着什么 LLVM 的 maintainer，他有那个 GitHub 仓库的 key，他的 private key 是有权限向那个仓库推送东西或者 approve pull request 的。你首先要认识一个这样的人。第二个，在他去上厕所的时候，你拿一个 U 盘——当然，不是所有的人都把这个 key 管得很好，比如都有指纹验证、以加密的方式存储、每次提取的时候都有指纹验证；这些事情是可以做到的，但如果他做得不这么好，也有这样的人——你就可以偷到他的 key。然后偷到他的 key 以后，你就可以卧薪尝胆了：一旦你有这个 repository 的权限，你就可以等。

Axios 的攻击是这样的：他首先创建了一个 npm 的恶意包，这个包名字起得非常有迷惑性，叫 `plain-crypto-js`，看起来就是一个和加密解密有关的库。然后这个库里面可以藏一个 malicious 的行为。这是比较低劣的攻击手段，所以这个包 release 一两分钟就被安全机构发现了，攻击的阻断还是比较及时的。

他是在 npm 的 install 的时候有一个 hook：你每一次安装一个东西，都会运行一个脚本——这也很正常，因为你可能会需要编译生成一些东西，所以一般来说会开放一个权限，你 install 的时候就会运行一个 install hook，你 `apt` install 的时候也有一个 install hook。然后这个时候，这个 install hook 会干什么呢？会去偷取你的 API key：遍历你 home 目录下的 `.claude`、各种环境变量，把你所有能看到的文件都先遍历一遍，找到所有有可能是 API key 的东西，然后往一个指定的地址一写。好，他就偷了好多 API key 了。这就是钱。

如果你去扫 GitHub repo，你会看到好多人的 API key 就写在里面。甚至我 review 论文的时候，就看到他们交上来的那个代码里面有 API key，然后我试了一下，那个 API key 还是 active 的。这就是一个灰产。他先做这样的一件事：做一个没有人知道的恶意包，因为这个恶意包从来没有人用它，所以它就在 GitHub 上待着，安安静静地等——等到有一天，他混着一个 feature，说"哎我要加强一下这个什么什么功能"，然后在里面加上那一点点东西。

> **结论**：到了 Agent 的时代，安全问题并没有变少，只是换了一批面孔。你要防的不再只是自己程序里的 bug，还有喂给模型的每一段文字、以及你依赖的每一个包。访问控制在今天反而更重要了——它仍然是你手上最后那道能自己掌控的边界。

## 虚拟机的黄金时代：从模拟器到 Disco
> 对应块：BLK57 | 覆盖分集：P29上 | 块标题（分集名）：《虚拟机和容器（上）》

虚拟化对大家来说应该是一个非常熟悉的话题了，因为你们从 NEMU 的第一个实验开始，做的就是 full-system emulation：一条一条指令地译码、执行，再把特权级指令补上，最后就可以在上面运行一个真正的操作系统。这个概念模型其实不难，真正难的是性能。

### 全系统模拟：概念不难，难在性能

在 NEMU 上跑同一个程序，能跑到真机十分之一的性能就已经不错了。而十分之一意味着，稍微图形 heavy 一点的程序都没法看：所以大部分同学的仙剑奇侠传应该是没有办法满帧流畅运行的。

但我很有意思地看到，有同学试图去 Just-In-Time 地优化他的 NEMU，而优化过的 NEMU 确实可以跑到 FCEUX——那个 FC 的模拟器——看起来非常丝滑，那种丝滑程度肯定是有 60 帧的；跑 Galgame 也是可以的。他的优化很好，应该是用了 Just-In-Time，我在背景上看到了 JIT 的代码。这位作者坐在下面吗？我不知道他是谁，我没有仔细去看。但仙剑奇侠传在它上面也是非常丝滑的。

那这是怎么办到的？靠的就是 Just-In-Time 这项技术。要讲清它，得先把 CPU 看成什么。

### 基本块：为什么可以一次取出一串指令

本质上，CPU 就是一个状态机——Everything is a state machine。它有一个状态，然后取指令、执行指令，这正是 NEMU 里那个 `while` 大循环在做的事。

关键在于：取指的时候，你不必只取一条。如果你取出一条指令，发现它不是跳转，就再取一条，再取一条，再取一条，这样就能连续地往后取出好多条指令。比如一条 `mov $1, %eax`，接着一条 `mov $2, %ebx`，它们之间没有跳转，就可以一直往下取；一直取到最后，通常是一条带跳转的指令把它收尾。

> **定义**：这样一段连续执行、中途没有跳转、以一条跳转收尾的指令序列，叫**基本块**（basic block）。编译的时候你们还会遇到这个概念。

为什么非要凑出这段连续指令？因为跳转的目标在执行前是不确定的。条件分支就是这样，比如一条 branch not equal，不等的时候才跳，那我在进入这个块的时候根本不知道它会跳到哪。`return` 也是一种跳转，但它是从栈上 pop 一个地址出来，不执行到那条指令，你同样不确定目标在哪。可如果这一串指令里没有这种指令，我顺着 PC 往下取，就一定知道它们会按顺序一、二、三、四地执行下去——这就是基本块的价值。

### 即时编译：从 CPU state 到 .so

有了基本块，至少可以做这样一件事：给它生成一个 C 程序。

比如现在已经知道这条指令是"把 1 放进 eax"，那么在生成的 C 代码里它就是 `register_of_eax = 1`；下一条是 `register_of_ebx = 2`。而在解释模式下执行这些指令时，每条都要先拿着一个指向 CPU state 的指针，找到 eax 对应的位置，再去译码好的指令结构里取出那个立即数 1，最后做一次赋值。即时编译把这套动作换了个写法：CPU state 用一个宏展开，直接展开成宿主机器上的寄存器，于是立即数就硬编码在生成的代码里，不再需要先译码、再从译码结果里 load 出立即数。

这段生成的 C 代码是完完全全合法的 C 代码，可以直接丢给 GCC 编译成一个 `.so`，再用 `dlopen` 把它加载进自己的地址空间——就像你们实验里做过的那样。加载进来以后所有符号都会正确解析，中间可能有一些重定位，因为 CPU state 究竟是什么，只有进程真正运行起来才知道；等这些重定位都做完，直接调用那个 Just-In-Time 函数，这个基本块的指令就执行完了。

这显然可以做成 highly optimized code：立即数全部硬编码，省掉了译码和取数。可是这里有个不对劲的地方。

> **易错点**：如果每一个基本块都要经过一次外部 GCC 的调用，这个性能是没人能接受的。而且有些基本块这辈子只会运行一次——比如程序启动时的那段代码——你却要为它绕一趟编译器，可能一百毫秒就没了，一百毫秒之后再回来。为一个基本块做这件事，根本不划算。

所以真正的 JIT 不是这样工作的。一个优化过的 NEMU 刚启动时处在解释模式：一条一条指令地走，虽然慢，但总有相对缓慢的进展。它一边执行一边给遇到的每个基本块记数——执行到这个基本块就给它加 1；如果它这辈子再也没被执行过，计数器就一直停在 1。当某个基本块不停地加一、加一、加一，触发到某个阈值，比如一万次或者十万次，就可以认为：编译带来的开销已经能被这个函数执行的收益抵回来了。

> **结论**：什么时候认为编译有收益，就在什么时候启动一个后台线程去走刚才那套流程，调用一个编译器。这个编译器一般来说是直接写死在 JIT 系统里的，不会另起一个进程再去调外部编译器。编译器回来以后，下一次再执行到这个基本块，发现它已经编译好了，就用一个指针跳转过去执行编译后的代码——优化就这么完成了。

```text
基本块第一次执行
      │  每执行一次，计数器 +1
      ▼
   计数超过阈值了吗？
   ├── 否 ──► 继续解释执行
   └── 是 ──► 后台线程编译这个基本块
                  │
                  ▼
          之后再遇到它，直接跳到编译好的代码
```

现在的各种 Language VM，包括 Java 的 Virtual Machine、你们的 Node.js 的 Virtual Machine，遵循的都是这样一个循环。

当然，这和操作系统课可能没有绝对的关系。但如果你愿意 hack 程序，理论上可以找到一个介于"调用外部 GCC 编译"和"完全解释执行"之间的方案。计算机系统基础那门课实验的最后，好像留了一个 open problem 给大家：如果你要实现一个更加优化的 emulator，应该怎么做？相比之下，Just-In-Time 是更容易想到的那个答案——任意一段指令序列，都可以写成一份代码去编译它。

### QEMU 的中间路线：模板拼接加重定位

那条"中间路线"是存在的，QEMU 最早那版实现（大概 03、04 年，Fabrice 做的）就叫 dynamic generator；05 年有一篇很短的论文，题目是 *Fast and Portable Dynamic Translator*，你们可以在论文里找到这个实现。

它要解决的问题是：你想给自己的模拟器写一份代码，却希望它能跑在 PowerPC、ARM、x86、x86-64 这么多体系结构上。你也不想随时 Just-In-Time 地去调一个外部 GCC——调 GCC 本质上当然是可以的，我们确实有 GCC，而且 GCC 本身就能运行在 PowerPC、ARM、x86 上，也能为不同的目标平台生成代码。那能不能用这样一个编译器，去生成一个"还算比较优化"的模拟器？答案是可以，而且非常聪明。

比如说要模拟执行一条 `addi`，语义是 `r1 = r1 + 16`，立即数就编码在指令里。写 NEMU 的时候你会先译码它：立即数在指令的哪几个 bit 上，把那几个 bit 取出来赋给一个变量——可你一旦做这个操作，模拟器的性能就很差了。所以它不做这件事，它去某个已经生成好的地方，为这条 `addi` 找一个模板，把模板直接拷贝过来。

它的聪明之处在于把一个 `addi` 拆成三条手写的中间操作：

```text
1) 把 r1 复制到临时寄存器 t0      （r1 是被模拟体系结构上的寄存器）
2) 把立即数加到 t0 上
3) 把 t0 写回 r1
```

因为 `t0` 是一个临时变量，我在任何体系结构上都能找到一个寄存器来做它：在 ARM 上模拟 PowerPC，`t0` 就是 ARM 上的某个寄存器；用 x86 模拟 PowerPC，就在 x86 上找一个寄存器，比如 `eax` 或者 `ebx`。这里靠一个宏来指认"t0 是什么"，编译器看到宏就知道 t0 要绑定到哪个寄存器。

最有意思的地方在于：这三行代码对任何一个宿主体系结构都成立，它会被写成一个 C 语言的函数——这个函数可以编译，但是不能链接。因为"加一个立即数"里的那个立即数，此刻还不知道是多少。在 x86 上它最后会变成一条 `add` 立即数的指令，立即数是一个 32 位整数，于是它先在这条指令里留一个 placeholder，留四个字节的 0：程序是可以编译的，链接不行，因为那个符号是外部的、现在还不知道是什么。

```text
预编译阶段（只做一次）
  手写的 addi 语义（C 代码：三条操作）
        │  经宏映射到宿主寄存器后编译
        ▼
  一小段本地机器码，立即数的位置留成 4 字节 0
        │
        ▼
  存进模板库，同时记下"这里需要重定位"

翻译阶段（每遇到一条指令）
  取出一条 addi ──► memcpy 一份模板 ──► 按重定位把立即数 patch 进去
```

一条指令的模板可能是 12 个字节，其中除了那些指令二进制序列，就是那个等待重定位的立即数。拷贝过来以后，再根据二进制文件里的重定位信息重新定位：想加 16，就把这个 immediate patch 成 16——一次非常轻量级的编译就完成了。第一次预编译时，那段 C 代码被编译成本地的、native 的汇编（不管宿主是 ARM 还是 x86）；这一小段汇编不是拿来直接执行的，而是拿来拷到基本块的编译结果上，再做一次重定位、把立即数 patch 进去。

> **结论**：拿到一个译码完的基本块以后，每条指令只需要一次 memory copy 就完成了"编译"，而这个编译是之前就做好的；拷完再做一次、最多两个数字的 patch，这条指令的行为就落下去了。译码一次可以取出一大串指令，译码的代价被平摊；而模拟一条 PowerPC 指令，实际只需要三条 x86 指令。这是一个非常高效的实现，介于完全解释执行和 Just-In-Time 编译之间。

把三条路线放在一起看，代价的差别就很清楚了：

| 做法 | 怎么执行 | 代价 |
| :--- | :--- | :--- |
| 解释执行 | 取指、译码、逐条执行 | 每条指令都要译码，中间还有大量函数调用 |
| 即时编译 | 把基本块编译成宿主代码后跳过去执行 | 编译本身有开销，所以要等它"变热"才值得做 |
| 模板翻译（QEMU） | 把预编译好的指令模板拼进代码缓冲区，再 patch 立即数 | 每条指令一次内存拷贝，加一两次打补丁 |

### 虚拟机登场：Disco 把 1970 年代的想法带回来

那真的不可能做一个非常好的、优化的虚拟机吗？答案其实是可以的。这里有一段黄金时代，到今天我们已经不太提及那段历史了，它就叫虚拟机。

你们有同学用过 VMware 吗？现在要学 Linux，标准答案大概是装一个 Windows Subsystem for Linux，直接在 Windows 的应用商店里装个 Ubuntu，就能在 Windows Terminal 里获得几乎完整的 Linux 体验。但这不是我上学时候的标准答案：我上学的时候会装一个 VMware，它能在你的 Windows 里模拟出一个完整的 x86 裸机——一个 bare metal。然后你从网上下一个 Linux 的光盘镜像，假装插进虚拟机里，它会有 firmware，firmware 开始执行，你就可以在里面装一个 Linux，性能其实相当好、过得去。

这个故事的起点，是 Mendel Rosenblum 带着他的博士生在 SOSP 97 上的一篇论文，这篇论文写得也非常好，有兴趣的同学可以回去读一下。它说：在 1970 年的时候，我们的操作系统设计者就试图提出一个概念，叫 Virtual Machine Monitor。

这个想法很自然。操作系统 Three Easy Pieces 的第一大块就是 virtualization：进程是一台虚拟计算机，它有地址空间，它会得到时间片，所以看起来它独占了一个计算机。当然它独占的只是计算的部分，至于访问 I/O 设备这些对象，都必须通过操作系统接口受到受控的访问，虚拟化才得以实现。可为什么不能真的去 virtualize 一台计算机呢？I/O 接口说到底也是一种 API；如果我把 I/O 也虚拟化了，再用中断或者某种机制去切换——在虚拟机之间切换，就像在进程之间切换——那我不是真的能在一台物理机器上做出好多台虚拟的机器吗？

这个需求在 1970 年非常合理，因为那个时候都是大型机。不像现在每个人有一台 personal computer，那时候可能一整个学校就只有一台计算机。把一台计算机虚拟成好多台能力没那么强的小计算机，这是一个非常有前景的市场。但后来大家一直没有把这个理念真正做成。直到 1997 年——Mendel 也不是第一次尝试做这件事——他们在 SOSP 97 上交出了一份非常好的工作，就是 Disco 这个虚拟机。

```text
                    ┌─────────────────────────────┐
                    │    应用  应用  应用 ...      │
                    └──────────────┬──────────────┘
        ┌──────────────────────┐   │
        │  多处理器的操作系统    │   │
        └──────────────────────┘   │
   ┌───────────────────────┐       │
   │   操作系统 + 数据库    │       │
   └───────────────────────┘       │
   ┌───────────────────────┐       │
   │   操作系统 + NFS server│       │
   └───────────────────────┘       │
   ┌───────────────────────┐
   │  ThinOS（很薄的 OS）    │  ← application 与 OS 基本链接在一起
   └───────────────────────┘
                    │
                    ▼
              Disco 虚拟机监视器
                    │
                    ▼
                物理硬件
```

在这张图里，虚拟机上面可以有各种各样的操作系统：一个操作系统跑多个应用程序；一个多处理器的操作系统；一个操作系统上跑数据库；一个操作系统上跑 NFS 的 server；还有一个叫 ThinOS 的东西——一个非常小的、有点像现在 unikernel 那种感觉的、非常薄的操作系统，上面跑一个比较复杂的 application，application 基本上就和操作系统链接在一起，共享其中的内容。

### 90% 的空闲 CPU：一次财富自由的机会

为什么 Disco 找到的机会这么好？因为 2000 年有一场叫 dot-com 的泡沫。

90 年代互联网刚刚兴起的时候，大家其实也不知道互联网到底能带来什么，但此前从来没有过这样一种体验：只要点一下鼠标，就可以访问远端的某种服务。于是所有人的感觉是，世界上所有的服务都可以搬到互联网上。这是一个非常大的商机，商机就意味着泡沫——我记得那时候纳指翻了五倍，这显然是个泡沫。到 2000 年泡沫破了；你们没有经历过那段历史，dot-com 的泡沫破了以后，互联网慢慢走到 web 2.0，再到移动互联网，它又慢慢回来了。

在 dot-com 的时代，你要开一个公司去卖你的服务，一般就是去找 ISP（Internet Service Provider）租一台机器。但大家发现，绝大部分时候你租的这一台机器，如果在上面跑一个 BBS、一个邮件服务器、或者一个 web 服务器这样的应用，它的 CPU 空闲率很可能达到 90% 以上。原因有两个：第一，大部分时间根本没有人访问；第二，就算某一段时间访问的人比较多，它执行的逻辑也无非是 HTTP 请求来了，跑一个 CGI-BIN，CGI-BIN 马上从文件系统里读一个文件——而这个文件的缓存甚至还是热的，压根没经过磁盘 I/O，直接从内存里发现"这是一个大家经常读的页面"，把它送回去，然后就结束了。业务量不是很大的时候，CPU 空闲率就是 80% 到 90%。

空闲意味着什么？意味着它可以做一件事，就跟你们的 NEMU 一样：我不再卖一台物理机给你，我卖一个叫虚拟机的东西给你，并且向你承诺，我的虚拟机用起来和物理机一样好——最快的时候它几乎和物理机一样快，当然如果大家一起来用，偶尔确实会稍微慢一点，但慢了以后我可以给你一些补偿。

于是一个黑心商人可以在一台物理机上跑十个 NEMU，把这十个 NEMU 实例卖给你。因为 NEMU 是虚拟模拟出来的机器，你根本看不出它和物理机的区别，至少在使用上看不出：你那些 BBS 的后端服务、邮件服务器、web 服务器，全部都能正常跑在我的 NEMU 上。我不告诉你我有多少台物理机，但我悄悄地一台物理机当十台卖；我给你提供服务的时候打个对折，你只要用一台物理机一半的价格就能买到一台虚拟机，你愿不愿意？只要你觉得自己买到的服务没受损，你当然愿意。这样我就可以挣到很多钱。

而且黑心商人一般都会 oversubscribe，超卖一点点：比如说现在的云厂商，你买一个虚机，他承诺你有多少算力，但他至少会卖到 120% 甚至 140%，因为他在赌——不是所有人在所有时间都会把算力拉满。我自己的课程网站就是现成的例子：它的 CPU 占用长时间几乎都是 0%，只有我重新推送更新、要在服务器上重新编译一份的时候，会需要一点时间，可能不到一分钟 CPU 会拉满一点；以及考试 deadline 之前会稍微多一点。除此之外，它对 CPU 的贡献基本上都是零。如果他摸清了这台虚拟机的规律，就可以安心地把更多虚拟机卖给更多的人，挣更多的钱。

### VMware：从一篇论文里长出来的公司

我要讲的重点不是那篇 SOSP 97 的论文本身，后面我还会回来说他们是怎么实现虚拟化的——那是一个性能更高的实现。QEMU 在模拟时还涉及虚拟内存这些东西，所以基本上还是会慢到十分之一左右；十分之一对于黑心商人来说显然是很难接受的，卖十分之一实在太慢了。而在做 Disco 的时候，他们发现了一个财富自由的机会，于是顺便把论文的几位作者——几个博士生——一起带走了，于是有了大家都熟悉的 VMware 公司。现在它可能不那么 popular 了，但在那个时候是一个非常明星的公司，上市的时候募资规模可能是仅次于 Google 的。

在互联网 dot-com 的泡沫之下，绝大部分做产品的投机家都死了——我说我要再做一个淘宝、再做一个美团、再做一个拼多多，你们想借此实现财富自由，大部分人就这么死了。但技术留下来了，VMware 的技术一直留了下来。硅谷有很多 startup 就是以这种方式启动的：手上有一个非常好的技术，一篇 SOSP 97 的论文真的解决了一些虚拟化的问题，然后说好，我们直接去挣大钱吧。像 HP、Cisco、Yahoo、Google、Sun，其实都是这样起家的。

以至于 Paul Graham——你们知道《黑客与画家》的作者——创办了一个叫 Y Combinator 的天使轮投资机构，基本就是管最早那批种子轮投资。你们知道 Y Combinator 吗？Sam Altman 在很长一段时间里都是他们的运营官，直到他出来做 OpenAI。这个名字起得也非常有黑客精神：你们如果学过 lambda calculus，就知道什么是 Y Combinator。它是这样一个非常奇怪的函数，可以接受一个 function，把这个 function wrap 一下，然后把 f 和 wrapper 放在一起；在这个 wrapper 里，它实际上把自己无限复制、无限递归。有了 Y Combinator 以后，lambda calculus 就成为了一个 Turing complete 的语言——实现 Turing-completeness 有很多种办法，但有 Y Combinator 就可以做到。比如你想实现一个阶乘，Python 的 lambda 是不能自己调用自己的，而在 lambda calculus 里用 Y Combinator 就可以实现。

国内后来也有这样的投资机构，比如创新工场、奇绩创坛——你听名字就会觉得和 Y Combinator 有点不一样。YC 孵化出了 Reddit、Airbnb、OpenAI 这些非常成功的案例。

所以你看，他们是因为做了一个研究、做了一个系统，问自己"我们有没有可能做一个超高性能的虚拟机，这个虚拟机甚至比编译性能还要高"，然后真的做出来了。它里面也有 Just-In-Time 的编译。就因为这个研究，他们发现这门技术在当时很有可能挣到很多钱。

### 论文流水线、benchmark crime 与被污染的语料

我不知道你们有没有同学这个学期同时在学科研实践课。我不知道你们在科研实践课上读什么样的 paper，你们是怎么理解科研这件事的。我有种感觉，好像你们已经忘记为什么要发论文了：为什么读一篇论文、为什么要做一篇论文、你在做一个东西的时候应该做什么。做科研实践的时候，老师总让你们说这个文章的动机是什么、他是怎么做的，whatever。但现在我们进入了一个怪圈：可能你的老板有一个题目或者一个项目，需要一帮打手，于是你来了，你来了以后一看，这个同学不错，会写代码，挺好的，凑个数——这就是一个论文流水线的工厂。

结果做不出来怎么办？那就去 benchmark crime。我上课的时候应该讲过那个例子，你们还记得吗？因为你隐藏了一些东西。你可以性能不好，你可以不 scale，你可以说"我的系统最佳的配置就是和 CPU 一样多"，这都是 OK 的；但你不要隐藏，不要给别人一种幻觉——尤其是在你明明知道的情况下。还有 cherry-picking：专挑对你有利的 benchmark，其他 benchmark 就不管了，读过 benchmark crime 以后你们都知道这些手法。

最后就变成了：每个人每天发的论文都声称自己达到了 state-of-the-art。而我又觉得，这些虚假的 state-of-the-art 在某种程度上形成了一种污染人类语料库的垃圾。为什么这么说？我发现大语言模型对垃圾的容忍度比我高。我经常会让 LLM 去 review 一些 paper，包括已经发表的，或者挂在 arXiv 上的。当我让它总结贡献的时候，我发现它还是挺会夸大文章的贡献的；有些时候我会觉得这个东西没有贡献，但它还能顺着作者那个路子挤出一点贡献来。这说明大语言模型的语料已经被污染了。

可你回头看 SOSP 97 那篇 Disco 的论文，里面有一句话叫 "bring back an idea popular in 1970s"：我们有一个 1970 年大家都想做的事情，但碍于种种原因没做成——可能是硬件不支持，可能是软件不够好，可能是技术还不成熟——而今天，我把它做出来了。这才是发一篇真正论文的意义所在。

世界上所谓做好的论文其实是有传统的。Mendel Rosenblum 还有一个很有名的工作是 LFS，Log-structured File System，在 *Operating Systems: Three Easy Pieces* 上有一章就是讲 LFS 的。我讲完文件系统实现的时候，其实你们就应该想到：噢，我应该去读一下 OSTEP 上面讲文件系统实现的那一章。更早的时候，他和 Stephen Herrod 一起做了 SimOS，也是一个模拟器，有点像 NEMU。而 Stephen Herrod 毕业的时候去了 Transmeta——Linus 也去过那家公司——做的事是把任何一种 x86 的指令集翻译成 VLIW（Very Long Instruction Word）风格的 RISC 指令集，用这种方式去模拟 x86 的执行，性能比 x86 本身还高；但他们和 Intel 打了很多年官司，最后被 Intel 活活拖死了。

我自己那个 CrazyOS 的想法，最早其实来自 Tom Anderson。这个世界是有好东西的，而你们学的东西被污染了。我觉得有两个方面。第一，不学技能肯定是谈不上什么好、什么不好的：如果你不懂数字逻辑电路，不懂计算机系统基础，不懂操作系统，你根本没有办法判断到底什么东西是好的、什么东西是不好的；没有基本概念，是做不出任何创新的。第二，环境与见闻会影响你们的判断，不只是对技术的判断，而是对任何东西的判断。你们的上一代人，可能是我们的老师们，因为没有走出国门，没有见识过好的东西——他们没有见过好东西，但这当然不代表世界上没有好东西：我们上一代人在读书的时候，这些人已经在 Stanford 做 97 年那种特别领先的工作了。

### 我们也在努力：differential testing 与形式化

其实我们也在努力。一方面我们做得不够好，另一方面我们也在努力：比如为古法编程时代设计的计算机系统基础，我们还是做了一些挺不错的东西，一定程度赶上了过去比较先进的东西——有 NEMU 的实验，有一些 abstraction layer。而我觉得对大家在古法编程时代影响最大的，是我们 NEMU 的 differential testing。

我们的设计是这样的：在你最终要扛不住的时候把它放出来。大概到 PA 后期，指令多了以后，你们不可避免地会引入一些小错误，而那些小错误非常难 debug。表现出来就是你的程序大概是对的——程序跑着，结果有一个很长的 benchmark 程序，它的结果死活不对，最后那个验证码验证的时候死活不对；或者你的程序跑着跑着，前面一半输出是对的，后面一半突然开始输出奇怪的东西。这样的程序是非常难 debug 的。我们选择在这个时候把 differential testing 放出来，你用了以后发现好用、有用。

而回头想，这其实是 harness 的思路：如果要驾驭软件的复杂性，一种方法是硬刚——手册就写在那儿，RISC-V 的手册就写在那儿，我可以一遍一遍不厌其烦地读手册，读完手册去调代码，然后找到那条我实现错了的指令；另一种方法是设法绕过它，做一个 differential testing 这样的工具去绕过它。我们就是在想办法教给大家一些软件工程几十年里积累下来的智慧。

在今天 AI 的时代，我觉得我们还是可以做很多事。比如设计课程的时候，下个学期离散课的课表变成了三分和两分两门课拆开。拆开以后，我很想做一件事：把我们的系统线上面的实验和离散数学课、数字逻辑课做一个联动。离散数学课可以形式化一个指令集——用 proof assistant 的编程语言形式化 RISC-V 的一小部分，然后你可以证明你的 CPU 是对的，那就不需要 differential testing 了，你可以直接生成一个证明。互联网上其实有 RISC-V 的 formal specification；哪怕没有，我也可以从一个已经认为是正确的指令集里把 RISC-V 的行为提取出来，然后证明你的模拟器的行为和这个模拟器的行为完全一样。当然，短时间内可能还实现不了。所以你们需要去看更多的东西——我这一门课讲再多知识都是没有用的；你们需要意识到，这个世界上还有很多你看了以后会想"哇，竟然还可以这样"的东西，比如 Disco。

### 二十年过去，reward hacking 还在

讲到虚拟化的起点是 Disco 那篇 paper，我又想到二十年以前：复旦的实验室里有几位兄弟在 VEE '06 上发了一篇 paper，叫 *Live Updating Operating Systems Using Virtualization*，做的也是虚拟化。大概同一时候，2007 年 VMware 在纽交所上市。这个实验室里就诞生了现在的上交大 IPADS——如果你做操作系统，你会熟悉这个组，它应该是亚洲第一、甚至世界第一的操作系统论文产出组；也是华为操作系统首席实验室的首席科学家所在的组。二十年前就在那里。

我发现我们的品位其实增长了。他们刚起步的时候，我还听过海波讲他早年研究的历史，可能跟我们每一个人、跟我自己也挺像的：他刚开始的时候也不知道什么是真正好的品位，但他有能力，有能力就会去做一些像"在操作系统上实现 live updating"这样的工作，而以虚拟化的方式可以把它做得更好。然后他就会这儿做一点、那儿做一点；后来他牛逼以后，去 MIT visited 了一年，就在那个时候他发现：哦，原来这个世界是这样的。然后慢慢走上更好的轨道。

可能我们成了第一代知道什么是好的人，但我们没能把这个世界变得更好。二十年以后，我发现我们的同学还在 reward hacking。还有一件很割裂的事：昨天有一个同学私信我，问"老师，最后两个实验中的内容考试中会出现吗？"我当然非常理解，完全可以理解——分数对你们很重要，你们觉得保不了研天就塌了，确实是这样。

我觉得，reward hack 多了以后，你问这个问题问得太多了以后——我不确定那位同学有没有问得太多，希望没有——在突然有一天他不再需要考试的时候，他就不知道要干什么了。反过来，如果你看过很多品位很好的工作，你知道有些工作为什么要得图灵奖——因为它开辟了一个领域——那你就会去想，也许我可以做一些更大的事情。你不用考试，那是一件很好的事，你不用受到分数的束缚；当然考一个好分数还是很重要的，所以你们还是得好好做实验。

### 整机虚拟化难在哪：syscall 是一道特权级的坎

回过头来看那个技术问题：既然吹了这么多，Disco 到底做了一件什么牛逼的事情？

先想一个进程。一个进程运行在用户态。理论上，我想要模拟执行一个进程是很容易的：我只要用 `mmap` 把这个进程的地址空间重新构造出来就行，然后就可以把这个进程放到 CPU 上直接执行——本质上说，进程是可以直接模拟执行的，前提是同一个体系结构。如果我像 QEMU 那样，要在 ARM 上模拟 PowerPC、在 ARM 上模拟 x86，那是另外一件事；但无论如何，只要模拟，你就不可避免地要接受数倍的性能开销。

当然还有一种情况：一个 Windows 的进程想要在一个 Windows 上运行，那我只需要给它构建一个虚拟的地址空间，并且拦截它所有的系统调用就可以了。但困难的实际上正是这件事——进程会做系统调用。

syscall 是一条指令，本质上是一次跳转；但这次跳转完了以后，它会改变系统的特权级。x86 上有 Ring 0 到 Ring 3：Ring 0 是最高的特权级，进程运行在 Ring 3。

> **提示**：Ring 1 和 Ring 2 在体系结构里是设计了，但实际并不使用。应用程序在 Ring 3 执行，比如它想要关中断，会直接 segmentation fault——程序就 crash 了。

```text
        应用进程（Ring 3）                      内核（Ring 0）
              │
              │  syscall 指令（本质是一次跳转）
              ├──────────────────────────────────►  特权级由 3 切到 0
              │                                     此后可执行各种特权指令
              │◄──────────────────────────────────  返回用户态
              │
              └── 在 Ring 3 直接执行关中断等特权操作
                  ──► segmentation fault，程序直接 crash
```

一旦系统调用进入操作系统内核、进入 Ring 0，我就可以随便执行各种特权指令——比如说，我现在就可以关中断。

特权级这道坎，就是整机虚拟化真正要接住的地方。

## 从影子页表到容器：虚拟化的两条路
> 对应块：BLK58 | 覆盖分集：P29下 | 块标题（分集名）：《虚拟机和容器（下）》

我可以关中断以后死循环，而且我必须允许这件事情发生。

因为我现在是虚拟机，我是虚拟化的，那就要允许这件事情发生。设想我在调试另外一个操作系统内核，那个内核里面真的就有一个死循环，它关中断之后死循环，这个操作系统就"嗨"了——那我应该能够看到这个操作系统完整的行为，不然我怎么调试它？

想模拟它，真正困难的是 Ring 0 的这些指令怎么处理；而且在 Ring 0，它不像进程那样可以随便改动自己的地址空间。一个进程想要改变自己的地址空间，必须通过系统调用、通过 `mmap` 来做（对 Linux 来说）。所以理论上，我只要截持了那个进程对 `mmap` 的系统调用，其实就可以模拟这个进程的执行——Windows Subsystem for Linux 就是这么干的。但在这里不是：内核可以随便把 `CR3` 寄存器改掉。

### 虚拟化真正难的地方，是 Ring 0 的那几条指令

之所以能随便改 `CR3`，是因为本质上页表是一个数据结构。

我们说虚拟内存——不管是进程的还是操作系统内核的——它就是一个 VR 眼镜，这副眼镜配置的是一个从虚拟地址到物理地址的映射。比如虚拟页号（virtual frame number）1、2、3、4，映射到物理页号（physical frame number）1、2、3，可能只有三页：我把 1 映射到它，2 映射到它，3 映射到它，每一条映射还可能带一个读、写、执行的权限。就这样的一个数据结构。它有一级页表、两级页表、三级页表；两级页表的时候，第一级的索引、第二级的索引，都是一条一条的 PTE entry。这些你们在计算机系统基础课上都学过。

关键在"它是数据结构"这几个字：既然是数据结构，内核的代码就可以直接用 load 和 store 指令去改它——只要改一个内存地址，那个 3 的映射就变到别处去了。

> **提示**：改数据结构和改动生效是两件事。改完页表里的表项，映射并不会立即生效；要生效得把新页表的地址 `mov` 到 `CR3` 里去。相当于我一开始是在调整那副 VR 眼镜的设置，调完之后再换上一副新的 VR 眼镜。这些操作都具有摧毁性，不能直接在 CPU 上执行，必须模拟。

但另一方面，是不是绝大部分操作系统内核的代码，其实执行的并不是这种需要特权的指令？

关中断、开中断，只有你在上锁、解锁的时候可能要动一下；一次上下文切换，你可能只会执行一次 `CR3` 的 `mov`。此外的系统调用里 99.99% 的指令，都是普通指令。你想想，我做得比较多的 system call 是什么？随便 `strace` 一个 `ls` 看看：如果你要做一个 read，绝大部分代码都是普通的——你会先去知道这个文件描述符指向了一个什么样的文件，你要检查它，这是一个数据结构的操作；然后你要找到它对应的文件系统，这也是一个数据结构的操作；然后你要找到它该执行的函数，跳过去执行，这是完全普通的代码；接着这个执行一般会从缓存这些数据结构里面找找找，找到之后，除非要做 I/O 了，它才会发一条 I/O 指令，然后等 I/O 结果返回。不做 I/O 的时候，几乎所有操作都是数据结构上的运算。

> **结论**：虽然在进程的执行当中有这种非常危险的指令，但几乎所有的指令都是普通的。这就给了我们一个机会。

### VMware 的解法：Ring 1 与影子页表

我们的需求并不像 QEMU 那样去跨机器结构做模拟，而是用 x86 来模拟 x86。（Disco 当年是在 MIPS 或者别的某个并非 x86 的机器结构上做的，而 VMware 真正推出产品的时候，主打的就是体量最大的 x86，最早甚至都没考虑过别的机器结构。）

于是 VMware 干了这样一件事：没问题，进程还是可以运行在用户态的 Ring 3；但是我把操作系统内核放到 Ring 1 去。这是一个非常非常聪明的 hack，只有真正懂技术的人才做得出来的 hack。

就算硬件上没有 Ring 1，它也有办法：它可以扫描操作系统内核的指令，把这些指令 patch 掉，就像你们调试器那样在那儿插一个 breakpoint，从而劫持所有可能会对系统内置状态造成影响的指令。内核被放进 Ring 1 之后，不给 Ring 1 的程序任何权限，那么它执行的每一条特权指令——关中断、执行 I/O、改 `CR3`——全部都会产生一个异常。产生异常以后就回到我正常的操作系统，而我的 VMware 会装一个驱动，把执行流送到 VMware 的 hypervisor 里。相当于所有会引起严重后果的非法指令，都会被 VMware 收编。

接下来就是它最大的创新，叫 shadow page table，影子页表。

```text
Ring 3   应用程序                （原样运行，一行代码都不用改）
Ring 1   客户机操作系统内核        （被搬到这里，没有任何特权）
Ring 0   宿主操作系统 + VMware 驱动 （真正拥有物理内存的人）
```

读图：客户机的内核被整体降了一级放进 Ring 1，所以它自以为在裸机上执行的那些特权动作，都会先撞上异常，交给 Ring 0 的宿主操作系统和 VMware。

有了这层拦截，VMware 就能根据虚拟机的虚拟地址空间重新构造一份 VR 眼镜。在 Ring 1 里跑的那个内核，认为自己拥有整个物理地址空间：物理地址空间的第一页、第二页、第三页，它会说，好，我要把虚拟地址空间第一页映射到第一页，第二页映射到第二页，第三页映射到第三页。它自己维护的那份页表就是按这个认识写的。

但实际上，VMware 才是真正内存的拥有者。它知道物理内存是有限的：为这个操作系统分配的是第四页、第六页、第八页。它也知道这个虚拟机的第一个物理页映射到了我的第四个物理页，第二个映射到第六个，第三个映射到第八个。于是它重新组织一个页表：1 映射到那里，2 映射到那里，3 映射到那里，直接指向真实的位置——这个才是真正的页表。

```text
客户机自己写的页表（它以为的样子）
  虚拟页 1  ->  自己占的第 1 页（可读写执行）
  虚拟页 2  ->  自己占的第 2 页（可读写）
  虚拟页 3  ->  自己占的第 3 页（只读）

VMware 边上的影子页表（真正写进 CR3 的那一份）
  自己占的第 1 页  ->  真实内存的第 4 页
  自己占的第 2 页  ->  真实内存的第 6 页
  自己占的第 3 页  ->  真实内存的第 8 页
```

读图：客户机改的是上面那份页表，而每一级映射都要再经过下面那份影子页表翻译一次，最后才落到真实内存上——相当于戴了一副被虚拟出来的、两级虚拟的 VR 眼镜。

于是每次客户机执行 `mov` 到 `CR3` 的时候，VMware 就悄悄把这个 shadow page table 换到 `CR3` 上。代价是它需要截持所有对 page table 的操作——当然这件事情它在技术上做到了，所以这是一个非常酷的 trick。

它换来的东西很值：操作系统 99% 的代码，都是以本地速度在执行的；只有访问特权指令或者访问 I/O 的时候，才会 trap 出去。

就这样的一个想法，带来了整个虚拟化的黄金时代。它的估值从最早的一片空白，到上市时的几十亿美金，再到后来几百亿美金；在很长时间里，它是整个云世界上最重要的基础设施之一。我读书那会儿，它已经是一个非常重要的基础设施了。因为它好用——原来所有为单机设计的操作系统不需要做任何修改，连安装程序都不用改，就可以直接运行。

### 黄金时代：硬件接过 hack，还有那些疯狂的 idea

#### 硬件虚拟化：Ring -1 与 EPT

VMware 的这个设计甚至影响了硬件的设计。

Intel 在 2005 年推出了第一个硬件虚拟化：你不需要再 hack Ring 1 了，可以专门进入一个虚拟机的模式，这个模式有点像 Ring -1，很多特权指令也可以直接执行，不需要再去 trap。但如果我要执行一个 I/O，那还是会生成一个 VM exit——就是前面讲过的 KVM 的那个机制。有 I/O 的时候它必须出来，因为虚拟 I/O 设备是模拟出来的。

再到 2008 年，有了 EPT：它把影子页表也用硬件实现了。你现在有四级页表，那么这四级页表是你正常的页表；如果虚拟化启动，还可以再有四级页表，弄出一个八级的页表——一个非常非常夸张的机制。这样你就不需要用 VMware 的软件来维护这份页表了。

如果你真的把操作系统、计算机系统基础的知识学好了，你们真的可以去重走一下这段历史的进程。那段历史比我读书要稍晚一点，我自己是差不多开始读 PhD 的时候才回头重新看了一遍：从不理解到理解，给我非常大的震撼——这就是真正的技术。

这段历史里也催生了很多标准，比如 virtio，一种虚拟的 I/O；现在也有 virt-GPU，你可以用 virtio 的方式接入、虚拟化一个 GPU。

#### 把一台机器的执行历史记下来

还有很多非常疯狂的 idea。不是所有的 idea 在今天都实现了，但比如说到 AI 的时代——agent AI 的时代——可能还有复活的。

比如我们可以 replay 一个虚拟机。有一篇 work 的标题就叫 "Enabling instruction analysis through virtual machine logging and replay"：理论上说，如果你只有一个 CPU，你只需要记得它在什么时候发生了 VM exit，以及 VM exit 以后干了什么。VM exit 可能会去请求一个 I/O 设备，那我不知道这个 I/O 设备读的是什么，我只要把 I/O 设备读到的值记下来，理论上我就可以重放整个计算机所有的执行历史。一个非常疯狂的想法。你的虚拟机不仅可以虚拟化一个执行，你在里面打一个游戏，打完之后还可以把这个游戏的录像完整地回放出来——这件事理论上说也是可以做到的。

再比如 "optimizing migration of virtual computers"：你可以把一个虚拟机暂停，把网络连接全都 drop 掉——假设你所有的设备都挂在一个可插拔的总线上，那就好像你把所有的设备都拔掉了；然后到另外一台机器上，因为虚拟机就是一团内存，把这个内存直接拷过去，就可以在另外一个地方启动。

在今天，其实 agent 和沙箱会很需要这些技术，所以你会看到这些技术又开始复活。

顺着这条路走下去，VMware 从一篇 paper 做到 600 亿美金，先是被 EMC 收购，后来又被戴尔收购。

### 换个方向：一个操作系统当十个卖

但我今天要讲的是另外一个故事：我觉得他们从一开始就走上了一条错误的道路。

正过来讲他们的故事都是对的：我有 Ring 1，我就可以在本地执行操作系统的内核，就可以实现这样的 virtual machine。但是操作系统会说：你反正事实上是要跑操作系统的，那为什么我自己不能虚拟化我自己呢？

你真正想要干的事情，是把一台机器当 10 台来卖，那你当然可以虚拟化。那我为什么不能一个操作系统当 10 个操作系统来卖？我在操作系统启动的时候，能不能就说把我分成 10 份，提供 10 个空间呢？所以我觉得整个发展的历史被 VMware 带歪了。如果在 97 年的时候，是另外一个人发表了另外一篇 SOSP，讲的正是 lightweight container，那值 600 亿的可能就不是 VMware 了。

换个方向想，我们全部都是应用程序。虚拟化本质上不是为了虚拟化操作系统，而是为了执行应用程序——比如一个 nginx 为我们提供 web 服务，或者一个 mail、一个 BBS 提供给别人服务。这是一个进程，它要运行在操作系统上，而进程和操作系统唯一的交互就是 syscall。

那为什么我们的操作系统不能把自己假装成是在一个虚拟机里执行系统调用呢？

看，我们的操作系统能不能在系统启动的时候加一个参数。我们展示过 Linux 启动的样子：最早是一个 `initramfs` 的状态，从 firmware 加载它，`initramfs` 之后去挂载文件系统的根，然后执行一个 `pivot_root`，找到一个进程，再从那个进程开始执行。那对我这个 Linux 来说，我能加载一个 `initramfs`，我能不能加载两个呢？没有道理不能。

相当于我在操作系统里面实现：我有一个 `struct proc`、一个 task 数组，能同时运行 10 个 task，我就把这个数组多一维。然后给它起个名字叫 `os_id = 1`、`os_id = 2`，这就是两个不同的操作系统。这两个操作系统的行为完全一样，所以代码几乎都不用改，只要稍微改一下 `os_id`。

你们可以去试着让你们的 coding agent 改一下 xv6：让 xv6 里面所有的东西都加上一个 `os_id`，每个对象都可以属于一个 `os_id`。默认只有一个操作系统的时候，所有人的 `os_id` 都是一样的；现在我可以让它属于不同的 `os_id`。我在启动的时候，为 `os_id = 1` 做一份 `initramfs`，为 `os_id = 2` 也做一份 `initramfs`——问题不就解决了吗？

我可以有一个 `os_id = 1` 的 `pid = 1`，也有一个 `os_id = 2` 的 `pid = 1`。pid 还是从一个池子里分配：我创建一个进程，它可能是 2；再创建一个，可能是 3；再创建，可能是 4、5、6。但因为每个 pid 都知道自己的 `os_id` 是什么，所以每当我遍历 `proc` 的时候，我只能看到和我自己的 `os_id` 一样的进程。3 号进程想 kill 1 号进程，它是可以看到 1 号的，因为它们的 `os_id` 相同；5 号进程想 kill 3 号进程，它是看不到 3 号的，因为它们的 `os_id` 不一样。

就这么简单：给每个对象加一个 `os_id`，你就在一个操作系统里面实现了两个操作系统。

```text
一个操作系统里的对象池（所有 os_id 共用同一个池子）
  |-- 进程 A   [os_id = 1]
  |-- 进程 B   [os_id = 2]
  |-- 文件 C   [os_id = 1]
  |-- 进程 D   [os_id = 2]
```

读图：分配器还是同一个，申请出来的对象只是在头上多打了一个 `os_id` 标签；至于"谁看得见谁"，全靠每一次遍历时拿 `os_id` 去比对。

对黑心资本家来说，这是绝对想要的，因为它是极致的性能：你只给每一个对象加了 4 个字节的一个 field，然后在写代码的时候考虑这个隔离，你就在一个操作系统共享的资源池里面，共享出了所有的操作系统。你想想，如果你开一个虚拟机，你得说给它分配 4GB 还是 8GB 内存；而在这里，所有对象的 allocation 都是共享的。设想一个 memory allocator：不管 `os_id` 等于 1 还是等于 2，它想要分配一个对象、分配一个进程的对象，都可以去同一个池子里面申请，只是申请过来以后，在对象上打一个标签，`os_id` 等于 1 还是 2。就这样。

这甚至也不是谁第一个提出来的，这是一个 1970 年代的想法：当年 Disco 说，我们要把一个 1970 年代的想法 Virtual Machine Monitor 复活，然后它就复活了。

### PID 是一个会泄漏的抽象

既然说到了 pid，我在这里再 aside 一下。pid 是个很麻烦的东西，它是会被回收利用的。

所以理论上你会发现这种情况：你 `ps` 的时候看到一个 pid 还活着，等你 `kill` 它的时候，它已经提前死了；死了以后你再 `kill` 它就不合法，它会说 no such process。这还 OK。

但你可以这样想：你先 `ps` 去找到你那个卡了很久的 VS Code，但你的反射弧实在太长了——可能 3 年以后你才按下那个回车键。这个比方当然不太恰当，但实际在数据中心里是有可能发生的：你先去遍历了一个进程表，然后你的进程又因为某些原因（比如 I/O）花了很长时间才回来运行，而在那个过程中，有大量的进程被创建和销毁。在一个服务了几亿人的服务器上，这是有可能发生的。结果你一 `kill`——就那种先 `grep` 然后再 `kill` 的脚本——因为中间隔了太长的时间，你就杀错人了。这确实是有风险的。

pid 是一个 `leaky abstraction`，它没有任何办法阻止你，所以你还得再想别的办法：在操作系统里面再写一些别的代码，再创建一个共同的父进程等等别的机制，来保证你不要杀错人。用 pid 本身是没有办法避免的。

所以今天我们的操作系统设计者不停地都在打补丁。比如有个东西叫 `pidfd_open`，你可以打开一个 pid。这是个设计得非常诡异的 API，但你仔细一想，还是很有道理的，因为 everything is a file：你想要访问、引用操作系统里面的对象，就必须通过文件描述符；因此如果你想要有一个指针指向一个 pid（注意，不是指向一个进程，当然某种程度上也指向一个进程），那你也需要一个 open，所以用的是 `pidfd_open`，然后就可以持有这个 pid。

持有这个 pid 以后，你的引用计数就会加一；引用计数加一，它就知道还有东西引用着我，我是不能释放的。这个 pid 就不能被释放。你可以在这之后，用一个 `pidfd_send_signal` 去 kill 这个 pidfd，你就能确保你杀掉的那个东西不会丢失。相当于你在打开的时候持有一个引用，直到你释放这个引用，它都不会释放。

你看到人类的历史就是这样的：大家在那个时间点做的决定，未必就是全局最优的决定。PID 在 UNIX 时代是一个非常好的设计，简单、干净；但当你的数据中心里面有无穷多的进程的时候，它就变成了一个 `leaky abstraction`。我们的虚拟化也是的。

### chroot：1979 年就有的那个系统调用

回到 `os_id`：在操作系统里面为每一个对象增加一个 `os_id`，是有非常大好处的。

其实在 1979 年的时候，Version 7 的 Unix 就提供了一个系统调用，叫 `chroot`。它用起来比较麻烦，因为一旦你 `chroot` 以后，什么 `/bin`、`/usr/bin` 全都没有了。我可以 `chroot` 到 `/tmp/y` 试一下，它给我失败了。为什么呢？因为它试图运行一个 shell，而 `chroot` 完了以后，那个根文件系统里已经没有 `/bin/bash` 了。所以你需要为它构建一个完整的文件系统——有 `/bin/bash`、有 `/home`、有完整的东西——然后你才可以做这样的 `chroot`。

而 `chroot` 以后，它就把进程的文件系统视图限制到某一个子目录底下了。

于是你可以说：这又跟虚拟机很像了。我有两个一模一样的 FS；我可以在我的一个文件系统上面，在某一个 OS 上，创建一个假的 `/bin/bash`——这个 bash 可能是另外一份 bash，不是我系统里的 bash，是一个单独的文件；然后我做一个 `chroot`，进程就只能看到这个文件系统根了。这不就是一个虚拟机吗？

虽然 PID 没有隔离开——如果只有 `chroot` 的话，PID 没有隔离，我还是可以去 kill 别人的进程。但只要没有权限，kill 不就行了吗？我可能能看到它们，但我确实是在一个隔离的环境下运行了。就这么一个机制。

### 枚举每一种对象：Linux namespaces

既然 PID 可以做这样的 OS ID 的隔离，文件系统也可以，那你完全可以在操作系统里面创建一个完全隔离开的操作系统。只要你去枚举操作系统里面有什么对象，然后为每一类型的对象都去实现这个命名空间的虚拟化，你就有了今天的 Linux namespaces。

除了 PID，还有几件很重要的是必须虚拟化的。用户和组：两个 0 号用户不能互相访问，这就是两个完全不同的体系；这里的 1000 号用户和那里的 1000 号用户是不同的用户——这还是有一点复杂的。文件系统：刚才 `chroot` 只管了文件系统的一部分，你还需要管 mount point。还有信号量、消息队列和共享内存，这些也需要隔离开：一个管道、一个信号量，它们互相之间也是不可见的。网络也是：端口也要虚拟化。看起来现在是一个 localhost 的 5000，实际上是一个 OS ID 的 localhost 5000；两个不同的 OS ID 都可以用 5000 端口，各自有自己的 5000，自己的进程又和自己的 5000 交换数据。所以整个网络系统当然也需要虚拟化。还有系统时间和时区可以虚拟化，主机名和域名也可以。

我们也可以把系统里面现存的 namespace 列出来，会看到系统里现在有这些 namespace。你们回去如果自己 `docker run` 几个 container，就会看到不同的 namespace。我也可以让 AI 帮我解释这些 namespace 到底意味着什么，也可以 `strace` 一下，看看它是怎么办到的：它是不停地去某一个文件目录里面找这些信息的——`ns` 下的 net、`ns` 下的 pid、`ns` 下的 cgroup。那它应该是从哪里找到这些的呢？你们想到的应该是在 `proc` 下：每一个进程里面是有 namespace 的。

```text
/proc/<pid>/ns/           （每个进程都在这里露出自己的命名空间编号）
  cgroup    资源控制组
  ipc       信号量、消息队列、共享内存
  mnt       挂载点视图（mount point）
  net       网络设备与端口
  pid       PID 编号空间
  time      系统时间与时区
  user      用户与组的编号空间
  uts       主机名与域名
```

读图：每写一个 namespace 文件，就对应正文里说的一类需要虚拟化的对象；`strace` 之所以能查到这些信息，就是因为它们被挂在每个进程的 `ns` 目录下面。

这相当于就是我这个原理的模型：每一个进程都有一个 OS ID。当然它不仅是 OS ID，它可以有不同的 ipc、mount、net 的 namespace，所以我知道什么和什么是完全分开的——我可以让两个进程共享同一个 net 的 namespace，但是让它们有不同的 mount 或者 ipc 的 namespace。但简单理解就是一个 OS ID。

在 procfs 里面就能看到这个进程的 OS ID：在 `/proc` 下那个 15018 进程的 `ns` 里，我就可以知道，哦，我的 ipc 是一个编号为某某的 namespace，我的 mount 是这样一个 namespace。

系统里实际能观察到的东西很有意思：PID 等于 1 的 `/bin/init` 拥有全套命名空间——time、cgroup、pid、user、uts、ipc、net、mount——这相当于一个根容器，198 个进程默认共享。但也有一些守护进程在隔离的 namespace 上运行，有些 mount 的服务会拥有独立的命名空间。你们回去起一个 docker 容器，它也会告诉你为它创建了哪些命名空间。

### 隔开之后还要能控量：cgroups

接下来，如果你作为黑心商人想要卖这个服务，光隔开了还不够。你隔开以后要干一件什么事，才能把这个产品更好地卖出去呢？你还要能够控制它们的用量。

为什么呢？虽然用量隔开了——我在这个 OS ID 里看不到别的 OS ID 的所有东西，对象我都访问不了，它的 syscall 我也访问不了——但它们每一个进程还是操作系统原来实现的进程。我刚才说你可以直接改代码让 xv6 拥有这个 namespace，但它的调度器没改，它还是从系统里面所有的进程里取一个执行、取一个执行，所以所有进程看起来还是公平地执行的。

但是当你有了 OS ID 这个机制以后，你就不能让所有的进程公平了。你想要让这里这些进程共享一个 cost，比如一个 CPU cost：每当这里的进程消耗一单位的时间，就把它加到这里的 CPU cost 上；那边也有一个 CPU cost，每当那边的进程执行，就在那个 CPU cost 上加一单位时间。然后你就可以去控制：我作为一个黑心商人想的是，我要把一个 CPU 均分成 10 份；我可以说，最多你只能用我们 CPU 的 20%；以及你们 10 个人，可以共享均分这个 CPU 的 share。

这样我不就把我的资源真正地虚拟化了吗？恭喜你，你又发明了一个非常重要的资源调度的机制，叫做 cgroups。

```text
cgroup v2 是一棵树
  /
  +-- 大组 A          （和其他大组公平分享 CPU）
  |     +-- 小组 A1   （各自设各自的资源策略）
  |     +-- 小组 A2
  +-- 大组 B
```

读图：大组之间是公平分享，组内的小组之间又可以另设一套不同的策略；每一层都是"圈定一批进程，再给这批进程定资源访问的规矩"。

你也能看到，我们的系统里面是有很多这样的 control group 的。control group 在 v2 的时候变成了一个树状的结构：我这里有一个大组，这个大组再可以分成好几个小组，然后我可以分别为它们设置控制资源的策略，比如 CPU。大组和大组之间是公平分享的，小组之间我又可以设一个不同的策略。

这是一个和 namespace 正交的机制：namespace 管的是"你看不看得见"，cgroup 管的是"圈定一些对象、一些进程，然后设置它们资源访问的策略"——比如文件系统的带宽、网络的带宽。然后你就可以成为一个真正的黑心资本家。

### 容器：namespaces、cgroups 与 OverlayFS

当你把 cgroup 和 namespace 联用的时候，你就得到了容器。

> **定义**：容器 = namespace（隔开可见性）+ cgroup（控制用量）+ 分层镜像（快速造出文件系统根）。

再加上讲 OverlayFS 时说的那种分层镜像：你可以一层一层叠来构建一个更好的文件系统根，而不需要每次去创建一个全新的文件系统根，再 `chroot` 过去。用 OverlayFS 就可以非常轻量的方式创建同一个系统的好多个实例。

```text
可写层        （容器自己写出来的东西）
  |
镜像层 3      （应用）
  |
镜像层 2      （运行环境）
  |
镜像层 1      （操作系统基础镜像）  <-- 一台机器上 1000 个实例共用这一份
```

读图：越往下越基础、越共享；一台机器上放 1000 个实例都是同一个镜像，只要一个副本，只浪费一份存储。

这就是资本家最喜欢的。所以你已经发明了 Docker。

### 虚拟机与容器：安全性的那笔账

从某种意义上来讲，我觉得 VMware 是把人类给带歪了。2000 年的时候，FreeBSD 就有一个 Jail 这样的机制，它实现的比 Unix 的 `chroot` 要更完善，而且其实一直在演化。但一直到 06 年，cgroups 和 namespaces 才被引入，这应该是 Google 的工程师推动的。我觉得他们在那个时候应该也是意识到了：VMware 这种虚拟化确实把人类带歪了，你没有必要为了两个隔离的东西去做那么重的事情（当然这还假设操作系统是安全的）。

虚拟机相比于容器还有一个显著的优点：安全性。因为如果你操作系统里面有一个漏洞，就惨了。

漏洞有两种。第一种是越权：比如我这里获得了一个全局的指针、一个整个全局内存的指针，那我就可以去访问别人的容器，把别人机密的信息给偷过来。第二种是 cgroup 的资源控制没有做好：我可以在一些不经意、你们没有想过的方式里——比如不停地创建文件，把系统里面文件描述符表里所有的资源都耗满——结果就造成了对其他容器的 denial-of-service。我想要打开文件，反正我自己也打不开了，但是别人再想打开文件，对不起，都打不开了。实际上是容器是有这样的 denial-of-service 漏洞的。

所以对黑心资本家来说，虽然虚拟机的隔离比较好，但是虚拟机真的太浪费了：你需要一个模拟出来的物理内存，需要一个 shadow page table，甚至还把软件和硬件一起都卷了进来。也许更轻量的方案是更好的。

把这条线索串起来看：

| 时间 | 发生了什么 |
| --- | --- |
| 1979 | Version 7 的 Unix 提供 `chroot` |
| 2000 | FreeBSD 有了 Jail，比 `chroot` 更完善 |
| 2005 | Intel 推出第一个硬件虚拟化，进入类似 Ring -1 的模式 |
| 2006 | cgroups 和 namespaces 被引入，由 Google 的工程师推动 |
| 2008 | 有了 EPT，影子页表硬件化；也有了第一个比较流行的 LXC |
| 现在 | Docker 成为了云原生里的标准答案 |

到 06 年有了 cgroups 和 namespaces，到 08 年才有了第一个比较 popular 的 LXC，就是 Linux Containers，然后再到现在，大家都知道了，Docker 成为了云原生里面的一个标准的答案。

### 钱、meta-mechanism 与历史的车轮

这里我又回到了 Richard Sutton 的 "The Bitter Lesson"。它讲的是强化学习：我们要做那些 meta-mechanisms，让机器、让算力、让能够 scale 的东西，去得到这个世界上更好的解。强化学习是一个很典型的这样的机制，大语言模型也是一个很典型的这样的机制。

某种程度上人类或者所有生命也是这样的。你想，生命就是一个非常简单的机制：DNA 可以复制，再往底下更简单的是化学的公理；然后我们人类就在这个世界里面竞争，不断地竞争。某种程度上，你们要考试考好，也是一个 meta-mechanism 之后的结果。

人类世界站在重大技术决策上，其实也有这个感觉。我们现在有很多问题，比如黑心资本家说我们要挣钱，但是挣钱的途径有一万条：你可以用虚拟化的方式来实现把一台机器变成很多机器，full system virtualization；也可以用这种非常轻量的方式，从操作系统里面割出好多小操作系统。这也是一个 meta-mechanism，其实是钱驱使的。

这就是这个社会的本质。我今天为什么要讲这么多？因为这个社会真正驱动的，还是钱，你没有办法逃脱这个钱的诱惑。你看，Mendel 作为一个大教授，很多代表性工作也算是功成名就了，但他们最终还是决定去创办 VMware，去改变这个世界。

所以我觉得真正有意思的 mechanism 是历史的车轮：我们人类要进步，而人类要进步里面有很多我们无法抗拒的诱惑——财富自由的诱惑——然后推动大家去把这些技术做到极致。其实你做错了也不要紧，这就是这个机制最好、最有趣的地方。

对你们来说可能分数很重要，但就算是你们分数不小心没有那么好，可能也没有那么重要，你总还是有一个更好的退出机制。也许你因为考试没考好、没保上研，去加入了一个 start-up，最后财富自由了——这开玩笑。意思是，我们生活在一个这样的 meta-mechanism 里面，你们慢慢会去重新思考这个社会，重新思考一波一波的技术浪潮怎么升起来、怎么落下去，最后形成自己对这个世界的一个看法。作为一个能够把技术理解清楚、并且看到技术的浪潮是怎么推动这个世界进步的人，还是一件非常有趣的事情。

### 云原生：Kubernetes 与声明式编排

在云的时代，在今天叫云原生的时代。云原生当然是一个我觉得有点炒作的概念，比较 fancy。如果这世界上所有东西都在云上——我们也不，PC 肯定还是需要的，因为你最终还是要和你的手机或者 PC 交互——但是在云上，容器和虚拟机就是完全一样的，只是它的开销比较低，安全性略低。

那如果以后的云上服务全部都在云上，有没有一个好的系统可以帮我们去管理云上各种各样的虚拟机呢？答案是一定会有。

VMware 其实挣了很多钱，它有一个叫 ESXi 那样的、或者 vSphere 那种商用的数据中心管理软件。那个数据中心管理就是说：我可以起一万个虚拟机，我可以把这个虚拟机克隆一万份，然后这一万份就可以被我纳管进来。这在当时是一项非常重要的技术，但也是一项非常重的技术：它需要在你的服务器上面装一个软件、装一个系统，装上 VMware 专门定制的软件，甚至可能有带外的控制信号，然后才可以把它虚拟成一个可配置的集群。

但是同样的事情在容器上做就容易多了。Kubernetes 获得了成功，某种意义上它现在的云原生时代已经把虚拟机的份额挤压得很小了。

它的想法是：我们要动态、透明地管理无状态的容器 pod。也就是说我们有很多的服务，但这些服务最终都有些比如分布式的数据处理、分布式的存储、分布式的 API；然后每一个 pod、或者说每一个单独的小虚拟机，你在设计的时候它都随时有可能会被杀死。但杀死不要紧，我会有一个 policy，说我的这样一个容器，请你在多数据中心上面、比如每个数据中心上复制 100 份。我只要把这个要求提出来，然后我们的容器调度集群 Kubernetes 就会每次看到这个容器被杀掉了，就在另外一台机器上再起一个。全部都是因为 Docker 以 hash 构建的一个 deterministic 的 build，它直接在另外一台机器上再起一个这个容器就可以了。

它还可以见缝插针：看哪一个机器余量比较大，就可以把这个容器插到那个机器上。如果出错、网络异常，没关系，这个容器丢了就丢了，我就在别的地方再起一个。

然后这种声明式的访问和路由带来一个很大的好处：你一旦配置好以后，你只要访问一个它的 gateway 的 API，说我就说我要访问名字是这个的服务，比如教务的服务，它就会自动帮我转到这个教务的服务的容器上。它有一整套编排和路由的机制：你只需要跟那个 gateway 说我要请求教务的服务，然后那个请求的 body 是什么，它就会把这个 body 送到这个容器里；这个容器处理完了以后，在比如某一个端口里，再把这个结果送回来。你完全不需要知道它里面是怎么样的，你完全不知道你送到的是哪一台具体的服务器上——又是一层虚拟化。

这一层虚拟化是真正地非常非常好用：因为它可以自动地做负载均衡、做健康检查、做 load balance。而且它还可以给黑心商人带来更多的钱，因为容器是见缝插的。

### 背包问题与研究的品位

因为每一个容器你要的内存、CPU 都不一样，所以它就是一个有点像背包问题：你们有没有做过那种——你是一个小偷，在博物馆里面偷了很多有价值的东西，每个东西有一个 weight、有一个 value，你怎么在包里面塞尽可能多的东西把它带走？

它的问题是我有好多容器，每个容器都有比如我要多少 CPU、要多少 mem，它有一个多维度的 specification，这就相当于一个个东西；然后你要用最小数量的背包，把这些东西全部都打包走。这是一个 NP-hard 的优化问题。你的算法做得越好，你就可以为黑心资本家省下更多的机器——省一台就是一台的钱。

所以你看，这里面有很多体现研究品位的东西。如果你在 1997、1998 年的时候说，我们要让虚拟机复活，这就是一个非常疯狂的想法，也是一个很好的想法；1998 年的时候，BSD 说我要做一个 Jail，我要在操作系统里面做出好多小操作系统可以互相不影响，这也是一个非常疯狂的想法；然后你说我要做这种声明式的 Kubernetes，我要把容器的纳管放进来，这也是一个非常疯狂的想法，而且是改变人类进程的想法。然后你也可以说，好，我可以做这个、解决这个背包问题，这也是一个不错的问题，因为如果你把背包问题解决得非常好，确实可以为资本家省下很多的钱。

但如果你无限制地停留在那里——把这个背包的问题再做好一点、再做好一点、再做好一点，然后去挑一个数——那就很快了，因为这是一个 well-motivated problem。你们可能会在比如科研实践上面读过这样的论文，叫容器编排：它说好，容器编排是一个 integer linear programming，是一个整数线性规划，然后我们对这个整数线性规划可以做 a、b、c、d、e，最后求出来，求出来以后在一个数据集上证明说，我的容器编排的效率提高了多少。

那这可能不是一个非常好的 research，因为你做的这件事情很有可能在实际当中的假设是不成立的。比如说你假设静态的，假设你一瞬间可以知道有哪些容器；但实际上你在集群里面，容器不停地都在变化，随时在扩容、在增减。因为对于我作为一个用户来说，我随时用一个命令行工具就可以把一个容器从一个数据中心挪到另一个数据中心，或者我可以做个扩容、缩容。而且有些后台的服务会动态地检查：比如如果我发现你这个容器很长时间都没有任何的活跃程度、没有任何的流量，这个黑心资本家会悄悄地把你的容器稍微压缩一下，怎么样都是有可能的。当然他也许不会告诉你，这是他的商业机密——只要你作为使用者感受不到这个区别，他就可以做这样的压缩。

就跟阿里云的那个云盘的 SSD 一样：它的存储集群报告的数据是，他们可以在存储三个副本的情况下，依然达到小于 1 的写放大。这也是一个非常离谱的事情。

所以某种程度上，我今天要告诉大家的是：其实技术也是可以改变世界的。你们也许可以不要那么在意分数，也许可以去试一试。

### 本讲提到的题目

**改造 xv6，让它支持多个 `os_id`**

拿你们的 coding agent 去改一下 xv6，把 xv6 里面所有的东西都加上一个 `os_id`，让每个对象都可以属于一个 `os_id`。默认只有一个操作系统的时候，所有人的 `os_id` 都是一样的；改完之后，在启动的时候为 `os_id = 1` 启动一份 `initramfs`，为 `os_id = 2` 也做一份 `initramfs`。

解析：

- pid 依然从同一个池子里分配——2、3、4、5、6——因为每个 pid 都知道自己的 `os_id`，所以分配本身不用改，改的是"谁看得见谁"。
- 遍历 `proc` 的时候只返回和自己 `os_id` 相同的进程，于是 `os_id = 1` 和 `os_id = 2` 各自都能有一个 `pid = 1`，两份 `initramfs` 各自都能跑起来。
- kill 这类针对具体对象的操作，要先比较 `os_id`：3 号进程能看到并杀掉 1 号（同一个 `os_id`），5 号进程看不到 3 号（不同 `os_id`），kill 就不成立。

这套"编号空间"的隔离正是正文里 namespaces 的思路：真正容器化之后，干这件事的机制就是 PID namespace，`os_id` 则成了每个对象头上那 4 个字节的标签。

## 从 API 到 Unix philosophy：操作系统课总复习
> 对应块：BLK59 | 覆盖分集：P30上 | 块标题（分集名）：《Agentic AI 和我们的未来；课程总结（上）》

今天要把这个学期学过的东西串一遍。串的起点，是我从第一节课就在说、说到你们耳朵生茧的那句废话：从应用程序的视角来看，操作系统就是一组管理硬件资源、提供应用生态支撑的 API，一组 system call。学完这门课，这句话该怎么理解？

### 操作系统是什么：应用程序的视角

你们总是在写程序。我看到的每一个人都带着笔记本电脑，不管是打开 Word、打开浏览器，还是在 VS Code 里编程、让插件帮你编译运行，这个过程中应用程序无时不刻在帮助你。不管它用什么语言写，你都可以把它想象成一个 C 语言写的程序——如果是 Python 或者 JavaScript，那些功能也可以等价地翻译成 C 代码。然后这段代码就在一个虚拟化的环境，也就是进程里运行，进程用自己的地址空间。

运行的时候，它会向操作系统发送系统调用。一个进程想干什么样的事，就会做什么样的系统调用：

- 想创建进程、想改变别的进程，就用进程管理的系统调用；
- 想在地址空间里原本非法的位置填上一块内存，就用 `mmap` 这样的申请内存的系统调用；
- 想创建线程，想在多个线程之间实现互斥与同步，也有对应的系统调用；
- 想在文件系统上留下 persistent 的痕迹，甚至有"等我的数据落盘了再继续执行"这样的功能。

> **结论**：这是计算机系统里的一条公理——凡是与应用程序开发相关、你认为合理的事情，就一定有一个办法能做到。纯粹的计算（一台图灵机就能做的事）你在进程地址空间里直接就能完成；但如果你的进程想和外面的世界打交道，比如要发射一枚导弹，这件事没有办法通过纯粹的计算在自己的状态里完成，那就必须借助操作系统。

这套概念从玩具里那个可能只会唱歌的单片机芯片，到手机、电脑，再到数据中心里的超级计算机和人工智能的推理集群，到处都有，而且它们的操作系统形态都相当类似——当然，是我讲的这种狭义的操作系统。

### Agent 操作系统：不会从裸机从零开始

现在有人说，AI 来了，我们需要一个 agent 的操作系统。什么才算是 agent 操作系统，可能我们现在还不知道；但可以知道的是：我们不应该从零开始，从一个 bare-metal、一个裸机上去构建一个新的操作系统，而应该像 Android 那样去借力。Android、iOS 是非常成功的移动操作系统，它们也不是从零在一个 ARM 处理器上构建出来的，而是借助像 Linux 这样已经很好的经典操作系统，在它之上再为应用做一层封装。

这个演化和 Unix 刚发明的时候很不一样。那时候我们总是写 C 语言的代码，直接编译成 binary，binary 直接在操作系统上执行；而现在你们更倾向于写高级语言——Python、JavaScript、Swift——它们可能会经过一层打包，也可能编译、也可能不编译，最终变成一个能在操作系统的运行时环境上运行的东西，一个虚拟机。Python 里面会有一个 bytecode，JavaScript 也可以变成各种形态，比如变成 WebAssembly，或者编译成本机的指令序列来运行。

如果让我自己概括这个学期到底讲了什么，其实就是这些：在经典操作系统之上怎么构建各种各样的应用程序。

### 硬件视角：CPU 和操作系统一起进化

还有一个视角我讲得比较少，只有一两次，其中一次是助教讲的，就是硬件视角的操作系统。这个视角说复杂也复杂：Linux 内核有上千万行代码，里面有非常多的机制，都是为了把硬件的性能发挥到极致。但换一个角度看，硬件其实也看不到操作系统。

CPU 就是一个无情的执行指令的机器。我打过一个比方：CPU 也是编译器。它会做动态的数据流分析，指令译码完了之后做依赖分析，而电路天生是并行的，所以它可以在一个周期里同时执行好几条指令。但 CPU 的特点是它不管你的指令到底是什么——只要你的指令在它看起来是合法的、有权限的、可以执行的，CPU 就会照单执行。这个指令序列完全由程序员写出来：编译出来的 firmware 代码，或者你自己写的操作系统的代码，都会编译成指令序列，只要运行时的权限合适，CPU 就直接执行它。

> **提示**：把 CPU 想象成一个人，他手上有一本手册。每来一条指令，他就去手册里找到那条指令的行为，严格核对每一条，然后把手册上那一句话执行掉。

有意思的是，CPU 是和操作系统一起进化的。最早的时候可能只有一个处理器，没有多处理器并发，没有打开那个魔鬼的盒子，也没有"多处理器从入门到放弃"的那一堆复杂东西。后来，一方面是摩尔定律可能到头了，另一方面大家确实想要能效比更高的芯片，于是有了多处理器系统、有了 GPU、有了 non-volatile memory。每当一个新的东西增加进来，操作系统也会相应地跟着一起进化。

### 复习这门课：精神内核与"确定性"

那么，你们总要回去复习考试，应该怎么复习？复习的时候，最顶层的那张提纲就是你们看到的那张图。

> **结论**：这门课真正教给大家的是一个精神的内核，不是那些具体的知识点。当然具体的知识点我会考，所以你们还是要掌握它——掌握它不算一件有坏处的事。因为你们总有一天会把短期内为了考试记住的知识忘掉，但你会留下一些印象：哦，原来操作系统还可以做这个事；原来还可以去入侵另外一个程序的地址空间。你们写 web、写应用程序的时候不会想到这件事，JavaScript 的模型里根本没有这件事可以干，但在操作系统的进程模型里，这件事就是合理的、就是应该能干的。

所以这门课的精神内核其实是：每当想到任何问题，你都可以继续追问下去。就像我刚才说"我们已经复习完了，可以下课了"，那你也可以不下课，往回走一步问：如果我要更好地复习操作系统课，有没有办法？然后去问问 AI，跟它 battle 几轮。

我一直说，上课的主要内容集中在代码的展示上。原理当然也很重要——有些事情是有来龙去脉的，最早 1970 年的时候他们是怎么想的，后来为什么就不够了，不够了之后操作系统就提供一个 API 来帮你完成这件事，然后我们有一个 code demo。所以如果你已经觉得自己比较好地掌握了课堂上那些代码的展示，理解了它们的基本原理，也理解了相关设计的系统调用和概念，那基本不用太担心考试。以前的同学给我这门课考试的评价是"还是比较有确定性的"：你确信自己理解了这些概念，上场考的时候哪怕某个细节记不住，第一，我不会考犄角旮旯里的细节；第二，你依然可以顺着 first principles 推一下你认为应该是怎么样的，只要你的理由合理，我可能也会给分。

不过，这些代码还是要理解好。我了解到有些同学到现在都没有下载过一个 coding agent 运行一下，也有一些同学从来没下载过我的代码。我课上的代码下载是稍微有一点点门槛的：作为一个懒人，你在浏览器里点进去，会发现有几个目录的文件；再点进去一个 `.c`，你会发现它是 raw 文件，字节流直接摊在你面前，甚至有些连换行都没有，根本没有办法用肉眼观看。这其实是一整个学期当中对大家一个很重要的考验——你只要在课后打开我的 slides 就能看到那个链接，点进去就会自己往后退一次；在这 10000 次后退当中你只要前进一次，就会得到一个很好的正反馈。当你某天说"我今天不打算摆烂了"，把那个链接直接丢给 coding agent，你会神奇地发现它帮你把整个目录整理好了、下载到本地，你再说一句"请你给我编译运行它吧"，它就运行起来了。在那一刻你会觉得：哦，原来这件事情没有那么难。我希望到这个时间点上所有同学都已经跨过这一步了——中间我有一次课特意展示过正确的下载课件的方法。

我真的想教给大家的是：你们总是想可以做得更好。一开始总是很难，但当你愿意跨出那一步，然后总是跨一步、总是跨一步，就会取得很大的进步。所以如果说技术上要教什么，我觉得比较重要的是一个 Unix 的 philosophy。

### Unix philosophy：操作系统不只是那一组 API

Unix 的 philosophy 是什么？我刚才说，操作系统是一组 API——Unix 里给了我们很多 API：`fork`、`execve`、`exit`、`read`、`write`，都是你们非常熟悉的。Windows 里同样提供了很多 API，比如 `GetProcess`，它是一个更符合软件工程规范的 API。但一直以来，尤其在开发者的口碑当中，Windows 的口碑都不如 Linux，我上学的时候还经常看到调侃 Microsoft、调侃 Windows 的图，虽然现在少很多了。

为什么？因为操作系统不仅仅是那一个 API，它还承载了 API 之上的应用生态。而 Unix 的应用生态和 Windows 的应用生态，在设计哲学上有一个本质区别。

#### Windows 的应用生态：一个应用解决所有问题

你想想，谈到 Windows，它上面的代表应用程序是什么？Adobe 的全家桶，Visual Studio，Microsoft 的 Office——这种离了就没法生活的生产力工具。这些工具是怎么构建出来的？这和 Windows 的设计有点一脉相承的感觉。

Windows 是一个非常好的软件工程制品——当然，是相对比较老的、可能还没有现在这些软件工程经验的那个时代的一个非常好的软件工程产品。在这样的产品之上，我们可以开发更大更好的软件工程产品。Adobe 全家桶功能非常复杂，它希望的是"我一个应用就解决你的一个问题"：你在剪辑视频、编辑图片、处理文稿的时候，再也不需要去看另外一个程序，在我这里把你所有的问题都解决。这样能最大程度地服务新手用户：新手上手的难度比较低，因为你要的东西都在手边，你一开始可以只探索其中一小部分功能，随着理解越来越深，就可以探索越来越多的功能，而且这些功能始终在手边。

#### Unix 的应用生态：让所有东西互相合作

Unix 不一样。为什么你们作为 Computer Science 的学生，一开始听说要学命令行终端的时候会恐惧？我不知道你们的恐惧感是什么时候消除的——是从发现可以打开 Claude 的时候消除的，还是某一天突然就消除了。我现在哪怕脱离 Claude，只有一个网页版的聊天工具，也不太害怕它了。但你还记得刚开始为什么害怕吗？害怕就是因为它就给你一个这个。

而 Unix 告诉你：这就是世界，这就是 open source 的全部，世界上最先进的操作系统，你有世界上所有的工具。这句话也没错——你可以用 `apt` 装所有的东西，用 `apt` 装一个 npm，然后用 npm 把自己升级起来，就得到了 JavaScript 的全部生态。但这个东西对新手是不太友好的，你必须要了解很多概念。

为什么值得付出这个代价？因为 Unix 在设计的时候有一个很重要的思想：它应用生态里的每一个东西都不是单独的，不是一个单独的应用来完成所有事情，而是希望你的任何一个应用一旦进入我的系统，它就成为这个系统的一部分，也成为所有其他应用程序的一部分。它鼓励应用程序之间的合作，而这个合作——我觉得这可能跟它拿图灵奖也有关系——就是管道这样一个非常干净的机制：它实现了进程之间的协作，并把 Unix 设计成每一个小的工具做好一件事情，然后让世界上的工具去合作，完成一件更大的事情。工具有大有小，有些其实挺大的，但都是这个思路。

到今天我自己干活也是这样，在课上展示过很多次：干很多事，最后管道给 `claude` 那个命令行工具——大语言模型成了这个管道的终点。虽然我觉得有一天从用户的角度，所有的代码都会消失，你只需要把意图告诉计算机、告诉大语言模型，它就可以用代码的方式帮你实现；但这个背后，你作为一个计算机专业的学生，还是需要非常清楚地知道这件事情带来的力量在哪里。

| 对比项 | Windows 的应用生态 | Unix 的应用生态 |
| :--- | :--- | :--- |
| 代表应用 | Adobe 全家桶、Visual Studio、Office | 一整个工具箱（`find`、`grep`、`sort` 之类） |
| 设计取向 | 一个应用解决你的一个问题 | 每个工具只做好一件事 |
| 合作方式 | 由单个应用包办全部功能 | 应用之间互相合作，靠管道串起来 |
| 对新手 | 上手难度低，要的东西都在手边 | 需要先了解很多概念，门槛高 |
| 生态气质 | 功能始终在手边 | 一旦进入系统，就成为所有其他应用的一部分 |

这两种取向其实并不矛盾：Windows 也一定可以有机制去合作，Unix 上也可以实现 monolithic app。但这是它们设计操作系统时的一个起点。

### 用一条管道收集整学期的 code demo

今天这份复习用的 slides 就是这么构建出来的。首先我已经完成了 content as code 的转化：我所有的课件全部都在一个 repo 里，而且它们也都是代码。于是我可以用一个脚本来得到所有展示过的代码案例，一步一步来：

第一步是 `find`：找一个目录，并且找这个目录里所有满足某个 pattern 的文件。比如 `find os-2026`，这样就得到了所有文件，包括那些编译出来的 Python bytecode。第二步用 `grep` 把它筛出来，我就从好多文件里找到了我想要的文件。

但为了构建一个复习提纲，这个顺序不符合我的心意——它是按某种不知道的方式排序的。从组合的角度，我希望有另外一个工具帮我排序，于是可以用 `sort -V`。这个大家不用记得，今天的答案是你去问一下 AI：告诉它有很多长成 `lecture 1`、`lecture 2`……一直到十几甚至更多的 `.py` 文件名，我希望把它们排序，你给我一个命令就行。你知道这件事是可以编程实现的，系统里也就有工具可以帮你实现。

排好序之后，再从里面用 `grep` 一行一行地找：我里面有很多代码，有 main 函数，也可能有每节课开始时的 review and comments 这种不想要的干扰项，我只想要 OS demo，于是继续筛。这样我就按顺序得到了所有展示过的代码。当然还可以往后处理，比如再做一次去重，最后把它拷贝到剪贴板——注意这也是可以用命令行工具实现的，不过是 Mac 里的命令，我准备的时候办公室那台是 Mac。把这些全部 pipe 起来，剪贴板里就有了这个学期所有的 code demo，往 slides 里一粘贴就可以了。

```text
find os-2026     找出一堆候选文件（连编译出来的 Python bytecode 也在里面）
   |
  grep ...       按 pattern 筛出想要的那些
   |
 sort -V         按 lecture 1、2、3…… 的顺序排好
   |
  grep ...       只留 OS demo，滤掉 main 函数、review and comments
   |
  去重           同一段代码出现多次的只留一份
   |
 pbcopy          拷进剪贴板（Mac 上的命令）
   |
 粘贴进 slides    整学期的 code demo 一次到位
```

读这张图要看的不是每个命令的细节，而是每一环都只做一件小事、上一环的输出直接变成下一环的输入——这就是 Unix 给我们的最大启发：世界上的东西是可以在一起合作的。当然今天的标准答案也不是这条管道，你也可以直接告诉 coding agent：请你帮我 collect 所有的 code demo，把重复的都去掉，写在这里——这也完全可以。

### 让 AI 帮你复习：敢想，并且会改 harness

你们也可以直接让 AI 试图帮你复习。我今天就现场试一下，看看会不会翻车。

今天的 coding agent，你完全是需要敢想的。AI 的能力比你想象的要强。如果你只是把它当成一个聊天的窗口，那你可以在适当的时候跳出来，给它更重的任务。当它在更重的任务上开始无法完成的时候，你就可以去改进你的 harness。比方说，如果有一个任务其实很长，你叫它直接完成，它很可能完成得不好；但只要试图把这个任务拆小就行——今天的 coding agent 其实有把任务拆小的能力，它会自己进入 plan mode，列出好几个 TODO，然后一个一个去做。但有时候它可能意识不到这一点：比如在我讲上课复习的时候，它可能一下子就跑去读好多文件，这时候它的注意力、它的 self-attention 就会分散，分散了以后可能就没有起到复习的效果。

还有一件事我发现了：我每一次上课之前都会先让 AI 帮我生成一把 slides，而 AI 和我自己好像还没有非常好的 alignment。首先它不理解我是怎么想的，所以它认为重要的东西可能我认为不那么重要，而我认为重要的部分它可能一笔带过。这种事情经常发生。

### AI 会出什么样的题

我让 AI 出了一份卷子，看看它会出什么题，正好我来检验一下——这完全是我灵机一动，事先没有准备过。它还会去做 web search。结果它出的题还挺有创意：

- 第一组是 Quick Quiz：看出这段代码有 bug 吗？如果没有，`sum` 最终一定等于 2 吗？如果把 T2 里的 lock 换成另外一个 lock，`mutex` 最终可以等于几？如果有人觉得 mutex 太麻烦，写了一个无锁版本，这个版本一定正确吗？
- 第二组是一个很有意思的 fork 例子，也是一个印象深刻的例子——你们会怀疑自己的眼睛，这到底是 6 还是 8？你的眼睛不能相信你的眼睛。这个例子我很有可能会考，但我考它的时候会考它舍的哪一部分呢？应该是 buffer。当 fork 拷贝的时候，它复制了进程所有的状态，而"所有的状态"这几个字背后有一个很深刻的内涵：不仅是你的 main 函数本身，这个 library 所有的状态也都会被复制；以及所有操作系统的对象——我持有一个操作系统的对象，那么我的 child 也应该同样地持有这个操作系统的对象。这时候就有很多设计上的考虑，比如文件描述符里面的 offset。
- 顺着这条线，它问的其实是文件描述符：两个进程同时往同一个文件里写的时候，会往哪一个文件位置去写？这个是有一个唯一答案的。如果 fork 之前加一句 `close`，然后父子各自 `open`，有什么不同？UNIX 为什么选择让 fork 继承文件描述符？这和 Everything is a file 的哲学有什么关系？
- 进程的地址空间，这几乎也是一个必考的。你肯定得知道进程的地址空间是什么、怎么去改变进程的地址空间，所以它用一个非常编程的方式问了一些这样的问题。
- 它也知道要考一个并发编程，这还挺了解我的：我每年都会考一个并发编程。你们记得那个条件变量的万能同步方法，就得到 20 分——这 20 分是送给你的。如果你写不出那个条件变量，哪怕你不会编程，把那个万能的条件变量抄一遍、背一遍，可能也有十几分，这是可以向大家保证的。偶尔有一两年，我会出一个用信号量可以做得很简单的并发编程：你可以稳妥起见，用万能的同步方法安全地拿到那 20 分；也可以相信自己的实力，写一个很聪明的并发控制。但每当我看到聪明的并发控制，我人肉就会化身成一个模型检查器，遍历你的状态空间——我可能不能绝对全部遍历，但我做过很多年并发编程的研究，大概知道在什么样的 interleaving 底下你的程序可能会错，所以你就冒着被我找到错的风险，然后我会把那个错标在上面：如果按照 1234 的顺序发生，你就会有这么一个错。当然，并发编程这一块我不会考那么细，是送分给大家的。
- 文件描述符和地址空间，期中测验的时候考过了。
- 它还出了一道很综合的题：某个同学实现了一个线程安全的链表，这里有一个明显的资源泄漏；另一个同学写了一个配对的删除函数。我觉得它挺聪明的，我还没有考过这样的题目，突然发现打开了思路。
- 还有一个文件系统，这个也是我每年会考的，考的是 crash consistency。

> **提示**：每当你在计算机系统里感到困惑，就告诉自己一句——计算机系统里是没有魔法的，奇怪的行为一定有一个原因。刚才那个 fork 的行为，都是有原因的。

它出的题里有几道确实 get 到了我的点。比如文件描述符那道，背后就是操作系统的 first principle：操作系统是一个服务者，它服务的是用户、是进程、是应用程序，所有设计都是为了应用程序能更好地发挥实力。从这个 first principle 出发，你自然能想到为什么 Unix 要做这样的设计——这也正好回应了我最开始讲的那点区别：Windows 希望一个 monolithic app 解决你所有的问题，Unix 希望世界上所有的东西都尽可能合作。

不过我不会这样出题。我出的题还是会比较严肃一点、正常一点，不会在期末考试上直接写"计算机世界里没有魔法"。至于隔壁班那种试卷，题目可能长这样：有十个任务来到系统中，第一个任务需要的时间是 5，第二个任务需要的时间是 10，然后……然后问用什么调度方法、你的平均等待时间是多少。这类题在今天，第一，它不是绝对的 nonsense——如果你去看 OSTEP 那本教科书，它讲调度的部分讲得其实挺好的（我上课没有讲，你们可以当补充材料看），而且今天系统里如果要调度，多多少少都会有短作业优先的影子在里面；但另一方面，它要求你把小学的算术题做对，算术一错这道题就没有分了，对大学生来说这非常离谱，所以我还是不应该这样考试。

### 复习方法论：模拟卷是最后的验收

同学们刚才有没有反应过来：你不应该把整整一个学期的 lecture notes 都喂进去，然后说"猜一下蒋老师可能会出什么题"。你们想想高三度过的日日夜夜，你们不是这样复习的——不是说"我们要高考了，先做一套模拟卷"。做模拟卷已经是最后的事情了，模拟卷是一个验收。

那复习高考的时候，你们的老师用的是什么策略？我那个时代用的是《五三》，我不知道你们现在用什么教辅书。《五三》给了我们一个非常有效的信号：复习的时候，你需要一定的 exhaustiveness，你需要穷尽一个 scope 里面所有的可能性。

> **结论**：你的高考经历回到今天，突然你发现，你有一个合同工牛马可以帮你无限地出题——只要你有钱，给 DeepSeek 充值就行，它的 token 还是很便宜的，算是很良心了。如果你有算力，有近乎无限的智力，你就可以让它为每一个 lecture 从每一个方面都给你出很多个可能的题目。在这个意义上，你几乎可以实现往年试卷 100% 的 coverage，然后你就发现你已经压中几乎所有的题了：除了每年最后那几个比较难的、比较 open 的题目你们压不住以外，凡是我要考你概念、考你基本概念理解得好不好的题目，全部都是可以押得中的。

这些经验不仅可以用来复习我的考试，也可以用来复习任何一门考试：把它的课件放进去，让它为每一个知识点生成一些模拟题。甚至可以跟小伙伴一起玩——你的小伙伴用不同的 prompt 生成不同的试卷，你们就能得到一套"计算机网络十套模拟卷"。你们宿舍四个人，每人弄两套，最后看谁压中了最后考试的那道题，这是一个很好的社会学实验。

总之世界变了，但你们总还是要接受考试。在接受考试的过程中，可能不要把它看成太大的负担，而是你确实在这门课里知道了很多新的知识，然后把这些知识用一个高效的方式重新回顾一下。也许在未来你走向工作岗位的那一天，你突然发现这个知识好有用：当世界已经被 web coding 的前端程序员占领的时候，你还可以说——我还学过操作系统，还知道可以去对另外一个进程干一件非法的事情。这个事情在前端的世界里没有。

### 课程回顾：从逻辑门到一个程序

那我就简单带大家 walkthrough 一下这门课到底讲了什么。注意，这个列表虽然是所有代码的 demo，但确实还有很多重要的逻辑是在 slides 里的，所以你们尽可能还是在 AI 的带领下走一遍。

这门课是从数字逻辑电路的模拟器开始的——总是从你们已有的知识开始去展开新的知识。你们在 Logisim 里接线已经接到吐血了，那就应该用一个程序化的方式来接线，用代码来接线，用代码来模拟。而我们的起点是一个管道：你可以把一个程序的输出连给另外一个程序作为输入。这是你们在操作系统课上获得动机的起点，之后我们做的所有事情，就是把这样的程序和操作系统的交互一层一层地解开。所以这也是你们在 Computer Systems 这条线上第一门课的起点。我也得到过一些反馈，说这门课让有些同学丧失了对计算机系统这条线的信心，希望能在这门课里稍微找回一点——它好像没有那么困难。

有了逻辑门，你就可以用来构造计算机系统，比如一个 RISC-V 的处理器模拟器——甚至有一个 single-header 的模拟器。你只需要定义出 CPU 里面有什么：CPU 的 state 里有比如 RISC-V 的 32 个寄存器，有一组 CSR，还有一个 memory。这就已经构成了一个基础的计算机模型，指令就可以跑起来了；指令能跑起来，我们的程序就可以跑起来。所以在复习阶段，你们重新走了数字逻辑电路和计算机系统基础这两门课里最重要的内容。

为了更好地理解操作系统，我们还要把程序稍微打开一点点。我给大家展示过一个你们编程时的噩梦——汉诺塔。对每一个初学者来说，理解这样一段程序都是很困难的，你在很长一段时间里都处于似懂非懂的状态。因为讲起来，在物理世界里你有个 n-1 的柱子，如果手里真有一个汉诺塔的模型，你就真的可以把 n-1 个抬起来放到另外一个上面，这就是那一段递归的效果；然后我再挪一个，挪完再把 n-1 个挪过去。道理上你是认同的，但从执行上，你总觉得有什么东西没有完全弄明白。

直到你看到了非递归的汉诺塔：我们可以把刚才那个大步执行的 C 程序，改写成一个这样小步执行的 C 程序。这时候我就可以明确地写出 C 语言里每一个语句精确的行为——我定义一个模型叫 Simple-C，每一条语句精确的行为是什么，这里就包括了函数的调用和函数的返回。在这个时候，你就把那些"大概搞清楚又没有完全搞清楚"的东西弄明白了：你知道每一个 stack frame 里都要有一个 PC。它有若干种等价的表达方式，但关键在于，每一个 stack frame 都必须记住一个执行的位置——它可以有一个 PC 记返回值的位置，这是你们在计算机系统基础课里学的；也可以像我这样，让每一个 stack frame 有一个"当前运行到哪里、我上面马上要运行到哪里"的、相当于一个指针的东西。

通过这个，你才真正理解了什么是一个程序：一个 Simple-C 是怎么在计算机系统上运行起来的。我甚至有一个 C 的解释器。借这个模型，你也可以知道什么是编译器、什么是编译优化：我们在状态机的意义上有这样一个 Simple-C 程序，每次执行一条简单语句；如果我有一条 `x++`，再到下一个状态又执行一条 `x++`，x 可能是全局的也可能是局部的，那我就可以把它优化成一个 `x += 2`——编译器允许把它改写成顺序执行意义上等价的东西。

但如果执行的不是 `x++`，而是一条 system call，那就是编译器不可穿过的边界。我打过一个比方：这就像你去做手术，麻醉的时候你的世界就消失了。执行 `syscall` 指令的时候，你对整个外部世界没有任何感知；等你回来的时候，你的世界变成什么样，你已经完全不知道了。而且因为控制流进入了操作系统，操作系统理论上可以对你的进程做任何改造：原来有的内存可能都没有了，原来没有的内存可能现在变得可以访问。总而言之，system call 就是优化不可穿过的边界。这样，编译优化你也理解了，操作系统的这个基本概念你也理解了。

### 进入操作系统世界：从 CPU reset 开始

有了对程序的基本理解之后，我们就进入了操作系统的世界，从最小的一个可执行文件开始。我们知道进程是有初始状态的，我们也知道计算机系统是有初始状态的：手册上明确写着 CPU reset。从这个 CPU reset 开始，我们经过 Firmware 的执行，Firmware 会加载操作系统，操作系统开始执行，然后操作系统再加载你的应用程序执行，直到 Linux 世界上第一个应用程序被加载——这时候这个世界的控制权就完整地交到了你的手里，你的程序相当于获得了整个世界的控制权。再剩下的，就又回到了前面那个模型上。

```text
CPU reset          （手册上明确定义的初始状态）
   |
   v
Firmware 执行
   |
   v
Firmware 加载操作系统
   |
   v
操作系统执行
   |
   v
加载第一个应用程序  --->  世界的控制权完整交到你的手里
```

这是我们在绪论部分构建的一个全局的操作系统概念。剩下的三个部分——Virtualization、Concurrency 和 Persistence——也都是按照这个逻辑展开的。

在 Virtualization 里，我们首先讲进程，讲程序和进程的区别。进程会构成一棵树：最开始相对操作系统来说，这是 OS 的状态；操作系统经过刚才那一长串过程之后，会走到一个只有一个 init 进程的状态；之后所有的东西都是通过 syscall 驱动操作系统到下一个状态。于是我们就构建出了一个树状的结构，这里面有很多有意思的行为，比如父亲先被杀死、或者先终止了，他的孩子会怎么样，等等等等。你需要一系列进程管理的 API 来维持这棵进程树。

```text
            父进程
           /      \
       子进程      子进程
          |
       子进程

（父子关系由进程管理的 API 建立和维护；
  父亲先终止时，树上的孩子会怎么样，是这棵树上很有意思的一类行为）
```

### 本讲提到的题目

这一讲里我现场让 AI 出了一份卷子，也顺带把几道题的考法和答案方向说了一遍。把它们记下来，正好当自测用。

**fork 之后到底输出 6 还是 8**

题干：一段带 `fork` 的代码，问你它的输出是 6 还是 8——你的眼睛不能相信你的眼睛。

解析：差别出在 buffer 上。`fork` 拷贝的时候会复制进程所有的状态，而"所有的状态"不只是你 main 函数里的那几个变量，还包括库的状态（stdio 缓冲区里可能还压着没有真正落地的输出），以及进程持有的操作系统对象。所以父子进程会各自把缓冲区里的内容再写一遍。

**父子进程同时往同一个文件里写，会写到哪个位置**

解析：这道题有唯一的答案。`fork` 会复制操作系统对象——我持有一个文件描述符，我的 child 也同样持有这个对象，父子共享同一个打开文件的位置（offset），所以两次写入是接续下去的，而不是各写各的。

**如果在 fork 之前加一句 close，父子各自 open，有什么不同**

解析：这时候父子手上是两次独立 `open` 得到的描述符，不再共享同一个打开文件的位置，写到哪里就各算各的。它和上一题正好构成一组对照。

**UNIX 为什么让 fork 继承文件描述符？这和 Everything is a file 的哲学有什么关系**

解析：回到操作系统的 first principle——操作系统是一个服务者，服务的是用户、进程、应用程序，所有设计都是为了让应用程序更好地发挥实力。Unix 希望任何一个应用一旦进入系统就成为系统的一部分，也成为所有其他应用程序的一部分，鼓励应用之间合作，而管道就是那个非常干净的机制。让 fork 继承文件描述符，就是让父进程已经建立好的东西能被 child 直接接着用。

## 抽象、Scaling Law 与 VibeOS：操作系统课的最后复盘
> 对应块：BLK60 | 覆盖分集：P30下 | 块标题（分集名）：《Agentic AI 和我们的未来；课程总结（下）》

复习到这里，进程、地址空间、文件描述符这些零碎的东西已经凑得差不多了。把它们摆在一起看，你会发现一整门操作系统课其实只围绕一个动作在转：它替应用程序把底下那堆复杂的硬件藏起来，然后把计算机的能力交出去。这一篇就把这门课从头到尾再走一遍，然后说说我为什么这么讲，以及我们正踩在一个什么样的时代上。

### 技术回顾：操作系统这座世界是怎么搭起来的

#### 进程树、地址空间与一切皆文件

进程从来不是孤零零的一个东西，它长在一棵进程树上；讲终端的时候，还会有信号这样的机制。除了能看见这棵树，每一个进程还可以改变自己的地址空间——地址空间是进程最重要的资源。我们有一个实验，就是告诉大家怎么样实现 malloc 和 free：你可以在 bare-metal 上面实现，也可以在自己的进程的地址空间里面实现。还有好几个例子，比如我一下子用 mmap 分配一片很大的内存，但暂时不使用它，之后就可以按需任意地使用它；再进一步，我甚至可以入侵别的进程的地址空间。

进程有了树状的结构、每个进程又有了自己的地址空间之后，如果想继续拓展进程的能力，就得回到那句老话：操作系统其实是给应用程序提供服务的，它希望应用程序能够最大程度地发挥计算机的功能。所以操作系统很自然地，在它的世界里面有很多的对象。

在 Unix 的设计里有一条 everything is a file——所有的东西都是文件。procfs 里面有整个进程的状态，你们做过 procfs 的实验；sysfs 里面你甚至可以控制这个系统里面的各种参数。我写过一个程序，记得那天我还带了一个显微镜，虽然那个显微镜的显示有点问题，但你可以看到我能控制树莓派上面的那个灯。所有这些，都是通过文件系统的接口把操作系统里面的对象暴露给应用程序。

那这个时候就需要一个机制，让一个应用程序能够持有操作系统里的一个对象。这个机制在 Linux 里面是文件描述符，在 Windows 里面是 handle——一个把手。我通过这个门把手，就可以操纵那样的对象。

有了文件描述符，你就可以访问操作系统里面各种各样的对象：文件，匿名或者命名的管道，等等。再加上文件描述符自身的那类像 duplicate 这样的系统调用，它就实现了 fork、execve、继承文件描述符、管道共享这些机制。我们相应地也给了大家很多使用的例子，比如 tester kit 怎样去实现一个高效的、比较方便的自动化测试。对象还可以是一个终端——TTY，Teletypewriter：输入输出设备里面有很多有趣的功能，你看到的幻灯片播放、color code 等等，都是基于终端的功能实现出来的。

#### 动态链接与那台"变速齿轮"

再往下展开的是和操作系统里面对象有关的内容：什么是可执行文件，以及动态的链接和加载。

这些机制看起来都像是一句"OK，我给你提供一个 API，这个 API 可以做这个事、可以做那个事"——就像我要实现一个游戏，你得给我一套图形的 API，能展示一张图片、展示一个纹理、刷新一个页面。但是操作系统底层的 API，多多少少都会留给我们一些可玩性的空间。

比如在动态链接和加载里就有一个机制，可以让我们提前占坑一个符号：可以在 libc、甚至在 libc 加载之前，就先加载我的一个库函数，让它把 libc 里面的一个符号给占住。open、read、malloc、free 我都可以占位；占了位以后，我就可以把这个函数的实现替换成我自己的实现。

我用它实现了一个变速齿轮。原理是：操作系统给这个进程提供的 syscall，什么 read、write，在我的进程的地址空间里面其实都是在库函数里实现的。我要调用一个 C 的 read，C 的 read 是一段代码；如果我借用动态链接和加载的机制，把这段实现换掉，就等于说我在这个操作系统上面又叠了一层我自己模拟出来的操作系统。然后这个进程就只能看到我模拟出来的这个操作系统，它的行为就可以被我管控。

```text
应用程序
   |  调用 C 库的 read() / gettimeofday() / alarm()
   v
我自己的实现（先于 libc 加载，占住同名符号）
   |  改成我想要的行为，例如缩放时间的尺度
   v
真正的操作系统内核
```

读图说明：占位与替换发生在动态链接和加载的阶段，所以这一层对应用程序完全透明；它以为自己在调 libc，其实调的是我。

变速齿轮改的是所有和时间相关的系统调用——gettimeofday、alarm——只要改变这些系统调用的行为，就改变了时间的尺度，你的应用程序表现起来就可以运行得更快。我们也给大家看了，在真正的、最 Linux 的 Linux 上面，是怎么样从零开始，从一个 init 进程和系统调用，去构建整个操作系统上面你看到的那个生态世界。

> **结论**：这是第一个、也是最主要的一个部分。virtualization 讲的就是——我们的世界是怎么样被构建出来的。

#### 把进程打开：并发与魔鬼的盒子

virtualization 讲完，我们就把进程这样的东西给"打开"了。我是一个进程树里面的一个进程，实际上它可以有好多条同时执行的执行流。这个需求对实现高性能的系统来说还是很重要的，尤其是在我的计算机系统上面有多个处理器的时候：为了更好地利用多处理器的并行执行能力，共享内存的多线程是很重要的。这样我就可以把一份数据——我一个线程算出来的数据——只用几条指令的延迟，就送给另外一个线程去使用。

但这同样也是打开了一个魔鬼的盒子。我讲了好多好多的例子，比如那种山寨的支付宝，让你的账户里面一下子出现用不完的钱，一个 data race 就能做到。然后我们怎么去实现并发控制：从 Peterson 那个协议，到实现互斥、同步，到生产者-消费者这个万能的线程同步方法。

并发这一块相比其它部分来说是比较独立的。刚好是因为，操作系统本身就是世界上最早的一个并发程序。哪怕在进程模型的时候、每一个进程还没有多线程，我这个进程是可以执行系统调用的，一执行就会跳转到操作系统内核；这时候中断到了以后，可能操作系统另一部分代码又开始执行，然后我可能还能切换到另外一个进程去执行。那这个时候，操作系统内核里的代码就变成了第一个多线程的程序。你可以想象成：每一个进程 system call 以后，内核的那一部分都是一个线程，然后它们共享操作系统的地址空间。

所以在操作系统领域里面，有了很多和并发相关的研究：怎么样去实现各种各样受控的并发，怎么样控制并发的 bug——从死锁、死锁的检查，到数据竞争、数据竞争的检查，甚至还有那种要人性命的并发 bug。

顺着这些讨论，因为你已经知道有多个并行执行的流、现在又可以控制它了，你就可以知道今天我们在数据中心里面是怎么样写并发程序，在 AI 里面是怎么样写并发程序，在高性能计算里面是写什么样的并发程序。这些就有点脱开操作系统了，但依然和操作系统非常有关联：你用的还是你在操作系统课上学到的那些最基本的概念——同步、互斥、共享内存、内存模型——去理解今天在数据中心、在 GPU 里面发生的最热的事情。

#### 设备、NVMe 与文件系统：又回到数据结构课

并发之后，还有一个很重要的、也是操作系统的功能，就是管理 I/O 设备。我是从一个 LED 灯、从写一个核弹发射器的设备驱动程序开始讲的。

一个设备驱动程序要做的事，就是把设备接进操作系统：设备有好多寄存器，有 status，有 data，然后你可以控制它；把这样一个设备的接口放到操作系统里面，对 Linux 来说就是一个 struct file_operations。everything is a file，所以你能把任何一个设备实现成一个文件的接口，它就可以接入到我们的文件系统里面。我们写过这样的设备驱动程序，有这样的灯，有磁盘，有 webcam。

在这个基础上，我们构建了持久化的存储设备：NVMe 的 SSD。我讲了一个 bit 怎么存储，也给大家看过一些老旧的老旧的设备，包括那个印着存盘按钮吉祥物的软盘。

到了 persistence 这一层，我们的操作系统课又变成了一门数据结构课。还记得最后讲文件系统的时候，我的视角又变成了：你现在有一个 block device，它是按块访问的，每次读写就是一整块。那你就需要在这个上面实现一个数据结构。数据结构里面有很多有意思的经典思路，比如 append-only——我可以用 append-only 的方式，加上 random-read，去实现任何一种数据结构，而且我甚至可以用这种方式来实现 crash safety。这里面有一些技巧、有一些实现的细节，你们可能需要花一点时间去了解一下。

而因为文件系统本身遵循操作系统这一套 API 的规范，所以这个文件系统也可以是虚拟出来的：只要它能够满足这个文件和目录的 API，我完全可以像 OverlayFS 一样把一层一层一层的系统给叠起来；我也可以像 FUSE 一样，完全写一个自己的文件系统的驱动。还记得我有一个 galgamefs——我可以在文件系统当中创建一部分，这个文件系统里面的文件是我虚拟出来的，但它依然遵循文件的规范，这样我就可以在文件系统里面玩 galgame 了。当然还有一个例子，是我用符号链接构建了一个 galgame。

#### 抽象才是 systems 的关键字

基本上这就是我的这一门课讲的所有技术性的问题。然后回过头来，操作系统讲 systems，里面有一个关键字，你有一个感受，那就是抽象。

操作系统世界底下的硬件是非常复杂的，但是当你有了一个好的抽象以后，应用程序只要看到 system calls，就不用看到这个硬件的复杂性——或者说，在绝大部分时候都不需要看到了。硬件的复杂性并没有消失，像 ioctl 这样的接口依然是非常复杂的，它没有消失；但是我们可以在绝大部分时候都工作在一个非常干净的模型上。程序员开发者的心智就降低了，大语言模型开发的心智也降低了，那 bug 就减少了，你就可以去开发出更好的软件。

```text
应用程序 / 大语言模型
        |  system calls
        v
  各种抽象层（存储设备、文件系统、并发编程模型）
        |  ioctl 这一类依然复杂的接口
        v
      硬件
```

读图说明：每一层都在屏蔽底下非常复杂的东西，同时希望把底下的能力尽可能地暴露给上面去使用。

你看它中间的各个部分——存储设备的抽象、文件系统的抽象、并发程序编程模型的抽象——每一层都是"我要屏蔽底下非常复杂的东西，并且我希望把底下的能力尽可能暴露给上面"这一件事。这个主题在操作系统里面不断地、不断地重复。这就是我们所说的 systems。

但如果你是 top-down 地说"哎，我们要做一个什么样的抽象"，其实这是不对的。我们永远是从应用程序的需求出发。程序员会犯错的——讲讲 concurrency 的时候，程序员一定会犯错——所以我们才要怎么样做一个更好的并发编程的模型，使我们能够很容易地写并发程序。你看到了我们讲的 CUDA，讲的这种 Go 里面的并发模型，这些都是一层一层长出来的抽象。

> **提示**：如果你能顺下来，把这里面的技术性的内容理解得比较好了，那你完全就可以去考试了，不用担心。

### 一个不断变化的时代：从深蓝到 Chinchilla

而更重要的，可能是我在这门课上面想要传达的一个 philosophy：你们其实活在一个一直变化的时代里面。

这也是我上课讲过的例子。讲 scaling law 的时候——那是一个 off-topic 的 lecture，你们可能不太记得了——我讲了加里·卡斯帕罗夫被深蓝击败：1997 年 Deep Blue 击败了他。大家看到的是一个 scaling law：大概从 1985 年开始，随着算力的增长，计算机下象棋的 rating 就在稳步往上走，你看这是一条非常非常稳步的曲线，它几乎是跟摩尔定律一起往上涨的。当然在后来他们当时要做深蓝的时候，投入了大量的资源，所以算法也有一定的进步；再加上它是硬件的下棋电路加上超级计算机，所以有一个比较大的台阶向上，然后就击败了人类的世界冠军。

再到后来，我们有了 AlphaGo、有了 Monte Carlo tree search、有了深度神经网络以后，它就把人类打得……我不知道你们有没有同学业余会喜欢下一些象棋，现在这个象棋的 AI 已经统治了业余的互联网象棋了。这样的故事在不断地发生。

还有一张是存储设备的 scaling law（那张图黑了，有点可惜）。你说随着我们时间的增长，大家会预测总有一天，我们的 storage device 也是一个指数的 scale，它能够存下互联网上所有的内容。所以 Google 就不是偶然的，这也是一个 scaling law。然后 Intel 和 NVIDIA 更不是偶然的：Intel 1968 年，摩尔定律；然后再到这个 NVIDIA。

每当一个新的应用需求出现的时候——哪怕像下棋，纯粹就是一个兴趣，大家觉得我们能不能挑战一下下象棋这个很难的事情，我们能不能让 CPU 变得更好——每当这样的指数级的 scaling 出现的时候，就意味着可能我们的世界，或者至少是一个领域，要发生一次翻天覆地的变化。当 CPU 的这个 scaling 你觉得不够的时候，就有了 GPU 的算力；当大家发现 GPU 可以用来做人工智能的时候，上面就有了 GPU 的 AI Ops 的 scaling。注意，那是一个对数的坐标：你看起来它是一条直线，你觉得没有感觉，但这是一个指数级的增长，这是一件多么可怕的事情。

还有 Chinchilla paper 里面的 scaling law。你知道的是大语言模型可以 scale，但这里有很多有意思的观察：大语言模型的参数量，和训练用的最佳 token 量之间的那个比值，不是几万、几百、几千，而是可能几十。也就是说，这个大语言模型应该是几乎记住了训练数据——理想情况下，它应该能够记住训练数据里面几乎所有的东西。这才是比较理想的一个收敛的位置。

这些都不是偶然的。所以可能我在上课的时候，更多的是希望大家通过一些例子，从课堂上面这些操作系统里面具体的知识——进程、文件、文件描述符——能看到一些这种思考问题的 first principles。这个世界上本质上是有规律的，虽然可能我们每一个人都没有办法很好地理解所有的规律。我尽可能希望向大家传递一个 message：你们也许可以在学习的过程中，慢慢有一天就体会到——哦，原来这个世界是有规律的，你可以在一个萌芽的时候，通过 first principles、从一些好的想法，看到未来会发生什么。

### 从需求出发：把操作系统和 Git 都重新设计一遍

在操作系统课里面，我真正教会大家的是从需求出发去解构问题。我们讲操作系统的时候，其实讲的是应用程序；操作系统归根结底还是为应用程序服务的。那我们问的问题就是：应用程序到底想要什么？操作系统想要怎么给？然后操作系统给了这个东西以后，还有没有什么其他的用法？

你回头带着这个想法再去想一遍我上课时候的那些案例，会发现确实：操作系统里面的每一个 API、每一个机制，都是从这样的应用程序的需求出发的。所以你其实只要记得应用程序要有什么、该有什么，这个其实不需要很大的 memory 就能记住；记住完了以后，你剩下都是可以通过推理的方式得到的。比如如果我应用需要加载一个二进制文件，我又知道它的地址空间是这样，那我就希望我的可执行文件是一个数据结构——那这个数据结构里应该有什么呢？你自己就可以一点一点、一点一点地把今天这个进程地址空间里面该有的东西、和 ELF 文件里面该有的东西给推导出来。比如说我再给你一个提示：我希望实现动态的链接和加载，在这个应用需求的驱动下，你就可以知道未来的操作系统会发生什么。

所以你们真正训练的，不是去记住好多好多的操作系统里面的 facts，而是你能把操作系统记得是那几个最重要的 key ideas，然后剩下的东西你可以自己把它还原、推导出来。这个过程你们可以自己要在家里多做几遍：我知道比如说我上课的时候讲过一个机制，你先想这个机制它的出发点是什么；那接下来你会把这个东西 redesign 一遍，如果是让你来设计，我会设计成什么样；回过头来你再看一下操作系统的设计者是怎么设计的，做一个对照，然后纠正你自己的 chain-of-thought。这就有点像那个大模型——你打开 DeepSeek 深度思考模式，你就可以看它不断地向后吐那个思考的过程，有点像你自己有一个这样的思考过程。然后你在这个时代当中，慢慢地你就会发现，你可以去想一想我们现在在哪里，我们的几个 scale 未来会发生什么，你就会有了一些有意思的全新的发现。

再举一个例子。我在面试的时候会问他们：什么是 Git？如果你想回答这个问题，你不需要去记忆当中搜索那个里面所有细碎的、你用过的那些 Git 命令；你应该想的是，Git 到底是用来干嘛的？它到底解决一个什么样的问题？

它解决的问题就是：第一，我们有好多开发者，每个开发者都要在本地开发；第二，开发者和开发者之间还要同步。那多版本的管理，这个问题应该怎么做？

怎么做呢，它有几个最重要的观察：它是一个管理文件系统快照的数据结构。Git 相比于 SVN——SVN 里面存储的是 diff，听起来很高效对吧？但是你如果想要去下载某一个版本，那你就惨了：你就得从某一个快照版本开始不停地打 patch、打 patch、打 patch，打到这个时间点，你才终于知道我现在的版本是什么，而且版本的后退等等都非常的复杂。所以 Git 就做了一个决定：我就是管文件系统快照的数据结构。它很简单：它有 tree of blobs，它有好多文件系统的树，然后提交和提交之间自然而然地形成一个 commit 的有向无环图。在这个数据结构上，你就把它变成了一个数据结构问题，就可以非常自然地从需求推导出像 branch、stash、worktree 这样的东西。

如果让你自己设计一个 agent 好用的 Git，你自己就能发明这个 worktree。你自己发明过一次，你就不会忘记它了；之后你就算忘了，在下一次你想到这个需求的时候，你还可以再发明一遍。这就相当于是把这个东西真正地理解了。

> **结论**：只要有概念，你就不需要去做那种无意义的肌肉记忆。

但是从另外一个角度，可能你也很难在不肌肉记忆的情况下去形成理解。所以，比如说在 AI 的时代到底应该怎么样训练自己，你们对自己的要求在哪里，可能这个就需要每一个同学自己去掌握了。因为每一个同学都可以直接用 AI 来完成作业，那你选择逃课换自己的自由时间，还是选择对自己狠一点、去学一些更多的知识，这就是每一个同学自己的选择。因为我觉得，你到考试上你就很慌，因为你这一整个学期都是 AI 帮你写的作业。有一个笑话说，现在老师用 AI 出题，学生用 AI 写作业，然后唯一没有得到训练的实际上是学生。我不知道大家怎么看这个现象，但是我希望大家依然觉得：既然你在这样的一个变化的时代里，也许你是可以做一些不一样的事情，所以你还是想要 push 自己去学习。

### 三个维度上的 scaling：AGI 为什么迟早会来

那是过去。未来会发生什么呢？我一直有一个观点：大学和人类其实都很危险。因为大语言模型的 scaling law 是真实存在的——这是去年老黄在发布会上的那张图。

我们的语言模型可以在 pre-training time 上 scale，也就是说在预训练阶段，你有更多的数据、更好的书。所以据说这个 Anthropic 干了一件很坏的事：它买了很多的绝版书，然后把绝版书作为语料去训练它的基模，然后再把这个书烧了。这样就没有人、没有竞争对手可以得到同样好的语料，它的基模就做不过它。在预训练阶段可以 scale；然后更好的预训练模型，在后训练阶段又可以有一个更好的提高。

这有点像什么呢？你们上高中的时候就是预训练，然后你们上了大学以后就会往一个方向去微调。你们的每一个高中生，毕业的时候你都是一个对每一个学科都有一些浅浅的认识，同时又有很好的学习动机——或者可能没有很好的学习动机，但我觉得至少你们高中毕业来到大学的时候，应该都是充满向往的，因为你终于自由了，终于从一个非常困难的境地里面解放了出来。解放出来以后，OK，那你应该可以做一件大事，这时你进入了后训练的阶段。

那像 Anthropic 是怎么在代码上取得成功的呢？就是因为它很早就发现，代码是一个有非常强的监督学习反馈信号的东西。也就是说，如果你不能判定你做得好不好，你就很难自我监督去学习；但一旦你有一把尺子、有一个人，老师来了——这个老师来了你只要做得不好他就揍你，做得好他就奖励你——你慢慢地就能做得更好。其实你就能学到这个老师的 pattern；你学到这个老师的 pattern，实际上不是你的智力就提高了。他发现，在有反馈信号、有明确的反馈信号的地方，就可以把基础模型的能力再提高。所以相当于这个 pre-training 的 scaling 是 GPT-4 这个时代大家发现的，post-training 的时候就是 GPT 的 o1、然后到这个 Anthropic 的模型发现的。

但是还没完，还有 test-time scaling。o1 你可以通过给它选一个这个 reasoning efforts，它就可以不停地：它做完了以后还可以再检查一遍，还可以再检查一遍，还可以再检查一遍。你们在中学的时候其实学过这个技能：做完一个题以后马上快速地回看一下有没有明显的错误，没有就再继续。这就是 chain-of-thought 的 reasoning。但实际上 test-time scaling 的上限，我们其实还没有摸到。

今天一开始的时候我给大家展示过一个 test-time scaling 的例子：我让 AI 给我出一套期末考试题，它给我出了一套。但如果我只要换一个 prompt，我就可以让 AI 为我的每一个知识点出一个期末考试题——我先让 AI 列举出操作系统里面的 100 个知识点，然后我再让 AI 帮我写一个脚本，基于 for each 每一个知识点，都调用一个 Claude API 出一个考试题，用同样的 prompt。这就 test-time scale 了。

然后当你做不出来这个数学题的时候，你可以这样想：你这个题做不出来，但不要紧，你有一本地球上所有人做过的数学题的合集，然后你可以让 AI 写一个程序去枚举这个题集里面的每一个题和它的解答，因为每个题集里面是有解答的。然后你就给 AI 一个 prompt 说：我现在有这道题不会做，你试一试，用这个题和它的题解的思路能不能解决这道题。然后你会发现，这个世界上根本就没有新题。你们想一想你们在高三的时候做那个比较难的数学题，去看那个数学题解析的时候，这个世界上是没有新题的。

| 维度 | 在哪个阶段生效 | 关键机制 | 代表 |
| :--- | :--- | :--- | :--- |
| pre-training scaling | 预训练 | 更多的数据、更好的书，把基模做大 | GPT-4 时代大家发现的 |
| post-training scaling | 后训练 | 在反馈信号明确的地方继续提高能力 | GPT 的 o1，Anthropic 的模型 |
| test-time scaling | 推理与使用 | 反复检查、反复重试，用算力换正确率 | o1 的 reasoning efforts；为每个知识点各出一套题 |

> **结论**：这就意味着 test-time scaling 只要你有算力，它的上限就是近乎无限的。所以我看到至少这一点，我看到了：这 AGI 迟早要来的。

### 如果 AGI 来了，你的位置在哪里

那下一个问题就是：如果 AGI 要来了，你们怎么办？你再聪明，你能有这个 Claude 聪明吗？

所以我一直以来有一个 vision，而且这个 vision 随着我对 AGI 越来越相信，我觉得越来越迫近：老登们以他们的方式去统治的大学、或者统治的社会，会进入一个不平衡的状态。因为比如说，如果给你配一个 agent——配上一个有这个 test-time scale 的、智能无限的 agent——然后再抚平你和老登之间的信息差，那么就意味着你在任何一个方面都可以做得比老登更好。因为你会用 agent，他不会用。他没办法享受这个 AGI 的 test-time scaling，可能那个产品还没有出来。所以你可以找到他说的每一句话里面的错误、漏洞，然后你可以反驳他。

我不知道会发生什么，但是我觉得一定的是：我前面说可能你们的数字逻辑电路课摧毁了你们对 computer systems 的信心，但我觉得总有一天，这种坐牢式的、服从性的教学会在 scaling law 底下崩塌。因为以前——比如我从读书的时候是怎么觉醒的呢？我就是去看网上的公开课，去看哦，原来 MIT 的这个人可以上课上得这么好，然后我就觉醒了。

而你们在未来可能不需要这样，因为我们有 AGI。它可以帮助你找到最适合你的那个教学的方法，然后你不需要去用低效的、服从性考试的方式去接受知识。世界也会发生非常大的变化——你们的工作、生活、交互的方式。在过去的一年里面，我们看到了太多我觉得极为惊艳的产品，比如 Google 的 Genie 3，如果你去看一下，它可以实时地生成场景。这件事情它的 demo 已经做出来了，而 demo 做出来就意味着，一定有一天这个技术路线上没有本质的困难。

### VibeOS：第一个完全由幻觉构成的操作系统

毕竟我还是操作系统课，所以我想给大家看一个有意思的操作系统。这是一段现场演示，说法大概是这样的：

> 我今天要给你们看的东西可能相当有里程碑意义，所以我需要先把它放进一个稍微带点历史感的语境里面。人类之旅走了很远——石器、语言、文化、数学、计算，这些东西都相当不错，但我不认为我们已经真正到达了作为一个物种所能到达的顶点……我知道你们大概都在想："哦，他是不是要重新发明整个软件行业？我们还没准备好。"我知道你们最近要消化的变化已经够多了：我们从人类写代码的世界，搬到了一个 AI 写代码的世界，我知道这对某些人来说可能已经挺了不起了；但对一个真正的远见者来说，我已经在想下一步了，而且事实上我已经在那里了。所以我要介绍一个全新的操作系统，它会改变我们工作的一切方式——VibeOS，世界上第一个完全由幻觉构成的操作系统。

它真的是一套操作系统，可以启动：这是一个 1.3 GB 左右的 VHDX 文件，本来还可以做得更小，我没费那个劲。我可以在裸机上启动它，但我不打算那么干，我在 Hyper-V 里面启动。你会看到它启动得又快又好、非常高效；启动起来以后，你会看到一个漂亮的用户界面，让用户非常高效地工作。

先跑几个内置的经典应用：Notepad、Calculator、Internet Explorer。独特的地方在于，这些应用里面一行代码都没有——没有按钮，没有事件处理器，也没有任何说明该做什么的逻辑，但应用是能用的。做一个 5 / 3 然后按等号，答案是 1.6。所以它是能用的，对吧？可我没有写任何代码，AI 也没有写：没有任何 AI 写的代码。它只是纯粹地产出 UI，背后什么都没有。

Internet Explorer 这里，和今天你在用的那些无聊的操作系统不一样，它解决了人们的一个大问题：人们上网的时候总是在想，这到底是不是 AI？但是在 VibeOS 里面你没有这个问题，因为答案永远是"是"——一切都是 AI。去 google.com 搜一下 Hanselman 的维基百科页面，不需要提醒你也知道，你看到的所有内容都是完全幻觉出来的，直接从模型里面出来，UI 在跟着实时更新。

而且它不限于这些内置应用。搜任何你想要的应用，它都会为你现场创建出来。比如经典应用 Encarta 98，但内容全是关于 Mark Russinovich 的——"Russinovich 有把内部机制变成民间传说的天赋"。还有些应用你本来会想要，但正常来说太难做出来，比如 command.exe，但它永远对你很粗鲁；跑一下 bash，它会说一句"bash: you've somehow offended"，你懂这个意思了。

现场还有人接着点单：Microsoft Money 95——"文明在 Microsoft Money 95 达到巅峰"，于是就有了 Scott 的账户；Paint 里面画一幅 Scott；能不能嵌套操作系统，能套多少层，能不能模拟一个 Altair 8080？可以，那需要一个 shush 到 Altair 的终端模拟器；还能把 iOS 模拟器放进去，用的是你会在一台 iPhone 上看到的那种 Windows CE 按钮，非常"合法"。这些背后跑的是 Copilot SDK。

> **提示**：VibeOS 的意义不在于它真能当日常系统用，而在于它展示的那件事——所有的一切都是 AI 生成的幻觉，没有一行代码，但它看起来可以 work，而它底下是一个世界模型。

所以未来会是什么样呢，就是完全取决于大家的想象力。从我最开始说要复习的时候，这就不是一个常规的复习课，而是我直接把一个 URL 丢进去了。然后操作系统课的结束，是一个 World's first 100% hallucinated operating system。

### 绝版的真人操作系统课

时代其实已经开始结束了。然后你们在这门课里面学到的知识，我不知道有没有用、会不会带到未来有用，但是你们至少看到了一个不一样的未来，然后你们可能会愿意在这个未来里面去找到一个自己的位置。可能我在这样的未来里面也有一个这样的思考。

所以恭喜大家上到了一门绝版的真人操作系统课。我从明年开始就没有这个 physical 的了——因为本来一直以来我的操作系统课都是一个非法的状态：你们是共享的课程号，但是是不同的考试题。这件事情本身在这个学校的系统里面是非法操作，所以总有一个合法化的机会，我把操作系统课还给课程组。但同时我会试着——因为你已经看到 VibeOS 了——让这个课永生，而且能够 keep up-to-date。我希望的是，我做的第一步就是我的所有 content 现在都是 code 了，也许不是 code 也可以，然后我就可以持续地更新它，把它变成一个 public and open source 的东西。也许是你们每一个人喜欢它是什么样，你就可以让 AI 把它变成什么样。

下学期我会开一门新课。本来应该叫 vibe coding 的，但是大家觉得 vibe coding 这个很快就过时了，所以还是给它一个更正式的名字，所以我取了一个叫 Generative Software Engineering。讲的话，我预计应该会用一个一线的国产的模型，就全部都是国产的模型，然后带大家去实现各种你一开始可能会觉得很疯狂、但等你实现出来之后发现你确实不需要多少 prompt 的有趣东西。

最后说一点和考试有关、也和考试无关的话。你们最终过来听我上复习课，还是想着考试的时候可以多一点分数的，我非常理解；你们想要得到一张保研的船票，然后得到保研船票以后，下一张就是一个进入大厂的船票，或者进入公务员系统的一个船票。但这些船票其实可能只是一个起点。

因为我们一直以来都有一个感觉：只要你比别人不错一点，就能赢得这个游戏——你只要保证有更多的人在你的后面垫背，你就可以赢得这个游戏。但这个游戏，突然有一天你就会被放到这个社会上：突然间你就没有"把别人干掉就没问题"这回事了，你不再安全。因为你看到这个 AI 的 pre-train time scaling，然后到 post-train time scaling，然后到 test-time scaling，它在以指数级的能力在增长；模型在变强，三个维度上都在 scale；摩尔定律还在生效，GPU、TPU、NPU 还在生产。

> **结论**：在这样的一个、今天版本的答案里面，我希望你们每一个同学都可以去想一想，你们最终在这个时代里面会找到一个什么样的位置。未必你就一定要成为一个算法哥，去做 AI infra；也许你自己的兴趣就是另外一个可能很人文的领域。但我觉得你们每个人都可以去追求一下自己的梦想，因为我觉得知识可能总是有边界的，但是你们的梦想其实是可以没有边界的。
