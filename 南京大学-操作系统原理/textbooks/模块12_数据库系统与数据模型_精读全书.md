## 一切应用数据都是数据结构：从文件系统到关系数据库
> 对应块：BLK53 | 覆盖分集：P27上 | 块标题（分集名）：《数据库系统（上）》

### 一切应用的数据都是数据结构

上一讲把文件系统的实现讲完了。文件系统是磁盘上的一个数据结构，所以如果数据结构课的内容掌握得足够好，这里其实没有新东西：我们要做的无非是一棵目录树——如果是 Unix 的文件系统，那就是一张目录图，用一个图的方式来存这个数据结构。虽然块设备上你按块访问，内存里按字节访问，但这两者没有本质区别。那一讲还捎带了两个只在 persistence 里才会出现的话题：文件系统的 crash consistency 和应用程序的 crash consistency。它们要解决的是同一个问题——数据结构随时可能消失、线程随时可能消失，你要保证重启之后它能 recover 到一个正确的状态：丢掉最近几次操作可以接受，但整个数据结构不能 corrupt。

顺着这个往下走：既然已经有了一个能用的文件系统实现，哪怕是 FAT，哪怕是 ext4，我们能拿它做什么？文件系统是用来保存数据的，保存的是应用程序的数据。这里有一个我觉得挺有意思的观点：我们嘴上说“我要访问那个 .pptx”“我要打开那个作业 .docx”，但真正访问这些文件的不是我们，是应用程序。你和计算机的交互说到底只有键盘、鼠标和屏幕，接管你键鼠输入、往屏幕某个区域输出的都是应用程序。哪怕我只是想 `cat` 一下，那也是一个应用程序用 `open`、`read` 这些系统调用完成了文件访问。这也是上一讲说应用程序的 crash consistency 同样重要的原因——文件系统是一致的，但应用会有 data loss，对应用的使用者来说一样难以接受。

用文件和目录管理应用数据，我们其实一直在这么做：pptx、docx、电影、你们的 OS Labs，都跑在文件系统那套目录树 API 上。今天要问的是：有没有更好的办法？如果你的应用程序要服务一万人、十万人、一百万人——从我的课程网站，到服务整个学校的教务网站，再到服务全世界的应用——你需要什么样的 persist data 的方法？这就是今天的主题：数据库系统。

#### 从教务系统的界面说起

先说什么是应用程序。这是我比较喜欢的一个我自己的观点：软件是物理世界的过程在信息世界里的一个投影。这个投影通常是有损的，因为计算机世界里能保存的信息有限，你很难把自己的感情、身边围绕你的那些 contacts 都带进软件当中。软件是一台相对来说还是比较无情的机器——虽然今天有 AI 了，你也可以在一定程度上把感情带进使用应用的过程当中。但对传统系统来说，软件天生就有要把数据 persist 的需求：你自己的个人信息，业务系统里的各种订单、支付记录、维护记录，等等。

本质上，所有应用程序在管理数据的时候，都是数据结构的增删改查。我打开南大的教务系统，扫码登录，我看到的界面会和你们看到的稍微有点不一样。这是一个非常典型的应用程序：它以 HTTP server 的方式在后台运行，就跟你们做 Lab 的时候一样。当我访问一个 URL，URL 比较小看不到，但请求一旦过去，你可以想象成任何一个网站——都像你们那个 CGI-BIN 一样，底下有一个应用程序，然后这个应用程序会启动一个进程（如果是服务全世界人的服务，它可能是一个很轻量级的协程或者别的东西，但总是一段代码），这段代码最后给你一些数据，数据回到我本地：是 HTML、CSS 就渲染出来变成一个界面，只是一个数据（比如 JSON）就被网页上面的 JavaScript 收到，再去改变信息。

在这个系统里我可以编辑教学班、编辑周历，所有这些操作都是数据库、或者说数据结构的增删改查。比如系统里有一条 record 叫“操作系统课”，它有一些 metadata，比如怎么考试；考核方式我是不能改的，这个比较危险——万一不小心改错了，最后排考试的时候系统没有排我，然后突然大家说那就不考了，你们就不用考了，所以我鼠标移过去会变成禁止符号。但授课类型这些可以改，你们的选课列表我也有权限打开，不过我不能打开看，打开就会暴露你们的个人隐私，我会看到你们的电话号码（你们应该也能在系统里看到我的电话号码）。这是一个很大的数据结构，有点像文件系统，增删改查。

而且有些你传统意义上不觉得它是一个数据结构的东西，它其实也是一个数据结构。一个典型的例子就是你们的 PowerPoint 文档。

#### 一个 pptx 也是一棵可以改的目录树

有没有同学以 zip 的方式解开过一个 PowerPoint 文档？这个很有用：别人给你的 .docx 或者 .pptx 里面有很多图片，你想把这个图片的原图一把头都导出来，那你可以干什么呢？我这里有一个下载来的离散数学课的 slides，LibreOffice 也能正常打开它——它讲的是命题逻辑，里面有一张图，是 Russell 的 famous quote。然后我可以直接干这样一件事，直接 unzip 它，一条命令：

```bash
unzip discrete-math-slides.pptx
cd ppt/media
ls image*.png
```

它是合法的。虽然我用 `file` 查看的时候它被识别成了 PowerPoint，但实际上它同时也是一个合法的 zip archive。解开以后你就看到里面有一些这样的文件，`ppt` 下的 `media` 下的 `image`，所以我可以 `cd ppt`，看到一些图片，然后把它的所有 png 都打出来——刚才那张图就在这儿，后面还有一些其他的图片，就是你们的 slides。

所以本质上说 pptx 它也是一个数据结构，而这个数据结构本质上是一个 XML：它有一个 OpenXML Formats 下的 Office document，有一套 specification，遵从 ISO/IEC 29500。这背后有点历史：以前的 doc 是一个不开放的标准，像欧盟这些方面就给微软施加压力，说如果你这个标准不公开，就可以在政府层面上禁用你，最后就促成了微软说还不如我自己做一个开放的标准，让大家来遵循我，于是就有了这一套文档标准。这个数据结构描述的是比如幻灯片里面的页，然后每一页里面的每一个东西在哪里、它是怎么保存的。

我甚至可以干这件事情：打开一个 coding agent，把刚才那个中文的离散数学 slides 交给它，给它一点耐心还是可以成功的，幻灯片的标题就变成了英文，每一页的标题都变成了英文。这完全是文本的修改，你完全可以做这个 hack。你还可以看到这里有 slide layouts，还有 layout masters、slide master，也就是幻灯片的母版。你在 PowerPoint 里面看到的所有东西，实际上都是这样一个结构化的数据结构的描述——一棵树，然后它都是文本，你都可以改。

这也是比如今天 Anthropic 官方的 docx 或者 pptx 的 skill 所做的事情，它就是去解析这个文件。解析这个文件我一直不认为是一个非常非常好的想法，因为你看到它的格式并不是非常的规整，也许我们需要一个更好的查询语言来改变它。实际上是有的，有那种像 COM 的 API，可以去改变这个 PowerPoint 文件。

所以结论是：所有应用程序的数据都是数据结构，所谓应用程序想要改变这些数据，都是数据结构的增删改查。因此实现应用数据 persistence 的本质，就是实现数据结构的 persistence。而实现数据结构的 persistence，有两个典型的方法。

### 办法一：用文件和目录把数据结构摊平

第一个方法就是使用文件和目录，因为 Unix 已经给了你一个 everything is a file 的接口。

如果要实现一个教务系统，我就会这样设计：为每一个同学我都可以建一个目录；在我的教务 app 底下，有我的课程号——比如操作系统课的课程号，代表某一次开课的信息；然后如果有一个同学选课，我就建一个目录叫 enrollment，001 号、002 号、003 号同学每一个放一个 markdown。刚才你们看到我在教务系统里可以编辑教学周历、编辑考核信息，这些东西都可以存在我的一个目录里面，比如一个 metadata.json，或者 syllabus 里面的 markdown，还有我的教科书是什么，也可以这样。

```text
app/
|-- OS2026/                    <- course id: one offering
|   |-- metadata.json          <- exam type, teaching type
|   |-- syllabus/
|   |   `-- syllabus.md        <- weekly calendar, textbook
|   `-- enrollment/
|       |-- 001.md             <- one enrolled student
|       |-- 002.md
|       `-- 003.md
```

读图：一门开课就是一个目录，目录里既有描述这门课本身的文件，也有一个 enrollment 子目录，每个选课的同学在里面占一个文件，所有信息都摊平成普通文件。

#### 目录树、符号链接与 agent 友好

这样存有一点什么好呢？你所有的东西都是平的，你 Unix 世界里面所有的工具都可以用。不仅仅是 find、grep 这些工具可以用，你的 agent 也可以用 Unix 世界里面的所有工具来编辑它——变成目录的结构其实是一个非常 agent-friendly 的方式。

我下学期会开一门叫生成式软件工程的课，其实就是 vibe coding。第一次课的作业我已经想好了：让你们做一个 deep research，给你们今年软件工程相关大会的论文，我找 100 篇，让你一个星期把它们全读完，然后告诉我哪些 paper，你来预测一下哪些 paper 可以得 best paper，为什么。在它 release 之前，我会找一些 preprint 状态的 paper，让你预测这个谁能得 best paper，为什么。而且你必须要搭建一个自己的 agent harness。这是一个很好的 practice，就是你可以把所有东西丢到文件系统里面。

像我自己就是：我的文件系统里面有我自己的各种 paper。如果我今天看到一个 paper 觉得我要读它，我不会再像一两年以前那样打开它读，而是直接往目录里面一丢——一个 iCloud 的云端同步目录——后台就会把那个文件捡走，一页一页逐页地 OCR 变成文本，然后把图和表也都给读出来；读完以后再由另外一个更强的模型去 review 它，给我不同粒度的摘要。最细的粒度其实就是这个向量（向量数据库就是干这件事的），这个向量可以帮助我找到和它相关的 paper；此外还有短一点的、中等一点的、长一点的文本性摘要。这样就形成了文件系统里面的一个数据库系统，而它就是一个数据结构——由好多 structured paper 组成的数据结构。但它实际上所有的数据都是以文件的方式访问的，这样不仅我可以很容易地看它改它，agent 也可以很容易地看它和改它。这是一个非常大的优势，因为我们可以借用操作系统里面的各种各样的机制，比如说符号链接。

符号链接其实是一个引用。这学期我的所有选课列表里面，每一个选课的都对应一位同学，我就可以不再是复制一份，而是直接用一个符号链接指向那个同学的目录：比如 231220001 这位同学选了我的课，我就在选课列表里放一个符号链接指向他的目录。这样那位同学的姓名、手机号码这些信息我就全部都有了，而且我没有再复制一份。如果有一天他更新了他的 email 或者手机号码，因为这是一个指向那个同学目录的符号链接，那么它同步地在我这里更新也会反映过来。

所以完全可以用目录来存储任何的数据结构。就像刚才看到的 docx、pptx 一样：虽然它存的时候是一个文件（因为如果不是一个文件的话，它拷来拷去很麻烦），但是它在解包以后，在内存里面它就是一个目录树，这个目录树里面每一页幻灯片都有一个 .xml，每一个图片都是单独的一个文件。这就是我们要的数据结构。

这个好处就是 tool-friendly 和 agent-friendly，它很好用，所以它非常适合小规模的系统：我不在意我要服务多少人，只要我的算力还够就行。一个典型的例子就是你们的课程网站。

#### 课程网站：一个跑在目录树上的真实系统

你们的课程网站就遵循了 Unix philosophy：你们所有的提交都在我一个目录底下，如果我现在删库的话，你们的提交就都没了。

你们在 `make submit` 的时候会设置几个环境变量，一个是 `course`，一个是 `module`。`course` 用来找这一层目录，`module` 用来找这一层目录。如果你刻意地改掉，比如 `course=OS2027`，我就给你一个 error message 说找不到——这个找不到实际上是因为我在 pathlib 试图打开那个目录的时候找不到这个目录，于是我就告诉你，你给我的那个 course 或者 module 是不合法的。然后是你们的学号；你每创建同一个提交的时候，都会在这里留下一个压缩包，这就是你们那个 upload 的压缩包。

压缩包放进来以后，我有另外一个监听程序，那个监听程序会不断地去找：如果你有一个压缩包但是它没有一个 result，我就会找到这样的文件，然后送去给 online judge 跑。我的 online judge 是我在办公室里面的一台台式机，它跑完以后就会把这个点 result 存进来。

```text
submissions/
`-- <course>/<module>/<student-id>/
    |-- submit-<n>.zip        <- uploaded by make submit
    `-- submit-<n>.result     <- written back by the online judge
```

读图：一次提交由两个文件配对表示——压缩包是待判的输入，`.result` 是判完的产出；监听程序要找的就是“有前者、没有后者”的那些目录。

那我要统计 M5 有多少份 accepted 的提交，就可以这么干：

```bash
grep accepted M5/*.result | wc -l
```

把 M5 下所有的 result 都打出来，grep 出 accepted，然后数它有多少行，我就知道了 M5 现在一共有 154 份提交是 accepted。当然一个同学可能会有多份提交，但我总有办法——我可以写一个稍微长一点的脚本，去算出来有多少个同学通过了这题。这所有这一切我都不需要知道任何 system，而且我可以让 agent 来帮我做这件事情。这就是文件系统的好处：它是一个公共的接口，agent 用得很溜，我自己用得也不错。

如果我想 rejudge 也更容易了：我只要找到所有 M5 里面满足我条件的，要 rejudge 这位同学的这次提交，就把那个 result 删了；如果我想 rejudge 所有的提交，我就把 M5 下面所有的点 result 都删了。然后我的 OJ 就知道它该去捡那些还没有 result 的文件。

这完全没有问题。第一，阿里云的机器还是非常可靠的；第二，就算是偶尔丢了一两个点 result，对同学来说也不是毁灭性的损失——你们发现 `make submit` 成功了，回头刷新刷新刷新，刷了 5 分钟，你那个提交都没有进入 pending 的状态，你自己会觉得有点不对，你会再提交一次的，那可能那个时候服务器重启了或者怎么样。退一万步讲，就算因为 crash consistency 的 recovery 让有些文件丢掉了，对大家也不是一个影响非常大的事情。而且阿里云的那个云 SSD 的服务还算是比较可靠，云计算的服务也比较可靠，我预期一年也不会因为意外重启一次，所以这完全可以在可接受的范围内。

#### 摊平的代价

当然也不是没有代价的，代价有两个。

第一个是 crash consistency 的粒度。文件系统本身有 crash consistency，但是当我想在这个“数据库”里维护这个数据结构的时候，尤其是当我有 multiple write 的时候，问题就来了。打比方，我希望把一位同学的选修课名单整个导入到这个系统的时候，我其实就涉及到好多文件的写，而文件系统本身是不支持这个多文件写的 atomicity 的：我现在要把名单导入，我要写 100 个文件，然后可能写到第 50 个文件的时候这个系统 crash 了，那这时候我的数据结构其实就进入了一个不一致的状态。我需要要么手工写一个 fsck，要么就像 Git 那样有一个 append-only 的机制。总之，你想要在文件系统上面实现一个 crash consistent 的 application，是很有挑战性的一个问题。

不是做不到。比如其实我们的文件系统的 `rename` 是支持原子性的，所以很多时候你可以用创建同一个目录、然后原子地把这个东西 rename 过去，这样来实现 atomicity。

第二个代价就是性能会稍微差一点。因为你每一次想要读写东西，都会经过文件系统的系统调用，所以它就有比如路径的检查，然后有 metadata 的 fetch；而 metadata 它还会有一些其实你维护数据结构不需要维护的那些信息，比如你本来就不需要维护这个 modification time。像我的 OJ，我的 OJ 那个时间是写在那个文件名里的，我不用操作系统的这个 modification time，但是操作系统依然会为每一个文件去维护它的 modification time。那就浪费了一些时间，浪费了一些空间，浪费了一些资源，然后就会带来一些这种隐藏的读写的放大，这种 cost。

当然，像比如说我这种小规模的系统，我不 care 这个 cost 的时候，或者说 online judge 为了跑一次你们的提交的 cost 远远大于我在文件系统上面付出的这个 cost 的时候，这件事情对我来说就是可以接受的。那我愿意接受它，我就可以在很快的时间里面把东西做出来，尤其是我有时候经常要 hotfix 一些问题的时候，会选这样的架构。我觉得这还是很好的，因为这是 agent 时代的一个标准答案。

### 办法二：在文件之上再造一个数据结构

如果你觉得刚才那样的方式性能有点不够，你不想付出任何额外的开销，那我们还可以这么干：我们可以在文件上面构建一个数据结构。

本质上，文件它就是一个 byte array。那我们的磁盘是不是也是一个 byte array 啊？我们的磁盘是 byte array，然后我们做了一个虚拟化——磁盘的虚拟化：我把磁盘上面放了一个数据结构，有可能是 FAT、文件分配表的那种数据结构，也可能是 Unix FS 那种基于 inode 的树和图的数据结构；但总归是我在磁盘上面存了一个数据结构，然后使得我在这里面可以有一个 a.txt 这样的 byte array，我可以随机地读写它。

既然我可以做这个抽象，通过一个数据结构把 byte array 抽象成好多好多散的东西，那我是不是也可以在一个 byte array 上面再做一个抽象，把它变成任何一个其他的数据结构呢？也可以的。你就这样想：你的 ELF 文件不就是一个数据结构吗？有一个 header，然后有 program headers，然后一个一个 `PT_LOAD` 的 section，然后还有什么符号表这种东西，它一段一段，然后都是指针指来指去，到处指来指去，relocation 指针指来指去。它就是一个数据结构。一个文件就是一个数据结构。

所以如果你想要实现一个教务系统，我就好像在我的文件上面实现一个文件系统一样：我一个 `struct super_block` 放在我的文件的头上，就像 ELF 的 header 一样。它有两个部分组成，一个是 students，好多好多的 `struct student`；还有好多好多的 course。那所谓的实现一个教务系统，无非也就是增删改查：往学生的链表里面加一个学生，往课程链表里面加一个课程，往 enrollment——或者学生里面有个数据结构是他选的所有课的一个链表——再在链表链表链表链过去。

#### 把文件映射到固定地址，指针就能落盘

那我们能不能干这样一个 hack 呢？虽然这个 byte array 是存储在磁盘上的、是一个 persistent 的文件，但是如果我每一次都把这个文件 mmap 到一个固定的地址上，那我是不是就可以直接在这个里面存指针了？

你看：比如说我的 super block，我如果永远把这个 super block 都映射到 `0x100000` 这个地方，如果我的这个东西是 32 个字节，那我的第一个学生就放在这儿，这个第一个学生的地址就是 `0x100020`。如果我有一个比如说 super block 里的 `struct student *pointer`，这个 pointer 的值不就是这个 `0x100020` 吗？它就相当于有一个指针指着这个学生。然后我可以把这个数据结构直接 mmap 到内存里，因为我每次都是加载到同一个内存地址的，我每次直接写进去不就可以了吗？

```text
file (persistent byte array)        fixed virtual address
+--------------------------+        +--------------------------+
| super_block  (32 bytes)  | mmap-> | 0x100000  super_block    |
|   head = 0x100020        |        | 0x100020  struct student |
|   count                  |        | 0x100040  struct student |
|   write-ahead log        |        | 0x100060  struct course  |
| students / courses ...   |        | ...                      |
+--------------------------+        +--------------------------+
```

读图：文件里的字节每次都被映射到同一段虚拟地址，于是“文件内的偏移”就等价于“指针的值”，指针可以直接写进文件，跨进程重启依然有效。

答案是真的可以的。我给大家做了这个 demo：一个 mmap 的数据结构。当然我把它映射到了另外的一个地址，应该是能够错开所有的东西的。你看我就是这样一个 super block——甚至我一会儿会讲，我还有一个 write-ahead log，就是有一个实现 crash consistency 的 log，直接就把 log 放在 super block 里，这也是完全可以的。

那想要怎么实现数据结构，就是怎么实现数据结构。比如说我有一个学生的链表——我只实现了学生——就是一个链表；然后这个链表还有一个 free 的空闲链表，用来分配。插入一个学生，代码完全就是你们在数据结构课上面学的代码：

```c
/* 从空闲链表分配一个节点，头插进学生链表 */
student_t *s = allocate();          /* 在这个文件里分配内存 */
s->next = superblock->head;
superblock->head = s;
superblock->count++;
```

只不过还是有个 hack 的：在我打开这个所谓的数据库的时候，我做了一个 mmap，直接把这个文件映射到地址空间的固定位置。我必须要保证的是每一次我映射的时候，它都是固定的位置，不然我就需要去 patch 里面所有的指针。我也可以每一次打开这个数据库以后，把这个 base 地址存下来，然后下次打开的时候再把这个 base 地址给减掉、再加上我那个新的 base 地址——理论上也可以把这个数据库映射到不同的地方。但是映射到同一个地方的时候我就不用改，这个数据库很大我也不要紧，就不用改它了。

#### 演示：一个能重启的教务数据库

现在是什么也没有的，然后我可以启动这个教务系统。这个界面比较简陋，就像你们大一的时候学 C++ 做过的那种大作业。但是理论上说，你看，如果这个东西是一个 CGI-BIN，是一个被 HTTP 调用的 CGI 程序，你退回到比如说 1990 年，你真的可以用它来挣一笔大钱：这就是一个真正的数据库系统，而且这个数据库系统是可以用的。你可以做个信息系统，你也许就是中国的网易、中国第一个新浪，你就可以挣很多钱。

比如我现在有两个学生，1 和 2。好，然后我可以退出。退出以后，我就会在文件系统里面留下一个 database 的文件——比如你看到我的名字其实就在这儿的，XYZ 也在那个二进制文件里。然后我可以再次打开它，注意我的学生还是在的：刚才我虽然这个进程结束了，但是我的文件中的数据完整地被 persist 下来了。这个时候当然如果我做一个 sync，那所有的数据落到磁盘上，那么就算内存里面所有的信息都摧毁了，我在 restart 以后我的系统依然是有这个文件的。

所以这就是把数据结构直接 mmap 到内存，直接去 persist 甚至所有的指针。这个想法还挺有趣的，但它其实隐藏了很多的坑。

#### mmap 的三个坑：msync、fdatasync 与 madvise

理论上你是可以用这样的 mmap 方式直接去实现真正的数据结构的，但是如果是在 production 里面真的要实现一个性能非常高的数据结构，你会遇到更多更多的坑。

第一个坑：你 mmap 一个文件的 region，你把这个磁盘上的数据搬到内存里，你对内存的修改不会立即反映到磁盘上。你这样想嘛，它是内存，所以内存的访问速度是非常快的，甚至你的数据写到这个 L1 cache 里面，它都不会立即送到 DRAM 的内存里面去。它都在 cache 里面是热的，你反复读写读写读写。如果你可以不断地读写这段内存，而如果操作系统希望把这个页面上的数据和磁盘上的数据保持同步的话，它就会在存储芯片上面造成大量的写入操作，这就相当于是一个无限大倍的写放大。你刚才看到，如果我要更新一个数据结构，我 `do_add` 的时候会频繁地做内存的写入；而我的应用程序不知道、或者操作系统也不知道应用程序想要把哪一部分数据 persist、想要哪一部分其实数据丢了也没有关系。所以 mmap 一个读写的文件，它在默认情况下是不 writeback 的：你所有的内存数据就那么写到内存里，然后如果丢了它就丢了。

所以如果你希望你的写入的数据要进入磁盘的话，你就需要 `msync` 这个系统调用。`msync` 是 synchronize a file with a memory map，它有三个参数：地址、长度和 flags。如果你写了这一段，你就要告诉操作系统说：我这一段内存写了，请你把它写回到磁盘上。

这个写回和 `fdatasync` 是不一样的：它只是告诉操作系统说我这段内存改了、你需要把它同步到磁盘上，而不是说等到这段内存写入磁盘以后再返回，它不是 `fdatasync`。所以你用了 `msync` 以后还需要一个额外的 `fdatasync`。它不保证、和 crash consistency 没有任何的关系；如果你希望实现有 crash consistency 的写，你还需要有额外的 `fdatasync`。

而且你还需要一个 `madvise` 的系统调用。它是 give advice about memory，它可以告诉你这段内存应该用什么样的方式来管理，对性能来说是比较好的。这甚至不是 POSIX 的 API，是有些系统里面，比如说 BSD 里面有，后来 Linux 里面也有了。你越来越看不懂它：normal、random、sequential 等等，它的行为就越来越复杂。操作系统既想要提供一个透明的抽象，说好，这是一个 memory mapped file，你只要随便读写就可以；但是当你需要写回的时候，你又想要控制它的写回策略。这个时候就引入了很多的复杂性。所以这可能并不是一个实现数据库真正非常好的 API。

#### 一个最小可用的 write-ahead log

前面说，我在刚才那个内存的数据结构里面实现了一个 write-ahead log。我的 super block 是这样设计的：开头是一个 32 位的 Magic，就是“教务DB”四个字符，表明这是教务 DB；接下来是一个 `write-ahead log:` 的前缀，冒号后面就是 write-ahead log 的内容。

这个实现不是 100% 的正确，我稍微偷了一点懒：我在 super block 里面放了一个大小为 1 的 log entry。每当我执行任何操作的时候，比如说我在这儿执行 `add jyy`，我会首先把这个字符串写到这个 log 里面，然后用 `msync` 把它写回磁盘，再 `fdatasync` 确保它落盘。那落盘以后，这个命令就被 persist 下来了。然后我再去更新这个实际的数据结构；更新完了以后，并且我确定这个东西落盘以后，我就可以把这个日志再清空，我就不需要 replay 它了。然后我就完成了一次事务的提交。

```text
commit order of one transaction
  1. write the operation (e.g. add jyy) into the log entry
  2. msync + fdatasync          -> the command is now persistent
  3. update the real data structure (linked list, ...)
  4. make sure the data structure reached the disk
  5. clear the log entry        -> transaction committed

crash recovery
  if the log entry is non-empty, replay it through the same execute()
```

读图：日志先于数据落盘，所以崩溃之后只要日志还在，就能把没做完的那一步重放出来；数据结构落盘之后日志才清空，所以也不会重复生效。

这里没有任何的优化。如果要优化的话，像我们 Minix 里面的 journaling block device，它会收到很多个 transaction 的请求，然后把它打包成一个，一起写到 log 里面，然后它会继续往后写、往后写、往后写。但我们没有，我们这个实现非常简单，就把我要做的、还没有落盘的 ongoing 的操作写进来。

我甚至可以看这样一件事：我可以直接 hack 这个教务 DB——我故意留了 WAL 冒号后面的位置，可以让我写我的命令。所以我直接进入 replace mode，比如说写 `add 99 叉叉叉`，就是一个 99 号叉叉叉的同学。我可以用像 ext4 那样的 checksum 来确保我的这个部分是合法的，我就不写这个 checksum 了，因为我编不出那个 checksum 了。

然后我再进入这个教务系统：因为我的 log 里面有这一条，它会用一模一样的代码——上来就会做一个 write-ahead log replay。所有的命令的入口都是 `execute`：我 add 一个什么人、删除一个什么人，都是从这个入口进来的。write-ahead log replay 以后，它就添加了一个 99 号同学。好，那这个 99 号的同学现在就真的有了。然后我再去看，write-ahead log 又被清空了——它 replay 完了以后，这个 write-ahead log 就可以清空了。

这里是一个 slot 的 log；但理论上你可以做一个多 slot 的 write-ahead log，你就可以做任意复杂的 write-ahead log。所以没有什么复杂的：你基本上可以在磁盘上面实现任何的数据结构，因为这个数据结构的实现真的和你数据结构课上面的那个是一模一样的。你实现一个 allocator——只是这个 allocator 比较特别，是要在这个地方分配内存的，它的 metadata 也应该是在这个地方的——有一个 allocator，然后以及一个 write-ahead log，就这些。

顺着这个思路，很自然会有下一个想法：刚才那个数据结构已经在内存里了，那我们有没有可能以后我们的程序，整个程序的内存都能 persist 到磁盘上？就相当于我的整个操作系统里面所有进程的内存，都是以 mmap 的形式映射到磁盘的。这样不就永远不会在 crash 以后丢失了吗？对我们来说，我们已经太过于习惯于我们的内存是 volatile memory：volatile memory 意味着你拔线拔电，你所有 ongoing 的东西都没有了。比如说我现在这个 session，文件可能是在临时目录里面的，然后我现在程序运行的状态，我屏幕上面的这些字符、解析出来的东西，全部都是在内存里的；这些内存里的东西意味着它在我的系统 restart 以后、或者断电以后就永远丢失了。但如果我们把程序的状态也 persist 到磁盘上，我们就得到了一个叫 single-level storage、single-level store 的操作系统。如果底下是一个非易失的 persistent memory 的话，这件事情就是可以办到的。你看，就是有一些这种疯狂的小 idea，然后你把这些 idea 不断地往实际当中去做，你就可以做出真正有用、甚至是有影响力的东西——这是 SOSP'21 的一篇 paper。

### 关系型数据库的野心

保存的是应用的数据，它就是一个数据结构，这个观点很重要。当然你要实现好它，你必须要利用好比如说磁盘访问的性能，要知道它的性能模型是什么，然后你要知道操作系统给你提供了怎么样的 API，能够让你在内存和存储之间完成同步等等。这些是原理性的东西；在这个原理上，你就可以发明各种各样有用的东西了。而我们的第一个发明，就是关系型的数据库。

这时你的需求就不再是刚才说的那个“教务系统里面一个支持 persistency、有 crash recovery、能管理学生和选课的小程序”了，你的野心就变得更大了。你能实现一个线性表，你凭什么不能实现一个更好、非常非常好的数据结构？

#### 好用、够快、永不丢数据

第一，它能够处理几乎任意类型的数据。所有的应用来了，不管是什么类型的应用来了，我都能够为你提供服务。

第二，这个软件对于任何人来说，甚至是没有经受过计算机编程训练的人来说，一定程度上他都可以上手。比如说以前就专门有一个职位叫做 DBA，database administrator，他可能不需要那么多的编程背景，但他只要能够操作数据库。比如说今天工程师过来说你的数据发生什么问题了，行，我马上写点什么就把你的数据给修了；或者你做了一个什么样的配置。对任何人来说都比较好上手。

而且，它有极致的性能：全校同学一起选课，系统是不能崩溃的；全世界的人都在发微信聊天，这个微信必须要能够扛得住。这才是它真正的野心——好用、极致的好用、极致的性能、crash consistency，你永远不会丢数据。除非是磁盘坏了：对单机的数据库来说，如果你的磁盘坏了，那它肯定是没有办法的；但是如果你的磁盘没有坏，你的系统在任何时候断电了再重启，你的数据都是正确的。

这当然不是一件很容易的事。如果你要实现一个又好用、性能又好的东西，你的数据结构必须是要支持 multi-write 的。比如说同学在选课的时候批量导入这个同学的选课信息，教务经常会干这个事；比如说我要批量导入成绩的时候，我可以提交一个 Excel 表格到这个系统，然后这个系统会解析我 Excel 表格里面每一个同学的分数，然后最后一下子把你们的分数给登上去。它想要避免的就是：我的分数登到一半的时候，一半的同学看到分数，一半同学没有看到——即便你的系统随时都可能会 crash。甚至在分布式的场景下，它都希望你的系统哪怕那个机器比如说有三份副本，哪怕有一份或者两份的数据就没有了、机器就物理地损坏了，你的数据库依然可以正确地提供服务，并且逐渐回到这个三副本的模式，实现一个分布式的一致的数据库。

所以这就是一个非常非常好用的数据结构。如果你能够设计出来，你就应该能得图灵奖——实际上也是的，就是设计这个人就得了图灵奖。他告诉大家：同时满足这些需求的东西是真的存在的，而且这个东西比你想象的可能要简单一点。

#### 指针不是好抽象，二维表才是

回过头来想，我们是怎么实现数据结构的？一个 student，然后 student 有一个 `struct student next`；然后如果我想要选一门课，它就希望是把一个学生和一门课给关联起来。再往后想，实际上关联两个对象之间的关系，就是这个世界的全部。我们人和人之间、事和事之间有各种各样的关系：你是属于这个班的，这个班是属于这个学校的，然后我们现在是属于这个教室的。当我们用来描述这个状态的时候，这个世界上有很多的 entities——有桌子、椅子、教室——然后加上所有的关系，你就可以用它来表达我们世界上面的所有的东西。

而在数据结构实现的时候，我们是怎么实现关系的呢？我们是用 pointer。我们会说我有一个 `struct enrollment`，然后这个 enrollment 有一个 `struct student *` 指向一个学生，然后一个 `struct course *` 指向一门课程。这是你在内存里面实现数据结构的时候一个非常本能的反应。但是 pointer 不是在做 database 的时候一个非常好的抽象。在数据结构课的概念里面，你们都是用指针，一个 node 的 left、right；但如果你想要把现实中的各种各样的东西放到一个统一的抽象框架里，那这个东西是什么呢？

答案是一个非常简单的东西：二维表。你就相当于是一个 Excel 的表格，这样你就好理解了。

| 表 | 一行是一条记录 | 列 |
| :--- | :--- | :--- |
| 学生 | 世界上面有概念的一个 entity | 学号、姓名 |
| 课程 | 世界上面有概念的一个 entity | 课号、课程名 |

学生有学号（一号、二号）和姓名，课程也有课号（一号、二号、三号）和课程名。这就是你们的一条一条的记录，每一条原始的记录在世界上面有概念的一个 entity。

有趣的地方在于：如果你想要实现选课，应该怎么办？这时候就比较麻烦，因为一个学生可能会选好多课，一门课可能有好多人选。所以如果你在实现 data structure 的时候，一般来讲一个很直接的可以做的是：在 `struct student` 里面有一个 list of course enrollment；或者反过来，在 `struct course` 里面有一个 enrollment list，里面是 student 的 ID。但这样的话，它就变成了程序的一部分——变成了一个 ad hoc 的、你自己实现的 data structure。

而这个抽象有意思的地方在什么呢？我们可以再在 Excel 里面添一张表：选课表。这张表里面每一行代表的就是一次选课，也就是“某个学生和某门课之间的一条关系”——每一行配一个选课 ID（一二三，编号本身并不重要）。到这一步，关系本身就从程序里面的指针变成了表里面的一行数据：原本要靠代码维护的关联，现在也成了可以被统一查询、统一修改的数据。

## 从关系代数到向量数据库
> 对应块：BLK54 | 覆盖分集：P27下 | 块标题（分集名）：《数据库系统（下）》

### 用一张选课表把学生和课程接起来

先看一个最朴素的问题。要让一个学生带上他选的课，最顺手的写法是什么？要么把课程塞进学生的结构里，要么把学生塞进课程的结构里，放一个 list 进去。这两种写法都要求你在一个数据结构里面再复合一个数据结构，写起来麻烦，改起来更麻烦。

换一个思路：不复合，而是另起一张表，用学号和课程号把两边关联起来。表里一行就是一条记录，比如「3 号学生选了 4 号课」「3 号学生选了 5 号课」「6 号学生选了 1 号课」。一个数据结构里复合另一个数据结构的需求，就这么被拆掉了。

这就是关系模型的起点。E. F. Codd 那篇拿了图灵奖的论文 *A Relational Model of Data for Large Shared Data Banks* 里说得很清楚：

> Future users of large data banks must be protected from having to know how the data is organized in the machine.

你只需要在概念层次上描述数据，就可以在上面建出任何你想要的数据系统。

### join：笛卡尔积加一个条件，把大部分东西筛掉

关系模型里真正让人眼前一亮的是它回答「怎么查询」的方式。

假设我开一门操作系统课，课号是 4，我想知道这门课的选课列表，怎么办？他给的答案在数学上非常有趣：把这里的每一个对象和那里的每一个对象做一个 cartesian product，也就是做一个乘法。第一个学生配第一个课程、第一个学生配第二个课程……全都乘一遍。这个操作在数据库里叫 join。

赤裸裸地乘一遍听着就低效，所以 join 还要带一个条件。把它写成循环就是这个样子：

```python
for s in students:
    for c in courses:
        for e in enrollment:
            if e.student_id == s.student_id and e.course_id == c.course_id:
                yield (s, c, e)
```

这一个条件就把绝大部分组合都筛掉了。因为 `student_id` 是唯一的、`course_id` 在那张表里也是唯一的，所以对选课表里的任意一行记录来说，只可能有一个学生满足条件、只可能有一个课程满足条件。于是这一行只会被展开成「3 号学生 + 4 号课程 + 这条记录」，学生的 3 号和课程的 4 号就这么被关联起来。

> **提示**：从实现一个 in-memory data structure 的角度看，这绝对是舍近求远——你绝不会想为了取一条选课记录去写三重循环。但关系模型的价值恰恰在这里：如果做数据库的人能把这个东西做得非常高效，那么你哪怕写一个 50 层循环的嵌套，它也能高效地给你算出来。这就是值得拿图灵奖的抽象。

支撑这个抽象的信念是：一个选课系统里只有三种最小的事实——学生、课程、选课。理论上说，你可以用这三种最小的事实，把你想要的任何其他事实推导出来。有了这三种事实，剩下的就是做数据库的人花十几年时间，做出我们今天能用的各种各样的数据库。

具体到 SQL，一条查询长这样：

```sql
SELECT courses.title
FROM student
JOIN take_courses ON student.id = take_courses.student_id
JOIN courses      ON take_courses.class_id = courses.class_id
WHERE student.name LIKE '张%';
```

join 就是 cartesian product，两次 join 分别踩在 `student.id` 和 `courses.class_id` 这两个 key 上。再往下，过滤条件可以随便加：可以只要名字以「张」开头的学生，可以只要这门课成绩还没录入的记录，可以只挑出成绩不及格的。基于一份已经分解到不能再分解的事实，你可以用这样的程序算出任何想要的东西——这就是它的表达能力。

### 关系模型给的三样东西：好用、通用、够快

数据库在这里做的是一整套抽象：你只负责建表（想建多少张都行）、写查询，剩下的归它。

**第一，它好用。** 它能处理任意类型的数据查询，足够通用——笛卡尔积这个能力本身就非常强。

**第二，它的性能其实可以非常好。** 看起来是个三重循环，但因为 `student.id` 和 `course_id` 都是唯一的，它们是 primary key。既然是 key，就可以建索引直接查找。于是执行这条查询时，你只需要遍历选课表：拿一个 3 去学生索引里找，拿一个 4 去课程索引里找，找出 s3 和 c4，拼起来就是一个结果，两重循环直接被消灭掉了。

**第三，持久化是可执行的**，这是数据库系统的设计实现者给你的保证。

除了查询，写操作也一样。`SELECT` 是查询，`INSERT INTO` 是往表里插数据，`UPDATE` 同样是一种查询。合起来，这就是一门很小的 domain-specific 语言——专门用来管理数据的编程语言。

### transaction：一把大锁保平安，但还要抵抗线程消失

数据库系统给你的是 ACID。A 是 atomicity 原子性，C 是 consistency 一致性，I 是 isolation 隔离性，D 是 durability 持久性。在这门课的语境里，真正要盯住的是两条：

| 性质 | 要求 | 对照 |
| :--- | :--- | :--- |
| serializability 可串行化 | 无论有多少个并发的事务，有的是读有的是写，最终都能把它们排成一个全局顺序 1、2、3、4……好像 1 执行完再执行 2，2 执行完再执行 3，没有 weak memory model 那种行为 | 一种 strong serializability |
| strong crash consistency | 系统随时 crash 都不会造成任何数据丢失，而且支持任意长的 multi-write | 文件系统总是不一致的 |

第二点值得多说一句。我们在实现那个山寨支付宝的时候讨论过：判断「钱够不够」再决定减不减，如果有两个线程同时去判断，那就糟糕了。并发场景下你们的答案是上一把锁。但在 database 的场景里没这么简单，因为除了并发，它还要抵抗另一种错误——**你的线程随时有可能消失**。

你要在一个人的账号里扣 100 块、在另一个人的账号里加 100 块。这是两次 load、两次 store：先把自己的余额读出来，减 100 写回去；再把对方的余额读出来，加 100 写回去。如果两个线程这么干，或者中途线程没了，麻烦就来了。

数据库为此提供了 transaction。在一个 transaction 里你可以写任何代码，任何 Turing-complete 的计算，甚至可以 sleep；这个 transaction 可以任意长，无限长。

```text
BEGIN
    read  userA.balance
    if userA.balance < m: ABORT          -- 钱不够，直接放弃
    write userA.balance - m
    write userB.balance + m
    ...更多计算，比如发现有内鬼，再 ABORT
COMMIT
```

它的语义是：`BEGIN` 之后你随时可以 `ABORT`，一旦 abort，前面那些「看起来已经执行了」的操作全部消失。只有到 `COMMIT` 的那一刻，所有过去执行的操作才立即生效，而且是 all or nothing——要么全部生效，要么完全不生效。

> **易错点**：这里的「原子」不是单条指令的原子，而是跨越成千上万条 load/store、可能持续任意长时间的一整段计算。线程可能在第 9999 步消失，而它之前的 9998 步对别人是不可见的。

真正体现实现能力的是：这些 transaction 还要跑得**快**。它的用法看起来就像一把大锁保平安——`transaction begin` 和 `transaction commit`，它从来没有让你去建什么 stack per slab 那种细粒度的锁，只有一个 begin、一个 commit。可它的性能却可能远远优于你自己细粒度加锁：你有一百个、一千个线程往同一张表里插入，它都能并行写入，后台用 append-only 的 LSM tree 之类的东西、或者高性能并发数据结构替你兜底，崩溃恢复还完全自动。你看到的是一把大锁，性能反而更好。

这也是商用数据库相比文件系统一直以来最大的优势：文件系统总是不一致的。二十年前的程序员从来没有受过 crash consistency 的教育，却要在文件系统之上构建 persistent 的数据结构，那天然就非常困难。数据库说：你只要交给我，所有事情都能搞定。

### 两阶段封锁：直观，但会死锁

并发控制是这里面最有难度的部分之一。每一个请求都会读写数据库的不同部分——你的数据库可能有几百张表，有的请求激活这一部分、读了这些地方、往那里写一个值；有的请求读另外一些部分、往别处写值。而为了 crash consistency，你还要应对这种情况：一个线程写了 x=1 之后就 crash 了，永远回不来，永远不提交；另一个线程写了 y，等了非常非常长的时间，才写 x=2，再 commit。这时候两个写可能是冲突的，你只能让一个人提交。

第一种方法叫 two-phase locking。想法非常直观：我想读 x 就上它的读锁，我想写 x 就上它的写锁，一边读写一边加锁。

```text
T1: lock(x)  read x   write x=1   lock(y)  read y   write y=2   commit
T2: lock(y)  read y   write y=1   lock(x)  read x   write x=2   commit
                     ↑ 两组加锁顺序相反，互相等对方手里的锁
```

我会按行、按 column、按分块去加锁，粒度可以很细。如果两个事务读写的是表里互不相干的部分，它们分别上锁、互不冲突，就能一起提交。

但这里故意埋了一个坑：`x=1, y=2` 和 `y=1, x=2`，这就是一个非常典型的 A-B、B-A 死锁。

> **易错点**：在操作系统里，这种情况是可以用 lock ordering 禁止的——你的 lockdep 会报错，内核里这么写代码就禁止你运行，你必须把它 fix 掉。数据库不行。因为数据库的查询是**别人写的**，甚至业务逻辑本身就是先写 A 再写 B，而另一个业务逻辑先写 B 再写 A。这些逻辑里包含图灵完备的计算，算出结果之后再去写某张表里的某个值，没有办法统一规定顺序。

所以数据库一般都会带一个 deadlock detector。它维护一张图，跟 lockdep 一样，检查有没有 A 到 B、B 到 A 最后连成一个圈。一旦成圈就破圈：挑一个 transaction（比如 T2），让它 abort、回滚，它做过的事情全部作废、从头再来一次，剩下那个 T1 就可以继续，直到 commit。

这里面还有无穷的复杂度：回滚到什么程度？怎么回滚？正因为如此，在 1980 年代实现一个好的 database system，对当时的程序世界是一个巨大的冲击。

### 多版本并发控制：像 git 一样开分支再 merge

第二个想法更现代，也更容易讲清楚。在任何时刻，你的数据结构都有一个快照，也就是当前所有数据的状态。

当作 transaction begin 的时候，你就想象自己已经把现在的一切都 `git add`、`git commit` 过了，当前状态是 OK 的。然后我直接 checkout 一个新的 branch——相当于把这个世界复制了一份，我就在这个世界上面改。

```text
main  o----------------------------------------o------>  已提交的世界
       \                                        ^
        \ transaction begin                     | merge: 无冲突则提交
         +--o-- T1: read x, write x=1 ----------+
         |
         \ transaction begin
          +--o-- T2: read y, write y=2 ---------x------>  与 T1 写同一行 -> 冲突，事务被摧毁
```

图里主线就是数据库当前已提交的状态；每个 transaction 从主线拉出一条自己的分支，在自己的那份拷贝上读写；结束时再试图 merge 回主线。

读，我永远读我自己的这个世界，别人怎么改都跟我没关系；写，我也直接写进我的世界，不会对 main 分支造成任何修改。如果同时有多个并发线程在做 transaction，没问题，每个都 checkout 出一条新分支，各自做各自的。

做完之后，它试图对 main 发起一个 merge。如果 T1 改了这一行、T2 改了另一行，merge 的时候没有 conflict——本质上这类似一份 write-ahead log，把操作 replay 一遍就行，两个都能提交。但如果两个分支写的是同一行、写的是不同的值，那对不起，其中一个分支就会被摧毁。所以它叫 multi-version。

> **提示**：它和 Git 还是有本质区别。Git 可以让你手动 resolve merge conflict，数据库不行——因为 transaction 中间可以有任何任意的计算，你的值可以是由程序算出来的。数据库系统只能管这段 transaction 本身，没法替你判断「两边算出来的值哪个是你想要的」。

理论上说，也许可以做出性能更好的 Multi-Version Concurrency Control。无论如何，这是一段超级复杂的并发程序，也是一个非常了不起的工程奇迹。正因为有这样的数据库系统，才有了云计算时代（可以说是在云分布式数据库之前）你看到的世界上的所有东西——新浪、网易、雅虎。它能服务互联网上非常非常大的人群，实际上也在服务我们每一个人。

### 数据库里藏着一个编译器

回头看那条 SQL，它本质上是一段程序。既然是程序，就意味着可以做 rewriting。

今天你们的编译器有 `-O0`、`-O1`、`-O2`，它本质上就是好多好多的 rewriting rules。数据库我不知道为什么走上了完全不同的路线——当然跟程序领域有很多数据库不太涉及的东西（比如指针）有关——但它们的本质都是有一大堆 rewriting rules。

举个例子：如果把这个循环往外提，就能提高性能。事实上确实如此——把循环外提之后，那两层循环就被消灭掉了，可以直接查 key。数据库就是这样不断地 rewrite、rewrite、rewrite，最后变成一个高效执行的 plan，一段可执行的程序，再落到磁盘上的高性能数据结构，比如 B-tree 这样的索引结构。再往后还有缓存、分库分表、并发控制、读写分离，各种手段。

结果是：一个单机上的数据库，只要不是大到国民级的应用，全部都能搞定。你的一台服务器或者一台 PC，只要你有足够的磁盘带宽、内存带宽和足够多的线程，它就可以帮你支撑一个非常非常大的应用。

有兴趣的同学可以去看 Andy Pavlo 的 15-445，非常有名的课程，它展示的就是右边有一个 `SELECT ... FROM ... WHERE ...` 的查询，然后一步一步做语义等价的改写，最终变成一个高性能的查询。昨天看的时候还发现你们的师兄在那个助教的 list 里面，也许可以直接去 cue 他。

### 手机里那个无处不在的 SQLite

数据库还有一个很大的好处：它给了非常强的一致性，而这个性能正是我们想要的。

打个比方，你们手机上都有「设置」界面，一打开有好多小拨片，不管是 QQ 还是整块系统，这些 settings 都是 persistent 的。当你按下那个小拨片，这个值是 0 还是 1，它就 persist 下来了。

你可能会想：这是不是用文件系统实现的？是不是每一个 preference 就是一个文件，把 0 或者 1 写到那个文件里，再做一个 fsync？实际上，这些是由一个很小的 SQLite 数据库来管理的。

它第一，数据库就是一个文件；第二，整个 library 就是一个文件。这个 C library 提供的是一个 small, fast, self-contained, high-reliability, full-featured 的 SQL 数据库引擎，它是 the most used database engine in the world——你每一个 Android app、每一个苹果 app 里都带着一个 SQLite 引擎。在系统里，一旦涉及到 persistence，第一件事就是求助于它。

它是 zero-configuration 的，你只要有那个 `libsqlite3.so`，就能享受数据库的所有好处。想做一个 preference 界面、想拿到一份动态构建的设置列表，直接一句 SQL 查询查出来；想改一个值，也是一句 SQL。而且它保证你的数据安稳地落到磁盘上，你不用再纠结「我写一个配置文件，需不需要 sync 它」。

### 一张表装不下全国人的聊天记录

这个产业的故事还没有结束。它想要变得更大、想实现国民级的应用，一个数据库就有困难了。

拿微信聊天记录来说，它本质上就是可以建模的，甚至可以就一张表。聊天记录就是一个气泡，气泡里面是一个 XML 文档，当然还有不少有意思的、几乎是 hard-coded 的编码规则。比如长按消息可以「回复某个人」——那是把那条消息拷贝了一份，在拷贝的消息下面加了好多个减号，然后这才是你的回复。微信解析这个格式，如果发现是这种格式，就自动 link 回那条被回复的消息。这样能在老版本微信、iPad 版、网页版上保持兼容：不支持的客户端会直接把那一堆减号原样显示出来。所以本质上，微信的聊天记录就是一张表，叫 chat records。

那么「点开最近十个聊天」就是一条 SQL：

```sql
SELECT *
FROM chat_records
WHERE sender_id = :me AND receiver_id = :peer
ORDER BY time DESC
LIMIT 10;
```

在百万、千万用户的时候，一台机器、一个 production 的 Postgres 这样的 SQL Server 其实就能处理这样的性能。但到了微信这个量级，SQL 数据库的压力就很大了：压力全给到数据库引擎，你需要做分库分表、读写分离，做正确的索引，做各种各样的缓存和优化。

问题的根源在于 SQL 提供的这套查询优化本身。它说：程序员不需要管查询是怎么执行的，你只负责把 fact 写好，把提取 fact 的查询写出来就好。**你永远无法预知程序员会写出多么糟糕的 query。**

见过那种互联网工厂里面向企业服务的系统就知道：你在淘宝或者京东下的一单，看起来只是一单，背后涉及的表非常非常多，一层一层包着。你会看到 50 个表 join 在一起，还有日期、limit 各种条件，剩下就是数据库在那儿疯狂地根据实际执行去挑一个好的计划。数据库提供了这些功能，就很难避免它被滥用，而滥用就意味着一个 performance bug。

公司里交付产品永远是第一位的。用户量小的时候，一个复杂查询可能是个 performance bug，但不致命；可它会在数据库不断增长的过程中越来越慢、越来越慢，使得你去优化它可能会有 10 倍甚至 100 倍的性能收益。这是任何 systems 都没法避免的技术债。所以用 SQL 开发像微信这样的系统，最终都不可避免地要陷入非常复杂的局面，或者需要一个特别好的架构师来帮你把数据库管好。

然后，还是不行。总有一天我们要走向分布式——一台机器怎么也容不下全国人民的聊天记录。

分布式当然有办法：先把不同的表丢到不同的机器上；当一张表大到一台机器放不下，就把这张表切成好多部分分到不同机器上。理论上，传统的 SQL 数据库也能 scale 到很多台机器上。但如果想一劳永逸地解决 scalability，一个更好的想法是做一个「够用、但可以 scale out」的子集。业务踩了很多坑之后回头会发现：SQL 给我们太多了。给得太多，一旦滥用就带来 performance bug；而在某些应用里给少一点，实现会更容易、性能可能更高、更容易分布式，也基本够用来构建你需要的应用。

### 退一步：key-value 就够用了

那什么数据结构大家用得最多、最简单、又够用？key-value dictionary。一个 key 和一个 value，就是一个 map，或者一个 unordered map，或者就是 Python 里的 dict。

应用程序理论上可以靠 key 来管理各种各样的数据。要管理一个用户的数据，就把 UID 拼在后面做 key，取出一个字符串——比如一个 JSON——就是这个人的信息，这是 read；要 write，就把 serialize 好的 JSON 再写回 `user:UID` 这个 key 里。查询和修改一个用户的信息，本质上就是数据结构的增删改查。

再扩展一点也行。key `enrollment:1` 指向一份 JSON（他选的课），而这个 JSON 里的 enrollment 可以是一个列表。列表可以是 append-only 的，也可以清零。把所有的选课记录和退选记录都 append 进去——这不就是一个教务系统了吗？

> **提示**：这里用到了一个关键判断——一个学生的选课退选不会特别多，你不会选一万个课再退一万个课（真发生的话，多半是你自己写的脚本出了 bug）。你对系统里的某些东西是有 knowledge 的，而 append-only 大家都知道比较容易实现。

于是每次想看这个学生的选课列表，就把它读出来 replay 一遍；也可以把 replay 完的当前 enrollment 缓存成 `user:2` 的视图。点赞也一样：直接往 list 里 append 一个。全球的人都在给你点赞也不要紧，因为 append 比「load 加一再 store」这样一个读写的 transaction 性能要好——append-only 更容易实现，consistency 也更容易保证。你甚至可以从好几个地方分别收到列表，在好几个线程里并行地 append，最后串起来再 append 回去，这也是正确的。

这样的数据结构好实现，也好扩展：

- 给 key 做 hash，就自动 load balance。只要 hash function 足够好，每个 key 就近似变成一个 random number；有多大台机器，就把这个随机数模机器数量，不就把请求送到一台随机的机器上了吗？自动 load balance，也自动 scale。
- 因为 everything is append-only，实现可以很高效，比如用 LSM tree 这样的结构。
- 分布式的高性能、crash consistency，也都可以实现。

### 内存里的缓冲层：把点赞数先攒着

key-value 甚至不必做成数据库，也可以做成 in-memory 的东西。

思路是：所有请求先进入内存里的 key-value，它隔一段时间把请求合并了，再写到后面的 database 里。

比如统计点赞数量。如果你每一次点赞都形成一个 transaction 把它 persist 下来，代价是比较大的。但这个地球上真的有很多人在给你点赞的时候，你完全可以在内存里放一个 counter——点赞这个数据对你来说不是那么重要，丢了损失也没那么大，尤其是全世界有几百万人在同时给你点赞的时候。进了内存以后，每一次都是加一，可以是一个 list 的 append，也可以就是一个 atomic 的加一，key 映射到一个 integer。每隔比如一分钟，我就知道这个 counter 走了多少，这时候再写一条 SQL：从 database 里把点赞数取出来，加上这一分钟里新点的 100 万次赞，再写回去。绝大部分事情都在内存里做，性能、scalability、并行度都上来了。

那层东西就是 Redis：它也是一个 key-value，支持 string、list、set、hash，可以做一个高性能的缓存，做数据库的缓存，也可以做这样一层缓冲。

```text
client 请求(点赞) --> [ in-memory key-value / Redis ]  --每 N 秒合并写回-->  [ 磁盘上的 database ]
                       key -> integer counter                                SQL / 持久化
```

图里左边是扛量的那一层：所有高频的小写入在这里被合并成计数；右边是真正的持久化数据库，只承受被压缩之后的、低频的写。有了这一层，就已经非常接近于今天的高性能架构了。

### 从 document 到 NewSQL：分野与回归

但 key-value 用起来终究还是不如 SQL 好用。SQL 的意思是我可以随便写——我可以写一个 50 层循环，你就自动帮我搞定。于是就有了各种「扩展 key-value」的尝试：

- MongoDB，一个 document-based database，所有操作都是 document-based，本质是 key 到一个 JSON。JSON 有一些数据结构的操作，你可以往里 append messages，结构化存储就比一个单纯的 list 更好用。
- Cassandra，一个 column database，也有查询语言（CQL），也是 table 的模型，但它不给你 full SQL 那种完整支持。
- 也有数据库想提供几乎完整的 SQL 支持，最有代表性的是 TiDB——我们国产的、出海的一个非常经典的 startup 案例。还有 Google 的 Spanner 和 CockroachDB。

| 类型 | 代表 | 模型 | 取舍 |
| :--- | :--- | :--- | :--- |
| 关系型 SQL | PostgreSQL、SQL Server | 表 + join，任意查询 | 表达力最强，但可能被滥用成 performance bug |
| key-value | Redis、dict/map | key → value（字符串、JSON、list） | 最简单最够用，表达力有限 |
| document | MongoDB | key → JSON 文档，可往里 append | 比单纯的 list 好用，但不是 full SQL |
| column | Cassandra（CQL） | table 模型，只给部分查询能力 | 用表达力换可扩展性 |
| NewSQL | TiDB、Spanner、CockroachDB | 几乎完整的 SQL | 试图两全 |
| vector | 向量数据库 | 向量 + 近邻搜索 | 用距离度量语义相近 |

这不是今天的标准答案，而是一个巨大的 industry，也许你们有同学就会加入到这个 industry 里面。

回过头看，前面讲的所有这些——SQL、key-value、document、column——本质上都是数据结构，都是程序。它们的目的是在 infrastructure 这一层把 crash consistency、分布式这些事情屏蔽掉，只给你一个 API，你直接调它，它就把所有事情都搞定。

### 向量数据库：让数据可以被「找相近」

今天还有一种新兴的 database，和前面这些都不一样：vector database。

来上课之前，我特意让一个小模型——大概是千问 3 的 8B——把每一次上课的提纲（每一页幻灯片有一个有意义的名字，比如你看到这一页的名字就是 vector DB）变成一个 4096 维的向量。这个向量其实可以存到 extended attributes 里，也就是 xattrs 里。

向量数据库把这些向量存下来，然后做 nearest neighbor search（近邻搜索）。你可以有上亿的文档、几万维的向量，任何时候给出一个向量，它就能在数据库里找到和它邻近的那些向量。度量可以用 dot product，也可以用 cosine distance（余弦距离）。基本上，向量的距离越近，就意味着两个文档的内容越接近。

```text
concurrency 簇    [ 13 14 15 16 17 18 19 20 21 ]  <- 聚成一团，彼此都近
文件系统 / DB 簇   [ 24 25 26 ] --强关联-- [ 27 database ]  (27 与 26 稍弱)
孤立点              [ 4 agentic AI ]   [ 6 进程地址空间 ]
```

上面这张图是按向量距离量出来的课程相似度：13 到 21 讲 concurrency 的那几讲全都聚在一起；今天是第 27 讲，讲 database，它和 26 讲（文件系统的实现）有比较弱的关联，但和前面 24、25、26 三讲文件系统有非常强的关联；第 4 讲是 agentic AI、讲 coding agents，它是一个孤岛，和其他所有讲都不太相关——它自己识别出来了这一节课是 off-topic 的，不过我又觉得在操作系统课里必须讲一讲；第 6 讲进程的地址空间也显得稍微有一点孤立。

未来这些会融合到一个信息系统当中。结构化的数据结构肯定不会消失，因为它是保存数据非常 efficient 的办法——微信的聊天记录用这种方式存、用那种方式存都很合适。但与此同时，数据库里又不可避免地会有向量的部分：理论上每一个 record、每一张表的每一条记录都可以 associate 一个向量，然后我们就可以智能地去查询这个世界里的东西。

比如构建一个论文数据库，能不能把和我提出的这个讨论相关的论文找出来？甚至是弱相关的东西，能不能给我一点启发？这样智能化的应用在未来会变成什么样，我不知道，但我相信世界会变成这样。

### 回到应用程序：一切都是增删改查

所以我今天讲了 database system，本质上要回到这样的应用程序上：所有应用程序都是数据结构的增删改查。

你看到我好像越讲越复杂了——SQL、NewSQL、Vector Database——但本质上它们都是某一个数据结构的增删改查。回到这个视角：打开一个教务系统，我的功能就是增删改查；我做的一个 PowerPoint，也是增删改查。理解任何一个产品的设计的时候，背后的那些数据管理的道理都是通的。
