## 多处理器编程：从入门到放弃（上）
> 对应块：BLK25 | 覆盖分集：P13上

虚拟化那部分收尾的时候，我们手上应该已经攒出一张完整的图景了。把它从头顺一遍：一台计算机，不管是我桌上这台还是你们手上的笔记本，都是从 CPU reset 开始的——它有一个最早的状态，reset 之后程序就开始运行，firmware 先把操作系统加载进来。加载之后操作系统会干一些事，比如 initramfs 里那棵文件系统树：最早的操作系统把它加载到内存里，让它变成一个文件系统，再加载里面的 init 程序。在这之前我们还讲清楚了"什么是程序"：execve 收到一个可执行文件，它是怎么被加载进内存、又是怎么被放到 CPU 上执行的。等这个 init 加载了你们磁盘上真正的文件系统，它会再执行一次系统调用，切换到一个新的 init 程序——也就是 pstree 里看到的第一个进程 systemd；systemd 再用各种各样的系统调用，把你们屏幕上看到的那个应用世界创建出来。

从操作系统往外看，这一切就是一组 system call、一个 API。但要构建起应用生态，它外面还有一层一层的洋葱：libc 是一个有 ISO 标准、可以移植的基座，写 C 程序就能很容易地移植到别的平台，甚至是那种微小的控制器；libc 之上有大量的库函数——你想在终端上显示字符、读取字符，想访问屏幕，想创建图形界面，都有相应的底层库函数；再往上又长出应用程序的生态，JavaScript 的、Python 的。你们打开一个 Visual Studio Code，它是 Electron 框架里跑的一个 JavaScript 程序，但它会一路依赖到最底下的 libc。

往下走，这套设计也可以兼容多个体系结构。这个学期我把讲台上原来那台机器换成了我的一台树莓派：一个是 x86，一个是 ARM64，还可以有 RISC-V，等等等等。但不同的体系结构上跑的是同一个操作系统的 API。Linux 内核用 C 实现，现在开始加入一部分 Rust；C 本身就具有一定的可移植性，它 freestanding 的环境在 x86 上能跑，在 ARM64 上也能跑。于是操作系统的 API 就成了一个很好的中间层：底下的硬件不需要知道上面的应用程序是干什么的，它只要机械地执行指令就行了；上面的应用程序甚至不需要知道自己跑在什么样的 CPU 上，只要写的是可移植代码，在 x86、ARM 上都能正确运行。内核里体系结构相关的代码总会有一些，但它是相对比较少的一部分。

复习的时候不妨顺着这条线回想一遍：应用程序的世界是怎样一点一点被构造出来的。

今天我们就正式进入下一个部分：并发编程的入门。这个标题叫"从入门到放弃"，不是让你们放弃并发编程——是让你们先知道，并发编程、尤其是多处理器上的并发编程会碰到什么样的困难。然后我们会在若干次课的时间里告诉大家，应该怎样去写并发程序，让它性能又好、又不容易出错。

### 为什么非要并发

在之前的世界里，我们一直假设程序就是一个一个状态机：程序是顺序执行的，它可以执行指令——如果是一个二进制的文件，它就是一条一条指令执行的；它也可以执行语句——如果这是一个 C 程序，就是一条一条语句。编译器做的事，无非是把高级语言描述的状态机编译成低级语言描述的状态机。这种模型叫顺序（sequential）模型。看起来很干净，可一旦你写稍微真一点的程序，就会感觉到明显的小麻烦。

#### 顺序模型的第一处别扭：写一个 HTTP 服务器

HTTP 服务器到处都是。你们打开手机，淘宝、抖音，所有你想从远端获取信息的时候，都是通过 HTTP 协议或者 HTTPS 协议完成的。假设你回到 200 几年，想开一家公司就叫淘宝，要上线一个信息系统：做一个网页，它收到一个请求（比如"我要淘宝的首页"），你就把这个首页返回给它。在顺序执行的模型下，你会写出这样的代码——我有一个 HTTP server，它有一个 fd，我不断地从这个 fd 上持续读取来自别人的请求（实际不完全是这个样子，先这么设想），每读一次先分配一个 buffer，从某个地方读到一些数据，读完了以后就去 handle 它。

```text
   顺序执行的服务循环

   +----------------------+
   | 从 fd 读一个请求      |  <-- 没数据就在这里死等
   +----------------------+
              |
              v
   +----------------------+
   | handle request       |  <-- 读磁盘 / 计算，这段时间别的活也干不了
   +----------------------+
              |
              +-------> 回到开头，处理下一个请求
```

读图说明：一个循环里既有等网络的部分，也有处理请求的部分，而它们是串起来的。

问题就在这里。有的时候这个读会等很长时间；有的时候 handle request 也能等相对比较长的时间，比如它去读磁盘。一个程序里可能同时有好几件事要做：既要读磁盘，又要读网络上的请求，还可以做计算。但如果是顺序模型，当我执行一个 syscall 的时候——比如一个 read——哪怕我手上还有别的事情可以做，我也不能去执行这个 read：read 没有数据的时候，我就必须等这个数据到来。CPU 就被卡住了，它不在处理我本来可以处理的事情，这是一种浪费。

所以这就有了第一个动机，或者说只是一个想法：我能不能有一个什么办法，让我能够同时做几件事情，如果它们真的能同时做的话。

#### 多处理器和共享内存就在手边

第二个动机是：我们现在的系统都是多处理器的。哪怕我那台树莓派，用 `lscpu` 去看一下，里面也有 4 个 CPU，编号是 0 到 3。你们自己看你们的 CPU 可能会有更多，可能有几十个处理器；甚至还有 128 核、256 核的机架上的服务器。这几十个处理器，不管是谁的，它们提供的硬件模型都是共享内存的：物理内存是一个地址空间，CPU 1 说要访问 1234 这个地址，CPU 2 说我也要访问 1234 这个地址，那 CPU 1 写进去的数据，CPU 2 过一会儿读就能读到。系统就是共享内存的，这个性质不用白不用。

那怎么利用好系统里的多处理器？举个例子：你现在写一个程序需要一张素数表，那就先把这张素数表算出来，然后 fork 100 份，于是得到 100 个进程，每一个进程都可以并行执行，会被放到一个 CPU 上。你们可以做个实验：能看到 CPU 的利用率变成了 200%、300%，它超过了 100%，就说明你的进程真的是在同时工作的。

但是这样的程序有一个问题：想把 fork 出去的结果收回来就很难了。比如你想把一个很大很大的区间分成好多段，每一段算出一个值，最后把它们加起来——如果它们是独立的进程，你就必须再用管道这样的机制，创建一个命名管道或者匿名管道，把这个数值送回给它的父亲进程，最后加到一起。这很麻烦。

那能不能更直接一点？这其实是一个非常显然的动机：既然是多进程共享内存，我在主进程里有一个 `sum`，能不能就在这里 `sum += ...`？在 fork 完的子进程里面，直接把这块内存写了；父亲的进程只需要等所有的进程结束，把 `sum` 打出来就可以了。这样我不仅可以做求和，还可以做更复杂的事情——甚至可以同时处理多个网络请求。这就是我们想要引入共享内存并发的动机。

### 线程：一份全局变量，几个各自独立的栈

想要共享内存的进程，其实用 fork 已经能实现了：fork 之后进程就变成了两份，在操作系统里它有两份，它们是完全一样的，除了一份返回子进程的 PID、另一个返回 0，其他都完全一样，然后就各自往前执行。那我们能不能让这两个进程不要是分开的——让它们程序可以独立执行，但是内存是共享的呢？这个东西就叫线程。

> **定义**：线程是这样一种执行实体——它有自己的栈，和别的线程共享同一份全局数据。

#### 从 simple-C 的执行模型推出来

回到 simple-C。一个程序有一个函数调用栈，最底下是 main，你每一次函数调用都会放一个新的栈帧到栈的顶上，每个栈帧里面都有一个 PC，这是 simple-C 的执行模型；除了栈帧之外，还有全局变量 globals。

你要让两个程序、或者说两个进程共享内存，同时又能独立执行，那么每一个执行的实体就必须要有一份自己的堆栈。栈必须是独享的：simple-C 执行一条语句的含义，就是从最顶上那个栈帧的 PC 里选一条语句出来执行；如果两个独立运行的实体共享一份栈，这件事就全乱套了。

于是把模型扩展成两个线程就很自然：T1 有自己的栈，T2 也有自己的栈；你也可以有 T3，它也可以有自己的栈。但它们的全局数据是共享的。

```text
     T1 的栈            T2 的栈            T3 的栈
   +-----------+     +-----------+     +-----------+
   |  栈帧(PC)  |     |  栈帧(PC)  |     |  栈帧(PC)  |
   |  栈帧(PC)  |     |  栈帧(PC)  |     |  栈帧(PC)  |
   +-----------+     +-----------+     +-----------+
         \                 |                 /
          \                |                /
           v               v               v
   +------------------------------------------------+
   |                 globals（全局数据，共享）        |
   +------------------------------------------------+
```

读图说明：栈是每个线程私有的（连同栈帧里的 PC），全局数据是所有线程共有的。

#### 迁移：把一个栈加一份全局看成一个进程

在这个基础上，"迁移"这件事怎么理解？你可以把一个栈加上全局内存看成是一个进程：T1 的栈加全局，就是一个我们之前讲过的进程；T2 的栈加全局，又是一个同样概念的进程（这里代码也放在全局的那一块里，先不单独画）。那么迁移就是我可以选 T1 执行一条语句，也可以选 T2 执行一条语句，也可以选 T3。

也就是说，我们是在"什么是程序"这个已有的定义上，定义出了"什么是线程"。

#### spawn 与 exit：线程只要两个原语

为了管理多线程，我们仍然沿用旧的模型：任何时候都有好几个 T1、T2、T3 的栈，再加上一个 globals。然后往系统里加一个 API，一个系统调用，叫 spawn：在已有线程不变的情况下创建一个新的线程。比如现在创建一个新的 T4，它里面有一个栈帧是 f（spawn 可以带上一个函数），而 globals 是不变的。除了 spawn，还可以有一个 exit，也就是 thread exit，它把一个线程从这个系统里面抹掉。

```text
   spawn(f) 之前              spawn(f) 之后
   T1栈  T2栈  T3栈            T1栈  T2栈  T3栈  T4栈（栈帧 = f）
   globals（不变）             globals（不变）

   thread exit 之后
   T1栈  T2栈                  （T3 从这个系统里被抹掉）
```

读图说明：spawn 只往上加一个栈，exit 只拿走一个栈，全局数据自始至终是同一份。

这和 fork、exit 很像，只不过这个 fork 不是发生在操作系统层，而是发生在进程里面：一个进程里面有共享内存的线程。如果让你们从零开始设计一个线程，你们就会这样设计。

#### 落到指令级：一个平坦地址空间，每个线程一个 SP

到了指令级上，它就只有一个平坦的内存、一个地址空间——顺便说，就是一个 mmap 创建出来的地址空间。我们要做的是在地址空间里为每一个线程分配不同的区域作为它的栈；每一个线程有它自己的寄存器，而寄存器里面有一个 stack pointer：线程 1 的 SP 必须指向 T1 的栈，线程 2 的 SP 必须指向 T2 的栈。

因为程序一旦被加载到 CPU 上运行，它就是一个无情的直接执行指令的东西，它只能 load、store 和 system call，它 load 和 store 的就是这个地址空间里的东西。程序从线程和进程的意义上看，地址空间就是从 0 开始到一个很大数字的字节数组，所有的一切都是由寄存器里的地址控制的。

```text
   高地址
   +---------------------------+
   |  thread 1 的栈区          |   <-- T1 的 SP 指在这里
   +---------------------------+
   |  thread 2 的栈区          |   <-- T2 的 SP 指在这里
   +---------------------------+
   |          ......           |
   +---------------------------+
   |  全局数据 / 代码（共享）   |
   +---------------------------+
   低地址（0）
```

读图说明：整张平坦内存里，每个线程分到一段区域当自己的栈，各自的 SP 指向各自那一段；代码和全局数据只有一份。

如果你们想要实现一套共享内存的进程，实现的就是 spawn 和 exit 这两个系统调用。所以可以说，这就是并发编程的全部了——剩下的所有内容，都是从这个模型上推出来的。

### 并发与并行：一字之差

线程一旦进入这个模型，它就是并发的，或者是并行的。这两个词之间有一个比较微妙的差别。

并发，意义上是逻辑上的同时执行。你可能只有一颗 CPU，那你就真的每次只能执行一条指令——一个单周期的 CPU，每个时钟周期它就真的只能执行一条指令。但是如果你有两个程序，你可以让它一会儿 A 程序在 CPU 上运行、一会儿 B 程序在 CPU 上运行，A B A B B 地交错执行；在一个比较长的时间尺度上，你看起来它们两个都被执行了，这就叫并发。它逻辑上在一个时间段里面都有往前的进展，但实际有可能是操作系统和运行时库模拟出来的轮流执行。

并行，则是在真正意义上的同时执行：比如有两颗 CPU，两个线程被加载到两个 CPU 上同时运行。

| 概念 | 含义 | 需要什么硬件 | 二者关系 |
| :--- | :--- | :--- | :--- |
| 并发 | 逻辑上的同时执行，可以是轮流交错出来的 | 一颗 CPU 也能做到（靠调度模拟） | 并发的程序可能并行，也可能不是 |
| 并行 | 物理时间上真正同时发生 | 需要多颗 CPU | 并行的程序一定也是并发的 |

> **易错点**：别把两个词当成同义词用。并发的程序可能是并行的，也可能不是；但并行的程序一定是并发的——它已经在物理时间上同时发生了。

#### 两种理解线程的方式

在刚才那个概念模型上，我有两种表示方法。

第一种就是前面定义的：现在有 T1 和 T2，我可以选 T1 执行一步，也可以选 T2 执行一步；如果选 T1 去执行 spawn，状态就从 {T1, T2} 变成 {T1, T2, T3}，之后我再在 T1、T2、T3 里挑一个走一步。

第二种更接近实际 CPU 的实现：你有 T1 和 T2，走一步的时候相当于 T1 和 T2 同时往前各走一步。

```text
   模型一：一次挑一个线程走一步
     T1:  - - - o
     T2:  - - - - - o        （任一时刻只有一个线程在动）
     T3:  - - o

   模型二：所有线程在每个"步"上一起前进
     T1:  - - - - - - -> o
     T2:  - - - - - - -> o    （每一步，所有线程同时往前走一步）
     T3:  - - - - - - -> o
```

读图说明：模型一是状态机意义上的交错，模型二是让所有线程同步地各走一步。

但你们也知道，实际的处理器处理每条指令的速度是不一样的。有的指令 cache hit 了，执行得就比较快；有的指令 cache miss 了，就执行得比较慢；有的 load、store 指令天生就比寄存器指令慢一点；乘法和除法可能要花好几个周期。所以模型二里面"让两个线程同时执行一条语句"这个说法，是有点过度简化的。

在实际的系统当中，在真实的 CPU 上，你是很难理解并行程序执行到底发生了什么的——因为你不知道一条指令到底执行得多快。一条指令执行的快和慢，取决于你当前整个系统里各种各样复杂的状态。这里是给魔鬼埋的一个伏笔，但概念上你们可以先接受这两种理解线程的方式。

### 用一个最小的线程库把模型跑起来

既然理论上把这件事想清楚了，那我们就可以做实验了。为了实验，我提供了一个方便大家理解的最小的线程库，它实现的就是我刚才说的 spawn 这个功能。

#### spawn 与 join

操作系统给我们提供的功能比我说的简化模型要多，手册是 `man 7 pthreads`（现在这个也可以直接管道给 AI 让它帮我看）。我把操作系统给我们提供的线程库做了一些减法，做了个只适用于最简单情形的版本，它只剩两个 API。

第一个是 spawn：它创建一个入口函数是 function 的线程，可以传一个函数指针进去。这个 function 长这样——每一个 function 有一个整数的线程号，线程号从 1 开始编号。所以我可以 spawn 一个 T，再 spawn 一个 T：两个是同一个函数，但它们的参数不一样，第一次 spawn 会启动一个线程去调用 T(1)，第二次会启动一个线程去调用 T(2)。它们共享内存，而且是独立运行的。

第二个是 join：等待所有我放出去的线程结束。因为你的函数是可以返回的，任何一个函数都可以返回，返回以后这个线程就结束了；join 就是等所有线程返回。

这里我做了一个简化：我的线程库里 main 会默认 join 所有线程，而操作系统给你的 pthreads 不会。我这样做是为了让代码看起来容易理解一些。它的行为是：每次创建一个新的线程我都记一个数（比如调用两次 spawn 就记 2），每一次线程结束也记一个数——一个结束了、两个结束了——然后就一直等，等到所有的线程都结束，main 函数才能真正结束。

有兴趣的同学可以去看一下这个线程库的实现，它也是比较 straightforward 的：它就是调用了 POSIX 标准的线程。因为是标准规定的，也就意味着各种各样的平台上都会支持它。

| | 我提供的最小线程库 | POSIX pthreads |
| :--- | :--- | :--- |
| 提供的 API | 只有 spawn 和 join | 完整的一套线程接口 |
| main 结束时的行为 | 默认 join 所有线程后才真正结束 | 不会自动等待其他线程 |
| 移植性 | 平台都支持 POSIX thread 即可用 | 标准规定，几乎所有足够好的平台都支持 |

一旦成为标准的好处就是，你可以放心地在绝大部分足够好的平台上使用它，比如你们的鸿蒙系统——它可能是一个和 Linux 不兼容的系统，但它一般都会兼容 POSIX thread，这样才能够把更多的第三方库函数、第三方应用程序移植到它的系统上。

#### hello.c：A 和 B 交替出现

看一个程序就知道了。我有一个 hello.c，这就是一个普通的 C 程序。一旦碰到 spawn，这个系统里面就多了一个函数，这个函数和其他函数是独立运行的：第一个函数 `while (1)` 打印 A，第二个函数 `while (1)` 打印 B。

那你预期看到什么？你不会看到 AAAA 打到底、BBBB 打到底，你会看到交替出现的 A 和 B。这种能力在之前不并发的世界里——多个进程理论上说也能实现这一点，但在一个进程、一个程序里面，以前你是实现不了这个功能的。

运行一下，你看到的是一个随机的、交替出现的 A 和 B，符合预期：首先你不知道操作系统什么时候会把 A 和 B 放出来执行，其次你也不知道它们谁执行得快一点、谁慢一点，所以你看到的就是一会儿 A、一会儿 B、一会儿 A、一会儿 B。这个结果符合我们对并发和并行的预期——它实际上是并行执行的。

#### 证明它们共享内存、栈各自独立

有了这个线程库，你马上就可以写代码了。作为第一次接触多线程编程的人，你可以问出什么问题呢？或者说，你想改一改那两个函数来实现哪些有趣的功能，来加深对线程这件事情的理解？

至少可以干几件事：证明这几个线程确实是并行的、确实共享内存；证明它的栈是独立的。如果每个线程的栈都是独立的、都在这一个地址空间里，那这个地址空间应该有一个头、有一个尾，这段空间到底有多大呢？这样一些问题都能帮你理解那个概念的模型——我在指令的意义上说过，地址空间是平的，是从 0 开始到一个很大数字的字节数组，所有的一切都由寄存器里的地址控制：栈有栈顶的指针，代码我也可以对 main 取地址，甚至可以把那个地址打印出来。

先证共享内存。我在这里做了两个线程，一个是 x++ 的，一个是 y++ 的：x++ 的线程每次把 x 加 1，然后 sleep 1 秒钟；y++ 的线程每次把 y 加 1 以后 sleep 2 秒钟。而在 main 函数里读 x 和 y——我每隔一小段时间就去读一次 x 和 y，然后把它打印出来。在一个线程里面写、在另外一个线程里面读，如果我能读到，就说明确实是共享内存的。运行这个程序，你能确实看到 x 走得比 y 快，那就非常确信地知道：至少数据的部分是共享的。

类似地你也可以证明代码的部分是共享的，也可以知道线程的栈位于同一个地址空间里。怎么知道？你可以定义一个局部变量，取它的地址打印出来——你会发现所有的东西都在同一个地址空间里。你甚至可以把一个指向局部变量的指针传递给另外一个线程，那个线程就可以访问这个局部变量，这都是可以的，因为它们都在同一个地址空间里。通过这些实验程序，你对线程就能有一个比较好的理解。

#### 线程的栈到底有多大

那线程是否有独立的栈、它的栈有多大？直接问 AI"线程栈有多大"，它马上就能告诉你；那你能够写一个程序来验证这一点确实是真的吗？也可以。

我给大家准备了一个 test-stack.c，它是这样工作的：有一个无穷递归，这个函数叫 probe，每次递归都会定义一个 scratch 数组——内容无所谓，我也不用它，就是每个栈帧都会有一个 64 字节的、不用的数组被分配；然后我就无穷递归，总有一天这个 stack 会 overflow，然后系统就 crash 了，线程就 crash 了。但是一边递归，我一边把我当前这个局部变量的范围更新到 high 和 low 里：我有两个指针，一个叫 high、一个叫 low，每次调用 update_range 就把它看到的、当前最小的和最大的地址都更新进去。

它的用意是这样的：我不知道这个线程栈在哪，但我知道的是，在我这个函数刚刚被调用的时候，它应该只用掉可用空间的一点点，绝大部分空间还没浪费掉；然后这个栈会从高地址往低地址生长（实际上就是高地址往低地址生长的）；每次函数调用我都会加一个新的栈帧，里面有一个 64 字节的局部变量。一直走下去，总有一天它会 overflow——那我只要在 overflow 之前，把我已知的最小和最大的地址不断打印出来，不就可以观察到我的栈有多大了吗？

运行 test-stack，你确实能看到这个栈越长越大、越长越大的过程：T1、T2、T3 一路探下来，T1 的 stack 最后打印的是 `T1 stack >= 8183`。这个数离某一个整数非常近——它离 8192 非常近。也就是说它有 8192 KB，就是 8 兆：每一个我创建出来的线程都有一个 8 兆的堆栈。

> **易错点**：这跟你们平时用程序的感觉不一样。在 Linux 里面，默认的时候程序可以用的栈几乎是无限的，它可以一直往后用；但因为每一个线程的栈都在地址空间里，所以你必须在创建线程的时候就决定好它的栈有多大——因为它必须在地址空间里面分配一段内存。

这类验证的工作也可以交给 AI：它可以读这个代码，理解以后帮我跑一遍，再帮我解读结果为什么是这样。

#### 用 GDB 把模型对上真实程序

多线程的程序能不能用 GDB 调试呢？答案也是肯定的。加一个 `-g` 的编译选项，直接运行 GDB——它说全都结束了、exited（程序跑得太快，直接就结束了）。

要调试一个多线程的程序，首先我可以打断点，在两个线程的入口处都打上断点。以前我们上这门课的时候，我的第一句话就是"你去 read the friendly manual 吧"，那就是 GDB 的文档：GDB 里面 threads 那一节告诉你怎样调试多线程的程序。现在 AI 帮你读过了，所以我展示一下就可以了。

GDB 还有一个功能叫 `info threads`，你们可能没有用过。info 里面可以看好多好多的东西，在 info 后面 Tab 补全一下，可以看到很多有用的信息——有些你知道，有些你可能不太知道，花点时间学一下还是很有好处的。`info threads` 让你看到现在的线程：只有一个，ID 是 1。

一般要调试多线程的程序，我们会用 `set scheduler-locking on`。它做的事情，和刚才说的线程的两种模型正好对应：一种是你可以选 T1 执行一步，相当于我选 T1 的时候，所有其他线程都被暂停了；另一种是我每一步让所有线程都往前推进。默认的时候，`scheduler-locking` 是 off：线程 1 执行一步的时候，线程 2 和线程 3 还在往前执行，这可能会影响我们调试。`set scheduler-locking on` 就是把调试器退回到"一次只走一个线程"的那个模式。

于是我可以正常调试它：spawn，spawn。但如果我 `continue`，main 函数实际上是在 join 里——main 返回之前有一个 join，join 要等待其他线程结束，可其他线程都卡住了、不会执行，所以这时候我要打断它。再 `info threads`，你就能看到三个线程了，1、2、3。然后我回到 thread 2 上 `continue`，它就在 Ta；我到 thread 3 上 `continue`，它就在 Tb。可以在线程之间切换。

这样我就把一个实际的程序——一个真正在 CPU 上运行的程序，你可以看它的 assembly，它是有 assembly 的——完美地对应到了这个模型上：我们有多个线程，每个线程都有自己的栈、有它的 PC；每一次我都可以在 GDB 里选一个线程执行一个单步，thread 1 就是选 T1，thread 2 就是选 T2，thread 3 就是选 T3。最终你就可以把这个多线程的模型调试好、理解好。

当然，调试多线程的程序是一个很大的麻烦，你会花很多时间在线程之间切来切去、切来切去。现在 AI 做得还不是特别好，但我们可以期待一下，也许明年的时候，AI 就可以很好地帮你调试并发程序了。

这就是多处理器编程的入门：你已经入门了，而且用这个线程库写出了一些有趣的代码，确保你对多处理器编程有一个比较好的理解。

### 放弃的第一件东西：状态迁移的确定性

那就该到放弃的部分了。你们第一个要放弃的，是状态迁移的确定性——那个魔鬼就来自这个模型。

#### 确定性来自函数的定义

说到要放弃什么，就得说一说"确定性"这个概念。这个词有点拗口。所谓确定性，这个字面的含义我还是很喜欢的：数学就是一种确定性，它绝对明确、没有分歧、没有别的可能性，只有一种可能性。

那数学的确定性来自什么呢？来自函数的定义。你们在学离散数学的时候都觉得函数的定义很奇怪，为什么要这样定义？你们至少花了一些时间去适应它。然后你回头想数学里面的函数，比如 $f(x)=x^2+1$：这个东西就是存在（existence），它存在在那、确定下来了；你给一个 $f(1)$，它永远是同样的值。你不管在什么时间、什么地点调用这个函数 f，它总是、一定产生唯一的、确定的输出——这就是数学的确定性。正是这个确定性，使得全世界研究数学的人可以都说同样的数学语言、大家达成共识，数学才能发展，计算机科学才能发展。

#### 程序同样是确定的

程序的确定性和数学的确定性其实是类似的。不管我们说的是 Simple C，是一个 C 程序，还是比如 NEMU 的模拟器：一旦程序的状态确定了，我们的迁移也就确定了。迁移是一个函数——你有没有想过，你实现的 NEMU 本质上实现的就是一个函数 $f(s)=s'$？对于状态 s，你可以确定地算出它的下一个状态。虽然你可能会从外面再读一个随机数，那也是状态的一部分。它是一个确定的、至少在绝大部分意义上确定的数学意义上的函数，可以把一个状态变成下一个状态。

这意味着什么呢？意味着给定相同的初始状态，你这个程序运行多少次，它的输出一定是一样的。因为你的每一步都是确定的，根据数学归纳法，你整个程序的执行也是确定的。

> **结论**：确定性给我们一种可控的感觉——这个程序不会今天运行它是对的、明天它就不对了；这个测试用例只要代码不改，你今天跑是 pass 的，明天作业交上去它还是 pass，总是可以重复的。

这也是我们喜欢函数式编程（functional programming）的原因，如果你们学过 SICP 的话：它要求你把所有的东西都写成数学意义上的 function、pure function——一个绝对 deterministically reproducible 的东西。这是我们喜欢它的原因。

实际上，实际的程序也在某种程度上是确定的。假设你不调用什么随机数，程序所有的不确定性都来自于系统调用。当这个程序执行 execve 的时候，它的初始状态里面确实是有一些东西，比如它的地址空间是随机的、main 函数的地址是随机的，里面还有 auxv 这样的系统信息；讲链接和加载的时候说过，内核里的加载器会在栈上面放上一些信息，甚至包括随机数种子这样的东西。但是，一旦你的进程的初始状态确定了，实际上迁移的函数也是确定的——除了系统调用：read 是不确定的，你不知道我这次键盘按的是 a 还是 b。程序的执行是确定的，程序是可以理解的。

#### 线程的速度没有保证，确定性就此崩塌

而共享内存的并发打破了这一点，因为线程执行的速度是没有保证的。回到刚才那个例子：两个线程，一个在执行 x++，一个线程在执行 y++，还有第三个线程在读 x 和 y。你们看到那个程序的时候，只觉得我们很好地证明了线程之间确实是共享内存的，没有意识到它带来的可怕之处——我们中间使用了 sleep，使用了系统调用。

线程执行的速度是没有任何保证的。哪怕我就是 `x = x + 1`、`x = x + 1` 地做，两个处理器它的频率可能不一样，它当时的缓存也不一样，它执行的速度就是不一样的。

## 确定性丧失之后

### 共享内存让每一次读都不再有唯一答案

共享内存一旦用上，我的每一次读都可能读到别的线程写进去的值——这正是我们想要的，线程之间要靠它通信。但也正因为是共享内存，这次读可能读到，也可能读不到；这一次错过了，下一次就得到了。

于是程序的执行模型变了。单线程的时候，就是取当前进程、执行一条语句，一直往前走；现在有两个线程 T1、T2，我可以选 T1，也可以选 T2；走到下一个状态，我还是可以选 T1 或者 T2。每一步都是一次二选一，组合起来就是指数级的爆炸：可以走 1 1，可以走 1 2，可以走 2 1，可以走 2 2。

```text
状态 S0 ──┬── T1 ──► S1 ──┬── T1 ──► ...
          │                └── T2 ──► ...
          └── T2 ──► S1' ──┬── T1 ──► ...
                           └── T2 ──► ...
```

每一步选谁都不确定，走出来的历史是指数条，谁也不知道程序最终落在哪里。

> **结论**：今天你的测试通过了，你测了 100 万次都通过了，不代表交到 Online Judge 上就能过。

马上在编程作业、在 Mini Lab 上就会体会到这种不确定性：什么也没有写错，就只是一个最简单的线程，一个在单线程库上随手就能写的东西，不确定性就能带来巨大的麻烦。

### 山寨支付宝：检查和写入之间的那道缝

我们创建两个一模一样的线程，执行同样的代码，都是转 100 块钱出去。

设想我的账户里只剩下 100 块了，现在要执行转账，转的也正好是 100 块。转账的逻辑是：先看余额够不够，如果够，就把这笔钱扣掉，然后给对方账号加上；如果不够，就走 else 分支，什么也不扣。

现在你脑袋里要同时装下两个线程。两个线程同时做这个"余额够不够"的判断，而且它们运行得一样快，于是两个线程都认为：余额是够的。账户里只有 100 块，两个线程却各自扣了 100 块——我的钱不就变成负数了吗？

那扣成负数会有什么后果？如果余额是一个 unsigned integer，账户里就凭空多出了无穷的钱。

这样的 bug 未必是并发导致的，但它的形态无处不在。有一段时间——那应该是你们还没入学的时候——食堂附近有一台打印之类业务的机器，可以用类似的方式把自己的余额变成负的；一旦变成负的，就可以永远无限制地继续用下去。具体的 bug 我已经记不清了，但这件事我们应该是 reproduce 过的。

它的问题和上面那个 check 与写入分开的例子是同一件事：判断和动作之间有一道缝，别人可以从这道缝里插进来。

### 一块钱复制出两份物品

不只是理论上有这种问题，真实的并发系统里也有很好玩的 bug，这是个复制物品的 bug。玩法是这样的：

先把包裹打开，分离出一块钱；再把要复制的物品丢在地上；然后把包裹关掉——这时候地上就有了一堆东西。接下来用鼠标点击地上的物品，人物就会走过去把它捡起来。

关键在这一刻：你手上还拿着那一块钱，当你点击这一块钱的时候，程序收到了这个鼠标事件，它会把"这一块钱"这个对象写进你"当前拿起的物品"那个变量里；可就在人物马上要捡起地上物品的瞬间，你点了这一块钱——你刚写进去的那个"我拿起的东西等于一块钱"，被地上那个物品覆盖了。这应该是一个全局变量被覆盖。两个人同时往一个全局变量里写，先写的那个就被盖掉了。

结果就是：你的物品被复制成两份，用一块钱变出了两份物品。100 块钱分出去一块钱，变成两个 99 块，最后变成 198 块，可以无限复制下去。

前面那个例子是真实多处理器上的并行，这个是鼠标事件上的并发——机制不同，破坏力一模一样。

### 连 1 + 1 都不会求了

有了线程库以后你会发现，你连 1 + 1 都不会求了。

看这个程序：创建两个线程，两个线程都执行 $n$ 次 `sum++`，最后你还能得到 $2n$ 吗？得不到了。把这份代码编译运行，它是非确定的，运行若干次，每次结果都不一样。

原因在 `sum++` 本身：

```c
sum++;              /* 一行 C，实际上是三步操作 */
```

```text
sum++  =  load sum → r      （把 sum 读到一个寄存器里）
          r = r + 1         （在寄存器里加一）
          store sum ← r     （把寄存器写回内存）
```

我是一个 load、加一、store。在 store 写回去之前，别的线程可能已经执行了自己的 `sum++`，我那个旧值啪一下就把别人写的值盖掉了。

比如我读到了 1000，正准备把 1001 写回去；另一个线程已经读到 1001、1002、1003、1004、1005，一路写到了 2000；然后我那个 1001 一下把 2000 盖掉。

```text
T1:  load sum → 1000        （读到一个旧值，还在慢慢算）
T2:  load 1000，加一写回 …… 一路推进到 sum = 2000
T1:  把 1001 写回 → sum = 1001     ← 2000 被一巴掌盖掉
```

两个线程就这么互相读、互相覆盖，互相读、互相覆盖，最后加出来的数没加多少。

> **易错点**：`sum++` 看着是一行、看着是一条语句，但它不是原子的。你在单线程程序里写它的时候，永远不会想到它中间会被人插一脚。

更可怕的后果是：你连最简单的程序都理解不了了。

### 三个线程，第一反应是 3，答案是 2

这曾经是某一年的期中考试题，期末我也把它做成一道交 OJ 的题。它很可能就是你们的期中或者期末测验题，考的正是你对概念的理解到不到位。

题目是：创建三个线程，每个线程执行 `sum++`；`sum++` 就是先 load 把 sum 读到寄存器，把临时变量加一，再写回；执行的模型是每次任选一个线程执行一行语句。问：最后 sum 的最小值是多少？

你们第一反应肯定是 3。

这道 OJ 题的要求是：提交一个执行的交错顺序（比如 T1、T2、T1、T2 这样一条一条交错下去），使 sum 达到最小值。当时这题大家做得也是惨不忍睹。

题目的答案是 2。为什么可以是 2？因为可以构造出这样一段读写的顺序：

先让线程 2 读到一个 0，但它不着急写，先在那儿等着，等一个时机再把 1 写进去；接下来让线程 1 把自己那份循环里的每一次 `sum++` 都写完——先 load 0、store 1，再 load 1、store 2；写完 store 2 之后再让它做一次 load，这时候它会读到 1，读到 1 之后就在那里延时很长很长的时间，最后再把 2 写回去；然后把其他所有线程都跑完。

```text
线程 2 :  load sum(读到 0) ────────────── store sum = 1 ─────────┐
线程 1 :  load 0 → store 1 → load 1 → store 2 → load(读到 1)      │
                                            ………… 长时间等待 ………… │
                                                              store sum = 2
其他线程: 在「线程 1 最后一次 store」之前全部跑完 ─────────────────┘
```

最后一次写是线程 1 写下的 2，所以最终 sum 就是 2。

这个极限的构造对线程数不敏感：不管你有多少个线程，我都可以用这么一个非常极端的方式，让它最后得到一个 2。细节不重要，它本质上就是一个智力游戏。

### 排列事件的小游戏，与一个 NP 完全问题

这道题难在哪儿？我专门做了一个 Web 端的小游戏。

游戏里有好几个线程：绿色的是线程 2，蓝色的是线程 1，红色的是线程 0。一个线程内部的事件顺序是固定的、不许改——我不能把 T0 的第一个事件挪到 T0 的第二个事件后面；但这几个线程之间的事件顺序可以任意排。

每个事件读写了什么变量、读到什么值、写下什么值都是给定的。比如 T2 先读出 `x = 0`，T2 又写了 `x = 2`，然后 T1 紧接着两次读出 `x = 2`。我手上要做的是把这些事件拖成一条全局的顺序，使得每一次读都读到最近一次写进去的值——也就是让这些事件排成一个 1 2 3 4 5 6 那样的全序。

如果拖出来的顺序不对，比如 T1 先读出 `y = 0`（这是对的），紧接着又读出 `y = 2`（这就不对了），那我就必须打破原来的安排，把 T2 那句「`y = 2` 的写」挪到前面去，挪完了它才对。

随便换几次，你总会碰到一些怎么绕也绕不过去的题目。为什么会绕不过去？因为这个问题本身是 NP 完全的：我给你每个线程看到的读写历史，让你组合成一个全局顺序，这件事就是 NP 难的；也就是说，求这个 sum 的最小值本身就是 NP 难的，只能不断地尝试。

> **提示**：所谓「每次任选一个线程执行一条语句」的模型，对应的正是确定性图灵机与不确定性图灵机的区别——非确定图灵机（non-deterministic）和确定图灵机（deterministic）。单线程的程序模型和多线程的模型之间，有这种很深刻的理论关联。确定性丧失的后果，就是把一个顺序执行、只有 syscall 不确定的程序，变成了每一步你都不知道会选谁的模型。

### 人类为「正确的 1 + 1」困扰了很多年

这个后果困扰了人类很多年，实现 1 + 1 比你想象的要困难。

1960 年代，大家争相在共享内存上实现原子性、实现互斥——这个模型那时候就已经提出来了。所有人都想实现并发控制，实现正确的 1 + 1，而且只是两个线程的 1 + 1，但几乎所有的实现都是错的。一直到 Dekker 的算法，才有了第一个真正对的、能做 1 + 1 的算法。

后来 Peterson 的论文里有一段很有意思的话，说某个算法被 reformulate 了，原话是：

> Unfortunately, the authors believe the correct solution is incorrect.

连做科研的人写进论文里的算法都是错的。因为这些实现面对的是一个 NP 完全的巨大空间，你要证明一个东西正确，没有那么容易。

并发性打开的是一个魔鬼的盒子，它影响了计算机系统里你看到的一切东西，我们过去讨论过的所有东西，某种意义上都错了。

### printf 的缓冲区：并发改写了每一个 API

还记得 printf 那个例子吗？`printf` 有 fork 的时候，我们在终端上看到的 hello 的数量，和把输出管道给另一个进程时看到的数量是不一样的。当时我一度以为我眼花了，反复验证，最后才知道：printf 是有缓冲区的。

而共享内存的多个线程，共享的正是这个缓冲区。两个线程都 printf，一个打 A、一个打 B，它们打到同一个缓冲区里，也就是同时执行 `buf[position++] = ch` 这样的语句。

并发影响了计算机系统世界里的一切：你做任何一个 API 的时候都要考虑，不能像以前那样随手写一个 `buf[position++] = ch`，因为 1 + 1 做不对，所以这个也做不对。两个线程各写 100 万个字符，你不会得到 200 万个字符交错在一起的结果，你会得到一个乱七八糟的字符串：有些位置是空的，有些被覆盖掉了。

那 printf 还能用吗？系统的设计者替你兜了这个底。POSIX 手册里告诉你，printf 这一系列是线程安全的——但它是安全的，并不保证原子性。像 memcpy 也是如此：在两个线程里面对同一块内存做 memcpy，会出现 sum++ 那种结果——它不会把内存损坏掉，但最后的结果可能一部分是这个线程写的、一部分是那个线程写的，不过依然可以放心调用。

> **提示**：几乎所有的系统调用你都可以在多个线程里正确使用，read、write 都没有问题，只是它们的行为可能会有微小的改变。真正危险的是你自己去跟共享内存打交道。

### 性能就是钱，所以编译器要来改你的程序

我们一直在讲的是一个 Simple C 的模型：C 语言的程序是由栈帧组成的，有全局变量，每次从 top frame 取一条指令或者一条语句继续执行。这是 clear-cut 的、非常清楚的。我甚至一直在想，能不能找一个同学做毕业设计，或者做一个 hobby project，写一个 fully functional 的 Simple C 解释器，可以解释执行任何 C 程序——在操作系统上直接把一个有图形界面的复杂 C 程序在源代码层面解释起来，做一个真正可用的东西，然后我们就能在上面做好多好玩的事，就像调试器一样。

但是世界没有 Simple C 那么简单。所有人都想要极致的性能，因为性能就是钱：如果程序能快一倍，解决同样的问题就只要一半的机器，成本就能降到二分之一。在 DeepSeek 把 token 打到白菜价之前，用 OpenAI 的模型是非常贵的——所有人都要感谢 DeepSeek 把模型的架构砍成白菜价。你们现在没有这个感觉，一旦开始大量使用 token，就会发现大模型其实还是很贵的。

为编译优化奠基的 Frances Allen 在 2006 年获得了图灵奖；在编程语言领域获得图灵奖的人就更多了。极致性能是一个非常非常重要的话题。

在编译器看来，一份 Simple C 的程序里写着 `x++`、再一条 `x++`、再一条 `x++`，这些纯粹的计算都是可以优化的：一旦初始状态确定，纯计算到达的目标状态就是确定的，所以编译器很想把它直接优化成一条 `x += 3`。

但有一种东西不能优化：system call。当 `x` 要被送进 syscall 的时候，优化就不能跨过 system call 的边界——因为 syscall 之后可能还有 `x++`，syscall 之前的 `x++` 可以合并成 `x += 3`，但如果你把后面的也合并进来变成 `x += 4`，那 syscall 送出去的字符就错了。所以在编译器看来，system call 是绝对不可优化的东西。

```text
编译器：  x++; x++; x++;   ──►   x += 3        （纯计算，等价改写）
          x++; x++; x++; syscall(x); x++;
                    ▲
                    └── 跨越 syscall 的边界合并是禁止的
```

麻烦在于，这些优化全部建立在「程序是确定性的」这个假设之上：编译器假设不需要管别人在这个时候会不会把值改成别的。如果编译器要考虑任何一个别的线程能把值改掉，它就什么优化都做不了了。

### 把线程想象成人：举起来的旗子为什么等不到

并发编程里有一个我会反复讲到的视角：把线程想象成人。

每个线程都是一个人，人都有自己的大脑——你读不到我的想法，我也读不到你的想法，能互相读想法是一件很危险的事情。在 Simple C 的模型里，局部的、private 的东西别人是不能访问的；只要我这个线程不主动把指向自己堆栈的指针泄露给别人，别人就读不到我头脑里的思想。所以每个线程的栈就是自己的大脑，而全局变量是我们共享的教室里的物理空间——教室里所有人在同一个空间里，我可以拿这个东西，你也可以拿这个东西，这是可以同时发生的。

用这个视角来做一个线程间的协议。假设我想等某件事情：你把什么东西算好以后我再继续。那就给一个同学一面旗子，这个变量叫 `flag`，一开始 `flag` 等于 0：

```c
while (!flag)      /* 旗子还没举起来，我就一直等 */
    ;
/* 旗子举起来之后，继续执行 */
```

同学在某一刻把 `flag = 1`，旗子举起来了，我的 while 循环条件成立、退出，我就继续执行了。看起来挺对的，也应该能实现我们想要的功能。

但是它实现不了。因为在编译器的意义上，编译器认为没有人可以改这个 `flag`。

这是个循环，如果没有人能改 flag——想想编译器平时怎么做循环优化：循环里有个 `sum += x + 1`，它很聪明地知道 `x` 在循环里没有改过，于是可以把这段计算提到循环外面，`t = x + 1; s += t`，甚至把 `t` 直接放进寄存器。它一点一点地做等价改写，让代码越来越快。

用同样的手法改写 `while (!flag)`：既然没人能改 flag，那我根本不需要再读，可以直接把它提到循环外面做一个判断——如果 flag 已经举起来了，我就什么也不做、直接出去；否则，再也没有人能把旗子举起来，我这里就是一个死循环。

```text
优化前：  while (!flag) ;          /* 每轮都重新读一次 flag */

优化后：  if (!flag)               /* flag 被认为不会变，读被提到循环外 */
              for (;;) ;           /* 于是这里成了死循环，永远不会退出 */
          /* flag 为真时直接继续 */
```

很多有经验的系统程序员都会写这种 ad-hoc synchronization——他自己觉得这样好像还挺快的——然后就惹上大麻烦，在某一次编译的时候它就出问题了。这是上一个时代的论文里才会有的故事，在 AI 的时代大概不会再有人犯这种错误了。

> **提示**：如果你确实要控制编译器的优化行为，有两种办法——当然这不是操作系统课推荐的方法，你们不需要掌握。
>
> 一是插入 compiler barrier，比如 `asm` 里带 clobber memory 的那段：它是一段空指令，但告诉编译器"这段汇编可能修改任意的内存"，于是优化不能跨过这个边界，后面的 `x++` 就不能和前面的合并了。
>
> 二是一个变量标记成 `volatile`，让它不能被合并式的优化掉。访问 memory-mapped register 时通常也需要它：比如从设备读数据，我要先读一个字节把它扔掉、再读一个字节读进真正要的变量里，如果没有 `volatile`，编译器会把这两次 dereference、两次内存读合并成一次，而这是不能合并的。
>
> 操作系统课告诉你们的是：不要跟 shared memory 做游戏。两个线程同时访问同一个内存地址叫 race condition，也就是数据竞争，在 C 和 C++ 里它是 undefined behavior，非常非常危险。当然，在你确信这段代码会编译成什么样的二进制时，有时候还是可以利用这个特性的。

### 同一份代码，-O1 和 -O2 给出两个答案

回到求和。刚才说这个求和得不到正确的结果，这次我分别用 `-O1` 和 `-O2` 编译了两个版本，看看会发生什么。

结果很奇怪：**`-O1` 下 sum 变成了 n**，而且我运行好多次，sum 都是 n；换成 `-O2`，sum 又奇迹般地对了。同一份代码、完全相同的代码，在不同的编译优化下，行为差距非常大。

`-O1` 下编译器做了循环优化：它先把 sum load 到寄存器里，然后在循环里不停地把寄存器 +1、+1、+1，最后才 store 回去。也就是说，它把一次 load 提到了循环前面，把一次 store 放到了循环后面，中间隔着一个很长的循环。

```text
-O1：
  T1:  load sum ──── [寄存器里 +1 +1 +1 …… 很长一段时间] ──── store sum
  T2:  load sum ──── [寄存器里 +1 +1 +1 …… 很长一段时间] ──── store sum
                              ▲ load 与 store 相隔很远
                                两个线程互相互相覆盖，最后只剩一份

-O2：
  T1:  load sum ── x += n ── store sum     （只要几纳秒）
  T2:  load sum ── x += n ── store sum     （只要几纳秒）
                              ▲ 窗口极窄，两个线程几乎撞不上
```

这就跟山寨支付宝的例子一样：两个线程上来都先读到"我的钱其实是够的"，然后哗哗哗往后做，最后互相覆盖，不管谁覆盖谁，都只得到一份。所以在 `-O1` 下，sum 变成了 n。

`-O2` 下呢？整个循环都被优化掉了，循环都没有了，直接变成一个 load、加等于 n、一个 store。两个线程执行这一小段代码都只要几纳秒、几十纳秒。而线程创建是有先后的，操作系统调度也有先后，这两段代码能碰撞到一起的概率非常低，所以你就得到了一个看起来正确的结果。

> **易错点**：这才是最危险的。用 `-O2` 编译以后，程序完全正确，你测试了 100 万次，100 万次都完全正确；你很开心，把程序交付了。某一天，你的客户那边它就挂了，而你不知道为什么。并发和非确定性会和各种机制互相交织，带来你很难理解的行为。

编译器打破了"程序按你写下的 Simple C 语句 1 2 3 4 5 往后执行"这件事。而可怕的还在后面：从 `.c` 到 `.s` 的这一层，编译器已经在大杀四方了——它会做内联，把别的函数的代码直接粘贴到你调用的位置上，调用参数里有常数的就把常数也粘贴进去，一边粘贴一边做等价改写，程序越写越高效，有些代码成了死代码就被删掉。

### CPU 也是一个编译器

还没完。CPU 的运行模型我们都清楚——算你们写 NEMU 也都很清楚：有 register、有 memory，那就 fetch、decode、exec，走到下一个状态。这是确定性的。

对不起，这样的 CPU 太慢了。

我们的 CPU 也是一个编译器。比如 `rax = 1` 和 `rbx = 2` 这两条指令，确实可以不必顺序执行，我可以先执行后一条再执行前一条——因为如果程序是顺序程序，调换这两条指令顺序的结果一定是一样的。处理器只论结果，它只在中断、I/O 的时候保证把正确的数据送到外面就可以了，这和编译器保证把正确的数据送进 syscall 是一回事。

处理器还干了一件非常牛的事：它不仅可以调换这两条指令的顺序，还可以让它们在一个时钟周期里执行。没有任何道理阻止处理器同时 decode 不止一条指令：一个 cache line 是 64 个字节，我取指令的时候既然把这条指令取出来了，为什么不顺便把其他指令也译码了呢？于是 CPU 内部有一堆 instruction 1、instruction 2、instruction 3，它会做动态的数据流分析，知道指令 2 要等指令 1 的结果、指令 3 要等指令 2 的结果……把编译器做的那套事情在电路上又做了一遍。

```text
编译器：  x++; x++; x++;       ──►   x += 3          （等价改写，只论结果）
CPU：     rax = 1; rbx = 2;    ──►   rbx = 2; rax = 1 （乱序，只论结果）
                                    一个周期里执行 2 / 4 / 8 条都有可能
```

于是一个周期可以执行两条指令，甚至四条、八条，都是有可能的。有的指令执行得慢也不要紧：一条 load 或 store 因为 cache miss 卡住了，它可以继续去取剩下的指令，因为处理器里有分支预测器，能猜你后面的程序是怎么执行的，去执行那些不依赖前面结果的指令。

> **结论**：你手上有两层编译器，都在调换你的指令顺序。所谓"每次选一个线程、执行一条指令"的 shared memory 模型，这个幻想根本就不存在。

### 没有人知道 memory 到底是什么

实际上，我们的计算机系统为了性能，根本不是一个 shared memory。看起来好像是每一个线程都有一份它自己的 memory 的副本，它的 load 和 store 都是跟自己的那份 memory 打交道；这些 memory 副本之间怎么交互，你完全不知道，由硬件厂商随便实现——当然也不是完全随便，硬件厂商只要达成内存上的最终一致（eventual consistency）就可以了：比如现在所有 CPU 都不再执行 load 和 store 了，最后它们的 memory 会慢慢达成一致；或者直到我执行一条特殊的指令，说我需要让这段内存达成一致，这些分布式的 memory 才会互相通信、最终一致。

```text
        线程 1 的 memory 副本              线程 2 的 memory 副本
        ┌───────────────────┐             ┌───────────────────┐
        │   load / store    │             │   load / store    │
        └─────────┬─────────┘             └─────────┬─────────┘
                  └──── 交互方式未知，只保证最终一致 ────┘
                        （要强一致，得执行特殊指令）
```

这带来一个极度糟糕的问题。看这样一份程序，两个线程，T1 是 `x = 1; load y;`，T2 是 `y = 1; load x;`，我给这四个事件编个号：1 2 3 4。

```text
T1 :  x = 1        load y         （事件 1、2）
T2 :  y = 1        load x         （事件 3、4）
```

在这个模型上，程序可以按哪些顺序执行？

| 全局执行顺序 | `load y` 读到 | `load x` 读到 |
| :--- | :--- | :--- |
| 1 2 3 4（T1 先走完） | 0 | 1 |
| 1 3 2 4 | 1 | 1 |
| 1 3 4 2 | 1 | 1 |

按 1 2 3 4 执行，`load y` 读到的是 0，`load x` 读到的是 1。按 1 3 2 4 执行，1 和 3 先做完，x 和 y 都已经是 1，两个 load 就都读到 1；1 3 4 2 也是一样。

无论你怎么排列，1 和 3 里至少有一个先执行——在顺序意义上，2 不能在 1 前面执行，4 也不能在 3 前面执行——所以两个 load 里至少有一个会读到 1。你能看到 1 0，能看到 0 1，能看到 1 1，但你**看不到 0 0**。

可是按照"处理器也是编译器"的道理，你应该能看到 0 0。为什么？因为你写 `x = 1` 的时候是往自己的 memory 里写的，它还没有送到另外一个 CPU 的 memory 里去；你这个时候就去读，就读到了 0。这件事是可以在代码上直接观察到的。

> **提示**：为了把这个观察实验写对，我用了很多你们不知道的东西——atomic load、fetch 异或之类的。给你们的忠告还是一句话：Don't play with shared memory。

这份代码稍微有点长，跟前面举旗子那个有点像：有两个线程 T1 和 T2，它们会等我把两面旗子同时举起来，然后就一起执行，执行完把结果打印出来；我再把旗子放下来、举起来、放下来、举起来，反复运行。

理论上我们应该看到 1 0、0 1 和 1 1。但如果你真的运行，你几乎只能看到 0 0——因为处理器跑得太快了，我写完这个马上就去读，写完这个马上就去读；这两段代码几乎不可能出现"x = 1、y = 1 都被写出去之后才被中断"的情况，那是一个非常罕见的场景。

这也正是我喜欢 Unix philosophy 的地方：刚才那份程序是无限次地做实验，我可以用一个 `head` 把它截成有限次；做完有限次实验以后还可以排序，排序以后把相同的合并，用一个 `uniq`，于是我就得到了每一次实验的统计：

```bash
./race | head -100000 | sort | uniq -c
#  60000  0 0
#  40000  0 1
#   少量  1 0        （这跟我打印也有关系）
#      0  1 1
```

十万次实验，六万次是 0 0，四万次是 0 1，1 0 很少，1 1 一次都看不到。单是这一点就告诉你：你在并发程序上的所有认识都崩塌了。

### 放弃的是那个简化的模型

我们用这种模型来理解程序已经很久了，理解顺序程序的时候它很好用，我们上课一直也用它。但在并发里，它全部都崩塌了。

> **结论**：「从入门到放弃」里放弃的，不是不去做并发编程，而是放弃用这种简化的方式去理解并发程序——如果你还用旧模型去理解，你会丢失掉很多可能发生的行为，从而招致严重的问题。

编程世界里有不少这种"图方便，直接把刀子递给程序员"的机制。今天我们说打开了一个魔鬼的盒子：写线程的时候，共享内存确实挺方便的，但你发现你 1 + 1 都不会写了；因为有共享内存、因为有宽松的内存模型，1 2 3 你多数不对了。malloc、free、open、close，都有同样的问题。

在 AI 的时代，AI 是一个核动力的牛马——只要有电，它真能一直跑——我们就不需要这种图方便的刀子了。我们只需要在关键路径上，为了极限性能，适当地开放一点共享内存的能力，让它麻烦一点，这我觉得不是问题。

### 本讲提到的题目

**题干**：创建三个线程，每个线程执行 `sum++`（每个线程要把自己那份循环跑完）。`sum++` 相当于先做一次 load，把 sum 读到寄存器，把临时变量加一，再写回去。假设程序执行的模型是每次任选一个线程执行一行语句、每次执行一行。问：执行结束后 sum 的最小值是多少？

他也把它做成了一道交 OJ 的题：提交一个线程间的交错执行顺序（例如 T1、T2、T1、T2 这样一条一条错开），使 sum 达到最小值。

**解析**：直觉答案是把每个线程各加的那一次都算上，得到 3；但 `sum++` 不是原子的，load 与 store 之间可以被别的线程插进来，写回时会把别人刚写的值覆盖掉。要拿到最小值，就用正文里的极端构造：让线程 2 读到 0 之后先不写、等到时机再把 1 写进去；让线程 1 把自己循环里的 `sum++` 全部做完（load 0 → store 1，load 1 → store 2），再做一次 load 读到 1，然后延时很久，最后把 2 写回；其他线程在最后一次 store 之前全部跑完。于是全局最后一次写是线程 1 写下的 2。

**答案**：最小值是 2。这个构造对线程数不敏感——不管有多少个线程，都可以用这种极限的排法得到一个 2。

## 一次只让一个人进屋：互斥的原理、用法与代价
> 对应块：BLK27 | 覆盖分集：P14上 | 块标题（分集名）：《并发控制：互斥（上）》

### 为什么操作系统课要讲并发

上一节讲的是「多处理器编程从入门到放弃」。入门那部分是再简单不过的：一个线程库 `thread.h`，两个 API——`spawn` 把一个函数当成线程跑起来，它就能和别的代码并发、并行地执行（在真正的多处理器硬件上就是并行）；而且你确实可以验证：线程之间共享内存，各自拥有独立的栈。等这个函数返回，用 `join` 把它等回来就行。多线程程序的「使用」就这么点东西。

接下来就是放弃的那部分。只靠线程库加共享内存，你连 1+1 都算不对：两个或多个线程一起做 `sum = sum + 1`，暂时没有任何手段让它正确；你甚至连 1、2、3 这样的顺序都数不出来，因为 weak memory model 会给你各种各样的奇怪行为。我讲这些，不是教你们去 hack 这些行为，而是要告诉你们：你们打开的是一个魔鬼的盒子。

那为什么并发要放在操作系统课里讲？

UNIX 引入进程之后，进程之间是不共享内存的。fork 出来的两个程序副本各自独立运行，各有自己的地址空间，早期实现里真的就是把内存一个字节一个字节拷贝了一份。所以「不共享内存」这件事本来很省心：如果只有 `fork` 和 `execve`，两个副本各干各的，谁也不碰谁。

但是，**系统调用的执行是共享内存的**。一条 `syscall` 指令的行为，其实和你们平时写的 `jump`、`call` 很像，只是它附带一次权限切换：穿过 `syscall` 之前，应用程序是不被信任的——你不能随便动计算机硬件的任何配置，包括 I/O 端口、包括中断，动了操作系统的霸权地位就受挑战了；穿过 `syscall` 之后，就像全身麻醉把自己交给医生一样，程序恢复到高权限状态。而在这个时候，每一个进程在操作系统内部执行的那部分，就变成了一个线程。

> **结论**：操作系统是最早的并发程序。

一旦 `syscall` 开始执行，麻烦就来了。一个进程在内核里执行 `read(fd, buf, size)`，另一个进程同时执行 `write(fd, buf, size)`；内核代码执行的时候依然是可以被中断的，也可能真的有两个处理器分别跑着 P1 和 P2 的内核部分。如果它们碰的是同一个文件，上一节那些 1+1、数顺序的问题就原样出现在内核代码里。

```text
      P1（用户态）                       P2（用户态）
   read(fd, buf, size)              write(fd, buf, size)
          |                                 |
          |      穿越 syscall：权限切换      |
          v                                 v
   +-----------------------------------------------------+
   |        内核代码：同一块共享内存，同一份数据结构       |
   |   进程在内核里执行的那部分 == 一个线程               |
   |   可以在同一颗 CPU 上被中断打断，也可以在两颗 CPU 上并行 |
   +-----------------------------------------------------+
                  同一个文件 / 同一份内核数据
```

图里左右分别是两个进程的用户态代码，它们各自穿过 `syscall` 进入内核；内核代码本身是共享的，于是两个「在内核里执行的进程」就成了两个真正共享内存的线程。它们是同一份并发问题的两个来源：既可以在一颗 CPU 上被打断而交错执行，也可以在两颗 CPU 上真并行。

所以很多早期和并发相关的成果都来自操作系统研究者，我们在这里讲并发是顺理成章的。

### 我们真正想要的：让一段代码 make it work

今天就来解决上一节没解决的那个 1+1——你觉得 1+1 都不能求，这实在太糟糕了。

我们希望操作系统里、编程语言里都有一个机制或者一个 API，让我们能写 `sum++`。真实需求还不止于一个 `sum++`：可能是几个 `sum++`，也可能不只是变量，而是要更新一整个数据结构，把这一大段代码全都包裹进一个叫 make it work 的代码块里，然后它就自动 make it work 了。

至少我们可以做到的是：**让这段代码退回到不并发执行**。当 T1 和 T2 都想执行到这个代码块时，如果 T1 已经进来了，T2 就不能同时进来——一旦两个 `sum++` 同时执行，处理器就会出现各种奇怪行为，让你难以理解。所以，我这个线程在 `sum++` 的时候，别的线程就不能做 `sum++`；它至少要一直等到这个 `sum++` 确实完成、而且值真的写进内存了，才能开始自己的 `sum++`。相当于把本来能并发、能并行执行的程序，变得不能并发、不能并行。

对，只要把所有 `sum++` 都包在里面，1+1 的问题就解决了。恭喜你发明了一个很有意思的机制。

#### 顺着这个想法走到极致：transactional memory

顺着「把一段代码包起来」再往前想一步：这块代码可以很长，我可以写很长很长，比如更新一个数据结构，然后给它一个 `atomic` 把它包起来。包起来之后，里面的代码要么全部执行完——不管你写了多少个内存单元，哪怕几十个，退出的时候一次性全部写进去；要么就好像什么也没有写一样。要么 all，要么 nothing，二选一。

这样就能正确实现 `sum++` 了。因为 `sum++` 实际上是三件事：

```text
   sum++  ==  load sum  ->  临时变量 + 1  ->  store sum
                （读）         （改）            （写）
```

一次读、一次改、一次写。三步作为一个整体全部完成或者全都不发生，问题自然消失。

从大概 1990 年代开始就有人研究这个机制，叫 transactional memory。到 2010 年左右，Intel 甚至把两条指令 `xbegin` 和 `xend` 加进了指令集：写一个 `xbegin`，中间几条指令，再来一个 `xend`。但这个机制引发了很多问题，包括安全漏洞在内，所以现在在消费级的笔记本电脑上基本已经看不到了，服务器上这个特性依然有。ARM 也在一段时间里加过这个特性，后来好像也不想在指令集里维护它了——因为它又是一条可以和所有指令产生关联的指令，有点像 `fork`，会给指令集体系结构的实现带来很大的麻烦。

但这就是我们想要的：make it work。

### 单处理器内核的土办法：把中断关掉

先岔开一下。如果你在一个单处理器系统上，而且你写的是操作系统内核代码，那要实现刚才那个 make it work，有一个非常简单的方式：**把中断关掉**。

设想现在只有一颗 CPU。把中断关掉，就意味着这颗 CPU 完全被我独占了。回到状态机模型：我们的模型从 firmware 的 CPU restart 开始执行 firmware、执行指令，但有一条我没有明说的是——每一条指令执行的时候，如果这颗 CPU 的中断处于打开状态，它就还有可能响应中断。

```text
   某个确定性状态 --[执行第 k 条指令]--> 下一个状态
                              |
                              +--> 若中断打开：可能被中断，跳去处理中断
                              |
                              +--> 若中断关闭：只能按指令语义继续往下走
```

> **结论**：计算机系统其实是非确定的，它在任何时候都有可能被中断。这就是操作系统内部并发的来源——中断是并发的来源。

但如果你把中断关掉，这种可能性就没有了。这个时候，假设指令集本身是确定性的（deterministic），那么我执行 `x = 1`、执行 `y = 1`、PC 取下一条指令、再取下一条，它执行的一定是相同的代码，是完全确定的。所以我只要在内核里把中断关掉，就实现了 make it work：系统的其它任何部分都再也不能打扰我了。

代价也很直接：如果你在内核里写了一个 `while(1)` 死循环，而且是关着中断的，这台计算机就死掉了。这就是为什么机器上会有一个 reset 按钮（CPU reset）。在软件工程还不成熟、大家还不知道怎么构造一个可靠操作系统的时候，Windows 蓝屏那是家常便饭——它经常有 bug，出 bug 以后可能卡死，也可能就蓝屏了。

当然，单 CPU 上关中断管用，是因为「关掉中断就真的没有别人了」。一旦世界上的别人不止一个，这一招就不够了：

```text
   只有一颗 CPU：关中断
     CPU0 [========== 内核代码，世界只剩我 ==========]

   有两颗 CPU：关中断只关掉了自己这一颗
     CPU0 [========== 我关了中断，没人能打断我 ==========]
     CPU1 [========== 别人照样在跑，它管不到 ==========]
```

### 为什么普通线程用不上这一招

我让 AI 写了一段「关掉中断、然后去死循环」的代码，需要借助一点点汇编，而且做了条件编译——在我的机器上你能看到它用一条 MSR 指令去写一个系统寄存器，把这个寄存器里的中断位消掉；在 x86 上也一样，有一条清中断的指令（clear interrupt）。你在计算机系统基础里学过的那个 flags 寄存器里，除了 overflow flag、zero flag 这些「上一条指令的结果是不是 0、是不是溢出」的标志位，还有一个位是操作系统内核可以控制的，就是中断位（interrupt flag）。把它清掉，处理器就进入不再响应中断的状态。

运行这段程序，你们肯定会预期这台机器不会卡死。结果我这里收到的是一个 SIGILL，非法指令（illegal instruction）——你在 x86 系统上很少见到它，但你可以试着把二进制文件胡乱改一改，它没法译码解码那条指令的时候，就会给你一个非法指令。

这份代码在两边的待遇是一样的，都是「你碰不到」：

- 在 ARM 上，用户程序不能执行那条 MSR，甚至这条指令都是不合法的、不存在的——它会认为你没有权限执行，你看不到这条指令，于是得到 SIGILL；
- 在 x86 上，用户态执行清中断会得到一个 protection error，也就是 segmentation fault。

> **易错点**：这里的 SIGILL 与 segfault 不是代码写错了，而是指令集体系结构的刻意设计——关中断这条门只对内核开。

好，这正是操作系统内核想要实现的效果：关中断与开中断，就是一对「我要开始这段关键代码了 / 我要离开这段关键代码了」的开关。把这个想法稍微扩展一下，普通线程能用的版本就出来了——**互斥的 API**。

### 互斥：临界区与 lock / unlock

所谓互斥，就是互相排斥，mutually exclusive：两个人不能同时进入一段代码。

> **定义**：被这把锁保护的那段代码叫 critical section，临界区。你在很多教科书上都会看到这个词。它就是一段代码。

我们要实现的接口是：任何线程都可以执行 `lock`；`lock` 返回以后我就可以执行任何代码，比如 `sum++`；等我觉得这段代码 OK 了、不再需要「别人不能和我一起并发执行」这个很强的保证，我就 `unlock`。`lock` 和 `unlock` 其实就是把并发给消除了——当我 `lock` 返回的那一刻，我就再也不能和别人的 `lock` 代码块并发。

#### lock 与 unlock 的时序

把它画在时间轴上，和刚才的 T1 是一样的：如果我 `lock` 并且它返回了，返回以后我可以做任何事，直到我 `unlock`。对于其它线程，不管有多少个，无论什么时候 `lock`，只要在这个时间点上别人还没有把锁释放掉，`lock` 就不能返回；它就等等等等等，直到 T1 把锁释放掉，T2 这个 `lock` 才能返回，返回以后再做它自己的代码。如果还有 T3 也执行了 `lock`，那它必须继续等下去。

```text
T1   ---- lock 返回 --- 任意代码（sum++ …） --- unlock ---->

                    |                        |
T2   ---- lock ---- +----（等）……（等）------ + --- lock 返回 --- 代码 --- unlock ---->

T3   ------- lock ----------（继续等）-------------------------- lock 返回 ---->

         ^ 别人没有 unlock，lock 就不返回                ^ 轮到自己进屋的时刻
```

这样就把所有并发都消除了，你得到的是一个确定的顺序。它未必是绝对确定的，但至少你能排出个一、二、三：第一次 T1 的 `lock` 返回、T1 的临界区执行、T1 的 `unlock` 返回；然后才轮到下一个。

#### unlock 不只是「放行」：可见性

`unlock` 还有一个额外的语义：它会保证所有在这个地方写的数据全部进入内存。不会像之前那样——我在这里写了 `x = 1`，`unlock` 之后再进来的人，`load x` 的时候一定能看到这个 `x = 1`。

这就是为什么 `lock`/`unlock` 也叫 acquire/release：`lock` 是你去拿钥匙的过程（acquire），`release` 是你把钥匙放回去的过程。你在 C++ 的内存模型文档里会看到 acquire semantics、release semantics 这种说法，讲的就是这件事——可见性：你 acquire 的时候，必须能够看到别人 release 之前写入的内存。

> **提示**：这些细节你不需要知道得这么细。你只要知道，只要所有代码都正确地使用 `lock` 和 `unlock`，答案就是对的。

### 锁的两种比喻：房间与钥匙

如果你把线程想象成人、把共享内存想象成物理空间，那么「锁」有两个很好用的解读视角。

第一种是**房间**：有一个小房间，房间里面只能容纳一个人。任何人进去以后都会把门锁上，别人就进不来了；进去的那个人就是拿到执行权的线程，他可以在里面继续做事。别人想执行同一段代码，就必须在 `lock` 的时候把房门打开、进屋才能执行；如果很多人同时想进这个房间，那就只有一个人能进去，其他人只能等，等到前一个人把房间的使用权让出来。

第二种是**桌上的一把钥匙**：`lock` 需要先得到钥匙才能继续执行。很多人同时想执行 `lock`，都会去摸那把钥匙，但物理空间里只有一把钥匙，所以只有一个人能摸到；摸到的人继续执行代码，`unlock` 的时候把钥匙还回来，剩下在等钥匙的人就可以把它再拿走。

两种解读说的是同一件事，也解释了 acquire/release 这对名字：acquire 是「去拿」的过程，release 是「放回去」的过程。

### 光有锁还不够：没用锁保护的那一行依然会错

现在你可以把 `sum++` 包在 `lock` 和 `unlock` 之间了。第一次 `sum++` 得到 1，第二次得到 2——只要每一处都在锁里面，就没有问题。

但如果你有一个 `sum++` 没有锁保护，那肯定还是不行。这相当于我们世界里的人要达成一个一致：只有进屋的人、只有拿到钥匙的人，才能做下一件事；你不遵守这个约定，没拿到钥匙就去做，那就错了，就会有麻烦。

> **易错点**：锁不会自动保护「共享变量」这个抽象概念，它只保护你把代码包进去的那些行的执行。少包一行，那一行就是上一节那个能算出错误的 `sum++`。

### 多把锁：不同数据用不同的钥匙

这个世界当然不必只有一把钥匙、一个房间。我们可以创建好几张桌子、好几种钥匙，访问不同变量时选不同的钥匙。

比如有两把锁，一个叫 lock A，一个叫 lock B。我可以在 acquire lock A 的时候做 `x++`，在 acquire lock B 的时候做 `y++`。这没有问题：如果有一对线程做 `sum++`、另一对做 `x++`，`sum` 和 `x` 是不同的内存地址，它们之间本来就不会互相干扰。那我只需要正确地在各自的临界区里用对应的那把锁，就能正确实现至少「x + 1」这样的互斥，不会再观察到入门到放弃那一段里的奇怪现象。

### 把 1+1 真正写对：mutex 与 sum.c

我们终于可以在今天学会写 1+1 了，不容易，这是一个很重要的里程碑。

线程库里面除了 `threads.h` 以外还有一个 `thread-sync.h`，所有和并发控制相关的代码都在这个头文件里。想要创建一把锁，就创建一个互斥锁（mutex），你也尽可以就叫它锁：`lock1`、`lock2`、`lock2` 想创建多少把都可以。

> **易错点**：对同一个变量的访问，必须用同一把锁把它保护起来。锁的「身份」不是变量名，而是你 acquire 的那一个对象。

`Tsum` 稍微麻烦一点：如果我要做 n 次 `sum++`，就把中间实际要做的事情包在 `lock` 和 `unlock` 之间，中间可以干任何事。这里我故意做了 10 次 `sum++`，并且在中间加了一个 compiler barrier，让编译器不要优化——如果我不加它，编译器会把这 10 次优化成 `sum = sum + 10`，那就变得很短了。加上这个 barrier 之后，编译器每次都必须老老实实做一次 load、加一、store：

```c
lock(&mutex);
for (i = 0; i < 10; i++) {
    sum++;              /* 一次 load、一次 +1、一次 store */
    compiler_barrier(); /* 拦住编译器，别把这 10 次合成 sum = sum + 10 */
}
unlock(&mutex);
```

于是这段临界区里会有 10 次 load、10 次计算、10 次 store——这其实已经算是比较长的一段代码了。如果发生并发或者并行的同时读写，肯定会出现上一节看到的那些问题；但有了 `lock` 和 `unlock`，这段代码所有可能的并发都被阻止了，你就预期它能得到正确结果。

编译运行一下，看起来没有问题。你可以多跑几次，至少在一定程度上相信：`lock` 和 `unlock` 确实给了你正确的互斥。

### 用对了锁，就可以当作 stop the world

学会互斥以后，怎么理解它、怎么在实践里用它？有一个简化的视角。

前提是：你**正确地**使用了互斥锁。在这个前提下，执行 `lock` 相当于执行了一个 stop-the-world——就像 JOJO 里那个「The World」的替身，它可以瞬间停止世界上所有其它的部分，而自己依然可以活动。

这个模型下，你 `lock` 之后可以随便做：可以 `sum++`，可以 `x++`，可以对共享内存干任何事情，然后 `unlock`；在 `unlock` 的一瞬间，你对这个世界施加的作用就全部成立了。

那为什么我 `lock(A)`、别人 `lock(B)`，而且我和他甚至跑在两颗不同的 CPU 上，我还可以认为自己 stop the world 了呢？关键就在「假设你能够正确地使用锁」这句话上。

如果锁用得正确，那么我在临界区里读写的所有变量，在外面都是不相干的。我在里面读 `x`、读 `sum`，就不可能同时有另外一个人写 `sum`——如果有，那你的实现就是错的。既然世界被停下来了，我在临界区里做很多次 `t = sum` 时必须看到同一个值。所以「正确性假设」的意思就是：别人永远不会写我读过的值。

> **结论**：T1 和 T3 在实际当中真的是并行同时执行的，但你在理解程序执行效果、理解程序执行结果的时候，可以把这一段程序的执行挪到后面或者挪到前面。无论按哪种顺序执行，结果都一样。所以我们理解的时候好像是 stop the world，实际上它还是并行的——这个模型依然好用。

这和内核里关中断是一回事：如果只有一颗 CPU，关了中断，这世界上真的就没有别人了，那确实实现了 stop the world；如果世界上哪怕还有别人，别人执行的效果也可以挪到前面或者后面，不会影响我看到的东西的正确性，所以「就好像」是 stop the world。

这就是互斥锁的价值：上对锁以后，上一节那些复杂的东西都没了，因为程序变成了顺序的程序——我们所有的编译优化、我们以前理解程序的方式又回来了。人类本质上是一个 sequential creature：在讲并发的时候，我们把线程比作人、把物理空间比作 shared memory，而人类做训练的时候从来只做好自己的就行，神经网络从来没有「同时推进多个人一件事」这回事。人类天生不擅长处理多头绪，除非专门训练过。计算机也一样，一个线程是 sequential 的；当多个线程可以互相影响的时候，你的脑子就炸了。而通过并发控制（比如互斥）达到 stop the world 的效果以后，理解这个程序又回到了你熟悉的顺序程序执行。

### 一万种用错锁的方法

上面那个模型有一个前提：**假设你的使用是正确的**。但你有 1 万种方法把它用错。

自从 acquire 和 release 这个 API 被设计出来开始，人类就走上了万劫不复的错误道路。这话说得夸张了点，但我可以毫无疑问地说：现在 Linux 内核里面还有数不清的、和锁相关的问题。因为 `lock`、`unlock` 都是程序员负责的——这和 `malloc`、`free` 一样：你记得 `malloc` 之后一定要配一个 `free`，但你做不到；你记得每一个 acquire 后面必须有一个 release，但你在函数的第一行写了 acquire、最后一行写了 release，中间有一个 `return`，这个程序就错了。

你说「我不会犯这种错误」，那是因为你只写一个文件里的代码。但真正有几十个文件、几十把锁的时候，你确实很难把它弄对。

#### acquire 与 release 配不上对

这种错误甚至不需要很复杂的代码。就像上面那个「中间有个 `return`」的例子：写代码的时候一切看着都好好的，函数开头 acquire、结尾 release，中间随便加一个提前退出，锁就再也没被释放，别人就永远等下去了。

#### 同一份数据配了两把锁

再看这个错误：

```c
lock(&l);  sum++;  unlock(&l);
...
lock(&i);  sum++;  unlock(&i);
```

看起来两处都是「同一把锁保护 `sum++`」，但你仔细看——一个是 `l`，一个是 `i`。因为 `l` 和 `i` 长得很像，这个错误你一眼扫过去根本看不出来，可 `l` 和 `i` 是两把锁，它们之间是可以并发的，形同虚设。

不要笑，这就是「小丑就是我自己」——我也经常犯这样的错误。现实中真的就是几十把锁、几十个文件、函数互相调用，谁都搞不清楚的时候，没有人能相信自己记得住。你经常能看到 Linux 内核里的人在讨论锁的问题：有一些动态检查工具可以在运行时检查你哪里漏上锁了，它已经查出来了，然后大家在里面对论到底是谁出的问题、应该怎么修。

> **提示**：还有些是在逻辑上就注定难的——一旦系统里要引入很多把锁，出错几乎是必然的。你也马上会在 lab 里知道，这里面有很多微妙的地方必须想清楚。如果世界上只有一把锁，说「我需要原子性、需要 stop the world」，那就 lock 再 unlock，这个世界就是简单的；否则，你要手工去管理复杂的锁，那就麻烦了。

### 并发数据结构的锁地狱：一条链表

举一个例子，链表。实现一个链表，你当然可以让世界上只有一把锁：一个链表一把锁，把锁锁住就可以访问整个链表。

但如果你要实现一个性能还过得去的并发数据结构（今天的 reading 里就有 concurrent data structure），你就不能用一把锁保护链表节点里面的所有东西——链表的每一个节点都要有一把锁。这就带来麻烦了。

你们的双向链表代码本来是那么简单的概念，你们都实现过：它有一个 `prev`，一个 `next`。可如果你想要遍历这个链表，你应该怎么办呢？答案是：**一边上锁，一边解锁**。

```text
      prev              cur               next
    +------+          +------+          +------+
    |      | -------> |      | -------> |      |
    +------+          +------+          +------+
                        [锁]              [锁]

   遍历时每一步的动作顺序：
     1. 此刻我持有 cur 的锁
     2. 先 acquire next 的锁        <-- 把 "cur -> next" 这条链接关系锁住
     3. 到达 next 之后，才敢释放 cur 的锁
     4. 站在 next 上，重复第 2、3 步
```

注意这里的关键：我持有当前节点的锁时，**不能**先把它释放掉——释放了就错了。我在持有这个节点的时候，首先要拿到下一个节点的锁，这样就相当于把「这个节点到下一个节点」的链接关系给锁住了；链接关系锁住非常重要，不然真的会错。等到我到了下一个节点，才能释放上一个节点的锁，再去试图 acquire 下下一个节点的锁。要保证这中间链接关系不发生改变。

你看，光是遍历就已经这么复杂了，你还要考虑插入和删除。它们都需要拿到 previous、current 和 next 三把锁。最麻烦的是删除之后的内存回收：你什么时候可以把这个内存回收掉？必须确保没有人还可以持有一个指向这个节点的引用的时候，才能把它回收掉。这件事比你想象的要困难，而且你们马上做 lab 的时候就会知道，这里面有很多微妙的地方必须想清楚。

所以「我想要 make it work」这个想法的含金量还在上升。你真正想要的是：写一个链表，然后说一句 make it work，让一个好的编译器把它翻译成高效的东西，而不是由你手工去翻译——并且它还能保证你是对的。也许离这一天我们也不远了，到那时候，我们讲的这些东西很快也就都用不上了。

### 新手建议：一把大锁保平安

操作系统课给你们的建议是：因为你们是第一次做并发编程，在可以的时候，**只需要一把锁就够了**。只有一把锁的时候，事情就简单了——但凡可能共享的东西都要上锁，而且都上同一把锁。

代价是把上锁的时间延长一点：从你要干这件事开始就持有这把锁，直到这件事全部干完再释放掉。别笑，看起来很蠢，但 Linux 内核在最早期、从单处理器迁移到多处理器的时候，干的第一件事就是引入一个东西，叫 Big Kernel Lock，缩写 BKL。你看这个名字就知道——big，一把大锁，所以叫「一把大锁保平安」。有这把大锁，你的实现就是对的，它没走错。

从单处理器到多处理器本来是件很可怕的事：单处理器的时候，我关中断就行了，全对——想保护 `sum++`，关中断、`sum++`、开中断，就完了。但到了两颗 CPU 的时候，这件事就不 work 了，必须找一个更好的机制。可它又不敢一下子写几万行代码，把锁一路拆到每个链表节点都拆开：那样做引入很多 bug 以后，整个内核可能在很长时间里都无法运行，都得修 bug。

所以它是从一把大锁开始，慢慢往小里拆：先找那些对性能影响非常关键的地方，把大锁拆成几把小锁，并且要做好充足的压力测试。

### 先把意图表达清楚，再谈优化

有一句话来自 Knuth，就是写《计算机程序设计艺术》的那位：

> premature optimization is the root of all evil.

你们写程序时可能有一种倾向：这里我写 `x = x * 2`，是不是编译器会把它编译成一条乘法指令，所以我该把它改成左移两位？千万不要干这样的事。编译器比你想象得聪明；而且你在绝大部分时候脑子一热做出的优化，根本不在那个关键的性能瓶颈上，所以你做了优化其实可能未必比没做更好，还给理解代码造成了麻烦。

**正确的途径是：先把你的代码想要做什么准确地表达出来。**你现在就是想要 stop the world，那就是你想要的，先表达出来；然后再慢慢优化那条真正导致瓶颈的路径。

这是一个警告，当然这种警告我说多少遍都是没用的。你后面这个星期的 lab 是要做一个线程安全的内存分配，`malloc` 和 `free`：你拿一把大锁，「easy test」就过了，完全正确；等你要把性能提上去、需要过「hard test」的时候，就得把锁拆开——一旦锁拆开，你会发现连 easy test 也过不去了。因为在非常大的压力下，你那个 `sum` 就好比有好几个地方要管理锁，你还得保证 `sum` 加完以后必须是那个对的值；只要有一点点小错，在压力负载下就会冒出各种各样奇怪的问题。

### 上了锁就没有并行了，为什么还要线程

学到这里，通常会产生一个疑问：`lock` 和 `unlock`，和并发、并行的动机是冲突的。

想一下：我们有 64 个、128 个处理器，可以同时执行程序；可一旦上了锁，它不就不能并行了吗？它退回到按 1、2、3 的顺序串行执行，而且因为有多个处理器之间的一、二、三协调，甚至比在单处理器上执行还要慢。既然都不并发了，我们为什么还要线程？

这里有两个很有意思的理论结论。

#### Amdahl's law：不可并行的部分说了算

第一个名气更大，叫 Amdahl's law（阿姆达尔定律）。

假设一个程序里有 1/2 的代码是不能并行的，比如你要先算一个素数表，这段花 1 秒；后面还有一大堆可以并行的代码，甚至并行得非常好，也花 1 秒。那么无论你的并行度有多高——哪怕可并行那部分的时间消耗是 0，哪怕你有 1 万个 CPU 在上面跑——你也只能加速一倍。

把它写成式子就很清楚：串行部分占比为 $f$ 时，加速比的上限是 $1/f$。$f = 1/2$，上限就是 2。

这个分析是对的。但实际情况不完全是这样的，还有一个更细致的版本。

#### Gustafson's law：更乐观也更贴近现实

第二个叫 Gustafson's law。它说的是：如果你不能并行的部分非常小，小到接近 0，而可以并行的部分非常非常可并行，那么你在有多少个处理器，就可以得到多少倍的加速比。这个结论的证明还挺有意思的，有兴趣的话你可以跟 AI 对话一下。

这个乐观的结论对我们来说更有用。

| | Amdahl's law | Gustafson's law |
|:---|:---|:---|
| 不可并行的部分 | 占比不算小（例如 1/2） | 非常小，甚至趋于 0 |
| 结论 | 再多的处理器也有加速上限 | 有多少处理器，就有多少倍加速比 |
| 对我们的启示 | 串行部分是天花板 | 现实程序里真正必须串行的部分其实很少 |

那这个乐观结论该怎么解读？如果你要算一个很大的东西，能够并行的部分是绝大多数，你只需要有很少、很少的地方用 `lock` 和 `unlock`，剩下的都是可以并行的代码。

### 物理世界是有局部性的

为什么这一点能成立？因为**我们的物理世界是有局部性的**。

我们一直说把自己想象成线程、把物理空间想象成 shared memory。那么每一个人都只占据自己的物理空间；要访问别人的物理空间，只能访问相邻的——我不能瞬间去访问太阳系任何一个地方的空间，不然我们就不需要发射火箭去探索月球了，我直接伸手把月球上的月壤拉过来就可以了。这件事我们做不到。

这意味着什么呢？假设我们要模拟一个物理系统——今天做天气预报、做神经网络、做各种各样的东西，都是这样的套路：做的第一件事就是把一个很大的、要模拟的网格世界切开，切成一块一块的计算任务。

```text
   +-------+-------+-------+-------+
   |       |       |       |       |
   |  块0  |  块1  |  块2  |  块3  |
   |       |       |       |       |
   +-------+-------+-------+-------+
   |       |       |       |       |
   |  块4  |  块5  |  块6  |  块7  |
   |       |       |       |       |
   +-------+-------+-------+-------+
   |       |       |       |       |
   |  块8  |  块9  |  块10 |  块11 |
   |       |       |       |       |
   +-------+-------+-------+-------+

   每一块用自己的数据算：并行、不上锁
   块与块的边界要交换数据：这里才需要交互、才需要上锁
```

每一块计算任务会用到它自己的数据，也可能会用到它边界上的数据；边界上的数据需要和别人交互。但绝大部分数据都是自己的。所以**一块里面的计算量，远远大于它需要和别人交互、需要上锁的那部分计算量**。

也就是说，我可以把任务切分成好多好多块比较均匀的部分，绝大部分计算都是独立完成的；独立完成就意味着我读写的这块内存别人不会读、不会写——别人不会读也不会写，就意味着这里完全可以并行，不需要上一把锁。

这样的例子不只在物理模拟里有。比如图书馆里一本一本的书，它天生就是独立的，每个同学可以拿一本书来读。拿书的时候你们会共享那个书架，必须要上好锁，需要一个数据结构来维护那个书架：两个同学同时看中同一本漫画书要去抢的时候——就相当于执行 `sum++` 的同时想从图书馆那个数据结构里 `pop` 一个东西出来——你必须上锁。这个过程是需要上锁的。

但是书一旦拿到我手上，它就变成我的 private memory 了，没有人能访问它。虽然它还在那个地址空间里，但世界上只有我现在能访问它，我就不需要再上锁，我就可以看书。所以看书的过程是可以并行、而且不需要上锁的。

再推广：索引整个互联网上所有的页面、训练深度神经网络（我们的大脑也是并行的，神经网络的训练也是并行的）、复杂问题的搜索——比如下围棋时一层一层地搜索，我们做过一个 fork-based 的 DFS，每次 fork 一个，在 DFS 要创建几个分支的时候就为每个分支创建一个进程，不用几层就能有几万个进程同时向前执行，它们又是可以并行的。同样的道理也可以用线程的模型来建模。

> **结论**：这并不矛盾。我们在做并发控制的时候，控制的只是那些关键的数据结构；我们可以在关键的数据结构里放一些需要执行很长时间的任务，而这个任务本身是不需要上锁的。这样依然可以用多个线程实现很高的并行度。所以虽然并发控制让我们退回到了串行，但真实的并发和并行程序里，真的需要串行的部分是非常非常少的。

### 用手工协议实现互斥的那些年

互斥的概念和使用讲完了，接下来看历史上的一个问题：`lock` 和 `unlock`、acquire 和 release，到底是怎么实现的。

#### Dekker 算法：1965 年的第一个正确解

早在 1965 年，我们有了第一个正确的、或者说公开的（publicly）正确算法。注意那个时候用的还不是线程，是进程——就像今天说的，操作系统里每一个进程都有一份共享内存的线程在执行，那是 process 的一部分；那个时候 thread 还没有在操作系统里出现。

它的描述是这样的：一个进程 P 能够进入临界区，if the other does not want to enter，如果别人不想进；否则，它只有在轮到它的时候才能进（only if it is its turn）。

听不懂，确实是绕口令。相关的材料里有一张图，是整个协议所有可能的状态（状态空间），也解释了 Dekker 的算法是怎么工作的——那段代码看起来很奇怪，一般操作系统书上都会讲。我不打算细讲 Dekker 算法，因为人类花了很长的时间在头脑风暴当中去想到各种各样的奇妙算法。

#### Peterson 算法：宿舍卫生间的协议

一直到 1981 年，才出现了大家可能真的觉得比较满意的算法——虽然它还是绕口令。

它的描述是：一个进程 p 能够进入临界区，如果别人不想进（the other is not）；或者，它已经表明了自己想进的意愿（it has indicated this desire），并且把「轮次」让给了另一个进程（and has given the other process that turn）。

完全不知道它在说什么。哪怕你看到那一小段非常短的代码——它和所有经典教科书上都是一样的：

```c
A = 1;                        /* 我想进：举手 */
term = B;                     /* 把轮次让给对方 */
while (B && term == B) { }    /* 别人想进、而且轮次还在对方手上：等 */
/* ---- 临界区 ---- */
A = 0;                        /* 我不想进了 */
```

（右边的 barrier 先忽略。）如果是 A 这个进程：`A = 1`、`term = B`，然后它会不断地等待——如果「not B」就 break，可以进；如果 `term` 不等于 B 也可以进。然后它就可以进入临界区；出去的时候 `A = 0`。

有点费解，对吧？有点费解。没问题，我们来讲一讲，看看那个时代的人是怎么解决并发问题的。你们所熟悉的仙林校区宿舍的卫生间，应该还是长这样的吧——Peterson 算法，他做了一个协议。

我需要两位同学来做帮手：一位 Alice，一位 Bob。Alice 手里拿着 Bob 的名字，Bob 手里拿着 Alice 的名字。这个操作暂时不知道是为什么，那我们可以先看一下——如果你想进入这个房间，你的协议是什么？

首先，Alice 要举起自己的手（想进房间的人要举手）；然后在不管任何事情的前提下，把手上那张名字贴到门上。这个时候，门上有一个名字，手也举起来了，她对整个世界的状态的修改就已经完成了。

把这两个动作和上面那段代码对起来看：

```text
   Alice 的协议                             代码里对应的动作
   1. 举起自己的手（我想进）                  A = 1
   2. 把手里 Bob 的名字贴到门上（让出轮次）    term = B
   3. 再看：对方还举着手吗？门上的名字          while (B && term == B) { }
      还是不是对方？是，就继续等
   4. 可以进去，执行临界区的代码
   5. 出来：把手放下                          A = 0
```

她贴名字这个动作，等于先把「轮次」让给了对方；她接下来能不能进屋，就取决于门外那只手和门上那个名字的状态。那个年代的人，就是用几个共享变量、一套读起来像绕口令的协议，硬生生地把「两个人不能同时进屋」写成了确定的事实。

## 互斥的工程化：原子指令、futex 与量化对比
> 对应块：BLK28 | 覆盖分集：P14下 | 块标题（分集名）：《并发控制：互斥（下）》

上一节我给出了 Peterson 算法的正确性证明，代码里那份 model checker 也把证明又验了一遍。顺带说一句，那个 model checker 就是在"这件事能不能做"这个问题被问出来之后做出来的——我一直坚持让你们多和 AI 对话，因为它是一种可以 scale 的智能：你拥有它、控制它，就能以比过去快得多的效率学到新东西。

但今天我要先说一件让人不舒服的事：那些证明全都是有假设的，而且做了过度简化的假设。

### 上一节的证明都建立在假设之上

这些证明的假设不外乎三条：

- 线程只在某一个特定位置才可能发生切换；
- `load` 和 `store` 指令瞬间完成、并且立即生效；
- 指令严格按程序书写的顺序执行。

放在 1965 年，这三条合情合理：那时既没有高性能编译器，也没有多处理器。在他们眼里，所有计算机都符合这个模型——一条指令执行完了才会执行下一条。这就是他们那个时代计算机的样子。

但按上一节的内容，后两条显然都不成立。所以今天我可以明确地告诉你们：照那样写出来的 Peterson 算法是错的。

我在代码里给了正确的版本，加了很多 barrier。如果把 barrier 定义成空的，这个程序就是不带 barrier 的版本，在你们自己的 PC 上跑，就能看到 `assert fail`。检查方式很直接：每当有一个进程进入，就让一个原子计数器加一；两个进程进去它就会变成 2，看到 2 就说明有两个进程同时进了 lock 保护的那个"房间"，那就错了。

> **提示**：让人惊奇的恰恰在这里。这样一个错误的程序，在我这台机器上竟然复现不出来。上一节为了说明多核之间确实存在弱内存模型的行为，我很明确地把它复现出来了，可 Peterson 这一处却复现不了。

这才是并发最可怕的地方。算法真的是错的，程序真的会 `assert fail`，但各种机缘巧合会让它看起来是对的。你们马上要做的实验也是同一个道理：跑了很多轮测试，觉得自己的 malloc、free 写得很对，交到 OJ 上就是过不掉——而且我还没有非常 intensive 地测试你们的程序。你面对的是一个指数大的状态空间，一个协议为什么对、到底对不对，远远超出我们的想象。

### 两个牌子写不下整个系统

Peterson 算法还有一个致命缺陷。刚才的协议里有两个牌子，一个写着 Alice，一个写着 Bob。这意味着 Alice 必须知道对方是 Bob，Bob 必须知道对方是 Alice，才能在自己那一份上写下 0 或者 1。

可现实里我们用 spawn 可以派生出很多很多线程，这些线程还能动态地再 spawn、再结束。我根本不知道任何时刻系统里还有多少个线程。所以它根本不 work。

它只适用于两个线程的同步。虽然有扩展的方法，但那些方法超出了本课要讨论的范围。我们要的不是智力体操，而是绝对正确的工程化方案。所以 Peterson 算法我不会考——我不会在课上让你们做智力题。你们需要的是理解中间的复杂性，并且用合适的方式管控它。我真正要教的是：到底怎么样实现一个正确的互斥。

Peterson 算法的错，是路线上的错。它试图在 `load` 和 `store` 之上实现互斥，也就是先假设 `load`、`store` 是原子的，再在它们上面搭互斥。1965 年这个假设还勉强成立，可计算机系统是我们自己造的。

### 推翻假设：系统是我们自己造的

所以说，解决问题的方式是解决提出问题的人——开个玩笑。实际上不是解决提出问题的人，而是推翻这个问题的假设。这才是我们做系统的人解决问题最好的思路：清清楚楚地理解假设，然后在工程意义上合适的地方把它推翻。假设一旦被推翻，你就打开了一片全新的天地。

这是计算机科学和自然科学很大的一点不同。你要是去做生命科学，人不是你造的，你不知道人是怎样收敛到今天这一步的，规则是自然定的，你只能理解规则、再在规则之上做你能做的事；物理实验至少是可重复的。而计算机科学的规则全是我们自己定的：只要不违背芯片、电路这些物理极限和公理，软件不好解决的问题，我们就让硬件来帮忙。

既然互斥是一件这么重要的事，那就让计算机系统给我们添一条指令，只要这条指令在电路上实现起来不太复杂就行。就像操作系统给一条关中断的指令，它就能实现互斥一样。这就是我们要的：在硬件上加一条指令，帮助我们在多处理器上实现互斥。

### 为什么光有 load 和 store 拿不起那把钥匙

回到最初的那个模型。什么是互斥锁？把它想成一张桌子，桌子上面放着一把钥匙。所谓 lock 或者 acquire，就是把这把钥匙拿过来；release 就是把钥匙放回桌上。

用这个模型回看 Peterson 算法，它假设里最大的挑战立刻暴露了：它规定一条指令要么做一次 `load`，要么做一次 `store`。翻译成现实意义就是——我 `load` 的时候，手必须背在后面不能动；我 `store` 的时候，眼睛必须是瞎的，得蒙起来。刚才说的两步，第一步举手是一个 `store`，第二步还是一个 `store`；一旦 `store` 完，你就只能观看。也就是说，读的时候只能看不能动，写的时候只能动不能看。

```text
   Peterson 的假设                    物理世界里的 acquire
   ──────────────────────            ─────────────────────────
   load  : 手背在身后，只能看         手伸过去拿钥匙的同时
   store : 眼睛蒙起来，只能动         眼睛能看着钥匙，边看边动
   → 一次只能做一件事                 → 一次 load + store 一气呵成
```

在物理世界里，伸手去桌上把那把钥匙拿起来，对人来说是再自然不过的过程，你从来没觉得这有什么困难。为什么？因为你是一边 load 一边 store 的：手伸过去的时候眼睛能看到它。两个同学同时伸手，你们自然而然地就会互相协同一下、谁快谁慢礼让一下，钥匙就拿过来了。这就是 acquire 的真实过程，和 Peterson 的根本假设不一样。

所以，要解决这个问题，其实只需要有一条指令帮我们同时完成一次 `load` 和一次 `store`。

那如果不加这条指令、直接照着这个过程写呢？看桌上有没有钥匙，有就把钥匙拿走；桌上没有，就 go to retry；unlock 的时候把钥匙放回桌上。这个代码直接跑为什么不对？和前两天讲的"山寨支付宝"一模一样：两个线程都想扣 100 块钱，都要先判断钱够不够扣，够扣就扣。本质就是我刚看到桌上还有钥匙，等我执行到"把钥匙拿走"的时候，钥匙已经被人拿走了。

> **结论**：只要把"判断"和"拿走"这两句话合成一个不可分割的、非常短小的时间段，做一次很小很小的 stop the world，问题就解决了。计算机系统提供的原子指令，就是这个 stop the world。

### 原子指令：让硬件替我们做一次 load 加 store

原子指令未必一定是原生的原子指令，还有一种办法是实现在一个很小、真的很小的时间段的 stop the world 里。

x86 的做法是指令前缀 `lock`：比如 `add 1, x`，写成 `lock add 1, x`。它真的有一把总线上的锁，会把总线锁住，别人就不能访问内存了。这个时候我就可以对同一个内存地址先做一次 `load`、再做一次 `store`——把这个地址彻底锁上，没有人能打扰我，效果上就等同于 stop the world。这个行为在最早的 80486 支持 `lock` 指令的时候就已经画在图上了：总线上真有一颗总线锁，执行译码器译出 `lock` 这个指令前缀时，它就会把总线锁住。（这个实现后来也给 x86 带来了很大的麻烦。）

只要做到这一点，不管哪个体系结构都支持，问题不就解决了吗？甚至它提供了一系列非常高效的原子指令：一条 `lock add 1, sum` 就能实现正确的 `sum` 加一。

我们这个层次的锁叫自旋锁（spinlock），用法和 mutex lock 完全一样，`spin_lock` / `spin_unlock` 就当成 `lock` / `unlock` 来理解。计算机世界里没办法直接表达出"一把钥匙"，只能用一个数：我手里有一张纸，纸上写着 0，另一张纸上写着 1。一张白纸代表空手，写着钥匙的那张代表钥匙。有了原子操作就有了办法，比如原子地加一，还有一个是把两张纸上的内容原子地交换。

```text
   桌上（内存）的值:  KEY=1        我手上的白纸: 0
   ── 原子 exchange ─────────────────────────────────
   桌上（内存）的值:  0            我手上: KEY=1    → 抢到钥匙，拿锁
   后来者再 exchange: 只能换到 0                    → 没抢到，重试
```

只要 exchange 这个指令实现得像是 stop the world，那么无论有多少人来，只有最先执行 exchange 的那个人能把钥匙换到手上：每个人都拿着一张白纸想跟它交换，谁先执行谁就拿走钥匙，剩下的人只能换走我留在桌上的那张白纸，也就是 0。

这条指令还有变体，比如 compare-exchange：先做一次比较，相等的时候再交换。换成它以后，我先看一眼里面是不是钥匙，是钥匙再把它换过来，这样就能省掉一次内存的写；看到不是钥匙，我就没有内存写，只有一次读，性能更好。不管 x86、ARM 还是 RISC-V，编译器都会帮你搞定，它是编译器的 built-in function。这里我用了更强一点的 acquire-release 内存模型，也都没问题。

于是 acquire 就是：原子地把 locked 换进去，并且把里面的结果拿出来；如果结果是 free，说明钥匙到了我手上，我就可以进入 critical section。这个例子和 mutex lock 的用法完全一样：程序里有一个 10 次循环，每次都做 `sum++`，它确实能在多处理器上实现 1+1，相当于手工实现了一个 mutex lock。

### 自旋锁的两个代价

#### 空转：一核有难，八核围观

第一个代价是显而易见的性能问题。想一想我们是怎么实现互斥的：桌上有一把钥匙，好多人都盯着它，每一个人都是一个 `while (1) { exchange }`，都试图把里面的钥匙换出来。一旦有人把钥匙换走了，他拿到了钥匙，很开心地继续执行；其他人在干什么？他们在死循环里拿白纸跟白纸交换，看到的永远是白纸。

而且没有任何一个线程知道这个人什么时候才会把钥匙还回来。所以除了拿到锁的那个线程能执行，其他处理器上的线程都在空转、都在浪费。这就是"一核有难，八核围观"——最早那几代处理器出来的时候，内存通信、缓存一致性和调度都有一些性能问题，我们经常这么说。如果你的临界区执行很久，那还不如把 CPU 让给别的线程去执行。

#### 被换出去：拿钥匙的人消失了

第二个问题更严重。操作系统可以关中断，应用程序不能。这就意味着，现在拿到钥匙的线程，它可能会被中断。

比如说现在这台树莓派上有 4 个或者 8 个 CPU，但我的系统里可能有 100 个可以运行的线程。拿着钥匙的线程被中断以后，操作系统会换另外一个线程上来运行一会儿——为了公平地造成一个并发的假象：100 个线程都要运行，我只能把一秒钟切成 1000 份，第一份给你，第二份给他，这样才能在长时间尺度上让这些程序看起来是并发的。

这下就惨了。持有自旋锁、刚刚用 exchange 换到钥匙的那个线程被切换出去了。操作系统就是这个世界的管理员，它可以把这个人切换走，扔到磁盘上也是可能的，甚至可以把这个线程做一个快照扔到另一台计算机上运行——有一个叫 CRIU 的工具，可以把一个进程做快照，再把快照丢到另一台电脑上跑，有兴趣的同学可以试一试。他消失了，可能要一年以后才会回来。

```text
   线程 A（持锁）                    其余 N-1 个线程
   ────────────────                  ────────────────────────────
   换到钥匙 → 被换出                 while (1) { exchange → 只换到 0 }
   （可能很久不回来）                一直在空转，纯烧 CPU
                                     锁拿不到，临界区也做不了
   → 系统里 100% 的算力都被浪费
```

这个时候系统里换上来一个线程，他也想要得到这把锁，于是所有资源都被浪费掉了。这显然不是你想要的结果。

#### 把"我在等锁"告诉操作系统

刚才那个 exchange 交换的方式确实实现了互斥，但如果我能把"现在拿钥匙拿不到"这件事告诉操作系统，操作系统就可以做出更好的决策。

比如我换了一次没换到，就告诉管理员：我先去睡觉了，能不能等钥匙回来了再把我叫醒？这样没拿到钥匙的人都去睡觉了，真正需要 CPU、可以运行的线程就能上来运行。而要告诉操作系统，当然是一个 syscall——这是线程自己解决不了的问题，必须通过系统调用。

所以理论上我们可以实现一个 `syscall acquire` 和 `syscall release`，把锁的实现放到内核里。内核里的锁既要关中断，又要像刚才那样不断地 exchange 自旋；剩下的工作都交给内核：内核发现这把锁还没被归还，就可以直接把这个线程变成睡眠状态，并且给它做一个标记，让内核知道这个线程等的是哪一把锁；等到那把锁被 release、钥匙回来的时候，再把这个线程唤醒。这是完全没有问题的。

### 把等待交给内核：futex

Linux 里并不是用 acquire 和 release 这两个系统调用实现的，而是一个很有趣的机制，叫 futex。它叫快速用户空间的互斥（fast userspace mutex），相关的两篇文章你们可以回去看，其中一篇叫《Futexes Are Tricky》，里面就在吐槽 futex 非常难用：文中提到 Rusty Russell 发布的一段代码实际上是错的，而评论它的内核维护者说，别见怪（no disrespect），弄错是很正常的，I got it wrong the first time as well。

futex 比 Peterson 算法还要更复杂，因为它一部分在用户态，一部分在内核态。它主要提供两个操作，一个 up、一个 down。

它的关键在于有一条用户态的 fast path：如果我 exchange 这把钥匙拿到了，就根本不需要进入内核，直接继续执行就行。也就是说，在没有人争抢这把锁的时候，我只要一次 exchange 就够了。一旦 exchange 失败，就必须有一条绝对正确的 slow path。

```text
                acquire
                   │
                   ▼
          用户态 exchange 抢钥匙
             │                │
           成功              失败
             │                │
             ▼                ▼
     直接进入临界区      陷入内核（slow path）
     （不进内核，fast）    登记在等哪把锁 → 睡眠排队
                           ← release 时被唤醒，重试
```

难点在于：你不仅要在 acquire 的 fast path 上想方设法不进内核，release 的时候也不想进内核，这就非常麻烦了。它实现的效果是：在锁不拥挤、没有两个人抢锁的时候，整个同步过程完全不进内核。细节我们现在不需要知道，但我们可以拿它和别的求和方式比一比。

> **提示**：futex 的"快"是有前提的——只有当没有竞争时快路径才生效。一旦真的有人抢锁，你还是得掉进内核态那条慢路径，所以它才那么难写对。

### 用一次实验量出四种实现的差距

今天讲了这么多实现互斥的方法：原子指令（exchange）、操作系统给的库函数 mutex、内核里的 futex，到底谁好谁坏、什么时候好什么时候坏？你们完全可以做一个实验来知道。而且在今天有 AI agent 的时候，做实验比过去前所未有的简单——我这次真的只用了一个 prompt。

实验程序是这样的：一共做 n 次 `sum++`，n 自己限定，然后把这 n 次分配到 T 个线程里，T 从命令行输入。把 main 和好几种实现链接起来：

- 原子指令：x86 里就是一条 `lock add`，ARM 上是用一套不太一样的机制来实现原子加一；
- pthread 的 mutex（这个实现和线程库里的 mutex lock 是一样的）；
- 刚才那个不停 exchange 的自旋锁；
- 还有一个我让 AI 写的、每次都强制进入系统调用的 futex 版本。

你们可能没想过还能做最后这件事：强制每一次 acquire 和 release 都走 futex 系统调用进内核，看看到底有多快、有多慢。

Prompt 的要点是控制变量的对比实验：

- 控制总的 `sum++` 次数不变，只改变线程数：1、2、4、8、16 个线程；
- 每种实现重复五次——一定要做能复现的实验，千万不要 cherry-picking：你可以做一万次实验，把最好的一次拿出来，那就没有人比得过你了；
- 统计一次 `sum++` 的平均时间；
- 把原始数据保存成 CSV，再生成一张带 error bar 的图（我后来换了 prompt，所以 error bar 这个要求没落地，但至少它把做实验的脚本给我写好了）。

你们完全不需要知道怎么写脚本，只需要知道你确实需要一个科学的、定量的对比，就能看到有趣的结果。它把原始结果收齐，也画成了图。

### 读图：从几纳秒到几百纳秒

它给了两张图：一张是每一次 `sum++` 所需的平均时间（纳秒），另一张把它取倒数，也就是一秒钟能执行多少次 `sum++`。结果符不符合你们的预期？

- 单线程时，所有实现执行一次 `sum++` 都是最快的——不管是陷入操作系统内核的、自旋的、mutex 的，还是原子指令的。
- 陷入内核的代价远远高于其他方式。一次系统调用要几百纳秒（至少在我这台机器上是几百纳秒，你们的 x86 上应该会更快一些）；而单线程下真的只要几纳秒到十几纳秒就能完成一次 `sum++`。所以你当然希望每一次系统调用都能一次读出尽可能多的数据；或者反过来，如果这个 read 本来就要从很远的地方读、要等一等，这几百纳秒很快就被抵消掉了。
- 一旦上到两个线程，表现就完全不一样了。这台虚拟机一共 4 个处理器，从 1 到 2 到 4，不管用原子指令、mutex 还是别的，差距都不大。
- 但线程数一旦超过处理器数量：mutex 和原子指令的性能基本上没有显著下降，而自旋锁下降得非常显著——正好就是前面说的那种情形：我在自旋、持有锁的时候被切换出去，那么在 CPU 上运行的所有线程都把算力浪费掉了，于是这个历史现象被我们观察到了。

第二张图（每秒操作数）看得更清楚：只做 `sum++` 的话，原子指令性能最好，和刚才一致；mutex 和自旋之间是有差距的，而且 mutex 的曲线更清楚——它的 scalability 更好，随着线程增加基本还是一条直线；而 trap 的性能很差，因为每次都进系统调用。

| 实现 | 单线程下每次 sum++ 的开销 | 线程数超过 CPU 数之后的扩展性 | 说明 |
| :--- | :--- | :--- | :--- |
| 原子指令（x86 上是 `lock add`） | 最低，几纳秒到十几纳秒 | 基本不下降 | 只做 `sum++` 时性能最好 |
| pthread mutex | 很低 | 基本不下降，接近直线 | 与线程库里的 mutex 实现一致 |
| 自旋锁（exchange） | 很低 | 下降非常显著 | 持锁线程被换出后，其余线程全在空转 |
| 强制每次进内核的 futex | 几百纳秒 | 很差 | trap 的开销远高于其他方式 |

这就是对待数据的科学方法：任何时候你都可以做很多对比实验，然后清楚地了解一个系统到底发生了什么。

### 做实验的底线：别犯 benchmarking crime

因为你们未来很可能会走上做一点科研的道路，我郑重地要求每一个同学在做实验之前，都再读一遍 Systems Benchmarking Crimes。里面列了很多 crime，虽然它是从体系结构的视角来讲的。

其中有一种叫 selective data set hiding deficiencies：用一个特定的数据集或配置，恰好把缺陷藏起来。那类图和我们前面那张还挺像——一个多线程服务器，随着线程增加，每秒能处理的数据量也增加，看上去是很好的结果。可如果把刚才那几个程序换成每个线程各用各的锁、各算各的 sum、最后再把 sum 汇总起来，你也会看到类似的曲线：看着不错，实际上这是一个有可扩展性（scalability）问题的程序，它跟刚才的自旋锁有点像——线程数量超过 CPU 数量的时候，性能会急剧下降。

难点在于：当线程数和 CPU 数差不多、每个 CPU 上都有一个 `sum++` 的线程时，"所有人围观"的情况是不会出现的，或者说非常罕见，所以看不出显著影响。你把实验的线程数限制在这个区间，瓶颈就被藏起来了——这正是这种 crime 的可怕之处：图是真的，结论是错的。

我还听说有些社区里把"提升 1%"的绝招是往训练集里混一点测试集的数据，据说在某些领域里是不成文的规矩；但在 systems 领域里我们还没有这种规矩。你们做任何定量的研究，都能从中获得很多有趣的观察，但一定要特别留意：不要有任何 benchmarking crime。
