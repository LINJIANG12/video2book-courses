# C 运行时、链接加载与 Linux 应用世界的构建

## 生态分层的底座

### C 的完全体

* **简单 C（Simple C）**

    * > **定义**：只覆盖 C 语言中与计算有关的那一半的模型——指针、数组、结构体、函数调用，全都是对内存与寄存器的直接操作。

    * 任何 C 程序都可改写成「赋值号左边是变量、右边只有一个操作」的形式，`if` 与循环也能写得极简，因此 Simple C 可以直译成汇编：只要跳转、寄存器腾挪、load、store 这些指令，x86、ARM、RISC-V 都一样。

    * 写成汇编甚至可以用手写完成，因为它没有超出「对内存和寄存器的直接操作」这个范围。

* **跨语言调用（Foreign Function Interface，FFI）**

    * > **定义**：允许在一种编程语言里访问用另一种语言写出来的代码的机制。

    * 几乎所有编程语言都预留了这样的接口，只是通常用得不多；C 作为底层语言，提供的是与汇编、二进制代码连接的能力。

    * 对 C 而言 FFI 有两条路——直接与汇编实现的函数链接，或在 C 里写内联汇编。

    * 一旦 C 能调用汇编、进而能发系统调用，应用世界里看到的所有东西就都可以实现。

### ISO C 与 POSIX 的意义

* **ISO C 标准**

    * 规定了 Simple C 的语法语义，以及更复杂的 C；有了标准，实现者都倾向于遵守，版本升级就不会破坏已有实现。

    * 用符合标准、可移植的方式写程序（例如不假设 `int` 是几个字节），同一份代码可以从个人电脑、超级计算机一直跑到只有 1KB 内存的设备。

* **可移植操作系统接口（Portable Operating System Interface，POSIX）**

    * 规定了 `fork`、`pipe`、`execve` 这类函数的接口与行为，几乎所有还在使用的操作系统都兼容它。

    * 一个系统只要兼容 C 与 POSIX，别人写的程序几乎不用修改就能完整运行；核心命令行工具集正是建立在这两个接口之上。

* **应用世界的分层**

    * 从下到上依次是：操作系统 → 汇编与系统调用指令 → Simple C 加 FFI → libc 与 POSIX → C++／Java 及各类运行时生态 → 自然语言编程、Python、JavaScript、Android 等。

    * 越往下越靠近机器，越往上越接近今天写代码的方式；C、libc、POSIX 这三层是支撑上面所有东西的底座。

    ```text
       自然语言编程 / Python / JavaScript / Android …
                        ^
            C++ / Java / 各类运行时生态
                        ^
          libc（C 标准库）        POSIX
                        ^
       Simple C（指针/数组/结构体/函数调用）
              +  Foreign Function Interface
                        ^
            汇编 / 系统调用指令
                        ^
                    操作系统
    ```

    * 对比之下，不断升级依赖的高级语言生态容易出现「开发时很爽、换一个依赖就跑不起来」的失控状态；C 用最小那部分写出来的程序反而不受此影响。

## 跨语言调用与内联汇编

### 直接与汇编函数链接

* **应用二进制接口（Application Binary Interface，ABI）**

    * > **定义**：规定参数放在哪个寄存器、栈顶是什么、返回地址在哪的一纸合同；C 与汇编双方照着做就能互相调用。

    * 以 x86-64 为例：第一个整型参数放 `rdi`，第二个放 `rsi`，以此类推；栈顶是返回地址，汇编跳过来后可直接用指令访问这些位置。

    * 只要 C 能调用汇编实现的函数，就能调用系统调用——`pipe`、`fork` 这类函数背后最终都落到一段汇编代码上。

### 内联汇编及其代价

* **内联汇编（Inline Assembly）**

    * > **定义**：把一段汇编指令以字符串形式嵌进 C 语句里的领域特定语言。

    * 设计动机是不大改 C 的语法解析器，所以它看起来像合法 C 语句：指令写在字符串里、括号必须配对、可以引用词法作用域里的变量。

    * 真正想做的事是：一段指令序列与作用域里的变量互相读写。为此引入 `%0`、`%1` 这样的占位符，后面还要跟约束——`=r` 表示写回某个寄存器，`+r` 表示同一个变量既读又写。

    * 编译器会生成大量优化过的指令序列，寄存器它可以任意占用；因此内联汇编必须声明自己破坏了哪些寄存器，才能与优化协同。想发系统调用又必须把参数寄存器全部写好，这正是它演化成复杂 DSL 的原因。

    * 这段代码最终原封不动丢给汇编器，所以它在 x86 上能正确编译，拿到 ARM 上汇编器会直接报「找不到这条指令」。真正需要它的场合是极致优化，例如让编译器针对目标机器已有的指令集改写向量点积这类循环。

### 编译器不解析字符串语义

* 字符串里的指令原样交给汇编器：编译器不知道指令集是什么，也不知道某条指令是什么意思，甚至可以是自定义指令。

* 漏写副作用（改动了某个寄存器却没说）在当次编译里可能完全测不出来，因为编译器恰好没有用到那个寄存器。

* > **易错点**：漏写副作用的 bug 表现为「换台机器、换个编译器就诡异复现」——编译器升级后更激进地使用寄存器，之前潜伏的错误才浮出水面。这类错误在真实内核代码里也出现过。

## 独立与有宿主运行环境

### 两种运行环境

* **有宿主环境（hosted）**

    * > **定义**：程序通过 FFI 落到汇编、再落到操作系统，必须依赖操作系统才能运行。

    * 判据：执行一次 `fopen` 要先持有文件描述符，就必须走 `open` 系统调用。

* **独立环境（freestanding）**

    * > **定义**：不需要操作系统的 C 运行环境。

    * 只用内联汇编发一条指令直接访问硬件，就可以用 C 写操作系统内核，这时程序没有操作系统也能跑。

    | 环境 | 依赖什么 | 典型例子 |
    | :--- | :--- | :--- |
    | hosted（有宿主） | 落到汇编、再落到操作系统，没有操作系统跑不起来 | `fopen` 必须先持有文件描述符，要走 `open` |
    | freestanding（独立） | 不需要操作系统 | 内联汇编直接访问硬件，用 C 写内核 |

### 机器相关的类型与格式串

* `int`、`long` 的宽度与机器字长相关：32 位机上 `long` 是 4 字节，64 位机上 `long` 是 8 字节；定宽类型与整数范围由标准提供。

* 打印定宽整数不能用 `%d`、`%ld` 去猜，要用 `PRId32`、`PRIu64`、`PRIx` 这类宏把类型与格式串绑在一起。

* 这些宏展开后是字符串字面量的拼接，依赖预处理器允许两个相邻字符串写在一起的机制。

* > **易错点**：`%d` 对应 `int`、`%ld` 对应 `long`，而 `long` 的宽度随机器变化，所以「打印一个定宽整数该用什么格式串」不能凭习惯猜。

### offsetof

* **成员偏移量（offsetof）**

    * > **定义**：给出结构体某个成员相对结构体头部偏移量的宏。

    * 实现方式：把地址 0 强制转换成该结构体指针，好像零地址处真有这样一个对象，然后取成员地址——成员地址的数值本身就是偏移量。

    * 这个指针只是被挪了一下、并不会真的被解引用，因此该操作在 C 语言里完全合法；编译器也可能有内建的更好实现。

### 变参数

* 32 位机器上 calling convention 把所有参数压栈，栈上天然出现参数数组，取第一个参数的地址就能顺着往后走。

* 在现代体系结构上参数大多由寄存器传递，取不到「参数数组」的地址；需要标准库与编译器协作，在函数序言里把寄存器中的参数存入栈、凑出一块连续结构，`va_list`、`va_arg` 才能逐个访问。

* > **易错点**：「取第一个参数的地址往后走」这个 hack 只对 32 位 x86 的 cdecl 约定成立，x86-64、ARM、RISC-V 上都不成立。

### 随手可写的标准函数

* `memcpy`、`memmove`、`strcpy` 用循环就能实现，`atoi` 做整数与字符串的互转。

* **伪随机数生成器（pseudorandom generator）**

    * > **定义**：同一种子必然得到同一序列，是一个「同样输入必得同样输出」的数学函数。

    * `rand` 就需要先给种子，种子相同则每次运行生成的随机数序列完全相同。

* `qsort` 难用，是因为 C 只给了有限的语法机制，要做通用排序只能把比较函数做成函数指针参数；自己写一个带比较成员的结构体反而更可读。

* 数学库里的 `sin`、`cos` 都能自己实现，但浮点与数学水很深。

* > **提示**：NaN 与任何数的比较（包括与自身比较）结果都不成立，所以 `x != x` 反而是判断 NaN 的常用写法。

## 跨栈跳跃 setjmp 与 longjmp

### 记录与弹栈

* **setjmp**

    * > **定义**：把当前栈帧位置与 PC 记到一个 buffer 里，然后正常返回、继续往后执行。

    * 纯 C 里无法知道底下有多少层函数调用；实际操作上不需要真的数层数，只要有一个指向那个栈帧的指针即可。

* **longjmp**

    * > **定义**：一个大号的 goto——把 buffer 拿出来，一次弹掉中间积累的所有栈帧，回到记下的位置与 PC。

    * 可以带一个返回值回来，它会作为 `setjmp` 的返回值返回。这个特性不需要任何系统调用，只要编译器配合生成正确的指令序列；常用它实现协程。

* 三层栈帧被一次弹掉的过程：

    ```text
       setjmp 时             走完 first、second 之后        longjmp 之后

       +-------------+       +-------------+               +-------------+
       |             |       |   second    |               |             |
       +-------------+       +-------------+               +-------------+
       |             |       |    first    |               |             |
       +-------------+       +-------------+               +-------------+
       |    main     |       |    main     |               |    main     |
       +-------------+       +-------------+               +-------------+
    ```

    * 左图是执行 `setjmp` 时栈上只有 `main`；中图是走过两层调用后栈帧压了上来；右图是 `longjmp` 之后更深的栈帧被一次性弹掉，只剩下 PC 已被改回记下位置的 `main`。

### 寄存器层面的行为

* 在 ARM64 上，`setjmp` 把 `x19` 到 `x28` 这一批寄存器存进内存 buffer，`longjmp` 再把它们 load 回寄存器；`x0` 到 `x18` 全程不参与保存与恢复。

* **调用者保存与被调用者保存（caller-saved / callee-saved）**

    * `x0` 到 `x18` 属于 call-clobbered：函数一进来这些寄存器就归它，可以随便改、不必负责。

    * 其余寄存器要用就必须先把原值存入内存，用完再恢复；这套命名是按「谁负责动手保存」命名的，而不是按「谁被保护」，所以翻译过来以后更容易绕晕。

* 由此可以逆向出部分 calling convention：编译器调整寄存器的使用顺序，保证调用任何函数返回之后，`x0` 到 `x18` 里的值都不会再被需要。

## stdio 作为文件描述符的封装

### struct FILE 的构成

* 结构体里包含一个文件描述符，还包含一个与管道相关的进程号；这两个整数就是它与操作系统相关的部分。

* 含有一个缓冲区指针承载缓冲；并用几个函数指针（读、写、定位、关闭）实现 C 版本的「面向对象」。

* 因此一个 IOFILE 可以对应多个后端：真实的操作系统文件，或一个字符串缓冲区（往缓冲区里打印时，只要把关闭、读、写、定位这几个函数相应实现好即可）。

* 因为持有文件描述符，`fopen`、`fread` 这些最终都能转译成对该文件描述符的系统调用。

### stdio 与文件描述符 API 的对应

| stdio 里的 API | 对应的文件描述符操作 |
| :--- | :--- |
| `fopen` | `open`（前者返回文件指针，后者返回文件描述符） |
| `fread` | `read` |
| `fseek` | `lseek` |
| `ftell` | 取当前位置，同样可以用 `lseek` 实现 |

* 还有 `feof` 之类，对应的都是那个文件描述符的状态；只要持有该描述符，就能对它做定位之类的操作。

### printf 家族只有一份实现

* 真正负责打印的只有一份 printf core：拿到格式串后从左到右解析 `%d`、`%s`，路由到相应的处理函数，最后都往文件结构里写。

* `printf` 就是向标准输出流的 `fprintf`；实现里用到变参数列表（本质是一段可以逐个往后走的内存）与一个不停前进的解析循环。真正打印时会先做一次试探性调用，确认不失败后再真正解析。

* `printf`、`sprintf`、`fprintf` 这一族没有代码克隆：功能收敛到一份实现，代码重复变少，项目维护就容易得多。

## 进程退出、协同与错误处理

### atexit 与正常退出收尾

* **退出处理函数注册（atexit）**

    * > **定义**：注册一个在程序正常退出时被调用的处理函数。

    * 典型用途是删掉运行时创建的临时文件：临时文件不删会持续占用存储，工具被反复调用时可能把临时空间占满。

    * 只在正常退出时生效；异常退出偶尔留下一两个文件，由清理机制处理。

### abort 与核心转储

* `abort` 的行为是给自己发 `SIGABRT` 信号，这个信号会触发一次核心转储。

* > **易错点**：`assert` 失败时终止调用的不是 `exit`，而是 `abort`。

* 因此 `assert` 失败时看到的退出状态是 134，即 $128 + 6$，其中 6 正是 `SIGABRT` 的信号编号。

* **核心转储文件（core dump）**

    * 名字来自早期的磁芯内存：把磁芯内存的状态转储到永久存储器上；今天用来指把进程内存放进一个文件。

    * 配置了大小上限后，崩溃时会把进程内存转储下来，之后可以用调试器调试这份快照。

### system 与 popen

* `system` 背后会启动一个 shell 并在其中执行命令，因此比较重，但很好用——拼出一个命令字符串再执行掉即可。

* `popen`、`pclose` 返回文件指针，比 `system` 好用的地方在于能把被调用程序的结果拿回来。

* 缺点是单向的：只能一个方向写、一个方向读。原因是文件结构里只有一个文件描述符，而管道需要两个，最终 API 设计者选择了一个带历史包袱的妥协。

### errno 与 perror

* 每个系统调用的手册都有一节 ERRORS；返回 -1 只代表失败，具体原因由错误号区分。

    | 错误号 | 什么时候出现 |
    | :--- | :--- |
    | `EAGAIN` | 暂时不行，下一次再试也许就可以 |
    | `ENOMEM` | 确实没有内存了 |
    | `EACCES` | 请求的访问不被允许，权限被拒绝 |
    | `EEXIST` | 路径已经存在，同时又用了创建标志 |

* 很多系统调用可能暂时性失败：此刻失败、过一会儿可能成功，此时返回 `EAGAIN`。

* **错误号（errno）**

    * > **定义**：libc 提供的一个可移植变量，对应上一次系统调用或库函数调用失败的原因。

* **perror**

    * > **定义**：先打印调用者给的字符串，再把上一个失败原因的字符串打印出来。

    * 输出用哪种语言，由当前语言环境配置决定——同一条报错用什么语言说出来是 libc 的事，不是调用者的事。

* 如果错误是程序要容忍的（依次尝试打开若干文件，都不存在就退出），可以不打任何信息；如果做的是给别人用的工具，就应该把错误打印给用户。

## 环境变量与 environ

### 环境变量的继承

* `execve` 系列里带 e 的函数才有环境变量参数；不带 e 的函数默认让子进程继承父进程的环境变量。

* 最底层的系统调用必须给出完整参数与环境变量，但用 libc 的 API 调用时默认继承。

* 于是一个进程设置的语言变量会传给所有子进程：登录时按用户设定语言，之后生成的 shell、shell 再 fork 出的程序，整棵进程树都带着它——这就是同一个程序对两个用户显示两种语言错误信息的原因。

### 环境变量表由谁赋值

* **环境变量表（environ）**

    * > **定义**：libc 提供的一个字符串二级指针变量，通过它可以拿到 `key=value` 形式的整张环境变量表。

    * libc 只提供这个符号；理论上可以用任意方式（只要类型正确）定义它，甚至先赋成空指针，程序照样正常终止，因为初始化代码随后会赋上正确的值。

* 环境变量与参数按 ABI 放在栈上，而栈的地址受地址空间随机化影响，所以这个指针每次运行的值都不一样。

* 在进程刚刚启动的那一刻打印它，得到的是 0；取它的地址，得到的是那个 8 字节变量本身在数据区的位置。

* 赋值发生在 libc 的初始化函数里，就是一句把全局环境变量指针设为传入参数的话；在 watchpoint 上停住时，这个指针已经指向栈上正确的环境变量。

## C 运行时：起点与终点

### 初始进程栈

* 进程被 execve 起来时，栈指针指向的第一个字是 `argc`，紧挨着上面依次是参数向量、一个空指针、环境变量向量、再一个空指针，最上面是辅助向量。

* 因此环境变量可以用「参数向量起始地址 + 参数个数 + 1」算出来，那个 `+ 1` 跳过的就是参数数组结尾的空指针。

* 调试时甚至可以访问参数数组结尾空指针的位置：按 C 语义那是越界访问，但它确实是进程栈上一块有效内存。

* 进程初始栈的布局：

    ```text
       高地址
       +-------------------+
       |       ...         |
       +-------------------+
       |       NULL        |   环境变量数组到此结束
       +-------------------+
       |     envp[n-1]     |
       |       ...         |
       |      envp[0]      |
       +-------------------+
       |       NULL        |   参数数组到此结束
       +-------------------+
       |    argv[argc-1]   |
       |       ...         |
       |      argv[0]      |
       +-------------------+
       |       argc        |  <-- 进程刚启动时，栈指针指向这里
       +-------------------+
       低地址
    ```

* 自己实现 libc 时第一步就是取到这三个东西：只要控制住入口符号、再用不链接任何库函数的编译选项，就能从零接管这个程序。

* `main` 的签名因此是整型参数个数、字符指针数组形式的参数、字符指针数组形式的环境变量；写成一维指针形式也是对的。调用它就是按 calling convention 把这三个值放进正确的寄存器再跳转过去。

### 启动链路

* libc 的一部分是入口符号 `_start`：一段最小的汇编代码，接管第一条指令后跳到它的 C 语言承接函数。

* 承接函数从传入的指针读出参数个数（第一个元素）与参数向量（紧随其后的地址），随后跳到 libc 的启动主函数，后者直接调用初始化函数。

* 初始化函数负责：把全局环境变量指针设为传入的环境变量；跳过全部环境变量字符串；逐个处理剩下的辅助向量；最后经一个函数指针进入启动主函数的第二阶段。

* 第二阶段最终落脚在一行上：先调用 `main` 并传入参数个数、参数向量、环境变量，再把返回值交给 `exit`。

* 整条链路：

    ```text
    _start                        <- 汇编入口，调试器从这里开始
      |
      +-> _start_c(long *p)       <- p 指向初始进程栈
            |
            +-> init_libc(envp)
            |     |  把全局 environment 复制给 envp
            |     |  跳过全部环境变量字符串
            |     +  逐个处理剩下的辅助向量 auxv
            |
            +-> stage2 (函数指针) == 启动主函数的第二阶段
                  |
                  +-> 启动钩子           <- 简单程序里没有实质工作
                  |
                  +-> main(argc, argv, envp)  ->  return 1
                        |
                        +-> exit(1)
                              |  stdio 等清理
                              +-> 最后一个 exit 直接调用 syscall
    ```

### 收尾链路

* `exit` 会调用注册过的退出处理函数，调用退出收尾逻辑，最后 flush 缓冲。

* 最后一步调用的那个退出是一个系统调用，它通过系统调用指令落到内核。

### 运行时与 ELF 入口

* **C 运行时（C runtime，CRT）**

    * > **定义**：编译链接时会一起进来的、负责初始化与收尾的那部分必要代码。

    * 除承载入口的启动目标文件外，链接过程还会引入若干与运行时相关的目标文件。

* ELF 头里有一个 entry 字段，由链接器填入入口符号的地址；它指向的正是运行时里的启动代码。

* 入口符号是自己实现的、但没有进 libc 的那种：本可以在它里面直接调用 `main`，而不是层层转到启动主函数。

### libc 提供什么

| 层次 | 内容 |
| :--- | :--- |
| freestanding 环境 | `setjmp`、`longjmp`、知道整数有多长、怎么打印一个整数 |
| 系统调用的封装 | 文件描述符、进程、乃至错误的编号 |
| 必要的代码 | 负责初始化、负责收尾的那部分运行时代码 |

* 读一个真正 libc 的实现会发现里面没有魔法：各种常量无非是宏定义，定位宏就是三个取值，缓冲区大小与文件名长度上限也都是直接写出来的数。

## 调试信息与调试工具

### 优化与调试的编译选项

* 编译出可调试程序的标准做法是加调试选项；要调试库内部还需要静态链接、并让库本身带上调试信息。

* 想看到未被优化的源码对应关系，可以降低优化等级。

* > **易错点**：把优化与调试选项加到汇编标志上是没有用的，编译 C 代码要加在 C 编译标志上；加错了就真的不会有调试信息——「脚本跑完了」并不等于「工具链被替换了、调试信息存在」。

### DWARF 调试信息

* **调试信息标准（DWARF）**

    * > **定义**：一种调试信息标准，以若干个节的形式嵌在 ELF 里；名字与 ELF 构成一对矮人与精灵的梗。

    * 内容包括：内存地址到编译单元的映射表、核心调试信息（类型、变量、函数）、调用栈展开所需的信息、行号表（PC 与源代码行的对应）、调试用的字符串表、变量在 PC 范围内的位置信息。

    * 编译单元就是一个源文件；地址到编译单元的那张表，就是拿内存地址去找它属于哪个编译单元。

* 断点没有落在函数的第一个字节，而是落在入口之后一点的位置，正是调试信息在起作用——它跳过了编译器插在函数开头的序言，找到第一条语句真正的起始指令。

* > **提示**：调试信息的义务之一，是把被优化掉的变量值捞回来；换一个编译器去编译，有时能捞出更多信息。

### 符号表与 addr2line

* 不需要任何调试信息，靠 ELF 里的符号表也能知道当前跑在哪个函数：符号表里记着每个符号所在的地址。

* **地址到行（addr2line）**

    * > **定义**：把 PC 的一个地址转换成源代码里一行的工具。

* 要精确到「在函数的哪一行」才需要调试信息；编译器不优化时，一条 C 语句基本能对应到连续的一块汇编。

* 如果编译器做了指令重排、内联，打乱了语句执行顺序，这个对应关系就变得比较困难。

### DWARF 里的虚拟机

* DWARF 内含一个小解释器，可以通过访问寄存器、对取出的地址做算术，算出一个变量的值；它甚至是一个有 bytecode、带分支、图灵完备的指令集。

* 设计目的不是让你写程序，而是描述「在某个 PC 范围内，变量的值在哪里、怎么把它算出来」。

* 需要它的直接原因之一是 C 的位域：一个 32 位整数里每一位都有名字，调试时要打印其中某一位，就需要一套指令集把这一位取出来。

* 同一套 bytecode 也用于 C++ 异常的栈展开：抛出异常、弹出栈帧、恢复上一个调用者的位置时，同样需要调试信息。

### JavaScript 的 source map

| | C / C++ | JavaScript |
| :--- | :--- | :--- |
| 调试信息放在哪 | ELF 文件里的 DWARF 节 | 独立的 source map 文件 |
| 要不要磁盘上的源码 | 要：调试器按路径去找源文件 | 不要：源码可以直接存在 map 里 |
| 为什么这样设计 | 有操作系统、有目录，假设目录里有源码是正常的 | 浏览器是沙盒，没有整个项目的目录结构 |

* C 侧需要磁盘上的源文件，因为调试器假设目录里有一份源代码；浏览器是沙盒，所以这套调试信息可以脱离原始代码仓库工作，直接把出错的行乃至代码本身存进去。

* 前端从 TypeScript 转译到 JavaScript、再转译到老版本 JavaScript，同样是从高级语言一层层翻译到底层，所以也需要把底层的行映射回源代码的行。

* > **注意**：这类 source map 不是完整项目（缺少构建清单），无法直接构建运行；从依赖里引入恶意包会在构建时执行脚本，可能泄露凭据，应在干净沙盒中处理。

### 采样与性能分析

* 有了调试信息，可以隔一小段时间把程序暂停一次、恢复出它的调用栈；采样足够多次就得到火焰图。

    ```text
       |<------------------- 时间轴 ------------------->|
       +---------+---------+---------+---------+--------+
       |                  main                           |  main 一开始就在栈上，
       +---------+---------+---------+---------+----------+  直到程序快结束才 pop
       |   func_b          |   func_c          |
       +---------+---------+-------+-----------+
       |   f_d   |   f_e   |  f_g  |  ...      |  进来一个函数就垒一层，
       +---------+---------+-------+-----------+  返回就出来一层
    ```

* 横轴是时间、纵轴是调用栈；栈底的部分（如 `main`）从头到尾基本不动。

* 采样是均匀的，而程序绝大部分时间通常花在少数函数上，所以能找出性能瓶颈；对比之下 `strace` 是把所有系统调用都记下来。

* 用精简 libc 编译出来的程序，在 `execve` 之后只有一两个与系统相关的系统调用；常见工具链编译出来的程序明显多得多，会多出诸如读取链接、取随机数之类的调用。

* 程序崩溃后留下的快照同样可以在汇编意义上调试，甚至可以改里面的值（例如改 PC 让它继续往后执行）。

### sanitizers

* **地址检查器与线程检查器（AddressSanitizer / ThreadSanitizer）**

    * > **定义**：把程序编译成带检查的版本，运行时报出内存与线程类错误的诊断工具。

    * 诊断报告会利用调试信息恢复出更多关于源代码的知识。

* **释放后使用（use-after-free）**

    * 指针被释放之后它的值并没有变，那块内存在地址空间的意义上仍然「能用」，所以程序往往不 crash。

    * > **易错点**：不 crash 绝不等于正确——它是未定义行为，可能导致潜在的安全漏洞。

## 不陷入内核的系统调用

### vvar 与 vdso

* **共享变量页（vvar）**

    * > **定义**：内核映射进每个进程地址空间的一段数据，由所有 CPU 共享。

    * 内容包含当前 CPU 编号、当前时钟计数等；时钟中断到来时这个计数加一，于是不精确的时间可以直接从这里读到。

* **虚拟动态共享对象（vDSO）**

    * > **定义**：操作系统内核提供给每一个进程的一小段代码，同样躺在进程地址空间里。

    * 配合 CPU 里精确的周期计数，就能算出比较精确的时间，全程不需要进入内核。

* 时钟中断频率可以配置（每秒上百次到上千次），因此从这里读到的时间精度大约是千分之一秒量级。

### 经辅助向量找到时间函数

* **辅助向量（auxiliary vector，auxv）**

    * > **定义**：内核在布置初始进程栈时放在环境变量数组之后的一段元数据，包含可用的真随机数种子、vDSO 的位置等。

    * 内核加载 ELF 程序后，通过栈把这些元数据传给运行时；由此运行时才知道内存布局、CPU 能力、链接器在哪等关键信息。

* 相关函数会做一次懒加载：从辅助向量里解析出符号地址，然后直接调用，全程没有陷入内核。

* 具体路径是：遍历辅助向量找到指向 vDSO 入口的那一项，拿到它的程序头表，再像加载器一样遍历符号表，找到内核提供的时间函数并跳过去执行。

### 两次读时钟计数

* 时间函数并不总是发系统调用：可以从共享变量页里直接读时钟计数，于是「读一个大概的时间」不进内核。

* 实现是一个类似顺序锁的读两次比对：先读一次计数放进寄存器，再读一次；两次相同就认为读到了稳定值，不同就重试。

* > **提示**：单步调试时这个循环一直出不来，不是循环写错了，而是调试本身太慢，让「读两次、比对」的窗口被时钟中断反复打断，于是只能一直重试。

* 进程状态就是寄存器与内存，进程自己没有时间概念，所以时间只能通过系统调用或这类共享数据获得。改变对时间相关调用的参数与返回值，就能给程序一个假的时间轴——这就是所谓的变速齿轮。

## malloc 与 free

### 分层与内存池

* 内核以页为单位分配内存（例如一页 4KB），只能给出页大小的整数倍，无法满足两个字节、四个字节这样的小请求。

* **libc 内存池**

    * > **定义**：libc 先向内核一次要一大块内存（用 `mmap`，更早的实现可以用 `brk`），再自己维护空闲区间、从中切出小块的机制。

    * `malloc` 每次从空闲区域里找一块足够大的空间割出来，`free` 把它还回去。

* `malloc` 允许分配极小的内存，甚至可以分配 0（此时返回一个可以成功传给 `free` 的唯一指针值），但最好不要依赖这个行为；它也可以分配 1GB 这样的大内存，那种情况下直接向操作系统要即可，头尾浪费一点也无妨。

* `calloc` 保证内存被清零；为了安全，现在的 `malloc` 一般也会返回清零的内存，代价是牺牲一点性能。

### 为什么这个接口不好

* `malloc` 引入了一个额外要求：每一条可能的路径上都必须有配对的 `free`，否则内存被浪费；而 `free` 之后指针立刻非法。

    | 对比项 | 文件描述符的 API | `malloc` / `free` |
    | :--- | :--- | :--- |
    | 提供的完备性 | 只认字节序列，不理解内容 | 分配与释放必须成对 |
    | 上层要负责的事 | 字节的编码与含义 | 每一条可能路径上的释放时机 |
    | 违反约定的后果 | 写进去什么就是什么 | 泄漏，或指针失效后的非法访问 |

* 文件描述符那套 API 把接口做到最小、不去理解字节序列的含义，责任边界清楚；`malloc`、`free` 则给程序员带来了巨大无比的心智负担。

* 在作用域中途 `return` 掉一个还能走到的 `free` 就是泄漏；这类代码很难写对，实际系统里因此有非常多这样的 bug。

* > **易错点**：`free(p)` 之后马上写 `*p = 1`，语法与编译器都不拦你，但指针已经被交还，这就是典型的释放后使用。

### 人类走过的弯路

* 没有指针的语言（Java、JavaScript）从语言层面绕开了释放时机问题。

* **资源获取即初始化（Resource Acquisition Is Initialization，RAII）**

    * > **定义**：在作用域里定义一个对象，构造时获取资源（如上锁）、析构时释放，用作用域规则保证成对。

    * 它把释放时机绑在作用域上，但遇到提前 `return` 仍需逐一处理。

* Rust 的所有权与借用机制从类型系统上拒绝这类代码；C 语言里大量安全漏洞都由内存引起，而攻击方（尤其是编码智能体）发现这类漏洞的能力还在增强。

* 一种编码规范要求 `free` 之后立刻把指针变成空，用来阻止释放后使用——但这又落回空指针问题：程序一旦违反约定就会 crash、不再提供服务。

* 实现思路本身是一道数据结构题：大内存直接向内核要，小内存从自己维护的若干不相交空闲区间里找一块切出来；入门解法是平衡二叉搜索树，但它不是现在实际分配器的实现方式。

## 可执行文件是进程初始状态的描述

### 可执行文件的本质

* 可执行文件首先是操作系统里的一个普通文件：可以打印、可以按十六进制转储，头部是 `7f 45 4c 46`，后三个字节正是 `E`、`L`、`F` 的 ASCII 编码。

* **可执行文件**

    * > **定义**：描述进程初始内存布局的一个数据结构。

* 进程的初始状态由两部分拼成：一部分是操作系统按 ABI 摆好的初始进程栈；另一部分是可执行文件描述的段——哪些代码、哪些数据、加载到哪里、什么权限。

    ```text
            高地址
            +-------------------------------------------+
            |  initial process stack（操作系统负责布置）  |
            |    argc / argv[] / envp[] / auxv            |
            |    sp 指向这里                              |
            +-------------------------------------------+
            |  ...                                       |
            |  可执行文件描述的段（可执行文件负责）        |
            |    .text   可读 可执行   代码                |
            |    .data   可读 可写     已初始化的数据       |
            |    .bss    可读 可写     未初始化的数据       |
            +-------------------------------------------+
            低地址
    ```

* **执行程序（execve）**

    * > **定义**：把参数所指文件描述的那个初始状态搬到当前进程内存里的系统调用；它接受的是一个路径名。

* 谈「执行」谈的就是这个系统调用：第一个进程由它创建别的进程、由它换成另一个程序，而它换进来的文件描述的就是进程的初始状态。

### a.out

* 早期 Unix 的可执行格式里那个 a 是 assembler 的意思（assembler output），它既能用于链接也能用于执行。

* 它简单到连偏移量字段都没有：代码、数据、未初始化数据要加载到内存的哪个位置，直接由平台与 ABI 相关的常数决定——也就是硬编码在操作系统自己的代码里。

* 代价很明显：不支持动态链接、不支持调试信息、不支持内存对齐与线程局部存储等后来才需要的东西。功能要往新格式里加，于是就有了 ELF。

### ELF 为机器效率而设计

* ELF 要描述：若干内存段从哪里到哪里加载、权限是读／写／执行中的哪些，往后还有链接、调试信息、符号表等内容。

* **字符串与符号身首异处**

    * 引用一个符号时，字符串并不在引用的地方，而存在符号表里；引用的地方只存一个偏移量，要像指针一样索引过去才知道它是什么。

    * 结果整个文件里大量的定位都是用偏移量在算，人脑根本算不过来，注意力很快就涣散。

* **属性用位域编码**

    * 「可读可执行不可写」这类信息以位域编码，必须经过一层翻译才能变成人类能理解的平坦结构。

    * 对机器来说这些都无所谓：加一个偏移、或者干脆改成指针就能读到；人不像机器那样适合处理这种复杂结构。

* ELF 包含的信息无非是基本信息（版本、机器结构）、内存布局（哪些部分是什么数据、访问权限），以及重定位、调试信息、符号表；这些信息总可以用另一种等价的描述形式表达出来。

### 等价描述形式的转换

* **自定义可执行格式**

    * > **定义**：自己定义一个描述二进制文件的数据结构，用 JSON 这类序列化格式（键值字典与数组）代替偏移量指针的表达方式。

    * 文件里直接声明「这是一个可执行文件」，用一个字段记符号的位置，用标志说明某段是指令，不需要在文件头上放一堆魔数；配套可以实现完整的编译器工具链，把 C 编译成这种格式，然后链接、加载。

    * 代价是用浪费空间换取可读性，好处是设计想改就改。

* 也可以换成 Markdown 或 SVG 来描述同一个二进制：开头写格式、位数、字节序、ABI、机器结构，一段要加载的内容就是一个可读可执行的段，里面是节、符号、重定位。

* 用 SVG 甚至可以把两个画布拼起来当作链接——只要你能开脑洞，链接与加载都可以用任何描述形式实现。

* 真正要紧的是把知识网络交到手里：知道存在这样的手册，知道有 `readelf -a` 这样的命令，知道重定位这类信息可以从哪里读出来。

## 链接与加载的机理

### 链接就是填一个数

* 编译时如果调用一个本文件之外的函数，编译器照样能生成二进制指令序列：一条调用指令后面留四个字节的 0。

    ```text
      x86 里一条 call foo 编译出来的样子：
            e8  ?? ?? ?? ??
            ^   ^
            |   +---- 四个字节，留给 foo 的地址差，编译时先填 0
            +-------- 操作码：这是一条 call
    ```

* 符号从头到尾没有被定义过，链接器就报找不到符号、无法链接；只要它存在，那四个字节里就要填一个表达式。

    | 场合 | 留出的空位 | 链接时要填的表达式 |
    | :--- | :--- | :--- |
    | 一条 `call foo` | 4 字节 | `message_end - 点 - 4` |
    | 一条取地址的 PC 相对寻址 | 4 字节 | `message - 点` |
    | 把字符串长度放进常数位 | 4 字节 | `message_end - message` |

* **重定位（relocation）**

    * > **定义**：把编译时留空的那些位置，在链接时按最终算出来的表达式填上数值的过程。

    * 一个目标文件里，代码节中地址引用的位置编译时被填成 0（在某些体系结构里是一个立即数位域），链接时才被真正填进去。

* 重定位最朴素的样子就是这样：指令里留出的空位，等所有符号都安排到位置上去之后，填进去的是一个「目标地址减参考地址」的差值。

### 加载就是照着字面搬

* **加载**

    * > **定义**：照着描述把该搬的东西搬进内存，并附带它该有的权限。

* 把一个可读可执行的段搬进内存，用一次 `mmap` 系统调用就全部解决。

* 一句话机理：链接是把空出来的空位填上一个只有等符号都排好位置才算得出来的数；加载是照着描述把该搬的东西搬进内存，附带它该有的权限。

### 加载器在内核里

* 内核里的加载器先检验数据结构的合法性，然后加载程序头表，映射各个段，最后创建运行时所需的表。

* 创建表这一步会在栈上布置参数个数、参数向量、环境变量和辅助向量，也就是初始进程栈。

* 架构相关的辅助向量项（例如指向 vDSO 入口的那一项）也在这一段代码里被插入。

* > **提示**：在这一层领域里有一条判据——程序的运行不会骗你。生成一段指令序列，链接、加载、运行起来，真的看到该打印的东西打印出来，才算确认链接器与加载器都正确生效了。

### shebang

* 用 `#!` 开头、后面跟一个解释器路径的文本文件可以直接执行；加上执行权限后就能作为可执行文件运行。

* 内核加载器会把文件头读出来判断类型：只有头两个字节是井号和叹号时，才继续把它当成脚本格式加载。处理 ELF 格式与处理脚本格式是两份不同的加载器代码。

* 参数拼装规则：解释器路径成为第一个参数，脚本自身的路径被原封不动插进去，然后才是调用时给的参数。

    ```text
      ./s 1 2 3
        |
        |  s 的第一行：#!  解释器 a  参数 b c
        v
      内核 execve 之后实际摆出来的 argv[]：

        argv[0] = "a"        #! 后面的解释器路径
        argv[1] = "b c"      Linux：剩下的整段算作一个参数
        argv[2] = "./s"      脚本本身的路径，原封不动插入
        argv[3] = "1"        调用时给的参数
        argv[4] = "2"
        argv[5] = "3"
    ```

* 标准没有规定第一行里解释器后面那段内容算一个参数还是两个：一种系统把剩下的整段作为一个参数传进去，另一种系统会把它拆成两个分开的参数，这是跨系统不一致的地方。

* 如果解释器路径不存在、或指向一个目录、或没有执行权限，执行都会失败。

### 静态链接留下的麻烦

* 静态链接时，所有库函数在每个可执行文件里都要多保存一份；库很小的时候还能接受，库大到几兆、系统里又有几千个可执行文件时，这份重复就不能忽视了。

    ```text
      静态链接：每个可执行文件都自带一份库
        可执行文件 #1   [ 自己的代码 | 库的一份拷贝 ]
        可执行文件 #2   [ 自己的代码 | 库的一份拷贝 ]
        可执行文件 #3   [ 自己的代码 | 库的一份拷贝 ]
        ...
        系统里几千个可执行文件，每个都带一份拷贝
    ```

* 想不浪费，唯一的出路是把应用程序掰碎——掰成许多小块，需要什么就共享什么。

## 动态链接与加载

### 收益与验证

* 大程序被拆成自己的代码与若干共享库，共享库在整个系统里只需要一份拷贝，磁盘空间就省下来了。

* 更大的好处是独立升级：只要接口不变就可以单独更新库。假如系统里上万个可执行文件全都静态链接了同一个库，发一个安全补丁会非常难受。

* 不只是系统库：大型项目也可以这样分解，把一个模块编译成共享对象，像「插进来」一样通过函数调用协作，甚至可以借此做差分测试。

* 内存里同样只有一份：只读的共享库在任意多个进程之间共享同一份物理副本。

    * 用一个装满空操作指令、体积达 40 兆的共享库做验证：启动上千个进程加载它并把里面所有指令执行一遍，系统依然流畅，内存占用远小于「每进程一份」的假设值。

    * 再用列出系统打开文件的工具查看，能数出引用这个库的进程正好是上千个（多出的一个是工具进程自己）。

    * 这类工具是靠遍历进程文件系统统计出来的：既看打开的文件表，也看地址空间映射，而不是只数文件描述符。

* 顺着进程文件系统还能看到某个进程映射了这个共享库，以及它打开的所有文件。

### interpreter 与第一条指令

* 动态链接的 ELF 在程序头里有一段描述解释器的字段，内容是一串形如「请求的程序解释器：某个加载器路径」的字符串。

* **解释器（interpreter）**

    * > **定义**：程序头里那串字符串所指的二进制文件；动态链接的二进制文件执行的第一条指令不是它自己的入口，而是这个文件的入口。

* 用调试器停在第一条指令上时，地址空间里只有三样东西：初始栈（参数个数、参数向量、环境变量、辅助向量）、可执行文件需要加载的部分、以及解释器所指的二进制文件（它本身也是一个 ELF）。

* 在程序入口上打一个断点继续运行之后再看，共享库才被加载进来。

* 解释器没有任何神秘之处，它就是程序头里的一段字符串：把它改成一个不存在的名字，执行就会失败并报「找不到解释器」；把这个名字创建出来（哪怕只是做一个符号链接），程序又可以执行。因此加载器完全可以换成任何一个自己实现的加载器。

### 先有鸡还是先有蛋

* 不论静态还是动态链接的可执行文件都有 ELF，都有入口指向启动代码；而启动代码又会调用 libc 里的启动主函数。

* 这个启动主函数已经是库函数的一部分，为了节省空间应当在系统里只有一份副本，所以它是动态链接的。

* 于是问题变成：动态链接的可执行文件被映射进内存后，它要用的那个库函数到底是谁加载的？答案在解释器那一环。

* 完整顺序：

    ```text
    execve(可执行文件)
      │
      ├─ 内核读 ELF program header，发现 PT_INTERP
      │      内容是一串字符串：请求的程序解释器 → 加载器路径
      │
      ├─ 把可执行文件需要加载的段映射进地址空间
      ├─ 映射内核自己塞进来的 vvar / vdso
      ├─ 把字符串所指的文件（它也是 ELF）映射进来
      └─ 建立初始栈：SP -> argc / argv / envp / auxv
            │
            ▼
       第一条指令：PC 指向加载器的 entry，不是程序自己的 _start
            │
            ├─ 加载器解析 auxv，找到那个可执行文件
            ├─ 递归加载它依赖的所有共享库
            └─ 全部就位后才跳到程序的 _start
                  │
                  ├─ _start（启动代码）
                  └─ __libc_start_main ──► main
    ```

* 精简的 libc 里，加载器与整个 libc 是链接在一起的，所以它不需要再加载任何额外库；换成主流 libc 时这个解释器就是所有动态链接程序统一的加载器入口。

### 加载器的环境变量与手册

* 动态链接器的行为记录在 8 号手册里，里面有大量有趣的行为，尤其是主流 libc 那个加载器。

* **库搜索路径（LD_LIBRARY_PATH）**

    * > **定义**：一个环境变量，加载器能读到它，据此知道去哪里找动态链接库。

    * 自己编译的共享库默认加载不到，把它所在的目录放进这个变量就能跑起来。

* **加载调试（LD_DEBUG）**

    * 输出加载过程的调试信息；例如设置为查看库的加载，就能看到任意一个程序到底加载了哪些二进制文件。

* **立即绑定（LD_BIND_NOW）**

    * 启动时就解析所有符号（关闭延迟绑定）；可以用它覆盖预期行为，把潜伏的分支逼出来。

* **依赖清单（ldd）**

    * > **定义**：假装启动一次加载器去解析，从而看出一个程序真实加载时会是哪几个文件，并递归解析依赖。

* **打印辅助向量（LD_SHOW_AUXV）**

    * 让加载器把实际的辅助向量打印出来；每次运行都能看到 vDSO 映射位置、程序头加载位置、随机数种子等都在变化。

### LD_PRELOAD

* 动态链接的符号解析默认是「先到先得」：谁先定义了这个符号，这个位置就被占了，以后的调用都会落到它上面。

* **预加载（LD_PRELOAD）**

    * > **定义**：预加载一个库，让它插到所有依赖之前，从而覆盖任何想要的符号。

    * 覆盖一个符号时可以保持它原来的行为，只在前后插入自己的代码——这就是钩子（hook），是非侵入式的，不用改被改程序的代码。

* 覆盖与时间相关的函数（取时间、取时钟、睡眠、闹钟，以及带超时的等待），就能实现改变应用时间感知的变速齿轮：正常睡一秒的程序在覆盖后 0.1 秒就返回，一个慢吞吞的游戏会明显变快。

* 其他玩法：监控内存分配得到分配日志，从而发现释放后使用之类的错误；覆盖随机数接口实现可控的随机；覆盖图形缓冲交换接口可以做透视类外挂。

### PLT 与 GOT

* 编译器对本文件内的函数和动态库里的函数一视同仁，都生成一条调用指令加四个字节的位移；区别在于动态库函数的地址在链接时还不知道。

* **过程链接表（Procedure Linkage Table，PLT）**

    * > **定义**：链接器在可执行文件里生成的一小段桩代码，把「跳到地址未知的外部函数」变成「跳到文件内地址已知的桩」。

    * 调用外部函数变成调用到它的 PLT 桩，桩里再到全局偏移表里查出运行时才填好的真实地址，然后跳过去。

    ```text
    main:
        call printf@plt        ; 位移很短，链接时就能确定
            │
            ▼
    程序里的 printf@plt:
        jmp *printf@GOT(%rip)  ; 查表：表项里存的是运行时才填好的真实地址
            │
            ▼
    共享库里的 printf          ; 真正的实现，地址在运行时才知道
    ```

* 做这件事的动机是跳转距离限制：ARM 用 26 位立即数（128 兆空间），x86 用 32 位立即数（2G 空间）；而 64 位地址空间一般只有 48 位有效，四个字节的位移根本跳不到共享库那里。

### 全局偏移表与位置无关代码

* **全局偏移表（Global Offset Table，GOT）**

    * > **定义**：存放运行时才确定的地址的表，供 PLT 间接跳转或位置无关代码取地址使用。

* 一句 `x = 1;` 到底访问本文件还是另一个共享库里的变量，编译时并不知道，结果取决于编译选项。

* 不做位置无关代码时，这句赋值只有一条存储指令：先把地址算出来，直接写进去。

* 做位置无关代码时，要先从全局偏移表里查一个地址出来再写进去——多一层间接访问，带来一定性能损耗。

* > **易错点**：在位置无关代码下，所有外部数据（例如声明为外部的外部整型变量）不管是否真能用一个短地址访问到，编译器都会增加一层间接访问；要控制这个行为需要额外的 hack。

## 从第一个进程构建 Linux 应用世界

### 最小的可执行文件与用户态模拟

* 一个最小的 64 位静态链接可执行文件：用系统调用打印一句话，再调用退出，不需要任何额外的库函数。

* 不同体系结构的二进制文件默认会进入模拟器执行：所有用户态的计算与访存指令都被模拟执行，而它发起系统调用时直接调用当前操作系统的系统调用。

### initramfs

* **初始内存文件系统（initramfs）**

    * > **定义**：初始时放在内存里的文件系统，内核启动早期唯一的文件来源。

    * 因为 `execve` 的参数必须指向一个文件，而内核刚开始并不知道文件系统在哪里，所以最早的那个文件必须来自内存里的这个文件系统。

    * 做法是把一棵目录树用归档工具打包、再压缩成一个镜像，交给内核解开当作初始文件系统。

* 内核在初始文件系统里按硬编码的若干候选路径逐个尝试第一个进程；这是默认行为，可以在内核命令行参数里覆盖，直接指定第一个进程是谁。

    ```text
    目录树（bin、init、驱动模块……）
      │  归档，再压缩
      ▼
    初始内存文件系统镜像
      │  启动时交给内核（内核镜像单独指定）
      ▼
    内核把它解开，当成初始的内存文件系统
      │  按硬编码路径逐个尝试；被命令行参数覆盖时直接用指定的那个
      ▼
    第一个进程被 execve 加载，成为 1 号进程
    ```

* 系统更新软件包时那个耗时特别长的操作，就是把新版本的软件打回这个初始文件系统里去，因为里面必须放着要加载的第一个程序。

### 第一个进程与 init 的特殊性

* 内核加载第一个进程之后，自己就变成系统调用的提供者：调用会调进来，中断会被响应，后台还要处理未完成的事情（例如把缓存写回磁盘）。

* 第一个进程可以不是系统默认的那一个：只要问出「能不能把第一个进程换成我们自己的进程」，合理的事情就一定能做到。

* **init 的特殊性**

    * 别的进程退出无所谓；init 一退出，内核立刻罢工并 panic，随之打印调用栈，整个系统挂掉。

### 真实 initrd 里有什么

* 真实系统里也有一个打好包的目录树，解开后目录结构非常像根目录：有库、有用户空间工具、有配置文件、有键盘布局与字体配置、有内核模块信息与固件。

* 里面的 init 可以是动态链接的，因为此时已经有文件系统、也有必要的动态链接库；而只有一个最小程序的初始文件系统里，init 只能是静态链接的。

* 它的主要职责是加载内核模块、检测并挂载实际的文件系统，然后显示一个启动画面。

* > **提示**：磁盘损坏、文件系统挂不上时可能进入这个初始文件系统的模式；只要它没损坏，就能得到一个可用的命令行环境，内核已经加载、系统调用都正常工作。

* 解包时可以用大小对不上来识别解包不完整：解开后文件总和明显小于镜像本身，说明后面还有数据没出来；这类镜像可能由多段压缩拼接而成，需要顺着尾部继续解。

* 内容上它还包含全套命令行工具（例如由一个多合一工具集提供的那些），以及读写特定文件系统格式的组件。

### pivot_root

* 初始文件系统阶段的最后会执行一个系统调用，改变根挂载：以真实根文件系统为根重建整个世界，然后这个新的 init 再创建出整棵进程树。

* 这个阶段的最后甚至可以弹出一个命令行与它交互，重新配置（例如找不到启动盘时换一块盘来启动）。

* > **易错点**：systemd 是 1 号进程，但它是执行「改变根挂载」之后才成为 1 号进程的；在初始文件系统那个阶段，1 号进程是那个文件系统里的 init。系统启动并不是「内核直接拉起 systemd」，中间隔着一整个阶段的初始文件系统。

### 只有 BusyBox 的世界

* 初始文件系统可以只包含一个 init 和一个多合一工具集的二进制，外加必要的驱动模块；这个世界里别的东西都没有。

* 用那个工具集列出它支持的所有命令，然后为每个命令创建一个指向它的符号链接，三行脚本就造出了整个 bin 目录里的一大堆二进制。

* 接着用创建目录、挂载等命令创建操作系统的对象：创建 procfs、sysfs，安装驱动，创建设备节点。

* 每个命令背后都是系统调用：符号链接对应创建链接的系统调用，创建目录对应创建目录的系统调用，挂载 procfs 对应挂载系统调用（把 procfs 里的所有对象在一个目录里创建出来）。

    | 设备文件 | 类型 | 主设备号 : 从设备号 |
    | :--- | :--- | :--- |
    | random | 字符设备 | 1 : 8 |
    | urandom | 字符设备 | 1 : 9 |
    | null | 字符设备 | 1 : 3 |
    | tty1 | 字符设备 | 4 : 1 |

* 创建块设备（例如一块虚拟磁盘）需要指定主设备号与从设备号，这个设备文件才能被创建出来。

* 有了 procfs，查看进程的工具才能工作——最开始没有 procfs 时它发现里面没有文件，自然什么也看不到；有了 procfs 之后还能编辑文件、用管道，都是标准行为。

### 换上真实文件系统

* 把虚拟磁盘挂到一个目录上，磁盘里文件系统的目录树就被放到了系统里；卸载之后那个目录就空了。

* 换到真实根文件系统后需要把这套工具、procfs、sysfs、设备节点再创建一遍，因为那是一个全新的文件系统。

* 图形输出：早期对话的是调试串口，图形设备一直是黑的；有了图形终端设备后，向它写内容就会显示在屏幕上——屏幕上的每个像素都是驱动程序画出来的，所以输出速度明显变慢。

* 装上模拟网卡驱动、配置地址后可以启动一个 HTTP 服务；借助端口映射，从宿主机访问对应端口就能看到虚拟机里的网页，取到文件系统里的脚本即证明这个最小系统真正点亮了。

* 从第一个进程开始，之后所有事情都是用系统调用实现的——这就是系统调用这个抽象真正厉害的地方。

## 应用生态、历史与操作系统定位

### Unix 的演化

* 早期 Unix 连 `fork` 都没有：shell 要运行一个外部程序时会关闭所有打开的文件、把标准输入输出打开到终端、自己退出从而从内存卸载，再用 execve 加载并执行目标程序，程序退出后 shell 再被加载回来。

* 于是最早的 Unix 上一台终端里最多只有两个程序：shell 与可执行文件，来回切换。

* 后来 Ken Thompson 用二十几行汇编就实现了 `fork`，因为早期进程模型很简单——代码从哪里到哪里、数据从哪里到哪里，几个指针就描述完了，复制一个进程非常容易。

* 所有复杂的东西在刚开始的时候都是很简单的；今天看起来可怕的模型，早期都只是你能理解的最简单的样子。

### Minix

| 版本 | 时间 | 兼容目标 |
| :--- | :--- | :--- |
| Minix 1 | 1987 年 | UNIX V7 完全兼容 |
| Minix 2.0 | 1997 年 | POSIX 兼容 |
| Minix 3 | 2006 年 | 完整的现代系统，至今仍在维护 |

* 它一度是世界上最流行的操作系统：凭借宽容的许可证被放进芯片组的固件里，于是每台计算机的芯片组上都有一颗协处理器运行着它。

* 兼容到什么程度：有完整的命令行工具、系统调用与库函数，有分册的手册，甚至带完整源代码；可以修改内核、加一个系统调用，再在系统内重新编译、把内核镜像烧回磁盘，改完的系统也能运行。

* 它随书发行代码，只需几个兆到几十兆的镜像就能跑起来，也是 Linux 实现的原点。

### 微内核与宏内核

* Minix 作者当时就做微内核：理想是几乎只有一个系统调用——发一条消息、再等一条消息回来；操作系统内部的各个服务（文件系统、CPU、内存）以用户态进程的形式运行，只是被赋予特别权限。

    |  | 宏内核 | 微内核 |
    | :--- | :--- | :--- |
    | 系统调用入口 | 一条系统调用指令直接进内核 | 发一条消息、等一条消息 |
    | 服务的位置 | 内核代码在同一地址空间里执行 | 内核里的服务可以是用户态进程，被赋予特别权限 |
    | 代价 | 代码全写在一起，改起来容易一团乱 | 参数要先拷进消息，进程切换加往返通信 |
    | 当年的结论 | 性能好，但结构上难维护 | 结构干净，但在当年的机器上太慢 |

* 在当年计算机很慢的背景下，发消息要把读写参数先拷进消息、再经系统调用转发给另一个进程、执行完再返一条消息回来，性能很低。

* 作者本人一直说，他做这个系统是为了上课，性能不是他要管的，未来某一天性能才会是问题。

* 另一位当事人（因 Unix 获图灵奖的那位）的评价是：微内核很可能是未来的方向，但宏内核更容易实现，也更容易在修改中很快变成一团乱——这两句后来都应验了。

### Linux 的诞生与弯路

* 1991 年 8 月 25 日，一个 21 岁的芬兰学生在 Minix 的邮件列表里发帖说自己正在做一个自由的操作系统，并留下了一句「只是一个爱好，不会像 GNU 那样庞大和专业」——这是 Linux 史上最有名的一句话。

* 他当时手上只有一台 386，从未想过支持别的机器结构；早期 Linux 还依赖 Minix：没有自己的文件系统时，要把磁盘格式化成 Minix 文件系统才能使用，运行的软件是当时的 GNU 工具链与 shell。

* 时间线：厂商陆续入场后成为可以严肃运行的服务器系统；内核 2.0 引入多处理器支持，2.4 时内核代码才真正能多处理器并行；2.6 发布恰逢云计算基础设施起步，源码规模巨大膨胀。

    ```text
    1987   第一版 Minix，UNIX V7 兼容，随书发行
    1991   Linux 起步：在 Minix 邮件列表发帖，
           四月份开始写，手上是一台 386；
           早期要把磁盘格式化成 Minix 文件系统
           │
           ▼  越来越多的厂商入场
               Linux 成为服务器上可以严肃运行的系统
     2.0   引入多处理器支持
     2.4   内核代码才真正能多处理器并行
           │
    2003   2.6 发布，恰逢云计算基础设施起步，源码规模巨大膨胀
           │
           ▼  多个子系统大规模重构，一度陷入泥潭
    今天   既像微内核、又像宏内核的现代操作系统
    ```

* 多个子系统经历了大规模重构，一度陷入泥潭；今天它既像微内核又像宏内核，是一个现代的、非常先进的操作系统。

* 关于那场论战：Minix 作者以官方身份下场批判 Linux 是宏内核的坏主意，Linux 作者喷了回去，而一位早已因 Unix 获图灵奖的人物实名发表了自己的工程经验——这段历史连同那些言论都被永久记录在邮件列表里。

### 狭义与广义的操作系统

* **狭义的操作系统**

    * > **定义**：操作系统原理课主要讲的那部分——操作系统给应用提供的 API 与对象。

* **广义的操作系统**

    * > **定义**：API 加上支撑它的整个生态：运行库、核心工具集、各种辅助工具、版本管理与系统管理，乃至每天发布新应用的厂商与个人开发者。

    ```text
    ┌────────────────────────────────────────────────────┐
    │ 应用生态：厂商与个人开发者每天发布的新应用          │
    ├────────────────────────────────────────────────────┤
    │ 核心工具集：shell、基本工具、3D 库、图形库……        │
    ├────────────────────────────────────────────────────┤
    │ 运行库：libc                                        │
    ├────────────────────────────────────────────────────┤
    │ 内核 API：系统调用与操作系统对象（最小的一层）      │
    └────────────────────────────────────────────────────┘
    ```

* 核心工具集里一个安全漏洞都不能有，一个漏洞就把整个系统拖垮；内核看起来已经是一两千万行的庞然大物，但相比整个应用生态只是一点点——一个复杂业务应用本身就可能上千万行。

* API 与应用程序是共同演化的：应用发现性能不够，操作系统就给出新的 API、新的对象或新的文件，最后长成今天的样子。所以是应用生态成就了操作系统的繁荣，操作系统本身只是一个 API。

### 软件分发与应用生态

| 时期 | 分发方式 |
| :--- | :--- |
| 早期 DOS 时代 | 软盘、光盘；序列号印在盘上或贴在盘里的纸条上，很容易破解 |
| 互联网时代 | 应用商店、APT、RPM、Python packaging index、NPM、Hugging Face、Ollama |

* 自由操作系统的「自由」说的不是钱，而是软件自由：所有软件可见，每一行源代码都能看到、能理解、能贡献。

* APT 在 1998 年就出现了，比移动端的应用商店早了若干年；它有一整套开源供应链管理流程：从不稳定分支一点点合进测试分支，愿意尝鲜的用户先用，再慢慢进入稳定状态。

* 随便取一个软件包解开，问清「安装这个软件包到底意味着什么」，就能理解整个应用生态是怎么构建起来的。

### 从最初的确定状态到整个世界

* 操作系统一定会到达一个确定的初始状态：这个绝对确定的初始状态由 CPU reset 决定，随后固件把操作系统加载好，操作系统再把第一个程序加载好。

* 从第一个程序的初始状态开始，剩下的整个世界只有两样东西：操作系统对象与 API。

    ```text
    上电
      │  CPU reset：寄存器和内存被置为确定状态，PC 指向 firmware
      ▼
    firmware（固件）
      │  内含 bootloader
      ▼
    bootloader 加载操作系统镜像
      │  一个静态链接的 ELF
      ▼
    内核开始运行
      │  在初始内存文件系统里按硬编码路径依次尝试候选的 init
      ▼
    第一个进程（初始文件系统里的 init）
      │  做完了该做的事，执行改变根挂载的系统调用
      ▼
    换成真实根文件系统上的 init（例如 systemd）
      │  它才成为进程树的根
      ▼
    整个进程世界
    ```

* 从初始内存文件系统开始，之后在系统里看到的每一个像素、桌面应用上的每一次操作，全部都是系统调用实现的——Android 上打开一个应用、服务器上生成一个页面，背后都是同一套 API。
