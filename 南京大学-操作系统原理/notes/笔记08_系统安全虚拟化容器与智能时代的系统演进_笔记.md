# 系统安全、虚拟化容器与智能时代的系统演进

## 安全的三条底线：保密、完整、可用

* **机密性（Confidentiality，保密性）**

    * > **定义**：你不想给别人看的东西，别人就看不到。

    * 实现的基本手段是加密：文件系统本身可以加密；现代手机（无论苹果还是安卓）都有一块加密计算区域，它甚至不信任操作系统，以极安全的方式保存指纹这类敏感信息。

    * 边界：删掉东西、甚至格式化，在当时都可能被捞回来，所以"删除"不等于保密。

* **完整性（Integrity）**

    * > **定义**：你不想让别人改的东西，别人就改不了。

    * 篡改别人的数据是入刑的行为，对应破坏信息系统罪。

    * 典型形态：用钓鱼的 XSS 链接发给有权限的人，对方在邮箱里点开即泄露 session，攻击者于是既能看（机密性）也能改（完整性）。

* **可用性（Availability）**

    * > **定义**：自己有的一个服务、一个能用的东西，必须一直能用。

    * 攻击可用性可以完全不碰前两条：把别人的柜子加一把锁再把钥匙扔掉，既看不到也改不了，但用不了了。

* **拒绝服务攻击（Denial-of-Service，DoS）与分布式拒绝服务（DDoS）**

    * 机理：先用入侵手段拿到大量机器的登录资格（例如一万台机器的 SSH 权限），再用这些资格同时对同一目标服务发起消耗性请求。

    * 门槛可以很低：在云上租几台主机，向网络服务发送超长请求，就能瞬间打瘫一个服务。

* **算法复杂性攻击（Algorithmic Complexity Attack）**

    * > **定义**：利用程序的最坏时间复杂性，精心构造让内部数据结构退化的输入。

    * 哈希表例子：正常情况元素均匀分散，每次操作平均 $O(1)$；若精心构造许多都哈希到同一地址的字符串，开放寻址或链表实现就退化成线性时间的数据结构。

    * 对策：桶大到一定程度时换成 worst case 优于线性的结构（例如一棵树）。

    * 提示：可用性更多是资源管控时要处理的事，操作系统的主要职责是提供实现保密性与完整性的机制。

## 无保护时代的硬件与网络

### 一台 8086 PC 的裸奔状态

* **实模式（Real Mode）**

    * 机理：`CS` 与 `IP` 各 16 位，把 `CS` 左移 4 位再与 `IP` 相加得到 20 位地址，于是有寻址 1 MB 的能力。

    * 后果：这个 CPU 没有任何保护，你可以 patch 任何一个程序的任何一条指令。

* **INT 系统调用**

    * 机理：`INT n` 算出地址 $n \times 4$，从地址空间最底部的**中断向量表**取出一段远地址，做一次长跳转，等价于一次函数调用，跳到 firmware 里只读的代码去执行。

    * 边界：系统调用实现在 firmware 里，你改不了它；但你可以任意改另一个程序地址空间里的内存，既没有 API 监管也没有审计。

* **加壳（Packing）**

    * > **定义**：在 ELF 文件里 patch 上任意一段代码，并把 ELF 的 `entry` 改成自己的代码。

    * 机理：程序启动先跑壳代码，壳跑完再跳回原来的 `entry`，外观与行为完全不变；但每次运行都会悄悄执行壳代码，于是可以复制自身、感染其他计算机。

    * 后果：破坏硬件也是可能的，CIH 就属于能破坏硬件的病毒。

### 网络层面的无防护状态

* 明文凭据

    * 机理：当时的网站（包括 HTTPS 尚未流行时的各类服务）把用户名和密码全部以明文在网络上传输，做一个钓鱼路由器就能收集到大量密码。

    * 后果：配合脚本暴力尝试登录，再爬到一份用户列表，就能批量得到账号。

* 性质转变

    * 边界：当互联网只是可有可无的东西时，不安全可以接受；一旦牵涉个人隐私与支付（例如账户里有真实的钱），安全性就从"无所谓"变成核心问题。

## 密码学的最小必要

* **单向函数（One-Way Function）**

    * > **定义**：$f(x)$ 正向很好算，逆向极难算。

    * 两个必备性质：给你 $y$ 极难求出 $x$ 使 $f(x)=y$；极难找到两个输入碰撞到同一个 hash value；你几乎只能暴力随机地找，输出看起来就是随机的。

    * 与标准库哈希的区别：标准库的 hash 追求快和分散，把字符串当 256 进制数取模，末尾字母从 `a` 改成 `b` 哈希值就加一，是可预测的；MD5、SHA-256 这类密码学哈希追求的是不可逆、不可碰撞。

    * 用途：做 hash digest 校验完整性与是否损坏，函数本身（MD5、sha1sum）是公开的。

    * > **提示**：标准库哈希用来做索引，密码学哈希才能用来做完整性校验和签名——两者不可互换。

* **陷门单向函数（Trapdoor One-Way Function）**

    * > **定义**：$f$ 依然正向易算、反向难算，但持有陷门 $t$（可理解为后门）的人可以轻松求逆。

    * 对应关系：`.ssh` 下的 `id_rsa.pub` 就是公开的那份函数，`id_rsa` 私钥就是陷门 $t$。

    * 正向使用实现机密性：用公开的 $f$ 把数据加密，任何拿到 $f$ 的人都能验证，但只有持 $t$ 的人能解回明文。

    * 反向使用实现认证：我生成随机 $y$ 交给你，你能在短时间内给出 $x = f^{-1}(y)$，就说明你持有 $t$，我不需要看到 $t$——这是一种在时间维度上的信任。

    * 把随机数换成任意文件的哈希，就得到**数字签名**。

    * > **注意**：公开 $f$ 的过程本身有危险，信任是不断传递的，所以必须在一个可信的地方去公开你的 $f$。

* **区块链（Blockchain）**

    * > **定义**：全世界共同维护的一份 append-only 数据结构，每个块的哈希覆盖它所有前缀的哈希。

    * 机理：每一块可理解为一个字符串加签名；实际实现不用链表，而用树状结构快速维护所有前缀哈希。

    * **工作量证明（Proof-of-Work）**：任何参与者向随机位置扔一根独一无二的骨头并广播，其他人只能随机地找（这正是靠单向函数保证的），捡到的判据是那根骨头是一个足够小的 hash value——于是它证明了你投入的时间。

    * 分叉规则：允许多人同时扔、捡，链会分叉，但所有参与者共同遵守"谁更长就听谁的"；由于捡骨头极难使 append 变难，短时间内不会出现全世界同时捡到骨头，所以分叉不多、收敛较快。

    * 扩展：append 的不一定是字符串，可以是一段图灵完备的代码（例如"从哪个钱包转多少钱到哪个钱包"），所有人 replay 链上全部状态，就得到全世界共识的 append-only 数据结构。

    * 边界：它带来绝对的可用性（全世界都是 replica），但它**没有任何机密性**，本来就是为了分布式共识而设计的。

    * 私钥的形态：24 个英文单词就是 private key，持有它才能对自己的转账做数字签名。

## 操作系统中的访问控制

* **默认隔离与 API 作为唯一出入口**

    * 现状：进程的地址空间是虚拟且隔离的，只执行计算指令时完全被封在自己的虚拟地址空间里；对操作系统所有对象的访问都必须通过 API 完成——不再像 8086 时代，任何程序都能访问所有硬件设备和每一个字节的内存。

    * 推论：API 是唯一的"口子"，操作系统牢牢抓住它，于是访问控制可以在这一层实现。

* **机制与策略的分离**

    * 机制：访问发生时的控制和检查——操作系统有权直接拒绝一次调用。

    * 策略：为系统配置哪些进程（主体）可以访问哪些对象。

    * 三类映射：拒绝越权的读得到机密性；拒绝无权限的写得到完整性；对资源管控对象的访问实现得足够公平则提供一定程度的可用性。

* **访问控制矩阵（Access Control Matrix）**

    * > **定义**：因为系统调用是程序访问对象的唯一边界，访问控制本质上就是一张巨大无比的表。

    * 三列结构：主体是进程或线程（一段可以运行、具有 running context 的东西才能访问对象），对象是操作系统里各式各样的资源，访问方式是读、写，或更细的如对 KVM 做 ioctl。

    * 规模问题：几千几万个进程 × 几百万个对象 × 多种访问方式，乘起来存不下。

    * 可压缩的本质：这个矩阵是低秩的——低权限用户对几乎所有东西都应当拒绝，除自己的东西与系统公用只读的那部分外什么都不能看、不能改。

* **用户与组**

    * 建模：UNIX 用整数表示身份，从现实世界的"每个物件有 owner、又可以在不同人之间共享"继承到用户与组的概念。用户与组都能在任意目录的正确 list 输出里看到。

    * **root（UID 0）**：权限绝对高，所有访问控制对他一律放行；无论 mode 写成什么，root 总能访问——否则一个错误配置会让文件连 root 都删不掉，等于在磁盘里塞进一堆删不掉又占空间的东西，反过来伤害可用性。

    * 登录与继承：root 可以 `setuid` 把自己变成任何一个别人，登录本质上是以最高权限做一次密码验证，通过后进程变成那个登录用户；子进程继承父进程的用户，所以在整棵进程树里权限相同。

    * 组的特点：一个用户可以属于多个组。

* **权限位与用户表**

    * 文件 mode 用三组三位分别描述文件所有者、所属组、其他用户的读、写、执行，于是那张大表被压缩成每个文件里的几个字节。

    | 归属关系 | 权限位 | 含义 |
    | :--- | :--- | :--- |
    | 文件的所有者 | 第 1 组三位 | 同一个用户的读、写、执行 |
    | 所属的组 | 第 2 组三位 | 同一个组的读、写、执行 |
    | 其它用户 | 第 3 组三位 | 剩下所有人的读、写、执行 |

    * `/etc/passwd` 的字段顺序为 `username : password : uid : gid : comment : home : login shell`；它对普通用户只读、只有 root 可改，密码的 hash（单向函数结果）就放在里面，`chsh` 改的就是第七个字段。

    * > **提示**：系统里"有哪些用户、有哪些组"这张表本身也需要一个载体，这就是 `/etc/passwd` 的角色。

* **setuid 与多套 UID**

    * > **定义**：设置了 setuid 位的文件，执行时以**文件所有者的权限**运行，而不是以当前用户的权限运行。

    * 机理：`/bin/passwd` 的 owner 是 root，mode 里 `x` 的位置上显示成 `s`（`rws`），以红色显示；普通用户执行它时该进程的 effective uid 变成 0，于是对 `/etc/passwd` 的写被放行。

    * 风险边界：把不属于自己的文件设成 setuid 是非常危险的操作——可执行程序因此获得超越执行者本身的权限；只要程序里有一个漏洞就可能被攻击，所以这个机制也不常用。

    * 演化现实：系统里有 real UID、saved UID、effective UID、file system UID（现已不用）等多套补丁。

    * > **易错点**：访问控制不是"UID 决定一切"这么简单，UID 上打满了为了实现系统功能的各种补丁；这套多 UID 设计被专门著文澄清过，正说明它不是直觉能推出来的。

## 访问控制的不同投影

* **把机制看作矩阵的投影**

    * > **定义**：各种实际机制都是在同一张访问控制矩阵上切出来的切面，区别只在行是什么、列是什么、格子里的判定有多细。

    * 排列方式：POSIX ACL、AppArmor、seccomp 这些机制都能顺着"这是矩阵的哪一种投影"被一件件摆开——先有人问"如果把某种访问控制机制当成整张矩阵的一个投影来理解该怎么解释"，这些机制就会一样一样被摆开。

* **POSIX ACL（Access Control List）**

    * > **定义**：以文件为对象、以用户和组为控制维度的细粒度访问控制，支持为用户和组分别设置权限。

    * 载体：挂在文件的扩展属性（extended attribute）上，等于把这套规则写进文件的元数据。

* **AppArmor**

    * > **定义**：访问控制落在 program 上，而不落在 user / UID 上。

    * 前提对比：普通程序的权限来自继承父进程的 UID——同一段不变的代码在 root 的 shell 里就是 root 权限，在普通用户下就是普通用户权限。

    * 机理：给程序一个访问上限（例如 Nginx 只能看到某几个目录里的文件），把系统里其他部分直接从它眼里抹去，它偷偷去调 `passwd` 这类危险动作就无从发生。

    * > **提示**：不逐条判断"你能不能访问它"，而是让它在自己的世界里根本看不到那个对象，这本身就是一种做访问控制的思路。

* **seccomp 与 eBPF**

    * 路线：在进程上砌一道墙，再留几个由 eBPF 把守的门；每当被监控的程序通过 API 访问对象时，额外走一个自己写的 access control function。

    * **eBPF（extended Berkeley Packet Filter）**：允许把一小段自己写的代码插入内核的机制，这段代码只读、不能随意改内核，但可以有返回值——返回的 yes / no 决定访问被接受还是拒绝。

    * 进展：从内核 5.7 开始，也有用 BPF 实现的 LSM 来做访问控制。

    * 边界：可以激进到为每一次单独的访问配一个图灵完备的程序检查，甚至调用大语言模型来裁决接受还是拒绝；也可以像 AppArmor 那样只关注常用部分，在效率与粒度间做 tradeoff。

## 程序内部没人走过的路径

* **访问控制管不住的边界**

    * 对外程序的正规做法：Nginx 这类暴露在外部的程序会选一个权限非常低的用户去执行，即使被入侵也破坏不了系统其他部分；Android 里每个应用都是一个单独的用户。

    * 问题所在：某些程序（如带 setuid 位的 `/bin/passwd`）跑在 root 权限下，而程序里隐藏着无数没有人能理解的路径——你无法预期用户会怎么恶意地使用你的产品。

* **模糊测试（Fuzz Testing）**

    * > **定义**：自动生成大量看起来随机、完全不对、无法解释的输入，把程序走到预先没有想象过的路径上。

    * 后果：那条路径可能悄悄泄露别人的个人隐私，或者悄悄在账户里加上很多钱——山寨支付宝的例子就是减到 0 后再扣，unsigned integer 让钱包变成无穷多的钱。

    * 规模与效率：OSS-Fuzz 已经找到上万个漏洞；用一条 prompt 就给 GCC 和 LLVM 找了 150 个 bug，模型入场后攻击者手上的 zero-day 会更多。

    * 边界：访问控制管得住"谁能碰哪个对象"，管不住"程序被喂了奇怪输入之后会走到哪一步"。

* **栈溢出与返回地址覆盖**

    * 模型：`char buffer[64]; scanf("%s", buffer);` 这种写法本身没有长度检查；栈从高地址向低地址生长，`call` 先压入 return address，函数栈帧再分配 buffer——`buffer[0]` 在低地址、`buffer[63]` 在高地址。

    * 机理：buffer overflow 是 **undefined behavior**（未定义行为），写入方向沿低地址到高地址一路往后，于是会覆盖掉位于高地址一侧的 return address。

    * 后果：覆盖返回地址后指针飞走，跳到一个不存在的页面，程序 crash。

    * 攻击形态：如果能知道 `system`、`execve` 的地址，就可以构造一个合法地址写进返回地址，让控制流跳过去并附带一个合法参数——对以 root 运行的 setuid 程序而言，这就直接换来一个 root shell。

* **代码注入与 NX**

    * 注入变体：把返回地址跳到自己的栈上，栈上就是一段可直接执行的代码，`return` 时 CPU 机械地跳过去执行，代码做一次 `execve("/bin/sh")`。

    * 细节约束：payload 里不能出现 `\0`，因为常见的溢出点是 `strcpy`，碰到 `\0` 就停止拷贝。

    * **NX（Execution Disable）**

        * > **定义**：页表里的一个 bit，被标上的页面不可执行。

        * 效果：所有分配给进程栈的页面都标上它，注入代码即使跳过去也只会得到 segmentation fault。

* **返回导向编程（Return-Oriented Programming，ROP）**

    * > **定义**：从已有代码里剪出以 `return` 结尾的片段作为 gadget，靠栈上排出的一串地址把它们按序串起来执行。

    * 机理：`pop rdi; ret` 可以控制第一个参数，`pop rsi; ret` 控制第二个；栈上放好几个返回地址，一条 `ret` 接一条 `ret`，就在已有代码的片段上到处跳，假装按顺序执行。

    * 边界：就这套架构而言，理论上没法防御——它用的全是你自己代码里合法的指令。

* **让攻击变贵的机制**

    | 机制 | 它挡的是什么 |
    | :--- | :--- |
    | NX（栈不可执行） | 直接跳到栈上执行注入的代码 |
    | stack-protector / canary | 在返回地址被覆盖时把这次破坏暴露出来 |
    | 地址空间随机化 | 让攻击者猜不到代码与栈的地址 |
    | CFI（`endbr64`） | 用已有代码片段拼出来的控制流（ROP） |
    | auditd 这类审计机制 | 程序做了不符合你预期的事，事后能发现 |

* **canary**

    * > **定义**：在 return address 之前放一个随机且猜不到的数字（例如进程启动时随机生成），一旦 buffer overflow 往外写就必须先把它覆盖掉；返回前检查它即可发现栈被破坏。

    * 命名来源：矿井里的金丝雀对一氧化碳的敏感度远高于人，它不叫了就说明气体泄漏，用牺牲自己来保护人的安全。

    * 同类思路：调试版本拿固定填充字节去填未初始化内存，中文编码下显示成一串"烫烫烫"，本质是用一个能察觉的记号把"这块内存被写入过／还没初始化"暴露出来。

* **控制流完整性（Control-flow Integrity，CFI）**

    * > **定义**：只有程序里写下来的那条控制流是应许的，其它所有跳转都是不应许的。

    * 机理：`endbr64` 意为"分支终止"，标记这里是合法的分支跳转目标；跳转落在它上面才被允许，想跳到 `pop rsi` 再 `return` 会因为那里不是合法跳转位置而失败。

    * 更深的形态：追踪程序的每一条指令、每一次函数调用、每一个参数与每一次跳转，看它是否契合你对这个程序的预期；auditd 这类审计机制其实也是一种访问控制。

    * 提示：攻与防互相成长；如果不那么在意开销、愿意接受运行时慢一点，安全问题会好解决得多。

## 旁路攻击

* **时间旁路（Timing Side Channel）**

    * 场景：内核里的 `check_password` 逐字节比较，任何一位不等就 `sleep(3)` 再返回 Access denied，功能上没有任何问题，而且 sleep 还防止暴力尝试。

    * 攻击前提：用户只能给 API 一个 password，但他可以改变这个 password 在内存里的排布——把它放在页面边界上，并设法让紧邻的那一页被换出内存。

    * 换页手段：申请大量内存（完全合法），疯狂读写其他内存，并伙同其他进程把系统内存压力做大，于是"从没访问过的冷数据"被放到磁盘上；内核里持续拣冷页压缩存放的机制在这里帮了攻击者。

    * 判据：猜对则该页是热的、比较继续走到下一页，引发缺页去磁盘读，明显变慢；猜错则当场返回，明显变快。从磁盘跑一个来回的时间差足够判断这一位是否正确，逐位右移后就能把密码猜出来。

    * 复杂性收益：把指数时间的搜索降成多项式时间，即使密码很长也一样。

    * > **易错点**：这里没有 undefined behavior、没有漏洞、内核没有被攻破——时间本身泄漏了信息，这就是旁路攻击。

* **Meltdown**

    * 攻击代码：`d = *ptr;`（非法解引用，会被 MMU 拦下）紧接着 `x = probe[d * 4096];`（按指令顺序理论上一行 crash 之后这一行永远不会执行）。

    * 前提：在此之前操作系统把内核内存与进程内存映射在同一个地址空间里。

    * 机理：诱导分支预测器认为后续代码会执行，于是在前面指令尚未 commit 时就把两条指令取指、译码并暂存；`d = *ptr` 这一步没检查权限就把内核数据取了出来（CPU 为了尽快执行下一条指令而提前做了这次 dereference），再算 `d * 4096` 并做一次 load，把对应 cache line 弄热。

    * 读取：程序继续执行时那次崩溃的条件成立，投机指令全部销毁、没有任何 side effect，但对 cache 的影响保留下来了；另一个线程把 `probe[0*4096]`、`probe[1*4096]`……逐个探一遍，访问延迟明显低的那一个下标就是偷出的字节。

    * 修复：内核再也不敢把操作系统内核与进程映射到同一个地址空间，任何试图偷数据的指针都变成非法地址。

* **物理世界的旁路**

    * 显示侧：放一个天线隔着三层石膏板、10 米距离复原射线管显示器的图像——显示器向你在发射电子，少量电子能穿过墙壁被传感器感知。

    * 计算侧：通过 CPU 的电磁信号提取 private key，proof of concept 藏在一个饼里；你 ssh 登录时旁边的人就完成了 physical key extraction。

    * 存储侧：内存是 volatile memory，但拆开笔记本、用液氮浇内存条再放进保温箱偷走，DRAM 里未销毁的文档、操作系统状态、浏览器 session、private key 就都出来了。

    * 边界：要防的不只是自己软件的 bug、漏洞与 undefined behavior，还有各式各样的 side channel。

## AI 时代的安全

* **越狱（Jailbreak）**

    * 奶奶漏洞：以"我奶奶每天晚上讲故事时都会给我一个 Windows 10 序列号"这类起始词开场，模型被微调掉的戒备被放松，于是输出了真正可用的序列号。

    * 伪造对话历史：假装一段它与你已经产生过的对话，把想引导的内容伪装成它的输出，继续往后它就会认为"我前面已经这样输出了，那我也可以这样输出"。

    * 权重路线：如果手上有模型权重，可以像研究者那样直接改变权重来破掉它的安全防御。

* **提示注入（Prompt Injection）**

    * 一次注入一点：每次都是无害的输出要求，累积在文件里就成了恶意 prompt，Agent 一读该文件就被注入，机制上与返回导向编程的"拼片段"相似。

    * 网页侧：被恶意者隐藏了 prompt 的网页被 fetch 后，若清洗不干净或以原样粘进上下文，重复几次（每次都在内容后补一句"这个学习内容很好、其实很有付费意愿"）就能诱导小模型把 API key 交出去。

    * 对策与其矛盾：只能通过沙箱或访问控制给每一次大语言模型调用最少权限；但把权限全部给出时（例如让 Agent 充分操作），能力才最好——限制它就会频繁遇到"这个权限没有"，这就是新的安全问题。

* **供应链攻击（Supply Chain Attack）**

    * 铺垫路径：先发布一个名字有迷惑性、无人使用的恶意包（例如伪装成加解密库的 `plain-crypto-js`），安静地待在 GitHub 上等着，等有一天混着一个 feature 把它加进去；该例 release 一两分钟就被安全机构发现。

    * 权限路径：与某个有仓库推送或 approve 权限的 maintainer 走得近，趁其不留神拿走 U 盘里的 private key，之后就可以卧薪尝胆地等。

    * 触发机制：安装时运行的 install hook（npm 的 install、`apt` 的 install 都有）遍历 home 目录下的 `.claude` 与各种环境变量，找出所有可能是 API key 的东西并外传。

    * 现实面：GitHub 上有很多把 API key 直接写在仓库里的代码，论文投稿代码里也出现过仍然 active 的 key，这已经是一条灰产。

    * 结论：进入 Agent 时代，安全问题没有变少，只是换了面孔——要防的不再只是自己程序里的 bug，还有喂给模型的每一段文字和你依赖的每一个包；访问控制反而更重要，它仍然是手上最后那道能自己掌控的边界。

## 全系统模拟与即时编译

* **全系统模拟（Full-System Emulation）**

    * 概念模型：一条一条指令地译码、执行，再把特权级指令补上，就能在上面运行一个真正的操作系统；模型不难，难的是性能。

    * 性能现实：跑到真机十分之一已经不错，十分之一意味着图形 heavy 的程序都没法看。

    * 参照：虚拟机时代之前，为 Windows 装 Linux 的标准答案是 VMware——在 Windows 里模拟出一台完整的 x86 裸机，加载光盘镜像后按 firmware 启动流程装系统。

* **基本块（Basic Block）**

    * > **定义**：连续执行、中途没有跳转、以一条跳转收尾的那段指令序列。

    * 取指方式：取出一条指令发现不是跳转就再取一条，一路取出好多条连续指令，直到一条带跳转的指令收尾。

    * 价值来源：跳转目标在执行前不确定——条件分支要等条件成立与否，`return` 要从栈上 pop 一个地址，只要序列里没有这类指令，顺着 PC 往下取就一定知道它们会按一、二、三、四顺序执行下去。

* **即时编译（Just-In-Time，JIT）**

    * 基本做法：把基本块翻译成一段合法的 C 代码，CPU state 用宏展开直接对应宿主机器上的寄存器，立即数硬编码进生成的代码；这段代码交给 GCC 编译成 `.so`，用 `dlopen` 加载进自己的地址空间，做完重定位后直接调用，省掉译码与从译码结果取数。

    * > **易错点**：如果每个基本块都要绕一次外部 GCC，性能没人能接受；而且有些基本块这辈子只运行一次（例如程序启动时那段代码），为它绕一趟编译器可能一百毫秒就没了，根本不划算。

    * 正确形态：优化过的模拟器刚启动时处于解释模式，一边执行一边给每个基本块计数；某个基本块计数累加触发阈值（例如一万或十万次）时，才认为编译开销能被收益抵回来，于是启动后台线程调用编译器——这个编译器一般直接写死在 JIT 系统里，不会另起进程去调外部编译器。

    * 生效方式：编译回来后，下一次执行到该基本块发现已经编译好，就用一个指针跳转过去执行编译后的代码。

    ```text
    基本块第一次执行
          │  每执行一次，计数器 +1
          ▼
       计数超过阈值了吗？
       ├── 否 ──► 继续解释执行
       └── 是 ──► 后台线程编译这个基本块
                      │
                      ▼
              之后再遇到它，直接跳到编译好的代码
    ```

    * 同源实现：Java 的 Virtual Machine、Node.js 的 Virtual Machine 等 Language VM 遵循的正是同一个循环。

* **QEMU 的模板翻译**

    * > **定义**：介于完全解释执行与 JIT 编译之间的路线——把预先编译好的指令模板拼进代码缓冲区，再 patch 立即数，出自早期名为 dynamic generator 的实现。

    * 目标问题：希望同一份模拟器实现能跑在 PowerPC、ARM、x86、x86-64 等多种宿主上，又不想随时去调外部 GCC；那就用一个能在各种宿主上运行的编译器，预先生成一批"还算比较优化"的模板。

    * 关键拆解：把一条 `addi`（语义 `r1 = r1 + 16`）拆成三条手写的中间操作——把 `r1` 复制到临时寄存器 `t0`、把立即数加到 `t0` 上、把 `t0` 写回 `r1`。因为 `t0` 是临时的，任何体系结构上都能找到寄存器来承载它（ARM 上模拟 PowerPC 就用 ARM 的某个寄存器），靠一个宏来指认"`t0` 是什么"。

    * 预编译阶段：这三行写成 C 函数后可以编译但不能链接，因为立即数此刻未知；在 x86 上最终会是一条 `add` 立即数指令，立即数占 32 位，于是先留四个字节的 0 作 placeholder，同时记下"这里需要重定位"，再把这一小段本地机器码存进模板库。

    * 翻译阶段：取出一条指令后 `memcpy` 一份模板，按重定位信息把立即数 patch 进去（要加 16 就 patch 成 16），一次非常轻量级的编译就完成了。

    * 收益：译码一次可取出一大串指令，译码代价被平摊；模拟一条 PowerPC 指令，实际只需要三条 x86 指令。

    ```text
    预编译阶段（只做一次）
      手写的 addi 语义（C 代码：三条操作）
            │  经宏映射到宿主寄存器后编译
            ▼
      一小段本地机器码，立即数的位置留成 4 字节 0
            │
            ▼
      存进模板库，同时记下"这里需要重定位"

    翻译阶段（每遇到一条指令）
      取出一条 addi ──► memcpy 一份模板 ──► 按重定位把立即数 patch 进去
    ```

* **三条路线的代价对比**

    | 做法 | 怎么执行 | 代价 |
    | :--- | :--- | :--- |
    | 解释执行 | 取指、译码、逐条执行 | 每条指令都要译码，中间还有大量函数调用 |
    | 即时编译 | 把基本块编译成宿主代码后跳过去执行 | 编译本身有开销，所以要等它"变热"才值得做 |
    | 模板翻译（QEMU） | 把预编译好的指令模板拼进代码缓冲区，再 patch 立即数 | 每条指令一次内存拷贝，加一两次打补丁 |

## 虚拟机的黄金时代

### Disco 与整机虚拟化的动机

* **虚拟机监视器（Virtual Machine Monitor）**

    * > **定义**：1970 年就被操作系统设计者提出的概念——真正去 virtualize 一台计算机，在一台物理机器上做出好多台虚拟的机器。

    * 类比推演：进程是一台虚拟计算机（有地址空间、有时间片，看起来独占计算机），I/O 访问通过操作系统接口受控才有虚拟化；而 I/O 接口说到底也是一种 API，把 I/O 也虚拟化、再用中断之类的机制在虚拟机之间切换，就像在进程之间切换。

    * 当年的合理性：1970 年代都是大型机，可能一整个学校只有一台计算机，把一台机器虚拟成好多台能力弱一些的小机器非常有市场前景，但这个理念长期没有真正做成。

    * Disco 的形态：虚拟机之上可以跑各种操作系统——一个操作系统跑多个应用、一个多处理器操作系统、一个跑数据库、一个跑 NFS server，以及一个很薄、类似今天 unikernel 的 ThinOS（application 与 OS 基本链接在一起）。

* **商业动机：90% 的空闲 CPU**

    * 背景：2000 年 dot-com 泡沫中纳指翻五倍；开公司卖服务一般是去找 ISP 租一台机器。

    * 观察：租来的机器上跑 BBS、邮件服务器或 web 服务器，CPU 空闲率常达 90% 以上——大部分时间没人访问；即使访问较多，处理逻辑也不过是 HTTP 请求来了跑一个 CGI-BIN，从文件系统读一个缓存还是热的文件就直接返回，压根没经过磁盘 I/O。

    * 做法：不再卖物理机，而是卖"虚拟机"，并承诺用起来和物理机一样好（最快时几乎一样快，一起用时偶尔稍慢则给补偿）；因为模拟出来的机器在使用上看不出区别，就可以一台物理机跑十个实例、卖十份服务。

    * **超卖（Oversubscribe）**：云厂商承诺算力但常常卖到 120% 甚至 140%，赌的是不是所有人在所有时间都把算力拉满；只推更新时才编译、deadline 前才多一点负载的站点，CPU 贡献几乎为零。

    * > **易错点**：QEMU 这种模拟会慢到十分之一左右，而十分之一对想"一台当十台卖"的商人显然不可接受——这正是需要更小开销虚拟化的原因。

* **从论文长出来的公司**

    * 起点：SOSP 97 上 Disco 的论文，写法上把自己的定位说成"bring back an idea popular in 1970s"——1970 年大家都想做的事，碍于硬件、软件或技术不成熟没做成，今天把它做出来了。

    * 落地：论文的几位作者（几个博士生）被一起带走创办了 VMware，上市时募资规模可能是仅次于 Google 的；后来先被 EMC 收购，又被戴尔收购。

    * 结论：泡沫里绝大部分做产品的投机家死了，但技术留下来了——硅谷很多 startup 就是这样起来的：手上有一篇真的解决了某个问题的论文，然后去想怎么挣大钱。

### 整机虚拟化的技术难点

* **特权级**

    * 现状：x86 上有 Ring 0 到 Ring 3，Ring 0 最高，进程运行在 Ring 3；Ring 1 和 Ring 2 在体系结构里设计了但实际不使用。

    * syscall 的双重性质：它是一条指令、本质上是一次跳转，但这次跳转会把特权级从 3 切到 0，此后就能执行各种特权指令（例如关中断）。

    * 边界：应用在 Ring 3 直接执行关中断这类特权操作会 segmentation fault，程序直接 crash。

    * 必须接住的行为：作为虚拟机必须允许客户机内核"关中断以后死循环"这件事发生——否则就看不到那个操作系统的完整行为，也就没法调试它。

* **CR3 与页表**

    * 本质：虚拟内存就是一副 VR 眼镜，配置的是虚拟地址到物理地址的映射（虚拟页号 1、2、3、4 → 物理页号 1、2、3），每条映射还可以带读、写、执行权限，无论一级、两级还是三级页表，都是索引加一条条 PTE entry 组成的数据结构。

    * 可被改写：既然是数据结构，内核代码就可以直接用 load / store 去改它，只要改一个内存地址，映射就变到别处去了。

    * > **提示**：改数据结构和改动生效是两件事——改完页表项映射不会立即生效，要把新页表的地址 `mov` 到 `CR3` 才生效；这些操作都具有摧毁性，不能直接在 CPU 上执行，必须模拟。

    * 困难所在：进程想改自己的地址空间必须通过系统调用（对 Linux 是 `mmap`），所以截持 `mmap` 就能模拟进程——Windows Subsystem for Linux 就是这么干的；但内核可以随便把 `CR3` 改掉。

    * 希望所在：内核里 99.99% 的指令都是普通指令——查文件描述符、找文件系统、跳到对应函数、在缓存数据结构里查找，全是数据结构的运算，只有真正要做 I/O 时才发一条 I/O 指令然后等结果返回。

* **VMware 的解法：Ring 1 与影子页表**

    * 分层设计：应用进程照旧跑在 Ring 3，客户机操作系统内核被搬到 Ring 1（不给它任何权限），Ring 0 是宿主操作系统加 VMware 驱动——真正拥有物理内存的人。

    ```text
    Ring 3   应用程序                （原样运行，一行代码都不用改）
    Ring 1   客户机操作系统内核        （被搬到这里，没有任何特权）
    Ring 0   宿主操作系统 + VMware 驱动 （真正拥有物理内存的人）
    ```

    * 拦截机理：客户机内核在 Ring 1 执行的每一条特权指令（关中断、执行 I/O、改 `CR3`）都会产生异常，执行流由 VMware 装的驱动送到 hypervisor，于是所有会引起严重后果的非法指令都被收编；如果硬件上没有 Ring 1，它还有办法——扫描内核指令并像插 breakpoint 那样 patch 掉它们来劫持。

    * **影子页表（Shadow Page Table）**

        * > **定义**：把客户机以为自己拥有的物理地址空间，重新翻译成真实物理地址的那份、真正写进 `CR3` 的页表。

        * 机理：客户机内核认为自己拥有整个物理地址空间，按"虚拟页 1→自己的第 1 页、虚拟页 2→自己的第 2 页"维护页表；而 VMware 才知道物理内存有限，为这个操作系统实际分配的是第四、第六、第八页，于是它重组一份 1→第 4 页、2→第 6 页、3→第 8 页的页表——相当于戴了一副两级虚拟的 VR 眼镜。

    ```text
    客户机自己写的页表（它以为的样子）
      虚拟页 1  ->  自己占的第 1 页（可读写执行）
      虚拟页 2  ->  自己占的第 2 页（可读写）
      虚拟页 3  ->  自己占的第 3 页（只读）

    VMware 边上的影子页表（真正写进 CR3 的那一份）
      自己占的第 1 页  ->  真实内存的第 4 页
      自己占的第 2 页  ->  真实内存的第 6 页
      自己占的第 3 页  ->  真实内存的第 8 页
    ```

    * 代价与收益：客户机每次 `mov` 到 `CR3` 时，VMware 悄悄把影子页表换上去，代价是要截持所有对 page table 的操作；换来的是操作系统 99% 的代码以本地速度执行，只有访问特权指令或 I/O 时才 trap 出去。

    * 产品意义：原来所有为单机设计的操作系统不需要任何修改，连安装程序都不用改，就能直接跑起来，这是它估值从空白到几十亿、几百亿美金的基础。

* **硬件接手的那些 hack**

    * 2005 年 Intel 推出第一个硬件虚拟化：不必再 hack Ring 1，可以专门进入一个虚拟机的模式（类似 Ring -1），很多特权指令可以直接执行；但执行 I/O 时仍会生成 VM exit，因为虚拟 I/O 设备是模拟出来的。

    * 2008 年 EPT：把影子页表用硬件实现，正常的四级页表之外还可以再有四级，构成八级页表，不再需要用软件维护那份页表；同期还有第一个比较流行的 LXC（Linux Containers）。

    * 标准化：virtio 提供虚拟 I/O 的接入方式，也有 virt-GPU 把 GPU 虚拟化接进来。

    * 疯狂的 idea：虚拟机日志与重放——单个 CPU 时只需记下何时发生 VM exit 以及 VM exit 之后干了什么，I/O 设备读到的值记下来就能重放整个计算机的执行历史；虚拟机迁移——暂停后把网络连接全部 drop 掉（假设设备都挂在可插拔总线上），虚拟机就是一团内存，把内存直接拷到另一台机器就能启动。

    * 复活场景：Agent 与沙箱需要这些技术，所以它们又开始复活。

## 从 os_id 到容器

### 操作系统自我虚拟化的思路

* **思路转向**

    * 反思：VMware 的路线是把整台机器虚拟化，但真正想干的事是把一台机器当十台卖；既然事实上总要跑操作系统，为什么操作系统自己不能把自己分成十份？

    * 本质还原：虚拟化本质不是为了虚拟化操作系统，而是为了执行应用程序（nginx、mail、BBS）；进程与操作系统唯一的交互就是 syscall。

* **os_id 方案**

    * 做法：操作系统启动时加载多份 `initramfs`（本来能加载一个，就没有道理不能加载两个），为每个对象增加一个 `os_id` 标签，相当于 `struct proc` 这类对象池多一维，`os_id = 1` 与 `os_id = 2` 就是两个不同的操作系统。

    * 隔离机制：pid 仍从同一个池子里分配（2、3、4、5、6），分配本身不用改，改的是"谁看得见谁"——遍历 `proc` 时只返回与自己 `os_id` 相同的进程，于是每个 `os_id` 都能有一个 `pid = 1`；3 号进程能 kill 1 号（同 `os_id`），5 号进程看不到 3 号（不同 `os_id`），kill 就不成立。

    * 性能收益：分配器不区分 `os_id`，所有对象的 allocation 共享同一个池子，只是在对象上打一个 4 字节的标签；对比虚拟机必须预先分配 4GB 还是 8GB 内存。

    ```text
    一个操作系统里的对象池（所有 os_id 共用同一个池子）
      |-- 进程 A   [os_id = 1]
      |-- 进程 B   [os_id = 2]
      |-- 文件 C   [os_id = 1]
      |-- 进程 D   [os_id = 2]
    ```

    * 来源：这本身也是 1970 年代的想法，正如 Disco 是把 1970 年代的想法复活一样。

### PID 的泄漏抽象

* **PID 会被回收利用**

    * 现象：`ps` 时看到一个 pid 还活着，等 `kill` 时它已提前死掉，于是报 no such process。

    * 风险：在服务几亿人的服务器上，先遍历进程表、进程因 I/O 等原因很久才回来运行，中间大量进程被创建和销毁，于是"先 grep 再 kill"的脚本可能杀错人。

    * > **定义**：PID 是一个 **leaky abstraction**（泄漏抽象）——它没有任何办法阻止你杀错，只能靠操作系统里再写别的机制（例如共同的父进程）来兜。

* **pidfd_open**

    * 设计逻辑：既然 everything is a file，想要引用操作系统里的对象就必须通过文件描述符——想要一个指向 pid 的指针（某种程度上也指向一个进程）也需要一次 `open`，所以 API 长成这样。

    * 引用语义：持有这个 pid 后引用计数加一，它就不可被释放；之后用 `pidfd_send_signal` 去 kill 这个 pidfd，就能确保杀掉的那个东西不会丢失。

    * 启示：PID 在 UNIX 时代是简单干净的好设计，当数据中心里有无穷多的进程时它就变成了 leaky abstraction；虚拟化也是一样——大家在某个时间点做的决定未必是全局最优的。

### 从 chroot 到 namespaces

* **chroot**

    * > **定义**：把进程的文件系统视图限制到某一个子目录底下的系统调用，Version 7 的 Unix 在 1979 年就提供了。

    * 使用门槛：一旦 `chroot` 什么 `/bin`、`/usr/bin` 都没有了，连 shell 都跑不起来；必须为它先构建一个完整的文件系统根（有 `/bin/bash`、有 `/home`）才能用。

    * 与虚拟机的关系：在两个文件系统上分别放一个假的 `/bin/bash`，再做 `chroot`，进程就只能看到这个文件系统根——很像一个虚拟机；但它没有隔离 PID，仍能看到别人的进程（没权限则 kill 不动）。

* **Linux namespaces**

    * 做法：枚举操作系统里有什么对象，为每一类对象实现这个命名空间的虚拟化，就得到了今天的 namespaces。

    * 需要虚拟化的对象：用户和组（两个 0 号用户互不访问，此处的 1000 号与彼处的 1000 号是不同用户）、文件系统（`chroot` 只管了一部分，还要管 mount point）、IPC（信号量、消息队列、共享内存互相不可见）、网络（端口也要虚拟化，两个 OS ID 都可以有各自的 localhost 5000）、系统时间与时区、主机名与域名、PID 编号空间。

    * 观察点：每个进程都在 `/proc/<pid>/ns/` 下露出自己的命名空间编号。

    ```text
    /proc/<pid>/ns/           （每个进程都在这里露出自己的命名空间编号）
      cgroup    资源控制组
      ipc       信号量、消息队列、共享内存
      mnt       挂载点视图（mount point）
      net       网络设备与端口
      pid       PID 编号空间
      time      系统时间与时区
      user      用户与组的编号空间
      uts       主机名与域名
    ```

    * 组合方式：不只是"一个 OS ID"，可以让两个进程共享同一个 net namespace 而有不同的 mount 或 ipc namespace；实际系统里 PID 1 的 init 拥有全套命名空间（根容器，其余进程默认共享），也有守护进程运行在隔离的命名空间上。

### cgroups 与容器

* **cgroups**

    * 动机：隔开之后还要能控量。用量虽然隔离了，但每个进程还是操作系统原来的进程，调度器没改的话所有进程仍然公平地执行。

    * 做法：给每个 OS ID 或组记一个 CPU cost，每当组内进程消耗一单位时间就往该组的 cost 上加一，于是可以规定某组最多用 CPU 的 20%，或让十个组共享均分一个 share。

    * 结构：cgroup v2 是一棵树——大组之间公平分享 CPU，大组内部的小组又可另设各自的策略。

    ```text
    cgroup v2 是一棵树
      /
      +-- 大组 A          （和其他大组公平分享 CPU）
      |     +-- 小组 A1   （各自设各自的资源策略）
      |     +-- 小组 A2
      +-- 大组 B
    ```

    * 正交关系：namespace 管的是"你看不看得见"，cgroup 管的是"圈定一批进程、再给这批进程定资源访问的规矩"（CPU、文件系统带宽、网络带宽）。

* **容器**

    * > **定义**：容器 = namespace（隔开可见性）+ cgroup（控制用量）+ 分层镜像（快速造出文件系统根）。

    * 分层镜像：用 OverlayFS 一层一层叠出文件系统根，而不必每次创建全新的根再 `chroot` 过去，可以非常轻量地创建同一个系统的好多个实例。

    ```text
    可写层        （容器自己写出来的东西）
      |
    镜像层 3      （应用）
      |
    镜像层 2      （运行环境）
      |
    镜像层 1      （操作系统基础镜像）  <-- 一台机器上 1000 个实例共用这一份
    ```

    * 收益：一台机器上放 1000 个实例都是同一个镜像，只要一个副本、只浪费一份存储——这就是资本家最喜欢的形态，也就等于发明了 Docker。

* **虚拟机与容器的安全性对比**

    * 虚拟机的优势：如果一个操作系统里有漏洞，容器会一起遭殃。

    * 容器漏洞之一（越权）：例如拿到一个指向全局内存的指针，就可以去访问别人的容器、偷走机密信息。

    * 容器漏洞之二（资源控制不足）：用不经意的方式（例如不停创建文件）把系统文件描述符表里的资源耗满，造成对其他容器的拒绝服务——自己想打开文件打不开，别人也打不开。

    * 成本权衡：虚拟机隔离更好但要模拟物理内存、影子页表，还得软件和硬件一起卷进来，实在太浪费；更轻量的方案可能更好，前提是接受略低的安全性。

* **两条路线的编年**

    | 时间 | 发生了什么 |
    | :--- | :--- |
    | 1979 | Version 7 的 Unix 提供 `chroot` |
    | 2000 | FreeBSD 有了 Jail，比 `chroot` 更完善 |
    | 2005 | Intel 推出第一个硬件虚拟化，进入类似 Ring -1 的模式 |
    | 2006 | cgroups 和 namespaces 被引入，由 Google 的工程师推动 |
    | 2008 | 有了 EPT，影子页表硬件化；也有了第一个比较流行的 LXC |
    | 现在 | Docker 成为了云原生里的标准答案 |

    * 判断：从 06 年的 cgroups 与 namespaces，到 08 年的 LXC，再到今天的 Docker；VMware 那条路把人类带歪了——没有必要为了两个隔离的东西去做那么重的事情（这还假设操作系统本身是安全的）。

    * 驱动力：挣钱的途径有一万条，full system virtualization 与从操作系统里割出小操作系统都是手段；真正的 meta-mechanism 是钱，以及"人类要进步"这个历史的车轮——即使做错了也不要紧，这正是这个机制最好、最有趣的地方。

## 云原生编排

* **Kubernetes 的编排模型**

    * 前提条件：Docker 用 hash 构建是 deterministic 的 build，所以可以直接在另外一台机器上再起一个同一个容器。

    * 做法：动态、透明地管理无状态的容器 pod——提出"这个容器在每个数据中心复制 100 份"这样的 policy，调度集群发现容器被杀就在另一台机器上再起一个；见缝插针地把容器插到余量比较大的机器上；网络异常或容器丢失都不要紧，换个地方再起。

    * 声明式访问与路由：配置好以后只访问 gateway 的 API，说"我要访问名字是教务的服务"，它自动把请求 body 送到对应容器并在某个端口把结果送回来；使用者完全不知道送到哪一台具体服务器上。

    * 收益：自动做负载均衡与健康检查，而且容器是见缝插针的，能给云厂商带来更多的钱；这也是把虚拟机的份额挤压得很小的主要原因（VMware 那边的数据中心管理软件要装专门的软件与带外控制信号，相对重得多）。

* **容器编排优化问题的边界**

    * 形式化：每个容器要多少 CPU、多少内存都不一样，等于一个有 weight 和 value 的背包问题——用最少数量的背包把所有东西打包走，是多维背包问题，属 NP-hard。

    * 品位问题：把容器编排写成整数线性规划再在数据集上证明效率提高，是很 well-motivated 的题；但如果假设静态、假设一瞬间就能知道有哪些容器，实际中前提往往不成立。

    * 现实动态性：集群里容器不停扩缩容，用户用一个命令行工具就能把容器从一个数据中心挪到另一个；后台服务还会动态检查并悄悄压缩长期无活跃度、无流量的容器——只要使用者感受不到区别，厂商就可以这么做。

    * 边界：这种压缩是商业机密的一部分，用户难以观测（类似存储集群在三个副本下仍能报告小于 1 的写放大这种看起来离谱的指标）。

## 操作系统与抽象

### 应用程序视角

* **操作系统的 API 定义**

    * > **定义**：从应用程序视角看，操作系统就是一组管理硬件资源、提供应用生态支撑的 API，一组 system call。

    * 需要的系统调用类别：想创建或改变进程就用进程管理的系统调用；想在原本非法的位置填上一块内存就用 `mmap`；想创建线程、实现互斥与同步也有对应系统调用；想在文件系统留下 persistent 的痕迹，甚至有"等数据落盘了再继续执行"这样的功能。

    * 一条公理：凡是与应用程序开发相关、你认为合理的事情，就一定有一个办法能做到。纯粹的计算（一台图灵机就能做的事）在进程地址空间里直接完成；一旦想和外面的世界打交道（例如发射一枚导弹），就必须借助操作系统。

    * 适用范围：从只会唱歌的单片机芯片，到手机、电脑，再到数据中心里的超级计算机与人工智能推理集群，操作系统形态都相当类似。

* **Agent 操作系统的起点**

    * 主张：不应该从 bare-metal、从裸机上从零构建一个新操作系统，而应该像 Android、iOS 那样借力——它们也不是在 ARM 处理器上从零构建，而是在 Linux 这样已经很好的经典操作系统之上再为应用封装一层。

    * 演化差异：过去写 C 直接编译成 binary 在操作系统上执行；现在写 Python、JavaScript、Swift 这类高级语言，经一层打包（编译或不编译）变成能在运行时环境上运行的东西——Python 有 bytecode，JavaScript 可以变成 WebAssembly 或编译成本机指令序列。

### 硬件视角

* **CPU 作为执行器与编译器**

    * 双面性：Linux 内核里上千万行机制都是为了把硬件性能发挥到极致；但反过来，硬件其实也看不到操作系统——CPU 就是一个无情执行指令的机器。

    * 编译器一面：做动态的数据流分析，指令译码后做依赖分析，电路天生并行，所以可以在一个周期里同时执行好几条指令；但它不管你的指令到底是什么，只要看起来合法、有权限、可执行就照单执行。

    * > **提示**：把 CPU 想象成一个人，手上有一本手册——每来一条指令就去手册里找到那条指令的行为，严格核对，然后把手册上那一句话执行掉。

* **协同进化**

    * 历史：最早只有一个处理器，没有多处理器并发，也没有"多处理器从入门到放弃"那一堆复杂东西。

    * 动因与结果：摩尔定律可能到头，加上大家想要能效比更高的芯片，于是有了多处理器系统、GPU、non-volatile memory；每当一个新东西加进来，操作系统也会跟着一起进化。

### 抽象这一关键字

* **抽象的作用**

    * 机理：操作系统世界底下的硬件非常复杂，有了好的抽象以后应用程序只需要看到 system calls，绝大部分时候不需要看到硬件的复杂性。

    * 边界：硬件的复杂性并没有消失——像 `ioctl` 这样的接口依然非常复杂——只是绝大部分时候我们可以工作在非常干净的模型上。

    * 收益：程序员与开发者的心智负担降低，大语言模型开发的心智也降低，于是 bug 减少，就能开发出更好的软件。

    ```text
    应用程序 / 大语言模型
            |  system calls
            v
      各种抽象层（存储设备、文件系统、并发编程模型）
            |  ioctl 这一类依然复杂的接口
            v
          硬件
    ```

* **抽象的生长方式**

    * 重复主题：存储设备的抽象、文件系统的抽象、并发编程模型的抽象，每一层都在做同一件事——屏蔽底下非常复杂的东西，并把底下的能力尽可能暴露给上面。

    * 生长方向：不能 top-down 地说"我们要做一个什么样的抽象"，而是永远从应用程序的需求出发；例如程序员在并发上一定会犯错，所以才需要更好的并发编程模型——CUDA、Go 的并发模型都是一层一层长出来的抽象。

    * 提示：能顺着把这些技术内容理解得比较好，就完全可以去考试，不用担心。

## Unix philosophy

* **两套应用生态的起点差异**

    * Windows 一侧：代表性应用是 Adobe 全家桶、Visual Studio、Office 这类生产力工具，一脉相承于"一个应用解决你的一个问题"——在它这里就把所有问题解决，最大程度服务新手：上手难度低，一开始只探索一小部分功能，随着理解加深再探索更多，而且功能始终在手边。

    * Unix 一侧：命令行给新手的第一印象就是恐惧来源；Unix 说这就是 open source 的全部，你有世界上所有的工具，可以用 `apt` 装 npm 再把自己升级起来——但门槛高，必须了解很多概念。

    * 值得付出的代价：Unix 设计中每个东西都不是单独的应用，而是希望任何应用一旦进入系统就成为系统的一部分，也成为所有其他应用程序的一部分。

    * 合作的机制：管道——一个非常干净的进程间协作机制，把 Unix 设计成每个小工具做好一件事，然后让世界上的工具去合作完成一件更大的事；工具有大有小，但都是这个思路。

    | 对比项 | Windows 的应用生态 | Unix 的应用生态 |
    | :--- | :--- | :--- |
    | 代表应用 | Adobe 全家桶、Visual Studio、Office | 一整个工具箱（`find`、`grep`、`sort` 之类） |
    | 设计取向 | 一个应用解决你的一个问题 | 每个工具只做好一件事 |
    | 合作方式 | 由单个应用包办全部功能 | 应用之间互相合作，靠管道串起来 |
    | 对新手 | 上手难度低，要的东西都在手边 | 需要先了解很多概念，门槛高 |
    | 生态气质 | 功能始终在手边 | 一旦进入系统，就成为所有其他应用的一部分 |

    * 边界：这两种取向并不矛盾——Windows 也可以有合作的机制，Unix 上也可以做 monolithic app——但这是它们设计操作系统时的不同起点。

    * 现状：干活时把事情做完最后管道给命令行工具，大语言模型成了管道的终点；即使将来用户只需要把意图告诉计算机，计算机专业的人依然要知道这件事的力量在哪里。

* **一条管道收集整学期的代码案例**

    * 前提：课件做了 content as code 的转化，全部在一个 repo 里且本身也都是代码，于是可以用脚本筛出所有展示过的代码案例。

    * 管道步骤：`find` 找出一个目录里满足 pattern 的所有文件（连编译出来的 Python bytecode 也在里面）→ `grep` 按 pattern 筛出想要的 → `sort -V` 按 `lecture 1`、`lecture 2`……的顺序排好 → 再一次 `grep` 只留 OS demo、滤掉 main 函数与 review and comments 这类干扰项 → 去重 → 拷进剪贴板 → 粘贴进 slides。

    ```text
    find os-2026     找出一堆候选文件（连编译出来的 Python bytecode 也在里面）
       |
      grep ...       按 pattern 筛出想要的那些
       |
     sort -V         按 lecture 1、2、3…… 的顺序排好
       |
      grep ...       只留 OS demo，滤掉 main 函数、review and comments
       |
      去重           同一段代码出现多次的只留一份
       |
     pbcopy          拷进剪贴板（Mac 上的命令）
       |
     粘贴进 slides    整学期的 code demo 一次到位
    ```

    * 要点：读这张图看的不是每个命令的细节，而是每一环都只做一件小事、上一环的输出直接变成下一环的输入——世界上的东西是可以在一起合作的。

    * > **提示**：今天的标准答案不是唯一答案，直接让 coding agent 收集全部 code demo 并去重，也完全可以。

## 复习方法与常见考题

* **复习策略**

    * 起点判断：不应该把一整学期的 notes 喂进去然后猜老师会出什么题；做模拟卷已经是最后一步，模拟卷是验收而不是起点。

    * 需要的性质：复习需要穷尽一个 scope 里所有的可能性；可以按每个 lecture、每个知识点各出一批可能的题目，这样几乎能实现往年试卷 100% 的 coverage，除最后那几道比较难的、比较 open 的题以外，凡是考基本概念理解的题都能押中。

    * 迁移与玩法：这套经验可以用来复习任何一门考试，也可以几个人用不同 prompt 生成不同试卷拼成一套多套模拟卷。

* **fork 的输出到底是 6 还是 8**

    * 解析：差别出在 buffer 上。`fork` 拷贝时会复制进程所有的状态，"所有的状态"不只 main 函数里的那几个变量，还包括库的状态（stdio 缓冲区里可能还压着没有真正落地的输出）以及进程持有的操作系统对象，所以父子会各自把缓冲区里的内容再写一遍。

    * > **提示**：每当在计算机系统里感到困惑就告诉自己——计算机系统里是没有魔法的，奇怪的行为一定有一个原因。

* **父子进程同时往同一个文件里写，落在哪个位置**

    * 解析：这道题有唯一的答案。`fork` 会复制操作系统对象——父进程持有的文件描述符，child 同样持有这个对象，父子共享同一个打开文件的位置（offset），所以两次写入是接续下去的，不是各写各的。

    * 对照：如果在 `fork` 之前加一句 `close`、父子各自 `open`，父子手上就是两次独立 `open` 得到的描述符，不再共享打开文件的位置，写到哪里各算各的。

* **UNIX 为什么让 fork 继承文件描述符**

    * 解析：回到操作系统的 first principle——操作系统是一个服务者，服务的是用户、是进程、是应用程序，所有设计都是为了让应用程序更好地发挥实力。

    * 与哲学的关系：Unix 希望任何应用一旦进入系统就成为系统的一部分、也成为所有其他应用程序的一部分，鼓励应用之间合作，而管道就是那个非常干净的机制；让 `fork` 继承文件描述符，就是让父进程已经建立好的东西能被 child 直接接着用。

    * 对照：Windows 希望一个 monolithic app 解决你所有问题，Unix 希望世界上所有东西尽可能合作——这道题的答案正对着这个区别。

* **每年固定会考的几类题**

    * 条件变量与并发编程：条件变量的万能同步方法是白送的 20 分；偶尔会出一道用信号量可以做得很简单的题，让你在稳妥与聪明之间自己选；写聪明的并发控制会被当作模型检查器人肉遍历状态空间，找到反例就标出错在哪一层 interleaving。

    * 文件系统：考 crash consistency。

    * 地址空间：进程的地址空间是什么、怎么去改变它，几乎必考；会用很编程的方式问。

    * 线程安全链表：一个线程安全的链表带明显的资源泄漏，另一个人写配对的删除函数——这是很综合的题，会编程又懂概念就应该能从零复原。

    * 调度算术题：给若干任务与各自所需时间，问用什么调度方法、平均等待时间是多少。这类题不是绝对的 nonsense（教科书讲调度的部分讲得不错，系统里真要调度多多少少都有短作业优先的影子），但它要求把小学算术做对，算术一错就没分，所以不适合作为考试方式。

## 课程主线回顾

* **从逻辑门到程序**

    * 起点：从数字逻辑电路的模拟器开始，用代码接线、用代码模拟；最初的动机是一个管道——把一个程序的输出连给另外一个程序作为输入，之后所有事情就是把这种程序与操作系统的交互一层层解开。

    * 计算机模型：定义 CPU 的 state（RISC-V 的 32 个寄存器、一组 CSR、一个 memory），指令就能跑起来，程序也就跑起来了。

    * 程序的理解：把大步执行的汉诺塔改写成小步执行的 Simple-C，精确定义每条语句的行为（含函数调用与返回），于是明白每个 stack frame 都必须记住一个执行位置——可以是一个记返回值位置的 PC，也可以是一个"当前运行到哪里、上面马上要运行到哪里"的指针。

    * 编译优化：状态机意义上连续两个 `x++` 可以合并成 `x += 2`，只要在顺序执行的意义上等价。

* **system call 是不可穿过的边界**

    * 类比：执行 `syscall` 指令时你对整个外部世界没有任何感知，就像手术麻醉时世界消失了；等你回来时世界变成什么样你完全不知道。

    * 后果：控制流进入操作系统后，操作系统理论上可以对你的进程做任何改造——原来有的内存可能没有了，原来不能访问的内存可能变得可以访问。

    * 结论：编译优化不能穿过 system call，这同时把编译优化与操作系统的基本概念讲通了。

* **启动链**

    * 顺序：CPU reset（手册里明确定义的初始状态）→ Firmware 执行 → Firmware 加载操作系统 → 操作系统执行 → 加载第一个应用程序；此时世界的控制权完整交到你的程序手里。

    ```text
    CPU reset          （手册上明确定义的初始状态）
       |
       v
    Firmware 执行
       |
       v
    Firmware 加载操作系统
       |
       v
    操作系统执行
       |
       v
    加载第一个应用程序  --->  世界的控制权完整交到你的手里
    ```

    * 展开方式：Virtualization、Concurrency、Persistence 三个部分都是按照这个逻辑展开的。

* **虚拟化部分：进程、地址空间、对象**

    * 进程树：操作系统从那条启动链走到只有一个 init 进程的状态，之后的一切都是通过 syscall 驱动操作系统到下一个状态；父子关系由进程管理 API 建立和维护，父亲先被杀死或先终止时孩子会怎样是这棵树上很有意思的一类行为。

    * 地址空间：这是进程最重要的资源；既有实验实现 `malloc` / `free`（在 bare-metal 上或在进程地址空间里），也有例子先用 `mmap` 分配一大片内存但暂不使用、之后再按需任意使用，甚至可以入侵别的进程的地址空间。

    * 文件描述符与一切皆文件：procfs 里有整个进程的状态，sysfs 里可以控制系统参数（例如控制树莓派上的灯）；Linux 用文件描述符、Windows 用 handle 来让应用持有一个操作系统对象；配合 duplicate 这类系统调用，就实现了 `fork`、`execve`、继承文件描述符、管道共享等机制。

    * 对象的种类：文件、匿名或命名的管道，以及终端（TTY，Teletypewriter）——幻灯片播放、color code 等有趣功能都建立在这类终端功能之上。

* **动态链接与"变速齿轮"**

    * 机制：可以提前占坑一个符号——在 libc、甚至在 libc 加载之前先加载自己的一个库函数，把 libc 里的符号占住，然后把它替换成自己的实现。

    * 能力范围：`open`、`read`、`malloc`、`free` 都可以占位。

    ```text
    应用程序
       |  调用 C 库的 read() / gettimeofday() / alarm()
       v
    我自己的实现（先于 libc 加载，占住同名符号）
       |  改成我想要的行为，例如缩放时间的尺度
       v
    真正的操作系统内核
    ```

    * 实例：变速齿轮——操作系统给进程的 syscall 在地址空间里其实是在库函数里实现的，把这段实现换掉，相当于在操作系统上又叠了一层自己模拟出来的操作系统，这个进程就只能看到被模拟出来的那个操作系统。

    * 效果：改掉所有与时间相关的系统调用（`gettimeofday`、`alarm`）就改变了时间的尺度，应用程序表现起来就可以运行得更快；这一层对应用完全透明——它以为自己在调 libc，其实调的是我。

* **并发与魔鬼的盒子**

    * 需求：一个进程实际上可以有好多条同时执行的执行流；在多处理器上用共享内存多线程，可以把一个线程算出来的数据只用几条指令的延迟就送给另一个线程使用。

    * 风险：一个 data race 就能让山寨支付宝的账户里出现用不完的钱；并发控制从 Peterson 协议一路走到互斥、同步与生产者-消费者这个万能的线程同步方法。

    * 操作系统本身是最早的并发程序：进程执行系统调用就跳转到内核，此时中断到来可能导致内核另一部分代码开始执行，还可能切到另一个进程；于是每个进程 syscall 之后的内核部分都像一个线程，共享操作系统的地址空间。

    * 研究脉络：受控并发怎么实现、并发 bug 怎么控制——从死锁与死锁检查，到数据竞争与数据竞争检查，甚至那种要人性命的并发 bug。

    * 迁移：数据中心、AI、高性能计算里的并发程序，用的还是操作系统课上的同步、互斥、共享内存、内存模型这些最基本的概念。

* **设备与文件系统**

    * 设备接入：设备有 status、data 等寄存器可供控制，把它接进操作系统对 Linux 来说就是一个 `struct file_operations`；因为 everything is a file，任何设备都能实现成文件的接口从而接入文件系统。

    * 讲过的对象：从一个 LED 灯、一个核弹发射器的设备驱动程序开始，到灯、磁盘、webcam，再到持久化存储设备 NVMe 的 SSD，还讲了一个 bit 怎么存储。

    * 回到数据结构：在 persistence 这一层，课又变成一门数据结构课——手里有一个按块访问的 block device，需要在其上实现一个数据结构；append-only 加上 random-read 可以实现任何一种数据结构，甚至可以用这种方式实现 crash safety。

    * 虚拟文件系统：只要满足文件和目录的 API，文件系统也可以是虚拟出来的——像 OverlayFS 那样一层层叠起来，像 FUSE 那样完全自己写一个文件系统驱动，甚至用符号链接拼出一个可以玩 galgame 的文件系统。

## 从需求出发的设计方法

* **解构问题的方法**

    * 原则：操作系统归根结底是为应用程序服务的，所以要问的是——应用程序到底想要什么、操作系统想怎么给、给了之后还有没有其他用法。

    * 记忆策略：只需记住应用程序要有什么、该有什么，其余都可以通过推理得到；不必记住大量 facts，把操作系统记成几个最重要的 key ideas，剩下的自己还原、推导。

    * 训练法：先想一个机制的出发点是什么，再自己把它 redesign 一遍，然后回头看设计者是怎么设计的，做对照并纠正自己的 chain-of-thought。

    * 推论示例：应用需要加载一个二进制文件、又知道地址空间长什么样，就会希望可执行文件是一个数据结构——那这个数据结构里应该有什么？于是进程地址空间里该有的东西、ELF 文件里该有的东西都可以自己推出来。

* **以 Git 为例**

    * 提问方式：不需要在记忆里搜索所有用过的 Git 命令，而要想 Git 到底是用来干嘛的、解决什么问题——多个开发者在本地开发，开发者之间还要同步，多版本管理该怎么做。

    * 关键观察：它是管理文件系统快照的数据结构。

    * 与 SVN 对比：SVN 存储的是 diff，听起来高效，但要下载某一个版本就得从某个快照开始不停打 patch 打到那个时间点，版本后退也非常复杂。

    * 数据结构与涌现出的功能：tree of blobs、若干文件系统的树、提交与提交之间自然形成的 commit 有向无环图；在这个数据结构上，branch、stash、worktree 都能从需求自然推导出来——自己发明过一次就不会忘记，忘了也能再发明一遍。

    * > **结论**：只要有概念，就不需要做无意义的肌肉记忆；但反过来，人也很难在不肌肉记忆的情况下去形成理解，所以对自己的要求需要自己掌握。

## Scaling Law 与未来

### 已经发生的 scaling

* **下棋**

    * 曲线：大约从 1985 年开始，随着算力增长，计算机下象棋的 rating 稳步往上走，几乎跟摩尔定律一起上涨。

    * 台阶与结果：做深蓝时投入大量资源、算法也有进步，加上硬件下棋电路与超级计算机，形成一个比较大的向上台阶，1997 年击败了人类世界冠军；此后 AlphaGo、Monte Carlo tree search、深度神经网络让 AI 统治了业余互联网象棋。

* **存储与芯片**

    * 预测：随着时间增长，存储设备也会指数级 scale，能够存下互联网上所有的内容。

    * 结论：Google 不是偶然，Intel 与 NVIDIA 也不是偶然——1968 年的摩尔定律与后来的算力供给，都是同一个规律的不同侧面。

* **Chinchilla 的观察**

    * 数值关系：大语言模型的参数量，与训练用的最佳 token 量之间的比值不是几万、几百、几千，而是可能几十。

    * 推论：这意味着理想情况下模型应该几乎记住了训练数据里所有的东西，这才是比较理想的一个收敛位置。

### 三个维度的 scaling

* **预训练 scaling（Pre-training Scaling）**

    * 机制：在预训练阶段用更多的数据、更好的书把基模做大。

    * 极端做法：买下很多绝版书作为语料训练基模再把书烧掉，让竞争对手拿不到同样好的语料。

* **后训练 scaling（Post-training Scaling）**

    * 机制：更好的预训练模型，在后训练阶段还能有更好的提高。

    * 有效的条件：在反馈信号明确的地方能力可以被继续提高——代码之所以能取得突破，是因为它有非常强的监督学习反馈信号；有尺子、做得不好就受罚、做得好就奖励，模型慢慢就能学到这个 pattern。

    * 类比：高中阶段像预训练（对每个学科都有浅浅的认识），上大学后往一个方向微调，进入后训练阶段。

* **测试时 scaling（Test-time Scaling）**

    * 机制：给模型选一个 reasoning effort，让它做完之后可以再检查一遍、再检查一遍；这就是 chain-of-thought 的 reasoning，上限其实还没有摸到。

    * 例子：先让 AI 列举操作系统里的 100 个知识点，再写脚本对每个知识点各调一次 API 出题，用同样的 prompt——这就 test-time scale 了。

    * 外推：一道数学题不会做时，枚举题库中所有题目与解答，再让模型参考同类型题与题解的思路——你会发现在这个意义上世界上根本没有新题。

    | 维度 | 在哪个阶段生效 | 关键机制 | 代表 |
    | :--- | :--- | :--- | :--- |
    | pre-training scaling | 预训练 | 更多的数据、更好的书，把基模做大 | GPT-4 时代大家发现的 |
    | post-training scaling | 后训练 | 在反馈信号明确的地方继续提高能力 | GPT 的 o1，Anthropic 的模型 |
    | test-time scaling | 推理与使用 | 反复检查、反复重试，用算力换正确率 | o1 的 reasoning efforts；为每个知识点各出一套题 |

    * > **结论**：test-time scaling 只要你有算力，它的上限就近乎无限，所以 AGI 迟早要来。

### VibeOS 与个人的位置

* **AGI 冲击下的位置问题**

    * 逻辑：如果再配一个有 test-time scaling、智能近乎无限的 agent，并把信息差抚平，那么会用 agent 的人在任何一个方面都能做得比不会用的人更好。

    * 趋势判断：坐牢式的、服从性的教学会在 scaling law 底下崩塌——AGI 可以帮你找到最适合你的教学方法，不必用低效的服从性考试去接受知识。

    * 提示：demo 做出来就意味着这条技术路线上一定有一天没有本质的困难。

* **VibeOS**

    * > **定义**：世界上第一个完全由幻觉构成的操作系统——一个约 1.3 GB 的 VHDX 文件，可以在 Hyper-V（也可以裸机）中启动。

    * 应用形态：Notepad、Calculator、Internet Explorer 这些内置应用里一行代码都没有——没有按钮、没有事件处理器、没有任何说明该做什么的逻辑，但应用是能用的（5 除以 3 按等号得到 1.6），也没有任何 AI 写的代码，只是纯粹产出 UI。

    * 实时生成：搜任何想要的应用都会现场创建；在它里面不用担心"这到底是不是 AI"，因为答案永远是"是"——所有内容都是完全幻觉出来的，直接从模型出来、UI 实时更新；背后跑的是 Copilot SDK。

    * 意义：不在于它真能当日常系统用，而在于它展示的那件事——所有一切都由模型生成的幻觉构成，没有一行代码，看起来却可以 work，而它底下是一个世界模型。

* **时代与选择**

    * 三个维度都在 scale，摩尔定律还在生效，GPU、TPU、NPU 还在生产；在指数级能力增长面前，"只要比别人不错一点、后面有人垫背"的游戏在某一天会突然失效，不再安全。

    * 建议：每个人都可以去想自己在这个时代里会找到一个什么位置，未必一定去做 AI infra；知识可能有边界，但梦想可以没有边界。
