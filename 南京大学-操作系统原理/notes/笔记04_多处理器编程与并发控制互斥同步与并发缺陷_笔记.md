# 多处理器编程与并发控制：互斥、同步与并发缺陷

## 线程与共享内存模型

### 线程的执行模型

* **线程（thread）**

    * > **定义**：一种执行实体，它拥有自己的栈，并与别的线程共享同一份全局数据。

    * 从 Simple C 的执行模型推出：一个函数调用栈（最底是 main，每次调用压入一个栈帧，栈帧里有 PC）加上一份全局变量 globals；要让两个执行实体共享内存又独立执行，每个实体必须独享一份栈——共享一份栈的话「从栈顶栈帧的 PC 取一条语句执行」这件事就全乱套了。

    * 管理线程只需要两个原语：`spawn` 在已有线程不变的前提下创建一个新线程（可以带上入口函数），`exit` 把一个线程从系统里抹掉；二者都只改动栈，全局数据自始至终是同一份。

    * 指令级上是「一个平坦地址空间（即一个 mmap 出来的地址空间）+ 每个线程一个 SP」：地址空间里为每个线程划出一段区域当栈，T1 的 SP 指向 T1 的栈，T2 的 SP 指向 T2 的栈；代码与全局数据只有一份。

    * > **提示**：实现一套共享内存的进程，要实现的就只是 `spawn` 和 `exit` 这两个系统调用；剩下所有并发内容都是从这个模型推出来的。

* **迁移（scheduling）**

    * 把一个栈加上全局内存看成一个进程：T1 的栈加全局是一个进程，T2 的栈加全局又是一个同概念的进程；迁移就是选择让哪个线程往前走一步。

    * 「什么是线程」是在「什么是程序」这个已有定义上定义出来的，是模型扩展而非另起炉灶。

* **线程的栈大小**

    * 线程栈必须在创建线程时就决定大小，因为它要在地址空间里分配一段内存。

    * 实测结论：每个创建出来的线程有 8192 KB（8 兆）的堆栈——探测程序一路递归到 overflow，打印出的栈跨度是 `T1 stack >= 8183`（K 为单位）。

    * > **易错点**：这跟平时写程序的感觉不同。Linux 里主程序的栈默认几乎可以无限往后用；线程栈不行，它被钉在地址空间里，创建时就定死。

* **用于验证模型的最小线程库**

    * 只留两个 API：`spawn` 把一个入口函数当线程跑起来（线程号从 1 开始编号，同一入口函数配不同参数就是不同线程），`join` 等待所有放出去的线程结束。

    * 该库让 main 默认 join 所有线程之后才真正结束（内部就是给 spawn 记数、给线程结束记数，计到零 main 才退出）；POSIX pthreads 不会自动等待其他线程。

    * 两套线程接口的差别：

        | 对比项 | 最小线程库 | POSIX pthreads |
        | :--- | :--- | :--- |
        | 提供 API | 只有 spawn 和 join | 完整的一套线程接口 |
        | main 结束时行为 | 默认 join 所有线程后才结束 | 不会自动等待其他线程 |
        | 移植性 | 平台支持 POSIX thread 即可用 | 标准规定，足够好的平台普遍支持 |

    * 成为标准的好处是可以放心移植：例如与 Linux 不兼容的系统一般也会兼容 POSIX thread，这样第三方库与应用程序才移植得过去。

* **共享内存与独立栈的验证手法**

    * 一个线程做 `x++` 每 1 秒一次，另一个线程做 `y++` 每 2 秒一次，main 每隔一小段时间读一次并打印：读到 `x` 走得比 `y` 快，说明数据部分是共享的。

    * 取一个局部变量的地址打印出来，所有东西都落在同一个地址空间里；把一个指向局部变量的指针传给另一个线程，那个线程也能访问它——说明所有线程的栈都在同一个地址空间内。

* **并发（concurrency）与并行（parallelism）**

    * > **定义**：并发是逻辑上的同时执行，一颗 CPU 靠调度轮流交错（A B A B B）也能做到；并行是物理时间上真正同时发生，需要多颗 CPU。

    * 并发的程序可能并行、也可能不并行；并行的程序一定也是并发的。

    * > **易错点**：两者不是同义词，不能互换使用；判断依据是「物理时间上是否真的同时」。

    * 两种理解线程的模型：模型一在任一时刻只挑一个线程走一步（状态机意义上的交错）；模型二让所有线程在每个「步」上一起前进。模型二对真实处理器是过度简化——不同指令耗时不同（cache 命中与否、load/store 天生慢、乘除要几个周期）。

* **调试多线程程序**

    * 加 `-g` 后用 GDB；`info threads` 列出当前所有线程及其 ID。

    * `set scheduler-locking on` 把调试器退回「一次只走一个线程」的模式，与「模型一」对应；默认是 `off`，某线程单步时其他线程仍在推进，会干扰调试。

    * 在 main 里 `continue` 会停在 join 处等待其他线程，需要在别的线程上 continue 才能前进；可在线程之间切换。

    * 用 GDB 可以把「多个线程、各有自己的栈与 PC、每次挑一个单步」这个模型与真实运行的程序（有 assembly）完全对应起来。

    * > **提示**：调试并发程序本身很费时间，会在线程间反复切换。两个线程即使执行同一段代码，参数不同也是两个不同线程。

## 确定性如何崩塌

### 非原子的读改写

* **读-改-写序列（read-modify-write）**

    * > **定义**：一次逻辑上完整的更新，在机器层面由读、算、写三步构成，中间可以被别的线程插进来。

    * `sum++` 的三步：

    ```text
    load sum -> r      把 sum 读进寄存器
    r = r + 1          在寄存器里加一
    store sum <- r     写回内存
    ```

    * 覆盖过程：T1 读到 1000 还在慢慢算，T2 一路推进到 2000，T1 把 1001 写回，2000 就被一巴掌盖掉；两个线程互相读、互相覆盖，最终加出来的数没加多少。

    * > **易错点**：`sum++` 看着是一行、一条语句，但它不是原子的；在单线程里写它时，永远不会想到中间会被人插一脚。

* **判断与动作之间的缝（check-then-act）**

    * 一模一样的两个线程各转 100 块，账户只剩 100 块：两个线程都判断「余额够」，于是各扣 100，余额变成负数；若余额是无符号整数，就等于凭空多出无穷的钱。

    * 真实世界的同类 bug：先把包裹打开分离出一块钱，再丢下要复制的物品；在人物即将捡起地上物品的瞬间点击手上那一块钱，鼠标事件把「当前拿起的东西」写成了一块钱，紧接着又被地上物品覆盖（一个全局变量被两个来源先后写）——于是物品被复制成两份。

    * 前者是多处理器上的并行，后者是鼠标事件上的并发，机制不同而破坏力一样；共同点是判断与动作之间那道缝，别人可以从缝里插进来。

* **缓冲区里的同类问题**

    * 两个线程各自 printf，共享的正是同一个缓冲区，即同时执行 `buf[position++] = ch` 这类语句；各写 100 万个字符不会得到 200 万个字符交错的结果，而是有些位置空着、有些被覆盖。

    * POSIX 手册说明 printf 系列是线程安全的，但「安全」不等于原子；`memcpy` 同理——多线程对同一块内存 memcpy 会出现类似 `sum++` 的结果（不会损坏内存，但结果可能一部分是这个线程写的、一部分是那个线程写的），不过依然可以放心调用。

    * > **提示**：几乎所有的系统调用都可以在多个线程里正确使用（read、write 都没问题），只是行为可能有微小改变；真正危险的是自己去跟共享内存打交道。

### 交错空间与不可判定

* **状态爆炸**

    * 两个线程 T1、T2 时，每一步都是「选 T1 还是选 T2」的一次二选一，组合起来是指数级的：可以走 1 1、1 2、2 1、2 2；每一步都不确定，走出来的历史是指数条。

    * > **结论**：今天你的测试通过了、测了 100 万次都通过，不代表交到 Online Judge 上就能过。

    * 「每次任选一个线程执行一条语句」这一模型对应确定性图灵机与不确定性图灵机的区别；确定性丧失把「顺序执行、只有 syscall 不确定」的程序，变成了每一步都不知道选谁的模型。

* **三线程 sum++ 的最小值**

    * 题目模型：三个线程各自执行 `sum++`（每个线程要把自己那份循环跑完），每次任选一个线程执行一行语句，问执行结束后 sum 的最小值。

    * 直觉答案是 3，正确答案是 2。构造：让线程 2 读到 0 后先不写；让线程 1 把自己循环里的 `sum++` 全部做完（load 0 → store 1，load 1 → store 2），再做一次 load 读到 1，然后延时很久，最后把 2 写回；其他线程在这次 store 之前全部跑完——全局最后一次写是线程 1 写下的 2。

    * 该构造对线程数不敏感：不管有多少个线程，都能用这种极限排法得到一个 2。

    * > **易错点**：最小值不是线程数；`sum++` 的 load 与 store 之间可以被插进来，写回时会盖掉别人刚写的值。

* **排列事件是 NP 完全问题**

    * 把每个线程内部的读写事件按「读到的值必须是最近一次写进去的值」排成一条全局全序，这件事本身是 NP 完全的；求 sum 的最小值本身也是 NP 难的，只能不断尝试。

    * 线程内部的事件顺序固定不可改（不能把 T0 的第一个事件挪到第二个后面），线程之间的事件顺序可任意排列。

    * 历史上人类为「正确的 1 + 1」困扰多年：1960 年代大家争相在共享内存上实现原子性与互斥，几乎所有的实现都是错的，一直到 Dekker 的算法才有了第一个真正对的、能做 1 + 1 的算法。Peterson 论文里有一句原话：`Unfortunately, the authors believe the correct solution is incorrect.`

### 编译器与处理器改写的顺序

* **编译器的等价改写**

    * 编译器看来，连续三条 `x++` 这样的纯计算一旦初始状态确定，目标状态就确定，于是很想合并成 `x += 3`。

    * system call 不可优化、也不能被跨过：`x++; x++; x++; syscall(x); x++;` 中前面的三条可以合并为 `x += 3`，但若把后面那条也并进来变成 `x += 4`，送进 syscall 的字符就错了。

    * 优化建立在「程序是确定性的」这个假设上：编译器假设不需要管别的线程会不会把值改掉；一旦要考虑，就什么优化都做不了。

    * 它会做内联（把别的函数代码粘到调用点、常数也粘进去）、一边粘贴一边等价改写，死代码直接删掉。

* **被优化掉的等待（盲等失效）**

    * 用一面旗子做协议：一方 `while (!flag) ;` 等旗子举起，另一方把 `flag = 1`；逻辑上能实现，实际实现不了。

    * 编译器认为没有人能改 `flag`，于是像做循环不变量提升那样把读提到循环外：若 `flag` 已举起就直接出去，否则再也没有人能举起旗子——此处成了死循环。

    * 控制优化行为的两条途径（不是本课推荐方法）：插入 compiler barrier（例如带 clobber memory 的空汇编，告诉编译器这段汇编可能修改任意内存），或把变量标记为 `volatile`（访问 memory-mapped register 时通常也需要它——先读一个字节扔掉、再读一个字节读进变量，没有 `volatile` 编译器会把两次内存读合并成一次，而这是不能合并的）。

    * > **易错点**：两个线程同时访问同一个内存地址叫 race condition（数据竞争），在 C 和 C++ 里是 undefined behavior；自己觉得「这样挺快」的 ad-hoc synchronization，会在某一次编译时出问题。

* **同一份代码两个答案**

    * `-O1` 下 sum 变成 n，且反复运行都是 n；`-O2` 下 sum 又对了。原因：`-O1` 把 sum load 进寄存器、在循环里反复 +1、最后才 store 回去——一次 load 提到循环前、一次 store 放到循环后，两条线程的 load 与 store 相隔很远，互相覆盖后只剩一份。

    * `-O2` 下整个循环被优化掉，只剩一个 load、加等于 n、一个 store，执行只需几纳秒到几十纳秒；线程创建与调度都有先后，两段代码碰撞的概率非常低，于是看起来正确。

    * > **易错点**：这才是最危险的形态——用 `-O2` 编译后程序完全正确，测了 100 万次全对，交付出去某一天客户那边挂了，你不知道为什么。并发与非确定性会和各种机制互相交织。

* **处理器也是一个编译器**

    * `rax = 1` 和 `rbx = 2` 可以调换执行顺序（顺序程序下结果相同）；处理器只论结果，只在中断、I/O 时保证把正确的数据送出去。

    * 一个 cache line 是 64 字节，取指令时顺便把其他指令也译码；CPU 内部有一堆指令做动态数据流分析（指令 2 等指令 1 的结果、指令 3 等指令 2 的结果），把编译器那套在电路上又做了一遍；一个周期执行 2、4、8 条都可能。

    * 一条 load/store 因 cache miss 卡住不要紧，处理器有分支预测器，去执行那些不依赖前面结果的指令。

    * > **结论**：你手上有两层编译器都在调换指令顺序，「每次选一个线程、执行一条指令」的 shared memory 模型这个幻想根本不存在。

### 内存模型的迷雾

* **内存不是一个共享内存**

    * 系统为了性能并不是一个 shared memory：看起来每个线程都有一份自己的 memory 副本，load 和 store 都跟自己的那份打交道；副本之间怎么交互由硬件厂商决定，只要达成内存上的最终一致（eventual consistency）即可——所有 CPU 都不再执行 load/store 后，memory 会慢慢一致；或执行一条特殊指令要求某段内存达成一致。

    * 观察实验：T1 是 `x = 1; load y;`，T2 是 `y = 1; load x;`，把四个事件编号 1 2 3 4。

    * 在顺序模型下，2 不能在 1 前、4 不能在 3 前，所以两个 load 里至少有一个读到 1：能看到 1 0、0 1、1 1，看不到 0 0。而按「处理器也是编译器」的道理，写 `x = 1` 是往自己的 memory 写、还没送到另一个 CPU，此时去读就读到 0，所以 0 0 应当可见。

    * 实测统计（用 `head` 截断、`sort`、`uniq -c` 统计十万次）：约 60000 次 0 0，约 40000 次 0 1，1 0 很少，1 1 一次都看不到。原因就是处理器太快：写完马上就读，几乎不可能出现「x = 1、y = 1 都写出去之后才被中断」的罕见场景。

    * > **提示**：把观察实验写对需要用 atomic load、fetch 异或之类的手段；忠告还是那句话——Don't play with shared memory。

* **被放弃的是什么**

    * > **结论**：「从入门到放弃」放弃的不是不做并发编程，而是放弃用那种简化的模型去理解并发程序——继续用旧模型会丢失掉大量可能发生的行为，从而招致严重问题。

    * malloc、free、open、close 都有同样性质的问题；共享内存确实方便，但代价是你连 1 + 1 都写不对、连 1 2 3 都数不对。

## 互斥：原理与代价

### 临界区与锁的语义

* **为什么操作系统课讲并发**

    * UNIX 引入进程后进程之间不共享内存，fork 出的两个副本各干各的，本是很省心的设计。

    * 但系统调用的执行是共享内存的：`syscall` 指令附带着一次权限切换，穿过之后程序恢复到高权限状态；每个进程在操作系统内部执行的那部分就变成了一个线程。

    * > **结论**：操作系统是最早的并发程序。一个进程在内核里执行 `read(fd, buf, size)`、另一个同时执行 `write(fd, buf, size)`，若碰的是同一个文件，1 + 1、数顺序的问题就原样出现在内核代码里；内核代码执行时依然可能被中断，也可能真的在两颗处理器上并行。

* **互斥（mutual exclusion）与临界区（critical section）**

    * > **定义**：互斥就是互相排斥，两个人不能同时进入一段代码；被锁保护的那段代码叫临界区。

    * 想要的接口形态：任何线程都可以执行 `lock`，`lock` 返回后就可以执行临界区代码（例如 `sum++`），不再需要「别人不能和我一起并发」这个强保证时执行 `unlock`；`lock` 返回的那一刻起，我就再也不能和别人的 `lock` 代码块并发。

    * 时序：T1 的 `lock` 返回、执行临界区、`unlock`；T2 只要在别人尚未释放时执行 `lock` 就不能返回，一直等到 T1 释放；T3 继续等下去。于是所有并发被消除，你得到一个「能排出个一二三」的确定顺序。

* **acquire / release 与可见性**

    * `unlock` 还有一条额外语义：保证在这个地方写的数据全部进入内存；之后进来的人 `load` 它一定能看到刚写下的值。

    * 这正是 `lock`/`unlock` 又叫 acquire/release 的原因：acquire 是去拿钥匙，release 是把钥匙放回去；C++ 内存模型文档里说的 acquire semantics、release semantics 讲的就是这条可见性——acquire 时必须能看到别人 release 之前写入的内存。

    * 上一次解锁的 release happens-before 下一次上锁的 acquire；因此链表里插入的节点、`sum++` 后的新值，在被保护的前提下一定彼此可见。

    * > **提示**：这些细节不必知道得这么细；只要所有代码都正确使用 `lock` 和 `unlock`，答案就是对的。

* **锁的两种比喻**

    * **房间**：一个小房间只能容纳一个人，进去的人把门锁上，别人进不来；很多人同时想进屋，只有一个能进去，其余等到前一个人让出使用权。

    * **桌上的一把钥匙**：`lock` 要先得到钥匙才能继续，很多人同时去摸钥匙而物理空间里只有一把，只有一个人能摸到；`unlock` 时把钥匙还回来。

### 锁的使用约定

* **必须用同一把锁保护同一份数据**

    * `sum++` 包在 `lock`/`unlock` 之间，第一次得到 1、第二次得到 2；只要每一处都在锁里就没有问题；有一处没锁保护，那一处就仍然能算出错误结果。

    * > **易错点**：锁不会自动保护「共享变量」这个抽象概念，它只保护你把代码包进去的那些行的执行；少包一行，那一行就是能算出错误的 `sum++`。锁的「身份」是你 acquire 的那一个对象，不是变量名。

    * 多把锁：`lock A` 时做 `x++`、`lock B` 时做 `y++` 没有问题——`sum` 和 `x` 是不同的内存地址，本来就不会互相干扰。

    * 编译器可能与程序作对：故意做 10 次 `sum++` 并加 compiler barrier，是为了不让编译器把它们合成 `sum = sum + 10`（合成后临界区变得极短）。加上 barrier 后每次都必须老老实实做一次 load、加一、store。

* **一万种用错锁的方法**

    * 不配对：函数第一行 acquire、最后一行 release，中间加一个提前 `return`，锁就再也没被释放，别人永远等下去。

    * 同一份数据配两把锁：一处 `lock(&l); sum++; unlock(&l);`，另一处 `lock(&i); sum++; unlock(&i);`——`l` 与 `i` 长得很像但确实是两把锁，二者之间可以并发，形同虚设。

    * > **提示**：只要系统里引入很多把锁，出错几乎是必然的。若世界上只有一把锁，说「我需要原子性、需要 stop the world」那就 lock 再 unlock，世界是简单的；否则手工管理复杂锁就很麻烦。

* **并发数据结构的锁地狱**

    * 让世界上只有一把锁，一个链表一把锁，锁住就能访问整个链表——简单但性能一般。

    * 要做性能过得去的并发数据结构，链表每个节点都要有一把锁；遍历时必须一边上锁一边解锁：

    ```text
    此刻我持有 cur 的锁
      1. 先 acquire next 的锁        <-- 把 "cur -> next" 这条链接关系锁住
      2. 到达 next 之后，才敢释放 cur 的锁
      3. 站在 next 上，重复第 1、2 步
    ```

    * 持当前节点的锁时不能先释放；先拿到下一个节点的锁才能释放上一个的锁，从而保证这中间的链接关系不变。

    * 插入与删除需要拿到 previous、current、next 三把锁；最难的是删除之后的内存回收——必须确保没有人还持有指向该节点的引用，才能回收。

* **stop the world 的理解视角**

    * 前提是「正确地使用」互斥锁；在这个前提下执行 `lock` 相当于执行了一次 stop-the-world，自己依然可以活动。

    * 正确性假设的含义是：别人永远不会写我读过的值；既然世界被停下，临界区里多次 `t = sum` 必须看到同一个值。

    * > **结论**：T1 和 T3 实际上是并行同时执行的，但理解程序执行效果时可以把这一段挪到前面或后面，两种顺序结果都一样；所以「好像」是 stop the world，实际仍是并行。

    * 这和内核关中断同理：只有一颗 CPU 时关掉中断，世界上真的没有别人；哪怕还有别人，别人执行的效果也可以挪到前或后、不影响我看到的正确性。

### 锁的代价与并行度

* **关中断只能用于单处理器内核**

    * 单处理器、内核代码中把中断关掉就独占了整颗 CPU：若指令集本身确定，执行的一定是相同代码，于是实现了 make it work。代价是内核里关着中断写 `while(1)` 会让整台机器死掉——这就是机器上需要 reset 按钮（CPU reset）的原因。

    * 普通线程用不了这一招：ARM 上用户程序不能执行那条 MSR（甚至是「不合法、不存在」的指令）→ SIGILL；x86 上用户态执行清中断 → protection error，也就是 segmentation fault。

    * > **易错点**：这里的 SIGILL 与 segfault 不是代码写错，而是指令集体系结构的刻意设计——关中断这条门只对内核开。

    * 两颗 CPU 时关中断只关掉了自己这一颗，别人照样在跑。

* **Amdahl 定律（Amdahl's law）**

    * > **定义**：程序里不可并行的部分占比为 $f$ 时，加速比的上限是 $1/f$。

    * 例：1/2 的代码不能并行（花 1 秒），后面一大堆可并行的代码也花 1 秒；那么无论并行度多高、哪怕可并行部分耗时变为 0、哪怕有 1 万个 CPU，也只能加速一倍（$f = 1/2$ → 上限 2）。

* **Gustafson 定律（Gustafson's law）**

    * 若不能并行的部分非常小、甚至趋于 0，而可并行部分非常可并行，那么有多少个处理器就能得到多少倍的加速比。

    * 这个更乐观的结论对实际更有用，也是现实世界有局部性这一事实的推论。

    * 两条定律的适用前提不同：

        | 对比项 | Amdahl 定律 | Gustafson 定律 |
        | :--- | :--- | :--- |
        | 不可并行的部分 | 占比不算小（例如 1/2） | 非常小，甚至趋于 0 |
        | 结论 | 再多的处理器也有加速上限 | 有多少处理器就有多少倍加速比 |
        | 启示 | 串行部分是天花板 | 现实程序里真正必须串行的部分很少 |

* **物理世界的局部性**

    * 每个人都只占据自己的物理空间，访问别人的物理空间只能访问相邻的。

    * 模拟物理系统的套路是把大网格切块：每块用自己的数据算——并行、不上锁；只有块与块的边界要交换数据，这里才需要交互、才需要上锁。一块里面的计算量远大于它需要和别人交互的部分。

    * 同样的例子：图书馆的书（拿书要抢书架、需要上锁，书拿到手上就变成 private memory，看书过程可并行且不需要上锁）、索引全部网页、训练深度神经网络、围棋搜索（fork-based DFS 每层为每个分支创建进程）。

    * > **结论**：并发控制让我们退回到串行只是就关键数据结构而言；可以在关键数据结构里放需要执行很长时间的任务，而任务本身不需要上锁，于是依然能取得很高的并行度。真正需要串行的部分非常少。

* **一把大锁保平安**

    * 新手建议：但凡可能共享的东西都上同一把锁；代价是把上锁时间延长（从要干这件事开始持有，直到全部干完再释放）。

    * Linux 内核从单处理器迁移到多处理器时干的第一件事就是引入 Big Kernel Lock（BKL）；它不敢一下子把锁拆到每个链表节点，因为那会引入大量 bug、让内核长时间无法运行，所以从一把大锁开始，先找对性能影响关键的地方拆成几把小锁，并做好充足的压力测试。

    * 实践警告：线程安全内存分配（malloc/free）用一把大锁「easy test」完全正确；要把性能提上去过「hard test」就得拆锁，一拆锁连 easy test 也过不去了——压力负载下一点点小错就会冒出各种奇怪问题。

    * Knuth 的话：premature optimization is the root of all evil。正确的途径是先把代码想做什么准确表达出来（例如「我现在就是想要 stop the world」），再慢慢优化真正导致瓶颈的那条路径。

* **既然上了锁就没有并行，为什么还要线程**

    * 上了锁程序退回按 1、2、3 串行执行，甚至比单处理器还慢；但由 Gustafson 定律与局部性可知，真实并发程序里需要串行保护的部分非常少。

## 互斥的实现路线

### 手工协议的三个假设

* **Dekker 算法**

    * 1965 年出现的第一个公开正确的算法，当时用的还不是线程而是进程（进程里负责共享内存执行的那部分就是线程）。

    * 描述：一个进程 P 能进入临界区，if the other does not want to enter（如果别人不想进）；否则只有在轮到它的时候才能进（only if it is its turn）。

* **Peterson 算法**

    * 1981 年出现、被普遍认为比较满意的算法：一个进程 p 能进入临界区，如果别人不想进（the other is not）；或者它已经表明了自己想进的意愿（it has indicated this desire）并且把轮次让给了另一个进程（and has given the other process that turn）。

    * 代码形态：

    ```c
    A = 1;                        /* 我想进：举手 */
    term = B;                     /* 把轮次让给对方 */
    while (B && term == B) { }    /* 别人想进、且轮次在对方手上：等 */
    /* ---- 临界区 ---- */
    A = 0;                        /* 我不想进了 */
    ```

    * 宿舍卫生间的类比：Alice 手里拿着 Bob 的名字、Bob 手里拿着 Alice 的名字；想进房间就举起自己的手（`A = 1`）、把手上对方的名字贴到门上（`term = B`）、再看对方还举不举手和门上名字（`while (B && term == B) { }`）、可以进就执行临界区、出来把手放下（`A = 0`）。

* **三个假设与它们的破产**

    * 这些证明的假设是：线程只在某一个特定位置才可能切换；`load` 和 `store` 瞬间完成、立即生效；指令严格按书写顺序执行。

    * 放在 1965 年这三条合情合理（那时既无高性能编译器也无多处理器）；但后两条今天都不成立，照那样写出来的 Peterson 算法是错的——正确的版本需要加很多 barrier。

    * 检查方式：每当有一个进程进入就让一个原子计数器加一，两个进程进去就变成 2，看到 2 就说明有两个进程同时进了 lock 保护的区域。

    * > **提示**：让人惊奇的是，这个错误的程序在某些机器上复现不出来——算法真的是错的、程序真的会 `assert fail`，但各种机缘巧合会让它看起来是对的。你面对的是一个指数大的状态空间。

    * Peterson 还有一个致命缺陷：协议里只有两个牌子（Alice 与 Bob），要求双方知道对方是谁；而 `spawn` 可以派生很多线程、还能动态再 spawn、再结束，任何时刻系统里有多少线程根本不知道。它只适用于两个线程的同步。

    * Peterson 的错是路线上的错：它试图在 `load` 和 `store` 之上实现互斥，即先假设二者原子，再在它们之上搭互斥。

* **推翻假设：系统是我们自己造的**

    * 解决思路不是「解决提出问题的人」，而是清清楚楚地理解假设，然后在工程意义上合适的地方把它推翻；假设一旦被推翻就打开了一片新天地。

    * 这是计算机科学与自然科学的差别：生命科学的规则是自然定的，你只能理解规则再做能做之事；计算机科学的规则全是自己定的，只要不违背芯片、电路这些物理极限，软件不好解决的问题就让硬件来帮忙。

    * 用钥匙与桌子回看：Peterson 的规定翻译成物理世界就是——`load` 时手必须背在身后只能看，`store` 时眼睛必须蒙起来只能动，一次只能做一件事。而真实世界里伸手拿钥匙是「手伸过去的同时眼睛能看着它」，即一次 load + store 一气呵成。

    * > **结论**：只要把「判断」和「拿走」合成一个不可分割、非常短小的时间段——一次很小很小的 stop the world，问题就解决了；计算机系统提供的原子指令就是这个 stop the world。

### 原子指令与自旋锁

* **原子指令（atomic instruction）**

    * x86 的做法是指令前缀 `lock`：例如把 `add 1, x` 写成 `lock add 1, x`，它真的有一把总线上的锁，会把总线锁住，别人不能访问内存；此时可以对同一个内存地址先 load 再 store，效果上等同于 stop the world。这个行为在 80486 支持 `lock` 时就已画在图上了（译码器译出 `lock` 前缀时把总线锁住）。

    * 一条 `lock add 1, sum` 就能实现正确的 sum 加一；该层次上的锁叫自旋锁（spinlock），用法与 mutex lock 完全一样，`spin_lock` / `spin_unlock` 就当成 `lock` / `unlock` 理解。

    * 计算机里无法直接表达「一把钥匙」，只能用一个数：一张白纸代表空手（0），写着钥匙的那张代表钥匙（1）。

    ```text
    桌上（内存）的值:  KEY=1        我手上的白纸: 0
    ── 原子 exchange ─────────────────────────────────
    桌上（内存）的值:  0            我手上: KEY=1    → 抢到钥匙，拿锁
    后来者再 exchange: 只能换到 0                    → 没抢到，重试
    ```

    * 只要 exchange 表现得像 stop the world，无论多少人来，只有最先执行的那个人能把钥匙换到手上，其余人只能换走留在桌上的白纸（0）。

    * compare-exchange 变体：先比较、相等时才交换，能省掉一次内存写（看到不是钥匙时只有一次读），性能更好。它是编译器的 built-in function，x86、ARM、RISC-V 上编译器都会处理。

    * 可见性语义：使用 acquire-release 内存模型（例如用更强的 exchange）都没问题；acquire 就是原子地把 locked 换进去并取出结果，结果是 free 就说明钥匙到手，可以进入临界区。

* **自旋锁的两个代价**

    * 空转：拿到锁的人继续执行，其他人在死循环里拿白纸换白纸，看到的永远是白纸；且没有任何线程知道持锁者何时归还，其他处理器上的线程全在浪费——即「一核有难，八核围观」。若临界区执行很久，还不如把 CPU 让给别的线程。

    * 被换出去：应用程序不能关中断，拿到钥匙的线程可能被中断；操作系统为了造出并发的假象会把时间切片轮转，持锁线程可能被换到磁盘上（甚至用 CRIU 做快照丢到另一台机器），可能很久不回来。此时系统里换上来想要这把锁的线程也拿不到，所有资源都被浪费。

* **把「我在等锁」告诉操作系统**

    * 交换一次没换到就告诉管理员「我先去睡觉，等钥匙回来再叫醒我」；没拿到锁的人都去睡觉，真正能运行的线程就能上来。这必须通过系统调用，线程自己解决不了。

    * 理论上可以实现 `syscall acquire` 和 `syscall release`，把锁实现放到内核里：内核里的锁既要关中断又要交换自旋，其余工作交给内核——发现锁没归还就把线程变成睡眠状态，并给它做一个标记让它知道等的是哪把锁；锁被 release 时再唤醒它。

### 内核介入与 futex

* **futex（fast userspace mutex）**

    * > **定义**：Linux 里实现互斥的机制，一部分在用户态、一部分在内核态，主要提供两个操作（up、down）；在没有竞争时整条同步路径完全不进内核。

    * 关键在于有一条用户态 fast path：exchange 拿到钥匙就直接继续执行，不需要进入内核；一旦 exchange 失败，就必须要有一条绝对正确的 slow path（陷入内核、登记在等哪把锁、睡眠排队，release 时被唤醒后重试）。

    * 难点在于 acquire 的 fast path 不进内核之外，release 时也不想进内核；在锁不拥挤、没有人抢锁时整个同步过程不进内核。

    * 相关文章《Futexes Are Tricky》吐槽 futex 很难用，文中提到 Rusty Russell 发布的一段代码实际上是错的，而评论它的内核维护者说弄错很正常（I got it wrong the first time as well）。

    * > **提示**：futex 的「快」有前提——只有没有竞争时快路径才生效；一旦真的有人抢锁，还是得掉进内核态那条慢路径，所以它才那么难写对。

    * futex 比 Peterson 算法还要复杂，因为一部分在用户态、一部分在内核态。

### 定量对比与实验准则

* **四种实现的开销对比实验**

    * 实验设计：一共做 n 次 `sum++`，把 n 次分配到 T 个线程（T 从命令行输入），把 main 与几种实现分别链接——原子指令（x86 上是 `lock add`，ARM 上用另一套机制）、pthread mutex、不断 exchange 的自旋锁、每次强制进入系统调用的 futex。

    * 控制变量的要求：控制总 `sum++` 次数不变、只改变线程数（1、2、4、8、16）；每种实现重复五次（做能复现的实验，不要 cherry-picking）；统计一次 `sum++` 的平均时间；把原始数据存成 CSV，再生成带 error bar 的图。

    * 结果：

    * 四种实现的量化对比：

        | 实现 | 单线程下每次 sum++ 的开销 | 线程数超过 CPU 数之后的扩展性 | 说明 |
        | :--- | :--- | :--- | :--- |
        | 原子指令 | 最低，几纳秒到十几纳秒 | 基本不下降 | 只做 sum++ 时性能最好 |
        | pthread mutex | 很低 | 基本不下降，接近直线 | scalability 更好 |
        | 自旋锁（exchange） | 很低 | 下降非常显著 | 持锁线程被换出后其余线程全在空转 |
        | 强制每次进内核的 futex | 几百纳秒 | 很差 | trap 的开销远高于其他方式 |

    * 单线程时所有实现都是最快的；一次系统调用要几百纳秒，而真的做一次 `sum++` 只要几纳秒到十几纳秒；一旦上到两个线程、在物理处理器数（例如 4）以内，各实现差距不大；线程数一旦超过处理器数量，mutex 与原子指令基本不下降，自旋锁下降非常显著。

    * 取倒数（每秒操作数）的图看得更清楚：只做 `sum++` 时原子指令性能最好，mutex 与自旋之间有差距且 mutex 曲线更接近直线，trap 的性能很差。

* **benchmarking crime**

    * 做实验前应先读 Systems Benchmarking Crimes；其中一种叫 selective data set hiding deficiencies：用一个特定的数据集或配置恰好把缺陷藏起来。

    * > **易错点**：若把实验线程数限制在「线程数与 CPU 数差不多、每个 CPU 一个 `sum++` 线程」的区间，所有人围观的情况非常罕见，瓶颈就被藏起来了——图是真的，结论是错的。

    * 同一个陷阱的另一种形态：每个线程各用各的锁、各算各的 sum、最后汇总，曲线看起来很好，实际上是有 scalability 问题的程序，线程数超过 CPU 数时性能会急剧下降。

## 同步与条件变量

### 同步的本质

* **同步（synchronization）**

    * > **定义**：两个或者两个以上随时间变化的量，在变化过程中保持一定的相对关系。

    * 直观的物理过程是线程之间（或异步的每个人之间）达成一次握手，这个握手就称为同步；所有同步例子的共性是「要等到某一件事情发生」——一开始同步条件不满足，先到的一方必须等，等到另一方把同步条件达成。

    * 现实中的同步各有机制：同步电机靠磁场锁定，同步电路靠时钟信号驱动（上升沿到来时寄存器/flip-flop 把值锁住，锁住后组合逻辑电路在周期内算到稳态，输出接到下一个寄存器输入，但要等下一个上升沿才锁存——边沿触发）。

* **全局同步状态与 happens-before**

    * > **定义**：同步条件达成的那一瞬间叫全局同步状态；此刻世界是容易理解的，可以写 `assert` 去断言条件（节拍已到、两个同学都在门口）。

    * 互斥做的是阻止并发、让执行要么 AB 要么 BA；同步实现的是在某时间点达到一个全局确定的状态，断言通过后两个线程才继续分叉、异步往前执行。

    * 同步还实现 happens-before：之前发生的所有事情 happens-before 之后发生的事情，同步条件达成的点形成物理时间上的隔断。例如上升沿到来 happens-before 电路模拟动作；最后一个线程结束 happens-before join 之后的代码；迟到的人到达 happens-before 两人开始争执。

    ```text
    异步执行（各自往前跑，结果不确定）
    ----+----+----+----+----+----+----+----+----+----+----+----+--->
                          |
                     同步条件达成
                    【全局同步状态】
               此刻状态确定，可以写 assert
                          |
    ----+----+----+----+----+----+----+----+----+----+----+----+--->
    异步执行（分叉之后又各管各的，结果重新变得不确定）
    ```

* **墙上时钟为什么搬不进计算机**

    * 人类相比计算机慢得像蜗牛，才发明了时分秒年月日这样的历法；把尺度放到计算机上，「线程 A 在某个时刻开始、线程 B 在一分钟后开始」这一分钟对处理器来说已经非常长。

    * 节拍不齐的可感阈值：节奏感强的音乐超过 20 到 30 毫秒的不同步就能被听出来；而这 20 到 30 毫秒对计算机来说可以执行上亿条指令。

    * 计算机之所以能不断播音乐：只要在硬件上放一个 buffer，先把未来 20 毫秒的声音填进去再开始播（实际延迟 20 毫秒），只要在这 20 毫秒内能把下一个 20 毫秒填进去，播放就可以交给实时性很强的硬件电路来保证不间断。

    * 时间因此不是计算机里好的同步方式——它第一不存在，第二实现它可能浪费非常多 CPU 周期。

* **四种等待的形状**

    * 乐团：`while not start`——没收到这一拍的指令就等，然后 play 一个 note。

    * 同步电路的模拟器：每个逻辑门并行工作，模拟 flip-flop 时不停等时钟上升沿；上升沿不到就不能锁存，输出只能是上一个周期的输出，看到上升沿才把要锁存的值存进去并更新输出。

    * 线程的 join：等最后一个线程结束才继续。

    * 不见不散：两个人任何一个人都可能先到，两边的等待条件都是「对方到了」，只有两人都到时条件才达成；到达时间不确定，可能早到也可能迟到。

* **盲等的代价**

    * 用一把锁硬做同步（例如乐团里线程反复检查指挥当前拍号、先上锁检查再放锁）逻辑上是正确的，但这是盲等待：不停看一下有没有，白白浪费 CPU。

    * 同步条件真的可能几天才达成，用几天时间去浪费 CPU 周期毫无必要；条件不满足时应把 CPU 让给真正要做事的线程。

    * 于是需要一个 API 帮我们实现条件检查的循环、并能把线程放到睡眠态（条件不满足就睡，条件满足就唤醒）——这就是条件变量；它底层与操作系统一起，这一系列并发 API 都是用 futex 实现的。

### 条件变量的语义

* **条件变量（condition variable）**

    * > **定义**：等待一个同步条件到达的机制；它带一把锁，检查条件必须在锁的保护下进行，否则刚检查完条件就可能被别人改掉。

    * `wait` 有两个参数：条件变量（需要初始化）与手里的那把锁。

    * 为什么必须自带一把锁：想清楚同步条件后，条件是针对共享世界里的共享状态说的；不上锁就会出现「检查完条件后别人把状态改了」的情况。

* **wait 的原子语义**

    * 执行到 `cond_wait` 时手里那把互斥锁还没有释放；因为别人想满足这个条件就必须修改 `condition` 依赖的状态、而修改状态必须持有这把锁——他不可能持有，因为我还没释放。

    * 调用的瞬间由操作系统原子地完成两件事：把这把锁释放掉；把这个线程放到睡眠状态。这两件事瞬间完成、不能被打断——不会出现「刚放锁、有人来叫醒我、我又睡着」。

    * 睡眠后线程卡在这一行，被操作系统丢到一个队列里，操作系统知道它睡在哪个条件变量上。

    * 锁已被释放，别的线程于是可以执行到需要锁的代码（例如 `lock; conductor.beat++`），未来总会有人满足我的同步条件。

    * **唤醒的假象**：虽然 `cond_wait` 时释放了锁，但被 `broadcast`/`signal` 唤醒后会重新执行 `acquire`，直到获得这把互斥锁为止——它可能不能立即得到（别人可能持有，甚至广播者自己就持有同一把锁）；拿到锁之后才继续执行后续逻辑，也就是马上把循环再执行一遍。

    * > **易错点**：条件变量给人「一整个区域都变成 atomic、都被同一把锁保护」的假象，但中间确实释放过锁；所以唤醒后必须回到循环重新判断，不能认为「被唤醒就说明条件成立」。

* **signal 与 broadcast**

    * `signal`：如果有线程因为这个条件变量在睡眠，就叫醒其中一个；`broadcast`：所有睡在这个条件变量上的线程全部唤醒。

    * `broadcast` 开销稍大，因为它有时会唤醒一个没必要唤醒的线程，那个线程还得再多循环几次做检查。

    * 两种唤醒方式的取舍：

        | 比较项 | signal | broadcast |
        | :--- | :--- | :--- |
        | 唤醒对象 | 只唤醒一个睡在该条件变量上的线程 | 唤醒所有睡在该条件变量上的线程 |
        | 开销 | 更小 | 略大，会唤醒本不必唤醒的线程 |
        | 正确性风险 | 需要自己判断该叫哪一个人，判断错了就漏唤醒 | 只要状态可能让条件成立就广播，不做判断 |
        | 建议 | 明确知道只需要一个等待者时 | 一律用它，正确性显而易见 |

    * > **提示**：选择很明确——任何一个线程使得同步条件可能达成时都用 `broadcast`，并在上锁的情况下调用，代码就永远是对的。

### 万能同步模板

* **等待模板（while 而非 if）**

    ```c
    lock(&mutex);

    while (!condition) {          /* 必须是 while，写成 if 很可能就是错的 */
        cond_wait(&cond, &mutex); /* 原子地：释放 mutex 并睡眠；被唤醒后重新 acquire */
    }

    /* 走到这里保证：1. mutex 还在我手上；2. condition 成立 */
    ...                           /* 操作共享状态 */

    unlock(&mutex);
    ```

    * `lock` 与最后的 `unlock` 一定要配对；所有对共享状态的检查与修改都在这把锁的保护下进行。

    * 走到循环外时，因为循环语义 `condition` 一定成立，又因为 `cond_wait` 返回时必然重新拿到锁，所以「持有锁」与「全局同步状态达成」在同一瞬间同时成立。

    * 循环之所以重要：线程可能被一个不该唤醒它的线程唤醒，或两个线程在等同一个东西而条件被别人先取走，于是回到循环再判断一次、必要时再次进入睡眠。

    * > **易错点**：把 `while` 写成 `if` 很可能就是错的——被唤醒不等于条件成立；一次生产者消费者在「一个生产者一个消费者」时看起来是对的，换成两对线程就会明显出错。

    * > **提示**：这段代码是期末考试值 20 分的模板。记住顺序：先上锁，`lock` 与 `unlock` 配对；要等某个条件发生就 `while (!condition)` 做 `cond_wait`；条件真正成立以后才去动共享状态。

* **修改共享状态的模板**

    ```text
    任何改变了共享状态的代码：
      lock(mutex)
      ---- 修改状态 ----           例如 count--、apples++、you_arrived = true
      broadcast(cond)              只要这个改动有可能让某个等待条件成立
      unlock(mutex)
    ```

    * 改状态与广播要在同一把锁的保护下完成；改完就广播把在等这个状态的人全部叫醒，被叫醒的人自己回到循环里重新判断。

    * 两个「绝对安全」合起来就能实现任何同步：任何时候都用 `while` 循环等同步条件；任何时候只要别的条件可能满足了就 `broadcast` 把所有人唤醒。

    * 为什么这么推荐：手工推理并发程序的行为是 NP-complete 的；用这套模板就不必试过所有可能性。

* **万能方法的核心动作**

    * 解决并发里所有同步问题就一句话：**想清楚什么是同步的条件**。生产者等桌上有空间，消费者等桌上有苹果；条件想清楚后剩下的就是无脑抄模板。

    * 条件变量里 `condition` 可以写任意逻辑，哪怕要把整个共享状态扫一遍；这正是它适合复杂条件与全局状态的原因。

### 条件变量的典型应用

* **同步电路的模拟**

    * 要模拟同步电路（例如可视化逻辑门模拟），条件就是「时钟上升沿到达」；每个逻辑门并行工作，需要并发版本。

* **线程 join 的计数器写法**

    * 每 spawn 一个线程，在持锁下把计数器加 1；等待的条件是 `count == 0`，不为 0 就进入等待循环。

    * 每一次有线程退出时上锁把 `count` 减 1；减到 0 时同步条件达成，主线程可以继续。

    * 只要有一片代码能使条件被满足、哪怕只有一点可能，就在上锁的情况下调用一次 `broadcast`，代码就永远是对的。

* **乐团式的节拍同步**

    * 线程要演奏一拍，条件是「指挥给我下这一拍」：读出当前拍号后释放锁，若这一拍还没到就再读再检查（就像乐团里的人必须盯着指挥，精神涣散就会跟错拍子）。

    * 指挥那边 `release_beat` 也要被互斥锁保护，保护好之后把拍号加一，相当于释放了一个 beat。

    * 前提条件是：所有对共享变量的访问都必须加锁，否则会出现 `sum++` 那种问题；上传锁与下一次上锁之间有 happens-before 关系，因此带上可见性保证。

* **水分子合成**

    * 三种线程（释放氢原子的、释放氧原子的），两个氢加一个氧合成一个水分子；顺序可以是氢氢氧、氢氧氢、氧氢氢；但任何时刻一旦已有两个 H，就不能再挤一个氢进去。

    * 换成缓冲池模型：一种线程往桌上放苹果、一种放香蕉，要求桌上恰好两个苹果一个香蕉然后一起拿走；同步条件与生产者消费者完全一样，只是要维护两个计数，条件为「苹果数 ≥ 2 且香蕉数 ≥ 1」。

* **打印括号（生产者消费者的简化）**

    * 两种线程都变成打印一个字符：生产者打印左括号，消费者打印右括号；左括号与右括号天生带 push / pop 的含义。

    * 括号配对的判定：碰到左括号加 1、碰到右括号减 1；减出负 1 说明出现了不合法的序列，最后不是 0 说明也没配对。

    * 加上桌子大小限制，也就是嵌套最大深度不能超过 $n$：

    ```text
    ( ( ( ) ) )      深度最深到 3，全程没有超过 3：合法
    ( ( ( ( )        出现过 4 个左括号，超过 n = 3：不合法
    ( ) ) ( )        拿走的比放进去的多，深度变成 -1：不合法
    ```

    * 打印的时候最好也持有这把互斥锁，否则可能看到不太对的结果。

* **不要相信你的眼睛**

    * 一旦试图让世界上有不止一把锁，就很容易写错；能输出日志、能检查正确性的代码，一定要再用另一个程序去检查——例如一个简单的检查器：从标准输入读字符，看到左括号加 1、右括号减 1，判定任何时刻括号深度都正常。

    * > **提示**：让这个简单的 checker 运行很长时间都不出问题，才能在一定程度上认为程序是正确的。

* **状态机式的同步：打出一条鱼**

    * 三种线程分别打印左尖括号、右尖括号、下划线，要求同步后打出头朝左或头朝右的鱼。换成信号量之类的经典机制实现生产者消费者还算容易，实现这种生造的同步问题就会非常困难；条件变量的思路是问「什么时候可以打印这个字符」，于是画状态机。

    ```text
                  '<'           '>'           '<'
           A ──────────► B ──────────► C ──────────► D
           │                                          │
       '>' │                                     '_'  │
           ▼                                          │
           E ──────────► F ──────────►────────────────┘
                  '<'           '>'
    ```

    * 状态与允许动作：

    * 状态与允许动作：

        | 当前状态 | 可以打印的字符 | 下一状态 |
        | :--- | :--- | :--- |
        | A | `<` | B |
        | A | `>` | E |
        | B | `>` | C |
        | C | `<` | D |
        | D | `_` | A |
        | E | `<` | F |
        | F | `>` | D |

    * 系统处于 A 状态时是不确定的：两种线程都可以选，相当于以一半的概率决定这条鱼朝哪边；一旦选定就必须按确定顺序打下去，打到 D 再回来。这个状态机不在操作系统里，就在程序里维护。

    * 用一个初值为 1 的 `quota` 保证任何时刻只有一个线程真正在打印；同步条件是「当前状态的下一个字符正好是我这个线程要打印的字符，并且此刻没有别人在打印」。

    * > **注意**：条件变量不是让人去做这种题目的；布置它只是为了理解同步的实现方式。实际并发编程里大部分时候用的还是生产者消费者和计算图模型。

## 计算图模型

### 依赖图与拓扑

* **计算图（computation graph）**

    * > **定义**：一张由有向无环图表达的计算依赖——节点上是计算任务，一条 $u \to v$ 的边表示节点 $v$ 会用到节点 $u$ 算出来的值，也就是一条 happens-before 依赖。

    * 节点可以任意使用共享内存、使用过去所有算出来的结果；只要每个节点独立计算的时间足够长，管理这张图的开销就可以忽略不计（一个节点花几秒钟，几百几千节点的图做一次拓扑排序只要几微秒）。

    * 若计算本身可大规模并行（例如神经网络），更倾向于不要把特别细碎的计算都建成节点，而是把一整层的计算写在一个节点里，得到一张简单清晰的计算图；模型也可以是动态的（每来一个 HTTP 请求动态生成计算任务）。

* **生产者消费者（producer-consumer）**

    * > **定义**：若干生产者线程往共享缓冲池里放任务，若干消费者线程从缓冲池里取任务并把任务做掉；缓冲池就是那张桌子，任务就是桌上的苹果（每个苹果上贴着「要去做一件什么事」的字条）。

    * 两条硬约束：苹果必须是放一个拿一个（有硬的 happens-before）；桌子的大小是有限的。

    * $n = 2$ 时最多同时放两个苹果：一万个生产者同时收到请求也最多两个放得上去，其余拿着苹果的生产者要等（等到有消费者把苹果拿走、桌上苹果数小于 2）；消费者必须等到桌上苹果数大于 0 才能拿走。

    * 现实里的实例：HTTP 服务器（gateway 把请求放到桌上，后端取走再查数据库做更耗时的操作），教务系统也是这样长起来的。

    * 也叫 master-slave 模式；因为 master-slave 不合时宜，还有 scheduler-worker 这个名字（一个调度者负责分配任务）。

* **现实世界的计算图实例**

    * 神经网络：PyTorch 会生成一张 FX Graph，就是一张有向无环的计算图，顺着顺序去计算。

    * Makefile：一个 `a.out` 依赖 `a.c` 配一条 recipe，还可以有别的 recipe 也 depend on `a.c`，再有东西同时 depend on `a.out` 和别的；不能有环（有环 Makefile 会 complain 并拒绝编译）。它可自动并行——做一次拓扑排序就看出中间若干条互不依赖的 recipe 可以并行，于是 `make -j4`、`make -j16` 能大幅提升编译速度。

    * 动态规划：最长公共子序列可以理解成二维网格图上的遍历——第 $i$ 行第 $j$ 列表示「在第一个字符串第 $i$ 个位置、第二个字符串第 $j$ 个位置」；字符相等可以斜着走一格（吃一分），也可以横向或纵向走一格跳过字符；转 90 度或用一条斜线去切，就有非常明显的层次关系，先算第一层再算第二层一路推过去。

    * 电路模拟：Verilator 之类的仿真器把电路切成若干部分，没有依赖关系的两部分独立并行计算，有依赖关系时必须等前一个结果算完。

### 两种实现方式

* **每个节点一个线程**

    * 节点的可执行条件就是所有前驱节点都执行完，这正是拓扑排序的定义。

    * 条件可以用两种方式表示：为每一条边设一个布尔变量（条件是 `done(e1) && done(e2) && done(e3)`，节点执行完就把所有出边的 done 置真）；或者用计数器——$v$ 初始就知道自己要等多少个完成信号（有几条入边），每完成一条入边就把计数器减一，减到零就可以执行。

    * 计数器实现的关键点：

    ```c
    /* 建图阶段：为每个节点数出它还要等几个前驱 */
    for (each edge u -> v)
        pending[v]++;

    void *Tworker(void *arg) {
        Task *t = arg;

        lock(&mutex);
        while (pending[t->id] != 0)          /* 同步条件：所有前驱都已完成 */
            cond_wait(&cond[t->id], &mutex); /* 每个任务一个条件变量，不必唤醒所有人 */
        unlock(&mutex);

        do_work(t);                          /* 这一段不需要持锁 */

        lock(&mutex);
        for (each edge t -> w) {             /* 更新整个图的依赖关系 */
            if (--pending[w] == 0)
                cond_broadcast(&cond[w]);    /* 只要有线程可能被唤醒就广播 */
        }
        unlock(&mutex);
        return NULL;
    }
    ```

    * `do_work` 可以不上锁：通常只需要在很少的一段代码里上锁（例如「从队列里把那个任务取出来」这一小段），任务带一个指向大块内存的指针、而这块内存在这段时间只有自己能访问，确定没有并发 `sum++` 这类问题时就可以去掉锁，从而拿到多处理器并行的好处。

    * 收尾的唤醒策略：处理完自己的任务后对每条出边把后继的 pending 减一，只要有 dependency 减到零就直接 broadcast；用 signal 也可以，但做得保守——不要为了一点点不存在的性能搬石头砸自己的脚。

    * 运行结果：node 0 先执行，然后 1、2、3 同时执行，再是 4 和 5；1、2、3 之间的顺序仍不确定。

* **线程池（executor pool）**

    * 不再为每个计算节点设置一个线程，而是按 CPU 数量创建线程（例如机器有 4 个 CPU 就建 4 个线程），每个线程配一个队列。

    * 先做一次拓扑排序，每当发现有节点可以算就放进队列；每个线程的 condition 就是「队列不空」，它从队列取一个任务去做——这就是消费者；同时它又是生产者：每做完一个任务就发现有一些任务被激活了，于是把新激活的任务放回队列。

    * 好处：可能有几百万个节点但只有四个 CPU，没有必要创建一百万个线程（创建线程本身也有开销）；加一个队列、用生产者消费者解决就够了。

    * 这份实现可以直接当模板：只要系统还能并行、并行度足够，就能很好利用多处理器的能力，而且还能使用共享内存——把中间结果写进内存保存到数据结构，后面的任务被激活后直接就能用到之前写入的值。

    * 同步条件的表述：为每个节点分配线程时是「我所有的前驱节点都执行完我才能执行」；用线程池时是「队列里有任务我的线程就可以拿一个，队列空就必须等」，创建出新任务放回队列就可能激活别的 worker thread。

## 信号量

### 钥匙与计数资源

* **信号量（semaphore）**

    * > **定义**：把「一把锁上只有一把钥匙」扩展成「一张桌子上可以放若干把钥匙」的计数型同步机制；`lock` 的语义从「看玩具有没有」变成「看玩具是不是大于 0 个」，有余量就拿走一把。

    * 操作叫 P 和 V（Dijkstra 当年选定、来自荷兰语）：P 是 try and decrease（也叫 down、wait）——先看同步条件，不达成就要等待，达成才减 1；V 是 increase（也叫 up、post、signal、release）——计数加 1。形象说法是 P 拿走一把钥匙、吃掉一个车位，V 放回一把钥匙、变出一个车位。

    * 现实模型：停车场（管理员手上有 4 个一模一样的玩具，对应 4 个车位，拿走一个余位减 1，还回一个余位加 1）、游泳馆（登记发手环，泳池本身是共享空间但进入必须拿到手环）、餐厅（高峰期门口取号）。

    * 计数推演（$count = 4$）：前 4 个 P 都能成功并把 count 减到 0；第 5 个 P 阻塞等待；某个线程 V 之后 count 变回 1 但等待中的线程立刻把它拿走（此时 count 仍是 0）；所有人陆续结束各自 V 完，count 回到 4。

    * 用万能模板写出来：P 操作先获得互斥锁，条件不达成就不满足地等待（准备消耗掉一个），条件达成才把玩具拿走、count 减 1；V 操作就是 `count++`，然后 broadcast。

    * > **提示**：P 就是停车场的闸门——进来剩余车位减 1，出去剩余车位加 1，至于你进来之后在里面干了什么它不负任何责任；在里面写出 undefined behavior、把内存 corrupt 掉都是可能的，里面的代码仍要非常谨慎地写。

* **信号量天生就是互斥锁**

    * 初始化一个 `count = 1` 的信号量就等于桌上只有一把钥匙、只有一个车位的停车场：任何想进入的车都必须执行 P，只有一辆车能拿走钥匙开进去，后面的车怎么等都进不来。

    * 想 unlock 就把玩具还回去，计数又变回 1；只要 lock 和 unlock 配对，任何时刻也只有一个人能出。

    * > **易错点**：这套推理的前提是代码写对了。若某条执行路径上出了 bug 让你 unlock 两次，就相当于凭空变出一个车位——违反「停车场只有一个车位」的约定后，从此会有两辆车能同时进入。

    * 用条件变量实现互斥锁与实现信号量是摆在一起的两段代码：一个条件是「玩具在桌上、$k == 1$」，另一个条件是「玩具个数大于 0」；扩展关系一目了然。

* **用信号量制造 happens-before**

    * 用之前必须先想清楚两件事：谁把这个玩具放到桌上，谁把这个玩具拿走。

    * 任何线程都可以对某个信号量执行 V（把玩具放到桌上），此后另一个线程（也可能是它自己）执行 P 把它取走，这就形成一次 happens-before：V 之前发生的所有事情都 happens-before P 之后发生的事情；例如在 V 之前往 buffer 写数据，另一个线程 P 成功后就能读到。

    * 实现一次临时的 happens-before：把信号量初始化成 0，先做完「V 之前」的事，然后释放这个 token；另一个线程如果等我完成，只需要去 P 这个 token。

    * 这正是「让锁跨线程传递」那个聪明想法的正面版本——在 main 里先把玩具都没收，然后用玩具的交接去实现同步。要注意真实的互斥锁不允许跨线程 acquire/release（线程库要求二者在同一线程里配对，内部有很多默认「谁上锁谁解锁」的 fast path），那是 undefined behavior。

### 信号量的用法

* **join 的两种写法**

    * 一桌一线程：为每个线程的执行结束设置一张桌子，T1 结束就把玩具摆到自己那张桌上，T2、T3、T4 各自如此；main 从第一个线程开始依次 P 每一个信号量，全部收进手里时一次 join 就完成了。

    * 一张桌子数数目：信号量支持多个玩具，所以不必每个线程一张桌子——main 知道自己创建了多少个线程，每个线程结束时往同一张桌上放一个玩具，main 就 P 那么多次，每 P 一次拿走一个，全部拿到就继续。信号量初始化成 0，每个线程结束时 V 一次。

    * > **结论**：信号量最合适的场景是管理计数型资源——游泳池里的人不能超过 n 个、停车场只有 n 个车位、餐厅只有 n 桌，或者我要等 n 个线程。

* **计算图上的两种写法**

    * 桌子放在边上：给每个线程的结束设置一张桌子，对应到计算图上就是在每一条边上放一个信号量；某个前驱执行完就在那条边上放一把钥匙，前驱都执行完就集齐三把钥匙才能继续。

    * 桌子放在节点上：把节点信号量初始化成 0，为每个节点创建一个线程；遍历阶段遍历该节点的所有入边、有多少条入边就 P 多少次（这几次 P 的是同一个信号量，也就是该节点对应的那张桌子，不在意钥匙以什么顺序被放到桌上）；计算做完后对每一条出边各 V 一次，把一把钥匙放到依赖我的那个节点的桌上。

    * 于是有了「信号量天然互斥锁」的另一面：本课讲互斥锁时是从「桌上只有 1 把钥匙」的角度实现的，这里则从「桌上有若干个玩具」的角度反过来看。

* **生产者消费者：最漂亮的应用**

    * 两个信号量 `empty` 与 `fill`，两个线程 `T_produce` 与 `T_consumer`；buffer 容量为 4 时 `empty` 桌上初始有四个玩具，`fill` 初始为 0。

    ```text
          +---------------+                     +---------------+
          |    empty      |                     |     fill      |
          |   count = 4   |                     |   count = 0   |
          +-------+-------+                     +-------+-------+
                  | P(empty) 拿走一把钥匙                | P(fill) 拿走一把钥匙
                  v                                     v
          Producer 往 buffer 放一份数据          Consumer 从 buffer 取走一份数据
                  |                                     |
                  v                                     v
          V(fill) 往 fill 桌上放一把钥匙         V(empty) 往 empty 桌上放一把钥匙
    ```

    * 生产者需要「至少要有一个空位」，于是 P(`empty`) 拿走一把钥匙，然后打印左括号；做完之后 V 的不是 `empty` 而是 `fill`——打印出左括号就意味着别人可以消费了。

    * consumer 做完全对称的事：P(`fill`) 拿走一个玩具、把东西消费掉、再 V(`empty`) 把玩具球放回去。

    * > **定义**：`empty` 桌上的一个玩具对应 buffer 里的一个空槽位；`fill` 桌上的一个玩具对应 buffer 里一份已写入、等待被消费的数据。

    * happens-before 链：P(`empty`) 返回 happens-before 生产，生产 happens-before V(`fill`)；只有真的把 buffer 那个格子占上、写进东西，才会执行 V(`fill`)；在此之前的 V 之前，玩具还拿在它自己手上。若两个 producer 都 P(`empty`) 成功，两人总有一天都会往 buffer 写数据并在 `fill` 桌上各放一个球，两份数据与两个球一一对应。

    * 全局不变式：`empty` 的数量 + `fill` 的数量 + 处在中间状态（已拿走钥匙、正在生产或消费途中）的数量恒等于 buffer 的大小；正是一一对应关系保证了交接链可靠。

    * 深度设成 1、2、3 都能正确同步；一次创建八对生产者消费者长时间压着跑、再用脚本核查输出也挑不出错。遇到生产者消费者完全可以 follow 这个 pattern。

### 与条件变量的分工

* **什么时候用信号量**

    * 只要脑子里的模型就是「桌上有钥匙，凑齐了才能往下走」，信号量就是优雅并且被推荐的选择：happens-before、join、计算图、生产者消费者都适合。

    * 信号量的用法要借助拟人化的「桌子、钥匙、人」去理解；好处是生产者消费者写得极干净。

* **什么时候必须用条件变量**

    * 同步条件里出现「或」（满足 A 或者满足 B 都行）是信号量最难表达的形状：信号量本质是一个计数器，它擅长表达「还差几个」，不擅长表达二选一。

    * 例：打鱼的状态机里，某个状态下左括号线程与右括号线程都是激活的、它们的同步条件同时达成，这里出现了一个「或」。用信号量硬做也能做（给每种线程各发一个信号量，每次打印完检查当前状态，若两个线程都该被放行就抛一枚硬币、以 1/2 的概率 V 某一个），但同步条件越复杂、越是涉及全局状态的函数，条件变量就越无所谓。

    * 例：生产者消费者加上 close 和 open。执行 close 后整个系统最终应回到初始状态（`empty` 桌上是满的球、`fill` 桌上一个球都没有）；但信号量的代码是写死的（put 就是 P(`empty`)、get 就是 V(`fill`)），根本没有位置放 close/open——又不能同时去 P(`empty`) 又去 P(`close`)。条件变量这边只要在全局状态上加一个 `closing` 标记，生产者看到它就停止生产，close 的线程还可以等所有人汇报收工。

    * > **易错点**：「满足 A 或者满足 B 就可以继续」这类语义在信号量里表达不出来；信号量只会在一条既定的、写死的路径上把计数减下去。

* **双向实现的不对称**

    * 用条件变量实现信号量很轻松：P 就是「等到 counter 大于 0 然后把 counter 减 1」（`while (counter <= 0) condition_wait(...); counter--;`），V 就是加一然后 `condition_broadcast`。

    * 反过来用信号量实现条件变量非常 tricky。一个看似合理的写法是维持计数器 `nwait`，wait 时先 `nwait++`、释放互斥锁、再 P 一个用于睡眠的信号量，醒来后重新拿锁；broadcast 时按 `nwait` 的数目往桌上放同样多的玩具。

    * 该写法错在哪：`nwait++` 之后那个 P 可能被推迟到一万年以后——于是 `nwait` 加了 1 却没有人真的睡下去；broadcast 时看起来唤醒三个线程、放三个玩具，实际因为多了一次 `nwait++` 就多执行了一个 V，而这个多出来的 V 会被下一个要睡眠的线程直接抢走（本该与自己的 P 配对，却和别人的 P 配对了）。虽然那个线程醒来后仍会被 `while` 循环挡住，但少唤醒了一个线程，整个实现就错掉。

    * > **结论**：根本困难在于 release 和 sleep 这两个操作必须合成一个原子操作；只要中间存在延迟，整个事情就坏掉。操作系统实现条件变量时用 futex 把它做成原子操作。

    * 教科书原话：One could view semaphores as a generalization of locks and condition variables——前半段没问题（桌子模型确实把锁推广了），但它并不是条件变量的推广；反向实现的难度用原话说就是 surprisingly tricky。

* **为什么不该用信号量做条件变量的活**

    * 一个并发算法到底对不对，唯一的办法是试过所有可能性；既然世界上已经有不需要试过所有可能性的方法（条件变量这种万能同步方案），就应先用它，不要让自己去排列线程里的事件顺序（那是 NP-complete 问题）。

    * 信号量正确性的「坑」往往不在单个信号量的语义，而在多个信号量之间的顺序；只有一个信号量时正确性不用担心，一旦有两个就麻烦得多，而它看起来又总是那么显然。

## 哲学家吃饭问题

### 条件变量解法

* **问题设定**

    * 每个哲学家就是一个线程，围成一圈；一共五个人、五份饭、五把叉子，要吃就必须同时拿到自己左手和右手边的叉子；线程可以吃也可以思考，思考时要把叉子放下来让别人有机会吃。

    * 编号规则：右手的编号就是自己的线程号，左手的编号是它减 1（在 mod n 的意义上减 1 等于加 n−1）。每个哲学家都是一个死循环，中间需要插入同步。

    * 吃饭的条件本身特别简单：左手叉子可用，并且右手叉子可用；检测到两个都空闲就把它们一起拿起来、二者立刻变成不空闲，然后就可以吃。

* **条件变量实现**

    ```c
    mutex_lock(&mutex);
    while (!(available[left] && available[right]))
        condition_wait(cv, &mutex);

    assert(available[left] && available[right]);
    available[left]  = 0;
    available[right] = 0;
    mutex_unlock(&mutex);

    /* 吃饭 */

    mutex_lock(&mutex);
    available[left]  = 1;
    available[right] = 1;
    condition_broadcast(cv);
    mutex_unlock(&mutex);
    ```

    * 关键保证是带锁：条件变量给的是「这段代码是锁上的」这一条保证——在我检查完条件、改完共享状态的这段区间里，不会有人能抢到我这把锁，所以「检查」和「更改」是连在一起、中间不被打断的。只要不用两把不同的锁保护同一份共享状态，就实现了一个原子的「把两把叉子一起拿起来」。

    * 吃完之后很简单：上好同一把互斥锁，把两个变量置回 1，然后 broadcast；谁先被唤醒一点都不重要，他们自己会回到循环里再检查一遍。

    * > **提示**：除非题目本身就是为了让你用一个特别巧妙的信号量，否则不要一上来就追求奇技淫巧——**第一件事先把锁上好**。这道题在期末里分量固定，是 20 分。

### 信号量解法与死锁

* **直接映射成信号量会死锁**

    ```c
    sem_wait(&forks[left]);     /* 拿起左手叉子 */
    sem_wait(&forks[right]);    /* 拿起右手叉子 */

    /* 吃饭 */

    sem_post(&forks[left]);     /* 放下左手叉子 */
    sem_post(&forks[right]);    /* 放下右手叉子 */
    ```

    * 推到一半时是对的：拿到两把叉子后确实没有人能再拿到我左右手这两把叉子，互斥成立。

    * 问题出在「所有人都先拿左手」：A 拿起左手叉子、B 也拿走自己的左手，一路走下去每个人左手上的叉子都被拿光；然后每个人去看右手，没有任何一个人能拿到——所有人都在等别人 release，而没人能 release。

    ```text
    P0 ──等──> fork0 ──被持于──> P1
    P1 ──等──> fork1 ──被持于──> P2
    P2 ──等──> fork2 ──被持于──> P3
    P3 ──等──> fork3 ──被持于──> P4
    P4 ──等──> fork4 ──被持于──> P0   ← 回到起点，闭环
    ```

    * 后果比想象中更惨：第一轮刚开始，每个人都拿了一把叉子、甚至还没人成功吃到任何东西，系统就已经崩了。

* **补丁一：赶走一个人**

    ```c
    sem_wait(&table);           /* 先在外桌拿一把钥匙，桌上一共有 n-1 把 */

    sem_wait(&forks[left]);
    sem_wait(&forks[right]);

    /* 吃饭 */

    sem_post(&forks[left]);
    sem_post(&forks[right]);

    sem_post(&table);           /* 退出外桌，把钥匙还回去 */
    ```

    * 再设一个信号量 `table` 初值取 $n - 1$：死锁必须是每个人都拿齐了一把叉子才可能发生，如果桌上最多只坐四个人，四个人对五把叉子就一定有人能拿到两把。因为外面最多只发出四把钥匙，最多四个人能进来，系统就不会死。

* **补丁二：给叉子编号（lock ordering）**

    ```c
    int a = left, b = right;
    if (a > b) { int t = a; a = b; b = t; }   /* 永远先申请编号小的叉子 */

    sem_wait(&forks[a]);
    sem_wait(&forks[b]);
    ```

    * 平时喜欢对称（对称意味着简单、每个人执行的 protocol 都一样），而要 fix 这个死锁恰恰要把它变得不对称一点：每个人都总是先拿编号小的叉子、再拿编号大的叉子。

    * > **结论**：这两种方法已经开始不如条件变量，因为它们的正确性**不写在程序里**，而是依赖一个额外的证明或者一段额外的说明。lock ordering 这种已被工业界广泛认可、已经成为定理的东西拿来用没问题；但「从桌上赶走一个人」这种靠补漏洞硬把事情补上的方式应当尽量避免。信号量解哲学家吃饭不算一次成功的尝试，更多时候是一个 workaround——对信号量感到受挫时就果断放弃它。

    * > **易错点**：正确性不写在程序里，就不能随着时间推移让系统变得更复杂——从第一行起就得非常小心地维护，等系统越长越大很可能就会失败。

### 集中式服务员

* **把任何同步问题变成生产者消费者**

    * 给哲学家请一个 waiter（服务员线程）来管全局的同步条件：干脆把五把叉子都放在自己手里，禁止每个线程直接访问那份全局状态，并发控制就完成了。

    ```text
    哲学家线程 ──send「我要 fork 1、3、4」──> [ 消息队列 buffer ] ──> waiter 线程
        ▲                                                                    │
        └────── 等服务员回一个 OK（PV）  <── 服务员从自己手里划掉 1、3、4 <──┘
    ```

    * 任何哲学家想吃饭就给 waiter 发一条消息；waiter 就是一个 `while` 循环从 buffer 里取消息。消息队列完全可以用 buffer 实现——send 就是往 buffer 放一个球，receive 就是从 buffer 取一个球，这就是标准的生产者消费者（`P(empty)`、`V(fill)`、`P(fill)`、`V(empty)`）。

    * 服务员手上有所有叉子的控制权，所以知道左手和右手那两把叉子是不是都在；甚至可以要一组叉子（说想要编号 4、3、1 的三把），服务员一看 1、3、4 都还在，就在自己的内存里把它们划掉——注意这份状态不是全局内存，而是他自己的一份内存——然后回一个 OK。这个 OK 就用 PV 实现：发送消息相当于 acquire 之前的等待，服务员回 OK 相当于一次 release。

    * 好处：需要你考虑的调度可能性从指数多个变成一个简单的串行逻辑。服务员每次 send 都在队列里排好队，每次拿出一个按固定顺序处理，他不并行、没有并发，逻辑简单到谁都会写。

    * 额外好处：它是一个调度器，可以实现各种策略——公平性、load balancing 都能做。例如某个线程被绑到大核上跑得特别快，就更容易抢到叉子；有集中式的 waiter 就可以在里面记录「什么时间点收到谁的消息」，故意让某个之前拿到太多叉子的哲学家多等一会儿（例如延时十毫秒再回应）。

    * 性能不成问题：决定「能不能把叉子分给你」往往只需要一次 hash table 或一个数据结构的判断，几纳秒就完成，时间复杂度很可能是 O(1)；而一次哲学家吃饭要花几秒钟或者几十毫秒。

    * 若请求量极大（128 核、256 核的 Web 服务器上一秒几万个请求），也可以放两个 waiter，把一半 CPU 绑到一个 waiter 上、另一半绑到另一个。

    * > **提示**：这也是生产者消费者这个模型的价值所在——有了它就可以实现一个 waiter 线程去管理所有哲学家。

    * 这正是做系统的智慧：先不要管算法有多漂亮，先要解决问题；解决过程中如果性能真的有问题，再去解决那个性能问题。

## 死锁

### 两类典型形态

* **死锁（deadlock）**

    * > **定义**：A deadlock is a state in which each member of a group is waiting for another member, including itself, to take action——互相等待，也可以是自己等自己。

    * 现实证据：公交车头尾相连连成一圈，没有一辆车可以 make progress；要发生这样的事条件挺苛刻（需要头尾正好接上），但它就是发生了。

* **AA 型死锁**

    * 同一个线程对同一把锁 lock 了一次再 lock 一次，具体后果取决于实现：

    * 同一次重复 lock 在两种实现下的后果：

        | 锁的实现 | 第二次 lock 同一把锁 | 要几次 unlock 才算真正释放 |
        | :--- | :--- | :--- |
        | 可重入锁（线程本地计数器） | 计数加一，立即成功 | 每次 unlock 减一，减到零才真正释放 |
        | 普通互斥锁 | 当成「已被别人持有」去等 | 永远等不到——持有者就是你自己 |

    * 可重入锁的做法是给锁配一个计数器（可以是线程本地的）：lock 一次加一、unlock 一次减一；lock 了两次就必须有两个 unlock 配对，第一次只把计数减到一、减不到零。

    * 真实世界的成因：线程正 acquire 一把锁时按了 Ctrl+C，而 Ctrl+C 的处理逻辑里认为有个并发数据结构要保护、于是也 acquire 同一把锁，AA 型死锁就这样形成。

    * > **结论**：一旦程序开始并发、开始异步，控制流就不可能再被完整地追踪；我们需要互斥来阻止并发，但阻止并发是有代价的——你会因此产生死锁。

* **ABBA 型死锁**

    * 两个线程：T1 先 lock A 再 lock B；若 T1 与 T2 没有交错，程序先后是 A、B 好像没问题。但如果 T2 先 lock B，此刻 T1 与 T2 各持一把锁：T1 想 lock B 就得等 T2 释放，而 T2 这时若执行 lock A 就要等 T1 释放——循环等待形成。

    * 哲学家就餐里这个环更复杂（5 个人、5 个线程绕成一圈），简化地讲它就是 ABBA 型死锁。

    * > **注意**：做实验时如果随意拆锁，很容易就把 ABBA 型死锁写出来；在实际的系统当中 ABBA 型死锁也是最常见的。

* **死锁通常不难发现**

    * 程序原本一秒钟不停地输出日志，突然一个日志都没有了，你马上就意识到系统里可能发生了死锁。

    * 预期一毫秒就该收工的线程到现在还没结束，输出也与预期不符（例如可重入锁本该出现两条打印、现在一条都没有），两个信号合起来就可以断定发生了死锁。

    * 用 GDB attach 上去，死锁也是相对容易查的一类 bug。

### 四个必要条件

* **四个必要条件**

    * > **定义**：死锁产生的必要条件，即这四个里任何一个不成立死锁就不会发生（当然还可能有别的问题）。出自 1971 年的经典论文 System Deadlocks。

    * 四条条件逐一对照：

        | 条件 | 用钥匙和桌子来说 | 打破它意味着什么 |
        | :--- | :--- | :--- |
        | mutual exclusion（互斥） | 一把钥匙只能被一个人拿到，拿到才能继续 | 根本不能再有锁这种东西 |
        | wait for（持有并等待） | 已经拿到钥匙的人，还想再拿别的钥匙 | 别用锁，或者让一组操作整体生效 |
        | no preemption（不可抢占） | 别人不能抢你的钥匙，你也不能抢别人的 | 抢锁就得能回滚别人已经做过的事 |
        | circular wait（循环等待） | 等待关系绕成一个环 | 给锁定一个全局顺序，只准从小到大上锁 |

    * $$\text{死锁可能发生} \Leftarrow \text{互斥} \wedge \text{持有并等待} \wedge \text{不可抢占} \wedge \text{循环等待}$$

    * 互斥：如果互斥不成立，那也就谈不上死锁了——锁都不是锁了；包间门上的锁都被拆掉确实不会死锁，但可能会有其它问题。

    * 持有并等待：AA 型死锁就是已经把钱进口袋还想再摸一把，ABBA 也是；如果世界上只有一个桌子一把钥匙、拿到钥匙的人永远不想要更多钥匙，就没有 AA 型死锁，「一把大锁保平安」确实也不会死锁。

    * 不可抢占：程序里不存在抢别人钥匙这种操作——锁在实现时那个 system call 就决定了我们只能不停地去看钥匙在不在，没有抢锁这个动作。

* **循环等待最容易打破**

    * 这是四个条件里最容易打破的一个；听起来反直觉，因为死锁的定义就是循环等待，但你使用锁的时候最容易打破的条件恰恰是它。

    * 不过编程上要满足它本身仍有很大困难，因为有一个 Rice's theorem：只给你程序，想分析出其中任何一个 non-trivial 的性质都是 Turing complete 的。你可以在任何地方嵌一段验证哥德巴赫猜想的程序，它永远不会结束；如果你能分析出它会不会死锁，就能证明哥德巴赫猜想了。

### 打破条件的手段

* **打破互斥：把锁换成通信**

    * 要打破它就必须彻底重构代码——不允许再用互斥锁。办法是引入一对 send 和 receive 的 API，例如哲学家就餐里引入一个 waiter 线程跟它通信；实现 send/receive 时仍然需要锁，但一旦这套收发机制做出来，就再也不需要锁。

    * > **结论**：分布式系统里那种 Master-Worker 结构就是这么设计的——不是直接用锁去互斥，而是通过集中式的方式来管理，自然而然也就把锁的问题解决掉了。

* **打破持有并等待：atomic 与事务内存**

    * 最直接的办法是「一把大锁保平安」（消灭 AA 型死锁就不会再遇到别的死锁），但性能很低。

    * 另一个方向是引入关键字 `atomic`（与 database transaction 同一个意思）：里面的代码要么好像全部执行完（stop the world、一次做完），要么好像一下都没有执行；在 `atomic` 里写两个 `sum++`、另一个线程也写同样的 `atomic sum++`，你看到的结果只能是 2、4、6、8、10，永远不可能看到奇数。

    * 有了它就像支付宝那样：可以先对全局状态做 check 再 modify，保证结果是 all-or-nothing。但事务内存（transactional memory）非常难实现，尤其里面还要有系统调用时更难——因为系统调用就像泼出去的水，不可能再收回来。

    * 从大约 1990 年代开始有人研究这个机制；2010 年左右 Intel 甚至把 `xbegin` 和 `xend` 加进指令集，但后来引发了很多问题（包括安全漏洞），所以消费级笔记本上基本看不到了，服务器上这个特性依然有；ARM 也加过一段时间后来不想在指令集里维护它——因为它是一条可以和所有指令产生关联的指令，有点像 fork，会给指令集体系结构的实现带来很大麻烦。

* **打破不可抢占：要抢就得能回滚**

    * 抢别人的钥匙很混乱：我处在 lock 状态、想把别人的锁抢过来，别人已经把 `sum` 改到一半、锁在他手上；我要么等他做完，要么把他从房间里踹出去——而踹出去就必须把他已经对系统产生的 side effect 全部回滚掉。

    * 所以这又指向事务内存：必须能回滚持有锁线程已经执行过的操作，才谈得上打破不可抢占。

    * > **提示**：仔细去想四个条件里的每一个，每一个都打开了一个新领域的分支，它们可能让编程这件事变得更好——这才是一个很好的、推动人类进步的 idea。为实现这些想法可能要费非常多精力，可能有上千篇论文和事务内存有关。

* **打破循环等待：lock ordering**

    * 把世界上所有的锁都编一个号，强制要求上锁时必须从小到大；给叉子编号后让边上那一个人先举右手叉子，就满足了 lock ordering。

    * 正确性证明：系统里的锁是有限的，任何时刻总有一个线程手上拿着编号最大的那把锁。持有当前最大编号锁的那个线程若要继续上锁，只能去申请编号更大的锁，而系统里不存在这样的锁，所以它不可能在等任何人——它百分之百可以继续运行，一定能把手里这段事做完、把所有锁都释放掉。无论怎么交错，系统里始终至少有一个线程可以往后执行。

    ```text
    上锁只允许从小到大：1 ──► 2 ──► 3 ──► 4

    T1: 持有 {1, 3}，想再拿 4      ← 4 比 3 大，合法，去抢
    T2: 持有 {2}，想再拿 4
    T3: 持有 {4}                   ← 世界上编号最大的锁在 T3 手上
    ```

    * 这个论证可以扩展到 lock group：按组号从小到大上锁，总有一个线程持有组号最大的锁，它一定可以往前执行；额外要求只是保证组内部不出现 ABBA 的问题，而这相对容易保证。

    * > **易错点**：一个线程不可能无限期地持有一把锁，它总会释放；但如果写代码时忘了 release，那照样死锁。lock ordering 保证的只是 ABBA 这一类循环等待不会再出现。

* **逐个锁的实现级别的困难**

    * > **提示**：一个看起来完全符合逻辑的实现，在并发意义上其实可能是不对的；并发算法到底对不对，唯一办法是试过所有可能性。

### 工程化防御

* **Unreliable Guide to Locking 与文档失效**

    * 内核里有一份文档叫 Unreliable Guide to Locking：教科书告诉你只要 apply lock ordering 就不会死锁，可这有一个假设，那就是你写的程序是对的；人天生容易写 bug，所以文档给出了一些工程意义上的 best practice——例如一把锁如果永远不暴露给别人、只在你自己这个 subsystem 里用，它天生就是「在叶子上」使用的，用完就释放，那就绝对不会产生死锁。

    * 大约 53% 的有文档记载 locking rule 的锁的使用，文档和实现实际上是不一致的：改了一份代码、测试通过之后，很有可能忘了去改那条注释或那份文档。程序员的上下文窗口非常有限，他没法看到整个项目。

    * > **提示**：这件事今天可能不会再发生了——上下文足够长的大语言模型能把所有相关的东西都塞进来，一次把所有地方都修好。

* **做最坏的假设**

    * 原则来自大型软件系统设计：做最坏的假设，做最防御性的编程。不管三七二十一，先假设你的程序是错的；未测代码永远是错的；除非你竭尽所能都没有办法向我证明它是错的，我才能相信它 somehow 是对的。

    * 不要「过了样例就交 OJ、编译通过就交 OJ」；写并发程序尤其困难，没有人能阻止程序员写出 deadlock，也没有人能阻止 AI 写出 deadlock。

    * 软件工程（作者刻意反过来说的 harness engineering「驾驭工程」）的本质就是：程序员都是不能相信的。

* **goto release**

    * 做最坏的假设就意味着假设程序员写了 lock、它一定很有可能在某些罕见路径上忘记 unlock。所以规定程序不能随心所欲地写：Linux Kernel 里有一个很好的 pattern——`goto release`，跳到 release 标签，该标签会检查你所有申请过的资源有没有被释放，没有就再释放一次。

    * `return` 非常危险：它只是说这个栈帧没了，栈帧没了而资源还留着——锁还占着、buffer 还没回收（就是 leak）。所以看到 `return` 要非常紧张，不要 return、就用 `goto release`；你平时可能不喜欢 goto，但在 C 里没有其它机制保证这件事时，`goto release` 自带的意思就是「我要释放所有资源然后安全地返回」。

    * 这不是万能方法：你还是会在 release 里忘了释放某个申请的 buffer。

* **RAII**

    * C++、Rust 的核心机制 Resource Allocation Is Initialization：创建一个对象、在任何一个 scope 里（甚至不需要到函数级，在一个代码块级定义局部变量本身就是很好的 practice）lock 一个对象——进入代码块时编译器保证构造函数被调用，离开时不管是用 `return` 还是别的方式离开都保证析构函数被调用。

    * 于是在构造时 acquire、在析构时 release，就能确保这把锁在这个作用域里生效；这可以阻止你上了锁忘记释放。

* **lockdep**

    * 找的是 ABBA 型的死锁：它可能在 99.99999% 的运行里都是先 A 后 B，但在一条非常罕见的路径里会先 B 后 A（例如按 Ctrl+C 的时候）。而 lock A、lock B 可能只占程序执行时间的 0.0001%，你根本碰不上把 lock B 插进去的时机——反复测试依然觉得没问题，等有一亿个用户时总有一个人按 Ctrl+C 时把 lock B 插了进去。

    * 做法：每一次 acquire 和 release 都打一条日志，看是否有某个线程上出现 B、A。即便你的程序可能是对的（例如线程之间有 spawn 同步关系：T1 里先 A 后 B，然后创建 T2，T2 里先 B 后 A，确实不会产生死锁），本着「不给程序员增加负担」的原则，依然要判定不要这样写——你的项目会改、会变，有一天 T2 那段代码被别人复用了它就错了。

    * 实现机制用 `LD_PRELOAD`：在每一次 `mutex_lock`/`unlock` 时都改成自己的代码（动态加载时覆盖操作系统原有的 API），把 lock/unlock 的日志像 strace 一样打印出来，再把输出管道给一个检查器。

    * 检查器本质上是在维护一个数据结构：顶点是锁，边是「某个线程在持有 X 的时候又去申请 Y」；如果有一天某个线程先上了 D、再上了 A，图里就形成了一个环。发现一条新的边、然后判断图里有没有环，就是一个动态数据结构问题。

    * 效果对比：一个开了 64 个线程、做 100 轮上锁的 test 没有发现显著问题；换成哲学家就餐这次运行触发了真正的死锁，而 lockdep 在前面就提前发现了问题。lockdep 每次运行都能检查到 ABBA（每次上锁都会找到该线程自己的上锁顺序并把它加进图里），而压力测试跑 100 万、1000 万次可能都触发不到那条罕见路径。

## 数据竞争与顺序类缺陷

### 数据竞争

* **数据竞争（data race）**

    * > **定义**：data race 是不同线程同时访问同一个内存，并且至少有一个是写。

    * 为什么必须至少有一个是写：两个线程都只读 x，则二者读到同样的值（事情已经过去，值不会再变）；一旦至少有一个是写，二者会赛跑，谁跑得快、谁跑得慢会造成一个 non-deterministic 的结果——读跑得快意味着写跑得慢，读就读不到刚被写进去的值。

    * 最小样本：原来 `x = 0`，一个线程写 `x = 1`、另一个线程这时读 `x`，读到 0；若写的一方快那么一点点先把 `x = 1` 落地，读到的就是 1。

    ```text
    交错一:   [ 写 x = 1 ]   [ 读 x ]        -> 读到 1
    交错二:   [ 读 x ]   [ 写 x = 1 ]        -> 读到 0
    ```

    * 写与写的竞争同理：一个线程写 `x = 1`、另一个写 `x = 2`，谁先到谁的值就被别人覆盖——跑得快的那个值反而丢了；程序运行的快慢会影响最终结果。

    * 还有更违反直觉的 weak memory model 行为：一个线程写 `x = 1`、写 `y = 1`，另一个线程读 `y`、读 `x`，结果却读到旧值——明明这两个写里至少有一个已经写过了。

* **它在语言里意味着什么**

    * > **定义**：undefined behavior（未定义行为）不是一个「结果不太好」的等级，而是编译器根本不需要为这个程序规定任何行为——程序的语义已经从根上失效了。

    * 后果：C 语言直接编译到指令，你的进程就在直接执行那些指令；一旦内存 corrupt，可能发生的事情是 PC 跳到地址空间里攻击者写的一段代码上，然后任何代码都可能被执行。

    * C 和 C++ 这么做是为了兼容：兼容任何机器结构、任何系统实现、任何编译优化，于是干脆把 data race 定义成 undefined behavior。

    * 两种语言走了不同的路线：

        | 语言 | 对 data race 的态度 | 后果 |
        | :--- | :--- | :--- |
        | C / C++ | 直接定义为 undefined behavior | 编译器可以假设它不存在；内存可被破坏，任意代码可能执行 |
        | Java | 试图定义 race 下可能的行为，给出最小保底 | 不保证一定读到某个值，但不会退化成能炸掉整个系统的 UB |

    * > **结论**：undefined behavior 非常危险，基本上就是——你用就是你错。

* **真正常见的坑**

    * 最常见的错误不是「完全不上锁」，而是**上错了锁**：一个线程里 `lock(A)`、另一个线程里 `lock(B)`，看起来互斥了其实根本没有——这两个 `sum++` 之间照样可能发生 data race（`sum++` 同时有 read-write 和 write-write 两种竞争）。

    ```c
    /* 线程 1 */                /* 线程 2 */
    lock(A);                    lock(B);
    sum++;                      sum++;
    unlock(A);                  unlock(B);

    /* 两把不同的锁，看起来像互斥，其实什么也没锁住 */
    ```

    * 另一种是**在比较罕见的路径上忘了上这把锁**：比如异步事件处理的某条分支，你忘了那段代码还会并发执行，一忘上锁 data race 就形成了。

    * 内存访问的形态：访问一个节点不仅要有它本身的锁，还必须持有它 previous 和 next 的锁，否则任何结构性修改都是错的。

    * 这些概念只有自己被死锁、被数据竞争坑过才知道它的样子；「原来在那种犄角旮旯的地方真的藏着一些 `sum++`」。

* **内存可以是地址空间里的任何一个指针**

    * 一个 data race 里的「内存」可以是全局变量、从堆区分配出来的新内存、一块早就被 free 掉的内存，还可以是一块栈上的内存——**栈上也有可能发生 data race**。

    * 「内存访问」也不仅是自己写的共享数据结构：它完全可能发生在别人写的代码里、可能发生在库函数里；你写的代码和别人的代码发生 race，甚至可能只是一条 `return` 指令。

    * 实例：实现一个要在多处理器上正确的操作系统内核，一旦允许把一个进程（或线程 T1、T2）从一个 CPU 移到另一个 CPU 就怎么都做不对，会发生非常神秘的重启。原因是 x86 在中断返回时会**借用这个线程的栈**——`iret` 会从栈上把 PC 之类的东西 pop 出来；在它执行完之前，这个线程的数据结构其实已经被挪到 CPU2，CPU2 上的这个线程已经开始执行、可以开始用这个栈了，于是形成栈与栈之间的 data race。

    ```text
    CPU1（正在离开这个线程）                 CPU2（接收了这个线程）
    -------------------------------------|--------------------------------
      ... iret 正准备从 T1 的栈上 pop PC   |
                                           |  框架代码把 T1 的数据结构挂到 CPU2
                                           |  T1 在 CPU2 上被调度，开始执行
      ... iret 仍在读这个栈                |  T1 也开始用同一个栈
                                           |
      两个 CPU 同时在使用同一块栈内存 -> 栈与栈的 data race
    ```

    * 修复需要一个同步：等 `iret` 执行完了以后，T1 才能在另外一个 CPU 上起得来；但这件事办不到——在 `iret` 之前你不能持有任何锁，不可能「把这条指令完成的动作」和「释放一把锁」变成同一件原子的事。

* **读-复制-更新（read-copy-update，RCU）**

    * > **定义**：在解决上述困境过程中发明的一种同步方法——等到当前这个 CPU 上完成了一次完整的线程调度以后，被迁移的线程才能被调度到另外一个 CPU 上起得来。

    * 它是一个在 Linux 内核里现在到处都有的机制；内核大概花了可能有十年时间把很多锁迁移到这种「几乎在读的时候可以不上锁」的机制上。

    * 它给出的教训是：不要把简单的定义想得太简单——不管是死锁的四个必要条件，还是 data race 这样的定义，实际中有无数的坑。

* **数据竞争的检查为什么更难**

    * 写 data race 的检查程序比写 lockdep 复杂，因为 lockdep 只需要看锁，而 data race 不一样——`lock A`、`sum++`，这个 `sum++` 本身就是一次内存访问。

### 检查与使用之间的窗口

* **原子性违背（atomicity violation）**

    * 先用 `if` 判断一个条件是不是满足、条件满足了才动手，就像一个极其常见的模式：如果我的余额大于要扣掉的那笔钱，我就把这笔钱扣掉；如果我的指针不是空，我就往这个指针里写东西。

    ```text
    我(调用方):   check: if (余额 >= 扣款额)  -> 通过
                  ... 中间那段时间窗口 ...
    我(调用方):   use:   余额 -= 扣款额

    窗口期内发生的事: 别人把这笔钱/这个资源动了或释放掉了，你这个就是一次 crash
    ```

    * 判断和使用之间那条时间缝，就是所有 atomicity violation 的入场券。

    * 条件变量之所以是经典好用的同步机制，正是因为它能保证 condition 成立——用 `while not condition` 那个循环时 condition 是可以成立的；而写 `if` 时你心里想的是「这里应该 assert 这个 condition」，若没有正确实现互斥、没有上好锁，这个 assert 很有可能不成立。

* **检查时刻到使用时刻（time-of-check to time-of-use，TOCTTOU）**

    * > **定义**：你「检查」和「使用」中间存在时间差，因此在检查通过之后、真正使用之前，被检查的对象可能已经被换掉。

    * 实例是 Unix/Linux 里的 `sendmail`（用来读邮件）：命令行邮件客户端先看一眼用户的 mailbox 是不是符号链接；如果不是符号链接，就说明它确实是属于该用户的 mailbox 文件，于是把一封邮件 append 进去。

    * 攻击者只有 `/home/abc` 与 mailbox 的访问权限，于是不停地先让 mailbox 变成正常文件、再把它做成指向 `/etc/passwd` 的符号链接。往 `/etc/passwd` append 一行可能意味着往系统里添加一个新用户，而这个用户可能属于权限很高的组，系统就被攻破。

    ```text
    攻击者（普通用户）                 sendmail（root）
    ---------------------------------|------------------------------------
                                     check: mailbox 不是符号链接 -> 可以写
    把 mailbox 换成指向
    /etc/passwd 的符号链接
                                     use:   open 并 append 这封"邮件"
                                     -> 一行内容被追加进 /etc/passwd
    ```

    * > **易错点**：这不是「两个线程抢一块共享内存」那种线程级 race，而是**资源级**的：操作系统里有一个对象，我访问这个对象时产生了 ABA／atomicity violation；我想要的本来是那一小段原子性，原子性被破坏，它就成了一个并发 bug。

    * 理论上**无法用 system call 防住**：可用的 system call 里没有一个能支持「原子地检查这个文件是不是符号链接，再把它打开」。只能通过修改程序架构解决，例如不在 root 权限下运行它。

### 生存期与投机执行

* **释放后使用（use-after-free）**

    * 把一个指针交给别的线程，然后别的线程或整个系统认为这个指针再也不会被访问、把它安全地 free 掉；之后再去读一块已经 free 的内存就是 use-after-free，非常危险——可能读到不属于你的数据，可能造成隐私泄露，内核里有很多这样的严重安全漏洞。

    * 如果 free 的时候同时把指针清掉（改成 NULL），程序也可能直接发生一个 crash。

* **并发式 use-after-free**

    * 需要一个同步：free 要等到所有可能的 user 都结束，相当于有一个 join，然后才能 free。可以用信号量实现——知道一共有三个线程有可能会去 use，就必须 P 三次那个信号量；相当于桌子上有三个玩具，必须把三个玩具都收回来才能动手，而每一个线程在再也不会访问它之后会把一个玩具放到桌上。

    * 放玩具的时机不对就会构成 concurrent use-after-free：在放完玩具之后**还去访问它**。

* **投机执行与 GhostRace**

    * 一个「程序里没有 use-after-free」的场景也会出问题：处理器会**投机执行**（speculative execution）。

    * 自旋锁的典型实现是拿不到就 go to retry：

    ```c
    /* 自旋锁的典型实现：拿不到就 go to retry */
    while (atomic_exchange(&lk, 1) != 0) {
        /* retry */
    }
    /* 拿到锁，进入临界区 */
    ...
    lk = 0;   /* unlock */
    ```

    * 顺序执行的逻辑上完全没问题：因为要先 `unlock` 那个 retry 才会终止，然后才会执行后面的代码；所以这次读 `ptr` 一定是 happen after 那个 unlock 的，那段代码一定不会被执行。

    * 但 CPU 有一个 `if` 条件在还不知道真假时可能把两个分支都执行了，只是把预测错误的那部分抹掉（可以弥补分支预测的延时，指令都已经 load 进来、也都执行了）。

    ```text
    顺序语义:  lock 成功 -> 进入临界区 -> unlock -> 读 ptr(NULL) -> 不 dereference
    实际硬件:  lock 失败 -> retry 分支被投机执行，此时 ptr 仍指向旧对象
               -> 投机地 dereference -> 留下 cache footprint
               -> 通过访问时间等 side channel 把指针泄露出去
    ```

    * 投机执行的指令会留下 cache footprint 这样的痕迹，成为 side channel（测信道），别人可以通过访问时间等把里面那个 pointer 偷出来，因为那条路径上有 dereference。

    * 在投机执行的那一瞬间，互斥锁其实是不在的、是获取不到的；但获取不到时 CPU 去投机执行这一条路径，这个 pointer 就是在的。

### 规模与应对

* **实证研究的结论**

    * 早期研究工作（ASPLOS '08）做了一次实证研究，考察了当时由顶级程序员维护的项目（如 MySQL、Apache、Mozilla 的 Firefox），结果是这些项目里依然有 105 个真实的、系统里的并发 bug。

    * 结论是：像 ABA 这样的问题，现实中的程序员还是会写出来的。

    * atomicity violation 这一类例子其实就是一个 data race，而且是一个极其常见的模式——跟支付宝的做法一样。

* **把执行摊平到时间轴**

    * 理论上任何一个程序的执行都可以做一个加强版的 lockdep、或者加强版的 ThreadSanitizer：因为本质上程序的执行就是指令，可以把指令的执行对齐到时间轴上，每一次函数调用（哪怕中间有线程）都能这样对齐。

    ```text
    时间轴 ---------------------------------------------------->

    线程1:  [ do_sum ]  [ lock ]  ...(blocked 等待)...  [ do_sum ]  [ unlock ]
    线程2:               [ lock ]  [ do_sum ]  [ unlock ]
    ```

    * 一旦执行被摊平成时间轴，谁在等谁、哪一步越了界，就不再是黑盒。

* **程序是人的投影**

    * 可以把每一个程序都想象成一个人：人做的每一件事都有动机、有解释；程序更是如此，**因为程序是人写的**——程序是物理世界里面发生的事情在信息世界的投影。

    * 让程序一边执行一边输出日志、在解释自己发生了什么，这个日志就变得可以**审计**；也可以让另外一个模型来监工，检查有没有发生 order violation。

    * 例：TOCTTOU 本质上要解决的问题是「不能往符号链接里面写数据」；内核里那个函数一边执行就知道「我打开了一个符号链接」，如果这时候外面站了一个大语言模型，它完全可以看出来这是一个不安全的、不正常的访问，就应该把它拦截下来。

* **形式语义与非形式语义**

    * 程序有 formal semantics：每一个指令、每一个语句、每一个函数的执行都是 well-defined 的；正是这种 well-defined 和 determinism，才给了我们控制计算机的绝对控制力。

    * 我们也可以给每一个函数一份 informal semantics：让它报告它做了什么，再把这些报告串联起来，就知道这个程序到底做了什么——这可以帮 AI 更有效地 debug 与审计。

* **为什么并发 Bug 永远与人类相伴**

    * 人类的整个训练过程（预训练、后训练、微调）都是在物理世界里完成的，而物理世界有一条基本规律：脑子在脑壳里飞不出来，我们能感知的只有自己的手脚和眼睛看到的东西——所以人天生就是 shared memory 里视角非常小的一个东西。

    * 这也是为什么学编程一开始教的就是顺序执行——编程语言本身是一个顺序执行的模型，因为它实在太自然了；一旦从顺序程序变到并发程序，就很容易产生关于程序执行的种种幻觉。

    * > **结论**：要理解一个并发程序所有的行为是 NP-hard 的——你必须枚举指数多个东西，才能知道它真正的行为是什么。
