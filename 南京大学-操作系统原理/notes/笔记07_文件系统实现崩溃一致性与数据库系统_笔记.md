# 文件系统实现、崩溃一致性与数据库系统

## 文件系统抽象

### 块设备与虚拟磁盘

* **块设备（block device）**
    * > **定义**：把存储介质抽象成按块访问的字节数组的设备，对外只有读一块、写一块，外加一个等待在途写落盘的口子。

    * 为了省空间与省电路，一般把比较多的 bit 打包成一块，常见 512 字节或 4 KB；一次 `read` 或 `write` 就是一整块，剩下的复杂性不用调用者操心。

    * 设备通过总线接入计算机系统，操作系统里有一份驱动，进程便可 read block、write block。

    * `lsblk` 会列出整盘与各分区，每个分区本身也是一个块设备；分区多大这类信息写在设备最前面的 metadata 里。

    * 块设备可以 `mmap` 到进程地址空间，映射完就能直接当内存访问。

* **为什么不让进程直接访问块设备**
    * 多个进程共享同一个数据结构非常麻烦：就像要在进程间共享一份堆那样，访问的时候就会冲突。

    * 于是在设备之上再加一层抽象把存储设备管起来，这一层就是文件系统。

* **虚拟磁盘与文件（file）**
    * > **定义**：内存一侧的抽象阶梯是「物理内存 → MMU 与页表 → 平坦虚拟地址空间 → `malloc`/`free` → 各种数据结构」；存储一侧与之对应，块设备到虚拟磁盘这一步的产物就是文件。

    * 内存模型可以理解成 byte array（两张 8G 内存条插上就是 0 到 16G 的物理地址空间），但挂在总线上传输时一般是 burst 传输，本质上也有一点像块设备。

    * 现实世界里的文件是「文字符号固定于纸张等载体上的信息记录」，在计算机世界里自然表示成一个字节序列。

    * 文件与脚下的磁盘最关键的差别是变长：磁盘买来多大就是多大，文件可以从几 KB 到一部电影那么大，还可以改它中间的值。

    * 文件通过文件描述符访问，支持 `read`、`write`、`lseek`、`ftruncate` 这组系统调用；`hello.c` 与 `a.out` 用的是同一组 API。

| 层次 | 内存世界 | 存储世界 |
| :--- | :--- | :--- |
| 物理介质 | 主板上的 DRAM 颗粒、内存条 | HDD / SSD / TF 卡这类块设备 |
| 访问特性 | 是 byte array，但总线上按 burst 连续传送 | 一次读或写一整个块，512 B 或 4 KB |
| 中间的硬件 | MMU 与页表 | 设备驱动 |
| 虚拟化的结果 | 每个进程一份平坦的虚拟地址空间 | 每个文件一份「虚拟磁盘」 |
| 之上的容器 | `malloc` / `free` | 文件系统（目录树） |
| 再之上 | list / set / dict 等数据结构 | 放进去的任何信息 |

### 目录树与隐藏文件

* **目录树（directory tree）**
    * > **定义**：用层次化的名字索引管理大量文件的数据结构，参照图书馆的分类法——信息有局部性，相关的东西放在一起，于是形成层次性的索引结构。

    * 进程用的命名机制是 PID，但它只是一个数字，对程序还行、对人极不友好：你看到的是几百万几十万的一个随机数字，根本不知道它是什么意思。

    * 如果文件系统里所有文件都只给一个编号，理论上也能跑起来，但以后所有 `open` 的第一个参数就不再是 `a.txt` 这样的路径，而是一个 `176358`，对人是没法用的。

    * 目录树里任何目录都能看到 `.` 与 `..`：`.` 指向当前目录自身，`..` 指向上一级。

    * 因此准确的模型是：上级目录里有一条以名字为 label 的边指向该目录，而该目录内部又有 `.` 指回自己、`..` 指回上级。

* **隐藏文件**
    * > **定义**：Unix 约定，所有以 `.` 开头的文件都是隐藏文件；这只是名字约定加上工具侧的一行过滤，操作系统并不真正区分隐藏与不隐藏。

    * `ls` 默认看不到 `.`、`..` 和任何以点开头的条目，只有 `ls -a` 才列出来。

    * 实现极其粗暴：用 `readdir` 遍历目录，每读出一个条目就判断 `d_name[0]` 是不是 `.`，是的话再看有没有 `-a` 选项，没有就 `continue`。

    * 这个设计把「引用自己和上级」与「隐藏」两件事合并在一起，顺便让 `.`、`..` 也能被隐藏掉。

    * > **提示**：Windows 的隐藏是给文件加属性的操作（右键属性勾选隐藏），Unix 则是 quick and dirty——操作系统根本不管，只是知道 `.` 和 `..` 是当前目录和上一级目录，剩下要隐藏的自己加个点，由 `ls` 过滤掉。

    ```c
    /* 示意：BusyBox ls 中隐藏文件的判定逻辑 */
    if (entry->d_name[0] == '.') {
        if (!(opt & OPT_A))   /* 没有 -a 就跳过 */
            continue;
    }
    ```

### mount 与回环设备

* **mount**
    * > **定义**：把一个块设备上的整棵目录树完整贴到文件系统某一个位置的操作。

    * 贴过来以后就能正常访问：贴到某个目录下面，你就能在这个路径下读文件；你对文件的写入也会真实反映到那个设备上。

    * 在系统调用层面 `mount` 要求一个块设备，而且必须由调用者告诉它是什么文件系统——操作系统不负责探测，认为不合法就会直接拒绝这次 `mount`。

    * 只读介质会被以 `write-protected, mounting read-only` 的方式只读挂载。

    * 设备除读写以外的所有控制类 API 全部塞进 `ioctl`：一次失败的 `mount` 的 `strace` 会看到先 `ioctl` 确定它是块设备、再 `ioctl` 确定大小、再 `ioctl` 查驱动器状态，然后用不了就 `close`。

    * 弹出光盘的 `eject` 也是这个套路：`open("/dev/sr0", ...)` 加一句 `ioctl(fd, CDROMEJECT)`，所以操作系统里其实看不到任何魔法。

* **回环设备（loopback device）**
    * > **定义**：一个表现出块设备的样子、但所有对块设备的读写都委托给某个文件的读写（调用该文件的 `file_operations`）的对象，用来绕开「`mount` 必须要求块设备」这条约束。

    * 因此 `mount` 也可以挂载一个文件，这就是从文件镜像里捞出图片那类实验的基础。

    * 流程：① 以只读方式打开镜像文件并探测它是什么文件系统（探测发生在应用侧）；② 以读写方式打开 `/dev/loop-control`；③ `ioctl(LOOP_CTL_GET_FREE)` 取空闲编号，第一次拿到 0，再要就是 1、2、3、4…，失败返回 -1，所以可以建很多个；④ 把镜像文件绑定进来，再执行一次真正的 `mount`。

    * 挂载完成后 `lsblk` 里会多出一个 `loop0`；装了 snap 之类包管理的系统同样能看到很多 loop device。

    * > **提示**：创建 loopback device 这个对象本身就是一个 `ioctl` 调用——「操作系统会创建一个回环设备」这句话到底意味着什么，写在 `strace` 里。

### 目录树的起点与共同语言

* **FHS（Filesystem Hierarchy Standard）**
    * > **定义**：规定 `/usr`、`/home`、`/mnt` 等目录含义的 Linux 标准，相当于图书馆里那套分类编号规定，是大家的共同语言。

    * 里面具体放什么由你自己决定，但整个文件系统的根最好长成这样；标准本身显得有点过时，尤其是设备越来越多的时候，但遵循它会有比较统一、安心的体验。

    * macOS 的内核实际上也是 Unix，却并不遵循 Linux 的 FHS。

* **根目录是怎么来的**
    * 内核启动时先有 initramfs——内存里的最小根，里面可能只有一个自己写的程序和 `/dev/console`，不认识任何文件系统。

    * 它找到一个启动设备后把该设备的根 `mount` 上来，再执行 `pivot_root` 这个系统调用（或 `switch_root` 命令），把真实根搬到 `/` 并丢掉 initramfs。

* **目录树的增删改查**
    * 创建目录、删除目录、遍历目录都是系统调用，例如 `mkdirat(AT_FDCWD, "1", 0777)` 就是在当前目录下创建目录 `1`，返回 0 表示成功。

    * 通配符（globbing）是 shell 的功能而不是系统调用：`strace echo /etc/*/*` 看不到任何展开过程，因为 bash 早就在交出命令前把 pattern 展开成一串具体路径贴了进去。

    * 想看清 globbing 用了哪些系统调用，得把它包进 `bash -c`，这时会看到大量 `openat` 与 `getdents64`；`getdents64` 就是 `readdir` 背后的系统调用。

    * 所有基于文件系统的工具都是同一原理：fuzzy finder 之所以能让交互式选中的文件被打开，背后仍然是那一套增删改查。

* **Windows 的另一套名字体系**
    * Windows 有一个所有操作系统对象的根 `\`，写着 `\Device\HarddiskVolume1`、`\Driver\NTFS` 这样的对象，但你在命令行 `cd \` 进不去，得到的是当前盘符的根目录。

    * `\\` 是网络入口，`\\server` 下的 `share` 会被转义成 `\Device\LanmanRedirector` 下的 `server` 下的 `share`；用 `CreateFile` 这类 API 可以打开这样的设备文件，拿到一个可以理解成文件描述符的 handle。

    * `\??\` 是 per-user 命名空间，两个不同用户可以各自有一个 `\\server\share`，同一个路径可以解析成两个不同的东西。

    * 系统盘是 C 盘，是因为 A、B 两个盘符已经分给了软盘驱动器；你看到的 C 盘只是 Windows 让你看到的，从对象根看它是 `\??\` 下的 C 盘。

## 链接与文件属性

### 硬链接与删除

* **硬链接（hard link）**
    * > **定义**：同一个 inode 的另一个名字——文件本身就是「一个带名字的指针」，所以就可以有两个普通文件名指向同一个对象。

    * `ln a.txt b.txt` 背后是 `link` / `linkat` 系统调用；改 `a.txt` 的内容，两个名字的大小一起变，`cat b.txt` 也是新内容。

    * 用 `ls -li` 看，两个名字后面跟着的编号完全相同，说明它们就是同一个文件；另建的 `c.txt` 编号就换了，是另一个数。

    * 用途直接：同一个运行时库可能存在多个版本（一堆 libc 版本并存，另外还需要一个「当前」的 libc），链接一份立省 100% 的空间。

    * 两个明确限制：不能指向目录（`.` 和 `..` 是例外），不能跨文件系统（它是文件系统内部的实现机制）。

    * > **易错点**：不允许给目录做硬链接是因为很容易成环。一旦成环，环里每个对象都被别的对象指着，引用计数永远不为 0；可这个环已经从整个目录树上 detach 下来，你再也不可能通过任何路径走到它——理论上它该被回收，但引用计数做不到。

* **inode 号**
    * > **定义**：文件的编号，在某个文件系统内部唯一，`ls -i` 打印出来的那一列就是它。

    * 进程有 PID，文件也有属于自己的编号；在 `/tmp` 这类临时文件系统（tmpfs）里编号很小，因为随手创建随手销毁，编号从小的开始发，而新下载的文件编号能到 264095 这样的量级，看得出接近顺序分配。

* **unlink**
    * > **定义**：删除文件实际使用的系统调用——它把「名字 → 对象」这条链接指针拿掉，然后把引用计数减一。

    * 你敲的命令看起来是 `rm c.txt`，实际发生的是一次 `unlink`（或 `unlinkat`）。

    * 只要还有别的名字指着它，这个文件的数据就不能回收；只有当引用计数减到 0，也就是没有任何人指向它了，文件系统才真正把这个对象回收掉。

### 符号链接

* **符号链接（symbolic link）**
    * > **定义**：本身就是一个文件，可以理解成一个文本文件，里面存了一段话：去哪里找；它不指向 inode，它指向一个路径。

    * 操作系统处理路径时一旦碰到符号链接，就会自动把这个字符串拼到你的路径上，然后继续往后解析，所以内容里写什么都行，写 `../t/a.txt` 也行。

    * 演示的要点：`ln -s a.txt symlink` 后 `ls -l` 显示 `symlink -> a.txt`；`rm a.txt` 执行的是 `unlink`，引用计数减一，但符号链接对象本身还在、内容还是那句话，此时 `cat symlink` 会因路径解析失败而报错；把 `a.txt` 拷回来它立刻又能用。

    * 它没有任何限制：可以指目录，可以指自己，甚至可以指来指去形成一个环。

    * > **提示**：`ls -l` 里能一眼看出 `l` 类型的符号链接，但硬链接是看不出来的——在这个模型里，每一个普通文件本来就是一个 link，硬链接并不比别的文件更特别。

| | 硬链接 | 符号链接 |
| :--- | :--- | :--- |
| 本质 | 同一个 inode 的另一个名字 | 一个内容为路径字符串的文件 |
| 能否指向目录 | 不能（`.` 和 `..` 除外） | 能 |
| 能否跨文件系统 | 不能 | 能 |
| 原文件被删掉之后 | 计数减一，数据仍在 | 链接对象仍在，但解析失败 |
| 能否成环 | 不能 | 能 |

* **用符号链接伪造目录结构**
    * 文字冒险的例子：状态机脚本里每个状态变成一个目录，目录里每个选项是一个符号链接，指向下一个状态的目录；`状态机` 这个符号链接指向上一级。

    * `cd 2` 之所以能当「选 2」用，是因为路径解析会替换掉这一跳；`cd ..` 就是时光回溯，连按几次 `cd ../../../` 就回到第一幕。

    * 一路 `cd` 进去之后 `pwd` 里会记着你走过的全部历史，因为你就是一级一级 `cd` 进来的；走到某个状态时路径看着还是那个路径，但目录里已经没有文件了，它就是结局。

    * > **注意**：这套东西没有任何神秘的运行时，它就是一个 bash 加上一堆目录和符号链接。

* **nix 包管理器**
    * > **定义**：一个 functional 的包管理器，只增不减——把所有文件放在 store 下，以文件内容的 hash 指纹加名字命名，再用符号链接把选中的版本拼成一个环境。

    * 与 `apt` 之类正好相反：后者的所有修改都是 in place，你 install 一个新版本就得把旧版本卸掉，中间还要跑一个 post-install 脚本。

    * 「只增不减」的依据是：有 random read 加 append-only 的 write，就可以实现任意的 persistent data structure——想修改一棵二叉树不是去改它，而是创建一个新的根节点、只把这条路径上的东西拷一份，其他指针统统指回原来的节点。

    * 推论很舒服：增加的时候不会对已有的软件产生任何影响，已有的所有环境都还在；nix 里有 listed generations 的概念，一代一代地记着，系统挂了直接回滚到上一个 generation 没有任何代价，因为实际的文件就在那里。

    * 现场拉一个环境是从一个已经装好的东西里把环境拉出来——创建一大堆链接，然后你的世界就有了；而且这个世界随时可以摧毁，因为它不改变 store 的部分。

    * 重要的不是记住创建 symlink 的是哪个系统调用，而是知道什么事情是能做的以及背后的运行机制大概是什么。

### 属性与权限

* **文件属性**
    * `ls -l` 能看到的属性：inode 编号、设备类型（字符设备 `c` / 块设备 `b`）、读写权限位、类型位。

    * 类型位就是第一列那个字母：`d` 是目录，`l` 是符号链接，`p` 是 pipe，`c` 是字符设备，`b` 是块设备。

    * > **易错点**：硬链接在这里看不到——每个文件本来就是一个 link，硬链接就是一个普通文件，你没法从 `ls -l` 上把它认出来；只有符号链接显示为 `l`。

* **权限位（mode）**
    * 权限位分成三组、每组三个 bit：user（文件的所有者）、group（同一个用户组）、other（其他所有人）；`111` 是可读可写可执行，`101` 是可读可执行但没有写权限。

    * 用 root 创建的文件，owner 和 group 都是 root，这两个本身也是文件的属性，所以文件属性一下子变多了。

    * `chmod 777 a.txt` 之后连 other 都能读写执行它；`chmod 000 a.txt` 之后权限被清得干干净净。

    * 权限位直接决定操作系统行为：root 可以绕过这些检查，照样访问所有文件、把可执行位加回去并执行它；普通用户完全不行，不但改不动它的 metadata，连打开都会在 `open` 系统调用上返回 `EACCES`（permission denied）。

* **DOS / FAT 与 Unix 的差别**
    * 更早的 DOS、FAT 文件系统里根本没有 user、group、permission 的概念，文件就那么几种属性。

    * 把 U 盘格式化成 FAT 插到任何设备上，任何人都可以读它写它；软盘是更典型的例子——文件系统里没有权限，就谈不上保护。

    * 是 Unix 引入了这样的权限，于是这些 metadata、这些属性就被加到了文件上，并从 Unix 一路演化增长。

### 扩展属性与访问控制列表

* **扩展属性（extended attribute，xattr）**
    * > **定义**：为每一个文件维护的一组 key-value，可以想成挂在文件上的一个小 JSON。

    * 可以放任意你想加的 key，比如 `user.author`、`user.description`、`user.version`；文件的真实 type 是什么、想给这个文件加一个 icon，都可以。

    * 典型用途：macOS 里一个下载到一半的文件，图标上会显示「下载了多少」那种小图示，这东西就存在扩展属性里；下载完之后的签名之类也可以存在里面。

    * 它对拷贝不友好：Linux 的 `cp` 可以 preserve xattr，但你的 `cp` 未必支持这个特性（比如 toybox 的 `cp` 可能就不支持），所以要先把帮助打出来、读一下文档，再用一个保留扩展属性的写法；`tar --xattrs` 同理也能保留。

    * 致命缺陷是知道的人太少：不是所有文件系统都支持它，把一个带扩展属性的文件拷到 FAT 上时，这东西就悄悄地消失了——操作系统和拷贝工具都不想每次都打断你的流程、问你一句「要丢了，你确认吗」，只能 silently 丢掉。

    * 后果是一来一回拷两趟文件就变了：看起来只是拷到 U 盘、拿到另一台电脑上编辑了一下、再拷回来，元数据却丢掉了。

* **访问控制列表（Access Control List，ACL）**
    * > **定义**：比 user / group / other 三档读写执行更细粒度的访问控制，能做「让所有用户都能访问一个文件，除了某一个用户」这类需求。

    * 这种事用用户和组来做就比较麻烦，你得专门创建一个组。

    * root 是绝对的，0 号用户拥有绝对的权限，并且会 bypass 掉这些检查：如果 root 都不能访问、不能删除某个文件，那就可以把整个系统的存储空间占满，而即便有最高权限的人也删不掉它，这显然不对。

    * 把一个属于某人的文件对该 owner 自己的访问 deny 掉，同样是一种不应该被允许的操作。

* **文件的 personality（还没被实现的 policy）**
    * 加这些属性的真正目的是希望文件——或者说这些虚拟磁盘、这些存储数据的对象——有一些自己的 personality。

    * 把「学习资料」这个目录设置成隐藏时，你真正想要的不是 `ls` 不显示，而是只有自己用这台电脑的时候能看见它，旁边只要有别人它就得藏起来。

    * 现在的文件系统是一个既要给人用也要给机器用的抽象层，它觉得判定「有没有人正在你电脑旁边」这种执行条件太复杂，所以只支持「这个文件是隐藏的」这样一个简单、由程序实现的语义。

## 文件系统监控

### 轮询与 inotify

* **用 stat 和 diff 硬拼一个监控**
    * 流程：立刻拿到当前所有文件的修改时间，睡两秒钟，把某个文件改掉，再 `stat` 一次，然后 `diff` 两边——有变化就说明变了，不改只睡觉 `diff` 就什么都不返回。

    * 可以用尖括号（进程替换）把一条命令伪装成一个文件，喂给像 `diff` 这样需要两个文件输入的命令；`stat` 输出 `mode`、modification time 这些属性，后面跟一个通配符就能遍历出目录下所有文件的信息。

    * > **提示**：这个办法的代价在文件数量上。目录里有几百万个文件时，每次遍历就是几百万次文件元数据查询；即便热数据会被放进内核缓存里，你仍然会觉得不该用这么暴力的方式去查。

* **inotify**
    * > **定义**：由内核在文件系统改变时投递事件的机制，把「一遍一遍把整个文件系统的时间查一遍」换成「收到事件直接处理」。

    * 关键系统调用是 `inotify_init` 和 `inotify_add_watch`，用完之后还可以 `inotify_rm_watch`。

    * `inotify_init` 返回一个文件描述符；Linux 里所有东西都是用文件描述符实现的，这意味着你可以用 `epoll`、`select` 去监听它，也可以同时持有好多个 inotify 的文件描述符，只要任何一个有更新你都能知道。

    * > **注意**：inotify 是不递归的，想覆盖一整棵目录树，得自己逐层登记。

    * 使用场景一抓一大把：文件管理器的自动刷新（别人 ssh 到你的机器、在一个终端里 `touch` 一个文件，你打开的 desktop 目录也应该正确反映变化）、编辑器的自动重载（VS Code 也用这个特性）、systemd 监控 unit 文件的变化、`tail -f` 等待文件被写入。

* **目录的修改时间只影响直接父目录**
    * `touch a.txt` 之后收到的事件序列是：`a.txt` 被 created、它所在的目录被 modified、随后是 open / modify / close。

    * 也就是创建文件的时候，它的目录本身也会跟着 modified；你改一个文件的 modification time，它上一级目录的 modification time 也会改。

    * > **易错点**：不会逐级向上传递。在 `t/1/2` 这样的结构里 `touch a.txt`，只有直接容纳这个文件的 `t/1/2` 会变，`t/1` 不会跟着变——目录的修改时间记录的是「这个目录里有什么发生了变化」，而不是「这棵子树里有什么发生了变化」。

### 从 strace 到 eBPF

* **trace 家族**
    * 有东西搞不懂它怎么工作的时候就去 trace 它：`strace` 把应用程序打开，就知道这个功能到底是用什么系统调用实现的；`ltrace` 告诉你它调用了哪些 library call。

    * inotify 告诉你什么时候调用了文件系统的那个 system call，可以理解成一种只 trace `open`、`close`、`modify` 的全局 `strace`。

    * 本质是 everything is a state machine：操作系统也是代码，代码执行时会有函数调用、会有结构体的修改，所以理论上说也能拿到操作系统里任何东西改变的事件。

* **eBPF（Extended Berkeley Packet Filter）**
    * > **定义**：允许你把自己写的一小段代码注入内核、在一些 hook point 上运行的机制；它最初源于防火墙的需求——把来自某个 IP 段的所有请求扔掉，若等包到了用户空间再执行代码再返回内核，context switch 开销太大。

    * 它也是一个虚拟机，最终编译成本地体系结构的机器码来执行；是一个 RISC-like 的指令集，有 11 个寄存器，`R0` 是返回值，在每一个 probe 的入口 `R1` 都指向一个 context 结构体，里面包含函数参数、function name 这些东西。

    * 有一条非常特殊的指令 `bpf_call_helper`，用来调用内核给你实现好的函数，比如 `bpf_get_current_pid_tgid` 可以询问当前的 PID、TGID，还可以做 buffer 的、BPF map 的 lookup element。

    * 因为它能改内核内存会很危险，所以有非常严格的验证器，只允许 bounded execution：不能有 unbounded 循环，有的话直接拒绝；这导致你没有办法在 BPF 里面实现自己的数据结构，想统计某个函数调用了多少次就必须借用它的 map 机制，那相当于它给你预实现好的数据结构。

    * 完整流程是：写一段 C 代码 → 编译成 eBPF 字节码 → 调用 BPF system call 把代码注入内核 → 内核中的 verifier 静态检查（代码只读、不允许 unbounded 循环）→ 优化的编译器编译成目标指令集上的指令 → 变成 hook，勾住一些关键的 hook point。

    * 内核里暴露了各种各样的 tracepoint，可以让 AI 帮你把全部列出来；追踪内核 block I/O 生命周期的那个程序就是一个 tracepoint，挂在 block request 的 insert 上，直接打印，打印相当于打印到一个 buffer 里，最终用户态可以看到。

    * > **易错点**：这种东西也是有 bug 的，我们在生产环境里遇见过——写了一个 eBPF 的 probe，里面有一个 `printf`，在它前面加了一个循环，然后那个 `printf` 就不执行了；根据语义你可以 100% 确信它要执行，但优化的编译器认为那是死代码，把它 optimize out 掉了。

    * 它能干的事很天马行空：用几百行 eBPF 的程序捕获所有键盘的按键和鼠标的移动，再结合 `execve` 这类关键系统调用的 trace，就能基本完整地复原出你在这台 Linux 电脑上干过的所有事情。

    * 也可以拿它做学习辅助：把每一个带时间戳的按键 trace 从内核里拉出来，结合编辑器 buffer 随时间演化的快照，去问大语言模型「我做这件事的时候是不是可以做得更好」，它会不断告诉你这个编辑应该这样做、那个编辑应该那样做。

| 方案 | 机制 | 代价 | 什么时候合适 |
| :--- | :--- | :--- | :--- |
| 轮询 + `diff` | 定期 `stat` 全部文件并比较结果 | 每次都要全量遍历文件元数据，文件一多就不可接受 | 文件很少，或者只是临时脚本 |
| inotify | 在内核登记 watch，事件到达时监听的那个文件描述符就可读 | 不递归，得多层目录逐个登记 | 目录级监控的常规解法 |
| fanotify | 可以监控整个文件系统，而无需逐个添加目录 | 长文未说明 | 需要覆盖整个文件系统时 |
| eBPF | 在内核的 hook point 上跑自己写的代码 | 要写 C、编译成字节码、过 verifier | 通用的内核行为追踪 |

## 快照与 Git

### 路径复制与快照

* **持久化数据结构（persistent data structure）**
    * > **定义**：有 random read 加 append-only write 就能实现的、把所有历史版本都保留下来的数据结构。

    * 在一棵二叉树上插入节点：把从根到那个节点的整条路径都拷贝一份形成新版本，只有发生改变的节点需要拷贝，没变的子树因为是指针指过来的直接复用。

    * 这样旧版本和新版本就都保存下来了，所有的历史版本也都保存下来了；在这类结构上创建快照只是把这个指针给一个名字记下来，几乎不是困难的事。

* **数据结构上的全局操作技巧**
    * 维护一个集合（比如 3、5、10）时，如果数据结构上还允许全局操作——比如对所有元素都加 10——就有两种实现：一种是老老实实遍历一遍变成 13、15、20；另一种是把「加 10」这个动作悄悄地写到数据结构的边上。

    * 后者的关键是：取一个元素 5 时加上那个 10 再返回 15；这时候如果要插入 9，不能去动那个永远带着的 +10，而应该插入一个 `-1`，所有元素都永远带着 +10，取出来正好就是 9。

### Git 的对象模型

* **Git**
    * > **定义**：依托文件系统实现的持久化数据结构，管理的是很多棵目录树的快照；所有东西都在文件系统里，都是文件，删掉 `.git` 就相当于所有历史也都没有了。

    * 三大对象都存储在 objects 下面：blob 就是文件的内容（不管写的是 C++ 还是别的什么，都以压缩的方式直接存进去）；tree 就是这样的文件系统的树（例如 `100644` 开头，那是文件的 mode，即是否可执行，后面是这个数据结构的二进制描述）；commit 也是一段文本，里面有 commit message、author 信息、时间戳，还有 tree 和 parent。

    * 每一个 commit 都有一个 tree object、一个 parent object；看到 tree 的那个哈希，就能在 objects 里找到对应的那个 tree object。

    * 所谓 append-only，就是直接往对象池子里丢一个文件，丢完之后把 tree 和 commit 这样的 object 也丢进去。

    * 剩下的一切都是指针，以文本方式存储：`HEAD` 是一个指针，指向 `refs/heads/master`，而这个文件又指向一个 commit object；你也可以在 `.git` 里创建一个文件叫 `tail`，里面同样放一个指针，然后就能 diff 那两个东西。

    * 一个分支就是一个指针，指向某一个 commit object；你再 commit 的时候这个指针就往后移；`checkout`、`commit` 都是非常平常的文件系统操作。

    * 创建分支时 objects 其实没有变化：只是多出 `refs/heads/new`、`refs/heads/new-new` 这样的文本文件，里面装的是同一个哈希；而如果在该分支上提交，对应的 ref 文件里的哈希就换成了新的。

    * > **提示**：所有的指针都是一个 hash，和你写二叉搜索树时的 `struct node *left`、`*right` 是一模一样的玩意儿——数据结构有不同的节点类型，节点上挂你自己想放进去的 data，仅此而已。

* **stash**
    * > **定义**：stash 其实也是一个 commit object，两个 parent 分别指向 HEAD 与上一个 stash，于是所有 stash 被串成了一个栈。

    * 手头有一些 ongoing 的修改、做到一半还不对、又不想 commit 到分支上时，就可以 `git stash push` 把它们暂存起来，然后看到 stash 列表并不断地往里 push。

    * 因为串成了栈，所以它既能 push 也能 pop。

### 合并的形态

* **merge 与 fast-forward**
    * 最基础的 merge 就是添加一个 E 节点，它有两个 parent：本地那条线和远端那条线，做的是一次三方合并——有一个公共祖先的 tree、一个 B 的 tree、一个 D 的 tree，中间那些提交不管是一万个还是十万个通通被展平。

    * 如果本地压根没有那些提交、远端有，那你直接把它们拉过来就同步了，这个叫 fast-forward；拉东西时看到 fast-forward 的 message，意思就是「我这边什么都没看见，就把你的东西放过来」。

    * 也可以特意要求 no-fast-forward，比如合一个分支时就要求你创建一个新的提交对象来代表它，打开这个新提交看它就有两个 parent 了。

* **cherry-pick 与 rebase**
    * cherry-pick 可以挑选任何提交：本质上是理解成——任何一个提交（比如从 A 到 B 的那个提交）就是一个 diff，A 是一棵树、B 是一棵树，你只要记录 A 和 B 之间的 diff，就可以把这个 diff 抄过来。

    * 它的典型场景是你复制了一份内核很多年，已经不可能整体合并，但某个地方给一段很老的代码打了个安全补丁，这个补丁跟你没有冲突，这时就可以把它拉过来。

    * rebase 做的事情是：先把对方的提交复制过来，然后在那个状态上试图 cherry-pick 从 main 到 A 的 Δ diff 得到一个 A'，再 replay 后续的 Δ 得到 B'，原来的提交就没了。

    * 它给你制造出一个假象：你本地写的是 Δ1 和 Δ2，远端的提交被插到了你的前面——你们本来是并行开发的，但看起来像是别人先做完、你在他那个基础上接着做的，这样你就省掉了那个 merge commit。

    * > **易错点**：rebase 是要慎用的。本地提交和对面没冲突（比如改的是不同文件）时基本没问题，但一旦 cherry-pick 发生冲突，基本上你就该放弃 rebase、老老实实 merge——因为它是逐个 replay delta，你可能 resolve 了这个冲突下一个又冲突了，两条线 diverge 的时间比较长会变得极度痛苦；而且即便 auto-rebase 成功了，它也可能隐藏逻辑上的冲突，你还是得回过头把这个 diff、那个 diff 都 review 一遍。

| 操作 | 是否产生新提交 | 特点 | 风险 |
| :--- | :--- | :--- | :--- |
| merge | 产生一个 E（两个 parent） | 三方合并，历史保留分叉 | 历史里多出 merge commit |
| fast-forward | 不产生 | 直接把 HEAD 移到远端提交 | 没有分叉时才可用 |
| no-fast-forward | 产生一个 merge commit | 强制保留「这里合过」的痕迹 | 长文未说明 |
| cherry-pick | 产生被挑选提交的副本 | 只搬一个 diff，不管历史 | 冲突需逐个解决 |
| rebase | 产生一串重写后的提交 | 把别人的工作插到自己前面 | 冲突连环、可能隐藏逻辑冲突 |

### worktree 与单线程假设

* **单线程假设与 stash hell**
    * Git 是为单线程设计的：它只有一个工作区、一个 HEAD，你在本地工作时是一条线性的 commit，直到需要跟别人同步时才会 merge 一下，大部分时候这个模型工作得很好。

    * 一旦从单线程变成多线程，事情就麻烦了：做到一半的东西不能 commit 只能 stash，做一个上下文切换去别的分支，回来之后可能又要 stash 一次。

    * 而 stash 是一个线性的 stack，它的设计之初就没有让你多线程工作，所以当你一定要多线程工作时就会出现 stash hell；一般有两三个 stash、同时 multitask 两三个事情还能管得过来。

* **worktree**
    * > **定义**：既然所有历史都是留着的、复制一个 persistent data structure 是没有代价的，那就把树直接复制一份出来做独立工作区——因为永远不修改，「复制」就是复制一个指针。

    * 真实仓库的 `.git` 是个目录，里面有 objects 与 `worktrees/<name>/` 下的 HEAD、gitdir 等元数据。

    * worktree 目录下的 `.git` 是一个**文件**而不是目录，可以直接 `cat` 它，内容是一行 `gitdir: /path/to/repo/.git/worktrees/<name>`，说的是「Git 目录实际在这里」。

    * 进去看会看到一堆指针、**没有 object**——它不需要存 object，因为是 persistent data structure，只要有一个 HEAD 指向一个合法的 HEAD、HEAD 再指向一个合法的 commit，这件事就搞定了。

    * `git reflog` 里能找到全部历史；`git reset --hard` 会丢掉没 add 的东西，但其他所有东西因为是 persistent data structure，对象都留在文件系统里；哪怕有一个 commit 变成了没有任何引用的孤儿提交，只要你不做 `git gc`，tree object、blob object 实际上都还在，都能捞回来。

* **Btrfs**
    * > **定义**：在块设备上从零实现持久化数据结构的文件系统，名字里的 B-tree 就是那个每个节点装在一个大块里（块大小 4096 字节）的 B-tree，所以它是一棵非常宽的多叉树，多叉索引结构可以把层数压得非常浅。

    * 它的 volume、文件系统目录树，所有东西都是以 append-only、copy-on-write 的方式做持久的；与 Git 的差别在于 Git 有文件系统抽象、可以直接往对象池里丢文件，而 Btrfs 要在块设备上从零实现。

    * 快照因此是免费的：只要持有一个文件描述符，对它做一次 `ioctl(BTRFS_IOC_SNAP_CREATE)` 就可以创建一个 snapshot，而对持久化的数据结构来说创建快照只是把这个指针给一个名字记下来。

## 联合文件系统与 OverlayFS

### 叠层语义

* **UnionFS / OverlayFS**
    * > **定义**：用一个系统调用把 upper（可写）与 lower（只读）两棵目录树拼成一个虚拟目录 merged，访问时先在 upper 里查、找不到再去 lower 里查、都没有就不存在。

    * 在 Linux 里完成拼接的那个系统调用就是 `mount`；从名字就能看出来，upper 拼在上面、lower 拼在下面，而 merged 是假的、是虚拟的。

    * 叠起来之后，lower 里可以放好多文件、当成一个系统盘，upper 里可以对 lower 做修改，而 lower 本身可以不变；这样你就可以创建好多好多个 merged 目录。

    * 挂载参数的约束：可以挂载不止一个 lower，但只能挂一个 upper，同时还要给它一个临时目录叫 `workdir`，`workdir` 必须是空的，不空它会报错。

    ```text
    mount -t overlay overlay \
        -o lowerdir=./lower \
        -o upperdir=./upper \
        -o workdir=./workdir \
        ./merged
    ```

* **copy-up 与 whiteout**
    * 往 upper 里放一个文件，它在 upper 里是在的，同时对 upper 的修改会反映到 overlay 里；反过来进 overlay 修改它，在 overlay 里的修改同样会反映到 upper 里。

    * 修改一个只存在于 lower 的文件时，overlay 的变了，但 lower 的没有变，同时在 upper 里面多了一个被改过的那一份副本——这就是 copy-up。

    * 删除是最有意思的：lower 里的那个文件永远不变，无论叠多少层都不会变，但在 upper 这一层里会产生一个**字符设备文件**，这个字符设备文件你当然没有办法访问，试着看它会说 `Permission denied`。

    * 这个假装出来的、不存在的文件叫 **whiteout** 文件：你删除，它就在 upper 里创建它；之后 overlay 里 lookup 这个文件就命中 whiteout，于是看起来「找不到」。

    * > **提示**：这就像在 hash table 里删除的时候需要一个 tombstone——底层那一层不动，靠上层造一个标记把名字遮掉。

### 叠层能干什么

* **一个 lower、十六个 upper**
    * 场景是一个刻盘工具，一次性可以把一个目录（比如 600M）写到一张光盘里；电脑上有 16 个光驱就意味着 16 倍的带宽，因为写光盘相对比较慢。

    * 麻烦在于必须在用刻盘工具的同时为每一张光盘写入一个不同的 CDKey，而这些 CDKey 会打印出来贴在光盘上一起卖。

    * 于是 lower 上有 600M 对每张盘都一样的文件，upper 上是一个 1M 每张盘都不同的文件；创建 upper1、upper2… 与同一个 lower 组合，空间就省下来了。

    * > **提示**：刻盘工具的要求是「burn 一个目录和一个驱动器」；如果没有这套机制，想并行就必须把这个目录拷 16 份、再为每一份写入不同的 CDKey，而操作系统在拷贝时也许内部做了优化，但那终究是 16 份。

* **把整个根当成 lower**
    * 把**整个文件系统的根**当成一个 lower，再在另外一个设备上做一个空的 upper 也挂在 `/`，相当于旧的根是 lower、新建的目录在另一块盘上作为 upper。

    * 然后做一次 `apt dist-upgrade`：apt 没什么神奇的，看它的 `strace` 就知道本质上是写文件、写文件系统，而因为这是根，所有写入都会落到 upper 里。

    * 结果就是旧系统还在、从来没有变过；下次重启挂载时把 lower 和 upper 都挂上，如果它成砖了也不要紧——回到 initramfs 那个模式下做一个配置把整个拿掉，你的系统又回来了。

    * 试完觉得没问题，可以直接用一个 `rsync` 把里面的所有数据同步搬回到 lower 那一层，相当于把这些修改 commit 到磁盘上；`overlayroot` 这个工具做成了这件事。

    * 原理在于：你对系统持久状态的所有修改都是反映在文件系统上的（往 `usr/share` 改东西、在 `etc` 下改配置文件、systemd 的很多 triggers），这就是 persistence。

* **网吧、考场与考试管理**
    * 网吧：把系统做在 lower 里、给用户一个 upper，等他下机直接把 upper 删掉就可以了。

    * 大规模考试管理：把考试机器的 `/home` 做成一个 overlay，把实际上的 upper 放在用户访问不到的地方；上午场的同学在上午场那个 upper 里工作，之后直接给它 mount 一个别的 upper，下午场又开始了。

    * 下午场的同学看不到上午的人的工作目录，但实际上的工作目录还是存在系统里的——最后把 U 盘回收的时候还是可以看到所有的东西。

### Docker 的 layer

* **layer 的叠加方式**
    * 从已有的镜像开始（可以假设是 Ubuntu 22.04），这在 Docker 里叫一个 layer；接下来配置环境变量，然后每运行一条 `RUN`，就相当于启动一个容器、创建一个 upper 挂载上去，底下是上面那层。

    * 让容器执行 `apt update`，它不就写到这个 upper 里了吗？写到 upper 里面，等容器运行结束，它就不再是 upper 了，它就是第一层。

    * 再运行下一个 `RUN` 时它会再放一个 upper，刚才那一层就变成了 lower 层，这层不再变化，而当前这层是 upper；install 完了以后要再执行下一个命令，它又变成一个新的 layer——就这样一层一层堆上去。

    * 漏装了一个软件要改某条命令时，就必须退到上一条命令创建出来的那个 layer 重新 replay 执行这条命令，并从那里开始执行后面所有的东西；如果改动了最底下的基础镜像，上面所有的东西都不对了，全都要重新 replay。

    * > **提示**：想要再装一个包，正确的方式是在最上面再加一条 `RUN` 而不是回头去改中间那条命令——这样底下所有层都是 lower，只有新加的这一层是可变层，它挂上去执行完，又变成 append-only。

* **容器不过是一堆共享 lower 的 upper**
    * 任何一个 layer——实际创建出来的是一个镜像——加上底下所有的东西，就变成了一个文件系统的快照。

    * 在这个基础上把底下所有东西全部当成 lower、再创建一个新目录作为 upper，你就得到了一个「虚拟机」；你可以创建好多好多个 upper 目录同时运行，而它们**共享一个 lower**，这就是容器。

    * 动机只是「我希望看到的目录可以是拼凑出来的」，而它能做到的事情远超你的预期。

### 跨过 CRUD 的边界

* **overlay 改变了文件系统的语义**
    * 快照与监控本质上都能用增删改查实现——快照你就把它拷贝一份，监控你可以用遍历的方式来实现。

    * 但 overlay **不能**用增删改查来实现，它其实改变了文件系统的语义：你把两个目录合并，「合并」是一个新的语义操作。

* **语义既然可以改写，文件系统就可以自己写**
    * 文件系统就是一个数据结构，而数据结构你是可以随便实现的，没有人规定它一定要按照某个方式实现——所以你应该能够直接自己写一个文件系统。

    * `/proc` 就是内核里面的一个文件系统：它的 `getdents64` 系统调用是它自己提供的，所以它就能有一些「能 `cd` 进去、但你 `ls` 看不到」的目录——这个行为由文件系统的实现确定。

## FUSE 与虚拟文件系统

### 文件系统可以欺骗你

* **procfs**
    * > **定义**：Linux 实现的一种特殊文件系统，挂载的时候类型写的是 `procfs`，所以这整个文件系统包括 `getdents64` 的实现，全部由 procfs 的代码自己决定，理论上它想做什么就能做什么。

    * 那些看起来像目录树的东西其实根本没有在操作系统里创建成对象，全是临时构建出来的：你遍历它会看到一个非常庞大的文件系统，但这些对象从来没有真正被构建出来。

    * 内核里真实存在的是可调度实体 `struct task`（里面有巨多关于线程的信息，比如 `pid_t pid`），每个 CPU 上有一个 runqueue 链着一大堆这样的 task，这些数据结构在内核里连得好好的。

    * procfs 的代码只有在你真的 `open` 了那个目录之后才开始工作，而且打开目录的时候那些对象都还没创建；只有在你真正调用 `getdents64` 的那一刻，它才去遍历系统里现存的 `struct task`，一边遍历一边动态地把结果生成出来。

* **文件系统可以欺骗你**
    * `ls 1695/` 可以（目录在），`cat 1695/status` 可以（看到它的信息），`cd 1695` 也可以，但 `ls | grep 1695` 就是看不到它。

    * 只要你的 API 返回的值是你想要的那个值，这件事就是成立的；`/proc/<pid>/memory` 这种东西也不是一个实在的文件，但文件系统帮你把它实现了——文件本来就不存在，那么让你看见、不让你看见、让你看见什么，完全由它决定。

### FUSE

* **FUSE（File System in User Space）**
    * > **定义**：把文件系统实现搬到用户态的办法——操作系统的内核会把 lookup、read、write 这些操作转发到 fuse driver，再由 fuse driver 转发给你的用户态进程。

    * 你所要做的所有事情就是实现一个 `struct fuse_operations`，里面有读、写、打开目录、遍历目录，甚至还有一个 `setxattr`——FUSE 是支持扩展属性的，它是一个 Unix 兼容的文件系统。

    * 从此这个文件系统就再也不是一个 CRUD 了：它背后没有任何文件，但你可以虚构出一棵目录树来，每一个目录和文件的读写都由你自己决定；代码是 Turing-complete 的，所以理论上你可以做任何事。

    * 另一条路是在内核里实现一个内核模块装到内核里，让内核支持这个文件系统，但 FUSE 是更通用的办法。

    * > **提示**：这是 everything is a file 的终极实现；理论上说，你也可以直接在 Windows 上面实现一个 `/proc`。

* **一个能玩的例子**
    * 开场声明 `FUSE_USE_VERSION 26`，然后找到 `fuse_operations`，只实现 `open`、`read`、`readdir` 这些成员就够了：实现 `readdir` 时想给它什么文件就给它什么文件，它问你要文件数据时你想给它什么数据就给什么数据。

    * 效果是：一开始目标目录是空的，挂载之后就进入了 galgame 模式，目录里面已经有文件了；这些文件完全是我虚构出来的，**没有一个对应磁盘上的真实文件数据**，打开什么它就返回原样的数据，理论上完全可以返回一个随机数给你。

    * 还有一个行为：往任何一个文件里写入任何数据——而写数据也就是回调了实现里面的一个 API——文件系统内部的状态就会感知到这一点，于是它可以做任何计算，可以驱动整个 galgame 的运行。

* **疯狂的人类已经用它干了什么**
    * 把远端的东西搬到本地：把一个远端的 ssh 目录映射成本地目录，只要把所有的目录操作代理到那个地方的目录操作就行；也可以把一个远端的 Git 仓库变成一个本地目录。

    * 用数据库来存文件系统：有些文件系统（比如 FAT）是不安全的，崩溃的时候可能会不一致，而数据库可能确实做到了一致，因为它是 append-only 方式实现的；于是可以用一个像 SQLite 这样的数据库引擎把文件系统保存在数据库里，文件系统操作全部改成 SQL 查询。

    * 反过来，把不是文件系统的东西变成文件系统：一个 JSON 的 key-value，把 key 变成目录、把 value 变成目录里的一个 `value.txt`，往那个 `value.txt` 里写入它就去更新那个 JSON，你每次读到的就是最新的、up to date 的那个 serialized version。

    * 也可以把一份学习资料真正隐藏起来：让 `readdir` 看不到那个条目，但你**可以 `cd` 进去**——只有知道那个名字的人才能进去，没有任何人能进去。

    ```text
    ls /mnt/xxx          → 看不到（readdir 不报告）
    cd /mnt/xxx/秘密名字  → 能进去（lookup 命中）
    ```

## 在块设备上实现文件系统

### 设备与分区

* **块设备对外的三个操作**
    * `mount` 要求一个块设备，而这个块设备对外其实就三个接口：一块一块地读、一块一块地写，以及等待正在途中的写落盘。

    * 真实的设备会比这复杂一点，比如它有一个队列，你往队列里提交请求，还要能知道这个请求什么时候完成；简单起见，可以把它类比成并发程序里的共享内存。

| 共享内存（并发程序） | 块设备 |
| :--- | :--- |
| byte array，按字节寻址 | block array，按块寻址 |
| load / store | read(#blk) / write(#blk) |
| barrier / mutex | block sync（等待在途的写落盘） |

* **GUID 分区表（GUID partition table，GPT）**
    * > **定义**：磁盘这个数据结构本身的 specification，是 UEFI specification 的一部分；UEFI 就是那个固件的 specification。

    * 布局是：block 0 是兼容用的 MBR，block 1 是 GPT header（整个磁盘数据结构的 root，指向分区表项），中间是各个分区的区间，最后一个 block 是 GPT header 的备份——头部一旦损坏，顺着尾巴往前找还能找回来。

    * 为什么磁盘的数据结构布局要由固件的标准来规定：因为系统一启动的时候就是 firmware 去看这个磁盘，如果它解析不了这个分区，它就不知道操作系统到底装在哪、数据盘在哪、该怎么挂载；所以所有可以被启动的磁盘都遵从这套标准。

    * 反过来，如果把一个完全被写成全 0 的存储设备插上来，它是识别不出分区的，只能看到一个光秃秃的整盘设备。

* **LVM（logical volume manager）**
    * > **定义**：把块设备一层一层虚拟化的机制，可以一对多，也可以多对一，也可以多对多。

    * 一个完整的演示链条：先创建 8 个 32 MB 的普通文件，再通过回环设备把它们变成看起来就像块设备的东西，这些就是一个个 physical volume；把它们虚拟成一个虚拟磁盘（创建出来有 224 MB），再格式化成 GUID partition table 切成两个分区，一个是 FAT、一个是 ext4。

    * 往里写数据会真实地落在背后那些镜像文件对应的字节上：在两个分区里分别写了不同的内容，做一次 `sync` 之后再去看，数据真的被正确地路由到了那两个虚拟磁盘的文件里。

    * 所有 LVM 相关命令里的系统调用全都是用 `ioctl` 实现的：建立回环设备是在 `/dev/loop-control` 上做 ioctl 拿空闲编号；`pvcreate` 用 `/dev` 下 mapper 里的 control，查到块设备大小，然后各种写入标签；创建组与逻辑卷时先 ioctl 查询 device mapper 的能力，再通过 `DM_DEV_CREATE` 把 name、UUID 写进去创建 DM 设备，分区的映射也是为每一个分区创建对应的 DM 设备。

    * 这就是为什么想再复制一份 Linux 非常困难：看着好像只要实现 `read`、`write`、`open` 就可以了，不是这样的——一旦你碰到 ioctl，你会发现内核里几乎每一个子系统的 API 都是用 ioctl 这种东西暴露出来的，甚至有些是通过文件系统、通过 sysfs 暴露出来的，这些复杂性你都得实现。

### 实现难点

* **读写放大**
    * 你很多时候真的只想要一个字节，比如只想要这个文件的大小或者 `stat` 信息，但为了读到这个信息你就得把一整块数据全部读进来，所以数据在磁盘上的排布就变得很重要。

    * 更新文件里面的一个字节，你不仅要更新这一个字节，还会更新它的 modification time（也就是元数据），这就涉及多个块的写入；而哪怕只是一个块的写入，你也得先把这个块读出来、把中间的部分改掉、再写回去。

    * 写一个块的时候又会牵涉到 SSD FTL 里面的 map table 的修改：SSD 里有一个像页表一样的东西做地址翻译，你看到的「我要写第一块」实际上写的是经过映射之后的那一块；要维护这个虚拟地址就又多了一个数据结构，而这个数据结构又是 copy-on-write 的，它要拷贝就会先拷贝根节点、然后一层层往下拷贝。

    * 所以理论上你写一个字节可能会有几万倍甚至几十万倍的写放大；退一步，写一块依然会有若干倍的读写放大，甚至到十倍都是有可能的。

* **buffer cache**
    * > **定义**：内核统一分配的一份文件系统缓存；`bread` 可以类比成共享内存里的 load，`bwrite` 就是 store。

    * 这个名字很糟糕（「buffer」和「cache」两个词连起来其实说不通），是历史原因，它就是一个 cache。

    * cache miss 说明 cache 里没有，它就去设备里找；而设备如果本身是一个虚拟设备，它又会往下走，走到回环设备，再走到文件里，经历一层层的转化。

    * 写的时候和 memory hierarchy 不太一样：因为已经是按块的写了，所以这个块可以直接写进 cache、把旧的覆盖掉，这就相当于 cache hit，下一次 read 就直接从 cache 里读走。

    * 想让文件系统高效，你就希望尽可能把经常会一起访问的数据结构放到一个块里——这一次读到了这个数据结构，下一次读它临近的那个数据结构时 cache 就 hit 了，从而在一定程度上减少读写放大。

### 设计依据与入口

* **真实文件系统的统计发现**
    * 想实现一个高效的文件系统，最好的做法是先去观察现有文件系统里的统计：到各种场景里取数据（数据中心、个人用户的 PC、不同的人手里），得到一些结论。

    * 绝大部分文件都比较小：生产的源代码不可能塞在一个巨大无比的文件里，那样维护会变得很困难；文档性的内容也都不会很大，图片这类 binary 也不算特别大。

    * 少数大文件用掉了绝大部分空间（一个数据库、一部电影确实会占掉磁盘的绝大部分）；一个目录里面的 entries 不会太多；文件系统大致是半满的——不管你留了多大的门限，人总会想办法把它填得比较满。

    * 这些结论稍微有点过时，但基本还符合今天 Unix 系统里的文件分布，尤其是个人电脑；数据中心会非常不一样，因为数据中心里大部分是管理用的数据块。

* **要实现什么、要回答什么**
    * 为了做出目录树这个数据结构，有好几样东西要一起实现：data（文件真正的字节内容）、每一个目录或文件的 metadata（大小、名字、访问权限 mode、时间戳）、目录树状的结构（内存里是一棵有 children 的树，磁盘上同样需要这样一个树结构）。

    * 第一个要回答的问题：metadata 怎么存——是直接跟数据存在这儿，还是存在别的什么地方。

    * 第二个要回答的问题：data 怎么存——一个文件是一个 byte array，由好多块组成，那就需要一个数据结构把它们串起来。

    * 第三个要回答的问题：一个大文件，你怎么知道它的每一个 offset 对应的块在哪——文件可能很小（2 KB、4 KB），也可能很大（几十个 GB），需要一个数据结构来存这个映射。

    * > **提示**：本质上你甚至可以把世界上所有跟数据结构相关的论文爬下来拼成一个 prompt 去问大语言模型「对于这个数据结构，我要在磁盘的特性上实现文件系统、优化什么样的 workload，这是不是一个好 idea」，把不好的 idea 都删掉，你就得到了一个新的文件系统实现。

* **数据结构都需要一个入口**
    * 你要在一个块设备上实现一个数据结构，它一般来说是一个 partition，本质上也是一个字节序列、一个 block 一个 block 的序列。

    * 你们的链表一般会有一个 head，一棵二叉树会有一个 root 指针指着它；各种各样的文件其实也是数据结构，比如 bitmap、比如用 `printf` 直接输出的 `.ppm` 图像。

    * ELF 也是：它有一个头，头里有 magic number 帮助 `file` 命令和加载器识别这是不是一个 ELF；头里还有一个结构体，结构体里有 ELF 的 entry、文件的大小、program header 的数量这些东西。

    * 所以第一件事是：数据结构都有一个 root，指向某一个 block，一般来说就放在最头上。

* **superblock**
    * > **定义**：分区里头也有的一个数据结构，是对整个数据结构来说最关键的一个 block；如果你只被允许损坏一个 block 并想给文件系统使用者造成最大的麻烦，那就应该把 superblock 抹掉。

    * 它通常有一个 magic number，然后有文件系统意义上的信息，比如 block 的 size；还有一个容易忽略的细节是「文件系统自己的 block 大小」和「设备物理上的扇区大小」是两件事。

    * 这个细节的后果：磁盘可能是 512 个字节一块，但文件系统可以说它按 4 KB 作为逻辑块来编号；用 32 位 block number 时，如果每块只有 512 字节，最大也只有 512 乘以 $2^{32}$ 这么大，但如果按 4 KB 编块，文件就可以更大一点。

    * 里面还有别的关键信息：这个文件系统还有多满、还有多少空间、还能剩下多少个文件可以分配、数据结构的起始位置和大小。

    * `mkfs` 的时候去 `strace` 它，就会看到它在前面写上这个数据结构；而 `mount` 命令其实也是根据 superblock 去确定文件系统的类型。

### FAT

* **File Allocation Table（FAT）**
    * > **定义**：用一张「cluster 号 → 某个值」的表作为核心数据结构的文件系统——它是一张表，你可以把它理解成一个 next 数组，本质上就是一条链表。

    * 它适用的场景是极小的存储设备：5.25 英寸的软盘单面是 160 KB，这意味着如果块是 512 个字节，它总共只有 320 个 block / sector；这么小的规模上花哨的数据结构只会浪费空间，你要的是极致的空间节约。

    * BPB（common to FAT12、FAT16 和 FAT32）就是它的 superblock，里面有很多字段：OEM name 可以存一些字符串信息；bytes per sector 说明这个存储设备每个扇区有多少字节，所以它可以兼容 512、1024 等各种设备。

    * cluster 是它的核心概念：物理上你按 512 个字节访问磁盘，但你可以把任意 $2^k$ 个 512 字节绑成一个 cluster，比如 $k=2$ 就是 4 个 512 字节（也就是 2 KB），于是有 cluster number 1、number 2、number 3…

    * 磁盘在 FAT 里已经被编成好多 cluster，前面有一些区域是不用的，从某处开始是 cluster number 1、2、3…

| 变体 | 表项位数 | 能编号的 cluster 数 |
| :--- | :--- | :--- |
| FAT12 | 12 bit | $2^{12}=4096$（实际可用还要更少一点） |
| FAT16 | 16 bit | $2^{16}=65536$ |
| FAT32 | 32 bit | $2^{32}$ |

* **next 的三种取值**
    * 假设 cluster 大小是 4 KB，`next[1] = 3` 的意思就是 cluster 1 里装的是文件的第一段数据，接下来第二段在 cluster 3，第一个 4 KB 在这儿、第二个 4 KB 在那儿。

    * `next[2] = 0` 说明这一块是 free 的、可以分配、没用过；`next[3]` 是结束标记就说明这个文件到这块就结束了。

    * 结束标记约定成全 1 的保留值，可以理解成 -1；此时文件最多只有两块、最大 8 KB，你只要再存一个文件 size，就能知道最后一块里到底有多少字节是真正属于这个文件的。

| `next` 的值 | 含义 |
| :--- | :--- |
| 另一个 cluster 号 | 这个文件的下一个 cluster 在哪 |
| 0 | 这一块空闲，可以分配 |
| 结束标记 | 文件到此结束（约定成全 1 的保留值，可以理解成 -1） |

* **12 个 bit 怎么压进 3 个字节**
    * FAT12 里一个指针就是 12 个 bit，而 12 不是 8 的整数倍，所以它把两个 12 bit 打包成 3 个字节按位紧压。

    * 3 个 byte 正好是 24 bit，一个 12 bit 属于上一个指针、另一个 12 bit 属于下一个指针，非常非常省空间。

    ```text
       byte 0            byte 1            byte 2
    +-----------+    +-----------+    +-----------+
    | ptr[n]    |    | hi4 | lo4 |    | ptr[n+1]  |
    | low 8 bit |    | of[n]|[n+1]|    | high 8bit |
    +-----------+    +-----------+    +-----------+
         \_______________/    \_______________/
              ptr[n]                 ptr[n+1]
              12 bit                 12 bit
    ```

* **大文件与碎片**
    * 小磁盘上小文件配这样一条线性链表性能完全没有问题：因为整个 FAT 是可以一起读出来的，一旦读进内存，就相当于你一下子把好多 next 指针都加载到了内存里，你几乎就是在内存里遍历这个数据结构。

    * 但到了几十个 GB 的文件系统，里面可能有几 GB 的电影这样的大文件；这时候 next 有两种情况，一种是最理想的——next 都是连续的，你访问一个文件的时候它在 cluster 里存的一大张也是连续的。

    * 可是分配的时候并不是这么回事：文件会不停地创建、删除、再创建、再删除，跟 memory allocation 一样，时间长了就会产生碎片；一旦产生碎片，FAT 就不连续了，它可能指向一个很远的地方、再指回来、又指到一个很远的地方，来回跳。

    * 如果是一个很大的文件、碎片又很多，就会造成很大的读放大：因为 FAT 本身也很大，FAT32 在很大的磁盘上 entries 非常多，于是你这段的 next 读出来了，它的下一个 next 在另一个 block 里，你就得把那个 block 也读出来；再下一个 next 又在别的 block 里，反复地读块。

    ```text
      连续（理想）：  464 -> 465 -> 466 -> ... -> 546

      碎片化：        2407 -> 2408 -> ... -> 2431
                            |
                            `-- FAT 里跳到很远的地方 --.
                                                      v
                      2511 -> 2512 -> ... -> 2587
    ```

* **用 mmap 把镜像当成数据结构来解析**
    * 一个检查 FAT 文件系统的小工具就是这么干的：直接用 `mmap` 把一整个磁盘镜像映射到进程的地址空间里，一旦映射完，FAT32 的 header（也就是它的 superblock）直接就变成了一个指针，就是一个数据结构。

    * 从这个指针里可以读出各种信息：bytes per sector、total sectors、volume number、serial number，等等。

    * 有了这些就可以用遍历数据结构的方式去遍历它——一个 DFS scan（深度优先搜索）把整个目录树扫一遍，目录结构可以正确地显示出来。

    * 那些不连续的片段是特意造出来的：不停地往里面写文件然后删掉，写文件、删掉、写文件、删掉，相当于不停地 allocate 一些随机大小的内存，时间长了 allocation 和 free 之后就会产生碎片，于是文件就可能分散在连续的几部分里。

* **目录在 FAT 里也是一个文件**
    * 最早的 FAT 里存储一个文件名用的是固定的 11 个字节（也就是 8.3 的格式，short file name），其中默认有 3 个字节是扩展名，所以文件名最多只有 8 个字符。

    * 会看到波浪线 1、波浪线 2、波浪线 3：如果文件系统是在今天创建的，为了保持向前兼容（比如在 DOS 里你依然可以访问这个目录），一个很长的文件名如果前缀又都相同，它就会把前缀截断，用 `~1`、`~2` 去区分这些文件。

    * 目录实现其实也是一个文件：它也是一个数据，也靠 next 串起来；你的目录里有好多好多项（一万个文件），这一万个文件就是不停地 next、next、next，所以它也是一个线性表，这个线性表里是一堆 directory entry（目录项，dentry）。

    ```text
      +----------------+--------+  ...  +-------------------+-----------+
      | name           | attr   |       | first cluster     | file size |
      | 11 bytes (8.3) |        |       | high(2B) + low(2B)|           |
      +----------------+--------+  ...  +-------------------+-----------+
              ^             ^                     ^                ^
           文件名      属性位：read-only /      第一块在哪      文件多大
                      hidden / system /           |
                      volume ID / 目录(0x10)      v
                                           顺着 next 一路找下一块
    ```

    * dentry 里有一个名字，有一个 attribute（这里的位告诉你它是不是 read-only、是不是 hidden、是不是 system、是不是 volume ID、是不是目录，比如 `0x10` 就说明这是一个目录），还有 first cluster（这个文件的第一个 cluster 在哪，有 high 和 low 两个两字节）以及 file size。

    * 作为文件系统的实现者，遍历目录就把这个目录文件当普通的文件读出来，读完之后它变成好多好多个数据结构的拼接，你去遍历这个数据结构，就知道这个目录里面有哪些文件。

    * > **提示**：也正因为目录项里存的就是这些字段，这个文件系统是不支持链接的——它就是一个最简单的实现。

### Unix 的设计

* **目录文件里存的是名字到 inode 编号的映射**
    * > **定义**：一个文件之所以找得到，靠的不是它叫什么名字，而是它被记在哪儿；目录靠的就是在目录文件自己的数据里存一个从文件名到 inode 编号的映射。

    * 完全不需要什么 fancy 的数据结构，顺序存就是了：一个文件名、一个 inode 编号、一个 `\0`；再来一个文件名、一个 inode 编号、一个 `\0`……一个目录文件就这么一路排下去。

    * 这等价于「要表示一张图，而且边上还得挂 label」：把目标节点的位置和边上的名字写在一块儿——「边上的 label」是文件名，目标节点就是 inode。

    * Unix 的文件系统是一张图而不是一棵树，因为设计者想要支持链接：`bin` 有一个点是指向它自己的、有一个点点是指向它上级的，边就把图闭合起来了。

    * 存这个图最自然的想法是定义一个 struct node，把节点所有重要的信息（就是在 `stat` 里能看到的那些东西，`st_mode`、`st_size`，各种东西）全部放进去；边则存在目录文件里——图中的每一个节点要么是普通的数据文件、要么是目录文件，不管哪一种它都有一个 byte array，除此之外它还拥有一个 index，这个 index 就相当于是一个指向它自己数据块的入口。

* **索引块：把文件头几块直接塞进 inode**
    * 经验事实是：大部分文件都是小文件，而且绝大部分时候你只读一个头——你要看一个东西是不是 binary、是个什么 binary，扫一眼开头就够了，后面的内容你根本不在意。

    * 既然如此，文件系统当然希望访问文件头部时越快越好，可它同时还得能装下很大的文件。

    * 于是 Unix 做了一个联合的数据结构：把文件最前面的那几块直接写在 inode 里（具体是 9 块、10 块还是 12、13 个指针记不准也不重要），这样你读文件头，读 inode 就拿到了，中间一个步骤都不用绕。

    * 文件要是超大了，再拿一个块来做一层间接索引，概念上就是一个一级页表——那个块里排的不是数据，而是指向数据块的指针；一级还不够，就在这个指针之外再挂一个二级表，二级还不够，再上三级。

    * 算一下账：4 KB 的块里面能放下 1024 个指针，所以一级间接覆盖 1024 块，二级 $1024 \times 1024$，三级 $1024 \times 1024 \times 1024$——三级表已经大得离谱了。

    * > **提示**：这是一个非常漂亮的、多个数据结构的联合，它把 locality 用到了极致——小文件读头直接从 inode 里拿，只有要往后读的大文件才逐级展开那张「页表」。

* **inode 聚成一片，符号链接还能偷索引区**
    * 第二个设计是把所有的 inode 放在一起，带来的也是 locality：一个目录里写了 10 个文件，分配的时候它们就是连续分配的，所以在 inode 区域里存得也近乎连续。

    * 于是你把这一片 inode 一次性读出来，相邻的、彼此相关的那些文件就一起进了内存；在有 cache 配合的前提下，inode 聚集是一个非常合理的、站得住脚的实现。

    * 这个设计还有一个更有意思的副作用：符号链接可以直接偷这块空间——如果符号链接的目标不超过 60 字节，它不必为数据单独分配任何一块，直接借用 inode 里那块本该放索引的内存，把 `../a` 这样的字符串塞进去就行。

* **动手看一眼真实的 ext4**
    * Unix 世界里有专门的工具做这件事，核心用的那个叫 `debugfs`；你甚至不需要先懂它的代码，让 AI 看一眼代码结构就行。

    * 但更重要的其实是先有一个观念：操作系统**应该**有办法把文件系统底层的信息暴露出来，不必事事都绕上层的 API。

    * 拿它去解剖一个 ext4 文件系统，你能看到整个目录树的结构：cd 进去、建一个目录、写一个文件、做一个链接，然后再把结构打出来看一眼；你能看到链接计数（link count），能看到各个节点，能看到每个文件占的 block ID。

    * 还能看到某个文件占用的那几个 block 在磁盘上还是**连续**的——前面讲的连续分配活生生地摆在你眼前；也能看到一个符号链接，它的目标如果是短的，就 inline 在 `i_block` 里面，压根没另外占块。

    * > **提示**：本质上文件系统就是一个数据结构，数据结构课其实完全可以把这些内容都讲好；但操作系统里的文件系统还背着一项数据结构课没有的职责——应对崩溃。

## 崩溃一致性

### 崩溃为什么危险

* **crash consistency（崩溃一致性）**
    * > **定义**：文件系统必须从一个 consistent 的 state 稳稳地挪到下一个 consistent state；即便发生掉电，文件系统里的数据也不能丢。

    * 崩溃可能是 power loss：设备没电池，一断电，内存里的数据瞬间全没。

    * 为什么这件事难？因为它终究还是个数据结构。哪怕你只是写个链表，要把 y 插到 x 后面，你也不是写一个指针就完事——先记住原来的后继，让 x 指向 y，y 指回 x，原来的后继改指 y，y 接上原来的后继。

    * 在并发语境下你会为了防止 data race 在这里加 lock、加 unlock，但你从来没想过：如果这时候这个线程突然被杀掉，会怎么样。

    * 必须把所有操作都执行完，这个数据结构才是一致的。

* **抽象成线程随时可能消失**
    * crash consistency 就有点像「线程随时随地都可能突然消失」：设想你刚做完 `x.next = y`、`y.prev = x`、`n.prev = y`，正打算写 `y.next`，线程消失了。

    * 此时 `y.next` 是空的、飘到 0 去了，你去遍历这个数据结构，它就崩了。

* **一次 append 背后是三个 bwrite**
    * 假设最简单的情形：往文件尾部 append 恰好一个 block。你需要做三件事：allocate 一个新的 block（把 bitmap 里那个位置置成占用）、写 data（把内容写进那一块）、更新元数据（把这一块记进 inode）。

    * 这三件事各自都是一次 `bwrite`；而麻烦在于，`bwrite` 执行之后，请求只是进了一个队列，这个队列通向**存储设备自己内部的那套计算机系统**。

    * 想想一块旋转硬盘：它有一个读写头，读写头怎么处理请求？当然是「离我近的先进」——如果盘片转过来时第 2 号请求正好在我底下，我就先做它。

    * 反正 1、2、3 落在不同 block 上，顺序做 1-2-3 还是 3-2-1，最终结果都一样；**正是这个「最终一样」，意味着实际顺序可以任意**。

    * 既然顺序任意，一次崩溃就意味着这三个 `bwrite` 的任意一个子集都可能落盘，其余的没来得及——三个写，$2^3 = 8$ 种可能。

| 实际落盘的写 | 后果 |
| :--- | :--- |
| 三个都落盘 | 一致，正常 |
| 只落了 data（bitmap、inode 都没动） | 相当于往一块仍然标为 free 的块里写了几个值，文件系统毫发无伤，安全 |
| data 与 inode 落盘了，bitmap 没落 | 文件当场读得出来、内容是对的；但那一块在文件系统眼里还是 free，将来被分配给别的文件、别人又写了一遍，里面的内容就被覆盖了，于是这份文件隔天打开内容自己变了 |

* > **易错点**：最后一种是最阴险的——损失不发生在当下，而是潜伏到未来某次分配才爆发，这就等于打开了一个魔鬼的盒子，和并发里那个 reorder 是同一套思考方式。

### fsck 与 lost+found

* **文件系统检查（file system check，fsck）**
    * 文件系统的实现者多半是知道 crash consistency 问题的，但在 1970 年代要做出 crash-safe 的数据结构显得太过复杂，于是干脆不管了——做 systems 的人都是这样，先挣钱、后还债。

    * 真出了问题怎么办？送去做一次文件系统检查，你在老一点的机器上见过开机时「正在扫描文件系统，找到多少坏簇并修复」。

    * 这套检查的思路是把不一致的状态搜出来再修：第 40 块在 bitmap 里是 free 但某个 inode 指向了 40，那你就扫描这条磁道上所有的 inode、遍历出所有**已被使用**的存储空间；既然 40 已经有人用了，它就不该是 free 的，去把 bitmap 里这一位置修回来。很长一段时间里大家做的都是这种 rule-based file system checking。

    * 它也有猜不出来的时候：目录被人移动以后，你可能得到一个看不懂的结构——第 1 个指向第 4，第 2 个也指向第 4，第 3 的父亲是第 1，第 4 的父亲是第 2；这时候没办法了，只能猜一个「之前到底发生了什么」才变成现在这样。

* **lost+found**
    * > **定义**：Unix 默认的 `fsck` 对某些孤儿文件的收容所——如果一个文件已经没有任何目录指向它（可能是它所在的目录文件损坏了），但它的 inode 还在，那就把它捞回来丢进这个目录里。

    * > **易错点**：`lost+found` 不是垃圾箱，它是「检查器只能救回 inode、救不回名字」的那些文件的收容所——文件内容还在，但原来的路径没了，只能靠编号去认。

* **硬件层面的教训**
    * 当年在美国的 lab 里做过一个小面包板：从 VGA 送一个可编程的信号出来，用这个信号物理性地把 SSD 的电源切断。

    * 结果发现很多 SSD 内部那套计算机系统有严重问题——crash 之后整块盘可能就死了，再也读不出任何数据；SSD 的修复还极其复杂，它和 HDD 不一样：HDD 坏了你还能拆盘，SSD 基本上没法修。

    * 这个工作后来促成厂商修了一大批固件，再后来就再也找不到这类问题了。

### 日志

* **append-only 与操作序列的视角**
    * 如果一棵树的节点带 parent 指针，你就和链表一样要面对**多处写更新**的问题：`5.parent = 6` 和 `6.left = 5` 是两次写，只要分两次写，它就是 crash unsafe 的——对数据结构的写本身就不安全。

    * 那什么东西容易做到 crash-consistent？**append-only**。

    * 所以数据结构其实有两种视角：第一种看数据结构本身（这是一棵有 `left`、`right`、`parent` 的树，查询 $O(\log n)$），第二种看记录这个数据结构的**操作序列**——只要你把所有的操作都记下来，哪怕这棵树当场不一致了、甚至整棵树丢了都没关系，只要 replay 这条插入序列，树就重建回来了。

    * 再往前推一步，可以做一个 memory trace：对共享内存的每一次修改和分配全都记下来，比如 `mem[6.left] = 5`、`mem[5.parent] = 6`；因为数据结构的本质归根到底都是通过 memory write 实现的，你只要把所有的 memory write 按顺序记下来、replay 它，就能得到一个一模一样的数据结构。

* **write-ahead log（写前日志，redo log）**
    * > **定义**：一边在 block 上存那个正常的数据结构，一边在磁盘上单独划出一块区域做 journaling；每次 `bwrite` 先以 append-only 的方式把它写进 journal，等这次写确确实实进了 journal，才再去把这个写落到真正的数据结构上。

    * 数据结构写进去了，journal 里那条记录就可以丢掉了；可只要数据结构那边还没写完，这条记录就始终在磁盘上待着。

    * 于是行为很清楚了：这时候如果 crash，磁盘上的数据结构是不一致的；但 reboot 以后，我可以把这些 `bwrite` 重新 replay 一遍，把它补完。

    * 它叫 write-ahead log（写前日志），也叫 redo log（重做日志）——你是在写之前先记一笔日志，而这笔日志是为了「重做」用的；有了它，**任意数据结构都能做到 crash consistency**。

* **transaction begin/end 与 happens-before**
    * 在文件系统里做 journaling，其实不需要做成对任意数据结构都成立的通用日志；你只需要在真正要写的时候，把要写的东西直接往里写，然后加两个标记。

    * 顺序是：把数据写下去，标一个 **transaction begin**（事务开始）；接着发起一次 flush，告诉磁盘「我要等这些数据全都落盘」；等它落盘完成，再写一个特殊标记 **transaction end**（事务结束）；完了可以再 flush 一次。

    * 这就建立了一条 **happens-before** 关系：这些数据 happens-before 那次 flush，那次 flush 又 happens-before 写 transaction end。

    * 反过来看，当我在磁盘上看到了 transaction end 这个标记，说明 transaction end 已经发生；它发生了，就说明 flush 一定发生并且完成了；flush 完成了，就说明那些数据一定已经落盘——于是这笔操作算数，只要 replay 它就行。

    * 这一步就是 **checkpointing**：把 journal 里的操作重放到真实的数据结构上，重放完 journal 就可以清掉。

    * 于是崩溃点的位置决定了一切：崩溃发生在 flush **之前**，就像这笔事务从来没做过（因为不能保证所有数据都落盘）；崩溃发生在 transaction end **之后**，只要重启时看到这个标记，这些操作就一定会在重启后被正确地反映到文件系统上。

    ```text
    时间 ────────────────────────────────────────────────────────────────▶
       │ 写数据 / 写 inode / 写 bitmap │  flush   │ 写 transaction end │ flush │
       │      （真正要落盘的东西）      │（等落盘）│      （结束标记）   │       │
                                      └── 此刻崩溃 ──▶ 整笔事务当作没发生过
                                                   └── 此刻崩溃 ──▶ 重放即可恢复
    ```

* **LSM-Tree（Log-Structured Merge-tree）**
    * > **定义**：把「只追加 + 内存缓冲」这条路走到极致的经典数据结构，现在的 key-value 系统甚至数据库很多都以它为根基。

    * 先在内存里放比较热的数据：要写一个数据直接写内存，内存里用一个对并发比较友好的结构（比如 skip list）承载。

    * 对所有这个结构的更新，都以 write-ahead log 的形式写进日志——所以哪怕随时 crash，内存里那份结构也能靠日志重建回来。

    * 等 memtable 写满，触发一次 flush，往磁盘持久化；磁盘上存的是一棵一棵**不可变**的树，靠均摊分析撑着。

    * 整个结构一层一层，下面那层总比上面那层大，最上面是小小的内存层；写满就往下层合并——插进这一层，发现这层太大了，继续往下一层并，一层层落下去，最终得到接近 $O(1)$ 的时间复杂度；核心就是「内存的层次化存储 + 一个 write-ahead log」。

### 日志的两处改良

* **把多次系统调用的 transaction 合并成一个**
    * 哪怕小到教学用的操作系统，也会把多个 ongoing 的写——写了这个文件、写了那个文件——合成一笔事务，那样只要 flush 一次。

    * 代价是 crash 时可能多丢一点东西，换来的是**减少等待磁盘同步的次数**。

* **Journaling Block Device（JBD，第二版叫 JBD2）**
    * 每个设备都有一个这样的 journaling daemon 在后台跑。

    * 它隔一段时间（比如 30 秒）才把东西做一次 snapshot，而不是你写完一个文件就立刻落盘——所以在系统里会显得稍微慢一点。

* **用 checksum 取代 transaction end**
    * 既然核心是那条 happens-before（要靠 flush 才能保证先数据、后标记），那我干脆不要 transaction end，也不必真的等那次 flush——当然你仍然可以把日志推落盘，那样更安全。

    * 改为在日志头部直接写一个 checksum 加一个长度：crash 之后我不再傻傻地扫遍整个 journal 区域，而是看这里有个 checksum、有个长度，按长度读出这一段，算一下 checksum 对不对。

    * 对，就说明它正确落盘了，replay 它；不对，就把后面的全扔掉。它用 checksum 这套机制，省掉了落盘的 synchronization。

* **metadata journaling**
    * ext4 默认采用 metadata journaling：它把 inode、bitmap 这些**元数据**的更新全写进日志，而对文件内容的修改不写进日志。

    * 理由是数据占了磁盘写入的绝大部分，你绝大部分时间其实是在写数据，而数据丢不丢通常对你不太要紧，应用程序在一定程度上有义务保证自己不丢数据。

    * crash consistency 的含义本来就是你崩溃时会丢一小段时间内的内容，所以它更看重的是**目录树的完整性**：不能因为目录节点出了问题，把你的目录整个搬进 `lost+found`，那对你就很糟糕。

    * 它要保证目录结构一致，数据可能丢，以此换性能。

## 用户空间的崩溃一致性

### 保存文件的两条规则

* **`O_TRUNC` 是个陷阱**
    * 你写了一个文本编辑器，在自己的 buffer（内存）里有一个 `a.txt`，要保存它时第一件绝对不能做的事，是直接 `open` 这个 `a.txt` 并带上 `O_TRUNC`——`open` 的那一瞬间文件内容就没了，要是这时候你的进程被别人杀掉，这个文件就彻底没了。

    * 那自然会想到的流程——先把新数据写进 `a.txt.tmp`、`close` 之后觉得「临时数据已经写进去了、我安全了」，接着 `unlink a.txt`，再 `rename a.txt.tmp` 到 `a.txt`——**是不行的**。

    * 因为操作系统做的是 metadata journaling，它对这个「数据」不负责：redo log 里记下的只有元数据操作——第一步，「创建一个空的 `a.txt.tmp`」（`O_CREAT` 本身是目录里的元数据操作）；第二步，「把 `a.txt` 删掉」（`unlink` 也是目录里的操作，同样要 journal）。

    * 然后 system crash 了，而 data 是不 journal 的；重启之后，日志里看到的就只有这两条，于是 `a.txt` 没了、`a.txt.tmp` 是个空的——你回来一看，文件就这么不见了。

    * > **提示**：这就是 metadata journaling 的边界——它保证的是目录结构一致，不是你的文件内容一定在。

* **只留一个 rename 就够了**
    * > **提示**：正确的方式其实简单到只有一句——把新内容写进临时文件、确保数据落盘之后，**不做 unlink，直接用一次 `rename` 换过去**。

    * `rename` 能保证 atomicity——它要么就换过去了，要么就完全没有换，没有中间态，这是 Linux 给出的保证。

    * 崩溃发生在 `rename` 之前，你手里的还是旧文件；发生在之后，你拿到的是新文件——中间不存在「两个都没有」的时刻。

    * 可是开发者怎么可能知道这一点呢？除了真正优秀的 systems programmer 写的软件，所有业余程序员写的软件应该都有 crash consistency 的问题——去验证，答案是 yes。

* **Git 为什么敢不管**
    * 因为 Git 本身是 append-only 的数据结构，它只要能确保所有 object 都在就行。

    * 理论上即便文件系统留下了一致性问题，你依然可以把 Git 回到一个过去的一致状态，因为所有的 commit object、tree object 都不会丢，它们都在文件系统里；你扫一遍，总能把该恢复的恢复回来，不会有东西真的丢掉——所以 Git 就干脆为了性能不管 crash consistency。

    * 后果是可控场景下的教训：虚拟机快速关闭相当于把线拔了，而文件系统那个 journaling block device 的日志——哪怕只是 metadata——可能都还没 replay、只写了一部分，这时候 Git 就进入了一个不一致的状态，因为有些 data 没了，你需要重新扫描它。

### sync 家族

* **sync 家族与 sync 命令**
    * 用户空间里这个行为是**可控**的，用来实现用户态 crash consistency 的系统调用就是 sync 家族，还有一个 `sync` 命令。

    * 典型用法是在 `git commit` 之后加一个 `sync`：做一次全局的文件系统同步，确保数据都落盘；代价是这一步会比较慢，尤其存储设备是慢家伙的时候会有肉眼可见的延时。

| 调用 | 同步的范围 |
| :--- | :--- |
| `sync` | 全局的文件系统同步，把所有东西落盘 |
| `syncfs` | 同步这个文件描述符所在的**整个文件系统** |
| `fsync(fd)` | 同步**这一个文件**的 data 和 metadata |
| `fdatasync(fd)` | 同步文件的 data，并且只有当 metadata **真的变了**，那份 metadata 才一起同步 |

* **fdatasync 为什么特别有用**
    * 如果你要在磁盘上实现一个数据库，你很可能会先分配一个固定大小的文件，比如一个 4GB 的 database。

    * 那这 4GB 的空间**已经被分配出去了**，任何一个 block 都已经映射到磁盘上的某个 block，此后你对它的任何修改都不会改变这个数据结构的映射关系，变的只有数据和那个 modification time。

    * 这时候 `fdatasync` 会更新数据，但**不去动 inode**——因为 size 和索引都没变，动 inode 反而要多涉及一个块的写入，白白多一份 inode 上的落盘开销。

    * 所以在应用程序里实现 redo log 这类东西，用 `fdatasync` 的性能是最好的。

### 谁踩了坑

* **踩坑软件清单**
    * GNU 的 make：可能给你留下一个不正确的 build。

    * sort：如果你做 in-place 的排序，那个文件可能会被整个丢掉；它是支持 in-place 的（有些程序不支持，因为用 `O_TRUNC` 打开就直接挂了），但它支持 in-place 的同时**并不支持 crash consistency**。

    * Perl：它本身支持像 sed 那样做正则替换，专门有个 `-i` 的就地修改选项，那个也会把你的文件整个丢掉；最后它把这个 bug 修掉了。

    * 2016 年 VS Code 刚起步那会儿，整个 JS、Node.js 的世界根本不存在一个可以安全保存文件的 API，也就是说所有 Node.js、Electron 的应用全都有 crash consistency 问题；有人在 issue 里说我要保存一个很大的文件、这时候磁盘空间满了，然后我的文件就消失了。

* **用模型去验证这件事**
    * 可以把多年前的那篇相关论文直接丢给大语言模型，让它实现一个 crash consistency 的 checker——一个简化版的、用户态的版本，将近 1000 行代码，修了几轮基本上就对了。

    * 拿它去检查一个支持 in-place 排序的程序：它能观测保存文件的过程——所有和文件相关的系统调用——然后生成大量模拟出来的、可能的 crash 现场。

    * 再让大模型直接去解读那份结果，它就能把结论复现出来：AI 知道这个程序会在截断之后发生一次崩溃，也知道它在写入中断的时候会发生部分数据丢失，能正确地定位这个 bug；而这个 bug 是否修复取决于维护者可移植性的取舍。

    * 顺着这个思路，还可以把实验规模扩大 100 倍——理论上可以去世界上所有的开源软件里都做一遍这个实验，用 LLM 替代掉所有原来只能依赖 heuristics 的判断。

## 一切应用数据都是数据结构

### 应用数据即数据结构

* **软件是物理世界过程的一个投影**
    * 软件是物理世界的过程在信息世界里的一个投影，这个投影通常是有损的，因为计算机世界里能保存的信息有限。

    * 你和计算机的交互说到底只有键盘、鼠标和屏幕，接管你键鼠输入、往屏幕某个区域输出的都是应用程序；哪怕我只是想 `cat` 一下，那也是一个应用程序用 `open`、`read` 这些系统调用完成了文件访问。

    * 这也是应用层的 crash consistency 同样重要的原因——文件系统是一致的，但应用会有 data loss，对应用的使用者来说一样难以接受。

    * 本质上，所有应用程序在管理数据的时候，都是数据结构的增删改查：打开教务系统编辑教学班、编辑周历、编辑考核信息，都是数据库或者说数据结构的增删改查。

* **一个 pptx 也是一棵可以改的目录树**
    * 一个 `.docx` 或者 `.pptx` 同时也是一个合法的 zip archive：直接 unzip 它，就能在它内部的 media 目录下把里面所有的图片原图一把导出来。

    * 本质上它是一个 XML，有一套 specification，遵从 OpenXML Formats 下的 Office document 规范；这背后有点历史——以前的 `.doc` 是一个不开放的标准，在政府层面要禁用的压力下，最后促成了厂商自己做一个开放的标准让大家来遵循。

    * 这个数据结构描述的是幻灯片里面的页，然后每一页里面的每一个东西在哪里、它是怎么保存的；里面还能看到 slide layouts，还有 layout masters、slide master，也就是幻灯片的母版。

    * 在内存里它就是一个目录树：这个目录树里面每一页幻灯片都有一个 `.xml`，每一个图片都是单独的一个文件；所以幻灯片里所有的东西都只是这样一个结构化的数据结构的描述，全是文本，都可以改。

    * > **提示**：解析这个文件我一直不认为是一个非常非常好的想法，因为它看到它的格式并不是非常的规整，也许我们需要一个更好的查询语言来改变它；实际上是有的，有那种像 COM 的 API 可以去改变这个文件。

### 用文件和目录摊平

* **摊平法**
    * > **定义**：第一个方法是使用文件和目录——因为 Unix 已经给了你一个 everything is a file 的接口。

    * 教务系统可以这样设计：为每一个同学建一个目录；在应用底下有课程号（代表某一次开课的信息），如果有一个同学选课，就建一个 enrollment 目录，每个同学放一个 markdown；教学周历、考核信息、教科书是什么，都可以存在一个目录里面。

    * 好处是所有东西都是平的，Unix 世界里所有的工具都可以用；不仅仅是 find、grep 这些工具，你的 agent 也可以用 Unix 世界里面的所有工具来编辑它——变成目录的结构其实是一个非常 agent-friendly 的方式。

    * 符号链接其实是一个引用：选课列表里的每个同学不再复制一份，而是直接放一个指向那位同学目录的符号链接，于是姓名、手机号码这些信息就全部都有了，而且没有再复制一份；如果有一天他更新了 email 或者手机号码，因为这是一个指向他目录的符号链接，同步地在我这里也会反映过来。

    * 个人知识库也可以这样搭：看到一个 paper 要读，就把它丢进一个目录（比如一个云端同步目录），后台会把它捡走、一页一页逐页 OCR 变成文本，把图和表也都读出来；读完以后再由另外一个更强的模型去 review 它，给我不同粒度的摘要，最细的粒度其实就是这个向量。

    * 这样就形成了文件系统里面的一个数据库系统，而它就是一个数据结构——由好多 structured paper 组成的数据结构；但它实际上所有的数据都是以文件的方式访问的，不仅我可以很容易地看它改它，agent 也可以很容易地看它和改它。

    * 它非常适合小规模的系统：我不在意我要服务多少人，只要我的算力还够就行。

* **一个跑在目录树上的真实系统**
    * 这个系统遵循了 Unix philosophy：所有提交都在一个目录底下；提交时会设置几个环境变量，一个用来找这一层目录、一个用来找下一层，如果刻意改掉就会得到一个 error message 说找不到——这个找不到实际上是因为在试图打开那个目录的时候找不到这个目录。

    * 每创建同一个提交的时候都会在这里留下一个压缩包；压缩包放进来以后，有另外一个监听程序不断地去找：如果你有一个压缩包但是它没有 result，我就找到这样的文件，然后送去给 online judge 跑，跑完以后就会把这个 result 存进来。

    * 一次提交由两个文件配对表示——压缩包是待判的输入，result 是判完的产出；监听程序要找的就是「有前者、没有后者」的那些目录。

    * 要统计某模块有多少份 accepted 的提交，就可以把那个模块下所有的 result 都打出来、grep 出 accepted、再数它有多少行。

    ```bash
    grep accepted M5/*.result | wc -l
    ```

    * 想 rejudge 也更容易：要 rejudge 某位同学的这次提交，就把那个 result 删了；如果想把所有的都 rejudge，就把该模块下面所有的 result 都删了——然后 OJ 就知道它该去捡那些还没有 result 的文件。

* **摊平的代价**
    * 第一个代价是 crash consistency 的粒度：文件系统本身有 crash consistency，但是当我想在这个「数据库」里维护这个数据结构的时候，尤其是当我有 multiple write 的时候，问题就来了。

    * 打比方，我希望把一位同学的选修课名单整个导入到这个系统的时候，其实就涉及到好多文件的写，而文件系统本身是不支持这个多文件写的 atomicity 的：写到第 50 个文件的时候系统 crash 了，那这时候我的数据结构其实就进入了一个不一致的状态。

    * 你需要要么手工写一个 fsck，要么就像 Git 那样有一个 append-only 的机制。

    * 也不是做不到：文件系统的 `rename` 是支持原子性的，所以很多时候你可以创建同一个目录、然后原子地把这个东西 `rename` 过去，这样来实现 atomicity。

    * 第二个代价是性能会稍微差一点：你每一次想要读写东西都会经过文件系统的系统调用，所以它就有比如路径的检查、metadata 的 fetch；而 metadata 它还会有一些其实你维护数据结构不需要维护的那些信息，比如你本来就不需要维护的 modification time。

    * 那就浪费了一些时间、空间和资源，然后就会带来一些这种隐藏的读写的放大；当然小规模的系统可以接受它，尤其是当跑一次业务的 cost 远远大于在文件系统上付出的 cost 时，而且你要经常 hotfix 问题时会选这样的架构——这是 agent 时代的一个标准答案。

### 在文件之上再造数据结构

* **把文件当成一个数据结构**
    * 文件它就是一个 byte array，而我们的磁盘也是一个 byte array；我们做了一次磁盘的虚拟化——在磁盘上面放了一个数据结构（可能是 FAT，也可能是基于 inode 的树和图），使得我在这里面可以有一个 `a.txt` 这样的 byte array 可以随机读写。

    * 既然我可以做这个抽象，通过一个数据结构把 byte array 抽象成好多好多散的东西，那我是不是也可以在一个 byte array 上面再做一个抽象，把它变成任何一个其他的数据结构呢？也可以的。

    * 你的 ELF 文件不就是一个数据结构吗？有一个 header，然后有 program headers，然后一个一个 `PT_LOAD` 的 section，然后还有什么符号表这种东西，它一段一段，然后都是指针指来指去，relocation 指针指来指去。

    * 所以如果你想实现一个教务系统，我就好像在我的文件上面实现一个文件系统一样：一个 `struct super_block` 放在我的文件的头上，就像 ELF 的 header 一样；它有两个部分组成，一个是 students（好多好多的 `struct student`），还有好多好多的 course。

    * 那所谓的实现一个教务系统，无非也就是增删改查：往学生的链表里面加一个学生，往课程链表里面加一个课程，往 enrollment（或者学生里面有个数据结构是他选的所有课的一个链表）再在链表链表链表链过去。

* **把文件映射到固定地址，指针就能落盘**
    * 虽然这个 byte array 是存储在磁盘上的、是一个 persistent 的文件，但是如果每一次都把这个文件 mmap 到一个固定的地址上，那我就可以直接在这个里面存指针了。

    * 举例：如果永远把 super block 映射到 `0x100000` 这个地方，而这个东西是 32 个字节，那第一个学生就放在这儿、地址就是 `0x100020`；如果有一个 `struct student *pointer`，这个 pointer 的值不就是这个 `0x100020` 吗？它就相当于有一个指针指着这个学生。

    * 文件里的字节每次都被映射到同一段虚拟地址，于是「文件内的偏移」就等价于「指针的值」，指针可以直接写进文件，跨进程重启依然有效。

    ```text
    file (persistent byte array)        fixed virtual address
    +--------------------------+        +--------------------------+
    | super_block  (32 bytes)  | mmap-> | 0x100000  super_block    |
    |   head = 0x100020        |        | 0x100020  struct student |
    |   count                  |        | 0x100040  struct student |
    |   write-ahead log        |        | 0x100060  struct course  |
    | students / courses ...   |        | ...                      |
    +--------------------------+        +--------------------------+
    ```

    * 演示里的 super block 还直接放了一个实现 crash consistency 的 write-ahead log，这也是完全可以的；学生链表的插入代码完全就是数据结构课上学的代码。

    ```c
    /* 从空闲链表分配一个节点，头插进学生链表 */
    student_t *s = allocate();          /* 在这个文件里分配内存 */
    s->next = superblock->head;
    superblock->head = s;
    superblock->count++;
    ```

    * 我必须要保证的是每一次我映射的时候它都是固定的位置，不然我就需要去 patch 里面所有的指针；也可以每一次打开这个数据库以后把这个 base 地址存下来，下次打开的时候再把这个 base 地址给减掉、再加上我那个新的 base 地址，理论上也可以把这个数据库映射到不同的地方。

    * > **提示**：这样做的效果是进程结束后文件中的数据完整地被 persist 下来了，再次打开它学生还是在的；如果做一个 sync 把所有的数据落到磁盘上，那么就算内存里面所有的信息都摧毁了，restart 以后系统依然是有这个文件的。

* **single-level store**
    * 顺着这个思路，很自然会有下一个想法：有没有可能以后我们的程序，整个程序的内存都能 persist 到磁盘上——相当于整个操作系统里面所有进程的内存，都是以 mmap 的形式映射到磁盘的。

    * 我们对内存是 volatile memory 这件事太过于习惯了：拔线拔电，你所有 ongoing 的东西都没有了；程序运行的状态、屏幕上面的这些字符、解析出来的东西，全部都是在内存里的，意味着它在系统 restart 或者断电以后就永远丢失了。

    * 但如果把程序的状态也 persist 到磁盘上，我们就得到了一个叫 single-level storage（single-level store）的操作系统；如果底下是一个非易失的 persistent memory 的话，这件事情就是可以办到的。

### mmap 的三个坑与最小 WAL

* **mmap 的三个坑**
    * 第一个坑：你 mmap 一个文件的 region，把这个磁盘上的数据搬到内存里，你对内存的修改不会立即反映到磁盘上——它是内存，访问速度非常快，甚至数据写到 L1 cache 里都不会立即送到 DRAM 去。

    * 如果你可以不断地读写这段内存，而操作系统希望把这个页面上的数据和磁盘上的数据保持同步，它就会在存储芯片上面造成大量的写入操作，这就相当于是一个无限大倍的写放大。

    * 而我们的应用程序不知道、操作系统也不知道应用程序想要把哪一部分数据 persist、想要哪一部分其实数据丢了也没有关系；所以 mmap 一个读写的文件，它在默认情况下是**不 writeback** 的：你所有的内存数据就那么写到内存里，然后如果丢了它就丢了。

    * 所以如果你希望写入的数据要进入磁盘，你就需要 `msync` 这个系统调用——synchronize a file with a memory map，它有三个参数：地址、长度和 flags。

    * 第二个坑：这个写回和 `fdatasync` 是不一样的，它只是告诉操作系统说我这段内存改了、你需要把它同步到磁盘上，而不是说等到这段内存写入磁盘以后再返回；所以用了 `msync` 以后还需要一个额外的 `fdatasync`——它不保证 crash consistency，和 crash consistency 没有任何关系。

    * 第三个坑：你还需要一个 `madvise` 的系统调用，它是 give advice about memory，可以告诉你这段内存应该用什么样的方式来管理；它的取值像 normal、random、sequential 等等，行为越来越复杂，甚至不是 POSIX 的 API（先出现在 BSD，后来 Linux 里也有了）。

    * > **提示**：操作系统既想要提供一个透明的抽象（这是一个 memory mapped file，你只要随便读写就可以），但是当你需要写回的时候，你又想要控制它的写回策略，这时候就引入了很多的复杂性——所以这可能并不是一个实现数据库真正非常好的 API。

* **一个最小可用的 write-ahead log**
    * 内存数据结构里这个 write-ahead log 的设计是：super block 开头是一个 32 位的 Magic（表明这是哪个 DB），接下来是一个 `write-ahead log:` 的前缀，冒号后面就是 write-ahead log 的内容。

    * 提交顺序是：① 把操作（比如 `add jyy`）写进 log entry；② `msync` + `fdatasync` 使这个命令持久化；③ 再去更新实际的数据结构；④ 确认这个东西落盘；⑤ 把日志清空，于是不需要 replay 它，一次事务的提交就完成了。

    ```text
    commit order of one transaction
      1. write the operation (e.g. add jyy) into the log entry
      2. msync + fdatasync          -> the command is now persistent
      3. update the real data structure (linked list, ...)
      4. make sure the data structure reached the disk
      5. clear the log entry        -> transaction committed

    crash recovery
      if the log entry is non-empty, replay it through the same execute()
    ```

    * 崩溃恢复就是：如果 log entry 非空，就用一模一样的代码——所有命令的入口都是 `execute`——上来做一次 write-ahead log replay，replay 完了以后日志又可以清空。

    * 这个实现不是 100% 的正确，稍微偷了一点懒：在 super block 里面放了一个大小为 1 的 log entry；理论上你可以做一个多 slot 的 write-ahead log，就可以做任意复杂的 write-ahead log。

    * 因为日志冒号后面的位置留了出来，甚至可以手工 hack：直接在日志里写一条命令（类似 `add 99` 某位同学），再进系统触发 replay，那位同学就真的被加上了——当然也可以用像 ext4 那样的 checksum 来确保这个部分是合法的。

    * > **提示**：要在这类文件里实现数据结构，基本就是实现一个 allocator（只是这个 allocator 比较特别，是要在这个地方分配内存的，它的 metadata 也应该在这个地方）以及一个 write-ahead log，剩下的和你数据结构课上的实现是一模一样的。

## 关系模型与事务

### 二维表与 join

* **为什么不用指针，而用二维表**
    * 我们描述这个世界时用的是 entities 加上所有的关系：人和人之间、事和事之间有各种各样的关系，你是属于这个班的、这个班是属于这个学校的。

    * 在数据结构实现的时候，我们是用 pointer 实现关系——本能地写一个 `struct enrollment`，它有一个 `struct student *` 指向一个学生，然后一个 `struct course *` 指向一门课程。

    * 但 pointer 不是在做 database 的时候一个非常好的抽象；如果你想要把现实中的各种各样的东西放到一个统一的抽象框架里，答案是一个非常简单的东西：二维表。

    * 学生表里一行是世界上面有概念的一个 entity，列是学号、姓名；课程表里一行也是一个 entity，列是课号、课程名——这就是一条一条的记录。

    * 想实现选课，就要再在表里添一张选课表：这张表里面每一行代表的就是一次选课，也就是「某个学生和某门课之间的一条关系」，每一行配一个选课 ID（编号本身并不重要）。

    * 到这一步，关系本身就从程序里面的指针变成了表里面的一行数据：原本要靠代码维护的关联，现在也成了可以被统一查询、统一修改的数据。

    * 关系模型的宣言是：*Future users of large data banks must be protected from having to know how the data is organized in the machine.*——你只需要在概念层次上描述数据，就可以在上面建出任何你想要的数据系统。

* **join 就是把笛卡尔积筛掉绝大部分**
    * 想查询某门课的选课列表，他给的答案在数学上非常有趣：把这里的每一个对象和那里的每一个对象做一个 cartesian product，也就是做一个乘法，全都乘一遍；这个操作在数据库里叫 join。

    * 赤裸裸地乘一遍听着就低效，所以 join 还要带一个条件，写成循环就是对学生、课程、选课表做三重循环，再 `if` 出 id 相等的那一组。

    * 这一个条件就把绝大部分组合都筛掉了：因为 `student_id` 是唯一的、`course_id` 在那张表里也是唯一的，所以对选课表里的任意一行记录来说，只可能有一个学生满足条件、只可能有一个课程满足条件。

    * 支撑这个抽象的信念是：一个选课系统里只有三种最小的事实——学生、课程、选课；理论上说，你可以用这三种最小的事实，把你想要的任何其他事实推导出来。

    * 性能来自 key：`student.id` 和 `course_id` 都是 primary key，既然是 key 就可以建索引直接查找；于是只需要遍历选课表，拿一个 3 去学生索引里找、拿一个 4 去课程索引里找，拼起来就是一个结果，两重循环直接被消灭掉了。

    ```sql
    SELECT courses.title
    FROM student
    JOIN take_courses ON student.id = take_courses.student_id
    JOIN courses      ON take_courses.class_id = courses.class_id
    WHERE student.name LIKE '张%';
    ```

    * 再往下，过滤条件可以随便加：可以只要名字以「张」开头的学生，可以只要这门课成绩还没录入的记录，可以只挑出成绩不及格的——基于一份已经分解到不能再分解的事实，你可以用这样的程序算出任何想要的东西。

    * 除了查询，写操作也一样：`SELECT` 是查询，`INSERT INTO` 是往表里插数据，`UPDATE` 同样是一种查询；合起来，这就是一门很小的 domain-specific 语言。

### transaction 与 ACID

* **ACID 中这门课要盯住的两条**
    * 数据库系统给你的是 ACID：A 是 atomicity 原子性，C 是 consistency 一致性，I 是 isolation 隔离性，D 是 durability 持久性。

    * **serializability 可串行化**：无论有多少个并发的事务（有的读、有的写），最终都能把它们排成一个全局顺序 1、2、3、4……好像 1 执行完再执行 2、2 执行完再执行 3，没有 weak memory model 那种行为；它是一种 strong serializability。

    * **strong crash consistency**：系统随时 crash 都不会造成任何数据丢失，而且支持任意长的 multi-write——对照之下，文件系统总是不一致的。

* **transaction 的语义**
    * 它的语义是：`BEGIN` 之后你随时可以 `ABORT`，一旦 abort，前面那些「看起来已经执行了」的操作全部消失；只有到 `COMMIT` 的那一刻，所有过去执行的操作才立即生效，而且是 all or nothing——要么全部生效，要么完全不生效。

    * 在一个 transaction 里你可以写任何代码，任何 Turing-complete 的计算，甚至可以 sleep；这个 transaction 可以任意长，无限长。

    * > **易错点**：这里的「原子」不是单条指令的原子，而是跨越成千上万条 load/store、可能持续任意长时间的一整段计算；线程可能在第 9999 步消失，而它之前的 9998 步对别人是不可见的。

* **看着像一把大锁，性能却可能更好**
    * 它的用法看起来就像一把大锁保平安——`transaction begin` 和 `transaction commit`，它从来没有让你去建什么细粒度的锁，只有一个 begin、一个 commit。

    * 可是它的性能却可能远远优于你自己细粒度加锁：你有一百个、一千个线程往同一张表里插入，它都能并行写入，后台用 append-only 的 LSM tree 之类的东西、或者高性能并发数据结构替你兜底，崩溃恢复还完全自动。

    * 这也是商用数据库相比文件系统一直以来最大的优势：二十年前的程序员从来没有受过 crash consistency 的教育，却要在文件系统之上构建 persistent 的数据结构，那天然就非常困难——数据库说：你只要交给我，所有事情都能搞定。

### 并发控制

* **两阶段封锁（two-phase locking）**
    * 想法非常直观：我想读 x 就上它的读锁，我想写 x 就上它的写锁，一边读写一边加锁；我会按行、按 column、按分块去加锁，粒度可以很细。

    * 如果两个事务读写的是表里互不相干的部分，它们分别上锁、互不冲突，就能一起提交。

    * 但它故意埋了一个坑：`x=1, y=2` 和 `y=1, x=2`，这就是一个非常典型的 A-B、B-A 死锁。

    * > **易错点**：在操作系统里这种情况是可以用 lock ordering 禁止的（lockdep 会报错，内核里这么写代码就禁止你运行），**数据库不行**——因为数据库的查询是别人写的，甚至业务逻辑本身就是先写 A 再写 B，而另一个业务逻辑先写 B 再写 A；这些逻辑里包含图灵完备的计算，算出结果之后再去写某张表里的某个值，没有办法统一规定顺序。

* **死锁检测器**
    * 所以数据库一般都会带一个 deadlock detector：它维护一张图，跟 lockdep 一样，检查有没有 A 到 B、B 到 A 最后连成一个圈。

    * 一旦成圈就破圈：挑一个 transaction（比如 T2），让它 abort、回滚，它做过的事情全部作废、从头再来一次，剩下那个 T1 就可以继续，直到 commit。

    * 这里面还有无穷的复杂度：回滚到什么程度、怎么回滚；正因为如此，在 1980 年代实现一个好的 database system，对当时的程序世界是一个巨大的冲击。

* **多版本并发控制（multi-version concurrency control，MVCC）**
    * 在任何时刻，你的数据结构都有一个快照，也就是当前所有数据的状态；当作 transaction begin 的时候，你就想象自己已经把现在的一切都 commit 过了，当前状态是 OK 的。

    * 然后你直接 checkout 一个新的 branch——相当于把这个世界复制了一份，你就在这个世界上面改。

    * 读，我永远读我自己的这个世界，别人怎么改都跟我没关系；写，我也直接写进我的世界，不会对 main 分支造成任何修改；如果同时有多个并发线程在做 transaction，没问题，每个都 checkout 出一条新分支，各自做各自的。

    ```text
    main  o----------------------------------------o------>  已提交的世界
           \                                        ^
            \ transaction begin                     | merge: 无冲突则提交
             +--o-- T1: read x, write x=1 ----------+
             |
             \ transaction begin
              +--o-- T2: read y, write y=2 ---------x------>  与 T1 写同一行 -> 冲突，事务被摧毁
    ```

    * 做完之后它试图对 main 发起一个 merge：如果 T1 改了这一行、T2 改了另一行，merge 的时候没有 conflict——本质上这类似一份 write-ahead log，把操作 replay 一遍就行，两个都能提交。

    * 但如果两个分支写的是同一行、写的是不同的值，那对不起，其中一个分支就会被摧毁；所以它叫 multi-version。

    * > **提示**：它和 Git 还是有本质区别——Git 可以让你手动 resolve merge conflict，数据库不行，因为 transaction 中间可以有任何任意的计算，你的值可以是由程序算出来的；数据库系统只能管这段 transaction 本身，没法替你判断「两边算出来的值哪个是你想要的」。

### 查询重写与 SQLite

* **数据库里藏着一个编译器**
    * 回头看那条 SQL，它本质上是一段程序；既然是程序，就意味着可以做 rewriting。

    * 今天你们的编译器有 `-O0`、`-O1`、`-O2`，它本质上就是好多好多的 rewriting rules；数据库不知道为什么走上了完全不同的路线，但它们的本质都是有一大堆 rewriting rules。

    * 举个例子：如果把这个循环往外提，就能提高性能——把循环外提之后，那两层循环就被消灭掉了，可以直接查 key。

    * 数据库就是这样不断地 rewrite、rewrite、rewrite，最后变成一个高效执行的 plan、一段可执行的程序，再落到磁盘上的高性能数据结构，比如 B-tree 这样的索引结构；再往后还有缓存、分库分表、并发控制、读写分离，各种手段。

    * 结果是：一个单机上的数据库，只要不是大到国民级的应用，全部都能搞定——你的一台服务器或者一台 PC，只要你有足够的磁盘带宽、内存带宽和足够多的线程，它就可以帮你支撑一个非常非常大的应用。

* **SQLite**
    * > **定义**：一个小而快、自包含、高可靠、全功能的 SQL 数据库引擎，它是世界上使用最多的数据库引擎——你每一个 Android app、每一个苹果 app 里都带着一个 SQLite 引擎。

    * 手机里那些 persistent 的小拨片，你可能会想它是不是每一个 preference 就是一个文件、把 0 或者 1 写到那个文件里、再做一个 `fsync`；实际上这些是由一个很小的 SQLite 数据库来管理的。

    * 它第一，数据库就是一个文件；第二，整个 library 就是一个文件。

    * 它是 zero-configuration 的，你只要有那个 `libsqlite3.so`，就能享受数据库的所有好处：想做一个 preference 界面、想拿到一份动态构建的设置列表，直接一句 SQL 查询查出来；想改一个值，也是一句 SQL。

    * 而且它保证你的数据安稳地落到磁盘上，你不用再纠结「我写一个配置文件，需不需要 sync 它」。

## 规模化的分野

### SQL 的边界

* **一张表装下聊天记录**
    * 聊天记录本质上就是可以建模的，甚至可以就一张表：聊天记录就是一个气泡，气泡里面是一个 XML 文档，当然还有不少有意思的、几乎是 hard-coded 的编码规则。

    * 比如长按消息可以「回复某个人」——那是把那条消息拷贝了一份，在拷贝的消息下面加了好多个减号，然后这才是你的回复；解析这个格式，如果发现是这种格式，就自动 link 回那条被回复的消息。

    * 这样能在老版本、iPad 版、网页版上保持兼容：不支持的客户端会直接把那一堆减号原样显示出来。

    * 那么「点开最近十个聊天」就是一条 SQL：从聊天记录表里按发送者与接收者过滤，按时间倒序取前十条。

    ```sql
    SELECT *
    FROM chat_records
    WHERE sender_id = :me AND receiver_id = :peer
    ORDER BY time DESC
    LIMIT 10;
    ```

* **SQL 的极限与滥用的代价**
    * 在百万、千万用户的时候，一台机器、一个 production 的 SQL Server 其实就能处理这样的性能。

    * 但到了那个量级 SQL 数据库的压力就很大了：压力全给到数据库引擎，你需要做分库分表、读写分离，做正确的索引，做各种各样的缓存和优化。

    * 问题的根源在于 SQL 提供的这套查询优化本身：它说程序员不需要管查询是怎么执行的，你只负责把 fact 写好、把提取 fact 的查询写出来就好——**你永远无法预知程序员会写出多么糟糕的 query**。

    * 见过那种互联网工厂里面向企业服务的系统就知道：你在电商平台下的一单，看起来只是一单，背后涉及的表非常非常多，一层一层包着；你会看到 50 个表 join 在一起，还有日期、limit 各种条件，剩下就是数据库在那儿疯狂地根据实际执行去挑一个好的计划。

    * 数据库提供了这些功能，就很难避免它被滥用，而滥用就意味着一个 performance bug；用户量小的时候它不致命，可它会在数据库不断增长的过程中越来越慢，使得你去优化它可能会有 10 倍甚至 100 倍的性能收益——这是任何 systems 都没法避免的技术债。

    * 所以用 SQL 开发这样量级的系统，最终都不可避免地要陷入非常复杂的局面，或者需要一个特别好的架构师来帮你把数据库管好。

    * 然后还是不行：总有一天我们要走向分布式——一台机器怎么也容不下全国人民的聊天记录；先把不同的表丢到不同的机器上，当一张表大到一台机器放不下，就把这张表切成好多部分分到不同机器上。

### key-value 与内存缓冲层

* **key-value 够用了**
    * 大家用得最多、最简单、又够用的数据结构是 key-value dictionary：一个 key 和一个 value，就是一个 map，或者一个 unordered map，或者就是 Python 里的 dict。

    * 要管理一个用户的数据，就把 UID 拼在后面做 key，取出一个字符串——比如一个 JSON——就是这个人的信息，这是 read；要 write，就把 serialize 好的 JSON 再写回 `user:UID` 这个 key 里。

    * 再扩展一点也行：key `enrollment:1` 指向一份 JSON（他选的课），而这个 JSON 里的 enrollment 可以是一个列表；列表可以是 append-only 的，也可以清零——把所有的选课记录和退选记录都 append 进去，这不就是一个教务系统了吗。

    * > **提示**：这里用到了一个关键判断——一个学生的选课退选不会特别多，你不会选一万个课再退一万个课（真发生的话，多半是你自己写的脚本出了 bug）；你对系统里的某些东西是有 knowledge 的，而 append-only 大家都知道比较容易实现。

    * 于是每次想看这个学生的选课列表，就把它读出来 replay 一遍；也可以把 replay 完的当前 enrollment 缓存成一个视图。

    * 点赞也一样：直接往 list 里 append 一个——全球的人都在给你点赞也不要紧，因为 append 比「load 加一再 store」这样一个读写的 transaction 性能要好，append-only 更容易实现、consistency 也更容易保证；你甚至可以从好几个地方分别收到列表，在好几个线程里并行地 append，最后串起来再 append 回去，这也是正确的。

    * 这样的数据结构好实现，也好扩展：给 key 做 hash 就自动 load balance（只要 hash function 足够好，每个 key 就近似变成一个 random number，有多大台机器就把这个随机数模机器数量，请求就送到一台随机的机器上），自动 load balance 也自动 scale；因为 everything is append-only，实现可以很高效，比如用 LSM tree 这样的结构；分布式的高性能、crash consistency，也都可以实现。

* **内存里的缓冲层**
    * key-value 甚至不必做成数据库，也可以做成 an in-memory 的东西：所有请求先进入内存里的 key-value，它隔一段时间把请求合并了，再写到后面的 database 里。

    * 比如统计点赞数量：如果你每一次点赞都形成一个 transaction 把它 persist 下来，代价是比较大的；但这个地球上真的有很多人在给你点赞的时候，你完全可以在内存里放一个 counter——点赞这个数据对你来说不是那么重要，丢了损失也没那么大。

    * 进了内存以后每一次都是加一（可以是一个 list 的 append，也可以就是一个 atomic 的加一，key 映射到一个 integer）；每隔比如一分钟，我就知道这个 counter 走了多少，这时候再写一条 SQL：从 database 里把点赞数取出来，加上这一分钟里新点的量，再写回去。

    * 绝大部分事情都在内存里做，性能、scalability、并行度都上来了。

    ```text
    client 请求(点赞) --> [ in-memory key-value / Redis ]  --每 N 秒合并写回-->  [ 磁盘上的 database ]
                           key -> integer counter                                SQL / 持久化
    ```

    * 那层东西就是 Redis：它也是一个 key-value，支持 string、list、set、hash，可以做一个高性能的缓存，做数据库的缓存，也可以做这样一层缓冲。

### 各种数据库的分野

* **从 document 到 NewSQL**
    * key-value 用起来终究还是不如 SQL 好用：SQL 的意思是我可以随便写——我可以写一个 50 层循环，你就自动帮我搞定。

    * MongoDB：一个 document-based database，所有操作都是 document-based，本质是 key 到一个 JSON；JSON 有一些数据结构的操作，你可以往里 append messages，结构化存储就比一个单纯的 list 更好用。

    * Cassandra：一个 column database，也有查询语言（CQL），也是 table 的模型，但它不给你 full SQL 那种完整支持。

    * 也有数据库想提供几乎完整的 SQL 支持，最有代表性的是 TiDB——一个国产的、出海非常经典的 startup 案例；还有 Google 的 Spanner 和 CockroachDB。

    * 这些尝试本质上是「做一个够用、但可以 scale out 的子集」：业务踩了很多坑之后回头会发现，SQL 给我们太多了——给得太多，一旦滥用就带来 performance bug；而在某些应用里给少一点，实现会更容易、性能可能更高、更容易分布式，也基本够用来构建你需要的应用。

| 类型 | 代表 | 模型 | 取舍 |
| :--- | :--- | :--- | :--- |
| 关系型 SQL | PostgreSQL、SQL Server | 表 + join，任意查询 | 表达力最强，但可能被滥用成 performance bug |
| key-value | Redis、dict/map | key → value（字符串、JSON、list） | 最简单最够用，表达力有限 |
| document | MongoDB | key → JSON 文档，可往里 append | 比单纯的 list 好用，但不是 full SQL |
| column | Cassandra（CQL） | table 模型，只给部分查询能力 | 用表达力换可扩展性 |
| NewSQL | TiDB、Spanner、CockroachDB | 几乎完整的 SQL | 试图两全 |
| vector | 向量数据库 | 向量 + 近邻搜索 | 用距离度量语义相近 |

* **共同的定位**
    * 前面讲的 SQL、key-value、document、column 本质上都是数据结构、都是程序。

    * 它们的目的是在 infrastructure 这一层把 crash consistency、分布式这些事情屏蔽掉，只给你一个 API，你直接调它，它就把所有事情都搞定。

### 向量数据库

* **vector database**
    * > **定义**：把这些向量存下来、然后做 nearest neighbor search（近邻搜索）的数据库；你可以有上亿的文档、几万维的向量，任何时候给出一个向量，它就能在数据库里找到和它邻近的那些向量。

    * 度量可以用 dot product，也可以用 cosine distance（余弦距离）；基本上，向量的距离越近，就意味着两个文档的内容越接近。

    * 这些向量其实可以存到 extended attribute 里，也就是 xattrs 里。

* **一个实测的相似度聚类**
    * 把每一次课的提纲（每一页幻灯片有一个有意义的名字）用一个模型变成一个 4096 维的向量之后，按向量距离量出来的课程相似度是这样的。

    ```text
    concurrency 簇    [ 13 14 15 16 17 18 19 20 21 ]  <- 聚成一团，彼此都近
    文件系统 / DB 簇   [ 24 25 26 ] --强关联-- [ 27 database ]  (27 与 26 稍弱)
    孤立点              [ 4 agentic AI ]   [ 6 进程地址空间 ]
    ```

    * 讲 concurrency 的那几讲全都聚在一起；讲 database 的那一讲和讲文件系统实现的那一讲有比较弱的关联，但和讲文件系统的那三讲有非常强的关联。

    * 讲 agentic AI 的那一讲是一个孤岛，和其他所有讲都不太相关——它自己识别出来了这一节课是 off-topic 的；讲进程的地址空间的那一讲也显得稍微有一点孤立。

* **结构化与向量的融合**
    * 未来这些会融合到一个信息系统当中：结构化的数据结构肯定不会消失，因为它是保存数据非常 efficient 的办法。

    * 但与此同时，数据库里又不可避免地会有向量的部分：理论上每一个 record、每一张表的每一条记录都可以 associate 一个向量，然后我们就可以智能地去查询这个世界里的东西。

    * 比如构建一个论文数据库，能不能把和某个讨论相关的论文找出来，甚至是弱相关的东西，能不能给我一点启发——智能化的应用在未来会变成什么样不知道，但世界会变成这样。

    * 回到应用本身：你看到 SQL、NewSQL、Vector Database 好像越讲越复杂了，但本质上它们都是某一个数据结构的增删改查——打开一个教务系统，我的功能就是增删改查；做的一个 PowerPoint，也是增删改查；理解任何一个产品的设计的时候，背后的那些数据管理的道理都是通的。
