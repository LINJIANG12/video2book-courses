# 死锁

## 死锁的处理策略

* **预防死锁（Deadlock Prevention）**

    * 思路：通过破坏死锁四个必要条件（互斥、不剥夺、请求和保持、循环等待）中的至少一个，使死锁不可能发生
* **避免死锁（Deadlock Avoidance）**

    * 思路：不破坏必要条件，而是在**每次分配资源之前**判断这次分配是否会使系统进入不安全状态，只放行不会导致不安全的请求；代表算法是银行家算法
* **死锁的检测和解除（Deadlock Detection & Recovery）**

    * 思路：允许死锁发生，用检测算法判断系统当前是否已发生死锁，检测到之后再设法解除

## 预防死锁

### 破坏互斥条件

* **SPOOLing 技术**

    * > **定义**：把必须互斥使用的独占设备在**逻辑上**改造成可以共享使用的设备的技术
    * 机理：以打印机为例——各进程的打印请求首先被输出进程接收并暂存，进程随即可以继续往下执行；输出进程再把各请求依次放到打印机上按序输出，在进程眼中它面对的就是一台共享设备
    * 局限：并非所有设备都能被改造成共享设备；且出于系统安全考虑，很多地方必须保留互斥性，因此该思路适用范围不广

### 破坏不剥夺条件

* **方案一：得不到新资源就全部释放**

    * 规则：进程请求的新资源暂时得不到满足时，必须立即释放自己已保持的所有资源，以后再用时重新申请
* **方案二：操作系统协助强行剥夺**

    * 规则：进程需要的资源正被其他进程占用时，由操作系统协助把该资源强行剥夺过来；一般要考虑进程**优先级**，优先级高者可剥夺低者——与剥夺调度方式同理（如处理机被更高优先级进程抢走）
* **缺点**

    * 实现比较复杂
    * 强行释放或剥夺可能使进程之前阶段的工作全部失效，故一般只适用于**容易保存和恢复状态**的资源（如 CPU 被剥夺时需保存寄存器等中间数据）
    * 反复申请和释放增加系统开销，降低系统吞吐量
    * 方案一中暂时得不到资源就要全部放弃，若反复发生，进程可能一直处于饥饿状态

### 破坏请求和保持条件

* **静态分配方法**

    * > **定义**：进程**运行之前一次性申请完全部所需资源**；不能全部满足则暂不投入运行，一旦投入运行，这些资源在整个运行期间都归它所有
    * 机理：进程投入运行后已拥有全部所需资源，不会再发出新请求，不存在「一边保持不放、一边请求新资源」的状态
    * 优点：实现比较简单
    * 缺点：只使用很短时间的资源也被整个运行期占用而大量闲置，系统资源严重浪费、利用率降低
    * 缺点：可能导致饥饿——A 类进程只要资源一、B 类只要资源二、C 类必须同时要两种；若 A、B 类进程源源不断到达，两种资源一释放就立刻分给下一个 A 或 B，C 类进程永远等不到两者同时空闲

### 破坏循环等待条件

* **顺序资源分配法**

    * > **定义**：给系统中各种资源编号，规定进程必须**按编号递增的顺序**依次请求资源；编号相同的同类资源必须一次申请完
    * 机理一：只有占有小编号资源才有资格申请大编号资源，已持有大编号资源的进程不可能反过来申请小编号资源；相互等待只能沿小号指向大号的方向发生，等待环闭不上，循环等待链无法形成
    * 机理二：任意时刻必有一个进程持有的资源编号最大，此时更大编号的资源全部空闲；该进程的后续申请必然畅通无阻，至少它能顺利执行结束，所以不可能出现所有进程都阻塞的死锁
    * 缺点：需要给所有资源编号，新增一种设备可能要把所有设备重新编号一遍
    * 缺点：实际使用顺序与编号递增顺序不一致时造成浪费——如打印机 5 号、扫描仪 7 号，进程必须先申请并长期占有暂时不用的打印机，直到用完扫描仪再回头用打印机
    * 缺点：用户编程麻烦——申请代码的先后被编号定死，换一个编号规则相反的系统，程序中申请资源的代码顺序也必须跟着改
* > **提示**：这部分容易结合死锁四个必要条件在选择题中考察，以理解为主；可回头分析哲学家进餐问题的三种解法分别破坏了哪个必要条件

## 避免死锁：银行家算法

### 安全序列与安全状态

* **安全序列（Safe Sequence）**

    * > **定义**：按该序列的顺序依次给各进程分配资源，各进程都能顺利完成，并把自己手里的资源依次归还系统
    * 安全序列**不一定唯一**：下例中 T→B→A 与 A→T→B 都是合法的安全序列
* **安全状态（Safe State）**

    * > **定义**：能找到一个安全序列的系统状态；安全状态一定**不会**发生死锁
* **不安全状态（Unsafe State）**

    * > **定义**：找不到任何安全序列的状态，之后**有可能**所有进程都无法顺利执行
    * 不安全未必真的死锁：若各进程没有提出会卡住的请求，系统只是处于不安全状态而未死锁；若有进程提前归还资源，系统还可能重新回到安全状态
    * > **易错点**：进入不安全状态未必发生死锁，但**发生了死锁一定处于不安全状态**——死锁状态是不安全状态的子集
* **经典银行家例子**

    * 场景：银行家掌握 100 亿资金；企业 B/A/T 的最大需求分别为 70/40/50 亿，已分别借走 20/10/30 亿，最多还会借 50/30/20 亿（最大需求 − 已借走），银行家手里还剩 40 亿
    * B 想再借 30 亿：答应后银行只剩 10 亿，而三家之后各还可能再借 20 亿，同时提出时无法满足，所有企业都被卡住 → 拒绝，不安全
    * A 想再借 20 亿：答应后银行剩 20 亿，先全部借给 T（T 的最大需求 50 亿得到满足），T 归还 50 亿后再满足 B，最后补足 A 还差的 10 亿 → 依次满足、依次收回，安全
* **避免死锁的核心思想**

    * 在资源分配**之前**预判：分配后会进入不安全状态就不允许本次分配；分配后仍安全才真正分配
    * 银行家算法由迪杰斯特拉提出，最初用于确保银行发放现金贷款不会出现「不能满足所有客户需求」的情况，后被引入操作系统用于避免死锁

### 银行家算法的数据结构

* 设系统有 $n$ 个进程、$m$ 种资源
* **Max 矩阵**：$n \times m$，各进程运行前声明的对各类资源的**最大需求数**
* **Allocation 矩阵**：$n \times m$，目前已分配给各进程的各类资源数
* **Need 矩阵**：各进程**最多还需要**的各类资源数

$$Need = Max - Allocation$$

* **Available 向量**：长度为 $m$ 的一维数组，系统当前还剩余的各类资源数
* **Request 向量**：长度为 $m$ 的一维数组，某进程本次申请的各类资源数
* 示例数据：5 个进程 P0~P4，3 种资源初始总量 (10, 5, 7)；P0 的最大需求 (7, 5, 3)、已分配 (0, 1, 0)；系统已分配合计 (7, 2, 5)，剩余可用 **(3, 3, 2)**

### 安全性算法

* 目标：尝试找出一个安全序列，判断系统当前是否处于安全状态
* 流程：每轮拿 Available 与各进程的 Need 逐一对比，找到能满足其最大需求的进程 → 把资源全部分给它，它必能顺利执行结束并归还全部资源 → 将它加入安全序列，Available 更新为「该进程已占有量 + 原剩余量」→ 重复，直到所有进程都进入安全序列（安全）或再无可满足的进程（不安全）
* 示例：剩余 (3, 3, 2) 可同时满足 P1 与 P3，两者一起加入；归还后可用资源变为 (7, 4, 3)，已能满足剩下的 P0、P2、P4 全部需求 → 存在安全序列，系统安全
* 不安全示例：改大部分进程的 Max 后，P1、P3 加入后可用 (7, 4, 3) 仍满足不了 P0（第一种资源不够）、P2（第二种资源不够）、P4（第三种资源不够）→ 找不到完整安全序列，处于不安全状态，**有可能**发生死锁
* 笔算技巧：考试中不必逐轮只推进一个进程，能同时满足几个进程就一起加入安全序列，速度更快
* 考察方式：一般给出 Available、Max、Allocation，Need 需自己用 $Need = Max - Allocation$ 算出后再判安全性；先理解算法逻辑再实现代码，不要反过来

### 银行家算法流程

* 设进程 $P_i$ 提出申请向量 Request（如 P0 申请 (2, 1, 1)），算法整体是对本次申请的**预判**：

```text
第一步：Request[i] ≤ Need[i]？
        是 → 申请未超过其声明的最大需求，合理，继续
        否 → 出错（申请量超过之前声明的最大需求）

第二步：Request[i] ≤ Available？
        是 → 继续试探分配
        否 → 系统尚无足够资源，该进程阻塞等待

第三步：试探性分配（只改数据做预判，不是真分配）
        Available     -= Request[i]
        Allocation[i] += Request[i]
        Need[i]       -= Request[i]

第四步：用安全性算法检查试探分配后系统是否仍安全
        安全   → 正式把资源分配给进程
        不安全 → 回滚到分配前的数据，不答应本次请求，进程阻塞等待
```

* 示例数值（P0 申请 (2, 1, 1)）：Available (3, 3, 2)→(1, 2, 1)；P0 的 Allocation (0, 1, 0)→(2, 2, 1)；P0 的 Need (7, 4, 3)→(5, 3, 2)
* 与安全性算法的分工：银行家算法负责「检查申请是否越界 → 检查剩余资源够不够 → 试探分配 → 拍板或回滚」；安全性算法负责「逐个找可满足最大需求的进程，加入安全序列并更新可用资源，直到确认所有进程能否全部入列」

## 死锁的检测

### 资源分配图

* **进程节点**

    * 每个节点对应一个进程
* **资源节点**

    * 每个节点对应**一类**资源，一般画成矩形；框内的小圆表示这类资源的个数（如 R2 画两个小圆即有两个 R2）
    * > **注意**：资源节点对应的是一类资源，不是一个资源
* **请求边**

    * 从进程节点指向资源节点，表示该进程对这类资源的一个请求；每一条边都对应一个资源
* **分配边**

    * 从资源节点指向进程节点，表示这类资源已分配给该进程一个

### 死锁检测算法（化简资源分配图）

* 核心思想：若系统剩余的可用资源足够满足某进程的请求，该进程就不应该被阻塞、能顺利执行下去；执行结束它会归还自己持有的全部资源、且进程结束后不再请求任何资源，因此可以**消去与它相连的所有边**；归还的资源又可能唤醒其他阻塞进程，如此继续化简
* > **定义**：若按上述方法能消除图中**所有的边**，则该资源分配图是**可完全简化的**，意味着此时没有死锁发生
* 化简到不能再消、图中仍残留边 → 系统发生了死锁；**最终还连着边的那些进程才是处于死锁状态的进程**（边上能消光的进程并未死锁）
* 本质：化简过程等价于找一个安全序列——能依次消光所有边 ⇔ 所有进程能依次顺利结束 ⇔ 安全 ⇔ 无死锁
* > **注意**：算法一句话概括——依次消除与「不阻塞进程」相连的边，直到无边可消；不阻塞进程即申请的资源数量仍然足够的进程
* 不可能化简的反例：P1 请求**两个** R2、另有一个持有 R2 的 P3，R1 与 R2 均已分配光 → P1、P2 都阻塞，只有 P3 能执行；P3 结束归还后 R2 仅空出一个，仍不满足 P1 需要的两个 → 化简停止，死锁发生
* **死锁定理**

    * 在资源分配图中找一个**既不阻塞、又非孤立点**的进程：不阻塞指申请的资源数量足够满足其需求；非孤立点指至少有一条边与它相连
    * 消去该进程所有的请求边和分配边，使之成为孤立点；它释放的资源可能唤醒其他进程，使后者也变为既不阻塞又非孤立点的进程，继续消边
    * 能用这种方式消掉所有的边 → 图可完全简化，没有死锁；反之图不可完全简化 → 发生死锁

## 死锁的解除

* 前提认知：检测出死锁后应立即解除；且**并非系统中所有进程都处于死锁状态**——化简后还连着边的才是死锁进程（资源剥夺法挂起的必须是死锁进程）
* **资源剥夺法**

    * 从死锁进程中选择一个或多个暂时**挂起**（暂时挪到外存），抢占它现在持有的资源，分配给需要的其他进程；同时应防止被挂起的进程长时间得不到资源而导致饥饿
* **撤销进程法（终止进程法）**

    * 强制撤销部分甚至全部死锁进程，并剥夺这些进程的资源；简单粗暴，但可能让已运行很久、接近结束的进程前功尽弃、从头再来，代价可能很大
* **进程回退法**

    * 选择一个或多个死锁进程，让它们回退到足以避免死锁的地步（如回退到只持有一个 R1 的时刻，腾出资源先让别的进程执行下去）；需要记录进程的历史执行信息、设置还原点，实现不容易
* 三种方法本质上都是让某个进程做出牺牲，牺牲者的选择角度：

| 考虑角度 | 选择逻辑 |
| :--- | :--- |
| 进程优先级 | 优先牺牲优先级低的进程 |
| 已运行时间 | 执行越久，回退或撤销的代价越大，选执行时间少的 |
| 还有多久完成 | 马上就能结束的进程优先获得资源，牺牲离完成还远的 |
| 已占用资源数 | 牺牲持有资源多的进程，死锁局面能尽快解除 |
| 交互式还是批处理式 | 干掉交互式进程用户极其不爽，优先牺牲批处理式进程 |
* > **提示**：考试中死锁检测部分常考（两种节点、两种边的含义 + 检测算法本身，也可能与数据结构结合）；死锁的解除一般只考选择题

## 内存的基本知识

### 内存的作用

* 内存的作用是**存放数据**：程序执行之前，必须先把相关的程序和数据放入内存，才可以被 CPU 处理
* 原因：程序平时放在外存（磁盘）中，磁盘读写慢而 CPU 处理快；为缓和 CPU 与外存之间的速度矛盾，必须先把待处理的程序和数据调入内存

### 存储单元与编址方式

* > **定义**：存储单元是内存中用于存放数据的最小单元；内存被划分为一个个存储单元，编号一般从 0 开始依次递增，每一个地址对应一个存储单元
* **按字节编址**：一个地址对应的存储单元存放 1 个字节（8 个二进制位）；操作系统课程的大部分题目都是这种情况
* **按字编址**：一个存储单元存放一个字；一个字是多少比特（16 位、32 位、64 位等）要根据题目给出的字长条件判断

### 容量单位与地址位数

* 数量换算：1K = $2^{10}$，1M = $2^{20}$，1G = $2^{30}$
* 数据单位：大 B（Byte）指字节，小 b（bit）指比特（一个二进制位）；1 Byte = 8 bit
* 4GB 内存、按字节编址：共有 $4 \times 2^{30}$ 个存储单元，即 $2^{32}$ 个地址，因此地址至少要用 **32 个二进制位**表示
* > **提示**：二进制与十进制转换不熟练的话要专门练习，这一步直接决定后续做题速度

### 指令的执行

* 高级语言代码经编译后形成等价的机器语言指令序列：如 `x = x + 1` 编译后大致对应三条指令——数据传送（从 x 所在内存单元取到寄存器）、加法（寄存器内容 +1）、数据传送（把寄存器内容写回 x 的内存单元）
* 指令由**操作码**（指明这条指令要干什么）和后续参数（指明操作的内存地址、寄存器编号等）组成；操作码相同的两条指令干的是同一种事情，只是参数不同
* 本质：CPU 执行一条条指令的过程，就是在处理内存或寄存器中的数据；定位这些数据靠**地址**——内存有编址，寄存器也有编址，指令中的参数告诉 CPU 去哪些地址读写数据

## 逻辑地址与物理地址

* **逻辑地址（Logical Address，相对地址）**

    * > **定义**：相对于进程起始地址的地址；程序经编译链接后形成的指令中指明的就是逻辑地址
* **物理地址（Physical Address）**

    * > **定义**：数据最终在内存中的实际存放地址；程序最终被装入内存的什么位置事先无法确定
* 问题：若进程不是从地址 0 开始存放（如从 100 开始），指令里写死的逻辑地址 79 会让 CPU 把数据写到 79 号单元——那片空间极可能属于其他进程，是危险的越界写；正确位置应是 100 + 79 = **179** 号单元
* 内存管理要解决的核心问题之一：**如何把指令中指明的逻辑地址转换为正确的物理地址**（本部分默认系统给进程分配一片连续的内存空间）

## 三种装入方式

### 绝对装入

* 时机：**编译时**完成逻辑地址到物理地址的转换——若事先知道装入模块从哪个地址开始存放（如 100），编译程序直接把指令中的地址改成正确的绝对地址（x 的地址改为 179）
* 局限：必须事先知道装入位置，灵活性特别差，换一台不能从该位置存放的电脑程序就无法执行；只适用于**单道程序环境**（早期还没有操作系统的阶段）

### 可重定位装入（静态重定位）

* 时机：装入模块中指令使用的仍是**从 0 开始的逻辑地址**，地址转换留到**装入内存时**一次性完成——装入的同时把程序中所有地址相关参数加上起始物理地址（全部 +100）
* 特点与局限：给作业分配的地址空间**必须连续**；作业必须**一次全部装入**内存；程序在**运行期间不可移动**——物理地址已写死在指令里，数据一移动地址指向就会出错

### 动态重定位（动态运行时装入）

* 时机：程序装入内存后，指令当中**仍然使用逻辑地址**；系统设置专门的**重定位寄存器**存放进程在内存中的起始地址，CPU 每次访问内存时把逻辑地址与重定位寄存器的值**相加**得到最终物理地址：79 + 100 = 179
* 运行期移动方便：把进程数据移到新位置（如从 200 开始）时，只需修改重定位寄存器的值
* 优点：可把程序分配到**不连续**的存储区；运行过程中**只需装入部分代码**即可投入运行；可在运行期间**动态申请分配内存**；便于**程序段的共享**；可给用户提供比实际存储空间**大得多**的地址空间
* 现代操作系统采用的方式

### 三种方式对比

| | 绝对装入 | 可重定位装入（静态重定位） | 动态运行时装入（动态重定位） |
| :--- | :--- | :--- | :--- |
| 指令中的地址 | 编译时直接生成绝对地址 | 逻辑地址 | 逻辑地址 |
| 转换时机 | 编译时 | 装入内存时一次性重定位 | 运行时每次访存：逻辑地址 + 重定位寄存器 |
| 硬件要求 | 无 | 无 | 需要重定位寄存器 |
| 局限 | 必须事先知道装入位置，只适用于单道程序环境 | 空间必须连续、必须一次全部装入、运行期不可移动 | 现代系统采用，运行期可移动、支持不连续分配 |
| 灵活性 | 特别低 | 中 | 高 |

## 从写程序到程序运行

* **编译**：源代码文件（`.c`）编译成与之一一对应的目标模块（`.o`）；目标模块中的指令已用逻辑地址编址，**每个模块各自从逻辑地址 0 开始**、相互独立
* **链接**：把各目标模块连同调用到的库函数组装成完整的**装入模块**（Windows 上的 `.exe` 可执行文件），装入模块拥有一套**完整的逻辑地址**——链接这一步确定完整逻辑地址
* **装入**：把装入模块放入内存，确定进程对应的**最终物理地址**——三种装入方式解决的就是这一步

```text
源代码文件(.c) ──编译──▶ 目标模块(.o，各自从0编址) ──链接──▶ 装入模块(.exe，完整逻辑地址) ──装入──▶ 内存中的进程(确定物理地址)
```

### 链接的三种方式

* **静态链接**：程序运行**之前**把各目标模块连接成一个完整的装入模块，之后不再拆开
* **装入时动态链接**：各目标模块不先连接，放入内存的时候才链接，进程的完整逻辑地址**一边装入一边形成**
* **运行时动态链接**：需要用到某个模块时才把它调入内存并链接；全程用不到的模块可以**不装入内存**；灵活性更高，并能**提升内存利用率**
