# 进程同步与互斥

## 进程互斥的硬件实现方法

* **关中断（中断屏蔽）**

    * > **定义**：用「关中断 / 开中断」这对指令把临界区武装起来的互斥方式——关中断后进程不可能被中断，也就不可能发生进程切换，直到访问完临界区执行开中断为止。原语「一气呵成、不可中断」的背后用的正是这组指令。

    * 优点：实现简单高效，逻辑清晰。

    * 缺点一：不适用于多处理机系统——关中断指令只对执行它的那台处理机生效，其他处理机不受影响，仍可能同时有进程进入同一临界区，互斥失效。

    * 缺点二：开/关中断是特权指令，必须在内核态执行，只适用于操作系统内核进程，不适用于用户进程。

* **TestAndSet 指令（TestAndSetLock，TS 指令 / TSL 指令）**

    * > **定义**：由硬件实现、执行过程不允许被中断的指令；用一个共享布尔变量 `lock` 表示临界区是否已上锁，一次性完成「记下旧值 + 置为上锁」两个动作。

    * 指令逻辑：先用变量 `old` 记录 `lock` 以前的值，然后无论是否已上锁都把 `lock` 置为 `true`，再把旧值返回出去。硬件实际执行就是把旧值放进某个物理寄存器、再覆盖 `lock` 为 `true`，并没有函数返回这回事。

    * 用法：`while(TestAndSet(&lock));` 之后进临界区，退出区执行 `lock = false`。若返回的旧值为 `true` 说明已上锁，进程卡在循环里反复执行 TSL，直到持锁进程解锁。

    * 与软件方法的联系：双标志先检查法出问题的根因是「检查」和「上锁」不能一气呵成，TSL 由硬件保证两件事一次做完，问题自然不存在。

    * 优点：实现简单、代码简洁，适用于多处理机环境。缺点：不满足让权等待，进不了临界区的进程占着 CPU 忙等。

* **Swap 指令**

    * > **定义**：硬件实现、不可中断的指令，功能是交换两个变量的值；用它实现互斥的逻辑与 TSL 一模一样。

    * 用法：设 `old = true`，循环 `while(Swap(&lock, &old));`——交换后 `old` 拿到旧的上锁状态、`lock` 被置为 `true`，同样完成「先记录旧值、再上锁」。

    * 优缺点与 TSL 完全相同：实现简单、适用于多处理机，但不满足让权等待，进入盲等。

* **互斥锁（lock）与自旋锁（spin lock）**

    * > **定义**：锁可理解为一个布尔变量，`true`/`false`（或 0/1）表示已上锁/未上锁；`acquire()` 负责上锁，`release()` 负责释放锁。

    * 用锁实现互斥的主要缺点仍是盲等：进不了临界区就一直被 `while` 循环卡住忙等，违反让权等待。

    * 忙等不等于「永远占着处理机」：忙等进程的时间片用完后，调度程序依然会让它下处理机。

    * 由于盲等需要不断循环检查，这类锁被称为自旋锁；TSL 指令、Swap 指令、单标志法都属于自旋锁，都有盲等问题。

    * 自旋锁的优点：等待期间不发生进程上下文切换，而切换代价很大。在多处理机系统中若临界区上锁时间很短，自旋等待代价反而很低——一个核自旋，另一个核上的进程很快解锁，且忙等的核不影响其他核工作。

    * 自旋锁不适用于单处理机系统：唯一处理机被自旋进程占着，持锁进程上不了处理机、不可能解锁，绝不会出现「自旋等着等着就拿到锁」的情况。结论：自旋锁更适用于多处理机系统。

## 信号量机制

* **信号量机制（semaphore）**

    * > **定义**：1965 年由荷兰学者迪杰斯特拉（Dijkstra）提出的方案——用户通过操作系统提供的一对原语 `wait(S)`、`signal(S)`（即 P、V 操作）来操作一种特殊变量，该变量可表示系统中某种资源的数量（如一台打印机对应初值为 1 的信号量）。

    * 用原语的原因：双标志先检查法的问题在于检查和上锁无法一气呵成，而原语执行不可被中断，把检查和上锁放进同一个原语即解决。

    * 考研需掌握两种类型：整型信号量与记录型信号量。

* **整型信号量**

    * > **定义**：用一个整数表示某种系统资源数量的信号量；与普通整型变量的区别是只允许三种操作——初始化、P 操作（wait）、V 操作（signal）。

    * P 操作逻辑：`while(S <= 0);` 检查剩余资源是否足够，随后 `S--` 表示申请到一个资源；V 操作即 `S++` 归还资源。

    * 它在 wait 里的「先检查后扣减」逻辑上与双标志先检查法一致，但由原语一气呵成完成，避免了双进程同时进入临界区的问题。

    * 缺陷：`while` 循环还在，资源不够时进程占着处理机盲等，不满足让权等待。

    * 考法：常考察它存在的问题（盲等、不满足让权等待），并与记录型信号量对比。

* **记录型信号量**

    * > **定义**：用记录型数据结构表示的信号量——`value` 表示该资源的剩余数量，`L` 是等待队列指针，指向正在等待这种资源的进程。

    * wait（P）操作：先 `S.value--`；若减完 `value < 0`，说明减之前就没资源了，执行 block 原语把当前进程**主动阻塞**并挂到该信号量的等待队列。

    * signal（V）操作：先 `S.value++`；若加完仍 `value <= 0`，说明等待队列里还有进程在等，调用 wakeup 原语唤醒等待队列**对头**的进程，把它从阻塞态转回就绪态，并把刚释放的资源分配给它。

    * 共同套路：先对 value 减减或加加，再对 value 做一次检查，判断是否需要阻塞或唤醒。

    * 资源视角结论：当 `value < 0` 时，其绝对值恰好等于正在等待该资源的进程数。

    * 满足让权等待的原理：暂时得不到资源的进程主动自我阻塞、主动放弃 CPU，而不是原地空转。

    * 记录型信号量是操作系统课程中最重要的知识点之一，大题小题概率都高；题目没特别说明时，信号量 S 默认指记录型——P 操作申请不到资源时进程进入阻塞状态而非盲等。

    ```c
    void wait(semaphore S) {         // P 操作：申请一个资源
        S.value--;
        if (S.value < 0) block(S.L); // 减完 < 0：减之前就没资源，自我阻塞
    }
    void signal(semaphore S) {       // V 操作：释放一个资源
        S.value++;
        if (S.value <= 0) wakeup(S.L); // 加完仍 <= 0：队列还有人等，唤醒对头
    }
    ```

* **两种信号量的对比**

    | 维度 | 整型信号量 | 记录型信号量 |
    | :--- | :--- | :--- |
    | 数据形式 | 一个整数 | 记录型结构（value + 等待队列） |
    | 申请不到资源时 | 卡在 `while` 循环盲等 | 主动 block，挂入等待队列 |
    | 让权等待 | 不满足 | 满足 |
    | 常考角度 | 它存在的问题 | P/V 操作的书写与执行过程 |

## 用信号量实现进程互斥

* **互斥信号量（mutex）套路**

    * > **定义**：为对临界区的互斥访问设置初值为 1 的互斥信号量 `mutex`，所有进程进入临界区之前对它执行 P、出临界区之后执行 V。

    * 三步法：先划定临界区（搞清哪段代码访问临界资源）；再设互斥信号量 `mutex = 1`；最后规定所有进程进临界区前 P、出临界区后 V。

    * 资源视角：`mutex` 表示「进入临界区的名额」，初值 1 即名额只有一个；P 是申请名额，V 是归还名额，归还时唤醒阻塞的申请者。

    ```c
    semaphore mutex = 1;      // 互斥信号量，初值为 1
    P1() {
        ...
        P(mutex);             // 进临界区之前：申请名额
        临界区;
        V(mutex);             // 出临界区之后：归还名额
        ...
    }
    ```

* **做题注意点**

    * 信号量定义写法：题目无特别说明时写 `semaphore mutex = 1;` 即可，不必写出数据结构；只要以 `semaphore` 关键字定义，就是记录型信号量（带阻塞排队，不会盲等）。

    * 不同的临界资源要设不同的互斥信号量：访问打印机的临界区用一个 mutex，访问摄像头的用另一个，不能混用一把锁。

    * P、V 必须成对出现：缺 P 无法保证互斥；缺 V 会让某些进程阻塞后永远得不到唤醒。

## 用信号量实现进程同步

* **进程同步（process synchronization）**

    * > **定义**：让并发执行的进程按要求的顺序有序推进——消除并发运行的异步性，使进程相互配合。并发的异步性意味着两个进程代码执行的先后顺序不可预知，而有些代码必须基于前序代码的运行结果才能执行。

    * 实现两步：分析哪里需要「一前一后」的同步关系；设初值为 0 的同步信号量 S，在后操作之前对 S 执行 P，在前操作之后对 S 执行 V。

    * 资源视角：S 初值为 0 表示这种资源刚开始不存在；只有执行前面操作的进程能释放它（前V），执行后面操作的进程必须先申请（后P），申请不到就阻塞，只能被前面的进程唤醒——同步关系锁死。

    * 口诀：**前V后P**——「前操作」之后 V，「后操作」之前 P；这是解决一切同步问题的关键。

    ```c
    semaphore S = 0;          // 同步信号量，初值为 0
    P1() { 代码1; 代码2; V(S); }   // 前操作之后：V
    P2() { P(S); 代码4; }          // 后操作之前：P
    ```

    * 推演：P1 先运行则 V 后 S 变 1，P2 的 P 不阻塞、顺利执行代码四；P2 先运行则被阻塞在 P 上，直到 P1 的 V 把它唤醒——保证代码二一定在代码四之前。

* **进程前驱问题（前驱图）**

    * > **定义**：用有向图表达多级同步——箭头起点是必须先完成的操作，只有起点完成后终点操作才能开始。

    * 解法：前驱图每一条边都是一对「一前一后」的同步关系，给每条边设一个初值为 0 的同步信号量，逐边套用「前V后P」。

    * 规律：每个进程在自己的代码之前，对所有「入边」信号量各做一次 P；代码之后，对所有「出边」信号量各做一次 V。如入边为 e、f、g 的末节点，其进程先依次 P(e)、P(f)、P(g) 再执行代码。

    * 无论哪个进程先上处理机，这套代码都能实现前驱图表达的全部同步关系：某进程的 P 不满足就阻塞，只能由前驱边的 V 唤醒，边的关系必然满足。

* **互斥与同步套路对比**

    |  | 实现互斥 | 实现同步 |
    | :--- | :--- | :--- |
    | 信号量初值 | 1 | 0 |
    | P 的位置 | 临界区之前 | 后操作之前 |
    | V 的位置 | 临界区之后 | 前操作之后 |
    | 口诀 | 进临界区前 P，出临界区后 V | 前V后P |

    * 信号量也可实现资源分配：如系统有三台打印机就把对应信号量初值设为 3，申请执行 P、用完执行 V。

## 生产者-消费者问题

* **问题与三对隐含关系**

    * > **定义**：一组生产者进程与一组消费者进程共享一个初始为空、大小为 n 的缓冲区；生产者每次放入一个产品，消费者每次取走一个产品。缓冲区有容量限制，由此挖出三对关系。

    * 关系一（同步）：只有缓冲区没满时生产者才可放入——缓冲区满时生产者必须阻塞等待腾出格子。

    * 关系二（同步）：只有缓冲区非空时消费者才可取走——缓冲区空时消费者必须阻塞等待；消费者取走数据后若有生产者阻塞，应唤醒它，唤醒后是否立即写由调度器决定。

    * 关系三（互斥）：缓冲区是临界资源，各进程必须互斥访问——反例：两个生产者并发检查都发现缓冲区未满、又选中同一格写入，后写者覆盖先写者的数据。

* **信号量设定**

    | 信号量 | 代表的资源 | 初值 | 为什么是这个初值 |
    | :--- | :--- | :--- | :--- |
    | mutex | 缓冲区（临界资源）的使用权 | 1 | 同一时刻只允许一个进程访问缓冲区 |
    | empty | 空闲缓冲区的数量 | n | 刚开始 n 个格子全是空的 |
    | full | 产品（非空缓冲区）的数量 | 0 | 刚开始一个产品都没有 |

    * 同步信号量初值看它对应资源的初始数量：消费者 P(full) 是在申请一个产品，full 即非空缓冲区数量；生产者每放一个产品消耗一个空闲缓冲区，empty 即空闲缓冲区个数。

    ```c
    semaphore mutex = 1;      // 互斥访问缓冲区
    semaphore empty = n;      // 空闲缓冲区的数量
    semaphore full  = 0;      // 产品（非空缓冲区）的数量

    producer() {
        while (true) {
            生产一个产品;
            P(empty);         // 放入之前：申请一个空闲缓冲区
            P(mutex);         // 临界区上锁
            把产品放入缓冲区;
            V(mutex);         // 临界区解锁
            V(full);          // 放入之后：产品数 +1
        }
    }
    consumer() {
        while (true) {
            P(full);          // 取走之前：申请一个产品
            P(mutex);         // 临界区上锁
            从缓冲区取走一个产品;
            V(mutex);         // 临界区解锁
            V(empty);         // 取走之后：空闲缓冲区 +1
            使用产品;
        }
    }
    ```

* **两个关键观察**

    * 互斥的 P、V 在**同一个进程**内出现——自己上锁、自己解锁；同步的 P、V 则分布在**不同进程**之间——对同一信号量，执行 V 的进程唤醒执行 P 的进程。

    * > **易错点** ⚠️：实现互斥的 P 操作一定要放在实现同步的 P 操作**之后**，顺序绝不能颠倒。若先 `P(mutex)` 再 `P(empty)`，在缓冲区已满（empty = 0）时：生产者先拿走 mutex 再阻塞在 empty 上，消费者阻塞在 mutex 上——生产者等消费者对 empty 的 V，消费者等生产者对 mutex 的 V，相互等待对方唤醒自己，循环等待形成死锁。缓冲区全空时消费者按「先 P(mutex) 再 P(full)」同理死锁。

    * 两个 V 操作的顺序可以交换：V 不会导致任何进程阻塞，不存在「阻塞在 V 上」的进程，交换不产生循环等待。

    * 「生产一个产品」「使用一个产品」放进 PV 操作之间逻辑上可行，但会拉长临界区、增长上锁时间，不利于各进程交替使用临界区——临界区代码要尽可能短，不建议放。

## 多生产者-多消费者问题

* **问题模型**

    * > **定义**：生产者生产的、消费者消费的产品**类型不一样**的生产者-消费者问题。典型场景：盘子一次只能放一个水果，父亲只放苹果、母亲只放橘子，女儿只吃苹果、儿子只吃橘子。盘子即大小为 1、初始为空的缓冲区。

    * > **易错点**：这里的「多」不是「多个」，应理解为「**多类**」——不同类别的生产者与消费者，生产/消费的产品不同。多个同类生产者上一模型已处理过，增量在「类别不同」上。

    * 互斥关系：盘子是缓冲区，对它的访问需要互斥进行。

    * 同步关系三对：父亲放苹果后女儿才能取苹果；母亲放橘子后儿子才能取橘子；只有盘子为空时父亲或母亲才可放入——「盘子变空」这一事件既可由女儿触发也可由儿子触发。

* **信号量设定与代码**

    * `mutex = 1`：互斥访问盘子；`apple = 0`：父亲放苹果 → 女儿取苹果的同步；`orange = 0`：母亲放橘子 → 儿子取橘子的同步；`plate = 1`：表示盘中还能放几个水果，刚开始盘子是空的所以为 1。

    ```c
    semaphore mutex  = 1;   // 互斥访问盘子（缓冲区）
    semaphore apple  = 0;   // 盘中已有几个苹果
    semaphore orange = 0;   // 盘中已有几个橘子
    semaphore plate  = 1;   // 盘中还能放几个水果

    father()  { while(1){ 准备苹果; P(plate); P(mutex); 放入苹果; V(mutex); V(apple); } }
    mother()  { while(1){ 准备橘子; P(plate); P(mutex); 放入橘子; V(mutex); V(orange); } }
    daughter(){ while(1){ P(apple); P(mutex); 取出苹果; V(mutex); V(plate); 吃掉苹果; } }
    son()     { while(1){ P(orange); P(mutex); 取出橘子; V(mutex); V(plate); 吃掉橘子; } }
    ```

* **能不能省掉 mutex**

    * 本题中即使不设 mutex 也能实现对盘子的互斥访问：根源在缓冲区大小为 1——apple、orange、plate 三个同步信号量同一时刻最多只有一个的值为 1，而各进程进临界区前都要对其中某一个执行 P，故最多只有一个进程不被阻塞、能进入临界区。

    * 把盘子容量改成 2 就不行了：父亲和母亲的 P(plate) 可能都通过，同时访问盘子，导致数据覆盖。

    * 结论：缓冲区大于 1 时必须设 mutex；缓冲区等于 1 时**有可能**不需要，但不是绝对的，要具体问题具体分析。考试来不及细分析时最好加上——加上肯定没错。

    * > **易错点** ⚠️：对 mutex 的 P 操作一定要放在实现同步的 P 操作之后，否则可能引起死锁。

* **从事件角度分析同步关系**

    * > **易错点**：进程同步要理解为「某一个**事件**必须发生在另一个事件之前」，而不是「某一个**进程的行为**要发生在另一个进程的行为之前」。

    * 从单个进程行为出发会把上题分析出四个同步关系（女儿取苹果可能导致父亲或母亲可放入、儿子取橘子同理）；正确做法是把它们抽象为一对事件——「盘子变空」必须发生在「放入水果」之前，四个关系实为**一对**。

    * 落到信号量：哪个进程可能引发某事件，就对对应信号量执行 V；哪个进程要执行某事件，就在执行前对它执行 P——女儿、儿子取完都 V(plate)，父亲、母亲放入前都 P(plate)。

## 读者-写者问题

* **问题与四条要求**

    * > **定义**：读者进程与写者进程并发访问一个共享文件，因读写对文件的影响不同而提出差异化要求：允许多个读者同时读；同一时刻只允许一个写者写；写者写时不允许其他读者或写者操作；写者写之前必须保证其他读者和写者都已全部退出。

    * 允许读读共享的原因：读操作不改变文件的数据信息，多个读者同时读谁也不会改掉数据。

    * 写者必须与其他一切进程互斥的原因：写者会改变文件内容——读者读到一半被写者插写新数据，之后读到的是不想读的数据；两个写者并发则后写者覆盖先写者的数据。

    * > **易错点**：读者进程不是生产者-消费者模型里的消费者——消费者会把数据取走（影响数据），读者读数据不清空、不改变文件内容。所以消费者之间照样互斥，读者之间却可以共存。

    * 后三条要求概括成一句话：当写者正在写（或想要写）时，其他任何进程都不能访问文件；写者必须等所有其他进程的操作结束之后才能开始写。

* **count 计数器方案**

    * > **定义**：设 `count` 记录当前正在访问文件的读者数量（初值 0），配一把读写互斥锁 `rw`——由**第一个读者负责加锁、最后一个读者负责解锁**，中间的读者来去不碰锁，实现「读读共享、写与一切互斥」。

    * 规则：读者加锁前检查 `count == 0`，是第一个就 `P(rw)` 上锁，然后 `count++`；读完 `count--`，减完为 0 说明自己是最后一个，`V(rw)` 解锁。只要有一个读者在读（count > 0），后来者跳过加锁直接进入。

    * 缺陷一：对 count 的**检查和赋值**不能一气呵成——两个读者并发时都发现 count 为 0、都去 P(rw)，第一个拿锁的读者反被第二个锁在门外。解决办法：再加互斥信号量 `mutex`，把对 count 的访问用 P(mutex)/V(mutex) 包起来。

    * 这里说的「一气呵成」不是指对 count 访问时不发生进程切换——切换依然会发生——而是用 PV 保证同一时刻只有一个进程在检查和修改 count。用一对 P、V 把「检查 + 修改」包起来的思路非常值得借鉴。

    * 缺陷二：只要还有读进程在读，写进程就一直阻塞在 rw 上——读进程源源不断到来都能跳过加锁，rw 永远不解锁，**写进程饿死**。这个算法相当于读进程拥有更高优先权。

* **w 信号量：读写公平法**

    * > **定义**：在读者和写者的入口与出口各加一对 `P(w)`、`V(w)` 的改进算法，解决写者饿死问题；完整方案共三个信号量：`rw = 1`（读写互斥）、`mutex = 1`（保护 count）、`w = 1`（防写者饿死）。

    ```c
    writer() {
        while (1) {
            P(w); P(rw);
            写文件;
            V(rw); V(w);
        }
    }
    reader() {
        while (1) {
            P(w); P(mutex);
            if (count == 0) P(rw);   // 第一个读者负责上锁
            count++;
            V(mutex); V(w);
            读文件;
            P(mutex);
            count--;
            if (count == 0) V(rw);   // 最后一个读者负责解锁
            V(mutex);
        }
    }
    ```

    * 两个读者并发：第一个读者在 P(w) 与 V(w) 之间被切换时，第二个读者阻塞在 w 上，直到前者 V(w)——之后两人都不再被阻塞，**依然可以同时读**，w 没有破坏读读共享。

    * 两个写者并发：第一个写者写文件时 w、rw 均为 0，第二个写者必阻塞在 w 上，直到前者 V(w)——写写互斥保持。

    * 读者在读、写者后到：写者 P(w) 不阻塞（读者读前已 P 又 V，w 回到 1），但会阻塞在 rw 上——此时写者已把 w 减成 0，于是**后来的读者被挡在 w 上**，只能等写者写完并 V(w) 才被唤醒。这就是 w 解决写饥饿的关键：写者在后续读者之前到来时，写者会先被唤醒。

    * 写者在写、读者与第二写者随后到达：两者都阻塞在 P(w) 上；读者先到排在对头，写者一写完 V(w) 唤醒的是队头读者——信号量除了计数还有**排队**功能。

    * 因此该算法并没有真正实现「写优先」，而是相对公平的**先来先服务**，也称读写公平法。

## 哲学家进餐问题

* **问题与编号规则**

    * > **定义**：五位哲学家围圆桌而坐，桌上有五只筷子，每人左右各一只；哲学家要么思考要么进餐，进餐需**同时拿起左右两只筷子**，且只能拿自己旁边的两只；某只筷子被别人用时，拿它的动作被阻塞。

    * 相邻哲学家之间互斥地访问两人之间的那只筷子。

    * 与一般互斥问题的本质区别：之前的进程通常只需持有一个临界资源，这里每个进程需要**同时持有两个临界资源**才能执行——临界资源分配不当时就可能死锁，如何避免死锁是这个问题最核心的议题。

    * 编号规则：哲学家与筷子都编号 0～4，哲学家 $i$ 的左筷编号为 $i$，右筷编号为 $(i+1) \bmod 5$。

* **直接写法为什么死锁**

    ```c
    semaphore chopstick[5] = {1,1,1,1,1};
    // 编号为 i 的哲学家进程
    P(chopstick[i]);            // 拿左筷
    P(chopstick[(i+1)%5]);      // 拿右筷
    吃饭;
    V(chopstick[(i+1)%5]);      // 放右筷
    V(chopstick[i]);            // 放左筷
    ```

    * 死锁推演：五个哲学家并发执行，每个人都先拿起自己左边的筷子；再去拿右边时会发现右筷已被邻座占用——所有人都手持一只、等待另一只，循环等待，谁也吃不上饭。这是「每个进程都持有资源不放，又互相等待对方释放资源」的死锁现象。

* **三种避免死锁的思路**

    * 最多只允许四个哲学家同时进餐：设一个初值为 4 的同步信号量，进餐前对它 P、吃完后 V。五只筷子、最多四人进餐，即使每人先拿一只也必剩一只，保证至少有一个哲学家拿到左右两只筷子、顺利吃完并放下，其余哲学家依次被激活（鸽子笼原理）。

    * 奇数号先拿左、偶数号先拿右：相邻哲学家同时想吃饭时会优先争抢两人之间的那只筷子，且只有一人抢到；抢输者在**手里一只筷子都没有**的状态下就被阻塞，避免了「占有一个资源后再等待另一个资源」，从而避免死锁。实现上在拿筷子前先判断自己序号的奇偶再做不同处理。

    * 仅当左右两只筷子都可用才允许拿：设互斥信号量 `mutex = 1`，拿筷子前 P(mutex)、两只都拿完后 V(mutex)——保证「拿筷子」这件事互斥进行。

    ```c
    P(mutex);
    P(chopstick[i]);
    P(chopstick[(i+1)%5]);
    V(mutex);
    吃饭;
    V(chopstick[(i+1)%5]);
    V(chopstick[i]);
    ```

    * 该方案不死锁的原理：即使一个哲学家拿到一半被阻塞，也不会有别的哲学家再进来拿筷子；他被阻塞说明有哲学家持有他需要的筷子，那位哲学家吃完还回筷子，他就能拿齐进餐并释放手中资源，所有哲学家依次被激活，循环等待形成不了。

    * > **易错点** ⚠️：书上「只有两边的筷子都可以用时才允许拿起筷子」的说法不严谨——推演可发现：即使某一边筷子不能用，哲学家仍可能拿起了另一只；即使两边都空闲，也可能被挡在 mutex 这一层进不来。准确说法是 mutex 保证各哲学家「拿筷子」互斥进行。

    * 考试提示：遇到「各进程需同时持有两个或两个以上临界资源」的题目，就考虑用这三种思路避免死锁。

## 管程

* **为什么引入管程**

    * > **定义**：管程（monitor）是一种高级同步机制，与信号量机制一样用于实现进程互斥和同步，但更方便易用——把 PV 操作里需程序员操心的互斥、排队、阻塞细节封装起来，对外只提供简单接口。

    * 引入背景：信号量机制编写程序困难、易出错——如互斥的 P 写在同步的 P 之前就可能导致死锁，程序员不得不小心关注 PV 操作顺序。

    * 1973 年 Brinch Hansen 在 Pascal 语言中首次引入管程成分。

* **管程的组成**

    * 局部于管程的共享数据结构说明（如生产者-消费者问题中双方共享的缓冲区对应的数据结构）。

    * 对该数据结构进行操作的一组过程（「过程」就是函数）。

    * 对局部于管程的共享数据设置初始值的语句。

    * 管程还需要有一个名字。管程的定义类似面向对象中的「类」——数据、操作函数、初始化语句齐备。

* **管程的基本特征**

    * 局部于管程的数据，只能被局部于管程的过程所访问。

    * 一个进程只有通过调用管程内的过程，才能进入管程访问共享数据。

    * 每次仅允许一个进程在管程内执行某个内部过程——这等于保证了对共享数据结构的每次访问只有一个进程在进行，这就是管程的精髓。

    * > **提示**：考试最爱考察后两条基本特征（特定入口访问共享数据、每次仅允许一个进程在管程内执行过程），以及两个补充点——互斥特性由**编译器**负责实现；管程中设条件变量与等待、唤醒操作解决**同步**问题。

* **用管程解决生产者-消费者问题**

    * 管程内定义共享数据结构（缓冲区）、计数变量 count、两个条件变量 `full`（对应缓冲区满）与 `empty`（对应缓冲区空），以及过程 `insert(product)` 和 `remove()`。

    * `insert` 逻辑：缓冲区已满则 `wait(full)` 等待在 full 条件变量上；否则放入产品、count++；若放入的是第一个产品（count == 1）则 `signal(empty)` 唤醒可能在等的消费者。

    * `remove` 逻辑：count == 0 则 `wait(empty)`；否则取走产品、count--；若取走之前缓冲区是满的则 `signal(full)` 唤醒可能在等的生产者；返回产品。

    * 互斥由**编译器**实现：编译时由编译器保证各进程互斥进入管程中的过程——第二个进程在第一个进程未退出时会被阻塞在过程入口，类似排队器。程序员不写任何 PV。

    * 同步靠条件变量与 wait/signal：进程在条件变量上等待时应**先释放管程的使用权**（让出入口）；signal 一般唤醒排在对头的等待者。

    * 互斥、同步细节全部封装在管程内部，进程只需调用入口函数——这就是程序设计中「封装」的思想。

    * Java 中有类似机制：用 `synchronized` 关键字描述函数，即可保证同一时间段内只能被一个线程调用。

    ```java
    class Monitor {
        synchronized void insert(Object product) {
            // 多线程并发调用时，后来的线程排队等待；
            // 当前线程执行完退出后，下一个线程才能进入。
        }
    }
    ```

## 死锁的基本概念

* **死锁（deadlock）**

    * > **定义**：并发环境下各进程因竞争资源而造成的互相等待对方手里资源的局面——各进程都阻塞、都无法向前推进；若无外力干涉（如操作系统干涉），这些进程都无法再推进。

    * 哲学家例子：五人各持左筷、同欠右筷，每人都持有左邻想要的资源又在等右邻手里的资源，全员阻塞。

    * 死锁的发生情形：对**不可剥夺的系统资源**进行竞争；**进程推进顺序非法**——如 P1 占 R1 又请求 R2、P2 占 R2 又请求 R1，换一种推进顺序（P1 一气呵成申请 R1、R2）就不会死锁；**信号量使用不当**——如互斥的 P(mutex) 写在同步的 P 操作之前。互斥信号量和同步信号量也可看作一种抽象的系统资源，故可总结为：当对不可剥夺资源的分配不合理时，就有可能导致死锁。

* **死锁、饥饿、死循环的区别**

    * 饥饿：进程长期得不到想要的资源而无法向前推进——如短进程优先算法下短进程源源不断，长进程一直得不到处理机。

    * 死循环：进程执行中一直跳不出某个循环，特指**程序逻辑 bug 导致**的那种（故意设计的死循环不属于讨论范围）。

    * 共同点：都是进程无法继续推进的异常现象，选择题常放在一起考。

    | 对比维度 | 死锁 | 饥饿 | 死循环 |
    | :--- | :--- | :--- | :--- |
    | 发生进程数 | 两个或以上 | 可能只有一个进程 | 可能只有一个进程 |
    | 进程所处状态 | 肯定处于阻塞态 | 可能阻塞态，也可能就绪态 | 可上处理机运行，可能处于运行态 |
    | 产生原因 | 循环等待对方的资源 | 长期得不到想要的资源（处理机、I/O 设备等） | 程序逻辑错误 |
    | 谁来解决 | OS 分配资源策略不合理，OS 负责 | 同左，OS 负责 | 程序员的 bug，与 OS 无关 |

    * 死锁进程是在等待资源分配，所以肯定阻塞态，且至少两个进程才能「互相等待」；饥饿进程可能等 I/O 设备（阻塞态）也可能等处理机（就绪态）；死循环进程能上处理机运行。操作系统会讲如何解决死锁和饥饿，但从不讲如何解决死循环——那不是 OS 该负责的问题。

* **死锁产生的四个必要条件**

    * > **提示**：四条条件中**任何一条不成立，死锁就不会发生**。

    * 互斥条件：进程只对必须互斥使用的资源进行争抢才会死锁——筷子是互斥资源；内存、扬声器这类可同时供多进程使用的资源不会导致死锁。

    * 不可剥夺条件：资源未用完之前不能被其他进程强行夺走，只能由该进程主动释放——若筷子可被抢走，抢到两只的哲学家总能吃饭，死锁不会出现。

    * 请求和保持条件：进程保持已有资源不放的同时，又请求新的、恰被别人持有的资源。

    * 循环等待条件：存在进程资源的循环等待链——如每个哲学家都在等右邻放下筷子，形成环形等待链。

* **循环等待未必死锁**

    * > **易错点**：发生死锁时一定有循环等待现象；但发生循环等待现象未必就是死锁。

    * 反例：想象第六个哲学家持有一只恰好可供 3 号哲学家右手使用的筷子——3 号在循环等待链之外多了一个可等的资源，第六人放下筷子即可打破等待，循环等待存在但死锁不发生。即：只要还有别的进程持有**同类型的、可替代的资源**，循环等待时死锁不一定发生。

    * 若系统中**每一类资源都只有一个**，循环等待就是死锁的充分必要条件——像没有第六人时，3 号能用的右筷只有那一根，循环等待一出现死锁必然发生。

* **死锁的处理策略**

    * 预防死锁：想办法破坏四个必要条件中的一个或几个（把死锁扼杀在发生之前）。

    * 避免死锁：用某种算法防止系统进入不安全状态——如银行家算法。

    * 死锁的检测和解除：**允许死锁发生**，但操作系统要负责检查是否发生死锁，发生时用某种策略解除。
