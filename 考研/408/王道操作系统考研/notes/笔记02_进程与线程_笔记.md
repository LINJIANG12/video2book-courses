# 进程与线程

## 进程的状态与转换

* **创建态（New，新建态）**

    * > **定义**：进程正在被创建期间所处的状态。

    * 此阶段操作系统做两件大事：给进程分配所需系统资源（如内存空间）、完成 PCB 的初始化。

* **就绪态（Ready）**

    * > **定义**：已具备运行条件、只差处理机这一种资源的状态；其余资源全部齐备。

    * 一个系统中可能同时存在大量就绪进程，都在排队等 CPU 空闲。

* **运行态（Running）**

    * > **定义**：CPU 正在执行该进程对应指令序列（程序代码）的状态；处理机与其他资源全部齐备。

    * 单 CPU 环境下，同一时刻最多只有一个进程处于运行态；多核 CPU 下可有多个进程并行运行。

* **阻塞态（Blocked，等待态）**

    * > **定义**：进程因等待某个事件（等待系统分配资源、等待其他进程响应等）而暂时无法继续执行的状态。

    * 除处理机之外，进程还在等待别的资源或事件；事件发生前必须让出 CPU。

* **终止态（Terminated，结束态）**

    * > **定义**：进程发出 `exit` 系统调用后，操作系统执行善后工作的状态。

    * 善后包括：让进程下 CPU、回收其占有的全部资源（内存、打印机等）、最后回收 PCB；全部完成后进程从系统中彻底消失。

* 五状态转换全景

```text
      创建完成            被调度选中              运行结束(exit) /
创建态 ─────────> 就绪态 ─────────> 运行态 ───────────────> 终止态
                  ^   ^             │      或遇到不可修复错误(如整数除以零)
                  │   └─ 时间片到 ──┤
                  │                 │ 请求等待某个事件（主动）
                  │                 v
                  │              阻塞态
                  └─ 等待的事件发生（被动）
```

* 状态转换的主动性与规则

    * 运行态 → 阻塞态：**主动**行为，进程通过系统调用申请系统资源或请求等待某个事件。

    * 阻塞态 → 就绪态：**被动**行为，等待的事件何时发生不由进程自己决定；且只能回到就绪态重新排队，不能直接杀回运行态。

    * 运行态 → 就绪态：时间片用完（CPU 收到时钟中断，发现进程已运行足够长时间）时发生；此时进程**仍然拥有继续执行的条件**，只是被剥夺了处理机，不需要等待处理机之外的其他事件。

    * > **易错点** ⚠️：一个进程不可能直接从阻塞态转到运行态，也不可能直接从就绪态转到阻塞态——要变成阻塞态必须主动发出请求，而发出请求的前提是正在 CPU 上运行，所以只可能从运行态转入阻塞态。

* 运行态、就绪态、阻塞态是**基本状态**——进程生命周期大部分时间处于这三种状态；创建态和终止态只是两个短暂的过渡阶段。

* 阻塞态又叫等待态，创建态又叫新建态，终止态又叫结束态，考试换叫法要认得出。

## 进程的组织

* 操作系统用 PCB 中的 `state` 变量记录进程状态，并把同一状态的各进程 PCB 有规律地组织起来统一管理。

* **链式方式**

    * 每种状态对应队列，队列指针指向该状态进程的 PCB：执行指针指向运行态 PCB，就绪队列指针指向就绪 PCB 链，阻塞队列按等待原因分成多个（等打印机的、等磁盘的各自成队）。

    * 两个细节：优先级更高的进程 PCB 常放在就绪队列**队头**（方便调度）；阻塞队列按阻塞原因分类，事件到来时按队列对症唤醒，效率更高。

* **索引方式**

    * 给各状态建立索引表，表项存放对应 PCB 的地址（指针）。

    * **大多数操作系统实际使用链式方式**，索引方式简要了解即可。

## 进程控制与原语

* **进程控制（Process Control）**

    * > **定义**：对系统中所有进程实施有效管理，具有创建新进程、撤销已有进程、实现进程状态转换等功能；本质就是实现进程的状态转换。

    * 状态转换必须**一气呵成**：PCB 里的状态变量与 PCB 所挂的队列两份信息必须始终对得上。若刚把 `state` 从 2（阻塞态）改成 1（就绪态）就被中断打断，而 PCB 还挂在阻塞队列里，关键数据结构信息不统一，可能让系统出错。

* **原语（Primitive）**

    * > **定义**：操作系统内核中一种特殊程序，执行具有**原子性**——运行必须一气呵成、中间不可被中断。

    * 原子性靠两条**特权指令**实现：**关中断**执行后 CPU 不再例行检查中断信号，**开中断**执行后才恢复检查并处理积压的中断；两条指令之间的指令序列必然不可被中断。

    * > **易错点** ⚠️：关中断、开中断只允许内核程序使用。若开放给用户程序，用户可在程序开头关中断、结尾才开中断，程序一上 CPU 就永久霸占 CPU 不被中断。

* **创建原语**

    * > **定义**：操作系统创建进程时使用的原语，使进程从创建态进入就绪态。

    * 四步：申请一个空白 PCB（PCB 是进程存在的唯一标志）→ 分配所需资源（如内存空间）→ 初始化 PCB（分配 PID、设置 UID）→ 把 PCB 插入就绪队列。

    * 引起进程创建的典型事件：用户登录（建立用户管理/通信进程）；作业调度（作业是还放在外存、未投入运行的程序，调度即选一个调入内存运行）；某进程向系统提出请求，系统建进程处理该请求；某进程请求创建**子进程**。

* **撤销原语**

    * > **定义**：终止一个进程时使用的原语，使进程转向终止态并最终从系统消失。

    * 五步：找到进程 PCB → 若正在运行则立即剥夺其 CPU 分给其他进程 → 杀死其所有子进程 → 把其占有资源归还给**父进程** → 从系统中删除 PCB。

    * 引起进程终止的事件：进程自己请求终止（`exit` 系统调用）；进程做了非法事件（整数除以零、非法使用特权指令）被强行撤销；外界干预（如任务管理器结束卡死进程）。

    * 进程间是**树形结构**的父子关系：0 号祖先进程是最祖先，它创建的 1 号**装入进程**启动了开机后的其他进程。系统启动时资源几乎全归祖先进程，创建子进程时按需分配下去，子进程终止后资源还给父进程——这正是"杀死所有子进程、资源归还父进程"两条特性的由来。

* **阻塞原语与唤醒原语**

    * 阻塞原语：找到 PCB → 保护进程运行现场 → 把 PCB 状态设为阻塞态 → 让进程下处理机并插入相应等待（阻塞）队列。

    * 唤醒原语：找到 PCB → 从等待队列移除 → 设为就绪态 → 插入就绪队列等待调度。

    * > **易错点** ⚠️：因什么事被阻塞，就该被什么事唤醒——**阻塞原语和唤醒原语必须成对使用**。

* **切换原语**

    * > **定义**：让当前运行态进程下处理机、回到就绪队列，并从就绪队列选一个进程上处理器运行的原语；一次改变**两个**进程的状态。

    * 四步：把当前进程运行环境信息存入其 PCB → 把它的 PCB 移到相应队列（如就绪队列）→ 挑选一个进程上处理器并更新其 PCB → 从新进程的 PCB 恢复其运行环境。

* 所有控制原语做的事都可归为三类：更新 PCB 信息（改状态、保存/恢复运行环境）、把 PCB 插入合适的队列、创建/终止场合分配与回收资源——不需要死记硬背，理解过程即可。

## 运行环境与进程上下文

* **寄存器**是 CPU 内部存放数据的地方，课程涉及的几类：

    * **PSW**（程序状态字寄存器）：保存 CPU 的状态——内核态还是用户态。

    * **PC**（程序计数器）：存放接下来要执行的指令的地址。

    * **IR**（指令寄存器）：存放当前 CPU 正在执行的那条指令。

    * **通用寄存器**：存放其他必要信息。

* 寄存器中会保留指令执行的**中间结果**：如 `x++` 由"写内存 → 读入寄存器 → 寄存器加一 → 写回内存"四条指令完成，做到一半时加好的 2 只在通用寄存器里。寄存器不归进程独属，别的进程上 CPU 会覆盖这些值——所以进程下处理机前必须保存运行环境。

* > **定义**：**进程的运行环境（进程上下文，Process Context）**就是进程运行过程中寄存器里存储的中间结果；进程下处理机时把运行环境（PSW、PC、通用寄存器等必要信息）存入自己的 PCB，重新上 CPU 时从 PCB 恢复，接着往下执行。

* 保存运行环境、恢复运行环境是实现**进程并发执行**的关键技术。

## 进程通信

* **进程通信（进程间通信，Inter-Process Communication，IPC）**

    * > **定义**：两个或多个进程之间产生数据交互。

    * 通信必须有操作系统支持：各进程的地址空间**相互独立**，进程 P 不能读也不能写进程 Q 的空间——这是出于安全考虑（防止垃圾软件偷走其他进程的私密数据）。这道"墙"只有操作系统有能力打通。

    * 操作系统支持的三种方式：**共享存储**、**消息传递**、**管道通信**。

### 共享存储

* 进程申请一片**共享存储区**，这片区域可被多个进程共同映射访问：P 先把数据写入共享区，Q 再从中读出，完成数据交换。

* Linux 实现：发起方用 `shm_open` 系统调用申请共享内存区，通信双方都用 `mmap` 把这片区域**映射到自己的虚拟地址空间**——调 mmap 后进程的页表项（或段表项）增加一项即可完成映射。

* 各进程对共享存储区的访问必须**互斥**：一个进程正在访问时，其他进程不能访问。互斥由**通信进程自己**借助操作系统提供的同步互斥工具（如 PV 操作）实现；其本质是一个**读者写者问题**——可同时读，不可同时写。

* > **易错点** ⚠️：共享存储方式的互斥访问要由通信进程自己负责实现；这与管道通信"互斥由操作系统保证"正好相反。

* 两种共享方式对比

    | 对比维度 | 基于数据结构的共享 | 基于存储区的共享 |
    | :---: | :--- | :--- |
    | 共享内容的形态 | 规定好格式（如一个长度为十的数组） | 一整片区域，操作系统只划不管 |
    | 读写自由度 | 只能按数据结构的格式访问 | 存哪、读哪完全由进程自己定 |
    | 速度 | 慢 | 快 |
    | 定位 | 低级通信方式 | 高级通信方式 |

### 消息传递

* > **定义**：进程间数据交换以**格式化消息**为单位，通过操作系统提供的**发送原语（send）**和**接收原语（receive）**进行。

* 格式化消息由两部分组成：**消息头**（发送者是谁、接收者是谁、消息长度等概要信息）+ **消息体**（要传送的具体数据）。

* **直接通信方式**

    * > **定义**：发送进程指明接收进程的 PID，接收进程也指明消息来自哪个进程——点名道姓地传递。

    * 流程：P 在自己地址空间组装消息 → 执行 `send`，内核把消息复制到内核空间并挂到 Q 的 PCB 中的**消息队列**里 → Q 执行 `receive` 指明接收 P 发来的消息，内核检查 Q 的消息队列，找到后把消息体从内核区复制到 Q 的用户区。

* **间接通信方式（信箱通信方式）**

    * > **定义**：通过**信箱**这个中间实体传递消息；发送方指明发到哪个信箱、接收方指明从哪个信箱取，都不直接指明对方进程。

    * 进程可通过系统调用申请信箱；操作系统通常允许多个进程往同一信箱发消息，也允许多个进程从同一信箱收消息。

### 管道通信

* > **定义**：管道是一种**特殊的共享文件**（pipe 文件），本质是在内存中开辟的大小固定的缓冲区；写进程从一端写入、读进程从另一端读取。

* 数据只能**单向**流动，一个管道只能支持**半双工通信**——同一时刻只能单向传输，方向可以改，但两个方向不能同时进行；要**全双工**（双方同时互传）必须申请**两个管道文件**。

* 读写遵循**先进先出**：写数据先填头部再依次往后，读数据先把头部读空才能读后面；准确地说这个缓冲区是一个**循环队列**——后半写满而前面有空位时，可从另一头继续写。

* 对管道的互斥访问**由操作系统保证**，不需要进程自己保证。

* 阻塞规则：管道被**写满**，写进程阻塞，等读进程取走数据腾出空位再被唤醒；管道被**读空**，读进程的 read 动作阻塞，等写进程写入数据再被唤醒——读、写进程都可能进入阻塞态。

* 管道里的数据**一旦被读出就彻底消失**，且数据没有指明接收者；多读进程同时读会导致读取次序错乱。

* > **易错点** ⚠️：关于"一个管道允许几个读进程"，不同操作系统实现不同（System V 只允许一个读进程；Linux 允许多个读进程但轮流读）。应试统一与高教社 2014 年真题说法一致：**可以有多个写进程，只能有一个读进程**；但见到"多个写、多个读"的说法也不要觉得奇怪，从现实应用看它并没有错。

* > **易错点** ⚠️：王道书上"写进程会先把管道缓冲区写满才让读进程读；缓冲区还有数据时写进程不写"这句话是**错误的**。实测（Linux 实验）结论：只要管道**不空**，读进程就可以读；只要管道**不满**，写进程就可以写。

## 信号

* **信号（Signal）**

    * > **定义**：一种进程间通信方式，用于通知某个进程"某个特定事件已经发生了"；进程收到后需对它进行相应处理。

    * > **易错点** ⚠️：信号（signal）和信号量（semaphore）是完全不同的两个东西——信号量用于实现进程间的**同步互斥**，信号用于实现**进程间通信**。

    * Linux 定义了 30 种符合 POSIX 标准的信号类型（另有更多）；早期 UNIX 只定义 19 种。每种信号有专属序号和信号名；**信号名本质是一个宏定义的常量**，背后对应信号的序号。

    * 触发示例：`Ctrl+C` 使内核向正在运行的进程发 **SIGINT**（序号 2），默认处理为终止进程；程序发生除以零等算术异常时，内核发 **SIGFPE**（序号 8，floating point exception），默认处理为终止进程并**转储内存**（把该进程的内存数据存到硬盘，即软件崩溃时保存崩溃信息的机制）。

### 信号的发送与保存

* 发送信号最常用、最灵活的系统调用函数是 **kill 函数**：第一个参数指明目标进程的 PID，第二个 int 型参数表示信号的序号。

* 发送权限：用户进程之间可以互发信号，但**允许发送的信号类型有限制**——如 SIGKILL（序号 9）只能由父进程发给子进程，其他用户进程不能随意发（否则系统会出错）；内核进程给用户进程发信号无限制（内核拥有最高权限）；进程也可以给自己发信号。

* PCB 中有两个**位向量**：

    * **pending**（待处理）：记录当前有哪些待处理的信号。

    * **blocked**（被阻塞）：记录哪些信号被阻塞（屏蔽），又称**信号掩码**；进程通过系统调用自行设置屏蔽哪些信号。

* 位向量每种信号只占 1 比特，带来两个后果：同一类信号重复发送时，**后到达的会被简单丢弃**；从位向量**无法区分**信号是哪个进程发来的。

### 信号的处理时机与方式

* 处理时机：**每次进程从内核态转为用户态时，例行检查是否有待处理的信号**——典型场景是系统调用返回、中断处理完成返回时。

* 检查方法：`pending & ~blocked`——先把 blocked 按位取反，再与 pending 逐位与；被阻塞的信号对应位结果为 0，不做处理。

```text
信号序号:             1  2  3  4  5  6  7  8
pending :             1  0  0  0  0  0  0  1    收到了信号1和信号8
blocked:              0  0  0  0  0  0  1  1    屏蔽了信号7和信号8
~blocked:             1  1  1  1  1  1  0  0    按位取反
pending & ~blocked:   1  0  0  0  0  0  0  0    逐位与：只需处理信号1
```

* 收到信号与处理信号的时刻是分开的：收到时只把 pending 对应位记 1，直到"内核态转用户态"的节点才检测并转去执行处理程序，处理完毕返回进程的下一条指令继续执行（除非处理程序直接把进程阻塞或终止）。

* 处理方式：每类信号都有操作系统配置的**默认处理程序**（SIGINT 终止进程、SIGFPE 终止并转储内存；SIGWINCH——窗口大小变化——默认处理是忽略，等价于一个空函数）；进程可通过系统调用为某些信号设置**用户自定义处理程序**，它会**覆盖**默认处理。实际开发场景：窗口大小变化时进程收到 SIGWINCH，自定义处理程序据此动态调整 UI。

* 概念题细节：

    * 处理了某个信号后，把对应的 pending 位重置为 0。

    * 同时收到多个不同类型的信号时，通常**优先处理序号更小**的信号。

    * 各进程的信号处理程序、pending、blocked **相互独立**，都由进程自己设置，只作用于自身。

    * > **易错点** ⚠️：有些信号**既不允许被用户自定义处理函数覆盖，也不允许被阻塞**——典型是 Linux 的 SIGKILL 和 SIGSTOP。

### 信号与异常

* 结论：**信号可以作为异常的配套机制，让进程对操作系统的异常处理进行补充**。

* 内核会捕获处理进程运行中的异常（缺页、整数除以零等），分两种情况：

    * 内核可**完成全部处理**的异常：如缺页异常，进程访问缺失页面引发，内核把处理全部做完。

    * 内核**无法完成全部处理**的异常：需用户进程配合补充。例：计算器程序被输入整数除以零，内核在异常处理程序中给该进程发 SIGFPE，默认处理是闪退崩溃——开发时可自定义处理程序，收到该信号时在页面上打印"出错了"提醒用户，实现个性化的补充处理。

## 线程

* **线程（Thread）**

    * > **定义**：一种"轻量级的进程"，是**基本的 CPU 执行单元**、**程序执行流的最小单位**。

    * 引入动机：传统进程是执行流的最小单位，只能串行地执行一段程序代码；但一个进程（如 QQ）需要同时视频聊天、文字聊天、传文件——把每件事的处理程序放进不同线程并发执行即可。引入线程是为了**增加系统的并发度**，CPU 调度服务的对象从进程变成线程。

    * 每个线程有一个线程 ID 和一个**线程控制块（Thread Control Block，TCB）**——为管理线程而创建的数据结构，类似 PCB。

* 引入线程前后的变化

    | 对比维度 | 传统进程机制 | 引入线程机制之后 |
    | :--- | :--- | :--- |
    | 资源分配 | 进程既是资源分配的基本单位，也是处理机调度的基本单位 | 进程只是资源分配的基本单位 |
    | 处理机调度 | 调度对象是进程 | 调度对象变成线程 |
    | 并发性 | 只能进程之间并发执行 | 进程之间、进程内各线程之间都可并发，并发度进一步提升 |
    | 并发的开销 | 进程间并发要切换进程的运行环境，开销较大 | 同一进程内的线程切换不需要切换进程运行环境，开销降低 |

* 线程切换开销的形象理解：图书馆换陌生人用桌子要"收书—摆书"（进程切换运行环境，有代价）；舍友换用同一张桌子可以不收书（同进程内线程切换，不用换运行环境，开销小得多）。

* **线程的属性**

    * 线程是处理机调度的单位。

    * 多核 CPU 中，每个线程可以占用不同的 CPU 核心。

    * 线程也有**就绪、阻塞、运行**三种基本状态。

    * 线程**几乎不拥有系统资源**——系统资源分配给进程而非线程；同进程内各线程共享该进程的资源，包括 I/O 设备、内存地址空间。

    * 同一进程内的线程共享内存地址空间，线程间通信可以**不需要操作系统干预**，直接通过共享地址空间传递信息。

    * 同一进程内的线程切换**不会引起进程切换**，开销小；不同进程间的线程切换**会引起进程切换**（需要切换进程运行环境），开销大。

## 用户级线程与内核级线程

* **用户级线程（User-Level Thread，ULT）**

    * > **定义**：由程序员编写的**线程库**实现、只有用户（线程库）能感知而操作系统感知不到的线程；用在早期只支持进程、不支持线程的操作系统上。

    * 线程可理解为**一段代码逻辑**：用 while 循环轮流执行三段代码（i 按 0、1、2 循环，分别处理视频聊天、文字聊天、文件传输），这个最简陋的 while 循环就是最简单的线程库——它完成了线程的管理和调度；实际语言提供的线程库更复杂，支持线程创建、销毁、调度等。

    * 管理工作由**应用程序通过线程库**完成，不涉及操作系统；线程切换**在用户态即可完成**，不需要转内核态；操作系统意识不到线程的存在，它只看到进程。

    * **优点**：管理（切换、创建等）不需要请求操作系统服务、不需要 CPU 状态切换到内核态，管理开销小、效率高。

    * **缺点**：只要其中一个线程被阻塞（如申请摄像头资源失败），整个进程的其他线程也被阻塞、全进程执行不下去，并发度不高；且此时 CPU 的调度单位依然是**进程**，多核环境下进程只能被分配一个核心，线程不能并行运行。

* **内核级线程（Kernel-Level Thread，KLT）**

    * > **定义**：操作系统视角能看到、由操作系统负责管理的线程；Windows、Linux 等现代操作系统大多支持。

    * 管理工作由操作系统完成；线程切换需要**从用户态转内核态**（切换完成后再转回）。

    * **优点**：内核级线程是处理机调度的基本单位（进程只作资源分配单位），多核下各线程可派到不同核心**并行执行**；线程相互独立，一个线程阻塞不影响其他线程继续执行——并发能力强。

    * **缺点**：切换需要 CPU 在用户态与内核态之间来回转换，线程管理成本更高、开销更大。

## 多线程模型

* > **定义**：在支持内核级线程的系统中引入线程库，把若干用户级线程映射到内核级线程上，按映射关系形成的模型。

```text
一对一模型        多对一模型          多对多模型(n >= m)

U1   U2   U3      U1  U2  U3         U1   U2   U3
|    |    |        \   |   /           \   |   /
K1   K2   K3           K1              K1      K2
```

* 三种模型对比

    | 模型 | 映射关系 | 优点 | 缺点 |
    | :--- | :--- | :--- | :--- |
    | 一对一 | 1 个用户级线程 : 1 个内核级线程 | 并发能力强：一个线程阻塞不影响其他线程；可多核并行 | 内核级线程多，管理成本高、开销大 |
    | 多对一 | 多个用户级线程 : 1 个内核级线程 | 管理开销小、效率高（用户态完成管理） | 一个线程阻塞全进程阻塞；不能并行，并发度不高 |
    | 多对多 | n 个用户级线程 : m 个内核级线程（n ≥ m） | 克服了多对一并发度不高的问题；管理开销比一对一小 | — |

* 多对一模型默认一个进程只被分配**一个**内核级线程（考试口径）；若分配多个内核级线程，多核下它们当然可并行。

* **用户级线程是代码逻辑的载体，内核级线程是"运行机会"的载体**——操作系统分配处理机、CPU 资源以内核级线程为单位；一段代码逻辑只有获得运行机会才能被 CPU 执行。这种分离让线程管理更灵活：视频聊天耗 CPU 多时，可让一个内核级线程专门执行它，另一个内核级线程并发执行文件传输和文字聊天的逻辑；文件传输耗 CPU 多时再把逻辑重新映射。

* > **易错点** ⚠️：引入内核级线程后，一个进程可能对应多个内核级线程，**只有当所有内核级线程都被阻塞时，才说这个进程进入了阻塞状态**。

## 线程的状态与控制

* 线程通常只关注**运行态、就绪态、阻塞态**三个核心状态，转换规则与进程完全一致：被调度选中上处理器（就绪→运行）；时间片用完下处理机（运行→就绪）；发出请求等待事件如等 I/O 完成（运行→阻塞，主动）；等待的事件发生（阻塞→就绪，被动）。

* **线程控制块（TCB）**的内容：

    * **标识信息**：线程自己的标识，与 PCB 类似。

    * **程序计数器 PC**：指明线程执行到哪了；下处理机时把 PC 值保存进 TCB，上处理机时从 TCB 取出填回 PC 寄存器。

    * **其他各种通用寄存器的值**：代码运行的中间结果保存在寄存器里，切换线程时需保存。

    * **堆栈信息**：堆栈保存函数调用信息（返回地址、各层局部变量），可能很大——TCB 只存**堆栈指针**，恢复时填回 SP 堆栈寄存器。

    * **运行状态**：运行、就绪还是阻塞；阻塞态还可记录阻塞原因等。

    * **线程的优先级**：供线程调度或系统分配资源时参考。

* PC、各寄存器值、堆栈信息这三部分就是线程切换时需保存和恢复的**运行现场**。TCB 与 PCB 高度同构，区别在于线程不负责资源分配，TCB 里没有资源分配相关的信息。

* **线程的组织**：把多个 TCB 有规律地分门别类形成**线程表**——可以每个进程一张、全系统一张，或按线程状态分类组织，不同系统策略不同。**线程的控制**就是让线程在各种状态间切换，与进程类似且往往更简单。

## 处理机调度

* > **定义**：当有一堆任务要处理、资源有限无法同时处理时，按某种规则（先到先服务、短任务优先等）决定处理顺序——如银行先到先服务、VIP 优先级更高；宿舍卫生间用时间短的先用。

### 三个调度层次

* **高级调度（作业调度）**

    * > **定义**：按调度规则从外存的**作业后备队列**中选一个作业调入内存，并为其建立对应进程（建立 PCB）。

    * 作业：用户让操作系统帮它启动的、处理具体任务的程序。内存资源不足时新提交的作业无法马上放入内存，就排队等待作业调度。

    * 每个作业整个生命周期**只调入一次、调出一次**：调入时建立 PCB，作业完成后被调出时撤销 PCB。频率在三层中**最低**。

* **低级调度（进程调度/处理机调度）**

    * > **定义**：按某种策略从**进程就绪队列**中挑选一个进程，把处理机资源分配给它。

    * **多道程序并发执行必然需要进程调度，它是操作系统中最基本的一种调度**；频率**最高**——只有高频调度才能让各进程很快轮流上 CPU，宏观上看起来像同时执行。

* **中级调度（内存调度）**

    * > **定义**：内存不足时，把不太紧急的进程数据从内存**调出到外存**（进入挂起态，PCB 组织成挂起队列），有空闲内存时再决定把哪个进程的数据**调回内存**。

    * 进程生命周期内可能**多次调出、多次调入**，频率比高级调度高。

    * 生活实例：手机切换应用有时快有时卡——卡顿可能就是系统在中级调度中把该进程的数据从外存读回内存，读回后进程才能顺利运行。

* 三层调度对比

    | 对比项 | 高级调度（作业调度） | 中级调度（内存调度） | 低级调度（进程调度/处理机调度） |
    | :---: | :--- | :--- | :--- |
    | 发生位置 | 外存 ↔ 内存 | 外存 ↔ 内存 | 内存 ↔ CPU |
    | 面向对象 | 面向作业 | 面向进程 | 面向进程 |
    | 调入调出次数 | 作业只调入一次、调出一次；调入建 PCB，调出撤 PCB | 进程可多次调出、多次调入 | 极高频，各进程轮流上 CPU |
    | 发生频率 | 最低 | 中等 | 最高 |
    | 对进程状态的影响 | 使进程从无到创建态，PCB 建好后放入就绪队列进入就绪态 | 使挂起态进程重新回到就绪态；细分挂起时也可使阻塞挂起的进程回到阻塞态 | 选择就绪态进程进入运行态 |

* 记名称要记**后面那个**：作业调度、内存调度、进程调度——考题中最高频的叫法。

### 挂起态与七状态模型

* **挂起状态**可细分为**就绪挂起**和**阻塞挂起**两种；五状态模型是 408 要求掌握的，七状态模型部分自主命题学校可能考察。

```text
  内存中的状态                        外存中的状态（挂起态）

┌────────────┐   挂起：调出到外存   ┌────────────┐
│   就绪态   │ ─────────────────> │  就绪挂起态 │
└────────────┘                    └────────────┘
┌────────────┐   挂起：调出到外存   ┌────────────┐
│   阻塞态   │ ─────────────────> │  阻塞挂起态 │
└────────────┘                    └────────────┘

激活：调回内存（就绪挂起 → 就绪态；阻塞挂起 → 阻塞态）
事件发生：阻塞挂起态 ──等待的事件发生──> 就绪挂起态
```

* 其他进入就绪挂起态的方式：运行态进程运行结束下处理机时可能直接放入外存，进入就绪挂起；创建态进程 PCB 建好后遇内存不足，也可能进入就绪挂起。

* > **易错点** ⚠️：挂起与阻塞都是暂时不能获得 CPU 服务的状态，区别在于：挂起态的**进程映像在外存**；阻塞态的进程映像还在**内存**中。

* 有的操作系统把就绪挂起和阻塞挂起分成两个挂起队列；有的还按阻塞原因把阻塞挂起的进程细分多个队列。

### 调度的时机

* 需要（可）进行调度与切换的情形分两类：

    * **主动放弃处理机**：进程正常终止；运行中发生异常不得不终止；进程发出 I/O 请求、主动进入阻塞态。

    * **被动放弃处理机**：时间片用完；有更紧急的事情要处理；优先级更高的进程进入就绪队列。

* **三种情况不能进行调度与切换**：

    * **处理中断的过程中**——中断处理过程复杂且与硬件相关，难以处理到一半去调度切换。

    * **进程在操作系统内核程序临界区中**——临界区访问的是就绪队列等内核数据结构，见下。

    * **原子操作（原语）的过程中**——如状态转换要同时"改 PCB 状态标志 + 移动 PCB 到新队列"，中间插入调度会导致 PCB 记录的状态与实际所在队列不匹配，给系统造成安全隐患。

* 概念铺垫：**临界资源**是一个时间段内只允许一个进程使用的资源，各进程需**互斥**访问；**临界区**是访问临界资源的那段代码；**内核程序临界区**一般用来访问某种内核数据结构（如就绪队列）。

* 内核程序临界区 vs 普通临界区：

    * 进程处于**内核程序临界区**时访问前会给就绪队列**上锁**，未退出未解锁期间若发生调度，调度程序要访问就绪队列选进程就无法顺利进行，还会影响内核的其他管理工作——所以**不能调度与切换**，必须让它尽快执行完临界区代码、尽快解锁。

    * 进程访问**普通临界资源**（如打印机）时若不允许调度，进程会霸占 CPU 空等慢速 I/O，浪费 CPU——普通临界区不影响内核管理工作，为了增加并发度、提高 CPU 利用率，**可以**进行进程调度和切换。

    * > **易错点** ⚠️：真题辨析（2012）——"进程在处于临界区时，不能进行处理器调度"这一表述**错误**。正确说法是"进程在操作系统**内核程序**临界区中不能进行调度与切换"，普通临界区可以调度，不能一概而论。

* 两种调度方式：

    * **非剥夺调度方式（非抢占式）**：只允许进程主动放弃处理机。规则简单、实现简单、系统开销小；但无法及时处理紧急任务，只适合早期批处理系统。

    * **剥夺调度方式（抢占式）**：有更重要更紧急的任务时，可暂停当前进程、剥夺其处理机资源；还能按时间片轮转执行（时间片到就强行剥夺）。适合**分时操作系统和实时操作系统**。

* 狭义的进程调度：从就绪队列中**选中**一个要运行的进程；若选中的不是刚暂停的进程，就还需要**进程切换**（前者让出处理机、后者占用）。题目里出现"进程调度"也可能指广义——包含"先选中、再切换"两步，读题时分辨即可。

* 进程切换完成两件事：把原运行进程的各种数据**保存**（存入 PCB），把新进程的运行环境**恢复**（从 PCB 读出放入相应寄存器；运行现场——程序计数器、程序状态字、各数据寄存器——一般存放在 PCB 中）。

* > **易错点** ⚠️：进程切换不能瞬间完成、有代价——**不能简单认为切换越频繁并发度越高**，切换过于频繁会把大量时间花在切换开销上，真正推进进程的时间反而减少、系统效率降低。

### 调度程序

* **调度器（调度程序，Scheduler）**是内核中非常重要的程序模块，负责"就绪→运行"和"运行→就绪"两个转换；决定两件事：**让谁去运行**（取决于调度算法：先来先服务、短作业优先、时间片轮转等）、**运行多长时间**（分配多大的时间片）。

* 触发调度程序工作（即进程调度的时机）的事件：

    * **创建新进程**：就绪队列改变，可能让新进程抢占当前运行的 CPU。

    * **进程退出**：正在运行的进程终结自己，处理机空闲。

    * **进程阻塞**：同上需要人接手处理机。

    * **发生 I/O 中断**：可能使某些阻塞进程回到就绪态，需检查新就绪进程能否抢占。

* 抢占与非抢占对唤醒方式的影响：**非抢占式**只有运行进程阻塞或退出时才触发调度程序，**不会由时钟中断唤醒**；**抢占式**下只要就绪队列一改变就要检查是否可抢占，这个例行检查由**时钟中断**触发（每个或每 k 个时钟中断唤醒一次调度程序）。

* 系统支持内核级线程时，调度对象就是**内核级线程**——内核线程作为调度的基本单位，进程作为资源分配的基本单位；不支持内核级线程的系统调度对象依然是进程。

### 闲逛进程

* > **定义**：就绪队列中没有其他就绪进程时，调度程序选中上处理器运行的进程；实际的系统中 CPU 永远不可能空闲。

* 特性：

    * **优先级最低**：只要有其他任何一个就绪进程，就不会选它上处理机。

    * **执行零地址指令**：不需要访存、甚至不访问 CPU 里的任何寄存器，CPU 能耗低、省电。

    * **每条指令周期末尾例行检查中断**：中断可周期性唤醒调度程序，检查有无其他就绪进程，有则让闲逛进程下处理机。

* 闲逛进程是调度程序永远可选的"备胎"；该考点大概率只出现在选择题。

## 调度评价指标

### CPU 利用率与系统吞吐量

* > **定义**：CPU 利用率表示 CPU 处于忙碌的时间占总时间的比例。

    * $$CPU\ 利用率 = \frac{CPU\ 忙碌的时间}{总时间} \times 100\%$$

    * 设计动机：CPU 造价昂贵，希望它尽可能多地工作。有的题也让算某设备（如 I/O 设备）的利用率，方法相同。

    * 单道程序算例：作业先 CPU 运行 5 秒、打印 5 秒、再执行 5 秒，总耗时 15 秒；CPU 忙碌 10 秒，CPU 利用率 $10/15 \approx 66.66\%$；打印机忙碌 5 秒，利用率 $5/15 \approx 33.33\%$。考研真题通常考**多道程序并发**，用**甘特图**辅助计算。

* > **定义**：系统吞吐量表示单位时间内完成了多少道作业。

    * $$系统吞吐量 = \frac{总共完成了多少道作业}{总共花了多少时间}$$

    * 例：处理完 10 道作业花 100 秒，吞吐量 $10 \div 100 = 0.1$ 道/秒。

### 周转时间

* > **定义**：从作业被提交给系统开始，到作业完成为止的这段时间。

    * $$周转时间 = 作业完成时间 - 作业被提交给系统的时间$$

    * 包括四个部分：作业在外存后备队列上等待作业调度的时间 + 进程在就绪队列上等待的时间 + 进程运行态的时间 + 进程阻塞态的时间；其中后三项在作业处理过程中会发生**多次**，而作业调度整个过程只发生一次。

* > **定义**：平均周转时间是各作业周转时间之和除以作业数。

    * $$平均周转时间 = \frac{各作业周转时间之和}{作业数}$$

* > **定义**：带权周转时间是作业周转时间除以作业实际运行的时间；**必定大于等于 1**（周转时间包含实际运行时间）。

    * $$带权周转时间 = \frac{作业周转时间}{作业实际运行的时间}$$

    * 设计动机：周转时间相同的两个作业，实际运行时间更长的那个等待占比更小、用户满意度更高（等厕所类比：只用 1 分钟却排 10 分钟共 11 分钟，感受糟糕；用 10 分钟只等 1 分钟同为 11 分钟，感受没那么糟）。所以实际运行时间长的作业带权周转时间更小；实际运行时间相同时，周转时间短的带权周转时间更小、满意度更高。

    * 周转时间、带权周转时间都是**越小越好**；带权周转时间也有对应的**平均带权周转时间**（各作业带权周转时间之和除以作业数），是系统关心的指标。

### 等待时间与响应时间

* > **定义**：等待时间是作业/进程**等待处理机被服务**的时间之和；等待越长满意度越低。同样有平均等待时间（所有进程或作业的等待时间之和除以个数）。

    * > **易错点** ⚠️：进程**等待 I/O 完成期间它正在被 I/O 设备服务**，这段时间**不能算进等待时间**；且作业的等待时间还要**加上在外存后备队列中等待被调度的时间**——作业与进程的等待时间算法稍有不同。

    * 一个作业总共需要被 CPU 服务多久、被 I/O 设备服务多久一般是**确定不变**的，所以调度算法只会影响作业或进程的**等待时间**。

* > **定义**：响应时间是从用户提交请求到**首次产生响应**所用的时间。
