# 处理机调度

## 分析框架与评价指标

* **调度算法分析六角度**

    * 分析任一调度算法的固定框架：算法提出（为解决什么问题）、算法规则、适用场景（用于作业调度还是进程调度、两者有无区别）、是否可抢占、优缺点、是否会导致饥饿。

* **饥饿**

    * > **定义**：进程或作业长期得不到服务，即处于饥饿状态。

    * 一直得不到服务的更严重饥饿称为进程（作业）**饿死**。

    * 是否饥饿速记：先来先服务、高响应比优先、时间片轮转不会饥饿；短作业优先、优先级调度、多级反馈队列可能饥饿。

* **周转时间**

    * > **定义**：完成时间 − 到达时间。

* **带权周转时间**

    * > **定义**：周转时间 ÷ 运行时间，表示周转时间是运行时间的多少倍。

    * 该值越大说明进程只需很少的服务时间却等了很久，用户体验越糟糕。

* **等待时间**

    * 纯计算型进程：等待时间 = 周转时间 − 运行时间。

    * 进程含 I/O 操作时：等待时间 = 周转时间 − CPU 运行时间 − I/O 设备服务时间，要具体题目具体分析。

* **平均值**

    * 平均周转时间、平均带权周转时间、平均等待时间：把对应一列求和除以进程个数。

## 先来先服务（FCFS）

* **先来先服务（FCFS）**

    * > **定义**：按到达就绪队列（或后备队列）的先后顺序依次服务，从公平角度出发，类似日常排队。

    * 用于**作业调度**时看谁先到达后备队列（在外存）；用于**进程调度**时看谁先到达就绪队列（在内存）。

    * 非抢占式：当前进程/作业主动放弃处理机时才调度下一个。

    * 实质上照顾的是等待时间最久的进程——等待越久越优先。

    * 优点：公平、实现简单。

    * 缺点：对长作业有利、对短作业不利；排在长作业后面的短作业要等很久，带权周转时间可能非常大。

    * 不会导致饥饿：前面的作业总会被处理完，迟早轮到。

    * 现今仍经常与其他算法结合使用。

    * > **易错点** ⚠️：等待时间 = 周转时间 − 运行时间 只对纯计算型进程成立，含 I/O 的进程还要再减去 I/O 服务时间。

    * 例题基准（P1~P4 到达 0/2/4/5、运行 7/4/1/4）：调度顺序 P1→P2→P3→P4，平均周转时间 8.75、平均带权周转时间 3.5、平均等待时间 4.75；P3 的带权周转时间高达 8。

## 短作业优先（SJF）

* **短作业优先（SJF）／短进程优先（SPF）**

    * > **定义**：每次挑选要求服务时间（运行时间）最短的作业/进程优先服务；用于作业调度称 SJF，用于进程调度称 SPF，规则相同。

    * 提出目的：追求更少的平均等待时间、平均周转时间和平均带权周转时间。

    * 默认**非抢占式**；抢占式版本为**最短剩余时间优先（SRTN）**。

    * 非抢占式规则：每次在**当前已到达**的进程中选运行时间最短者；运行时间相同时先到达者优先。

    * SRTN 规则：盯住两个时机——**就绪队列改变**（新进程到达）时，比较新进程与当前运行进程的剩余时间，更短则抢占、被抢占者回就绪队列；**当前进程完成**时按剩余时间重新调度。

    * 抢占式下进程执行可能断断续续（同一进程被切成多段），算指标时别踩坑。

    * 例题对比（同上数据）：平均周转时间 FCFS 8.75 → 非抢占 SJF 8 → SRTN 7；平均等待时间 4.75 → 4 → 3；抢占式指标优于非抢占式。

    * > **易错点** ⚠️：「SJF 得到的平均等待时间和平均周转时间最少」不严谨——必须加条件「所有进程**几乎同时到达**」，或者改说成「抢占式 SRTN 得到的平均等待时间和平均周转时间最少」。

    * 考试技巧：相比 FCFS、HRRN 等算法，SJF 仍能获得**比较少**的平均等待/周转时间；若选项「SJF 最少」的其余选项错误明显，也可选它。教材说法没有绝对严格的标准，要学会选错误更少、更合适的选项。

    * 缺点：对短作业有利、对长作业不利；源源不断的更短作业到来会导致**长作业饥饿**，甚至饿死。

    * 运行时间是用户提供的估计数据，用户可把长作业报短——SJF 未必真能做到短作业优先。

## 高响应比优先（HRRN）

* **高响应比优先（HRRN）**

    * > **定义**：每次调度时计算当前已到达各进程/作业的响应比，选响应比最高者服务；兼顾等待时间与运行时间的折中算法。

    * 响应比 = $\frac{等待时间 + 要求服务时间}{要求服务时间}$，分子比分母多一个正的等待时间，故响应比恒 ≥ 1。

    * 非抢占式，可用于作业调度和进程调度；只有进程/作业**主动放弃处理机**（正常或异常完成终止、主动要求阻塞）时才重新计算响应比。

    * 等待时间相同时，要求服务时间短者响应比更高——体现 SJF 的优点；要求服务时间相同时，等待久者响应比更高——体现 FCFS 的优点。

    * 长作业随等待时间增长响应比不断变大、被调度机会越来越高——**不会导致饥饿**，避免了 SJF 的长作业饥饿问题。

    * 例题（同上数据）：调度顺序 P1→P3→P2→P4；服务时间相同的 P2、P4，因 P2 先到达、等待更久，每个决策点都是 P2 胜出（7 时刻 P2 响应比 2.25 对 P4 的 1.5）。

## 三种批处理算法对比

| 角度 | 先来先服务 | 短作业优先 | 高响应比优先 |
| :---: | :--- | :--- | :--- |
| 调度依据 | 等待时间（谁等得久） | 要求服务时间（谁最短） | 响应比（等待与运行兼顾） |
| 是否抢占 | 非抢占 | 默认非抢占（抢占版为 SRTN） | 非抢占 |
| 对长/短作业 | 长作业有利、短作业不利 | 短作业有利、长作业不利 | 两者兼顾、相对折中 |
| 是否饥饿 | 不会 | 会，严重时饿死 | 不会 |

* 三种算法主要关心用户作业/进程的**公平性**，追求平均周转时间、平均等待时间等**系统整体性能**指标；不关心响应时间、不区分任务紧急程度，交互性糟糕。

* 一般用于**早期批处理系统**——当时计算机昂贵，人们更追求系统整体表现而非单个用户的体验。

## 时间片轮转（RR）

* **时间片轮转（RR，Round-Robin）**

    * > **定义**：按进程到达就绪队列的顺序，轮流让每个进程执行一个时间片；时间片用完被强行剥夺处理机、排回就绪队列队尾。

    * 为公平地轮流服务、让各进程在一定时间间隔内都得到响应而提出；伴随**分时操作系统**的诞生而诞生。

    * **只用于进程调度**：时间片是处理机的时间片，进程才是分配处理机的基本单位，作业须先放入内存建立进程才可能被分配时间片。

    * **抢占式**：进程未运行结束、时间片一到就被剥夺处理机；由时钟装置（计时硬件）发出时钟中断通知 CPU「时间片已到」。

    * 排队惯例：默认**新到达的进程先插入就绪队列**，刚下处理机的进程随后回到队尾；题目另有说明时按题目规则。

    * 进程运行时间小于时间片时主动放弃处理机，同样发生一次调度；轮到某进程时若就绪队列已空，允许它继续再跑一个时间片。

    * 时间片长短没有定数，有的系统设得长、有的设得短、有的动态调整。

    * 分时系统更关心**响应时间**而非周转时间，一般不算平均周转/等待指标（题目明确要求时仍要会算）。

    * 优点：对各进程公平、响应快，适合分时操作系统。

    * 缺点：进程切换有开销；不区分任务紧急程度——再急的活也得排队等片。

    * 不会饥饿：轮流服务，谁也不会被落下。

    * 例题要点（P1~P4 到达 0/2/4/5、运行 5/4/1/6）：时间片 = 2 时 16 时刻全部完成；时间片 = 5 时除多一道「时间片是否用完」的检查外，调度时机与顺序和 FCFS 完全一致。

### 时间片大小的影响

* **时间片太大**

    * 大到几乎每个进程都能在一个时间片内完成时，**退化为先来先服务算法**——调度只发生在进程主动放弃处理机时，顺序完全按到达先后。

    * 响应时间增大：10 个进程并发、时间片 1 秒时，用户在时间片刚用完时发出的调试命令最坏要等 9 秒才可能被响应。

* **时间片太小**

    * 进程切换要保存/恢复运行环境，有**时间代价**；切换过于频繁时系统把大部分时间耗在切换本身，真正用于进程执行的时间比例下降。

    * 设计参考准则：切换开销占比不超过 1%（一般不考，拓展了解）。

    * > **易错点** ⚠️：时间片太大 → 退化为 FCFS、响应时间增大；时间片太小 → 切换开销占比过高。这组对比在选择题中经常出现。

## 优先级调度

* **优先级调度**

    * > **定义**：为每个作业/进程设置一个优先级，调度时选择优先级最高的那一个。

    * 提出背景：越来越多的应用需要按任务的紧急程度、重要程度决定处理顺序。

    * 适用面宽：既可用于**作业调度**（从外存后备队列挑作业进内存），也可用于**进程调度**（从内存就绪队列挑进程），还可用于 I/O 调度。

    * **非抢占式**：只在进程主动放弃处理机的时刻调度、检查；**抢占式**：除此之外，就绪队列发生改变时（如新进程到达）也要检查是否抢占。

    * 优先级相同时先到达者优先。

    * 例题要点（P1~P4 优先数 1/3/4/3、数大者级高，到达 0/2/4/5、运行 7/4/1/4）：非抢占顺序 P1→P3→P2→P4；抢占式下 P2、P3 到达时均抢占 P1/P2，最后 P1 补完剩余时间。

    * > **易错点** ⚠️：**优先数 ≠ 优先级**——有的题目优先数越大优先级越高，有的越小越高，必须看题目给出的说明，不能默认。

    * 优点：灵活区分任务紧急程度与重要程度，适合**实时操作系统**；想让谁优先就把谁的优先级设高。

    * 缺点：源源不断的更高优先级进程到来时，低优先级进程可能长期得不到服务，**可能饥饿**。

### 优先级的组织与设置

* **就绪队列组织**

    * 可按优先级设置多个就绪队列；也可只设一个队列，按优先级从高到低动态调整队内进程位置，让高优先级者靠近队头。

* **静态与动态优先级**

    * 静态优先级：创建进程时确定，之后一直不变。

    * 动态优先级：先给初始值，之后根据运行情况动态调整。

* **初始值设置三原则**

    * 系统进程高于用户进程——系统进程是管理者。

    * 前台进程高于后台进程——前台进程的流畅程度对用户更重要。

    * 偏好 I/O 型（I/O 繁忙型）进程，而非计算型（CPU 繁忙型）进程——I/O 设备与 CPU 可**并行工作**，让 I/O 型进程优先运行能使 I/O 设备尽早投入工作，提升 I/O 设备利用率与系统吞吐量。

* **动态优先级的调整时机**

    * 进程在就绪队列**等了太长时间** → 适当提升优先级；高响应比优先的响应比本质上就代表优先级，可视为一种动态优先级算法。

    * 进程**已运行很长时间** → 适当降低优先级，出于公平考虑。

    * 进程**频繁进行 I/O 操作** → 适当提升优先级，利于资源利用率与吞吐量。

## 多级反馈队列调度

* **多级反馈队列调度**

    * > **定义**：设置多级就绪队列，各队列优先级从高到低、时间片从小到大，综合 FCFS、SJF、RR、优先级调度优点的折中算法。

    * 一般用于**进程调度**；考试口径（汤子瀛教材）认为它是**抢占式**算法——实际操作系统也可能把它实现为非抢占式版本。

    * 规则一：新进程到达，先进入**优先级最高的第一级队列队尾**，按 FCFS 原则排队等待分配时间片。

    * 规则二：只有当更高优先级的队列**全部为空**时，才调度更低优先级队列中的进程。

    * 规则三：时间片用完且未结束 → 降到**下一级**队列队尾；已在最后一级且时间片用完仍未结束 → 回**本级**队尾再次排队。

    * 规则四（抢占）：有更高优先级的进程到达时剥夺当前进程的处理机；被抢占的进程**放回原来这一级的队尾**，而不是降到下一级。

    * 例题要点（P1 运行 8、P2 运行 4、P3 运行 1；队列时间片 1/2/4）：P3 在 5 时刻到达 Q1，抢占正在 Q2 运行的 P2，P2 回 Q2 队尾、唤醒后补完本时间片剩余额度；P1 降到 Q3 后无法再降，跑满 4 个单位的时间片回 Q3 队尾，再被调度一次即可完成。

    * 优点：对各类进程相对公平（新进程必先被最高级队列处理，FCFS 之长）；响应快（新进程在第一级队列很快被调度，RR 之长）；短进程只需经历高优先级的几个短时间片队列即可完成（SJF 之长）；**不需要预先估计运行时间**，避免了 SJF 中用户虚报运行时间的作假空间。

    * 灵活调整偏好的示例：I/O 型进程因发出 I/O 请求**主动阻塞**、被唤醒后让它**放回原来那一级队列**而非降级，使其长期保持较高优先级——即可偏好 I/O 密集型进程。

    * 缺点：源源不断的短进程在第一级队列拿个短时间片就能跑完时，已降级的进程可能长期得不到服务，**可能饥饿**。

    * UNIX 系统采用多级反馈队列调度算法。

## 多级队列调度

* **多级队列调度**

    * > **定义**：按**进程的类型**设置多个就绪队列，给不同队列设置不同优先级；进程创建后按类型分入相应队列。

    * 示例分层（优先级从高到低）：系统进程队列 > 交互式进程队列 > 批处理进程队列。

    * 排序依据：系统进程最高无可厚非；交互式进程需要及时响应反馈（打游戏、打字要立即得到反馈）；批处理进程（AI 模型训练、视频渲染等）对及时性不敏感，放低优先级不影响体验。实际系统可做更多分类、更多级队列。

    * 调度流程：每次调度先选中一个队列，再按该队列内部的调度算法选出一个进程上处理机。

### 队列间与队列内的调度

* **队列间两种策略**

    * 绝对的、固定的优先级：只要高优先级队列不空，就一定先运行其中的进程——可能不合理（就绪队列里有一个系统进程，打字动作就永远得不到响应）。

    * 按比例分配时间：如 100ms 中系统进程 50%（50ms）、交互式 40ms、批处理 10ms——保证固定时间范围内**任何一类进程都至少被响应一次**。

* **队列内可用不同算法**

    * 系统进程队列用优先级调度（谁紧急先处理谁）；交互式队列用时间片轮转（保证各交互进程短时间内都至少被响应一次）；批处理队列用先来先服务——仅为示例，可设其他算法。

## 交互式系统算法的定位

* 时间片轮转、优先级调度、多级反馈队列、多级队列适合**交互式系统**（分时操作系统、实时操作系统）。

* 计算机造价降低后，交互式系统更注重对各进程的**响应时间**以及**公平性、平衡性**，而不是批处理系统里平均周转时间那种宏观指标；这几种算法恰好能提供较快的响应时间、追求公平平衡的性能。

## 多处理机调度

* **多处理机调度**

    * > **定义**：多核 CPU 环境下的调度，每个核可独立运行一个进程；除按调度算法选出进程外，还要决定进程上**哪一个 CPU** 运行——相比单处理机调度多出的第二个维度。

    * 是 2025 考研大纲新增考点。

    * 两个新调度目标：**负载均衡**与**处理机亲和性**；两者存在张力——迁移进程能均衡负载，但会牺牲亲和性。

* **负载均衡**

    * > **定义**：尽可能让各个 CPU 都同等忙碌。

    * 例：CPU1 负载 50%、CPU4 负载 95% 时，应让 CPU1 替 CPU4 分担任务。

* **处理机亲和性**

    * > **定义**：尽可能让一个进程调度到**同一个** CPU 上运行，以发挥 CPU 缓存（cache）的作用。

    * 各 CPU 有各自 cache、缓存各进程的数据；进程被调到没有自己数据副本的 CPU 上时，只能更多访问主存，而访问主存比访问 cache 慢得多。

### 公共就绪队列

* **公共就绪队列**

    * > **定义**：系统内所有就绪进程的 PCB 用队列形式连成一条统一就绪队列（位于内存内核区），每个 CPU 空闲时都运行调度程序，从公共队列中按调度算法选进程运行。

    * 调度算法原理与单处理机完全一样（如各 CPU 空闲时各自选当前优先级最高的进程）。

    * 各 CPU 对公共就绪队列的访问必须**互斥（上锁）**：CPU 并行运行，若两个调度程序同时不上锁地访问，同一进程可能被调度到两个 CPU 上。

    * 优点：**天然实现负载均衡**——CPU 一空闲必然从公共队列选到进程，不会出现有的 CPU 一直空闲、有的一直忙碌。

    * 缺点：**处理机亲和性不好**——进程会频繁切换 CPU，cache 作用发挥不出来。

    * 补救——两种亲和性：**软亲和**由操作系统调度程序**尽量**保证进程固定在同一 CPU（不得已的情况仍可能迁移）；**硬亲和**由用户进程通过**系统调用**主动要求操作系统分配一个固定 CPU。现实应用中两者通常混用。

### 私有就绪队列

* **私有就绪队列**

    * > **定义**：操作系统给每一个 CPU 各配一条就绪队列，CPU 空闲时总是从自己的私有队列中调度进程运行，调度程序不跨队列挑活。

    * **天然实现处理机亲和性**：进程一段时间内总在同一个 CPU 上运行，自然发挥 cache 作用；但负载太高时进程仍可能被迁移到其他 CPU。

    * 程序员要确保亲和性同样可用硬亲和：通过系统调用声明进程不希望在运行中迁移。

* **推迁移（push）**

    * 一个特定的系统程序**周期性检查**各 CPU 的负载，把忙 CPU 私有队列中的就绪进程**推**到闲 CPU 的队列里，重新分配任务——类似系统里有个「包工头」专门派活。

* **拉迁移（pull）**

    * 每个 CPU 的调度程序周期性（如规定**每调度十次**）检查自身与其他 CPU 的负载，发现自己闲、别人忙时主动**拉**一些就绪进程进自己的队列——类似同事之间互帮互助。

* 两方案互补：公共就绪队列天然负载均衡、靠软/硬亲和补亲和性短板；私有就绪队列天然亲和性好、靠推迁移和拉迁移补负载均衡短板。

## 进程同步与进程互斥

### 进程同步

* **异步性**

    * > **定义**：各并发执行的进程以各自独立的、不可预知的速度向前推进。

    * 异步性使并发进程的推进顺序不可预知；当应用场景要求特定次序（如管道通信中**写数据必须发生在读数据之前**，写满后读进程才能读）时，异步性是必须解决的问题。

* **进程同步**

    * > **定义**：为完成某项任务而相互合作的进程间，需要确定并协调它们之间的工作次序；又称**直接制约关系**——进程之间有直接的合作。

    * 操作系统需提供进程同步机制，让各进程按想要的顺序依次推进。

### 进程互斥

* **临界资源**

    * > **定义**：一个时间段内只允许一个进程使用的资源；对其访问必须**互斥**进行——一个进程访问时，其他想访问的进程必须等待，直到资源被释放。

    * 来源于资源的**互斥共享**方式；与之相对的**同时共享**方式允许一个时间段内多个进程宏观同时（微观可能交替）访问。

* **访问临界资源的四部分逻辑**

    * 进入区：检查此时能否访问临界资源，可以则上锁、设置「正在访问临界资源」的标志。

    * 临界区：实际访问临界资源的那段代码（如对打印机执行写操作的代码），又名**临界段**。

    * 退出区：解除进入区设置的「正在访问」标志（解锁）。

    * 剩余区：做其他处理。

    * > **易错点** ⚠️：「进入区和退出区是用于访问临界资源的那段代码」是常见干扰说法——真正访问临界资源的是**临界区**，进入区只做检查 + 上锁，退出区只做解锁。

* 没有互斥的后果：进程 A 使用打印机到一半时间片用完被切走，B 接着使用打印机，两个进程的内容就打印混在一起；若 A、B 互斥访问打印机则不会出问题。

### 互斥实现的四个原则

* **空闲让进**：临界区空闲、没有被任何进程访问时，应允许一个请求进入的进程立即进入。

* **忙则等待**：已有进程在访问临界区时，其他想进入的进程必须等待。

* **有限等待**：进程暂时进不了临界区时，要保证它在有限时间之后能进入，不能发生饥饿。

* **让权等待**：进程暂时进不了临界区时，应立即释放处理机，防止「盲等待」——明明无法推进却一直占着处理机，使处理器无法为别的进程服务。

* 制约关系区分：同步是**直接制约关系**（有直接合作）；互斥是**间接制约关系**——进程间本无直接合作，只因都想使用同一临界资源才产生制约。

## 互斥的软件实现方法

* 考察频率很高，选择题、大题都常考；学习时抓三点：理解算法思想原理、弄清进入区/退出区各做什么、结合四原则分析缺陷。

### 单标志法

* **单标志法**

    * 核心机制：设变量 `turn` 表示当前允许进入临界区的进程号（`turn == 0` 允许 0 号进）；进程访问完在**退出区把使用权转交对方**——P0 退出时 `turn = 1`，P1 退出时 `turn = 0`，本质是一次「谦让」。

    * 进入区：`while (turn != 自己的编号);` 不轮到自己就在循环里不断轮询，直到对方用完转交权限。

    * 缺陷：只能**轮流**使用——临界资源明明空闲，却因为上次是自己做的谦让、这次没轮到自己而进不去，违反**空闲让进**。

### 双标志先检查法

* **双标志先检查法**

    * 核心机制：布尔数组 `flag[i]` 表示 i 号进程想进入临界区的意愿（`true` 想进）；进入区**先检查对方**是否想进，对方不想再表达自己的意愿（`flag = true`，即上锁）；退出区置回 `false`（解锁）。

    * 缺陷：并发运行时，「检查」和「上锁」两个动作**不能一气呵成**，中间可能发生进程切换——两个进程都检查通过、先后置位、**同时进入临界区**，违反**忙则等待**。

    * 思路本身是好的，问题只出在检查与上锁之间可被打断；后面的硬件实现方法能让这两个动作一气呵成，从而保证正确。

### 双标志后检查法

* **双标志后检查法**

    * 核心机制：与先检查法同样用 `flag` 数组表达意愿，但顺序反过来——**先上锁、后检查**。

    * 并发推演：两进程先后置位后，互相发现对方想进，各自卡在检查循环里，**都进不了**临界区。

    * 缺陷：解决了忙则等待（不可能两进程同时进入），却违背**空闲让进**（临界区空闲也进不去）和**有限等待**（无限等待、无法推进）——各进程长期无法访问临界资源，产生**饥饿**。

### Peterson 算法

* **Peterson 算法**

    * 核心机制：结合双标志法的**意愿**（`flag` 数组）与单标志法的**谦让**（`turn` 变量），同时设置两者。

    * 进入区三步：**主动争取**（自己 `flag = true`）→ **主动谦让**（`turn = 对方的编号`）→ **检查**（对方也想进**并且**最后谦让的是自己，才循环等待；两个条件有一个不满足就进入临界区）；退出区把自己 `flag` 置回 `false`。

    * 关键规律：各进程对 `turn` 的设置必有先后顺序，**最后设置 `turn` 的人就是最后做谦让动作的人，失去行动优先权**，让对方优先进入临界区。

    * 软件方法实现了互斥，满足**空闲让进、忙则等待、有限等待**三原则。

    * 缺陷：**没有遵循让权等待**——进不了临界区就一直卡在 while 循环里占着 CPU 不断轮询检查。四种软件方案中最好的一个，但依然不够好。

```c
bool flag[2];   // 意愿：flag[i] == true 表示 i 号进程想进入
int  turn = 0;  // 谦让：turn 表示优先让谁用

// P0 进程                       // P1 进程
flag[0] = true;                  flag[1] = true;                 // 主动争取
turn = 1;                        turn = 0;                       // 主动谦让
while (flag[1] && turn == 1);    while (flag[0] && turn == 0);   // 检查
临界区;                          临界区;
flag[0] = false;                 flag[1] = false;                // 撤销意愿
```

### 四种软件实现对比

| 算法 | 核心机制 | 主要缺陷 | 违反的原则 |
| :--- | :--- | :--- | :--- |
| 单标志法 | `turn` 变量，用完把权限转交对方 | 只能轮流使用，资源空闲也进不去 | 空闲让进 |
| 双标志先检查法 | `flag[]` 表达意愿，先检查后上锁 | 并发下检查、上锁之间可被打断，两进程同时进入 | 忙则等待 |
| 双标志后检查法 | `flag[]` 表达意愿，先上锁后检查 | 两进程都进不去，无限等待、饥饿 | 空闲让进、有限等待 |
| Peterson 算法 | `flag[]` 表达意愿 + `turn` 表达谦让 | 进不去时死循环轮询，仍占用 CPU | 让权等待 |

* 软件方式实现互斥离不开两种核心思想：**谦让**（`turn` 类变量，转交使用权）与**表达意愿**（`flag` 类数组，声明想进入）；题目换变量名、做细微变化时，抓住这两点即可分析。
