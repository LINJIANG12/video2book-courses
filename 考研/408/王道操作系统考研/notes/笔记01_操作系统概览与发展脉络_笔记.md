# 操作系统概览与发展脉络

## 计算机系统的层次结构

```text
            用户
             │
             │  GUI（图形用户接口）、命令接口（联机 / 脱机）
             ▼
         应用软件
             │
             │  系统调用（程序接口）
             ▼
         操作系统
             │
             ▼
      裸机（纯硬件）
```

   * **裸机**

       * > **定义**：只有硬件、不包含任何软件的机器。

       * 厂家把 CPU、主板等硬件组装成裸机，出售前一般会预装操作系统；用户再在操作系统之上安装应用程序。

   * **层次关系**

       * 自底向上依次为：裸机（纯硬件）→ 操作系统 → 应用软件 → 用户。

       * 用户通过 GUI 和命令接口直接使用操作系统；应用程序通过系统调用（程序接口）与操作系统交互——这些接口就是层次之间「相连的部分」。

---

## 操作系统的定义与角色

   * **操作系统（Operating System，OS）**

       * > **定义**：操作系统是控制和管理整个计算机系统的硬件与软件资源、合理地组织调度计算机的工作与资源分配、并为用户和其他软件提供方便的接口和环境的最基本的系统软件。

       * 定义拆成三层，对应三个角色：系统资源的管理者；向上层（用户和应用程序）提供方便易用的服务；计算机系统中最基本的系统软件。

       * 操作系统是一种软件而不是硬件，但它是最接近硬件的一层软件。

   * **资源管理者的具体工作**

       * 管理对象既包括软件资源（正在运行的进程，即正在运行的程序），也包括硬件资源（CPU、内存等的使用情况监控）。

   * **拓充机器（虚拟机）**

       * 裸机上没有任何软件支持；覆盖了软件（安装操作系统）之后的机器称为**拓充机器**，或称**虚拟机**。

       * 机理类比汽车传动系统：发动机只会转、轮胎只会滚，覆盖传动系统后发动机就能带着轮子转——操作系统把 CPU、内存等硬件合理组织起来，让它们相互协调配合工作，简单硬件因此组合出更多、更复杂的功能，实现对硬件机器功能的拓展。

---

## 操作系统的资源管理功能

   * **文件管理**

       * 系统中文件的组织和管理由操作系统完成——例如在文件夹中一层层找到某个程序的安装位置。

   * **存储器管理**（主存管理、内存管理）

       * 程序执行前必须先把程序的数据放到内存里：双击运行一个程序的背后，是操作系统把程序数据从磁盘放入内存，并安排放在内存的什么位置。

   * **处理机管理**

       * 程序运行过程中需要被处理机（CPU）处理，什么时候给哪个程序分配处理机资源由操作系统决定。

   * **设备管理**

       * 摄像头这类设备资源由操作系统管理，由它决定设备分配给哪个程序使用——例如视频聊天时把摄像头分配给相应进程。

## 操作系统提供的接口

   * **封装思想**

       * 最底层的硬件只听得懂二进制的机器语言，对外暴露的是丑陋、不友好的交互接口；操作系统把硬件功能封装成简单易用的服务，上层用户只需向操作系统发出简单命令，由操作系统翻译成二进制交给硬件执行——类比汽车把复杂构件封装成方向盘、刹车、油门。

   * **GUI（图形化用户接口）**

       * 用户通过形象的图形界面操作，例如把文件拖拽到回收站完成删除；简单动作背后由操作系统完成大量工作。现代操作系统一般都提供 GUI，早期操作系统未必有图形界面。

   * **联机命令接口**

       * 又叫**交互式命令接口**。典型例子：命令解释器（小黑框）里执行 `time` 命令，系统报出当前时间后再让用户输入新时间——用户说一句，系统跟着做一句，人机不断交互。

   * **脱机命令接口**

       * 又叫**批处理命令接口**。典型例子：执行 `.bat` 文件——把一系列命令罗列在一个清单里，系统按顺序一条一条执行；用户一次提出一堆请求，系统做一堆。

       * | 对比项 | 联机命令接口 | 脱机命令接口 |
         | :--- | :--- | :--- |
         | 别名 | 交互式命令接口 | 批处理命令接口 |
         | 典型例子 | `time` 命令 | `.bat` 批处理文件 |
         | 交互方式 | 用户说一句，系统做一句 | 用户说一堆，系统做一堆 |

       * > **易错点** ⚠️：联机与脱机命令接口的区别是选择题常见考察点，别把两种交互方式记反。

   * **程序接口（系统调用）**

       * > **定义**：由许多系统调用组成的、供程序员使用的接口；应用程序请求操作系统服务的**唯一方式**就是通过系统调用。

       * 普通用户不能直接使用程序接口，只能通过编写程序代码的方式间接使用。

       * 机理示例：C 语言的 `printf` 是库函数，其底层实现使用了操作系统提供的与显示相关的系统调用；操作系统收到请求后替用户操作硬件（显示器）。

       * 有的教材把系统调用称为「广义指令」。

   * **用户接口**

       * 有的教材把命令接口和程序接口统称为「用户接口」——狭义的用户接口不包含 GUI。

## 操作系统的四个特征

并发和共享是操作系统**最基本的两个特征**，二者互为存在条件。

### 并发与并行

   * **并发（Concurrency）**

       * > **定义**：两个或多个事件在同一**时间间隔**内发生。

       * 宏观上同时发生，微观上交替发生——单手撸两只猫，一段时间内左一下右一下，宏观同时在撸、微观每一时刻只撸一只。

       * 操作系统的并发性：计算机中「同时」运行多道程序，实际是宏观同时、微观上交替占用处理机。

       * 多核 CPU 依然离不开并发：四核 CPU 只能同时并行运行四道程序，再开第五道程序（如 QQ 音乐）时，只能让程序交替上处理机运行，由操作系统实现这种交替。

   * **并行（Parallelism）**

       * > **定义**：两个或多个事件在同一**时刻**发生。

       * 宏观微观都同时发生——双手各撸一只猫，两个事件在同一时刻同时进行。

### 共享性

   * **共享（Sharing）**

       * > **定义**：资源共享，即系统内有限的硬件资源供多个并发执行的进程共同使用。

       * 操作系统需要协调有限资源：什么时候把资源分给 A 进程、什么时候分给 B 进程。

   * **互斥共享方式**

       * 同一时间段只允许**一个**进程访问该资源。典型例子：摄像头——打开系统相机的同时无法再让微信视频使用摄像头。

   * **同时共享方式**

       * 一段时间内允许多个进程「同时」访问，但微观上可能是交替访问。典型例子：QQ 和微信两个进程同时往硬盘发不同文件；音乐软件与视频应用同时使用扬声器。

   * **并发与共享互为存在条件**

       * 没有并发性：一段时间内只有一道程序运行，所有资源都归它使用，共享就没有存在的必要。

       * 没有共享性：多个进程无法共同使用资源，并发运行（如两个进程同时各发一个文件）也无法实现。

### 虚拟性

   * **虚拟（Virtualization）**

       * > **定义**：把一个物理上的实体变为若干个逻辑上的对应物——物理实体实际存在，逻辑对应物是用户感知到的。

       * 典型场景：物理内存只有 4GB，却可以同时运行要求 4GB 内存的 GTA5、QQ、迅雷、网易云音乐，用户感知到的内存远大于实际物理内存。

   * **空分复用**

       * 把有限的物理内存在**空间上**切分成多个部分，各部分独立地让各进程复用——虚拟存储器技术的思想。

   * **时分复用**

       * 把 CPU 的服务**时间**拆分成多个时间分片，每个分片分给某个进程，交替往复；单核 CPU 在用户看来似乎有多个 CPU 同时为自己服务（虚拟处理器技术）。

### 异步性

   * **异步（Asynchronism）**

       * > **定义**：多道程序环境下进程并发执行，但由于资源有限，进程的执行不是一贯到底，而是走走停停、以不可预知的速度向前推进。

       * 机理示例：微信进程要发送一张还存在云盘里的图片，需要等云盘进程先把图片下载到本地；两个进程各走各的、速度不可预知，若微信在下载中途就尝试发送，会把只下载了一半的图片发出去，产生错误结果。

   * **进程同步机制**

       * 异步性是操作系统内部必须解决的问题：进程同步机制让多个互不相干的进程能够配合完成事情，防止并发进程的异步性带来问题。

## 操作系统的发展与分类

```text
手工操作阶段（示意）：
|--装带--|--慢速读入--|--计算--|--慢速输出--|--取走--|--下一轮重复--|
                      ↑ CPU 只有这一小段在干活

多道批处理（示意）：
CPU    ：|--计算作业1--|--计算作业2--|--计算作业3--|--...
输入设备：|--读入作业2--|--读入作业3--|--...
输出设备：            |--输出作业1--|--输出作业2--|--...
```

   * **手工操作阶段**

       * 程序写在纸带上（有孔为 1、无孔为 0），程序员手工装卸纸带，计算机从纸带机读入程序、输出结果。此阶段操作系统尚未诞生。

       * 两大缺点：**用户独占整机**——前一个程序没运行完，第二个程序员不能上机；**资源利用率极低**——人机速度矛盾，手工装卸很慢、计算很快，计算机大部分时间空闲，而机器造价十分昂贵。

       * > **易错点** ⚠️：这个阶段连操作系统都没有，它只是演化的起点，作用是暴露矛盾，不要把它当成某一种「操作系统」。

   * **单道批处理系统**

       * 引入**脱机输入输出技术**：由专门的**外围机**（外围控制机）把纸带上的程序先转到磁带上，计算机直接从速度更快的磁带读写。

       * 内存中运行**监督程序**，控制计算机自动地从磁带输入输出作业：读入作业 1 → 计算 → 输出到磁带 → 紧接着读入作业 2，以此类推。

       * 效果：作业输入输出占用的时间比例降低，资源利用率有一定提升；但**内存中同一时刻只能有一道程序**，程序间串行执行，CPU 仍有大量空闲。

   * **多道批处理系统**

       * **操作系统正式诞生**的阶段。支持多道程序并发运行：一次往内存读入多道程序，让它们并发执行、共享 CPU 和输入输出设备——CPU 计算作业 1 时输入设备读入作业 2，作业 1 输出时 CPU 转去计算作业 2，三者错峰忙碌。

       * 优点：资源利用率大幅提升，CPU 大量时间处于忙碌状态。

       * 缺点：**不提供人机交互功能**——作业提交后用户只能干等，无法调试程序、无法在运行中输入参数。

   * **三种系统的演进逻辑**

       * | 系统 | 要解决的问题 | 手段 | 遗留的缺点 |
         | :--- | :--- | :--- | :--- |
         | 手工操作 | ——（起点） | 纸带 + 人工装卸 | 用户独占整机；人机速度矛盾，CPU 利用率极低 |
         | 单道批处理 | 手工装卸太慢、I/O 占比太高 | 脱机 I/O + 监督程序 | 内存只有一道程序，程序间串行 |
         | 多道批处理 | 串行导致 CPU 大量空闲 | 多道程序并发共享资源 | 不提供人机交互，无法调试程序 |

   * **分时操作系统**

       * 以**时间片**为单位轮流为各个用户（作业）服务，例如每人 50ms；用户通过键盘、鼠标等终端交互。

       * 优点：用户的请求可以被及时响应。缺点：不能优先处理紧急任务——对各个用户完全公平，谁也不能插队。

   * **实时操作系统**

       * 按任务优先级优先响应紧急任务，要求接到信号后及时处理、在严格的时间时限内完成并保证结果正确。主要特点：**及时性和可靠性**。

       * **硬实时系统**：必须绝对严格地在规定时间内完成处理，否则后果严重——导弹控制系统、自动驾驶系统。

       * **软实时系统**：要求实时响应但偶尔不及时也不至于严重后果——火车订票系统要求实时显示剩余票量。

       * > **提示**：判断硬实时还是软实时，问一句「错过时限的后果是否灾难性的」——错过就是事故的，硬实时；只是体验变差的，软实时。

   * **其他类型**

       * 网络操作系统、分布式操作系统、个人计算机操作系统——长文仅简单提及，未展开说明。

## 操作系统的运行机制

### 两种程序与两种指令

   * **机器指令**

       * > **定义**：让处理器（CPU）能够识别并执行的最基本的命令，例如一次加法、一次赋值。

       * 高级语言程序经编译器翻译成二进制机器指令，一行 C 代码可能对应很多条机器指令；程序运行的本质就是 CPU 一条一条执行机器指令。

       * > **易错点** ⚠️：小黑框里输入的 `ls`、`cd` 是交互式命令接口的**命令**，不是这里的**指令**；「指令」一律按二进制机器指令理解。

   * **内核程序与应用程序**

       * 应用程序是跑在操作系统之上的普通程序（如 QQ、微信）；操作系统开发人员编写的程序是内核程序，众多内核程序组成操作系统的**内核**（kernel）。

       * 内核是操作系统最核心、最接近硬件的部分，作为资源管理者的管理工作就在内核实现；图形用户界面不在内核里实现——内核只包含最重要、最核心、最必不可少的功能（例如只有 Linux 内核也能实现 Linux 的全部功能）。

   * **特权指令**

       * 运行后可能影响其他程序正常运行的指令（如内存清零），只允许系统管理者——操作系统内核——使用。

       * 应用程序只能使用**非特权指令**（如加减乘除运算）。CPU 在设计和生产时已划分好特权与非特权，拿到指令就能分辨。

### 两种 CPU 状态

   * **内核态（管态）**

       * > **定义**：CPU 正在运行内核程序时的状态，可以执行特权指令。

   * **用户态（目态）**

       * > **定义**：CPU 正在运行应用程序时的状态，只能执行非特权指令。

       * > **易错点** ⚠️：「管」对应管理者（内核态），「目」对应用户态，两个别名不要对调。

   * **程序状态寄存器（PSW）**

       * CPU 用其中的某一个二进制位标记当前状态：为 1 表示内核态、为 0 表示用户态（也有 CPU 反过来标，无关紧要）；一个二进制位即可完成状态标记。

### 两种状态的切换

   * **内核态 → 用户态**

       * 由内核执行一条**修改 PSW 标志位的特权指令**完成，意味着操作系统内核**主动让出** CPU 的使用权。

       * 典型场景：开机初始化（内核程序运行，CPU 处于内核态）完成后，内核改 PSW 为用户态、让出 CPU，应用程序上机运行。

   * **用户态 → 内核态**

       * 由**中断**引发，由 CPU **硬件自动**完成切换；切换后 CPU 停止执行当前应用程序，转而执行处理中断的内核程序。

       * 典型场景：应用程序（用户态）试图执行特权指令——CPU 读入时即识别出特权指令，又查 PSW 发现自己处于用户态，判定非法，产生中断信号，立即强行转为内核态并拒绝执行该指令。

       * > **结论**：两个方向的切换机制不对称——一个是主动交权（特权指令改 PSW），一个是强行夺权（中断，硬件自动）；触发中断就意味着操作系统强行重新夺回 CPU 使用权。

   * **触发中断的共性**

       * 凡是需要操作系统介入开展管理工作的时候，就会触发一个中断信号。

## 中断机制

   * **中断的地位**

       * > **定义**：中断是让操作系统内核重新夺回 CPU 使用权的**唯一途径**，且中断会使 CPU 由用户态变为内核态。

       * 应用程序上 CPU 后会一直运行下去，除非发生中断；没有中断技术就无法实现多道程序并发，甚至可以说没有中断技术就没有操作系统。

   * **分类标准**

       * 内中断：中断的产生**和当前执行的指令有关**，信号来自 CPU **内部**；外中断：与当前执行的指令**无关**，信号来自 CPU **外部**。

       * 很多教材把内中断称为「异常」（exception），把外中断直接称为「中断」——考试遇到的中断通常指狭义中断（外中断），广义的中断包含内外两类。

```text
            广义的中断
               /\
      内中断 \/  \/ 外中断
      （异常）      （狭义的中断）
        /\              /\
   指令引发的      时钟中断 / I/O 中断
 （信号来自 CPU 内部）（信号来自 CPU 外部）
```

   * **内中断的典型来源**

       * 指令本身非法：用户态执行特权指令。

       * 指令参数非法：执行除法指令时发现除数为零。

       * 程序主动请求服务：应用程序执行**陷入指令**（trap 指令），主动引发内中断、把 CPU 使用权交还给内核，请求内核提供服务——系统调用就是这么实现的。

       * > **易错点** ⚠️：陷入指令不是特权指令——它恰恰要在用户态执行，而用户态能执行的必然是非特权指令；它是「用户态通往核心态的合法大门」。

   * **时钟中断（外中断）**

       * 由时钟部件每隔一段时间（如 50ms）向 CPU 发出，与当前执行的指令无关。正是靠它实现了多道程序并发：程序 1 用满 50ms → 时钟中断 → 内核程序发现时间片用完 → 把 CPU 交给程序 2 → 50ms 后再次中断、切换回来，如此往复。

   * **I/O 中断（外中断）**

       * I/O 设备完成任务后向 CPU 发中断信号，例如打印机打印完成后通知 CPU「任务已完成」，CPU 用对应的内核程序处理。

   * **外中断的检查时机**

       * CPU 在**每一条指令执行结束的时候**例行检查是否有外部中断信号需要处理；内中断则在执行指令的过程中当场发现。

   * **中断向量表**

       * CPU 检测到中断信号后，根据信号**类型**查询**中断向量表**，找到该类型中断对应的**中断处理程序**；中断处理程序是内核程序，运行在内核态。

       * 中断机制两步归纳：检查中断信号（内中断在执行指令时查、外中断在指令周期末尾查）→ 分派处理（查中断向量表找到对应处理程序）。

### 异常的三种类型

   * **陷入（trap）**

       * 由陷入指令引发、程序**故意**引发的异常——程序想请求操作系统服务时故意执行该指令；系统调用的实现原理。

   * **故障（fault）**

       * 由**错误条件**引起、**可能被内核程序修复**的异常；内核修复后把 CPU 使用权还给应用程序继续执行。典型例子：缺页故障。

   * **终止（abort）**

       * 由**致命错误**引起、内核程序无法修复的异常；内核不再把 CPU 使用权还给引发者，直接把该应用程序干掉。典型例子：整数除以零（程序 bug）、非法使用特权指令。

       * > **易错点** ⚠️：三分界线在于「是否故意」和「能否修复」——陷入是故意的、故障能修复后继续跑、终止修不了直接杀进程；除零算终止不算故障，因为它是程序自己的 bug，操作系统修不了。

## 系统调用

   * **系统调用（System Call）**

       * > **定义**：应用程序（程序员）请求操作系统内核服务的途径，与编程时的函数调用很类似。

       * 层次关系：应用程序调用高级语言的库函数，库函数在底层使用系统调用，系统调用请求操作系统内核的服务。

       * > **易错点**：库函数和系统调用不是一一对应——`math.h` 取绝对值这类函数在用户态就能完成，底层不需要系统调用；而创建新文件这类操作必须请求内核服务，底层一定用到系统调用。系统调用一定比库函数更底层。

   * **为什么系统调用是必须的**

       * 并发进程共享互斥资源时会出事：打印店里 WPS 和 Word 两个进程若能随意共享打印机，会交替提出打印请求，两篇论文的内容混杂打出。

       * 对策：由操作系统内核统一管理共享资源，应用程序只能通过系统调用请求分配资源，之后才能使用和访问，由内核协调各进程请求。

       * 判定规则：**凡是与共享资源有关的操作，都需要通过系统调用完成**——内存的分配与回收、I/O 设备的使用、文件操作都是如此，以此保证系统稳定性和安全性、防止非法操作。

   * **一次系统调用的完整过程**

       * 传参：应用程序用传参指令把参数放入 CPU 寄存器，其中一个参数指明本次系统调用的类型（如 Linux 的 fork）；传参指令可能有多条。

       * 陷入：执行陷入指令（trap 指令 / 访管指令），主动引发一个**内中断**，把 CPU 控制权交还内核，CPU 暂停应用程序。

       * 转向内核程序：CPU 执行**系统调用入口程序**（属于内核程序，运行在内核态；本质上就是处理陷入指令所引发内中断的中断处理程序）。

       * 分派与执行：入口程序检查寄存器参数，通过第一个参数确定系统调用类型，调用对应的**系统调用处理程序**上 CPU 运行，依据其余参数完成具体服务。

       * 返回：处理完毕，CPU 转回用户态，应用程序从暂停处继续执行。

   * **必考细节**

       * 陷入指令在**用户态**下执行，是非特权指令；执行后引发内中断使 CPU 进入核心态。

       * 发出系统调用请求在**用户态**进行，对系统调用的处理在**核心态**完成——请求在用户态，处理在核心态。

       * 陷入指令的别名：trap 指令、访管指令，指同一个东西。

## 操作系统的体系结构

### 内核的功能划分

   * **必须放进内核的功能**

       * 时钟管理（靠时钟中断实现计时，实现程序并发离不开它）、中断处理、原语——这三样**与硬件结合最紧密**，必须放在内核。

       * **原语**：一种特殊的程序，具有**原子性**——要么一气呵成全部运行完成、要么就不运行，执行过程不可被中断；即使执行中有外部中断信号到来，CPU 也要先把原语执行完才去处理。

   * **可不放内核的功能**

       * 进程管理、存储器管理等功能更多是对数据结构的操作，不直接涉及硬件，有的操作系统不把它们放进内核。

   * **内核的定义**

       * > **定义**：内核是操作系统最核心、最基本的部分，由一系列内核程序组成，这些内核程序必须运行在**内核态**。

### 大内核与微内核

   * **大内核（宏内核）**

       * 把操作系统**几乎所有功能**都包含在内核中，模块之间像普通函数调用一样直接相互调用。

       * 应用请求同时涉及进程管理、存储管理、设备管理时，只需 **2 次** CPU 状态转换（用户态→核心态→用户态）。

       * 典型代表：Linux、UNIX。

   * **微内核**

       * 内核中只保留与硬件关系最紧密的部分，进程管理、存储管理、设备管理等模块放在用户态。

       * 模块间调用只能通过**消息传递**：进程管理向微内核发消息（指明想调用谁、参数是什么），由微内核的进程间通信功能把消息传给存储管理，返回结果同样经微内核协助。

       * 同样的请求需要 **6 次** CPU 状态转换（三个模块各 2 次）；状态转换有成本，频繁切换降低系统性能。

       * 典型代表：Windows NT。

       * | 对比维度 | 大内核（宏内核） | 微内核 |
         | :--- | :--- | :--- |
         | 内核里放什么 | 几乎所有功能，模块间直接函数调用 | 只保留与硬件最紧密的基本功能，模块间靠消息传递通信 |
         | 性能 | 高，状态转换次数少 | 低，需要频繁在核心态与用户态之间切换 |
         | 结构与维护 | 内核代码庞大、结构混乱、难以维护 | 内核功能少、结构清晰、方便维护 |
         | 可靠性 | 模块间相互依赖强，任一模块出错都可能导致整个内核崩溃 | 功能模块在内核之外，某模块出错不会导致整个系统崩溃 |
         | 典型代表 | Linux、UNIX | Windows NT |

       * > **注意**：CPU 状态转换在日常讨论里被戏称「变态」，但考试答题必须写成「CPU 状态的转换」。

### 分层结构

   * **结构规则**

       * 内核分为多层（最底层硬件、最上层用户接口），每层**只能调用相邻的更低一层**提供的接口，不能跨层调用；只有最靠近硬件的第一层能直接操作硬件。

   * **优点**

       * 便于调试和验证：自底向上逐层调试——第一层只依赖出厂即正确的硬件，验证完第一层再基于它调第二层，逐层向外。

       * 易于扩充和维护：层间调用接口在设计之初规定好且固定不变，在原有两层之间插入新的一层（对上提供同样接口、对下使用下层已实现的功能）即可。

   * **缺点**

       * 难以合理定义各层之间的边界：功能之间往往互相需要（如进程管理与内存管理互有调用），严格的「只能高层调低层」不灵活。

       * 效率低：不允许跨层调用，一个系统调用哪怕只需要最底层的功能，也要一层层往下传递、一层层返回，执行时间变长。

### 模块化结构

   * **结构规则**

       * 内核划分为多个模块（进程管理、存储器管理、文件管理、设备驱动程序等），模块下可再分子模块；整个内核由**主模块**和**可加载内核模块**组成。

       * 主模块是必不可少的核心模块（如进程管理、内存管理）；可加载内核模块可**动态加载**，如设备驱动程序——有没有它不影响系统正常运行，只影响可拓展性。

   * **优点**

       * 模块间逻辑清晰、易于维护：按逻辑功能划分，只要规定好模块间接口就可以**多模块并行开发**。

       * 支持动态加载新内核模块：新设备驱动、新文件系统都可作为新模块加载进来，**不需要重新编译整个内核**。

       * 任何模块之间都可以直接调用，无需消息传递，效率高。

   * **缺点**

       * 模块之间的接口定义未必合理、也比较难：开发中其他模块常需要新功能，相互调用多导致接口难定义。

       * 模块间相互依赖、难以调试和验证：出问题时分不清是本模块的问题、被调模块的问题还是相互调用后产生的问题——分层结构因有清晰的单向依赖，调试起来明显更容易。

### 外核

   * **外核（Exokernel）**

       * 系统由**内核**和**外核**两部分组成：内核只负责进程调度、进程通信等；外核负责为用户进程分配**未经抽象的硬件资源**（如磁盘存储空间、内存存储空间），并保证这些资源的使用安全——A 到 B 的空间已分配给某进程后，其他进程访问该区域、或该进程访问区域之外的空间，都要被外核发现并制止。

   * **与普通操作系统的差别**

       * 普通操作系统给进程分配的是**经过抽象、虚拟化**的资源：进程看到连续的虚拟地址空间，实际虚拟页面被映射到离散的物理页框，文件块在磁盘上也可能离散存放。

       * 外核直接分配未经抽象的物理资源：进程可以申请一整片连续的磁盘块（如 0 号到 1024 号块）存放需要频繁随机访问的文件，磁头移动距离变少、性能提升；也可以申请一整片连续的**物理**内存，进程看到的就是真实的物理地址空间。

   * **优点与缺点**

       * 优点：用户进程使用资源更灵活；减少了虚拟硬件资源的映射层——普通系统访问内存要查页表（甚至二三级页表）多次访存做地址转换，外核可直接访问，效率提升。

       * 缺点：降低了系统的一致性——有的进程拿虚拟地址空间需要映射，有的进程拿物理地址空间不需要映射，分配和管理策略都要考虑各种情况，系统更复杂。

## 操作系统的引导

   * **引导要解决的问题**

       * > **定义**：操作系统引导就是开机时让操作系统在电脑上运行起来的过程。

   * **主存的两部分**

       * 主存由 **RAM** 和 **ROM** 组成：RAM 断电即清空；ROM 芯片集成在主板上，存储 **BIOS**（基本输入输出系统），其中最重要的程序是 **ROM 引导程序**（又称**自举程序**）——所以 CPU 一通电就能在主存固定位置找到并执行它。

   * **磁盘里与引导相关的数据**

       * **主引导记录（MBR）**：存放在磁盘开头留出的区域，包含**磁盘引导程序**和**分区表**（说明每个分区占多大空间、地址范围）。

       * **活动分区**：安装了操作系统并用它启动的分区（如 C 盘）；其内部开头是**引导记录（PBR）**，还有**根目录**相关的数据。

```text
 ┌──────────────────────────────────────────────────┐
 │ 主引导记录 MBR：磁盘引导程序 + 分区表             │ ← 磁盘开头留出的区域
 ├──────────────────────────────────────────────────┤
 │ C 盘（活动分区：装了操作系统，并用它启动）        │
 │   ├ 引导记录 PBR                                 │
 │   ├ 根目录（双击打开 C 盘看见的文件夹和文件）     │
 │   └ 其他内容                                     │
 ├──────────────────────────────────────────────────┤
 │  D 盘   │   E 盘   │   F 盘   │   ……             │
 └──────────────────────────────────────────────────┘
```

   * **引导的四个步骤**

       * 第一步：CPU 从主存特定地址开始执行 ROM 引导程序（自举程序），通常先做**硬件自检**（有没有插磁盘、内存条等），硬件全部正常才进行下一步。

       * 第二步：把磁盘第一块——主引导记录 MBR——读入内存并执行其中的磁盘引导程序，**扫描分区表**找到活动分区（装了操作系统的分区）。

       * 第三步：读入活动分区第一部分的引导记录 PBR 并执行，它负责从**根目录**下找到**启动管理器**（操作系统初始化程序）。

       * 第四步：执行操作系统初始化程序，完成一系列开机动作（Windows 下对应 C 盘 `Windows\boot` 文件夹里的内容）。

## 虚拟机

   * **虚拟机（Virtual Machine，VM）**

       * > **定义**：用虚拟化技术把一台物理机器虚拟化为多台虚拟机器，每台虚拟机器上都可以独立运行一个操作系统。

       * 解决的问题：一台物理机只能运行一个操作系统时，多个应用挤在同一操作系统上会相互影响、争夺资源（如两家游戏服务器）；各自迁移到独立物理机又浪费硬件——虚拟化让二者兼得。

   * **虚拟机管理程序（Virtual Machine Monitor，VMM）**

       * 负责把物理机器虚拟化为多台虚拟机器的程序，又称 Hypervisor、虚拟机监控程序——这些术语同义。

### 第一类虚拟机管理程序

   * **结构**

       * 直接运行在**硬件之上**，把总硬件资源划分为多个部分分给各虚拟机，每台虚拟机可装各自独立的操作系统（Windows、Linux 不限），其上再运行各自的用户进程。

       * 资源分配方式：单核 CPU 划分时间片分给各虚拟机（上层操作系统以为自己独占一个 CPU）；磁盘、内存按空间划分。

       * **只有虚拟机管理程序运行在内核态**，只有它能执行特权最高的指令；上层操作系统和应用程序都运行在用户态。

       * 上层操作系统并不知道自己运行在用户态——它以为自己运行在内核态、依然会使用特权指令；这些指令的使用被虚拟机管理程序**截获**并做等价转换，模拟出「执行成功」的效果。上层操作系统因此运行在**虚拟内核空间**：实际是用户空间，只是它自以为在内核空间。

### 第二类虚拟机管理程序

   * **结构**

       * 运行在**宿主操作系统**（Host OS）之上，典型如 VirtualBox、VMware；其上可启动一个或多个**客户操作系统**。

       * 资源分配方式：虚拟机管理程序**只能请求宿主操作系统分配**硬件资源，硬件资源的管理者依然是宿主操作系统。

       * 拿到的是宿主操作系统**抽象后**的虚拟资源：例如要给虚拟机分配 10GB 磁盘，实际是向宿主操作系统申请创建一个 10GB 的大文件（存放位置由宿主操作系统决定，10GB 在磁盘上未必连续）；要分配内存时拿到的是虚拟内存，再拆分给各虚拟机——多一层「二次虚拟」的套娃。

### 两类管理程序的差异对比

   * | 对比项 | 第一类虚拟机管理程序 | 第二类虚拟机管理程序 |
     | :--- | :--- | :--- |
     | 物理资源控制权 | 直接运行在硬件之上，直接控制和分配物理资源 | 运行在宿主操作系统之上，只能向宿主操作系统申请、由其分配 |
     | 分配的资源形态 | 可以把未经抽象的物理资源直接分配给虚拟机 | 拿到的是宿主操作系统抽象后的虚拟资源，再转手「二次虚拟」 |
     | 性能 | 更好，地址映射层次少 | 更差，总要通过宿主操作系统作为中介，多层映射 |
     | 同等硬件可支持的虚拟机数量 | 更多，它拥有全部硬件资源 | 更少，宿主操作系统及其进程也要消耗资源 |
     | 虚拟机可迁移性 | 迁移动作比较麻烦 | 非常方便，导出镜像拷走即可 |
     | 商业化应用 | —— | 目前更广泛，使用起来灵活 |
     | 运行模式 | 运行在最高特权级（零环） | 一部分运行在用户态，一部分以驱动程序形式运行在内核态 |

   * **性能差异的根源**

       * 每多一层硬件虚拟化，上层使用资源时就要多一层地址映射才能到达最终物理地址；第二类总要经宿主操作系统作为中介，性能必然更差。

   * **可迁移性差异**

       * 第二类可把客户操作系统导出为 ISO 镜像文件拷走，在另一台机器的 VirtualBox 上加载安装即得到完全一样的系统（含装好的程序和数据）——因此商业化应用更广泛。

   * **第二类的运行模式细节**

       * 运行在内核态的部分以**虚拟机驱动程序**的方式加载到宿主操作系统内核中；客户操作系统内进程发出的系统调用（如 write）会被虚拟机管理程序截获，由它代替上层操作系统向宿主操作系统发出 write 系统调用请求服务。

### 特权级的细分

   * **多级特权级**

       * 近年 CPU 的指令特权级可分为更多层（零级、一级、二级、三级），越往下特权级越高；第一类虚拟机管理程序运行在最高特权级**零环**（Ring 0）。

   * **细分的价值**

       * 若只有特权/非特权两级，每条特权指令都要被虚拟机管理程序截获、判断合法性再模拟。细分为：管理程序在零环、客户操作系统内核在一环（次高）、用户进程在二环（最低）后，一环二环的指令直接放行，只检查少数零环的**敏感指令**是否该执行。

## 进程初识

### 程序与进程

   * **程序**

       * > **定义**：静态的、存放在磁盘里的可执行文件（如 QQ.exe），是一系列指令的集合。

   * **进程（Process）**

       * > **定义**：动态的，是程序的一次**执行过程**；同一个程序多次执行，每一次执行都对应一个不同的进程。

       * 直观例子：同一台电脑开三次 QQ 程序登录三个号，任务管理器里出现三个 QQ 进程——它们执行的是同一个 QQ.exe 程序。

### PID 与操作系统的台账

   * **PID（Process ID，进程 ID）**

       * > **定义**：进程的唯一不重复标识，相当于进程的身份证号，由操作系统创建进程时分配。

       * 很多操作系统的 PID 分配采用「每次加一」的简单策略：退出程序再重新打开，新进程的 PID 会递增（如 2641 → 2642）。

   * **操作系统记录的其他信息**

       * 进程描述信息：PID、用户 ID（UID）等，用于区分各进程。

       * 资源分配情况：分配了多少内存、正在使用哪些 I/O 设备和文件，帮助操作系统管理系统资源。

       * 进程控制和管理相关信息：CPU 使用时间、磁盘读写量、网络流量等，支持控制与调度策略——例如经常写磁盘的进程是需要常访磁盘的进程，管理时可据此制定策略。

### PCB 与进程实体

   * **PCB（Process Control Block，进程控制块）**

       * > **定义**：存放操作系统管理进程所需全部信息的数据结构，是进程存在的**唯一标志**——进程创建时建立 PCB，进程结束时回收 PCB。

       * Linux 中的 PCB 叫 `task_struct`，定义在 `sched.h` 中，包含 `state`（进程当前状态）、`files`（打开了哪些文件）、`io_context` 等，字段极多；除三类已述信息外，PCB 还保留**处理机相关信息**——只有保存了它才能实现进程切换。

   * **程序段与数据段**

       * 程序段：从硬盘读入内存的那一系列指令序列，进程执行就是 CPU 从内存逐条读取执行它们。

       * 数据段：程序运行过程中产生、需要使用的各种数据（如定义的变量 x）。

       * PCB 是给管理者（操作系统）用的；程序段和数据段是给进程自己用的，与进程自身的运行逻辑有关。

   * **进程实体（进程映像）**

       * > **定义**：由 PCB、程序段、数据段三个部分组成的静态概念，可理解为进程在某一时刻的快照——进程是动态的，进程实体是静态的，运行中不断变化（x 从 1 变 2）。

       * 严格说法：**进程是进程实体的运行过程**，是系统进行**资源分配和调度的独立单位**——操作系统以进程为单位分配内存等资源；调度就是操作系统决定让哪个进程上 CPU 运行。

       * 三个 QQ 进程：PCB 各不相同，数据段各不相同（各自账号信息存在数据段），但**程序段内容相同**（运行同一个程序）。

### 进程的特征

   * **动态性**

       * 进程是程序（进程实体）的一次执行过程，动态地产生、变化和消亡——进程**最基本**的特性。

   * **并发性**

       * 内存中同时有多个进程实体，各进程可以并发执行。

   * **独立性**

       * 进程能独立运行、独立获得资源、独立接受调度。

   * **异步性**

       * 各并发进程以各自独立的、不可预知的速度向前推进；异步性可能使执行结果不确定，需要进程同步机制让并发进程相互配合。

   * **结构性**

       * 每个进程都由一个 PCB、一段程序段、一段数据段构成。

   * **基本单位的归属**

       * 进程是**独立获得资源、独立接受调度**的基本单位；引入线程后，进程不再是接受调度的基本单位，但**依然是获得资源的基本单位**。
