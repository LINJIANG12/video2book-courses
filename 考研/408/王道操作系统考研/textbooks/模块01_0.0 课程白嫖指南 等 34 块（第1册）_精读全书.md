### 你天天在用的操作系统，到底是什么

先来看一下大家都熟悉的操作系统都有哪些。手头比较宽裕的同学可能比较喜欢苹果的设备：苹果的电脑用的是 macOS，苹果的手机用的是 iOS。但比起苹果的这种浮夸，我个人还是比较喜欢安卓和 Windows 操作系统的这种质朴的优雅。对普通老百姓来说，可能 99% 的人都在用这几种操作系统；而对于我们技术专业的同学来说，Linux 操作系统也是必须学习使用的一个；另外现在可能还有一些「野人」还在用诺基亚的塞班系统。

可以看到，在学习这门课之前，我们其实已经积累了很多关于操作系统的体验和感性经验。所以学这门课的时候，要善用自己平时使用这些系统的经验，结合知识点来思考——这样能帮助你更好地理解课程内容，把操作系统知识和现实生活连接起来，做到学以致用。

在这个小节里，我们只介绍操作系统最基础的概念和定义，并结合例子加深理解。其中，「概念和定义」要回答的是**什么是操作系统**，「功能和目标」要回答的是**操作系统需要做什么**。

#### 一台电脑是怎么「长」出来的

先结合生活经验，看看操作系统在整个计算机体系当中所处的位置和角色。我们现在用的电脑，是这样一步一步变成你所看到的样子：

第一步，厂家会把 CPU、主板等等这一系列硬件组装成一台**裸机**。所谓裸机，就是只有硬件的机器，不包含操作系统。但在出售之前，厂家一般还会在这个裸机的基础上为我们安装一个操作系统（最常用的就是 Windows）。当我们买到电脑之后，就可以在这个操作系统之上安装一些我们想用的应用程序，比如 QQ。之后，我们作为用户就可以使用这些应用程序了。

从一台电脑的诞生过程，就能看出计算机系统的层次结构：

```text
            用户
             │
             │  GUI（图形用户接口）、命令接口（联机 / 脱机）
             ▼
         应用软件
             │
             │  系统调用（程序接口）
             ▼
         操作系统
             │
             ▼
      裸机（纯硬件）
```

最底层是纯硬件，又称之为裸机；裸机上面安装一层操作系统；基于操作系统又可以安装一系列应用软件；我们用户处于最上面一层。

细心的同学可能会发现：图里用户和操作系统、应用程序和操作系统之间都画了「相连的部分」——为什么是这样？这个问题先留个悬念，一会儿解释。

#### 操作系统的定义

了解了操作系统所处的位置之后，我们给出定义。王道书上是这样说的：操作系统是指**控制和管理整个计算机系统的硬件和软件资源，并合理地组织调度计算机的工作和资源的分配**的软件。

> **定义**：操作系统是控制和管理整个计算机系统的硬件与软件资源、合理地组织调度计算机的工作与资源分配、并为用户和其他软件提供方便的接口和环境的最基本的系统软件。

这句话拆成三层来读，每一层对应操作系统的一个角色：

1. **它是系统资源的管理者**——管理系统的硬件资源和软件资源；
2. **它要向上层提供方便易用的服务**——服务对象包括用户和普通的应用程序；
3. **它是计算机系统中最基本的系统软件**——注意，操作系统是一种软件，而不是硬件，但它是最接近硬件的一层软件。

接下来把这三个角色逐个展开，让大家更形象地体会操作系统到底在干什么。

#### 作为系统资源的管理者

先用任务管理器直观感受一下。在 Windows 里打开任务管理器，可以看到当前系统中正在运行的进程有哪些——所谓**进程**，其实就是正在运行的程序，比如大家熟悉的 QQ、Chrome 等等。所以操作系统肯定是在管理这些软件资源的。再看任务管理器的另一半界面：CPU、内存等等这一系列硬件资源的使用情况也在被监控着，比如 QQ 这个进程此刻占用了 138.9 MB 的内存空间。所以操作系统作为软硬件中间的一个层次，既管理软件资源，也管理硬件资源。

> **结论**：操作系统作为软件和硬件中间的层次，是系统资源的管理者——既管理软件资源，也管理硬件资源。

我们再用「用 QQ 和朋友视频聊天」这个例子，看看操作系统作为管理者具体要做哪些事：

- 第一步，在文件夹中一层一层地找到 QQ 的安装位置，双击打开 QQ.exe。系统里有各式各样的文件，而这些文件的组织和管理其实是操作系统在帮我们完成的——这对应操作系统的**文件管理**功能。
- 第二步，双击 QQ.exe 之后程序开始运行。这里要补充一个跨考的同学可能不知道的知识点：一个程序在执行之前，需要先把程序的数据放到内存里。所以双击打开 QQ.exe 的背后，操作系统帮我们做了一件很重要的事——把程序的数据从磁盘放入内存，放到内存的什么位置也由它安排。这对应**存储器管理**（也叫主存管理、内存管理）。
- 第三步，QQ 程序运行的过程中，需要被处理机（也就是 CPU）处理。什么时候给 QQ 分配处理机资源，这件事是操作系统在背后替我们完成的——这对应**处理机管理**。
- 第四步，视频聊天时，需要把摄像头这个设备分配给 QQ 使用。摄像头这类设备资源也要由操作系统管理，由它决定设备该分配给哪个程序——这对应**设备管理**。

> **提示**：王道书第二章讲的就是处理机管理，第三章是存储器管理，第四章是文件管理，第五章是设备管理。这门课后期重点学习的就是操作系统作为系统资源的管理者，要如何设计和实现这些功能。现在只需要建立这样一个全局观，各部分的理解会随着后续学习不断深入。

#### 向上层提供方便易用的服务：封装的思想

通过刚才的分析我们知道，计算机的最底层是裸机、也就是纯硬件，而硬件只能听得懂二进制指令——机器语言。也就是说，要直接和硬件打交道，只能通过二进制语言和它交互。所以我们说，最底层的硬件对外暴露的是一些**丑陋的、不友好的交互接口**，正常的人类很难和纯硬件直接打交道。

而在硬件之上安装的操作系统，会向上层提供一种更美丽、更友好的交互接口：安装了操作系统之后，用户和应用程序不需要直接和硬件打交道，只需要告诉操作系统想要的服务；操作系统会把用户的命令需求翻译成二进制告诉硬件，再由硬件执行我们想要的操作。

这其实是一个很典型的**封装**思想：操作系统把丑陋的硬件功能封装成简单易用的服务，使用户能够更方便地使用计算机——上层用户不需要再关心底层的硬件细节，只需要用更简单的方式对操作系统发出命令，剩下的操作系统替我们完成。

这种封装思想在日常生活中也经常被使用。比如汽车，把它拆解了会发现里面有很多很多复杂的构件，但汽车设计师把这些底层复杂的构件隐藏起来，封装成简单易用的接口——对用户暴露的只有方向盘、刹车、油门这些用户能理解的接口，用户不需要关心底层到底怎么实现转向、加速、减速。操作系统做的事情，本质上和这种封装没有任何区别。

那么操作系统屏蔽了底层硬件细节之后，向上提供了哪些方便易用的服务呢？

##### GUI：图形化用户接口

这是我们最熟悉的一种服务。用户可以通过形象的图形界面操作，比如在 Windows 里要删除一个文件，只需要把它拖拽到回收站即可——这种操作方式对我们用户来说很形象、很容易理解。但在这个简单的拖拽动作背后，操作系统其实为我们做了很多很多的事情。现代操作系统一般都会对上层用户提供这种图形化的用户接口，不过一些早期的操作系统并没有图形界面。

##### 命令接口：联机与脱机

早期操作系统让用户通过命令接口（也就是命令行）和系统交互。命令接口又分两种：一种是**联机命令接口**，一种是**脱机命令接口**。

联机命令接口又叫**交互式命令接口**。以 Windows 为例，可以打开命令解释器——就是我们平时经常看到的那个小黑框，在里面输入 `time` 命令，系统会告诉我们当前的时间是几点几分；接下来系统会让用户输入一个新的时间，也就是你想把系统时间调到几点几分几秒。像 `time` 这样的命令就是典型的交互式命令：**用户说一句，系统跟着做一句**；接下来用户再说一句，系统才再跟着做一句——整个过程用户和操作系统在不断交互。除了 `time` 之外还有很多别的交互命令，由这些命令组成了所谓的交互式命令接口，即联机命令接口。

脱机命令接口又叫**批处理命令接口**。还以 Windows 为例，可以在 C 盘里搜索后缀为 `.bat` 的文件，随便打开一个，里面是密密麻麻的一系列命令。别看它复杂，其实本质上和我们刚才的 `time` 命令没有任何区别——只不过是把这一系列命令罗列在一个清单里。执行这个 `.bat` 文件的时候，操作系统会按照文件里的命令一条一条往后执行。也就是说，用脱机命令接口时，我们是**一次提出一堆请求**，操作系统按照我们的指示一条一条执行——这也是它被称作「批处理」命令接口的原因。

| 对比项 | 联机命令接口 | 脱机命令接口 |
| :-- | :-- | :-- |
| 别名 | 交互式命令接口 | 批处理命令接口 |
| 典型例子 | `time` 命令 | `.bat` 批处理文件 |
| 交互方式 | 用户说一句，系统做一句 | 用户说一堆，系统做一堆 |

联机和脱机命令接口的区别有可能在选择题中考察，大家要注意。

##### 程序接口：给程序员用的系统调用

刚才提到的 GUI、联机命令接口、脱机命令接口，都是可以让普通用户直接使用的。操作系统还有一种对外提供的接口，叫做**程序接口**——它是给我们程序员使用的，我们可以在自己写的程序中，通过**系统调用**的方式来使用程序接口。注意：普通用户不能直接使用程序接口，只能通过编写程序代码的方式间接地使用。

用一个例子来加深理解。写 C 语言的 hello world 程序时会用到 `printf` 函数，程序执行时会在屏幕上打印出 hello world 这两个单词。虽然我们只是简单调用了 `printf` 函数，但这个函数在底层实现时，肯定使用到了操作系统提供的、和显示相关的那些系统调用功能。也就是说：普通程序员使用的是 C 语言提供的库函数（`printf`），而这个库函数在底层实现时使用了操作系统提供的系统调用；操作系统收到这个系统调用相关的请求之后，才会替我们去操作硬件——显示器——并在上面显示出 hello world。

> **结论**：系统调用很类似我们熟悉的函数调用。很多操作系统都提供了上百种系统调用，由这些系统调用组成了所谓的**程序接口**。应用程序请求操作系统服务的**唯一方式**，就是通过系统调用。

> **提示**：有的教材当中，系统调用又被称为「广义指令」，这个术语大家稍微注意一下。

现在可以回答开头留的那个悬念了：为什么层次图里用户和操作系统、应用程序和操作系统之间有「相连的部分」？因为用户通过 GUI 和命令接口可以直接使用操作系统，而应用程序需要通过系统调用（也就是程序接口）来和操作系统进行交互——这些接口就是相连的那一部分。

> **注意**：在有的教材当中，会把命令接口和程序接口统称为「用户接口」——也就是说，狭义的用户接口其实不包含 GUI。这点大家稍微注意一下。

#### 作为最接近硬件的层次：实现对硬件机器的拓展

这个小节最后一个内容：操作系统作为最接近硬件的层次，需要做的事情就是**实现对硬件机器的拓展**。如果一个计算机当中没有任何软件支持，这种计算机就称之为裸机；而在裸机上安装了操作系统之后，就可以把裸机改造成功能更强、使用更方便的机器。覆盖了软件的这种机器称为**拓充机器**，或者称为**虚拟机**。当然这些只是一些无关紧要的概念名词，更重要的是理解：为什么说操作系统可以实现对硬件机器的拓展？

还是用汽车的例子来类比。汽车当中原本只有一些零碎的硬件：比如发动机，它只有一个功能，就是会转；轮胎也只有一个功能，就是会滚。但如果在这种原始的硬件机器上再覆盖上一层**传动系统**，就可以让发动机带着轮子转，汽车就可以开始往前走了——增加了这样一个系统之后，以前简单的硬件机器就得到了功能上的拓展。操作系统对硬件机器的拓展也是类似的：操作系统把 CPU、内存等等这一系列硬件合理地组织起来，并且让这些硬件能够相互协调配合着工作，这样这些简单的硬件就可以组合起来实现更多、更复杂的功能。所以说，操作系统实现了对硬件机器功能的拓展，使这些单纯的硬件功能更强、使用更方便。

到这里，这个小节就用很多例子帮助大家感性认识了什么是操作系统、操作系统要实现什么样的功能。这门课最关注的是它作为系统资源的管理者所要实现的那些功能——该怎么设计、怎么实现，后面的课程会详细讲解。而这个小节里有可能作为选择题考察的，是操作系统对上层提供了哪些服务：要理解什么是 GUI、什么是命令接口、联机命令接口和脱机命令接口的区别是什么；另外，由一系列系统调用组成了程序接口——系统调用这个概念，后面还会专门用一个小节进一步分析讲解。

### 四个特征：并发、共享、虚拟、异步

本节课我们学习操作系统的四个特征：**并发、共享、虚拟、异步**。其中并发和共享是操作系统**最基本的两个特征**，并且二者互为存在条件。这节课的内容通常考察概念性的选择题。

#### 并发与并行：单手撸猫和双手撸猫

先认识并发。和并发很相似的另一个概念叫做并行，先理清二者的区别。

| 对比项 | 并发 | 并行 |
| :-- | :-- | :-- |
| 定义 | 两个或多个事件在同一**时间间隔**内发生 | 两个或多个事件在同一**时刻**发生 |
| 宏观 | 同时发生 | 同时发生 |
| 微观 | 交替发生 | 同时发生 |

举个例子。我家养了两只猫，左边这只叫招财，右边这只叫进宝，两只猫都很粘人。如果我采用**单手撸猫**的方式，为了照顾到两只猫，我会在一段时间内左一下、右一下，左一下、右一下，就这样交替地抚摸。由于是单手撸猫，宏观上看，我们可以说在这一段时间内我是在同时撸两只猫；但微观上看，在某一个具体的时刻，我只会撸其中的一只猫——这就是**并发撸猫**。

再看**并行撸猫**：同样是招财和进宝，这次我们用左右两只手分别撸一只猫。此时撸招财和撸进宝这两个事件在**同一时刻同时发生**，并不是微观上交替进行的——这就是并行。

理清概念之后，来看操作系统的并发性：计算机当中「同时」运行着多道程序——注意这里的「同时」打了双引号，现在你知道了，所谓同时运行，有可能只是宏观上同时、微观上交替运行。这就是操作系统的并发性。

有同学可能会说：现在电脑手机的 CPU 都是多核的，多核 CPU 意味着同一时刻允许有多个程序并行执行，每一个核心执行一道程序，那多核 CPU 其实是支持多道程序并行执行的呀。然而即便是多核 CPU，操作系统的并发性依然不可或缺。比如英特尔的酷睿 i3 处理器是一个四核 CPU，意味着可以同时并行运行四个程序；但我们在玩电脑或者手机的时候会同时开很多个程序——在这四道程序运行的同时，我们还想再听个 QQ 音乐，这时四核 CPU 就没办法同时支持五道程序的并行执行了。此时只能让 QQ 音乐和 Word 文档这样的程序**交替着上处理机去运行**。

```text
CPU 时间轴：  │ QQ音乐 │ Word │ QQ音乐 │ Word │ QQ音乐 │ Word │
              └────────── 宏观：多道程序「同时」运行 ──────────┘
                          微观：交替占用处理机
```

什么时候该让 QQ 音乐上处理机运行、什么时候该让 Word 上处理机运行，这个交替运行的过程就是操作系统在背后实现的——这就体现了操作系统的并发性。至于操作系统如何调度多道程序运行，会在第二章进程管理那个部分学习，当前阶段建立起一些粗浅的认知就行。

#### 共享：摄像头不给同时用，硬盘可以

操作系统的第二个特征是**共享性**。所谓共享，指的是**资源共享**：一台计算机内部，硬件资源往往是有限的，那么有限的资源如何让多个并发执行的进程共同使用呢？这就是共享要解决的问题。操作系统需要协调系统内的有限资源，什么时候该把资源分给 A 进程、什么时候分给 B 进程。

共享的方式有两种：有的资源需要用**互斥共享**的方式，有的资源可以用**同时共享**的方式。

| 共享方式 | 含义 | 典型例子 |
| :-- | :-- | :-- |
| 互斥共享 | 同一时间段只允许一个进程访问该资源 | 摄像头 |
| 同时共享 | 一段时间内允许多个进程同时访问（宏观同时、微观交替） | 硬盘、扬声器 |

**互斥共享**：同一时间段只允许一个进程访问这种资源。比如你手机的摄像头——大家可以试一下，打开系统相机的同时，有没有可能再用微信跟家人朋友视频？也就是说，摄像头这个资源有没有可能同时分配给相机进程和微信进程使用？大家可以试试，至少我的手机的操作系统不支持摄像头这种资源的同时共享——同一时间段内只允许一个进程访问该资源。

**同时共享**：有一些系统资源在一段时间内可以让多个进程同时访问。但注意，这里所谓的「同时」也有可能是宏观上同时、微观上交替访问。摄像头属于互斥共享的资源，而**硬盘**这种设备就可以实现同时共享：比如你可以用 QQ 给朋友发送文件 A，与此同时用微信给另一个朋友发送文件 B——文件 A 和文件 B 都存储在你的硬盘里，两个进程同时发送文件，就意味着 QQ 和微信这两个进程需要在一段时间内同时访问硬盘这个资源，这就是所谓的同时共享。学到后面大家会知道，所谓两个进程「同时」访问硬盘，背后微观上其实是两个进程交替访问这个磁盘的，当前阶段先不展开细聊。还有一个典型的可以由多个进程同时共享的设备是**扬声器**——无论手机还是电脑，扬声器都属于 I/O 设备：比如你一边用音乐软件播放音乐，一边打开哔哩哔哩看视频，那么音乐软件和哔哩哔哩这两个进程就同时共享着扬声器这种资源。

通过这些例子不难感受到：操作系统需要对有限的硬件资源进行管理，在恰当的时候把资源分配给某一个或者某几个进程去共享使用。

#### 为什么说并发和共享互为存在条件

这节课开篇我们说，并发特性和共享特性互为存在条件。来解释一下为什么。

并发性是指多个程序「同时」运行；共享性是指系统中有限的资源被多个并发的进程共同使用。假设 QQ 进程正在发送文件 A，微信进程正在发送文件 B——这体现了并发性。而正是因为两个进程会同时运行、又都需要访问硬盘这种资源，所以它们俩才需要去共享这个硬件资源。反过来推：假如没有并发性，一段时间内系统中只会有一道程序正在运行，那系统内所有的资源都让给这一个程序使用不就 OK 了吗？也就是说，**没有并发性，共享性就没有存在的必要**。

再反过来看：如果操作系统不提供共享的特性，那 QQ 和微信想要并发地运行、并发地分别发送文件 A 和文件 B，这个事情也没办法实现——**没有共享，并发性也不可能实现**。

> **结论**：并发性和共享性是操作系统最基本的两个特性，二者互为存在条件。没有并发，共享就没有存在的意义；没有共享，并发也不可能实现。

#### 虚拟：4GB 内存怎么跑得动 GTA5 还挂着 QQ 和迅雷

第三个特征叫做**虚拟性**。所谓虚拟，是指把一个**物理上的实体**变为若干个**逻辑上的对应物**——物理上的实体是实际存在的，而逻辑上的对应物是用户感知到的。这句话读起来比较抽象，我们结合例子来理解。

大家应该都知道，一道程序要运行之前，需要先放到内存里边——先把程序放入内存，才可以给这个程序分配 CPU，程序才能跑起来。所以打开一个软件时，通常第一次打开会比较慢，那个慢的过程其实就是把这个程序的数据从硬盘装入内存；一旦数据放入内存，就可以分配 CPU、让它运行起来了。

我上大学期间很喜欢玩一个游戏，叫 GTA5，这个游戏官方给的运行内存下限是 4GB。大学期间我打这个游戏的时候，还会同时挂个 QQ、打开迅雷下载一些东西，还可能开着网易云音乐听歌。然而我的电脑只有 4GB 的物理内存——只够装 GTA5 的运行数据，对吧？但实际用下来，我一边打 GTA、一边挂 QQ、一边挂迅雷、一边听音乐，这几件事情同时进行是完全 OK 的。所以对于我这个用户来说，我在逻辑上感知到的是：有 4GB 内存支持 GTA5 运行，再加上 256MB 支持 QQ 运行，再加上 256MB 支持迅雷运行，再加上 256MB 还可以支持网易云音乐运行——我感知到的内存比实际物理内存大得多。

这就是操作系统虚拟性的体现：操作系统实现了**虚拟存储器技术**（本门课第三章会学习），虽然电脑物理上只有 4GB 内存，但在用户看来它似乎远远大于 4GB。虚拟存储技术是典型的**空分复用**思想——把一个有限的物理内存在空间上切分成很多个部分，各个部分可以独立地让各个进程去复用：比如 GTA5 需要用到很多内存的时候，就把其中很多空间先分给它；而如果游戏当前不需要这么多内存，就可以把一些空间清空出来，分块分给其他进程使用。学完第三章会对这个概念有更深的认知，这里简要了解即可。

除了空分复用，操作系统中还会使用**时分复用**的思想来实现虚拟性。比如某个单核 CPU，用户同时打开了六个软件。物理上看，这台计算机似乎只能支持一个程序的运行；但在用户视角看来，这台计算机似乎拥有六个 CPU，一样可以同时支持六个程序运行。这背后是**虚拟处理器**技术：一个单核 CPU 在用户看来似乎有六个 CPU 在同时为自己服务——相当于把 CPU 的服务时间拆分成了很多个**时间分片**，每个时间分片分给某一个进程使用：第一个时间分片给 QQ，第二个运行 Chrome，第三个运行 QQ 音乐，如此交替往复。在用户看来，好像一段时间内所有程序都在同时运行一样。因为是把 CPU 的时间进行拆分、让各个进程复用这些时间片，所以这种技术叫做时分复用技术。

> **结论**：操作系统有可能用时分复用的思想、也有可能用空分复用的思想来实现虚拟性——都是「一个物理实体，变成若干个逻辑对应物」。

#### 异步：微信怎么知道图片下载完了没有

最后一个特性叫做**异步性**。所谓异步，是指在多道程序环境下，多个程序是并发执行的，但由于系统的资源有限，进程的执行并不是一贯到底，而是**走走停停、以不可预知的速度向前推进**——这就是进程的异步性。这句话不好懂，我们结合例子来解释。

我现在有一台 iPhone 手机，iPhone 有一个云盘软件叫做 iCloud，跟微软的 OneDrive 类似。我会把我所有的文件都存到 iCloud 云盘里，这样手机本地的存储空间就可以省下来。接下来故事是这样的：有时候我想用微信给朋友发送一张存储在 iCloud 云盘上的图片，而这张图片还停留在云盘里、没有下载到本地。所以当我在微信上点击「发送图片」的时候，iCloud 云盘这个进程会默默开始下载这张图片。由于我的手机上同时并发运行着很多很多个进程，所以 iCloud 进程下载图片这个动作也是**走走停停**的——我的手机并不随时都在为它服务。经过两三秒的下载，图片下载完成之后，微信进程才可以去发送这个图片文件——因为在这个时间点，图片文件才真正从云盘来到了手机本地，微信是从手机本地读取图片数据、再发给朋友的。

现在思考这样一个问题：对于微信进程来说，当我点击发送按钮的那一刻，它就已经准备好随时随地都可以发图片了；而微信进程和 iCloud 进程是并发运行的，各走各的、各干各的——那微信怎么知道 iCloud 的下载有没有做完呢？也就是说，两个进程都在以**不可预知的速度**向前推进，都是走走停停的。假设微信进程在中间的某个时间点就尝试发送图片，那意味着什么？意味着图片可能只下载了一半，就被微信发出去了——这显然会导致错误的结果。

所以在操作系统内部，这种进程的异步性是**必须去解决的问题**。在本门课的第二章，我们会学习操作系统的**进程同步机制**：有了进程同步机制，多个互不相干的进程之间想要配合完成一些事情的时候，就可以用它来解决，以此防止并发进程的异步性带来的问题。

## 从纸带打孔到中断：操作系统的诞生与运行机制
> 对应块：BLK02 | 覆盖分集：P04-P06 | 块标题（分集名）：《1.2 操作系统的发展与分类》

这一讲我们沿着操作系统出现的时间顺序走一遍：手工操作、单道批处理、多道批处理、分时、实时，看每一种系统是为了解决什么问题才被发明出来的。然后把镜头拉近，看看操作系统在计算机上到底是怎么运行的——两种指令、两种 CPU 状态、两种程序，它们一一对应，最后再讲清楚把这一切串起来的核心机制：中断。前面的内容重点考理解"各类型操作系统想解决什么问题"，优缺点可能出选择题；后面运行机制和中断的内容则十分重要，很容易在选择题里出现。

### 手工操作阶段：CPU 大部分时间在发呆

在这个阶段，操作系统其实还并没有诞生。程序员写程序是写在纸带上的：纸带上有一些小孔，有孔的地方代表二进制的一，没孔的地方代表二进制的零。程序员通过在纸带上打孔的方式写好程序，把纸带装到纸带机上，计算机从纸带机里读取要运行的程序；程序运行结束后，再把结果输出到纸带机上，由程序员手工取走。

这套流程有一个很明显的问题：程序员用手工的方式把纸带装上去、或者从纸带机取走结果，这个过程是超级慢的。我们来走一遍一个程序员提交作业的完整时间线：

- 首先，程序员要花很长时间把自己的程序装到纸带机上；
- 然后计算机从纸带机把程序数据读进来——这个读取过程也是一个很慢速的过程，要消耗不短的时间；
- 但计算机真正计算的速度是非常快的，只需要花很短的时间就能把程序运行结束；
- 运行完了，又要花比较长时间把结果输出到纸带机上，程序员再手工取走；
- 第一个程序员取走结果之后，第二个程序员才能接着用计算机，重复上面这一整套慢动作。

所以手工操作阶段有两个主要缺点。第一是**用户独占整机**：第一个程序没有完全运行结束之前，不允许第二个程序员同时使用计算机，谁在上机谁就独占着。第二是人机速度矛盾导致的**资源利用率极低**：手工操作很慢，计算机计算很快，这么长的时段里计算机真正在忙碌的只有一小段，很大比例的时间它都处于空闲状态。

> **易错点**：这个阶段连操作系统都还没有，别把它当成某一种"操作系统"。它只是演化的起点，作用是暴露矛盾——CPU 太贵、等待太久。

更糟的是，这个阶段计算机的造价十分昂贵。让这么昂贵的资源大量时间处于空闲状态，显然是一种很不经济、很低效的方式。于是为了解决这个问题，人们发明了单道批处理系统。

### 单道批处理：用脱机输入输出缓解矛盾

单道批处理阶段引入了**脱机输入输出技术**。各个程序员把自己的程序依次放到纸带机上，由一台叫**外围机**（外围控制机）的专门机器，控制着把纸带里的程序数据先转到磁带上；之后计算机直接从磁带读取程序数据——而磁带的读写速度要比纸带机快很多。

此时的计算机里运行着一个叫**监督程序**的程序，由它控制计算机自动地从磁带中输入输出作业的数据。整个流程变成：监督程序控制计算机从磁带读入第一个作业（比从纸带机读入快得多），接着进行运算，再把结果输出到磁带上；第一个作业完成后紧接着读入第二个作业，计算、输出，以此类推。

用甘特图的视角对比一下，效果是这样的：

```text
手工操作阶段（示意）：
|--装带--|--慢速读入--|--计算--|--慢速输出--|--取走--|--下一轮重复--|
                      ↑ CPU 只有这一小段在干活

单道批处理（示意）：
|--读入作业1--|--计算--|--输出--|--读入作业2--|--计算--|--输出--|
              ↑ 脱机 I/O 让"读入/输出"的时间比例小了很多
```

读图说明：引入脱机输入输出之后，作业输入输出所占用的时间比例降低了很多，CPU 有更高比例的时间处于忙碌的计算状态，资源利用率有了一定提升，人机速度矛盾得到了一定程度的缓解。

但是这种方式很显然，资源利用率依然不够高。关键限制在于：**内存中同一时刻只能有一道程序运行**，只有这个程序运行结束并且输出完成，才能继续读入第二个程序——各个程序之间是串行执行的。所以虽然比上一个阶段有所提升，CPU 依然有大量时间是在空闲等待，资源利用率依然很低。

> **提示**：注意"单道"这两个字就是问题本身——一道程序独占内存，串行执行，CPU 在这道程序做 I/O 时无事可做。这个"道"字的限制，正是下一个阶段的突破口。

### 多道批处理：操作系统正式诞生

为了解决"串行"这个问题，人们发明了**多道批处理系统**。在这个阶段，**操作系统就正式诞生了**。有了操作系统，就可以支持多道程序并发运行：每一次可以往内存中读入多道程序，让它们并发地执行。

还是用甘特图来看它和单道的区别。假设 CPU 在计算第一个作业：

- CPU 计算作业 1 的时候，输入设备是空闲的——那就让输入设备同时把作业 2 读入内存；
- 作业 1 计算完成，它使用输出设备把结果输出到磁带；这时候只是输出设备在忙，CPU 已经空闲了——那就让 CPU 为作业 2 服务，开始计算作业 2；
- 同理，这时候输入设备又空闲了——就同时读入作业 3；
- 后面的过程以此类推。

```text
多道批处理（示意）：
CPU    ：|--计算作业1--|--计算作业2--|--计算作业3--|--...
输入设备：|--读入作业2--|--读入作业3--|--...
输出设备：            |--输出作业1--|--输出作业2--|--...
```

读图说明：CPU、输入设备、输出设备三者错峰忙碌，几乎不再出现大段空闲——这就是并发共享资源的直观效果。

总之，引入多道程序技术之后，多道程序可以并发执行，共享计算机中的资源（输入设备、输出设备、CPU 等等），资源利用率得到大幅提升，CPU 有大量时间处于忙碌状态，利用率比单道批处理又上了一个台阶。

不过多道批处理有一个软肋：**它不提供人机交互功能**。用户把自己的作业提交了之后，接下来就只能干等着计算机把作业处理完——用户无法调试自己的程序，也不可能在程序运行过程中输入一些参数，这些事情统统无法实现。

到这里先做个阶段小结，三种系统一脉相承：

| 系统 | 要解决的问题 | 手段 | 遗留的缺点 |
| :--- | :--- | :--- | :--- |
| 手工操作 | ——（起点） | 纸带 + 人工装卸 | 用户独占整机；人机速度矛盾，CPU 利用率极低 |
| 单道批处理 | 手工装卸太慢、I/O 占比太高 | 脱机 I/O + 监督程序 | 内存只有一道程序，程序间串行 |
| 多道批处理 | 串行导致 CPU 大量空闲 | 多道程序并发共享资源 | 不提供人机交互，无法调试程序 |

### 分时与实时：公平与优先的取舍

为了实现人机交互功能，人们发明了**分时操作系统**。分时系统以**时间片**为单位，轮流为各个用户（或者说各个作业）服务：比如先给这个用户服务 50ms，再给那个用户 50ms，再来一个用户 50ms。用户可以通过键盘、鼠标这类终端和计算机进行交互。

分时操作系统的主要优点就是**用户的请求可以被及时响应**。但它也存在一个明显的缺点：**不能优先处理一些紧急的任务**——这种系统对各个用户都是完全公平的，谁也别想插队。

那要让计算机能优先处理紧急任务怎么办？人们又提出了**实时操作系统**。实时系统能根据任务的优先级来优先响应紧急任务，它要求计算机在接收到紧急信号之后及时处理，并且要在严格的时间时限内处理完成，还要保证处理结果的正确。所以实时操作系统的主要特点是**及时性和可靠性**。

实时系统又分为硬实时和软实时两种：

- **硬实时系统**：像导弹控制系统、自动驾驶系统这类，必须绝对严格地在规定时间内完成相应的处理，否则会导致严重的问题——比如导弹射偏了，或者自动驾驶的汽车直接开到马路下面去。
- **软实时系统**：比如我们熟悉的 12306 火车订票系统。它要求网站上实时显示剩余票量，但即使偶尔更新得不是很及时，也并不会产生特别严重的后果。

> **提示**：判断硬实时还是软实时，就问一句——"错过时限的后果是否灾难性的"。错过就是事故的，硬实时；只是体验变差的，软实时。

除了上面这些，还有网络操作系统、分布式操作系统和个人计算机操作系统。这几种大家只需要有个简单的了解，自己阅读一下就可以——考试当中一般考察的是前面提到的那几种，这里就不再展开。

### 机器指令：CPU 唯一听得懂的语言

接下来进入操作系统运行机制的部分。这个小节涉及两个概念组：两种类型的指令、两种处理器状态、两种程序，它们一一对应，我们一层一层慢慢讲。根据往届同学的反馈，很多跨考的同学认为这部分很难理解，会涉及一些底层硬件的知识；而且不少同学报考的学校并不考计算机组成原理，所以我们先准备一点预备知识。

先解释程序在计算机硬件上底层是怎么运行的。我们平时用 C 语言这类高级语言写的程序，都会经过编译器编译，翻译成计算机能够听得懂的二进制代码，也就是**机器指令**。一行 C 语言代码经过编译之后，可能会对应很多很多条机器指令。比如定义一个 int 型变量 `x = 1`，再加一个自增 1 的操作，这两行短短的代码经过编译，形成的机器指令就会是一长串。那串二进制数我们人是看不懂的（其实写讲义的时候也是随便举的数，反正都长一个样），但对 CPU 来说，这样的二进制代码才是它能看懂的语言。

所以一段程序运行的过程，本质就是 CPU 把这些机器指令一条一条执行的过程；这些机器指令在背后实现的，就是我们用代码写的那段逻辑。所谓**机器指令**，就是让处理器（CPU）能够识别并执行的最基本的命令，比如进行一次加法操作、进行一次赋值操作等等。

> **易错点**：这里的"指令"很容易和另一个概念混淆。很多同学习惯把在 Linux、Windows 的小黑框里输入的 `ls`、`cd` 这类命令称为"指令"——但那其实是交互式命令接口的命令，和我们这里说的指令不是一回事。我们这里指的指令是二进制的机器指令。后面再看到"指令"两个字，一律按机器指令理解。

### 内核程序与应用程序

在操作系统这门课当中，需要注意区分两种类型的程序：一种叫**内核程序**，一种叫**应用程序**。

应用程序就是跑在操作系统之上的、我们平时很熟悉很喜欢用的那些程序，比如 QQ、微信等等。我们普通程序员写的程序，就是应用程序。但还有一些人——比如微软、苹果公司里负责开发操作系统的那帮人——他们写的程序就是**内核程序**。

这帮人编写了许许多多的内核程序，这些内核程序最终组成了操作系统的**内核**（kernel）。内核是操作系统最核心的部分，也是最接近硬件的部分。我们之前提过，操作系统最重要的角色之一是作为系统资源的管理者，而这个管理工作就是在内核部分实现的。我们甚至可以说，一个操作系统只要有内核就可以了——比如接触过容器技术的同学可能知道，Docker 容器里只需要有 Linux 内核，就可以实现 Linux 的所有功能。而我们用户平时使用的操作系统，包含的并不只是内核的功能：比如图形化用户界面就不是放在内核里实现的，即使没有图形界面，我们依然可以用命令行（就是小黑框那种方式）来使用操作系统。所以内核当中包含的，只是操作系统里最重要、最核心、最必不可少的那些功能。

### 特权指令与 CPU 的两种状态

既然操作系统内核是系统资源的管理者，它作为管理者这个角色，有时就需要让 CPU 执行一些比较特殊的指令，比如**内存清零**的指令。这种指令一旦执行，会对其他程序的运行造成很严重的影响——像这样的**特权指令**，运行之后是有可能影响到其他程序正常运行的，所以只应该允许系统的管理者（也就是操作系统内核）来使用。

也就是说：假如一段程序是内核程序，那这些指令当中可以出现特权指令；假如这段程序是普通应用程序，那其中就不应该包含特权指令，只能使用**非特权指令**——比如让 CPU 做加减乘除运算的那一系列指令。

关键在于，CPU 在设计和生产的时候，就已经划分好了哪些指令属于特权指令、哪些属于非特权指令。所以 CPU 拿到一条指令时，它是能分辨出这条指令是特权还是非特权的。

那么问题就来了：CPU 在执行程序的时候，只负责把指令一条一条执行。它虽然能分辨特权与非特权，但它怎么分辨此时正在执行的指令，到底属于应用程序还是属于内核程序呢？

为了让 CPU 能区分这一点，CPU 被划分成两种状态：

- **内核态**（又称管态）：说明此时 CPU 正在运行内核程序，可以执行特权指令；
- **用户态**（又称目态）：说明此时 CPU 正在运行应用程序，只能执行非特权指令。

> **易错点**：用户态的别名是"目态"，内核态的别名是"管态"——"管"对应管理者（内核），别把这两个对调了。考试里这两个术语都可能出现。

那 CPU 怎么知道自己处于哪种状态？CPU 当中有一个寄存器（也就是一个存数据的地方）叫**程序状态寄存器**（PSW）。它当中的某一个二进制位标记着当前状态：这个位为 1 表示内核态，为 0 表示用户态。当然也有一些 CPU 是反过来用 0 表示内核态、1 表示用户态的，但这无关紧要——我们只需要知道，用一个二进制位就可以实现对 CPU 状态的标记。

### 一条指令引发的"变态"：两种状态如何切换

接下来探讨 CPU 怎么实现两种状态之间的切换。我们直接用一个例子，把整个过程走一遍——这也是本讲最精彩的一段故事。

**第一步：开机。**开机时需要加载操作系统，操作系统要进行一些初始化工作。系统初始化是由操作系统当中的某些内核程序完成的，所以开机过程中执行的是内核程序，此时 CPU 肯定处于内核态。

**第二步：内核让出 CPU。**开机完成后，用户启动某个应用程序。但刚才 CPU 明明在执行内核程序，要让它转去运行应用程序，怎么实现？此时内核程序会执行一条**特权指令**，这条特权指令把 PSW 的标志位从内核态改为用户态——CPU 状态切换完成。接下来操作系统内核让出 CPU 的使用权，应用程序上 CPU 运行。由于此时 CPU 已经是用户态了，应用程序就在用户态下运行，CPU 一条一条地执行它的指令。

**第三步：黑客登场。**此时一个小故事发生了。假如有一个猥琐的黑客，在这个应用程序当中植入了一条特权指令，会发生什么？

首先，CPU 在读入这条指令的时候，就已经能判断出这是一条特权指令。但它又检查了自己的 PSW 寄存器，发现自己此时处于用户态——这就说明我此刻正在运行的是应用程序，而不是内核程序。一个应用程序竟然想用特权指令？这个事情坚决不能让它干！

于是这个非法事件引起了一个**中断信号**。CPU 检测到中断信号之后，会立即强行"变态"——强行变成核心态（内核态），并且拒绝执行这条特权指令。接下来 CPU 暂停执行这个应用程序后面的指令，转而去执行一个处理中断信号的内核程序，此时 CPU 就在内核态下运行这个内核程序。也就是说，中断发生之后，操作系统内核重新夺回了 CPU 的控制权，对中断进行相应处理；处理完了之后，才会把 CPU 的使用权重新还给应用程序。

把这个故事里的两条切换规则提炼出来：

- **内核态 → 用户态**：由内核执行一条修改 PSW 标志位的**特权指令**完成。执行这条指令，就意味着操作系统内核主动让出 CPU 的使用权；
- **用户态 → 内核态**：由**中断**引发，由 CPU **硬件自动**完成状态切换。切换之后 CPU 停止运行当前的应用程序，转而运行一个内核程序。

> **结论**：触发一个中断信号，就意味着操作系统会强行重新夺回 CPU 的使用权。这两个方向的切换机制不对称——一个是主动交权（特权指令），一个是强行夺权（中断），这个不对称是选择题的高频考点。

除了非法使用特权指令之外，还有很多别的事件也会触发中断信号。它们的共性是：**但凡需要操作系统介入开展管理工作的时候，就会触发一个中断信号**。具体有哪些中断，下一节展开。

### 中断：操作系统夺回 CPU 的唯一途径

上一节其实已经埋了伏笔，这里把中断的作用正式讲清楚——这个内容十分重要，所以愿意再当一次复读机。

CPU 上运行着两种程序：操作系统的内核程序和普通的应用程序。内核程序是整个系统的管理者。计算机刚启动的时候，上面跑的肯定是内核程序；时机合适的时候，内核程序会把 CPU 的使用权主动让给应用程序（这部分怎么"让"属于第二章进程管理的内容，暂且不展开）。总之应用程序上 CPU 运行之后就会一直运行下去，**除非发生了中断**——而一旦发生中断，就会让 CPU 立即停止当前正在执行的应用程序，转而执行相应的内核程序。

所以：**中断是让操作系统内核这个管理者重新夺回 CPU 使用权的唯一途径**，同时中断会使 CPU 由用户态变为内核态。

我们可以反过来想一个问题：假如没有中断机制，会怎样？一旦一个应用程序上了 CPU，它就可以一直运行下去。一个 CPU 一直在运行同一个应用程序，那我们还怎么实现多道程序并发？所以——没有中断技术，就没办法实现多道程序并发；甚至可以说，**没有中断技术，就没有操作系统**。内核作为管理者，想让出 CPU 使用权的时候可以主动让；想夺回来的时候，靠的就是中断。结合上一节那个黑客的故事，这应该不难理解了。

### 内中断与外中断：信号从哪来

中断分为两大类：**内中断**和**外中断**。区分标准只有一条：

- 内中断：中断的产生**和当前执行的指令有关**，中断信号来源于 CPU **内部**；
- 外中断：中断和当前执行的指令**无关**，中断信号来源于 CPU **外部**。

```text
            广义的中断
               /\
      内中断 \/  \/ 外中断
      （异常）      （狭义的中断）
        /\              /\
   指令引发的      时钟中断 / I/O 中断
 （信号来自 CPU 内部）（信号来自 CPU 外部）
```

读图说明：判断归属不看事件大小、不看严重程度，只看中断信号的产生和当前执行的指令有没有关系、信号来自 CPU 内部还是外部。

先看内中断的例子。第一个就是上一节的黑客故事：应用程序运行在用户态，黑客尝试植入一条特权指令；CPU 拿到这条指令时发现自己处于用户态、正在运行应用程序，于是这个非法事件触发中断信号，CPU 拒绝执行，自动转为内核态，开始执行处理这个中断的内核程序。CPU 在执行当前这条指令的时候，由这条指令本身引发了中断——这是很典型的内中断。

第二个例子：有时候即使 CPU 执行的是**非特权指令**，也可能引发内中断。比如 CPU 执行一条除法指令时，发现除数是零——这种情况下肯定不能让程序继续执行下去，也会引发一个内中断。

> **提示**：把这两类归纳一下——当前执行的指令本身非法（比如用户态想执行特权指令），或者指令的参数非法（比如除数为零），都会产生内中断信号。

第三个内中断的例子稍微不同：应用程序运行在用户态，但有时它想**请求操作系统内核提供服务**。这种情况下，应用程序会执行一条特殊的指令，叫**陷入指令**（trap 指令）。这条指令会引发一个内中断信号，CPU 随后转向处理这个中断的内核程序。应用程序执行陷入指令，就意味着它**主动**把 CPU 使用权还给操作系统内核，请内核为自己提供某些服务——我们之前提到的**系统调用**，就是用陷入指令完成的。

> **易错点**：陷入指令是一条比较特殊的指令，但它**不是特权指令**。理由很直接：应用程序运行在用户态，而用户态下可以执行陷入指令——用户态能执行的指令，必然是非特权指令。

再看外中断的例子。第一个叫**时钟中断**：由计算机当中的一个硬件部件——时钟部件——发出，它每隔一段时间（比如 50ms）给 CPU 发一个中断信号。别小看这个机制，正是靠时钟中断，才实现了多道程序并发运行。我们来看整个故事：

1. 应用程序 1 运行在用户态，CPU 执行它的指令；
2. 执行了两条指令后，时钟部件发现已经过了 50ms，于是给 CPU 发送一个中断信号——注意这个信号和当前执行的指令没有关系，它来自 CPU 外部；
3. CPU 检测到中断信号，暂停当前应用程序，转为内核态，执行处理这个时钟中断信号的内核程序；
4. 内核程序执行过程中发现：应用程序 1 已经用了 50ms 了，公平起见，让第二个应用程序上 CPU 运行。于是内核把 CPU 使用权交给应用程序 2，切换回用户态，程序 2 开始运行；
5. 程序 2 执行一段时间后，又过了 50ms，时钟部件再次发来来自外部的中断信号；
6. CPU 又去执行对应的内核程序，发现程序 2 也用了 50ms，公平起见让程序 1 接着上 CPU 运行……

如此不断相互切换——这个故事清晰地展示了两个应用程序是如何在**中断机制的支持下**实现并发运行的。上一讲分时系统里"以时间片轮流服务"的承诺，底层靠的就是时钟中断。可以看到中断在现代计算机当中的作用有多大。

第二种外中断来自 **I/O 设备**（input / output，输入输出设备）。比如某个应用程序请求打印机的打印服务，打印机在打印输出完成之后，会向 CPU 发送中断信号，通知 CPU"我的任务已经完成了"。接下来 CPU 用与这个中断信号相对应的内核程序来处理它。

> **结论**：CPU 在**每一条指令执行结束的时候**，都会例行检查是否有外部中断信号需要处理。这就是外中断能被及时感知的机制保证。

### 异常的三张面孔：陷入、故障、终止

先澄清术语。判断内中断还是外中断，只需要看中断信号的产生和当前执行的指令是否有关。前面一直用"内中断 / 外中断"这对术语，因为"内、外"这两个字能很形象地体现本质区别。但在很多教材和很多学校的考试当中，**内中断一般称为"异常"（exception），外中断一般直接称为"中断"**。所以考试里遇到的"中断"，通常指狭义的中断，特指外中断；而我们前面一直在说的是广义的中断。做题时更要注意"中断 / 异常"这对术语——接下来的讲解中会经常用到"异常"，它指的就是内中断。

异常又可以进一步划分为三种，这个分类**曾经考过**：

- **陷入（trap）**：就是前面讲的由陷入指令引发的异常。这种异常是**程序故意引发的**——程序想请求操作系统服务时，就会故意执行这条指令。这也是系统调用的实现原理（系统调用的细节下一小节展开）。
- **故障（fault）**：由**错误条件**引起、并且**可能被内核程序修复**的问题。内核程序把故障修复之后，会把 CPU 使用权还给应用程序，让它继续执行下去。比如后面第三章会学到的**缺页故障**——现在理解不了没有关系，等学完第三章再回来细细品味。
- **终止（abort）**：由**致命的错误**引起，这种错误一般是内核程序无法修复的。发生这种异常后，内核程序一般不会再把 CPU 使用权还给引发终止的应用程序，而是直接把这个应用程序干掉、让它终止。比如前面提过的整数除以零——这其实是程序 bug，不是操作系统能修复的，那是程序本身的问题；再比如非法使用特权指令——这样的程序也应该直接干掉，不能把 CPU 使用权再还给它。

> **易错点**：三种异常的分界线在于"是否故意"和"能否修复"。陷入是故意的、请求服务的；故障是出错了但能修、修完继续跑；终止是致命的、修不了、直接杀进程。除以零为什么算终止而不是故障？因为它是程序 bug，操作系统修不了——该怪程序，不该怪系统。

### 中断机制怎么实现：查中断向量表

最后简单介绍一下中断机制背后的基本原理。前面举了各种各样的中断：有的是整数除以零，有的是时钟部件引起的，有的是应用程序自己引发的。很显然，这么多种中断类型不可能用同一个程序来处理。所以 CPU 会**根据中断信号的不同**，找到与这个信号相对应的中断处理程序。

具体做法是：CPU 检测到中断信号之后，根据中断信号的**类型**查询**中断向量表**，通过中断向量表找到该类型中断所对应的**中断处理程序**。结合前面讲过的内容，大家应该能想到：中断处理程序其实就是一种**内核程序**，肯定需要运行在**内核态**。

整个中断机制可以归纳为两个步骤：

1. **检查中断信号**：内中断信号在 CPU 执行指令的过程中就会检查（执行到非法指令、除零、陷入指令时当场发现）；外中断信号的检查在每个指令周期的末尾——CPU 每执行完一条指令，都例行检查是否有外部中断信号需要处理；
2. **分派处理**：检测到中断信号后，查询中断向量表，找到该类型中断对应的中断处理程序来处理。

至于具体的硬件上怎么实现，那是计算机组成原理那门课要教的内容；不考那门课的同学，理解到这里就差不多了。

---

把这一讲收拢成几句话：操作系统沿着"手工 → 单道批处理 → 多道批处理 → 分时 → 实时"的路线演化，每一种新系统都是为了补上一种旧系统的短板——先是人机速度矛盾，再是串行执行，然后是没有交互，最后是不能优先处理紧急任务。运行机制上，CPU 用 PSW 里的一个二进制位区分内核态与用户态；内核态到用户态靠一条修改 PSW 的特权指令（内核主动让权），用户态到内核态只能靠中断（硬件自动强行夺权），没有第二条路。中断由此成为操作系统一切管理工作的入口：内中断（异常）分陷入、故障、终止三种，外中断靠时钟部件和 I/O 设备驱动，靠中断向量表分派到对应的内核态处理程序。没有中断，就没有多道程序并发；没有多道程序并发，就没有我们今天使用的操作系统。这一讲的运行机制部分初学时觉得懵是正常的，放心大胆往后学，随着之后章节的展开，对这里的理解会越来越深；结合教材和课后习题巩固即可。

## 系统调用、操作系统体系结构与引导
> 对应块：BLK03 | 覆盖分集：P07-P10 | 块标题（分集名）：《1.3.3_系统调用》

操作系统作为用户和计算机硬件之间的接口，需要向上提供简单易用的服务：给普通用户用的是命令接口和 GUI，而给程序员用的是程序接口——程序接口由一堆系统调用组成。这一讲我们从系统调用讲起，看它为什么必须存在、它背后发生了什么；然后钻进操作系统的内部，看看内核该怎么设计（大内核、微内核，以及大纲新增的分层结构、模块化结构和外核）；最后回答一个每个人每次开机都会经历、却从没想过的问题——按下电源键之后，操作系统是怎么被"引导"起来的。

### 系统调用：应用程序请求内核服务的通道

系统调用其实就是应用程序（程序员）请求操作系统内核服务的一个途径，它和我们平时编程时使用的函数调用很类似。

不过写程序的时候，通常不是直接发起系统调用。理论上你完全可以用汇编语言直接请求系统调用的服务，但现在更多的是使用高级语言编程，所以一般会直接使用高级语言提供的库函数。这些库函数在底层会用到操作系统提供的系统调用功能，替你向操作系统请求服务。所以层次关系是这样的：

```text
   应用程序
      │ 调用
      ▼
   高级语言的库函数（封装得更好用的编程接口）
      │ 底层
      ▼
   系统调用（操作系统向上提供的接口）
      │ 请求
      ▼
   操作系统内核
```

库函数在上、系统调用在下，应用程序通过系统调用的方式请求操作系统内核的服务；高级编程语言用库函数把系统调用封装起来，向更上层的应用程序程序员暴露一些更好用的编程接口。

但要注意：**并不是所有的库函数在底层都会使用系统调用**。比如 C 语言里 `math.h` 提供的取绝对值这类数学运算函数，它们的功能不需要特权指令也能完成，所以这类库函数在底层并不需要系统调用。而另一些库函数，比如创建一个新文件——这个事情必须请求操作系统内核的服务才可以完成，所以它在底层就肯定用到了系统调用。

> **易错点**：库函数和系统调用不是一一对应的关系。有的库函数纯粹在用户态就能干完活，有的库函数底下套着系统调用；系统调用一定比库函数更底层。

### 为什么系统调用是必须的：打印店的故事

我们来虚构一个这样的场景：你去学校打印店打印论文，用 WPS 点下了打印按钮，打印机开始工作。可当你的论文打印到一半时，另一个同学用 Word 也按下了打印按钮，请求打印他自己的论文。

WPS 和 Word 在这台电脑里是两个**正在并发运行的进程**。如果这两个进程能够随意地、并发地共享使用打印机资源，会发生什么？两个进程交替地向打印机提出打印请求，打印机就会交替收到两边发来的命令——先打印一行你的，再打印一行他的——两篇论文的内容混杂在一起打出来。这显然不是我们想要的结果。

问题的根源在于：系统中有各种各样的并发进程，这些进程需要共享使用打印机这样的共享资源，而这类共享资源是需要各个进程**互斥**共享的。那怎么实现对共享资源的互斥访问？最好的方式就是让操作系统内核——也就是系统的管理者——对共享资源进行统一的管理；上层的应用程序只能通过系统调用的方式，请求操作系统给它分配这种资源，之后这个进程才可以对共享资源进行使用和访问。各个进程的请求由操作系统内核来协调处理，保证它们并发运行时不会发生这种奇奇怪怪的事情。

从这个例子就能看到，系统调用的功能是必须存在的。

那么到底哪些功能需要用系统调用的方式对外提供呢？它们有一个共同的特点——**凡是和共享资源有关的操作，都需要通过系统调用来完成**。内存是一种共享资源，对内存的分配与回收要用系统调用；I/O 设备是一种共享资源；文件也是共享资源。这些共享资源是有限的，操作系统要对它们进行统一的管理和分配，所以应用程序在使用这些资源时，就必须通过系统调用请求操作系统内核来帮它进行接下来的处理——这样才能保证系统的稳定性和安全性，防止非法操作。相信通过打印机的例子，大家能有比较直观的体会。

王道书上还给出了系统调用按功能的分类，什么设备管理、文件控制等等，这里不展开，大家自己看一下、有个印象就可以。有兴趣的同学可以去百度搜索一下 Linux 的系统调用，看看 Linux 操作系统向上提供了哪些系统调用。

### 一次系统调用的完整过程

假设一个应用程序想要进行系统调用，它背后需要做哪些事情？我们完整地走一遍。

应用程序运行在**用户态**，它的各个指令会被 CPU 依次执行。当它想要发出系统调用时：

```text
用户态  应用程序依次执行指令
          │
          │ ① 传参指令（可能有多条）：把参数放入 CPU 寄存器，
          │    其中一个参数指明本次系统调用的类型（如 Linux 的 fork）
          ▼
        执行陷入指令（trap 指令 / 访管指令）
          │
          │ ② 陷入指令主动引发一个内中断，CPU 暂停应用程序
          ▼
内核态  执行系统调用入口程序（属于内核程序，须在内核态运行）
          │
          │ ③ 检查寄存器里的参数：通过第一个参数，
          │    知道应用程序想要哪种类型的系统调用服务
          │ ④ 调用与该类型对应的系统调用处理程序，
          │    让它上 CPU 运行，依据其余参数完成具体服务
          ▼
        处理完毕，CPU 转回用户态
          │
          ▼
用户态  应用程序从暂停处继续往下执行
```

分步来说：

- **传参**：应用程序先用传参指令给 CPU 的寄存器传递一些必要的参数。比如在某个寄存器里放入一个参数，这个参数指明了此次要进行哪种类型的系统调用（比如 Linux 里的 fork 系统调用）。传参指令可能会有多条，主要看这个系统调用需要传递几个参数——操作系统会根据这些参数判断应用程序想要的到底是哪种类型的服务。
- **陷入**：参数都放到寄存器之后，应用程序会执行一条很特殊的指令——**陷入指令**。执行陷入指令之后，就意味着这个应用程序把 CPU 的控制权**主动**交还给了操作系统内核，用这种方式来请求内核的服务。陷入指令的执行会引发一个**内中断**。
- **转向内核程序**：CPU 检测到这个内部中断信号之后，发现它是由陷入指令引起的，于是暂停运行应用程序，转而去执行处理这个中断的程序——它就是**系统调用入口程序**。显然，接下来要执行的这个程序属于内核程序，需要在**内核态**下运行；我们也可以说它其实是某一种中断处理程序，只不过它处理的是由陷入指令引发的那个内中断。
- **分派与执行**：系统调用入口程序检查寄存器里的参数，通过第一个参数知道应用程序想要哪种类型的系统调用服务，于是调用与该类型对应的**系统调用处理程序**，让它上 CPU 运行。处理程序在执行时，再根据应用程序传递的其他参数，确定具体要提供哪些服务。
- **返回**：系统调用被处理完之后，CPU 又会转回用户态，接着执行之前的那个应用程序。

把前面讲的库函数和系统调用串起来：我们普通程序员用高级编程语言写代码，代码中调用高级语言提供的库函数；有的库函数内部用到了操作系统提供的系统调用——先传递系统调用所需的参数，再执行陷入指令，陷入指令引发内中断后，CPU 转向执行处理系统调用的内核程序（核心态），处理完再返回应用程序继续往下执行。

#### 几个一定会考的小细节

第一，**陷入指令是在用户态下执行的**。它是一条很特殊的指令，但它**不是特权指令**，是非特权指令——正因为非特权，应用程序才可以在用户态执行它；执行之后它会主动引发一个内中断，让 CPU 进入核心态运行内核程序。

> **易错点**：陷入指令 ≠ 特权指令。特权指令只能在核心态执行，而陷入指令恰恰要在用户态执行；它是"用户态通往核心态的合法大门"。

第二，**发出系统调用请求这个动作是在用户态进行的，而对系统调用的相应处理是在核心态下完成的**。一句话记住：请求在用户态，处理在核心态。

第三，陷入指令还有另外两个名字：**trap 指令**和**访管指令**。不同教材使用的术语不一样，但要知道它们指的都是同一个东西。

### 内核里应该放哪些功能

这一部分我们学习操作系统的体系结构，也就是操作系统的内核应该怎么设计。考试中常考的是两种体系结构：一种叫大内核，一种叫微内核。

我们已经知道计算机系统的层次结构，但操作系统内部还可以进一步划分：一部分是**内核的功能**，另一部分是**非内核的功能**。操作系统最核心的那些功能需要放在内核当中，比如时钟管理、中断处理、原语，以及进程管理、存储器管理、设备管理等等。

- **时钟管理**：用之前提过的时钟中断来实现计算机计时的功能。想要实现程序并发，就必然离不开时钟管理这个很重要的内核功能。
- **中断处理**：之前已经举过很多例子，不再多解释。
- **原语**：一种特殊的程序，具有**原子性**——要么一气呵成地全部运行完成，要么就不运行，它的执行过程是不可被中断的。也就是说，执行原语这一小段程序的过程中，即使有外部中断信号过来，CPU 也会继续把原语执行完成，才去处理那个外部中断信号。

这里列举的时钟管理、中断处理、原语这三样，是**和硬件结合最为紧密**的，所以它们必须放在操作系统的内核当中。而进程管理、存储器管理这些管理功能，更多的是对**数据结构**的操作，不会直接涉及硬件，所以有的操作系统并不把这些管理功能放在内核里，只在内核中保留与硬件接触最紧密的部分。

顺带说一句：像 Ubuntu 这些我们耳熟能详的 Linux 操作系统，它们的开发团队主要干的事情其实是实现**非内核**的功能，内核用的就是 Linux 的内核。跨考的同学如果不知道这些是什么东西也无所谓，不需要深究。

> **定义**：内核是操作系统最核心、最基本的部分，它由一系列内核程序组成，这些内核程序必须运行在**内核态**。

"管理功能放不放内核"这个问题，就引出了两种截然不同的内核设计方法。另外补充一句：以前的大纲只介绍宏内核（也就是大内核）和微内核，今年大纲又增加了分层结构、模块化结构以及外核。这一部分如果考，肯定是对各种操作系统结构特性的考察，以及每种结构有什么优点缺点——选择题大概率从这个角度命题。

### 大内核与微内核

把操作系统所有功能都包含在内核当中，这种结构就叫**大内核**（也叫宏内核）；如果内核当中只保留与硬件关系最紧密的部分，这种内核就叫**微内核**。

这个划分直接决定了"哪些代码运行在内核态"。采用微内核结构时，属于内核的功能需要运行在内核态，不属于内核的功能就运行在用户态——这会对系统性能造成影响。我们用一个更直观的例子体会一下。

假设应用程序想请求操作系统的服务，并且这个服务的背后需要**同时涉及**进程管理、存储管理、设备管理这几个功能：

- **大内核**：这几个功能都划分在内核里，都运行在内核态。应用程序提出服务请求，CPU 从用户态切换为核心态，运行这一系列内核程序，干完再切回来——整个过程只需要 **2 次** CPU 状态转换。
- **微内核**：只有与硬件最紧密的功能在内核里、在内核态运行，进程管理、存储管理、设备管理这些模块都在用户态。而这几个模块在处理应用程序的请求时，各自又需要得到内核的支持——每请求一次内核服务，就涉及一次 CPU 从用户态转到内核态、服务完成后又转回用户态的过程。三个模块都要请求内核服务，整个过程就需要 **6 次** CPU 状态转换。

```text
大内核： 应用 ─(用户态→核心态)→ 内核统一处理 ─(核心态→用户态)→ 回到应用
         整个过程共 2 次状态转换

微内核： 应用 ⇄ 进程管理 ⇄ 内核     2 次
         应用 ⇄ 存储管理 ⇄ 内核     2 次
         应用 ⇄ 设备管理 ⇄ 内核     2 次
         整个过程共 6 次状态转换
```

CPU 的状态转换这个过程其实是有成本的，需要消耗不少时间，所以频繁切换 CPU 状态会降低系统性能。

> **注意**：为了描述方便，我们把 CPU 状态转换戏称为"变态"。但考试的时候不要用这个词——答题要写得正规一点，必须说成是 **CPU 状态的转换**。

再往深了看一层。事实上，宏内核也采用了模块化的设计思想：内核当中有进程管理、存储管理、设备管理，以及和硬件关系最紧密的中断处理、原语、时钟管理等等，所有功能都放在内核里，内核里的各种功能之间可以直接相互调用——就跟普通的函数调用一样。而微内核只把最基本的、与硬件最紧密的功能放在内核中，大多数功能被放在内核之外，这时功能之间的调用就没有那么方便了：比如进程管理想调用存储管理的功能，只能通过**消息传递**的方式——进程管理向微内核发送一个消息，消息里指明想调用谁、调用参数是什么，由微内核里负责进程间通信的功能把消息传递给存储管理模块；存储管理收到消息后才处理这个调用请求，要返回结果，同样得通过消息传递、由微内核协助完成。显然，直接进行函数调用肯定要比通过消息传递来调用快得多。

把这些拼在一起，两种结构的画像就完整了：

| 对比维度 | 大内核（宏内核） | 微内核 |
| :--- | :--- | :--- |
| 内核里放什么 | 几乎所有功能，模块之间直接函数调用 | 只保留与硬件最紧密的基本功能，模块间靠消息传递通信 |
| 性能 | 高，状态转换次数少 | 低，需要频繁在核心态与用户态之间切换 |
| 结构与维护 | 内核代码庞大、结构混乱、难以维护 | 内核功能少、结构清晰、方便维护 |
| 可靠性 | 模块间相互依赖很强，任何一个功能模块出错都可能导致整个内核崩溃 | 功能模块都在内核之外，某一个模块出错并不会导致整个系统崩溃 |
| 典型代表 | Linux、UNIX | Windows NT |

典型的大内核操作系统像 Linux、UNIX；微内核的可以去看一下 Windows NT。当然这些具体系统并不是考试考察的重点，考试只会考察这两种体系结构的优缺点，有个印象就可以。

### 分层结构：像洋葱一样一层套一层

分层结构的操作系统：最底层是硬件，最上层是用户接口，操作系统的内核被分为**多层**——就像一个洋葱一样。每一层可以**单向地**调用更低一层提供的接口，而且注意：每一层**只能调用相邻的那一层**。

```text
        ┌────────────────────────┐
        │        用户接口        │
        ├────────────────────────┤
        │      内核第三层        │ ← 只能调用第二层的接口
        │      内核第二层        │ ← 只能调用第一层的接口
        │      内核第一层        │ ← 只有第一层可以直接操作硬件
        ├────────────────────────┤
        │          硬件          │
        └────────────────────────┘
```

比如内核分了第一层、第二层、第三层：第一层最接近硬件，只有它能直接操作硬件；第二层只能使用第一层提供的功能接口；第三层只能使用第二层提供的功能接口。每一层只能调用更低的**相邻**那一层，不能跨层调用。

这种设计带来两个优点：

**一是便于调试和验证**，只需要自底向上逐层调试和验证就够了。因为每一层只会用到相邻低层的功能：第一层只用到底层的硬件，而硬件厂商出厂时已经保证硬件特性没问题，所以只要把第一层自己的代码验证一遍，第一层的调试就结束了；接下来调第二层——第二层只用第一层的功能，而第一层刚才已经确认没问题，所以第二层的调试可以基于"正确的第一层"来进行。就这样一层一层往外调，先保证低层被验证是 OK 的，再调更高一层。操作系统开发完之后，软件测试的过程就变得非常清晰明了。

**二是易于扩充和维护**，因为各层之间的调用接口清晰固定。这种结构在设计之初就必须规定好层与层之间的调用接口：这个函数名叫什么、需要提供哪些参数、每个参数的含义是什么、每一次调用会返回什么东西——这些都是最初设计时规定好的。既然层间接口固定不变，我们要在原有的两层之间再新加一层也是 OK 的：只要保证新加的这一层向更上层提供同样的接口，并且它对更下层接口的使用是下层已经实现的，就完事了。所以在两层之间扩充新的一层很简单，维护起来也方便。

缺点也有两个，而且都不好绕开：

**一是难以合理定义各层之间的边界**。A 功能有可能调用 B 功能，而 B 功能有时候难免也要使用 A 提供的功能——比如进程管理有时需要用到内存管理相关的功能，内存管理有时又需要用到进程管理提供的东西。这种"只能由高层调用低层"的严格规定就不太灵活：很难把操作系统的功能严格一层一层分出来，同时还要保证只能高层调低层。

**二是效率低**。因为不可以跨层调用，系统调用执行的时间会变长。打个比方：A 和 D 要说一句话，但分层结构规定 A 不能直接和 D 讲话，A 只能先告诉 B，B 再告诉 C，C 再告诉 D；如果 D 要给 A 回话，那 D 只能先给 C 回话，C 给 B，B 再给 A——A 和 D 之间不可以直接相互调用和返回结果。一个系统调用哪怕只需要最底层的功能，最上层也没法直接调用，只能一层一层往下传递。执行时间变长，效率就变低。

### 模块化结构：主模块加可加载内核模块

模块化是一种很经典的程序设计思想：把操作系统的内核划分为多个模块，各模块之间相互协作着工作。比如把内核分为进程管理、存储器管理、文件管理、设备驱动程序等模块，每一个模块又可以进一步划分为子模块。

整个内核由**主模块**和**可加载内核模块**组成。主模块是必不可少、最核心最重要的那些模块——没有它们操作系统就无法运行，比如进程管理、内存管理，这些重要模块共同组成所谓的主模块。可加载内核模块则是可以**动态加载**到内核当中的，比如设备的驱动程序：有这个驱动程序还是没有，并不会影响系统能不能正常运行，只会影响系统的可拓展性——加载了驱动模块，系统就可以支持新设备。所以可加载内核模块算是一个锦上添花的东西。

它的优点有三个：

**一是模块之间逻辑清晰、易于维护**。我们是按逻辑功能划分模块的，有的模块专门管进程、有的专门管内存，逻辑自然清晰。而且只需要确定好各模块之间的接口，就可以**多模块同时并行开发**——比如进程管理模块对外暴露三个功能接口，只要规定好这三个函数的名字、参数列表和返回值，哪怕这个模块还没开发完，其他模块也可以按照提前约定好的接口并行往前赶。

**二是支持动态加载新的内核模块**。想让操作系统支持一个新设备？把这个设备的驱动程序作为一个新的内核模块加载进来就行；想让操作系统支持一个新文件系统？把新文件系统的代码和数据作为一个新内核模块加载进来。这种特性使得操作系统的适应性增强，而且加载一个新模块**不需要重新编译整个内核**。

**三是任何模块之间都可以直接调用其他模块，无需采用消息传递进行通信，效率高**。我要用你的功能，就直接调你的函数，跟你平时写代码直接调一个函数一样。相比之下，微内核结构就得靠消息传递来调用其他模块的功能——前面已经解释过为什么那会慢。

缺点有两个：

**一是模块之间的接口定义未必合理、也比较难**。我这个模块本来只提供这三个功能，但开发过程中你会发现其他模块好像还需要一个新功能——由于模块之间相互调用会比较多，接口在开发时是比较难定义好的。

**二是模块之间相互依赖，难以调试和验证**。你调我、我调你，相互调用——调试时发现我这个模块好像出了问题，那到底是我模块本身的问题，还是我调用的那个东西的问题，还是我调了它、它又调了我之后才产生的问题？这就导致调试和验证比较困难。相比之下，分层结构其实也是一种模块化的设计思想（每一层就是一个模块），但分层结构的模块之间有清晰的单向依赖关系——高层调用更低一层，所以分层结构调试起来显然更容易一些。

### 外核：把未经抽象的硬件资源直接分给进程

最后一种操作系统结构叫**外核**，这种结构非常少见。它的系统由**内核**和**外核**两部分组成：应用程序可以通过系统提供的库函数去调用普通内核的功能，也可以通过库直接去调用外核提供的功能。

分工是这样的：**内核**只负责进程调度、进程通信等等这些功能；**外核**负责为用户进程分配**未经抽象的硬件资源**，比如磁盘的存储空间、内存的存储空间——这些硬件资源都由外核来负责管理，内核只管进程调度、进程通信这些和硬件资源分配回收无关的工作。

什么叫"给用户进程分配未经抽象的硬件资源"？对比一下普通操作系统就明白了。在普通的操作系统当中，用户进程想申请一片内存空间，系统给它分配的是**经过抽象、经过虚拟化**的内存：用户进程自己看到的视角，似乎是自己拥有一整片连续的内存空间，但事实上那只是**虚拟的地址空间**，操作系统内核会把这些虚拟页面映射到实际的物理页框当中，而这些物理页框在内存当中通常是离散的。外存也一样：进程觉得自己的文件好像是连续的一个地址空间，但事实上文件的各个块在磁盘当中很有可能是被离散存放的。

外核不同——它直接给用户进程分配未经抽象的硬件资源。这种资源管理策略在有的时候非常有用：

- **磁盘的例子**：一个用户进程很可能知道自己的这片存储空间是需要经常**随机访问**的——一会儿访问 A 这个地方，一会儿访问 B 这些地方。在普通操作系统里，用户进程的文件在外存中到底被零散地分布到哪些位置，完全由操作系统决定，用户进程自己控制不了；如果分配到的磁盘空间是离散的这一块、那一块，进程随机访问自己文件块的时候，磁头就需要来回横跳，随机访问的性能就低了。而采用外核策略，进程知道自己这个文件需要频繁被随机访问，就可以向外核申请分配一整片连续的磁盘块——比如从 0 号块到 1024 号块全部都是我的——文件数据直接存放到这几个连续的磁盘块里，之后随机访问文件里的任何一块，磁头移动的距离就会变少，性能就提升了。
- **内存的例子**：在采用外核的操作系统里，一个应用程序完全可以向外核申请分配连续的一整片**物理**内存空间——从 A 到 B 这个地址都是我的地盘。外核给进程分配的这片内存区域是未经抽象的，用户进程看到的就是一片实实在在的物理地址空间，而不是虚拟的、经过抽象的地址空间。

外核除了分配、回收这些未经抽象的硬件资源之外，还需要负责**保证这些硬件资源的使用安全**。比如 A 到 B 这个空间已经分配给了某个进程，那么另一个进程 P2 想访问这片区域，外核就需要及时发现并且制止；反过来，原本的那个进程如果要去访问 A 和 B 之外的其他空间，这个行为也应该被外核发现并制止。

优点和缺点总结一下。由于给用户进程分配的是不虚拟、不抽象的硬件资源，用户进程在使用这些资源时就可以**更灵活**；同时这种分配方法**减少了虚拟硬件资源的映射层**，提升了效率——普通操作系统给进程分配的是虚拟内存，进程访问自己的地址空间时只能提供虚拟地址，操作系统需要去查页表、甚至查二级三级页表，通过多次访存才能把虚拟地址转换成实际的物理地址，这个映射过程是有时间代价的，会降低系统的整体效率；而外核直接给进程分配的就是 A 到 B 这片区域，只要进程访问的物理空间在 A 到 B 之内，直接访问就行了，不需要操作系统帮你做地址映射，效率自然提升。

缺点是**降低了系统的一致性**：在这种系统当中，有的进程 P1 申请的可能还是虚拟地址空间，系统还要帮它映射；有的进程 P2 申请的可能就是物理地址空间，操作系统不需要帮它映射。给各个进程分配内存、外存的策略，以及后续的管理，都需要考虑到各种各样的情况——系统因此变得更加复杂。

### 开机那一刻：磁盘里和引导有关的数据

最后我们学习操作系统的引导。你可能刚看见这个词的时候会觉得莫名其妙、不明觉厉——什么是操作系统的引导？简单来说：**当你开机的时候，如何让操作系统在你的电脑上运行起来**，这就是操作系统引导做的事情。

为了解释清楚这个问题，我们先看看磁盘里有哪些和引导相关的数据。

如果你花钱买了一个新磁盘，它的内部刚开始就像你的钱包一样，空空的。作为计算机专业的同学，我们都应该有能力把一个新磁盘安装到电脑主板上，然后就可以在这个磁盘里安装操作系统了。安装完之后，磁盘里大概长这样：

```text
 ┌──────────────────────────────────────────────────┐
 │ 主引导记录 MBR：磁盘引导程序 + 分区表             │ ← 磁盘开头留出的区域
 ├──────────────────────────────────────────────────┤
 │ C 盘（活动分区：装了操作系统，并用它启动）        │
 │   ├ 引导记录 PBR                                 │
 │   ├ 根目录（双击打开 C 盘看见的文件夹和文件）     │
 │   └ 其他内容                                     │
 ├──────────────────────────────────────────────────┤
 │  D 盘   │   E 盘   │   F 盘   │   ……             │
 └──────────────────────────────────────────────────┘
```

后面的 C、D、E、F 盘你应该很熟悉，操作系统就安装在 C 盘里。除了这些看得见的分区之外，磁盘的**开头**位置会留出一片区域，用于存储**主引导记录**（MBR）。这里边主要包含两个重要的东西：

- **磁盘引导程序**——它有什么用，马上就知道了；
- **分区表**——顾名思义就是一个数据结构，说明了磁盘当中每个分区分别占多大的空间，以及每个分区的地址范围。

再看 C 盘内部。C 盘安装了操作系统，并且会使用 C 盘来启动操作系统——这种情况下，我们就把 C 盘称为这个磁盘的**活动分区**。把 C 盘内部进一步细分，有两个比较特别的部分：一是一片用于存储**引导记录**的区域（英文缩写 PBR），它的用处稍后解释；二是**根目录**相关的数据——根目录就是你双击打开 C 盘之后看见的那些东西，里面有文件夹也有文件。除了这两个部分，其他内容暂时不解释。

### 操作系统引导的四个步骤

操作系统要启动，操作系统的数据肯定需要被放到**主存**里。这里补充一个知识：计算机的主存由 **RAM** 和 **ROM** 两部分组成。我们平时说手机内存多少、电脑内存多少，通常说的是 RAM；除此之外还有 ROM 芯片，它被集成在电脑主板上，里面存储的是 **BIOS**——基本输入输出系统。BIOS 由一系列程序组成，其中最重要的一个程序就是 **ROM 引导程序**，又可以称为**自举程序**。

RAM 芯片里的数据一断电就被清空了，但 ROM 芯片里的数据不会因为断电而丢失。这就意味着：当我们开机、CPU 一旦通上电，CPU 就可以去主存当中**固定的位置**找到这个 ROM 引导程序，然后一条一条往后执行它里面的指令。接下来的过程环环相扣：

```text
CPU 通电
  → 从主存固定位置取指令，执行 ROM 中的 ROM 引导程序（自举程序）
       └─ 通常先进行硬件自检：有没有插磁盘、有没有插内存条……
          所有硬件都没问题之后，才进行下一步
  → 读入磁盘的第一块（主引导记录 MBR），执行其中的磁盘引导程序
       └─ 根据分区表找到活动分区（C 盘）的位置
  → 读入并执行活动分区的第一部分：引导记录 PBR（本质上也是一个程序）
       └─ 它负责从根目录下找到启动管理器（操作系统初始化程序）
  → 执行启动管理器，完成操作系统初始化的一系列工作，开机完成
```

按步骤说：

- **第一步**：CPU 首先从一个特定的主存地址开始取指令——因为 ROM 引导程序存储在某个固定不变的位置。从这个位置开始一条一条往后执行，这些指令就是 ROM 引导程序。它通常会先进行**硬件自检**，检查有没有插磁盘、有没有插内存条等等，所有硬件都没问题之后才进行下一步。
- **第二步**：把磁盘当中的第一块——也就是主引导记录 MBR——读入内存，同时执行这个磁盘引导程序，并且**扫描分区表**，找到活动分区（也就是安装了操作系统的分区）。
- **第三步**：只要找到了活动分区的起始地址，接下来就可以读入活动分区第一部分的内容，也就是引导记录 PBR，把它读入内存之后执行里面的程序。这个程序完成的事情，是从根目录下面找到完整的**操作系统初始化程序**——也就是我们刚才提到的启动管理器，它通常存放在根目录下的某个位置。
- **第四步**：执行这个操作系统初始化程序，就可以完成一系列开机的动作。

最后拓展一个小东西：如果你用的是 Windows 操作系统，可以去找一下你的 C 盘，下面应该有一个 `Windows` 文件夹，再在这个下面找到一个 `boot` 文件夹——这个文件夹下面的东西，就是我们刚才说的操作系统初始化程序相关的那些内容。所以第四步本质上就是要从 C 盘的根目录出发，找到操作系统初始化程序，再运行这一系列程序，从而完成开机的动作。大家开机的时候看见电脑在转圈圈、显示"正在启动"，看见那个画面的时候，背后执行的就是这些东西。

有兴趣的同学可以自己去翻一下你的电脑——学了理论，再结合实践去看一下这些东西，可以让你的记忆更牢固，也会让你对一门学科更有兴趣。

## 虚拟机与进程初识
> 对应块：BLK04 | 覆盖分集：P11-P12 | 块标题（分集名）：《1.6_虚拟机》

### 一台物理机只能装一个操作系统的烦恼

先来看传统的计算机：一台物理机器上只能运行一个操作系统，操作系统之上再运行各种各样的用户进程。这看起来似乎很合理，但在有的商业环境当中，这会导致硬件资源利用率不充分的问题。

比如你拥有一台性能非常强大的物理机，想把它租给其他人使用。由于这台机器上只能运行一个操作系统，那么所有人的东西都只能在同一个操作系统之上运行——王者荣耀的游戏服务器和吃鸡的游戏服务器，就必须放在同一个操作系统之上来运行。但两个进程在同一个操作系统之上，是不是有可能会有安全隐患？他们之间可能相互影响，也会相互争夺操作系统管理的资源。所以在商业环境当中，让两个应用同时跑在一个操作系统上，可能造成隐患。

一种解决方法是把其中一个应用迁移到另一台物理机器上，各自有独立的操作系统，这样两个应用就不可能相互影响了。但这又会导致物理机器硬件资源的极大浪费——很多商业级物理机的性能很强，我的硬件本来可以同时支持你们两个进程绰绰有余，但为了安全起见，我又不得不把其中一个进程迁移到另一台机器上去运行。

所以传统的这种结构会带来很多应用上的限制。于是就有人发明了虚拟机（Virtual Machine，缩写 VM）：使用**虚拟化技术**，把一台物理机器虚拟化为多台虚拟机器，每一台虚拟机器上都可以独立地运行一个操作系统。

> **定义**：虚拟机管理程序（Virtual Machine Monitor，缩写 VMM）负责把一台物理机器虚拟化为多台虚拟机器。也有人称它为 Hypervisor，中文翻译为虚拟机监控程序——虚拟机管理程序、虚拟机监控程序、VMM、Hypervisor 这些术语都是一个意思，后文统一用"虚拟机管理程序"。

### 虚拟机管理程序的两类实现

#### 第一类：直接运行在硬件之上

第一类虚拟机管理程序直接运行在硬件之上，由它把一个物理机器虚拟化为多台虚拟机器，把一个总的硬件资源划分为多个部分，分别给各个虚拟机使用。每一台虚拟机器上面可以安装各自的操作系统——比如第一台虚拟机上装 Windows，第二台上装 Linux，第三台上又装 Windows；每一个操作系统之上又可以运行各自的用户进程。

```text
+-----------------------------------------------------------+
|   VM1        |   VM2        |   VM3                       |
|   Windows    |   Linux      |   Windows                   |
|   用户进程    |   用户进程    |   用户进程                   |
+--------------+--------------+-----------------------------+
|        虚拟机管理程序（VMM，唯一运行在内核态）                 |
+-----------------------------------------------------------+
|                          硬件                               |
+-----------------------------------------------------------+
```

读图：虚拟机管理程序夹在硬件和所有虚拟机之间，向上把硬件切成多份，各虚拟机互不知情，都以为自己独占一台机器。

这里可以简单说一下怎么把硬件资源分配给各个虚拟机器。比如一个单核的 CPU，它也可以模拟多台虚拟机器——只需要把这个 CPU 的时间片进行划分，给每个虚拟机器分配若干个时间片。这样在上层的操作系统看来，似乎给自己分配的就是一个独立的 CPU，但事实上只是把这个物理 CPU 的某些时间片分配给它了而已。磁盘和内存的分配更不用说了：把磁盘空间划分出来、内存空间划分出来，分配给各个虚拟机器，每个虚拟机器就都拥有了各自独立的硬件资源。

这有点类似传统计算机当中操作系统对硬件资源的划分：CPU 按时间划分为时间片，内存、磁盘这些划分为不同的空间，分配给各个进程，每个进程也就拥有了"自己独立的资源"。所以第一类虚拟机管理程序就有点类似我们传统的操作系统——直接管理硬件资源、分配硬件资源，**这只是一层更深的套娃而已**。

这里有一个值得注意的点：**只有虚拟机管理程序是运行在内核态的**，只有它可以执行特权最高的那些指令；而上层的操作系统和应用程序，实际上都运行在用户态。

> **易错点**：上层的操作系统可不知道自己运行在用户态——它以为自己运行在内核态，所以它依然会使用一些特权指令。但它又不能真的用特权指令，怎么办？

当上层操作系统想要使用特权指令的时候，这个行为动作会被虚拟机管理程序截获，由它负责把这条特权指令做等价的转换，模拟出"这条指令执行成功了"的那种感觉。所以我们说上层操作系统运行在**虚拟内核空间**——它并不是真正的内核空间，实际上是用户空间，只不过它自己以为自己运行在内核空间而已。

#### 第二类：运行在宿主操作系统之上

第二类虚拟机管理程序不是直接运行在硬件上的，而是运行在一个**宿主操作系统**（Host OS）上。比如在我的 Mac 电脑上装了 macOS，我可以在这台电脑上安装第二类虚拟机管理程序——很多同学可能听过 VirtualBox 或者 VMware，这是国内学生比较常用的两款，我电脑上装的就是 VirtualBox。

装好之后，我就可以去下载另一个操作系统的镜像文件，比如我在 VirtualBox 上装了一个 Linux 操作系统，并且可以指定给它分配多大的内存、多大的磁盘空间。接下来我就可以点"启动"，在我的 Mac 电脑上套娃启动一个 Linux 操作系统。如果我愿意，也可以再装一个 Windows 客户操作系统，只要我的硬件资源足够，我可以在宿主操作系统之上同时启动多个客户操作系统（当然也可以只启动一个）。

```text
+-----------------------------------------------------------+
| 客户操作系统 1（Linux） | 客户操作系统 2（Windows）          |
+-----------------------------------------------------------+
|      虚拟机管理程序（如 VirtualBox / VMware）               |
+-----------------------------------------------------------+
|  宿主操作系统（如 macOS）+ 录课用的 PPT 等日常进程            |
+-----------------------------------------------------------+
|                          硬件                              |
+-----------------------------------------------------------+
```

读图：第二类虚拟机管理程序夹在宿主操作系统和客户操作系统之间，它自己也是宿主操作系统之上的一个"程序"。

我平时录课用的就是这种结构：电脑上运行着 PPT 相关的进程，同时也可以启动客户操作系统让它正常工作。客户操作系统启动了之后就跟正常的操作系统一样，我可以在上面安装软件、正常运行。有时录课想给大家演示 Windows 操作系统的一些情况，我就启动一个 Windows 虚拟机，在上面装些 Windows 应用程序来演示。

关键区别在于：这个虚拟机管理程序想要给各个虚拟机器分配硬件资源，**只能请求宿主操作系统给它分配**——硬件资源的管理者依然是宿主操作系统。

#### 两类管理程序的差异对比

两类虚拟机管理程序思想各不相同，实现方式的不同也就造成了一些特性上的差异。

| 对比项 | 第一类虚拟机管理程序 | 第二类虚拟机管理程序 |
| :--- | :--- | :--- |
| 物理资源控制权 | 直接运行在硬件之上，直接控制和分配物理资源 | 运行在宿主操作系统之上，只能向宿主操作系统申请、由其分配 |
| 分配的资源形态 | 可以把未经抽象的物理资源直接分配给虚拟机 | 拿到的是宿主操作系统抽象后的虚拟资源，再转手"二次虚拟" |
| 性能 | 更好，地址映射层次少 | 更差，总要通过宿主操作系统作为中介，多层映射 |
| 同等硬件可支持的虚拟机数量 | 更多，它拥有全部硬件资源 | 更少，宿主操作系统及其进程也要消耗资源 |
| 虚拟机可迁移性 | 迁移动作比较麻烦 | 非常方便，导出镜像拷走即可 |
| 商业化应用 | —— | 目前更广泛，使用起来灵活 |
| 运行模式 | 运行在最高特权级（零环） | 一部分运行在用户态，一部分以驱动程序形式运行在内核态 |

逐项展开说一下。

**资源分配方式的差异。** 第一类虚拟机管理程序在安装客户操作系统时，会直接在原本的硬盘上划分一些存储空间分配给它——比如我把 0 号块到 1024 号块全部分配给第一台虚拟机 VM1，把 1025 号块到 2048 号块全部分配给第二台 VM2。它可以直接把未经抽象的物理资源分给上层虚拟机。相比之下，第二类虚拟机管理程序向宿主操作系统申请物理资源时，拿到的是**经过抽象**的资源。比如它想给第一台虚拟机分配 10 GB 的磁盘空间，那么它会向宿主操作系统申请创建一个大小为 10 GB 的大文件——这个大文件具体存放在磁盘的哪些位置，由宿主操作系统决定。虚拟机管理程序拿到这 10 GB 的大文件后，再把它分配给第一台虚拟机，让虚拟机以为自己拥有了 10 GB 的磁盘，但这只是一个虚拟磁盘，这 10 GB 在磁盘当中未必连续，背后就是宿主操作系统文件系统里的一个大文件而已。

内存的分配同理：第二类虚拟机管理程序向操作系统请求分配一片内存，宿主操作系统给了它 4 GB——但这是 4 GB 的**虚拟内存**，各个页面也许是离散存储的。它拿到这 4 GB 后又可以拆分，比如给第一台虚拟机分 2 GB、第二台也分 2 GB。它就是这么干的：多增加了一层套娃，它本身得到的已经是虚拟的硬件资源，然后又把这个虚拟的硬件资源再虚拟。

**性能差异。** 显然第一类虚拟机管理程序性能更好。因为每进行一次硬件的虚拟化，就意味着上层操作系统在使用这些硬件资源时，地址需要先映射为虚拟机管理程序获得的虚拟地址空间，宿主操作系统又需要把这个虚拟地址空间再映射到实际的物理地址空间。经过了多层虚拟，就意味着使用资源时要经过多层映射才能对应到最终的物理地址——所以第二类虚拟机管理程序性能更差，总是需要通过宿主操作系统作为中介。

**支持虚拟机数量的差异。** 在一台机器的硬件资源固定不变的情况下，第一类往往可以支持更多台虚拟机，因为它拥有所有的硬件资源；第二类的资源需要向宿主操作系统申请，而宿主操作系统本身需要硬件资源，它上面的那些进程也需要使用硬件资源，所以同等硬件下第一类能支持更多虚拟机。

**可迁移性差异。** 第一类迁移虚拟机比较麻烦；第二类非常方便。比如我要把我的 Linux 客户操作系统给你用，只需要把它导出为 ISO 镜像文件，你把这个镜像拷过去，在你自己的 VirtualBox 上一加载、一安装，就能用到跟我这边完全一样的操作系统——包括我在客户操作系统上安装的程序、数据什么的都可以一起打包给你。正因为可迁移性好，第二类虚拟机管理程序的商业化应用目前更广泛一些。

**运行模式差异。** 第一类虚拟机管理程序运行在最高的特权级别，可以使用最高特权的指令。以前介绍指令的时候，我们只是把指令分为非特权指令和特权指令两个特权级别，但近几年的 CPU 当中，指令的特权级可能被划分为更多层次——比如零级、一级、二级、三级，越往上特权级越低，越往下特权级越高。所谓第一类虚拟机管理程序运行在"零环"（Ring 0），指的就是它运行在最高的特权级别。

把指令划分为更多特权级是有好处的。如果指令只分为非特权和特权两级，那么任何一条特权指令的使用，都需要虚拟机管理程序截获、判断这条指令的使用是否合法，合法的话还要由它模拟出执行效果。但如果进行更精细的分类——让第一类虚拟机管理程序运行在最高特权级零环，让客户操作系统的内核运行在一环（次高特权级），让用户进程运行在二环（最低特权级）——那么当上层客户操作系统使用一环、二环的指令时，虚拟机管理程序不用管，直接让它执行就行了；只有用到少数零环指令时才检查该不该让它执行、会不会不安全。这相当于把原本的特权指令进一步细分：把特权指令当中的一些**敏感指令**放在零环，不敏感的放在一环，虚拟机管理程序就不用检查每一条特权指令，只需要检查某些敏感指令的执行就可以了。

第二类虚拟机管理程序则是一部分运行在用户态、一部分运行在内核态——运行在内核态的部分，是以**虚拟机驱动程序**的方式加载到宿主操作系统内核当中的。举个例子：上层应用程序发出系统调用（比如 write），上层操作系统可以直接去读写磁盘吗？显然不可以。所以用户进程的系统调用会被虚拟机管理程序截获，由它进行处理，代替上层操作系统向底层的宿主操作系统发出 write 系统调用，请求宿主操作系统的服务。

所以无论怎么看，第二类虚拟机管理程序的性能肯定都更差一些——宿主操作系统总是要作为一个工具人、作为中介来被使用。

> **提示**：虚拟机是第一章最后一个考点，重点理解两类虚拟机管理程序的结构即可，大概率以选择题方式考察。而且不负责任地预测一下：肯定会考第一类和第二类虚拟机管理程序的区别，所以上面那个对比表是一个非常有可能出现的命题角度。

### 进程：正在运行的程序到底是什么

从这一节开始我们正式进入第二章处理机管理的内容。先来认识一个很重要的概念——进程。第一章里我们经常说"系统中正在运行的程序怎么怎么地"，偶尔也提到进程这个术语；对很多跨考的同学来说，进程和程序这两个概念其实比较容易混淆，不易理解。

#### 先看三个 QQ 进程

按照去年同学们的反馈，这个地方如果直接抛出文字性的描述，很多跨考的非科班同学会比较难理解，所以我们换一种更贴近生活经验的方式来讲。

在 Windows 电脑里打开任务管理器，就能看到此时系统当中正在运行的进程。此时如果我想要使用 QQ，我打开 QQ 程序，QQ 就开始运行，相应地在"进程"这一栏里会看到一个和 QQ 相关的条目。而如果我想要同时登录两个甚至三个 QQ 号，我可以再打开两次 QQ 程序——这时候会发现进程这一栏里 QQ 相关的条目出现了三条，也就是说系统当中此时有三个 QQ 进程正在运行。这三次我打开的都是同一个 QQ.exe 这个程序，但这个程序的三次执行会对应三个不同的进程。大家如果电脑就在身边，可以自己动手验证一下。

于是进程和程序的区别就出来了：

> **定义**：程序是静态的、存放在磁盘里的可执行文件（Windows 里就是 QQ.exe 这样的文件），它其实就是一系列指令的集合；进程是动态的，是程序的一次**执行过程**。即使是同一个程序，多次执行，每一次执行都会对应一个不同的进程。

#### PID：进程的身份证号

问题来了：既然这三个进程执行的都是同一个程序，操作系统在背后要怎么区分它们呢？总不能把三个都叫做"腾讯 QQ 进程"。为了解决这个问题，操作系统在创建一个进程的时候，会给它分配一个唯一的、不重复的 ID，叫做 PID（Process ID，进程 ID）。

> **定义**：PID 就是进程的身份证号。就像我们每个人的身份证号都是唯一不重复的一样，每个进程的 PID 也是唯一不重复的。

还是看一个直观的例子。我录视频用的是苹果电脑，macOS 上有一个叫"活动监视器"的小工具，和 Windows 的任务管理器其实是一样的。在它的进程列表里可以看到 PID 这一列，让进程按 PID 递减排列，可以看到各个进程的 PID 都不重复。此时我打开一个叫做 toro 的应用程序，注意观察：出现了和它相对应的进程，PID 是 2641。然后我把这个应用程序退出，再一次打开——有没有发现 PID 变成了 2642？

这就很好地说明了一个问题：每一次新建一个进程，都会分配一个不重复的唯一 ID。在很多操作系统当中，PID 的分配用的就是"每次加一"这样一个很简单的策略。可以看到系统在背后又自己创建了一个新进程——虽然我不知道这个进程是干嘛的，但它的 PID 依然是递增的。回到刚才的图：虽然那些进程的名称都叫"腾讯 QQ（32 位）"，但它们背后都有各自的 PID，肯定不重复。

#### 操作系统还在记什么账

细心的同学可能会发现，除了 PID 之外，操作系统还会记录各个进程的其他信息：比如它使用了多久的 CPU 时间、它是由哪个用户创建的（用户 ID，简称 UID）、各个进程对内存的使用信息（比如某个进程使用了 745.7 MB 的内存），另外还会统计各个进程对磁盘的访问情况（比如某个进程向磁盘写入了 3.45 GB 的数据，而其他进程读写的数据量少得多），还有最后一列列出的各个进程对网络流量的使用情况。

这些信息在进程管理当中都是很有必要的。比如那个经常往磁盘里写数据的进程，它肯定是一个需要经常访问磁盘的进程，操作系统管理这些进程的时候，就可以根据它们各自的特性制定相应的策略。

归纳一下操作系统记录的这些信息：

- **进程描述信息**：PID、UID 等，用来区分各个进程；
- **资源分配情况**：分配了多少内存、正在使用哪些 I/O 设备、正在使用哪些文件，帮助操作系统实现对系统资源的管理；
- **进程控制和管理相关信息**：CPU 使用时间、磁盘使用情况、网络流量使用情况等，帮助操作系统实现对进程的控制和调度等一系列管理策略。

既然操作系统在背后要记录这么多信息，这些信息都会被统一地放在一个叫做 **PCB** 的数据结构当中——英文是 Process Control Block，进程控制块。

> **定义**：PCB 是进程存在的**唯一标志**。当进程被创建时，操作系统会为它创建相应的 PCB；当进程结束时，操作系统就会回收它的 PCB。但凡操作系统管理进程所需要用到的信息，都放在 PCB 当中。

#### 去 Linux 源码里看一眼 PCB

接下来让大家看一个令人脑壳疼的东西。我在网上找到了 Linux 的内核源码，在 `sched.h` 这个文件当中，可以看到 Linux 操作系统里定义的 PCB 长什么样子——在 Linux 当中，PCB 的名字叫做 `task_struct`。有兴趣的同学可以去 Linux 官网下载源码来看这个文件。

在这个 `task_struct` 里会记录各种各样的信息。比如 `state` 字段记录进程当前的状态——是处于就绪态、运行态还是阻塞态等等（进程状态是下一个小节会展开介绍的内容）；再看 `files` 字段，记录的是当前进程打开了哪些文件；还有一个 `io_context` 字段，记录的是 I/O 管理当中所需要使用的信息。这个数据结构里定义了好多好多字段，光是这个数据结构的定义就写了 1900 多行代码，这么多代码是很让人抓狂的一个事情。

总之，我们想要认识 PCB 当中的所有字段是不可能的，只需要知道：**PCB 当中存放的都是操作系统在对进程进行管理时所需要的那些信息**。

除了进程描述、控制管理、资源分配这三类刚才都已经介绍过的信息之外，PCB 中还会保留**处理机相关的信息**——只有在 PCB 中保存了处理机相关的信息，才可以实现进程的切换。这个坑我们先留着，之后再填。

#### 进程实体：PCB、程序段和数据段

除了 PCB 之外，进程还有两个很重要的组成部分：程序段和数据段。刚才说过，PCB 是给操作系统用的数据结构，而程序段和数据段其实是给进程自己用的。

我们具体来看一个例子。第一章学过，程序在运行之前需要编译成二进制的机器指令，程序执行的过程就是 CPU 一条一条执行这些指令的过程。把这件事再细化一下：写完一个程序之后，经过编译链接等一系列步骤，最终会形成一个可执行文件（Windows 里就是 .exe 文件），平时存放在硬盘当中，里面保存的就是那一系列指令序列。当程序要运行之前，需要把它从硬盘读入到内存当中，并且操作系统会建立与之相对应的进程——根据刚才的分析，它会建立相对应的 PCB。

除了 PCB 之外，程序的那一系列指令序列也读入了内存，这一系列指令序列我们就称为**程序段**。进程执行的过程，就是 CPU 从内存中读入这些一条一条的指令、然后执行它们。而在执行指令的过程中还会有一些中间数据——比如我们定义了一个变量 x——这些变量的内容也需要放在内存当中，所以还有另外一个叫做**数据段**的区域，用来存放程序运行过程中所产生、所需要使用的各种数据，比如我们定义了哪些变量，这些信息就放在数据段里。

> **定义**：进程实体（也叫进程映像）由 PCB、程序段和数据段三个部分组成。PCB 是给管理者（操作系统）使用的；程序段和数据段里的内容是给进程自己使用的，和进程自己的运行逻辑有关。

这里要抠一个字眼：我们之前一直在说"进程由哪些部分组成"，但更严格地说，应该说**进程实体（进程映像）**由 PCB、程序段和数据段组成。进程是动态的，进程实体是静态的——可以把进程实体理解为进程在动态执行过程中某一时刻的一个快照、一张照片，它能反映进程在某一时刻的状态。比如进程运行过程当中 x 的值本来是 1，执行了自增操作之后 x 就变成 2 了，所以在进程的运行过程中，进程实体是不断变化的。不过除非题目特别考察进程和进程实体（进程映像）的区别，不然大家也可以认为所谓的进程就是进程实体，没必要钻这个牛角尖。

由此可以给出进程的严格定义：

> **定义**：进程是进程实体的运行过程，是系统进行资源分配和调度的独立单位。

进程是**资源分配**的独立单位，这一点很好理解——从活动监视器就可以看到，操作系统是以进程为单位给各个进程分配资源（比如内存）的。这里还涉及另一个概念——**进程的调度**：所谓调度，就是操作系统决定让哪个进程上 CPU 运行，调度相关的内容会在之后的小节进一步学习。

再回到三个 QQ 的例子。一个程序运行多次会对应多个进程，同时挂三个 QQ 号，那么这三个 QQ 进程的 PCB 和数据段都是各不相同的——PCB 不相同很好理解；数据段不相同，是因为三个 QQ 号的账号信息数据都存放在数据段当中。但这三个 QQ 进程背后运行的是相同的 QQ 程序，所以它们的**程序段内容其实是相同的**。

绕来绕去耗费了不少时间，对于很多科班出身的同学来说可能觉得讲得太啰嗦，但根据同学们的反馈，这些内容确实是跨考的同学比较难理解的，所以花这些时间是值得的。

#### 进程的五个特征

相比于程序，进程拥有以下几个特征：

- **动态性**：进程是程序（进程实体）的一次执行过程，它是动态地产生、变化和消亡的。动态性很好理解，它也是进程**最基本**的特性。
- **并发性**：内存当中同时会有多个进程实体，各个进程可以并发执行。经过第一章的学习，这一点也很好理解。
- **独立性**：进程能够独立运行、独立获得资源、独立接受调度。
- **异步性**：各个并发运行的进程以各自独立的、不可预知的速度向前推进。进程并发带来的异步性可能会让进程的执行结果不确定，但有时我们又必须让并发执行的进程相互配合协调工作——具体怎么实现，会在进程同步的小节当中学习，这里先不展开。
- **结构性**：每个进程都由一个 PCB、一段程序段、一段数据段构成。

这些特性大家都只需要理解，不需要死记硬背。

最后有两个需要注意的点：第一，进程的动态性是它最基本的特性；第二，进程是**独立获得资源、独立接受调度**的基本单位——之所以要专门强调这一点，是因为在引入了线程之后，进程就不再是接受调度的基本单位了，但进程依然是获得资源的基本单位。这一点还会经过后续的小节进一步讲解，暂时先不展开。

## 进程的一生：五种状态与一套"一气呵成"的控制术
> 对应块：BLK05 | 覆盖分集：P13-P14 | 块标题（分集名）：《2.1.3_进程的状态与转换》

程序平时就是躺在硬盘里的一个可执行文件，它想跑起来，得先被调入内存，操作系统再为它建立相应的 PCB——到此为止，一个进程才算诞生。但进程被创建出来之后，它的一生并不是一直"运行"到底的：它会等待、会被打断、会最终消亡。这一讲我们就把进程一生中经历的各种状态、状态之间怎么转换、操作系统又是用什么手段保证这些转换不出差错，一次性讲透。

### 从硬盘到 CPU：进程的五副面孔

先顺着上小节的故事往下走。程序被调入内存、操作系统为它建立 PCB 之后，进程并没有立刻上 CPU，它首先要经历一个"正在被创建"的阶段。

**创建态**：当一个进程正在被创建的期间，它就处于创建态。这个阶段操作系统要做两件大事——给进程分配所需的系统资源（比如分配内存空间），以及完成对 PCB 的初始化工作。

创建完毕，进程进入**就绪态**。处于就绪态的进程其实已经具备了运行的条件，只不过此时 CPU 比较忙、还没空闲下来，所以 CPU 暂时不能为它服务。一个系统中可能会同时存在很多很多个就绪态的进程，大家都在排队等 CPU。

等 CPU 空闲了，操作系统就从这一堆就绪进程中挑一个让它上 CPU 运行。此时这个进程就处于**运行态**——意味着 CPU 正在处理这个进程背后的程序，也就是正在执行这个进程对应的那条指令序列。

接下来是关键的一幕。假设正在运行的进程二执行到它的指令三时，发出一个系统调用，请求操作系统给它分配打印机资源。可此时打印机很忙，正在为别的进程服务，资源暂时分配不了。那进程二下一条指令——往打印机输出数据——就没办法往下执行了。既然接下来的指令暂时执行不了，我们显然不应该让这个进程一直霸占着 CPU。像这种情况非常普遍：进程在运行过程中会主动请求等待某个事件的发生——可能是等系统分配某种资源，也可能是等待其他进程的响应等等。在事件发生之前，进程没办法继续往下执行，所以操作系统就会剥夺它对 CPU 的使用权，让它下 CPU，并进入一个新状态：**阻塞态**。也就是说，这个进程因为等待某个事件而被阻塞了。

CPU 再次空闲后，操作系统又选一道就绪进程上 CPU。故事继续：之前忙碌的打印机服务结束了，空闲下来，于是操作系统可以把打印机分配给当初请求它的进程二。等待的事件一旦发生，进程二就再次拥有了上处理机运行的条件，于是它从阻塞态**回到就绪态**——注意，是回到就绪态，而不是直接杀回运行态，它还得重新排队等调度。

再看生命周期的终点。假设正在运行的进程一运行结束了，它会发出一个叫做 `exit` 的系统调用，请求操作系统终止自己。此时进程进入**终止态**：操作系统让它下 CPU，然后做一系列善后工作——回收这个进程占有的各种资源（内存空间、打印机设备等等，总之所有资源都要回收），并且最后回收它的 PCB。这些终止工作全部完成之后，这个进程就从系统中彻底消失了。

### 状态转换图：哪些是主动的，哪些是被动的

用一张图把刚才的五个状态和它们之间的转换串起来：

```text
        创建完成             被调度选中                 运行结束(exit) /
 创建态 ────────> 就绪态 ────────> 运行态 ────────────────> 终止态
                   ^    ^           │       或遇到不可修复错误(如整数除以零)
                   │    └─ 时间片到 ─┤
                   │                │ 请求等待某个事件（主动）
                   │                v
                   │             阻塞态
                   └─ 等待的事件发生（被动）
```

读图说明：创建态创建完成后进入就绪态；就绪进程被操作系统调度后上 CPU 进入运行态；运行中的进程要么主动请求等待某个事件转入阻塞态，要么因时间片用完回到就绪态，要么因运行结束或出错进入终止态；阻塞态的进程在等待的事件发生后被动地回到就绪态。

这几个转换里藏着两组重要的"主动性"分析，也是选择题爱挖的坑。

**运行态 → 阻塞态，是进程自身的主动选择。**一般来说都是进程通过系统调用的方式申请某种系统资源，或者请求等待某个事件的发生——是它自己主动请求的。

**阻塞态 → 就绪态，却是进程控制不了的。**一个进程在等打印机，那打印机什么时候分配给它，可不是这个进程说了算的。所以这个转换是一种被动的行为。

由这两条还能推出两个"不可能"，这是非常经典的考点：

> **易错点**：一个进程不可能直接从阻塞态转换成运行态，也不可能直接从就绪态转换成阻塞态。道理很简单——进程要变成阻塞态，肯定需要它主动发出请求；而要发出主动请求，它就必须正在 CPU 上运行。所以只可能从运行态转换成阻塞态，不可能从就绪态直接跳进阻塞态。

还有一个刚才没提到的转换：**运行态可以直接回到就绪态**。比如操作系统给进程分配的时间片用完了的时候。什么叫时间片用完？还记得第一章提过的时钟中断吗——一个进程本来在处理机上运行得好好的，CPU 突然收到一个时钟中断信号，发现这个进程已经运行了很长时间、不应该让它继续执行下去了，这就是时间片到、时间片用完。此时进程被剥夺 CPU 的使用权，从运行态回到就绪态。注意它和阻塞态的区别：这种情况下进程**仍然拥有继续往下执行的条件**，它只是被剥夺了处理机而已，并不需要再等待处理机之外的其他事件。

再看一遍五个状态各自"缺什么"，转换关系就全通了：就绪态的进程**只差处理机**这一种资源，其他资源都齐了；运行态的进程则是其他资源齐、处理机也有；阻塞态的进程除了处理机之外，还在等别的资源或事件。

### 五状态模型的几个要点

上面这套就是经典的**进程五状态模型**——去年有同学管它叫"丁字裤模型"，确实很形象。

五个状态里，**运行态、就绪态、阻塞态是基本状态**，因为进程在整个生命周期中大部分时间都处在这三种状态里；创建态和终止态只是两个短暂的过渡阶段。

还有两点要强调：

1. **单 CPU 环境下，处于运行态的进程同一时刻最多只有一个。**如果是多核 CPU，多个进程可以并行运行，那就可能有多个进程同时处于运行态。
2. **注意各状态的别名**：阻塞态又叫等待态，创建态又叫新建态，终止态又叫结束态。考试换个叫法别认不出来。

### PCB 怎么记状态，进程怎么排队

那么操作系统怎么记录进程的状态呢？上小节提过，PCB 当中有一个变量 `state`，就是用来表示进程当前状态的——比如用不同的数字编号代表各种状态。另外，操作系统还会把处于**同一个状态**的各个进程的 PCB 有规律地组织起来，方便统一管理。"怎么组织各个进程的 PCB"这个问题，就是**进程的组织**要探讨的内容。

组织方式有两种：**链式方式**和**索引方式**。

链式方式是指操作系统管理一系列的队列，每个队列的指针指向相应状态的那些进程的 PCB：

```text
 执行指针 ────────> [运行态进程的 PCB]

 就绪队列指针 ────> [PCB] ──> [PCB] ──> [PCB] ──> NULL
                    （优先级更高的进程的 PCB 排在队头）

 等待打印机队列 ──> [PCB] ──> [PCB] ──> NULL
 等待磁盘队列   ──> [PCB] ──> NULL
```

读图说明：执行指针指向运行态进程的 PCB；就绪队列指针指向所有就绪进程的 PCB 组成的队列；阻塞队列按等待原因分成多个，等打印机的归等打印机的队列，等磁盘的归等磁盘的队列。

两个细节：为了方便调度，操作系统经常把**优先级更高的进程的 PCB 放在就绪队列的队头**；而很多操作系统还会**根据阻塞原因的不同把阻塞队列分成多个**——因为等待打印机而阻塞的进程挂在等待打印机的队列里，等待磁盘的挂在等待磁盘的队列里，事件到来时按队列对症唤醒，效率更高。

索引方式则是给各种状态的进程建立相应的**索引表**，索引表的每个表项指向相应的一个 PCB：

```text
 索引表                       PCB
 就绪态索引表: [表项1]──> PCB   [表项2]──> PCB   [表项3]──> PCB
 阻塞态索引表: [表项1]──> PCB   [表项2]──> PCB
```

读图说明：每种状态一张索引表，表项里存放对应 PCB 的地址（或指针）。

索引方式看图就懂了。但要知道，**大多数操作系统实际使用的是链式方式**，所以索引方式有个简要了解就够了。进程组织这块大家稍微有个印象即可；这一讲更值得注意的还是进程的状态、以及状态之间的转换——这是考研最高频的考点部分，希望大家主动通过课后习题再对这部分内容巩固和理解。

### 进程控制：为什么必须"一气呵成"

下一小节讲**进程控制**。王道书上给的定义是：进程控制的主要功能是对系统中的所有进程实施有效的管理，它具有创建新进程、撤销已有进程、实现进程状态转换等功能。

说白了，**进程控制就是要实现进程的状态转换**。创建一个新进程，不就是让一个进程从无到有、到创建态再到就绪态吗？撤销一个已有进程，不就是让进程进入终止态、最终把它干掉的过程吗？那么问题来了：在进程状态转换的时候，操作系统具体需要做些什么？为什么这件事还必须"一气呵成"地做？

先回答"怎么做到一气呵成"：要用**原语**来实现。原语这个概念第一章出现过——操作系统内核中有一种特殊的程序叫原语，它的执行具有**原子性**，也就是说运行必须一气呵成，中间不可以被中断。

再回答"为什么必须一气呵成"。回忆一下：PCB 中有个变量 `state` 表示进程当前的状态，假设 `state` 为 1 表示就绪态、为 2 表示阻塞态。那么一个 `state = 1` 的进程，它的 PCB 肯定要挂在**就绪队列**里；`state = 2` 的进程，PCB 就应该挂在**阻塞队列**里。也就是说，PCB 里的状态变量和 PCB 所处的队列，这两份信息必须始终对得上。

现在考虑：阻塞队列里的进程二（PCB 2）等待的事件发生了，它应该从阻塞态转换为就绪态。这个转换至少要做两件事——**第一**，把 PCB 中的 `state` 变量从 2 改为 1；**第二**，把 PCB 2 从阻塞队列中摘出去，挂到就绪队列当中。

关键来了：假设操作系统刚把 `state` 改成 1，突然检测到一个中断信号，系统必须转去处理中断。就在这个瞬间——从 `state` 变量看，这个进程是就绪态；可从它所处的队列看，PCB 2 还在阻塞队列里。**两份关键信息对不上了。**这些数据结构非常重要，这种不一致可能会影响操作系统后续的其他工作，甚至让系统出错。

> **结论**：进程的状态转换（也就是进程控制）如果中间不能一气呵成，就可能出现关键数据结构信息不统一的情况。所以状态转换必须一气呵成——而原语这种特殊内核程序恰好具有一气呵成、不可被中断的美好性质，我们就用它来实现进程控制。

### 原语的原子性从哪来：关中断与开中断

那原语凭什么能一气呵成不被中断呢？靠的是两条特权指令：**关中断**和**开中断**。

回忆第一章：CPU 每执行完一条指令之后，都会**例行检查**是否有中断信号需要处理。如果发现中断信号，CPU 就暂停当前程序，转去执行中断处理程序，处理完再回来继续往下执行。这就是平时的行为模式。

现在看关中断怎么改变这一切：

```text
 CPU:  指令一  指令二  [关中断]  指令a  指令b  ...  [开中断]  恢复例行检查
                        │                                      │
                        │  期间即使有中断信号到来也不理会，        │
                        │  继续往下执行 —— 一气呵成               │
                        └──────────────────────────────────────┘
                                                    执行完开中断后，
                                                    才处理积压的中断信号，
                                                    转向中断处理程序
```

读图说明：执行了关中断这条特权指令之后，CPU 不再例行检查中断信号；直到执行了开中断指令，才恢复"每执行完一条指令就检查中断"的习惯，这时才会发现之前积压的中断信号并转去处理。关中断与开中断之间的这一系列指令，执行必然不可被中断——原子性就是这样实现的。

那么思考一个问题：这两条指令能不能开放给普通用户程序使用？显然不能。想象一下，如果允许用户程序用，那我完全可以在自己程序的开头就植入一条关中断指令，一直到程序末尾才执行开中断指令——只要我的程序上了 CPU，它就会一直霸占着 CPU 不被中断。这种情况是绝对不应该让它发生的。

> **结论**：关中断和开中断是**特权指令**，只允许内核程序使用，不允许普通用户程序使用。

到目前为止两条主线都通了：第一，进程控制必须一气呵成，用原语实现；第二，原语的原子性靠关中断、开中断两条特权指令配合完成。接下来就看进程控制相关的各个原语，背后具体干了些什么。

### 五个控制原语各自做什么

#### 创建原语：从无到就绪

操作系统要创建一个进程，就必须使用**创建原语**。它做四件事：

1. **申请一个空白 PCB**——PCB 是进程存在的唯一标志，要创建进程当然得先有与之对应的 PCB；
2. **给进程分配所需的资源**，比如内存空间；
3. **初始化 PCB**，比如分配 PID、设置 UID；
4. **把 PCB 插入就绪队列**——到此，创建原语让进程从创建态进入了就绪态。

有哪些典型事件会引起创建进程？一是**用户登录**时，操作系统会建立与之对应的用户管理进程或用户通信进程等；二是发生**作业调度**时——根据去年的反馈，很多同学不知道作业到底是什么。其实作业就是此刻还放在外存里、还没有投入运行的程序；所谓作业调度，就是从外存中挑选一个程序放入内存让它开始运行，而程序要开始运行肯定需要创建对应的进程，所以要用到创建原语。三是某个进程向操作系统提出请求，系统专门建立一个进程来处理这个请求；四是一个进程主动请求创建一个**子进程**。

#### 撤销原语：让进程彻底完蛋

终止一个进程时使用**撤销原语**，使用之后进程从原有状态转向终止态，最终从系统中彻底消失。它要做的事：

1. **找到这个进程的 PCB**；
2. 如果它此时正在运行，**立即剥夺它的 CPU 使用权**，把 CPU 分配给其他进程；
3. **杀死它的所有子进程**；
4. 把这个进程占有的资源**归还给它的父进程**；
5. 最后**把 PCB 从系统中删除**——到这一步，这个进程就彻底完蛋了。

这里冒出了父进程、子进程的概念，我们用一个很实际的例子来理解。我录这期视频用的电脑上，进程管理界面就是以父子关系的方式显示正在运行的进程的：可以看到一个 PID 为 0 的进程，它是最祖先的**祖先进程**；祖先进程创建了一个 PID 为 1 的进程，叫做 launch，它其实就是第三章会学到的**装入程序（装入进程）**——开机之后我们启动的所有其他进程，其实都是这个装入进程启动的，所以它们都是装入进程的子进程。除了它之外，其他进程也可以创建自己的子进程来完成一系列工作，比如访达这个进程就创建了自己的几个子进程。

这种设计有什么好处？可以想一下：系统刚启动时，几乎所有的资源都是最祖先的那个进程所拥有的——比如我这台电脑 8GB 的内存，全部归它。之后它在建立自己的子进程时，可以按照子进程的需要把手头的资源分配下去：本来手里有 8GB 内存，把其中 50MB 分给这个进程、54.5MB 分给那个进程；而当这些子进程终止之后，它们再把自己手里的资源**还给父进程**。所以操作系统中各个进程之间的关系，其实是一种**树形结构**：0 号进程和 1 号进程是最祖先的两个进程，它们各自创建子进程，各个进程又可以再创建自己的子进程。当然这并不是操作系统这门课的考察重点，讲它是为了帮大家更深入地理解"杀死所有子进程""资源归还父进程"这两个特性——不是为了把大家绕晕。

哪些事件会引起进程终止？一是进程**自己请求终止**，也就是使用 `exit` 系统调用，此时操作系统在背后就会用撤销原语把进程撤销掉；二是进程做了**非法事件**，比如整数除以零、非法使用特权指令，会被操作系统强行撤销、强行干掉；三是**外界干预**——比如用 Windows 电脑时经常遇到卡死，很多同学喜欢用那套熟悉的快捷方式打开任务管理器，结束掉某个卡死的进程，这就是典型的外界干预。

#### 阻塞原语与唤醒原语：必须成对使用

有时一个进程会从运行态进入阻塞态，这时操作系统就在背后执行**阻塞原语**。阻塞一个进程要做的事情比较简单：找到对应的 PCB；**保护进程运行的现场**——什么叫保护现场，这是个比较庞大的话题，一会儿细说；把 PCB 中的状态信息设置为阻塞态；让进程下处理机，并把它插入相应的等待（阻塞）队列。

反过来，当进程等待的事件发生了，它就会被唤醒——操作系统让它的状态从阻塞态回到就绪态，这时要用**唤醒原语**：找到它的 PCB；把 PCB 从等待队列中移除；设置为就绪态；把 PCB 插入就绪队列，等待被调度。

> **易错点**：一个进程因为什么事情被阻塞，就应该被什么事情唤醒，所以**阻塞原语和唤醒原语必须成对使用**。

这一小节内容确实比较多，可能听到这你已经比较疲惫了，但这些原语到底要干什么，**不需要死记硬背**——考试不可能让你默写这些东西，着重理解背后的过程就可以。

#### 切换原语：一上一下换人

最后一个原语叫**切换原语**。它让当前处于运行态的进程下处理机、回到就绪队列，并从就绪队列中选一个就绪进程上处理器运行——所以切换原语会让**两个**进程的状态发生改变。

它要做的事：把进程的运行环境信息存入 PCB；把下处理机进程的 PCB 移到相应的队列（比如就绪队列）；挑选一个进程上处理器运行，并更新它的 PCB 内容；同时从这个新上场的进程的 PCB 当中，恢复它所需要的运行环境。

什么叫"保存运行环境"、什么叫"恢复运行环境"？这是最难理解的地方，我们得深入探讨一下。

### 寄存器与 x++：到底什么叫"运行环境"

之前我们认识的是：程序运行之前要把指令放入内存，CPU 从内存中一条一条读取指令并执行。现在要拓展一个更深层的细节——CPU 执行指令的过程中需要进行一系列运算，所以 CPU 当中设置了很多**寄存器**，用来存放指令、存放程序运行过程中需要的某些数据。总之，寄存器就是 CPU 里边用于存放数据的地方。

这门课需要稍微了解的寄存器有这几类：

- **PSW**（程序状态字寄存器）：CPU 的状态——是内核态还是用户态——就保存在 PSW 当中；除此之外它还保存别的信息，那是计算机组成原理要学的内容，这里不展开。
- **PC**（程序计数器寄存器）：存放接下来需要执行的那条指令的地址。
- **IR**（指令寄存器）：存放当前 CPU 正在执行的那一条指令。
- **通用寄存器**：存放其他一些必要的信息。

现在来分析一段指令序列在背后发生了什么。我这里胡乱写了四条指令，它们合起来完成一件事：定义一个变量 x，并实现 x 自增。执行过程如下表：

| 指令 | 它让 CPU 干什么 | 执行后的效果 |
| :---: | :--- | :--- |
| 指令一 | 向内存某个位置写入变量 x 的值 | 内存中 x = 1 |
| 指令二 | 从内存取出 x 的值，放进某个通用寄存器 | 通用寄存器 = 1 |
| 指令三 | 把通用寄存器里的值加一 | 通用寄存器 = 2 |
| 指令四 | 把寄存器的内容写回 x 存放的位置 | 内存中 x = 2 |

假设 CPU 正在执行指令一：它会把指令一的内容读到 IR 中，同时 PC 中存放着接下来该执行的指令二**的地址**。CPU 解析指令一，发现它要往内存某处写入变量 x 的值，于是写入 1。执行完指令一，CPU 从 PC 中知道下一条要执行的是指令二，于是取出指令二放进 IR，PC 的内容更新为再下一条指令的地址。执行指令二：CPU 从内存取出 x 的值放进通用寄存器，寄存器变成 1。接着取指令三进 IR、PC 再次更新；指令三让寄存器里的数据加一，于是通用寄存器从 1 变成 2。最后执行指令四：把通用寄存器的内容写回 x 存放的位置，内存中的 x 就从 1 变成了 2。

可以看到，执行一次 x 自增，背后是 CPU 执行了一系列更基本的指令。而且注意一个要命的细节：这些指令顺序执行的过程中，**很多中间结果放在寄存器里**——x 自增做到一半时，加好了的 2 其实只在通用寄存器里，还没写回内存。

但寄存器并不是这个进程独属的！如果其他进程上 CPU 运行，这些寄存器同样会被别的进程使用。会发生什么？把这个故事从头捋一遍：CPU 依次执行指令一、二、三，执行到指令三之后，寄存器里的值已经是 2。此时如果切换到另一个进程——另一个进程也要用这些寄存器，很可能就把前一个进程保留在寄存器里的中间结果**覆盖掉**。中间结果没了，前一个进程即使重新上 CPU 也没法再往下执行了。

解决办法：当一个进程要下处理机时，把它运行环境的信息**保存在自己的 PCB 当中**。当然并不需要把所有寄存器都存下来，只保存必要的信息即可——比如 PSW、PC、通用寄存器。保存了运行环境之后，才可以切换别的进程；别的进程随便往寄存器里写什么数据都无所谓。等之前那个进程重新回到 CPU 运行时，操作系统根据 PCB 中保存的信息**恢复它的运行环境**：恢复之后，CPU 知道接下来要执行的是指令四、通用寄存器里是 2，于是按 PC 的指向把指令四取进 IR、让 PC 指向下一条指令，解析发现指令四是把寄存器内容写回 x 的位置——执行，把 2 写回，x 自增这个操作才算真正完成。

> **定义**：所谓进程的运行环境，也叫**进程上下文**，就是进程在运行过程中寄存器里存储的那些中间结果。进程下处理机时把运行环境存入自己的 PCB，重新上 CPU 时从 PCB 恢复运行环境、继续往下执行。

**保存运行环境、恢复运行环境，是实现进程并发执行的关键技术。**

补一句给跨考和不考计算机组成原理的同学：这一段扯了不少底层硬件的知识，学过计组的同学可能觉得都很好理解，但我们不得不照顾到跨考的同学。在操作系统这门课里，硬件相关知识**不需要深究**，提它们只是为了帮大家理解某些关键的操作系统概念——毕竟操作系统是最接近硬件的一层软件嘛。

### 万变不离其宗：所有原语都在做三件事

这一小节干货确实多，收个尾。注意原语这个概念：它靠**关中断和开中断**实现执行必须一气呵成、不可中断；之后介绍的各个控制原语各自做了各自的事情——但这些都不需要死记硬背。其实无论是哪一个控制原语，它所做的无非就是三件事：

1. **更新 PCB 中的信息**——主要是修改进程的状态（也就是 `state` 那个变量），或者往 PCB 中保存运行环境、从 PCB 恢复运行环境；
2. **把 PCB 插入合适的队列**；
3. 像**进程创建和进程终止**这样的场合，还可能需要分配和回收进程的资源。

了解了这些控制原语背后做的事情，能帮我们更好地理解进程管理、处理机管理这一系列知识。所以虽然这一小节看起来内容很多，但更多都是理解性的东西，大家不需要花时间去记忆，不要惊慌。

## 进程通信：两个进程之间怎么传数据
> 对应块：BLK06 | 覆盖分集：P15 | 块标题（分集名）：《2.1.5_1 进程通信》

### 一个"分享链接"引发的通信

你刷微博的时候刷到一篇某明星的八卦吃瓜文，想把它分享给微信好友。不用复制粘贴，直接用微博应用内置的分享功能，一点，这篇文章的链接就到了微信那边。这个过程看似平平无奇，其实背后已经发生了一次进程之间的通信——本来吃瓜文的链接挂微博这个进程这儿，通过分享功能，它跑到了微信那个进程里。两个或多个进程之间产生了数据交互，这就叫进程之间的通信。

一个系统当中可能同时存在多个进程，它们都在运行，难免需要相互配合着工作，所以进程和进程之间的数据通信就显得很有必要了。那问题来了：进程之间的通信应该如何实现？答案是需要操作系统的支持。

> **定义**：进程通信（进程间通信），指的就是两个或多个进程之间产生数据交互。

### 为什么通信必须由操作系统插手

要探究这个问题，首先得聊清楚一件事：为什么进程之间的通信一定要有操作系统内核的支持？

原因在于，系统给各个进程分配内存地址空间的时候，各个进程的地址空间是**相互独立**的。进程 P 可以访问自己的空间，进程 Q 可以访问自己的空间，但是 P 不可以访问 Q 的地址空间——无论读还是写，都不行。

这么规定是出于安全的考虑。你想一下，如果一个进程可以随意访问其他进程的内存地址空间，那它是不是就可以随意修改、随意读取别的进程的数据了？比如说你手机里不知道什么时候装了个垃圾软件，如果它随便就能访问其他进程的地址空间，那它可能直接就把你微信里的私密聊天数据、私密照片给偷走了。这显然很危险。

```text
进程 P 的地址空间                进程 Q 的地址空间
+-----------------+             +-----------------+
|   只能访问自己   |   X 读 / 写  |   只能访问自己   |
+-----------------+             +-----------------+
        两个进程互相都碰不到对方的空间
```

正因为进程不可以直接访问其他进程的空间，进程 P 想把数据传给 Q，就不可能直接把数据写到 Q 的那片空间里去。这个"传不过去"的墙，只有操作系统有能力打通——所以进程间的通信必须要有操作系统的支持才能完成。

操作系统支持的通信方式有三种：**共享存储**、**消息传递**、**管道通信**。下面一种一种来看。

### 共享存储：划一块大家都能碰的内存

各个进程只能访问自己的那片空间，但如果操作系统支持共享存储这种功能，那么一个进程可以申请一片**共享存储区**，这片区域也可以被其他进程共享。这样，进程 P 要给 Q 传数据，就先把数据写到这片共享存储区里——因为它对这片区域有访问权限——然后进程 Q 再从这片区域里把数据读出来，数据交换就完成了。

```text
进程 P 的地址空间          共享存储区           进程 Q 的地址空间
+--------------+         +----------+         +--------------+
|              | --写--> |          | --读--> |              |
+--------------+         +----------+         +--------------+
              由操作系统划出，被多个进程共同映射
```

Linux 里怎么实现？进程 P 和 Q 想要通信，发起通信的进程 P 可以使用 `shm_open` 这个系统调用来申请一片共享内存区；接下来 P 和 Q 都需要使用 `mmap` 这个系统调用，把这片存储区域**映射到自己的虚拟地址空间**当中。

现在大家还不知道什么叫虚拟地址空间，等学到第三章再回头看这部分会更清晰。如果用第三章要学的内容来解释：调用了 `mmap` 之后，进程的页表项（或段表项）就会增加一项，这个页面或这个段就可以映射到刚才申请的那片共享存储区。总之，只需要简单地加一个页表项或段表项，就可以完成共享内存区的映射，非常简单。这样，各个进程的虚拟地址空间当中就都包含了这片共享存储区，它们都可以访问它。

#### 访问必须互斥

还有一个问题要注意：如果多个进程都往这片区域写数据，是不是有可能导致写冲突？比如 P 正在往这片区域写，Q 也往这片写，就可能发生数据覆盖。

所以各个进程使用共享存储方式通信时，需要保证对共享存储区的访问是**互斥**的——当 P 正在访问这片区域的时候，其他进程就不能访问。

那互斥怎么实现？操作系统内核会提供一些同步互斥工具，比如 2.3 节要学的 PV 操作。各个进程可以用类似 PV 操作这样的机制，来实现对共享存储区的互斥访问，这部分等学了 2.3 再回来理解会更好。这里先留个伏笔：对共享存储区的访问，本质上是一个**读者写者问题**——多个进程可以同时从这片区域读，但不可以同时往这片区域写——这是 2.3 节里一个经典的同步互斥问题。

> **易错点**：共享存储方式下，互斥访问要由**通信的进程自己**负责实现（借助操作系统提供的同步互斥机制，比如 PV 操作）。这一点和后面管道通信"互斥由操作系统保证"形成鲜明对比。

#### 基于存储区的共享 vs 基于数据结构的共享

刚才说的这种方案，是基于**存储区**的共享：操作系统给你划定了这么大一片区域——比如整片 4 KB——至于写进程到底要往这块写还是往那块写、读进程要从哪里读，这些都很自由。操作系统只负责把这片区域划给你，**并不管你怎么使用**。数据怎么存、存在什么位置，都由要通信的进程们自己决定。所以这种共享方式灵活性非常高，传送数据的速度很快，是一种**高级通信方式**。

相比之下，还有一种基于**数据结构**的共享。比如操作系统给你们两个进程划定的共享区域，规定只能存放一个长度为十的数组。大家可以把它理解为一个"特殊的全局变量"——之所以叫特殊，是因为我们平时写代码定义的全局变量是局部于一个进程的，而这里所谓的特殊全局变量可以被各个进程所共享。

但是当我们定义这个全局变量的时候，比如说定义了一个 `int a[3]`，那各个进程共享这个数据结构时，对这个区域的读写就只能按照这个数据结构规定的格式来进行：只有三个 int 型的变量，每次要么读、要么写一个 int 型的变量，自由度就没那么高了，传送数据的速度也比较慢。所以基于数据结构的共享是一种**低级的通信方式**。

| 对比维度 | 基于数据结构的共享 | 基于存储区的共享 |
| :---: | :--- | :--- |
| 共享内容的形态 | 规定好格式（如一个长度为十的数组） | 一整片区域，只划不管 |
| 读写自由度 | 只能按数据结构的格式访问 | 存哪、读哪完全由进程自己定 |
| 速度 | 慢 | 快 |
| 定位 | 低级通信方式 | 高级通信方式 |

### 消息传递：以格式化消息为单位

第二种方式叫消息传递。采用这种方式时，进程之间的数据交换会以**格式化的消息**为单位，通过操作系统提供的**发送原语**和**接收原语**这两个原语来进行。

什么叫格式化的消息？它由两个部分组成：

```text
+--------------------------+------------------------------+
|         消息头            |           消息体              |
|  发送者是谁、接收者是谁、  |   进程要传送给另一个进程的     |
|  消息长度是多少等概要信息  |        具体数据               |
+--------------------------+------------------------------+
```

消息头要注明：这一整坨消息到底是由谁发送的、要发送给谁、整个消息的长度是多少等等，就是一些概要信息；消息体里放的就是具体要传的数据。

消息传递又可以进一步划分为**直接通信方式**和**间接通信方式**。

#### 直接通信方式：点名道姓

直接通信方式就是发送进程要指明接收进程的 ID——系统里每个进程都有一个进程 ID（PID），发送的进程需要指明到底是谁来接收。相当于我发送进程直接点名：我就是要他接收。

来看一遍完整的流程。故事是这样的：进程 P 要给进程 Q 发一个消息。

第一步，P 在自己的地盘——自己的地址空间里——完善这个消息的信息，包括消息头和消息体。

第二步，P 使用操作系统提供的发送原语 `send`，指明我的这个 message 是要发送给 Q 这个进程的。这个发送原语会导致操作系统内核接收到这个消息，并且把它挂到进程 Q 的**消息队列**里边。操作系统的内核区域管理着各个进程的 PCB（进程控制块），Q 的 PCB 当中就包含一个消息队列，其他进程发送给 Q、应该被 Q 接收的消息，都挂在这个队列里。也就是说，这个消息从进程 P 的用户空间被复制到了内核空间。

第三步，如果进程 Q 开始运行，它可以使用接收原语 `receive`，指明我要接收一个 message，而且是接收 P 进程发来的 message——接收时也要指明消息来自哪个进程。Q 执行接收原语之后，操作系统内核会检查 Q 的消息队列，看哪个消息是 P 发过来的；找到了，内核就把这个消息体的数据从内核区复制到进程 Q 的用户区。

```text
进程 P（用户空间）        操作系统内核            进程 Q（用户空间）
+--------------+  send(Q, message)  +-------------+  receive(P)   +--------------+
| 组装消息头+体 | ----复制(挂接)--> | Q 的 PCB     | ----复制----> | 取走消息体数据 |
+--------------+                    |  - 消息队列   |               +--------------+
                                    +-------------+
```

所以所谓直接通信方式，就是要**点名道姓**地进行消息传递：发送方指明我到底要传给谁，接收方指明我要接收的是来自谁的消息。

#### 间接通信方式：经过信箱

间接通信方式要通过一个叫**信箱**的中间实体来进行消息的传递，所以又称为**信箱通信方式**。

具体是这样实现的：比如进程 P 和 Q 要通信，P 可以通过系统调用申请一个邮箱——比如申请一个叫 A 的邮箱，当然也可以申请多个，比如另一个叫 B。

现在两个进程怎么通信？进程 P 首先在自己的地址空间里完善消息体的内容。这个过程大家理解吗？其实就相当于你写进程 P 的代码时定义了一个变量 message，然后给它赋一个值——所谓"在自己的地址空间内完善消息"，就是一个赋值而已。

然后 P 用发送原语 `send`，指明我要发送到**哪个信箱**：发送到 A 信箱，发送的是 message 这个消息体。注意，这里指明的是我要发送到 A 信箱，**并没有指明我要发送给哪个进程**——这是和直接通信方式最关键的区别。直接通信方式是点名道姓指明要发给 Q 这个进程，而间接通信方式只是指明要发送到 A 这个邮箱。

进程 Q 使用接收原语的时候，指明我要从 A 这个信箱接收一个 message。这样，信箱 A 里的这个消息就会被操作系统复制到进程 Q 自己的空间里。

通常来说，操作系统是允许多个进程往同一个信箱里发消息的，也允许多个进程从同一个信箱里接收消息。

### 管道通信：一根单向的水管

最后一种方式叫管道通信。"管道"这个词很形象，它就像我们的水管：写进程可以从水管的一边写入数据，读进程从水管的另一边取走数据，而且这个数据的流动只能是**单向**的——就像水管里的水流，要么从左到右，要么从右到左。大家见过一个水管里的水既往右流、同时又往左流吗？没有见过这样的水管，对吧。所以管道通信的数据流向只能是单向的，不可以双向同时进行。

站在操作系统的层面，管道是一种**特殊的共享文件**，又叫 pipe 文件（pipe 就是英文里"水管"的意思）。两个进程要用管道通信，首先需要某个进程通过系统调用来申请一个管道文件，操作系统会新建这个管道文件。这个文件的本质，其实就是在**内存中开辟了一个大小固定的内存缓冲区**，然后两个进程可以往这个缓冲区里写数据和读数据，但读写是**先进先出**的。

#### 管道和共享内存到底差在哪

去年有很多同学在这里有疑问：一个管道文件本质上是一个大小固定的内存区域，这不跟共享内存没什么区别了吗？共享内存也是操作系统给两个进程 P 和 Q 分配一片可以被共享访问的内存区域，而管道也是一片大小固定、可以被 P 和 Q 访问的内存区域，区别在哪？

区别在这：共享内存的方式下，这片内存区域你想怎么玩就怎么玩——想把数据写在这儿、写在这儿、写在这儿都 OK，想从这儿读、从那儿读也都 OK，**没有任何限制**，很自由。

但管道通信是**数据流**的形式。这个区域大小有限，P 往里写的时候，如果头部是空的，就先往头部写一个字节，然后挨着往后写、再往后写；Q 要取走数据的时候，并不是想读哪儿就读哪儿，它只能先把头部的数据取了，再依次往后取。写数据时前面还有空位，数据肯定先放在前面的位置，只有前面填满了，才会继续往后面写；读数据时也是一样，只能先把前面的数据读空了，才可以读后续的数据。

```text
  写入数据                                 读取数据
 写进程 --------> +----------------------+ --------> 读进程
                 | 头 ● ● ● ● ● ○ ○ ○ 尾 |
                 +----------------------+
                   先进先出，写满尾部、读空头部
```

所以管道通信的读写一定是先进先出的，就是一个队列嘛。更准确地讲，应该把这个管道的内存缓冲区理解为一个**循环队列**——现在大家应该都学过数据结构了，循环队列的原理我们知道：如果整片区域的后半部分写满了，但前面这些位置空出来了，那 P 就可以往循环队列另一头空着的地方继续写入数据。

总结一下这组对比：共享内存没有任何读写位置的限制；管道是先进先出这种限制，读写都要遵循队列的规则。

#### 半双工：想要双向就修两根管

刚才提过，一个管道的数据流向一定是单向的。所以一个管道只能支持**半双工通信**——某一段时间内只能实现单向的传输。半双工指的就是同一时刻只能支持单向传输，但这个方向的传输结束之后，可以把传输的方向改过来，只是两个方向的传输不可以同时进行。

如果两个进程需要同时互传数据——你要给我传，同时我也要给你传，两个方向的数据传输都要同时进行——这叫**全双工通信**。这种情况下，就需要向操作系统申请**两个管道文件**：一个负责从左往右的数据传输，另一个负责从右往左。就像现实中想要两个方向的水流同时存在，就得建两根水管。

#### 读写什么时候会阻塞

关于管道还有三个要点。

第一，各个进程对管道的访问也应该是互斥进行的。但注意，对管道的互斥访问是**由操作系统来保证的**，不需要由进程自己来保证——这和共享存储方式正好相反。

第二，管道是大小固定的内存缓冲区，既然大小固定，这片缓冲区肯定会被写满。写满之后，写进程就不能继续往里面写数据了。所以**如果管道被写满，写进程应该被阻塞**，等待读进程把管道里的数据取走、管道有空位了，再把写进程唤醒。反过来看读这边，数据有可能被读空，**如果管道被读空，读进程的 read 动作就应该被阻塞**，直到写进程往管道里写入数据，才把读进程唤醒。所以管道通信这种方式，不管是读进程还是写进程，都有可能进入阻塞状态。

第三，也是管道通信这个部分很多教材最有争议的一个点：管道的实现方式决定了，管道里的数据**一旦被读出，就彻底消失了**。而管道里的数据并没有指明"我到底是给进程 Q 的还是要给进程 M 的"，所以如果有多个读进程同时读一个管道，就有可能导致错乱——第一块数据可能被 M 读走了，第二块数据可能被 Q 读走了，读取的次序会很乱。

针对这个问题，不同的操作系统有不同的解决方案。比如早期的 System V 操作系统在实现管道时，就规定一个管道**允许多个写进程**同时往里写，但**读进程只允许有一个**。2014 年那道 408 真题，高等教育出版社的官方答案也是这么说的：一个管道可以有多个写进程、一个读进程。但在有的操作系统当中，比如 Linux，又允许有多个写进程和多个读进程，只不过系统会让各个读进程**轮流**从管道当中读数据——你读一次我读一次，由操作系统来控制这个轮流读的过程。所以很多操作系统的教材里你会看到"一个管道可以被多个进程写、多个进程读"的说法，而另一些教材又会说"允许多个进程写、但只允许一个进程读"，前年和去年这个地方争议非常大，很多同学不知道该信谁。

> **结论**：实际情况是，一个管道确实可以允许多个写进程和多个读进程。但我们最终要面对考试，应试考试得有所谓的标准答案，以后讨论管道通信时，统一和高教社 2014 年真题的说法一致：**可以有多个写进程，只能有一个读进程**。做题时如果看到"一个管道可以有多个写进程、多个读进程"的说法，也不要觉得奇怪——从现实应用的角度看，这种说法并没有什么错误。

### 一个写在王道书上的错误

最后再跟大家说一个王道书上的小问题。这个小问题也是前年和去年让无数人抓狂、不知道它说的对不对的一个地方。今年我查阅了大量资料，并且自己也在 Linux 操作系统上做了管道通信的实验，现在我可以告诉大家一个很笃定的答案。

王道书里有这样一句话：写进程会先把管道缓冲区给写满，然后才让读进程读；当缓冲区中还有数据时，写进程不会往缓冲区里写数据。

这句话是**错误的**。它读起来就像是说：一个管道必须全部写满之后，读进程才可以把数据取走。但事实上不是这样。我在 Linux 上做了实验验证了这个问题：当写进程往管道里写数据的时候，即便管道没有被写满，也可以被读进程读走。读进程能读只有一个条件——**管道别空**。只要管道没空，读进程就可以继续从管道里读数据。对写进程也是一样的：我不管管道有没有被读空，反正只要管道**没满**、还有空间可以让我写，我就可以继续往管道里写数据。

所以大家把王道书上这句话修改一下，那段话是说的有问题的。

### 三种方式放在一起看

这一讲介绍了共享存储、消息传递和管道通信这三种常见的进程间通信方式。这三种通信功能都需要操作系统的底层来支持：

- **共享存储**：操作系统分配一个共享内存区域，并把它映射到各个进程的虚拟地址空间当中（学到第三章知道什么是段表、页表之后，再回来看就会恍然大悟——把一片内存区域映射进进程的虚拟地址空间，只需要加一个段表项就能做到，非常简单）。互斥访问需要各个通信进程自己负责实现，比如使用 PV 操作等同步互斥机制，本质上是一个读者写者问题。
- **消息传递**：以格式化消息（消息头 + 消息体）为单位，通过 send / receive 原语交换数据。直接通信方式点名道姓指明收发双方，操作系统把消息直接挂到接收进程的消息队列里；间接通信方式又叫信箱通信方式，消息先被操作系统放到指定信箱当中，接收者也要指明自己从哪个信箱取消息。
- **管道通信**：对操作系统而言，管道是一个特殊的共享文件——你在 Linux 里采用管道通信的话，是可以在系统里找到这个文件的——但本质上它就是一个内存缓冲区。结合数据结构的知识来看，这个内存缓冲区就是一个循环队列：写满了写进程阻塞，读空了读进程阻塞。一个管道文件只能实现半双工通信，想要双向同时传输，就需要两个管道，就像一根水管里的水不可能既往左流又往右流。

> **承前启后**：上一节讲完「进程通信：两个进程之间怎么传数据」，下一节接着讲「信号与线程：从事件通知到更细粒度的并发」。

## 信号与线程：从事件通知到更细粒度的并发
> 对应块：BLK07 | 覆盖分集：P16-P18 | 块标题（分集名）：《2.1.5_2 信号》

先说一个很容易踩的坑：这一讲的主角叫"信号"，它和我们之前学过的"信号量"长得非常像，但他们俩是完全不同的两个东西。信号量的英文术语叫 semaphore，信号的英文术语叫 signal。信号量主要用于实现进程之间的同步互斥，而信号这种机制主要用于实现进程间的通信。

信号还是 2025 届考研大纲新增的考点，所以值得专门花一讲的工夫。这一讲我们会按这样的顺序展开：先看信号的作用，并认识几个 Linux 定义的具体信号；然后看信号是如何发送、如何保存的；再看进程收到信号后，在什么时机、用什么方式去处理；最后探讨一个疑难点——信号和异常有什么关系。讲完信号，我们会进入线程的世界：为什么要引入线程、线程带来哪些变化、线程有哪些属性、线程的两种实现方式，以及三种多线程模型。

### 信号的作用：通知进程"某件事发生了"

考研大纲把信号归为进程间的一种通信方式。我们可以用信号这种机制通知某个进程：某个特定的事件已经发生了。进程收到这个信号之后，就需要对它进行相应的处理——具体怎么处理，后面展开。

Linux 操作系统定义了 30 种信号类型，课件上罗列的是符合 POSIX 标准的那 30 种；事实上除了这 30 种，Linux 还定义了更多的信号。这张表不用怕，我们简单了解即可。表格的每一行对应一种具体的信号：每个信号有一个序号（编号），还有一个信号名。不同的操作系统对信号类型的定义是不一样的，比如早期的 UNIX 操作系统只定义了 19 种信号，不过原理和 Linux 类似——每种信号都有自己专属的序号，并且有一个信号名。

> **定义**：所谓信号名，本质就是一个宏定义的常量。比如 SIGINT 对应序号 2，在 Linux 内核代码里这个信号名就是用一个宏定义实现的——一个信号名的背后，对应的是这个信号的序号。

当某些特定事件发生的时候，就会触发一个信号。举两个例子：

- 在 Linux 的小黑框（终端）里正在运行一个程序，这时我们按下 `Ctrl+C`，这个动作就会触发一个信号，使得操作系统内核向正在运行的进程发送一个 SIGINT 信号。SIGINT 默认的处理方式就是终止当前进程。
- 如果程序里有个 bug，发生了除以零这样的算术异常，这个事件会导致内核向正在运行的进程发送 SIGFPE 信号。FPE 是 floating point exception（浮点异常）的缩写。进程收到 8 号这个信号后，默认的处理是终止当前进程，并且**转储内存**——所谓转储内存，就是把这个出现浮点异常的进程的内存数据存储到硬盘里。这一点大家是有体会的：当你正在使用的软件突然崩溃，那些崩溃信息其实就被存储到硬盘里了。

总之，当某些特定事件发生时，可以向相关的进程发送一个对应的信号，通知它"这个事件发生了"。对 Linux 有兴趣的同学可以研究一下那张完整的信号表，它引用自《深入理解计算机系统》，而那本书又套娃引用了一个网站，有兴趣可以顺藤摸瓜看看。

### 信号的发送与保存：PCB 里的两个位向量

了解了信号的作用，接下来看它的实现原理——信号是怎么发送的，收到之后又是怎么保存的。

每个进程有一个对应的 PCB（进程控制块），PCB 当中有这样两个**位向量**：一个叫 pending，意思是"待处理"；一个叫 blocked，对应"被阻塞"。

> **定义**：pending 位向量记录当前有哪些待处理的信号；blocked 位向量记录哪些信号被阻塞（屏蔽）。blocked 位向量也可以称为**信号掩码**。

假设某个操作系统总共定义了八种信号，用序号 1~8 对应，那么这个系统就需要用八个比特的位向量来表示当前待处理的信号，同样用八个比特表示被阻塞的信号。一个进程具体要屏蔽哪几种信号，是可以通过系统调用自行设置的。

#### 谁能给谁发信号

最常用、最灵活的发送信号的系统调用函数是 kill 函数。它有两个参数：第一个参数指明 PID，也就是"我的这个信号要发给谁"；第二个参数是一个 int 型的值，表示信号的序号。

来看一个具体的例子。假设进程 P1 的 PID 是 2666，那么两个用户进程和一个内核进程都可以调用 kill 函数给它发信号：进程 P2 调用 kill，指明要给 2666 这个进程发送 1 号信号；进程 P3 指明要给 2666 发送 8 号信号；内核进程也指明要给 2666 发送 1 号信号。执行这三个 kill 函数，最终的效果就是 P1 的 pending 位向量里，信号 1 对应的比特由 0 变成 1，信号 8 对应的比特也由 0 变成 1——很好理解吧，这意味着 P1 收到了 1 号信号，也收到了 8 号信号。

从这个例子能看到：用户进程和用户进程之间可以相互发送信号，内核进程也可以给用户进程发送信号。另外补充一点——一个进程也可以给自己发送信号。

不过要注意，**用户进程之间允许发送的信号类型是有限制的**。比如在 Linux 系统中，SIGKILL（序号 9）可以用于杀死一个进程：一个父进程可以给自己的子进程发送 SIGKILL 信号，但其他用户进程不能随意发送。道理很简单——如果每个进程都可以随意杀掉其他进程，整个系统就会产生很多错误。而操作系统内核给用户进程发信号就没什么限制了，因为内核拥有最高权限。

#### 一比特的代价：重复信号被丢弃

pending 是位向量，意味着每一种信号类型只能用一个比特来保存信息。这带来两个直接后果：

1. 虽然 P2 和内核进程都给 P1 发送了 1 号信号，但 P1 只能接收一个 1 号信号，后到达的信号 1 会被简单地丢弃；
2. 从 P1 的位向量当中，无法区分出这个信号到底是哪个进程发过来的。

除了 kill 函数，其实还有其他函数也可以发送信号，只不过 kill 函数最灵活、最常用，所以我们主要以它为例。

### 什么时候处理信号：内核态转回用户态的那一刻

信号发出去了、也保存在 pending 里了，那进程什么时候会去处理这些信号呢？答案很简单：**每一次进程从内核态转为用户态的时候，都会例行检查是否有待处理的信号**，如果有就处理。

哪些场景会出现"内核态转用户态"？比如一个进程从系统调用返回的时候，就是从内核态转回用户态；再比如一个进程收到中断，对中断处理完返回的时候，也会从内核态转回用户态。总之每次从内核态回到用户态，都要例行检查一遍。

#### 检查怎么做：pending 与 blocked 取反后逐位与

具体怎么检查？拿 pending 和 blocked 这两个 N 比特位向量做一次运算。继续用前面八种信号的例子——P1 收到了信号 1 和信号 8，同时它屏蔽了信号 7 和信号 8（所以 blocked 的末尾两个比特是 1）：

```text
信号序号:          1  2  3  4  5  6  7  8
pending :          1  0  0  0  0  0  0  1    收到了信号1和信号8
blocked:           0  0  0  0  0  0  1  1    屏蔽了信号7和信号8
~blocked:          1  1  1  1  1  1  0  0    blocked 全部按位取反
pending & ~blocked:1  0  0  0  0  0  0  0    逐位与的结果
```

读图说明：先把 blocked 位向量按位取反，再和 pending 逐位做与运算。值得注意的是第 8 个比特——虽然 P1 确实收到了信号 8，但由于信号 8 是被阻塞的，取反再逐位与之后，第 8 个比特就变成了 0。根据这个运算结果就可以判断：此时需要处理的是信号 1，而信号 8 可以不做处理。这就让我们真切感受到了 blocked 这个变量有什么作用——被阻塞的信号不需要处理，具体屏蔽哪些信号由进程自己决定。

#### 一个执行流里的完整时序

检测出了待处理的信号，接下来就该处理它。处理之前先看它在一个进程执行流里发生在什么位置。我们知道，一个进程的执行本质上就是在运行一段指令序列。假设进程 P1 在执行过程中收到了信号 1 和信号 8，它并不会立即响应这些信号，直到从内核态转为用户态的时候，才会检测并处理。

```text
进程P1的执行流（时间自上而下）:

  执行指令 K          ← 假设 K 是 trap 指令，引发系统调用，进程转入内核态
      |
  内核态执行系统调用
      |
  系统调用结束，即将从内核态转回用户态
      |               ← 此刻例行检查：pending & ~blocked，发现只有信号1待处理
      |
  转去执行信号1的处理程序
      |
  处理程序执行完毕，返回进程P1
      |
  从指令 K+1 继续往下执行
```

读图说明：收到信号的时刻和处理信号的时刻是分开的——收到时只是把 pending 里的对应位记下来，直到某个"内核态转用户态"的节点才真正处理。

换一种假设也能走通同样的流程：假如指令 K 只是一条很普通的指令，P1 在执行完 K 之后收到了一个 I/O 中断，那么 I/O 中断同样会使进程从用户态先转为内核态，中断处理完成之后又从内核态回到用户态——在这个时刻，同样需要例行检查是否有待处理的信号，有就运行对应的处理程序。

### 怎么处理一个信号

时机（when）清楚了，接下来是方式（how）的问题。

#### 默认处理程序与自定义处理程序

操作系统会给**每一类信号**都设置一个默认的信号处理程序。回到前面那张信号表：对 SIGINT 的默认处理，是执行终止进程相关的代码逻辑；对 SIGFPE 的默认处理，是终止进程并且转储内存。不过有的信号会被直接忽略，比如 SIGWINCH——窗口大小变化（window change）——这种信号的默认处理就是忽略，你可以理解为它的默认处理程序是一个空函数。

那我们可不可以不执行这种默认处理呢？当然可以。操作系统允许一个用户进程为某些类型的信号设置**用户自定义的信号处理程序**。比如进程一可以通过系统调用去设置信号 2 的处理程序，这段程序由进程一自己写——假如它希望收到信号 2 时输出 hello world，那"输出 hello world"就是用户自定义的处理逻辑。自定义的处理程序会**覆盖掉**系统的默认处理。

这种机制有什么用？举一个做开发时很实际的例子。在 Linux 当中，当一个应用程序的窗口大小发生变化时，内核会向它发送 SIGWINCH 信号，这类信号的默认处理是直接忽略、什么也不做。但平时我们都有这样的体会：调整某个应用的窗口大小时，应用内部的 UI 往往需要根据窗口大小动态调整——窗口缩小了或扩大了，一些按钮的位置就得重新摆一摆。如果对窗口大小变化什么都不做，UI 的动态调整就很难实现。此时信号机制就发挥了作用：窗口大小变化时进程一定会收到 SIGWINCH，我们就可以自定义一个处理程序，规定收到这个信号时根据窗口大小的变化去动态调整 UI。所以用户自定义的信号处理程序，在做开发的时候是很有用的。

> **结论**：没有自定义处理程序，就执行操作系统配置的默认处理逻辑（有的默认处理程序是空函数，等于忽略）；有自定义处理程序，它就覆盖默认的处理逻辑。

#### 值得记住的几条规则

关于信号处理，还有几条细节，概念题里容易考到：

- 信号处理程序运行结束之后，通常会返回进程的**下一条指令**继续执行——结合上面的时序图不难理解；除非这个处理程序直接把进程阻塞了，或者直接把它终止了。
- 一旦处理了某个信号，就会把对应的 pending 位重置为 0。比如 P1 处理了信号 1，就把信号 1 的那个比特清回零。
- 如果重复收到同类信号，重复的信号将被简单丢弃——因为每一类待处理的信号只用一比特记录，这是由数据结构的特性所限制的。
- 当同时收到多个不同类型的信号时，通常会优先处理**序号更小**的信号。比如信号 1、2、3 都待处理，就先处理 1，再处理 2，最后 3。

还有一点需要强调：**各个进程的信号处理程序是相互独立的**。进程一可以自定义"收到信号 2 时按我写的这段逻辑处理"，进程二也可以自定义"收到信号 4 时按我写的逻辑处理"——每个进程自定义的处理程序只作用于它自身，不会作用于其他进程。同理，每个进程都有自己的 pending 位向量和 blocked 位向量：P1 阻塞了 7、8 这两种信号，P2 可能阻塞了 1、2、3 这几种，各管各的，互相独立，都由进程自己通过系统调用设置。没有自定义处理程序的进程，就执行操作系统配置好的默认处理程序。

最后一条特别容易考：**有些信号既不允许被用户自定义处理函数覆盖，也不允许被阻塞**，比较典型的就是 Linux 当中的 SIGKILL 和 SIGSTOP 这两个信号。从信号表里也能看到这一点。

### 信号和异常的关系

现在来探讨这一讲的疑难点：信号和异常有什么关系？先说结论——**信号可以作为异常的配套机制，让进程对操作系统的异常处理进行补充**。

进程运行的过程中，有些特殊事件可能会引发异常，操作系统内核会捕获并处理这些异常，比如缺页异常、整数除以零的异常。但这里要分两种情况：

- 有些异常，内核可以**完成全部处理**，最典型的就是缺页异常——进程访问了缺失的页面引发缺页异常，内核会把缺页异常的全部处理做完。
- 而有些异常，内核**无法完成全部处理**，可能还需要用户进程配合，对异常进行补充处理。

第二种情况我们用一个场景来体会。假设你开发了一个应用程序，就是一个简单的计算器，它会被各种各样的人使用。假设你的舍友用你这个程序的时候总喜欢输入整数除以零——这种操作会触发一个异常，操作系统内核捕获它之后，会在异常处理程序当中给你的计算器进程发送 SIGFPE 信号。SIGFPE 的默认处理是把进程终止并转储内存，也就是说，如果你不修改这种信号的默认处理程序，那么每当你的舍友进行整数除以零这种骚操作的时候，你的应用程序就会闪退崩溃。这种体验如何？有同学说妙极了——其实一点都不妙，显然这种用户体验会非常糟糕。

所以这时候就可以通过自定义的信号处理程序来处理这种情况：当舍友输入整数除以零时，你在计算器页面上打印"出错了"，提醒他输入有问题，而不是直接让程序闪退。

从这个例子可以感受到：操作系统检测到一个异常时，有些异常比较复杂，可能需要根据应用程序的实际需求做个性化的处理，这种情况下就可以使用信号机制，对操作系统的异常处理进行个性化的补充。所以信号这种机制在开发当中还是很常用的。

### 为什么要引入线程

在很久很久以前——在没有引入进程之前，系统中的各个程序只能串行执行。那个时候，我们想一边运行音乐播放程序、一边运行 QQ 这个程序，显然是实现不了的，不可能边聊 QQ 边听音乐。之后引入了进程机制，就可以一边聊 QQ 一边听音乐了。

但是大家再深入思考一下：QQ 可以做一些什么事情呢？我们可以用 QQ 进行视频聊天，同时还可以和其他人进行文字聊天，然后同时还还在传送文件——这些事情是怎么在一个进程当中完成的？很显然，在传统的进程定义当中，进程是程序的一次执行，但视频聊天、文字聊天、传送文件这些功能，显然不可能由一个程序顺序执行来处理。如果只能顺序处理，那就不可能在用户看来这几件事情是同时发生的。所以有的进程其实需要**同时处理很多事情**，就像刚才的 QQ 那样；但传统的进程只能串行地执行一系列程序代码。

在传统的进程机制当中，CPU 会轮流为各个进程服务，这些进程就可以并发执行；每个进程有自己的一系列程序代码，被 CPU 服务时这些代码就一句一句往下执行。所以在传统机制中，**进程是执行流的最小单位**——这句话什么意思，听完后面的讲解大家就能理解了。

为了满足"一个进程内宏观上同时做很多事情"的需求，人们引入了线程机制，用来增加系统的并发度。引入线程之后，CPU 调度服务的对象就不再是进程，而是进程中的线程：每个进程可能包含多个线程，CPU 按照一定的算法轮流为这些线程服务。这样，同一个进程就被分成了多个线程——视频聊天和传送文件这两件事想并发执行，就把它们对应的处理程序放到两个不同的线程里，这两个线程并发执行，这两件事自然就并发完成了。

所以引入线程之后，**线程成了程序执行流的最小单位**。没有引入线程之前，一个进程对应一份代码，这些代码只能顺序依次往下执行；引入线程之后，一个进程可以有多个线程，这些线程可以有各自不同的代码，也可以是不同的线程运行同一份代码，但它们都会被 CPU 并发地调度、依次执行下去。所谓"执行流的最小单位"，就是这个意思。

> **定义**：线程可以理解为一种"轻量级的进程"。以前 CPU 调度的单位是进程，现在 CPU 的服务对象以线程为单位，所以线程是**基本的 CPU 执行单元**，也是**程序执行流的最小单位**。

### 引入线程之后，世界有什么不同

引入线程之后，进程之间可以并发执行，进程内的各个线程也可以并发执行，并发度进一步提高，一个进程内也可以并发处理各种各样的任务——就像刚才说的 QQ 聊天、传文件那样。对照传统的进程机制，变化主要体现在三个方面：

| 对比维度 | 传统进程机制 | 引入线程机制之后 |
| :--- | :--- | :--- |
| 资源分配 | 进程既是资源分配的基本单位，也是处理机调度的基本单位 | 进程只是资源分配的基本单位 |
| 处理机调度 | 调度对象是进程 | 调度对象变成线程 |
| 并发性 | 只能进程之间并发执行 | 进程之间、进程内各线程之间都可并发，并发度进一步提升 |
| 并发的开销 | 进程间并发需要切换进程的运行环境，系统开销较大 | 同一进程内的线程切换不需要切换进程运行环境，开销进一步降低 |

其中"切换进程运行环境的开销"值得展开。我们用去图书馆看书的例子来理解：假如你正在用图书馆的某张桌子，突然一个你不认识的人也要用这张桌子，那么你需要把你的"运行环境"——你的书——收走，他再把自己的书放上去。这就是进程切换所带来的运行环境切换，这个过程是要付出代价的：你搬走书，他摆上书。但如果这时是你的舍友想用这张桌子呢？既然你们认识，就相当于你们俩属于同一个进程，这种情况下可以不收自己的书，书依然放在桌上——这就类似于同一进程内的线程切换。同一进程内的线程切换不需要切换进程的运行环境，由于不需要把书挪来挪去，开销自然降低很多。

还有一个配套的变化要说清楚：引入线程之后，**进程不再是 CPU 调度的基本单位，它只作为 CPU 之外的系统资源分配单元**。也就是说，计算机系统里各种各样的系统资源是被分配给进程的，而不是分配给线程的。

### 线程的属性

把线程的几条重要属性归拢一下：

- **线程是处理机调度的单位**——前面已经强调过很多次了。
- 在多核 CPU 的计算机当中，每个线程可以占用不同的 CPU。比如现在的 CPU 一般都是双核、四核、八核的，各个线程可以被分配到不同的核心里去。
- 每个线程会有一个线程 ID，以及一个线程控制块 TCB 这样的数据结构。线程控制块有点类似我们之前学过的 PCB（进程控制块），也是用于管理线程而创建的数据结构。
- 和进程类似，线程也有**就绪、阻塞、运行**三种基本状态。
- 因为线程只是处理机调度的基本单位，而系统资源是分配给进程的，所以**线程几乎不拥有系统资源**。那线程要用的资源从哪来？同一个进程中的不同线程可以共享使用这个进程所拥有的系统资源，包括 I/O 设备、内存地址空间这样的资源。
- 由于同一进程内的线程共享内存地址空间，同一进程中的线程之间的通信可以**不需要操作系统干预**，直接通过共享的内存地址空间就能完成信息传递。
- 同一进程中的线程切换**不会引起进程切换**；但不同进程中的线程切换**会引起进程切换**。切换同进程内的线程，不需要切换进程的运行环境，系统开销小；切换不同进程间的线程，会导致进程切换、需要切换进程运行环境，系统开销大——就是刚才图书馆那个例子。

### 用户级线程：程序员自己写的线程库

接下来看线程的实现方式。线程的实现分为用户级线程和内核级线程两种，另外还有些系统会把两种混合起来使用，后面会看到实际的例子。

先看用户级线程。这种实现方式用在早期那些只支持进程、还没有支持线程的操作系统上。当时所谓的线程，是由程序员写的**线程库**来实现的：操作系统的视角里看到的依然只有进程，但程序员写的应用程序可以利用线程库，实现多个线程并发运行这样的事情。

还是结合 QQ 那个例子来理解。QQ 要一边视频聊天、一边文字聊天、一边传文件。上一小节我们提出的方案是：在不支持线程的系统当中，可以分别建立三个进程，各处理其中一件事。但其实从单纯的代码角度看，我们还可以这样做——用一个 while 循环，让变量 i 按 0、1、2、0、1、2 这样循环变化：当 i 等于 0 时处理视频聊天，等于 1 时处理文字聊天，等于 2 时处理文件传输：

```c
while (true) {
    if (i == 0) {
        处理视频聊天;    // i = 0 的分支
        i = 1;
    } else if (i == 1) {
        处理文字聊天;    // i = 1 的分支
        i = 2;
    } else {
        处理文件传输;    // i = 2 的分支
        i = 0;
    }
}
```

由于这个程序进行 while 循环的速度非常快，我们其实可以把这三段代码看作三段并发运行的代码，分别处理不同的事情。所以从代码逻辑的角度看，一个线程其实可以理解为**一段代码逻辑**——这三段代码逻辑，我们就可以把它看作三个线程。而这段 while 循环的处理逻辑，其实就可以看成一个最简陋、最"弱智"的线程库：它完成了对各个线程管理和调度的工作，调度规则也很简单——第一次先处理视频，第二次处理文字，第三次处理文件，第四次又处理视频，第五次处理文字，以此类推。一个简单的 while 循环加几个 if 语句，就实现了一个最简单的线程库。

当然，很多编程语言提供的线程库要比我们的 while 循环复杂多了，程序员可以利用这些线程库实现用户级线程的创建、销毁、调度等一系列功能。

理解了这个例子，四个关键问题就都能回答了：

1. **这些用户级线程的管理工作由谁完成？** 刚才那个 while 循环就简单地实现了对三个线程的管理，让它们交替运行。所以管理工作是由**应用程序通过线程库**完成的，并不是操作系统负责的。
2. **线程切换是否需要 CPU 从用户态转换为内核态？** 线程切换是由 while 循环控制的，不涉及请求操作系统服务之类的事情，所以在**用户态下就可以完成**线程切换，不需要操作系统干涉。
3. **操作系统能否意识到用户级线程的存在？** 显然不能。操作系统只能看到这个进程的存在，它只知道这个进程是一坨代码，而这一坨代码里又分成了几个线程，操作系统是意识不到的。这也是"用户级线程"这个名字的由来——**只有用户（线程库）能感知到它的存在，操作系统感知不到**。
4. **这种实现方式有什么优点和缺点？** 优点：用户级线程的管理工作（包括切换、创建等）不需要请求操作系统服务，不需要 CPU 状态切换到内核态——而 CPU 状态切换是有开销、有成本的——所以管理开销小、效率高。缺点往下看。

#### 用户级线程的死穴：一个阻塞，全体阻塞

回到我们实现的这三个最简单的用户级线程。假设 QQ 进程上处理器运行，这一次 i 的值是 0，也就是视频聊天这段代码上处理机运行。再假设视频聊天这段代码在运行过程中发生了阻塞——比如它想申请摄像头资源但申请失败，由于想要的系统资源得不到满足，这段代码的执行就被阻塞了。想一想：这段代码被阻塞在这儿了，while 循环还能继续下去吗？肯定不行了，只有阻塞被解除，while 循环才能继续执行。

所以用户级线程有一个很明显的缺点：**只要其中一个线程被阻塞，整个进程里的其他线程也会被阻塞**，整个进程都执行不下去，并发度并不高。

另外还有一个隐藏的问题：上一小节我们说引入线程之后线程成了 CPU 调度的基本单位，但如果线程是用用户级方式实现的，那么在这种情况下 **CPU 的调度单位依然是进程**——操作系统是给进程分配 CPU 时间的。因此即便电脑是多核处理机，由于进程才是调度单位，这个进程只能被分配一个核心，这些线程并不能并行运行。

### 内核级线程：操作系统看得见的线程

随着操作系统的发展，越来越多的操作系统开始支持线程——操作系统支持的这种线程就叫**内核级线程**，也就是操作系统视角也能看得到的线程。现代操作系统大多支持内核级线程，比如我们很熟悉的 Windows、Linux 等等。

还是思考同样的三个问题：

1. **管理工作由谁完成？** 内核级线程是在操作系统层面实现的线程，所以管理工作当然由操作系统来完成。
2. **线程切换是否需要 CPU 状态转换？** 既然由操作系统负责管理，切换肯定需要操作系统介入，因此线程切换时需要**从用户态转变为内核态**。
3. **操作系统能否意识到它的存在？** 这个不用说了，能。

据此分析优缺点。**优点**：在支持内核级线程的操作系统中，内核级线程是处理机调度的基本单位，进程只作为分配资源的基本单位。因此在多核 CPU 环境下，这几个线程可以分别派到不同的核心上**并行执行**；而且由于线程之间相互独立，即便其中一个线程被阻塞（比如视频聊天的线程阻塞了），其他两个线程（文字聊天、文件传输）依然可以继续执行。所以这种方式的线程并发能力强。

**缺点**：一个进程可能对应多个内核级线程，操作系统需要对它们进行管理，所以内核级线程之间的切换需要 CPU 从用户态变为内核态，切换完成之后还要从内核态转回用户态——CPU 状态切换是有成本、有开销的，所以这种方式的线程管理成本更高、开销更大。

### 三种多线程模型

用户级线程开销小但并发能力弱，内核级线程并发能力强但管理开销大——有没有可能把两种方式结合起来？在支持内核级线程的系统当中，如果再引入线程库，就可以实现把若干个用户级线程映射到某个内核级线程上。根据这种映射关系，就引出了三种多线程模型：

```text
一对一模型          多对一模型           多对多模型(n >= m)

U1   U2   U3        U1  U2  U3          U1   U2   U3
|    |    |          \   |   /            \   |   /
K1   K2   K3             K1               K1      K2
```

读图说明：用户级线程（U）是代码逻辑的载体，内核级线程（K）是"运行机会"的载体——这个对应关系后面还会展开。

#### 三种模型各自的账

**一对一模型**：一个用户级线程对应一个内核级线程，一个进程有多少个用户级线程就有多少个内核级线程，一一对应。优点就是一个线程被阻塞之后别的线程还可以继续执行（因为内核级线程是处理机分配的基本单位），而且这些线程可以派到多核处理机上并行执行。缺点和刚才分析内核级线程时一样：管理成本高、开销大，因为线程的管理工作需要切换到内核态，只要涉及 CPU 状态切换，开销就会变大。

**多对一模型**：多个用户级线程映射到一个内核级线程。这种映射关系其实就退化成了前面讲的纯粹的用户级线程实现方式：一个进程只被分配一个内核级线程，在这个内核级线程上面通过线程库实现了多个用户级线程，线程的管理工作在用户态就能完成，所以管理开销小、效率高；但缺点是其中一个用户级线程阻塞之后，其他用户级线程也跟着被阻塞，并发性不高，并且这些用户级线程不可能并行运行——因为只有内核级线程才是处理机的分配单位，一个进程只对应一个内核级线程，同一时刻就只能被分配一个 CPU 核心。当然，如果给进程分配多个内核级线程，多核环境下这些内核级线程肯定可以并行运行；不过在我们的考试当中，如果提到多对一线程模型，默认一个进程只被分配一个内核级线程。

**多对多模型**：把 n 个用户级线程映射到 m 个内核级线程上，n 大于等于 m。由于一个进程有多个内核级线程，其中一个被阻塞时另一个可以继续运行，所以它克服了多对一模型并发度不高的缺点；另一方面，n 大于等于 m 意味着内核级线程的数量比用户级线程少，操作系统对这些线程的管理开销也相应更小——而一对一模型里有多少个用户级线程就要创建多少个内核级线程，内核级线程太多管理开销就大，所以多对多又克服了一对一模型线程管理开销太大的缺点。

| 模型 | 映射关系 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| 一对一 | 1 个用户级线程 : 1 个内核级线程 | 并发能力强：一个线程阻塞不影响其他线程；可多核并行 | 内核级线程多，管理成本高、开销大 |
| 多对一 | 多个用户级线程 : 1 个内核级线程 | 管理开销小、效率高（用户态完成管理） | 一个线程阻塞全进程阻塞；不能并行，并发度不高 |
| 多对多 | n 个用户级线程 : m 个内核级线程（n ≥ m） | 并发度不高的问题得到克服；管理开销比一对一小 | — |

#### 代码逻辑的载体与运行机会的载体

最后总结一下用户级线程和内核级线程的区别与联系，可以这么理解：**用户级线程是代码逻辑的载体**——比如这个用户级线程承载文字聊天相关的代码逻辑，那个承载文件传输相关的代码逻辑；**内核级线程是"运行机会"的载体**——因为操作系统分配处理机、CPU 资源的时候，是以内核级线程为单位进行分配的。所以在多对多模型的例子里，一个进程虽然有多个用户级线程，但最多只可能被分配两个 CPU 核心。一段代码逻辑只有获得了运行机会，才可以被 CPU 执行。

这种分离还能让线程管理更灵活。比如在那个多对多的例子里，如果 QQ 视频聊天需要耗费比较多的 CPU 资源，我们可以让左边的内核级线程专门执行视频聊天相关的代码逻辑，右边的内核级线程并发执行文件传输和文字聊天这两部分逻辑；如果某一时刻文件传输又要耗费很多 CPU 资源，我们可以把文字聊天这一块的逻辑映射过去，让另一个内核级线程来处理。

还有一个需要注意的细节：引入内核级线程之后，一个进程可能对应多个内核级线程，而**只有所有的内核级线程都被阻塞的时候，我们才说这个进程进入了阻塞状态**。

根据去年同学们的反馈，这一小节的内容不太容易理解，特别是对跨考、没有自己写过程序的同学来说，理解起来可能比较吃力。对跨考的同学来说，学完数据结构、有了一些写代码的思想之后再回来理解这部分内容，可能会更容易一些。再次强调：**用户级线程是用户视角能看到的线程，由线程库实现**——就像那个很简单粗暴的 while 循环，可以认为是最简单的线程库；**内核级线程才是操作系统视角能看得到的线程，由操作系统负责管理，所以内核级线程才是处理机分配的单位**。这几种多线程模型，主要理解它们各自的优缺点；另外这部分内容比较容易考察关于阻塞的问题，大家在课后习题当中会有体会。

## 线程的状态转换与处理机调度全景：从 TCB 到调度评价指标
> 对应块：BLK08 | 覆盖分集：P19-P23 | 块标题（分集名）：《2.1.6_3 线程的状态与转换》

线程的状态与转换，其实和进程的状态与转换几乎是一模一样的。这一讲我们就从这个"抄作业"式的结论出发，把线程的管理讲清楚，然后顺势进入本篇的主战场——处理机调度：什么是调度、调度的三个层次、什么时候能调度什么时候不能、调度程序是个什么角色、闲逛进程为什么存在，最后落到评价一个调度算法好坏的五把尺子上。

### 线程的三状态模型

我们通常只关注线程最核心、最主要的三个状态：**运行态、就绪态和阻塞态**，它们之间的转换和进程完全一致。

```text
             被调度程序选中                发出请求等待事件（如等待 I/O 完成）
   就绪态 ────────────────▶ 运行态 ─────────────────────────▶ 阻塞态
      ▲                      │                                │
      │    时间片用完，        │                                │
      │    下处理机           │                                │
      └──────────────────────┘                                │
      ▲                                                       │
      └──────────────── 等待的事件发生了 ────────────────────────┘
```

读图：就绪态与运行态之间是双向通道——时间片用完下来、被选中上去；运行态到阻塞态是线程自己主动发出请求（比如等 I/O 完成）；阻塞态到就绪态则是等待的事件发生后被动归来。

四条转换规则逐一对应进程的情形：一个运行态的线程被分配的时间用完了，就下处理机进入就绪态；一个就绪态的线程被调度程序选中，就回到运行态上处理器运行；一个正在运行的线程发出了某种请求、等待某个事件的发生（比如等待 I/O 完成），就从运行态转为阻塞态；一个阻塞的线程等的事件发生了，就从阻塞态回到就绪态。着重关注这种三状态模型就够了。

### 线程的组织与控制：TCB 里装了什么

线程的组织与控制和进程也非常类似。管理进程时，操作系统靠的是 PCB（进程控制块）；那要管理线程，首先就得给各个线程建立一个与之对应的数据结构——这就是 **TCB，线程控制块**，每个 TCB 表示一个线程。它里面大致包含这些内容：

- **标识信息**：线程自己的标识，这和进程的 PCB 很类似；
- **程序计数器 PC**：指明线程现在执行到哪了。线程切换下处理机时，要把处理机上 PC 的值保存到 TCB 当中；线程上处理器运行（从就绪态回到运行态）时，再从 TCB 中取出 PC 的值放回 PC 寄存器，恢复运行现场；
- **其他各种通用寄存器的值**：学过计组我们都知道，代码运行的中间结果会保存在各种各样的寄存器里，所以切换线程时也需要保存这个线程各种寄存器的值；
- **堆栈信息**：堆栈用于保存函数调用的信息——A 调用了 B、B 调用了 C，每一层函数调用结束之后应该返回到哪一句代码（返回地址），以及每层函数的局部变量，都记录在堆栈里。线程的堆栈可能是比较大的，是内存里的一大片区域，把整片堆栈都存进 TCB 显然没必要——我们只需要保存**堆栈指针**，通过这个指针就能找到这个线程的堆栈在内存里的哪片区域。恢复时把它填回 SP 堆栈寄存器即可；
- **运行状态**：运行、就绪还是阻塞；如果是阻塞态，还可以把阻塞原因等更详细的信息记录进去；
- **线程的优先级**：线程调度或系统分配资源时，可以根据线程的优先级来分配或制定策略。

上面圈出来的三部分——程序计数器 PC、其他各种寄存器的值、堆栈信息——就是线程切换时需要保存和恢复的**运行现场**：下处理机的线程把这些信息保存到 TCB 当中，上处理机的线程从 TCB 当中取出这些信息，填回到相应的位置。

> **提示**：TCB 里的这套清单和 PCB 高度同构，区别只在于线程不负责资源分配，所以 TCB 里没有进程那些资源分配相关的信息。

有了 TCB 之后，把多个线程的 TCB 组织起来就形成**线程表**。组织方式有很多种：每个进程给它设置一张线程表；或者系统当中所有线程组成一张线程表；也可以按照线程的状态不同，组织成不同的线程表。不同的系统可以采取不同的策略。总之所谓**线程的组织**，无非就是按照需求把各个 TCB 有规律地分门别类、分类管理；所谓**线程的控制**，就是让线程在各种状态之间来回切换。这两部分新学的内容，无非是把"进程"换成了"线程"而已——而且线程往往比进程还要更简单。

### 什么是调度：从银行和宿舍卫生间说起

调度这个概念和我们的生活离得并不遥远。去银行的时候，银行可能只有几个窗口为客户服务，那到底应该先为谁服务呢？银行一般采用的就是先到先服务的原则；如果此时有一个 VIP 客户——在这个银行里存了几个小目标（就是存了几个亿）——那这个 VIP 客户可能就会被优先服务，它的优先级更高。

再看另一个场景：早上起床，每个宿舍只有一个卫生间，但大家都想成为那个"坐在王座上的男人"。有的人要用三分钟，有的人要十分钟，有的人只要一分钟，还有一个人也需要三分钟。大家商量之后定下原则：使用时间短的先使用，时间长的后使用；时间长度相同的，先排队先使用。于是大家就按 1、2、3、4 这样的顺序来使用卫生间这个资源。

所以所谓**调度**，就是当我们有一堆任务要处理、而当前资源有限、这些事情没办法同时被处理时，按照某种规则（先到先服务、时间短的优先等等）来决定用什么顺序处理这些任务——这就是调度研究的问题。

### 调度的三个层次

程序运行的整个生命周期内，什么时候会发生调度？按层次分有三种。先补充一个概念：**作业**。书里会看到"用户向操作系统提交了一个作业"这样的描述，你可以理解为：用户让操作系统帮他启动某一个特定的程序，这个程序用来处理某一个具体的任务。

#### 高级调度：作业调度

我们要启动一个程序，程序相关的数据肯定需要从外存放到内存里。但内存资源有限，如果内存已经满了、资源不足，我们提交的这些作业就可能没办法马上放进内存马上启动。这个时候操作系统就会进行**高级调度**（作业调度）：按照作业调度相关的规则，从**作业后备队列**里选择一个作业先调入内存，并且为这个作业建立相对应的进程——也就是建立一个 PCB。

如果用户提交了很多作业，就由操作系统决定到底先调入哪个。要注意：每个作业在整个生命周期内**只会调入一次**，调入的时候建立 PCB；当作业完成任务之后被调出，这时才撤销与之对应的 PCB。一进一出，就这一次。

#### 低级调度：进程调度

内存里同时会存在很多很多个进程，但系统的 CPU 资源有限，所以操作系统也需要制定某种策略，从**进程就绪队列**当中挑选出一个进程，把处理机资源分配给它。**多道程序并发执行这件事肯定需要用到进程调度，所以进程调度是操作系统当中最基本的一种调度。**

并且进程调度的频率是很高的——只有高频率的进程调度，才可以让各个进程很快地轮流上 CPU 执行，让用户在宏观上看起来各个进程好像是同时执行的。

#### 中级调度：内存调度

刚才说过，计算机有可能出现内存资源不足的情况。这时可以让一些不太紧急、不太重要的进程，把它的数据先从内存调出到外存。一个进程的数据从内存放到了外存，这个进程此时就处于**挂起状态**；操作系统会把处于挂起状态的进程的 PCB 组织成一个**挂起队列**，类似于之前学过的就绪队列、阻塞队列。等有了空闲的内存资源，操作系统又需要通过某种调度策略决定先把哪个进程的数据调回内存——这就是**中级调度**，又叫内存调度。

不知道你平时用手机的时候有没有这样的体验：切换程序的时候，有的时候进程切换得很快，有的时候又很慢。有一种可能的原因是：切换很快的时候，这个进程的数据正放在内存里；而切换很卡很慢的时候，有可能那个进程的数据之前已经不在手机内存里了，而是被系统调到了外存。你一切换，系统发现这个进程现在非运行不可了，就临时把它相关的数据从外存读回内存——只有读回内存之后这个进程才可以顺利运行，所以你会感受到那么一丝丝卡顿。**卡顿的过程就是系统在进行中级调度**：它选中了你的那个进程，让它回内存来运行。

显然，一个进程在运行的生命周期内有可能**多次调出、多次调入**，所以中级调度发生的频率肯定比高级调度更高。

### 挂起态与七状态模型

既然提到了挂起状态，就补充一个课本上没有太多提及的知识点——**七状态模型**。挂起状态可以进一步细分为**就绪挂起**和**阻塞挂起**两种。我们之前学的五状态模型是 408 要求掌握的；但对于一些自主命题的学校，也有可能会考察七状态模型，所以不要掉以轻心。

```text
         内存中的状态                          外存中的状态（挂起态）

   ┌────────────┐    挂起：调出到外存    ┌────────────┐
   │   就绪态   │ ────────────────────▶ │  就绪挂起态 │
   └────────────┘                       └────────────┘
   ┌────────────┐    挂起：调出到外存    ┌────────────┐
   │   阻塞态   │ ────────────────────▶ │  阻塞挂起态 │
   └────────────┘                       └────────────┘

   激活：调回内存（就绪挂起态 → 就绪态；阻塞挂起态 → 阻塞态）
   事件发生：阻塞挂起态 ──等待的事件发生──▶ 就绪挂起态
```

读图：左边是内存中的两个状态，右边是外存中的两个挂起态，"挂起"与"激活"是它们之间的往返通道；另外注意一条容易漏掉的转换——处于阻塞挂起的进程，当它等待的事件发生时，会**直接进入就绪挂起状态**，之后被调回内存时直接回到就绪态，而不是回到阻塞态。

除了上面两条主通道，还有几种值得注意的进入就绪挂起态的方式：一个处于运行态的进程运行结束、下处理机的时候，有可能被直接放到外存当中，进入就绪挂起状态；一个处于创建态的进程，创建完 PCB 之后有可能遇到内存空间不够的情况，这时创建态的进程之后也可能先进入就绪挂起状态。

> **易错点**：挂起和阻塞的区别。这两种状态都是暂时不能获得 CPU 服务的状态，但区别在于：处于挂起态的进程，**进程映像放在外存里**；而处于阻塞态的进程，它的进程映像还在**内存**当中。

有的操作系统会把就绪挂起和阻塞挂起的进程分成两个不同的挂起队列；也有的操作系统还会根据阻塞原因的不同，把阻塞挂起的进程再细分为多个队列。

### 三层调度的联系与对比

三层调度分别要做什么，前面已经讲得比较细了，这里把它们放到一起来对比。

```text
      外存                            内存                        CPU
 ┌──────────────┐  高级调度(作业调度) ┌──────────┐  低级调度(进程调度/处理机调度) ┌─────┐
 │  作业后备队列 │ ─────────────────▶ │ 就绪队列 │ ────────────────────────────▶ │ CPU │
 └──────────────┘   调入一次/调出一次  └──────────┘        (频率最高)              └─────┘
                                        ▲    │
                                        │    │ 中级调度(内存调度)
                                        │    ▼    可多次调出/调入
                                   ┌──────────┐
                                   │ 挂起队列 │（在外存）
                                   └──────────┘
```

读图：高级调度和中级调度都是发生在外存和内存之间的调度，低级调度则是内存和 CPU 之间的调度。

| 对比项 | 高级调度（作业调度） | 中级调度（内存调度） | 低级调度（进程调度/处理机调度） |
| :---: | :--- | :--- | :--- |
| 发生位置 | 外存 ↔ 内存 | 外存 ↔ 内存 | 内存 ↔ CPU |
| 面向对象 | 面向作业 | 面向进程 | 面向进程 |
| 调入调出次数 | 作业只调入一次、调出一次；调入时建立 PCB，调出时撤销 PCB | 进程可多次调出、多次调入 | 极高频，各进程轮流上 CPU |
| 发生频率 | 最低 | 中等 | 最高 |
| 对进程状态的影响 | 使进程从无到创建态，PCB 创建完毕后放入就绪队列进入就绪态 | 使处于挂起态的进程重新回到就绪态；若细分挂起，也可以使阻塞挂起的进程重新回到阻塞态 | 选择一个处于就绪态的进程让它进入运行态——投入处理机才是运行 |

> **提示**：这三种调度的名称，要特别记住**后面那一个名称**（作业调度、内存调度、进程调度）——它们才是在考题当中最高频、最容易出现的叫法。

这一讲介绍三种调度时都在说"按照某种规则"，本课程主要学习的就是作业调度和进程调度相关的这些规则——也就是之后要研究的**调度算法**问题。

### 进程调度的时机：什么时候能调，什么时候不能

进程调度也叫低级调度，指按照一定的算法从就绪队列当中选择一个进程为它分配处理机。那么什么时候需要进行进程调度和切换？主要分为两大类：当前运行的进程**主动**放弃处理机，或者**被动**地被迫放弃处理机。

主动放弃的情形：进程正常终止；运行过程中发生了某种异常而不得不终止；再或者进程发出了一个 I/O 请求，主动请求进入阻塞状态去等待 I/O 完成。被动放弃的情形：分配的时间片用完了；有更紧急的事情需要处理；当前有一个优先级更高的进程进入了就绪队列——这些情况下，就有可能把当前运行的进程强行剥夺处理器使用权，它不得不被动放弃处理机。

而进程调度**并不是什么时候都可以进行的**，有三种情况不能进行调度与切换：

**一是处理中断的过程中。** 中断处理的过程很复杂，并且和硬件息息相关，因此在中断处理的过程中，很难做到处理到一半去进行进程调度和切换。

**二是进程在操作系统内核程序临界区中。** 这一点不太容易理解，下面单独展开。

**三是原子操作的过程中**，也就是之前介绍过的一些**原语**。举个例子：一个进程的状态发生改变——比如从阻塞态变为就绪态——我们既需要修改进程 PCB 当中的状态标志位，同时也需要把 PCB 放到新的就绪队列里。如果只做了前面这一件事、中间就开始进行进程切换和调度，就有可能导致 PCB 当中记录的状态标志，和 PCB 实际放置的位置（就绪队列还是阻塞队列）不相匹配。这种数据的不匹配可能会给系统造成安全隐患，所以原语或者说原子操作的中间过程，绝对不能允许进行进程切换。

#### 内核程序临界区不能调，普通临界区可以调

先聊一个暂时还没接触的概念：**临界资源**，指一个时间段内只允许一个进程使用的资源，各个进程需要**互斥**地访问它——你访问的时候我不能访问，我访问的时候你不能访问。**临界区**就是访问临界资源的那段代码，因此各个进程也只能互斥地进入临界区、互斥地执行这段代码。而**内核程序临界区**，一般就是用来访问某种内核数据结构的，比如进程的就绪队列。

当一个进程处于内核程序临界区、且这个临界区要访问就绪队列时，它在访问之前会把就绪队列**上锁**。如果这个进程还没有退出内核程序临界区，就意味着这个临界资源没有被解锁。而没有解锁的过程中如果发生进程调度，调度程序肯定需要访问就绪队列这个临界资源——它要从就绪队列里挑选进程、分配处理器。就绪队列还处于上锁状态，进程调度就没办法顺利进行下去。所以对于内核程序临界区访问的这些内核数据结构而言，如果它们没有被尽快释放，就会影响到操作系统内核的其他管理工作（进程切换就是其中之一）。因此在访问内核程序临界区期间不能进行调度和切换，必须让这个进程迅速、尽快地执行完临界区代码，完成对临界资源的访问后尽快解锁——只有这样，操作系统的其他内核管理工作才能继续有序进行。

而另一种情况：假如进程访问的是**普通的临界资源**，比如一台打印机。访问前会先上锁，打印机在打印完成之前，这个进程一直处于临界区内、保持着对打印机的访问，临界资源不会被解锁。但打印机是一种慢速的 I/O 设备——如果这种情况下不允许进程调度切换，那这个进程就得一直空等着打印机打印结束，空等的同时还霸占着 CPU，CPU 一直在空闲、没做任何有意义的事情。所以进程在访问普通临界资源、处于普通临界区当中时，**其实应该进行进程调度**：普通临界资源不会像内核数据结构那样直接影响操作系统内核的管理工作，为了增加系统的并发度、提高 CPU 利用率，访问普通临界区时是可以进行进程调度和切换的。

> **本讲真题辨析**：有一道 12 年的真题，某个选项说"进程在处于临界区时，不能进行处理器调度"——这个表述是**错误的**。正确的表述是"进程在操作系统**内核程序**临界区中不能进行调度与切换"。区别就在于上面分析的普通临界区与内核程序临界区之别（解析见文末题目节）。

#### 非抢占式与抢占式

有的操作系统只允许进程**主动**放弃处理机，不允许进程在运行过程中被迫被剥夺处理机资源；而有的操作系统允许在有更紧急任务需要处理时，强行剥夺当前运行进程的处理机资源。由"当前运行的进程是否可以被强行剥夺处理机资源"这个问题，引出了进程调度方式的两种分类：

**非剥夺调度方式**（非抢占式）：只允许进程主动放弃处理机——除非进程正常或异常地终止，或者它主动要求进入阻塞态，不然处理机会一直为当前运行的进程服务。这种方式规则简单，实现起来简单，系统管理的开销也更小；但缺点是没办法及时处理紧急任务，所以它只适合于早期的一些批处理系统。

**剥夺调度方式**（抢占式）：如果此时有一个更重要、更紧急的任务需要处理，当前执行的进程就会被暂停执行、被剥夺处理机资源，处理器分配给那个更重要更紧急的进程。它可以优先处理更紧急的进程，还可以让各个进程按时间片轮转的方式执行——时间片到了就强行剥夺当前进程的处理器资源。这种方式比较适合后来出现的**分时操作系统和实时操作系统**。

#### 进程切换：有代价的操作

进程调度的目的是为了进程切换，那两者有什么区别？**狭义的进程调度**指的是从就绪队列中选中一个要运行的进程——这个要运行的进程可以是刚刚才暂停执行的进程，也可以是另一个进程；如果选中的是另一个进程，就需要进行**进程切换**：之前的那个进程让出处理机、之后的进程占用处理机的过程。而有的题目当中出现"进程调度"，指的是**广义的进程调度**，包含了上面说的这两个步骤（先选中、再切换）。读题时遇到两种含义不要觉得奇怪，能分辨它是狭义还是广义的就可以了。

进程切换的过程主要完成两件事：第一，把原来正在运行的进程的各种数据**保存**下来；第二，把新进程的各种运行环境之类的数据**恢复**过来。运行现场的信息——程序计数器、程序状态字、各种数据寄存器——一般存放在 PCB 当中，所以"保存"就是存入 PCB，"恢复"就是从 PCB 当中读出这些数据、放到相应的寄存器里。

经过这个分析会发现：进程切换并不是一瞬间就能完成的，它需要付出一定的时间代价。所以我们**不能简单地认为进程切换越频繁，进程的并发度就越高**——切换过于频繁反而会导致整个系统效率降低，因为系统把大部分时间都花在了切换开销上，真正用于执行进程、推进进程的时间反而减少了。进程切换是有代价的，理解这一点对于理解之后的时间片轮转调度算法至关重要。

### 调度程序：它管两件事，什么时候被唤醒

调度器（调度程序）是操作系统内核当中非常重要的一个程序模块。一个进程会在就绪、运行、阻塞之间来回横跳，而其中"就绪→运行"和"运行→就绪"这两个状态的转换，就是由调度程序负责完成的。调度程序要决定两件事：**让谁去运行**——这取决于它采用的调度算法，先来先服务、短作业优先还是时间片轮转等等；**运行多长时间**——不同的进程可以给它分配不同的时间片大小。反正就是用来管调度的：当前运行的进程要不要让它下处理机？下了处理机之后，队列里的这些进程要让谁上处理机运行？

之前讲的"进程调度的时机"，可以换一种说法：**什么样的事件会触发调度程序开始工作**。有这么几种：

- **创建新进程**：就绪队列发生了改变，一变就有可能让新进程抢占当前正在运行进程的 CPU，所以调度程序会出来工作一下，检查一下要不要让这家伙上处理机；
- **进程退出**：正在运行的进程决定终结自己，处理机不就空闲了吗？调度程序得出来看一下接下来让谁上处理机；
- **进程阻塞**：同理，正在运行的进程阻塞了，也需要调度程序出来看一下接下来让谁上；
- **发生 I/O 中断**：有可能使某些阻塞的进程回到就绪态。同样，只要就绪队列一改变，调度程序就需要出来检查一下这个新就绪的进程应不应该上处理器、应不应该抢占。

另一点值得注意：如果采用的是**非抢占式**的调度策略，那么只有运行的进程阻塞或者退出的时候，才会触发调度程序的工作——平时只要这个进程还在运行，就没有必要频繁唤醒调度程序，因此非抢占式**不会由时钟中断来唤醒**调度程序。而**抢占式**策略下，只要就绪队列一改变，就必须检查一下新就绪的进程有没有可能抢占当前正在运行的进程——这个检查的动作就是由**时钟中断**触发的：每个时钟中断、或者每 k 个时钟中断，都例行地唤醒一下调度程序，让它检查此时就绪队列有没有新进程到达、需不需要抢占。

还有一个点：如果系统支持的不只是进程、还支持线程，那么调度程序调度的对象就变成了线程。在不支持内核级线程的操作系统当中，调度对象依然是进程；而支持内核级线程的系统，调度的对象就是内核级线程——**内核线程作为调度的基本单位，进程作为资源分配的基本单位**。

### 闲逛进程：调度程序永远可以选的备胎

如果就绪队列当中没有其他就绪进程的时候，调度程序就会选中**闲逛进程**让它上处理器运行——也就是说，实际的系统当中 CPU 永远不可能空闲：即便没有其他就绪进程，至少还有一个闲逛进程可以运行。就跟你没事干的时候喜欢抖腿一样，CPU 没事干的时候也需要闲逛嘛。

闲逛进程有这几个特性：

- **优先级最低**：在所有就绪进程当中它的优先级是最低的，但凡有其他任何一个就绪进程，肯定不会选择让它上处理机运行；
- **执行零地址指令**：我们在计组当中学过零地址的指令。闲逛进程通常就反复执行一些零地址指令——零地址指令意味着不需要访存，甚至不需要访问 CPU 里的任何一个寄存器，因此这种指令会让 CPU 的能耗比较低，闲逛的时候更省电、更不耗能；
- **每条指令周期末尾例行检查中断**：执行完闲逛进程的每一条指令之后，指令周期的末尾会例行检查中断，这个中断就可以周期性地唤醒调度程序，让它检查此时到底有没有其他就绪进程。有的话，就让闲逛进程下处理机、让其他进程上处理机。

闲逛进程是调度程序永远可以选择的一个**备胎，不离不弃**。知道它的作用和特性就行，这种考点大概率只会在选择题当中出现。

### 评价调度算法的五把尺子

这一节学习一系列用于评价调度算法好坏的指标，包括 CPU 利用率、系统吞吐量、周转时间、等待时间和响应时间。学习过程中要注意理解各个指标**为什么这么设计**，并且要会**计算**每一个指标。

#### CPU 利用率与系统吞吐量：站在计算机的角度

早期计算机的造价很昂贵，特别是 CPU 这个部件，占了造价的很大一部分——基本上就是用钱堆出来的一个很奢侈的东西。即便在现在的计算机里 CPU 也不便宜。正因为 CPU 这么贵，人们就希望让它尽可能多地为人工作，于是设计了 **CPU 利用率**这个指标，表示 CPU 处于忙碌的时间占总时间的比例：

$$CPU\ 利用率 = \frac{CPU\ 忙碌的时间}{总时间} \times 100\%$$

有的题目不只让算 CPU 利用率，还会让算某种设备的利用率，比如 I/O 设备。举个单道程序的例子：某计算机只支持单道程序，有个作业刚开始需要在 CPU 上运行 5 秒，然后打印输出 5 秒，之后再执行 5 秒然后结束。整个过程总耗时是 $5+5+5=15$ 秒；CPU 忙碌的时间是前 5 秒加后 5 秒共 10 秒，所以 CPU 利用率是 $10/15 \approx 66.66\%$；打印机忙碌的时间是中间那 5 秒，打印机利用率是 $5/15 \approx 33.33\%$。

不过真正的考研题目通常考察**多道程序并发执行**的情况，这种题目可以用**甘特图**来辅助计算——这里先不展开，课后习题会遇到并有相应的讲解。

计算机肯定希望用尽可能少的时间处理完尽可能多的作业，于是有了**系统吞吐量**这个指标，表示单位时间内完成了多少道作业：

$$系统吞吐量 = \frac{总共完成了多少道作业}{总共花了多少时间}$$

比如某计算机处理完 10 道作业花了 100 秒，吞吐量就是 $10 \div 100 = 0.1$ 道/秒，平均每秒完成 0.1 道作业。

#### 周转时间家族：站在用户的角度

对用户来说，最关心自己的作业从提交到完成总共花了多少时间——越少越好。**周转时间**指从作业被提交给系统开始，到作业完成为止的这段时间。它总共包括四个部分：作业在外存后备队列上等待作业调度的时间、进程在就绪队列上等待的时间、进程处于运行态的时间、进程处于阻塞态的时间。注意后三项（就绪、运行、阻塞）在整个作业处理过程中会发生**多次**，而作业调度整个过程只会发生一次。计算上很简单：

$$周转时间 = 作业完成时间 - 作业被提交给系统的时间$$

操作系统更关心系统整体的表现，所以有**平均周转时间**：

$$平均周转时间 = \frac{各作业周转时间之和}{作业数}$$

再想一个问题：各个用户提交的作业，有的运行时间长、有的运行时间短。在周转时间相同的情况下，实际运行时间更长的那些作业，用户的感受肯定稍微更好一些。举个很直观的、有味道的例子——排队等厕所：你本来只需要使用一分钟，但要排队排十分钟，整个周转过程总共花了 11 分钟，这种感受肯定很糟糕——本来就只需要用一会儿，却要等那么长时间；而对另一个人来说，他总共需要使用十分钟，但只需要等一分钟，他的周转时间也是 11 分钟，只不过这 11 分钟里只有一分钟是用来等待的，所以这一分钟的等待对他来说感受没那么糟糕。

所以在周转时间相同的情况下，实际运行时间的长短不同，带给用户的感受就不同。因此人们又提出了**带权周转时间**：

$$带权周转时间 = \frac{作业周转时间}{作业实际运行的时间}$$

由这个式子可以看出两点：周转时间相同的两个作业，实际运行时间更长的那个，被服务的时间所占比例更大，带权周转时间更小、用户满意度更高；实际运行时间相同的两个作业，周转时间短的那个满意度更高，相应的带权周转时间也更小。并且**带权周转时间肯定大于等于 1**——因为周转时间包含了实际运行时间，肯定比它大。和周转时间一样，带权周转时间也是越小越好；同样地也有**平均带权周转时间**（各作业的带权周转时间加和再除以作业数），这是系统会比较关心的指标。这几个是本节比较容易忘记的指标，结合上面那个有味道的例子来理解"为什么这么设计"，理解了其实就不难了。

#### 等待时间与响应时间

用户肯定希望自己的作业尽可能少地等待处理机，**等待时间**就是用来度量作业等待处理机被服务的时间之和——等待越长，满意度越低。

当一个作业刚被提交时，它先被放到外存中的作业后备队列，等待被作业调度；被调度后放入内存、建立进程；进程建立之后会被 CPU 服务、也会被 I/O 设备服务，当然也有等待被服务的时间；直到最后进程结束、作业移出内存。这里有个容易搞错的点：进程**等待 I/O 完成的期间，它正在被 I/O 设备服务**，所以这种时间**不能算到等待时间里**。另外，对作业而言，不仅要算建立了进程之后的一系列等待时间，还要**加上它在外存后备队列中等待被调度的那段时间**——所以作业的等待时间和进程的等待时间计算起来有些不同，稍微注意一下。

通过之后的课后习题你会发现一个现象：一个作业总共需要被 CPU 服务多久、被 I/O 设备服务多久，这些总时间一般来说是**确定不变**的——所以调度算法其实只会影响作业或进程的**等待时间**。和前面的指标一样，等待时间也有对应的**平均等待时间**（所有进程或作业的等待时间加和再除以作业数）。

最后一个指标是**响应时间**：用户提交了一个请求——比如在键盘里输入了一个调试命令——肯定希望尽早被系统服务、被回应。**响应时间**指的就是从用户提出请求到**首次产生响应**所用的时间。

### 本讲提到的题目

**12 年真题选项辨析**："进程在处于临界区时，不能进行处理器调度。"——该表述**错误**。

解析：正文中已明确分析过，临界区分两种。若是**内核程序临界区**（访问就绪队列等内核数据结构），在退出前临界资源处于上锁状态，此时进行调度会因无法访问就绪队列而无法顺利进行，还会影响操作系统内核的其他管理工作，所以不能调度与切换；但若是**普通临界区**（比如访问打印机这种慢速 I/O 设备），不允许调度反而会让进程霸占 CPU 空等、降低 CPU 利用率，为了增加系统并发度，这种情况是**可以**进行进程调度和切换的。所以"处于临界区就不能调度"一概而论是错的。

## 三种批处理调度算法：先来先服务、短作业优先、高响应比优先
> 对应块：BLK09 | 覆盖分集：P24 | 块标题（分集名）：《2.2.5_1 调度算法：先来先服务、最短作业优》

这个小节我们学三种调度算法：先来先服务（FCFS）、短作业优先（SJF）和高响应比优先（HRRN）。学习每一种算法时，我们都会按照同一套框架来分析，先把这套框架立起来，后面三个算法就能一个模子套到底。

### 分析一种调度算法的框架

拿到一个调度算法，我们从六个角度依次过一遍：

1. **算法提出**：它是想解决什么问题、出于什么目的被提出的；
2. **算法规则**：出于这个目的，它采用了什么样的规则；
3. **适用场景**：它到底用于作业调度还是进程调度？用在两者时有没有什么区别；
4. **抢占与否**：它有没有抢占式的版本和非抢占式的版本——这就是之前介绍调度方式时强调的两个知识点；
5. **优缺点**：考试选择题里经常考察各个算法的优点和缺点，这个很重要；
6. **是否饥饿**：它有没有可能导致"饥饿"的问题。

饥饿这个概念之前还没提过，其实很简单：**如果一个进程或者一个作业长期得不到服务，那它就处于饥饿的状态。**

后面每一个算法都按这六条来过，大家自己复习的时候也可以照这个框架来回忆。

### 先来先服务（FCFS）

#### 思想与规则

先来先服务的思想，其实和我们日常生活中排队买东西特别类似，主要是从**公平**的角度来考虑的。跟它的名字一样：先到达就绪队列（或后备队列）的进程或作业，就先为它服务。

这里有一个小小的、但考试爱考的区别：

- **用于作业调度**时，考虑的是哪个作业**先到达后备队列**——后备队列是在外存中的，上一个小节刚强调过；
- **用于进程调度**时，考虑的是哪个进程**先到达就绪队列**——就绪队列是在内存中的。

先来先服务一般是**非抢占式**的算法：对于当前正在占用处理机的那个进程或作业，只有它**主动放弃**处理机的时候，才会进行调度，才会用这个算法的规则去挑下一个得到服务的进程。

#### 例题：算一遍四个指标

直接看一个例子会更容易理解。有 P1 到 P4 四个进程，到达时间和运行时间如下（时间单位当成秒或毫秒都可以，无所谓）：

| 进程 | 到达时间 | 运行时间 |
| :---: | :---: | :---: |
| P1 | 0 | 7 |
| P2 | 2 | 4 |
| P3 | 4 | 1 |
| P4 | 5 | 4 |

先来先服务的规则很简单：按到达的先后顺序依次调度。反过来说，它事实上考虑的是哪个进程**等待的时间更长**——等待时间越久的进程就越优先得到服务。P1、P2、P3、P4 依次在 0、2、4、5 到达，所以调度顺序就是 P1 → P2 → P3 → P4，甘特图长这样：

```text
0        7      11   12       16
|-- P1 --|-- P2-|-P3-|-- P4 ---|
```

P1 从 0 时刻开始运行 7 个时间，之后 P2 运行 4 个，P3 运行 1 个，P4 运行 4 个。

下面计算评价指标。**周转时间** = 完成时间 − 到达时间：P1 在 7 时刻完成、0 时刻到达，周转时间就是 7；P2 在 11 完成、2 到达，周转时间 11 − 2 = 9；P3、P4 同理。

**带权周转时间** = 周转时间 ÷ 运行时间：P1 周转时间是 7、运行时间也是 7，所以带权周转时间是 1；其余几个同样处理。

**等待时间**在这道题里比较简单，可以直接用周转时间减掉运行时间——把上面那排式子的除号统统换成减号就行。

| 进程 | 完成时间 | 周转时间 | 带权周转时间 | 等待时间 |
| :---: | :---: | :---: | :---: | :---: |
| P1 | 7 | 7 | 1 | 0 |
| P2 | 11 | 9 | 2.25 | 5 |
| P3 | 12 | 8 | **8** | 7 |
| P4 | 16 | 11 | 2.75 | 7 |

平均周转时间 8.75，平均带权周转时间 3.5，平均等待时间 4.75——把各自那一列加起来除以进程个数 4 就行。

> **易错点**：等待时间 = 周转时间 − 运行时间，这个公式**不是一成不变的**。这道题里四个进程都是**纯计算型**的进程，只需要 CPU 为它们服务，所以一个进程到达之后只可能处于两种状态：要么在等被调度，要么在运行，周转时间减运行时间剩下的自然就是等待时间。但如果题目给的是**既有计算又有 I/O 操作**的进程，等待时间就得用周转时间，减去它在 CPU 上运行的时间，**再减去 I/O 设备为它服务的时间**，这样得到的才是真正的等待时间。要具体问题具体分析，课后习题遇到这种例子自己巩固一下。

#### 优缺点：对谁有利？

看表里 P3 那一格：它的带权周转时间算出来是 8，非常大的一个值。带权周转时间表示的是"整个周转时间比运行时间大多少倍"，这么大的值意味着：这个进程本来只需要很少的服务时间，却要等很久才能被处理完。对于 P3 的用户来说，体验就特别糟糕。

所以先来先服务的**优点**很直白：公平，而且实现起来简单。**缺点**就是刚才看到的：排在长作业（长进程）后面的短作业（短进程）要等很久才被服务，短作业用户体验糟糕——**它对长作业有利，对短作业不利**。

来个更感性的体验：你到奶茶店排队买奶茶，店里的规则一般就是先来先服务。可你前面突然冒出一个人要买 20 杯，店里做这 20 杯要半个小时；你只买一杯，做你的奶茶只要一分钟——但因为前面突然出现了一个"长作业"，你这个"短作业"的体验就特别糟糕。你可以算一下，你的带权周转时间会特别特别大。什么叫对长作业"有利"、对短作业"不利"，这样一讲应该就有体感了。

至于饥饿：先来先服务**不会导致饥饿**。因为不管哪个作业，只要一直等着，它前面的那些作业或进程总会被处理完，它迟早轮得到。

### 短作业优先（SJF）

#### 提出的目的与规则

从刚才的例子我们已经知道，先来先服务在带权周转时间、平均等待时间这些指标上不太优秀。短作业优先算法的提出，就是为了追求**更少的平均等待时间、平均周转时间和平均带权周转时间**。

它的规则也很简单：最短的作业（进程）优先得到服务。这里的"最短"，指的是要求被服务的**时间最短**的那个优先。

- 用于**作业调度**时叫短作业优先，缩写 SJF，J 指的是 job；
- 同样的规则用于**进程调度**时，一般称为**短进程优先**（SPF），P 指的是 process。

短作业优先默认是**非抢占式**的，但它也有抢占式的版本，称为**最短剩余时间优先**（SRTN）。下面用同一道例题把这两种版本各跑一遍，看看区别。

#### 非抢占式的短作业优先

还是刚才那道题，改用非抢占的短作业优先来跑。严格来说，例题给的是进程调度的场景，应该说"非抢占式的**短进程优先**调度算法"；不过很多题目也不会太在意这个细节，只要知道两者的规则一样——按要求服务时间（运行时间）排优先级——就可以了。

规则是：**每次调度时，选择当前已经到达的、并且运行时间最短**的作业或进程，为它分配处理机。注意"当前已经到达"这个限定。

- 0 时刻：只有 P1 到达，没得挑，P1 上处理机；
- 7 时刻 P1 运行完：其余进程全部已到达，P3 要求的运行时间最短（1），所以第二个调度 P3；
- 8 时刻 P3 运行完：剩 P2 和 P4，两者运行时间一样（都是 4），但 P2 先到达就绪队列，所以优先调度 P2；
- 最后是 P4。

```text
0        7  8       12       16
|-- P1 --|P3|-- P2 --|-- P4 --|
```

结合图和到达时间，可以很快算出每个进程的周转时间、带权周转时间和等待时间（建议自己动手算一遍）：

| 进程 | 完成时间 | 周转时间 | 带权周转时间 | 等待时间 |
| :---: | :---: | :---: | :---: | :---: |
| P1 | 7 | 7 | 1 | 0 |
| P3 | 8 | 4 | 4 | 3 |
| P2 | 12 | 10 | 2.5 | 6 |
| P4 | 16 | 11 | 2.75 | 7 |

和先来先服务对比：

| 指标 | 先来先服务 | 非抢占短作业优先 |
| :---: | :---: | :---: |
| 平均周转时间 | 8.75 | 8 |
| 平均带权周转时间 | 3.5 | 2.56 |
| 平均等待时间 | 4.75 | 4 |

三项指标全部下降——短作业优先在这些方面的表现优于先来先服务。

#### 抢占式的短作业优先：最短剩余时间优先（SRTN）

抢占式的短作业优先还有另一个名字：**最短剩余时间优先**（SRTN）。它是抢占式的，所以每当有**新进程进入就绪队列**、就绪队列发生改变时，就要算一算：新来的进程的**剩余时间**，是不是比当前正在运行的进程的剩余时间更短？更短的话，就让新进程抢占处理机，被抢占的那个回到就绪队列。另外，当当前运行的进程**主动放弃处理机**（正常完成）的时候，也要用这个规则重新调度。

所以这种算法要盯住两个时间点：**就绪队列改变的时候**，以及**一个进程完成的时候**。按这个规则逐时刻分析：

- **0 时刻**：只有 P1 到达，P1 的剩余时间是 7，P1 上处理机；
- **2 时刻**：P2 到达，就绪队列改变。P1 已运行 2 个时间，剩余 5；新来的 P2 剩余 4。P2 更短，P2 抢占处理机，P1 回就绪队列；
- **4 时刻**：P2 还没做完，但 P3 到达。P3 剩余 1，比其他所有进程都少，P3 被抢占处理机；
- **5 时刻**：P3 正常完成，同时 P4 也在 5 时刻到达。此时就绪队列里有 P1（剩 5）、P2（之前只运行了 2 个，剩 2）、P4（剩 4），P2 剩余最短，P2 上处理机；
- **7 时刻**：P2 把剩余的 2 个时间跑完，正常完成。剩 P1（5）和 P4（4），P4 剩余最短，P4 上处理机；
- **11 时刻**：P4 完成，最后才轮到 P1 把剩下的 5 个时间跑完。

```text
0   2    4  5    7        11      16
|P1 | P2 |P3| P2 |-- P4 ---|-- P1 -|
```

要注意，抢占式的短作业优先里，进程的执行可能是**断断续续**的——P1 被切成了两段，P2 也是两段，这和前面两种算法不太一样，算指标的时候别踩坑。

| 进程 | 完成时间 | 周转时间 | 带权周转时间 | 等待时间 |
| :---: | :---: | :---: | :---: | :---: |
| P1 | 16 | 16 | $16/7 \approx 2.29$ | 9 |
| P2 | 7 | 5 | 1.25 | 1 |
| P3 | 5 | 1 | 1 | 0 |
| P4 | 11 | 6 | 1.5 | 2 |

把非抢占式短作业优先得到的三个指标放在一块儿对比：采用抢占式的短作业优先（最短剩余时间优先）之后，平均周转时间、平均带权周转时间、平均等待时间这三个指标比非抢占式的**还要更小**——抢占式版本在这些方面的表现优于非抢占式版本。这道题里平均周转时间是 7、平均等待时间是 3，都进一步降低了。

#### 关于"最短"的三个细节

例题做完了，抢占式和非抢占式怎么做题应该有直观理解了。但除了做题，还有几个小细节要注意。

**第一，默认非抢占。** 题目里提到"短作业优先"或"短进程优先"算法时，默认指的是**非抢占式**的。

**第二，书上那句话不严谨。** 很多书上（包括王道书）会写这样一句：短作业优先算法得到的平均等待时间和平均周转时间最少。但根据刚才的计算，最短剩余时间优先算法得到的这两个指标还要更少——所以这句话严格来说是**错误、不严谨**的。要让它严谨，得加个条件：

> **结论**：在**所有进程同时可运行**（或者说所有进程**几乎同时到达**）时，采用短作业优先调度算法，得到的平均等待时间和平均周转时间最少。

为什么要用"几乎"这种表述？因为进程的到达肯定还是有先后顺序的，只不过宏观上看，连续、快速到达的那些进程可以认为是几乎同时到达；它们事实上有先后顺序，只是微观上的事。

或者不加这个条件，换一种说法：**抢占式的**最短剩余时间优先算法，得到的平均等待时间和平均周转时间最少——这个是没有问题的。数学基础好的同学可以试试看，能不能证明它为什么最少。

**第三，考试里"比烂"的技巧。** 虽然短作业优先的平均等待时间、平均周转时间不一定最少，但相比先来先服务、高响应比优先这些算法，它仍然能获得**比较少**的平均等待时间和平均周转时间。所以有的选择题会遇到"短作业优先的平均等待时间和平均周转时间最少"这样的选项——遇到时一定要再看看其他三个选项是不是有很明显的错误，如果别的选项都错得很明显，那也可以选它、认为它正确。

操作系统这门课不像物理、数学那些基础理学学科，很多概念和算法的说法、定义，不同版本的教材会有所不同，并没有一个很严格的说法。做课后习题时你可能会发现讲解和习题说法不完全一致、前后有那么一点点矛盾——要学会适应这种情况，考试时判断所有选项，选一个**错误更少、更合适**的。

#### 优缺点与饥饿

短作业优先的**优点**："最短"的平均等待时间和平均周转时间——这个"最短"为什么打双引号，前面已经讲清楚了，遇到时知道那句话不严谨这个细节就行。

**缺点**也很明显：对短作业有利、对长作业不利。如果就绪队列中**源源不断地有更短的作业到来**，长作业就可能一直排不上队，产生**长作业饥饿**的现象。

还有一层：作业或进程的**运行时间是用户提供的数据**。用户可以把自己本来应该是长作业的运行时间写得很短——所以短作业优先这种算法，事实上**并不一定真能做到短作业优先**这件事。

至于饥饿：**会导致**。而且如果一个进程或作业是**一直**得不到服务，这种更严重的饥饿现象，就叫进程**饿死**或作业**饿死**。

### 高响应比优先（HRRN）

#### 提出的动机：把等待时间和运行时间都顾上

回头看，先来先服务和短作业优先正好是两个极端：

- 先来先服务每次调度只考虑**等待时间**——谁等得久谁先来，至于每个作业的运行时间是长是短，它并不关心，所以对长作业友好、对短作业不友好；
- 短作业优先只考虑**（估计的）运行时间**——每次都挑估计运行时间最短的，完全不管每个进程到底等了多长时间，所以对长作业不友好，甚至导致长作业饥饿。

那能不能设计一种算法，**既考虑每个作业的等待时间，又兼顾它的运行时间**？人们就按这个想法提出了**高响应比优先**算法。

#### 规则与响应比公式

它的规则相对复杂一些：每次调度时，计算**当前已到达**的各个进程或作业的响应比，选**响应比最高**的为它服务。响应比的定义是：

$$响应比 = \frac{等待时间 + 要求服务时间}{要求服务时间}$$

从这个式子能立刻看出，**响应比一定大于等于 1**：要求服务时间在分子分母里都出现，分子还多了一个正的等待时间，所以分子肯定比分母大。

这个算法既可以用于作业调度，也可以用于进程调度，一般是**非抢占式**的——只有当一个作业或进程**主动放弃处理机**时（正常或异常完成终止，或者进程主动要求阻塞），才需要用它来计算各进程的响应比。

#### 例题：还是那道题

进程的到达时间和运行时间还是一样，改用高响应比优先。这道题里全是纯计算型进程，不会有 I/O 操作，也就不会主动要求阻塞，所以只需要盯"进程完成"这一个时机。

- **0 时刻**：就绪队列里只有 P1，管它响应比是多少，肯定是 P1 上处理机。非抢占式，P1 要跑满 7 个时间、主动放弃 CPU 时才会进行第二次调度；
- **7 时刻**：就绪队列里有 P2、P3、P4。P2 从 2 到达等到 7，等待了 5 个时间，要求服务时间是 4，响应比 $\frac{5+4}{4} = 2.25$。P3、P4 同样算，会发现 **P3 的响应比最高**，P3 上处理机；
- **8 时刻**：P3 只跑 1 个时间就完成了。还剩 P2 和 P4，按同样的规则再算，**P2 的响应比更高**，P2 上处理机；
- **12 时刻**：P2 执行完，就绪队列里只剩 P4，不用算响应比了，P4 直接上处理机。

整个过程是 P1 → P3 → P2 → P4。

这里有个值得玩味的地方：响应比公式是 $\frac{等待时间 + 要求服务时间}{要求服务时间}$，而 P2 和 P4 的要求服务时间（运行时间）相等，都是 4。既然 P2 先到达就绪队列，P2 的等待时间就更大——分母相同、分子更大，P2 的响应比自然更高。每个时刻都是这样：7 时刻 P2 是 2.25、P4 是 1.5；8 时刻 P2 是 2.5、P4 是 1.75。等待久的那个总会胜出。

#### 为什么说它是折中的优等生

高响应比优先**综合考虑了等待时间和要求服务时间**，等于把前两个算法的优点各取了一半：

- 两个进程**等待时间相同**时，要求服务时间更短的那个响应比更大，会优先——这是短作业优先的优点；
- 两个进程**要求服务时间相同**时，等待时间更长的那个响应比更大，会优先——这是先来先服务的优点。

对一个长作业来说，随着等待时间越来越大，它的响应比也会越来越大，被调度的机会越来越高——所以这个算法**避免了短作业优先造成的长作业饥饿问题，不会导致饥饿**。

### 三种算法放在一起看

三个算法按同一套框架过完了，规则和做题方法大家要能自己回忆出来。这里从整体上再串一遍：

| 角度 | 先来先服务 | 短作业优先 | 高响应比优先 |
| :---: | :---: | :---: | :---: |
| 调度时看什么 | 等待时间（谁等得久） | 要求服务时间（谁最短） | 响应比（等待与运行兼顾） |
| 是否抢占 | 非抢占 | 默认非抢占（抢占版为 SRTN） | 非抢占 |
| 对长/短作业 | 长作业有利、短作业不利 | 短作业有利、长作业不利 | 两者兼顾、相对折中 |
| 会不会饥饿 | 不会 | 会（严重时饿死） | 不会 |

这三种算法其实主要关心的是对用户作业或用户进程的**公平性**问题——像先来先服务要求的是绝对公平；同时它们追求平均周转时间、平均等待时间这些**评价系统整体性能**的指标。所以这三种算法**不关心响应时间，也不区分各种任务的紧急程度**，对用户来说交互性基本没有、特别糟糕。它们一般用在**早期的批处理系统**当中——那个阶段计算机很昂贵，人们更追求系统的整体表现，而不是各个用户的用户体验，这也是情有可原的。

其中先来先服务虽然老，但现在也经常会**结合其他算法一起使用**，在今天仍扮演着重要角色。批处理系统的调度算法之外，下一小节我们会继续介绍适用于**交互式系统**的调度算法。

最后强调一句：学这个小节和下一小节的调度算法，**一定要尝试动手画一画、算一算**——那几张甘特图和指标表，光看懂不算会。I/O 型进程"等待时间 = 周转时间 − 运行时间 − I/O 服务时间"的变形，课后习题遇到时自己巩固。
