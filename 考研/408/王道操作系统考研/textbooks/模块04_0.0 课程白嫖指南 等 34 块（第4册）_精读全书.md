## 文件的基本操作与文件共享
> 对应块：BLK28 | 覆盖分集：P67-P68 | 块标题（分集名）：《4.1_7_文件的基本操作》

平时在电脑上点一下右键、新建一个文本文档，看似只是鼠标的一下单击，背后其实是操作系统在替我们干活。这一讲我们就把文件的几种基本操作——创建、删除、打开、关闭、读、写——逐个拆开，看看每一次点击背后系统调用到底做了哪些事；后面再讲一个大家可能不太熟悉的主题：操作系统是怎么让多个用户共享同一个文件的。

### 创建文件：create 系统调用

先从最熟悉的操作说起。在某个文件夹下右键新建一个 txt 文本文档——点了"新建"之后，背后其实就是调用了操作系统的 create 系统调用。

发起 create 系统调用时，需要提供几个参数：

- **外存空间大小**：新建的文件需要占用多大的外存空间。比如一个盘块是 1 KB，这次申请的就刚好是一个盘块、1 KB 这么大小的空间；
- **存放路径**：文件放在哪里，比如 D 盘的 demo 目录下；
- **文件名**：这个文件叫什么名字。

在 Windows 里右键新建文本文档时，这些参数是系统在背后自动帮我们填好的，文件名默认就是"新建文本文档.txt"。大家可以动手去自己的电脑上试一下。

操作系统接收到 create 请求后，主要做两件事：

> **定义**：create 系统调用的处理流程是——① 在外存中找到并分配文件申请的磁盘空间；② 在文件存放路径对应的目录表中插入该文件的目录项。

第一件事是**分配存储空间**。这里可以结合上一小节学的空闲表法、空闲链表法、位示图法、成组链接法等管理策略来思考：为文件分配存储空间到底是个什么样的流程。管理策略不同，分配时需要做的事情、用的算法也不一样——这正是上个小节介绍的内容。

第二件事是**插入目录项**。既然文件放在某个文件夹（目录）下，就需要找到这个目录对应的目录表，在其中插入该文件的目录项，目录项里要包含文件名、文件的存放位置等信息——这是文件目录那个小节讲过的内容。

### 删除文件：delete 系统调用

删除文件和创建文件刚好是相反的过程。右键删除一个文件时，背后调用的是 delete 系统调用，需要提供的参数有两个：文件的存放路径（D 盘的 demo 目录下）、文件名（test.txt）。

操作系统收到请求后的处理流程，正对着创建过程倒着走一遍：

1. 根据**存放路径**找到 demo 目录对应的目录表；
2. 根据**文件名**在目录表中找到对应的目录项——找到了目录项，就知道这个文件在外存中存放在什么位置、占用了哪些磁盘块，于是根据这些信息**回收文件占用的磁盘块**（回收时同样按空闲表法、空闲链表法等不同策略做不同处理）；
3. 磁盘块全部回收之后，把目录表中对应的**目录项也删除**。

### 打开文件：open 系统调用

接下来是一个大家可能不太熟悉的操作。在很多操作系统当中，对文件进行操作之前，都要求先用 open 系统调用把文件"打开"。

发起 open 系统调用时需要提供三个参数：

- 文件的**存放路径**；
- **文件名**；
- 对文件要进行哪些**操作类型**——比如只打算读，还是既可能读也可能写。想进行的操作类型不同，提供的参数也不同。

操作系统处理 open 时主要做两件事：

> **定义**：open 系统调用的处理流程是——① 按路径找到目录表，并根据目录项**检查用户的操作权限**；② 检查通过后，把该文件的**目录项复制到内存中的打开文件表**。

第一步，根据提供的存放路径在外存中找到目录对应的目录表。注意，不同用户对文件的操作权限是不一样的：有的用户只可以读这个文件，有的用户既可以读也可以写。这些访问权限信息就记录在目录项当中，所以可以根据目录项检查此时用户请求的操作是否合法——如果用户没有这种操作的权限，就拒绝打开、终止处理。

第二步，如果权限检查通过，操作系统会把文件对应的目录项**复制到内存中的打开文件表**。这一步的意义很大：文件打开之后，文件相关的信息就已经放到内存里了，之后用户再想操作这个文件，只需要根据打开文件表的编号就能找到想要操作的这个文件的一切信息，**不需要每次查文件都重新访问目录**。因此，把目录项复制到打开文件表，可以大幅度地提升文件访问的速度。

#### 两种打开文件表

这里要特别注意：内存中有**两种**打开文件表。

- **系统的打开文件表**：整个系统只有一张，记录所有正在被进程使用的文件的信息；
- **进程的打开文件表**：每个进程都有自己的这张表，只记录自己此时已经打开了哪些文件。

进程的打开文件表中，会有一个指向系统表表项的索引号。看个示意图：

```text
进程 A 的打开文件表            系统的打开文件表（全系统仅一张）
+----------------+           +------+----------------------+
| fd（索引号）= k  |----+      | 编号 k | test.txt 及文件属性   |
+----------------+    |      |      | 打开计数器 = 2        |
进程 B 的打开文件表     |      +------+----------------------+
+----------------+    |         ^  ^
| fd（索引号）= k  |----+---------+  |
+----------------+                 |
其他进程的打开文件表                 |
+----------------+                 |
| fd（索引号）    |-----------------+
+----------------+
```

两个进程打开的是同一个文件 test.txt，所以它们各自的进程表表项都指向系统表中的同一个表项 k。这里有个**系统打开文件表特有的字段**——**打开计数器**，用来记录这个文件此时已经被几个进程打开了。现在有两个进程打开了它，计数器就是 2。

设置这样一张全系统的总表，能很方便地实现一些文件管理功能。举个例子：在 Windows 里，如果你要删除某个 txt 文件，而这个文件已经被某个记事本进程打开了，系统会提示你"暂时无法删除该文件"。大家可以自己动手试一下。系统在背后做的事就是：当你选择删除文件时，先查一下系统打开文件表，看这个文件是否已经被某个进程打开——如果正在被使用，文件的数据显然暂时不能删除。有了这张总表，这类功能实现起来就非常方便。

#### 进程打开文件表里的两个特殊字段

在进程的打开文件表中，还有两个比较特殊的字段：

- **读写指针**：记录这个进程对文件进行读写操作，此时进行到了什么位置。不同进程对同一个文件读写的进度是不一样的，所以每个进程的读写指针也应该不一样；
- **访问权限**：标明这个进程对文件的访问权限。比如进程 A 打开 test.txt 时只声明了自己是只读，那如果它之后尝试对这个文件进行写操作，系统会检查它之前申请的访问类型——它只声明了只读，所以这个写操作会被拒绝，判定为不合法。不同进程打开文件时申请的访问类型不同，因此访问权限这个字段也应该放在进程的打开文件表中。

当然，除了这两个字段，进程打开文件表里还有其他文件信息，这里没有全部列举。

### 关闭文件：close 系统调用

用完一个文件选择关闭时，背后要做两件事：

> **定义**：close 的处理流程是——① 删除进程打开文件表中对应的表项，回收分配给该文件的内存缓冲区等资源；② 将系统打开文件表中对应表项的**打开计数器减一**，计数器减到零才删除系统表中的表项。

第一步，把进程自己的打开文件表中这个文件对应的表项删除，相应地回收分配给这个文件的内存缓冲区等一系列资源。

第二步，对系统打开文件表中对应表项的打开计数器做减一操作。此时如果打开计数器仍然大于零，说明文件还在被其他进程使用，系统打开文件表中的这个表项**暂时不能删除**；只有打开计数器变为零时，才需要删除系统表中的表项。这和硬链接共享方式里链接计数的思路如出一辙，后面还会见到类似的处理。

### 读文件与写文件：read 和 write 系统调用

**读文件**：双击打开 test.txt 这个文本文档时，背后其实是调用了操作系统提供的 read 系统调用。不过通过前面的讲解我们知道，对文件进行读写操作之前一定要先打开文件，所以正式开始读的时候，记事本这个进程的打开文件表当中已经有了这个文件对应的表项。因此 read 系统调用需要提供的参数是：

- 要读的**哪一个文件**——进程只需要指明这个文件在（进程）打开文件表中的编号是多少；
- 需要读入**多少数据**——比如要把这个文件全部 1 KB 的内容都读入内存，就指明读入 1 KB；
- 读入的数据要放在**内存中的什么位置**。

这些参数的填充，都是记事本这个应用程序在背后替我们完成的事情。操作系统处理 read 时，会根据打开文件表中**读指针**所指向的外存地址，读入用户指定大小的数据，放到用户指定的内存区域中。

**写文件**：操作和读文件很类似。编辑完一个文本文档之后点击"保存"，背后就是记事本帮我们调用了 write 系统调用，它的作用是把文件在内存中的数据写回到外存、保存起来。write 需要提供的参数同样是三个：写的是哪个文件（同样只给打开文件表的序号）、要写回多少数据（比如把内存中的 1 KB 全部写回外存）、这些数据在内存中的什么位置。操作系统根据这些参数，从用户指定的内存区域读出指定大小的数据，写到**写指针**所指向的外存区域中。

### 打开不等于读入：这一讲最要紧的几个考点

这个小节最需要注意的是**打开文件**这个操作，以及它和读文件的区别。这里有几条容易混淆的点，一定要分清：

> **易错点**：打开文件时**并不会把文件的数据直接读入内存**，只是把文件的目录项复制到内存的打开文件表当中。只有**读文件**的时候，文件的数据才会真正从外存读入内存。这一点是最容易混淆、也最容易在选择题里考的。

再看两个对比，帮大家把字段和职责归位：

| 字段 | 放在哪张表 | 为什么 |
| :-- | :-- | :-- |
| 打开计数器 | 系统打开文件表 | 统计的是文件总共被多少个进程打开，是全文件级别的信息 |
| 读写指针 | 进程打开文件表 | 每个进程读写进行到的位置各不相同 |
| 访问权限 | 进程打开文件表 | 每个进程打开文件时申请的访问类型各不相同 |

还有两个术语层面的提醒：

1. 系统会把打开文件表中的**索引号返回给用户**，之后用户就根据这个索引号查询打开文件表、直接操作文件，不再需要每一次都查询目录。这个索引号在有的教材上也称为**文件描述符**——这个概念在考试当中出现过，指的其实就是打开文件表的一个序号，大家要注意这个术语。
2. 对文件进行读写操作的时候，用户**不需要再提供文件名、文件路径**这些信息，只需要提供文件描述符（文件在打开文件表中的索引号），操作系统就知道要读要写的到底是哪一个文件了。

打开文件和读文件这两个操作，是最容易在选择题当中考察的，需要重点关注。

### 文件共享：先分清"共享"和"复制"

下面进入另一个话题：操作系统应该怎么实现文件共享的功能。用户可以使用操作系统提供的文件共享功能，方便地实现多个用户共享地使用同一个文件。实现方式有两种：

- **基于索引节点的共享方式**，又叫**硬链接**；
- **基于符号链的共享方式**，又叫**软链接**。

先用一个反例把概念掰清楚。**共享**意味着系统当中其实**只有一份文件数据**，只要某一个用户修改了这份文件数据，其他用户也能看到数据的变化。而与共享容易混淆的是**复制**：如果多个用户都复制了同一个文件，那系统里其实有好几份数据，其中一个用户修改了自己的那一份，其他用户的文件数据并不会受到影响。这就是共享和复制的区别。

### 硬链接：让多个目录项指向同一个索引节点

索引节点的知识是在之前文件目录的小节里介绍过的：它其实是一种文件目录的"瘦身"策略。由于按路径检索文件时只需要用到文件名，所以可以把除了文件名之外的其他信息都挪到索引节点中，目录项就变得更小，只需要包含文件名和一个指向索引节点的指针。

那这个瘦身策略能带来什么好处呢？正好在这里体现。假设用户 User1 创建了一个新文件 aaa，这个文件会对应一个索引节点，索引节点中包含文件的物理地址和文件相关的其他属性。另外，索引节点中还会设置一个叫做**链接计数**的变量（图中的 count），用于表示此时链接到这个索引节点上的用户目录项到底有多少个。

```text
User1 的目录                              User2 的目录
+-------------+                          +-------------+
| aaa | 指针 --|--------\        /--------| bbb | 指针 --|
+-------------+         v        v        +-------------+
                      +----------------------+
                      |       索引节点        |
                      | 物理地址、文件属性     |
                      | 链接计数 count = 2    |
                      +----------------------+
```

假设第二个用户 User2 也想共享使用这个文件，那么 User2 的目录当中也会有一个目录项指向这个文件的索引节点。此时有两个目录项指向这个索引节点，所以 count 的值要加一，变成 2——count 等于 2，就说明此时有两个用户正在共享地使用这个文件。

这就是硬链接的本质：**让不同用户的目录项指向同一个文件的索引节点**。而且注意一个细节：不同用户给这个文件起的名字可以不同——User1 的目录下它叫 aaa，User2 的目录下它叫 bbb，但指向的是同一个索引节点、同一份数据。

#### 硬链接下删除文件的细节

采用硬链接共享时，删除文件有一些小细节需要注意：

> **结论**：某个用户删除文件时，系统只是删除该用户目录中对应的目录项（断开这条链接），并把索引节点的 count 减一。**只有 count 减到零**，说明再没有任何用户使用这个文件，文件数据连同它的索引节点才可以真正从系统中删除；count 大于零时绝不能直接把文件数据干掉，否则其他用户手里的链接就成了悬空指针。

这正是这一讲要重点理解的地方：硬链接方式下删除文件，必须盯住 count，否则会导致指针悬空的情况。

### 软链接：记录路径的 Link 型文件

接着刚才的例子往下分析。假设 User1、User2 正在用硬链接方式共享文件一，现在另一个用户 User3 想用软链接的方式共享这个文件一。

User3 会建立一个新的文件，这是一种特殊的 **Link 型文件**，它里面记录的是文件一的**存放路径**。比如可以通过 `C:/User1/aaa` 这样的路径找到文件一——当然，存放路径也可以保存为 `C:/User2/bbb`，用这条路径同样能找到文件一。

```text
User3 的目录                        User1 的目录
+------------------+               +----------------+
| ccc（Link 型文件）|               | aaa | 指针 ----|---> 索引节点
+------------------+               +----------------+     (count = 2)
        |
        | 文件内容：记录文件一的存放路径 C:/User1/aaa
        v
  操作系统按此路径一层一层地查找目录，最终找到 aaa 的目录项，
  于是开始访问文件一
```

也就是说，软链接**并不是把自己的目录项直接指向这个文件的索引节点**，而是创建了一个新的 Link 型文件，Link 型文件当中记录了要共享的文件的存放路径，之后操作系统根据这个路径找到想要共享的那个文件。

这种 Link 型的文件，就很类似于 Windows 操作系统当中的**快捷方式**。看一个真实的例子：假设 QQ 程序安装在某个路径下，那个路径里有一个 QQ 的启动程序 .exe 文件。我们右键点击这个 .exe 文件，选择"发送到桌面快捷方式"，桌面上就会出现一个快捷方式，而且可以随便给它取名字。之后右键查看这个快捷方式的属性就会发现：它其实就是用软链接的方式——用一个路径——链接到了 QQ 的启动程序那里。双击桌面的快捷方式时，操作系统会判断它是一个快捷方式类型的文件，也就是一种 Link 类型文件，于是根据文件中记录的路径信息一层一层往下检索目录，最终找到 QQ 的启动程序。大家课余可以自己捯饬一下 Windows 快捷方式的属性，玩过之后就理解软链接到底是怎么回事了。

#### 软链接为什么慢，被删目标为什么失效

用软链接共享文件，有两个推论需要掌握：

第一，**删除共享文件会让软链接失效，但 Link 型文件本身依然存在**。假设 User1、User2 都不再需要文件一了，count 变成零，文件和它的索引节点就可以直接被删掉。此时如果 User3 再去访问 ccc 这个 Link 型文件，操作系统还是会先检查 C 盘下的 User1 目录，尝试从中找到 aaa 对应的目录项——但 aaa 的目录项已经被删除了，通过这个路径已经找不到文件一，因此这个软链接就失效了。对照 Windows 的例子：把路径下的 QQ 启动程序删掉之后，再双击桌面上的快捷方式，系统会提示"此快捷方式所指向的项目 QQLaunch.exe 已经删除"——本质就是通过软链接中记录的路径已经查不到对应的目录项了。注意，**Link 型文件自己还在**，只是沿路径查找会失败。

第二，**软链接访问共享文件的速度比硬链接更慢**。软链接每访问一次共享文件，都要按记录的路径一层一层地查询目录；而通过前面的讲解大家也知道，一层一层查询目录的过程是需要磁盘 I/O 操作的。硬链接是目录项直接指向索引节点，没有这个逐层检索的开销，因此软链接的访问速度更慢。

### 两种共享方式放在一起看

| 对比项 | 硬链接（基于索引节点） | 软链接（基于符号链） |
| :-- | :-- | :-- |
| 共享结构 | 多个用户的目录项直接指向同一个索引节点 | 新建 Link 型文件，内容是共享文件的存放路径 |
| 允许的文件名 | 各用户的目录项可以使用不同的文件名 | Link 型文件名字随意，类比快捷方式 |
| 删除共享文件 | count 减一，count 为零才真正删除文件数据和索引节点 | 文件可直接删除；Link 型文件仍在，但按路径查找会失败（链接失效） |
| 访问速度 | 快（目录项直达索引节点） | 慢（每次访问都要按路径逐层检索目录，伴随磁盘 I/O） |

重点掌握硬链接在删除文件时的处理——只有 count 变为零才可以真正删除文件数据和索引节点，否则会导致指针悬空；而软链接（符号链接）大家回去玩一下自己 Windows 的快捷方式，其实就可以理解了：它无非就是在 Link 型文件当中记录了要共享的那个文件存放的路径，操作系统根据这个路径一层一层查找目录，最终找到需要共享的文件。

> **承前启后**：上一节讲完「文件的基本操作与文件共享」，下一节接着讲「文件保护与文件系统的全局结构」。

## 文件保护与文件系统的全局结构
> 对应块：BLK29 | 覆盖分集：P69-P72 | 块标题（分集名）：《4.1_9_⽂件保护》

一个文件放在磁盘上，操作系统就得对它的安全负责。这一讲我们从"怎么保护一个文件"讲起——口令、加密、访问控制三条路各有各的账要算；然后换个视角，看看整个文件系统从上到下分成哪几层、每层干什么活；再从一个磁盘出厂那一刻讲起，看文件系统如何一步步在外存和内存里建立起来；最后遇到"一台电脑同时插着好几种文件系统"的现实问题，引出虚拟文件系统（VFS）和文件系统的挂载。这一整条线串下来，文件系统的全貌就齐了。

### 文件保护的三种方式

操作系统需要保护文件数据的安全，一般来说可以采用三种方法：口令保护、加密保护和访问控制。我们按顺序一个一个来学。

#### 口令保护：把口令存在 FCB 里

做法很直白：用户为自己的文件设置一个口令，比如 ABC112233。其他用户想访问这个文件，就必须提供相同的口令，由操作系统负责验证。

那正确的口令存在哪儿？一般来说，就存放在与文件相对应的 FCB 或者索引节点当中。验证的时候，操作系统从 FCB 里读出正确口令，和用户提供的口令对比，对上了就放行。

这种方式最大的优点就是**开销小**，而且小在两处：

- **空间开销小**：保存口令无非就是保存一个字符串；
- **时间开销也小**：你想访问一个文件，操作系统无论如何肯定要找到它对应的 FCB 或索引节点，顺手从中取出口令对比一下，几乎不花额外的时间。

但缺点也很致命：正确口令是存放在**系统内部**的。一旦有人入侵系统、拿到了正确口令，那这个人就可以畅通无阻地访问这个文件了。口令放在系统里，终归不够安全。

#### 加密保护：密码只在你自己脑子里

第二种方式是加密保护：用某个密码对文件进行加密，访问时用户需要提供正确的密码，才能把文件正确解密。

我们来看一个最简单的加密算法——**异或加密**。学过计组的话，大家对异或运算应该很熟悉：两个相同的二进制位异或，结果是 0；两个二进制位不同，异或结果是 1。

假设加密解密用的密码是 `01001` 这样一串二进制位，就用它和文件的原始数据**依次**做异或运算，得到加密结果 `01100`；然后再对接下来的五个二进制位重复这个过程，以此类推，把整个文件的数据都加密完。

所以系统中保存的其实**不是文件的原始数据**，而是加密之后的这一份。用户想访问文件就必须先解密，不然读出来就是一串没有意义的乱码。而解密过程说来有趣——还是用同一串密码对密文逐位异或，相同的位异或出 0、不同的位异或出 1，走一遍就还原了。你可以自己动手试一下，对比原始数据和解密之后的结果是否一致。总之，加密、解密用的是同一个密码时，异或两次就回到了原始数据。

> **提示**：异或运算天然满足"自己异或自己等于零"，所以同一个密码加密一次、再异或一次就是解密，这是异或加密能 reversible 的根源。

那如果用**错误的密码**解密会怎样？假设用户拿 `01111` 这么一个错误的密码来解密，最终解出来的结果和文件的原始数据就对不上了。也就是说，不知道加密解密密码的用户，是没办法正常访问文件数据的。

这种方式的好处就很明显了：**保密性强**，而且**不需要在系统当中存储密码**——密码只有用户自己记住。如果他想让别的用户也能访问自己的文件，把密码告诉对方就行。

不过缺点也很明显：加密和解密（也就是编码和译码）的过程，需要**花费一定的时间**。天下没有免费的午餐。

#### 访问控制：一张表管住每个用户能干什么

第三种方式叫访问控制。系统会在每个文件的 FCB 或者索引节点当中，增加一个**访问控制表**（Access Control List），记录各个用户可以对这个文件进行哪些操作。

要注意，**每一个文件都会有自己的一张访问控制表**。用户对文件执行的操作可以分成这样一些类型：读、写、执行、添加、删除、列表清单等等。不同系统对操作类型的划分不一样，这个地方不是很重要，大家自己看一下就可以。

举个例子：假设某个系统控制的操作类型就这几种，系统里有三个用户——父亲、母亲、儿子，那么某个文件的访问控制表可能就长这样（表中 1 表示允许，0 表示拒绝）：

| 用户 | 读 | 写 | 执行 | 添加 | 删除 | 列表清单 |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| 父亲 | 1 | 1 | 1 | 1 | 1 | 1 |
| 母亲 | 1 | 0 | 1 | 0 | 0 | 1 |
| 儿子 | 0 | 0 | 0 | 0 | 0 | 0 |

父亲可以对这个文件进行读、写、执行、添加、删除、列表清单等一系列操作；母亲只可以读、执行和列表清单，不能写、添加、删除；而儿子嘛，不可读、不可写，什么都不能干。

于是在这个系统中，某个用户请求访问某个文件时，操作系统就查一下这个文件的访问控制表，看这个用户有没有对应操作的权限，没有就拒绝访问——文件的安全性就这么保住了。

#### 用户太多怎么办：精简的访问控制表

上面这个例子是以**每个用户为单位**来标识权限的。但如果一台计算机上有很多用户，访问控制表就会变得很长很大。这个问题可以用**精简的访问控制表**来解决——以**组**为单位，标记各组用户可以对文件执行哪些操作。

比如把计算机的用户分成四个分组：系统管理员、文件主、文件主的伙伴、其他用户。每一个用户都会从属于其中的一个或者两个分组，操作系统也需要管理这些分组信息，记录哪个用户属于哪个分组。精简后的访问控制表就是四行：

| 分组 | 读 | 写 | 执行 | 添加 | 删除 | 列表清单 |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| 系统管理员 | 1 | 1 | 1 | 1 | 1 | 1 |
| 文件主 | 1 | 1 | 1 | 1 | 1 | 1 |
| 文件主的伙伴 | 1 | 0 | 1 | 0 | 0 | 1 |
| 其他用户 | 0 | 0 | 0 | 0 | 0 | 0 |

用户访问文件时，系统检查他**所属分组**是否有相应权限。如果文件主想给某个用户开"读"的权限，就把这个用户放进"文件主的伙伴"这个分组，他就能读文件了。

#### 到 Windows 上走一遍

访问控制不是纸面上的东西，Windows 就是这么实现的，我们可以亲手走一遍。

首先可以在"设置"里给自己电脑添加一个新的本地账户——比如建一个叫"临时访客"的账户，建完在"家庭和其他成员"里就能看到它，点开始菜单也能直接切换到这个用户。

然后随便打开自己电脑中的一个文件或文件夹，右键 → 属性 → "安全"页签，在这里就能看见 Windows 对各种用户的分组、以及各个用户访问控制的界面。以我的电脑为例，它默认分了四个分组，其中 users 分组中的用户对一个"照片"文件夹只可以进行三种操作，"写入"这类操作是不允许的。

还记得刚才创建的"临时访客"吗？如果不想让他访问"照片"文件夹，就点"编辑"按钮，点"添加"、输入"临时访客"、确定，列表里就出现了这个用户。接着把临时访客对照片文件夹**所有类型**的操作都设为"拒绝"。点确定之后，系统会弹出一条提示：

> **拒绝项优先于允许项**。

也就是说，临时访客本来属于 users 分组，users 分组本来是允许读取文件信息的；但我们又在临时访客这儿单独选择了拒绝读取。由于拒绝项的优先级高于允许项，所以虽然他也在 users 分组里，操作系统依然认为他不允许读取这个目录。

现在切换到临时访客，尝试打开"照片"文件夹——系统提示：当前用户无权访问该文件夹。系统在背后做的事情，其实就是找到了照片这个目录文件对应的 FCB，根据 FCB 当中记录的访问权限信息，判断临时访客到底有没有权限访问，最后发现没有，于是弹出这个提示框。

#### 三种方式放到一起比

最后把这三种方式放在一起比一比。

口令保护和加密保护是最容易混淆的一对，区分的关键在**密码存不存进系统**：

| 对比项 | 口令保护 | 加密保护 | 访问控制 |
| :--- | :--- | :--- | :--- |
| 正确口令/密码存放位置 | 存在系统内部（FCB 或索引节点中） | 不存入系统，只有用户自己知道 | 权限信息存在 FCB 或索引节点的访问控制表里 |
| 系统如何把关 | 验证用户提供的口令是否正确 | 用户用密码自行解密 | 查访问控制表核对操作权限 |
| 优点 | 保存和验证的开销都很小 | 保密性强，系统里没有密码可偷 | 能按操作类型精细划分权限，灵活 |
| 缺点 | 口令在系统内部，被入侵即失守 | 加解密要花一定时间 | 需要额外管理用户/分组与权限信息 |

再强调一点：口令保护和加密保护，只要用户拿到了口令或密码，就可以对这个文件执行**所有类型**的操作；而访问控制可以把操作分成不同类型，不同的用户执行不同类型的操作，所以它实现的文件保护**更灵活**，绝大多数现代操作系统都支持它。大家也可以自己动手去 Windows 下看看各个文件的安全属性，再动手捯饬一下，对这部分内容会有更深的理解。

> **易错点**：如果对某个目录进行了访问权限的控制，那么也需要对这个目录下面的所有文件进行相同的访问权限控制——就像"照片"文件夹的例子，一个用户不允许访问照片这个目录，他同时也不允许访问这个目录下的所有文件。

### 文件系统的层次结构

看完了"怎么保护文件"，我们升高一个视角：一次文件请求从用户出发，到磁盘落地，中间要经过哪几层？文件系统从上至下可以分成这样一些层次，每一层各管一段：

```text
+----------------------------------------------+
| 用户接口                                     |  ← 最接近用户和应用程序
+----------------------------------------------+
| 文件目录系统                                 |  ← 靠路径找 FCB
+----------------------------------------------+
| 存取控制模块                                 |  ← 验证访问权限
+----------------------------------------------+
| 逻辑文件系统与文件信息缓冲区                 |  ← 记录号 → 逻辑地址
+----------------------------------------------+
| 物理文件系统                                 |  ← 逻辑地址 → 物理地址
+----------------------------------------------+
| 辅助分配模块                                 |  ← 分配/回收存储空间
+----------------------------------------------+
| 设备管理模块                                 |  ← 最接近硬件，直接和设备交互
+----------------------------------------------+
```

从上往下逐层看。**最上面一层是用户接口**，它是最接近用户和应用程序的层次，主要功能就是向上层提供一些简单易用的功能接口，并负责处理用户和应用程序提出的系统调用请求——就是咱们之前介绍过的 read、write、open、close 等等这一系列。所以用户接口这一层要做的事情，其实就是"文件的基本操作"那个小节介绍的那些东西。

用户访问一个文件时，一般先提供一个**文件路径**。于是**文件目录系统**这一层就需要通过这个路径一层一层地找到文件对应的 FCB，也就是完成查询目录等一系列工作。所有和目录、目录项相关的管理工作都在这一层完成——比如管理活跃的文件目录表，还有管理**打开文件表**。为什么打开文件表也归它管？因为打开一个文件，无非就是把文件对应的目录项复制到打开文件表当中，这自然属于目录管理这一层的活儿。

找到了 FCB 之后，是不是就可以直接访问文件了？其实不然。为了保证文件数据的安全，还需要验证一下这个用户是否拥有他所提出的那种访问权限——这正是上一节文件保护的内容。所以**存取控制模块**这一层，主要完成的就是文件保护相关的功能。

确定了访问权限之后，下一层负责把用户提供的**记录号**转换成这个记录存放的**逻辑地址**——这就是**逻辑文件系统与文件信息缓冲区**这一层。那文件信息缓冲区是干嘛的？还记不记得"文件的逻辑结构"里讲过的索引文件？采用索引文件这种逻辑结构时，会为文件中的各个记录建立一个索引表，查询记录对应的逻辑地址就要查索引表，而查索引表之前，得先把索引表调入到内存的文件信息缓冲区当中。这就是文件信息缓冲区的功能。

找到了记录的逻辑地址，接下来就要把它转换成实际的**物理地址**——这是**物理文件系统**这一层的事。

再往下，如果此时是往文件里**添加**记录，那显然可能需要为文件新分配一些物理块；如果是**删除**记录，则可能需要回收文件本来占用的一些物理块。这是**辅助分配模块**做的事：负责文件存储空间的管理，负责分配和回收存储空间。

最后，前面所有这些准备，最终都是为了操作外存——磁盘上的数据。所以需要**设备管理模块**负责和设备直接交互，它也是最接近硬件的层次。所有和硬件相关的管理工作——分配设备、分配设备缓冲区、磁盘调度、启动磁盘、释放设备等等——都由设备管理模块负责。

#### 一个例子串起所有层

整个层次结构不用死记，用一个例子辅助记忆就够了。假设某个用户要请求删除"学生信息"这个 Excel 表里**最后的 100 个记录**，这件事是怎么完成的？

1. 用户首先得通过操作系统提供的接口发出请求——用到了第一层**用户接口**；
2. 用户操作文件时提供的是文件的存放路径，所以要一层一层查找目录、找到对应的目录项——用到了第二层**文件目录系统**；
3. 找到文件对应的 FCB 或索引节点之后，操作系统还要验证这个用户有没有"删除记录"这种操作的权限——由第三层**存取控制模块**（或者叫存取控制验证层）负责；
4. 确定有权限之后，要把用户提供的记录号转变成对应的逻辑地址——需要第四层**逻辑文件系统与文件信息缓冲区**的帮助；
5. 得到逻辑地址后，再把这些逻辑地址转换成实际的物理地址——需要**物理文件系统**的帮助。只要知道了这些记录的物理地址，我们就可以做到删除它们这件事；
6. 删除记录最终肯定还是要和磁盘设备打交道——需要**设备管理程序模块**的帮助；
7. 记录删掉之后出现了一些空闲的磁盘块，这些磁盘块需要进行回收处理——需要**辅助分配模块**的帮助。

还有一个对法子：每一层做的事情，正好对应咱们之前学过的各个小节——用户接口对应"文件的基本操作"，文件目录系统对应"文件目录"，存取控制模块对应"文件保护"，逻辑文件系统与文件信息缓冲区对应"文件的逻辑结构"，物理文件系统对应"文件的物理结构"，辅助分配模块对应"文件的存储空间管理"，设备管理模块则是之后磁盘管理那些小节要介绍的内容。王道书上也给出了另外一种层次结构图，大家回归课本再对照看一下。

### 文件系统的全局结构：从出厂到可用

接下来是第四章的新考点——文件系统的全局结构。我们从一个磁盘出厂、物理格式化、再到逻辑格式化，一步一步认识文件系统在外存中是如何被建立的。

#### 物理格式化：划分扇区，悄悄换掉坏扇区

一个磁盘刚生产出来的时候，里面还没有划分扇区。第一步要做的是**低级格式化**，又叫**物理格式化**。

物理格式化会把磁盘划分为一个一个的扇区，同时检测磁盘当中有没有坏扇区存在。如果有坏扇区，就用一些**备用扇区**来顶替它。

有意思的是，坏扇区的存在对操作系统来说是**透明**的。假设操作系统要访问编号为 n 的坏扇区，磁盘驱动器在物理格式化之后知道这是个坏扇区，当操作系统想访问 n 号扇区时，它就会在背后悄悄地用一个备用扇区——一个好的扇区——来完成替代。操作系统根本意识不到坏扇区的存在。

所以物理格式化做的事情就三件：划分扇区、检测出坏扇区、用备用扇区替换坏扇区。

#### 逻辑格式化：划分分区，建立文件系统的骨架

物理格式化完了，接下来是**逻辑格式化**，又叫**高级格式化**。它会把磁盘划分为一个一个的**分区**，又叫一个一个的**卷**——大家最熟悉的 C 盘、D 盘、E 盘，就是三个不同的分区。

一个磁盘被分成多个分区，那每个分区大小是多少、从哪个地址到哪个地址？这需要用**分区表**来记录。而每一个分区当中，可以建立各自独立的文件系统——比如在 C 分区里建一个 UNIX 文件系统。

UNIX 文件系统内部的结构长这个样子：

```text
+--------+--------+--------+-----------+--------+----------------------------+
| 引导块 | 超级块 | 位示图 | i 节点区  | 根目录 | 其他文件与目录（暂时为空） |
+--------+--------+--------+-----------+--------+----------------------------+
```

逐块看过去。**超级块**我们在"磁盘空闲分区管理"那个部分学过：有了超级块，就可以迅速找到这个磁盘分区里所有的空闲块——当我们要新建一个文件、给文件分配磁盘块时，就从超级块出发，迅速找到很多很多个空闲磁盘块用来分配。

另外还有一个和空闲空间管理相关的数据结构——**位示图**。大家应该有印象，一串 0 和 1，0 代表一个磁盘块空闲，1 代表不空闲。位示图可以迅速判断**某一个特定的磁盘块**此时到底是否空闲，而超级块的作用更多是迅速找到**若干个**空闲盘块。所以这两个数据结构在功能上有一定的重合性，都可以标记哪些盘块空闲，但实际使用中会有一些区别。

**i 节点区**存放的就是我们熟悉的索引节点。UNIX 文件系统中，所有的索引节点都**连续**存放在这个 i 节点区——你可以把它想象成一个超大的数组，数组元素就是一个个索引节点。由于索引节点连续存放、而且每个索引节点大小都相同，我们就可以通过索引节点的**下标**迅速定位到任何一个指定的索引节点：知道了所有索引节点的起始存放地址、每个索引节点的大小，再结合要找的下标，位置就算出来了。

**根目录**：逻辑格式化完成时，根目录也会被建立起来——任何一个文件系统都必须从根目录出发，去建立下一级的目录或者存储新的文件。

所以在上面这张图里，灰色的部分（引导块、超级块、位示图、i 节点区、根目录）就是逻辑格式化填充进去的、已经有实际数据的部分；白色的区域则用于保存其他文件和其他目录，逻辑格式化之后暂时为空，只有你新建了文件或目录之后才会慢慢被填充上数据。

#### 内存里有什么：目录缓存与两张打开文件表

外存这边讲清楚了，接下来看文件系统在**内存**当中的结构。内存分为用户区和内核区，内核区当中有三个重要的东西。

第一个是**目录的缓存**。你最近访问过的一些目录的数据会被暂时缓存在内存当中。比如你最近查找过目录 M，查找时需要把目录 M 的数据——也就是目录中包含的那些 FCB——都读入主存；那接下来一段时间内再访问目录 M，就没必要反复从外存一次一次地读入了，那样很耗费时间。缓存近期访问过的目录数据，可以**加快目录检索的速度**。

另外两个是很重要的数据结构：**系统打开文件表**和**用户打开文件表**（也可以称为进程打开文件表）。顾名思义，系统打开文件表**整个系统只有一张**；进程打开文件表**每个进程有一张**，它包含在每个进程的 PCB 当中，记录了这个进程当前打开了哪些文件。

#### 跟着 open 走一遍：fd 是怎么来的

这些结构怎么协同工作？用一个例子梳理一下。假设现在用 open 系统调用，尝试打开 M 目录下面的文件 a：

```text
open(".../M/a")
   │
   ▼
把目录 M 的数据读入主存并缓存
   │  逐个对比目录项，找到文件名对得上的那一项
   ▼
复制 a 的 FCB（目录项）──→ 系统打开文件表（新建条目，引用计数 = 1）
   │
   ▼
发起 open 的进程在自己的进程打开文件表中新建条目
（记录打开方式：只读？还是又读又写？）
   │  条目里只存一个指向系统打开文件表条目的索引
   ▼
向程序员返回该条目对应的文件描述符 fd
```

第一步，把目录 M 的数据读入主存、缓存起来。读进来之后就可以检查目录项了，一个一个对比，发现有一个目录项的文件名和要找的文件 a 能对上。

接下来把 a 这个文件的 FCB（目录项）**复制**到系统打开文件表当中，表示这个文件被打开了，同时设置它的**引用计数**为 1——意味着当前有一个进程正在使用 a 这个文件。

另一个方面，刚才发起 open 系统调用的那个进程，要在它自己的进程打开文件表当中**新建一个条目**，条目里记录**打开方式**——到底是只读，还是又要读又要写，这是 open 打开文件时要指明的东西。注意，进程打开文件表里**不会**保存文件 a 的 FCB，只会有一个**指向系统打开文件表的索引**。这样通过进程打开文件表就能找到系统打开文件表中对应的条目，而这个条目里就能找到文件对应的 FCB。

最后，open 会返回这个条目的**文件描述符**（fd）。你可以简单地把文件描述符理解为指向进程打开文件表的一个指针——open 之后系统调用给程序员返回一个 fd，之后我们就通过这个 fd 对打开的文件进行操作。

比如接下来要对文件 a 执行读操作（read 系统调用），只需要传入这个 fd，同时指明要读多少个字节、读到什么地方。操作系统收到 read 之后，就可以根据 fd 先在**进程打开文件表**中找到对应条目，再根据索引信息找到**系统打开文件表**中对应的条目，再从条目中找到文件的 FCB——接着通过这个 FCB，操作系统就能确定文件 a 存放在外存当中的什么位置。

通过这个例子，文件系统在内存当中的这些东西有什么作用、它们之间的逻辑关系，我们就能直观地感受到了。

### 虚拟文件系统 VFS：给上百种文件系统立规矩

继续看下一个新考点：虚拟文件系统。先看一个**没有**虚拟文件系统的情况，问题就好理解了。

#### 问题从哪儿来

我们使用计算机时，难免插上各种各样的外部存储设备——移动硬盘、U 盘。不同存储设备里的文件系统格式可能各不相同：移动硬盘可能是 NTFS，U 盘可能是 FAT，而电脑里本身就有的磁盘，可能是 UFS。也就是说，一台计算机内部可能**同时存在各种各样的文件系统**。

麻烦在于：不同文件系统的开发者在开发时，定义的**函数接口可能各不相同**。同样是"打开文件"，说不定 UFS 的函数就叫 `open`、带两个参数；NTFS 的函数名不一样，叫 `fopen`，只有一个参数；FAT 可能又是另一个名字，参数列表和参数格式也不一样。

这会导致什么？我们写代码时，操作左边这个文件系统得按它的规范写，中间那个又是另一种调用格式——对上层用户和程序员来说是不是很麻烦？这意味着我还得根据文件到底存放在哪种文件系统里来调整代码；只要底层文件系统不一样，我就得改我的代码。

所以操作系统内核应该向上层的用户进程提供一个**统一标准的函数调用接口**——于是就引入了虚拟文件系统，英文缩写 VFS，这个 V 就是 virtual（虚拟）的意思。

#### VFS 的三板斧

有了虚拟文件系统之后，用户进程打开文件时，只需要按 VFS 制定的标准写代码——比如函数名叫 `open`，参数就是 x、y、z 这样三个。至于文件实际存放在哪个文件系统里，写代码的时候完全不用管。

这就是虚拟文件系统的**第一个特性**：向上层的用户进程提供**统一标准的系统调用接口**。对用户而言，VFS 帮你**屏蔽了底层具体文件系统的实现差异**。像 Linux，就是按照 POSIX 标准来定义这套接口的。

但接下来第二层麻烦来了。VFS 收到标准的系统调用请求后，要负责去操作底层一个具体的文件系统，可每个文件系统对外的函数名字、参数都不统一——那 VFS 在调用具体文件系统时，它的调用代码岂不是也得跟着不同的文件系统改？这意味着要频繁修改操作系统内核的代码，这显然也不科学。

于是 VFS 反过来对底层立规矩，这就是**第二个特性**：要求底层的各个具体文件系统，**必须实现 VFS 规定好的函数接口**。任何一个文件系统，只要想在这个操作系统上被支持、被使用，就必须按照 VFS 给的标准去实现规定好的那些函数——函数名叫什么、每个参数是什么含义、什么格式，都规定死了。比如 open、read、write 等等。如果你实现不了，那抱歉，这个文件系统就不被这个操作系统所支持。我们要创造一个新文件系统想在某个操作系统上被使用，就必须满足这个要求。

还有第三层麻烦。VFS 底下可能是 UFS，也可能是 FAT，而这两种文件系统的**目录项格式差别很大**：UFS 每个目录项只包含**文件名**和 **i 节点编号**两个信息，需要根据 i 节点编号把 i 节点读入主存，才能知道文件具体的元数据和存储地址；而 FAT 只要读入了某个文件的目录项，关于这个文件的**所有信息**就都有了。

那问题来了：VFS 打开一个具体文件时，文件来自 UFS，读进来的信息长一个样；来自 FAT，读进来的信息又长另一个样。难道 VFS 在内存中要为不同文件系统的文件信息用**不同的数据结构**来表示？这也很麻烦。

解决的办法是虚拟文件系统的**第三个特性**：每当我们 open 打开了一个文件，VFS 就会在主存当中为这个文件新建一个 **vnode**（v 节点）。无论打开的文件来自 UFS 还是 FAT、管你来自什么文件系统，打开之后都会把这个文件相关的信息复制到这个 vnode 当中。这样 VFS 就可以用**一个统一的数据结构**表示任何一个文件的信息。

vnode 里除了文件的各种元数据之外，还保存了一个涂了重点的东西——**函数功能指针**。刚才说了，每个文件系统都要实现 VFS 规定的 open、read、write 等函数，但每个文件系统背后具体的代码各不相同。所以 vnode 中的函数功能指针，指向的是**对应文件系统的函数功能列表**。这样一来，只要 open 打开了一个文件，之后要对文件进行的任何操作——read 也好、write 也好——都可以先找到这个文件的 vnode，根据其中的函数功能指针找到对应文件系统的函数功能列表，再去执行具体的函数，实现从上至下一层一层的函数调用。

整个调用关系可以画成这样：

```text
用户进程：按统一接口调用 open / read / write
   │
   ▼
虚拟文件系统 VFS（统一接口 + 立规矩 + 统一数据结构 vnode）
   │
   ▼
各文件系统：按 VFS 要求实现规定好的函数接口
   ├── UFS   的函数功能列表
   ├── NTFS  的函数功能列表
   └── FAT   的函数功能列表
```

#### vnode 和 i 节点：名字像，东西完全不一样

最后有两个地方值得特别注意。

第一，**vnode 和 i 节点看起来很像，但它们是两个完全不一样的东西**。vnode **只存在于主存当中**——每一个被打开的文件，在主存中都会有一个与之对应的 vnode；而 i 节点既会被调入主存，同时**在外存当中也会存储**。如果此时打开的文件刚好在 UFS 文件系统里，那么找到文件对应的目录项之后，会先把文件的 i 节点从外存读入主存，然后在主存中不是新建了一个 vnode 吗？读入的这个 i 节点里的各种信息，会被**复制到 vnode 当中**。vnode 和 i 节点的这个区别，我认为很适合作为选择题的一个选项，大家一定要记牢。

第二，就是前面强调的：vnode 当中除了文件的元数据之外，还会保存这个文件所属文件系统提供的**函数功能列表**（通过指针指向）。

### 文件系统的挂载

最后看文件系统的挂载，又叫文件系统的安装或者装载——讲的是如何把一个文件系统挂载到操作系统上。

其实大家经常使用文件系统挂载的功能，只是没发现：比如把 U 盘插到电脑上，U 盘的文件系统就需要挂载到操作系统上——具体来说，就是挂载到操作系统的**虚拟文件系统**里边。

挂载需要做三件事。

第一，**在虚拟文件系统中注册新挂载的文件系统**。内存中，VFS 会管理一个数据结构，叫做**挂载表**，包含每个文件系统的相关信息——文件系统的格式、容量大小等等基本信息。比如图里边挂载了三个文件系统，挂载表里就有三个表项，分别指向 UFS、NTFS 和 FAT 这三个文件系统。当挂载一个新的文件系统时，也要给它新建一个表项——这就完成了文件系统的注册，让 VFS 能发现这个新来的。

第二，**向 VFS 提供自己的函数地址列表**。每个文件系统对 open、read、write 这些函数的实现都各不相同，所以新挂载的文件系统需要向 VFS 提供一份自己的函数地址列表——我的 open 系统调用代码存放在哪个地址、我的 read 存放在什么地址。有了这个东西，VFS 才能调用新挂载文件系统所提供的功能函数。这正是前面 vnode 里函数功能指针指向的那份东西。

第三，**把新文件系统加到指定的挂载点当中**——也就是把新文件系统挂载到某一个目录下面。这话说着抽象，其实不难理解。什么是挂载点？

- 如果你用的是 **Windows** 电脑：插入移动硬盘或 U 盘时，界面上会出现一个新的**盘符**——每个盘用不同的编号，C、D、E、H、G 等等，用一个盘符标识新的设备和文件系统。所以对 Windows 而言，新挂载文件系统的挂载点，就是和 C 盘、D 盘、E 盘**平级**的那个位置。
- 如果你用的是 **Mac** 电脑：可以自己试一下，接上一个硬盘或 U 盘，到系统根目录下面找到叫 **Volumes** 的文件夹，在这个目录下面就能看到你新挂载上去的文件系统。所以对 Mac 而言，挂载点就是根目录下的 Volumes 目录之下。

一个新加入的文件系统，需要被挂载到某一个特定的位置——某一个原本存在的父目录下面。只有确定了新文件系统挂载的位置，接下来我们才可以正常地访问和使用这个新的文件系统。

到这里，这一条线就走完了：口令、加密、访问控制三种保护手段各有取舍；文件系统从用户接口到设备管理模块层层接力；一块磁盘从物理格式化到逻辑格式化长出文件系统的骨架，内存里用目录缓存和两张打开文件表把 open 与 read 串起来；面对五花八门的底层文件系统，VFS 用统一接口、强制实现的函数规范和统一的 vnode 把差异压在底下；最后用挂载把新文件系统接到操作系统上。动手在 Windows 上建一个"临时访客"、改一改文件夹的安全属性，这一章的知识就真正落了地。

## I/O 设备、I/O 控制器与四种 I/O 控制方式
> 对应块：BLK30 | 覆盖分集：P73-P75 | 块标题（分集名）：《5.1_1_I-O设备的概念和分类》

从这一部分开始，我们进入操作系统这门课的最后一个章节——设备管理。回顾一下之前的脉络：操作系统作为系统资源的管理者，既要管理上层的软件，也要管理下层的硬件。处理机、存储器这些硬件我们已经学过了，但它们都在计算机的主机内部。这一章要探讨的"设备管理"，指的是操作系统对**计算机主机外部的那些硬件设备**的管理。在正式展开之前，得先把地基打好：I/O 设备是什么、怎么分类，I/O 控制器在里面扮演什么角色，以及随着计算机的发展，I/O 控制方式是怎么一步步进化出四种形态的。

### 什么是 I/O 设备：把外设当成一种特殊的文件

I/O 设备又可以叫**外部设备**。所谓 I/O，I 代表 input，O 代表 output，也就是输入和输出——这个设备的作用和它的名字一样直白：要么是把数据输入到计算机当中的一种设备，要么是可以接收计算机输出数据的一种外部设备。

举几个大家最熟悉的例子就清楚了：

- **键盘、鼠标**是典型的输入型设备。比如键盘，可以把一个一个的字符数据输入到计算机当中。
- **显示器**是典型的输出型设备，它接收计算机主机输出的图像数据，并且把这些图像显示出来。
- **移动硬盘、U 盘**则属于既可以输入又可以输出的设备：既可以把移动硬盘里存储的数据输入到计算机中，也可以把计算机中的数据输出到移动硬盘里存储。

所以输入的过程，无非就是把设备准备好的数据**读入**计算机；输出的过程，无非就是把计算机准备好的数据**写出**到输出设备上。

正因为如此，**Unix 系统把外部设备抽象成了一种特殊的文件**。这样用户就可以用读文件、写文件的方式去操作外部设备：`write` 操作就是向外部设备写出数据，也就是数据输出的过程；`read` 操作就是从外部设备中读入数据，也就是数据输入的过程。在后面的讲解里，你会经常看到"对一个设备进行 write 操作 / read 操作"这种说法，它们对应的就是输出和输入的过程。

> **定义**：I/O 设备（外部设备）就是把数据输入到计算机、或接收计算机输出数据的外部设备；在 Unix 中被抽象为特殊文件，用 `read`/`write` 统一操作。

### I/O 设备的三种分类视角，重点只有最后一个

#### 按使用特性分：人机交互、存储、网络通信

按使用特性，I/O 设备可以分成三种类型：

1. **人机交互类外设**：平时我们用来和计算机交互的设备，比如鼠标、键盘、打印机。这类设备的数据传输速度一般比较慢，传输是以字节、或者几十字节为单位的。
2. **存储设备**：比如移动硬盘、光盘，就是用来存放数据的，传输速度一般比较快。
3. **网络通信设备**：比如大家平时熟悉的"猫"（调制解调器）、路由器。这类设备的速度介于前两者之间——比人机交互类的快一些，又比存储类的慢一些。

#### 按传输速率分：低速、中速、高速

按传输速率，又可以分为低速、中速、高速三种：

| 类别 | 大致速率 | 典型例子 |
| :---: | :---: | :--- |
| 低速设备 | 每秒几个到几百个字节 | 鼠标、键盘 |
| 中速设备 | 每秒数千至上万个字节 | 激光打印机 |
| 高速设备 | 每秒数千字节，甚至更快 | 移动硬盘 |

为什么键盘是低速的？你想，我们每敲击一次键盘，其实只是往计算机里输入了一个字符，所以这种设备和计算机进行数据交换的速度是很慢的。

> **提示**：高中低速其实并没有一个很明确的界限划分，这个知识点不需要特别记忆，有个印象就行，基本不可能作为考点考察。

#### 按信息交换的单位分：块设备与字符设备（重点）

这是三种分类方式里**最需要重点关注**的一种：按信息交换的单位，分为**块设备**和**字符设备**。

- **块设备**：像移动硬盘、磁盘这类，数据传输的基本单位是"一块一块"进行的。经过上一章（文件管理）的学习，大家对"块"的概念应该已经很清楚了。块设备的特点是**传输速率比较高**，并且**可寻址**——所谓可寻址，就是可以随机地读写任意一块。
- **字符设备**：类似鼠标、键盘这种，数据传输的基本单位是字符或者字节。所以这类设备传输速度一般比较慢，并且**不可寻址**。在输入输出时，字符设备一般采用**中断驱动**的 I/O 控制方式——中断的概念在第一章已经详细介绍过，下文讲 I/O 控制方式时还会继续展开。

这两类设备最本质的区别，就是与计算机进行数据交换时的**基本单位**：一个是块，一个是字符。除此之外，还要结合上一章的内容记住：块设备可寻址，字符设备不可寻址。

> **提示**：前两种分类方式（按使用特性、按传输速率）没有明确的划分界限，一般不太可能考察；真正要吃透的是块设备与字符设备在传输单位和可寻址性上的区别。

### I/O 控制器：CPU 与机械部件之间的中介

#### 机械部件与电子部件

I/O 设备其实是由**机械部件**和**电子部件**两部分组成的：

- **机械部件**就是我们看得见摸得着的部分，主要用来执行具体的 I/O 操作。比如鼠标、键盘、显示器里那些实体的机械结构，再比如显示器那块 LED 屏，就是用来显示输出的图像数据的。
- **电子部件**一般来说就是一块印刷电路板，它就是我们要说的 **I/O 控制器**（也叫设备控制器）。在操作系统这门课里，重点掌握的是电子部件相关的知识。

关键在于：当 I/O 设备连上电脑之后，**CPU 是没办法直接控制这些设备的机械部件的**，它必须通过电子部件来间接地控制机械部件。所以 I/O 控制器其实就是 CPU 和 I/O 设备机械部件之间的一个**中介**——就像它的名字一样，用于实现 CPU 对 I/O 设备的控制。

#### 控制器要干的四件事

作为中介，I/O 控制器需要完成四个主要功能，而且每个功能都对应着一种专门的寄存器：

**第一，接收和识别 CPU 发出的命令。** 我们最熟悉的命令当然就是读或写。但除了命令本身，CPU 还会告诉控制器执行这个命令相关的一些**参数**，比如要读多少个字节、要写多少个字节。因此控制器里要设置一个**控制寄存器**，用来存放 CPU 发出的命令和参数；控制器再根据寄存器里的内容，确定自己到底要执行什么操作。

**第二，向 CPU 报告设备的状态。** 一个设备此刻到底是忙碌的、空闲的，还是处于故障状态？CPU 作为系统资源的管理者，当然需要知道各个设备的状态。所以控制器里还设置一个**状态寄存器**，CPU 读取它的内容就能判断设备状态。比如我们可以规定：1 表示空闲，0 表示忙碌；如果有更复杂的状态，就用更多的二进制位来表示。

**第三，实现数据交换。** 控制器既然是 CPU 和机械部件之间的中介，当然也要充当数据交换的中间使者。所以控制器里会设置**数据寄存器**：输出时，数据寄存器先暂时存放 CPU 发过来的数据，之后控制器再把它的内容传送给设备；输入时数据流向刚好相反，设备送来的数据先暂存在数据寄存器里，CPU 再从中取走。

**第四，地址识别。** 前面说了，控制器里会设置各种各样的寄存器，而且每种寄存器可能还有多个。为了识别这些寄存器，就要像给内存编址一样，给各个寄存器编上地址。CPU 往寄存器里读、写数据时，就是通过寄存器对应的地址来操作的；控制器则根据 CPU 提供的地址，判断 CPU 想操作的到底是哪一个寄存器。

#### 控制器的三个组成部分

了解了功能和实现思路，再来看 I/O 控制器由哪些部分组成。它可以分为三个部分：

```text
              ┌─────────────────── I/O 控制器 ───────────────────┐
              │                                                  │
   ┌────┐     │  ┌────────────┐  ┌─────────┐  ┌────────────┐     │    ┌──────────┐
   │CPU │ ════╪══│ CPU与控制器 │══│  I/O    │══│ 控制器与设备 │ ═══╪════│ 设备的    │
   └────┘     │  │    接口     │  │  逻辑   │  │    接口     │     │    │ 机械部件  │
              │  └────────────┘  └─────────┘  └────────────┘     │    └──────────┘
              │     数据线/地址线/     命令翻译、         数据线/      │
              │     控制线             地址译码          控制线       │
              └──────────────────────────────────────────────────┘
```

左边是 CPU 与控制器的接口，右边是控制器与设备的接口，中间夹着 I/O 逻辑。

还记不记得那句话——I/O 控制器是 CPU 和设备机械部件之间的**中介**？那么左边这个部分，就是中介与 CPU 连接的部分；右边这个部分，是中介与设备机械部件连接的部分。而中介在连接 CPU 和设备时，必然要做一些中间处理，这些处理主要就在 **I/O 逻辑**里完成：它负责接收和识别 CPU 发来的各种命令，负责地址识别（地址译码），并在识别命令之后，把它翻译成设备能够明白的命令，再通过控制器与设备的接口发送给具体设备，让设备执行相应的操作。

这里有个值得注意的细节：**一个 I/O 控制器可能会对应多个设备接口**，也就是说一个控制器可能负责控制多个具体的 I/O 设备。为了区别 CPU 此时要操作的是哪一个设备，需要给这些设备编号（或者说给各个设备接口一个地址），CPU 在发出 I/O 命令时也要指明自己操纵的是哪个设备。

我们来捋一捋中间的过程。CPU 首先会通过一条叫**控制线**的线路，向 I/O 控制器发出具体的 I/O 指令，同时在**地址线**上说明自己要操纵的是哪一个设备。如果此时要输出数据，CPU 会通过**数据总线**把要输出的数据放到 I/O 控制器的数据寄存器中；CPU 发出的 I/O 指令若带有参数，参数会放进控制寄存器；而为了实现对各个设备的管理，I/O 逻辑会把各设备的状态（忙碌、空闲还是故障）写入状态寄存器，供 CPU 读取。这就是 CPU 与控制器接口的职责——完成 CPU 和控制器之间的通信。

控制器与设备的接口则完成控制器和设备之间的通信。以输出为例：CPU 通过数据总线把数据写入数据寄存器，I/O 逻辑取出数据寄存器的内容，通过这个接口的数据通路把数据输出到外部设备上；输入时流向相反。除了传送数据的通路，设备还要及时向控制器反馈自己的状态（忙碌还是空闲），I/O 逻辑再把状态写入对应的状态寄存器。这个接口里还有一个用于实现设备控制的电路，I/O 逻辑根据 CPU 发出的命令和参数，对对应的设备发出控制命令，让设备执行具体的工作。

正因为一个控制器可能对应多个设备，而各个设备要输入输出的数据、各自的状态肯定不同，如果这些设备同时工作，只设一个数据寄存器、状态寄存器显然满足不了需求。所以**数据寄存器、控制寄存器、状态寄存器这些寄存器都会有多个**——这就引出了下一个问题：这么多寄存器，怎么编址？

#### 寄存器怎么编址：内存映像 I/O 与独立编址

给这些寄存器编址一般有两种方式，它们的区别必须搞清楚。

**第一种：内存映像 I/O**——让寄存器占用内存地址的一部分。假设内存总共有 $n$ 个地址，编号是 $0 \sim n-1$；系统里有一个设备控制器 0，它有三个寄存器，那么这些寄存器就顺着内存的地址继续往下编：寄存器 0 的地址是 $n$，寄存器 1 是 $n+1$，以此类推。如果还有别的设备控制器也有寄存器，同样接着往下编。也就是说，**控制器里的寄存器和内存采用统一的编址**，共用一个地址空间。

**第二种：寄存器独立编址**——采用 I/O 专用地址。内存还是 $0 \sim n-1$，但设备控制器的寄存器会**从零开始另行编号**（有的系统里，各个控制器的寄存器也可能采用连续编号的方式，比如 3、4、5——这些细节不用纠结）。关键在于：这些寄存器和内存的地址空间**不是统一的，是两个独立的体系**。

两种方式的优缺点对比就出来了：

- 独立编址的明显缺点：**需要设置专门的指令**来实现对这些寄存器的存取操作。而且在寄存器地址相互独立的情况下，指令不仅要指明要操作的寄存器编号，还要说明操作的是哪一个控制器——是控制器 0 还是控制器 1。
- 内存映像 I/O 的好处：**不需要设置专门的指令**，用对内存单元操作的那些相同指令来操作这些寄存器就可以了。

> **提示**：本节考的频率并不高，但要有大致印象。要重点注意的是两种寄存器编址方式的区别与各自优缺点。另外，控制器由三个部分组成这件事也别偷懒——选择题有四个选项，如果是出题老师，完全可能把这三个正确答案再加一个错误选项，让你选"错误的那个"。所以控制器的组成、主要功能，都要有个大体印象。

### 程序直接控制方式：CPU 一路轮询到底

接下来是本章的重要考点——**I/O 控制方式**。上一节学了 I/O 控制器，但随着计算机的发展，控制器本身也在不停发展，它对设备的控制方式也出现了不同的变化或者说进化。我们需要掌握四种 I/O 控制方式：**程序直接控制方式、中断驱动方式、DMA 方式、通道控制方式**。

学习每一种方式时，都盯着五个问题：

1. 完成一次读写操作的**流程**分别是怎么样的？
2. CPU 对 I/O 操作的**干预频率**如何？
3. 进行一次 I/O 所传送数据的**单位**是多少？
4. 数据的**流向**是怎样的？
5. 各种控制方式的**主要优点和主要缺点**是什么？

什么是干预频率、什么是传送单位、什么是数据流向，现在听起来可能比较模糊，没关系，看具体的例子就能理解。

先看最早期的**程序直接控制方式**，以读操作为例来分析整个流程：

- CPU 首先通过控制线向 I/O 控制器发出一条**读指令**；控制器根据 CPU 的要求启动相应的设备，并把设备的状态设置为**未就绪**（忙碌）。假设状态寄存器为 1 表示设备正在忙碌。
- 接下来设备开始准备计算机想要读入的数据。但由于设备的速度比 CPU 慢很多，在设备完成 I/O 之前，**CPU 会一直不断地轮询检查设备的状态**——也就是不断检查状态寄存器里的值。只要它一直为 1，就说明设备还在忙碌，还没准备好要读的数据。这个轮询检查的过程，背后其实就是 CPU 在不断地执行一个程序的循环。
- 设备准备好输入数据后，会把数据传送给 I/O 控制器，并报告自己的状态已变成**已就绪**。I/O 逻辑把设备传来的数据放到数据寄存器中，并把状态寄存器改为 0（已就绪）。
- CPU 依然在不停轮询，一旦发现状态寄存器变为 0，就从数据寄存器中读出此次要输入的数据——先读入 **CPU 自己的寄存器**，再把 CPU 寄存器的内容**转存到内存**。这才完成了一次读操作。
- 如果还要继续读别的数据，CPU 会再发送下一条读指令，然后重复刚才这一整套流程。

所以采用程序直接控制方式，要掌握的核心词就是**轮询**。完整流程画出来是这样：

```text
   CPU 发出读命令（CPU → I/O）
        │
        ▼
   读 I/O 模块的状态（I/O → CPU）◄─────────────┐
        │                                     │
        ▼                                     │
   数据已就绪？ ──否（或出错条件，继续轮询）─────┘
        │ 是
        ▼
   从 I/O 模块读一个字到 CPU 寄存器（I/O → CPU）
        │
        ▼
   把该字写入存储器（内存）
        │
        ▼
   本次读操作完成（还要继续读 → 回到最初步骤再来一遍）
```

图里有两个不太容易理解的点，解释一下。为什么有"CPU 指向 I/O"的标注？因为发出读命令是 CPU 向 I/O 控制器发出的。"读 I/O 模块的状态"为什么是"I/O 指向 CPU"？因为这一步其实是把 I/O 控制器状态寄存器中的数据读出，放到 CPU 的寄存器中进行分析。图中的**错误条件**是因为 I/O 设备可能出现故障——设备出错时会在状态寄存器中写入相应的错误代码，CPU 根据这些代码就能判断设备是否已产生错误。

另一个容易卡住的问题：**为什么数据读入 CPU 寄存器之后，还要往存储器里写一道？** 看一段我们都很熟悉的 C 语言代码就明白了。只要是写过 C 语言的同学，肯定写过 `scanf` 这个函数——从键盘这种 I/O 设备读入输入，赋值给其中某个变量。而我们知道，定义的变量 a、b、c、d 其实都是存放在存储器（内存）中的，所以这些数据从键盘读入之后，最终肯定要被放到内存里。因此 CPU 拿到从键盘输入的数据后，事情还没结束，还得把数据写入存储器的相应单元。原理相同：用 `printf` 输出数据时，做的事情就是把内存中变量的数据拿出来，经过 CPU 再输出到输出设备上。

然后按开篇说的那五个维度给程序直接控制方式"体检"：

- **CPU 干预频率**：非常频繁。CPU 需要不断轮询检查 I/O 是否完成——不仅 I/O 开始之前、完成之后需要 CPU 介入，**等待 I/O 完成的过程中 CPU 也要不断轮询**。这是它最大的缺点。
- **数据传送单位**：每次读入或写出的数据量是**一个字**。
- **数据流向**：读入时从 I/O 设备到 CPU 寄存器再到内存；输出时从内存到 CPU 再到 I/O 设备。每一个字的读写都需要 CPU 介入帮忙，CPU 要花大量时间辅助完成 I/O。
- **优点**：实现简单，用软件方式就能实现。正因为轮询过程其实就是执行一系列循环检查的程序指令，这种方式才叫"程序直接控制方式"——通过执行一系列特定的循环检查程序代码，就能实现这种控制。
- **缺点**：CPU 和 I/O 设备只能**串行**工作。CPU 发出 I/O 指令后不能去做别的事情，必须一直循环检查 I/O 是否完成，长期处于**盲等**状态，CPU 利用率低；反过来，当 CPU 在做别的计算时，I/O 设备肯定也是空闲的，所以 I/O 设备的利用率也低。

### 中断驱动方式：发完指令就去干别的

怎么解决串行和盲等的问题？为此人们提出了**中断驱动方式**。中断这个概念之前已经接触过很多次了，相信大家并不陌生。

与程序直接控制方式相比，中断驱动方式主要引入了**中断机构**，可以让 CPU 在发出 I/O 指令之后转头去做别的事情——也就是切换到别的进程。具体来说：I/O 设备速度很慢，CPU 是速度很快的硬件，所以 CPU 发出 I/O 指令后，可以把需要等待 I/O 的那个**进程先阻塞起来**，然后 CPU 去干别的事情（先切换到别的进程执行）；等 I/O 完成之后，I/O 控制器会向 CPU 发出**中断信号**，CPU 检测到中断信号后，根据中断信号的类型执行相应的**中断处理程序**——在处理中断的过程中，它会从 I/O 控制器中读出一个字的数据，传送到 CPU 寄存器，再写入存储器。之后 CPU 就可以恢复之前被阻塞的进程继续执行；当然也可以选择不恢复它，让它继续在就绪队列里等待，先执行别的进程。这些点在之前的章节里已经聊过很多次了，不再赘述。

有两个需要注意的点：

- CPU 会在**每个指令周期的末尾**检查中断——每条指令执行结束后，CPU 都会例行检查一下此时有没有中断信号到达。
- 中断处理过程中，CPU 需要**保存和恢复进程的运行环境**，这个过程是有时间开销的。所以如果中断发生得太频繁，显然也会降低系统性能。

对照五个维度：

- **CPU 干预频率**：比程序直接控制低了很多。CPU 只需在每一次 I/O 操作**开始之前**发出一条 I/O 指令，然后转头做别的事情；I/O **完成之后**介入处理一次中断。
- **数据传送单位**：每发出一条读或写指令，只会读入或写出**一个字**。
- **数据流向**：和程序直接控制方式相同——读入时从 I/O 设备到 CPU 寄存器，再转存到内存；写出时相反。
- **优点**：解决了程序直接控制方式最大的缺点。引入中断技术后，CPU 和 I/O 设备可以**并行工作**，CPU 不再需要不停地轮询，CPU 利用率和 I/O 设备利用率都得到明显提升。
- **缺点**：由于每次中断只能传送一个字，要传送大量数据时显然会发生**大量中断**，而每一次中断处理都要付出一定的时间代价，中断太频繁就会消耗很多 CPU 时间，导致系统性能降低。另外，这种方式下数据的读入、写出仍然**必须先经过 CPU** 中转。

### DMA 方式：数据不再经过 CPU

看到这里你可能会想：读入数据，无非就是把 I/O 设备准备好的数据放到内存里；写出数据，无非就是把内存中的数据写到 I/O 设备上。那能不能把"必须经过 CPU 中转"这一步砍掉呢？为此人们又提出了一种新的 I/O 控制方式——**DMA 方式**，中文名叫**直接存储器存取**，遇到这个名词要知道它指的就是 DMA。这种方式主要用于对**块设备**的 I/O 控制。

相比中断驱动方式，DMA 方式有三点进化：数据传送单位由**字**变为**块**，每次读入或写出一个块；数据流向**不再经过 CPU**，可以在 DMA 控制器的控制下直接从设备放入内存、或直接从内存写出到设备；CPU 的干预频率进一步降低，**仅在传送一个或多个数据块的开始和结束时**才需要干预。

#### DMA 控制器的组成

DMA 方式的大致流程是：CPU 给 I/O 模块发出一条读或写**一个块**的指令，之后就可以转头去做其他事情；DMA 控制器根据 CPU 给出的命令和参数，完成 CPU 指定的这一系列工作；当指定的块读完或写完之后，DMA 控制器向 CPU 发出中断信号，CPU 再介入处理中断。CPU 发出读/写指令时，需要说明此次要读入或写出的数据量有多少、这些数据应存放在内存的什么位置、数据在外部设备上应存放在什么位置——这些信息是交给 DMA 控制器的。

我们刚才一直在说的 DMA 控制器，其实也是一种 I/O 控制器，只不过和上一节的 I/O 控制器有些小区别。它依然由三个部分组成：**CPU（主机）与控制器的接口、I/O 控制逻辑、块设备与控制器的接口**——与 I/O 控制器的三部分一一对应，不难理解。为了实现控制器和 CPU 之间的通信，接口处设置了一系列寄存器，CPU 通过系统总线读写这些寄存器，达到控制 I/O 设备的目的。

```text
                 ┌──────── 系统总线 ────────┐
                 │                          │
             ┌───┴───┐              ┌──────┴─────┐
             │  CPU  │              │ DMA 控制器  │
             └───────┘              │ ┌────────┐ │
                                    │ │  DR    │ │
                                    │ │  MAR   │ │
                                    │ │  DC    │ │
                                    │ │  CR    │ │
                                    │ └────────┘ │
                                    └──────┬─────┘
                                           │
                                    ┌──────┴─────┐
                                    │   块设备    │
                                    └────────────┘
```

这些寄存器各有分工：

- **DR**（数据寄存器）：暂存从设备到内存、或从内存到设备的数据，相当于一个中转站，和之前介绍的数据寄存器没有太大区别。
- **MAR**（内存地址寄存器）：存放内存地址。数据从设备输入时，MAR 中存放读入的数据应放到内存的什么位置；数据从内存输出到设备时，MAR 中指明要输出的数据存放在内存的什么位置。
- **DC**（数据计数器）：记录此时还要读或写的字节数还剩多少。
- **CR**（命令/状态寄存器）：存放 CPU 发来的命令相关参数，还有设备的状态等信息。

和之前的 I/O 控制器一样，这些寄存器也可能有多个（这里并没有列全，这几个是最主要的）。控制器与块设备之间也有相应接口，实现控制器对块设备的通信控制。而**系统总线还会把 DMA 控制器和内存直接连在一起**，所以 DMA 控制器和内存之间可以直接进行数据的读写，不再需要经过 CPU。

比如 CPU 在开始时指明：这次要读入的数据存放在磁盘的什么位置（读入的数据应存放到内存的什么位置，这个信息放在 MAR 里）、此次要读入的数据量是多少（放在 DC 里）。接下来 DMA 控制器就根据这些参数，从磁盘的相应位置读入数据写到内存里，全程不再需要 CPU 干预；只有 DMA 控制器完成了整个 CPU 指定的任务之后，才向 CPU 发出中断信号，CPU 再介入做后续处理。

> **易错点**：DMA 控制器并不是每次直接读入一整块数据、一整块塞进内存。它在读入数据的过程中，依然是**一个字一个字读入的**——每读入一个字，先暂存在 DR（数据寄存器）中，再从 DR 写入内存。用这样一个字一个字的方式，最终完成一整块数据的读入。

#### DMA 方式的五个维度

- **CPU 干预频率**：进一步降低，仅在传送一个或多个数据块的**开始和结束**时干预——开始前 CPU 发出 I/O 指令并指明参数，结束后 CPU 处理中断、做后续处理。
- **数据传送单位**：从一个字变成了一个**块**。CPU 每发出一条读/写指令，DMA 控制器就能完成对一个块或者多个块的读写。
- **数据流向**：不再经过 CPU，数据从 I/O 设备读入后，在 DMA 控制器的控制下直接放入内存；输出时刚好相反。
- **优点**：数据以块为单位传输，CPU 介入频率进一步降低，数据传输也不再经过 CPU，传输效率进一步提升。这一切带来的结果，就是让 CPU 从繁杂的 I/O 工作中抽离出来，有更多时间去处理别的计算任务——CPU 和 I/O 设备的并行性、资源利用率都得到进一步提升。
- **缺点**：CPU 每发出一条 I/O 指令，只能读/写**一个或多个连续的数据块**。如果想读入多个离散的块，或者读入的块需要离散地存放在内存的不同位置，就得由 CPU 发出**多条** I/O 指令——并且这些块读入内存之后必须连续存放。这是 DMA 方式还可以继续改进的地方。

### 通道控制方式：一个"弱鸡版 CPU"

为了解决"离散块要发多条指令"的问题，人们又提出了**通道控制方式**。所谓通道，其实是一种**硬件**。大家可以把它理解为是一种**弱鸡版的 CPU**：通道可以识别并执行一系列的**通道指令**，就类似于 CPU 识别的那些指令一样。为什么叫"弱鸡版"？因为通道能识别的指令与 CPU 能识别的指令相比非常单一，而且通道并没有自己的内存，它需要和 CPU 共享主机的内存——所以才这么叫。第一次学这块内容的同学可能不太容易理解通道，记住这个比喻就行。

通道的工作原理是这样的。CPU、内存、通道通过系统总线连接到一起：

- 首先 CPU 向通道发出 I/O 指令，并指明此次要执行的**通道程序**（或者说通道指令的序列）存放在内存的什么位置，同时指明此次要操作的设备到底是哪一个。
- 把这些信息告诉通道之后，CPU 就可以切换到其他进程执行，抽离出去开始干别的事情。
- 通道根据 CPU 的指示，去内存中找到此次要执行的通道程序。这个**通道程序可以理解成一种任务清单**——它就是一系列通道指令的集合，本质上和我们熟悉的普通程序是一样的。在任务清单的通道指令当中，会向通道指明此次要读入/写出的数据是多少、读写的数据应放在内存的什么位置、在外存中又是什么位置等等——这些都是通道在执行程序的过程中自己就能知道的。
- 所以采用这种方式，相当于 CPU 只是告诉通道：你现在去执行这样一个任务，任务清单我已经放在内存里了。具体这个任务要做什么，并不是由 CPU 直接告诉通道的，而是由通道自己去读取内存中的程序，一步一步执行。
- 通道执行完这一系列任务之后，向 CPU 发出中断信号；CPU 接到中断信号后处理中断，再继续执行接下来的程序。

对照五个维度收个尾：

- **CPU 干预频率**：进一步降到**极低**。CPU 可以一次扔给通道一堆事情，这些事情都写在通道程序里，通道根据通道程序的指示一步一步完成 I/O 操作，等它完成了一系列数据块的读写之后，才向 CPU 发一次中断。
- **数据传送单位**：DMA 方式每一次读写是一个数据块（或多个连续块），而通道方式每一次读写可以完成对**一组数据块**的读写操作。
- **数据流向**：与 DMA 类似，在通道的控制下，数据可以直接从 I/O 设备读入内存，或直接把内存中的数据输出到 I/O 设备。
- **优点**：CPU、通道、I/O 设备可以**并行**工作，资源利用率特别高。
- **缺点**：实现复杂，需要专门的**通道硬件**的支持。

另外要注意层级关系：**一个通道可以控制多个 I/O 控制器，而一个 I/O 控制器又可以控制多个设备**。

```text
   CPU ═══ 系统总线 ═══ 通道 ═══ I/O 控制器（可多个） ═══ 设备（可多个）
```

### 四种控制方式放在一起看

最后把四种 I/O 控制方式横向摆到一张表里，五个维度一目了然：

| 控制方式 | CPU 干预频率 | 数据传送单位 | 数据流向 | 主要优点 | 主要缺点 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 程序直接控制 | 极高，不断轮询 | 字 | 设备 → CPU 寄存器 → 内存 | 实现简单，纯软件即可 | CPU 与 I/O 串行，CPU 盲等，双方利用率都低 |
| 中断驱动 | 每次 I/O 开始前、结束后各一次 | 字 | 设备 → CPU 寄存器 → 内存 | CPU 与设备并行，利用率明显提升 | 频繁中断消耗 CPU 时间；数据仍须经过 CPU |
| DMA | 一块（或多块连续块）传送的开始和结束 | 块 | 设备 ↔ 内存直达，不经过 CPU | 干预少、传输效率进一步提升 | 只能读写连续块，离散块需多条指令 |
| 通道 | 极低，一组块完成后中断一次 | 一组数据块 | 设备 ↔ 内存直达 | CPU、通道、设备并行，资源利用率特别高 | 实现复杂，需专门通道硬件 |

回看这条进化链会发现一个规律：**每一个阶段的优点，都是解决了上一个阶段留下的最大缺点**。而整个 I/O 控制方式的发展主线，就是尽量减少 CPU 对 I/O 过程的干预，把 CPU 从繁杂的 I/O 控制事务中解脱出来，以便更多地去完成数据处理的任务。正因如此，CPU 的干预频率从极高慢慢变成极低；每次 I/O 的数据传输单位，从"字"这么小的单位慢慢变成块，最后的通道方式甚至支持每次传输一组块——整个发展过程都在追求这一件事。

流程细节是这一节常考的形态，经常在选择题里考察每种控制方式下完成一次读写操作的大致流程，以及各种方式的 CPU 干预频率高低、传输单位是字还是块。这一节内容十分重要，把流程图亲手捋一遍，比背结论管用。

## I/O 软件的层次结构与两类接口
> 对应块：BLK31 | 覆盖分集：P76-P77 | 块标题（分集名）：《5.1_4_I-O软件层次结构》

分层这个设计思想，我们在计算机网络里已经见过一次了：每一层使用下一层提供的服务来实现某些功能，再向上层提供一些更简单、易用的接口。I/O 软件用的正是同一套思路。这个思想说起来简单，但它是整个 I/O 管理这一章的骨架——下面要讲的统一接口、驱动程序、中断处理，全部挂在这副骨架上。

### 四层软件加一层硬件

I/O 软件从上至下依次分为四层：用户层软件、设备独立性软件、设备驱动程序、中断处理程序。最底下还有一层 I/O 硬件。

```text
┌────────────────────────────┐
│       用户层软件            │ ← 内核之外，用户态可实现
├────────────────────────────┤
│       设备独立性软件         │
│       设备驱动程序           │ ← I/O 核心子系统（内核部分）
│       中断处理程序           │
├────────────────────────────┤
│   I/O 硬件（机械部件+电子部件）│
└────────────────────────────┘
```

图中用户层软件和下面三层的"颜色"不一样，这不是随手画的：下面三层属于操作系统内核部分，所以它们又被称作 I/O 核心子系统（或者简称 I/O 系统）；而用户层软件在内核之外，是可以在用户态下实现的一系列功能。I/O 硬件由机械部分和电子部分组成，它的组成和原理在 I/O 控制器那个小节里已经讲过了，这一讲重点关注的是软件层面要实现的功能。

层次之间的规矩只有一句话：**越靠近上层越接近用户，越靠近下层越接近硬件；每层使用下一层的功能，并向上层提供服务。**

当用户发出一个 I/O 请求时，这个请求会从上至下经过各个层次处理，最后被扔给 I/O 硬件执行实际的 I/O 操作；当硬件做完操作、发出 I/O 应答（中断信号）时，又由这些层次从下往上依次处理，最后返回给用户。

### 用户层软件：把系统调用包装成库函数

用户层是最接近用户的层次，它要做的就是向用户提供简单易用的交互接口——一般来说就是一些与 I/O 操作相关的库函数。

回想 C 语言里的 `printf("hello world")`，这句代码做的事情是在显示屏这个 I/O 设备上打印输出。`printf` 这个库函数就是由用户层软件提供的。既然要使用 I/O 设备进行输出，而只有操作系统才有对硬件操作的权利，所以用户层软件最终得请求操作系统提供服务——它会使用设备独立性软件这一层向上提供的系统调用接口。`printf("hello world")` 在用户层软件处理完之后，会被翻译成等价的 `write` 系统调用，调用时还会填入相应参数，比如要打印的字符串 "hello world"。

> **提示**：设备独立性软件是处理系统调用的层次，所以在有的题目里它也被称为"系统调用处理层"，要注意这个别名。

Windows 也是一样的套路。Windows 会向外提供一些系统调用，但系统调用太低级了，还需要进一步封装才方便用户使用，所以 Windows 在用户层做了进一步封装，向用户提供库函数接口——有兴趣可以去搜一下 Windows API，它就是用户层软件提供的库函数接口。

### 设备独立性软件：与硬件特性无关的那些事

设备独立性软件又叫设备无关性软件。正如名字所说，**基本上与设备硬件特性无关的功能，几乎都在这一层实现**。它要干的活可以列成六件：

**第一，向上层提供统一的调用接口**，比如 `read`、`write` 这一系列系统调用。刚才用户层翻译出的 `write`，接它的就是这一层。

**第二，实现设备的保护。**原理类似于对文件的保护：很多操作系统把设备看作一种特殊的文件，而不同用户对各个文件的访问权限不一样，那对"设备这种特殊文件"的访问权限自然也各不相同，所以操作系统需要提供设备保护的功能。之后的小节还会细聊。

**第三，差错处理**，也就是对设备产生的错误进行处理。这里有个印象就可以了，不需要了解细节——差错的类型实在太多，所以对差错处理基本不太可能考察。

**第四，设备的分配与回收。**经过之前那一系列学习，大家应该有直观体会：很多设备是临界资源，不可以同时分配给多个进程使用，所以操作系统当然要对设备这种资源进行分配与回收的管理。

**第五，数据缓冲区管理。**缓冲区用来屏蔽各个设备之间数据交换单位大小和传输速度的差异。缓冲区管理怎么实现，很容易在选择题里考察，之后的小节会专门讲解。

**第六，建立逻辑设备名到物理设备名的映射关系，并根据设备类型选择调用相应的驱动程序。**这是本层里值得展开讲的重头戏，下面单独说。

#### 逻辑设备表 LUT

什么叫逻辑设备名？就是用户在请求使用设备时所提供的名字，也就是用户所看到的设备名。

下次去学校打印店可以观察一下：打印店的电脑连着很多台打印机和复印机，你要打印输出时，它会让你选择用哪一台打印机或复印机。你看到的"打印机一""打印机二"，这些就是逻辑上的设备名。操作系统在背后管理这些设备，还有一个物理设备名。当你选择了某个逻辑设备，操作系统必须知道这个逻辑设备具体对应的是哪一台物理设备。

这个映射关系一般通过**逻辑设备表**（LUT，Logical Unit Table）来实现。表里除了映射关系，还会记录每个逻辑设备对应的设备驱动程序的入口地址：

```text
逻辑设备表 LUT
┌───────────────────┬──────────────┬────────────────────────┐
│ 逻辑设备名         │ 物理设备名    │ 驱动程序入口地址         │
├───────────────────┼──────────────┼────────────────────────┤
│ /dev/打印机1      │ 3 号打印机    │ 打印机驱动程序的入口地址  │
│ /dev/打印机2      │ 7 号复印机    │ 复印机驱动程序的入口地址  │
└───────────────────┴──────────────┴────────────────────────┘
```

表里的逻辑设备名竟然还带着类似文件路径的东西——这正是前面说的"设备被当作一种特殊的文件"，文件当然有存储路径。每个表项记录了逻辑设备名到物理设备名的映射，以及对应驱动程序入口地址在什么地方。

管理这张 LUT 有两种方式：

```text
方式一：整个系统只设一张 LUT
  → 不同用户若用相同的逻辑设备名，映射可能紊乱
  → 只适合单用户操作系统

方式二：为每个用户设置一张 LUT
  → 不同用户的逻辑设备名可以重复
  → 相同的逻辑设备名可以映射到不同的物理设备
```

方式一是这样出问题的：用户使用设备时用的都是逻辑设备名，操作系统又根据逻辑设备名查找 LUT 表项，所以只要两个用户用了相同的逻辑设备名，逻辑设备到物理设备的映射就会紊乱。

发现没有，这两种方式就有点类似文件管理里的**单级目录和两级目录**的区别：单级目录下不同用户的文件名不允许相同；两级目录下不同用户的文件名可以相同。"为每个用户设一张 LUT"，本质上就有点类似设置了两级目录。这两种方案和我们之前学过的知识点是有内在联系的——这种新旧知识挂上钩的地方，考试最爱考。

### 为什么必须有设备驱动程序

刚才说 LUT 里记着"驱动程序入口地址"，那为什么不同类型的设备需要不同的驱动程序？

在网上搜一下打印机，会有各种品牌、各式各样的打印机，不同打印机不仅外形不同，我们看不到的内部电子部分也可能是完全不同的结构。举个例子：假设佳能品牌的打印机内部有两个数据寄存器，状态寄存器里存 0 代表空闲、存 1 代表忙碌；换一种惠普打印机，内部可能只设了一个数据寄存器，而且状态寄存器存 1 代表空闲、存 0 代表忙碌——刚好和佳能的 0、1 所代表的意思相反。

通过这个例子会发现：不同型号的设备，内部电子部件可能完全不一样。而各个设备内部的硬件特性，肯定只有厂家的设计者才知道。操作系统要通过设备的控制器来控制设备的具体运行，就必须了解设备内部的硬件细节；但 I/O 设备多种多样，操作系统不可能了解所有设备的内部细节。

所以设备出厂时，厂家一般会提供一个与设备对应的**驱动程序**。要控制某个设备时，CPU 只需要执行这个设备相对应的驱动程序，就可以完成对该设备控制器的控制——比如设置控制器里的寄存器，或者检查设备的状态寄存器，这些工作都通过执行驱动程序来完成。

> **定义**：设备独立性软件不可以直接操纵硬件，它必须调用厂家提供的设备驱动程序，由驱动程序完成对硬件的具体控制（比如设置设备里的各种寄存器）。

生活里的印证：买一个机械键盘或者雷蛇鼠标，设备第一次插上电脑时，右下角总会弹出"正在安装驱动程序"的小提示——这个自动安装的驱动程序就是厂家提供的，为了让操作系统实现对新设备硬件的具体控制。另外，各类型的设备驱动程序在系统中一般以**独立进程**的方式运行存在。

回到 LUT：要使用"打印机一"，操作系统查表之后就知道接下来要执行的设备驱动程序入口地址在哪儿，于是根据表项记录的信息找到对应的驱动程序。为什么不同设备要对应不同驱动程序？就是因为各种设备内部硬件特性不一样，必须执行与之对应的特定驱动程序，才能正常完成对设备硬件的控制。

### 中断处理程序：I/O 应答的入口

中断相关的概念在第一章已经学过很多了，这里相当于复习。

硬件设备完成 I/O 操作之后，会发出一个中断信号作为 I/O 应答。系统根据中断信号的类型，找到与它对应的中断处理程序，然后执行这个程序进行中断处理。处理流程是这样的：

```text
硬件完成 I/O 操作 → 发出中断信号
      ↓
根据中断信号类型找到对应的中断处理程序
      ↓
从设备控制器中读出设备状态，判断这次 I/O 是否正常结束
      ├─ 正常结束：从控制器的数据寄存器读出一个字的数据
      │            经由 CPU 放到内存缓冲区 → 完成一个字的读入
      └─ 非正常结束（如硬件故障）：根据异常原因做出相应处理
```

中断处理程序把这次要输入的数据放入内存之后，接下来交给设备驱动程序进一步处理；驱动程序处理完，再交给上一层的设备独立性软件再进一步处理，一层一层往上，最后返回给用户。所以要输入一个数据，对这个数据的处理是从下往上依次层层处理的。

从刚才的讲解中也发现一个关键事实：除了设备驱动程序会直接和硬件打交道，**中断处理程序也需要直接和硬件打交道**；再往上的设备独立性软件和用户层软件，就不会直接和硬件打交道了。

### 最常考的东西：层次顺序与功能归属

把这一小节从上至下过了一遍，考试最常考的其实是**各个层次之间的顺序**：经常问一个 I/O 请求的处理次序是什么样的，或者发生 I/O 应答时每一层软件的处理顺序依次是怎么样的。所以一定要理解并记住从上至下的顺序：请求由上至下层层处理，最后扔给 I/O 硬件执行实际操作；硬件做完发出中断信号，软件层次由下至上层层处理，最后返回用户。

另外也可能考察各个层次要完成什么功能。抓住一个最重要的特点：**设备驱动程序和中断处理程序是直接和硬件打交道的**。凡是直接涉及硬件细节的操作，肯定由下面这两层完成；除此之外的功能，基本都是在设备独立性软件完成的。再加上对逻辑设备表 LUT 的功能有个大体印象，这个小节就齐了。

### 为什么一个统一接口不够用

进入第五章的新考点：输入输出应用程序接口。还是从层次结构图出发：上层的用户应用程序需要通过系统调用的方式，请求使用底层的某一种 I/O 设备。但 I/O 设备的种类和特性非常多样化，上层应用程序很难通过一个统一的系统调用接口来操作所有类型的 I/O 设备。

为什么"很难"？拿块设备来说，它有寻址的概念——一个磁盘，我们可以指定读这个磁盘的哪个地址，可以用一个读写指针指向磁盘的某一个位置，每次还可以指定要读几个字节、多少 KB。所以从块设备读数据的 `read` 系统调用，是不是就可以写成：指明要操作的是哪个块设备、此次要读入几个字节、从哪儿开始读。

那这种读操作的系统调用接口，适用于字符型设备吗？显然不适用。字符型设备是不可寻址的——键盘就是最典型的字符型输入设备，每次只能读一个字符，键盘没有地址的概念。用系统调用从键盘读一个字符时，能指明"从哪个地址读"吗？显然不行。

因此，由于底层设备多种多样，对各种类型设备的 I/O 读写所需提供的系统调用参数各不相同，用户层应用程序**无法用一个统一的系统调用接口完成所有类型的设备 I/O**。于是设备独立性软件需要对上层应用程序提供若干种类型的程序接口：访问字符设备、块设备、网络设备，调用的系统调用接口各不相同。

这三类接口的定义其实都遵循同一个逻辑——**接口是依据这种设备的特性来定义的**：

| 设备类型 | 系统调用 | 地址参数 | 读写单位 |
| :---: | :--- | :---: | :--- |
| 字符设备 | `get` / `put` | 无 | 一个字符 |
| 块设备 | `seek` + `read` / `write` | 有 | 多个字节 |
| 网络设备 | `socket` / `bind` / `connect` + `read` / `write` | 由 IP + 端口定位 | 数据包 |

字符型设备没有地址的概念，所以 `get` 和 `put` 就不需要提供地址参数；块设备有地址的概念，访问时就需要提供地址参数，指明要读或写哪个地址。

- **字符设备接口**：`get` 从指定字符设备读出一个字符，`put` 往指定字符设备写一个字符，读写以字符为单位。
- **块设备接口**：就是我们最熟悉的 `read` 和 `write`。先用 `seek` 系统调用把读写指针放到磁盘的某个地址，之后就可以用 `read` 或 `write` 往指针所指位置往后读/写若干个单位的字符——每次读写多个字节，同时要指明读写的地址。

### 网络设备接口：socket 一家子

网络设备大家不熟悉，值得单独展开。你的电脑里有个"网卡"，它就是所谓的网络控制器，用于收发网络数据包。网卡可能会收到很多很多数据包，而不同的数据包应该丢给不同的应用程序——比如你同时开着支付宝和微信，网卡既会收到给支付宝的数据包，也会收到给微信的数据包，这些数据包到底该给哪一个应用程序？我们得做一些区分。

为了达成这个目的，网络设备接口又叫**网络套接字接口**，向上层应用程序提供这样几个系统调用：

- `socket`：创建一个网络套接字，创建时还需指明连接使用的网络协议，比如 TCP 还是 UDP。它会返回一个描述符，可以理解为指向这个套接字的指针。
- `bind`：把套接字绑定到本地的某一个端口上。学过计算机网络都知道，每台电脑有各自的 IP 地址，IP 定位到一台主机；再加上一个端口号，端口号就可以映射到计算机当中的某一个应用程序。
- `connect`：把套接字连接到远程的某台主机上。

套接字初始化完毕之后，就可以用 `read` 或 `write` 对网络套接字进行数据读写了。

#### 一次完整的套接字通信

这么说比较抽象，用一个两台主机通信的完整例子来感受一遍。

```text
  主机一（IP1）                              主机二（IP2）
  ┌───────────────┐                        ┌───────────────┐
  │ P1        P2  │       网络             │      P3       │
  │  ↓socket+bind │ ═══════════════════>  │  socket+bind  │
  │ 端口 211      │                        │  端口 6666     │
  └───────────────┘                        └───────────────┘

  发送：P1 准备数据 → write(fd) → 数据复制到内核缓冲区
        → 驱动程序把数据输出到网卡 → 数据包按 IP+端口 发上网络
  接收：到达主机二，网卡发出中断信号 → 中断处理程序把数据
        搬进 6666 端口对应的内核缓冲区 → P3 用 read 取走
```

主机二的 P3 进程要进行网络通信，先用 `socket` 系统调用创建一个网络套接字。"网络套接字"这个翻译我认为可能不太好理解，不妨简单理解为**申请一片内核存储空间**，这片空间会用于接收或发送数据。`socket` 会返回一个描述符（可以理解为指向套接字的指针）。有了套接字对象，还需要 `bind` 把它绑定到本地某个端口，比如绑定到 6666 端口，这样主机二的套接字就可以等待被连接了。

主机一做相同的操作：P1 进程通过 `socket` 申请创建套接字对象，通过 `bind` 绑定到本机的 211 端口。现在两台主机都有了各自的套接字和收发数据的端口号，接下来用 `connect` 把本机套接字连接到另一台机器的套接字上——让主机一的 P1 调用 `connect`，指明要把 fd 所指向的套接字连接到某个 IP 地址的 6666 端口，也就是把 IP 地址和端口号作为参数写进去。这个系统调用会使两个套接字之间建立起连接：结合计网来看，这个连接属于应用层的连接，传输层可以指定一种规定好的协议，比如 TCP 或 UDP。

连接建好，就可以通信了。P1 想给 P3 发一个数据包：P1 先在自己的用户区准备好数据，然后 `write` 系统调用指明往 fd 所指向的套接字里写入这些数据。设备独立性软件收到 `write` 之后，会把用户进程准备好的数据复制到内核区——套接字对应的那片缓冲区（这片内核缓冲区由设备独立性软件管理）。接着设备独立性软件再调用驱动程序来处理这批数据，驱动程序负责把准备好的数据输出到网络设备上，数据包就可以发送到网络上了。发送时要用到计网里学的 TCP、UDP 那一系列东西：套接字对象知道数据包应该发送到哪个 IP 的哪个端口，所以网络控制器发送数据包时也明确知道这个包该何去何从。

数据包一路顺着网线爬到主机二，网卡会向主机发出一个中断信号，主机二的中断处理程序出来工作，把收到的数据搬到内核缓冲区里。因为早就知道数据该送到 6666 端口，所以数据会被复制到 6666 端口对应的那片内核缓冲区中。接下来 P3 要接收数据包，只需要 `read` 系统调用，指明从 fd 所指的套接字对象中读出一个数据包——设备独立性软件就会从缓冲区里把这坨数据复制到用户进程的用户区，P3 就可以使用收到的数据了。

通过这个例子，网络设备接口已经有了一个直观理解：**用户进程用网络设备相关的系统调用接口创建套接字对象，套接字和套接字之间建立点对点的连接；每个套接字绑定一个本机端口，通过主机的 IP 地址结合套接字绑定的端口，就可以找到全世界任何一个套接字对象。**刚才 P1 建立了和 P3 的套接字连接，那同一台主机上的 P2 想和另一台主机的另一个套接字建立连接怎么办？P2 同样可以用 `socket` 申请一个新的套接字，再绑定另一个端口就 OK 了。

正因为不同的套接字绑定了不同的端口，你的网卡收到很多数据包之后，才可以根据数据包里指明的端口信息，把数据包放到合适的、对应的套接字对象上。这就是为什么你的手机同时运行那么多软件、所有软件都需要网络通信，但数据包的传输不会出现任何失误。

### 阻塞 I/O 与非阻塞 I/O

很简单的两个概念，但对着例子理解：

**阻塞 I/O**：应用程序发出 I/O 相关的系统调用之后，需要转为阻塞态，等待 I/O 完成。比如从键盘 `get` 读入一个字符，只要键盘输入的动作没完成，这个进程是不是就得一直等下去？我们初学者写 C 语言等待键盘输入的时候，只要键盘不输入，进程就没法继续往下执行——这就是阻塞 I/O：发出系统调用请求之后需要阻塞等待。

**非阻塞 I/O**：发出系统调用请求之后，系统调用可以迅速返回，进程无需阻塞等待。比如用 `write` 系统调用往磁盘写数据，即便磁盘正在忙碌，也是这样：进程准备的数据在用户区，操作系统内核有内核区，你发出 `write` 想把这块数据写到磁盘时，设备独立性软件那一层会迅速响应你的系统调用请求，先把你的数据复制到内核再说。只要数据复制到内核，接下来内核慢慢把数据写回磁盘就行了；至于用户进程，只要完成了数据复制这一步，就可以继续往下执行了。所以这种类型的系统调用不需要阻塞等待，可以迅速返回。

### 设备驱动程序接口：操作系统给厂商定标准

最后一个新考点：设备驱动程序的接口。同样从层次结构出发——设备独立性软件需要根据实际操作的设备不同，去调用不一样的设备驱动程序。

问题来了：罗技和雷蛇各生产各自的设备，这些公司需要自己实现自己的驱动程序。假如对罗技的设备做读操作，它驱动程序里的读函数叫 `read`、后面跟两个参数；而另一个公司的驱动程序接口可能不一样，同样叫 `read`，却要传入三个参数。这对设备独立性软件来说是不是就很麻烦？我要调用不同公司编写的驱动程序，还得修改我的函数调用代码——也就是要**频繁地修改操作系统内核**，这显然不科学。

因此，操作系统会统一一个标准，要求设备厂商在制作驱动程序时按照规定好的统一标准来开发。比如我规定：任何一个厂商，你想让你的设备在我这个操作系统上正常被支持、被使用，那你提供的 `read` 就必须名字叫 `read`，后面必须有三个参数，而且参数的类型、大小什么的，我都会给你统一的标准。这样各个厂商就根据操作系统规定的标准，去开发专属于这个操作系统的驱动程序。

我自己平时录课会用到一块数位板，这也是一个 I/O 设备。在它的官网上你会看到，它有 Mac 系统的驱动程序，也有 Windows 系统的驱动程序——因为不同的操作系统对设备驱动程序的接口标准各不相同，设备厂商必须根据不同操作系统提出的标准要求开发不同的驱动程序，只有这样自己的设备才能在各种操作系统上被支持、被使用。

> **结论**：驱动程序这一层需要向上层的设备独立性软件，提供一个统一标准的接口。

## I/O核心子系统：功能布局、假脱机技术与设备分配
> 对应块：BLK32 | 覆盖分集：P78-P80 | 块标题（分集名）：《5.2_1_IO核心子系统》

从这个小节开始，我们学习 I/O 核心子系统相关的一系列功能。先回忆一下 I/O 软件的层次——它可以分为这样的四个层次，其中**设备独立性软件、设备驱动程序、中断处理程序**这三层是属于操作系统内核部分的，所以它们也称作 **I/O 核心子系统**，又可以简称为 I/O 系统。

因此，I/O 核心子系统需要实现的功能，就是这三层需要实现的功能。上一个 小节中咱们已经提过，考研当中需要重点掌握的是：**I/O 调度、设备保护、假脱机技术（SPOOLing 技术）、设备分配与回收、缓冲区管理**这几种功能的原理和实现。那这些功能分别需要在哪些层次实现呢？

> **结论**：所有和硬件直接相关的，肯定是设备驱动程序和中断处理程序负责的；但刚才列的那些功能当中，没有一个直接与硬件相关。

其中，假脱机技术又叫 SPOOLing 技术，它一般来说是在**用户层**实现的——因为假脱机技术需要使用到磁盘这种设备的设备独立性软件这一层的服务，所以它落在用户层软件当中。而 I/O 调度、设备保护、设备的分配与回收、还有缓冲区管理，这几个功能是在**设备独立性软件**这一层实现的。

```text
┌────────────────────────────────┐
│         用户层软件              │ ← 假脱机（SPOOLing）在这层实现
├────────────────────────────────┤
│       设备独立性软件            │ ← I/O调度、设备保护、
│                                │    设备分配与回收、缓冲区管理
├────────────────────────────────┤
│       设备驱动程序              │
├────────────────────────────────┤   这三层属于操作系统内核
│       中断处理程序              │   ＝ I/O核心子系统（I/O系统）
└────────────────────────────────┘
```

这张图把功能和层次对上了：内核三层是 I/O 核心子系统，考研重点功能几乎都压在设备独立性软件这一层，唯一的例外是假脱机技术——它实际在用户层实现，但在 408 考研大纲中也被归为 I/O 核心子系统要实现的功能之一，所以我们按从上至下的顺序来展开。

### 先热身：I/O 调度与设备保护

在展开重头戏之前，先简单介绍两个我们很熟悉的功能的实现。

**I/O 调度**。其实 I/O 调度和处理机调度是很类似的：用某一种算法来确定一个好的顺序，来处理各个 I/O 请求。就比如说咱们上一章学过的磁盘调度，其实就是用某一种算法来确定应该先满足哪些磁盘的访问请求——而磁盘本身也是一种 I/O 设备，所以磁盘调度本来就是 I/O 调度的问题。除了磁盘之外，像打印机等等这些设备，也同样可以采用先来先服务、优先级算法或者短任务优先等等这些算法，来确定一个合适的 I/O 调度顺序。这些咱们之前已经训练过很多次了，这里不再赘述：**根据题目中提供的算法名字，再结合之前学过的调度算法思想来分析做题就可以了。**

**设备保护**。怎么实现设备保护？这一点咱们也已经很熟悉了。在 UNIX 系统当中，设备会被看作是一种**特殊的文件**。因此系统也会为各个设备建立一个相应的 FCB（文件控制块）。就像文件管理章节中学到的一样，不同的用户对不同的文件有不同的访问权限——某个用户对有的文件只能读，对有的文件又可以读也可以写。那么只要把设备看作一种特殊的文件，当一个用户想要访问某种设备的时候，系统就会根据这个设备对应的 FCB 来判断这个用户是否有相应的访问权限，这样就实现了所谓的设备保护。

> **提示**：设备保护本质上就是文件保护那一块所需要做的事情。这个知识点如果回忆不起来，可以再参考文件管理章节中"文件保护"那一小节的内容。

这一部分只是对 I/O 核心子系统需要实现哪些功能做了简要概述。之后的小节我们会展开设备分配与回收、缓冲区管理怎么实现，而排在最前面先讲的，是假脱机技术。

### 脱机技术：纸带机逼出来的智慧

要理解假脱机技术，得先明白什么是脱机技术、它解决什么问题——假脱机技术，其实就是**用软件的方式来模拟实现脱机技术**。

咱们在第一章"操作系统的发展历程"那一个小节当中学过：在还没有操作系统的手工阶段，需要用速度特别慢的纸带机把程序员的程序读入，CPU 需要直接和纸带机交互。纸带机的速度特别慢，所以输入数据、把结果输出的过程都很慢。CPU 的处理速度明明很快，但在数据输入和输出的时候，它依然需要迁就纸带机这种慢速的输入输出——这就是那个阶段暴露出的很严重的**速度矛盾**，对 CPU 这种昂贵的资源是一种极大的浪费。

于是在之后的批处理阶段，人们引入了脱机技术。刚开始的脱机技术是用磁带来实现的：

```text
   脱机输入                                   脱机输出
┌──────┐   ┌────────┐   ┌──────┐    ┌──────┐   ┌────────┐   ┌────────┐
│纸带机│──▶│外围控制机│──▶│ 磁带 │    │ 主机 │──▶│  磁带  │──▶│ 纸带机 │
│(慢)  │   └────────┘   │(快)  │    └──────┘   │  (快)  │   └────────┘
└──────┘                └──────┘                └────────┘        (慢)
                              ▲
                       CPU 直接从磁带读取输入数据
```

输入的方向是：程序和数据先由纸带机读入、经外围控制机送到**速度比纸带机快很多**的磁带上，之后 CPU 可以直接从磁带中读取想要的输入数据——这就很大地缓解了速度矛盾。输出的方向也一样：主机首先把数据输出到快速的磁带上，之后再由磁带把数据依次输出到慢速的纸带机上。由于磁带比纸带机快得多，CPU 在输出的时候就可以节省很多等待输出完成的时间了。

为什么这种技术叫"脱机"呢？所谓**脱机**，就是指**脱离主机的控制来进行输入和输出的操作**。刚才的讲解里大家应该已经明白了：输入和输出的过程并不需要主机或者说 CPU 的干预和控制，这样 CPU 就可以有更多时间去处理别的计算任务了。

所以引入脱机技术之后，好处有两个：

- 除了缓解 I/O 设备和快速的 CPU 之间的速度矛盾之外——
- 即使 CPU 正在忙碌，也可以先把数据**预先**输入到磁带当中；而在输出的时候，即使纸带机正在忙碌，CPU 也可以先把数据输出到磁带当中。

> **结论**：脱机技术实现了数据的**预输入**和**缓输出**——输入不必等 CPU、输出不必等纸带机，两边各忙各的。

### 假脱机（SPOOLing）：用软件模拟一套"脱机"

基于脱机技术的思想，人们又发明了假脱机技术，又叫 SPOOLing 技术。假脱机技术当中的"脱机"，是用软件的方式来模拟实现的。

一个 SPOOLing 系统（假脱机系统）一般来说有这样几个组成部分。首先，系统会在**磁盘**上开辟出两个存储区：

- **输入井**：用于模拟脱机输入时的那个磁带，收容从输入设备输入的 I/O 数据；
- **输出井**：用于模拟脱机输出时的那个磁带，收容用户进程输出的数据。

除了磁带之外，还需要模拟外围控制机——这就是两个进程：**输入进程**用于模拟脱机输入时的外围控制机，**输出进程**模拟脱机输出时的外围控制机。显然，输入进程和输出进程需要和用户进程**并发地执行**，才能完成这种模拟脱机输入、模拟脱机输出的过程。

> **易错点**：SPOOLing 技术肯定是需要**多道程序技术**的支持的——没有并发，就不存在"输入进程/输出进程与用户进程同时推进"这回事。

再来看数据是怎么流动的。当有数据需要从设备输入到计算机的时候，输入进程会把这些要输入的数据放到磁盘的输入井当中；输出进程模拟脱机输出的原理也类似，无非就是从磁盘的输出井当中取出数据，然后输出到设备上。但这里还有一个细节要注意：在**内存**当中也会开辟两个缓冲区——**输入缓冲区**和**输出缓冲区**。它们的作用是在模拟脱机输入、模拟脱机输出的时候充当一个**数据的中转站**：

```text
【模拟脱机输入】
输入设备 ──▶ 输入进程 ──▶ 输入缓冲区(内存) ──▶ 输入井(磁盘) ──▶ 用户进程

【模拟脱机输出】
用户进程 ──▶ 输出井(磁盘) ──▶ 输出缓冲区(内存) ──▶ 输出进程 ──▶ 输出设备
```

也就是说，输入进程实现模拟脱机输入时，先接收输入设备的数据，把数据先放到输入缓冲区里，之后再把输入缓冲区当中的数据放到磁盘的输入井当中；数据输出时则反过来：输出进程从输出井当中取出数据，放到内存的输出缓冲区当中，之后再由输出缓冲区往输出设备写出数据。这就是假脱机技术的原理，大家结合上面的图再自己理解一下。

假脱机系统的组成部件和脱机技术的部件是一一对应的，对照着记最省事：

| 脱机技术（磁带时代） | 假脱机技术（软件模拟） |
| :------------------- | :--------------------- |
| 脱机输入用的磁带 | 磁盘上的**输入井** |
| 脱机输出用的磁带 | 磁盘上的**输出井** |
| 外围控制机（输入侧） | **输入进程** |
| 外围控制机（输出侧） | **输出进程** |
| （无对应物） | 内存中的**输入/输出缓冲区**（数据中转站） |

### 共享打印机：SPOOLing 的经典应用

接下来看一个具体的假脱机技术的应用——共享打印机的实现。

先回忆两个概念：**独占式设备**和**共享设备**。独占式设备就是指那些只允许各个进程**串行使用**的设备：在一段时间内，这种设备只能满足一个进程的请求、只能为一个进程服务，为这个进程服务结束之后才可以接着答应下一个进程的请求。而共享设备是一种允许多个进程同时使用的设备——注意，所谓"同时"有可能是宏观上的同时，微观上可能是各个进程交替地使用这个设备，所以一个共享设备其实是可以同时满足多个进程的使用请求的。

打印机肯定是一种独占式设备，因为它的速度很慢——这一点大家在生活当中也有所体会。打印机在一段时间内只能为一个用户、一个进程服务：如果同时处理多个进程的请求，就有可能导致各个进程的打印输出结果相互混杂在一起，这显然不是我们期待的。所以对于独占式设备来说，如果一个进程正在使用打印机，另一个进程再请求使用打印机时必然需要阻塞等待，只有第一个进程使用完并且释放了这个资源之后，第二个进程才可以被激活，然后继续发出打印请求。

那既然打印机是独占式设备，为什么还把它称作**共享打印机**呢？其实这所谓的"共享"，就是用 SPOOLing 技术来实现的。如果有多个用户提出要使用打印机的请求，系统首先会**答应他们的请求**——但并不会直接把打印机分配给其中某一个进程，而是由一个叫做**假脱机管理进程**的东西，为每个用户进程做两件事：

1. 在磁盘的**输出井**当中为这个进程申请一个空闲的缓冲区——注意这是磁盘里的缓冲区，而不是内存中的缓冲区。之后假脱机管理进程会把用户进程想要打印输出的数据，先放到给它申请的这个缓冲区当中。
2. 再为这个用户进程申请一张空白的**打印请求表**，并且把用户的打印请求的各种参数填入表中。这个表就是用来说明用户的打印数据存放在哪个缓冲区里、存放在什么地方等等这一系列信息的。

所以不要被"打印请求表"这个浮夸的名词给迷惑，它的本质无非就是一个**打印任务的说明书**，对吧。接下来这个"说明书"会被挂到一个叫做**脱机文件队列**的队列上——这个队列其实就是一系列打印任务的队列。

之后，**输出进程**会从这个任务队列当中取出某一个任务，根据打印请求表的说明来执行相应的打印任务。比如刚才这个用户进程提出的打印任务此时挂在队列的队头，那输出进程就应该先满足队头的这个任务：根据打印请求表，它可以知道要打印输出的数据在哪一块缓冲区当中，于是从这块缓冲区当中读出数据，首先读入到内存的输出缓冲区当中，之后再从输出缓冲区把数据输出到打印机上，让打印机执行具体的打印任务。当这个打印任务完成之后，这张打印请求表就可以从队列当中删除了。之后只要打印机空闲，输出进程就可以从队列中再取出下一个任务，根据这个任务的指示执行后续的打印。

在采用了 SPOOLing 技术之后，虽然系统当中只有一台打印机，但每个进程提出打印请求的时候，系统都会为这个进程在输出井当中申请一个缓冲区、一个存储区——**这就相当于为这个进程分配了一个逻辑上的设备**。这样每个用户进程都会感觉到似乎是自己独占了一台打印机设备，于是就实现了对打印机的共享使用。

> **结论**：SPOOLing 技术可以把一台物理设备虚拟成逻辑上的多台设备，把独占式设备改造成共享设备。

### 设备分配要考虑什么

下面进入设备独立性软件这一层的重头戏：设备的分配与回收。设备分配的时候应该考虑哪些因素？三个方面：**设备的固有属性、设备的分配算法、设备分配中的安全性**。

**设备的固有属性**可以分为三种。**独占设备**：一个时间段内只能分配给一个进程使用的设备，比如咱们很熟悉的打印机。**共享设备**：可以同时分配给多个进程使用的设备，比如磁盘——但所谓共享是宏观上共享，微观上各个进程有可能是交替使用这个设备的。**虚拟设备**：就是上一个 小节介绍的，采用 SPOOLing 技术把独占设备改造成的虚拟的共享设备——把独占式的打印机改造成共享打印机，并且同时分配给多个进程使用。

**设备的分配算法**：可以用很多我们很熟悉的算法来进行设备的分配，比如先来先服务、优先级高者优先、短任务优先等等。这些算法的具体策略通过名字就可以判断，不再展开赘述。

**设备分配中的安全性**，这是重点，有两种方式：

| 分配方式 | 做法 | 优点 | 缺点 |
| :------- | :--- | :--- | :--- |
| 安全分配方式 | 为进程分配设备后，就把该进程阻塞，直到它释放这个 I/O 设备之后才唤醒它 | 破坏了"请求和保持"条件，**不会死锁** | 进程的 CPU 与 I/O 设备只能**串行**工作，系统资源利用率低，进程执行效率也低 |
| 不安全分配方式 | 进程发出 I/O 请求、分到设备后**不阻塞**，继续往下执行，还可以发出更多新的 I/O 请求；直到某一个 I/O 请求得不到满足时才阻塞 | 进程的计算任务和 I/O 任务可以**并行**执行，效率高 | 不安全，**可能死锁** |

用请求打印机打印输出的例子体会一下这两种方式的差别。**安全分配方式下**：一个进程请求使用打印机、打印机分配给它之后，这个进程就必须先阻塞等待。虽然按理来说，这个进程只需要把数据丢给打印机，就不用再管打印机了，它完全可以继续往下执行——但由于采用的是安全分配，这个进程不得不阻塞，一直到打印结束之后才会被再次唤醒、继续往下执行。这样在一个时间段内，每个进程只能使用一个设备。**不安全分配方式下**：进程请求打印机服务之后，系统把打印机资源分配给它，但这个进程把数据丢给打印机之后就不需要再管打印过程了，可以继续往下执行，甚至在之后的执行过程中还可以申请使用别的 I/O 设备，比如扫描仪等等——一个进程可以同时使用多个设备。缺点就像名字所说的：不安全，有可能发生死锁。

> **提示**：第二章死锁那一章学过，如果采用的是不安全分配方式，可以用**死锁避免**——也就是**银行家算法**来避免系统进入不安全状态。

### 静态分配与动态分配

接下来是两种我们很熟悉的设备分配方式。

**静态分配**：指进程运行之前就为其分配它所需要的全部资源，一直到进程运行结束之后才把资源归还给系统。如果进程在运行之前，它所需要的全部资源暂时得不到完全的满足，那么这个进程就暂时不能投入运行。

**动态分配**：进程在运行过程当中动态地申请设备资源，并不是刚开始就得到全部的资源。

这两种方式咱们在死锁那个小节当中也讲过，不再展开。

> **提示**：静态分配方式就是破坏了"请求和保持"这个产生死锁的必要条件，所以不会发生死锁。讲到这里，希望大家再回忆一下死锁发生的四个必要条件，分别可以用什么样的方法破坏它们——这是需要思考和复习的地方。

### 四张表管住所有设备

设备分配管理需要用到哪些数据结构？讲这些数据结构之前，先复习一下设备控制器和通道之间的关系：**一个通道可以控制多个控制器，而一个控制器又可以控制多个设备**，所以我们可以把它们之间的关系理解为一个树的形状：

```text
              ┌────────┐
              │  通道  │        （一个系统可能有多个通道）
              └───┬────┘
          ┌───────┼───────┐
     ┌────┴───┐ ┌─┴────┐ ┌─┴──────┐
     │ 控制器 │ │控制器│ │ 控制器 │
     └───┬────┘ └─┬────┘ └───┬────┘
       ┌─┴─┐    ┌─┴─┐      ┌─┴─┐
     ┌─┴┐ ┌┴─┐ ┌┴┐ ┌┴┐    ┌┴┐ ┌┴─┐
     │设备││设备││设备││设备│  │设备││设备│
     └───┘└──┘ └─┘ └──┘    └──┘ └──┘
```

从另一个角度说，每一个设备肯定有它所从属的控制器，每一个控制器也肯定有它所从属的通道。要注意，一个系统中可能会有**多个通道**。由于要控制一个设备，肯定需要找到这个设备的控制器；要控制一个控制器，肯定又需要找到这个控制器所从属的通道——所以设备分配管理中的数据结构，需要表示出这种**从属关系**。沿着这条树走一遍，四张表就好记了。

#### 设备控制表 DCT

系统会为**每一个设备**配置一张设备控制表（DCT），用于记录设备的使用情况。常用的字段有这些：

- **设备类型**：这个设备到底是打印机、扫描仪还是键盘等等；
- **设备标识符**：就是我们之前提到过很多次的**物理设备名**，它是这个设备的唯一 ID，系统中各个不同的设备标识符都不同；
- **设备状态**：区分这个设备此时是忙碌、空闲还是故障等等；
- **指向控制器表的指针**：用来找到一个设备所从属的控制器到底是哪一个；
- **重复执行次数或时间**：设备有很多机械零件，故障的几率其实是很大的——比如使用打印机或复印机的时候经常出现卡纸。不过并不是说执行一次 I/O 操作失败之后就认为这次 I/O 操作真的失败了，系统会重复执行多次这个 I/O 操作，这个字段就用于记录它到底失败了几次；只有重复执行多次之后仍然不成功，才认为这次 I/O 是失败的；
- **设备队列的队首指针**：用于指向此时正在等待使用这个设备的进程队列，这个队列由进程的 PCB 组成。还记得进程管理章节提过的吗？系统会根据各个进程阻塞原因的不同，将进程的 PCB 挂到不同的阻塞队列当中。假如进程此时正在等待某一个 I/O 设备的分配，而这个 I/O 设备暂时没法分配给它，那么这个进程就会挂到那个 I/O 设备的设备控制表所指向的等待队列当中。

#### 控制器控制表 COCT

每一个设备控制器都会对应一张控制器控制表（COCT），系统根据这个表当中的信息对设备控制器进行相应的操作和管理。常用字段：

- **控制器标识符**：各个控制器的唯一 ID；
- **控制器状态**：比如忙碌还是空闲；
- **指向通道表的指针**：每一个设备控制器都会有一个它所从属的通道，系统可以根据这个指针找到它所从属的通道；
- **队首指针和队尾指针**：指向正在等待这个设备控制器的进程队列。

#### 通道控制表 CHCT

每个通道都会对应一张通道控制表（CHCT），操作系统根据这个表的信息对通道进行相应的操作和管理。与前面的结构很类似：

- **通道标识符**：这个通道的唯一 ID；
- **通道状态**：指明它是忙碌、空闲还是故障；
- **与通道连接的控制器表首指针**：操作系统可以根据这个字段找到这个通道控制的**所有**控制器相关的信息，也就是找到这些控制器控制表的集合；
- **队首指针与队尾指针**：如果通道暂时不能为一个进程服务，那么这个进程依然需要等待这个通道的服务，这两个字段就是用于指向等待这个通道的那些进程队列的。

#### 系统设备表 SDT

第四个需要设置的数据结构叫系统设备表（SDT），它记录了**系统中全部设备**的情况：每一个设备对应一个表目，表目中记录该设备的**设备类型**（打印机、扫描仪还是键盘）、**设备标识符**（物理设备名，唯一的）、这个设备的**设备控制表 DCT**，最后还记录了这个设备的**驱动程序的入口地址**。

> **易错点**：系统设备表记录的是系统中**全部**设备的情况，而不是某一个设备的。所以当用户用设备名请求使用某一个设备的时候，操作系统是可以从系统设备表当中找到用户指定的设备到底是哪一个的。

### 设备分配的完整流程

基于这四张表，我们来看设备分配的具体步骤。

```text
进程提供【物理设备名】作为系统调用参数
   │
   ▼  查系统设备表 SDT（逐个表目比对设备标识符）
找到匹配的表目 ──▶ 得到该设备的设备控制表 DCT
   │
   ▼  检查 DCT 中的设备状态
 设备忙？──是──▶ 把进程挂到该设备的等待队列（阻塞队列）
   │否（空闲，分配设备）
   ▼  根据 DCT 中"指向控制器表的指针"找到 COCT
 控制器忙？──是──▶ 把进程挂到控制器的阻塞队列
   │否（空闲，分配控制器）
   ▼  根据 COCT 中"指向通道表的指针"找到 CHCT
 通道忙？──是──▶ 把进程挂到通道的阻塞队列
   │否（空闲，分配通道）
   ▼
 设备 + 控制器 + 通道 三者都分配成功
   ▼
 启动 I/O 设备，开始数据传送
```

第一步，操作系统根据进程提出的**物理设备名**查找系统设备表 SDT。用户在编程的时候需要提供物理设备名作为系统调用的参数；操作系统查找系统设备表时，会把各个表目当中记录的设备标识符和用户提供的物理设备名进行比对，找到相匹配的一个表项，之后就可以找到这个设备对应的设备控制表 DCT 了。

接下来根据 DCT 当中记录的信息判断此时这个设备是否空闲：空闲就把设备分配给进程；如果设备忙碌，就需要把这个进程挂到这个设备对应的等待队列（阻塞队列）当中，直到设备空闲、并且把设备分配给该进程之后，才把这个进程重新唤醒。

但除了分配设备本身之外，还需要把这个设备对应的**控制器**也分配给这个进程：系统根据 DCT 中指向控制器表的指针找到控制器控制表 COCT，检查控制器是否空闲——空闲就把控制器分配给进程，忙碌就把进程放到控制器的阻塞队列当中。分配了控制器之后，还要分配相应的**通道**：又根据指针找到通道控制表 CHCT，过程同样类似——通道空闲就分配，通道忙碌就把进程挂到通道的阻塞队列当中。

> **结论**：只有**设备、控制器、通道**这三个东西都分配成功的时候，这次设备分配才算成功，之后才可以开始启动 I/O 设备进行数据传送。

### 逻辑设备名：让编程不再绑定具体设备

我们来思考一下刚才这个分配过程有什么缺点。还记不记得——用户在编程的时候，是需要提供**物理设备名**作为系统调用的参数的，所以这种方式对用户编程来说很不方便。假如用户使用的物理设备名叫 A，而之后这个物理设备又进行了更换，换成了物理设备 B——由于用户编程时使用的依然是 A 这个名字，只要物理设备更换了，用户之前所写的程序就无法运行了，它再请求使用物理设备 A 时肯定没办法分配成功。

除了这个缺点之外：当一个进程请求的物理设备正在忙碌时，**即使系统当中还有同类型的设备**，这个进程依然必须阻塞等待。比如我们一台电脑上连了三台打印机，进程请求使用的是第一台打印机，那么虽然第二台和第三台打印机此时有可能是空闲的，但只要第一台忙碌，这个进程依然需要阻塞等待——可显然其实可以把这个打印任务分配给第二台或者第三台打印机去做。所以采用这种方式也会导致**设备利用率不高**的问题。

解决这个问题的方法咱们之前谈到过：建立**逻辑设备名与物理设备名之间的映射机制**。用户编程的时候使用的是**逻辑设备名**，由操作系统负责完成逻辑设备名到物理设备名的转换。

引入这种机制之后，进程请求使用某种设备时只需要提供逻辑设备名。所谓逻辑设备名，其实就是指明它所要使用的**设备类型**——比如"我想使用打印机这种类型的设备"。由于系统设备表当中有一个字段记录的就是设备的类型，因此操作系统可以根据用户提供的逻辑设备名（也就是设备类型）去查找系统设备表，找到一个**指定类型的、并且空闲的**设备，把它分配给进程；只有这个类型的设备**全部**都处于忙碌状态的时候，才需要把这个进程阻塞。

把设备分配给进程之后，操作系统还需要在**逻辑设备表 LUT** 当中新增一个表项。逻辑设备表就是用于记录**逻辑设备名到物理设备名的映射关系**的一张表，除了这个映射关系之外，还需要记录这个设备对应的驱动程序的入口地址。之后的操作就和之前一样了：根据设备控制表找到相应的控制器控制表，把控制器分配给进程；再根据控制器控制表找到通道控制表，把通道分配给进程。

还有一个细节：只有进程**第一次**通过逻辑设备名申请使用一个设备的时候，操作系统才会去查询系统设备表。如果之后进程再次以相同的逻辑设备名来请求使用设备，操作系统首先做的是在**逻辑设备表**当中查找这个逻辑设备对应的物理设备，找到相应的表项之后，就可以直接找到这个设备对应的驱动程序了。

逻辑设备表有两种设置方式：

| 设置方式 | 特点 | 适用场景 |
| :------- | :--- | :------- |
| 整个系统只有一张 LUT | 各个用户使用的逻辑设备名**不允许重复** | 单用户操作系统 |
| 每个用户设置一张 LUT | 不同用户的逻辑设备名**可以重复** | 多用户操作系统 |

### 设备回收与考前提醒

这个 小节我们介绍了设备的分配与回收问题，主要介绍的是设备的分配——其实设备的回收无非就是把那些数据结构再改回来就行了。

复习的时候有几个点要留心。设备分配时要考虑的三种因素当中，不太容易记的是"设备的固有属性"那三种分类（独占设备、共享设备、虚拟设备）和"设备分配中的安全性"两种方式——复习到相应概念的时候稍微留个心眼，**选择题当中有可能进行考察**。另外，静态分配和动态分配这两个术语也要有印象：静态分配方式就是破坏了"请求和保持"这个产生死锁的必要条件，所以不会死锁；不安全分配方式则有可能产生死锁，一般来说可以用银行家算法来避免死锁，或者结合资源分配图来对死锁进行检测和解除——银行家算法的规则、死锁的检测和解除，也是大家需要回顾的知识点。

至于那四张数据结构表，**并不需要死记硬背**。设备控制表、控制器控制表、通道控制表分别对应设备、控制器、通道这三种东西，只需要理解这三者"一个通道控制多个控制器、一个控制器控制多个设备"的树形对应关系，就可以知道这些数据结构大致需要做什么事情了。而且无论是设备、控制器还是通道，它们都会有一个等待队列的指针字段——当这种资源暂时不能分配给某个进程的时候，就需要把这个进程的 PCB 插入到相应资源的等待队列当中。系统设备表则集中了所有设备相关的信息，操作系统通过这个表来统一地对设备进行查询检索。

最后是最需要着重理解的点：如果采用**物理设备名**来请求使用一个设备，会存在两个很明显的缺点——编程绑定具体设备、设备一换程序就跑不了，以及同类设备空闲也照样阻塞、设备利用率不高；而这些缺点可以用**逻辑设备名和物理设备名映射**的方式来解决。这个地方很有可能在选择题当中进行考察。

## 缓冲区管理与磁盘基础
> 对应块：BLK33 | 覆盖分集：P81-P83 | 块标题（分集名）：《5.2_4_缓冲区管理》

CPU 的速度很快，I/O 设备却很慢，这对速度矛盾贯穿了整个 I/O 管理的学习。这一讲我们先解决它：办法就是在内存里开辟一片"缓冲区"，让快的和慢的各干各的、互不拖累。缓冲区管理讲完之后，我们再把视角转到磁盘本身——磁道、扇区、盘面、柱面这些东西到底长什么样、怎么用物理地址定位一个扇区；最后聊聊磁盘初始化、引导块和坏块管理这几个小而常考的知识点。

### 缓冲区是个什么东西

> **定义**：缓冲区就是一个存储区域，可以由专门的硬件寄存器组成，也可以由内存来充当。

用硬件做专门的缓冲区，成本高、容量小。典型例子就是我们之前学过的联想寄存器，也就是快表——它就是一种用硬件实现的缓冲区。由于对快表的访问频率非常高，快表速度一高，整个系统的性能提升就很明显，所以在那种场合下，用这种高成本的方案是值得的。

但一般情况下，更多的是用**内存作为缓冲区**。设备独立性软件这一层的"缓冲区管理"，管理的其实就是这种内存缓冲区，所以这一讲介绍的所有缓冲方案，都围绕内存缓冲区展开。

#### 缓冲区能解决什么问题

在内存中开辟一小片区域作为缓冲区之后：

- **输出数据**时，CPU 产生的数据首先被放进内存缓冲区。CPU 速度很快，很快就能把缓冲区充满；缓冲区满了之后，CPU 就可以转头去做别的事情，让 I/O 设备慢慢从缓冲区里取走数据。
- **输入数据**时也是类似的：I/O 设备慢慢把数据放到缓冲区，缓冲区满了之后，CPU 再快速地从缓冲区中取走。

```text
【输出方向】
 CPU（快）──快速冲入──▶ 内存缓冲区 ──慢慢取走──▶ I/O 设备（慢）

【输入方向】
 I/O 设备（慢）──慢慢放入──▶ 内存缓冲区 ──快速取走──▶ CPU（快）
```

读图说明：缓冲区夹在快的 CPU 和慢的设备中间，两边都只跟缓冲区打交道，各自按自己的节奏工作。由此带来四个好处：

1. **缓和 CPU 与 I/O 设备速度不匹配的矛盾**。这是最直接的收益。
2. **减少 CPU 的中断频率，放宽 CPU 对中断响应时间的限制**。想象没有缓冲区的情形：I/O 设备每输入或输出一定单位的数据，就得向 CPU 发一个中断信号请求处理。假如这是字符型设备，那每输入/输出一个字符都要打断 CPU 一次。我们之前强调过，中断的处理是要付出时间代价的，CPU 频繁处理这些中断显然会拖垮系统性能。有了缓冲区，只有缓冲区中的数据被全部取走、或者输入的数据充满了缓冲区时，CPU 才需要介入处理中断，中断频率一下子就降下来了。
3. **解决数据粒度不匹配的问题**。比如 CPU 上运行的输出进程每次能生成一整块数据，但 I/O 设备每次只能输出一个字符。没有缓冲区的话，输出进程只能一个字符一个字符地喂给设备；有了缓冲区，输出进程直接把一整块数据放进缓冲区，让设备从缓冲区里一个字符一个字符往外取。输入方向同理。
4. **提高 CPU 与 I/O 设备之间的并行性**。设备在缓冲区里慢慢干活的同时，CPU 可以处理别的数据，两者并行推进。

### 单缓冲：平均处理一块数据要多久

假设用户进程请求某种**块设备**读入若干块数据。采用单缓冲策略时，操作系统会在内存中为用户进程分配**一个**缓冲区，大小和一块数据相等。

这是考研中经常考察的题型：每处理一块数据，平均需要多长时间？我们来把它彻底分析清楚。

#### 先记住缓冲区的"死规矩"

缓冲区有一个特点，所有分析都建立在它之上：

> **结论**：缓冲区不空时，不能往里冲入数据，只能从中传出数据；缓冲区为空时，可以往里冲入数据，但必须把它**充满**之后，才能从里面传出数据。

也就是说，"充满才能取、取空才能放"，没有第三种状态。

#### 三个时间：T、M、C

处理一个数据块要经过三个阶段：

- **T**：块设备产生一块数据、把它输入到缓冲区，所耗费的时间；
- **M**：把缓冲区中的这块数据传送到用户进程的工作区，所耗费的时间。数据进了缓冲区还不算完——还记得之前小节里 C 语言 `scanf` 的例子吗？从键盘输入的数据，最终要被传送到用户进程的内存空间里，用户进程才能真正处理它；
- **C**：用户进程对这一块数据进行计算处理所耗费的时间。考研中默认用户进程的工作区也刚好放得下一块数据，处理完之后工作区就被腾空了。

#### 分析套路：锁定初始状态，等它再回来

书上给了一个很好用的技巧：**假定一个初始状态，然后分析下一次到达相同状态需要多少时间——这段时间的长度，就是平均处理一块数据所需要的时间**。

单缓冲问题中，一般假设初始状态为**工作区满、缓冲区空**，然后看下一次再回到"工作区满、缓冲区空"要多久。

#### T 大于 C 的情况：瓶颈在输入

刚开始工作区是满的、缓冲区是空的，所以两件事同时开工：CPU 立刻处理工作区里的数据（耗时 $C$），同时块设备因为缓冲区是空的，立刻往里冲入一块数据（耗时 $T$）。

由于 $T > C$，CPU 花 $C$ 时间处理完之后，**并不能紧接着处理下一块**——此时缓冲区里的数据还没充满。必须先等缓冲区充满（到 $T$ 时刻），再把这块数据传送到工作区（耗时 $M$）。传完之后，工作区又满了、缓冲区又被取空了，正好回到初始状态。

```text
时刻        0          C           T        T+M
CPU     [  处理 C  ]...........[ 传送 M ]
设备    [     充入缓冲区 T      ]
                    ↑ T 时刻缓冲区满，立刻开始向工作区传送
T+M 时刻：工作区满、缓冲区空，回到初始状态 → 一轮耗时 T + M
```

所以 $T > C$ 时，平均每处理一块数据耗时 $T + M$。

#### C 大于 T 的情况：瓶颈在处理

刚开始同样两件事并行：设备往空缓冲区充数据（耗时 $T$），CPU 处理工作区里已有的数据（耗时 $C$）。

到 $T$ 时刻缓冲区已经满了，但由于 $C > T$，工作区里的数据还没处理完，**不能**把缓冲区数据往工作区里传。必须等 $C$ 时刻工作区腾空，才能开始传送（耗时 $M$）。传送完之后，工作区满、缓冲区空，又回到了初始状态。

```text
时刻        0      T           C        C+M
设备    [ 充入 T ].............
CPU     [      处理 C       ]........
传送                      [ 传送 M ]
                      ↑ C 时刻工作区腾空，传送才能开始
C+M 时刻：工作区满、缓冲区空，回到初始状态 → 一轮耗时 C + M
```

所以 $T < C$ 时，平均每处理一块数据耗时 $C + M$。

#### 单缓冲的结论

> **结论**：单缓冲策略下，每处理一块数据平均耗时 $M + \max(C, T)$，即传送时间 M，加上处理时间 C 和输入时间 T 中更大的那一个。

### 双缓冲：多加一个缓冲区快在哪

双缓冲策略下，操作系统在内存中为进程分配**两个**缓冲区，每个大小仍然是一块。同样考察"每处理一块数据平均耗时多久"，思路和单缓冲类似：假定一个初始状态，分析下一次到达它需要多久。这里假设初始状态为**工作区空、其中一个缓冲区满、另一个缓冲区空**。

#### T 大于 C+M 的情况

刚开始，缓冲区一里有一块数据，可以立刻把它传送到工作区（耗时 $M$），传完 CPU 就开始处理（耗时 $C$）；另一方面，缓冲区二是空的，设备从零时刻就往缓冲区二里输入数据（耗时 $T$）。

由于 $T > C + M$，CPU 在 $C + M$ 时刻就把工作区处理空了，但此刻缓冲区二还没充满，只能干等到 $T$ 时刻缓冲区二充满。到 $T$ 时刻，工作区空、一个缓冲区满、另一个空——正好回到初始状态。

```text
时刻        0        M       M+C         T
传送    [  M  ]............
CPU         [  处理 C  ].........
设备    [       充入缓冲区二 T       ]
T 时刻：工作区空、缓冲区一空、缓冲区二满 → 一轮耗时 T
```

所以 $T > C + M$ 时，平均每处理一块数据耗时 $T$——输入速度完全跟得上，每来一块就处理一块。

#### T 小于 C+M 的情况

设备从零时刻往空缓冲区二里充数据（耗时 $T$）；同时缓冲区一是满的，立刻把它的数据传到工作区（耗时 $M$），传满后 CPU 开始处理（耗时 $C$）。

处理完工作区这块数据时（$C + M$ 时刻），缓冲区二早已经充满了下一块数据，可以紧接着传送、接着处理，流水线转起来了。再看设备侧：$T$ 时刻缓冲区二充满后设备一度空闲，但缓冲区一的数据在 $M$ 时刻就被取空了，所以设备随即转入缓冲区一继续冲入下一块数据（又是耗时 $T$）。这样两块缓冲区交替充放，设备忙个不停。

这里有个小插曲：在 $T < C + M$ 的情况下，其实**很难再找到一个和初始状态一模一样的时刻**。比如 $T$ 时刻，缓冲区二虽是满的，但工作区还没处理空；$M + C$ 时刻，工作区虽是空的，可缓冲区二满着、缓冲区一还冲了一部分进去，是"半满"状态。所以课本上介绍的"等初始状态重现"的技巧，在这种情形下就不太好使了。自己用这种甘特图的方式多往下分析几次就会发现：**每经过 $C + M$ 这么长的时间，就有一块数据被处理完毕**。

#### 双缓冲的结论

> **结论**：双缓冲策略下，每处理一块数据平均耗时 $\max(T, C + M)$——$T$ 大就取 $T$，$C + M$ 大就取 $C + M$。

循环缓冲和缓冲池不需要做这种时间分析，大致原理了解即可；真正要会算的就是单缓冲和双缓冲这两个式子。

### 通信中的单缓冲与双缓冲

单缓冲和双缓冲不仅仅用在主机和设备之间的数据传送，**两台主机通信时也可以采用缓冲策略**，用于数据的发送和接收。

如果两台通信的主机各配**单缓冲区**：A 主机要发送数据，先把数据放进自己的缓冲区，充满之后才能往 B 主机的缓冲区一个一个地发送；B 主机要等把这些数据全部处理完、缓冲区腾空之后，才能把**自己要回发**的数据放进这个缓冲区。根子还是那条缓冲区的死规矩——只有充满之后才可以取走数据，只有取空之后才可以往里放入数据。因此在任何一个时刻，**只能实现数据的单向传输**。

要实现同一时刻双向传输，就给两台机器各配**双缓冲区**：一个缓冲区用来暂存即将发送的数据，另一个用来接收对方发来的数据。这样两台主机可以同时往自己的发送缓冲区充入数据、同时往对方的接收缓冲区充入数据，实现同一时刻的双向传输。

### 循环缓冲区

很多时候，只有两个缓冲区依然满足不了进程的实际需要。于是操作系统可以给进程分配**多个大小相等的缓冲区，让它们连成一个循环队列**。图中橙色表示已被充满数据的缓冲区，绿色表示空缓冲区。

系统保持两个指针来管理：

- **in 指针**：指向下一个可以冲入数据的**空**缓冲区；
- **out 指针**：指向下一个可以取出数据的**满**缓冲区。

in 所指的缓冲区被充满后，in 就前移指向下一个空缓冲区；out 所指的缓冲区数据被取空后，out 也前移指向下一个满缓冲区。两个指针在环形队列上你追我赶，生产与消费就持续运转下去。

### 缓冲池：把缓冲区统一管理起来

最后来看一个不太容易理解、但原理并不复杂的方案——**缓冲池**。缓冲池由一系列缓冲区组成，就像它名字说的那样：一个放满了各种各样缓冲区的池子。需要使用或归还缓冲区时，对这个池子里的缓冲区进行操作就行。

缓冲池中的缓冲区按使用状况分成**三个队列**：

```text
 空缓冲队列   [空]→[空]→[空]→[空]→
 输入队列     [装满输入数据]→[装满输入数据]→
 输出队列     [装满输出数据]→[装满输出数据]→
```

另外，根据一个缓冲区在实际运算中扮演的功能不同，又设置了**四种工作缓冲区**：用于收容输入数据的、用于提取输入数据的、用于收容输出数据的、用于提取输出数据的。这些名字都很奇怪、很拗口，不过对应到具体操作就很好理解了：

| 操作 | 从哪里取缓冲区 | 拿来做什么 | 用完挂回哪里 |
| :-- | :-- | :-- | :-- |
| 收容输入 | 空缓冲队列队头 | 充入设备输入的数据 | 充满 → 输入队列队尾 |
| 提取输入 | 输入队列队头 | 数据传送到计算进程的工作区 | 取空 → 空缓冲队列队尾 |
| 收容输出 | 空缓冲队列队头 | 充入计算进程要输出的数据 | 充满 → 输出队列队尾 |
| 提取输出 | 输出队列队头 | 数据慢慢取走输出到 I/O 设备 | 取空 → 空缓冲队列队尾 |

逐条过一遍：输入进程请求输入一块数据时，系统从空缓冲队列**队头**取下一个空缓冲区，作为收容输入的工作缓冲区，充满之后挂到**输入队列队尾**；计算进程想取一块已输入的数据时，系统从输入队列队头取下一个缓冲区，把它里面的数据传进计算进程的工作区，取空后挂回**空缓冲队列队尾**；计算进程准备好数据想输出时，系统从空缓冲队列队头取下一个空闲缓冲区作为收容输出的工作缓冲区，充满后挂到**输出队列队尾**；输出进程请求输出一块数据时，系统从输出队列队头取下一个缓冲区，把数据慢慢取走，取空后挂回空缓冲队列队尾。

可以看到，四种操作的模式完全一致：**从某个队列的队头取、往某个队列的队尾挂**，缓冲池就这样周而复始地循环利用每一个缓冲区。

### 磁盘、磁道与扇区

缓冲区讲完，我们把目光转向磁盘本身。先看最基本的概念。

**磁盘的表面由一组磁性物质组成**，就用这些磁性物质来记录二进制数据。把一个硬盘拆开，里面圆圆的东西就是磁盘的**盘片**；要读取盘片上存储的二进制数据，需要由**磁头臂**（简称磁臂）带动**磁头**移动，把磁头放到相应位置去读取那个位置上的数据。

一个盘面会被划分为一条一条的**磁道**，每一圈就是一个磁道。实际磁盘里磁道的数量非常多——成千上百甚至上万条，示意图上画不下，只能画几条示意。每个磁道又被划分为一个一个的**扇区**，一小片扇区就是我们之前提到过的**磁盘块**。**每个扇区存放的数据量都是相同的**，比如每个扇区 1 KB，也就是一个磁盘块 1 KB。磁盘中间有一个马达，马达转动时带动整个磁盘旋转。

另外，可以对扇区进行编号：0 号扇区、1 号扇区、2 号扇区……以此类推。

> **易错点**：由于每个扇区存放的数据量相同，而最内侧的扇区面积最小、存储的数据量又和其他扇区一样多，所以**最内侧扇区的数据密度是最大的**。这个推论常被拿来做文章。

### 怎么读写一个扇区

要读写数据，分两步走：

1. **磁头定位**：由磁头臂带动磁头，移动到想要读/写的扇区**所在的磁道**上。磁头的移动位置是固定的两个方向——要么往里、要么往外；
2. **磁盘旋转**：磁盘由中间的马达带动转起来，当目标扇区从磁头下面划过时，就完成了对这个扇区的读或写。

比如磁头此刻停在最外侧的磁道上，想读的扇区在里面的某条磁道上，那就先让磁头臂移动、把磁头放到那条磁道上，然后磁盘一转，想读的扇区依次从磁头下面划过，读写就完成了。

### 盘面、柱面与磁盘的物理地址

上面只看了一个盘面，事实上磁盘是由很多个这样的盘片**垒起来**的，每个盘面上都会有一个专门读取该盘面数据的磁头。可以给盘面编号：0 号盘面、1 号盘面、2 号盘面……而且有的磁盘，一个盘片的正面是一个盘面、背面还可以是另一个盘面。

```text
       磁臂（统一带动所有磁头，共进退）
         │
 盘面0 ──┴──  ← 磁头0
 盘面1 ─────  ← 磁头1
 盘面2 ─────  ← 磁头2
         ║
         ║ ← 主轴（马达带动盘片旋转）
```

读图说明：所有磁头统一连在同一个磁臂上，所以**所有磁头只能共进退**——一个磁头往里移动，其他磁头必然也跟着往里移动。

所有盘面当中，**相对位置相同的磁道组成了柱面**：各个盘面上同一半径的那一圈圈磁道，合起来构成一个柱面。

有了这三个层次，磁盘的物理地址就可以用三元组表示：

$$（柱面号，盘面号，扇区号）$$

- **柱面号**用来定位磁道——磁头臂要移到哪一圈；
- **盘面号**用来选择到底是哪个盘面上的磁道；
- **扇区号**用来选择这条磁道上的哪一个扇区。

还记得文件物理结构小节里经常说的"文件数据存放在外存的几号块"吗？那个块号其实就可以转换成柱面号、盘面号、扇区号这样的地址形式。要读取文件在某个盘块中的数据时，磁盘按三步走：

1. 根据**柱面号**移动磁臂，让磁头对准指定的柱面；
2. 根据**盘面号**选定对应的盘面，激活该盘面上的磁头；
3. 磁盘旋转的过程中，该磁道上的所有扇区都会从这个磁头下面划过，读到**扇区号**对应的扇区，取出数据。

> **提示**：读某个扇区时磁头必须先移动到目标磁道上，而磁头的移动是要耗费时间的——这一点在下一个小节的磁盘调度算法中会有直接的应用，务必先建立这个物理直觉。

### 磁盘的分类

按磁头是否可移动分两类：

- **活动头磁盘**：就是我们一直在讲的这种，磁臂来回伸缩带动磁头移动，从而定位到指定磁道。每个盘面只需一个磁头；
- **固定头磁盘**：磁头不可移动，**每一个磁道都有一个与它对应的磁头**，想读哪条磁道的数据，只需激活对应的那个磁头，不需要移动。示意图上每个盘面都该画满一圈圈的磁头，画起来麻烦、也比较丑陋，就不再画了。

按盘片是否可更换，又分为**可换盘磁盘**（盘片可以更换）和**固定盘磁盘**（盘片不可更换）。

> **易错点**：固定头磁盘是**每个磁道一个磁头**，移动头磁盘是**每个盘面一个磁头**。这一对非常可能在选择题里考。

### 磁盘初始化的三个步骤

磁盘刚被制造出来时，只被划分成了一个一个的磁道。从出厂到我们能正式使用，要经历三步。

#### 低级格式化：划分扇区

磁盘正式出厂之前，需要进行**低级格式化**（也叫**物理格式化**），这个过程就是划分扇区。一个扇区分为**头、数据区域、尾**三个部分：

```text
|←──────────── 一个扇区 ────────────→|
┌──────┬──────────────────┬──────┐
│  头  │     数据区域      │  尾  │
└──────┴──────────────────┴──────┘
          （如 512 B）
```

每个扇区的数据区域所能存放的数据量都相同，比如 512 字节——我们平时说的"一个扇区能存放多少数据"，指的就是数据区域的大小。那头和尾用来做什么？两件事：

- **存放链接指针**。文件物理结构里讲过链式结构：文件的数据块用链接方式串起来，前一个块指向下一个块的指针就可以存在尾部，不必占用数据区域，这样方便操作系统管理；
- **存放管理扇区所需要的数据结构**，比如**扇区校验码**。计组里学过的奇偶校验、循环冗余校验码等，就可以放在头尾，用来检查数据区域中的数据是否出错，大幅提高磁盘存储数据的可靠性。

#### 分区与逻辑格式化

正式使用磁盘之前，还需要对磁盘进行**逻辑上的分区**：每个分区由若干个**相邻的柱面**组成。所谓分区，就是我们平时熟悉的 C 盘、D 盘、E 盘。

划分了分区之后，进行**逻辑格式化**。它做的事情主要是**创建文件系统**：创建根目录的目录文件，并且初始化那些用于存储空间管理的数据结构——之前学过的**位示图、空闲分区表**等，都是在这个步骤中建立的。

三步连起来记：**低级格式化（划扇区）→ 磁盘分区（分 C、D、E 盘）→ 逻辑格式化（建文件系统）**，每一步做什么要能理解并记住。

### 引导块：开机时到底发生了什么

磁盘完成物理格式化、分区和逻辑格式化之后，就可以把操作系统相关的数据写进去了——也就是我们平时"自己安装操作系统"的过程。

计算机开机启动时，需要进行一系列初始化工作：初始化 CPU、初始化内存、初始化寄存器等硬件部件。而初始化是需要执行程序的——所谓**初始化程序**，也叫**自举程序**。

问题是自举程序放在哪？传统做法是放在 **ROM（只读存储器）** 里：ROM 中的数据在出厂时就已写入、以后不能修改，而且 ROM 一般出厂时就直接集成在电脑主板上。开机时计算机首先读取并执行 ROM 中的自举程序，完成初始化。

但想一想：把自举程序整个放在 ROM 里有什么问题？**更新起来很不方便**——ROM 的数据无法更改，而自举程序本身比较复杂，我们不可能保证它的相关数据永远不改变。

现代操作系统的解决办法是拆成两半：

- ROM 当中只存放**很小的一个自举装入程序**——它简单到可以保证不出错、永远不需要更改；
- **完整的自举程序**则存放在磁盘的**引导块**（也叫启动块、启动分区）上，位置固定。比如存放在 C 盘的某几个盘块上，这块区域就称为启动分区，也就是引导块。

```text
开机
 │
 ▼
执行 ROM 中的自举装入程序（很小、简单、出厂固化、永不更改）
 │  它知道完整的自举程序存放在磁盘的哪个固定位置
 ▼
从磁盘的引导块中读出完整的自举程序
 │
 ▼
执行自举程序，完成 CPU、内存、寄存器等一系列初始化
```

读图说明：开机先跑 ROM 里那小段自举装入程序，由它引导 CPU 去磁盘上读出完整的自举程序。这样一来，自举程序需要更新时，只需重写引导块中的数据即可，更新非常方便。

一般来说，拥有这个启动分区（引导块）的逻辑磁盘，被称为**启动磁盘**或**系统磁盘**。平时熟悉的 C 盘就是系统磁盘——也就是说，C 盘的某一个固定位置上装着我们的自举程序。

### 坏块管理

所谓**坏块**，就是那些坏了的、无法正常使用的扇区。它属于**硬件故障**，操作系统无法通过软件的方式修复它。为了防止错误地使用这些坏块，就必须把它们标记出来。管理方式分两类：

**简单磁盘**：在**逻辑格式化**时标明哪些磁盘块是坏块，比如在 FAT（文件分配表）上做标注。操作系统对存储空间进行管理时肯定要读取文件分配表的内容，而哪些块是坏块就记录在 FAT 当中——所以这种方式下，**坏块对操作系统是不透明的**，OS 自己知道、自己绕着走。

**复杂磁盘**：磁盘内部的硬件部件——**磁盘控制器**——会负责维护一个**坏块链表**，顾名思义就是用某种方式把这些坏块链接起来。磁盘出厂时就可能已有坏块，所以出厂前的检查会在低级格式化（物理格式化）时初始化坏块链。此外，磁盘控制器还会保留一些**好的备用扇区**，用来替换坏块：当操作系统想使用某个已经坏掉的块时，在硬件层次上，磁盘控制器会拿某个备用块替换它。**整个过程对操作系统是透明的**，OS 完全不可知。这种方案也称为**扇区备用**。

> **易错点**：两种方案的关键区别就在"透明"二字——简单磁盘由 OS 借 FAT 标注坏块，坏块对 OS **不透明**；复杂磁盘由磁盘控制器在硬件层用备用扇区顶替，坏块对 OS **透明**。

---

最后梳理一下这一讲的轻重缓急：缓冲区的各种优点要有大体印象，应付选择题；**单缓冲 $M + \max(C, T)$、双缓冲 $\max(C + M, T)$ 的平均耗时计算是重中之重**，选择题里经常出现；循环缓冲和缓冲池只需理解原理；磁盘结构部分要吃透磁道、扇区、盘面、柱面和"柱面号、盘面号、扇区号"的物理地址结构；磁盘管理部分的初始化三步骤、引导块和坏块管理都不难，有印象、能应付选择题就够了。

## 磁盘调度算法与固态硬盘
> 对应块：BLK34 | 覆盖分集：P84-P86 | 块标题（分集名）：《5.3_3_磁盘调度算法》

这一节要啃的是一个非常重要、也非常高频的考点——磁盘调度算法。不过先别急着背算法，我们得先把一笔时间账算清楚：一次读磁盘、写磁盘的操作，到底要花多少时间？它由寻道时间、延迟时间、传输时间三个部分组成，而磁盘调度算法的不同，影响的正是其中寻道时间的长短。所以选一个合适的调度算法，对磁盘整体性能的影响是很大的。

先算清时间账，再看算法怎么省时间，最后认识一个新考点——固态硬盘。

### 一次读写要花多少时间

确定想读的数据存放在哪个磁道之后，第一件事就是把磁头移动到指定磁道上去。这个移动磁头的过程是要花时间的：磁头是由磁头臂带动的，所以在移动之前要先启动磁头臂，假设花 $s$ 秒；磁头臂启动之后，带动磁头移动，假设磁头匀速移动、每跨越一个磁道耗时 $m$、总共要跨越 $n$ 条磁道，那移动的耗时就是 $m \times n$。

> **定义**：寻道时间 $T_s = s + m \times n$，其中 $s$ 是启动磁头臂的时间，$m$ 是每跨越一条磁道的时间，$n$ 是跨越的磁道数。

用个具体的场景走一遍：假设要读的数据在最里侧磁道的橙色扇区里，那就要先启动磁头臂（花 $s$ 秒），再把磁头一路移到最里面的磁道（每条磁道耗时 $m$，移 $n$ 条就是 $m \times n$）。现在的硬盘移动一个磁道大约需要 0.2ms，磁臂启动时间大约是 2ms——这是读写操作的第一步。

磁头到位了还不算完。延迟时间指的是：通过旋转磁盘，把目标扇区转到磁头下面所需要的时间。磁头虽然已经停在目标磁道上了，但想读的那个扇区此时未必正好在磁头下方，得让磁盘转过来。假设磁盘转速为 $r$ 转/秒，那么 $\frac{1}{r}$ 就是磁盘转一圈所需的时间；而定位到目标扇区，平均只需要转半圈，所以再乘一个 $\frac{1}{2}$：

$$T_{延迟} = \frac{1}{r} \times \frac{1}{2} = \frac{1}{2r}$$

市面上的机械硬盘，典型的转速是 5400 转/分钟或者 7200 转/分钟——不信可以去京东、淘宝搜一下，看看磁盘的"转速"这个参数。从公式也能看出来：转速越高，延迟时间越小，磁盘的读写速度就越快。所以自己买磁盘的时候，经济允许的话，买转速更高的准没错。

第三部分是传输时间，指从磁盘读出或者向磁盘写入数据本身所经历的时间。假设转速为 $r$ 转/秒，每个磁道可以存放 $n$ 个字节，这一次要读（或写）$b$ 个字节。那么这 $b$ 个字节需要分布在 $\frac{b}{n}$ 条磁道上，磁头就要读写 $\frac{b}{n}$ 条磁道；而每读写一条磁道所花的时间，刚好是磁盘转一圈的时间 $\frac{1}{r}$：

$$T_{传输} = \frac{1}{r} \times \frac{b}{n} = \frac{b}{rn}$$

把三部分加起来，一次读或写操作的总时间就是：

$$T = T_s + T_{延迟} + T_{传输}$$

> **结论**：延迟时间和传输时间都与转速 $r$ 线性相关，转速越快，两者都越短。但转速是硬盘的固有硬件属性，操作系统不可能用软件的方式加快磁盘转速，所以这两部分时间是操作系统无法优化的。操作系统唯一能影响的就是寻道时间——不同的磁盘调度算法，会让寻道时间产生巨大差异。

接下来登场的各个调度算法，玩的都是"怎么让磁头少跑路"这个游戏。

### 先来先服务（FCFS）

这个算法很简单：根据进程请求访问磁盘的先后顺序来进行调度，谁先来就先服务谁。

来看一个贯穿全篇的例子。磁头现在停在 100 号磁道上，多个进程陆陆续续请求访问这些磁道（按到达顺序）：

```text
请求队列：55, 58, 39, 18, 90, 160, 150, 38, 184
磁头初始位置：100 号磁道
```

按先来先服务的思想，磁头就得按到达顺序依次响应：

```text
100 → 55 → 58 → 39 → 18 → 90 → 160 → 150 → 38 → 184
```

算一下总移动量：100 号到 55 号移动了 $100 - 55 = 45$ 个磁道，55 号到 58 号移动了 $58 - 55 = 3$ 个磁道，其余类推。整个过程磁头总共移动了 498 个磁道，处理这 9 个请求，平均寻找长度就是 $498 \div 9 = 55.3$ 个磁道。

这个算法的优点是很公平，先来的先得到服务；并且如果请求访问的磁道比较集中，它的性能还算可以。但缺点也很明显：如果有大量进程竞争使用硬盘、请求访问的磁道又很分散，先来先服务的性能就会很差——它在性能上其实近似于随机调度算法。磁道一分散，寻道时间就长，平均寻找长度自然也长。

### 最短寻找时间优先（SSTF）：贪心的代价

这个算法的思想是：优先处理此时与当前磁头离得最近的那个磁道，保证每一次寻道时间都最短。

还是用刚才的例子。磁头在 100 号，离它最近的是 90 号（只差 10 个磁道，而 150 号差 40 个），所以先响应 90 号；接着离 90 号最近的是 58 号，再接着是 55、39、38，一路从右往左处理到 18 号；处理完 18 号之后，此时离磁头最近且还没处理的请求就变成了 150 号，于是又一路向右，处理 150、160、184：

```text
100 → 90 → 58 → 55 → 39 → 38 → 18 → 150 → 160 → 184
```

总移动量可以两段来算：从 100 依次移到 18，移动了 $100 - 18 = 82$ 个磁道；再从 18 依次移到最右的 184，移动了 $184 - 18 = 166$ 个磁道。总共 $82 + 166 = 248$ 个磁道，平均寻找长度 $248 \div 9 = 27.5$ 个磁道——比先来先服务的 55.3 少了一大半。

> **易错点**：SSTF 只能保证"每一次"寻道时间最短，并不能保证"总体"的寻道时间最短。这和贪心算法是一个思想：只选择眼前最优的，但总体上未必最优。

它还有一个更要命的缺点：有可能产生饥饿现象。接着上面的例子分析：假设磁头处理到 18 号磁道时，又来了一个 38 号磁道的请求，那处理完 18 号后，离磁头最近的就是 38 号，磁头移回 38 号；处理 38 号的过程中又来一个 18 号的请求，它又回到 18 号……只要系统当中源源不断地有 18 号和 38 号磁道的请求到来，磁头就会一直循环地为这两个磁道服务，而 150、160、184 号的请求长期得不到处理——这就发生了饥饿。

饥饿的根因在于：磁头有可能在一个小区域内来来回回地移动，只要这个小区域内有源源不断的请求，它就一直被困在里面，跳不出去为其他区域的请求服务。

怎么破？人们提出了扫描算法。

### 扫描算法（SCAN）：像电梯一样服务

扫描算法规定：只有磁头移动到最外侧磁道的时候，才可以往内侧移动；只有移动到最内侧磁道的时候，才可以往外移动。这个磁头移动的方式很像我们平时坐的电梯，所以它也叫电梯算法。

还是用同一个例子，并补充两个条件：磁盘的磁道号是 0～200，磁头初始位置 100 号，并且此刻正朝着磁道号增大的方向（向右）移动。那么磁头先向右依次处理 150、160、184；注意，虽然 184 号右边已经没有任何待处理的请求了，但扫描算法要求必须移到最外侧的 200 号才能回头；然后向左依次处理 90、58、55、39，一直到 18：

```text
向右：100 → 150 → 160 → 184 → 200（右边没请求也必须走到最外侧）
向左：200 → 90 → 58 → 55 → 39 → 38 → 18
```

总移动量：$200 - 100 = 100$，加上 $200 - 18 = 182$，总共 282 个磁道，平均寻找长度 $282 \div 9 = 31.3$ 个磁道。比先来先服务好很多；虽然比 SSTF 的 27.5 略差，但换来的是不会产生饥饿——磁头总会扫过每一个区域，谁也不会被永久搁置。

不过它也有两个可以挑刺的地方：

- 到了最边上的磁道才能改变方向。可实际上处理完 184 号之后，右边已经没有请求，磁头完全可以立即回头，没必要空跑到 200 号。
- 对各个位置的磁道，响应频率不平均。比如磁头刚处理完 90 号磁道，那 90 号的下一次被服务，要等磁头走到最右边、再折返回来到 90 号才行，等待时间很长；而 184 号靠近边缘，磁头到边上马上折返就能再次服务它。同样是刚被服务过，90 号的再次响应频率就明显更低。

### LOOK：前方没请求就掉头

针对第一个缺点，人们提出了 LOOK 调度算法。它在扫描算法的基础上加了一条策略：如果在磁头移动方向上已经没有别的请求了，就可以立即改变移动方向。说白了，就是一边移动磁头、一边"观察"（look）前方还有没有请求——所以叫 LOOK 算法。

还是这个例子：磁头从 100 号出发向右，依次访问 150、160、184；到了 184 号发现右边没有别的请求了，立即掉头向左，依次处理 90、58、55，最后到 18 号：

```text
向右：100 → 150 → 160 → 184（前方没请求，立即掉头）
向左：184 → 90 → 58 → 55 → 39 → 38 → 18
```

总移动量：$(184 - 100) + (184 - 18) = 84 + 166 = 250$ 个磁道，平均寻找长度 27.5 个磁道——比扫描算法的 31.3 又进一步缩短了。

### 循环扫描（C-SCAN）：只朝一个方向干活

再解决扫描算法的第二个缺点（响应频率不均）。人们提出了 C-SCAN 算法，也叫循环扫描算法。它规定：只有磁头朝某一个特定方向移动时才处理磁道访问请求；而在返回起点的过程中，直接快速移动到起始端，不进行任何请求处理。

用例子走一遍：磁头从 100 号向右，依次服务 150、160、184，然后照样移到最边缘的 200 号；接着直接从 200 号快速返回 0 号，中间不处理任何请求；到了 0 号之后开始新一轮扫描，向右依次处理剩下的 18、38，一直到 90 号：

```text
向右：100 → 150 → 160 → 184 → 200
返回：200 ⇢ 0（快速返回，不处理任何请求）
再向右：0 → 18 → 38 → 39 → 55 → 58 → 90
```

总移动量：$100 + 200 + 90 = 390$ 个磁道，平均寻找长度 43.3 个磁道。

为什么这样频率就平均了？比如刚服务过 150 号，那下一次响应 150 号，得等磁头慢慢移到最右边、回到起点、再扫回 150 号才行——对其他任何位置的磁道也是同样的流程。每个磁道的响应频率都很平均，这正是循环扫描的卖点。

当然它也有和扫描算法类似的毛病：一是必须到最边上的磁道才能改变方向，其实处理完 184 号就没必要再往右空跑了；二是返回时直接回到 0 号，可 0 号此时并没有任何请求，其实只需要返回到最靠左的有请求的位置——18 号——就够了。

### C-LOOK：循环扫描的改良

C-LOOK 算法就是用来解决 C-SCAN 这些缺点的，思想和 LOOK 一脉相承：如果磁头移动方向上已经没有任何访问请求了，就立即让磁头返回；而且磁头只需要返回到有磁道访问请求的那个位置就行。

还是这个例子：磁头从 100 号向右处理 150、160、184；184 号右边没请求了，立即返回，并且直接回到最靠左的待处理磁道 18 号（而不是 0 号）；然后从 18 号开始新一轮向右扫描，依次处理完剩下的请求：

```text
向右：100 → 150 → 160 → 184（前方没请求，立即返回）
返回：184 ⇢ 18（直接回到最靠左的请求处，不空跑）
再向右：18 → 38 → 39 → 55 → 58 → 90
```

总移动量：$(184 - 100) + (184 - 18) + (90 - 18) = 84 + 166 + 72 = 322$ 个磁道，平均寻找长度降为 35.8 个磁道，寻道时间进一步缩短。

### 六种算法放在一起看

同一个例题跑下来，六个算法的成绩单如下：

| 算法 | 磁头移动总道数 | 平均寻找长度 | 一句话点评 |
| :--- | ---: | ---: | :--- |
| FCFS | 498 | 55.3 | 公平，但请求分散时近似随机调度 |
| SSTF | 248 | 27.5 | 每步最优但总体未必最优，可能饥饿 |
| SCAN | 282 | 31.3 | 不饥饿，但须到边缘才掉头、响应频率不均 |
| LOOK | 250 | 27.5 | SCAN 的改良：前方没请求就掉头 |
| C-SCAN | 390 | 43.3 | 各磁道响应频率均匀，返回不干活 |
| C-LOOK | 322 | 35.8 | C-SCAN 的改良：不空跑边缘、直接回到请求处 |

复习时抓三条主线就够：SSTF 可能导致饥饿，并且只保证眼前最优、不保证总体最优；SCAN 和它的改良 LOOK、C-SCAN 和它的改良 C-LOOK 是两组"规定版 vs 灵活版"；磁头是否必须走到最边缘，是区分这两组的关键。

> **提示**：做题时如果题目没有特别说明，题目中所指的 SCAN 算法其实就是 LOOK 算法，所指的 C-SCAN 算法其实就是 C-LOOK 算法——也就是说磁头并不一定非要移动到最外侧的磁道，只要移动方向上没有别的请求了，就可以立即改变方向。

课后习题当中有很多与这一小节相关的练习题，这些移动道数的计算一定要自己动手算，光看是记不住的。

### 交替编号：给扇区留出处理的间隙

寻道时间怎么省，上一节讲完了。这一节专门对付延迟时间——回忆一下，延迟时间就是"把目标扇区转到磁头下面"所花的时间。

这里有个容易被忽略的物理事实：磁头读完一个扇区之后，需要一小段时间来处理，这段时间里磁头并不能接着读下一个扇区；可磁盘又是在不停地旋转的。麻烦就出在这儿。

假设现在要连续读取逻辑上相邻的 2、3、4 号扇区，而它们在物理上也相邻：磁头先转动磁盘，把 2 号扇区转到磁头下方读入；读完 2 号后磁头需要一小段处理时间，可就在这段时间里，3 号扇区已经从磁头下方划过去了——错过了。想读 3 号，唯一的办法就是让磁盘继续转，等 3 号扇区再一次到达磁头下方。也就是说，多等了一整圈。

所以如果把逻辑上相邻的扇区安排成物理上也相邻，连续读入这几个扇区就需要多转好几圈磁盘，延迟时间会特别长。

解决办法就是交替编号：让逻辑上相邻的扇区在物理上间隔一定的距离。比如 0 号扇区之后，隔一个扇区的位置才编成 1 号，以此类推。再看读 2、3、4 号的过程：磁头读完 2 号后开始做中间准备，这段时间里磁头不能读任何数据；但正因为 3 号和 2 号物理上隔了一个位置，在 3 号划过磁头之前，磁头已经做好了下一次读取的准备，于是磁盘继续旋转，3 号从磁头下方划过时，数据被顺利读入。

> **结论**：交替编号让磁头的"处理间隙"正好落在两个逻辑相邻扇区之间，省下了多转一整圈的时间，可以大幅度减少延迟时间。

### 柱面号为什么排在盘面号前面

磁盘的物理地址分为柱面号、盘面号、扇区号三个部分。一个值得琢磨的问题是：为什么是这个顺序？为什么不是盘面号在前、柱面号在后？柱面号为什么一定要放在前面？

我们用一个具体的磁盘来分析。假设它有 8 条磁道（也就是 8 个柱面），需要 3 个二进制位来编号（刚好表示 0～7）；有 4 个盘面，需要 2 个二进制位；每个磁道分成 8 个扇区，需要 3 个二进制位。

先看"盘面号在前"会发生什么。假设要连续读取物理地址从"盘面 0、柱面 0、扇区 0"到"盘面 0、柱面 0、扇区 7"的扇区，也就是 0 号盘面最内侧磁道上的全部 8 个扇区：磁头转一圈可以依次读入前几个扇区，转第二圈读完剩下的，两圈读完。接下来按连续地址，该读"盘面 0、柱面 1、扇区 0"了——柱面号变了，意味着必须启动磁头臂、让磁头往外移动一个磁道。启动磁头臂和移动磁头是实打实的机械运动，花费的时间是比较高的。

再看"柱面号在前"：要连续读取的地址范围是"柱面 0、盘面 0、扇区 0～7"，同样是 0 号盘面最内侧磁道的全部扇区，转两圈读完。接下来该读"柱面 0、盘面 1、扇区 0"了——盘面号变了，但柱面没变！也就是说磁头位置根本不用动，只需要激活 1 号盘面对应的那个磁头（每个盘面各有一个磁头），电子切换即可，完全不需要再启动磁头臂、来回移动磁头。

> **结论**：柱面号放在盘面号之前，读地址连续的磁盘块时就不需要在柱面之间移动磁头，只需切换激活的磁头，减少了磁头移动所消耗的时间。本质还是那句话——让磁头少跑路。

这个知识点不太容易理解、也很容易被人忽略，选择题当中很可能作为陷阱来考察，多留个心眼。

### 错位命名：盘面之间也要错开

交替编号解决的是同一条磁道内的间隙问题；错位命名处理的则是盘面与盘面之间的同样问题。

先明确一个前提：所有的盘面是连在一起同轴旋转的，同步转动。先看不采用错位命名会发生什么。假设 0 号盘面和 1 号盘面在相对位置相同的扇区编号也相同——0 号盘面 0 号扇区的正下方，恰好是 1 号盘面的 0 号扇区。现在要连续读取"0 号盘面最内侧磁道的所有扇区"直到"1 号盘面 0 号扇区"（物理地址顺着编号一路排下来，0 号盘面读完紧接着就是 1 号盘面的 0 号扇区）：激活 0 号盘面的磁头，磁盘旋转，转两圈读完这条磁道的全部扇区；读最后一个扇区时，由于盘面同步旋转，1 号盘面的 0 号扇区也正好转到自己磁头的下方——可磁头刚刚读完一个扇区，正需要一小段处理时间，还暂时不能读数据！于是 1 号盘面的 0 号扇区就这么从磁头下面划过去了。想读它？只能等磁盘再转一整圈。

这就是把各盘面相对位置相同的扇区都编成相同号码的代价：切换盘面继续读时，很可能平白多等一圈，增加延迟时间。

解决办法就是错位命名：让相邻盘面的扇区编号错开。比如 0 号盘面 0 号扇区的正下方，对应的改成 1 号盘面的 7 号扇区——1 号盘面的编号整体错开一个位置，"错位命名"的名字就是这么来的。这样一来，读完 0 号盘面最后一个扇区、磁头利用间隙做好准备之后，1 号盘面的 0 号扇区才第一次划过磁头下方，一次就顺利读入，不用再多转一圈。

无论是交替编号还是错位命名，参考的原理其实都是同一个：磁头读完一个扇区之后，需要一段时间准备，才可以继续读入下一个扇区。把编号排布得和这个间隙配合起来，延迟时间就省下来了。

### 固态硬盘长什么样

下面看一个新考点——固态硬盘（SSD）。这个考点既被加进了计组的考研大纲，也被加进了操作系统的考研大纲，我们通过这一节把两边要求掌握的内容通通搞定。它最有可能在选择题当中考察，所以下面把这些特性一条条讲透，帮你理解着记，降低记忆负担。

先看它长什么样。传统的机械硬盘靠盘面上的磁性物质来记录二进制的 0 和 1；固态硬盘里看到的则是一块块黑色的小芯片，这些芯片就是用来存储数据的——它存储数据基于闪存技术，大家熟悉的 U 盘采用的也是闪存。本质上，闪存属于一种电可擦除的 ROM，也就是 EEPROM。

一个固态硬盘由两个部分组成：一是闪存翻译层，二是由多个闪存芯片组成的存储介质。结构大致长这样：

```text
            I/O 总线
               │  逻辑块号（逻辑地址）
               ▼
        ┌────────────┐
        │  闪存翻译层  │ ← 负责逻辑地址 → 物理地址的翻译
        └────────────┘
               │
      ┌────────┼────────┐
      ▼        ▼        ▼
  ┌──────┐ ┌──────┐ ┌──────┐
  │闪存芯片│ │闪存芯片│ │闪存芯片│ ...
  └──────┘ └──────┘ └──────┘
```

系统通过 I/O 总线把此次要读或写的逻辑块号发给 SSD；这个逻辑地址经由闪存翻译层翻译之后，被映射到具体的某一个物理地址。所以闪存翻译层做的就是一个地址变换的工作。

### 块与页：读写以页为单位，擦除以块为单位

继续深挖每一块闪存芯片的内部结构：一块闪存芯片由若干个块组成，每个块的大小可能是 16KB～512KB；每个块又进一步拆解为一个个页，每个页的大小可能是 512B～4KB。

这里有个特别容易混淆、也特别爱考的点：系统对固态硬盘的读写是以**页**为单位的。

对比一下就清楚了。如果数据存放在机械硬盘里，系统指明的一个逻辑块，对应的就是磁盘的一个块（一个扇区），磁盘以块为单位读写。但如果这个逻辑块存放在固态硬盘里，它对应的应该是固态硬盘的一个**页**，而不是一个块。所以：

> **提示**：固态硬盘的一个页，相当于磁盘的一个扇区；固态硬盘的一个块，可以理解为相当于磁盘的一个磁道——一个磁道里包含多个扇区，一个块里也包含多个页。"块"和"页"这些术语在其他地方也出现过、且含义不同，很容易混淆，记住"SSD 读写按页、逻辑块对应页"这一条。

另一方面要特别注意：固态硬盘会以**块**为单位对数据进行擦除。一个块被擦干净之后，其中的每个页都可以被写一次、被读无限次。

"写一次"是什么意思？如果一个页已经被写入数据了，再想往这一页写新数据是不被允许的；想重写，就必须先把这一整块擦除——就像用橡皮擦一样，把整块都擦干净，然后再往里面写。只能这么做。

### 为什么读快、写慢

现在问题来了：一个块里的每一页都可能有数据，我只是想往其中一页写新数据，却必须把一整块全擦干净才能写，那其他页的数据不就跟着消失了吗？这显然不合理。

处理办法是：固态硬盘会先把这块里其他页的数据复制到另一个块（一个已被擦干净的块）的对应位置，然后再把想写的新数据写到目标页，最后把原来的块整个擦除——这样其他页的数据就不会丢失。

数据不丢了，但地址映射又出新问题了：闪存翻译层原本把逻辑块号（比如 X 到 X+N 这一范围）映射到刚才被擦除的那个位置，可这些数据现在被挪到别的地方去了。为了让映射关系保持正确，闪存翻译层在做完数据迁移之后，会把这些逻辑块号重新映射到新的位置，原有的映射舍弃。

> **提示**：对固态硬盘来说，一个逻辑地址对应的实际物理位置是可能变化的，只不过闪存翻译层始终会把映射关系修改正确，上层感觉不到。

把这些串起来，就能理解固态硬盘的一个核心特性了：**读的速度通常很快，而写的速度会比读慢得多**——因为写操作可能会引起擦除动作，以及数据迁移动作。

### 电路定位：随机访问的底气

固态硬盘支持随机访问。给定一个逻辑地址（逻辑块号），闪存翻译层可以通过电路迅速定位到对应的物理地址。

相比之下，机械硬盘给定一个逻辑地址要找到物理位置，得移动磁臂、旋转磁盘，全是机械操作。要访问的物理地址离磁臂当前位置比较远，就得移动磁臂，等的时间自然长。所以机械硬盘访问不同的地址，需要等待的时间各不相同；而固态硬盘访问任何一个地址，所需要花的时间都是相同的。

### 固态硬盘与机械硬盘的对比

把两边特性摆在一起看，这是选择题的高频考法：

| 特性 | 机械硬盘 | 固态硬盘 |
| :--- | :--- | :--- |
| 读写速度 | 受寻道时间、旋转延迟影响，较慢 | 电路控制，读写更快 |
| 随机访问 | 移动磁臂＋旋转磁盘定位，不同地址耗时不同 | 电路直接定位，访问任何地址耗时相同 |
| 噪音 | 盘片要转、磁臂要动，夜里能听见转动的声音 | 就是一块电路板，安静无噪音 |
| 抗震耐摔 | 机械部件容易坏 | 没有机械部件，电路板焊死了很难坏 |
| 能耗 | 更费电 | 能耗更低 |
| 价格 | 便宜 | 更贵 |
| 寿命 | 扇区不会因为写得次数多而坏掉 | 块被擦除次数太多会坏（比如擦了 1 万次后就不能再用了） |

最后一条寿命问题特别重要，它引出了本节最后一个知识点。

### 磨损均衡：别在一只羊身上薅羊毛

固态硬盘的一个块如果被擦除的次数太多，就会坏掉：比如反复地往同一个块里不断写东西，这个块就会反复被擦除，擦了大约 1 万次之后就不能再使用了。机械硬盘的扇区则没有这个毛病，不会因为你写得太多而坏。

由于这个特性，固态硬盘通常会引入**磨损均衡技术**，思想就一句话：把擦除平均地分布在各个块上，以提升使用寿命。

这个道理跟薅羊毛一样——薅羊毛不能老是在一只羊身上薅，容易把这只羊给薅秃了。那怎么把"羊毛"摊到整群羊身上？靠的还是前面说过的那个能力：闪存翻译层可以把逻辑块号映射到任何一个地方，物理位置是可变的。如果发现某个块被擦除的次数已经很多、已经"老了"，那接下来要写数据的时候，把数据迁移过去、写到更新的块里就行——新块被擦除的次数还少，寿命还够用。

磨损均衡技术分为两种：

- **动态磨损均衡**：在每一次写入数据的时候，固态硬盘优先选择累计擦除次数更少的新块来写。反正无论写到哪个位置，闪存翻译层都能把逻辑地址映射正确——既然如此，把数据写到新块里岂不是更好？
- **静态磨损均衡**：固态硬盘在后台悄悄地监测哪些块经常被读、哪些块经常被写。想想你下载到本地的电影这种数据——你基本上只可能去读它，不可能去写它。对于这种读多写少的数据，就可以把它迁移到更老的、寿命更短的块里去：因为读操作并不损耗块的寿命，写操作才可能引发擦除，而每擦除一次，块的寿命就减一。让老块承担"只读"的任务，让更新、寿命更充足的块去承担写操作更多的任务。

到此为止，固态硬盘这个考点在操作系统和计组两边要求掌握的内容就都覆盖了。其中**读写性能特性**和**磨损均衡技术**这两部分是操作系统大纲明确要求掌握的，其余部分也有可能在选择题当中考察，都别掉以轻心。
