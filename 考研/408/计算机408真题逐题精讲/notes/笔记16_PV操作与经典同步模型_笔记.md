# PV 操作与经典同步模型

先说一句大实话：PV 操作这类题，考的不是你背没背过 `P` 和 `V` 的定义——定义只有两行，谁能背不下来。考的是你能不能把一句大白话描述的流程，从自然语言里翻译成信号量。题目年年换皮：09 年是传送带取件、11 年是银行取号、13 年和 14 年是环形缓冲区连取十件、15 年是双信箱辩论、17 年是三个线程抢同一批全局变量、22 年是六道操作的前驱关系、24 年是缓冲区上的三种操作、25 年是三个人植树。场景一个比一个花哨，底下那套动作却一模一样。

所以这一篇我们不按年份走，按知识主题横着过。目标就一个：**把"看到题目 → 落笔写 PV"这条路，变成肌肉记忆。**

## 信号量的语义与两个原语

### wait 与 signal 到底做了什么

信号量就是一个整型量，但它身上背了两条规矩：wait（P）操作负责**申请**，signal（V）操作负责**释放**。

wait 干的事是：先看 S 大小于等于 0 还是大于 0。小于等于 0，说明你要的东西现在没有，那就一直判断下去等着；一旦大于 0，就把 S 减一，申请成功，走人。

signal 干的事更简单：资源被释放出来了，S 加一。

```text
semaphore S = n;

wait(S):        signal(S):
  while (S <= 0)   S = S + 1
      ;             ;
  S = S - 1
```

这两条原语在系统里是**原子操作**的——所谓原子，就是不可分割。别的进程不可能在"判断"和"减一"这中间插进来。这一条是后面所有讨论的地基：只要原语本身是原子的，信号量机制就能保证临界区不被并发闯入。

### 为什么对信号量本身的访问必须互斥

这一点很多人绕不过去，值得单独说：21 年那道题第一问就问这个。

理由就藏在操作定义里。wait 要对 S **减一**，signal 要对 S **加一**，而这个 S 是被所有进程的这两个操作**共享**着的。多个进程同时去动 S，就是对 S 同时做读和写。

> **结论**：S 是一个**临界资源**，对它的读-写冲突必须互斥。道理和"多个进程同时改一个共享变量"一模一样，只是这里的共享变量换成了信号量本身。

### 资源信号量与同步信号量的分工

信号量按用途可以分成两族，这两族的初值和用法完全相反，混淆了就是灾难。

**互斥信号量**初值恒为 1。它的语义是"一把钥匙"：初值 1 表示门本来就是开着的，先来的直接进去，后来的人发现 S 变 0 了，就在门外排队。P/V 必须**在同一个进程内严格配对**——每个 P 后面必须有一个 V 让它还回去，否则锁就永远漏出去了。

**资源信号量**初值等于资源的**初始数量**。它的语义是"计数器"：空位 3 个就写 3，产品 0 个就写 0。它的 P/V **跨进程配对**：一个进程的 V 唤醒的是另一个进程的 P。

**同步信号量**初值恒为 0。它表达的是"某件事还没发生"：初值 0 就是说此刻没人 signal 过它，谁上来 P 谁就等。它的 P/V 同样跨进程配对，但配对的方向永远是"执行完的一方 signal，等待的一方 wait"。

> **易错点**：同一个题目里出现一个初值 0 的信号量和一个初值 1 的信号量，长得几乎一模一样，但身份和用途天差地别。24 年那道缓冲区题就是活例子：初值 0 的是同步信号量——双方都在等对方先做；初值 1 的是互斥信号量——门本来就开着，先来的先进去，后来的在门外排队。

### 信号量初值怎么定

初值不是随手填的，它必须**和"系统刚启动那一刻的真实状态"对得上**。定初值只有两条路：

- **计数型的**（空位数、顾客数、碗数、椅子数）：数一数系统刚起来时手里到底有几个，初值就写几个。银行取号窗口只有 10 个座位，`empty` 就是 10；三个人植树坑数上限 3、能挖的名额就是 3；博物馆 500 人上限，`empty` 就是 500。
- **事件型的**（有没有奇数、有没有邮件、有没有树苗、有没有人在等）：刚启动时这件事一次都没发生过，初值就是 0。09 年缓冲区里一个数都没放，哪来的奇数、哪来的偶数，`odd` 和 `even` 全是 0。

> **提示**：`tree` 那个信号量的初值只能是 0。初始坑数是 0，坑里根本没有树苗，如果这里给 1，丙一上来就会去浇一个根本不存在的苗，同步关系从第一拍就乱了。初值给错一个数，后面所有推导全部作废。

## PV 写同步的通用套路

这一节是整篇的骨架。不管题目换成什么皮，动手之前都走这五步。

### 第一步：把题目读成一个模型

拿到题目别急着写代码，先用一句话把题目说成"谁在干什么、等谁"。这一步做对了，后面全顺；这一步糊弄过去，后面必错。

判断依据是关键词：

- 一边往里放、一边从往外取 → **生产者—消费者**
- 有人往里放、有人往外放、还是同一个人干 → **既是生产者又是消费者**
- 大家轮流用同一件工具（碗、椅子、窗口、取号机） → **互斥为主**
- 题目说"必须先……才能……"、"只有……才允许" → 这句话就是一条**前驱边**，背后必然藏着一个信号量

15 年那道双信箱题就是"既是生产者又是消费者"的标本：A 从自己的信箱里取（消费），往对方的信箱里放（生产）；B 也一样。图上明明只有两个进程两个信箱，却画出四条箭头——因为箭头本来就是双向的。

```text
   ┌───────────┐           放入新邮件           ┌───────────┐
   │   进程 A  │          ---------->           │ B 的信箱  │
   └───────────┘                                └───────────┘
         ▲                                            ▲
         │  取出邮件                                  │  取出邮件  │
         ▼                                            ▼
   ┌───────────┐                                ┌───────────┐
   │ A 的信箱  │          <----------           │   进程 B  │
   └───────────┘           放入新邮件           └───────────┘
```

### 第二步：分清角色——谁在等谁，谁在抢谁

这一步的核心动作是：把每一个进程的每一个动作都拆开，逐个动作问一句"它凭什么能做"。

"凭什么能做"只有两个来源：

- 资源够（有空位、有人、没满）→ 这是**资源信号量**，P 在前
- 别人没占用（临界资源）→ 这是**互斥信号量**，P 在后

"谁在等谁"则是看：题目里每一句"必须先……才能……"，谁等谁。09 年那道题里，"只有缓冲区里真的出现了奇数，P2 才能取"——这就是 P2 等 P1，一个 `odd` 信号量就位了。

角色判完，信号量往往就自己长出来了。25 年三人植树那一道，把三个人的动作拆开之后，四个信号量直接浮出水面。

### 第三步：确定进程边界与循环

这一步最简单，也最容易丢分——**循环是必须写上去的**。

判断标准只有一条：**这个进程是干一次就结束，还是会重复干？**

- 干一次就结束 → **不写循环**。博物馆的参观者：进门、参观、出门，各一次，没有第二圈。24 年那道题明确说 P1 执行 C1 一次、P2 执行 C2 一次，也不循环。银行取号窗口的顾客进程同理：领号、坐、等叫号、被服务完就结束了，顾客 i 里的 i 就是进程编号。
- 持续重复 → **必须套 `while`**。生产者、消费者、营业员、植树的三个人、信箱模型的 A 和 B，全都要套。

> **易错点**：漏掉 `while` 循环的答案，考场上是拿不到分的，哪怕信号量一个没错。这一步没有任何技巧，就是别忘。

### 第四步：列出每个进程的信号量操作

逐个进程写，写的时候守死这个次序：

> **结论**：先同步，后互斥。**资源信号量的 P 在前，互斥信号量的 P 在后**；**互斥信号量的 V 在前，资源/同步信号量的 V 在后**。

这条次序不是风格问题，是正确性问题，理由下一节展开。

### 第五步：回头检查配对与顺序

写完必须回头扫两遍：

- **互斥信号量成对**：每个 `P(mutex)` 都要在同一个进程里找到配对的 `V(mutex)`。少一个 V，这个进程退出临界区之后就再也进不去了。
- **资源信号量跨进程配对**：一个进程的 V 唤醒的是另一个进程的 P，错位了同步关系就全断。

> **提示**：答题时尽量把伪代码写完整，别只写个提纲。**PV 操作的位置、数量、顺序，每一个都是给分点**。另外题目如果明确要求"说明信号量含义及初值"，那几句话必须写在答案里，一句都省不掉。

### 通用流程图

整条 PV 操作流程长这样，考场上脑子里要有这张图：

```text
              ┌──────────── 一个进程对临界资源的完整访问 ────────────┐
              │                                                     │
   条件不满足 │  P(资源信号量)                                       │
   （资源不够）│  ── 申请不到就阻塞在这里，排队等别人的 V ──▶         │
              │        │                                           │
   条件满足   │        ▼                                           │
   ────────▶ P(mutex)   ← 进入区：申请互斥信号量，拿到"钥匙"        │
              │        │                                           │
              │        ▼                                           │
              │   { 临界区 }        ← 真正读写共享数据的一段          │
              │        │                                           │
              │        ▼                                           │
              │   V(mutex)         ← 退出区：立刻把钥匙还回去        │
              │        │                                           │
              └────────┼───────────────────────────────────────────┘
                       ▼
               V(资源/同步信号量)   ← 通知别人：我这边腾出来了
```

临场告诫一句：进入区到退出区之间那一段，就是临界区。**临界区里只能放对共享数据的操作**，像 `countOdd++` 这种统计"取出来的数"的累加，就该放在临界区外面，材料里那几道题都是这么写的。

## 各类经典模型的信号量设计

### 各模型信号量对照表

这张表是这一节的地图，动手之前先在脑子里对一遍：

| 模型 | 出现年份 | 互斥信号量 | 资源/同步信号量 | 进程数 | 是否循环 |
| :--- | :---: | :--- | :--- | :---: | :--- |
| 传送带取件（一拖二） | 09 | `mutex = 1` | `empty = N`、`odd = 0`、`even = 0` | 1 生产 + 2 消费 | 三个都循环 |
| 银行取号窗口 | 11 | `mutex = 1` | `empty = 10`、`full = 0`、`service = 0` | 顾客 i + 营业员 | 只有营业员循环 |
| 博物馆进出 | 13 | `mutex = 1` | `empty = 500` | 参观者 i | 不循环 |
| 环形缓冲区连取十件 | 13 / 14 | `mutex1 = 1`、`mutex2 = 1` | `empty = 1000`、`full = 0` | 多生产者 + 多消费者 | 都循环 |
| 双信箱辩论 | 15 | `mutex_a = 1`、`mutex_b = 1` | `full_a = X`、`empty_a = M−X`、`full_b = Y`、`empty_b = N−Y` | A、B 各一 | 两个都循环 |
| 三线程抢全局变量 | 17 | `mutex_Y1`、`mutex_Y2`、`mutex_Z` 全为 1 | 无 | 3 个线程 | 无循环 |
| 缓冲区 C1/C2/C3 | 24 | B 非空时 `mutex = 1` | B 为空时同步信号量 `mutex = 0` | P1、P2 各一次 | 不循环 |
| 三人植树 | 25 | `mutex = 1`（铁锹） | `position = 3`、`pit = 0`、`tree = 0` | 甲、乙、丙 | 三个都循环 |
| 六操作前驱关系 | 22 | 无 | `S_AC = 0`、`S_CE = 0` | 2 个线程 | 无循环 |

> **提示**：看一眼这张表就会发现，年份换了、场景换了，但**信号量的家族永远是那三四个**：`mutex` 管锁、`empty/full` 管一增一减的计数、`service`/`tree`/`S_CE` 这类管"某件事发生了没有"。认出家族，题就做掉一半了。

### 生产者—消费者：传送带取件

09 年那道题：三个进程 P1、P2、P3 互斥地使用一个包含 $N$ 个单元的缓冲区。P1 每次用 `produce` 生成一个正整数、用 `put` 送入某个空单元；P2 每次用 `getOdd` 取出一个奇数、用 `countOdd` 统计；P3 每次用 `getEven` 取出一个偶数、用 `countEven` 统计。

一上来先对号：这就是标准的**生产者—消费者问题**，只是消费者被拆成了两个，而且两个消费者还各挑各的。缓冲区是临界资源，P1 是生产者，P2 只取奇数，P3 只取偶数——"一拖二"是这道题唯一的花样，其余全是经典骨架。

```text
semaphore mutex = 1;   // 互斥信号量：互斥访问缓冲区这个临界资源
semaphore empty = N;   // 资源信号量：缓冲区中空单元的个数
semaphore odd   = 0;   // 资源信号量：缓冲区中奇数的个数
semaphore even  = 0;   // 资源信号量：缓冲区中偶数的个数
```

四个信号量四个含义，这四句话必须写进答案里。

```c
P1() {                        // 生产者
    while (true) {
        x = produce();
        P(empty);             // 先申请空单元
        P(mutex);             // 再互斥访问缓冲区
        put(x);
        V(mutex);             // 放完立刻让出缓冲区
        if (x % 2 == 0) V(even);
        else             V(odd);
    }
}

P2() {                        // 消费者：只取奇数
    while (true) {
        P(odd);               // 等一个奇数出现
        P(mutex);
        getOdd(x);
        V(mutex);
        V(empty);             // 取走一个，空位多一个
        countOdd++;           // 统计在临界区之外做
    }
}

P3() {                        // 消费者：只取偶数，与 P2 对称
    while (true) {
        P(even);
        P(mutex);
        getEven(x);
        V(mutex);
        V(empty);
        countEven++;
    }
}

cobegin
    P1(); P2(); P3();
coend
```

这里藏着三个考点，每一个都值得单独说：

- **信号量的身份要看清**。`odd` 和 `even` 不是互斥信号量，它们是**资源信号量**，初值为 0，被 P1 的 V 操作"生产"出来。系统刚起来缓冲区是空的，哪来的奇数偶数。
- **V 的位置**。`V(odd)` / `V(even)` 放在 `V(mutex)` **之后**：放进缓冲区这个动作在临界区里完成，"通知消费者"在离开临界区之后才做。`countOdd` 统计的是**取出来的数**，更不该待在临界区里。
- **P 的次序**。`P(empty)` 必须在 `P(mutex)` 前面，顺序反了就出事，理由见后面的常见错法。

### 环形缓冲区与"连取十件"的附加条件

13 年和 14 年那道题，是标准生产者消费者加了一条附加要求：**一个消费者进程从缓冲区连续取出十件产品后，其他消费者进程才可以取产品。**

这条附加要求就是解题的抓手。经典的四个信号量不够用了——"连续的十次"必须被整体锁住，中间不能被其他消费者插队。

```text
| 信号量   | 含义                                              | 初值  |
| -------- | ------------------------------------------------- | ----- |
| `empty`  | 缓冲区中空位置的个数                                | 1000  |
| `full`   | 缓冲区中产品的个数                                  | 0     |
| `mutex1` | 生产者之间、以及生产者与消费者之间访问缓冲区的互斥  | 1     |
| `mutex2` | 消费者之间访问缓冲区的互斥（保证连取十件不被插队）  | 1     |
```

两个互斥信号量一定要分清楚：`mutex1` 管的是"缓冲区的物理读写"这件事本身，谁碰都得排队；`mutex2` 管的是"一整轮连续取十件"这个逻辑过程，只有消费者用得上，生产者进程里压根不出现它。

```c
semaphore empty  = 1000;
semaphore full   = 0;
semaphore mutex1 = 1;
semaphore mutex2 = 1;

process producer() {
    while (1) {
        生产一件产品;
        P(empty);        // 先申请一个空位置
        P(mutex1);       // 再互斥访问缓冲区
        将产品放入缓冲区;
        V(mutex1);
        V(full);         // 产品数 +1
    }
}

process consumer() {
    while (1) {
        P(mutex2);               // 把"连续取十件"整体互斥起来
        for (int i = 0; i < 10; i++) {
            P(full);             // 缓冲区里得有产品才能取
            P(mutex1);           // 与生产者、其他消费者互斥
            从缓冲区取出一件产品;
            V(mutex1);
            V(empty);            // 空位 +1
        }
        消费取出的这十件产品;
        V(mutex2);
    }
}

cobegin
    producer();
    consumer();
coend
```

> **易错点**：`P(mutex2)` 和 `V(mutex2)` 必须**夹在整个 `for` 循环的前后**。写到循环里面去，等于没加这把锁——每取一件就放一次，其他消费者照样能插进来。这一步是整道题的命门。
>
> 另外，每一次循环里都要 `P(full)`。哪怕正处在那个"连续十件"的循环里，缓冲区里没产品照样取不出来。

### 银行取号窗口

11 年这道题：顾客进程领号、坐进座位等叫号，营业员进程叫号、服务。两个进程，四个信号量。

先把框架定死：题目明确说整个过程由**两个进程**构成——一个顾客进程、一个营业员进程。每位顾客都是各自独立的进程，所以顾客进程**不需要循环**。营业员只有一个，而他的工作是持续重复的，叫号、服务、再叫号、再服务，所以营业员进程外面必须套 `while`。

| 信号量 | 初值 | 含义 |
| :--- | :---: | :--- |
| `mutex` | 1 | 取号机的互斥信号量，一次只允许一位顾客使用 |
| `empty` | 10 | 空座位的数目 |
| `full` | 0 | 已取号落座、等待叫号的顾客数目 |
| `service` | 0 | 营业员已叫到号、可以开始服务的次数 |

`empty` 和 `full` 这一对是这道题里最需要想清楚的关系：**申请座位用 `empty`，通知"座位上有人了"用 `full`**，一个减一个增，位置正好错开。

```c
process 顾客i {
    P(empty);              // 先看有没有空座位
    P(mutex);              // 再互斥访问取号机
    从取号机获取一个号码;
    V(mutex);              // 用完取号机，放回去
    V(full);               // 落座了，在座顾客数 +1
    P(service);            // 等叫号、等服务
    接受服务;
}

process 营业员 {
    while (true) {
        P(full);           // 先看座位上有没有人在等
        叫号;
        V(empty);          // 这位顾客离开座位了，空位 +1
        V(service);        // 轮到这一位了，可以服务
        为顾客服务;
    }
}
```

三处次序都有讲究：

- 顾客那边 `P(empty)` 必须在 `P(mutex)` 前面。否则这个顾客就卡在临界区里出不来，取号机被他占着，别人连号都取不到——**抱着锁去排队等座位，等的人永远等不到**。
- `P(full)` 放在营业员流程的最前面，因为**没有顾客的时候根本没必要叫号、也没必要服务**。
- `V(empty)` 放在 `V(service)` 前面，因为顾客是从座位上被叫起来才去接受服务的，座位是这时候才空出来的。

整道题的做法其实就一句话：**逐个分析每一步操作需要参考谁的信号量，就给它设置什么样的信号量，然后把 PV 操作加在每个操作的前后。** 框架是现成的，我们只是往里填东西。

### 博物馆进出

13 年另一道题简单得几乎算送分：某博物馆最多容纳 500 人同时参观，只有一个出入口，一次仅允许一个人通过。参观者进程的动作是：进门 → 参观 → 出门。

信号量只有两个，一个都不用多：

| 信号量 | 初值 | 含义 |
| :--- | :---: | :--- |
| `mutex` | 1 | 出入口的互斥资源信号量 |
| `empty` | 500 | 博物馆内的空位个数 |

```c
semaphore mutex = 1;    // 出入口互斥
semaphore empty = 500;  // 博物馆空位数

process visitor_i {
    P(empty);      // 先申请一个空位，馆里塞满了就等着
    P(mutex);      // 再申请门的互斥访问
    进门;
    V(mutex);      // 人进来了就把门让出来，不然别人申请不上
    参观;
    P(mutex);      // 出门同样要互斥
    出门;
    V(mutex);
    V(empty);      // 人走了，容纳量加一
}
```

门口有两对 `mutex`（进一次、出一次），`empty` 一对，成对了就没有错。

> **提示**：回头看这道题，它跟生产者消费者其实非常像。**进门就是生产者**，把人放进博物馆；**出门就是消费者**，把人从馆里拿出来。唯一的区别是，这里两件事被塞进了同一个进程里，而经典的生产者消费者是两个独立进程。看到这种"一个进程干两件事"的题，先往经典模型上靠。

### 双信箱辩论

15 年那道题不给代码，只给一整段描述：A、B 两人通过信箱辩论，每人从**自己的**信箱取出对方的问题，把答案和新问题组成一封邮件放进**对方的**信箱。A 的信箱最多放 $M$ 封，B 的最多放 $N$ 封，初始分别有 $X$、$Y$ 封。

顺着"取"和"放"两条动作线拆下去，每个信箱各需要三个信号量，一共六个。

```text
| 信号量   | 含义                  | 初值      |
| -------- | --------------------- | --------- |
| `full_a` | A 信箱中已有的邮件数  | $X$       |
| `empty_a`| A 信箱中还能存的邮件数| $M - X$   |
| `mutex_a`| A 信箱的互斥访问权    | 1         |
| `full_b` | B 信箱中已有的邮件数  | $Y$       |
| `empty_b`| B 信箱中还能存的邮件数| $N - Y$   |
| `mutex_b`| B 信箱的互斥访问权    | 1         |
```

`empty_a` 的初值为什么是 $M - X$ 而不是 $M$？因为初始时 A 的信箱里已经占了 $X$ 封，能再放的是 $M - X$ 封。**初值是"剩下的"，不是"总共的"**——这一条到哪道题都成立。

```c
进程 A（循环执行）
    P(full_a);                 // A 信箱里有邮件，才能取
    P(mutex_a);                // 互斥地进入 A 信箱
    从 A 的信箱中取出一个邮件;
    V(mutex_a);
    V(empty_a);                // 取走一个，空出来的位置 +1

    回答问题，并提出一个新问题;

    P(empty_b);                // B 信箱有空位，才能放
    P(mutex_b);
    把新邮件放入 B 的信箱;
    V(mutex_b);
    V(full_b);                 // 放入一个，B 信箱的邮件数 +1

进程 B（循环执行）        // 同一个模子，把信箱换过来
    P(full_b);
    P(mutex_b);
    从 B 的信箱中取出一个邮件;
    V(mutex_b);
    V(empty_b);

    回答问题，并提出一个新问题;

    P(empty_a);
    P(mutex_a);
    把新邮件放入 A 的信箱;
    V(mutex_a);
    V(full_a);
```

> **结论**：这道题相比经典生产者消费者，真正新增的难点只有一个——**临界区从一个变成了两个**。信箱从一个变成两个之后，互斥信号量配两份，资源信号量按信箱分别记账。这个"一份变两份"的动作，就是全部考点。

### 三人植树

25 年那道题：甲、乙、丙三个人，一把铁锹、一个水桶、一片树坑。甲挖坑，乙放树苗再填土，丙浇水。坑数小于 3 才能挖，初始坑数为 0。

这类题没有捷径，但也不需要灵感——**把每个人的动作拆开，谁在等谁、谁在抢谁，抠出来信号量就自己长出来了**。

```text
   甲 挖坑 ──► 乙 放树苗 ──► 乙 填土 ──► 丙 浇水 ──► 回到甲
    │            │             │             │
  铁锹 mutex   坑位 position  铁锹 mutex    树苗 tree
```

| 信号量 | 初值 | 管的是什么 | 谁申请 / 谁释放 |
| :--- | :---: | :--- | :--- |
| `position` | 3 | 还能挖几个坑 | 甲 `wait`，乙放完苗 `signal` |
| `pit` | 0 | 已挖好、还没填土的坑数 | 甲挖完 `signal`，乙 `wait` |
| `mutex` | 1 | 那把唯一的铁锹 | 甲、乙都要 `wait` / `signal` |
| `tree` | 0 | 已填好土、可以浇水的树苗 | 乙填完 `signal`，丙 `wait` / `signal` |

```c
semaphore position = 3;   // 还能挖几个坑
semaphore pit       = 0;   // 已挖好、尚未填土的坑数
semaphore mutex     = 1;   // 铁锹，甲乙互斥
semaphore tree      = 0;   // 已种好、等待浇水的树苗

P1() {                        // 甲：挖坑
    while (true) {
        wait(position);
        wait(mutex);          // 抢铁锹
        挖坑;
        signal(mutex);        // 还铁锹
        signal(pit);          // 坑多了一个
    }
}

P2() {                        // 乙：放树苗 + 填土
    while (true) {
        wait(pit);            // 先得有坑
        放树苗;
        signal(position);     // 坑被占住，能挖的名额还回去
        wait(mutex);          // 填土也要铁锹
        填土;
        signal(mutex);
        signal(tree);         // 树苗种好了，丙可以来浇
    }
}

P3() {                        // 丙：浇水
    while (true) {
        wait(tree);           // 有种好的树苗才浇
        浇水;
        signal(tree);         // 水桶只有我用，不设互斥信号量
    }
}
```

三个最容易被扣分的地方：

- **"能挖的坑名额"和"已挖好的坑数"是一对反向的量，别搞混。** 甲挖完坑之后增加的是**树坑的数量**——坑挖出来了，说明坑位还占着，可挖的名额根本没有释放出来。等到乙把树苗放进去，坑被占住了，可挖的名额才该 signal 回去。
- **水桶不设信号量。** 水桶只有丙一个人用，跟别人没有冲突，所以**根本不需要为它设互斥信号量**。少设一个，本身就是得分点。
- **三个人的代码都要 `while`**。题目说他们都在持续工作，挖完不能停、填完不能停、浇完也不能停。

### 三线程抢全局变量

17 年那道题是这一类里最"反直觉"的一个。要求是：**添加必要的信号量和 PV 操作，确保线程互斥访问临界资源，并且最大程度地并发执行。**

注意"最大程度地并发执行"这半句，它是这道题的命门。

先把临界资源认出来。题目给的结构体有两个成员，然后定义了一组**全局变量** `X`、`Y`、`Z`。

> **结论**：只有**全局变量**才需要互斥访问，局部变量不用管。局部变量只在本线程里访问，其他线程根本够不着它。这道题里每个线程的 `W` 都是局部的，一眼就能排除。

再看每个线程在干什么：

```c
void thread1() { struct CMN W; W = Add(X, Y); }        /* 读 X、读 Y */
void thread2() { struct CMN W; W = Add(Y, Z); }        /* 读 Y、读 Z */
void thread3() { struct CMN W; W.a = 1; W.b = 1;
                 Z = Add(Z, W); Y = Add(Y, W); }      /* 读 Z、写 Z、读 Y、写 Y */
```

> **结论**：只需要盯两类关系——**读和读之间可以同步进行，不需要互斥；读和写、写和写之间不可以同时进行，需要互斥**。所以后面分析只盯读写、写写这两种就够了。

冲突浮出来一共三对：

| 冲突对 | 争用的资源 | thread1 | thread2 | thread3 |
| :--- | :--- | :--- | :--- | :--- |
| thread2 与 thread3 | Z | 不涉及 | 读 | 读 + 写 |
| thread1 与 thread3 | Y | 读 | 不涉及 | 读 + 写 |
| thread2 与 thread3 | Y | 不涉及 | 读 | 读 + 写 |

X 全程只有 thread1 在读，没人写它，不需要互斥；W 是每个线程自己的局部变量，同样不需要锁。

互斥关系有三对，就设三个互斥信号量：Z 上一个 `mutex_Z`；**Y 上要设两把**——`mutex_Y1` 管 thread1 和 thread3，`mutex_Y2` 管 thread2 和 thread3。

> **易错点**：为什么 Y 要拆成两把、而不是共用一把？原因就藏在"最大程度地并发执行"这句要求里。thread1 和 thread2 之间对 Y 只有读、没有写，本来就不冲突；让它们各拿一把互不相干的锁，谁也不挡谁，并发度才是最高的。**共用一把锁虽然也对，但把不必要的人挡在了门外，违背题意。** 这是这道题最锋利的一刀。

```c
semaphore mutex_Y1 = 1;
semaphore mutex_Y2 = 1;
semaphore mutex_Z  = 1;

void thread1() {
    struct CMN W;
    P(mutex_Y1);
    W = Add(X, Y);
    V(mutex_Y1);
}

void thread2() {
    struct CMN W;
    P(mutex_Y2);
    P(mutex_Z);
    W = Add(Y, Z);
    V(mutex_Z);
    V(mutex_Y2);
}

void thread3() {
    struct CMN W;
    W.a = 1;
    W.b = 1;

    P(mutex_Z);
    Z = Add(Z, W);
    V(mutex_Z);

    P(mutex_Y1);
    P(mutex_Y2);
    Y = Add(Y, W);
    V(mutex_Y1);
    V(mutex_Y2);
}
```

下 PV 的原则就一句：**在哪一行访问了受保护的全局变量，就在那一行的前后夹一对 P、V。**

### 读者—写者模型

17 年那道题在判断 thread1 读 Y 时提了一句"读写文件模型"——多个进程可以同时读同一个文件，这就是**读者—写者问题**的标准形态：允许多个读者同时读，但写者写的时候必须独占。

信号量三个：`mutex` 保护读者计数 `readcount`，`rw` 卡住写者。

```c
semaphore mutex = 1;    // 互斥访问 readcount 这个共享变量
semaphore rw    = 1;    // 读写互斥：写者来时必须独占
int readcount  = 0;     // 当前正在读的读者数

Reader() {
    P(mutex);                 // 改 readcount 必须互斥
    readcount++;
    if (readcount == 1)
        P(rw);                // 第一个读者才真正去抢读权限
    V(mutex);

    读文件;                    // 多个读者可以同时进入这一段

    P(mutex);
    readcount--;
    if (readcount == 0)
        V(rw);                // 最后一个读者离开才把读权限还回去
    V(mutex);
}

Writer() {
    P(rw);                    // 独占，读者进不来
    写文件;
    V(rw);
}
```

两个设计要点，一个都不能少：

- **只有一个读者、一个写者时需要 `mutex`；有多个读者时也必须有 `mutex`。** 少一个就会在 `readcount++` 这类操作上产生竞态。
- **只有第一个读者去 P(rw)，只有最后一个读者去 V(rw)。** 改成"每个读者都 P/V 一遍"，就退化成了互斥模型，多读的优势全部消失。

> **结论**：这个模型的价值在于它诚实地承认了"读读不冲突"这件事。17 年那道三线程题要求"最大程度并发"，思路和它是一脉相承的：**能并行的就别加锁，只锁真正冲突的那部分。**

### 哲学家进餐与多一只碗

五位哲学家围着一张圆桌，各有一只碗，两根筷子（一根左一根右）分放左右。相邻两位的筷子是共用的，每人吃饭需要左右两根筷子齐备。

死锁的根源在于四条同时满足的必要条件：互斥、请求并保持、不可剥夺、循环等待。最要命的是第四条——五个人都在等"左边那位"先吃饭，形成一个环。

破解的思路很朴素：**打断这个环**。有两种改法。

**改法一，多一只碗。** 碗加到 6 只，筷子也加到 6 根。哲学家一共只有 5 个，所以无论什么时候都至少有一只空碗；有人能拿到碗，就一定能拿到碗旁边那两根筷子，于是环被切断了。

```c
semaphore bowl      = 6;                  // 空碗数
semaphore chopstick[0..5] = {1,1,1,1,1,1}; // 每根筷子一个信号量

Philosopher_i() {                         // i = 0, 1, 2, 3, 4
    P(bowl);                              // 先拿一只碗
    P(chopstick[i]);                      // 再拿左边的筷子
    P(chopstick[(i + 1) % 6]);            // 再拿右边的筷子
    吃饭;
    V(chopstick[(i + 1) % 6]);            // 放筷子
    V(chopstick[i]);
    V(bowl);                              // 放碗
}
```

**改法二，奇偶编号。** 碗和筷子数不变，规定**奇数号的哲学家先拿左筷、再拿右筷，偶数号的先拿右筷、再拿左筷**。这样"全都左手先拿着等右手"的死锁局面根本构不成。

```c
semaphore bowl      = 5;
semaphore chopstick[0..4] = {1,1,1,1,1};

Philosopher_i() {
    P(bowl);
    if (i % 2 == 0) { P(chopstick[i]);       P(chopstick[(i+1)%5]); }
    else             { P(chopstick[(i+1)%5]); P(chopstick[i]);       }
    吃饭;
    V(chopstick[i]);
    V(chopstick[(i+1)%5]);
    V(bowl);
}
```

> **结论**：这两个改法的共同点，都是"在碗这一环上留一个缺口"。**信号量机制本身能防死锁（不存在死锁四个必要条件里的互斥例外），但需要你设计得当。**

## wait/signal 与前驱关系

### 前驱图的读法

22 年那道题给的是一张前驱图：一个进程里有两个线程 T1、T2 并发执行，A 到 F 共六个操作，T1 执行 A、E、F，T2 执行 B、C、D。

```text
   A(T1)
      │
      ▼
B(T2) ──► C(T2) ──► D(T2)
            │
            ▼
          E(T1)
            │
            ▼
          F(T1)
```

读图就是读约束：**C 在 A、B 之后执行；D 和 E 在 C 之后执行；F 在 E 之后执行。**

两个别多手的点：

- 题目要的是 `wait` 和 `signal`，就老老实实写 `wait`、`signal`，**别换成 P、V**。题目没注明可以用 PV，换了等于自找麻烦。
- 题目没说循环执行，所以外面不用套 `while`。

### 一条前驱边配一个信号量

常规 PV 题里每个节点代表一个进程，照着箭头走向直接分配信号量就行。这道题把节点拆散放进了两个线程，所以要看的是**两个线程之间交接的那一点**。

> **结论**：**凡是有先后关系、又跨线程的地方，就配一个信号量。一条前驱边一个信号量。**

逐个线程走一遍：

**T1 这边**：A 没有前驱，可以直接执行。A 之后是 E，而 E 的前驱是 C，C 在 T2 手里，所以 E 之前必须先申请 C 这条线段对应的信号量，记作 $S_{CE}$，拿到才能执行 E。E 执行完轮到 F，F 的前驱就是 E，已经满足，直接做。

```text
T1:  A  →  wait(S_CE)  →  E  →  F
```

**T2 这边**：B 没有前驱，直接执行。B 之后是 C，而 C 的前驱除了 B 还有 A，A 在 T1 手里，所以 C 之前要申请 A 这条线段的信号量 $S_{AC}$。T1 执行完 A 之后正好释放 $S_{AC}$，把门给 T2 打开。T2 拿到信号量才能执行 C；C 执行完，T1 的 E 就解禁了，所以紧接着 signal($S_{CE}$) 把 T1 唤醒；然后做 D，D 的前驱只有 C，已经满足。

```text
T2:  B  →  wait(S_AC)  →  C  →  signal(S_CE)  →  D
```

| 信号量 | 初值 | 作用 |
| :--- | :---: | :--- |
| $S_{AC}$ | 0 | T2 执行 C 之前要等 T1 把 A 做完 |
| $S_{CE}$ | 0 | T1 执行 E 之前要等 T2 把 C 做完 |

初值取 0 的原因很直白：这两个信号量一开始谁都没被 signal 过，wait 一上来就得把执行权让出去，把"必须等待"的语义钉死。

### 同一线程内的前驱边不用信号量

对上那道题，注意 D 前面那条 C → D：F 的前驱 E 也在 T1 里，E 完成后直接做 F，中间一个信号量都没有。

> **结论**：**只有跨线程的前驱关系才需要信号量，同一线程内的先后顺序靠程序本身的顺序执行天然保证。** 多设一个信号量不但多余，还可能因为初值给错而制造出本来不存在的问题。

## 临界区互斥的实现

### 临界资源的判断：读读不算冲突

判断一道题里哪些东西是临界资源，只问两句话：

1. 它是**多个进程/线程都要访问**的吗？只有一个访问，那就跟互斥无关。
2. 有没有**至少一个写**？全是读，就不存在冲突。

> **结论**：读-读不算冲突，读-写、写-写才算冲突。这条判据是 17 年那道三线程题的全部立身之本，也是读者-写者模型存在的理由。

临界区结构长这样，这张示意图要能默写：

```text
cobegin
   process Pi {
       进程前部代码;
       P(mutex)          ← 进入区：申请互斥信号量
       {
           临界区         ← 访问临界资源的核心段
       }
       V(mutex)          ← 退出区：释放互斥信号量
       进程后部代码;
   }
coend
```

三条要求：临界区里只放对共享数据的操作；进入区申请、退出区释放且必须成对；临界区不能太长，能少写的别多写。

### 硬件指令：swap 与 test-and-set

软件忙等的效率太低，硬件可以直接提供"**读并写**"这条原子指令。

**swap 指令**交换两个存储单元的内容。`swap` 与一个自变量配合就能实现互斥：

```c
int mutex = 0;                    // 临界资源初值为 0，表示空闲

wait(mutex) {
    int old;
    do {
        old = mutex;              // ① 把 mutex 读出来
        swap(&mutex, &old);      // ② 原子地交换：mutex 拿到 old(0)，old 拿到 mutex 原值
    } while (old == 1);           // ③ 交换前 mutex 是 1，说明锁被别人占着，重来
}

signal(mutex) {
    mutex = 0;                    // 直接清 0，等于解锁
}
```

> **易错点**：`swap` 指令之所以能互斥，靠的是它"**读和写这两件事在硬件上不可分割**"这一条性质。它不是靠"交换"这个动作本身实现的。另外注意 `while` 判断的是 **交换前**的旧值——`old == 1` 说明进临界区之前锁已被别人拿走。

**test-and-set 指令**返回原值并把目标置 1，逻辑更直白：

```c
wait(mutex) {
    while (test_and_set(&mutex) == 1) ;   // 返 1 表示锁被占，自旋等待
}

signal(mutex) {
    mutex = 0;
}
```

这两个函数都需要在"关中断 → 判 → 改 → 开中断"的框架里才安全，因为只判不取之间必须保证没有别的进程插进来。

### 软件方案：Peterson 算法

不用硬件指令也能用软件造一把锁。Peterson 算法给每个进程两个标志位 `flag[i]` 和一个 `turn`：

```c
// 进程 i 进入临界区
flag[i] = true;                 // 我想进
turn = j;                       // 把优先权让给对方
while (flag[j] && (turn == j)) ;  // 对方也想进，且优先权在他手上，才让路

// 进程 i 退出临界区
flag[i] = false;
```

算法之所以能成立，靠的是那句 `turn = j`——**你总有一瞬间把优先权让出去**。哪怕两个进程同时想进，一个刚设完 flag 对方还没设，另一个的 `turn` 赋值就打断了僵持。

代价是它只有两个进程时才干净，而且要占额外空间、等得慢。所以实务上还是优先用信号量。

### 开关中断指令实现互斥：死循环里必须开中断

21 年那道题给了两种"用开关中断指令实现信号量操作互斥"的方法，第一种是错的，我们把错在哪看清楚。

**方法一的错误**在于：这个 `while` 被关中断整段圈在了里面。

```text
方法一 wait(S)                        方法一 signal(S)
  关中断                                 关中断
  while (S <= 0) ;                      S = S + 1
  S = S - 1                              开中断
  开中断
```

signal 没问题：关中断、加一、开中断，一气呵成，不会卡。问题在 wait：

```text
本进程：关中断 -> 卡在 while(S<=0) 里出不来
其他进程：进不来（中断关着），没人能执行 signal 把 S 加 1
     ↓
  S 永远 <= 0  ->  while 永远成立  ->  死循环
```

关中断期间其他进程根本没法访问 S（它本来就是临界资源），也就没人能把它加上去。S 一直小于等于零，while 一直成立，这个进程就再也出不来了。

> **结论**：方法一**错误**。wait 中在关中断状态下执行 `while (S <= 0)`，一旦 S 持续小于等于零，由于中断关闭其他进程无法执行 signal 修改 S，进程将陷入死循环。

**方法二**的 wait 变成：

```text
方法二 wait(S)
  while (1) {
      关中断
      if (S > 0) {
          S = S - 1
          开中断
          return
      } else {
          开中断          <-- 关键就在这一句
      }
  }
```

差别全在那个 `else` 分支里补的**开中断**：即使 S 小于等于零，判断完也把中断打开再出去转一圈。这样别的进程就能进来访问 S、执行 signal 把资源释放掉。别的进程一改，S 就有可能变成大于零，下一轮判断成立，wait 顺利脱身。

> **结论**：方法二**正确**。它让出了中断，其他进程可以修改 S，循环不会锁死。
>
> **提示**：这一对方法要放在一起记，差别就一句话——**死循环里要不要开中断**。凡是用"忙等"等待资源的地方，中断必须放开，否则你等的那个释放动作永远等不到。

至于用户程序能不能用这条路，答案是不行：**开关中断指令属于特权指令，特权指令只能在核心态执行**。这道题不只考 PV 操作，还把它和前面的"特权指令只能在核心态执行"串了起来。

## 同步互斥的常见错法

### 错法对照表

这张表把 PV 题里所有的坑集中列一遍，写完代码拿它过一遍：

| 错法 | 表现 | 后果 | 正确做法 |
| :--- | :--- | :--- | :--- |
| 关中断包住忙等 | wait 里关中断后 `while (S <= 0);` | 死循环，其他进程进不来 signal | 循环体内补开中断，判断完再放出去转 |
| 顺序反了 | 先 `P(mutex)` 再 `P(empty)` | 死锁：抱着锁等资源，别人等的就是这把锁 | 资源信号量 P 在前，互斥信号量 P 在后 |
| 漏掉 V | 某个 `P(mutex)` 没有配对的 V | 该进程退出临界区后再没人进得去 | 逐个 P 回头找 V |
| 锁放错位置 | `V(mutex)` 写在临界区外面 | 临界区后半段裸奔 | V 紧跟临界区结束 |
| 循环写在里面 | 把 `P(mutex2)` 写进 `for` 循环体内 | 每取一件放一次，插队照样发生 | 夹在整段 `for` 的前后 |
| 漏写 while | 该循环的进程没套 `while` | 干一轮就结束，直接丢分 | 持续重复的进程一律套 `while` |
| 统计放错区 | `countOdd++` 写在临界区里 | 白白拉长临界区，降低并发度 | 对共享缓冲区的操作在临界区内，统计在临界区外 |
| 多设信号量 | 没人用的资源也设互斥量 | 逻辑没错但违背"尽可能少/最大并发" | 无人竞争的资源不设量；Y 拆两把而非共用一把 |
| 少设信号量 | 两个人抢的工具没设量 | 临界区被并发进入 | 找齐所有"多进程要用且有写"的资源 |
| 初值写错 | 事件型信号量给了 1，计数型给了总数 | 同步关系从第一拍就乱 | 初值 = 启动时刻的真实状态 |
| V 顺序颠倒 | 先 `V(full)` 后 `V(mutex)` | 在临界区内通知，拖长临界区 | 先 V(mutex) 再 V(资源量) |
| 换用别的原语 | 题目要 `wait/signal` 却写 P/V | 形式上不符，阅卷可能扣分 | 题面怎么写就怎么写 |

### 每种错法值得多看一眼的地方

**顺序反了是正确性问题，不是风格问题。** 先 `P(mutex)` 再 `P(empty)`，这个进程攥着锁站在门外等空位；而别的进程想进去，必须先拿到这把锁——它永远不会来。两个人互相干瞪眼，谁也动不了。这就是死锁。记住那句口诀：**先申请资源，再申请锁；先释放锁，再释放资源。**

**"最大程度并发"是一句硬要求。** 17 年那道题，Y 上设两把锁而不是一把，标准答案就是这么给的。共用一把锁不会出错，但把两个只读的线程无谓地串行化了，违背题意的另一问。这类"既要正确、又要最优"的大题，最优解往往就是命题人埋的区分点。

**能少设一个信号量就是得分点。** 25 年植树那题，水桶只有丙用，不设量；24 年那道题，第二问"尽可能少的信号量"就只要一个。命题人明明白白在数你的信号量。

**初值不是随手填的。** 再强调一遍：它必须和"系统刚启动那一刻的真实状态"对得上。`empty_a = M − X` 而不是 `M`，`tree = 0` 而不是 1，`service = 0` 而不是 1，差别全在这里。

**"说明信号量含义及初值"是独立得分点。** 光写代码不写含义，考场上是要扣的。每写完一个信号量，脑子里过一遍它的名字、含义、初值，三句话。

## 落点

回头看这些年的题，09 年的传送带、11 年的取号窗口、13 年的博物馆、14 年的连取十件、15 年的信箱辩论、17 年的三线程、22 年的前驱关系、24 年的缓冲区、25 年的植树——场景换了九次，动作模板换了一次。

真正需要记住的只有三件事：

- **模型是有限的。** 生产者消费者、读者写者、哲学家、前驱关系，此外就是某个自定义流程。见到新题第一件事是把它往这几个模型上靠。
- **信号量的家族也是有限的。** `mutex` 管锁、`empty`/`full` 管一增一减的计数、`service`/`tree`/`S_CE` 管"某件事发生没有"。初值只有两类：资源数量、事件 0。
- **顺序和配对是硬考点。** 资源 P 在前、互斥 P 在后；互斥 V 在前、资源 V 在后；每个 P 都要有配对的 V。这几条背熟，PV 题的分就不会丢。

做题时把每一句"必须先……才能……"都当成一条前驱边抠出来，把每一个共享对象都问一遍"多进程要用吗？有没有写"，信号量和代码就自己站住了。剩下的就是回头检查配对——这一步谁做谁稳。
