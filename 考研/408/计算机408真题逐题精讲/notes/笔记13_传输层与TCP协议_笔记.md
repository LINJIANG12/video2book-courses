# 传输层与 TCP 协议

这一块在 408 里的存在感，比很多同学以为的要重。回头数数真题：2015 年第 33 题考 POP3 底下压的是什么、第 39 题整整一道拥塞窗口的计算；2025 年第 37 题问 NAT 转发 UDP 报文时会动哪几个字段、第 38 题问收到一个确认之后还能再发几段、第 39 题问 UDP 和 TCP 的 RTT 差多少。**十年之内，同一个知识点被戳了五六次，而且专挑"看起来简单、算起来绕"的角度下手。**

所以这一块我不按年份给你捋，我们直接谈知识本身。谈之前先把一句话摆在这儿，它是整个传输层的纲：

> **结论**：网络层解决的是"主机到主机"，传输层解决的是"进程到进程"。分界点就是一个东西——**端口号**。

## 传输层给应用层的东西：端口与复用分用

### 端口号：从主机里挑出那一个进程

IP 地址能把你送到那台机器上，可一台机器上同时跑着几十个进程：浏览器、邮箱、数据库、SSH 客户端。**数据报到了网卡，怎么知道该交给谁？** 靠的就是传输层在数据前头贴的那张标签——**端口号**。

```text
   应用进程                    传输层                        网络层
 ┌──────────┐            ┌────────────────┐           ┌────────────┐
 │ 邮件客户端 │ ──数据──▶ │ 源端口  目的端口 │ ──IP 包──▶ │ 源 IP 目的 IP│
 └──────────┘            │  (给谁看进程的)  │           └────────────┘
                         └────────────────┘
                            ↑ 这一层就是传输层
```

端口号是 **16 位**，取值 $0 \sim 65535$。它是一个**四元组**问题的一半：一条 TCP 连接由「源 IP、源端口、目的 IP、目的端口」四者唯一确定。

> **定义**：**端口号（Port Number）**是传输层用来标识主机上不同应用进程的逻辑编号。IP 地址标识到"主机"，端口号标识到"进程"，两者拼起来才是一台机器上一个具体的通信端点，我们叫它**套接字（Socket）= IP 地址 : 端口号**。

> **易错点**：端口号和 IP 地址层级不同，**不要拿 IP 地址那套"网络号 + 主机号"的思路去套端口号**。端口号是一个 16 位的整体编号，没有网络前缀这一说，它标识的也从来不是"网络"，就是本机上的一个进程入口。

### 复用与分用：把两个方向的事都办了

传输层要同时干两件看起来矛盾的事，这两件事共用一个端口号空间。

> **定义**：**复用（Multiplexing）**指发送方向——一个进程要发数据时，传输层在其数据前**加上本层首部**，然后把多个进程的数据汇合后一起往下交给网络层，等于"多个进程共用一条网络链路"。**分用（Demultiplexing）**指接收方向——数据报上来后，传输层**根据首部的目的端口号**，把数据交给对应的那个进程。

一句话记忆：**往下汇是复用，往上分是分用。**

> **提示**：UDP 是把"复用"和"分用"摆到明面上的——它首部里就明明白白写着源端口和目的端口，谁进来一眼就看得见。TCP 要麻烦一点，因为 TCP 首部前面还要先解决"是哪条连接"的问题，光看端口不够，还得看 IP 地址，四元组一起才定位得到。

### 应用层协议踩在谁的肩膀上

这一条不是传输层内部的，但它年年考，而且考法就是"某某协议底下压的是什么"（2015 年 33 题、2025 年 40 题）。我给你一张底座对照表，背下来能省两三年反复回忆的力气。

| 应用层协议 | 传输层 | 记它的理由 |
| --- | --- | --- |
| FTP（文件传送） | TCP | 文件内容必须一个字节不少 |
| HTTP（超文本传送） | TCP | 网页、图片都要完整 |
| POP3（邮件接收） | TCP | 邮件正文必须完整，端口 110 |
| SMTP（邮件发送） | TCP | 同上 |
| DNS（域名解析） | UDP | 查询报文短小，容得下丢一次重查 |

> **结论**：只要底下是 TCP，那必然"有连接且可靠"——这是 2015 年 33 题的答案，也是一条可以直接拿来用的推理链，**不用算，回顾一下就知道**。反过来，看到 POP3 就该想到 110 端口。

> **易错点**：这一块最爱设的陷阱是"忘了它有把握手"而选了"无连接"。POP3 收邮件要建连接、要说重传保证正文不缺一个字，**这个"有连接且可靠"的判断不用犹豫**。而 DNS 站在 UDP 这边——一次查询就几十个字节，**丢了再查一次比握一次手划算**，这个成本账要能张口就来。

### UDP 和 TCP：一张表把分工说死

| 对比维度 | UDP | TCP |
| --- | --- | --- |
| 连接性 | 无连接 | 面向连接 |
| 是否可靠 | 不可靠，尽力而为 | 可靠交付 |
| 是否有序 | 不保证按序到达 | 保证按序交付 |
| 流量控制 / 拥塞控制 | 都没有 | 都有 |
| 首部开销 | 固定 8 字节 | 远大于 8 字节，长度随选项变化 |
| 典型时延代价 | 1 个 RTT 即可拿到结果 | 需先握手，共 2 个 RTT |

最后一行值得单独说一句。2025 年 39 题给的 RTT 是 8 ms，问从客户发出请求到收到信息为止最短要多久：UDP 不用握手，请求直接出去，**1 个 RTT，8 ms**；TCP 还得先走三次握手，**2 个 RTT，16 ms**。

> **提示**：这里有个特别容易犹豫的点——"TCP 是不是也能 1 个 RTT 拿到结果？"**能，但要求第三次握手把请求捎带出去。** 讲清楚这个前提，答案就锁死在 2 个 RTT 上，不会再晃。

## UDP：8 字节首部里那点事

### UDP 首部的四个字段

UDP 首部定长 **8 字节**，一个字节都不多给。就四个字段：

```text
              UDP 首部（共 8 字节，固定长度）

   0          16         32         48        64
   ┌──────────┬──────────┬──────────┬──────────┐
   │  源端口  │  目的端口 │   长度   │  校验和  │
   │  2 字节  │  2 字节  │  2 字节  │  2 字节  │
   └──────────┴──────────┴──────────┴──────────┘
                        ↑
              长度 = 首部(8) + 数据部分
            （不是只有数据的长度！这一点栽过很多人）
```

- **源端口、目的端口**：各 2 字节，就是上面说的那张"进程标签"。
- **长度**：2 字节，指的是**首部加数据部分的总长度**，不是单纯的数据长度。
- **校验和**：2 字节，是 UDP 的"防错条"。

> **易错点**：**长度字段是"首部 + 数据"，不是只有数据。** 题目问"首部哪些字段会被 NAT 修改"的时候，这条就是答案的分水岭：首部长度是固定的 8 字节，数据原封不动送过来，加起来当然不变。

### 伪首部：校验和真正在保护什么

UDP 校验和最不一样的地方是，它算的时候还要额外加一个**伪首部**。这个东西不真的加在报文里，它只是在**计算校验和的时候临时拼上去**。

```text
   参与 UDP 校验和计算的完整范围：

   ┌──────────────┬──────────────┬──────────┬───────┬──────────────┐
   │   源 IP      │   目的 IP    │ 协议 17  │  UDP  │   数据部分   │
   │  （4 字节）  │  （4 字节）  │ （1 字节）│  长度  │              │
   └──────────────┴──────────────┴──────────┴───────┴──────────────┘
        └──────────── 这四块拼起来就是「伪首部」───────────┘
                                  ↓
              算出 16 位校验和，填进 UDP 首部最后 2 字节
```

> **定义**：**伪首部（Pseudo-header）**是一个只在计算 UDP/TCP 校验和时临时构造的字段块，内容包含**源 IP 地址、目的 IP 地址、协议号、UDP/TCP 长度**。它**不会**作为一个真实的字段被发出去，接收端收到数据时会用自己这一边的源/目的 IP 重新拼出同一个伪首部再验一遍。

> **结论**：伪首部里含着**源 IP 和目的 IP**——这一条是 2025 年 37 题的全部推理起点。**源 IP 一改，校验和必然要跟着改**，因为覆盖范围变了。你以后碰到任何"某某字段变了，它算进校验和里没有"的问题，第一反应都应该是去翻伪首部。

> **提示**：伪首部的作用其实很巧妙：它让传输层**能独立验证数据有没有在中途被送错了地方**。IP 首部里的目标地址如果在中途路由器上被改了，传输层的校验和一变就露馅，接收方直接丢包——**跨层的完整性检查**，这才是设计者的本意。

### 实验题：NAT 到底动了 UDP 首部的哪几个字段

2025 年 37 题给的是一台有 NAT 功能的路由器，主机 H 在私有网络里，要向 Internet 发一个 UDP 报文段，问**路由器在封装转发过程中，UDP 首部可能修改哪些字段**。

先把选项拆开，一个一个过：

| 字段 | 会不会变 | 理由 |
| --- | --- | --- |
| 源端口 | **可能变** | NAPT 会把源端口换成 NAT 路由器上一个对应的端口 |
| 目的端口 | **不变** | 要请求的那个 Internet 上的具体进程没变，NAT 换的是"你是谁"，不是"你要找谁" |
| 长度 | **不变** | 首部固定 8 字节，数据原封不动，加起来当然一样 |
| 校验和 | **一定变** | 伪首部里有源 IP，源 IP 改了，覆盖范围就变了 |

先把 NAT 是干什么的说清楚。H 在**私有网络**里，私有地址在全球范围内**不是唯一的**，不能拿它对外交流，所以必须过 NAT 路由器，**把报文的源 IP 换成全球唯一的公网地址**。这是 NAT 的本职工作，所以**源 IP 一定要变**。

顺着这个，逐项推出上面这张表。答案落在**源端口和校验和**上。

> **定义**：NAT 在实际中有三种类型——**静态 NAT、动态地址 NAT、NAPT（网络地址转换端口）**。前两者只换 IP 地址，**只有 NAPT 会连端口一起换**。题目虽然没提 NAPT，但 NAT 本身包含这个功能，所以源端口号"**可能**"被改。注意题干的用词是"可能"，凡是问"可能"的选项，理由就得是"存在这种模式"，而不是"一定如此"。

> **易错点**：**不要因为题目没提 NAPT 就排除源端口。** 这类"可能"型选项的判定标准是"只要存在一种合法情形使其成立"。而校验和那一项要注意用词差别——校验和是"**一定**变"，因为源 IP 必改，它没有第二种可能。

## TCP 首部：每个字段在考题里扮演什么角色

### 首部格式：一张图背下来

TCP 首部**最少 20 字节**（无选项时），有选项就往上加，最长到 60 字节。

```text
                TCP 首部（固定部分 20 字节，选项可加长）

  0         16         32         48         64
  ┌─────────┬─────────┬─────────┬─────────┐
  │  源端口 │ 目的端口│  序号 SEQ   │  2 + 2
  │  2 字节  │  2 字节 │  4 字节    │  字节
  ├─────────┼─────────┴─────────┬─────┬───┤
  │   确认号 ACK    │ 数据偏移 │保留 |Flags   2+1+1
  │    4 字节       │  4 位    │ 6 位 │ 8 位   字节
  ├─────────┼─────────┬─────────┴─────┴───┤
  │     窗口 rwnd      │      校验和       │   2 + 2
  │     2 字节         │      2 字节       │   字节
  ├─────────┼─────────┬─────────────────────┤
  │   紧急指针 URG    │   选项（0 ~ 40 字节）   │
  │     2 字节         │                     │
  └─────────┴─────────┴─────────────────────┘
```

> **易错点**：**数据偏移的单位是"字节"，不是"比特"。** 它算的是首部占多少个 4 字节的字（word），因为首部是 4 字节对齐的。TCP 首部固定 20 字节 = 5 个字，所以数据偏移最小值是 5，对应 5 × 4 = 20 字节。很多人一看"偏移"就条件反射以为该数比特，一数就错。

### 序号与确认号：先分清这是谁的号

这是 TCP 首部里最容易被绕晕的一对字段，**几乎每年都有人在这里栽跟头**（2025 年 38 题就是拿它当烟雾弹设的）。我把判定规则给你说死。

> **定义**：**序号 SEQ**是**本方自己**发送的数据的字节编号，从一个初始序号 ISN 开始，对**自己发出去的每一个字节**依次加一。**确认号 ACK**是**对方**发过来的数，含义是"**我已经收到你序号在这个号之前的所有字节了，我下一个想收到的字节是这个号**"。

用大白话再钉一遍：

- **SEQ 讲的是"我发到哪儿了"**，是发送方的自述；
- **ACK 讲的是"我收到哪儿了"**，是接收方的反馈。

> **易错点**：**在一个报文段里，SEQ 和 ACK 各自只管对端一个方向。** 你收到一个确认段，看到 `SEQ = 4001`，那是**乙自己的序号**，对**甲的发送窗口毫无影响**；看到 `ACK = 3001`，那才是说"我期待收到你从 3001 开始的数据"。

### 窗口字段

**窗口字段 rwnd，2 字节（无符号）**，是**接收方**把自己的接收缓存大小通告给发送方，说的是"我这儿还能再吃多少"。发送方据此限制自己别把数据一股脑砸过来。

> **提示**：注意 `rwnd` 这个名字里的 `r`——**receiver window，接收方窗口**。它由**接收方**填写、由发送方遵守。谁通告谁，是判断题最爱设的钩子。

### 标志位

8 个标志位里，考研真正反复考的就那么几个，记住它们的**位置和用途**：

- **SYN**（第 0 位）：**同步序号**，用于建立连接。三次握手里第 1、2 段带 SYN。
- **ACK**（第 1 位）：**确认标志**。注意——**它表示"确认号这个字段有效"，本身不代表"这是一条纯确认"。** 第 2 个报文段是 `SYN=1, ACK=1`，SYN 用来建连接，ACK 用来确认对方那个 SYN。
- **FIN**（第 2 位）：**发送方数据发送完毕**，用于释放连接。
- **RST**（第 3 位）：**复位**，连接被异常中止，要求重新建立。
- **URG**（第 4 位）：紧急数据，配合**紧急指针**使用。

> **易错点**：**别把"ACK=1"和"这是确认报文"划等号。** 三次握手的第 2 段里 SYN 和 ACK 是一起置 1 的，ACK=1 只是说"我的确认号字段有意义"，那条报文的主要身份是 SYN。判断报文性质，看**谁在主导**，不要只看标志位里有没有 ACK。

## TCP 的连接管理：三次握手与四次挥手

### 三次握手时序图

```text
        主动方（客户端）                          被动方（服务器）
  ─────────────────────────────────────────────────────────────
  CLOSED
        │  ① SYN=1, seq=x
        ├───────────────────────────────────▶  LISTEN
        │                                       │
        │            ② SYN=1, ACK=1,          │
        ◀───────────────────────────────────┤  seq=y, ack=x+1
  SYN-SENT                                     │
        │                                       SYN-RECEIVED
        │  ③ ACK=1, seq=x+1, ack=y+1          │
        │     （可以捎带请求数据！）             │
        ├───────────────────────────────────▶  ESTABLISHED
  ESTABLISHED                                  ESTABLISHED
              ★ 三次握手完成，连接建立 ★
```

三次握手的三个报文，关键数字都在这里：

- 客户端先出一个自己的初始序号 `x`；
- 服务器回一个**自己的**初始序号 `y`，同时**确认号是 `x+1`**（因为我已经收到你的第 x 号字节了，下一个要 x+1）；
- 客户端再发一个确认，**确认号是 `y+1`**。

> **结论**：**第三次握手的确认号 = 对方的初始序号 + 1**，这个 "+1" 是最容易漏的。序号记的是字节位置，**"收到了 x 及以前的全部"意味着"下一个要 x+1"**，不是"下一个要 x"。

> **提示**：为什么非要三次，两次不行吗？两次握手的问题是**服务器无法确认自己的初始序号是否被客户端收到了**。设想那个 ② 报文在网络中丢失，服务器会一直以为自己连接建好了、在那儿守着，而客户端根本没收到确认、连接并不存在。第三次握手就是让客户端再回一次"我收到了你的 y"，服务器据此确认双向通道都通。**第三次握手的本质是"让服务器也确认一次"。**

### 握手和请求的 RTT 代价

（2025 年 39 题）

```text
   UDP（无连接）：1 个 RTT  = 8 ms
   客户 ──── 请求 ────► 服务器
   客户 ◄─── 信息 ──── 服务器

   TCP（面向连接）：2 个 RTT = 16 ms
   客户 ──► 服务器   SYN
   客户 ◄── 服务器   SYN + ACK             ┐
   客户 ──► 服务器   ACK（捎带请求）       ├─ 第 1 个 RTT
   客户 ◄── 服务器   对应的信息             ┘  ┐
                                             ├─ 第 2 个 RTT
                                             ┘
```

> **结论**：**第三次握手是可以携带请求数据的。** 把请求捎在 ③ 上，等服务器把信息发回来，TCP 才算走完全程，所以是**两倍 RTT，16 ms**。UDP 没握手，**1 个 RTT，8 ms**。

> **提示**：这道题的分水岭在于"**收到信息的那一刻到底是哪一刻**"。如果你脑子里画的是"第三次握手之后服务器才开始干活、然后才发数据"，那就会犹豫 TCP 是不是要 3 个 RTT。**捎带数据这一条落到位，答案就再也不会晃。**

### 四次挥手时序图

```text
        主动关闭方                                  被动关闭方
  ─────────────────────────────────────────────────────────────
  ESTABLISHED
        │  ① FIN=1, seq=u
        ├───────────────────────────────────▶  ESTABLISHED
        │  ② ACK=1, ack=u+1
        ◀───────────────────────────────────┤
  FIN-WAIT-1                                       CLOSE-WAIT
        │  ③ FIN=1, seq=v, ack=u+1               │
        ◀───────────────────────────────────┤
  FIN-WAIT-2                                       LAST-ACK
        │  ④ ACK=1, ack=u+1
        ├───────────────────────────────────▶  CLOSED
  TIME-WAIT
        │      （静默等待 2MSL）
        │  ⑤ 2MSL 到期
  CLOSED
```

把四步连起来读一遍，就明白为什么**是四个报文而不是三个**：

1. 主动方发 FIN 说"我这边数据发完了，要关了"；
2. 被动方立刻回 ACK——**但它这边可能还有数据没发完**，所以不能马上跟一个 FIN，而是先进入 CLOSE-WAIT 状态继续发数据；
3. 等被动方的数据也发完了，它才发自己的 FIN；
4. 主动方回最后一个 ACK，然后进入 **TIME-WAIT**。

> **结论**：**三次握手能合并、两次挥手不能合并，根源在于 TCP 是全双工的。** 收到 FIN 只说明"**对方**没有数据要发了"，不等于"我也没有数据要发"。主动方随时可以确认被动方的 FIN，但它的 FIN 必须等自己的数据也发完才能发——这个时间差是**不可压缩**的，所以必须有 4 个报文。

> **易错点**：**确认号始终只确认对方**，所以被动方 ② 回的是 `ack=u+1`（确认客户端的 FIN），③ 发 FIN 时是 `seq=v`，**其中 v 是它自己的序号**。这个图里 SEQ 和 ACK 又是各管一个方向，别又看成一条线。

### TIME_WAIT 与 2MSL：主动关闭方的专属状态

看上面那张图，**只有主动关闭方才有 TIME-WAIT**。这一格是这一节的重头戏，也是最容易答"它有什么用"的地方。

> **定义**：**TIME_WAIT** 是 TCP 主动关闭方在发出最后一个 ACK 之后进入的状态。它必须**静默等待 2MSL（最长报文段生存时间，Maximum Segment Lifetime）**，等计时结束才彻底进 CLOSED。**MSL 是报文在网络里最多能存活的时间，2MSL 就是它的两倍。**

我给你记两条作用，一条是"防止旧报文复活"，一条是"保证最后的 ACK 能到达"。

**第一条：保证最后那个 ACK 一定能被对方收到。**

万一 ④ 这个 ACK 丢了，被动方那边还停在 LAST-ACK，会一直等。它不会主动重发（FIN 只发一次），所以只能靠**主动方再补一个 FIN**。而主动方重发 FIN 的能力，恰恰来自它此刻正处在 TIME_WAIT——**只要它还在 TIME_WAIT，就随时能重发**。如果它立刻就进 CLOSED、断开心情，那 ④ 一丢，连接就永远吊在半空中，两边都以为对方走了，其实谁也走不了。

> **易错点**：这一条的关键字是"**静默等待**"——TIME_WAIT 期间**不能传数据**，就是要让这个连接安静地躺在那儿当个保险丝。

**第二条：让本次连接里所有乱序的、迟到的旧报文全部消失。**

SEQ 是 32 位的，一个序号空间用完会**回绕**。如果旧连接里还有一个在网络里迷了路的段，它冷不丁在新连接里冒出来，序号可能正好落在新连接的有效窗口内，就被误当成新数据收下了，等于凭空多出一段垃圾。

要避免这个，靠的就是**等**。等 2MSL 的时间，足够长到"任何一个旧报文都不可能还活着"——凡是能在新连接里捣乱的旧报文，2MSL 之前就全被丢光了（或者 TTL 到期了）。**同时也保证了新连接的初始序号不会和旧连接的序号撞车。**

> **结论**：2MSL 里的"2"不是凑数，是"**进**去一个方向、**出**来一个方向"各等一个 MSL。让旧报文**彻底死透**，也让新连接**安全起步**。

### 主动方与被动方的状态对照

上面两张时序图里冒出来一堆状态名，考试常让你"某方此刻处于什么状态"或者"哪些状态是某方独有的"。我把这张对照表给你摊开：

| 时刻 | 主动方（主动打开 / 主动关闭） | 被动方（被动打开 / 被动关闭） |
| --- | --- | --- |
| 连接建立之前 | CLOSED（关闭） | LISTEN（监听） |
| 发出 SYN 之后 | SYN-SENT（同步发送） | LISTEN（监听） |
| 发出 SYN+ACK 之前 | SYN-SENT（同步发送） | SYN-RECEIVED（同步收到） |
| 收到 SYN+ACK 之后 | SYN-SENT（同步发送） | SYN-RECEIVED（同步收到） |
| 发出第三个 ACK 之后 | **ESTABLISHED（已建立）** | **ESTABLISHED（已建立）** |
| 收到对方 FIN 之前 | ESTABLISHED（已建立） | ESTABLISHED（已建立） |
| 自己先发 FIN | FIN-WAIT-1（终止等待 1） | ESTABLISHED（已建立） |
| 收到对方对自己 FIN 的确认 | FIN-WAIT-2（终止等待 2） | CLOSE-WAIT（关闭等待） |
| 收到对方的 FIN | FIN-WAIT-2（终止等待 2） | LAST-ACK（最后确认） |
| 发出最后一个 ACK 之后 | **TIME-WAIT（时间等待）** | **CLOSED（关闭）** |
| 2MSL 到期之后 | CLOSED（关闭） | CLOSED（关闭） |

从这张表里能直接读出三条规律，考试判断题基本可以直接秒判：

> **结论**：**LISTEN、SYN-RECEIVED、CLOSE-WAIT、LAST-ACK 这四个状态是"被动方专属"**——**只要对方没有主动，就是这几个状态**。反过来，**SYN-SENT、FIN-WAIT-1、FIN-WAIT-2、TIME-WAIT 是"主动方专属"**。

> **结论**：**TIME-WAIT 和 CLOSE-WAIT 两个名字长得像，性质完全相反，千万别混。** **CLOSE-WAIT 在被动方**，它表示"对方的 FIN 我收到了，但我自己这边还有数据要发"，是个**活的、还要接着干活**的状态，停留时间长说明被动方拖着不关闭；**TIME-WAIT 在主动方**，它表示"我这边彻底结束了，只是在等保险丝生效"，是个**静的、什么都不干**的状态。

> **易错点**：最容易被设的坑是"**被动关闭方有没有 TIME-WAIT**"。答案是**没有**。被动方发完最后的 ACK 就直接 CLOSED 了，它不用等 2MSL——因为它**不是**那个发 FIN 的人，它不用担心"最后那个 ACK 丢了自己发不出去"。这个不对称是连接管理里最好用的一条判定规则。

## 可靠传输：序号、确认、重传、流量、拥塞

这一节要把五件被混在一起的事拆开。408 特别爱出"下列关于 TCP 的叙述，错误的是"这种题，而选项往往就是拿这五样互相串台：**说重传是流量控制、说确认等于流量控制窗口**。所以必须先把边界划清。

### 序号与确认：可靠性的地基

TCP 之所以可靠，底子就两块：**给数据编号（序号）** + **让对方告诉我收到哪了（确认）**。

- **序号**给每一个字节编号。哪怕中间丢了一段，接收方也能靠序号**把洞指出来**——"我这里少了一截"，而不是稀里糊涂地把后面全收下。
- **确认**是接收方对序号空间的**累积确认**。`ACK = 3001` 的意思是"3001 之前的我全收齐了"。

> **结论**：TCP 用的是**累积确认**——一个 ACK 覆盖了它序号之前的所有字节。所以只要某个 ACK 回来了，**它之前的所有段默认都已正确到达**，重传只需要从缺口处开始，不必一 acknowledgment 一 acknowledgment 地对账。

> **易错点**：注意接收方报一个 ACK **不代表这一段本身被确认了**。2025 年 38 题里，`ACK = 3001` 说明"2001-3000 那段已被确认，3001-4000 那段**还没**收到确认"。**ACK 号本身是"下一个想要的号"，被它跨过去的那一段才是已确认的**——把这条读反，窗口就整体错一格。

### 重传：可靠性真正落地的那一步

光有序号和确认还不够，**丢了怎么办？** 三条路：

1. **超时重传**：发出一个段之后启动重传计时器，超时还没等到确认，就重发；
2. **快速重传**：连续收到**三个重复确认**，不等计时器超时就立刻重传——因为三个重复 ACK 说明后面至少三个段都到了，**只可能是中间那一个丢了**；
3. **选择重传**：只重传真正丢的那一段。

> **提示**：快速重传的判据是"**收到 3 个重复的 ACK**"，这 3 个重复 ACK 是**对后面连续到达的段的确认**，它唯一合理的解释就是缺口在它们前面。**收到重复 ACK 说明后续数据到了、说明网络双向都通**，所以可以不等超时直接重传。超时重传则应对的是"整条链路都哑了"这种更严重的情况。

### 流量控制与拥塞控制：最容易串台的一对

这两件事的目标不同，**是考试最爱设的两个陷阱**。

> **定义**：**流量控制（Flow Control）**是对**接收方**的保护。接收方把接收缓存还剩多大（`rwnd`）通告出去，发送方据此限制自己发多快——**慢了就少发**。**拥塞控制（Congestion Control）**是对**网络**的保护。发送方自己根据网络状况推出一个窗口（`cwnd`），网络差了就收窄——**没人告诉你该收多窄，得自己判断**。

| 对比项 | 流量控制 | 拥塞控制 |
| --- | --- | --- |
| 保护谁 | 接收方 | 网络（中间的路由器、链路） |
| 窗口叫 | 接收窗口 `rwnd` | 拥塞窗口 `cwnd` |
| 谁决定 | **接收方**通告，发送方遵守 | **发送方**自己根据拥塞状况推算 |
| 触发原因 | 接收方缓存不够用，**来不及收** | 链路/路由器队列溢出，**中间堵了** |
| 收回的时机 | 接收方把数据读走，窗口就放大 | 拥塞缓解，窗口才缓慢扩大 |
| 慢开始阶段 | 不参与 | 主导 |

> **结论**：**一句话区分：流量控制是"对端说不行"，拥塞控制是"我自己觉得不行"。** 一个是别人告诉你的，一个是你自己判断的。这条判据放在任何判断题里都不会错。

> **易错点**：不要以为"接收窗口大"就一定能发得多。**发送方实际能发多少，是两个窗口取小**——见下一节。另外，**"重传"和"拥塞控制"是两回事**：超时或快速重传**会触发**拥塞窗口收缩（这是拥塞控制对"网络出事"的反应），但重传本身是可靠性的手段，不是拥塞控制。

### 慢开始：一格一格涨，不是瞬间翻倍

**慢开始**和**拥塞避免**的切换点，是一道名叫**慢开始门限（拥塞阈值）**的坎。

> **定义**：**慢开始门限**，就是拥塞窗口长到这个值时，**从慢开始算法切到拥塞避免算法**。

两个阶段的脾气完全相反：

- **慢开始阶段**：**每收到一个确认，拥塞窗口加 1 个 MSS**。于是一轮 RTT 下来窗口"翻倍"——但**它不是一瞬间翻的**。
- **拥塞避免阶段**：**每收到一个确认，拥塞窗口只加 $1/\text{cwnd}$ 个 MSS**（按字节算的 MSS）。从整体上看，**每个 RTT 窗口只加 1 个 MSS**，增长非常慢。2015 年那道题的门限是 32 KB，一旦到 32，窗口就变成这个不紧不慢的爬法。

> **易错点**：**"慢开始一个 RTT 翻倍"这句话是个陷阱。** 它翻倍的条件是"**收到这一轮全部的确认**"。如果只收到其中一个确认，窗口只加了 1，而不是加了一半、更不是直接翻倍。**慢开始是按"确认个数"加的，不是按"轮次"加的**——这个细节直接决定了下一节那道题的答案。

## 发送窗口的计算

### 发送窗口 = min(cwnd, rwnd)

（2015 年 39 题、2025 年 38 题都考这一个式子）

> **结论**：**发送窗口 = min(拥塞窗口 cwnd, 接收窗口 rwnd)。** 这是一个**取小**，不是相加，不是任取其一。

为什么是取小？因为两个限制**同时成立**：网络说"你最多能发 cwnd"、对端说"我最多能收 rwnd"，**你只能取二者中更严的那个**，否则要不就是把网络塞爆，要不就是把对端缓存撑爆。

> **易错点**：**2015 年那道题之所以出成经典题，就是因为它把两个窗口做成了"一升一降"**。$cwnd$ 在慢开始阶段一路涨，而 $rwnd$ 因为对端**"收到的数据全部存入缓存不被取走"**而一路掉。所以**不能对同一个 RTT 只看一边，也不能拿 RTT 结束时的 $cwnd$ 去和 RTT 开始时的 $rwnd$ 配对**——**每轮都得重新取一次小值。**

### 一格一格推：慢开始全程的窗口表

（2015 年 39 题的完整推演，我按 RTT 摆正）

条件：初始慢开始门限 **32 KB**，最大段长 **1 KB**，对端接收缓存 **16 KB**，忽略传输时延，全程无超时。

> **注意一个细节**：表里 `cwnd` 是"**这一轮确认全部到达之后**"的值，`rwnd` 是"**这一轮数据全部到达之后**"的剩余值，而真正决定发送窗口的，是**这一轮末尾二者取小**。

| 第几个 RTT | 这一轮发出 | 乙缓存剩余 `rwnd` | 确认后 `cwnd` | 本轮结束后实际发送窗口 |
| --- | --- | --- | --- | --- |
| 1 | 1 KB | 15 KB | 2 | 2 KB |
| 2 | 2 KB | 13 KB | 4 | 4 KB |
| 3 | 4 KB | 9 KB | 8 | 8 KB |
| 4 | 8 KB | 1 KB | 16 | **1 KB** |

一段一段读：

- **第 1 个 RTT**：初始窗口就是 1 个 MSS，发出 1 KB，缓存剩 15 KB；收到确认后 $cwnd = 2$。
- **第 2 个 RTT**：窗口 2 KB 全发出去，缓存剩 13 KB；两个段都确认后 $cwnd = 4$。
- **第 3 个 RTT**：发 4 KB，缓存剩 9 KB；四段确认后 $cwnd = 8$。此刻 $cwnd = 8$、$rwnd = 9$，取小的，还是 **8**。**注意——这时才只经历了三个 RTT。**
- **第 4 个 RTT**：连发 8 个段、8 KB 数据全部到达，缓存只剩 **1 KB**；八段确认后 $cwnd$ 涨到 **16**。可**下一轮真正决定发送窗口时**，$min(16, 1) = 1$。

所以经过四个 RTT，甲的发送窗口是 **1 KB**，不是 16 KB。

> **结论**：这道题 $cwnd$ 最大只涨到 16 MSS，**根本没摸到 32 KB 那道慢开始门限**，所以全程都还待在慢开始阶段，一次拥塞避免都没进入。**如果只盯着 $cwnd$ 的 16 就作答，说明取小这一步整个漏掉了。**

> **易错点**：这道题"陷阱全在取小那一步"——$cwnd$ 一路涨、$rwnd$ 一路掉，**必须时时刻刻记住取二者较小值**，不能对同一个 RTT 干看一边的数字。这是 2015 年第 39 题选 A 而不是其他选项的全部原因。

### 收到一个确认之后还能再发几段

（2025 年 38 题，这是这一类题里最值得反复练的一道）

条件：甲向乙发 TCP，$T_0$ 时**慢开始门限 = 8**、**$cwnd$ = 2**、发送窗口也是 2，最长段长 **1000 字节**，甲始终以最大段长发送。甲发出的两段分别是**序号 2001~3000** 和 **3001~4000**。$T_1$ 时收到一个确认段，内容是 `SEQ = 4001`、`ACK = 3001`、`RWND = 4`。问：**在收到新确认之前，还能再发几个段？**

先把 $T_1$ 之前发生了什么理清：两段各占 1000 字节发出去，$T_1$ 之前收到的确认是关于 2001 的。那么 $T_1$ 收到的这个确认段里：

- **`SEQ = 4001`**——这是**乙发过来的**、**乙自己的**序号，**对甲的窗口完全不受影响**，是干扰项；
- **`ACK = 3001`**——这代表**乙期望接收来自甲 3001 开始的数据**，说明甲那两段里乙只收到了 2001 开头的那一段，**3001 那段还没确认**；
- **`RWND = 4`**——乙说"我还能收 4 个段"。

窗口因此**向后滑动到 3001 开头**。

现在算 `cwnd`。当前还没到门限 8，所以走**慢开始**：

> **易错点**：**虽然慢开始是"一个 RTT 窗口翻倍"，但它并不是一下子从 2 蹦到 4。** 慢开始是**每收到一个确认加 1**。甲在 $T_1$ 之前发了 2 段，现在**只收到了 1 个确认**（关于 2001 那段），所以此刻 $cwnd = 2 + 1 = \mathbf{3}$，**不是 4**。

再和接收窗口取小：$min(3, 4) = 3$，所以此刻的发送窗口是 3 个段。

```text
  T1 之前已经发出：   [ 2001-3000 ]   [ 3001-4000 ]
  T1 收到 ACK = 3001，rwnd = 4
      → 2001-3000 已被确认，窗口起点滑到 3001
      → 3001-4000 还没收到确认，它仍然占着发送窗口的位置
      → 发送窗口 = min(cwnd, rwnd) = min(3, 4) = 3 个段

  T1 之后的发送窗口：起点 3001，共 3 个段

     ┌───────────────┬───────────────┬───────────────┐
     │   3001-4000   │   4001-5000   │   5001-6000   │
     │ 已发出·待确认 │    还没发出    │    还没发出    │
     │  ← 占着窗口   │   ← 还能再发   │   ← 还能再发   │
     └───────────────┴───────────────┴───────────────┘
```

**窗口会扩大，但已经发出、还没收到确认的那些段仍然留在窗口里、依然占着位置。** 而我们能发的，是那些**还没被占用的空间**——也就是 **4001 开头和 5001 开头的这两段**，答案 **2 个**。

> **结论**：这类题的固定套路就三步：**① 读 `ACK` 号定窗口起点**（被它跨过去的是已确认的）；**② 用"收到几个确认"定 `cwnd`**（慢开始阶段加确认个数，不是翻倍）；**③ `min(cwnd, rwnd)` 定窗口大小；再数窗口里还空着几个位置**。四问里只要有一问搞错，答案就整体偏移一格。

> **易错点**：最容易错的是第 ② 步想成"我的窗口已经更新到 4 了"或者"接收窗口都告诉我 4 了，那就把剩下的 3 个都发出去"。**这恰恰是错的**——$rwnd = 4$ 是**乙的**接收能力，**甲当前受制的是自己的 $cwnd = 3$**，而 3001-4000 那段还没确认，它**还占着一个位置**。至于 `SEQ = 4001` 和 `ACK = 3001` 这两个字段，**一个不看一个必看**。

上面那张图就是最朴素的样子，我再把推进规则抽出来：

```text
     │ 3001-4000  │ 4001-5000         │              │
     └────────────┴───────────────────┴──────────────┘
                              ↑左边界继续右移
```

三条规则，说完滑动窗口就通了：

> **结论**：**滑动窗口的"滑"体现在左右边界同步右移**。左边界由**累积确认**推动（收到 `ACK = x` 就滑到 $x$），右边界 = 左边界 + 发送窗口大小（`min(cwnd, rwnd)`）。窗口**不能缩**，只能往右平移。

> **结论**：**左边界滑动 = 已有数据被确认；右边界滑动 = 窗口规模变大。** 这两件事**可以分开发生**。2025 年 38 题就是"左边界移了一格、右边界因为 `cwnd` 从 2 涨到 3 而移了一格"——**注意那第 3 段（3001-4000）在它被确认之前，是不能发的**。

> **提示**：**为什么要"滑动"而不是"一次全发完再统一确认"？** 因为链路在**传播的时候是空转的**——发完一个段要等一个 RTT 才能拿到确认，这段时间链路白瞎了。**窗口的意义就是让"这个段在等确认"的空转时间里，把后续的段先塞进去。** 窗口越大，空转被摊得越薄，链路利用率才上得去。这个道理接着往下就是传输效率。

## 传输效率与窗口的账

### 首部开销：有效载荷占比

先算最朴素的一笔账：一条报文里，真正属于用户数据的部分占多少。

$$\text{有效载荷占比} = \frac{\text{数据长度}}{\text{首部长度} + \text{数据长度}}$$

代进两个常考的首部：

- **UDP 首部固定 8 字节**。发 $L$ 字节数据，有效载荷占比 $= \dfrac{L}{8 + L}$。
- **TCP 首部最少 20 字节**。发一个 MSS 大小的段，有效载荷占比 $=\dfrac{\text{MSS}}{20 + \text{MSS}}$。

> **提示**：拿 **MSS = 1000 字节** 试算一下——$1000 / (20 + 1000) \approx 98\%$。**同一个 1000 字节，挂在 UDP 上占比接近 99.2%，挂在 TCP 上掉到 98%。** 这就是"TCP 首部远大于 8 字节、长度还随选项变化"（前面那张对照表最后几行）在计算上的具体代价：**段越小、段发得越碎，首部吃掉的比例越高**。

> **易错点**：计算时**单位要统一**。长度都给的是"字节"就直接算；如果给的速率是 bit/s、数据量是字节，**必须先乘 8 换算**。这个坑我们下面算时延的时候天天见。

### 链路的账：时延构成与利用率

先把一条链路上的时间拆干净，这笔账和上面那道 2015 年第 35 题是同一笔：

```text
   发送方                                            接收方
     │                                                  │
     │◄── Td：把一个帧推上链路（帧长/速率）──►│          │
     │                                     │          │
     │        ◄──── Tprop ────►           │          │
     │            （数据走出去）              │          │
     │                     ◄──── Tprop ────►│          │
     │                          （确认走回来）  │          │
     │                                     ▼          │

  停等协议的一个发送周期：  Td + Tack + 2*Tprop
  滑动窗口的一个发送周期：  Td + 2*Tprop   （窗口往分子上乘）
```

> **结论**：**分母里那一项 $T_D + 2T_{prop}$ 是不随窗口变动的**——不管你一次发几帧，一个"发送周期"总是这么多时间。**窗口大小 $N$ 是往分子上乘的。** 这句话是所有这类计算题的钥匙。

$$U = \frac{N \cdot T_D}{T_D + T_{ACK} + 2 T_{prop}}$$

拿 2015 年 35 题的数走一遍（那道是数据链路层，但账是同一笔，一通百通）：帧长 1000 字节、速率 128 kbit/s、传播时延 250 ms、忽略确认帧开销。

$$T_D = \frac{1000 \times 8}{128 \times 10^3} = \frac{1}{16}\ \text{s} = 62.5\ \text{ms}$$

$$0.8 = \frac{N \times 62.5}{62.5 + 500} \quad\Rightarrow\quad N \ge \frac{0.8 \times 562.5}{62.5} = 7.2$$

窗口大小取整 $N = 8$。读图时看那段空转：**数据走出去 250 ms、确认走回来 250 ms，这 500 ms 链路是空转的**；窗口越大，这段空转被摊得越薄，利用率才上得去。

> **提示**：**"链路在等待时是空转的"这句话你一定要有体感。** 传输效率题本质上问的就是一句话——**这条链路到底有多大比例的时间在真正传数据？** 分子是真正在传数据的时间，分母是整个周期。所有优化手段（窗口、捎带确认）本质上都是在**填那两段 $T_{prop}$ 的空**。

### 从利用率式子里直接读出的结论

$$N \ge \frac{U\,(T_D + 2T_{prop})}{T_D}$$

把式子拉直成另一种说法——**要装满这条链路，窗口至少要能塞下"链路里同时在飞的那一整个往返"**：

$$\text{链路中在飞的数据量} = \text{带宽} \times \text{往返时延}$$

这个量在传输层叫**带宽时延积**。

> **结论**：**窗口如果小于带宽时延积，这条链路就永远填不满。** 这是"为什么 TCP 的接收窗口不能太小"的根本答案：窗口小了，发送方一确认完就得停下来等，而这段时间链路是空的。**窗口必须大到能覆盖一个完整往返里能传的数据量。**

### 窗口大小与序号位数

接着这个问题往下追一层：窗口要开到这么大，**序号得编多少位**？

```text
   序号位数 n  与  窗口大小的关系

   后退 N 帧 GBN ：  W_T ≤ 2^n - 1     （留一个位给"全确认"的特殊情形）
   选择重传 SR   ：  W_T ≤ 2^n       （窗口可以开满整个序号空间的一半以上）
```

> **易错点**：这一块有**两个都长得像 N 的东西**，务必分开：**小写 $n$ 是序号的比特位数**（GBN 里 $W_T \le 2^n - 1$，SR 里 $W_T \le 2^n$）；**大写 $N$ 是窗口大小**。习惯上大家都用 $N$ 来表示，很容易混，但在计算题里它们**必须分开算**。

> **结论**：把窗口的单位和序号的位数**当成两个数**，这是最常见的丢分点。算出来 $N \ge 7.2$ 时得到的是**窗口大小 8**，而最终答案问的是**序号 4 位**。**别去选那个等于 8 的选项。**

### TCP 里的窗口为什么能开那么大

GBN 和 SR 那边，窗口大小被序号位数死死卡着（4 位序号最多也就撑到 15、16）；**TCP 这边却能开到几万字节**，靠的不是序号多，而是**字节序号**。

> **结论**：**TCP 的序号是对每一个字节编号的**，不是对每一个段编号。所以一个 32 位的序号空间能表示 $2^{32}$ 字节，这个天文数字完全撑得住一个几十 KB 的窗口。而滑动窗口协议那边的窗口单位是"帧数"，所以窗口大小和位数是硬绑死的。**这就是为什么"数据链路层的窗口"和"TCP 的窗口"不能拿同一个公式去算。**

## 把这一块串成一条线

最后我帮你把散落的点收一下，因为考试最爱出的就是"下面这些说法里哪个错"这种横跨多个点的题：

1. **定位**：IP 找主机，**端口找进程**；复用往上汇，分用往下分（分用时**看的是目的端口**）。
2. **协议**：UDP 无连接、8 字节首部、校验和**覆盖伪首部**（含源/目的 IP）；TCP 面向连接、首部最少 20 字节、**三次握手 + 四次挥手**。
3. **握手**：三次的意义是**让双方都确认**；`确认号 = 对方序号 + 1`；第三次握手**可以捎带请求**，这是 TCP 要 2 个 RTT 而 UDP 只要 1 个的原因。
4. **挥手**：四次不可合并，因为**全双工、我的数据没发完就不能发我的 FIN**；**TIME_WAIT 只在主动关闭方**，作用是**等 2MSL**——一个保 ACK 能重发、一个让旧报文死透。
5. **可靠**：序号编号 + 累积确认 + 超时/快速重传，三件套。
6. **两个窗口**：**流量控制护接收方（`rwnd`，对端通告）**，**拥塞控制护网络（`cwnd`，自己判断）**；**发送窗口 = `min(cwnd, rwnd)`**，取小不是相加。
7. **慢开始**：每收一个确认加 1 个 MSS，一个 RTT 才翻倍；**到门限转拥塞避免，每 RTT 只加 1 个 MSS**。
8. **效率**：**分子乘窗口、分母不动**；窗口至少要盖住一个**带宽时延积**；首部开销按 $L/(首部+L)$ 算，**单位先统一**。

> **结论**：这八条里，**第 6 条的取小**和**第 7 条的"加确认个数而不是翻倍"**，是 2015 年 39 题和 2025 年 38 题这两道经典题的全部命门。**这两处想通了，传输层这一块你就没有不会做的题。**

> **易错点**：最后再强调一遍那个贯穿全块的判据——**看到 SEQ 想到"对方的发"，看到 ACK 想到"对方的收"**。两条线上四个字段只要这么一分，`ACK = 3001` 到底确认了哪一段、`SEQ = 4001` 为什么无关，答案立刻就出来了。**考场上乱，十有八九是这两个字段读反了。**
