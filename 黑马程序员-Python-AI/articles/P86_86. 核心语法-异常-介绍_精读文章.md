# Python 异常的定义、作用与捕获语法

教务管理系统前面的功能都做完了，添加、修改、删除、查询我们也逐个测过，全部正常。可这里有个问题：我们测的全是正常情况，异常情况一条都没试过。而做程序测试，各种情况都要尽量覆盖到，只有这样，才能在开发阶段就把程序里可能出现的问题解决掉，程序的健壮性与逻辑正确性才有保证。

那就不妨再运行一次这个系统，专门试试异常输入。

先按正常流程走一遍：在菜单里输入 `1` 进入添加学生，姓名输入「王琳」，语文成绩 `90`，数学成绩 `98`，英语成绩 `95`，回车之后添加学生信息成功。这一轮没有任何问题。

现在换一个输入。还是输入 `1` 添加学生，姓名填「王麻子」，语文成绩 `98`，数学成绩填 `95.555`，回车。程序直接报错了，控制台刷出一段报错信息，而且整个系统随之退出，进程终止运行。

> **结论**：一个成绩输入得不规范，就让整个系统退出，这个体验显然不能接受。

那这里就有一个必须回答的问题：用户在系统里输入的数据有问题时，到底应该直接把程序崩掉，还是应该明确告诉他问题出在哪、让他重新输入？显然应该是后者——提示出对应的信息，让用户重新输入，而不是终止程序运行。

测试做到这一步就能看出，我们当前写的程序代码逻辑还不够完善。要解决这个问题，就得学习 Python 里的异常，以及异常的处理方案——这也是 Python 核心语法的最后一部分。

## 异常的定义

提到异常，写代码的人都不陌生，甚至有的同学相当拿手，因为写代码的过程中总会遇到各种各样的异常。

> **定义**：异常（Exception）也称为 Bug，指的就是程序在运行过程当中所出现的错误；这个错误会中断程序正常的执行流程，一旦出现错误，程序就终止运行。

所以平时说「程序出 Bug 了」，说的就是程序出异常了、程序出错了。

## 异常的作用

走到这里，很容易生出一种想法：异常对程序开发好像没什么好处，只会拖慢我们写代码的速度，要是没有它反而清净。

我们可以反过来假想一下。假设 Python 里根本没有异常，那么代码运行时是不是也不会报错？可再往下想一步：如果程序运行永远不会报错，那我们的逻辑即使写错了、数据处理即使出错了，也不会有任何提示，最终数据处理和程序运行的结果肯定是混乱的。

所以异常的作用其实很明确，有两点。

第一，它可以保证数据以及逻辑的正确性，避免程序在执行过程中出现混乱。输入的数据、我们写的逻辑一旦有问题，程序会直接报错，这个报错就是在提示我们：这块逻辑有问题，去修正它。

第二，通过异常，我们在开发阶段能够尽可能多地发现程序当中的问题，并把这些问题尽早解决掉，从而保证程序的正常执行。

> **结论**：异常并不是一个坏东西，它是我们编写健壮程序的重要手段和工具。

当然，前提是我们得正确地处理异常。

## 常见的异常类型

Python 为我们提供了各种各样的异常类型，不同类型的异常对应不同性质的错误，我们据此就能定位程序当中的问题。

| 异常类型 | 触发场景 |
| --- | --- |
| `NameError` | 变量名或函数名在定义、调用时出现问题 |
| `TypeError` | 数据的类型出现问题 |
| `IndexError` | 索引访问出现问题 |
| `KeyError` | 键（Key）出现问题 |
| `ValueError` | 值出现问题，比如运算的结果值不合法 |

能按类型区分错误，我们就能按类型给出处理方案，这正是下面要展开的内容。

## 异常的两种处理方案

程序当中出现异常，一般有两种处理方案。

### 不做处理

所谓不做处理，就是写代码时根本不考虑异常。程序运行过程当中一旦出现异常、出现一个 Bug，程序就中断执行。

我们之前写的 Python 代码都没有做任何异常处理，所以刚才添加学生时一旦出现异常——报出来的正是 `ValueError`——整个程序就直接中断了。

这种方案正常运行还好，一旦运行中出现 Bug 就会导致整个程序中断。学习阶段为了快速实现一些功能，这么做可以接受；但在项目开发当中，强烈不建议这么做。

### 捕获异常

第二种方案是出现异常之后把异常捕获住，抓住它，然后按照我们自己的处理方式去处理，处理完之后让程序正常继续往下运行。

> **定义**：捕获异常相当于在编写程序的时候就做好一份预案；程序一旦出现异常，就按预案里的逻辑来处理，处理完继续往下运行。

这样就能避免程序因为一个 Bug 而中断整个执行流程。这也就是我们给教务管理系统要补上的东西——一个 Plan B、一个 B 计划。

## 捕获异常的语法

要在代码里捕获异常，用到的关键字是 `try`。

`try` 代表我要进行异常捕获了。`try` 代码块里写的就是可能会出异常的业务代码——所有可能出异常的业务代码都可以放进这个代码块。这些代码运行时会从上往下逐行执行；一旦某一行在执行过程中出现异常，它下面那些代码就不再运行了，异常会被下面定义的 `except` 代码块捕获到。

`except` 代码块就是用来捕获异常的。它后面方括号里的内容可以写，也可以不写。

- 不写：代表捕获所有类型的异常，所有类型的异常都捕获到，然后按 `except` 里的预案逻辑执行；
- 写了：代表只捕获指定类型的异常。注意这里写的是**异常的类型**。

如果我们还想拿到这个异常的信息，可以在 `as` 之后跟上异常变量名，通过这个变量名就能取到异常当中的信息。

最后还有一块可选结构 `finally`，翻译过来就是「最终」的意思。

> **定义**：`finally` 代码块中的代码，无论程序运行过程中是正常执行还是出现异常，最终都会运行。

`try ... except ... finally ...` 这套结构的分工可以这样记：

| 结构 | 作用 |
| --- | --- |
| `try` | 放入可能出现异常的业务代码 |
| `except` | 声明捕获什么类型的异常，以及捕获之后做什么 |
| `as e` | 给异常起个别名，通过它读取异常信息 |
| `finally` | 无论正常还是异常都执行，通常做资源释放、环境清理等扫尾工作 |

`finally` 是可选的，需要就加，不需要就不写。

## 捕获语法的执行流程

先看一段样例代码，体会这套结构是怎么跑的。

```python
try:
    print("---------------------------")
    print(my_name)
except NameError as e:
    print("程序运行报错了，错误信息是：", e)
finally:
    print("释放资源")
```

- `try` 里第一句输出一条分割线，这行没问题；
- 第二句输出 `my_name`，而 `my_name` 这个变量在前面并没有定义。变量没定义就直接用，程序到这一行就会报错；
- 一旦在这一行报错，它下面的代码就不再运行，异常被 `except` 捕获——因为报出来的错刚好就是 `NameError` 这个类型，而 `except` 要捕获的正是 `NameError`；
- 捕获到之后按里面的逻辑处理，也就是提示用户程序运行出错了、错误信息是什么；
- 最后执行 `finally` 当中的代码：无论正常执行还是出现异常，它都会运行。

这套结构里，`except` 只有在类型匹配时才会接住异常；匹配不上会怎么样，后面的实测会给出答案。

## 案例：捕获 NameError

关掉案例文件，在第二章的目录下新建一个文件，专门演示异常处理。

先写业务代码，不做任何处理：

```python
print("---------------------------")
print(my_name)
print("---------------------------")
```

直接运行，这一块就报错了，告诉我们 `my_name` 这个名字不存在、未定义。报出来的异常类型就是 `NameError`。

接下来做异常捕获：给可能出现异常的代码加上 `try`，选中这几行按 `Tab` 加上缩进；然后在 `try` 下面、与 `try` 同级的位置定义 `except`。要报的错是 `NameError`，所以 `except` 后面直接写 `NameError`。

```python
try:
    print("---------------------------")
    print(my_name)
    print("---------------------------")
except NameError:
    print("程序运行出错了，请联系管理员！")
```

这里为了看清运行轨迹，在关键位置打一个断点，右键 Debug 运行。首先输出这串分割线，这句代码执行没问题；紧接着要输出 `my_name`，但这个变量不存在；一旦不存在，下面那句输出分割线的代码就不会再运行；接着走到 `except` 这一行——它是异常捕获的代码，会开始运行。抛出来的正好是 `NameError` 类型的异常，所以被捕获到，并输出这句话：程序运行出错了，请联系管理员。这走的就是我们的 Plan B。

如果还想拿到具体的错误信息，在 `except` 后面加上关键字 `as`，给异常起个别名，比如 `e`，然后把它输出出来：

```python
try:
    print("---------------------------")
    print(my_name)
    print("---------------------------")
except NameError as e:
    print("程序运行出错了，异常信息是：", e)
```

再运行一次，输出会告诉我们异常信息是 `my_name` 这个变量没定义。通过 `as` 起的这个别名，我们就拿到了这块的错误信息。

## 捕获异常的匹配机制

上面演示的是变量名不存在、未定义。那换一种异常，`NameError` 还能不能捕获到？试一下。

把代码注释掉，重新写一句：我想看一下 `1 / 0` 的结果是多少。先别急着算——数学里 0 是不能做除数的。那么问题来了：在 Python 里，`1` 能不能被 `0` 除？

```python
try:
    print("---------------------------")
    print(1 / 0)
    print("---------------------------")
except NameError:
    print("程序运行出错了，请联系管理员！")
```

运行之后报错了，但这一次没有输出「程序运行出错了，请联系管理员」这句提示，只输出了最开始的那条分割线，然后走到报错的那句就停了，下面的代码没有运行。

原因在于类型不匹配：`1 / 0` 报出来的错并不是 `NameError`，它叫 `ZeroDivisionError`——除 0 的异常。

> **易错点**：抛出异常之后，并不是见到 `except` 就一定被捕获到。它会拿抛出来的异常去和 `except` 声明的异常类型做匹配，类型不匹配就捕获不了。

匹配是一个自上而下逐级比较的过程：

```text
                抛出异常
                   |
                   v
        +----------------------+
        | except 1: 类型匹配?  |-- 不匹配 --> 继续往下
        +----------------------+
                   | 匹配
                   v
        +----------------------+
        | 执行该 except 块内的  |
        | 异常处理逻辑          |
        +----------------------+
                   |
        (全都匹配不上 -> 异常直接抛出，程序报错)
```

读图说明：异常从抛出点往上交给 `except` 列表，逐个比较类型，命中第一个匹配的 `except` 就执行它内部的逻辑；整张列表都比较完仍未命中，异常就不再被处理，直接抛出去、程序报错。

既然类型要对得上，那就再加一个 `except`，专门捕获 `ZeroDivisionError`，并用 `as e` 拿到它的信息：

```python
try:
    print("---------------------------")
    print(1 / 0)
    print("---------------------------")
except NameError as e:
    print("名字不存在，请检查变量或函数的名字，异常信息是：", e)
except ZeroDivisionError as e:
    print("0不能做被除数，异常信息是：", e)
```

这样针对不同类型的异常就有了不同的处理方案，错误提示也能写得更精准：捕获到 `NameError`，提示名字不存在、请检查变量或函数的名字；捕获到 `ZeroDivisionError`，提示 0 不能做被除数。两种情况都把异常信息一并输出。

再打上断点、用 Debug 一步一步跟踪：往下走一步，`1 / 0` 报错，程序自上而下匹配这些 `except`——抛出来的异常是 `NameError` 吗？不是；接着匹配是不是 `ZeroDivisionError`？是的，于是执行这个代码块里的逻辑，提示 0 不能做被除数，异常信息告诉我们出现了除 0 的问题。

> **结论**：异常处理时会从上往下一级一级地匹配；匹配到了就执行相应代码块里的逻辑，最终都没匹配到就直接报错。

## 案例：捕获 IndexError

再换一个场景。写一个字符串 `"abc"`，去取它索引为 `10` 位置的元素。

```python
print("abc"[10])
```

`"abc"` 的长度总共才 3，最大索引是 2，取第 10 个位置的元素必然报错。直接运行，报出来的错误是 `IndexError`——`Index` 是索引的意思，`Error` 就是错误的意思，连起来就是索引错误；后面还提示这个字符串的索引超出了对应的范围，上面则告诉我们哪一句代码出错了：第 14 行的 `print("abc"[10])`。

之所以会走到报错这一步，还是因为自上而下匹配：没匹配到，这个异常对我们的代码来说就处理不了，直接抛出来展示错误信息。

要捕获 `IndexError` 也是同样的办法，再补一个 `except`，把类型换成 `IndexError`，并在里面提示索引错误：

```python
try:
    print("abc"[10])
except NameError as e:
    print("名字不存在，请检查变量或函数的名字，异常信息是：", e)
except ZeroDivisionError as e:
    print("0不能做被除数，异常信息是：", e)
except IndexError as e:
    print("索引错误，异常信息是：", e)
```

再次 Debug 运行跟踪一遍：程序出错后自上而下匹配——是 `NameError` 吗？不是；是 `ZeroDivisionError` 吗？不是；是 `IndexError` 吗？是的，于是进入这段异常处理逻辑，输出对应的错误信息。

## 捕获所有异常

走到这里自然会冒出一个想法：是不是以后写代码，所有可能出现的错误都要这样一种类型一种类型地捕获、在下面一类一类地处理？其实并不需要。

再模拟一个错误：输出字符串 `"abc"` 当中的一个属性，比如 `hello` 这个属性。这个属性并不存在，运行之后又报错了，这次是 `AttributeError`。

```python
print("abc".hello)
```

难道还要再补一个捕获 `AttributeError` 的代码块？这么做当然可以，但其实我们可以用**一种异常类型把所有异常都捕获下来**。

做法是去看一下这些异常类型的源码：按住 `Ctrl` 点进 `IndexError` 或 `NameError`，进去之后能看到 `class NameError`——`NameError` 就是这个类的类名；而它括号里写的是 `Exception`。这就是 Python 当中类与类之间的继承体系：`NameError` 继承了 `Exception`，`Exception` 是 `NameError` 的父亲，`NameError` 本身也是 `Exception` 这种类型。而 `Exception` 是我们常见这些异常**顶级的父亲**，所有常见的异常都属于 `Exception` 这种类型。

所以 `except` 后面直接写 `Exception`，就代表捕获所有异常；而写具体类型，代表捕获具体类型的异常。

```python
try:
    print("abc".hello)
except NameError as e:
    print("名字不存在，请检查变量或函数的名字，异常信息是：", e)
except ZeroDivisionError as e:
    print("0不能做被除数，异常信息是：", e)
except IndexError as e:
    print("索引错误，异常信息是：", e)
except Exception as e:
    print("程序运行出错了，请联系管理员，异常信息是：", e)
```

这个兜底的 `except` 要放在所有具体类型的 `except` 后面。再打一个断点运行：从上往下匹配，前面几个都没匹配成功，最后一个 `Exception` 把所有类型的异常都兜住，于是执行它里面的代码，输出「程序运行出错了，请联系管理员」。

> **提示**：想捕获所有异常还有一种简化写法——把 `Exception` 直接省略，写成 `except:`。这时 `as e` 里的 `e` 也就不存在了，直接输出同样可以捕获所有类型的异常。但一般来说我们都不会省略：一旦省略，开发工具就会给出提示，说「异常子句过于泛化」，建议你指定一下要捕获的是什么异常。

## finally 的执行时机

最后演示 `finally` 这个代码块。

`finally` 里的代码通常是做资源释放的操作，后面的项目里会用到：比如操作文件，文件用完之后最终要把它关闭掉，这个关闭动作就可以写在 `finally` 当中。

它的执行时机比较特殊——无论程序是否正常运行，`finally` 代码块当中的代码都会运行。

验证两次就够了。先把出异常的代码注释掉，这一步不会出现异常，运行后可以看到「释放资源」这句照常执行；再把错误代码放回去，让程序报错，运行后「释放资源」依然执行。即便把最后那个兜底的、捕获所有异常的代码块也注释掉，运行这句代码时出现的错误前面几个 `except` 都捕获不了，程序报错了，释放资源仍然可以正常运行。

## 小结

这一部分要明确两个问题。

为什么要捕获异常？因为不捕获的话，程序运行过程当中一旦出现异常，程序就中断了。捕获异常就是在程序出现异常时给它一份预案、一个 Plan B，一旦出现异常就按 Plan B 执行，而不是让程序中断。

如何捕获异常？关键就是 `try`、`except` 以及可选的 `finally`。把所有可能出现异常的代码放进 `try` 代码块；一旦出现异常，就会被 `except` 的捕获代码接住；接住之后会去匹配抛出来的异常是不是这个 `except` 所声明的类型，是就被捕获并执行其中的处理逻辑，不是就从上往下挨个匹配，直到匹配成功；如果都匹配完还没有匹配到，程序运行就直接报错了。想捕获所有异常，就用 `Exception` 这种类型——我们常见的所有异常都属于 `Exception` 类型。

`finally` 的执行时机需要掌握：无论程序正常执行还是出现异常，它里面的代码都会执行，通常用来做资源释放、环境清理；`finally` 是可有可无的。
