# 异常的传递特性与教务管理系统案例完善

异常的处理方案和操作语法我们已经掌握了，但还有一个特性必须单独拎出来讲清楚——异常的传递。它是我们在真实项目里决定「异常到底在哪一层处理」的依据。

## 异常传递的定义

> **定义**：异常的传递，指的是异常在函数调用或者方法调用的过程当中层层上报的这个过程。

在这个层层上报的过程当中，它会去找有没有能够处理这个异常的函数或方法，直到有人能处理它为止。如果始终没有人能够处理这个异常，那么这个时候程序就会崩溃。

## 异常传递的执行过程

先把例子看掉。这里定义了三个函数：`function1`、`function2`、`function3`。`function1` 里调用了 `function2`，`function2` 里又调用了 `function3`，而 `function3` 里面输出了两句话。

```python
def function3():
    print("hello")
    print(my_color)

def function2():
    function3()

def function1():
    function2()

function1()
```

程序运行的时候调用的入口是 `function1`。这样一来，函数调用就是一层套一层。

对比一下正常情况就清楚了：如果 `my_color` 这个变量已经定义，那么 `function3` 执行完，有返回值就一层一层往回返——`function3` 的返回值返回给 `function2`，`function2` 的返回值返回给 `function1`，`function1` 有返回值的话，谁调用我，我就把返回值返回给谁。

现在是异常情况：`my_color` 这个变量并未定义，未定义就直接使用，就会抛出异常。而 `function3` 当中并没有对异常做处理，这时候谁来接手？

谁调用我，我就抛给谁，这就是所谓的层层上报。

```text
        主程序（入口）
            |  调用
            v
        function1            <- 未处理，继续上报
            |  调用
            v
        function2            <- 未处理，继续上报
            |  调用
            v
        function3            <- 抛出异常，本身未处理
            |  print(my_color) 触发
            v
        异常沿调用链反向逐层上报
            |
            v
        一路无人处理 -> 程序中断，异常信息直接抛给用户
```

读图说明：异常在触发点抛出后，不会在调用链上原地消失，而是沿着「谁调用了它」这条关系原路往返回，每经过一层就询问这一层是否处理，直到被某一层接住，或者走完整个调用链导致程序中断。

具体到这个例子里：`function2` 调用了 `function3`，所以 `function3` 把异常抛给 `function2`；`function2` 也没有处理，于是抛给调用它的 `function1`；`function1` 同样没有处理，就把异常抛给主程序；主程序也没处理，最终程序中断运行，异常信息直接抛给用户。

## 异常的处理位置选择

那假设我想处理这个异常，到底在哪一层处理最合适？

在 `function3` 里处理可以，在 `function2` 里处理也可以，在 `function1` 里处理同样是 OK 的。

> **结论**：最合适的处理位置是主程序——在最后一道防线、最后一层把异常统一捕获、统一处理。

原因在于捕获范围。如果在 `function3` 里做异常处理，那么假设 `function2` 当中出现错误，`function3` 里的处理逻辑捕获不了 `function2` 抛出来的异常；同理，如果只在 `function2` 里处理，它也捕获不了 `function1` 当中抛出来的异常。所以要让最外层统一兜住。

## 异常传递的调试观察

回到 PyCharm，这里已经准备好了这三个函数：`function1`、`function2`、`function3`，程序中调用了 `function1`，`function1` 调用 `function2`，`function2` 调用 `function3`，而 `function3` 里输出了两句话，其中一句用到了并未定义的 `my_color`，所以这一行代码一旦运行就会报错。当前程序里我们并没有进行异常处理，也没有捕获任何类型的异常。先运行看一下效果。

运行结果和预期一致：报错了，类型是 `NameError`。

这一次要仔细读一下这串错误信息，因为通过它能分析出具体是哪出了错。从上往下看，它会告诉我们：运行的时候调用了 `function1`，`function1` 调用了 `function2`，`function2` 调用了 `function3`，而 `function3` 当中有某一行代码出错了，也就是 `print(my_color)` 这一行。

```text
Traceback (most recent call last):
  File "demo.py", line 12, in <module>
    function1()
  File "demo.py", line 9, in function1
    function2()
  File "demo.py", line 6, in function2
    function3()
  File "demo.py", line 3, in function3
    print(my_color)
NameError: name 'my_color' is not defined
```

最终整个错误是由最后一行代码 `print(my_color)` 引起的。由于这行代码在 `function3` 当中，异常就往上上报；`function3` 把异常再次上报给 `function2`，`function2` 把异常上报给 `function1`——因为是 `function1` 调用了 `function2`；而 `function1` 当中并未捕获、处理这个异常，所以它就一路直接抛了出来。

> **提示**：这串信息里的调用栈正是「谁调用了谁」的完整记录。自下往上看，能一路看到异常是从哪个入口进来的；从上往下看，能一路看到调用链是怎么一步步走到出错那一行的。

通过异常信息还能清楚地看到具体是哪一行出错：`function3` 的第 40 行代码出错了，点击报错信息中的位置就能直接跳到第 40 行。有了这些信息，我们就能精准定位错误出现的位置。

## 在程序入口捕获异常

既然默认情况下函数嵌套调用出现异常会层层上报，那要处理它的最省事做法就是直接在程序入口这一块处理。

在入口加上 `try`，把可能出现异常的代码放进 `try` 代码块；再来一个 `except` 捕获所有异常——这里直接捕获 `Exception`，不再一种一种地捕获：

```python
def function3():
    print("hello")
    print(my_color)

def function2():
    function3()

def function1():
    function2()

try:
    function1()
except Exception as e:
    print(f"程序运行出错了，请联系管理员，{e}")
```

再次运行，可以看到程序进入了 `except` 代码块：捕获到异常之后告诉我们「程序运行出错了，请联系管理员」，异常的错误信息也一并提示了出来。

这就是异常的传递特性。理解了它，我们在开发一些复杂功能的时候，就只需要在程序运行的入口处捕获异常，而不必在每一层函数里逐一处理。

## 教务管理系统：异常场景复现

异常捕获的方案与操作语法到此讲完，最后回到教务管理系统，把案例里那个问题解决掉。

再次把程序运行起来，重现刚才的错误：输入 `1` 添加学生，姓名输入「王玲」，语文成绩 `98`，英语成绩输入 `95.666`，回车。这一块报错了，报的是 `ValueError`——值错误。

报错信息告诉我们：你输入的字符串没法转成 `int` 类型，所以报错了；并且指出最终是在调用 `add_student` 这个方法的时候报的错。

分数输入是浮点数，程序却要拿它去做 `int` 转换，类型对不上，就会抛出 `ValueError`。

## 教务管理系统：异常处理位置

那这个错怎么解决？先看程序的运行路径。

系统运行之后会调用 `run` 方法。在 `run` 方法里，先输出菜单，然后根据用户输入的操作数字去执行不同的操作——`run` 方法里调用了具体的这些功能方法。这些功能方法一旦报错，最终都会抛给 `run` 方法。

> **结论**：只需要在 `run` 方法里处理异常就行，不用在各个功能方法当中一个一个地处理。

`run` 方法就是运行系统的入口，所以在 `run` 方法这个入口处处理即可。

接下来要判断哪些代码可能出异常。输出那段固定的字符串会出现异常吗？不会。接收键盘的录入会出现异常吗？不会。真正可能出异常的，是我们调用这些功能方法的时候。所以把调用功能方法的那段代码放进 `try` 代码块。

> **易错点**：`match` 和 `case` 是一个完整的语句结构，不能从中间切开。不能走到 `match` 里面直接加一个 `try`、把某个 `case` 单独塞进 `try`，那会让 `match` 和 `case` 不再是完整的代码结构。要把整个 `match ... case ...` 语句作为一个整体放进 `try` 代码块，然后整体往后缩进。

## 教务管理系统：按类型处理异常

刚才抛出来的异常类型是 `ValueError`，所以第一个 `except` 直接写 `ValueError`，用 `as e` 拿到异常信息，提示「输入的数据有问题，请检查，然后重新输入」。

这样写，对当前这个程序来说就只能捕获 `ValueError` 这一个类型的错误，出现其他类型的错误就捕获不了了。于是后面再补一个 `except`，捕获其他所有的异常，输出「程序运行出错了，请重新选择」：

```python
def run(self):
    while True:
        # 输出菜单
        print("#" * 30)
        print("1. 添加学生")
        print("2. 修改学生")
        print("#" * 30)
        choice = input("请选择要执行的操作（1-6）：")
        try:
            # 整个 match-case 语句作为业务代码整体放入 try 中
            match choice:
                case "1":
                    self.add_student()
                case "2":
                    self.update_student()
                # 其余分支同样是调用各功能方法
                case _:
                    print("输入错误，请选择 1 到 6 之间的菜单功能")
        except ValueError:
            print("输入的数据有问题，请检查，然后重新输入!!!")
        except Exception:
            print("程序运行出错了，请重新选择")
```

一旦重新选择，由于我们处在 `while True` 这个循环当中，代码会又输出一次菜单，让我们重新选择。

> **提示**：这里不需要看详细的错误信息，所以 `as e` 可以省略掉，直接写 `except ValueError:` 就行。

关于循环要不要显式往下走：在这段代码里，`try` 代码块后面并没有其它任何逻辑，所以捕获异常后直接输出一句话就可以。如果下面还有其它逻辑，而出现异常之后你不想再运行那些逻辑、要直接进入下一轮循环，那就需要在这一块加上关键字 `continue`。对当前这个程序来说，下面没有其它逻辑，不加也可以。

改完之后做一轮测试。运行程序，输入 `1`，姓名还是「王玲」，语文成绩 `98`，英语成绩故意输一个不正常的 `96.666`——这是一个浮点数，没法转成 `int`。回车之后，异常处理机制生效了，提示「输入的数据有问题，请检查，然后重新输入」。

关键在于接下来发生的现象：程序中断了没有？没有。捕获到异常、输出提示信息之后，程序继续运行，进入下一轮循环，再次让我们输入对应的数据。

再输一次：输入 `1`，姓名「王麻子」，语文成绩 `90`，数学成绩 `99`，英语成绩 `89`，回车——这一块成功添加了。
