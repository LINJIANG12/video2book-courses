# AI应用：大模型部署、网络协议与API调用

## 人工智能与大模型部署方案

### 人工智能与大语言模型基础体系
* **人工智能（Artificial Intelligence，AI）**

    * > **定义**：研究、开发用于模拟、延伸和扩展人类智能的理论、方法、技术及应用系统的一门综合性学科，其核心目标是让机器具备独立思考、学习、推理以及解决现实复杂问题的能力。

    * 运行机理：机器通过编写程序并结合高维数学算法，在数字世界中模拟人脑生物神经网络（数百亿神经元与突触连接）的组织结构与信号传递机制，具备模式识别与推理生成能力。

    * 生物与机器智能映射关系：
        ```text
        +-------------------------------------------------------------------+
        |                           生物与机器智能映射                        |
        +-------------------------------------------------------------------+
        | 人类大脑机制:   [海量生物神经元] + [神经突触连接]  ===> 思考 / 学习 / 推理 |
        |                       |                 |                         |
        |                       v                 v                         |
        | 机器模拟实现:   [大规模参数矩阵] + [数学算法与代码] ===> 模式识别 / 文本生成|
        +-------------------------------------------------------------------+
        ```

* **大语言模型（Large Language Models，LLM）**

    * > **定义**：参数规模庞大、经过海量多模态或文本语料深度预训练，能够理解自然语言语义、进行逻辑推理并生成符合人类表达习惯内容的深度人工神经网络程序。

    * 本质特征：从软件工程视角看，大语言模型本质是一段模拟人脑神经网络的代码程序；其“大”是指网络结构内部可调权重参数量达到数百亿（Tens of Billions）至数千亿（Hundreds of Billions）级别，通过协同运作涌现出上下文理解与严密推理能力。

    * 国际主流厂商生态：OpenAI（GPT 系列）、谷歌（Google Gemini 系列）、xAI（Grok 模型）、Anthropic（Claude 系列）。

    * 国内主流厂商生态：深度求索（DeepSeek 系列）、阿里巴巴（通义千问 Qwen 系列）、字节跳动（豆包大模型系列）、科大讯飞（星火认知大模型）、腾讯（混元大模型）、月之暗面（Kimi 长上下文大模型）。

* **AI应用（AI Application）**

    * > **定义**：将 AI 大模型的推理认知能力与具体的垂直业务场景、业务逻辑及交互界面深度融合，用以解决现实生产生活痛点或提供增值服务的软硬件系统。

    * 落地形态：涵盖对话式助手、自动化智能客服、音视频与网盘内容摘要提取、数字人克隆无人直播、短剧剧本与分镜设计、电商个性化导购助手、医疗诊断辅助筛查、金融量化交易系统。

    * 实战推进阶段：第一阶段打通基础底座与工程支撑（部署架构、网络通信协议与提示词工程）；第二阶段构建核心业务项目（现代化 Web 界面、人设配置与生产级多会话管理）；第三阶段进行复杂业务场景延伸与工程调优。

### 大模型主流部署架构对比
* **本地私有化部署（On-Premise Deployment）**

    * > **定义**：将开源大模型权重文件与推理运行时引擎直接部署并运行在本地个人计算机或企业自建私有服务器的架构模式。

    * 优势特征：数据隐私绝对安全（数据仅流转于本地内存与显存，零公网外泄风险）；完全自主可控（拥有从底层运行环境到推理框架全部控制权，支持垂直领域私有微调）；长期零增量边际成本（硬件属固定资产，日常运行不产生 Token 费用）。

    * 约束边界：初始硬件资金门槛极高（对显卡显存位宽与容量要求严苛）；运维维护负担转移至本地（环境排错、驱动匹配与依赖升级需自理）；受限于消费级显卡算力，通常仅能运行轻量蒸馏版或裁剪版模型，推理性能与能力受限。

* **官方开放接口调用（Official Open API）**

    * > **定义**：客户端基于标准网络请求协议，直接接入大模型研发厂商在万卡算力集群上全托管运维的大模型接口服务模式。

    * 优势特征：零初始硬件投入（普通便携笔记本即可发起调用）；零底层部署运维成本（高可用、模型加载与分布式负载均衡由厂商兜底）；算力满血供给（直接调用集群承载的高阶全量参数模型）。

    * 约束边界：存在公网传输数据安全与出境合规顾虑；调用费用按出入 Token 量持续线性累加；底层网络权重不可触及修改。

* **第三方云服务聚合平台（Third-Party Cloud Aggregator）**

    * > **定义**：云厂商在统一云端底座上集中部署多款主流开源与商业化大模型，对外抽象出标准化调用与计费网关的中台服务模式（如阿里云百炼、百度千帆、字节火山引擎）。

    * 优势特征：模型选型自由度极高（单一平台平滑切换 DeepSeek、通义千问、Llama 等多款模型，避免分散开户）；免除本地硬件与运维负担。

    * 约束边界：业务数据托管于第三方公网环境；按量计费长期累加成本。

* **部署方案选型对比**

    * 核心指标综合比对：
        | 评估维度 | 本地私有化部署 | 官方开放 API 直连 | 第三方云服务聚合平台 |
        | :--- | :--- | :--- | :--- |
        | **部署实体所在** | 本地 PC 或自建私有服务器 | 官方公网分布式算力集群 | 大型公网云厂商托管集群 |
        | **初期硬件成本** | 极高（需采购专业 GPU 算力） | 零（无需自建算力环境） | 零（无需自建算力环境） |
        | **长期调用费用** | 零（仅设备电费与折旧损耗） | 持续按请求 Token 量计费 | 持续按平台统一标准计费 |
        | **数据隐私安全** | 完全私有，数据零外泄 | 依赖厂商隐私协议与数据出境策略 | 依赖云厂商合规与存储安全隔离 |
        | **运行维护负担** | 重（自管驱动、引擎与故障修复） | 零（厂商全托管保障） | 零（平台全托管保障） |
        | **模型选择灵活性** | 受硬件制约，仅限特定轻量开源版 | 单一（仅限该厂商特定产品） | 极高（一站式聚合主流多种模型） |
        | **模型能力上限** | 多为裁剪蒸馏版，推理性能受限 | 满血版本，具备高阶逻辑推理算力 | 多提供标准全量或高规格优化版 |

### 开发者开放平台与接入凭证
* **应用程序编程接口（Application Programming Interface，API）**

    * > **定义**：不同软件系统之间标准化的程序通信协议与桥梁，允许开发者在无需理解目标系统底层实现细节的前提下直接调用其暴露的功能与数据。

    * 业务形态架构：DeepSeek 官网提供“开始对话”（面向 C 端用户的 Web 交互产品）与“API 开放平台”（面向软件开发者的开放接入网关）双轨业务入口。

* **接口密钥（API Key）**

    * > **定义**：开发者向云端 API 服务端发起请求时，用以证明自身身份合法性、调用权限并绑定计费账户的高熵加密字符串凭证。

    * 账户充值规则：云端接口按消耗 Token 计费，日常学习与调试场景可通过“自定义金额”充值 1 元人民币，满足极长时间的调试调用，切忌盲目大额预充。

    * 安全管理守则：
        ```text
        +-------------------------------------------------------------------+
        |                     API Key 关键安全管理守则                      |
        +-------------------------------------------------------------------+
        |  1. 界面仅展示一次: 弹窗一旦关闭，控制台将永久脱敏隐藏，无法再查阅  |
        |  2. 立即落盘本地:   创建后立即复制，保存至安全的本地离线记事本中     |
        |  3. 严禁公开外泄:   严禁将 Key 硬编码上传至 GitHub 等公开平台仓库   |
        |  4. 泄露处置机制:   一旦发生泄露，应立即在控制台手动点击删除作废    |
        +-------------------------------------------------------------------+
        ```

        * 生成弹窗关闭后控制台将永久脱敏隐藏，无法再次查看明文；丢失无法找回，只能注销后重新创建。
        * 创建后必须立即复制保存至本地安全存储介质，严禁硬编码上传至公开代码平台；一旦泄露须立即在控制台手动删除作废。

## 本地大模型部署与管理框架

### Ollama 本地运行架构与环境配置
* **Ollama 框架（Ollama Framework）**

    * > **定义**：开源的轻量级大语言模型本地运行与管理框架，将底层 C/C++ 推理引擎、权重加载与跨平台硬件加速封装为统一的命令行工具与 REST API 服务接口。

    * 运行与调度架构：
        ```text
        +-------------------------------------------------------------------------+
        |                        Ollama 本地运行与调度架构                         |
        +-------------------------------------------------------------------------+
        |   +-----------------------+              +--------------------------+   |
        |   | Ollama CLI 客户端交互 |  (命令行交互) |  Python / 外部应用 HTTP  |   |
        |   +-----------+-----------+              +------------+-------------+   |
        |               |                                       |                 |
        |               \-------------------\ /-----------------/                 |
        |                                    v                                    |
        |                        +-----------------------+                        |
        |                        |  Ollama 后台守护服务  |                        |
        |                        |  (127.0.0.1:11434)    |                        |
        |                        +-----------+-----------+                        |
        |                                    |                                    |
        |         +--------------------------+--------------------------+         |
        |         v                                                     v         |
        |  +--------------+                                      +--------------+ |
        |  |  模型权重管理 | (OLLAMA_MODELS 存储目录)             | 显存/内存引擎 | |
        |  | DeepSeek-R1  |                                      | GPU 加速推理 | |
        |  +--------------+                                      +--------------+ |
        +-------------------------------------------------------------------------+
        ```

    * 服务监听规格：默认在本地主机 `127.0.0.1` 监听 `11434` 端口。

* **本地安装与存储重定向**

    * > **定义**：通过命令行安装参数与系统环境变量，干预 Ollama 核心程序及大模型权重文件落盘路径的工程配置手段。

    * 安装路径指定：Windows 安装器默认执行静默安装并灌入系统 C 盘，需在终端显式指定安装路径：`OllamaSetup.exe /DIR="D:\develop\Ollama"`。

    * 权重存储重定向：模型权重默认存放于系统盘用户目录；新建系统环境变量 `OLLAMA_MODELS` 并指定大容量分区路径（如 `D:\develop\Ollama\models`），避免系统盘空间告警。

    * > **易错点**：⚠️ 双击运行安装器会将程序与模型默认注入系统 C 盘；需使用命令行参数 `/DIR="路径"` 指定安装目录，并配置系统环境变量 `OLLAMA_MODELS` 重定向模型权重存储目录。

### 参数规模量级与硬件选型
* **模型参数量级（Parameter Scale，b）**

    * > **定义**：大模型型号后缀中的字母 `b` 代表十亿（Billion），数值表示该深度人工神经网络所包含的可训练参数总量。

    * 规格梯队：包含 `1.5b`（15 亿参数）、`7b`（70 亿参数）、`8b`（80 亿参数）、`14b`（140 亿参数）、`32b`（320 亿参数）、`70b`（700 亿参数）以及 `671b`（6710 亿参数满血完整版）。

    * 满血版运行条件：`671b` 拥有顶尖推理能力，但需由 8 张专业级顶级加速卡（如 NVIDIA H200）、累计显存达数百 GB 的高密机架服务器集群方可驱动。

* **硬件算力匹配规则**

    * > **定义**：根据计算设备的显存位宽、显存容量及处理器类型，匹配合适参数量级模型的决策边界。

    * 独立显卡选型：配备 8GB 独立显存（如 NVIDIA RTX 4070）环境，推荐拉取 `8b`（如 `deepseek-r1:8b`，文件体积约 5.2GB），显存可完全容纳计算上下文，运行流畅。

    * 显存溢出机制：若在 8GB 显存设备上强行加载 `14b` 模型，显存溢出后将调用系统共享内存，推理生成速率断崖式下跌并严重卡顿。

    * 算力兜底选型：集成显卡、轻薄本或老旧设备应选用 `1.5b`（文件体积约 1.1GB）版本以保障基本可用性。

### 命令行生命周期维护与交互控制
* **Ollama 命令行工具（Ollama CLI）**

    * > **定义**：用于对本地大模型生命周期进行全流程控制与交互操作的终端指令集。

    * 核心维护指令：
        * `ollama serve`：初始化并在后台启动本地服务守护进程。
        * `ollama run <模型名>`：启动指定模型；本地不存在时先自动联网拉取再拉起。
        * `ollama list`：输出本地已部署的模型清单（显示模型唯一标识、占用磁盘空间、更新时间）。
        * `ollama show <模型名>`：查看目标模型的结构与元数据详情。
        * `ollama stop <模型名>`：停止正在显存中运行推理的模型进程。
        * `ollama pull <模型名>`：仅从远端仓库拉取模型权重到本地，不进入即时会话。
        * `ollama push <模型名>`：将本地打包定制的模型推送到共享仓库。

    * 会话控制指令：在终端交互提示符 `>>>` 下，输入 `/?` 查看交互指南，输入 `/bye` 终止会话并退回操作系统终端。再次启动只需执行 `ollama run deepseek-r1:8b` 即可秒级拉起，无需重复下载。

* **思维链（Chain of Thought，CoT）**

    * > **定义**：推理模型在输出最终结论前，在上下文内部展开的显式自省推导与分步演算机制。

    * 表现特征：DeepSeek-R1 模型在响应时首先以 `<think>` 标签包裹并流式打印思考链过程，随后输出最终回答文本。

## 网络通信机制与分层传输模型

### 设备寻址与端口定位体系
* **互联网协议地址（Internet Protocol Address，IP 地址）**

    * > **定义**：分配给接入网络设备的数字标签，具有网络范围内的排他唯一性，用于在逻辑与物理层面精确定位网络设备。

    * IPv4 结构机理：采用 32 位二进制数字表示，分为 4 组、每组 8 位二进制（$4 \times 8 = 32$ 位），经独立换算为点分十进制形式；每段数值范围严格限定在 $0 \sim 255$ 之间（$2^8 = 256$ 种状态），如 `132.12.86.125`。

    * IPv6 扩展特征：采用 128 位二进制长度，划分为 8 组、每组 16 位，表现为冒号十六进制，解决 IPv4 约 43 亿地址资源耗尽问题。

    * 规格对比：
        | 协议版本 | 二进制位数 | 结构划分 | 表现形式 | 设计定位 |
        | :--- | :--- | :--- | :--- | :--- |
        | **IPv4** | 32 位 | 4 组 $\times$ 8 位 | 点分十进制（如 `132.12.86.125`） | 传统互联网通用寻址标准，单段范围 $0 \sim 255$ |
        | **IPv6** | 128 位 | 8 组 $\times$ 16 位 | 冒号十六进制（如 `2001:0db8::1`） | 解决地址枯竭问题，支撑海量终端接入 |

* **本地回环地址（Loopback Address，127.0.0.1）**

    * > **定义**：代表当前运行代码的主机本机自身的回环网络接口。

    * 闭环转发机制：发送给 `127.0.0.1` 的数据包由操作系统网络栈在本地内存回路中直接闭环转发，无需经过物理网卡对外广播。

* **域名系统（Domain Name System，DNS）**

    * > **定义**：由特定字符和点号组成的层次化字符型助记标识（域名），以及在网络中维护域名与 IP 地址映射记录的分布式数据库系统（DNS 服务器）。

    * 两阶段解析机制：客户端浏览器输入域名（如 `www.baidu.com`）后，先向 DNS 服务器发起递归查询获取数字 IP（如 `110.242.69.21`）；随后客户端才基于该数字 IP 建立底层物理链路连接。

    * 本地通用域名：`localhost` 为系统内置专属本机的通用域名，与 `127.0.0.1` 在路由寻址上完全等价。

* **网络端口（Port）**

    * > **定义**：操作系统为识别同一物理设备内部不同网络通信进程而开辟的逻辑通道编号，本质为一个取值在 $0 \sim 65535$ 之间的无符号整数。

    * 强排他性规则：同一台设备内部针对同一种传输层协议，绝对不允许两款不同的软件进程抢占同一个端口号。

    * 默认端口约定：访问 URL 省略端口时协议自动补齐；HTTP 默认端口为 `80`，HTTPS 默认端口为 `443`。

    * 端到端两阶段寻址机制：
        ```text
        +-------------------------------------------------------------------+
        |                         端到端两阶段寻址                           |
        +-------------------------------------------------------------------+
        | 第一阶段 (主机锁定): 域名 --(DNS解析)--> IP地址 ===> 锁定物理/虚拟主机 |
        | 第二阶段 (进程锁定): IP数据报 + 端口号 (Port)    ===> 锁定具体运行进程 |
        +-------------------------------------------------------------------+
        ```

### 分层网络模型与协议解耦
* **分层网络体系（Layered Network Architecture）**

    * > **定义**：将复杂的跨网络通信过程切分为若干个职责高度内聚、接口标准统一的上下游处理阶段的体系架构。

    * 核心收益：职责解耦（各层专注自身通信难题，上层屏蔽底层硬件细节）；故障隔离（自顶向下或自底向上快速定位协议异常所在层级）。

    * 工业标准对照：OSI 七层参考模型（应用层、表示层、会话层、传输层、网络层、数据链路层、物理层）；TCP/IP 四层实用模型（将高三层合并为应用层，保留传输层与网络层，底两层合并为网络接口层）。

    * 流水线装配映射：
        ```text
        +---------------------+    汽车装配流水线类比
        |  应用层 (HTTP 等)   |    第 1 工位: 装配车身与控制台（面向用户业务交互）
        +---------------------+           | 移交数据块
        |  传输层 (TCP/UDP)   |    第 2 工位: 安装发动机与传动轴（封装源端口/目标端口）
        +---------------------+           | 移交数据段
        |  网络层 (IP)        |    第 3 工位: 粘贴出厂车架号与导航牌（封装源 IP/目标 IP）
        +---------------------+           | 移交数据报
        |  网络接口层 (链路/物理) |    第 4 工位: 承载托盘推入物理发运轨道（比特流收发）
        +---------------------+
        ```

    * 协议栈职责分工：
        * 应用层（Application Layer）：直接面向用户界面与业务程序（HTTP、FTP、SMTP），将业务数据格式化封装为标准文本数据块并移交传输层。
        * 传输层（Transport Layer）：负责应用层数据端到端的可靠投递，在数据包头部追加源端口与目标端口。
        * 网络层（Network Layer）：核心为 IP 协议，封装源 IP 与目标 IP，指导路由器进行寻址路由与跳步转发。
        * 网络接口层（Network Interface Layer）：驱动网卡等物理硬件，将 IP 数据报转换为电信号、光信号或无线电磁波进行比特流传输。

* **传输控制协议（TCP）与用户数据报协议（UDP）**

    * 传输层协议特征对比：
        | 传输层协议 | 连接状态 | 传输可靠性 | 开销与延迟 | 核心应用场景 |
        | :--- | :--- | :--- | :--- | :--- |
        | **UDP** | 无连接 | 不保证可靠传输，不重传 | 协议头部小，延迟低，开销小 | 屏幕共享、视频通话、实时语音直播 |
        | **TCP** | 面向连接（三次握手） | 严格可靠，具确认应答、超时重传与流量控制 | 存在建连开销与流量控制成本 | 网页访问、API 接口调用、银行与支付转账 |

    * 应用开发边界：大模型 API 及常规 Web 业务全部构建于应用层，开发者无需介入下三层协议细节，聚焦 HTTP 规范即可。

## 超文本传输协议报文规范与测试

### HTTP 协议核心传输机制
* **超文本传输协议（HyperText Transfer Protocol，HTTP）**

    * > **定义**：规定客户端与服务端在网络中进行数据传输所必须遵循的统一结构与解析规则的应用层规范。

    * 文本传输特征：协议报文命令与头部全部采用标准的纯文本字符串组织，不包含私有二进制控制字节，具备高度的人类可读性与通用调试便利性。

    * 传输层依赖：底层完全依赖面向连接的 TCP 协议，确保报文数据无损、有序、不丢包。

* **无状态机制与请求响应模型**

    * > **定义**：HTTP 通信所固有的以客户端为单向驱动核心的一问一答交互模型，以及服务端不保留历史连接记忆的无状态隔离机制。

    * 交互模型示意：
        ```text
        客户端                                             服务端
          |                                                  |
          | -------- 1. 主动发起 HTTP 请求 (Request) ------> |
          |                                                  | (处理请求)
          | <------- 2. 返回对应 HTTP 响应 (Response) ------ |
          |                                                  |
          |         (连接完成，不保留任何上下文状态)         |
          |                                                  |
          | -------- 3. 再次发起全新请求 (Request) --------> |
          |                                                  | (视为全新独立事件)
        ```

    * 请求-响应模型（Request-Response Model）：通信严格遵循“一问一答”；通信主动权永远在客户端，服务端绝不主动推送；一次请求严格对应一次响应。

    * 无状态机制（Stateless）：服务端在请求与响应生命周期中不留存关于客户端的交互历史或身份状态；连续发起的请求彼此完全孤立，后一次请求绝不默认继承前次上下文要素。

### 请求报文结构与参数传递
* **HTTP 请求报文（HTTP Request Packet）**

    * > **定义**：由客户端按照 HTTP 规范组装并发送给服务端的结构化数据包，由请求行、请求头、空行与请求体四个区域自上而下顺序拼接而成。

    * 请求报文物理排布：
        ```text
        +-------------------------------------------------------------------+
        | 请求行: POST /a/course HTTP/1.1                                   |
        +-------------------------------------------------------------------+
        | 请求头:                                                           |
        | Accept: application/json                                          |
        | Content-Type: application/json                                    |
        | Content-Length: 139                                               |
        +-------------------------------------------------------------------+
        | 空行 (CRLF 物理空行分隔符)                                         |
        +-------------------------------------------------------------------+
        | 请求体 (承载实际业务数据载荷):                                    |
        | {"course_id": 1024, "action": "enroll"}                           |
        +-------------------------------------------------------------------+
        ```

    * 请求行物理语法：`[请求方式] [请求资源路径] [协议及版本]`（以单个空格隔开，固定占报文第一行）。

    * 空行物理界标：请求头与请求体之间必须强制插入连续的 CRLF 回车换行控制符作为协议边界界标。

    * > **易错点**：⚠️ 请求头与请求体之间必须保留一个独立的 CRLF 物理空行作为边界界标，缺失空行将导致协议解析器无法识别载荷起始位置。

* **请求方式特征对比（GET vs POST）**

    * 传输维度对照：
        | 核心维度 | GET 请求方式 | POST 请求方式 |
        | :--- | :--- | :--- |
        | **参数承载位置** | 请求行中的 URL 路径后（由 `?` 引导，`&` 分隔） | 封装于报文末端的请求体（Body）内 |
        | **数据传输容量** | 受到 URL 字符长度物理限制，严禁传大文件 | 协议本身无体积上限，支持海量数据与文件上传 |
        | **请求体状态** | 严格没有请求体 | 可以包含请求体（亦可为空，默认有载荷） |
        | **典型应用场景** | 幂等检索、静态页面读取、简单关键词查询 | 账户登录、表单提交、大模型 Prompt 提交、文件上传 |

* **核心请求头字段（Request Headers）**

    * 组织形式：采用 `key: value` 格式每行一组，向服务端声明运行环境与数据约束。

    * `Accept`：向服务端声明客户端期望接收的返回数据格式（如 `application/json`、`text/plain`）。

    * `Accept-Language`：向服务端声明客户端首选的自然语言环境（如 `zh-CN` 优先简体中文）。

    * `Content-Type`：明确标示客户端本次在请求体中向服务端发送的真实数据格式（调用大模型时固定为 `application/json`）。

    * `Content-Length`：精确指示本次请求体所包含的数据长度（以字节数或字符数衡量，例如 `139`）。

### 响应报文结构与状态管理
* **HTTP 响应报文（HTTP Response Packet）**

    * > **定义**：由服务端在处理完请求后组装并回传给客户端的结构化数据包，由响应行、响应头、空行与响应体四个区域自上而下顺序拼接而成。

    * 响应报文物理排布：
        ```text
        +-------------------------------------------------------------------+
        | 响应行: HTTP/1.1 200 OK                                           |
        +-------------------------------------------------------------------+
        | 响应头:                                                           |
        | Server: nginx/1.24.0                                              |
        | Date: Mon, 20 Oct 2025 08:30:00 GMT                               |
        | Content-Type: application/json;charset=UTF-8                      |
        +-------------------------------------------------------------------+
        | 空行 (CRLF 物理空行分隔符)                                         |
        +-------------------------------------------------------------------+
        | 响应体 (服务端回传的真实业务结果数据):                            |
        | {"code": 0, "msg": "success", "data": {...}}                      |
        +-------------------------------------------------------------------+
        ```

    * 响应行物理语法：`[协议及版本] [状态码]`（如 `HTTP/1.1 200`）。

    * 核心响应头字段：`Server`（标识服务端底层 Web 软件类型如 nginx）、`Date`（服务端生成时间戳）、`Content-Type`（响应体格式自述，如 `application/json`）。

    * 响应体载荷：承载服务端运算的真实业务结果；在大模型 API 调用中全盘标准化为 JSON 字符串格式。

* **响应状态码（Status Code）**

    * > **定义**：由三位纯数字组成的标准化结果代码，用于向客户端指示请求的处理结果及失败的根源类别。

    * 核心状态码诊断规则：
        | 状态码区间 | 归属分类 | 核心代表 | 状态含义与诊断方向 |
        | :--- | :--- | :--- | :--- |
        | **`2xx`** | 成功响应 | **`200 OK`** | 请求处理成功，结果数据完整携带于响应体中 |
        | **`4xx`** | 客户端错误 | **`400 Bad Request`** | 客户端传参错误、缺少必填参数或数据结构畸形 |
        |  |  | **`404 Not Found`** | 访问的接口路由不存在、URL 路径输错或后端资源已下线 |
        | **`5xx`** | 服务端错误 | **`500 Internal Server Error`** | 服务端业务代码抛出未捕获异常，内部处理崩溃 |

### 浏览器开发者工具抓包实证
* **网络监听面板（DevTools Network）**

    * > **定义**：利用现代浏览器内置开发者工具捕获并检查客户端与服务端之间往返的真实 HTTP 报文底层的实证手段。

    * 操作流向：按下快捷键 `F12` -> 切换至 `Network` 标签页 -> 过滤器勾选 `All` -> 刷新页面或触发业务交互 -> 选中目标请求条目。

## 大模型接口协议与会话记忆架构

### 客户端调用约束与测试工具配置
* **浏览器调用局限与 POST 约束**

    * 协议限制：浏览器地址栏输入 URL 敲回车发起的网络请求在协议层恒为 `GET` 请求。

    * 容量冲突：GET 请求仅支持在 URL 末尾拼接参数，容量上限通常仅数 KB；大模型交互的提示词（Prompt）、代码片段与业务规则体量动辄数 KB、数十 KB 乃至数百 KB，因此大模型开放接口从协议层直接限定必须为 `POST` 请求方式。

* **接口测试工具（Apifox）**

    * > **定义**：集 API 设计、开发与测试于一体的可视化接口联调平台，支持自主组装 HTTP 请求方式、请求头及请求体。

    * 目录部署规范：自定义安装时必须在开发目录下新建专用子文件夹（如 `D:\develop\Apifox`）收敛文件，防止执行依赖散落。

    * > **易错点**：⚠️ 自定义安装路径时若直接选定开发根目录，安装程序会将所有依赖文件散落于根层级；必须新建专用子文件夹（如 `D:\develop\Apifox`）收敛文件。

    * 工作台配置：在团队项目中新建项目，进入“快捷请求”，选择 `POST` 方式，填入端点 URL，分别在 `Headers` 与 `Body` 标签页配置鉴权与 JSON 参数。

### 官方接口契约与数据规范
* **OpenAI 兼容接口规范（OpenAI-Compatible Specification）**

    * > **定义**：大模型服务商广泛遵循的事实标准 API 契约，DeepSeek API 在协议层与报文格式上与其完全保持兼容。

    * 基准 curl 终端调用四要素：
        * 传输协议与端点：`https://api.deepseek.com/chat/completions`（基于传输层安全加密的 HTTPS 协议）。
        * 格式标识头：`-H "Content-Type: application/json"`。
        * 鉴权凭证头：`-H "Authorization: Bearer $DEEPSEEK_API_KEY"`。
        * 报文主体：`-d '{ "model": "...", "messages": [...], "stream": false }'`。

* **请求头配置标准**

    * `Content-Type`：固定填入 `application/json`，声明载荷遵循标准 JSON 格式。

    * `Authorization`：填入 `Bearer <你的API_KEY>`；令牌前缀 `Bearer` 与密钥字符串之间必须保留一个半角空格。

* **JSON 数据类型与词法约束（JSON Specification）**

    * > **定义**：轻量级跨语言通用数据交换格式，采用键值对集合结构，词法校验具有刚性约束。

    * 词法规则清单：
        * 键（Key）：必须且只能使用英文双引号 `""` 包裹，严禁使用单引号或省略引号。
        * 字符串（String）：必须强制使用英文双引号 `""` 闭合。
        * 数值（Number）：整数与浮点数（如 `12`、`3.14`）直接裸写，严禁添加引号。
        * 布尔值（Boolean）：取值仅限 `true` 与 `false`，必须全小写。
        * 对象与列表（Object & Array）：对象采用大括号 `{}`，序列采用中括号 `[]`，元素以逗号分隔，末尾元素后绝对不可残留多余逗号。

    * > **易错点**：⚠️ JSON 规范中的布尔值必须全小写写作 `true` 与 `false`；若沿用 Python 语法大写首字母（`True`/`False`）会被判为未定义标识符，若加双引号则会被解析为字符串破坏类型契约。

### 请求参数体系与用量计费机制
* **大模型核心控制参数**

    * `model`：指定调用的云端大模型标识；官方开放平台开放通用对话模型 `deepseek-chat` 与深度推理模型 `deepseek-reasoner`（必须严格区分本地标签如 `deepseek-r1:8b`）。

    * `stream`：输出流控布尔开关；`false` 为整包一次性返回，`true` 为分块流式实时推送。

    * `messages`：包含交互上下文的消息对象数组，每个元素由 `role`（角色）与 `content`（正文）构成。

* **基础消息角色体系**

    * 系统角色（`role: "system"`）：对应系统提示词（System Prompt），负责为大模型初始化身份认知、行为准则、应答风格与业务边界，全局统领模型推理逻辑。

    * 用户角色（`role: "user"`）：对应用户提示词（User Prompt），承载真实终端用户提交的具体问题、任务描述或业务指令。

* **响应结构与双向 Token 计费机制**

    * 响应实体提取：大模型应答封装在 `choices[0].message` 中，其 `role` 为 `assistant`，`content` 存储模型遵循系统设定生成的最终回复文本。

    * Token 用量统计（`usage`）：大模型计费基于 Token 双向计量：
        * `prompt_tokens`：客户端发送的所有提示词（系统设定 + 用户输入）切词后消耗的输入 Token 数量。
        * `completion_tokens`：大模型生成应答文本所消耗的输出 Token 数量。
        * `total_tokens`：本次 HTTP 事务消耗的总 Token 数（`prompt_tokens + completion_tokens`）。
        * 结算规则：云端服务商通常以百万 Token（Per Million Tokens）为单位制定输入与输出的阶梯单价，两者均计入账单成本。

### 大模型无状态特性与滚雪球会话记忆
* **大模型无状态断层机制**

    * 底层机理：大模型 API 在底层架构上完全**无状态（Stateless）**；每个发往服务端的 HTTP 请求都是彼此完全孤立的独立事务，服务端不留存历史连接的会话上下文。

    * 断层现象：单轮独立提问“12个苹果均分给3个人”后，下一次请求直接追问“那两个人呢？”，大模型因缺乏上下文而产生逻辑断层、出现困惑反问或胡乱幻想。

* **滚雪球方案（Context Accumulation）**

    * > **定义**：由客户端应用在本地维系对话历史，并在发起新一轮请求时，将此前所有轮次的时序消息（包含用户提问与大模型回复）全部追加至 `messages` 列表后全量提交给大模型处理的工程方案。

    * 角色职责协同：
        | 消息角色（Role） | 角色来源与属性 | 在多轮对话中的工程定位 |
        | :--- | :--- | :--- |
        | `system` | 开发者预设的系统提示词 | 始终置于 `messages` 首位，全局统领 AI 人设、行为准则及规则约束。 |
        | `user` | 终端用户输入的指令或问题 | 包含历史提问以及当前最新触发的一轮提问。 |
        | `assistant` | 由大模型在历史轮次中生成的响应 | 由客户端在上一轮响应中提取，原样追加至上下文，供模型回溯前序输出。 |

    * 演进时序结构：
        ```text
        +-------------------------------------------------------------------+
        |                        滚雪球上下文演进时序                       |
        |                                                                   |
        | [第一轮请求]                                                      |
        | messages: [                                                       |
        |   { role: "user",      content: "12个苹果三个人怎么均分？" }      |
        | ]                                                                 |
        |                                                                   |
        | [第二轮请求] (将大模型第一轮回答作为 assistant 角色滚入历史)      |
        | messages: [                                                       |
        |   { role: "user",      content: "12个苹果三个人怎么均分？" },     |
        |   { role: "assistant", content: "12 / 3 = 4，每人4个。" },        |
        |   { role: "user",      content: "那两个人呢？" }                  |
        | ]                                                                 |
        |                                                                   |
        | [第三轮请求] (继续滚入第二轮回答，承上启下)                       |
        | messages: [                                                       |
        |   { role: "user",      content: "12个苹果三个人怎么均分？" },     |
        |   { role: "assistant", content: "12 / 3 = 4，每人4个。" },        |
        |   { role: "user",      content: "那两个人呢？" },                 |
        |   { role: "assistant", content: "12 / 2 = 6，每人6个。" },        |
        |   { role: "user",      content: "那六个人呢？" }                  |
        | ]                                                                 |
        +-------------------------------------------------------------------+
        ```

    * 上下文裁剪规则：针对带推理链的模型，响应中的 `thinking` 字段属于中间态，在滚入下一轮历史时应予剔除，仅保留 `content` 正文以节约有限的上下文窗口空间。

    * 成本增长边界：随对话深入，全量追加导致每次请求携带的输入 Token（`prompt_tokens`）呈线性累加，单次请求的调用成本持续上升。

### 本地接口规范与流式传输控制
* **Ollama 本地 REST API 对接**

    * 聊天端点定位：`http://localhost:11434/api/chat`，请求方式为 `POST`。

    * 参数契约：请求体包含 `model`（必须严格填入本地具体标签如 `deepseek-r1:8b`）、`messages` 及 `stream`。

    * 接口特征对比：
        | 对比维度 | DeepSeek 官方开放 API | 本地 Ollama 私有化 API |
        | :--- | :--- | :--- |
        | 网络请求地址 | 公网接口域名（如 `https://api.deepseek.com`） | 本机私有地址（`http://localhost:11434/api/chat`） |
        | 访问鉴权方式 | 必须在请求头携带 `Authorization: Bearer <API_KEY>` | 本地局域网内默认无需鉴权 |
        | 模型标识参数 | 官方模型标识（如 `deepseek-chat` 或 `deepseek-reasoner`） | 本地具体标签（如 `deepseek-r1:8b`） |
        | 思考链字段 | 部分推理模型在内容或扩展字段中返回 | 本地 R1 模型独立返回 `thinking` 字段展示推理链 |

* **流式传输模式（Stream Mode）**

    * 传输机制：设定 `"stream": true` 时，服务端采用分块传输编码（Chunked Transfer Encoding），在大模型推理过程中以数据流分块形式实时持续推送生成的 Token 或字符。

    * 体验差异：非流式模式需等待完整生成后整包返回，首字等待延迟长；流式模式具备低延迟优势，字符呈打字机动效渐进式涌现；Apifox 支持勾选“自动合并”开关将持续流入的数据流分片重组为连续段落。

### 系统环境变量配置与鉴权异常排查
* **环境变量持久化配置**

    * 配置路径：鼠标右键“此电脑” -> 属性 -> 高级系统设置 -> 环境变量 -> 系统变量/用户变量新建。

    * 变量键值：变量名填入 `DEEPSEEK_API_KEY`，变量值填入控制台生成的有效 API Key 密文字符串，逐层点击确定保存。

* **401 鉴权失败异常排查与解决**

    * 异常特征：控制台抛出 `AuthenticationError: Error code: 401 - {'error': {'message': 'Authentication Fails ...'}}`。

    * 根源机理：修改操作系统环境变量后，已在运行状态中的 PyCharm 或 IDE 进程不会动态热重载外部环境，其内存中保留的仍是启动之初的空环境快照，导致 `os.environ.get()` 读取为 `None`。

    * 解决规则：彻底退出 PyCharm 进程并重新启动，重启后 IDE 从操作系统完整同步最新的环境变量表。

    * > **易错点**：⚠️ 操作系统环境变量更新后，运行中的 PyCharm 进程不会热重载环境快照，直接运行会导致读取空密钥并抛出 401 鉴权失败异常；必须彻底重启 IDE 进程同步最新环境变量。

### 客户端代码实现与响应数据逐级解析
* **Python 接口调用三步法**

    * 工程实现代码：
        ```python
        import os
        from openai import OpenAI

        # 步骤一：创建与 AI 大模型交互的客户端对象
        client = OpenAI(
            api_key=os.environ.get("DEEPSEEK_API_KEY"),
            base_url="https://api.deepseek.com"
        )

        # 步骤二：向大模型发起交互请求
        response = client.chat.completions.create(
            model="deepseek-chat",
            messages=[
                {"role": "system", "content": "你是一名非常可爱的AI助理，你的名字叫小甜甜。"},
                {"role": "user", "content": "你是谁？你能帮我做什么？"}
            ],
            stream=False
        )

        # 步骤三：解析并输出大模型返回的回复文本
        print(response.choices[0].message.content)
        ```

* **响应对象多层级解析链路**

    * 响应对象结构拆解图：
        ```text
        response (完整响应对象 / 顶级 JSON)
           │
           ├── .id: "chatcmpl-xxxxxxxx"
           ├── .model: "deepseek-chat"
           └── .choices (候选回答列表，对应 JSON 数组 [ ... ])
                  │
                  └── [0] (获取列表中下标为 0 的第一个候选元素)
                        │
                        └── .message (核心消息字典 / 载荷对象)
                              │
                              ├── .role: "assistant"
                              └── .content: "我是小甜甜，一个超级可爱的AI助手..."
        ```

    * 逐级解析职责：
        * `response`：API 交互返回的顶层封装对象。
        * `.choices`：模型生成的候选回复列表。
        * `[0]`：取得默认单候选场景下下标为 0 的第一个回复元素。
        * `.message`：提取候选对象封装的消息载荷字典。
        * `.content`：提取消息主体中包含的最终生成文本字符串。

### 提示词工程原则与设计技巧
* **提示词（Prompt）与提示词工程（Prompt Engineering）**

    * > **定义**：提示词（Prompt）是指向大模型输入的所有文本指令、问题与上下文约束；提示词工程（Prompt Engineering）是指通过系统化、技巧性地设计与组织提示词，引导大模型生成内容最大程度契合业务预期的持续优化过程。

    * 质量边界：泛化指令（如“给我讲一个故事”、“用Python写个游戏”、“法国大革命爆发的原因”）缺乏边界、受众背景与格式约束，大模型仅能基于预训练概率自由发散；高质量提示词能激活深度推理链，明确任务步骤并刚性约束风格格式，使输出高度收敛于业务预期。

    * 闭环模型：提示词设计非单次定型，而是包含“编写 -> 验证 -> 评估 -> 迭代”的持续演进闭环。

* **提示词六大设计技巧**

    * 核心技巧规范：
        ```text
        +-------------------+------------------------------------------------------+
        | 核心技巧          | 具体指导策略与工程要求                               |
        +-------------------+------------------------------------------------------+
        | 1. 定义角色与能力 | 明确赋予 AI 专业的身份背景、从业经验与核心专业擅长     |
        +-------------------+------------------------------------------------------+
        | 2. 明确请求与任务 | 直奔主题，清晰表达希望大模型完成的核心业务目标         |
        +-------------------+------------------------------------------------------+
        | 3. 拆解复杂步骤   | 将复合型任务分解为清晰的阶段性思考链路与执行流程       |
        +-------------------+------------------------------------------------------+
        | 4. 设定风格与语气 | 约定语言风格（口语/严谨），并严格列出负向禁忌词与雷区 |
        +-------------------+------------------------------------------------------+
        | 5. 约束输出格式   | 给出固定的组织框架（如 Markdown 标题、分块模板等）    |
        +-------------------+------------------------------------------------------+
        | 6. 提供输入输出示例| 给出输入数据样本或标杆风格示例（Few-Shot 引导）       |
        +-------------------+------------------------------------------------------+
        ```

    * 应用原则：在实际编写中不要求机械堆砌全部六项，依具体业务目标灵活组合。

* **提示词三要素法则（Role-Task-Constraint Framework）**

    * > **定义**：提示词工程落地中最精炼的实践方法论，将设计要素高度归纳为定角色、给任务、提要求三大核心支柱。

    * 结构模型：
        ```text
        +-------------------------------------------------------------------------+
        |                        优秀提示词编写的三要素法则                       |
        +-------------------------------------------------------------------------+
                                             │
                 ┌───────────────────────────┼───────────────────────────┐
                 ▼                           ▼                           ▼
            【定角色】                  【给任务】                  【提要求】
        设定身份背景与能力边界        明确核心业务目标与步骤        约束风格、格式与负向禁忌
        例: "资深历史老师"           例: "讲解原因并拆解维度"      例: "禁止黑话、套用模板"
        ```

    * 结构化案例实操（以解释法国大革命原因为例）：
        * 定角色：设定为“经验丰富的高中历史老师，擅长用生动有趣的语言讲解复杂历史事件”。
        * 给任务：向高中生解释法国大革命爆发的主要原因。
        * 提要求：语气简洁口语化、富有戏剧画面感（借鉴《人类群星闪耀时》叙事手法），禁止堆砌学术黑话与枯燥年份；内容分为现场氛围、根本原因（政治/经济/思想三维度并配生动事例）、结尾提供高中生记忆妙招；强制以预设 Markdown 框架输出。

    * 实测对比效果：结构完全合规（严格按历史现场氛围、危机根源解析、记忆法宝展开）；语境戏剧冲突强烈；受众适配精准，提炼出“三火记忆法”，产出具有确定性与高可用性。
