## 1. 安全性与完整性的分野

> **一句话主旨**：界定安全性防未授权访问与完整性防语义错误的本质区别，并给出从物理层到 DBMS 层的纵深防御层次。

* **数据库安全性（Database Security）**
    * > 定义：保护数据库以防止因非法使用而造成数据泄露、更改或破坏。
    * 防护对象是未经授权的非法用户越权存取机密数据，对应「防盗」。
    * 违约例：普通用户越权读取了本身真实有效、但无权查看的数据（如教师银行卡薪资）。
    * > 来源: P30

* **数据库完整性（Database Integrity）**
    * > 定义：保证数据符合客观世界业务规律的逻辑正确性。
    * 防范合法用户因误操作或代码缺陷写入错误、矛盾数据，对应「防错」。
    * 违约例：合法用户误将成绩录入为 `-88`，系统未经校验直接保存。
    * > 来源: P30, P36

* **安全性 vs 完整性对比**
    * 两概念的防护目标、通俗类比与违约场景对照：
        | 对比维度 | 数据库安全性 | 数据库完整性 |
        | :--- | :--- | :--- |
        | 防护目标 | 防未授权非法用户越权存取 | 防合法用户写入语义错误数据 |
        | 通俗类比 | 防盗 | 防错 |
        | 违约场景 | 越权读取真实有效数据 | 合法权限下录入非法值 |
    * > 来源: P30

* **纵深防御体系（Defense-in-Depth）**
    * 保障数据库安全须在计算机全栈构建多层防线，而非只在 SQL 层配置密码。
    * 自外向内三层：物理安全层（机房门禁、防灾监控、防电磁辐射与物理窃听）→ 操作系统与网络安全层（防火墙隔离、SSL/TLS 传输加密、OS 账号防护）→ DBMS 安全层（身份鉴别、存取控制、视图隔离、审计追踪、落盘加密）。
    * > 来源: P30

## 2. 安全评估准则与商用基线

> **一句话主旨**：给出 TCSEC 四级七等划分、主流商用 DBMS 的 C2 安全基线，以及 B1 级起引入强制存取控制的等级门槛。

* **TCSEC（可信计算机系统评估准则，橘皮书）**
    * > 定义：美国国防部制定的计算机系统安全评估标准，将安全程度由低到高划分为 4 组 7 个等级。
    * 各级特征：
        | 等级 | 名称与特征 |
        | :--- | :--- |
        | D | 最小保护；硬件无内存保护、软件无用户鉴别，早期 MS-DOS 属此级 |
        | C1 | 自主安全保护；初级自主存取控制，将用户与数据分离 |
        | C2 | 受控存取保护；细粒度自主存取控制 + 强制身份鉴别 + 审计 |
        | B1 | 标记安全保护；引入强制存取控制（MAC），强制阻断越权渗透 |
        | B2~A1 | 面向国防核控制与绝密军事情报，安全内核须经形式化数学证明不存在隐蔽通道 |
    * > 来源: P30

* **主流商用安全基线 C2**
    * C2 级核心特征为细粒度自主存取控制，并引入强制性身份鉴别与审计机制，可记录谁在什么时刻对哪些数据执行了操作。
    * Oracle、Microsoft SQL Server、PostgreSQL 等主流商业数据库的原生标准配置均达到 C2 级。
    * > 来源: P30

* **CC（Common Criteria，通用准则）**
    * 与 TCSEC 并列的国际通用安全评估准则。
    * > 来源: P30

## 3. 身份鉴别技术

> **一句话主旨**：身份鉴别回答「你是谁」、是访问数据库的第一道防线，含口令类与生物特征、硬件令牌两类技术。

### 3.1 鉴别定位与口令类技术

* **身份鉴别（Authentication）**
    * > 定义：验证试图连入系统的用户是否确为其声称的合法实体，回答「你是谁」这一问。
    * 与存取控制构成两道防线：鉴别失败立即切断网络连接并记入安全审计日志；鉴别通过后由存取控制裁定「你能干什么」。
    * > 来源: P31

* **静态口令鉴别（Static Password Authentication）**
    * 原理：将用户输入的密码哈希摘要与系统内部加密存储的散列值（如 PBKDF2、SHA-256 带盐）比对。
    * 薄弱点：易受弱口令字典攻击、网络中间人窃听与重放攻击。
    * > 来源: P31

* **动态口令鉴别（Dynamic Password / OTP / MFA）**
    * 原理：引入双因子认证，口令随时间（TOTP）或计数事件单向动态生成，一次一密，数十秒后自动作废失效。
    * 收益：单次口令即使被窃听捕获，因时效已过无法用于第二次登录。
    * > 来源: P31

### 3.2 生物特征与硬件令牌技术

* **生物特征鉴别（Biometric Authentication）**
    * 利用指纹、虹膜、人脸、静脉血管等人体独有生物学特征比对，几乎不可能被窃取或转借他人。
    * > 来源: P31

* **智能卡与数字证书（Smart Card / USB Key）**
    * 用硬件加密芯片存储用户的非对称私钥，登录时经挑战-应答机制做公私钥密码学签名验证，防篡改防复制。
    * > 来源: P31

## 4. 自主存取控制与权限治理

> **一句话主旨**：DAC 由对象属主自主授权与转授，以授权有向图追踪权限扩散；GRANT/REVOKE 落地授权与 CASCADE/RESTRICT 收权。

### 4.1 DAC 与授权有向图

* **自主存取控制（Discretionary Access Control, DAC）**
    * > 定义：对象属主可自主决定将其对象权限授予其他用户，并允许被授权者把权限进一步转授给第三方。
    * 用户对自己创建的数据库对象天然拥有最高属主权限；SQL 层通过数据控制语言（DCL）落地。
    * > 来源: P31

* **特洛伊木马（Trojan Horse）攻击脆弱性**
    * 攻击路径：拥有绝密表的高权限用户 A 被诱骗运行看似正常的统计程序（木马），木马在 A 的合法会话上下文中读取绝密表并 `INSERT` 进人人可读的公共表，恶意用户 B 再读取该公共表。
    * 本质：链条中每一步操作都符合 DAC 授权规则，DAC 对合法主体发起的越权拷贝完全无能为力。
    * > 来源: P31, P34

* **授权有向图（Authorization Graph）**
    * DAC 下权限流转形成动态的授权有向图，系统通过传播选项追踪权限的扩散与回收。
    * SQL 规范强制要求授权有向图中严禁出现有向环；每次执行带转授的 `GRANT` 时，系统扫描数据字典防止 $A \to B \to C \to A$ 的回环循环引用。
    * > 来源: P32

### 4.2 GRANT 与权限转授

* **GRANT 授权语句**
    * > 定义：DCL 中向指定用户或角色赋予对特定数据库对象操作权限的指令。
    * 语法：`GRANT <权限> [, <权限>]... ON <对象类型> <对象名>... TO <用户>... [PUBLIC] [WITH GRANT OPTION];`
    * 权限类型：表级 `SELECT`、`INSERT`、`DELETE`、`ALL PRIVILEGES`；列级 `UPDATE(<列名>)`；参照外码 `REFERENCES(<列名>)`。
    * 被授权者可为用户名、数据库角色，或保留字 `PUBLIC`——一次性开放给全数据库所有现存用户以及未来新建的所有新用户。
    * > 来源: P32

* **WITH GRANT OPTION 传播选项**
    * > 定义：附加于 `GRANT` 末尾，使被授权者可将该权限自主转授给其他合法用户。
    * 未指定时，被授权者只能在自身会话中使用该权限，绝无权转借给任何人。
    * > 来源: P32

### 4.3 REVOKE 与级联收权

* **REVOKE 收权语句**
    * 语法：`REVOKE <权限> [, <权限>]... ON <对象类型> <对象名> FROM <用户>... [CASCADE | RESTRICT];`
    * > 来源: P32

* **CASCADE 级联收权**
    * 系统顺授权图向下回溯，所有直接或间接由被收权者转授出去的派生权限被一并连带收回（雪崩级联失效）。
    * 独立来源保护：若下游用户同时从 DBA 或另一合法用户处独立获得相同授权，收回源头权限后仍合法保留。
    * > 来源: P32

* **RESTRICT 受限收权**
    * 系统发现被收权者已将该权限转授他人时，立即拒绝执行收权并报错，强制要求管理员先手工清理下级授权再收回源头权限。
    * > 来源: P32

* **两种收权模式对比**
    * 两种模式的行为差异对照：
        | 收权模式 | 行为 |
        | :--- | :--- |
        | `CASCADE` | 连带收回所有直接或间接派生的权限；下游若有独立授权源则保留 |
        | `RESTRICT` | 被收权者已转授他人时立即拒绝并报错，须先清理下级授权 |
    * > 来源: P32

## 5. 角色机制 RBAC

> **一句话主旨**：角色是被命名的权限集合，在用户与权限之间建立解耦层，规避直接用户授权导致的权限矩阵爆炸。

### 5.1 角色引入与权限堆积

* **数据库角色（Role）**
    * > 定义：被命名的一组与数据库操作相关的权限的集合。
    * 在用户与具体数据权限之间建立间接抽象解耦层，构成 RBAC（Role-Based Access Control，基于角色的访问控制）模型。
    * > 来源: P33

* **权限矩阵爆炸与权限残留**
    * 直接用户授权下，员工调岗须手动检索并逐一撤销其几十项旧权限、再逐一配置新岗位权限。
    * 易产生权限残留（Privilege Creep）安全漏洞；同岗位 50 名员工权限稍有差异时，故障排查与合规审计极难。
    * > 来源: P33

### 5.2 角色生命周期管理

* **创建与销毁角色**
    * 创建：`CREATE ROLE <角色名>;`；销毁：`DROP ROLE <角色名>;`
    * > 来源: P33

* **为角色打包权限**
    * `GRANT <权限> ON <对象> TO <角色>;`——角色可像普通用户一样接收来自对象属主或 DBA 授予的数据定义、操作与控制权限。
    * 示例：`GRANT SELECT, INSERT, UPDATE(Grade) ON TABLE SC TO Role_Teacher;`
    * > 来源: P33

* **将角色授予用户**
    * `GRANT <角色> TO <用户> [WITH ADMIN OPTION];`
    * 一个用户可同时被授予多个角色，其实际权限为所有已赋角色权限的并集；角色可授予另一个角色实现嵌套继承（如 Role_Dean 自动继承 Role_Teacher 的全部权限）。
    * > 来源: P33

* **角色的回收**
    * 从角色剥离权限：`REVOKE <权限> ON <对象> FROM <角色>;`，所有绑定该角色的用户立即全部失去该权限。
    * 从用户剥离角色：`REVOKE <角色> FROM <用户>;`
    * > 来源: P33

### 5.3 两种传播选项

* **WITH ADMIN OPTION**
    * > 定义：附加于角色授予的选项，使被授权者可将该角色进一步授予其他用户或回收该角色。
    * 撤销带 `WITH ADMIN OPTION` 的角色授权时，通常不发生下游雪崩式级联撤销（No Cascading Revoke），下游用户依然保留角色，避免单个管理员调岗导致整个部门角色瘫痪。
    * > 来源: P33

* **GRANT OPTION 与 ADMIN OPTION 对比**
    * 两类传播选项的适用范围与撤销行为对照：
        | 对比项 | WITH GRANT OPTION | WITH ADMIN OPTION |
        | :--- | :--- | :--- |
        | 适用对象 | 对象权限（表、视图的增删改查） | 系统权限或角色 |
        | 下游撤销 | 配合 `CASCADE` 可雪崩式级联收回 | 通常不级联撤销，下游保留角色 |
    * > 来源: P33

## 6. 强制存取控制与多级安全

> **一句话主旨**：MAC 由安全管理员为客体打密级标记、为主体赋许可证级别，DBMS 内核按不可逾越的规则强制执行，用户无权更改或转让。

* **强制存取控制（Mandatory Access Control, MAC）**
    * > 定义：系统强制为所有数据（客体）固化敏感度标记、为所有用户（主体）分配许可证级别，由 DBMS 内核依不可逾越的数学规则强制执行判定。
    * 任何普通用户无权更改密级，更无权转让权限。
    * > 来源: P31, P34

* **主体（Subject）**
    * 系统中的活动实体，既包括数据库用户，也包括代表该用户运行的后台进程、事务与线程。
    * 每个主体被安全管理员正式赋予一个固定的许可证级别（Clearance Level）。
    * > 来源: P34

* **客体（Object）**
    * 系统中的被动实体，是受操作系统与 DBMS 保护的数据载体（基本表、视图、物理文件、数据页、单个元组行）。
    * 每个客体被固化打上一个密级标记（Classification Level）。
    * > 来源: P34

* **敏感度标记（Security Label）高低序**
    * 绝密（Top Secret, TS）> 机密（Secret, S）> 秘密（Confidential, C）> 公开（Public, P）。
    * > 来源: P34

## 7. Bell-LaPadula 模型

> **一句话主旨**：BLP 模型以「向下读、向上写」两条规则从数学上封死信息由高密级向低密级的流动，切断特洛伊木马外泄通道。

* **Bell-LaPadula（BLP）模型**
    * 1973 年由 David Bell 与 Leonard LaPadula 提出的多级机密性访问控制模型，包含两条核心不可违背的访问定理。
    * > 来源: P34

* **简易安全特性（Simple Security Property）**
    * > 定义：向下读（No Read Up）——主体 $S$ 被允许读取客体 $O$，须满足 $L(S) \ge L(O)$。
    * 现实语义：拥有「机密」许可证的主体可向下读取机密、秘密、公开客体，绝不可向上越权读取绝密客体。
    * > 来源: P34

* **星号特性（$\star$-Property）**
    * > 定义：向上写（No Write Down）——主体 $S$ 被允许写入、追加或修改客体 $O$，须满足 $L(S) \le L(O)$。
    * 现实语义：绝密级主体只能向绝密级客体写入，绝不能向秘密、机密、公开等更低密级客体写入哪怕一个字节。
    * 防木马机理：高密级木马即使读到绝密数据，试图写入低密级公共表时因 $L(S) \not\le L(O)$（绝密并不小于等于公开）被底层安全内核强行中断写入并报警。
    * > 来源: P34

* **DAC 与 MAC 双重校验**
    * 高安全系统（TCSEC B1 级以上）不用 MAC 取代 DAC，而是组合为双重防火墙：请求先过 DAC 自主权限检查，再比主体许可证 $L(S)$ 与客体密级 $L(O)$ 执行 MAC 强制规则校验，两者同时放行方可存取。
    * > 易错点：不存在「有 MAC 就不再需要 DAC 检查」；两级检查必须同时通过，任一未过立即报错拒绝或安全拦截。
    * > 来源: P31, P34

## 8. 视图、审计与加密

> **一句话主旨**：视图提供行列级数据隔离，审计提供事后追溯与威慑，加密以传输与落盘两道密码学防线对抗窃听与物理窃取。

### 8.1 视图安全机制

* **视图安全机制（View-based Security）**
    * > 定义：通过视图定义排除敏感列、用 `WHERE` 限定可见行，再仅对视图授权，向用户隐蔽底层基本表数据。
    * 基本表常含敏感字段，直接对基本表授予 `SELECT` 会导致全量暴露。
    * > 来源: P35

* **视图授权标准方案**
    * 三步：先创建排除敏感字段并限定范围的专用安全视图 → 收回普通用户对底层基本表的访问权限 → 仅向用户授予该视图的查询权限。
    * 效果：列级保护（隐藏薪资、银行卡号）与行级保护（限制到本部门），视图成为数据访问沙箱（Sandbox）。
    * > 来源: P35

### 8.2 安全审计

* **安全审计（Auditing）**
    * > 定义：DBMS 把用户对数据库的所有或特定操作自动记录到专用的系统审计日志（Audit Trail）中。
    * 功能：事后追溯与法律取证（还原攻击路径、追查内鬼账号与发生时间戳）与威慑内部越权犯罪；是 TCSEC C2 级以上系统的硬性指标。
    * > 来源: P35

* **审计粒度分类**
    * 用户级审计：针对特定可疑用户发起的所有操作进行全程盯防录像。
    * 系统级审计：监控所有用户对数据库系统结构模式（`CREATE`、`DROP`、`ALTER`）以及用户授权命令的发起。
    * 对象级审计：专门记录极度敏感核心业务表（如银行核心账务表）的一切 DDL 与 DML 操作。
    * > 来源: P35

* **审计开销权衡**
    * 每次审计记录都引发额外的持久化磁盘写 I/O；对全库所有表的每一条简单 `SELECT` 无脑全开审计会导致吞吐骤降并迅速撑爆磁盘。
    * 工业界遵循「关键对象审计 + 高危写操作审计」的针对性配置：`AUDIT UPDATE, DELETE ON TABLE Student;` 开启，`NOAUDIT UPDATE, DELETE ON TABLE Student;` 取消。
    * > 来源: P35

### 8.3 数据加密

* **传输加密（In-Transit Encryption）**
    * 客户端与数据库服务器之间通过 SSL/TLS（安全套接层 / 传输层安全协议）建立双向加密隧道。
    * 防止黑客利用 Wireshark 等网络嗅探抓包工具窃听明文 SQL 与返回数据。
    * > 来源: P35

* **透明数据加密（Transparent Data Encryption, TDE）**
    * > 定义：数据在内存缓冲池写入磁盘数据文件时由引擎利用硬件加速指令集（AES-256）实时加密，从磁盘加载回内存时自动解密，对上层应用与开发人员完全透明。
    * 核心价值：黑客物理潜入机房拔走服务器硬盘或盗取离线冷备份时，因缺失主加密密钥，打开数据文件后是完全不可逆的乱码。
    * > 来源: P35

## 9. 实体完整性与参照完整性

> **一句话主旨**：实体完整性以 PRIMARY KEY 保证主码唯一且非空，参照完整性以外码绑定表间关联并按四种违约策略联动。

* **实体完整性（Entity Integrity）**
    * > 定义：通过 `PRIMARY KEY` 声明主码，保证主码唯一且绝对非空。
    * 单属性主码可声明为列级约束或表级约束；复合主码（由两个或更多属性联合构成）必须且只能在表末尾声明为表级约束。
    * > 来源: P36

* **实体完整性检查机理**
    * 对 `INSERT` 或主码列 `UPDATE`，事务层先做非空检查，扫描主码各分量是否存在 NULL，存在则立即报错拒绝并抛实体完整性违约异常。
    * 全部非空后再经主键索引做唯一性二分快速比对，发现索引中已存在相同键值即报错拦截主键冲突。
    * > 来源: P36

* **主键唯一索引机制**
    * 主流关系数据库在定义 `PRIMARY KEY` 的同时，自动在底层为主码列（或属性组）构建一个唯一的 B+ 树索引。
    * 借助 B+ 树对数级二分查找，主键唯一性校验耗时被严格锁定在几微秒以内，无需每次插入都全表遍历扫重。
    * > 来源: P36

* **参照完整性（Referential Integrity）**
    * > 定义：通过外码（`FOREIGN KEY`）将不同基本表之间的实体关联严格绑定。
    * 外码未声明 `NOT NULL` 时一般允许取 NULL（代表暂时未分配关联）；若外码属性同时是本表主码的组成部分，则根据实体完整性非空铁律绝对不能取空值。
    * > 来源: P36

* **违约动作四策略**
    * 四种违约处理策略的语法与行为对照：
        | 违约动作策略 | 关键字语法 | 核心行为与业务语义 |
        | :--- | :--- | :--- |
        | 拒绝执行（默认） | `ON DELETE NO ACTION` / `RESTRICT` | 从表存在任何引用则严禁主表行被删改，抛错中断事务 |
        | 级联联动 | `ON DELETE CASCADE` / `ON UPDATE CASCADE` | 主表主键被删改时自动连带删改从表所有引用该主键的行 |
        | 自动置空 | `ON DELETE SET NULL` / `ON UPDATE SET NULL` | 主表行删改时自动将从表外码列值更新为 NULL（前提是该列允许为空） |
        | 设为默认值 | `ON DELETE SET DEFAULT` | 主表行删除时从表外码自动回退填充为预设的默认值 |
    * > 来源: P36

## 10. 用户定义完整性与约束治理

> **一句话主旨**：用户定义完整性把具体业务规则落为属性级与元组级 CHECK 约束，并用 CONSTRAINT 显式命名以支持动态维护。

### 10.1 属性级约束

* **用户定义的完整性（User-defined Integrity）**
    * > 定义：直接体现特定业务领域规则、语义契约与法律条文、针对具体应用定义的约束。
    * 由 DBMS 在数据存入时强制执行，如「月薪不低于法定最低工资」「信用卡有效期必晚于发卡日期」「性别只能二选一」。
    * > 来源: P37

* **属性级约束（Column-level Constraints）**
    * 作用对象为某一个具体单列，直接定义在该列数据类型定义之后。
    * `NOT NULL`：强制该列在任何元组中都必须有明确赋值，严禁录入 NULL。
    * `UNIQUE`：限制该属性所有非空值互不相同；一个表只能有一个主键，但可有多个 `UNIQUE` 列。
    * `CHECK`：用布尔表达式限制合法取值范围，支持范围（`Sage >= 15 AND Sage <= 45`）、枚举（`Ssex IN ('男', '女')`）与格式（`ZipCode LIKE '[0-9][0-9][0-9][0-9][0-9][0-9]'`）。
    * > 易错点：`UNIQUE` 通常允许 NULL，且多条元组的 UNIQUE 列可同时为 NULL——三值逻辑下 `NULL = NULL` 结果为 UNKNOWN，不被判定为相等。
    * > 来源: P37

### 10.2 元组级约束

* **元组级约束（Tuple-level Constraints）**
    * > 定义：当完整性业务规则涉及同一张表中多个属性列之间的逻辑关系时，属性级约束无法满足，必须在建表语句末尾声明为表级约束。
    * > 来源: P37

* **典型跨列约束**
    * 时间先后逻辑：`CHECK (StartDate <= EndDate)` 校验项目起止日期。
    * 跨列业务一致：`CHECK (Msex = '女' OR Title NOT IN ('Ms.', 'Mrs.'))` 使性别为男时尊称严禁写为 Ms.。
    * > 来源: P37

## 11. 约束命名与动态维护

> **一句话主旨**：为每个完整性约束赋予全局唯一语义化名称以便精准定位报错，并通过 ALTER TABLE 随业务规则演进动态增删。

* **约束命名子句（CONSTRAINT）**
    * 语法：`CONSTRAINT <约束名> <约束条件>`；企业级系统开发严禁写匿名的完整性约束。
    * 报错定位：匿名约束报错形如 `Error: CHECK constraint SYS_C0038192 violated`，无从判断哪一列违反了什么规则；命名为 `C_Student_Age_Range` 则一目了然。
    * 动态维护：只有具备名称的约束才能通过 `ALTER TABLE` 被精准删除或修改。
    * > 来源: P37

* **ALTER TABLE 动态维护**
    * 删除旧约束：`ALTER TABLE Student DROP CONSTRAINT C_Student_Age;`
    * 追加新约束：`ALTER TABLE Student ADD CONSTRAINT C_Student_Age_New CHECK (Sage BETWEEN 15 AND 60);`
    * > 来源: P37

## 12. 断言机制

> **一句话主旨**：断言把跨表全局约束写成声明式谓词，任何相关表变动都自动重新评估，但全量开销使其难被商用品直接支持。

* **断言（Assertion）**
    * > 定义：跨越单张基本表的声明性全局约束，语法为 `CREATE ASSERTION <断言名> CHECK (<谓词表达式>);`
    * 执行机理：涉及该断言依托的任何基本表发生增删改，DBMS 必须自动重新评估断言；谓词评估为 `FALSE` 时该操作被立即强制拒绝并全部回滚。
    * 删除：`DROP ASSERTION <断言名>;`
    * > 来源: P38

* **断言实例与工业困境**
    * 限制每门课程最多 60 人选修：`CHECK (60 >= ALL (SELECT COUNT(Sno) FROM SC GROUP BY Cno))`。
    * 困境：断言要求全库任意相关表细微变动都重跑跨表聚合查询，给高并发事务带来灾难性性能开销；主流商业数据库（如 Oracle、MySQL）通常选择不直接支持声明式断言，交由触发器实现。
    * > 来源: P38

## 13. 触发器与 ECA 机制

> **一句话主旨**：触发器由事件驱动、无需手动调用即可隐式执行，遵循 ECA 规则并在行级提供新旧值的伪行变量。

### 13.1 触发器与 ECA 规则

* **触发器（Trigger）**
    * > 定义：用户定义在基本表上、由事件驱动的特殊存储过程，不需要应用程序手动调用，而是在特定数据库写操作发生时由 DBMS 引擎自动隐式触发执行。
    * > 来源: P38

* **ECA 规则（Event-Condition-Action）**
    * 事件（Event）：究竟在发生什么底层写操作时唤醒触发器，包括 `INSERT`、`UPDATE`、`DELETE`。
    * 条件（Condition）：唤醒后经 `WHEN <条件>` 二次评估，只有条件为真时才激活动作。
    * 动作（Action）：具体执行的业务逻辑，通常是一个由 `BEGIN ... END` 包裹的过程化 SQL 代码块。
    * > 来源: P38

### 13.2 触发时机与执行粒度

* **触发时机维度**
    * `BEFORE` 前置触发：在数据落盘前执行，专门用于拦截、校验与篡改修正。
    * `AFTER` 后置触发：在数据成功写入后执行，专门用于连带级联更新。
    * > 来源: P38

* **触发执行粒度**
    * 行级触发器（`FOR EACH ROW`）：SQL 影响了 N 行，触发器就循环执行 N 次，提供 `:OLD` 与 `:NEW` 伪行变量。
    * 语句级触发器（`FOR EACH STATEMENT`）：整条 SQL 无论影响多少行，仅执行 1 次。
    * > 来源: P38

### 13.3 伪行变量

* **伪行变量（:OLD / :NEW）**
    * `:OLD` 代表该行元组在被修改或被删除之前的原始旧值快照；`:NEW` 代表该行元组正准备被插入或修改之后的新目标值。
    * > 来源: P38

* **伪行变量可用性**
    * 三种写操作下 `:OLD` 与 `:NEW` 的可用性对照：
        | 操作类型 | `:OLD` 可用性 | `:NEW` 可用性 | 核心典型用途 |
        | :--- | :--- | :--- | :--- |
        | `INSERT` | 不可用（为 NULL） | 可用（准备写入的新行） | 检查新录入字段是否合规、补充默认计算字段 |
        | `UPDATE` | 可用（修改前的老值） | 可用（修改后的新值） | 比较新旧属性变化幅度（防降薪、防跳变） |
        | `DELETE` | 可用（被删行的全量数据） | 不可用（为 NULL） | 归档已删除历史记录到审计备份表 |
    * > 来源: P38
