## 1. 数据库编程的三条技术路线与嵌入式 SQL

> **一句话主旨**：说明数据库编程要解决 SQL 与宿主语言的能力互补问题，并给出嵌入式 SQL 的预编译流程与三类通信要素。

### 1.1 数据库编程的动因与技术路线

* **数据库编程（Database Programming）**
    * > 定义：把 SQL 的集合数据操纵能力与宿主语言的过程化控制能力结合起来的开发方式。
    * 宿主语言为通用高级程序设计语言，包括 C/C++、Java、Python。
    * SQL 的能力边界：标准 SQL 不支持 `if-else` 分支、`while/for` 循环与复杂业务算法；也无法直接构建人机交互系统。
    * > 来源: P57

* **三条技术路线**
    * 嵌入式 SQL（Embedded SQL）：SQL 直接嵌入 C/COBOL 等宿主语言源码，依赖预编译器。
    * 过程化 SQL（PL/SQL）：把过程化逻辑注入 DBMS，以存储过程与函数在服务端执行。
    * 通用 API / 驱动（ODBC、JDBC）：标准接口，是现代应用开发的事实标准。
    * > 来源: P57

### 1.2 嵌入式 SQL 的预编译机制

* **预编译器（Precompiler）**
    * > 定义：把混写 SQL 与宿主语言的源码转换为纯宿主语言源码的 DBMS 专属工具。
    * 输入源码扩展名为 `*.ec` / `*.sqc`，内容为宿主语言与 `EXEC SQL` 混写。
    * 处理动作：识别并提取所有 `EXEC SQL` 块 → 转换为底层标准 DBMS 运行库的函数调用 → 生成纯净的 `*.c` 文件。
    * 流水线：预编译器 → 宿主语言编译器 → 链接器（引入数据库动态链接库）→ 最终可执行文件。
    * > 来源: P57

* **SQL 语句的语法标识**
    * 所有嵌入的 SQL 语句必须以前缀 `EXEC SQL` 开头，以分号结束：`EXEC SQL <SQL 语句>;`。
    * 通用高级语言编译器本身不认识 SQL 语法，前缀是预编译器识别语句的入口。
    * > 来源: P57

### 1.3 主变量、指示变量与 SQLCA

* **主变量（Host Variable / 共享变量）**
    * > 定义：由宿主语言程序定义、并被嵌入 SQL 语句直接引用的变量。
    * 输入主变量：应用程序把变量值作为查询条件参数传给 SQL；输出主变量：SQL 执行后把字段值回填给程序变量。
    * 声明位置：`EXEC SQL BEGIN DECLARE SECTION;` 与 `EXEC SQL END DECLARE SECTION;` 之间。
    * 在 SQL 语句中引用主变量必须加冒号前缀（如 `:my_age`），用以与表列名区分；在纯宿主语言语句中引用不加冒号。
    * > 来源: P57

* **指示变量（Indicator Variable）**
    * > 定义：配合主变量接收并判定 SQL 空值（NULL）与字符串截断长度的辅助主变量。
    * 类型为 2 字节整型 `short`，紧跟在目标主变量之后并以冒号引导（`:hs_grade :ind_grade`）。
    * 取值规范：查询返回 NULL 时置为负数（通常为 `-1`）；非空时为 `0`；发生字符串截断时记录截断前的原始长度（正数）。
    * 存在原因：C 等宿主语言没有 NULL 数据类型，只能承载 0 或空指针。
    * > 来源: P57

* **SQL 通信区（SQLCA，SQL Communication Area）**
    * > 定义：DBMS 向宿主程序反馈每一步 SQL 执行状态的数据结构。
    * 引入方式：`EXEC SQL INCLUDE SQLCA;`
    * 核心字段 `SQLCODE`：`= 0` 执行成功无异常；`> 0` 成功但有告警；`< 0` 遭遇严重错误（语法错误、主键冲突、网络中断）。
    * `SQLCODE == 100` 表示未找到符合条件的元组，或游标已读取到末尾。
    * > 来源: P57

## 2. 游标机制与当前行定位更新

> **一句话主旨**：化解 SQL 一次一集合与宿主语言一次一记录的阻抗失配，给出游标四步生命周期与定位更新语法。

* **阻抗失配（Impedance Mismatch）**
    * > 定义：SQL 的集合运算模型与宿主语言的变量模型之间的理论鸿沟。
    * SQL 是“一次一集合（Set-at-a-time）”，一条 `SELECT` 可检索上万行二维集合。
    * 高级语言变量是“一次一记录（Record-at-a-time）”，主变量通常只能容纳单个标量或单一结构体。
    * > 来源: P58

* **游标（Cursor）**
    * > 定义：在活动集（Active Set）上逐行推进、把当前行按序填充到主变量的行级缓冲指针。
    * 作用：化解集合操作与单行处理之间的冲突。
    * > 来源: P58

* **游标四步标准生命周期**
    * 第 1 步 `DECLARE`：`EXEC SQL DECLARE <游标名> CURSOR FOR <SELECT 语句>;`，仅声明性绑定逻辑 SQL，不执行查询、不占运行时内存。
    * 第 2 步 `OPEN`：`EXEC SQL OPEN <游标名>;` 正式执行查询，在系统内存开辟活动集合缓冲区；指针初始停在第一条元组之前。
    * 第 3 步 `FETCH`：`EXEC SQL FETCH <游标名> INTO <主变量1> [, <主变量2>]...;` 指针下移定位到下一条合法元组，并把各列分量按序一对一赋值给主变量。
    * 第 4 步 `CLOSE`：`EXEC SQL CLOSE <游标名>;` 销毁对应活动集，释放服务器内存与会话缓存句柄。
    * > 来源: P58

* **循环终止判定**
    * 读完最后一行后再次执行 `FETCH`，DBMS 自动把 `SQLCODE` 置为 `100`（NOT FOUND），程序据此跳出 `while` 循环。
    * `SQLCODE < 0` 表示读取发生异常，需另行处理。
    * > 来源: P58

* **`FOR UPDATE` 加锁声明**
    * 声明可更新游标时必须显式追加 `FOR UPDATE` 子句。
    * 作用：强制 DBMS 在扫描时为活动集的行施加排他锁，防止并发事务提前篡改。
    * > 来源: P58

* **`WHERE CURRENT OF` 定位更新**
    * > 定义：在 `UPDATE`/`DELETE` 中定位游标当前行、实施原地覆写的固定语法。
    * 写法：`WHERE CURRENT OF <游标名>;`
    * 不可替代性：普通单条 `UPDATE` 只能做常量赋值或统一公式的批量修改；当修改决策依赖宿主语言中的复杂过程化算法（调用外部接口、多重规则判定、二次交互确认）时必须用游标逐行提取后再定位覆写。
    * > 来源: P58

## 3. 存储过程与存储函数

> **一句话主旨**：服务端预编译封装带来的性能与安全收益，IN/OUT/INOUT 参数流转，以及存储过程与存储函数的本质分野。

### 3.1 服务端封装与三项核心优势

* **存储过程（Stored Procedure）/ 存储函数（Stored Function）**
    * > 定义：为完成特定功能的 SQL 语句与过程化控制逻辑的集合，经编译后长久保存在数据库服务器的数据字典中。
    * 应用只需发送简短调用命令（如 `CALL`）并传入必要参数，业务逻辑在服务器端内存闭环运行。
    * > 来源: P59

* **三项核心优势**
    * 预编译执行：第一次创建时 DBMS 完成语法解析与代价估算，生成二进制执行计划并常驻共享内存缓冲池，后续调用跳过编译与优化阶段。
    * 削减网络流量：将多次网络往返、反复序列化反序列化收敛为服务端本地执行，网络中只流动一条调用报文与最终标量结果。
    * 增强安全：可锁死底层物理表的直接 `SELECT`/`UPDATE` 权限，仅授予特定存储过程的 `EXECUTE` 权限，用户只能通过受控过程逻辑改数据，阻断 SQL 注入与越权篡改。
    * > 来源: P59

### 3.2 参数模式与创建调用

* **IN / OUT / INOUT 三种参数模式**
    * `IN`（默认输入模式）：外部调用者传入参数值，过程体内部只读、不可篡改外部，类似 C 语言的按值传递。
    * `OUT`（纯输出模式）：初始值为 NULL，过程体内部计算并赋值，退出时把最终值回传给调用方。
    * `INOUT`（双向模式）：外部传入初始值作为输入，过程体内部修改后作为输出回传，类似 C 语言的按引用指针传递。
    * > 来源: P59

* **创建语法与调用**
    * 骨架：`CREATE PROCEDURE <过程名> ([IN|OUT|INOUT] <参数名> <数据类型> [, ...]) BEGIN <过程化 SQL 代码块>; END;`
    * MySQL 需用 `DELIMITER //` … `DELIMITER ;` 包裹过程定义，以分号不冲突。
    * 过程中用 `DECLARE` 声明局部变量、`SELECT ... INTO` 取值、`IF ... THEN ... ELSE ... END IF;` 分支、`SET` 赋值。
    * 调用：`CALL TransferStudent('202601', '软件工程', @status);`，再用 `SELECT @status;` 读取 `OUT` 结果。
    * > 来源: P59

### 3.3 存储过程与存储函数的区别

* **二者核心区别**

| 比较维度 | 存储过程（Stored Procedure） | 存储函数（Stored Function） |
| :--- | :--- | :--- |
| 关键字 | `CREATE PROCEDURE` | `CREATE FUNCTION` |
| 返回值机制 | 无直接单一返回值，需通过 `OUT` 或 `INOUT` 参数间接传回多个值 | 强制包含 `RETURNS <类型>` 与 `RETURN <单值>` 语句 |
| 调用执行方式 | 必须通过独立的 `CALL` 语句单独触发 | 可直接嵌入在任何普通 SQL 表达式中 |
| 典型调用场景 | `CALL ProcName(p1, @out);` | `SELECT Sno, CalcRank(Grade) FROM SC;` |

* **存储函数示例要点**
    * `CREATE FUNCTION GetGradeLevel (p_grade INT) RETURNS VARCHAR(10) DETERMINISTIC`，函数体按 `>=90` 优秀、`>=80` 良好、`>=60` 及格、否则不及格分级 `RETURN`。
    * 函数可直接作为 `SELECT` 目标列表的表达式调用。
    * > 来源: P59

## 4. 过程化 SQL 的块结构、动态类型与异常

> **一句话主旨**：PL/SQL 用块结构把结构化编程要素焊进 SQL，用动态类型解耦列定义，用异常捕获体系拦截运行错误。

### 4.1 块结构与流程控制

* **PL/SQL 块结构（Block）**
    * `DECLARE`（可选）：声明局部变量、动态类型、游标与自定义异常。
    * `BEGIN`（必选）：核心业务逻辑执行体，含 `IF`/`LOOP`/`FOR` 控制语句与 `SELECT INTO`/`UPDATE`/`INSERT` 原生 SQL 语句。
    * `EXCEPTION`（可选）：运行时异常与错误拦截捕获。
    * `END;`：块结束标志，以分号闭合。
    * 运行位置：数据库内核的过程化引擎（PL Engine）。
    * > 来源: P60

* **流程控制语句**
    * 条件分支：`IF ... THEN ... ELSIF ... ELSE ... END IF;`
    * 循环结构：`WHILE v_count < 100 LOOP ... END LOOP;`
    * > 来源: P60

### 4.2 动态类型绑定（%TYPE 与 %ROWTYPE）

* **`%TYPE`（列级绑定）**
    * > 定义：让变量的数据类型与底层表的某列定义动态镜像同步。
    * 写法：`变量名 表名.列名%TYPE;`，如 `v_sname Student.Sname%TYPE;`
    * 价值：底层字段扩容或变型时程序自动无感同步适配，免去逐一修改变量长度并重新编译。
    * > 来源: P60

* **`%ROWTYPE`（行级绑定）**
    * > 定义：让变量自动成为一个包含整张表全部字段的复合记录结构体（Record）。
    * 写法：`变量名 表名%ROWTYPE;`
    * 用法：`SELECT * INTO v_stu FROM Student WHERE Sno = '202601';` 一次性装入单行数据，再用点号语法访问成员（如 `v_stu.Sname`）。
    * > 来源: P60

### 4.3 游标 FOR 循环

* **游标 FOR 循环（Cursor FOR Loop）**
    * > 定义：PL/SQL 中全自动完成游标生命周期的循环范式。
    * 自动完成四件事：隐式 `OPEN`、自动 `FETCH`、自动判空退出、自动 `CLOSE`。
    * 写法：`FOR stu_rec IN cur_cs_students LOOP ... END LOOP;`，循环变量 `stu_rec` 自动具备记录结构。
    * > 来源: P60

* **与传统手动游标的差异**
    * 传统游标需手动执行“声明 → 打开 → 推进提取 → 判空跳出 → 关闭”的繁琐步骤；FOR 循环将其全部自动化。
    * 价值：彻底杜绝程序员疏忽漏写 `CLOSE` 导致的数据库内存游标泄露事故。
    * > 来源: P60

### 4.4 异常处理体系

* **异常处理骨架**
    * `EXCEPTION WHEN <异常名1> [OR <异常名2>] THEN <处理语句>; WHEN OTHERS THEN <全局兜底处理语句>;`
    * 作用：避免除零错误、查无数据或主键冲突导致整个事务异常崩溃中断。
    * > 来源: P60

* **四大预定义系统异常（Predefined Exceptions）**

| 异常标识名 | 触发条件 | 典型应对策略 |
| :--- | :--- | :--- |
| `NO_DATA_FOUND` | `SELECT INTO` 未返回任何数据行（0 行） | 赋默认值或提示记录不存在 |
| `TOO_MANY_ROWS` | 标量 `SELECT INTO` 返回超过 1 行 | 检查外层查询条件的主键唯一性 |
| `DUP_VAL_ON_INDEX` | 插入违反 `PRIMARY KEY` 或 `UNIQUE` 索引的重复键值 | 拦截主键冲突，提示改用更新操作 |
| `ZERO_DIVIDE` | 算术运算中除数为 0 | 将分母置空或设为无穷大兜底 |

* **`OTHERS` 兜底与错误码**
    * `OTHERS` 作全局兜底，可配合 `SQLCODE`（错误码）与 `SQLERRM`（错误详情）输出未知系统异常。
    * > 来源: P60

## 5. ODBC 开放数据库互连

> **一句话主旨**：以统一 API 与厂商驱动解耦数据库产品，给出 ODBC 四层架构、DSN 数据源、三大句柄与六步工作流。

* **ODBC（Open Database Connectivity，开放数据库互连）**
    * > 定义：与特定操作系统、编程语言、底层数据库产品完全解耦的通用数据访问标准接口。
    * 目标：打破厂商私有协议壁垒，让应用面向标准接口编程，支持异构多源数据库与数据源热插拔。
    * > 来源: P61

* **四层体系架构**
    * 用户应用程序（Application）：只与标准 ODBC API 规范打交道，代码中不含任何特定数据库产品的专有头文件或底层网络库。
    * ODBC 驱动程序管理器（Driver Manager）：操作系统级调度核心（Windows 下 `odbc32.dll`、Linux 下 `unixODBC`），负责加载、配置、管理驱动，校验参数版本并路由 API。
    * 数据库驱动程序（Database Driver）：各数据库厂商针对自身产品开发的动态链接库（DLL），把通用 ODBC 函数翻译成底层原生网络报文（如 Oracle TNS 协议）。
    * 数据源（Data Source / DSN，Data Source Name）：包含数据库物理 IP、监听端口、目标库名、字符集与鉴权配置的逻辑命名实体。
    * > 来源: P61

* **三大核心句柄（Handle）**
    * 环境句柄（HENV / SQLHENV）：管理整个全局环境上下文与版本。
    * 连接句柄（HDBC / SQLHDBC）：管理与特定物理数据库的数据连接。
    * 语句句柄（HSTMT / SQLHSTMT）：管理单条正在执行的 SQL 语句与游标。
    * > 来源: P61

* **六步标准执行工作流**
    * 第 1 步分配环境句柄：`SQLAllocHandle(SQL_HANDLE_ENV, SQL_NULL_HANDLE, &henv);` 并 `SQLSetEnvAttr(..., SQL_ATTR_ODBC_VERSION, ...SQL_OV_ODBC3...)`。
    * 第 2 步分配连接句柄并连接：`SQLAllocHandle(SQL_HANDLE_DBC, henv, &hdbc);` 后 `SQLConnect(hdbc, "MyDSN", ...);`
    * 第 3 步分配语句句柄：`SQLAllocHandle(SQL_HANDLE_STMT, hdbc, &hstmt);`
    * 第 4 步执行 SQL：`SQLExecDirect(hstmt, "SELECT Sno, Sname FROM Student", SQL_NTS);`
    * 第 5 步绑定列变量并循环读取：`SQLBindCol(...)` 后用 `while (SQLFetch(hstmt) == SQL_SUCCESS)` 逐行取数。
    * 第 6 步级联释放句柄断开连接：`SQLFreeHandle`（STMT）→ `SQLDisconnect(hdbc)` → `SQLFreeHandle`（DBC、ENV）。
    * > 来源: P61

## 6. JDBC 与现代数据访问架构

> **一句话主旨**：Java 面向对象的数据库访问标准，围绕四大接口、参数化预编译防注入，以及连接池与 ORM 的生产级架构。

* **JDBC（Java Database Connectivity）**
    * > 定义：面向 Java 语言环境的数据库访问标准接口，由 Sun（现 Oracle）在吸收 ODBC 解耦思想上推出。
    * 形式：一套纯 Java 抽象接口类（`java.sql.*` 与 `javax.sql.*`），提供统一的类型安全的连接、事务、批处理与元数据能力。
    * 架构：Java 应用 → `java.sql.DriverManager` 调度 → 厂商纯 Java 驱动（Connector/J、Thin Driver）→ 目标数据库引擎。
    * > 来源: P62

* **四大核心接口调用链**
    * `DriverManager`：驱动调度与连接工厂。
    * `Connection`：代表与物理数据库的 TCP 会话通道，承担事务控制最高职责——`conn.setAutoCommit(false);`、`conn.commit();`、`conn.rollback();`
    * `PreparedStatement`：预编译语句对象，执行带参数的动态 SQL。
    * `ResultSet`：查询结果的逻辑游标迭代器，通过 `while (rs.next())` 逐行推进。
    * > 来源: P62

* **SQL 注入漏洞（Statement 字符串拼接）**
    * 致命写法：`String sql = "SELECT * FROM Users WHERE User='" + inputUser + "' AND Pwd='" + inputPwd + "'";`
    * 攻击示例：输入 `inputUser = "admin' --"`，拼接后密码校验被 SQL 注释符 `--` 截断，攻击者可无密码登录超级管理员。
    * > 来源: P62

* **`PreparedStatement` 参数化预编译**
    * > 定义：SQL 骨架先编译生成静态语法树，占位符 `?` 是不可改变语法结构的字面插槽。
    * 安全收益：无论参数中出现多少 `' OR '1'='1` 或 `--`，引擎只当作普通标量字符串处理，绝不改变原语法树分支结构。
    * 性能收益：服务端缓存预编译执行计划，循环执行 10000 次插入时骨架只编译 1 次，后续只传输二进制参数。
    * 用法：`pstmt.setString(1, inputUser);`、`pstmt.setString(2, inputPwd);` 后 `pstmt.executeQuery();`
    * > 来源: P62

* **数据库连接池（Connection Pool）**
    * 痛点：建立一次 TCP 网络连接需经历握手、协议协商、密码核验与线程开辟，开销高达几十毫秒。
    * 机制（如 HikariCP、Druid）：系统启动时预先创建一组常驻长连接池化，应用用时“借”、用完“还”，避免频繁断开重连。
    * > 来源: P62

* **对象关系映射（ORM，Object-Relational Mapping）**
    * 映射规则：把关系数据库的二维表映射为面向对象语言中的类（Class），把表中每一行元组映射为一个对象实例（Object）。
    * 主流框架：MyBatis、Hibernate、JPA，全自动完成数据对象与 SQL 之间的类型转换。
    * > 来源: P62

## 7. 关系查询处理的四阶段模型

> **一句话主旨**：把声明式 SQL 文本翻译为高效机器指令序列，经历分析、检查、优化、执行四个阶段。

* **关系查询处理（Relational Query Processing）**
    * > 定义：将高级声明式 SQL 文本翻译并转化为底层执行效率最高的机器指令操作序列，并在物理介质上执行。
    * 关系数据库高度非过程化，用户只说明“要什么”，不告诉系统“怎么取”。
    * > 来源: P63

* **阶段 1 查询分析（Parsing）**
    * 词法分析：从 SQL 字符流中识别独立有效词素（关键字 `SELECT`、标识符 `Student`、运算符 `>`、常量 `'20'`）。
    * 语法分析：依据 SQL 文法检查语句合规性，把平面文本构造成一棵层次分明的语法分析树（Parse Tree）。
    * > 来源: P63

* **阶段 2 查询检查（Checking）**
    * 语义有效性检查：访问系统数据字典，检验数据库名、表名、列名是否真实存在。
    * 用户安全权限审查：检验连接用户是否对目标表拥有 `SELECT` 或 `UPDATE` 存取权限。
    * 完整性约束与视图消解：若查询涉及视图，在此阶段执行视图消解合并。
    * 产出：把语法树转化为内嵌核心运算的初始关系代数表达式（关系代数语法树）。
    * > 来源: P63

* **阶段 3 查询优化（Optimization）**
    * 任务：通过逻辑代数优化（规则变换）与物理优化（基于代价模型 CBO 估算 I/O 与 CPU 开销），从指数级候选路径中选代价最低者。
    * 产出：执行计划（Execution Plan）。
    * > 来源: P63

* **阶段 4 查询执行（Execution）**
    * 依据执行计划生成底层代码或算子流水线（Volcano 迭代器模型）。
    * 调用底层存储管理器执行磁盘 I/O、内存页面加载与比较过滤，最终把格式化结果集回传客户端。
    * > 来源: P63

## 8. 连接的三种物理实现算法

> **一句话主旨**：连接是关系数据库最耗算力与 I/O 的瓶颈，三种物理算法的适用场景与复杂度各不相同。

* **连接运算的核心地位**
    * 连接运算是最耗费算力与 I/O 的核心瓶颈。
    * 现代引擎实现三种主流物理连接算法：嵌套循环连接、排序合并连接、散列哈希连接。
    * > 来源: P63

* **嵌套循环连接（Nested Loop Join，NLJ）**
    * 逻辑：对外层表 R 的每个元组，遍历内层表 S 的每个元组，键值相等则输出拼接结果。
    * 复杂度：$O(|R| \times \log|S|)$。
    * 带索引优化（Index Nested Loop Join）：驱动表（外表）极小且被驱动表（内表）连接键上有 B+ 树索引时，外表每取一行，内表直接走 B+ 树做 $O(\log n)$ 检索，无需扫描整张内表。
    * > 来源: P63

* **排序合并连接（Sort-Merge Join，SMJ）**
    * 逻辑两阶段：先排序（若两表未按连接键有序，用外部归并排序分别升序排好），再合并扫描（在 R、S 上设双指针从小到大同步前移比对，相同直接合并输出）。
    * 特点：每个物理块最多只被读取一次；复杂度为 $O(N \log N)$ 排序加扫描。
    * 适用场景：连接条件含 `<, <=, >, >=` 等范围比较，或两表已通过聚集索引物理有序。
    * > 来源: P63

* **散列哈希连接（Hash Join，HJ）**
    * 逻辑两阶段：构建阶段选取基数较小的构建输入表，全部载入内存并用哈希函数对连接键散列，建立散列表；探测阶段顺序扫描另一张大表（探测输入表），逐行计算同样哈希值去内存散列表瞬时命中匹配（$O(1)$）。
    * 优势：完全不需要预先排序，在海量乱序大数据等值连接场景下吞吐量远超传统循环。
    * 复杂度：近似线性 $O(|R| + |S|)$。
    * > 来源: P63

* **三种算法横向对比**

| 算法 | 核心逻辑 | 复杂度 | 最佳适用场景 |
| :--- | :--- | :--- | :--- |
| 嵌套循环连接（NLJ） | 双重循环比对 | $O(\|R\| \times \log\|S\|)$ | 外表很小、内表连接键有索引 |
| 排序合并连接（SMJ） | 先排序后双指针归并 | $O(N \log N)$ 排序 + 扫描 | 范围连接、或数据本已物理有序 |
| 散列哈希连接（HJ） | 小表建哈希表、大表探针 | 近似线性 $O(\|R\| + \|S\|)$ | 海量无序大数据的等值连接 |

* **算法选择示例**
    * 表 R 仅 100 行、表 S 有 10,000,000 行，等值条件 `R.ID = S.ID` 且 `S.ID` 有 B+ 树聚簇索引。
    * 应选带索引的嵌套循环连接：以 R 为外层驱动表，每次外层迭代走 B+ 树对数级寻道（每次约 3~4 次 I/O），全表连接约 $100 \times 4 = 400$ 次磁盘页读取，耗时数毫秒。
    * > 来源: P63

## 9. 关系代数等价变换规则

> **一句话主旨**：逻辑优化的数学基石是关系代数等价性，七大变换定理构成查询优化器的规则库，选择下推是核心王牌。

* **等价（Equivalence）**
    * > 定义：若对关系数据库的任意一个合法关系实例，两个关系代数表达式 $E_1$ 与 $E_2$ 计算所得结果关系完全相同（同模式、同元组集合），则称两者等价，记作 $E_1 \equiv E_2$。
    * 优化本质：在全部数学等价的表达式中，寻找物理执行时中间数据最少、I/O 资源占用最少的表达式。
    * > 来源: P64

* **定理 1 连接与笛卡尔积的交换律与结合律**
    * 交换律：$E_1 \times E_2 \equiv E_2 \times E_1$；$E_1 \Join_F E_2 \equiv E_2 \Join_F E_1$；$E_1 \Join E_2 \equiv E_2 \Join E_1$
    * 结合律：$(E_1 \times E_2) \times E_3 \equiv E_1 \times (E_2 \times E_3)$；$(E_1 \Join_F E_2) \Join_G E_3 \equiv E_1 \Join_F (E_2 \Join_G E_3)$
    * 优化价值：可自由调换多表连接先后次序，优先让能大幅缩减数据量的表先连接。
    * > 来源: P64

* **定理 2 选择算子的串接律**
    * $\sigma_{F_1 \land F_2}(E) \equiv \sigma_{F_1}(\sigma_{F_2}(E)) \equiv \sigma_{F_2}(\sigma_{F_1}(E))$
    * 优化价值：把复合过滤条件打散为原子条件，为向不同子表分别下推奠定基础。
    * > 来源: P64

* **定理 3 投影算子的串接律**
    * $\pi_{A_1,\dots,A_n}(\pi_{B_1,\dots,B_m}(E)) \equiv \pi_{A_1,\dots,A_n}(E)$，其中 $\{A_i\} \subseteq \{B_j\}$。
    * 优化价值：只有最外层投影真正生效，可直接消除无意义的冗余中间投影。
    * > 来源: P64

* **定理 4 选择与连接/笛卡尔积的分配律（优化核心）**
    * 单表条件下推：若 $F$ 涉及属性全部来自 $E_1$，则 $\sigma_F(E_1 \Join E_2) \equiv (\sigma_F(E_1)) \Join E_2$；对笛卡尔积同理 $\sigma_F(E_1 \times E_2) \equiv (\sigma_F(E_1)) \times E_2$。
    * 双表条件各自下推：若 $F = F_1 \land F_2$，$F_1$ 只涉及 $E_1$、$F_2$ 只涉及 $E_2$，则 $\sigma_{F_1 \land F_2}(E_1 \Join E_2) \equiv (\sigma_{F_1}(E_1)) \Join (\sigma_{F_2}(E_2))$。
    * 优化价值：选择算子跨越昂贵的连接下推到基表，可带来数量级性能飞跃。
    * > 来源: P64

* **定理 5 选择与投影的交换律**
    * 若 $F$ 涉及的属性都包含在投影属性集 $A$ 中，则 $\sigma_F(\pi_A(E)) \equiv \pi_A(\sigma_F(E))$。
    * 若 $F$ 涉及不在 $A$ 中的属性 $B$，则可先扩展投影包含 $B$，完成选择后再最终投影去除 $B$。
    * > 来源: P64

* **等价变换推导示例**
    * 原始表达式：$E_{\text{raw}} = \pi_{\text{Sname}}(\sigma_{\text{Student.Sno}=\text{SC.Sno} \land \text{Sdept}='CS'}(\text{Student} \times \text{SC}))$
    * 第 1 步用选择串接律拆开复合条件；第 2 步因 `Sdept='CS'` 仅属 Student，用分配律下推到笛卡尔积下方；第 3 步把外层的笛卡尔积与其上方的等值选择合并为等值连接。
    * 结果：先筛出计算机系少量学生再发起索引连接，执行代价缩减 99% 以上。
    * > 来源: P64

## 10. 查询树的启发式优化

> **一句话主旨**：把关系代数表达式实例化为查询树，用下推准则与五步算法把朴素树重构为中间数据最少的执行树。

* **关系代数语法树（Query Tree）**
    * 叶子结点（Leaf Nodes）：查询依托的物理基本表（Base Tables）。
    * 内部非叶结点（Internal Nodes）：施加在数据流上的关系代数运算算子（选择 $\sigma$、投影 $\pi$、连接 $\Join$、笛卡尔积 $\times$）。
    * 根结点（Root Node）：最终输出给用户的查询结果集合。
    * 边（Edges）：中间数据关系的流动方向（自底向上流转）。
    * > 来源: P65

* **启发式优化的下推准则**
    * 选择运算尽可能先做：数据刚从叶子磁盘读入时立即做最大程度行过滤，杜绝无效元组进入上层高成本计算。
    * 投影运算尽可能先做：及早丢弃后续不再使用的列，压窄中间元组物理宽度，提升单页缓存密度。
    * 将相邻的选择与笛卡尔积合并为连接运算：消除无约束的笛卡尔积展开，转为精准哈希或索引连接。
    * 提取公共子表达式：多处逻辑共享相同子树时只计算一次并缓存结果。
    * > 来源: P65

* **启发式查询树优化五步算法**
    * 第 1 步拆解选择：用选择串接律把所有复合条件 $\sigma_{F_1 \land F_2 \land \dots \land F_n}$ 拆为单一原子选择算子。
    * 第 2 步选择算子下推：单表条件直接推到该基本表叶子节点正上方；跨表连接条件推到这两张表做笛卡尔积/连接算子的正上方。
    * 第 3 步消除笛卡尔积：把笛卡尔积算子与其紧邻上方的等值选择合并为等值连接 $\Join_{A=B}$ 或自然连接。
    * 第 4 步投影算子下推：把最终所需投影属性连同沿途选择与连接必须依赖的属性（主外键）组合，下推到各中间节点与基表上方，及早削减列宽。
    * 第 5 步树形剪枝收敛：消除连续冗余投影，合并相邻算子，输出最优关系代数执行树。
    * > 来源: P65

* **三表连接优化实例**
    * 查询：`SELECT Student.Sname, SC.Grade FROM Student, Course, SC WHERE Student.Sno=SC.Sno AND SC.Cno=Course.Cno AND Course.Cname='数据库系统概论';`
    * 未优化树：先做三表全量广义笛卡尔积再过滤；设学生 1 万人、选课 10 万条、课程 1000 门，中间元组达 $10^4 \times 10^5 \times 10^3 = 10^{12}$（一万亿）条，服务器内存崩溃。
    * 优化后：`Course` 先过滤为 1 门；与 `SC` 走索引连接筛出约 100 条记录；再与 `Student` 基于学号索引做 100 次点查连接；全过程仅处理数百条元组，耗时从几小时缩短至 2 毫秒。
    * 优化后的执行树：

    ```text
                    π_(Sname, Grade)
                           │
                           ⋈ (基于 Sno 连接)
                         /   \
       π_(Sno, Sname)     π_(Sno, Grade)
              │                  │
           Student               ⋈ (基于 Cno 连接)
                               /   \
              π_(Sno, Cno, Grade)   π_(Cno)
                     │                 │
                     SC        σ_(Cname='数据库系统概论')
                                       │
                                     Course
    ```
    * > 来源: P65

## 11. 物理优化与基于代价的优化

> **一句话主旨**：逻辑优化只定运算次序，物理优化裁决存取路径与算法，CBO 依靠统计信息与选择度选择总代价最小的计划。

* **物理优化（Physical Query Optimization）**
    * > 定义：对底层硬件执行算法与物理存取路径（Access Path）作出最终裁决的过程。
    * 待裁决问题：选择算子走全表扫描还是 B+ 树辅助索引；连接算子选嵌套循环、排序合并还是散列哈希；两表连接谁作外层驱动表。
    * > 来源: P66

* **RBO 与 CBO 两大流派**

| 维度 | 基于规则的优化器（RBO） | 基于代价的优化器（CBO） |
| :--- | :--- | :--- |
| 决策依据 | 预设的静态优先级经验规则（如唯一索引 > 范围索引 > 全表扫描） | 数据字典中的真实统计信息 |
| 能力边界 | 无法感知数据量与数据倾斜（表仅 5 行也死板走索引，反而变慢） | 精算 I/O 块数、CPU 周期与内存开销，动态选取总代价最小计划 |
| 现状 | 早期规则式 | 现代主流数据库绝对标配 |

* **CBO 的总代价模型**
    * $\text{Total Cost} = C_{\text{I/O}} \times W_{\text{I/O}} + C_{\text{CPU}} \times W_{\text{CPU}} + C_{\text{MEM}} \times W_{\text{MEM}}$
    * 物理 I/O 代价 $C_{\text{I/O}}$：磁盘加载到内存的数据页（Blocks/Pages）数量，因磁盘访问以毫秒计，通常权重最高。
    * CPU 计算代价 $C_{\text{CPU}}$：元组比较、谓词过滤、哈希运算与排序的指令周期开销。
    * 内存缓冲开销 $C_{\text{MEM}}$：排序区与哈希表占用的工作内存空间。
    * > 来源: P66

* **统计信息指标体系**
    * $T(R)$：关系 $R$ 的总元组行数。
    * $B(R)$：关系 $R$ 占用的物理磁盘块总数（Data Blocks）。
    * $V(A, R)$：属性 $A$ 在关系 $R$ 中的不同取值基数（Number of Distinct Values）。
    * 列的数据直方图（Histograms）：记录数据分布倾斜特征，例如全校 90% 学生集中在计算机系、天文系仅 1%。
    * > 来源: P66

* **选择度（Selectivity）估算**
    * > 定义：满足过滤条件的元组占全表总元组数的比例 $S$，$0 \le S \le 1$。
    * 等值单条件 $\sigma_{A=\text{常数}}$：假定数据均匀分布，$S = \dfrac{1}{V(A,R)}$，预估行数 $\text{Rows} = T(R) \times S = \dfrac{T(R)}{V(A,R)}$。
    * 范围条件 $\sigma_{A>\text{常数}}$：结合最小值与最大值线性插值，$S = \dfrac{\text{MAX}(A) - \text{常数}}{\text{MAX}(A) - \text{MIN}(A)}$。
    * > 来源: P66

* **全表扫描与索引扫描的抉择临界点**
    * 高选择性（$S < 5\% \sim 15\%$，命中行极少数）：果断走 B+ 树索引扫描，定位少量目标行，回表 I/O 极少。
    * 低选择性（$S > 15\% \sim 20\%$，大面积命中）：果断顺序全表物理扫描，连续物理块大并发顺序预读，避免海量随机回表 I/O 造成磁头抖动灾难。
    * > 易错点：建了索引却被 `EXPLAIN` 显示走全表扫描并非优化器 BUG。当查询命中表中 30% 以上数据时，走辅助索引需成千上万次随机离散回表寻道，代价远高于一次顺序扫盘，优化器会科学地放弃索引。
    * > 来源: P66
