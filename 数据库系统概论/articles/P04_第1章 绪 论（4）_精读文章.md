# 数据库系统体系结构（四）：三级模式、二级映像与数据独立性本质

## 1. 核心概念与本质内涵：型与值的辨析（模式与实例）

在深入剖析现代数据库管理系统的内部体系结构之前，必须首先确立数据库理论中两个不可混淆的基石概念：**模式（Schema）**与**实例（Instance）**。

### 1.1 模式（Schema）与实例（Instance）的形式化界定

计算机程序设计语言中，“数据类型（Type）”与“变量取值（Value）”具有明确的分界。数据库系统同样遵循这一基本思想：

```text
  【型 (Type) - 相对稳定】                    【值 (Value) - 动态演化】
         模式 (Schema)                               实例 (Instance)
               │                                            │
  • 数据库全体逻辑结构与特征描述               • 数据库在某一特定时刻存储的具体数据
  • 包含实体名、属性名、数据类型与约束         • 随插入、删除、修改操作实时变化
  • 设计建库时一次性确立，极少变动             • 任意时刻状态均为模式的一个合法实例
```

1. **模式（Schema）**：
   - 定义：数据库中全体数据的逻辑结构和特征的描述；
   - 包含内容：定义了有哪些实体型、各实体型包含哪些属性、各属性的取值范围（域）、主外码定义以及相互之间的语义约束规则；
   - 本质特性：模式仅仅涉及“型”的描述，不涉及具体的数值。**模式是相对稳定的，在系统设计时确定后极少发生变动**。

2. **实例（Instance）**：
   - 定义：模式的一个具体值，即数据库在某一特定时刻所保存的具体数据内容的状态快照；
   - 本质特性：同一个模式可以对应无数个不同的实例。随着应用程序不断执行数据的插入、更新和删除，**数据库的实例是高度动态、时刻变动更新的**。

## 2. 数据库系统的三级模式结构与内部调度机制

为了有效组织数据、降低系统复杂性并提供安全隔离，ANSI/SPARC（美国国家标准学会标准化计划与规约委员会）于 1975 年提出了经典的**三级模式结构（Three-schema Architecture）**。现代主流商用 DBMS 内部均严格遵循该体系设计。

```text
               用户层 (Users & Applications)
        ┌───────────────────┬───────────────────┐
        ▼                   ▼                   ▼
    应用系统 A          应用系统 B          交互式查询用户
        │                   │                   │
  [外模式 1 (视图 A)]   [外模式 2 (视图 B)]   [外模式 3 (视图 C)]
        └───────────────────┼───────────────────┘
                            ▼  【外模式 / 模式 映像】(保证逻辑独立性)
  +-----------------------------------------------------------------+
  |             模式 (Schema / 概念模式 / 全局逻辑视图)             |
  |             (全体数据的逻辑结构和特征，全局唯一)                |
  +-----------------------------------------------------------------+
                            │
                            ▼  【模式 / 内模式 映像】(保证物理独立性)
  +-----------------------------------------------------------------+
  |             内模式 (Internal Schema / 存储模式)                 |
  |             (数据物理存储结构、组织方式、索引与路径)            |
  +-----------------------------------------------------------------+
                            │ 物理 I/O
                            ▼
                     物理存储介质 (磁盘 / 阵列)
```

### 2.1 外模式（External Schema / 子模式 / 用户模式）

- **定义**：是数据库用户（包括应用程序员和最终用户）能够看见和使用的**局部数据的逻辑结构和特征的描述**，是数据库用户的数据视图；
- **数量规则**：**一个数据库可以有多个外模式**；
- **设计考量**：
  1. **面向特定业务与安全隔离**：不同业务部门的需求不同。例如财务部门的外模式只包含员工工号与薪资字段；人事部门的外模式只包含员工工号、籍贯和学历字段。外模式使得用户只能访问系统授权其可见的数据，构成了数据库安全性的第一道逻辑屏障；
  2. **降低应用复杂度**：外模式通常通过 SQL 视图（VIEW）机制实现，对最终用户屏蔽了复杂的多表关联底层细节。

### 2.2 模式（Schema / 概念模式 / 逻辑模式）

- **定义**：是数据库中**全体数据的逻辑结构和特征的描述**，是所有用户的公共数据视图；
- **数量规则**：**一个数据库有且仅有一个模式**；
- **核心定位**：
  - 模式是数据库系统体系结构的**核心枢纽**；
  - 它不仅描述所有实体的属性结构（例如完整的全量学生表、课程表、成绩表定义），还涵盖实体之间的相互联系以及所有的全局完整性约束；
  - 模式完全独立于数据的物理存储细节（不涉及具体的磁盘文件组织、页大小或 B+ 树扇出比），也独立于具体的编程语言和终端应用程序。

### 2.3 内模式（Internal Schema / 存储模式）

- **定义**：是数据**物理结构和存储方式的描述**，是数据在数据库内部的组织方式；
- **数量规则**：**一个数据库有且仅有一个内模式**；
- **包含范畴**：
  - 记录在磁盘上的物理存储方式（如定长存储还是变长压缩存储）；
  - 物理块与页（Page）的划分策略；
  - 索引的物理组织形式（如聚簇索引、非聚簇 B+ 树索引、哈希索引）；
  - 数据的加密与物理压缩规约。

## 3. 二级映像与数据独立性的实现机理

数据库系统之所以能够实现高水平的**数据独立性（Data Independence）**，其本质秘密完全在于 DBMS 在三级模式之间提供的**二级映像机制**。

### 3.1 外模式/模式映像（External/Conceptual Mapping）——保证逻辑独立性

- **映射机制**：对于每一个外模式，数据库系统都提供一个外模式与模式之间的对应映射定义；
- **逻辑独立性（Logical Data Independence）的生效机理**：
  - 当数据库的总体逻辑结构（模式）发生变更时（例如：为了支撑新业务，在学生关系中增加了“手机号”和“微信号”两个新属性，或者将某个关系进行了无损模式分解）；
  - 数据库管理员（DBA）只需相应地**修改相关的「外模式/模式映像」定义**；
  - 既有的外模式本身可以保持完全不变，使得面向该外模式编写的既有应用程序无需修改任何源代码，系统重新编译即可直接运行。

### 3.2 模式/内模式映像（Conceptual/Internal Mapping）——保证物理独立性

- **映射机制**：数据库系统提供唯一的全局模式与内模式之间的对应映射定义；
- **物理独立性（Physical Data Independence）的生效机理**：
  - 当数据库的物理存储结构发生改变时（例如：系统升级，将机械硬盘阵列更换为高速 NVMe SSD，更改了数据文件的存储目录；或者为了加速查询，在某个频繁过滤的字段上新增了 B+ 树索引，重组了磁盘聚簇）；
  - DBA 只需相应地**修改「模式/内模式映像」定义**；
  - 全局概念模式（Schema）本身保持稳定不变，进而所有的外模式与上层应用程序完全无感、不需要做任何调整。

> **提示**：二级映像机制将数据的“外部呈现”、“逻辑核心”与“物理存储”彻底解耦。正是这两层动态转换机制，将应用程序从繁重脆弱的底层存储细节中彻底解放出来，构成了数据库技术的最大工程价值。

## 4. 典型例题与深度认知辨析

### 辨析 1：三级模式中，谁是唯一的？谁是多样的？

- **归纳总结**：
  - **外模式（External）**：**多个**（不同部门、不同应用拥有各自专属的外模式视图）；
  - **概念模式（Schema）**：**有且仅有一个**（全局统一的业务实体与联系逻辑核心）；
  - **内模式（Internal）**：**有且仅有一个**（全局统一的底层物理磁盘组织规则）。

### 辨析 2：为什么修改物理存储不需要改动用户程序？

- **推导路径**：
  1. 物理结构改变 $\rightarrow$ 内模式改变；
  2. DBA 修改「模式/内模式映像」；
  3. 概念模式保持不变；
  4. 概念模式不变 $\implies$ 「外模式/模式映像」无需改动；
  5. 外模式保持不变 $\implies$ 依赖于外模式编写的应用程序完全无需改动。
  6. 结论：此即**物理独立性**。

## 5. 随堂巩固自测

### 自测题 1（单项选择题）
在数据库的三级模式结构中，用于保证数据“逻辑独立性”的是（ ）
A. 模式/内模式映像  
B. 外模式/模式映像  
C. 外模式/内模式映像  
D. 模式/应用映像  

**【答案】**：B  
**【解析】**：
- 当模式（总体逻辑结构）改变时，通过修改「外模式/模式映像」使外模式保持不变，从而保证应用程序不改，对应的是数据的**逻辑独立性**；
- 「模式/内模式映像」对应的是数据的**物理独立性**；系统不存在所谓“外模式/内模式映像”。故选 B。

---

### 自测题 2（综合辨析题）
数据库管理员在系统上线半年后，发现针对学生表的查询响应变慢，因此在 `Student` 表的 `Sname` 属性上创建了一个非聚簇 B+ 树索引，并调整了底层的磁盘数据页填充因子。
请问：
1. 这一操作引起了三级模式中哪一级模式的修改？
2. 该操作会破坏既有应用程序的兼容性吗？请结合二级映像机理解释原因。

**【参考答案与解析】**：
1. **修改的模式层级**：创建索引与调整数据页填充因子属于底层存储路径和物理组织规约的变更，因此引起了**内模式（Internal Schema）**的修改；
2. **应用程序兼容性判定与机理解析**：
   - 该操作**绝不会**破坏既有应用程序的兼容性；
   - **原因剖析**：当内模式改变时，DBMS 通过调整「模式/内模式映像」吸收该变化，而全局概念模式（Schema）中的实体属性定义、数据类型与完整性约束并未发生任何改变。既然概念模式未变，上层的外模式及其应用程序完全不受波及，既有查询语句无需修改任何代码即可透明地享受到底层新索引带来的性能加速。这正是数据库系统**物理独立性**的具体体现。
