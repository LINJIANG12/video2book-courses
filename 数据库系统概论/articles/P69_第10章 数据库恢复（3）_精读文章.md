# 数据库恢复策略与检查点技术（三）：REDO/UNDO队列算法与检查点加速机理

## 1. 核心概念与本质内涵：三大故障的标准恢复处理机制

依据故障类型的不同，数据库恢复子系统采取高度特异化的恢复策略：

```text
               三大故障类型的标准恢复处置策略
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
【1. 事务故障的恢复】                           【2. 系统故障的恢复 (软崩溃)】
 反向扫描日志文件                               正向扫描日志，构建双队列:
 • 找到该事务的更新操作                         • 已提交事务 ──> 放入 REDO 队列 (重做)
 • 执行逆操作 (用旧值 BI 覆盖)                  • 未提交事务 ──> 放入 UNDO 队列 (撤销)
 • 直到该事务的 BEGIN 记录为止                  (先全部撤销未完事务，后全部重做已完事务)
                                                       │
                               ┌───────────────────────┘
                               ▼
                 【3. 介质故障的恢复 (硬崩溃)】
                  • 1. 重装最新的物理数据库转储备份
                  • 2. 重装转储开始以后的日志文件副本
                  • 3. 重放日志: 重新执行所有已提交事务 (REDO)
```

## 2. 传统日志扫描的致命性能痛点

在传统的恢复策略中，每当系统突发断电崩溃重启时，恢复程序必须**从日志文件的开头（从建库以来的第一行日志）一直顺序扫描到文件末尾**：
1. **耗时极其漫长**：生产系统常态化运行数月，日志积累可达数百 GB 甚至数 TB，全量扫描可能耗费数小时乃至数天，导致企业停机时间（RTO，Recovery Time Objective）严重违约；
2. **产生大量无意义的重做**：许多半年前就已经提交的事务，其数据早已在磁盘中安全固化，但在传统机制下仍被迫重复执行一次 REDO，造成极其巨大的算力浪费。

为了终结这一弊端，现代数据库系统无一例外地采用了**具有检查点（Checkpoint）的恢复技术**。

## 3. 具有检查点（Checkpoint）的恢复技术核心机理

### 3.1 检查点记录与定周期刷盘机制
DBMS 设立专门的后台检查点进程，以固定时间间隔（如每隔 5 分钟）定期执行以下**三项原子性保障操作**：
1. **将日志缓冲区中的所有日志记录强制刷入磁盘**；
2. **将内存缓冲池中所有的脏数据页（Dirty Pages）强制刷入物理数据库磁盘（Flush to Disk）**；
3. **在磁盘日志文件中写入一条特殊的检查点记录（Checkpoint Record）**，记录当前时刻正在活跃运行的所有事务清单及其在日志中的起始位置。

```text
               检查点时刻的物理状态保真
检查点时刻 t_c 到达!
         │
         ▼
 内存中的全部脏数据页全部被强制同步刷入物理磁盘!
         │
         ▼
 写入检查点记录 [CHECKPOINT: Active_Transactions = {T2, T3}]
         │
         ▼
 【关键定理】: 凡是在 t_c 之前就已经成功 COMMIT 的事务，
             其修改后的数据此时【百分之百已经安全保存在物理磁盘中】!
             ===> 重启时彻底无需对它们进行任何 REDO 重做!
```

## 4. 具有检查点的系统故障恢复四步判定算法

当系统突发崩溃重启时，恢复程序**只需逆向扫描日志定位到最近的一个检查点记录**，并按照以下四个标准步骤构建 **REDO 队列** 与 **UNDO 队列**：

```text
               检查点恢复决策时空分布图
               t_c (检查点时刻)              T_f (故障发生时刻)
──────────────────────┼──────────────────────────────┼─────> 时间轴
                      │                              │
[T1]: ─── 提交 ───┤   │                              │ (t_c 前提交: 彻底不管!)
                      │                              │
[T2]: ───────────────┼─────────────── 提交 ────────┤ (跨越检查点，已提交: REDO)
                      │                              │
[T3]: ───────────────┼────────────────────────────── (跨越检查点，未提交: UNDO)
                      │                              │
[T4]:                 │ ── 启动 ─── 提交 ──────────┤ (检查点后启动，已提交: REDO)
                      │                              │
[T5]:                 │ ── 启动 ──────────────────── (检查点后启动，未提交: UNDO)
```

### 4.1 四类事务判定黄金法则：
1. **在检查点时刻 $t_c$ 之前已经提交的事务（如 $T_1$）**：
   - 数据必然已经通过检查点操作固化在物理磁盘中；
   - **既不需要 REDO，也不需要 UNDO**，直接忽略！
2. **在检查点时刻 $t_c$ 处于活跃状态，但在故障发生时刻 $T_f$ 之前已经提交的事务（如 $T_2$）**：
   - 虽然已提交，但脏页可能未及再次刷盘，**放入 REDO 队列**；
3. **在检查点时刻 $t_c$ 处于活跃状态，但在故障发生时刻 $T_f$ 尚未提交的事务（如 $T_3$）**：
   - 包含部分未完工修改，**放入 UNDO 队列**；
4. **在检查点时刻 $t_c$ 之后才启动运行的事务**：
   - 若在故障前已提交（如 $T_4$）$\implies$ **放入 REDO 队列**；
   - 若在故障前未提交（如 $T_5$）$\implies$ **放入 UNDO 队列**。

## 6. 随堂巩固自测

### 自测题 1（单项选择题）
在具有检查点（Checkpoint）的系统故障恢复机制中，对于在检查点记录写入时刻之前就已经成功提交（COMMIT）的事务，在系统崩溃重启恢复时，系统应该采取的处理方式是（ ）
A. 必须放入 UNDO 队列执行撤销  
B. 必须放入 REDO 队列执行重做  
C. 既不需要执行 REDO，也不需要执行 UNDO  
D. 必须重新装载最新的全量数据备份  

**【答案】**：C  
**【解析】**：检查点机制在写入日志时，已经强制将内存中所有的脏数据页刷新写入了磁盘物理介质。因此，凡是在检查点时刻前就已经提交的事务，其物理修改必然已经安全持久化，重启时既无需重做也无需撤销。故选 C。

### 自测题 2（经典考研恢复推导大题）
设有 5 个事务 $T_1, T_2, T_3, T_4, T_5$ 在系统中并发执行。系统日志按时间顺序记录了如下关键事件序列：
1. $T_1$ 开始，修改数据；
2. $T_2$ 开始，修改数据；
3. $T_1$ 提交（COMMIT）；
4. **系统建立检查点（CHECKPOINT，此时活跃事务为 $T_2$）**；
5. $T_3$ 开始，修改数据；
6. $T_2$ 提交（COMMIT）；
7. $T_4$ 开始，修改数据；
8. $T_4$ 提交（COMMIT）；
9. $T_5$ 开始，修改数据；
10. **系统突然遭遇断电软崩溃！**  
请问：在重新上电后，恢复子系统应将哪些事务放入 **REDO 队列**？将哪些事务放入 **UNDO 队列**？哪些事务**无需做任何处理**？

**【参考答案与步骤解析】**：
1. **无需做任何处理的事务**：**$T_1$**  
   - 理由：$T_1$ 在检查点建立（步骤 4）之前就已经成功提交（步骤 3），其数据在检查点时刻已经强制刷盘固化，故既无需 REDO，也无需 UNDO。
2. **放入 REDO 队列的事务**：**$T_2$ 和 $T_4$**  
   - 理由：$T_2$ 在检查点后完成提交（步骤 6）；$T_4$ 在检查点后启动并在故障前成功提交（步骤 8）。根据事务持续性要求，必须重做已提交的修改。
3. **放入 UNDO 队列的事务**：**$T_3$ 和 $T_5$**  
   - 理由：$T_3$ 在检查点后启动（步骤 5），至故障发生时从未提交；$T_5$ 在步骤 9 启动，至故障发生时亦未提交。根据事务原子性要求，必须使用日志中的旧值完全撤销其半拉子修改。
