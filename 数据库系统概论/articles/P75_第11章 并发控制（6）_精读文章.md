# 封锁粒度与意向锁全景（六）：多粒度树、意向锁五元矩阵与全书知识体系终极大闭环

## 1. 核心概念与本质内涵：什么是封锁粒度？

在关系数据库并发控制中，加锁的对象究竟应该多大？
封锁的对象可以是很大的逻辑单元（如整个数据库、一张完整的基本表），也可以是很小的逻辑单元（如表中的某一行元组、某个具体的属性字段），甚至可以是物理单元（如一个 16KB 数据页或磁盘块）。

**封锁对象的大小，在数据库理论中被称为封锁粒度（Lock Granularity）**。

```text
               封锁粒度的并发度与系统开销权衡天平
           粗粒度 (如: 表锁 Table Lock)           细粒度 (如: 行锁 Row Lock)
     ───────────────────────────────────   ───────────────────────────────────
     • 系统需要管理的锁对象极少             • 系统需要为每行维护锁结构，内存开销大
     • 锁冲突概率极大，并发度极低           • 锁冲突概率极小，高并发性能极其强悍
     • 适合: 批量离线数据备份、整表重构     • 适合: 互联网高并发在线联机事务 (OLTP)
```

## 2. 多粒度封锁树与全表扫描性能瓶颈

为了兼顾不同业务场景的需求，现代数据库系统支持**多粒度树形封锁机制（Multiple Granularity Tree）**：

```text
               多粒度树形层次拓扑结构
                    [ 数据库 (Database) ]
                              │
                    [ 关系表 (Relation) ]
                              │
                    [ 数据页 (Page) ]
                              │
                    [ 单行元组 (Tuple) ]
```

### 2.1 隐式封锁与显式封锁
- **显式封锁（Explicit Locking）**：事务直接向某个节点施加的锁（如事务对表加了表锁）；
- **隐式封锁（Implicit Locking）**：当上层父节点被显式加锁后，其**所有下层后裔节点自然自动受到该锁的约束**（例如：对整张表加了 X 锁，表中所有的 100 万行元组隐式自动全部被上了 X 锁）。

---

### 2.2 致命性能瓶颈：多粒度共存下的全量遍历检查难题

> **【没有意向锁时的架构灾难】**：
> 1. 事务 $T_1$ 正在对某电商订单表中的**某一行元组**执行更新，持有该行的行级 X 锁；
> 2. 事务 $T_2$ 随后由于要执行整表重组，试图对该订单表申请一个**表级的排他 X 锁**；
> 3. 此时，锁管理器如何判定 $T_2$ 的申请能否批准？
>    - 按照多粒度规则，如果表中有任何一行被加了 X 锁，表级 X 锁就绝不能批准；
>    - **恐怖代价**：锁管理器必须沿着树形结构，**将表中的全部 1000 万行元组逐行扫描遍历一遍**，以确认其中是否藏有一把行锁！
>    - 每次申请表锁都要耗费数秒进行全表数千万次比对，系统并发性能彻底崩溃！

## 3. 破局神器：意向锁（Intent Lock）机制

为了彻底消除申请表级锁时对整张表成千上万行元组进行无休止遍历扫描的恐怖开销，数据库理论引入了**意向锁（Intent Lock）**。

> **意向锁的核心思想（挂门牌机制）**：  
> **如果一个事务想要对底层的某个具体后裔节点（如行）加锁，必须首先在它的所有上层祖先节点（如表）上，挂上一把“意向锁”！**

```text
               意向锁的门牌机制直观映射
当事务想修改房间里的某张桌子 (行级 X 锁):
1. 事务必须先在大门 (表头) 上挂一个 "内有人正打算写数据" 的意向牌 (IX 锁);
2. 随后进入房间给桌子加行级 X 锁。
                               │
                               ▼
随后另一事务想把整个大楼全封锁 (申请表级 X 锁):
只需看一眼大门上的 "意向牌"，瞬间获知里面有人在加锁，立即原地等待!
彻底无需派人把整栋大楼的一万个房间逐一敲门翻查!
```

## 4. 三大意向锁形式化定义与五元锁相容矩阵

根据下层后裔节点所申请的锁类型不同，意向锁形式化地定义为三种：

1. **意向共享锁（Intent Share Lock，IS 锁）**：
   - 语义：如果要对某个数据对象的后裔节点加 **S 锁**，必须先对该数据对象加上 **IS 锁**；
2. **意向排他锁（Intent Exclusive Lock，IX 锁）**：
   - 语义：如果要对某个数据对象的后裔节点加 **X 锁**，必须先对该数据对象加上 **IX 锁**；
3. **共享意向排他锁（Share Intent Exclusive Lock，SIX 锁）**：
   - 语义：对当前整个数据对象加 **S 锁**（本表全表可读），同时打算对其某些后裔节点加 **X 锁**进行修改（即 $\text{SIX} = \text{S} + \text{IX}$）。

---

### 4.1 完整的五元锁相容矩阵（Lock Compatibility Matrix）

这是数据库并发控制领域最全、最高阶的锁相容矩阵：

```text
                  五元锁相容判定矩阵 (Compatibility Matrix)
                                    已有事务持有的锁
               ────────────────────────────────────────────────────────
                无 (None)     IS          IX          S          SIX         X
  申请的锁模式 ┌───────────┬───────────┬───────────┬───────────┬───────────┬─────┐
        IS     │     Y     │     Y     │     Y     │     Y     │     Y     │  N  │
        IX     │     Y     │     Y     │     Y     │     N     │     N     │  N  │
        S      │     Y     │     Y     │     N     │     Y     │     N     │  N  │
        SIX    │     Y     │     Y     │     N     │     N     │     N     │  N  │
        X      │     Y     │     N     │     N     │     N     │     N     │  N  │
               └───────────┴───────────┴───────────┴───────────┴───────────┴─────┘
               (注: Y 代表兼容批准; N 代表冲突阻塞挂起)
```

#### 矩阵核心口诀与记忆秘籍：
1. **IS 锁最宽容**：除了与霸道的 X 锁冲突外，与其余所有锁（包括 S, IS, IX, SIX）全部相容；
2. **IX 与 IX 相容**：两个事务分别在同一个表上持有 IX 锁，代表它们各自打算修改表内**不同**的行，表头互相不冲突，行级自会排队；
3. **IX 与 S 互斥**：有人持有 S 锁表明全表正在被整表只读扫描，此时绝不允许有人带着 IX 意图去改行；
4. **X 锁排斥一切**：只要有 X 锁存在，全矩阵一律为 N！

---

### 4.2 意向锁加锁与释放的四步时序规约
在多粒度树形结构中，事务加锁和释放锁必须严格遵循：
1. **【自上而下加锁（Top-Down Locking）】**：对任一节点加锁（S 或 X），必须先对其所有祖先节点施加对应的意向锁（IS 或 IX）；
2. **【自下而上放锁（Bottom-Up Unlocking）】**：释放锁时，必须先释放叶子节点上的显式锁，最后才能释放祖先节点上的意向锁。

## 6. 随堂巩固自测

### 自测题 1（单项选择题）
在关系数据库多粒度封锁树形体系中，关于意向锁（Intent Lock）的核心工程价值，叙述最准确的是（ ）
A. 意向锁使得事务能够直接绕过数据库的写前日志协议（WAL）  
B. 意向锁保证了在申请表级锁时，锁管理器无需逐行遍历全表成千上万行记录来排查行锁冲突，将锁冲突判定的时间复杂度降至 $O(1)$  
C. 意向锁彻底消除了数据库死锁的发生  
D. 意向锁只允许单用户进行单事务排队  

**【答案】**：B  
**【解析】**：意向锁通过在上层表节点悬挂“内部有行加锁”的意向标记，使得其他事务在申请表级 S 锁或 X 锁时，只需比对表头门牌标记即可瞬间判定相容性，彻底消除了全表扫描检查行锁的巨大开销。故选 B。

### 自测题 2（全课程终极综合大题）
设有事务 $T_1$ 试图对基本表 `Student` 中的某一行元组 `Row_100` 执行修改操作（`UPDATE`），而事务 $T_2$ 紧接着试图对整张 `Student` 表执行全表重组并申请表级排他锁（`X` 锁）。  
请根据**多粒度树形封锁与意向锁协议**，详细回答：
1. 事务 $T_1$ 在修改 `Row_100` 之前，必须先后在哪两个层级的节点上分别申请什么类型的锁？申请遵循什么时序方向？
2. 事务 $T_2$ 随后申请整张表的表级 X 锁时，系统锁管理器将如何进行相容性判定？判定结果是什么？最终系统如何执行？

**【参考答案与完整推导】**：
1. **事务 $T_1$ 的加锁操作与时序**：
   - 遵循**自上而下加锁（Top-Down）**原则：
   - **第一步（表级加意向锁）**：$T_1$ 必须首先在父节点 `Student` 表上申请并获得**意向排他锁（IX 锁）**；
   - **第二步（行级加排他锁）**：在持有表级 IX 锁后，系统才允许 $T_1$ 进入表内，对目标行 `Row_100` 申请并获得**行级排他锁（X 锁）**。
2. **事务 $T_2$ 的申请与判定流程**：
   - 事务 $T_2$ 试图对 `Student` 表申请表级 $X$ 锁；
   - 锁管理器直接检查 `Student` 表当前的持锁状态，发现当前表上已被 $T_1$ 挂上了 $IX$ 锁；
   - **查阅锁相容矩阵**：$X$ 锁与已有的 $IX$ 锁判定为**不相容（N）**！
   - **判定结论与执行结果**：锁管理器无需对表内的数据行进行任何遍历扫描，**当场拒绝 $T_2$ 的加锁请求，直接将事务 $T_2$ 置于阻塞等待队列中挂起休眠**，直到事务 $T_1$ 彻底完成修改并提交（COMMIT）、自下而上释放了行级 X 锁和表级 IX 锁之后，$T_2$ 才会被唤醒并授予表级 X 锁继续执行。这一机制完美捍卫了系统的并发隔离性与极致运行效率。
