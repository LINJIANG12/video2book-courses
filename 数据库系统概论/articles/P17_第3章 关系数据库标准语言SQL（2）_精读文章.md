# SQL数据定义（二）：模式定义、基本表创建与完整性约束规约

## 1. 核心概念与本质内涵：模式与基本表的关系

在 SQL 环境中，一个关系数据库由若干个**模式（Schema）**组成，而一个模式内部又包含若干个**基本表（Base Table）**、视图（View）与索引（Index）。

模式本质上是数据库对象的组织容器和命名空间（Namespace）：
- 不同的模式可以包含同名的基本表（例如 `HR.Employee` 与 `Finance.Employee` 不会产生命名冲突）；
- 权限控制可以精准绑定到模式级别。

```text
               SQL 数据库命名空间与对象层级
+-------------------------------------------------------------------+
| 数据库 (Database / Catalog)                                       |
|                                                                   |
|   模式 A (Schema: "S_CAMPUS")      模式 B (Schema: "S_FINANCE")   |
|   +--------------------------+     +--------------------------+   |
|   | 基本表: Student          |     | 基本表: Tuition          |   |
|   | 基本表: Course           |     | 基本表: Payroll          |   |
|   | 基本表: SC               |     | 视图:   V_Salary         |   |
|   | 视图:   V_CS_Student     |     | 索引:   Idx_PayDate      |   |
|   | 索引:   Idx_Sno          |     +--------------------------+   |
|   +--------------------------+                                    |
+-------------------------------------------------------------------+
```

## 2. 模式的定义与删除（Schema DDL）

### 2.1 定义模式（CREATE SCHEMA）

- **标准语法结构**：
  ```sql
  CREATE SCHEMA <模式名> AUTHORIZATION <用户名> [子句集];
  ```
- **语法参数剖析**：
  - `<模式名>`：新创建的命名空间标识符；若省略模式名，则模式名默认为 `<用户名>`；
  - `AUTHORIZATION`：指定该模式的所有者（Owner）角色；
  - `[子句集]`：允许在定义模式的同时，直接一次性创建该模式下的基本表、视图及授权语句。
- **经典示例**：
  ```sql
  -- 为用户 WANG 创建一个名为 TEST_SCHEMA 的模式，并在其中直接创建学生表
  CREATE SCHEMA TEST_SCHEMA AUTHORIZATION WANG
      CREATE TABLE TAB1 (
          COL1 INT PRIMARY KEY,
          COL2 CHAR(20),
          COL3 NUMERIC(10, 2)
      );
  ```

### 2.2 删除模式（DROP SCHEMA）

- **标准语法结构**：
  ```sql
  DROP SCHEMA <模式名> <CASCADE | RESTRICT>;
  ```
- **两大删除选项的行为差异**：
  1. **`CASCADE`（级联删除）**：删除模式的同时，把该模式下所包含的全部数据库对象（所有的基本表、视图、索引）全部连带自动删除；
  2. **`RESTRICT`（限制删除）**：只有当该模式下**没有任何下属数据库对象**（为空模式）时，才允许成功删除；若模式内存在任何表或视图，系统立即报错拒绝执行。

## 3. 基本表的创建与数据类型体系（CREATE TABLE）

### 3.1 常用 SQL 标准数据类型矩阵

| 数据类型 | 描述与取值规约 | 典型应用场景 |
| :--- | :--- | :--- |
| `INT` / `INTEGER` | 4 字节带符号整数（约 $-2.1 \times 10^9 \sim 2.1 \times 10^9$） | 计数器、主键 ID、学生年龄 |
| `SMALLINT` | 2 字节带符号整数（$-32768 \sim 32767$） | 较小范围的整数（如学分、星期） |
| `BIGINT` | 8 字节大整数 | 海量互联网流水号、全局分布式 ID |
| `NUMERIC(p, s)` / `DECIMAL(p, s)` | 高精度定点小数：$p$ 为总有效位数（Precision），$s$ 为小数位数（Scale） | 银行金额、财务结算（杜绝浮点精度丢失） |
| `CHAR(n)` | 固定长度字符类型（不足 $n$ 位时末尾自动填充空格） | 长度固定的编码（如学号、身份证号、性别） |
| `VARCHAR(n)` | 可变长度字符类型（最大长度 $n$，按实际内容占用存储） | 姓名、文章标题、通信地址 |
| `DATE` | 日期类型（格式：`YYYY-MM-DD`） | 出生日期、开学日期 |
| `TIME` | 时间类型（格式：`HH:MM:SS`） | 上课时间、打卡时间 |
| `TIMESTAMP` | 时间戳（含日期、时间及毫秒，支持时区） | 订单创建时间、审计日志 |

### 3.2 基本表创建语法与完整性约束内嵌

在执行 `CREATE TABLE` 时，系统不仅定义字段物理结构，还同时形式化声明三大完整性约束：

```sql
CREATE TABLE <表名> (
    <列名> <数据类型> [列级完整性约束条件],
    <列名> <数据类型> [列级完整性约束条件],
    ...
    [表级完整性约束条件]
);
```

#### ① 列级约束与表级约束的区分规则：
- **列级约束**：紧跟在某一列定义之后，只能针对该单一列生效（如 `NOT NULL`, `UNIQUE`）；
- **表级约束**：写在所有列定义完成后的末尾，**当约束涉及多个列（如复合主码、外码）时，必须声明为表级约束**。

## 4. 经典三表模式 DDL 完整创建实战

以下为高校经典三表模型在工业级 SQL 环境下的标准化完整建表脚本：

```sql
-- 1. 创建学生表 Student (主码为单列 Sno)
CREATE TABLE Student (
    Sno   CHAR(9) PRIMARY KEY,          -- 列级主码约束 (隐含 NOT NULL + UNIQUE)
    Sname VARCHAR(20) NOT NULL,         -- 列级非空约束
    Ssex  CHAR(2) CHECK (Ssex IN ('男', '女')), -- 用户定义完整性 (枚举检查)
    Sage  SMALLINT CHECK (Sage >= 15 AND Sage <= 45),
    Sdept VARCHAR(20) DEFAULT '计算机系' -- 默认值约束
);

-- 2. 创建课程表 Course (含自参照外码 Cpno)
CREATE TABLE Course (
    Cno     CHAR(4) PRIMARY KEY,
    Cname   VARCHAR(40) NOT NULL,
    Cpno    CHAR(4),                    -- 先修课号
    Ccredit SMALLINT NOT NULL CHECK (Ccredit > 0),
    FOREIGN KEY (Cpno) REFERENCES Course(Cno) -- 表级自参照外码约束
);

-- 3. 创建选课成绩表 SC (复合主码 + 双重外码)
CREATE TABLE SC (
    Sno   CHAR(9) NOT NULL,
    Cno   CHAR(4) NOT NULL,
    Grade SMALLINT CHECK (Grade >= 0 AND Grade <= 100),
    -- 表级复合主码定义 (两个属性联合唯一且非空)
    PRIMARY KEY (Sno, Cno),
    -- 表级外码约束 1: 参照 Student(Sno)
    FOREIGN KEY (Sno) REFERENCES Student(Sno)
        ON DELETE CASCADE               -- 级联删除: 学生退学时自动清理其选课
        ON UPDATE CASCADE,              -- 级联更新: 学号变更时同步联动
    -- 表级外码约束 2: 参照 Course(Cno)
    FOREIGN KEY (Cno) REFERENCES Course(Cno)
        ON DELETE RESTRICT              -- 限制删除: 有人选修的课严禁删除
);
```

> **易错点**：在创建存在外码参照的表时，**必须先创建被参照的“主表”（`Student`, `Course`），后创建参照的“从表”（`SC`）**；否则在编译外码引用时系统会因找不到目标表而报错中断。

## 5. 随堂巩固自测

### 自测题 1（单项选择题）
在定义复合主码（由两个及以上属性共同构成的主码）时，在 SQL 语法中必须采用的书写方式是（ ）
A. 分别在每个主码列的定义后添加 `PRIMARY KEY` 列级约束  
B. 在所有列定义之后，添加一个表级约束：`PRIMARY KEY (属性1, 属性2)`  
C. 在建表语句末尾添加 `INDEX (属性1, 属性2)`  
D. 复合主码不能通过 SQL 直接创建，必须在系统上线后由 DBA 手动配置  

**【答案】**：B  
**【解析】**：若在多个列后面分别写 `PRIMARY KEY`，系统会判定为试图声明多个独立主码而报错（一个表只能有一个主码）。定义复合主码必须在表级使用 `PRIMARY KEY (列1, 列2, ...)` 联合声明。故选 B。

### 自测题 2（DDL 设计与排错题）
阅读下列建表 SQL 代码片段，指出其中存在的 2 处逻辑或语法错误，并给出修正方案：
```sql
CREATE TABLE Department (
    DeptID INT,
    DeptName VARCHAR(50),
    PRIMARY KEY (DeptID)
);

CREATE TABLE Employee (
    EmpID INT PRIMARY KEY,
    EmpName VARCHAR(20),
    DeptID INT,
    FOREIGN KEY (DeptID) REFERENCES Department(DeptID),
    Salary NUMERIC(8, 2) CHECK (Salary < 0) -- 错误处
);
```

**【参考答案与解析】**：
1. **错误 1（检查约束逻辑反向）**：`Salary NUMERIC(8, 2) CHECK (Salary < 0)` 要求工资必须小于 0，这与现实业务常理完全相悖。  
   - **修正**：应改为 `CHECK (Salary >= 0)` 或设定合理区间 `CHECK (Salary BETWEEN 1000 AND 1000000)`。
2. **表级外码命名与依赖完整性规范建议**：虽然上述 `FOREIGN KEY` 语法合法，但外码未显式命名（不易于后续维护删除），且 `Department` 表的 `DeptName` 缺少 `NOT NULL` 与 `UNIQUE` 业务约束。
