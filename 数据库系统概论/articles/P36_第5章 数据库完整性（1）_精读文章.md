# 数据库完整性控制（一）：实体与参照完整性内核实现及违约联动策略

## 1. 核心概念与本质内涵：完整性控制是数据质量的守护神

在关系数据库系统中，数据的有效性与真实性取决于**数据库完整性（Database Integrity）**。
- 完整性保证数据符合客观世界业务规律的逻辑正确性（例如成绩不能是负数、学生的选课必须绑定有效的在籍学号）；
- 关系模型将完整性内建于系统内核之中，由 DBMS 的完整性子系统负责统一自动化检查，从而将应用程序员从编写海量、繁琐的防御性校验代码中彻底解放出来。

```text
                  关系数据库完整性控制核心体系
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
【实体完整性 (Entity Integrity)】              【参照完整性 (Referential Integrity)】
 • 主码唯一且绝对非空                          • 外码表间参照链路维护
 • DBMS 自动构建 B+ 树唯一索引                 • 违约处理动作:
 • 毫秒级防重冲突拦截                            NO ACTION (报错拒绝)
                                                 CASCADE   (级联更新/删除)
                                                 SET NULL  (自动置空)
```

## 2. 实体完整性的底层实现与检验机制

### 2.1 形式化声明与语法规范

实体完整性通过 `PRIMARY KEY`（主码）短语进行显式形式化定义：
- **单属性主码**：可以在列定义处声明为**列级约束**，也可以在表末尾声明为**表级约束**；
- **复合主码（由两个或更多属性联合构成）**：**必须且只能在表末尾声明为表级约束**。

```sql
-- 1. 单列主码 (列级约束)
CREATE TABLE Student (
    Sno CHAR(9) PRIMARY KEY,
    Sname VARCHAR(20) NOT NULL
);

-- 2. 复合主码 (表级约束)
CREATE TABLE SC (
    Sno CHAR(9) NOT NULL,
    Cno CHAR(4) NOT NULL,
    Grade SMALLINT,
    PRIMARY KEY (Sno, Cno) -- 复合主码必须在表级声明
);
```

### 2.2 DBMS 内核对实体完整性的检查机理

当用户向表中发起 `INSERT` 或对主码列执行 `UPDATE` 时，DBMS 事务层按以下两步严格执行判定：

```text
               实体完整性自动检查流向
新数据行写入 / 修改主码属性
         │
         ▼
[第 1 步: 非空检查 (NOT NULL Check)]
 扫描主码各分量是否存在 NULL
 ├── 存在 NULL ──> 立即报错拒绝，抛出实体完整性违约异常
 ▼ 全部非空
[第 2 步: 唯一性二分快速比对 (Uniqueness Check)]
 借助底层自动创建的 B+ 树主键索引快速探针寻道
 ├── 索引中已存在相同键值 ──> 立即报错拒绝，拦截主键冲突
 ▼ 无冲突
允许数据页写入落盘
```

> **底层性能机制**：为了防止每一次插入数据都去进行全表遍历扫重，**主流关系数据库会在定义 `PRIMARY KEY` 的同时，自动在底层为该主码列（或属性组）构建一个唯一的 B+ 树索引**。通过 B+ 树的对数级二分查找，使得主键唯一性校验的耗时被严格锁定在几微秒以内。

## 3. 参照完整性的实现与违约联动策略（Referential Action）

参照完整性将不同基本表之间的实体关联通过外码（`FOREIGN KEY`）严格绑定。

### 3.1 违约动作的四大策略

当发生对被参照表（主表）的删除或修改，或者对参照表（从表）的新增或修改时，极易破坏两表之间的关联一致性。SQL 标准允许在定义外码时，显式指定四大违约处理策略：

| 违约动作策略 | 关键字语法 | 核心行为与业务语义 |
| :--- | :--- | :--- |
| **拒绝执行（默认）** | `ON DELETE NO ACTION` / `RESTRICT` | 只要从表中有任何一条外码记录引用了主表当前行，**严禁主表行被删除或修改**，系统抛错中断事务 |
| **级联联动** | `ON DELETE CASCADE` / `ON UPDATE CASCADE` | 主表记录被删除或主键修改时，**自动连带将从表中所有引用该主键的行同步删除或修改** |
| **自动置空** | `ON DELETE SET NULL` / `ON UPDATE SET NULL` | 主表记录被删除或修改时，**自动将从表中所有引用该行的外码列值更新为 NULL**（前提是该外码列允许为空） |
| **设为默认值** | `ON DELETE SET DEFAULT` | 主表行删除时，从表外码自动回退填充为其预设的默认值 |

---

### 3.2 经典三表外码级联联动生产实战

```sql
CREATE TABLE SC (
    Sno CHAR(9) NOT NULL,
    Cno CHAR(4) NOT NULL,
    Grade SMALLINT CHECK (Grade >= 0 AND Grade <= 100),
    PRIMARY KEY (Sno, Cno),
    
    -- 外码 1: 绑定 Student 表，配置级联策略
    CONSTRAINT FK_SC_Student 
        FOREIGN KEY (Sno) REFERENCES Student(Sno)
        ON DELETE CASCADE       -- 现实语义: 学生退学注销档案时，其所有选课记录自动被级联抹除
        ON UPDATE CASCADE,      -- 现实语义: 学生学号因升学规则变更时，其选课表中的学号同步联动
        
    -- 外码 2: 绑定 Course 表，配置拒绝限制策略
    CONSTRAINT FK_SC_Course 
        FOREIGN KEY (Cno) REFERENCES Course(Cno)
        ON DELETE RESTRICT      -- 现实语义: 只要尚有任何学生选修了这门课，该课程绝不允许被教学办擅自删除!
        ON UPDATE CASCADE
);
```

## 4. 典型例题与深度认知辨析

### 辨析 1：外码可以取空值，那什么时候绝对不能取空值？

- **深度判定**：
  - 一般情况下，外码若未声明 `NOT NULL`，允许取 `NULL`（代表暂时未分配关联，如新员工未分配部门）；
  - 但如果**外码属性同时是本表主码的组成部分**（如选课表 `SC(Sno, Cno)` 中的 `Sno` 和 `Cno`），根据**实体完整性必须非空的最高铁律**，此时它们绝对不能取空值！

## 5. 随堂巩固自测

### 自测题 1（单项选择题）
在关系数据库中，定义外码约束时声明了子句：`ON DELETE CASCADE`。若从被参照主表中删除了主键为 `'1001'` 的一条记录，则数据库系统将（ ）
A. 报错并拒绝删除主表记录  
B. 删除主表记录，并将从表中所有外码为 `'1001'` 的记录自动同步删除  
C. 删除主表记录，并将从表中所有外码为 `'1001'` 的字段修改为 NULL  
D. 只删除从表记录，保留主表记录  

**【答案】**：B  
**【解析】**：`CASCADE`（级联）选项表示当主表中的父记录被删除时，系统自动将所有依赖它的子从表记录一并级联删除，以维持参照完整性。故选 B。

### 自测题 2（SQL DDL 设计题）
设有两张表：部门表 `Dept(DeptID, DeptName)`，员工表 `Emp(EmpID, EmpName, DeptID)`。
请为员工表编写建表语句，要求：
1. `EmpID` 为主码；
2. `DeptID` 为外码，参照 `Dept` 表的 `DeptID`；
3. 当部门被删除时，该部门的所有员工的 `DeptID` 自动置为 `NULL`（不删除员工）；
4. 当部门编号发生变更时，员工表中的 `DeptID` 自动同步联动修改。

**【参考答案】**：
```sql
CREATE TABLE Emp (
    EmpID INT PRIMARY KEY,
    EmpName VARCHAR(30) NOT NULL,
    DeptID INT,
    CONSTRAINT FK_Emp_Dept 
        FOREIGN KEY (DeptID) REFERENCES Dept(DeptID)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);
```
