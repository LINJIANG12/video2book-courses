# 数据库高级完整性（三）：全局断言机制、ECA触发器规则与第五章全景复盘

## 1. 核心概念与本质内涵：跨表复杂业务规则的实现困境

前文介绍的列级与元组级 `CHECK` 约束，其作用边界严格局限在**单张基本表内部**。
然而在实际大型信息系统中，海量的业务完整性规则是**跨越多张表的全局动态强约束**：
- “全校任何一名教授所主持的科研项目经费总和，不得超过该教授所在院系年度总预算的 $20\%$”；
- “每一门专业选修课的选修人数上限为 60 人，达到 60 人后系统必须自动封顶拒绝新选课”；
- “员工的薪资一旦录入，后续调整只能上调、绝不允许单向调低”。

为了解决涉及跨表聚合与过程化复杂逻辑的完整性控制，数据库理论与 SQL 标准引入了**断言（Assertion）机制**与**触发器（Trigger）机制**。

```text
               数据库高级完整性控制双引擎
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
【断言机制 (Assertion)】                        【触发器机制 (Trigger)】
 • 声明性跨表全局约束                           • 过程化、事件驱动的业务规则 (ECA)
 • 任何表变动自动触发全量验证                   • 事件 (Event) + 条件 (Condition) + 动作 (Action)
 • 理论优雅但系统全局开销巨大                   • 行级 (FOR EACH ROW: :OLD/:NEW) vs 语句级
```

## 2. 断言机制（Assertion）的形式化规约

### 2.1 创建断言（CREATE ASSERTION）

```sql
CREATE ASSERTION <断言名> CHECK (<谓词表达式>);
```

- **执行机理**：断言创建后，系统视其为全库级别的常态监控规则。**只要数据库中涉及该断言所依托的任何基本表发生修改（增删改），DBMS 必须自动重新评估该断言**；
- 若某次操作导致断言的谓词评估结果为 `FALSE`，该操作被立即强制拒绝并全部回滚。

### 2.2 经典断言实战
**需求**：限制每一门课程最多只能被 60 名学生选修。

```sql
CREATE ASSERTION Asse_Max_Students
CHECK (
    60 >= ALL (
        SELECT COUNT(Sno) 
        FROM SC 
        GROUP BY Cno
    )
);
```

### 2.3 断言的工业界困境与删除
```sql
DROP ASSERTION <断言名>;
```
> **工程现实说明**：由于断言要求在全库任意相关表发生任何细微变动时，都必须重新执行复杂的跨表聚合查询，会给高并发事务带来灾难性的性能开销。因此，主流商业关系数据库（如 Oracle, MySQL）通常选择不直接支持声明式断言，而是将这类跨表复杂约束全面交由**触发器（Trigger）**灵活实现。

## 3. 触发器机制（Trigger）与 ECA 核心规则

触发器是用户定义在基本表上的一类由**事件驱动的特殊交互式存储过程**。它不需要应用程序手动调用（如 `CALL`），而是在特定的数据库写操作发生时，由 DBMS 引擎自动隐式“触发”执行。

### 3.1 触发器的 ECA 规则（Event-Condition-Action）
- **事件（Event）**：究竟在发生什么底层写操作时唤醒触发器？包括 `INSERT`, `UPDATE`, `DELETE`；
- **条件（Condition）**：唤醒后是否必须无脑执行？通过 `WHEN <条件>` 进行二次评估，只有条件为真时才激活动作；
- **动作（Action）**：具体执行什么业务逻辑？通常是一个由 `BEGIN ... END` 包裹的过程化 SQL 代码块。

---

### 3.2 触发器的两大核心分类维度

```text
                     触发器的正交分类矩阵
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
【触发时机维度】                                【触发执行粒度】
 • BEFORE (前置触发):                            • 行级触发器 (FOR EACH ROW):
   在数据落盘前执行，专门用于拦截、校验与篡改修正  SQL 影响了 N 行，触发器就循环执行 N 次!
 • AFTER (后置触发):                             提供了 :OLD 与 :NEW 伪行变量访问新旧值
   在数据成功写入后执行，专门用于连带级联更新    • 语句级触发器 (FOR EACH STATEMENT):
                                                   整条 SQL 无论影响多少行，仅执行 1 次!
```

---

### 3.3 行级触发器的伪行引用（OLD 与 NEW）

在行级触发器（`FOR EACH ROW`）中，系统提供了两个极其强大的伪行变量：
- **`:OLD`**：代表该行元组在被修改或被删除**之前的原始旧值快照**；
- **`:NEW`**：代表该行元组正准备被插入或修改**之后的新目标值**。

| 操作类型 | `:OLD` 的可用性 | `:NEW` 的可用性 | 核心典型用途 |
| :--- | :--- | :--- | :--- |
| `INSERT` | **不可用（为 NULL）** | **可用**（即准备写入的新行） | 检查新录入字段是否合规、补充默认计算字段 |
| `UPDATE` | **可用**（修改前的老值） | **可用**（修改后的新值） | 比较新旧属性变化幅度（如防降薪、防跳变） |
| `DELETE` | **可用**（被删行的全量数据） | **不可用（为 NULL）** | 归档已删除历史记录到审计备份表 |

## 4. 经典触发器开发生产实战

### 案例 1：业务合规防降薪与变动审计（BEFORE 行级触发器）
**业务规则**：在员工表 `Employee(EmpID, EmpName, Salary)` 中，任何员工的调薪操作，调整后的工资必须大于调整前的工资（只能涨不能降），否则抛出自定义错误中断事务。

```sql
CREATE OR REPLACE TRIGGER Tri_Salary_Check
BEFORE UPDATE OF Salary ON Employee   -- 仅在修改 Salary 列之前触发
FOR EACH ROW                          -- 行级触发器
WHEN (NEW.Salary < OLD.Salary)        -- 触发条件: 新工资小于旧工资
BEGIN
    -- 抛出异常中断事务
    RAISE_APPLICATION_ERROR(-20001, '业务违规: 员工薪资调整只能上调，严禁下调!');
END;
```

---

### 案例 2：跨表自动级联统计（AFTER 行级触发器）
**业务规则**：课程表中有 `StudentCount` 字段记录当前选课人数。当选课表 `SC` 成功插入一条新选课记录时，对应课程的选课人数自动加 1；当退选删除记录时，对应人数自动减 1。

```sql
CREATE OR REPLACE TRIGGER Tri_Update_StudentCount
AFTER INSERT OR DELETE ON SC
FOR EACH ROW
BEGIN
    IF INSERTING THEN
        UPDATE Course 
        SET StudentCount = StudentCount + 1 
        WHERE Cno = :NEW.Cno;
    ELSIF DELETING THEN
        UPDATE Course 
        SET StudentCount = StudentCount - 1 
        WHERE Cno = :OLD.Cno;
    END IF;
END;
```

## 6. 随堂巩固自测

### 自测题 1（单项选择题）
在关系数据库管理系统中，当执行如下触发器创建语句时：
```sql
CREATE TRIGGER Tri_Audit AFTER INSERT ON Orders FOR EACH ROW ...
```
该触发器属于（ ）
A. 前置语句级触发器  
B. 后置行级触发器，每次批量插入 N 条订单时，触发器动作将执行 N 次  
C. 后置语句级触发器，每次批量插入 N 条订单时，触发器动作只执行 1 次  
D. 声明性全局断言  

**【答案】**：B  
**【解析】**：语句中包含关键字 `AFTER`（后置触发）与 `FOR EACH ROW`（行级触发）。行级触发器对受 SQL 影响的每一行元组都会触发执行一次动作。因此批量插入 N 条时，将循环执行 N 次动作。故选 B。

### 自测题 2（触发器实战设计题）
设有商品表 `Goods(GID, Gname, Stock)`（商品编号、名称、库存量）与订单明细表 `OrderDetail(OrderID, GID, Quantity)`（订单号、商品编号、购买数量）。
请编写一个数据库触发器，满足如下要求：
“当用户向 `OrderDetail` 插入一条购买记录时，自动检查 `Goods` 表中对应商品的库存量是否足够：
- 若库存不足（`Stock < Quantity`），则阻止该订单插入并报错；
- 若库存充足，则自动在 `Goods` 表中将对应商品的库存量扣减掉本次购买数量”。

**【参考答案】**：
```sql
CREATE OR REPLACE TRIGGER Tri_Deduct_Stock
BEFORE INSERT ON OrderDetail
FOR EACH ROW
DECLARE
    v_CurrentStock INT;
BEGIN
    -- 1. 查询当前商品的实际库存
    SELECT Stock INTO v_CurrentStock
    FROM Goods
    WHERE GID = :NEW.GID;
    
    -- 2. 判定库存充裕性
    IF v_CurrentStock < :NEW.Quantity THEN
        RAISE_APPLICATION_ERROR(-20002, '库存不足，无法完成下单支付!');
    ELSE
        -- 3. 库存充足，直接扣减
        UPDATE Goods
        SET Stock = Stock - :NEW.Quantity
        WHERE GID = :NEW.GID;
    END IF;
END;
```
