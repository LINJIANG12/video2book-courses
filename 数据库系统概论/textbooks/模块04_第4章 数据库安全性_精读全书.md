## 第 1 章：第4章  数据库安全性（1）
> 对应分集：P30 | 原始标题：《第4章  数据库安全性（1）》

### 1. 核心概念与本质内涵：什么是数据库安全性？

在现代数字化社会中，数据库中集中存储着国家战略资源、银行金融交易、企业商业秘密以及公民个人隐私。数据的价值越高，面临的非法窃取、恶意篡改与破坏风险就越巨大。

#### 1.1 数据库安全性（Database Security）的形式化界定
**数据库安全性是指保护数据库以防止因非法使用而造成数据泄露、更改或破坏**。
- **与数据库完整性的核心分野**：
  - **安全性（Security）**防护的是“**防盗与防贼**”：防范未经授权的非法用户越权存取机密数据；
  - **完整性（Integrity）**把控的是“**防错与防假**”：防范合法用户因误操作、代码 BUG 写入不符合业务客观规律的错误或矛盾数据。

```text
               数据库安全性与完整性的本质区别
+---------------------------------------------------------------+
| 数据库安全性 (Security) ───────> 防非法用户 / 防未授权渗透 (防盗) |
| 数据库完整性 (Integrity) ──────> 防数据逻辑错误 / 防语义矛盾 (防错) |
+---------------------------------------------------------------+
```

---

### 2. 数据库系统的多层安全控制拓扑

保障数据库安全绝非单纯在 SQL 层配置密码，而必须在计算机全栈架构中构建**纵深防御体系（Defense-in-Depth）**：

```text
                     数据库系统纵深安全防御拓扑
+---------------------------------------------------------------+
| 1. 物理安全层 (Physical Security):                            |
|    - 机房门禁、防灾监控、防电磁辐射与物理窃听                 |
+---------------------------------------------------------------+
                              │
                              ▼
+---------------------------------------------------------------+
| 2. 操作系统与网络安全层 (OS & Network Security):              |
|    - 防火墙隔离、网络传输 SSL/TLS 加密、操作系统账号防护      |
+---------------------------------------------------------------+
                              │
                              ▼
+---------------------------------------------------------------+
| 3. 数据库管理系统安全层 (DBMS Security):                      |
|    - 用户身份鉴别 (Authentication)                            |
|    - 存取控制策略 (Access Control: DAC / MAC)                 |
|    - 视图机制隔离 (View Isolation)                            |
|    - 审计与追踪记录 (Audit Trail)                             |
|    - 存储数据落盘加密 (Transparent Data Encryption, TDE)       |
+---------------------------------------------------------------+
```

---

### 3. 权威安全标准：TCSEC 与 CC 评估准则体系

为了形式化度量计算机系统与数据库系统的安全防护能力，国际上颁布了一系列权威的评估标准。其中最著名的是美国国防部制定的 **TCSEC（可信计算机系统评估准则，俗称“橘皮书”）**与国际通用准则 **CC（Common Criteria）**。

#### 3.1 TCSEC 安全等级划分谱系（从低到高）

TCSEC 将计算机系统的安全程度由低到高划分为 **4 组 7 个等级**：

```text
      D 级           C 级 (自主保护)          B 级 (强制保护)        A 级 (验证)
   (无安全)      ┌───────────┴───────────┐    ┌─────┴─────┐              │
       │         ▼                       ▼    ▼     ▼     ▼              ▼
     [ D ]     [ C1 ]                  [ C2 ][ B1 ][ B2 ][ B3 ]        [ A1 ]
    最低档    初级自主存取            受控存取 标号 结构化 安全域     形式化验证
              (非安全系统)            (主流商用)
```

1. **D 级（Minimal Protection，最小保护）**：
   - 没有任何安全性保护措施。硬件上没有内存保护，软件上没有用户鉴别。早期的 MS-DOS 即为典型的 D 级系统。
2. **C1 级（Discretionary Security Protection，自主安全保护）**：
   - 初级的自主存取控制。将用户与数据分离，支持按用户身份分配对文件或表的访问权限。
3. **C2 级（Controlled Access Protection，受控存取保护）——主流商用 DBMS 的安全基线**：
   - **核心特征**：实施更细粒度的自主存取控制（DAC），并引入了强制性的**身份鉴别（Authentication）**与**审计（Auditing）机制**；
   - 能够记录谁在什么时刻对哪些数据执行了操作；
   - 现代主流商业数据库（Oracle, Microsoft SQL Server, PostgreSQL）的原生标准配置均达到此级别。
4. **B1 级（Labeled Security Protection，标记安全保护）——国家级敏感系统门槛**：
   - 引入了**强制存取控制（Mandatory Access Control, MAC）**；
   - 系统为所有数据（客体）打上**敏感度标记（Security Label）**，为所有用户（主体）分配许可证级别，通过底层硬件与内核强行阻断越权渗透。
5. **B2 ~ A1 级（验证设计与形式化数学证明）**：
   - 面向国防核控制、极端绝密军事情报领域，要求其安全内核通过形式化的数学定理完全证明其不存在任何隐蔽通道（Covert Channel）。

#### 自测题 2（概念对比分析题）
请用简练、精确的技术语言阐述“数据库安全性”与“数据库完整性”的核心区别，并各举一个系统违约反例。

**【参考答案与深度解析】**：

   - **安全性**强调“防非授权访问”，防止非法用户窃取或破坏机密数据；
   - **完整性**强调“防数据语义错误”，保证合法用户输入的数据在逻辑上真实、准确和有效。

   - **完整性违约反例**：教务处老师在录入期末成绩时手误输成了 `-88` 分，系统未经校验直接保存（操作者具有完全合法的权限，但数据值违反了客观业务规则，属完整性失效）。

## 第 2 章：第4章  数据库安全性（2）
> 对应分集：P31 | 原始标题：《第4章  数据库安全性（2）》

### 1. 核心概念与本质内涵：防线的第一道关卡与核心枢纽

任何用户试图访问数据库中的数据，必须先后跨越 DBMS 的两道核心防线：
1. **身份鉴别（Authentication）——“你是谁？”**：验证试图连入系统的用户是否确实是其声称的那个真实合法实体；
2. **存取控制（Access Control）——“你能干什么？”**：在确认用户真实身份后，依据系统安全策略，严格裁决该用户针对特定数据库对象（表、列、视图）被允许执行哪些具体操作（读、写、修改、删除）。

```text
               数据库安全访问的双道关卡流向
客户端连接请求 (Client Connection)
         │
         ▼
【第一道防线: 身份鉴别 (Authentication)】
 • 检验用户名与口令 / 动态 OTP 令牌 / 生物特征 / 数字证书
 • 验证失败 ──> 立即切断网络连接，记入安全审计日志
         │
         ▼ (鉴别通过，确立用户身份 Context)
【第二道防线: 存取控制 (Access Control)】
 每次执行具体 SQL 语句时 (如 SELECT / DELETE):
 • 扫描系统数据字典与权限授权表
 • 判定该用户是否具有执行该指令的显式或继承权限
 • 权限不匹配 ──> 抛出 "Permission Denied" 并拦截执行
```

---

### 2. 现代数据库用户身份鉴别技术体系

#### 2.1 静态口令鉴别（Static Password Authentication）
- **实现原理**：用户输入账号和预设的固定密码，DBMS 将用户输入的密码哈希摘要与系统内部加密存储的散列值（如 PBKDF2, SHA-256 带盐 Salt）进行比对；
- **安全薄弱点**：极易受到弱口令字典攻击、网络中间人窃听（Sniffing）以及重放攻击。

#### 2.2 动态口令鉴别（Dynamic Password / OTP / MFA）
- **实现原理**：引入双因子认证（Multi-Factor Authentication, MFA），口令随时间（TOTP）或计数事件单向动态生成，一次一密，数十秒后自动作废失效；
- **防护收益**：即使攻击者窃听捕获了单次口令，因时效性已过，无法用于第二次登录。

#### 2.3 生物特征鉴别（Biometric Authentication）
- 利用人体独一无二的生物学物理特征（指纹、虹膜、人脸 3D 拓扑、静脉血管）进行比对，几乎不可能被窃取或转借他人，安全性极高。

#### 2.4 智能卡与数字证书（Smart Card / USB Key）
- 采用硬件加密芯片存储用户的非对称私钥，登录时通过挑战-应答机制（Challenge-Response）进行公私钥密码学签名验证，防篡改防复制。

---

### 3. 存取控制机制的两大核心流派：DAC vs MAC

在通过身份鉴别后，DBMS 通过存取控制机制实施授权。在计算机安全理论中，存在两大经典的存取控制范式：

```text
                  DAC (自主存取控制) vs MAC (强制存取控制)
                                 │
     ┌───────────────────────────┴───────────────────────────┐
     ▼                                                       ▼
【自主存取控制 (DAC)】                         【强制存取控制 (MAC)】
 • 灵活性极高，权力下放                        • 极度严密，权力绝对收归中央
 • 用户对拥有的数据具有自主控制权              • 系统强制为所有数据与用户打上密级标记
 • 可将自己拥有的权限自主转授他人              • 用户绝不能自主转授权限!
 • 存在隐蔽泄露通道 (无法防御木马)             • 彻底阻断信息由高密级向低密级单向流动
```

#### 3.1 自主存取控制（Discretionary Access Control, DAC）
- **机制原理**：
  - 用户对于自己创建的数据库对象（如某用户建了一张表），天然拥有最高属主权限；
  - 该用户可以**自主决定（Discretionary）**是否将该表的读、写权限授予其他用户；
  - 甚至允许被授权者将该权限**进一步转授给第三方**（`WITH GRANT OPTION`）。
- **致命缺陷——“特洛伊木马（Trojan Horse）”攻击脆弱性**：
  - 在纯 DAC 环境下，若超级用户 A 拥有绝密表，恶意用户 B 诱骗 A 运行了一个看似正常的统计程序（木马）；
  - 该木马在 A 的合法会话上下文里执行，读取绝密表并将数据悄悄 `INSERT` 进一个所有人均可读的公共垃圾表；
  - 最终用户 B 轻松读取了绝密数据，而 DAC 机制对此类**合法主体发起的越权拷贝**完全无能为力！

#### 3.2 强制存取控制（Mandatory Access Control, MAC）
- **机制原理**：
  - 每一个数据库对象（行、列、表）被系统强制固化赋予一个**敏感度标记（Security Label）**；
  - 每一个系统用户被安全管理员赋予一个**许可证密级（Clearance Level）**；
  - 系统根据一套不可逾越的数学规则（如 Bell-LaPadula 模型），由 DBMS 内核强制执行判定，**任何普通用户无权更改密级，更无权转让权限**。

### 4. 随堂巩固自测

#### 自测题 1（单项选择题）
在关系数据库安全体系中，关于自主存取控制（DAC）与强制存取控制（MAC）的说法，错误的是（ ）
A. DAC 提供了极好的使用灵活性，但在防范特洛伊木马非法窃取敏感数据方面存在结构性缺陷  
B. MAC 要求系统对所有主体和客体进行形式化的密级标号与强制访问控制  
C. 在支持 MAC 的高安全级别系统中，通常不再需要执行 DAC 检查  
D. 商业数据库普遍支持 DAC，而在国防等极端敏感领域必须引入 MAC  

**【答案】**：C  
**【解析】**：在高安全级别数据库（如 TCSEC B1 级以上）中，系统执行的是**先自主后强制的双重综合检查**：即一个访问请求必须首先通过 DAC 自主权限检查，随后还必须通过 MAC 强制密级规则校验，两者同时放行方可存取。故选项 C 错误。

---

#### 自测题 2（安全分析与推导题）
为什么说在只有自主存取控制（DAC）的系统中，敏感数据存在隐蔽外泄的风险？请简述该风险的发生路径。

**【参考答案与解析】**：
在纯 DAC 系统中，权限的流转主要依赖于用户的“自主意志”。拥有敏感表查询权限的用户，完全可以创建一个自身拥有所有权的新普通表，并编写一条 `INSERT INTO NewTable SELECT * FROM SecretTable;` 语句将敏感数据全量复制进去。随后，该用户可以自主地将 `NewTable` 的读取权限公开授予任何人。这种合法主体被恶意利用或主动转储的行为，使得安全边界彻底失控，导致敏感信息在没有触发任何权限违约报警的情况下被隐蔽外泄。

## 第 3 章：第4章  数据库安全性（3）
> 对应分集：P32 | 原始标题：《第4章  数据库安全性（3）》

### 1. 核心概念与本质内涵：SQL 的权限赋予与收回法则

SQL 标准通过强大的**数据控制语言（DCL）**全面落地自主存取控制（DAC）。管理员或对象属主可以通过两条最核心的控制指令：
- **`GRANT`（授权）**：向指定的用户或角色赋予对特定数据库对象（表、视图、属性列）的操作权限；
- **`REVOKE`（收权）**：从指定的用户或角色身上撤销已授予的权限。

在 DAC 体系下，权限的流转形成了一棵动态的**授权有向图（Authorization Graph）**，系统通过传播选项严格追踪权限的扩散与回收。

```text
               权限授予与转授扩散树 (Authorization Graph)
                          [DBA / 表属主 A]
                                 │
                   GRANT SELECT ON Student TO B
                        WITH GRANT OPTION;
                                 │
                                 ▼
                             [用户 B]
                                 │
                   GRANT SELECT ON Student TO C;
                                 │
                                 ▼
                             [用户 C]
```

---

### 2. GRANT 授权语句的语法体系与传播选项

#### 2.1 GRANT 标准语法规约

```sql
GRANT <权限> [, <权限>]...
ON <对象类型> <对象名> [, <对象类型> <对象名>]...
TO <用户> [, <用户>]... [PUBLIC]
[WITH GRANT OPTION];
```

##### ① 权限类型（Privileges）细粒度控制：
- **表级与行级权限**：`SELECT`, `INSERT`, `DELETE`, `ALL PRIVILEGES`；
- **列级精细控制**：`UPDATE(<列名1>, <列名2>)`——只允许用户修改特定列，严禁篡改其他敏感列；
- **参照外码权限**：`REFERENCES(<列名>)`——允许在创建从表时将该列作为外码引用。

##### ② 被授权者（TO 子句）：
- 可以是具体的一个或多个用户名（如 `TO U1, U2`）；
- 可以是数据库角色（如 `TO Role_Analyst`）；
- 可以是系统保留关键字 **`PUBLIC`**：将权限一次性开放给全数据库的**所有现存用户以及未来新建的所有新用户**。

---

#### 2.2 WITH GRANT OPTION 的传播与安全铁律

- 若在 `GRANT` 语句末尾追加了 **`WITH GRANT OPTION`**：
  - 获得该权限的用户不仅自己可以使用该权限，还可以**自主地将该权限进一步转授给其他合法用户**；
  - 若未指定此子句，被授权者只能在自身的会话中使用该权限，**绝无权将其转借给任何人**。
- **防止死循环传播公理**：SQL 规范强制要求：**授权有向图中严禁出现有向环（Cycle）**。系统在每次执行带转授的 `GRANT` 时，都会通过数据字典拓扑扫描，防止出现 $A \to B \to C \to A$ 的回环循环引用。

---

### 3. REVOKE 收权语句与级联收回机理

#### 3.1 REVOKE 标准语法规约

```sql
REVOKE <权限> [, <权限>]...
ON <对象类型> <对象名>
FROM <用户> [, <用户>]... [CASCADE | RESTRICT];
```

---

#### 3.2 CASCADE（级联收权）算法深度推导

> **【高频考研与工业核心痛点】**：如果用户 A 将权限转授给了 B，B 又将权限转授给了 C。现在 A 决定收回对 B 的授权，那么 C 的权限应该怎么办？

```text
【级联收回算法图解】
      用户 A (属主)
           │
      REVOKE SELECT FROM B CASCADE;
           │
           ├──> [用户 B 的权限被强制剥离]
           │
           └──> [由于 B 已无权限，B 派生给 C 的权限随之发生"雪崩级联失效"!]
                [用户 C 的权限被系统自动同步收回!]
```

1. **`CASCADE`（级联模式）**：
   - 系统顺着授权图向下回溯，**所有直接或间接由被收权者转授出去的派生权限，被系统一并连带收回**；
   - **例外保护（独立来源合法性）**：如果用户 C 不仅从 B 处获得了该权限，**同时还独立从 DBA 或另一个合法用户 D 处获得了相同的授权**，那么在收回 B 的权限后，C 依然合法保留该权限。
2. **`RESTRICT`（受限模式）**：
   - 系统检查若发现用户 B 已经将该权限转授给了他人（如 C），则**立即拒绝执行收权并报错**，强制要求管理员先手工清理下级节点的授权后，再收回源头权限。

---

### 4. 经典授权实战代码矩阵

```sql
-- 1. 把对 Student 表和 Course 表的全部操作权限授予用户 U1 和 U2
GRANT ALL PRIVILEGES 
ON TABLE Student, Course 
TO U1, U2;

-- 2. 把对 SC 表的查询权限授予所有用户 (PUBLIC)
GRANT SELECT 
ON TABLE SC 
TO PUBLIC;

-- 3. 把对 Student 表的学号和姓名修改权限授予用户 U3，并允许其转授
GRANT UPDATE(Sno, Sname) 
ON TABLE Student 
TO U3 
WITH GRANT OPTION;

-- 4. 从用户 U3 身上收回对 Student 表学号的修改权限，并执行级联收权
REVOKE UPDATE(Sno) 
ON TABLE Student 
FROM U3 CASCADE;
```

## 第 4 章：第4章  数据库安全性（4）
> 对应分集：P33 | 原始标题：《第4章  数据库安全性（4）》

### 1. 核心概念与本质内涵：为什么现代数据库必须引入“角色”？

在早期的自主存取控制（DAC）中，权限是直接绑定在每一个独立的用户账号身上的（如 `GRANT SELECT ON Student TO User_Wang`）。

#### 1.1 直接用户授权在大型组织中的管理灾难
当企业规模扩大、拥有成百上千名员工、成千上万张数据表时，直接用户授权会迅速引发“**权限矩阵爆炸**”：
- **人员流动开销巨大**：当一名员工调动岗位时，管理员必须手动检索其拥有的几十项权限逐一撤销，再逐一配置新岗位的权限，极易产生权限残留（Privilege Creep）安全漏洞；
- **配置复杂度高且易出错**：若同一岗位的 50 名员工权限稍有微小差异，排查系统故障与合规审计将变成一场噩梦。

#### 1.2 角色（Role）的形式化界定
**数据库角色（Role）是被命名的一组与数据库操作相关的权限的集合**。
它在用户与具体数据权限之间建立了一个优雅的间接抽象解耦层，构成了现代信息安全理论中著名的 **RBAC（Role-Based Access Control，基于角色的访问控制）**模型。

```text
               RBAC 基于角色的访问控制架构
+-----------------------------------------------------------------+
| 权限空间 (Privileges):                                          |
| SELECT ON Student / UPDATE ON SC / INSERT ON Course ...         |
+-----------------------------------------------------------------+
                                ▲
                                │ 1. 将一组细粒度权限统一打包赋予角色
+-----------------------------------------------------------------+
| 角色集合 (Roles):                                               |
| - Role_Teacher (教师角色)   - Role_Dean (教务长角色)             |
| - Role_Student (学生角色)   - Role_Auditor (审计员角色)          |
+-----------------------------------------------------------------+
                                ▲
                                │ 2. 将特定角色赋予具体用户 (一对多/多对多)
+-----------------------------------------------------------------+
| 用户群体 (Users):                                               |
| 张老师 (工号 101)  李老师 (工号 102)  王同学 (学号 2026) ...     |
+-----------------------------------------------------------------+
```

---

### 2. 数据库角色的完整生命周期管理

#### 2.1 创建角色（CREATE ROLE）

```sql
CREATE ROLE <角色名>;
```
例如，为高校教务管理系统分别设立“教务处管理员”角色与“任课教师”角色：
```sql
CREATE ROLE Role_Dean;
CREATE ROLE Role_Teacher;
```

---

#### 2.2 为角色分配权限（GRANT ... TO Role）

角色本身可以像普通用户一样，接收来自对象属主或 DBA 授予的各种数据定义、操作与控制权限：

```sql
-- 为教师角色赋予查询学生表和录入成绩的权限
GRANT SELECT ON TABLE Student TO Role_Teacher;
GRANT SELECT, INSERT, UPDATE(Grade) ON TABLE SC TO Role_Teacher;

-- 为教务长角色赋予全量管理权限
GRANT ALL PRIVILEGES ON TABLE Student, Course, SC TO Role_Dean;
```

---

#### 2.3 将角色授予具体用户（GRANT Role TO User）

权限打包完成后，只需将角色绑定给实际的用户账号：

```sql
GRANT <角色1> [, <角色2>]...
TO <用户1> [, <用户2>]... [角色]
[WITH ADMIN OPTION];
```

- **参数解析**：
  - 一个用户可以同时被授予**多个角色**（其拥有的实际权限为所有赋予角色的权限**并集**）；
  - **`WITH ADMIN OPTION`**：获得该角色的用户还可以自主地将该角色进一步授予其他用户或回收该角色；
  - **角色嵌套与继承（Role Hierarchy）**：可以将一个角色授予另一个角色（例如将 `Role_Teacher` 授予 `Role_Dean`，则教务长角色自动继承教师角色的全部权限）。

```sql
-- 将教师角色分别赋予工号为 T01、T02 的实际老师
GRANT Role_Teacher TO Teacher_Zhang, Teacher_Li;

-- 将教务长角色授予管理员，并允许其转授权限
GRANT Role_Dean TO Dean_Wang WITH ADMIN OPTION;
```

---

#### 2.4 回收角色的权限与撤销角色授权（REVOKE）

1. **从角色身上剥离权限**：
   ```sql
   -- 取消教师角色修改成绩的权限 (所有绑定了该角色的教师立即全部失去该权限)
   REVOKE UPDATE(Grade) ON TABLE SC FROM Role_Teacher;
   ```
2. **从用户身上剥离角色身份**：
   ```sql
   -- 当张老师离职或转岗到后勤时，直接剥离其教师角色
   REVOKE Role_Teacher FROM Teacher_Zhang;
   ```
3. **销毁角色**：
   ```sql
   DROP ROLE Role_Teacher;
   ```

---

### 3. 典型例题与深度认知辨析

#### 辨析 1：`WITH GRANT OPTION` 与 `WITH ADMIN OPTION` 有何区别？

- **本质对比**：
  - **`WITH GRANT OPTION`**：专门用于**对象权限（Object Privileges）**的授予传播（针对表、视图的增删改查）；
  - **`WITH ADMIN OPTION`**：专门用于**系统权限（System Privileges）或角色（Roles）**的授予传播；
  - 核心行为差异：使用 `REVOKE` 撤销带 `WITH ADMIN OPTION` 的角色授权时，**通常不会发生下游雪崩式的级联撤销（No Cascading Revoke）**，下游获得该角色的用户依然保留角色，避免了因单个管理员调岗导致整个部门角色瘫痪。

B. 将权限的集合与用户解耦，极大简化了用户权限的批量分配与离职调岗维护成本

## 第 5 章：第4章  数据库安全性（5）
> 对应分集：P34 | 原始标题：《第4章  数据库安全性（5）》

### 1. 核心概念与本质内涵：为什么自主存取控制（DAC）不够安全？

自主存取控制（DAC）依靠客体属主的意愿进行授权。在第 2 讲中我们指出，DAC 存在一个致命的根本缺陷——**无法抵御“特洛伊木马（Trojan Horse）”式的信息隐蔽流动**：
- 如果一个拥有最高“绝密”权限的指挥官，在终端上运行了一个被植入恶意木马脚本的外部数据统计程序；
- 该程序利用指挥官的高合法权限，暗中读取了国防绝密表，并随手将其 `INSERT` 到一个权限公开的公共临时表中；
- 随后，敌方间谍只需以最低的公开用户身份登录，即可读取该公共表并窃取全部情报；
- 在整个攻击链条中，所有用户与程序的每一步操作都完全符合 DAC 的自主授权规则，DAC 安全系统对此类合法实体的恶意背叛完全无知无觉！

为了从根本上彻底杜绝这种非法信息泄露，关系数据库安全理论引入了**强制存取控制（Mandatory Access Control, MAC）**。

```text
               强制存取控制 (MAC) 的中央集权模型
+---------------------------------------------------------------+
| 中央安全策略内核 (Security Kernel): 规则不可篡改、权限不可转让 |
+---------------------------------------------------------------+
                              │
        ┌─────────────────────┴─────────────────────┐
        ▼                                           ▼
【主体 (Subject: 用户/进程)】               【客体 (Object: 表/行/字段)】
 分配许可证级别 (Clearance)                  标记密级 (Classification)
 • 绝密 (Top Secret, TS)                    • 绝密 (Top Secret, TS)
 • 机密 (Secret, S)                         • 机密 (Secret, S)
 • 秘密 (Confidential, C)                   • 秘密 (Confidential, C)
 • 公开 (Public, P)                         • 公开 (Public, P)
```

---

### 2. 主体、客体与敏感度标记体系

在 MAC 体系中，系统中的一切实体被抽象并形式化标记：

1. **主体（Subject）**：
   - 是系统中的**活动实体**，既包括数据库的具体用户，也包括代表该用户在后台运行的进程、事务与线程；
   - 每个主体被安全管理员正式赋予一个固定的**许可证级别（Clearance Level）**。
2. **客体（Object）**：
   - 是系统中的**被动实体**，是受操作系统与 DBMS 保护的数据载体（基本表、视图、物理文件、甚至单个数据页与单个元组行）；
   - 每个客体被固化打上一个**密级标记（Classification Level）**。
3. **敏感度标记（Security Label）的高低顺序**：
   $$\text{绝密 (Top Secret, TS)} > \text{机密 (Secret, S)} > \text{秘密 (Confidential, C)} > \text{公开 (Public, P)}$$

---

### 3. Bell-LaPadula（BLP）多级机密性访问控制模型

为了从数学上证明信息绝不会由高密级向低密级非法渗透，David Bell 与 Leonard LaPadula 于 1973 年提出了著名的 **Bell-LaPadula（BLP）机密性模型**。BLP 包含两条核心不可违背的访问定理：

```text
                      BLP 模型的两大黄金读写规则
                                  │
      ┌───────────────────────────┴───────────────────────────┐
      ▼                                                       ▼
【规则 1: 简易安全特性 (No Read Up)】          【规则 2: 星号特性 (No Write Down)】
        "向下读" (Read Down)                           "向上写" (Write Up)
 • 仅当: 主体许可证 ≥ 客体密级                  • 仅当: 主体许可证 ≤ 客体密级
 • 高密级主体可以读取低密级客体                 • 低密级主体可以向高密级客体写入数据
 • 严禁向上偷窥更高密级信息!                    • 严禁高密级主体向低密级客体写出数据!
```

---

#### 3.1 规则 1：简易安全特性（Simple Security Property）——“向下读（No Read Up）”

- **形式化表达**：主体 $S$ 只有在满足下述条件时，才被允许对客体 $O$ 执行**读取（Read / SELECT）**操作：
  $$L(S) \ge L(O)$$
- **现实语义**：一个拥有“机密（S）”许可证的特工，可以向下阅读“机密（S）”、“秘密（C）”和“公开（P）”的情报文件；但**绝对不能向上越权阅读“绝密（TS）”**的文件。

---

#### 3.2 规则 2：星号特性（$\star$-Property）——“向上写（No Write Down）”

- **形式化表达**：主体 $S$ 只有在满足下述条件时，才被允许对客体 $O$ 执行**写入/追加/修改（Write / INSERT / UPDATE）**操作：
  $$L(S) \le L(O)$$
- **直觉认知冲突与反常识解密**：
  > **【初学者最大困惑】**：“为什么不允许高密级的人向低密级写东西？难道司令官还不能给小兵发一份公开通报吗？”

##### 为什么必须强制“No Write Down”？
- 这正是**彻底斩断“特洛伊木马”外泄通道的核心命门**！
- 设想：若允许高密级主体向低密级客体写数据，那么指挥官（TS 级）运行的木马程序，就可以合法地把 TS 级的数据写入 P 级公共表；
- 一旦强制推行了“**No Write Down**”：
  - 拥有“绝密（TS）”许可证的主体，在当前会话中**只能向 TS 级客体写入，绝对不能向 S, C, P 等更低密级的表写入哪怕一个字节**！
  - 此时，即使木马程序偷偷复制了绝密数据，当它试图写入公共表（P 级）时，底层安全内核会因为 $L(S) 
ot\le L(O)$（$\text{TS} 
ot\le \text{P}$）而**强行中断写入并报警**！
- 这一规则从数学上严格封死了数据由高密级流向低密级的任何可能性。

---

### 4. MAC 与 DAC 的综合双重校验架构

在支持强制存取控制的高安全系统（TCSEC B1 级以上）中，系统**并不是用 MAC 取代 DAC，而是将两者组合为双重防火墙**：

```text
           DBMS 访问请求的双重过滤漏斗
用户发出 SQL 数据访问请求 (User Query)
                 │
                 ▼
     [第一道关卡: DAC 自主存取检查]
      检查该用户是否拥有该表的 SELECT 权限
                 │
                 ├── 没通过 ──> 立即报错拒绝
                 ▼ 通过
     [第二道关卡: MAC 强制密级规则检查]
      比对主体许可证 L(S) 与客体密级 L(O)
      严格验证 No Read Up 与 No Write Down
                 │
                 ├── 没通过 ──> 立即安全拦截
                 ▼ 通过
          执行磁盘 I/O 返回结果
```

---

### 5. 随堂巩固自测

#### 自测题 1（单项选择题）
在基于 Bell-LaPadula（BLP）模型的强制存取控制系统中，许可证级别为“机密（Secret）”的用户，在系统中被允许执行的操作是（ ）
A. 读取“绝密（Top Secret）”客体，写入“公开（Public）”客体  
B. 读取“秘密（Confidential）”客体，向“绝密（Top Secret）”客体追加数据  
C. 读取“绝密（Top Secret）”客体，向“绝密（Top Secret）”客体修改数据  
D. 向“公开（Public）”客体写入数据，且能读取所有级别客体  

**【答案】**：B  
**【解析】**：
- 读规则（No Read Up）：$L(S) \ge L(O)$，机密级（Secret）用户只能向下读取密级 $\le \text{Secret}$ 的客体（即 Secret, Confidential, Public）；
- 写规则（No Write Down）：$L(S) \le L(O)$，机密级（Secret）用户只能向上写入密级 $\ge \text{Secret}$ 的客体（即 Secret, Top Secret）。
- 对照选项：读取“秘密”满足 $L(S) \ge L(O)$；写入“绝密”满足 $L(S) \le L(O)$。故选 B。

---

#### 自测题 2（安全模型机理分析题）
请简要说明 Bell-LaPadula（BLP）模型中“星号特性（$\star$-Property，即 No Write Down）”是如何从机制上彻底粉碎特洛伊木马窃密攻击的？

**【参考答案与推导】**：
特洛伊木马窃取机密的基本手法是：潜伏在高许可证级别（如绝密 TS 级）用户的操作上下文中，读取绝密客体，然后利用该用户的权限将数据转录到低安全级别（如公开 P 级）的共享客体中，供低权限攻击者读取。
BLP 模型的“星号特性”强制规定：**任何主体的写操作只能指向密级大于等于自身许可证的客体，严禁向低密级客体写出数据**。因此，当高许可证用户运行木马时，即便木马读到了绝密信息，由于其执行主体密级为 TS，系统内核会直接切断其向 P 级或低密级文件的一切写入尝试，使得被盗取的机密信息无法降级转移，从而在数学上彻底斩断了特洛伊木马的信息外泄通道。

## 第 6 章：第4章  数据库安全性（6）
> 对应分集：P35 | 原始标题：《第4章  数据库安全性（6）》

### 1. 核心概念与本质内涵：多维安全防护与事后追溯机制

除了前文详述的身份鉴别与存取控制（DAC/MAC）之外，成熟的企业级数据库安全体系还必须涵盖三大关键防御与治理手段：
1. **视图机制（View-based Security）**：实现轻量、细粒度的行级与列级数据隐蔽隔离；
2. **安全审计（Auditing）**：建立坚固的不可抵赖事后溯源与入侵取证记录；
3. **数据加密（Data Encryption）**：对抗脱机物理窃取与网络中间人嗅探的终极密码学防线。

```text
                     数据库高级安全防护三大支柱
                                 │
     ┌───────────────────────────┼───────────────────────────┐
     ▼                           ▼                           ▼
【视图机制: 逻辑隐蔽】         【安全审计: 事后取证】      【数据加密: 物理封锁】
 • 排除机密列 (列级屏蔽)       • 记录谁在何时做了什么      • 存储落盘加密 (TDE)
 • 谓词限定行 (行级隔离)       • 审计日志独立受保护        • 网络传输加密 (SSL/TLS)
 • 配合 GRANT 授予虚表权限     • 威慑内部恶意破坏人员      • 防止拔硬盘/脱机冷备份失窃
```

### 2. 视图机制在安全性控制中的深度应用

在关系数据库中，视图是天然的**数据访问沙箱（Sandbox）**：
- 基本表往往包含完整、敏感的数据字段（例如员工表 `Employee` 包含工号、姓名、部门、身份证号、银行卡号与核心薪资）；
- 普通业务人员（如部门考勤员）只需要访问工号、姓名和部门，若直接对基本表授予 `SELECT` 权限，会导致敏感薪酬与隐私全量暴露；
- **标准安全架构方案**：
  1. 创建一个排除了敏感字段并限定了部门范围的专用安全视图：
     ```sql
     CREATE VIEW V_Dept_Attendance AS
     SELECT EmpID, EmpName, Dept
     FROM Employee
     WHERE Dept = '研发部';
     ```
  2. **收回普通用户对底层 `Employee` 基本表的任何访问权限**；
  3. **仅向考勤员授予该视图的查询权限**：
     ```sql
     GRANT SELECT ON V_Dept_Attendance TO Clerk_Zhang;
     ```
- 这样，考勤员不仅无法窥探薪资和银行卡等敏感列（列级保护），而且在逻辑上也绝无可能读取到市场部或财务部的员工信息（行级保护）。

### 3. 数据库安全审计机制（Auditing）

审计机制是 TCSEC C2 级以上系统的硬性刚性指标。

#### 3.1 审计的定义与核心功能
**审计（Auditing）是指 DBMS 把用户对数据库的所有或特定操作自动记录到专用的系统审计日志（Audit Trail）中**。
- **事后追溯与法律取证**：当数据库遭到恶意篡改、非法拖库或商业机密外泄时，安全分析员可以通过分析审计日志，精确还原黑客攻击路径，追查内鬼账号与发生的确切时间戳；
- **威慑心理**：合法用户一旦得知自身的一切操作（即使是拥有极高权限的管理员）均被不可篡改地持续记录在案，会极大遏制内部越权犯罪冲动。

#### 3.2 审计的粒度与分类
1. **用户级审计（User-level Auditing）**：针对特定可疑用户发起的所有操作进行全程盯防录像；
2. **系统级审计（System-level Auditing）**：监控所有用户对数据库系统结构模式（如所有的 `CREATE`, `DROP`, `ALTER` 语句）以及用户授权命令的发起；
3. **对象级审计（Object-level Auditing）**：专门针对极度敏感的核心业务表（如银行核心账务表、社保基金表）的一切 DDL 和 DML 操作进行记录。

```sql
-- 开启审计: 对 Student 表上的所有更新和删除操作进行全量审计
AUDIT UPDATE, DELETE ON TABLE Student;

-- 取消审计配置
NOAUDIT UPDATE, DELETE ON TABLE Student;
```

> **性能与磁盘权衡**：审计机制每次记录都会引发额外的持久化磁盘写 I/O。如果对全库所有表的每一个简单 `SELECT` 查询无脑全开审计，会导致系统吞吐骤降并迅速撑爆磁盘。工业界通常遵循“**关键对象审计 + 高危写操作审计**”的针对性配置原则。

### 4. 数据库数据加密技术（Encryption）

#### 4.1 传输加密（In-Transit Encryption）
- 客户端与数据库服务器之间通过 **SSL / TLS（安全套接层 / 传输层安全协议）**建立双向加密隧道；
- 防止恶意黑客利用 Wireshark 等网络嗅探抓包工具窃听明文 SQL 和返回数据。

#### 4.2 存储落盘加密（At-Rest Encryption / TDE）
- **透明数据加密（Transparent Data Encryption, TDE）**：
  - 数据在内存缓冲池写入磁盘数据文件时，由引擎利用硬件加速指令集（AES-256）自动执行实时加密；
  - 数据页从磁盘加载回内存时，自动解密；
  - 对上层应用程序和开发人员完全透明无感；
  - **核心价值**：即便黑客物理潜入机房拔走了整块服务器硬盘，或者盗取了数据库的离线冷备份文件，因缺失主加密密钥，打开数据文件后看到的完全是一堆不可逆的乱码。

### 6. 随堂巩固自测

#### 自测题 1（单项选择题）
数据库系统中，使用视图机制（View）来加强数据安全性的核心机理是（ ）
A. 视图在磁盘上自动采用了 RSA 2048 位非对称加密  
B. 通过在视图中限定属性列与行选择条件，并对视图授权，向用户隐蔽敏感数据  
C. 视图自动开启了后台审计日志追踪  
D. 视图强制执行了 Bell-LaPadula 模型的星号特性  

**【答案】**：B  
**【解析】**：视图本身是一个查询定义，通过在视图定义中排除机密列并利用 WHERE 子句限制可见行，配合 DBMS 的存取控制只授予用户对视图的权限，从而精确限制用户的访问视野，达到安全隔离的目的。故选 B。

#### 自测题 2（综合安全设计题）
某金融借贷系统有一张核心客户表：`Customer(CID, Cname, Phone, CreditScore, LoanAmount, BankCard)`。
现有两组外部业务角色：
1. **呼叫中心客服人员（CallAgent）**：仅允许查看客户编号、姓名和联系电话，以便拨打电话，严禁接触信用分、借贷金额与银行卡号；
2. **风控审核专员（RiskAuditor）**：允许查看客户编号、姓名、信用分和借贷金额，但为保护个人隐私，严禁查看手机号和完整银行卡号。  
请使用**视图机制**与 **SQL 权限授予（GRANT）**，为这两类人员设计标准、合规的安全性解决方案。

**【参考答案】**：
```sql
-- 1. 为呼叫中心客服建立专用视图 (列级脱敏)
CREATE VIEW V_CallAgent_Customer AS
SELECT CID, Cname, Phone
FROM Customer;

-- 2. 为风控审核专员建立专用视图 (隔离通信与银行卡)
CREATE VIEW V_RiskAuditor_Customer AS
SELECT CID, Cname, CreditScore, LoanAmount
FROM Customer;

-- 3. 创建对应的数据库角色
CREATE ROLE Role_CallAgent;
CREATE ROLE Role_RiskAuditor;

-- 4. 仅对视图授权，绝不对底层 Customer 基本表直接授权
GRANT SELECT ON V_CallAgent_Customer TO Role_CallAgent;
GRANT SELECT ON V_RiskAuditor_Customer TO Role_RiskAuditor;

-- 5. 将角色分配给具体的业务用户组
GRANT Role_CallAgent TO User_Call01, User_Call02;
GRANT Role_RiskAuditor TO User_Risk01;
```
