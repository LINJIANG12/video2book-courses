## 第 1 章：第8章 数据库编程（1）
> 对应分集：P57 | 原始标题：《第8章 数据库编程（1）》

### 1. 核心概念与本质内涵：为什么需要数据库编程？

SQL 是一种声明式语言（Declarative Language），在关系数据集合的查询与批处理上极具威力。
然而，单纯依赖交互式 SQL 无法解决复杂的现实应用需求：
1. **缺乏过程化控制能力**：标准 SQL 不支持分支判断（`if-else`）、循环迭代（`while/for`）和复杂的业务算法（如复杂的薪资计算公式、图形渲染）；
2. **无法直接构建人机交互系统**：最终用户无法直接在命令行敲击原始 SQL，必须通过图形界面（Web、移动端 APP、桌面客户端）与数据交互。

因此，必须将 **SQL 的强大集合数据操纵能力** 与 **通用高级程序设计语言（宿主语言，如 C/C++, Java, Python）的灵活过程化控制能力** 有机结合起来，这就是**数据库编程（Database Programming）**。

```text
                     数据库编程的技术演进路径
                                 │
     ┌───────────────────────────┼───────────────────────────┐
     ▼                           ▼                           ▼
【1. 嵌入式 SQL (ESQL)】        【2. 过程化 SQL (PL/SQL)】    【3. 通用 API / 驱动】
 • SQL 嵌入 C/COBOL 等宿主语言   • 将过程化逻辑直接注入 DBMS   • ODBC / JDBC 标准接口
 • 依赖预编译器 (Precompiler)    • 存储过程与函数 (服务端执行) • 现代应用开发事实标准
```

---

### 2. 嵌入式 SQL（Embedded SQL）的核心工作机理

嵌入式 SQL 是将 SQL 语句直接嵌入到高级宿主语言（Host Language）源代码中编写的一种传统工业级标准。

#### 2.1 预编译机制（Precompilation）
通用高级语言（如 C 语言的 `gcc` 编译器）并不认识 SQL 的语法结构。因此，系统引入了**预编译器（Precompiler）**：

```text
              嵌入式 SQL 预编译与编译两阶段流水线
 嵌入式源代码 (*.ec / *.sqc, 混写 C 与 EXEC SQL)
                      │
                      ▼
            [DBMS 专用预编译器]
                      │
   ├── 1. 识别并提取所有 EXEC SQL 块
   ├── 2. 转换为底层标准 DBMS 运行库 C 语言函数调用
   └── 3. 生成纯净的标准 C 语言源码文件 (*.c)
                      │
                      ▼
               [宿主语言 C 编译器]
                      │
                      ▼
               [链接器 (Linker)] ──> 引入数据库动态链接库
                      │
                      ▼
           最终可执行二进制程序 (*.exe)
```

---

### 3. 语法标识与宿主语言通信三剑客

在嵌入式 SQL 中，为了让预编译器精准识别，所有 SQL 语句必须以前缀 **`EXEC SQL`** 开头，并以特定符号（C 语言中为分号 `;`）结束：

```c
EXEC SQL <SQL 语句>;
```

#### 3.1 通信核心 1：主变量（Host Variable / 共享变量）
- **定义**：由宿主语言程序定义，并被嵌入的 SQL 语句直接引用的变量；
- **作用**：扮演数据传输的“双向邮差”：
  - **输入主变量**：应用程序将变量值作为查询条件参数传递给 SQL 语句；
  - **输出主变量**：SQL 语句执行后将查询到的字段值回填给应用程序变量；
- **核心语法规则**：
  1. 主变量必须在 `EXEC SQL BEGIN DECLARE SECTION;` 与 `EXEC SQL END DECLARE SECTION;` 块中声明；
  2. **在 SQL 语句中使用主变量时，主变量名前面必须加冒号（`:`）作为前缀引导**（用以与数据库中的表列名做明确区分）；而在纯 C 语言语句中引用该变量时，不加冒号。

```c
EXEC SQL BEGIN DECLARE SECTION;
    char hs_sno[10];     /* 主变量: 对应数据库中的 Sno */
    char hs_sname[21];   /* 主变量: 对应数据库中的 Sname */
    int  hs_sage;        /* 主变量: 对应数据库中的 Sage */
EXEC SQL END DECLARE SECTION;
```

---

#### 3.2 通信核心 2：指示变量（Indicator Variable）与 NULL 处理

> **【阻抗失配难题】**：C 语言等传统宿主语言中根本没有“空值（NULL）”这一数据类型（只有 0 或空指针）。当数据库中某个字段的值是 `NULL` 时，如何传递给 C 语言变量？

- **解决方案**：引入**指示变量（Indicator Variable）**；
- 指示变量是一个 2 字节的整型主变量（`short`），紧跟在目标主变量后面（以冒号引导）；
- **取值规范**：
  - 若查询返回的值为 `NULL`，DBMS 自动将指示变量的值赋为**负数（通常为 `-1`）**；
  - 若查询返回的值非空，指示变量的值为 **`0`**；
  - 若发生字符串截断，指示变量记录被截断前的原始长度（正数）。

```c
short ind_grade; /* 声明指示变量 */

EXEC SQL SELECT Grade INTO :hs_grade :ind_grade 
         FROM SC 
         WHERE Sno = :hs_sno AND Cno = 'C01';

if (ind_grade < 0) {
    printf("该学生缺考，成绩为 NULL!\n");
} else {
    printf("学生实际得分: %d\n", hs_grade);
}
```

---

#### 3.3 通信核心 3：SQL 通信区（SQLCA）与状态码

DBMS 通过一个名为 **SQLCA（SQL Communication Area）**的数据结构向宿主程序反馈每一步 SQL 的执行状态：
```c
EXEC SQL INCLUDE SQLCA;
```
- **核心状态字段 `SQLCODE`**：
  - **`SQLCODE == 0`**：SQL 语句执行成功无异常；
  - **`SQLCODE > 0`**：执行成功，但有告警（最典型的 `SQLCODE == 100` 代表**未找到符合条件的元组，或游标已读取到末尾**）；
  - **`SQLCODE < 0`**：执行遭遇严重错误（如语法错误、主键冲突、网络中断）。

### 1. 核心概念与本质内涵：什么是“阻抗失配”？

在数据库与高级程序语言交互的世界中，存在一条著名的理论鸿沟——**阻抗失配（Impedance Mismatch）**：
- **SQL 语言的运算模型是“一次一集合（Set-at-a-time）”**：一条简单的 `SELECT` 查询可以瞬间从数据库中检索出 10,000 条数据行构成的二维集合；
- **通用高级语言（C/C++, Java）的变量模型是“一次一记录（Record-at-a-time）”**：主变量通常只能容纳单个标量或单一结构体。

> **核心工程矛盾**：宿主语言程序根本无法直接用一个普通的变量去承载并逐行处理包含几百上千行的 SQL 结果集！

为了化解集合操作与单行处理之间的致命冲突，关系数据库系统设计了核心的中介数据结构——**游标（Cursor）**。

```text
                  游标作为行级缓冲指针的协调机制
 SQL 多行查询结果集 (Active Set)               宿主语言 C 程序环境
+-------------------------------+              +--------------------+
| Row 1: 202601  张  三   20    |              | 主变量:            |
+-------------------------------+              | char  hs_sno[10];  |
| Row 2: 202602  李  四   19    | <──[游标指针]| char  hs_sname[20];|
+-------------------------------+              | int   hs_sage;     |
| Row 3: 202603  王  五   21    |              +--------------------+
+-------------------------------+                         ▲
| Row N: 202699  赵  六   20    |                         │ 每次 FETCH 推进一行，
+-------------------------------+                         │ 提取当前行填充主变量
```

---

### 2. 游标操作的四步标准生命周期

在嵌入式 SQL 程序中，使用游标处理多行查询必须严格遵循**声明 $\to$ 打开 $\to$ 推进提取 $\to$ 关闭**的四步曲：

```text
               游标四大生命周期阶段
[第 1 步: DECLARE CURSOR (声明游标)] ──> 静态绑定 SQL 语句，尚未执行
                 │
                 ▼
[第 2 步: OPEN CURSOR (打开游标)]    ──> 执行查询，生成活动集，指针置于首行前
                 │
                 ▼
[第 3 步: FETCH ... INTO (推进读取)] ──> 循环向下推进行指针，填充主变量
                 │ (直到 SQLCODE == 100 抵达结果集末尾)
                 ▼
[第 4 步: CLOSE CURSOR (关闭游标)]   ──> 释放游标占据的内部临时缓冲区
```

---

#### 2.1 阶段 1：声明游标（DECLARE CURSOR）
- **语法**：
  ```sql
  EXEC SQL DECLARE <游标名> CURSOR FOR <SELECT 语句>;
  ```
- **机理**：此步骤是一条声明性说明，**DBMS 并不真正执行查询**，也不占用任何运行时内存，仅仅在数据字典中绑定该游标对应的逻辑 SQL。

---

#### 2.2 阶段 2：打开游标（OPEN CURSOR）
- **语法**：
  ```sql
  EXEC SQL OPEN <游标名>;
  ```
- **机理**：DBMS 此时正式执行该 `SELECT` 语句，从底层磁盘检索数据并在系统内存中开辟一块**活动集合缓冲区（Active Set）**；
- **指针初始位置**：游标指针初始化停留在**活动集第一条元组的前面（虚空位置）**。

---

#### 2.3 阶段 3：推进游标并提取数据（FETCH INTO）
- **语法**：
  ```sql
  EXEC SQL FETCH <游标名> INTO <主变量1> [, <主变量2>]...;
  ```
- **机理**：
  1. 将游标指针沿活动集向下推移定位到**下一条合法元组**；
  2. 将该元组各列的分量值，按顺序一对一精准赋值给 `INTO` 子句后面对应的宿主主变量；
- **循环终止检测**：当游标已经读完最后一行、再次执行 `FETCH` 时，DBMS 会自动将通信区中的 **`SQLCODE` 置为 `100`（代表“未找到数据 / 已达末尾”）**，程序通过检测此状态码平滑跳出 `while` 循环。

---

#### 2.4 阶段 4：关闭游标（CLOSE CURSOR）
- **语法**：
  ```sql
  EXEC SQL CLOSE <游标名>;
  ```
- **机理**：通知 DBMS 销毁对应的活动集合，**彻底释放其占用的服务器内存与会话缓存句柄**。

---

### 3. 完整 C 语言游标查询实战范式

```c
#include <stdio.h>
EXEC SQL INCLUDE SQLCA; /* 引入通信区 */

int main() {
    EXEC SQL BEGIN DECLARE SECTION;
        char dept[20] = "CS";
        char sno[10];
        char sname[21];
        int  sage;
    EXEC SQL END DECLARE SECTION;

    /* 连接数据库 */
    EXEC SQL CONNECT TO my_database USER db_user IDENTIFIED BY secret;

    /* 1. 声明游标: 检索计算机系全部学生 */
    EXEC SQL DECLARE cur_student CURSOR FOR
        SELECT Sno, Sname, Sage 
        FROM Student 
        WHERE Sdept = :dept;

    /* 2. 打开游标 */
    EXEC SQL OPEN cur_student;

    printf("学号\t\t姓名\t\t年龄\n");
    printf("----------------------------------------\n");

    /* 3. 循环推进提取数据 */
    while (1) {
        EXEC SQL FETCH cur_student INTO :sno, :sname, :sage;
        
        if (sqlca.sqlcode == 100) {
            /* 已读取到结果集末尾，优雅跳出 */
            break;
        }
        if (sqlca.sqlcode < 0) {
            printf("读取数据发生异常: %ld\n", sqlca.sqlcode);
            break;
        }

        printf("%s\t%s\t%d\n", sno, sname, sage);
    }

    /* 4. 关闭游标 */
    EXEC SQL CLOSE cur_student;

    /* 断开连接 */
    EXEC SQL DISCONNECT CURRENT;
    return 0;
}
```

### 4. 基于游标的当前行定位更新与删除（WHERE CURRENT OF）

在很多交互式批处理系统中，业务逻辑要求：在读取到某一行数据并进行本地逻辑分析后，**当场对游标当前所指向的这一行记录发起物理修改或删除**：

#### 核心语法规约：
1. **加锁声明**：在声明游标时，必须显式追加 `FOR UPDATE` 子句（这会强制让 DBMS 在扫描时为活动集的行施加排他锁，防止并发事务将其提前篡改）；
2. **当前行定位**：在 `UPDATE` 或 `DELETE` 语句的 `WHERE` 子句中，使用固定语法：
   ```sql
   WHERE CURRENT OF <游标名>;
   ```

```c
/* 声明可更新游标 */
EXEC SQL DECLARE cur_salary CURSOR FOR
    SELECT EmpID, Salary FROM Employee WHERE Dept = 'CS'
    FOR UPDATE;

EXEC SQL OPEN cur_salary;
while (1) {
    EXEC SQL FETCH cur_salary INTO :empid, :salary;
    if (sqlca.sqlcode == 100) break;
    
    if (salary < 5000) {
        /* 精确对游标当前指向的这一行员工记录涨薪 500 元 */
        EXEC SQL UPDATE Employee 
                 SET Salary = Salary + 500 
                 WHERE CURRENT OF cur_salary;
    }
}
EXEC SQL CLOSE cur_salary;
```

### 5. 随堂巩固自测

#### 自测题 1（单项选择题）
在嵌入式 SQL 程序中使用游标处理多行查询时，当游标指针已经扫描并提取了活动集中的最后一条元组、再次执行 `FETCH` 时，系统通信区中的 `SQLCODE` 将被置为（ ）
A. 0  
B. -1  
C. 100  
D. NULL  

**【答案】**：C  
**【解析】**：SQL 标准明确规定，当没有满足条件的元组返回，或游标推进已抵达集合末端时，状态码 `SQLCODE` 统一被赋值为正整数 `100`（NOT FOUND），程序据此终止循环。故选 C。

---

#### 自测题 2（概念分析题）
为什么普通的 `UPDATE Employee SET Salary = Salary + 100 WHERE Dept = 'CS'` 无法完全替代游标的 `WHERE CURRENT OF` 定位更新？请列举游标定位更新独有的核心优势场景。

**【参考答案与解析】**：
普通单条 `UPDATE` 语句只能执行简单的常量赋值或基于统一公式的批量修改。但在很多复杂业务场景中，**后续的修改决策高度依赖于高级语言中极其复杂的过程化算法**（例如：需要调用外部风控系统的微服务接口、根据用户复杂的信誉模型做多重规则判定、甚至需要与终端操作员进行二次弹窗交互确认）。在这种无法用纯单行 SQL 表达的场景下，通过游标将数据逐行提取到宿主程序内部，经过复杂的条件计算后，再利用 `WHERE CURRENT OF` 实施安全、精准的原地覆写，具有不可替代的工程价值。

### 1. 核心概念与本质内涵：什么是存储过程与存储函数？

在传统的客户端-服务器（C/S）交互架构中，应用程序通过网络向数据库服务器逐条发送零散的 SQL 语句。每条语句都需要经历网络往返、服务端文本解析、词法语法分析、语义校验、查询优化与执行计划生成，造成沉重的网络延迟与 CPU 算力浪费。

为了解决这一弊端，数据库技术引入了**存储过程（Stored Procedure）**与**存储函数（Stored Function）**：
- **定义**：它们是一组为了完成特定功能的 SQL 语句与过程化控制逻辑的集合，**经过编译后长久保存在数据库服务器的数据字典中**；
- 应用程序只需通过网络发送简短的调用命令（如 `CALL`）并传入必要参数，整个复杂的业务逻辑全权在服务器端内存中极速闭环运行。

```text
               普通网络交互 SQL vs 存储过程架构对比
【普通交互式 SQL: 多次往返】                   【存储过程: 一次调用，服务端闭环】
  应用客户端              数据库服务端           应用客户端              数据库服务端
      │                       │                      │                       │
      │ ── 1. 发送 SQL 1 ───> │                      │ ── CALL Proc(p1) ───> │ [加载预编译计划]
      │ <── 返回中间数据 1 ── │                      │                       │ ├── 内部循环执行
      │ ── 2. 发送 SQL 2 ───> │                      │                       │ ├── 内部事务控制
      │ <── 返回中间数据 2 ── │                      │                       │ └── 内部运算统计
      │ ── 3. 发送 UPDATE ──> │                      │ <── 仅返回最终结果 ── │
  (高网络延迟，频繁序列化反序列化)               (极低网络消耗，执行速度达到内存级极致)
```

---

### 2. 存储过程的核心优势矩阵

1. **预编译执行的高性能（Precompiled Execution）**：
   - 存储过程在第一次创建时，DBMS 就会对其进行深度的语法解析和代价估算，生成最优的底层二进制执行计划并**常驻在共享内存缓冲池中**；
   - 后续任何客户端再次发起调用，彻底跳过编译与优化阶段，直接以机器码级别极速执行。
2. **大幅削减网络流量（Reduced Network Traffic）**：
   - 将涉及几千行数据循环、数十次条件判断的复杂业务全权收敛在服务端本地执行，网络中只流动一条轻量的调用报文与最终标量结果。
3. **增强的数据安全防护（Security Decoupling）**：
   - DBA 可以将底层核心物理表（如银行资金表）的直接 `SELECT`, `UPDATE` 权限对普通应用账号完全锁死；
   - **仅向应用程序员授予特定存储过程的 `EXECUTE` 执行权限**。用户只能通过受控的过程逻辑黑盒修改数据，彻底阻断了 SQL 注入与非授权越权篡改。

### 3. 存储过程的创建语法与三大参数模式

#### 3.1 语法规约与参数模式（IN, OUT, INOUT）

```sql
CREATE PROCEDURE <过程名> (
    [IN | OUT | INOUT] <参数名> <数据类型> [, ...]
)
BEGIN
    <过程化 SQL 代码块>;
END;
```

```text
                       三大参数传递模式深度剖析
                                  │
      ┌───────────────────────────┼───────────────────────────┐
      ▼                           ▼                           ▼
【IN 参数 (默认输入模式)】      【OUT 参数 (纯输出模式)】      【INOUT 参数 (双向模式)】
 • 外部调用者传入参数值         • 初始值为 NULL               • 外部传入初始值作为输入
 • 过程体内部只读，不可篡改外部 • 过程体内部计算并赋值        • 过程体内部修改后作为输出回传
 • 类似 C 语言的按值传递        • 退出时将最终值回传给调用方  • 类似 C 语言的按引用指针传递
```

#### 3.2 存储过程生产开发实战演练

**需求场景**：为高校教务系统编写一个存储过程 `TransferStudent`，将某学生从原系别转移到新系别。
- 输入参数：学生学号 `in_sno`，目标系别 `in_new_dept`；
- 输出参数：操作执行状态码 `out_code`（0 代表成功，-1 代表该学生不存在）。

```sql
DELIMITER //

CREATE PROCEDURE TransferStudent (
    IN  in_sno      CHAR(9),
    IN  in_new_dept VARCHAR(20),
    OUT out_code    INT
)
BEGIN
    DECLARE v_count INT DEFAULT 0;

    -- 1. 检查目标学生是否存在
    SELECT COUNT(*) INTO v_count 
    FROM Student 
    WHERE Sno = in_sno;

    IF v_count = 0 THEN
        -- 学生不存在，返回错误码
        SET out_code = -1;
    ELSE
        -- 2. 学生存在，执行修改
        UPDATE Student 
        SET Sdept = in_new_dept 
        WHERE Sno = in_sno;
        
        SET out_code = 0;
    END IF;
END //

DELIMITER ;
```

##### 调用与执行方式：
```sql
-- 声明用户会话变量接收结果
CALL TransferStudent('202601', '软件工程', @status);
SELECT @status AS 执行结果状态码;
```

### 4. 存储过程 vs 存储函数的本质分野

除了存储过程，SQL 标准还提供了**存储函数（Stored Function）**。二者核心区别如下：

| 比较维度 | 存储过程（Stored Procedure） | 存储函数（Stored Function） |
| :--- | :--- | :--- |
| **关键字** | `CREATE PROCEDURE` | `CREATE FUNCTION` |
| **返回值机制** | **无直接单一返回值**，需通过 `OUT` 或 `INOUT` 参数间接传回多个值 | **强制必须包含 `RETURNS <类型>`** 与 `RETURN <单值>` 语句 |
| **调用执行方式** | 必须通过独立的 **`CALL` 语句** 单独触发 | **可以直接嵌入在任何普通的 SQL 表达式中**！ |
| **典型调用场景** | `CALL ProcName(p1, @out);` | `SELECT Sno, CalcRank(Grade) FROM SC;` |

```sql
-- 存储函数示例: 依据成绩返回等级
CREATE FUNCTION GetGradeLevel (p_grade INT)
RETURNS VARCHAR(10)
DETERMINISTIC
BEGIN
    IF p_grade >= 90 THEN RETURN '优秀';
    ELSEIF p_grade >= 80 THEN RETURN '良好';
    ELSEIF p_grade >= 60 THEN RETURN '及格';
    ELSE RETURN '不及格';
    END IF;
END;
```

CREATE PROCEDURE AdjustInterest (

    SET Balance = out_new_balance
    WHERE AccountID = in_acc_id;
END //

### 1. 核心概念与本质内涵：什么是过程化 SQL？

标准 SQL 虽然功能强大，但其核心本质是说明性的。当需要编写复杂的科学计算、多步骤串行依赖业务或自动化运维脚本时，必须将 SQL 扩展为图灵完备的结构化编程语言。

**过程化 SQL（Procedural SQL，以 Oracle 的 PL/SQL 及各家方言为代表）**是关系数据库管理系统对标准 SQL 的重大扩展：
- 它将变量声明、条件分支、循环遍历与异常捕获等传统结构化程序设计语言要素，与底层的 SQL 语句无缝焊接在一起；
- 整个代码块直接在数据库内核的**过程化引擎（PL Engine）**中高效运行。

```text
               PL/SQL 块的基本架构模型 (Block Structure)
[DECLARE] ──────────────── 可选: 声明局部变量、动态类型、游标与自定义异常
    -- 变量定义与类型绑定
BEGIN ──────────────────── 必选: 核心业务逻辑执行体
    -- 过程化控制语句 (IF / LOOP / FOR)
    -- 原生 SQL 操纵语句 (SELECT INTO / UPDATE / INSERT)
[EXCEPTION] ────────────── 可选: 运行时异常与错误拦截捕获
    -- WHEN 异常名 THEN 处理逻辑
END; ───────────────────── 块结束标志 (分号闭合)
```

### 2. 动态类型绑定神器：%TYPE 与 %ROWTYPE

在传统的嵌入式编程中，若数据库中的列定义从 `VARCHAR(20)` 扩容到 `VARCHAR(50)`，程序员必须在宿主代码中逐一修改变量长度并重新编译，否则会引发静默的内存截断或溢出崩溃。

PL/SQL 通过引入**动态元数据绑定属性**，从根源上彻底解除了这种强耦合：

```text
                  %TYPE 与 %ROWTYPE 动态映射
                             │
     ┌───────────────────────┴───────────────────────┐
     ▼                                               ▼
【列级绑定: %TYPE】                             【行级全记录绑定: %ROWTYPE】
 变量名 表名.列名%TYPE;                         变量名 表名%ROWTYPE;
 • 变量数据类型与底层表的某列严格镜像同步       • 变量自动变成一个复合记录结构体 (Record)
 • 底层字段扩容或变型，程序自动无感同步适配!    • 包含该表的全部字段，单行数据一次性打包装载!
```

#### 2.1 经典声明示范
```sql
DECLARE
    -- 1. 列级动态绑定: v_sname 的类型永远与 Student 表的 Sname 列完全一致
    v_sname Student.Sname%TYPE;
    v_grade SC.Grade%TYPE;
    
    -- 2. 行级全记录动态绑定: v_stu 自动拥有 Student 表全部列的结构
    v_stu Student%ROWTYPE;
BEGIN
    -- 一次性将一整行元组读入记录变量中!
    SELECT * INTO v_stu 
    FROM Student 
    WHERE Sno = '202601';

    -- 通过点号语法访问成员属性
    DBMS_OUTPUT.PUT_LINE('学生姓名: ' || v_stu.Sname || ', 年龄: ' || v_stu.Sage);
END;
```

### 3. 流程控制结构与优雅的“FOR 游标循环”

#### 3.1 条件分支与标准循环
```sql
-- 1. IF-THEN-ELSIF 条件分支
IF v_score >= 90 THEN
    v_level := '优秀';
ELSIF v_score >= 60 THEN
    v_level := '及格';
ELSE
    v_level := '不及格';
END IF;

-- 2. WHILE 循环结构
WHILE v_count < 100 LOOP
    v_count := v_count + 1;
END LOOP;
```

#### 3.2 游标操作的终极优雅范式：Cursor FOR Loop
在第 58 讲中，我们详细讲解了传统游标的“声明 $\to$ 打开 $\to$ 推进提取 $\to$ 判空跳出 $\to$ 关闭”的繁琐五步。
在 PL/SQL 中，提供了一种**全自动化的“FOR 游标循环”**：

```sql
DECLARE
    CURSOR cur_cs_students IS
        SELECT Sno, Sname, Sage FROM Student WHERE Sdept = 'CS';
BEGIN
    -- FOR 循环自动完成: 1. 隐式 OPEN; 2. 自动 FETCH; 3. 自动判空退出; 4. 自动 CLOSE!
    FOR stu_rec IN cur_cs_students LOOP
        DBMS_OUTPUT.PUT_LINE('学号: ' || stu_rec.Sno || ' 姓名: ' || stu_rec.Sname);
    END LOOP;
END;
```
> **架构价值**：零心智负担！彻底杜绝了因程序员疏忽漏写 `CLOSE cur` 导致的数据库内存游标泄露事故。

### 4. 完善的异常处理体系（Exception Handling）

在执行数据操作时，难免遇到除零错误、查无数据或主键冲突。若不加捕获，整个事务将异常崩溃中断。PL/SQL 提供了类似现代高级语言（Java/Python）的**结构化异常捕获系统**：

```sql
EXCEPTION
    WHEN <异常名1> [OR <异常名2>] THEN
        <处理语句>;
    WHEN OTHERS THEN
        <全局兜底处理语句>;
```

#### 4.1 四大最常见预定义系统异常（Predefined Exceptions）

| 异常标识名 | 错误触发条件与底层错误码 | 典型应对策略 |
| :--- | :--- | :--- |
| **`NO_DATA_FOUND`** | `SELECT INTO` 语句在执行时**未返回任何数据行（0 行）** | 赋默认值或提示用户记录不存在 |
| **`TOO_MANY_ROWS`** | 标量 `SELECT INTO` 语句在执行时**返回了超过 1 行的元组（多行冲突）** | 检查外层查询条件的主键唯一性 |
| **`DUP_VAL_ON_INDEX`** | 试图向表中插入违反 `PRIMARY KEY` 或 `UNIQUE` 索引的重复键值 | 拦截主键冲突，提示改用更新操作 |
| **`ZERO_DIVIDE`** | 算术运算中除数为 0 | 将分母置空或设为无穷大兜底 |

---

#### 4.2 综合生产级带异常保护的业务实战

```sql
DECLARE
    v_sno   Student.Sno%TYPE := '202699';
    v_sname Student.Sname%TYPE;
BEGIN
    -- 试图查询目标学生姓名
    SELECT Sname INTO v_sname
    FROM Student
    WHERE Sno = v_sno;

    DBMS_OUTPUT.PUT_LINE('查询成功，学生姓名为: ' || v_sname);

EXCEPTION
    WHEN NO_DATA_FOUND THEN
        DBMS_OUTPUT.PUT_LINE('【业务告警】: 未找到学号为 ' || v_sno || ' 的学生信息!');
    WHEN TOO_MANY_ROWS THEN
        DBMS_OUTPUT.PUT_LINE('【数据错误】: 该学号在系统中对应多条记录，请检查主键完整性!');
    WHEN OTHERS THEN
        DBMS_OUTPUT.PUT_LINE('【未知系统异常】: 错误码 ' || SQLCODE || ', 详情: ' || SQLERRM);
END;
```

### 1. 核心概念与本质内涵：统一异构数据库访问标准的历史使命

在传统的嵌入式 SQL 或专有扩展语言中，代码与特定的数据库管理系统（DBMS）紧密绑定：
- 针对 Oracle 编写的代码，若试图迁移到 SQL Server 或 DB2 上运行，必须推倒重写底层数据访问层代码；
- 随着企业级架构向异构多源数据库发展，软件工程迫切需要一种**与特定操作系统无关、与特定编程语言无关、与底层具体数据库产品完全解耦的通用数据访问标准接口**。

为了打破厂商私有协议壁垒，微软与国际标准化组织先后推出了 **ODBC（Open Database Connectivity，开放数据库互连）**规范，为全行业的数据库应用软件开发确立了通用的底座标准。

```text
                  ODBC 的“驱动解耦”核心思想
                +-------------------------------+
                | 用户应用程序 (C/C++ / Python) |
                +-------------------------------+
                                │ 统一调用标准 ODBC API (如 SQLConnect, SQLExecDirect)
                                ▼
                +-------------------------------+
                | ODBC 驱动程序管理器 (DriverMgr)|
                +-------------------------------+
                                │ 动态路由，调度对应数据库厂商提供的驱动适配器
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
+---------------+       +---------------+       +---------------+
| Oracle Driver |       | MySQL Driver  |       | PgSQL Driver  |
+---------------+       +---------------+       +---------------+
        │                       │                       │ 厂商底层私有协议
        ▼                       ▼                       ▼
 [Oracle 数据库]         [MySQL 数据库]         [PostgreSQL 库]
```

---

### 2. ODBC 四层体系架构全景解剖

ODBC 体系由以下四个分层构件协同工作组成：

1. **用户应用程序（Application）**：
   - 开发者编写的高层业务软件；
   - 应用程序**只与标准 ODBC API 规范打交道**，代码中不包含任何特定数据库产品的专有头文件或底层网络库。
2. **ODBC 驱动程序管理器（Driver Manager）**：
   - 操作系统级别的调度核心（如 Windows 下的 `odbc32.dll` 或 Linux 下的 `unixODBC`）；
   - 负责为应用程序加载、配置和管理具体的数据库驱动程序；
   - 校验参数版本，并在运行时将应用程序的标准 API 函数路由分发给具体的底层驱动。
3. **数据库驱动程序（Database Driver）**：
   - 由各个数据库厂商针对自身产品专门开发并提供的动态链接库（DLL）；
   - 扮演“翻译官”角色：负责将应用程序调用的通用 ODBC 函数，翻译成底层数据库网络监听进程能够识别的原生网络报文（如 Oracle 的 TNS 协议、MySQL 的客户端连接报文）。
4. **数据源（Data Source / DSN，Data Source Name）**：
   - 包含了数据库所在物理 IP 地址、监听端口、目标数据库名、字符集以及鉴权配置的逻辑命名实体。

---

### 3. ODBC 核心工作机制：三大句柄与六步标准工作流

ODBC 采用**句柄（Handle）机制**来跟踪和管理系统上下文、网络连接与正在执行的 SQL 游标资源：

```text
                 ODBC 三级核心句柄拓扑体系
               [环境句柄 (HENV / SQLHENV)]
            (管理整个全局环境上下文与版本)
                         │
                         ▼
             [连接句柄 (HDBC / SQLHDBC)]
            (管理与特定物理数据库的数据连接)
                         │
                         ▼
             [语句句柄 (HSTMT / SQLHSTMT)]
            (管理单条正在执行的 SQL 语句与游标)
```

---

#### 标准六步执行工作流：

```text
[第 1 步: 分配环境句柄]
 SQLAllocHandle(SQL_HANDLE_ENV, SQL_NULL_HANDLE, &henv);
 SQLSetEnvAttr(henv, SQL_ATTR_ODBC_VERSION, (void*)SQL_OV_ODBC3, 0);
             │
             ▼
[第 2 步: 分配连接句柄并连接数据源]
 SQLAllocHandle(SQL_HANDLE_DBC, henv, &hdbc);
 SQLConnect(hdbc, (SQLCHAR*)"MyDSN", SQL_NTS, (SQLCHAR*)"user", SQL_NTS, (SQLCHAR*)"pwd", SQL_NTS);
             │
             ▼
[第 3 步: 分配语句句柄]
 SQLAllocHandle(SQL_HANDLE_STMT, hdbc, &hstmt);
             │
             ▼
[第 4 步: 执行 SQL 语句]
 SQLExecDirect(hstmt, (SQLCHAR*)"SELECT Sno, Sname FROM Student", SQL_NTS);
             │
             ▼
[第 5 步: 绑定列变量并循环读取数据]
 SQLBindCol(hstmt, 1, SQL_C_CHAR, sno, sizeof(sno), &ind1);
 SQLBindCol(hstmt, 2, SQL_C_CHAR, sname, sizeof(sname), &ind2);
 while (SQLFetch(hstmt) == SQL_SUCCESS) {
     printf("学号: %s, 姓名: %s\n", sno, sname);
 }
             │
             ▼
[第 6 步: 级联释放句柄断开连接]
 SQLFreeHandle(SQL_HANDLE_STMT, hstmt);
 SQLDisconnect(hdbc);
 SQLFreeHandle(SQL_HANDLE_DBC, hdbc);
 SQLFreeHandle(SQL_HANDLE_ENV, henv);
```

### 1. 核心概念与本质内涵：Java 世界的数据访问中枢

随着互联网与企业级 Java 应用的爆发式崛起，Sun 公司（现 Oracle）在吸收了 ODBC 跨平台解耦思想的基础之上，面向对象地推出了专门面向 Java 语言环境的数据库访问标准接口——**JDBC（Java Database Connectivity）**。

JDBC 定义了一套全纯粹的 Java 抽象接口类（`java.sql.*` 与 `javax.sql.*`），为 Java 开发者提供了完全统一的、类型安全的数据库连接、事务处理、批处理与元数据探针能力。

### 2. JDBC 四大核心接口与标准交互范式

现代 JDBC 核心交互规范围绕四个经典接口展开：

```text
                      JDBC 四大核心接口调用链条
DriverManager ──> Connection (网络连接与事务控制: setAutoCommit, commit)
                       │
                       ▼
                 PreparedStatement (预编译 SQL 与参数绑定，防 SQL 注入)
                       │
                       ▼
                 ResultSet (结果集游标，通过 rs.next() 逐行提取)
```

1. **`Connection` 接口**：代表与物理数据库建立的 TCP 网络套接字会话通道。它同时承担着**事务控制的最高职责**：
   - `conn.setAutoCommit(false);` —— 开启手动显式事务；
   - `conn.commit();` —— 提交事务；
   - `conn.rollback();` —— 事务异常回滚。
2. **`PreparedStatement` 接口**：预编译语句对象，用于执行带参数的动态 SQL。
3. **`ResultSet` 接口**：代表查询结果的逻辑游标迭代器，通过 `while (rs.next())` 逐行滚动推进。

### 3. 核心安全命门：Statement vs PreparedStatement（彻底粉碎 SQL 注入）

> **【全行业最高危漏洞防御】**：为什么在一切正规企业级生产开发中，**100% 严禁使用普通的 `Statement` 字符串拼接，必须且强制使用 `PreparedStatement`**？

```text
【Statement 字符串拼接致命漏洞 (SQL 注入)】
String sql = "SELECT * FROM Users WHERE User='" + inputUser + "' AND Pwd='" + inputPwd + "'";
若黑客恶意输入:
inputUser = "admin' --" 
拼接后的 SQL 瞬间变为:
SELECT * FROM Users WHERE User='admin' --' AND Pwd='...'
(密码校验逻辑被 SQL 注释符 "--" 彻底切断，黑客直接无密码登录超级管理员!)
```

#### 3.1 PreparedStatement 彻底终结 SQL 注入的底层机理

```java
// 正确的预编译安全写法:
String sql = "SELECT * FROM Users WHERE User = ? AND Pwd = ?";
PreparedStatement pstmt = conn.prepareStatement(sql);
pstmt.setString(1, inputUser); // 无论黑客传入何种恶意字符，一律作为纯文本字面值对待!
pstmt.setString(2, inputPwd);
ResultSet rs = pstmt.executeQuery();
```

##### 双重核心技术收益：
1. **彻底杜绝 SQL 注入（Security）**：
   - `PreparedStatement` 采用**参数化预编译（Parameterized Compilation）**；
   - SQL 语句骨架在传入数据库时，先被编译生成静态语法树，其中的占位符 `?` 是不可改变语法结构的字面插槽；
   - 无论黑客在参数中输入多少个 `' OR '1'='1` 或 `--` 注释符，引擎只将其作为普通的标量字符串数据处理，绝不可能改变原 SQL 的语法树分支结构！
2. **执行性能大幅提升（Performance）**：
   - 数据库服务器端会缓存预编译后的执行计划；
   - 当循环执行 10,000 次插入时，SQL 骨架只需在服务器编译 1 次，后续 9,999 次只需要传输二进制参数，省去海量 CPU 编译优化开销。

### 4. 现代数据库访问架构演进：连接池与 ORM

#### 4.1 数据库连接池技术（Connection Pool）
- **物理痛点**：数据库建立一次 TCP 网络连接需要经历复杂的网络握手、协议协商、权限密码核验与内存线程开辟，开销高达几十毫秒；
- **连接池机制（如 HikariCP, Druid）**：
  - 系统启动时预先创建一组常驻的“长连接”池化管理；
  - 应用程序用时向连接池“借”，用完“还”回池中，避免频繁断开重连，性能提升数十倍。

#### 4.2 对象关系映射（ORM，Object-Relational Mapping）
- 将关系数据库中的**二维表**映射为面向对象语言中的**类（Class）**；
- 将表中的**每一行元组**映射为一个**对象实例（Object）**；
- 现代主流框架（如 MyBatis, Hibernate, JPA）全自动完成数据对象与 SQL 之间的类型转换。

在 Java JDBC 编程中，使用 `PreparedStatement` 替代传统的 `Statement` 的核心安全与性能优势在于（ ）
A. `PreparedStatement` 支持自动连接池管理

#### 自测题 2（JDBC 核心编程设计题）
请使用标准 Java JDBC 规范（包含 `try-with-resources` 自动资源管理与 `PreparedStatement` 参数化安全查询），编写一段核心代码：
“根据传入的方法参数 `String queryDept`，查询 `Student` 表中属于该系的所有学生的学号（`Sno`）与姓名（`Sname`），并打印输出”。

**【参考答案】**：
```java
public void printStudentsByDept(Connection conn, String queryDept) {
    String sql = "SELECT Sno, Sname FROM Student WHERE Sdept = ?";
    
    // 使用 try-with-resources 确保 PreparedStatement 与 ResultSet 安全自动关闭
    try (PreparedStatement pstmt = conn.prepareStatement(sql)) {
        // 参数化绑定占位符，杜绝 SQL 注入
        pstmt.setString(1, queryDept);
        
        try (ResultSet rs = pstmt.executeQuery()) {
            System.out.println("学号\t\t姓名");
            System.out.println("------------------------");
            while (rs.next()) {
                String sno = rs.getString("Sno");
                String sname = rs.getString("Sname");
                System.out.println(sno + "\t" + sname);
            }
        }
    } catch (SQLException e) {
        System.err.println("数据库查询发生异常: " + e.getMessage());
    }
}
```
