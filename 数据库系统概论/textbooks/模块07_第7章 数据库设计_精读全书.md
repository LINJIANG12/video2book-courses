## 第 1 章：第7章 数据库设计（1）
> 对应分集：P48 | 原始标题：《第7章 数据库设计（1）》

### 1. 核心概念与本质内涵：什么是数据库设计？

**数据库设计（Database Design）**是指对于一个给定的应用环境，构造优化的数据库逻辑模式与物理结构，并据此建立数据库及其应用系统，使之能够有效地存储和管理数据，满足各种用户的应用需求（信息要求和处理要求）。

数据库设计绝非简单地在图形工具中拉几张表，而是一项横跨计算机科学、软件工程、业务领域知识与硬件调优的综合工程学：
- 它是整个软件系统架构的**数据地基**；
- 统计表明，软件系统后期出现的大量性能瓶颈、数据不一致、重构成本失控等问题，其根源 $80\%$ 以上可追溯到前期不成熟的数据库设计。

---

### 2. 经典数据库设计六阶段生命周期模型

现代软件工程将规范化的数据库设计严格划分为**六个环环相扣的推进阶段**：

```text
               数据库设计六阶段工程流水线
[阶段 1: 需求分析 (Requirement Analysis)]
 收集用户业务诉求、编写数据流图 (DFD) 与数据字典 (DD)
           │
           ▼
[阶段 2: 概念结构设计 (Conceptual Design)]
 绘制实体-联系图 (E-R 图)，形成独立于具体软硬件的信息世界模型
           │
           ▼
[阶段 3: 逻辑结构设计 (Logical Design)]
 将 E-R 图映射为关系数据模型 (二维表模式)，执行 3NF/BCNF 规范化优化
           │
           ▼
[阶段 4: 物理结构设计 (Physical Design)]
 结合具体 DBMS，确定存储介质、聚簇、B+树索引、页分布与存取路径
           │
           ▼
[阶段 5: 数据库实施 (Implementation)]
 编写 SQL DDL 建表脚本，组织历史数据清洗与初始批量载入，联调测试
           │
           ▼
[阶段 6: 数据库运行与维护 (Operation & Maintenance)]
 上线运行、实时性能监控、慢 SQL 治理、主从备份演练、数据库重构
```

---

#### 2.1 六大阶段的核心输入、产出与关注点

| 设计阶段 | 核心任务 | 关键输入 | 核心产出物 | 软硬件依赖性 |
| :--- | :--- | :--- | :--- | :--- |
| **1. 需求分析** | 弄清用户需要存什么、怎么处理 | 最终用户业务调研、现行单据 | **数据流图（DFD）与数据字典（DD）** | **完全独立**于软硬件与 DBMS |
| **2. 概念设计** | 抽象出业务实体与联系 | 数据字典、业务流程 | **全局 E-R 图** | **完全独立**于具体机器与 DBMS |
| **3. 逻辑设计** | 将概念模型转为 DBMS 关系模式 | 全局 E-R 图 | **关系模式集合、外模式（视图）** | 依赖于数据模型（关系模型），但**独立于具体产品** |
| **4. 物理设计** | 选择最高效的物理存储与索引结构 | 关系模式、数据量与查询负载 | **物理存储方案、B+树/哈希索引配置** | **强依赖**于特定硬件设备与 DBMS 内核 |
| **5. 实施** | 建库、载入真实数据、联调 | 逻辑与物理设计方案 | **真实可运行的生产数据库** | 依赖于具体生产环境 |
| **6. 运维** | 保证高可用与应对业务增长 | 日常监控、故障日志 | **审计日志、调优方案、重组报告** | 贯穿系统整个生命周期 |

---

### 3. 结构与行为分离设计方法学

在早期朴素的系统开发中，程序员往往将“界面代码”与“建表”杂糅在一起。现代数据库设计方法学明确推行：

> **【数据结构设计与数据处理行为设计紧密结合】**：  
> 1. **结构设计（Structure-driven）**：分析系统所涉及的静态实体型及其内在联系，确立模式范式；  
> 2. **行为设计（Process-driven）**：分析业务事务的数据流向、处理逻辑与事务频率。两者交替迭代，相互印证，确保结构既有理论纯洁性，又能满足极端业务事务的吞吐性能。

---

#### 自测题 2（概念分析题）
为什么说在需求分析和概念设计阶段，过早考虑“使用 MySQL 还是 Oracle”、“采用哪个存储引擎”是一种糟糕的系统设计习惯？

**【参考答案与解析】**：
1. **认知过载与逻辑污染**：需求分析和概念设计的核心矛盾是搞清楚“用户客观业务现实究竟是什么”。若过早陷入底层产品的物理细节（如页大小、存储引擎差异、特定语法），会极大地分散架构师的精力，导致业务边界与核心实体关联分析出现严重遗漏；
2. **丧失高内聚低耦合优势**：概念模型（E-R 图）应当具备最高水平的独立性。如果概念模型中混杂了特定数据库的物理特性，未来一旦因架构升级更换数据库，整个设计蓝图将彻底失效作废。遵循分阶段推进是软件工程降低复杂度的铁律。

## 第 2 章：第7章 数据库设计（2）
> 对应分集：P49 | 原始标题：《第7章 数据库设计（2）》

### 1. 核心概念与本质内涵：需求分析是系统成败的源头

在数据库设计生命周期中，**需求分析（Requirement Analysis）**是第一阶段，也是最耗时、最具挑战性的阶段。
- **任务使命**：深入业务现场，充分了解原系统的工作概况，明确用户的**信息要求**（必须存取什么数据）、**处理要求**（要做哪些统计处理、事务响应时间与吞吐要求）以及**安全性与完整性约束要求**；
- **核心成果**：需求分析的最终产物是**系统需求说明书**，其形式化、结构化的技术核心是**数据流图（Data Flow Diagram, DFD）**与**数据字典（Data Dictionary, DD）**。

```text
               需求分析工程化流程与产出流向
现场业务调研 (业务单据 / 现行报表 / 访谈调研)
         │
         ▼
 业务流程建模 ──> 绘制数据流图 (DFD: 描述动态数据在各部门的处理流动)
         │
         ▼
 元数据条目固化 ──> 编制数据字典 (DD: 对 DFD 中所有要素进行精确文字规约)
         │
         ▼
 作为后续概念结构设计 (E-R 图) 的绝对基准输入
```

---

### 2. 数据流图（DFD）：动态业务行为的结构化表达

数据流图（DFD）通过图形化符号直观展现数据在系统内部从输入到产生输出的全部流转演进路径。

#### 2.1 DFD 的四大标准图元构件

```text
1. 外部实体 (External Entity) ───── [ 方框表示: 系统边界外的源点或终点，如"学生"、"银行" ]
2. 处理过程 (Process)         ───── ( 圆角矩形或圆圈表示: 具体数据加工动作，如"计算总学分" )
3. 数据流 (Data Flow)         ───── ───> ( 命名箭头表示: 动态流动的数据包，如"选课申请单" )
4. 数据存储 (Data Store)       ───── ═ 双横线表示: 数据的静态持久化驻留点，如"选课库" ═
```

---

### 3. 数据字典（Data Dictionary, DD）的五大条目体系

如果说数据流图绘制了系统动态运转的“血管脉络”，那么**数据字典则是对血管中流淌的每一个细胞做出的精确静态显微说明**。数据字典通常包含五类标准化条目：

```text
                       数据字典五大核心条目架构
                                   │
       ┌───────────────────┬───────┴───────┬───────────────────┐
       ▼                   ▼               ▼                   ▼
  1. 数据项           2. 数据结构         3. 数据流           4. 数据存储 / 5. 处理过程
 (最小不可分逻辑元)  (数据项的有序组合)  (流动中的数据集合)  (静态暂存点 / 业务逻辑算法)
```

#### 3.1 条目 1：数据项（Data Item）——系统最小不可分原子
- **定义内容**：数据项名称、属性含义、所属数据结构、数据类型、存储长度、合法取值范围等。
- **编制范式规范示例**：
  ```text
  数据项名称: 学号 (Sno)
  含义说明:   全校在籍学生的唯一识别代码
  数据类型:   固定长度字符型 (CHAR)
  长度:       9 字节
  取值范围:   第 1~4 位为入学年份 (2000~2099)，第 5~6 位为院系代码，后 3 位为顺序流水号
  ```

#### 3.2 条目 2：数据结构（Data Structure）——字段逻辑编排
- **定义内容**：描述某些数据项是如何组合在一起构成一个有意义的复合对象的。
- **示例**：
  ```text
  数据结构名称: 学生简况 (Student_Summary)
  含义说明:     记录学生的基本人事学籍信息
  组成结构:     学号 + 姓名 + 性别 + 出生年月 + 所在院系
  ```

#### 3.3 条目 3：数据流（Data Flow）——动态传输载体
- **定义内容**：数据流名称、来源、流向、组成结构、平均流量、峰值流量。
- **示例**：“网上选课流水”、“缴费扣款确认报文”。

#### 3.4 条目 4：数据存储（Data Store）——静态持久化仓库
- **定义内容**：数据存储名称、输入数据流、输出数据流、数据结构组成、存取频度与存取方式（随机读取/批量扫描）。

#### 3.5 条目 5：处理过程（Process）——业务算法加工
- **定义内容**：处理过程名称、简要说明、输入、输出、处理频度以及处理逻辑（常用判定树、判定表或结构化英语伪代码详细描述）。

## 第 3 章：第7章 数据库设计（3）
> 对应分集：P50 | 原始标题：《第7章 数据库设计（3）》

### 1. 核心概念与本质内涵：概念设计的战略地位

**概念结构设计（Conceptual Structure Design）**是数据库设计六阶段中最关键的认知飞跃阶段：
- **任务目标**：将需求分析阶段采集到的庞杂非结构化数据、数据流图（DFD）与数据字典（DD），经过高度的抽象提炼，构建成一个**统一的、独立于任何特定 DBMS 与硬件平台的概念数据模型（E-R 图）**；
- **设计策略**：在处理大型复杂系统时，通常采用**自底向上（Bottom-Up）策略**——先为各业务部门或子系统分别设计**局部 E-R 图（Local E-R Diagrams）**，随后通过视图集成统一汇聚为全局 E-R 图。

```text
                  概念结构设计的经典工程路径
             +-------------------------------+
             |  需求分析产物: DFD 与数据字典 |
             +-------------------------------+
                             │
             ┌───────────────┴───────────────┐
             ▼                               ▼
  【子系统 1: 教务选课域】        【子系统 2: 人事档案域】
    设计局部 E-R 图 1               设计局部 E-R 图 2
             │                               │
             └───────────────┬───────────────┘
                             ▼  【视图集成与冲突消除】
             +-------------------------------+
             |   全局概念模型 (全局 E-R 图)   |
             +-------------------------------+
```

---

### 2. E-R 图的三大标准图元规范

在 Peter Chen（陈品山）提出的实体-联系模型中，所有概念模型均严格由以下三类标准几何图元构成：

```text
1. 实体型 (Entity Type) ──── [ 矩形框表示: 框内写明实体名，如 "学生"、"教师" ]
2. 属性 (Attribute)     ──── ( 椭圆框表示: 框内写明属性名，用无向边与所属实体相连 )
                             ( 码属性通常在椭圆文字下方加下划线标明 )
3. 联系 (Relationship)  ──── < 菱形框表示: 框内写明联系名，用无向边连接参与联系的实体 >
                             ( 边线上必须标明联系的基数类型: 1:1, 1:n, m:n )
```

---

### 3. 实体与属性的绝对划分黄金准则

> **【架构师最高频两难抉择】**：在面对一个具体的业务对象时（例如“医院的病房”、“企业职工的部门”、“汽车的颜色”），它究竟应该被画成一个**实体型（矩形）**，还是应该被画成某个实体的**属性（椭圆）**？

为了消除概念设计中的随意性与主观偏差，关系数据库理论确立了**两条刚性的划分黄金准则**：

```text
               实体 vs 属性判定决策树
是否需要进一步描述该对象的其他内部特征?
或者该对象是否需要与系统内其他实体发生独立关联?
                │
        ┌───────┴───────┐
        ▼ 是            ▼ 否
【必须作为实体型!】     是否满足分量原子性且无独立联系?
(提升为独立矩形框)              │
                        ▼ 是
                【可以作为属性!】
                (降格为实体下的椭圆)
```

#### 3.1 准则 1：属性不可分性（Atomicity）
- 属性必须是**不可再分的标量数据项**，不能再包含子结构；
- 若某个对象自身还拥有若干属性需要进一步描述（例如“部门”不仅是一个名称，它还拥有部门电话、办公楼、部门预算），则**该对象必须作为实体型，绝对不能作为属性！**

#### 3.2 准则 2：属性无关联性（No Relationships on Attributes）
- **联系只能发生在实体型之间，属性绝对不能与其他实体发生任何形式的关联**；
- 若某个对象需要与系统中的其他对象建立联系（例如“病房”需要与“护士长”建立管理联系），则“病房”必须作为实体，不能仅仅作为病人实体的“病房号”属性。

### 4. 局部 E-R 图构建实战示例

设有教务选课子系统，其局部概念抽象过程如下：
- **实体型 1**：`学生`（属性：学号、姓名、性别、年龄）；
- **实体型 2**：`课程`（属性：课程号、课程名、学分）；
- **联系**：`选修`（一名学生可选修多门课，一门课可被多名学生选，属 **$m:n$ 联系**；联系自身包含属性：`成绩`）。

```text
       (学号)    (姓名)                           (课程号)  (学分)
         \        /                                  \      /
       [ 学  生 ] >─────< 选  修 >─────< [ 课  程 ]
                         ( m : n )
                             │
                          (成绩)
```

### 5. 随堂巩固自测

#### 自测题 1（单项选择题）
在概念结构设计中，关于把某个现实对象抽象为“实体”还是“属性”的准则，下列叙述中正确的是（ ）
A. 任何现实对象都可以根据设计者的个人喜好任意设为实体或属性  
B. 如果一个对象具有自身的描述属性，或者它需要与别的实体产生联系，则该对象必须抽象为实体  
C. 属性内部可以嵌套包含复杂的子对象结构  
D. 属性可以直接与其他实体型通过联系菱形框相连  

**【答案】**：B  
**【解析】**：根据划分准则，属性必须是不可分的原子项，且属性不能与其他实体建立联系。一旦对象具备进一步的描述属性或需要参与关联，必须提升为独立的实体型。故选 B。

#### 自测题 2（概念建模分析题）
某高校设计人事档案时，初期将“系别”作为教师实体的一个属性：`教师(工号, 姓名, 系名, 系主任, 系办公电话)`。请从实体与属性的划分准则出发，评判该设计的合理性，并给出规范的重构方案。

**【参考答案与重构推导】**：
1. **设计缺陷评判**：
   - 该设计严重违背了“属性不可分性”准则；
   - 在该设计中，“系别”包含了“系主任”、“系办公电话”等多项内部特征，这表明“系别”本质上是一个具有自身独立属性集合的复杂客观对象；

   - 将“系别”提升为独立的**实体型**：`系别(系编号, 系名, 系主任, 系办公电话)`；
   - 在 `教师` 实体型与 `系别` 实体型之间建立人事归属联系：**教师与系别之间形成 $n:1$（多对一）联系**。

## 第 4 章：第7章 数据库设计（4）

### 1. 核心概念与本质内涵：为什么局部 E-R 图必须进行视图集成？

在实际的大中型软件工程项目中，各个子系统的局部 E-R 图通常是由不同的架构小组针对不同的业务部门（如销售部、财务部、仓储部、人事部）独立分别绘制的。

由于各部门所站的业务立场不同、认知习惯各异、甚至术语口径存在部门壁垒，各局部 E-R 图之间必然存在大量的矛盾与冲突：
- 销售部门眼中的“客户”，在财务部门可能被称为“付款单位”；
- 仓储部门将“零件”作为实体型，而在采购部门仅作为采购单上的一个普通属性。

因此，必须通过**视图集成（View Integration）**，逐一排查并化解所有冲突，将孤立的局部视图缝合为一个统一、和谐、自洽的**全局概念模型（全局 E-R 图）**。

```text
               局部 E-R 图视图集成漏斗模型
 [局部 E-R 图 1: 销售域]   [局部 E-R 图 2: 财务域]   [局部 E-R 图 3: 生产域]
         │                         │                         │
         └─────────────────────────┼─────────────────────────┘
                                   ▼
                 【视图集成核心检验漏斗: 排查三大冲突】
                 ├── 1. 属性冲突 (域类型、取值单位、精度范围)
                 ├── 2. 命名冲突 (同名异义、异名同义)
                 └── 3. 结构冲突 (实体vs属性抽象层级、联系基数矛盾)
                                   │
                                   ▼
                 【消除冗余实体、冗余联系与冗余属性】
                                   │
                                   ▼
                       [统一的全局 E-R 图蓝图]
```

---

### 2. 局部 E-R 图合并中的三大类核心冲突与消解机制

在视图集成过程中，系统面临的三大典型冲突及其标准工程消解策略如下：

```text
                       三大 E-R 合并冲突谱系
                                 │
     ┌───────────────────────────┼───────────────────────────┐
     ▼                           ▼                           ▼
【1. 属性冲突】                 【2. 命名冲突】             【3. 结构冲突】
 • 属性域/类型冲突               • 同名异义 (一词指代两物)   • 抽象层级不同 (实体 vs 属性)
 • 取值计量单位不一致            • 异名同义 (两词指代一物)   • 属性组成不一致 (取全集)
 (协商统一全局标准)              (重命名区分 / 统一口径)     • 联系基数不一致 (就宽不就窄)
```

---

#### 2.1 冲突 1：属性冲突（Attribute Conflicts）

1. **属性域冲突（Domain / Type Conflict）**：
   - 现象：同一属性在不同局部图中定义了不同的数据类型或取值范围。
   - 典型案例：学号在教务处被定义为 9 位定长字符 `CHAR(9)`，而在图书馆管理子系统中被定义为自增数字整数 `INT`；
   - 消解策略：组织各业务部门会商，统一确立全校标准的属性域规约。
2. **属性取值计量单位冲突（Unit Conflict）**：
   - 现象：同一属性在不同部门使用了不同的度量单位。
   - 典型案例：大宗原材料重量在车间局部图中以“千克（kg）”计量，而在外贸报关局部图中以“英磅（lb）”计量；零件单价在采购系统按“元”计算，在跨国结算系统按“美元”计算；
   - 消解策略：在全局概念模型中统一固定基础法定计量单位，若需换算，在应用层或视图派生层动态提供换算接口。

---

#### 2.2 冲突 2：命名冲突（Naming Conflicts）

1. **同名异义（Same Name, Different Concepts）**：
   - 现象：**同一个名称在不同的部门代表完全不同的客观事物**；
   - 典型案例：“项目”这个名词，在科研处局部图中代表“国家自然科学基金课题”；而在总务后勤处局部图中代表“校区教学楼修缮工程”；
   - 消解策略：**消除歧义，重新命名**。将前者重命名为“科研课题（ResearchProject）”，将后者重命名为“基建项目（ConstructionProject）”。
2. **异名同义（Different Names, Same Concept）**：
   - 现象：**不同的名称指代的是现实中同一个客观实体或属性**；
   - 典型案例：同一个学生，在教务处叫“学号（Sno）”，在校医院病历叫“就诊卡号（CardID）”，在保卫处门禁叫“通行编号（PassID）”；
   - 消解策略：**破除部门壁垒，确立全库唯一主名词**，统一规范化为“学号（Sno）”。

---

#### 2.3 冲突 3：结构冲突（Structural Conflicts）——最深层的逻辑矛盾

1. **抽象层级冲突（同一对象在不同局部图中抽象不同）**：
   - 现象：某对象在一个局部 E-R 图中被抽象为了**实体型（矩形框）**，而在另一个局部 E-R 图中却被画成了某个实体的**属性（椭圆框）**；
   - 典型案例：在人事档案图中，“汽车”只是高管实体的“专车车牌”属性；而在车辆调度保障部门，“汽车”是一个拥有车辆编号、发动机号、行驶里程、年检日期的独立实体型；
   - **消解黄金原则**：**【一律向上看齐，统一提升为“实体型”】**！
     - 理由：实体型的表达能力和语义丰富度远大于简单属性。将其统一升级为实体型，并在人事图中建立该高管与该汽车的“配备”联系，不仅无损原有人事信息，更能完整保全车辆调度部门的全部内部特征。
2. **联系基数冲突（同一联系在不同图中类型不同）**：
   - 现象：在局部图 A 中，实体 A 与实体 B 是一对一（$1:1$）联系；但在局部图 B 中被画为一对多（$1:n$）联系；
   - **消解黄金原则**：**【就宽不就窄，采用包容性更强的多重联系（$1:n$ 或 $m:n$）】**。

---

### 3. 消除全局 E-R 图中的冗余联系与冗余属性

在多个局部 E-R 图合并之后，由于不同部门从各自角度引入了辅助联系，往往会在全局图中形成**闭合环路（Cycle）**，造成数据的派生冗余：

```text
               典型闭合三角冗余联系示例
                     [ 工  程 ]
                    /          \
            (使用) /            \ (指派)
                  v              v
               [ 零  件 ] <────── [ 职  工 ]
                           (加工)
```

- 若业务规则明确规定：“每个职工在某个工程上所加工的零件，就是该工程所使用的全部零件”；
- 则联系“工程-使用-零件”完全可以由另外两条联系（职工指派给工程、职工加工零件）复合推导出来；
- 此时该联系属于**冗余联系**，在最终全局 E-R 图中**必须予以坚决删除**，避免在逻辑结构设计阶段产生多余的关系模式与维护开销。

A. 强制将部门 A 的实体降格为属性

## 第 5 章：第7章 数据库设计（5）
> 对应分集：P52 | 原始标题：《第7章 数据库设计（5）》

### 1. 核心概念与本质内涵：从概念蓝图到关系二维表矩阵

**逻辑结构设计（Logical Structure Design）**是数据库设计中将“概念模型”落地为“计算机逻辑模型”的核心枢纽。
- **任务目标**：将概念结构设计阶段产出的**全局 E-R 图**，依照严格的形式化数学规则，**完全映射转换为关系数据库管理系统（DBMS）所支持的关系模式集合（一组包含属性、主码与外码的二维表规约）**；
- **核心挑战**：实体型转换为表非常简单直接，**最核心的难点与设计考量完全在于：实体型之间的各类复杂联系（$1:1$, $1:n$, $m:n$, 多元联系, 自联系）应该如何映射才能避免产生数据冗余与多余表**！

```text
               E-R 图向关系模式转换的核心映射矩阵
【E-R 概念世界】                                 【关系逻辑世界】
 实体型 (矩形框)          ==================>    独立关系模式 (基本表)
 实体属性 (椭圆框)        ==================>    关系属性 (列)
 实体码 (下划线)          ==================>    主码 (Primary Key)
 实体间联系 (菱形框)      ==================>    外码嵌入 (1:1, 1:n) OR 独立关系表 (m:n)
```

---

### 2. 实体间联系转换的五大黄金形式化铁律

#### 2.1 铁律 1：实体型的转换（基石）
- **规则**：**每一个实体型都必须转换为一个独立的关系模式**；
- **属性与码**：实体的全部属性转换为关系的属性，实体的码转换为关系的主码。

---

#### 2.2 铁律 2：一对一（$1:1$）联系的转换规则

设实体型 $A$ 与实体型 $B$ 之间存在 $1:1$ 联系：

```text
              一对一联系 (1:1) 的两种映射策略
                            │
        ┌───────────────────┴───────────────────┐
        ▼                                       ▼
【方案 A: 独立建表 (少用)】             【方案 B: 嵌入合并 (推荐工程做法)】
 建立独立关系模式:                      不需要建立第三张表!
 R_Rel(A的主码, B的主码, 联系属性)      选择将联系属性与对方主码
 主码可选 A的主码 或 B的主码            直接合并到 A 或 B 的关系模式中!
 (多了一张表，增加连接查询开销)         (最佳实践: 合并到完全参与/必选端)
```

##### 工程最佳实践（嵌入合并）：
- **合并法则**：可在 $A$ 关系的属性中加入 $B$ 的主码（作为外码）和联系本身的属性；或者在 $B$ 关系中加入 $A$ 的主码和联系属性；
- **防空值策略**：如果其中一端是**完全参与（必有端）**（例如每个班级必然有且仅有一名正班长，而普通学生不一定是班长），**必须将外码合并到完全参与端（班级表）**中，这样可以完全避免产生 `NULL` 空值外码。

---

#### 2.3 铁律 3：一对多（$1:n$）联系的转换规则

设实体型 $A$（$1$ 端，如院系）与实体型 $B$（$n$ 端，如学生）之间存在 $1:n$ 联系：

> **【绝不允许随意独立建表】**：  
> 理论上虽可独立建表，但在工业界与标准规范中：  
> **一律直接将联系合并到 $n$ 端（多端）实体对应的关系模式中！**

- **具体操作**：
  1. 在 **$n$ 端实体（学生表）**中，追加加入 **$1$ 端实体（院系表）的主码**作为外码；
  2. 同时在 $n$ 端实体中加入联系本身的属性；
  3. **主码依然是 $n$ 端实体自身的主码**。

```text
【院系表 Department (1端)】:  Department(DeptID, DeptName)
                                       ▲
                                       │ 参照外码 DeptID
                                       │
【学生表 Student (n端)】:      Student(Sno, Sname, Sage, DeptID)
                                                        ▲
                                             (将1端主码作为从表外码嵌入)
```

---

#### 2.4 铁律 4：多对多（$m:n$）联系的转换规则（绝对刚性公理）

设实体型 $A$（如学生）与实体型 $B$（如课程）之间存在 $m:n$ 联系（如选修）：

> **【不可违背的绝对铁律】**：  
> **多对多联系（$m:n$）必须且只能转换为一个独立的关系模式！严禁直接并入两端的任何一张表！**

- **独立关系模式结构规约**：
  1. **属性组成**：参与联系的**各实体型的主码** $+$ **联系自身的属性**；
  2. **主码构成**：**由各实体主码联合构成的复合主码**；
  3. **外码构成**：各实体主码分别作为外码，参照对应的主表。

```sql
-- 选修联系 (m:n) 独立转换为选课成绩表 SC
CREATE TABLE SC (
    Sno   CHAR(9) NOT NULL,             -- 实体 1 (Student) 的主码
    Cno   CHAR(4) NOT NULL,             -- 实体 2 (Course) 的主码
    Grade SMALLINT,                     -- 联系自身的属性
    PRIMARY KEY (Sno, Cno),             -- 复合主码!
    FOREIGN KEY (Sno) REFERENCES Student(Sno),
    FOREIGN KEY (Cno) REFERENCES Course(Cno)
);
```

---

#### 2.5 铁律 5：多元联系与自联系的转换

1. **三个或更多实体间的多对多联系（如三元供应联系：供应商-项目-零件）**：
   - **必须转换为一个独立的关系模式**；
   - 其属性为参与各实体主码与联系属性的并集，**主码为各实体主码的联合复合码**：
     $$\text{SPJ}(\underline{\text{Sno}}, \underline{\text{Pno}}, \underline{\text{Jno}}, \text{Qty})$$
2. **同一实体型内部的自联系（如员工与直属领导联系）**：
   - 若为 $1:n$ 自联系：在实体表内部增加一个参照自身主码的外码列（如 `Employee(EmpNo, Ename, MgrNo)`，其中 `MgrNo` 参照 `EmpNo`）；
   - 若为 $m:n$ 自联系（如零件结构组成/BOM 物料清单：一个零件包含多个子零件，一个子零件可用于多个装配件）：**必须独立转换为子件关系表**：`BOM(ParentPartID, ChildPartID, Quantity)`。

---

### 3. 典型综合实战设计大题

设有企业物流业务 E-R 模型：
- 实体型：`仓库(仓库号, 面积, 地址)`；
- 实体型：`商品(条形码, 名称, 单价)`；
- 实体型：`保管员(工号, 姓名, 电话)`；
- 联系 1：一个仓库有多名保管员，一名保管员只在一个仓库工作（仓库与保管员：$1:n$ 雇用联系）；

### 1. 核心概念与本质内涵：范式越高真的越好吗？

在第 6 章中，我们学习了严格的规范化理论：从 1NF 一路提纯到 3NF、BCNF 乃至 4NF。
规范化从数学上彻底消除了数据冗余与更新异常。

然而，在工业界实际的大规模高并发系统中，**盲目追求高范式往往是一场灾难**：
- 范式级别越高，原本集中存储的数据就被切分得越零碎；
- 当业务需要呈现一个综合报表时，系统必须对 5 张、8 张甚至 10 张小表执行极其昂贵的多表自然连接（`JOIN`）；
- 多表连接会产生巨大的中间笛卡尔积，引发内存暴涨、磁盘临时文件交换与 CPU 密集计算，导致线上查询响应时间严重超时。

因此，现代数据库逻辑设计方法学确立了一条核心折中辩证法：
> **【规范化是基础，反规范化是权衡】**：  
> 先按规范化理论设计出纯洁的 3NF/BCNF 逻辑模型，随后针对系统的实际读写负载画像，适度、受控地进行**反规范化（Denormalization）**调优。

```text
               规范化与反规范化的工程钟摆天平
         规范化 (Normalization)               反规范化 (Denormalization)
   ──────────────────────────────────   ──────────────────────────────────
   • 核心目标: 消除冗余与更新异常       • 核心目标: 提升极端高频读查询性能
   • 核心代价: 多表 JOIN 性能开销巨大   • 核心代价: 产生受控冗余，增加维护一致性成本
   • 适用场景: 写多读少、严防不一致     • 适用场景: 读多写少、高并发秒级响应
```

---

### 2. 反规范化（Denormalization）的核心技术手段

在 3NF 的关系模型基础上，根据系统高频慢 SQL 分析，通常采用以下三大反规范化工程策略：

```text
                     三大核心反规范化技术谱系
                                 │
     ┌───────────────────────────┼───────────────────────────┐
     ▼                           ▼                           ▼
【1. 增加冗余/派生列】          【2. 水平表分割 (Partitioning)】 【3. 垂直表分割 (Vertical)】
 • 将高频 JOIN 键直接冗余到从表 • 按时间/地域将行切分到子表   • 高频列留在主表 (定长高速)
 • 预先计算并固化聚合值 (总金额)• 减小单表行数，提升命中率   • 低频大文本独立剥离 (TEXT/BLOB)
```

---

#### 2.1 策略 1：增加受控冗余属性与派生属性

1. **直接增加常用冗余列（消除跨表 JOIN）**：
   - 典型案例：在订单详情表 `OrderDetail(OrderID, ProductID, Qty, UnitPrice)` 中，为了显示商品名，每次都要与 `Product` 表连接；
   - 优化措施：直接在 `OrderDetail` 中冗余存储 `ProductName` 字段，查询详情单时单表直出，彻底省去一次 JOIN。
2. **增加预聚合派生列（预计算）**：
   - 典型案例：在订单主表 `Orders` 中冗余一个 `TotalAmount`（订单总金额）字段；
   - 虽然 `TotalAmount` 完全可以由 `SUM(Qty * UnitPrice)` 动态求得，但高频统计报表若每次都去扫描几十万条明细做聚集求和，开销巨大；
   - 优化措施：在下单写入时通过事务一次性算好总金额并存入主表，查询时直接读取标量值。

> **反规范化的刚性代价与底线防御**：  
> 引入冗余列后，当商品改名或明细金额修改时，必须通过**数据库事务（Transaction）或触发器（Trigger）**保证多处冗余数据同步更新，严防数据不一致！

---

#### 2.2 策略 2：关系的水平分割（Horizontal Partitioning）

- **定义**：将一个极大规模的基本表中的**数据行（元组）**，按照某种业务规则切分存储到多个物理结构完全相同的独立子表中；
- **常见切分维度**：
  - **按时间范围切分（冷热数据分离）**：如将日志流水表拆为 `Log_2026`、`Log_2025`、`Log_Historical`，日常高频写入与查询只命中当年的小表，大幅减少单表 B+ 树索引层级；
  - **按地域或租户切分**：如按省份代码将用户表水平分片（Sharding）。

---

#### 2.3 策略 3：关系的垂直分割（Vertical Partitioning）

- **定义**：将一个基本表中的**属性列**切分为两个或多个关系，使经常在一起高频访问的常用列放在主表中，将访问频度低、或占用空间极大的宽字段剥离到扩展表中；
- **典型案例**：
  - 用户表 `User` 包含：`UserID`, `Username`, `Password`, `Phone`, `UserBio`（万字个人主页长文本描述）, `AvatarBlob`（高清头像二进制图片）；
  - 若将全部列塞在一张表里，导致每行记录体积达到数 KB，一个 16KB 数据页只能放几条记录，内存缓冲池中能缓存的用户行数急剧减少；
  - **优化方案**：垂直拆解为两张表：
    1. 核心表：`User_Core(UserID, Username, Password, Phone)`（全为紧凑定长列，单页缓存上千行，高频登录鉴权极速命中）；
    2. 扩展表：`User_Profile(UserID, UserBio, AvatarBlob)`（低频点击查看主页时才按需回表读取）。

---

### 3. 用户子模式（外模式 / 视图）的设计原则

在完成了全局逻辑模式的规范化与优化之后，逻辑设计的最后一步是面向各业务终端设计**用户子模式（即外模式 / 视图体系）**：
1. **简化复杂调用**：将底层经过垂直拆分、反规范化处理的多张物理碎表，通过视图重新拼接，为前端业务系统提供稳定、优雅的虚拟业务对象；
2. **逻辑数据独立性防护墙**：当未来因性能问题对底层基本表再次进行分库分表或列结构微调时，只需调整视图底层的映射 SQL，对上层几十个微服务应用程序完全透明无感；
3. **敏感信息动态屏蔽**：针对不同岗位的操作员定制不同的外模式视图，落实最小权限原则。

### 1. 核心概念与本质内涵：什么是数据库物理设计？

在完成了逻辑结构设计之后，我们拥有了一套规范化的关系模式（表结构、主外码与约束）。然而，计算机并不能直接在一个抽象的“二维逻辑表”上运行，数据最终必须落盘到由扇区、磁道、块（Block）和闪存芯片构成的物理介质上。

**物理结构设计（Physical Database Design）**的任务是：**为一个给定的逻辑数据模型选取一个最适合应用环境的物理结构（包括存储结构与存取方法），以在存储空间开销、时间响应性能与维护成本之间取得最优平衡**。
- **阶段强依赖性**：与前几个阶段的硬件独立性完全不同，**物理结构设计强依赖于具体的计算机硬件配置、操作系统特性以及所选用的特定 DBMS 内部存储引擎机制**。

```text
                  物理结构设计的两大核心阵地
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
【1. 确定存取方法 (Access Methods)】            【2. 确定物理存储布局 (Storage Layout)】
 • B+ 树索引设计 (单列 / 复合 / 覆盖索引)        • 数据文件与日志文件的物理磁盘分离 (防争用)
 • 聚簇存取方法 (Cluster: 物理顺序绑定)          • 表数据文件与索引数据文件分盘存放 (并发 I/O)
 • 散列存取方法 (Hash: O(1) 等值极速检索)        • 内存缓冲池与数据页填充因子配置
```

---

### 2. 核心存取方法的工程选择决策机制

存取方法是 DBMS 在底层物理存储介质上快速定位目标元组的算法通道。常见的存取方法包括**B+ 树索引、聚簇存取与 Hash 散列**：

```text
               三类存取方法的决策树指南
                  高频查询的特征是什么?
                           │
       ┌───────────────────┼───────────────────┐
       ▼                   ▼                   ▼
【纯等值点查，无范围】  【连续范围区间 / 高频排序】 【通用复合过滤 / 前缀模糊】
 适合选用:              适合选用:                   适合选用:
 Hash 散列存取方法      聚簇索引 (Clustered Index)  B+ 树索引 (B+ Tree Index)
 (复杂度 O(1))          (连续扇区顺序预读，极速)    (通用平衡，全场景兼容)
```

---

#### 2.1 聚簇存取方法（Clustered Index）的配置决断法则

聚簇存取是将关系表中元组的物理存放位置，与某个或某些属性列的逻辑键值顺序强制绑定：

##### ① 极度适合建立聚簇索引的场景：
1. **经常需要按某列进行范围查询（`BETWEEN AND`）**：由于逻辑连续的数据在磁盘物理扇区上也是严格相邻的，操作系统可以一次性触发连续预读（Sequential Read），避免磁盘磁头来回机械寻道；
2. **经常需要按某列进行排序输出（`ORDER BY`）或分组统计（`GROUP BY`）**：物理已经天然有序，排序开销直接归零；
3. **两张大表经常需要基于某公共键进行频繁的高频连接（`JOIN`）**：将两张表的连接键均设为聚簇，可直接触发归并连接（Merge Join），吞吐暴增。

##### ② 绝对不适合建立聚簇索引的禁区：
1. **经常需要执行更新（`UPDATE`）的列**：更新键值会导致整行数据被迫在磁盘物理页之间搬家迁移，引发高频的**数据页分裂（Page Split）**；
2. **极少出现在连接、排序和范围条件中的列**；
3. **低基数、区分度极差的列**（如性别、状态标志位）。

---

#### 2.2 复合索引与覆盖索引（Covering Index）性能优化

- **最左前缀匹配原则（Leftmost Prefix Rule）**：
  - 若在 `(A, B, C)` 三列上建立了复合 B+ 树索引，该索引能够加速 `WHERE A = 1`、`WHERE A = 1 AND B = 2` 以及 `WHERE A = 1 AND B = 2 AND C = 3` 的查询；
  - 但**绝对无法加速**只提供 `WHERE B = 2` 或 `WHERE C = 3` 的查询！
- **覆盖索引（Covering Index）**：
  - 如果一个索引的叶子节点所包含的列，**已经完全覆盖了查询语句中 `SELECT` 所要投影的所有列**；
  - 数据库引擎只需在内存中的索引树上直接读取数据即可完成返回，**彻底无需再次根据物理指针发起磁盘回表查询（Zero Table Lookup）**，性能达到理论极致。

```text
+---------------------------------------------------------------+
```

### 4. 随堂巩固自测

#### 自测题 1（单项选择题）
在关系数据库的物理设计中，关于聚簇索引（Clustered Index）的描述，错误的是（ ）

B. 一个基本表上最多只能建立一个聚簇索引  
C. 经常进行范围查询和排序的属性非常适合建立聚簇索引  
D. 经常被高频执行 UPDATE 更新操作的属性最适合作为聚簇索引列  

**【答案】**：D  
**【解析】**：聚簇索引决定了物理磁盘位置。更新聚簇索引列会导致数据行物理位移和页分裂，产生高昂的 I/O 维护开销，因此频繁更新的列绝对不适合建立聚簇索引。故选 D。

#### 自测题 2（物理设计与 I/O 优化实战题）
某系统运维团队在监控数据库时发现，每当有批量交易写入时，系统的读查询响应时间会发生剧烈抖动，磁盘 I/O 队列持续被打满。排查发现，该系统的基本表数据文件、非聚集索引文件以及事务重做日志文件（WAL/Redo Log）全部存放在同一个单盘卷 `D:\data` 目录下。  
请从物理结构设计的角度，给出两项核心的物理存储重构优化措施，并阐明优化原理。

**【参考答案与解析】**：
1. **措施 1：将事务日志文件（Redo Log）与表数据文件物理分盘存储**：  
   - **原理**：事务提交要求日志必须同步强行落盘（WAL 机制），日志写入是纯粹的高频顺序写（Sequential Write）。如果将日志与进行大量随机读写的数据文件混在同一块物理磁盘上，磁头会频繁在随机寻道与顺序追加之间来回切换争用。将其拆分至独立的物理硬盘后，日志写入享受专用物理 I/O 通道，彻底消除争用。
2. **措施 2：将高频使用的索引文件与基本表数据文件分开放置在不同的物理磁盘阵列中**：  
   - **原理**：当执行非覆盖索引查询时，系统需要先读索引页获取行指针，再立即回表读取数据页。将索引与数据隔离到两组独立的物理磁盘后，存储系统可以利用独立的 I/O 控制器并发并行地读取索引与表数据，大幅缩短 I/O 等待延迟。

### 1. 核心概念与本质内涵：从纸面方案到生产实体的跨越

在完成了逻辑设计与物理设计之后，数据库方案仍然停留在设计图纸阶段。
- **数据库实施（Database Implementation）**：是将图纸落地为真实生产环境中可运行的数据库，并完成历史数据清洗、批量导入与联调测试；
- **数据库运行与维护（Operation & Maintenance）**：数据库一旦正式上线，便开启了长达数年乃至数十年的运维生命周期。系统必须时刻对抗硬件故障、数据腐化、性能劣化以及业务剧变带来的挑战。

```text

编写 DDL 建表脚本 ──> 历史数据 ETL 清洗与初始灌库 ──> 应用程序联合调试
                                                          │
                                                          ▼
数据库重组 (清理碎片) <── 日常性能监控与调优 <── 试运行与双轨制割接上线
         │
         ▼ (业务重大演进时)
```

### 2. 数据库实施的关键工程任务

#### 2.1 数据的载入与组织（ETL 阶段）
在大型老旧系统重构或新业务上线时，通常存在大量遗留历史数据（如来自旧 FoxPro 数据库、Excel 表格或老旧文本文件）：
- **数据抽取、转换与加载（ETL，Extract-Transform-Load）**：
  - **抽取**：从各异构老系统安全拉取存量数据；
  - **清洗转换**：修正历史脏数据、统一缺失值、转换编码格式、按新范式要求消除冗余；
  - **批量加载（Bulk Insert）**：为了加快入库速度，通常在批量加载前**临时禁用从表外键约束和二级辅助索引**，待千万级历史数据灌满后，再重新启用外键并由引擎一次性并行批量构建 B+ 树索引。

---

#### 2.2 数据库试运行与“双轨制”安全割接

在正式将业务流量切换到新数据库之前，必须经过严格的**数据库试运行（Pilot Run）**阶段：
1. **功能与性能压力测试**：模拟业务峰值并发请求，校验高并发读写下死锁率、连接池耗尽与事务吞吐表现；
2. **双轨运行机制（Dual-Run / Parallel Operation）**：
   - 生产环境中最安全的割接方式；
   - **新系统与老系统同时并行运行一段时间（通常为 1~3 个月）**；
   - 线上真实的每一笔业务操作，在新老两套数据库中同时双写双跑；
   - 每天夜间比对新老系统的最终账目与报表数据，只有连续数周完全吻合、零差异后，才正式下线老系统，实现业务平滑零风险割接。

---

### 3. 数据库运行阶段的日常治理与 DBA 职责

系统正式投产后，数据库管理员（DBA）必须常态化执行三大核心监控与防护任务：

#### 3.1 备份与容灾演练
- **全量备份（Full Backup）**：每周定期对全库数据文件做冷/热备份；
- **增量备份（Incremental Backup）**与**事务日志备份（Log Backup）**：高频备份每一次修改的 Redo/WAL 日志；
- **定期灾难恢复演练**：**未经恢复演练验证的备份等于没有备份**！必须定期在隔离环境测试能否利用备份文件将系统精准还原到故障发生前的最后一秒。

#### 3.2 性能监控与慢 SQL 治理
- 实时监视内存缓冲池命中率（Buffer Pool Hit Ratio，生产基线通常应保持在 $99\%$ 以上）；
- 捕获慢查询日志（Slow Query Log），利用 `EXPLAIN` 分析低效 SQL 的执行计划，排查是否存在全表扫描与索引失效。

### 4. 核心学术与工程辨析：数据库“重组” vs 数据库“重构”

这是软件工程与数据库考试中界限最严格的一对核心概念：

```text
               数据库重组 vs 数据库重构深度对比
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
【数据库重组 (Reorganization)】                 【数据库重构 (Restructuring)】
 • 逻辑结构与外模式【完全不改变】!               • 逻辑结构与概念模式【发生了物理修改】!
 • 仅仅调整物理存储空间与磁盘布局                • 如: 增加新实体、拆分宽表、调整外码
 • 典型动作: 清理磁盘碎片、重建膨胀的B+树        • 影响范围: 必须重新编写部分业务应用程序
 • 影响范围: 上层应用程序完全无感                • 诱发原因: 客观现实业务发生重大演化
```

### 5. 随堂巩固自测

#### 自测题 1（单项选择题）
数据库上线运行一段时间后，由于频繁的增删改操作导致数据文件产生了严重的磁盘碎片，B+ 树索引空间膨胀、查询响应逐渐变慢。DBA 决定对数据库执行清理碎片、回收空闲空间并重新组织索引的操作。该操作属于数据库维护中的（ ）
A. 数据库重构  
B. 数据库重组  
C. 模式逆向工程  
D. 数据库需求分析  

**【答案】**：B  
**【解析】**：只调整物理存储布局、清理磁盘碎片和重建索引，完全不修改数据库的总体逻辑结构（模式未变）和外模式，属于典型的**数据库重组（Reorganization）**。若修改了表结构、增删实体则属于数据库重构。故选 B。

#### 自测题 2（工程分析题）
为什么在企业级核心数据库割接上线时，通常强烈推荐采用“双轨运行（Dual-Run）”策略，而不是直接一步到位的“休克式停机强行切换”？

**【参考答案与解析】**：
1. **彻底消除单点灾难风险**：一步到位的停机强切一旦遇到未预料到的严重兼容性 BUG 或性能雪崩，会导致全公司核心业务瞬间瘫痪，回滚老系统极度困难且极易造成数据丢失；
2. **多重校验数据一致性**：双轨运行允许新老两套系统针对完全相同的实时生产流量并行计算。通过每天对账比较两套系统生成的数据与财务报表，能够全面暴露新系统在边缘边界场景下的计算缺陷；
3. **给运维团队提供演练缓冲期**：在双轨期若新库发生故障，老系统可无缝承担全量业务，系统具备完全的容错韧性，为故障修复与性能调优留出充裕的调试窗口。

### 2. 步骤一：业务需求调研与实体关系抽象

经过需求分析，提炼出电商平台核心交易域的四大核心实体型及其业务规则：
1. **用户（User）**：拥有用户 ID、用户名、手机号、注册时间；
2. **店铺（Shop）**：拥有店铺 ID、店铺名称、信用评级、法人姓名；
3. **商品（Product）**：拥有商品 ID、商品名称、售价、当前库存量；
4. **订单（Order）**：拥有订单编号、下单时间、订单状态、实付总金额。

#### 业务联系逻辑界定：
- **店铺与商品（开设联系）**：一个店铺可上架售卖多种商品，一种商品只归属于一个特定店铺（$1:n$ 联系）；
- **用户与订单（下单联系）**：一个用户可以创建多笔订单，一笔订单归属于唯一一个购买用户（$1:n$ 联系）；
- **订单与商品（明细联系）**：一笔订单可以包含多种商品，一种商品可以出现在多笔不同的订单明细中（**$m:n$ 联系**，联系本身包含属性：`购买数量 Quantity` 和 `成交单价 DealPrice`）。

### 4. 步骤三：逻辑结构设计与五大转换规则落地

应用第 52 讲中的标准转换规则进行形式化映射：

1. **用户关系模式（实体型独立转换）**：
   $$\text{User}(\underline{\text{UserID}}, \text{Username}, \text{Phone}, \text{CreateTime})$$
   主码：`UserID`；唯一键：`Phone`。
2. **店铺关系模式（实体型独立转换）**：
   $$\text{Shop}(\underline{\text{ShopID}}, \text{ShopName}, \text{CreditLevel}, \text{LegalPerson})$$
   主码：`ShopID`。
3. **商品关系模式（$1:n$ 联系合并至多端商品表）**：
   $$\text{Product}(\underline{\text{ProductID}}, \text{ProductName}, \text{Price}, \text{Stock}, \text{ShopID})$$
   主码：`ProductID`；外码：`ShopID`（参照 Shop 表）。
4. **订单主表模式（$1:n$ 下单联系合并至多端订单表）**：
   $$\text{Orders}(\underline{\text{OrderID}}, \text{OrderTime}, \text{Status}, \text{TotalAmount}, \text{UserID})$$
   主码：`OrderID`；外码：`UserID`（参照 User 表）。
5. **订单明细关系模式（$m:n$ 明细联系必须独立建表）**：
   $$\text{OrderItem}(\underline{\text{OrderID}}, \underline{\text{ProductID}}, \text{Quantity}, \text{DealPrice})$$
   复合主码：`(\text{OrderID}, \text{ProductID})`；  
   双重外码：`OrderID` 参照 Orders 表，`ProductID` 参照 Product 表。

### 5. 步骤四：模式规范化检验与反规范化工程调优

#### 5.1 规范化范式判定（3NF / BCNF）
- 检查 `OrderItem` 表：主码为 `(OrderID, ProductID)`。非主属性 `Quantity` 和 `DealPrice` 必须同时依赖于订单与具体商品，不存在部分依赖，亦不存在传递依赖，严格达到 **3NF 与 BCNF**；
- 检查 `Product` 表：主码为单属性 `ProductID`，自动消除部分依赖，不存在传递依赖，达到 **BCNF**。

#### 5.2 反规范化工程性能调优
在 `Orders` 主表中保留 `TotalAmount`（实付总金额）字段属于**受控的派生反规范化设计**：
- 避免每次用户查询“我的订单列表”时，都去跨表扫描 `OrderItem` 做乘加统计；
- 保证高并发场景下首页订单流秒级渲染。

### 6. 步骤五：生产级标准 ANSI SQL DDL 脚本落地

```sql
-- 1. 创建用户表 User
CREATE TABLE Users (
    UserID     CHAR(10) PRIMARY KEY,
    Username   VARCHAR(30) NOT NULL,
    Phone      CHAR(11) NOT NULL UNIQUE,
    CreateTime TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 2. 创建店铺表 Shop
CREATE TABLE Shop (
    ShopID      CHAR(8) PRIMARY KEY,
    ShopName    VARCHAR(50) NOT NULL,
    CreditLevel SMALLINT DEFAULT 5 CHECK (CreditLevel BETWEEN 1 AND 5),
    LegalPerson VARCHAR(20) NOT NULL
);

-- 3. 创建商品表 Product (包含 Shop 外码)
CREATE TABLE Product (
    ProductID   CHAR(12) PRIMARY KEY,
    ProductName VARCHAR(100) NOT NULL,
    Price       NUMERIC(10, 2) NOT NULL CHECK (Price > 0),
    Stock       INT NOT NULL CHECK (Stock >= 0),
    ShopID      CHAR(8) NOT NULL,
    CONSTRAINT FK_Product_Shop 
        FOREIGN KEY (ShopID) REFERENCES Shop(ShopID)
        ON UPDATE CASCADE ON DELETE RESTRICT
);

-- 4. 创建订单主表 Orders (包含 User 外码)
CREATE TABLE Orders (
    OrderID     CHAR(18) PRIMARY KEY,
    OrderTime   TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    Status      VARCHAR(10) NOT NULL CHECK (Status IN ('待付款', '已付款', '已发货', '已完成', '已取消')),
    TotalAmount NUMERIC(12, 2) NOT NULL CHECK (TotalAmount >= 0),
    UserID      CHAR(10) NOT NULL,
    CONSTRAINT FK_Orders_User 
        FOREIGN KEY (UserID) REFERENCES Users(UserID)
        ON UPDATE CASCADE ON DELETE RESTRICT
);

-- 5. 创建订单明细表 OrderItem (复合主码 + 级联外码)
CREATE TABLE OrderItem (
    OrderID   CHAR(18) NOT NULL,
    ProductID CHAR(12) NOT NULL,
    Quantity  INT NOT NULL CHECK (Quantity > 0),
    DealPrice NUMERIC(10, 2) NOT NULL CHECK (DealPrice >= 0),
    PRIMARY KEY (OrderID, ProductID),
    CONSTRAINT FK_Item_Order 
        FOREIGN KEY (OrderID) REFERENCES Orders(OrderID)
        ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT FK_Item_Product 
        FOREIGN KEY (ProductID) REFERENCES Product(ProductID)
        ON DELETE RESTRICT ON UPDATE CASCADE
);

-- 6. 物理索引优化
CREATE INDEX Idx_Product_Shop ON Product(ShopID);
CREATE INDEX Idx_Orders_User ON Orders(UserID, OrderTime DESC);
```

### 8. 随堂巩固自测

#### 自测题 1（综合设计大题）
在上述电商系统设计中，若系统要求记录“订单支付流水信息（包括支付流水号 PayID, 支付方式 PayMethod, 支付时间 PayTime, 支付金额 PayAmount）”。假定每一笔订单最多只能成功支付一次，且一次支付只对应一笔订单。
请问：
1. 「订单」与「支付流水」之间属于何种基数类型的联系？
2. 按照一对一联系的最佳工程设计方案，应如何将该支付信息映射为关系模式？

**【参考答案与推导】**：
1. **联系类型**：一笔订单对应一次支付，一次支付对应一笔订单，二者是严格的 **$1:1$（一对一）联系**；
2. **最佳工程设计方案**：
   - 考虑到有大量未付款订单（如超时取消订单）永远不会产生支付流水，若将支付字段合并到订单表会造成大量空值（NULL）；
   - 因此推荐采用**独立建表**或**外码合并到完全参与端**的策略，此处将支付流水作为从属实体独立建表：
     $$\text{Payment}(\underline{\text{PayID}}, \text{PayMethod}, \text{PayTime}, \text{PayAmount}, \text{OrderID})$$
     - 主码：`PayID`；
     - 外码：`OrderID` 声明为 `UNIQUE` 唯一外码（强制约束 $1:1$ 语义），参照 `Orders(OrderID)`。
