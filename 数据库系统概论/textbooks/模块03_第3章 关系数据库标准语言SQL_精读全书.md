## 第 1 章：第3章  关系数据库标准语言SQL（1）

### 1. 核心概念与本质内涵：SQL 的诞生与时代使命

**SQL（Structured Query Language，结构化查询语言）**是关系数据库系统的通用标准语言。1974 年由 Boyce 和 Chamberlin 提出（最初称为 SEQUEL），并在 IBM 的 System R 实验关系数据库系统上得以实现。随后，美国国家标准学会（ANSI）与国际标准化组织（ISO）先后将其确立为国际工业标准，至今经历了 SQL-86, SQL-89, SQL-92, SQL:1999, SQL:2003, SQL:2016 等多次迭代演进。

SQL 之所以能统治关系数据库长达半个世纪，核心在于其完美统一了数据的定义、查询、操纵与控制功能。

```text
                       SQL 语言的功能与命令矩阵
                                  │
      ┌───────────────────┬───────┴───────┬───────────────────┐
      ▼                   ▼               ▼                   ▼
【数据定义 (DDL)】    【数据查询 (DQL)】  【数据操纵 (DML)】  【数据控制 (DCL)】
  CREATE (创建)         SELECT (查询)       INSERT (插入)       GRANT  (赋权)
  DROP   (删除)                             UPDATE (修改)       REVOKE (收回)
  ALTER  (修改)                             DELETE (删除)       COMMIT / ROLLBACK
```

---

### 2. SQL 语言的核心技术特征

#### 2.1 综合一体（All-in-one）
在传统的非关系型数据库中，数据定义语言（DDL）、数据操纵语言（DML）和数据控制语言（DCL）往往彼此分离且语法差异极大。
SQL 则将四种能力有机融为一体：
- 数据定义与操纵语言风格高度统一，使得数据库管理员（DBA）与应用开发者可以在同一个终端会话中自由流转；
- 支持在数据库运行生命周期中**动态修改模式（Dynamic Schema Evolution）**，无需停机重新编译。

#### 2.2 高度非过程化（Non-procedural）
- 使用 SQL 进行数据操作时，用户只需提出“做什么（What to do）”，即明确结果数据应满足的约束条件；
- 完全不需要指定存取路径，也不需要了解底层数据在磁盘上是以何种物理文件存储、使用何种树形索引；
- 复杂的存取路径选择与代数优化完全由 DBMS 引擎内部自动完成。

#### 2.3 面向集合的操作方式（Set-at-a-time）
- 传统的格式化模型采用的是“一次一记录（Record-at-a-time）”的游标循环逻辑；
- SQL 则彻底采用“一次一集合（Set-at-a-time）”机制：不仅查询结果是元组的集合，而且一次 `INSERT`, `UPDATE`, `DELETE` 语句的作用对象同样可以是由条件过滤出的一组元组。

#### 2.4 以同一种语法结构提供两种使用方式
- **交互式 SQL（Interactive SQL）**：供最终用户或管理员在终端、Navicat、DBeaver、pgAdmin 等工具中直接输入并即时执行；
- **嵌入式 SQL（Embedded SQL / Host Language）**：允许将 SQL 语句嵌入到高级程序设计语言（如 C/C++, Java, Python, Go）中，通过游标或现代 ORM 框架与宿主语言紧密协同。两种场景下 SQL 的语法体系完全保持一致。

### 3. 数据库三级模式结构在 SQL 中的落地映射

《数据库系统概论》第 1 章介绍的 ANSI 三级模式结构，在 SQL 标准中找到了具体、精准的工程具象化映射：

```text
三级模式体系结构 (Theoretical)              SQL 工程实现架构 (SQL Implementation)
───────────────────────────────              ─────────────────────────────────────
    [外模式 (External Schema)]     <=======>    视图 (View) 与部分导出表
                │                                (对用户可见的局部虚拟定制逻辑结构)
                ▼                                              │
    [概念模式 (Schema)]            <=======>    基本表 (Base Table)
                │                                (独立存在的实际表，全局数据逻辑核心)
                ▼                                              │
    [内模式 (Internal Schema)]     <=======>    存储文件 (Stored File)
                                                 (物理磁盘上的数据块、页、B+树索引簇)
```

1. **基本表（Base Table）对应概念模式**：
   - 基本表是本身独立存在的表，每个基本表对应一个关系；
   - 一个关系数据库中由若干基本表构成的全局逻辑结构，正是概念模式的物理落地；
2. **视图（View）对应外模式**：
   - 视图是从一个或几个基本表（或其他视图）导出的“虚表”；
   - 数据库中只存放视图的定义（SQL 语句元数据），不存放视图对应的数据（数据仍保存在原基本表中）；
   - 用户通过视图观察数据，实现了对敏感字段的隐藏与定制化呈现，精确落地外模式；
3. **存储文件（Stored File）对应内模式**：
   - 逻辑上的基本表在物理层由一个或多个存储文件实现；
   - 存储文件内部包含具体的记录物理存储格式、页面布局以及索引结构。

### 4. 典型例题与深度认知辨析

#### 辨析 1：基本表与视图的本质区别是什么？

- **本质对比**：
  - **基本表**：是物理磁盘上有真实数据行落盘的物理关系，拥有独立持久化的数据空间；
  - **视图**：是虚拟表，在数据字典中仅仅记录了一段查询定义的文本（SQL 逻辑）。当用户查询视图时，DBMS 动态执行**视图消解（View Resolution）**，将其转化为对底层基本表的查询。

#### 辨析 2：SQL 为什么被称为“非过程化”语言？

- 在 SQL 中没有 `for` 循环、没有指针跳转、没有内存偏移量计算。例如 `SELECT * FROM Student WHERE Sage > 20;` 仅仅陈述了结果集的筛选规则，系统底层是用全表扫描还是走 B+ 树索引，对用户完全屏蔽。

### 1. 核心概念与本质内涵：模式与基本表的关系

在 SQL 环境中，一个关系数据库由若干个**模式（Schema）**组成，而一个模式内部又包含若干个**基本表（Base Table）**、视图（View）与索引（Index）。

模式本质上是数据库对象的组织容器和命名空间（Namespace）：
- 不同的模式可以包含同名的基本表（例如 `HR.Employee` 与 `Finance.Employee` 不会产生命名冲突）；
- 权限控制可以精准绑定到模式级别。

```text
               SQL 数据库命名空间与对象层级
+-------------------------------------------------------------------+
| 数据库 (Database / Catalog)                                       |
|                                                                   |
|   模式 A (Schema: "S_CAMPUS")      模式 B (Schema: "S_FINANCE")   |
|   +--------------------------+     +--------------------------+   |
|   | 基本表: Student          |     | 基本表: Tuition          |   |
|   | 基本表: Course           |     | 基本表: Payroll          |   |
|   | 基本表: SC               |     | 视图:   V_Salary         |   |
|   | 视图:   V_CS_Student     |     | 索引:   Idx_PayDate      |   |
|   | 索引:   Idx_Sno          |     +--------------------------+   |
|   +--------------------------+                                    |
+-------------------------------------------------------------------+
```

---

### 2. 模式的定义与删除（Schema DDL）

#### 2.1 定义模式（CREATE SCHEMA）

- **标准语法结构**：
  ```sql
  CREATE SCHEMA <模式名> AUTHORIZATION <用户名> [子句集];
  ```
- **语法参数剖析**：
  - `<模式名>`：新创建的命名空间标识符；若省略模式名，则模式名默认为 `<用户名>`；
  - `AUTHORIZATION`：指定该模式的所有者（Owner）角色；
  - `[子句集]`：允许在定义模式的同时，直接一次性创建该模式下的基本表、视图及授权语句。
- **经典示例**：
  ```sql
  -- 为用户 WANG 创建一个名为 TEST_SCHEMA 的模式，并在其中直接创建学生表
  CREATE SCHEMA TEST_SCHEMA AUTHORIZATION WANG
      CREATE TABLE TAB1 (
          COL1 INT PRIMARY KEY,
          COL2 CHAR(20),
          COL3 NUMERIC(10, 2)
      );
  ```

#### 2.2 删除模式（DROP SCHEMA）

- **标准语法结构**：
  ```sql
  DROP SCHEMA <模式名> <CASCADE | RESTRICT>;
  ```
- **两大删除选项的行为差异**：
  1. **`CASCADE`（级联删除）**：删除模式的同时，把该模式下所包含的全部数据库对象（所有的基本表、视图、索引）全部连带自动删除；
  2. **`RESTRICT`（限制删除）**：只有当该模式下**没有任何下属数据库对象**（为空模式）时，才允许成功删除；若模式内存在任何表或视图，系统立即报错拒绝执行。

### 3. 基本表的创建与数据类型体系（CREATE TABLE）

#### 3.1 常用 SQL 标准数据类型矩阵

| 数据类型 | 描述与取值规约 | 典型应用场景 |
| :--- | :--- | :--- |
| `INT` / `INTEGER` | 4 字节带符号整数（约 $-2.1 \times 10^9 \sim 2.1 \times 10^9$） | 计数器、主键 ID、学生年龄 |
| `SMALLINT` | 2 字节带符号整数（$-32768 \sim 32767$） | 较小范围的整数（如学分、星期） |
| `BIGINT` | 8 字节大整数 | 海量互联网流水号、全局分布式 ID |
| `NUMERIC(p, s)` / `DECIMAL(p, s)` | 高精度定点小数：$p$ 为总有效位数（Precision），$s$ 为小数位数（Scale） | 银行金额、财务结算（杜绝浮点精度丢失） |
| `CHAR(n)` | 固定长度字符类型（不足 $n$ 位时末尾自动填充空格） | 长度固定的编码（如学号、身份证号、性别） |
| `VARCHAR(n)` | 可变长度字符类型（最大长度 $n$，按实际内容占用存储） | 姓名、文章标题、通信地址 |
| `DATE` | 日期类型（格式：`YYYY-MM-DD`） | 出生日期、开学日期 |
| `TIME` | 时间类型（格式：`HH:MM:SS`） | 上课时间、打卡时间 |
| `TIMESTAMP` | 时间戳（含日期、时间及毫秒，支持时区） | 订单创建时间、审计日志 |

#### 3.2 基本表创建语法与完整性约束内嵌

在执行 `CREATE TABLE` 时，系统不仅定义字段物理结构，还同时形式化声明三大完整性约束：

```sql
CREATE TABLE <表名> (
    <列名> <数据类型> [列级完整性约束条件],
    <列名> <数据类型> [列级完整性约束条件],
    ...
    [表级完整性约束条件]
);
```

##### ① 列级约束与表级约束的区分规则：
- **列级约束**：紧跟在某一列定义之后，只能针对该单一列生效（如 `NOT NULL`, `UNIQUE`）；
- **表级约束**：写在所有列定义完成后的末尾，**当约束涉及多个列（如复合主码、外码）时，必须声明为表级约束**。

### 4. 经典三表模式 DDL 完整创建实战

以下为高校经典三表模型在工业级 SQL 环境下的标准化完整建表脚本：

```sql
-- 1. 创建学生表 Student (主码为单列 Sno)
CREATE TABLE Student (
    Sno   CHAR(9) PRIMARY KEY,          -- 列级主码约束 (隐含 NOT NULL + UNIQUE)
    Sname VARCHAR(20) NOT NULL,         -- 列级非空约束
    Ssex  CHAR(2) CHECK (Ssex IN ('男', '女')), -- 用户定义完整性 (枚举检查)
    Sage  SMALLINT CHECK (Sage >= 15 AND Sage <= 45),
    Sdept VARCHAR(20) DEFAULT '计算机系' -- 默认值约束
);

-- 2. 创建课程表 Course (含自参照外码 Cpno)
CREATE TABLE Course (
    Cno     CHAR(4) PRIMARY KEY,
    Cname   VARCHAR(40) NOT NULL,
    Cpno    CHAR(4),                    -- 先修课号
    Ccredit SMALLINT NOT NULL CHECK (Ccredit > 0),
    FOREIGN KEY (Cpno) REFERENCES Course(Cno) -- 表级自参照外码约束
);

-- 3. 创建选课成绩表 SC (复合主码 + 双重外码)
CREATE TABLE SC (
    Sno   CHAR(9) NOT NULL,
    Cno   CHAR(4) NOT NULL,
    Grade SMALLINT CHECK (Grade >= 0 AND Grade <= 100),
    -- 表级复合主码定义 (两个属性联合唯一且非空)
    PRIMARY KEY (Sno, Cno),
    -- 表级外码约束 1: 参照 Student(Sno)
    FOREIGN KEY (Sno) REFERENCES Student(Sno)
        ON DELETE CASCADE               -- 级联删除: 学生退学时自动清理其选课
        ON UPDATE CASCADE,              -- 级联更新: 学号变更时同步联动
    -- 表级外码约束 2: 参照 Course(Cno)
    FOREIGN KEY (Cno) REFERENCES Course(Cno)
        ON DELETE RESTRICT              -- 限制删除: 有人选修的课严禁删除
);
```

> **易错点**：在创建存在外码参照的表时，**必须先创建被参照的“主表”（`Student`, `Course`），后创建参照的“从表”（`SC`）**；否则在编译外码引用时系统会因找不到目标表而报错中断。

#### 自测题 1（单项选择题）
在定义复合主码（由两个及以上属性共同构成的主码）时，在 SQL 语法中必须采用的书写方式是（ ）
A. 分别在每个主码列的定义后添加 `PRIMARY KEY` 列级约束  
B. 在所有列定义之后，添加一个表级约束：`PRIMARY KEY (属性1, 属性2)`  
C. 在建表语句末尾添加 `INDEX (属性1, 属性2)`  
D. 复合主码不能通过 SQL 直接创建，必须在系统上线后由 DBA 手动配置  

**【答案】**：B  
**【解析】**：若在多个列后面分别写 `PRIMARY KEY`，系统会判定为试图声明多个独立主码而报错（一个表只能有一个主码）。定义复合主码必须在表级使用 `PRIMARY KEY (列1, 列2, ...)` 联合声明。故选 B。

#### 自测题 2（DDL 设计与排错题）
阅读下列建表 SQL 代码片段，指出其中存在的 2 处逻辑或语法错误，并给出修正方案：
```sql
CREATE TABLE Department (
    DeptID INT,
    DeptName VARCHAR(50),
    PRIMARY KEY (DeptID)
);

CREATE TABLE Employee (
    EmpID INT PRIMARY KEY,
    EmpName VARCHAR(20),
    DeptID INT,
    FOREIGN KEY (DeptID) REFERENCES Department(DeptID),
    Salary NUMERIC(8, 2) CHECK (Salary < 0) -- 错误处
);
```

**【参考答案与解析】**：
1. **错误 1（检查约束逻辑反向）**：`Salary NUMERIC(8, 2) CHECK (Salary < 0)` 要求工资必须小于 0，这与现实业务常理完全相悖。  
   - **修正**：应改为 `CHECK (Salary >= 0)` 或设定合理区间 `CHECK (Salary BETWEEN 1000 AND 1000000)`。
2. **表级外码命名与依赖完整性规范建议**：虽然上述 `FOREIGN KEY` 语法合法，但外码未显式命名（不易于后续维护删除），且 `Department` 表的 `DeptName` 缺少 `NOT NULL` 与 `UNIQUE` 业务约束。

### 1. 核心概念与本质内涵：模式的动态演进（Schema Evolution）

在现代软件系统的实际生产运行中，业务需求会随着组织发展不断变化（例如：因新业务上线，学生表需要增加“入学时间”和“联系邮箱”；原有字段长度不足需要扩容；或者需要追加新的防重业务约束）。

关系数据库系统的一大核心优势在于：**支持模式的动态演进（Dynamic Schema Evolution）**。管理员无需停机导出数据、重写建表脚本并重建数据库，而是通过 `ALTER TABLE` 语句在运行期直接完成表结构的在线动态修改。

```text
                     基本表模式的动态修改架构
                                │
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
【列级维度变更】        【约束级维度变更】      【整体销毁与级联】
 • ADD COLUMN (加列)     • ADD CONSTRAINT (加约束)• DROP TABLE RESTRICT
 • DROP COLUMN (删列)    • DROP CONSTRAINT(删约束) (受限模式: 被引则拒)
 • ALTER COLUMN(改类型)                           • DROP TABLE CASCADE
                                                 (级联模式: 抹除依赖)
```

---

### 2. 修改基本表（ALTER TABLE）的核心语法体系

`ALTER TABLE` 语句的标准语法框架如下：

```sql
ALTER TABLE <表名>
    [ ADD [COLUMN] <新列名> <数据类型> [列级完整性约束] ]
    [ DROP [COLUMN] <列名> [CASCADE | RESTRICT] ]
    [ ALTER COLUMN <列名> <新数据类型> ]
    [ ADD CONSTRAINT <约束名> <表级完整性约束> ]
    [ DROP CONSTRAINT <约束名> [CASCADE | RESTRICT] ];
```

#### 2.1 新增列操作（ADD COLUMN）

- **标准语法**：
  ```sql
  ALTER TABLE Student ADD EntranceDate DATE;
  ```
- **核心规约与工程易错点**：
  > **易错点**：当表中已经存在历史持久化数据时，**新增的列通常不能声明为 `NOT NULL`**（除非同时指定了 `DEFAULT` 默认值）。
  > **原因剖析**：如果声明为 `NOT NULL` 且未提供默认值，既有的所有历史记录在该新增列上无值可填，将直接违反非空约束，导致 DDL 执行报错。

#### 2.2 修改列属性与数据类型（ALTER COLUMN）

- **标准语法**：
  ```sql
  -- 将原 VARCHAR(20) 的姓名列扩容为 VARCHAR(50)
  ALTER TABLE Student ALTER COLUMN Sname VARCHAR(50);
  ```
- **约束规则**：数据类型的变更通常只允许**向前兼容扩容**（如 20 字符扩为 50 字符）；若试图将字段类型缩小，或将包含字符串的数据转换为数值型，当既有数据中存在超长或不兼容字符时，DBMS 会终止变更以保护数据完整性。

#### 2.3 增加与删除表级完整性约束（ADD / DROP CONSTRAINT）

通过显式命名约束，可以极大地提高后续数据库维护的灵活性：

```sql
-- 1. 为 Student 表的 Sage 字段追加一个名为 C_Student_Age 的范围检查约束
ALTER TABLE Student 
    ADD CONSTRAINT C_Student_Age CHECK (Sage BETWEEN 15 AND 40);

-- 2. 后续因业务放宽，删除该年龄检查约束
ALTER TABLE Student 
    DROP CONSTRAINT C_Student_Age;
```

### 3. 删除基本表（DROP TABLE）与其依赖判定机理

当某个基本表不再需要时，使用 `DROP TABLE` 语句予以彻底删除：

```sql
DROP TABLE <表名> [RESTRICT | CASCADE];
```

#### 3.1 `RESTRICT`（限制模式，默认规则）
- **判定逻辑**：系统在执行删除前，会严格扫描全库数据字典：
  1. 检查是否有其他基本表的外码**参照了该表的主码**；
  2. 检查是否有**视图基于该表定义**；
  3. 检查是否有触发器、存储过程依赖于该表；
- **执行结果**：只要存在**任何上述依赖对象**，系统立即报错拒绝删除。必须由管理员先手工删除所有依赖对象后，方可删除该表。

#### 3.2 `CASCADE`（级联模式）
- **判定逻辑**：系统不作任何阻拦，强制销毁该表；
- **连锁反应**：
  - 该基本表本身及其全部数据行被彻底从磁盘抹除；
  - 所有建立在该表上的**索引（Index）自动销毁**；
  - 所有基于该表建立的**视图（View）全部自动失效并随之删除**；
  - 所有参照该表的外码约束（Foreign Key）被自动从系统数据字典中注销。

```text
【DROP TABLE CASCADE 级联破坏效应示意】
               DROP TABLE Student CASCADE;
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
 [Student 表实体抹除]   [所有索引自动销毁]   [所有依赖视图一并销毁]
 (磁盘数据块被释放)     (Idx_Sno 瞬间清空)   (V_CS_Student 视图失效)
```

### 4. 典型例题与深度认知辨析

#### 辨析 1：`DELETE FROM Table` 与 `DROP TABLE Table` 有何本质区别？

- **本质对比**：
  - `DELETE FROM Student;` 是 **DML 操作**：它仅仅清空表中的所有数据元组（行），**表的模式定义、列结构、索引以及约束仍然完整保存在数据字典中**，后续依然可以执行 `INSERT`；
  - `DROP TABLE Student;` 是 **DDL 操作**：不仅清空全部数据，更将表本身的**元数据结构、模式定义彻底从系统数据字典中抹去**，该表不复存在。

#### 辨析 2：为什么生产环境中严禁盲目使用 `CASCADE` 选项？

- `CASCADE` 具有极强的隐式级联破坏性。在复杂的大型企业级数据库中，一张核心主表（如 `User`）可能被几十个外部视图和外键弱依赖。一条带 `CASCADE` 的语句可能会在不知情的情况下摧毁大量下游关键业务报表与视图，造成不可逆的重大生产事故。

## 第 4 章：第3章  关系数据库标准语言SQL（4）

### 1. 核心概念与本质内涵：为什么关系数据库必须依赖索引？

关系数据库在逻辑上呈现为行与列构成的抽象集合，但在底层物理存储介质（机械硬盘或固态硬盘 SSD）上，数据是以**数据页（Data Page，通常为 4KB、8KB 或 16KB）**的形式存储在磁盘扇区中的。

#### 1.1 全表扫描的性能噩梦
如果没有索引，当执行一条简单的查询（如 `SELECT * FROM Student WHERE Sno = '202601'`）时：
- 数据库引擎必须从物理文件的第一个数据页开始，自前向后加载全部数据页到内存中逐行比对；
- 这种方式被称为**全表扫描（Table Scan）**，其时间复杂度为 $O(n)$；
- 当表中的记录达到数百万乃至数亿条时，海量的物理磁盘 I/O 将彻底拖垮系统吞吐。

#### 1.2 索引（Index）的物理本质
**索引是存储在磁盘上的一种特殊的辅助数据结构**（如同新华字典的“部首检字表”或“拼音索引表”）：
- 索引按指定的排序列组织指针，将检索复杂度从线性的 $O(n)$ 骤降至对数级的 $O(\log n)$；
- 现代数据库系统通过建立索引，使得用户在不改变逻辑表结构的前提下，获得百倍以上的查询加速。

```text
       无索引检索 (全表扫描)                   基于 B+ 树索引检索
+-------------------------------+       +-------------------------------+
| Page 1: 扫描第 1..100 行      |       |           [根结点]            |
| Page 2: 扫描第 101..200 行    |       |         /         \           |
| ...                           |       |    [内部结点]   [内部结点]    |
| Page N: 扫描第 9999..10000 行 |       |     /      \     /      \     |
+-------------------------------+       | [叶子]   [叶子] [叶子]   [叶子]|
  (全盘 I/O 读取，耗时数十秒)           +-------------------------------+
                                          (对数次 I/O 定位，耗时数毫秒)
```

---

### 2. 索引的物理结构与分类体系

#### 2.1 B+ 树索引（B+ Tree Index）——工业界的主导支柱

在几乎所有的主流商用关系数据库中（Oracle, MySQL InnoDB, PostgreSQL, SQL Server），**B+ 树是应用最广泛、最成熟的索引结构**。

##### B+ 树的核心物理特性：
1. **多路平衡查找树**：所有的叶子结点都处于完全相同的深度，树的高度极低（通常为 3~4 层，即可支撑数千万级数据检索），查询单条记录只需 3~4 次磁盘 I/O；
2. **非叶子结点仅存索引键值与指针**：非叶子结点不存储具体的行数据，因此单页可以容纳海量的分支指针，大幅提升树的扇出比（Fan-out）；
3. **叶子结点全覆盖与双向顺序链表**：
   - 所有的实际数据记录指针（或真实行记录）均保存在底层的**叶子结点**中；
   - 所有叶子结点按照键值升序通过**双向链表**串联。这赋予了 B+ 树极其强大的**范围查询（Range Query）与排序输出**能力（如 `BETWEEN 20 AND 30` 只需要定位左边界，然后沿着叶子链表向后顺序遍历即可）。

---

#### 2.2 聚集索引（Clustered Index）与非聚集索引（Non-clustered Index）

根据索引的组织顺序是否决定表中数据的物理存放顺序，索引划分为两大派系：

```text
                      聚集索引 vs 非聚集索引
                                │
        ┌───────────────────────┴───────────────────────┐
        ▼                                               ▼
【聚集索引 (Clustered)】                        【非聚集索引 (Non-clustered / 辅助索引)】
 • 表中行的物理存放顺序与索引顺序完全一致        • 索引逻辑顺序与磁盘物理顺序完全无关
 • 叶子结点就是真实的数据页 (包含全部字段)      • 叶子结点仅存储: 索引键值 + 行物理指针 (RID)
 • 一个基本表上最多只能建立一个聚集索引!        • 一个基本表上可以建立多个非聚集索引
```

##### ① 聚集索引（Clustered Index）的核心规约：
- **唯一性定律**：**一个基本表上最多只能建立一个聚集索引**；
  - **原因剖析**：物理磁盘上的数据行在空间中只能有一种物理排布次序。既然聚集索引规定“数据物理顺序必须完全贴合索引顺序”，那么表中数据只能按照某一个键值进行物理落盘排序，不可能同时既按学号物理排序又按年龄物理排序；
- **优缺点分析**：
  - **巨大优势**：查询连续范围（如范围检索）或分组排序极快，连续的数据页在磁盘上是物理相邻的，可触发顺序预读；
  - **维护代价**：当对聚集索引列进行更新或插入乱序新行时，为了维持物理排序，DBMS 必须在底层执行昂贵的数据行物理位移乃至**数据页分裂（Page Split）**。因此：**频繁变动修改的属性绝不适合建立聚集索引**。

##### ② 非聚集索引（Non-clustered Index / 二级辅助索引）：
- 索引表与基本表在物理存储上彼此独立；
- 辅助索引的叶子节点存放索引列的值以及一个指向主表对应数据行的**物理寻址指针（Row ID, RID）**或主键值；
- 检索时先查辅助索引取得主键/RID，再根据该指针回到主数据表中提取其他字段，该过程被称为**回表查询（Bookmarking Lookup）**。

---

### 3. 索引 DDL 定义与管理规约

#### 3.1 建立索引（CREATE INDEX）

```sql
CREATE [UNIQUE] [CLUSTER] INDEX <索引名>
ON <表名> (<列名> [<次序>] [, <列名> [<次序>]]...);
```

- **参数解析**：
  - `UNIQUE`：表明此索引的每一个键值只对应唯一的一条记录。DBMS 会在写入时强制进行唯一性校验；
  - `CLUSTER`：表明要建立的是**聚集索引**；
  - `<次序>`：可选 `ASC`（升序，默认值）或 `DESC`（降序）。

##### 经典建索引实战：
```sql
-- 1. 在 Student 表的学号列上建立唯一聚集索引
CREATE UNIQUE CLUSTER INDEX Idx_Student_Sno 
ON Student(Sno ASC);

-- 2. 在 SC 选课表上建立复合非聚集索引 (按学号升序，课程号降序)
CREATE INDEX Idx_SC_SnoCno 
ON SC(Sno ASC, Cno DESC);

-- 3. 在 Course 表的课程名上建立唯一辅助索引
CREATE UNIQUE INDEX Idx_Course_Cname 
ON Course(Cname);
```

#### 3.2 删除索引（DROP INDEX）

```sql
DROP INDEX <索引名> [ON <表名>];
```
删除索引只是删除了加速查找的辅助 B+ 树文件，**原基本表中的业务数据绝不受任何损害**。

---

### 4. 索引设计的工程权衡法则（Trade-off）

> **重要工程原则**：索引并不是建得越多越好！索引是一把双刃剑。

```text
【建立索引的成本收益天平】
              收益 (Pros)                         代价 (Cons)
        ─────────────────────────           ─────────────────────────
        • 极速提升 SELECT 读查询性能         • 额外占用大量磁盘存储空间
        • 显著降低 ORDER BY 排序开销         • 拖慢 INSERT / UPDATE / DELETE
        • 强化主外码唯一性校验               • 每次写数据必须同步维护 B+ 树
```

#### 适合建索引的列：
1. 经常需要作为查询过滤条件（`WHERE` 子句）的列；
2. 经常用于连接（`JOIN` 的公共键，如外码）的列；
3. 经常需要按照其进行分组（`GROUP BY`）或排序（`ORDER BY`）的列。

#### 不适合建索引的列：
1. 极少在查询条件中出现的列；
2. 包含极少不同取值的列（低基数，如“性别”只有男女两种值，区分度极低，走索引反而不如全表扫描高效）；
3. 频繁进行高频修改写入的列；
4. 数据量极小的小字典表（仅几行几十行，单次 I/O 即可全表读取）。

## 第 5 章：第3章  关系数据库标准语言SQL（5）
> 对应分集：P20 | 原始标题：《第3章  关系数据库标准语言SQL（5）》

### 1. 核心概念与本质内涵：SELECT 语句的执行逻辑骨架

数据查询是数据库系统最核心、最高频的操作。SQL 的数据查询通过 `SELECT` 语句实现。在关系代数的理论映射中：
- `SELECT` 目标列表达式对应**投影（Projection, $\pi$）**；
- `WHERE` 条件表达式对应**选择（Selection, $\sigma$）**。

一条标准单表查询的逻辑执行模型如下：

```text
               单表 SELECT 查询的逻辑执行流向
+-------------------------------------------------------------+
| 1. FROM 子句: 确定数据来源基表 (载入目标关系)               |
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 2. WHERE 子句: 逐行评估谓词表达式 (过滤出满足条件的元组集合)|
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 3. SELECT 子句: 提取指定属性、执行标量计算并处理 DISTINCT   |
+-------------------------------------------------------------+
```

---

### 2. 目标列表达式的丰富形态

```sql
SELECT [ALL | DISTINCT] <目标列表达式> [, <目标列表达式>]...
FROM <表名>;
```

#### 2.1 查询指定列与投影去重（DISTINCT）
- **`ALL`（默认）**：保留结果集中的所有重复元组；
- **`DISTINCT`**：强制执行集合去重，消除重复行。
  ```sql
  -- 查询选修了课程的所有学号，消除重复记录
  SELECT DISTINCT Sno FROM SC;
  ```

#### 2.2 目标列表达式中的动态计算与函数转换
目标列不仅可以直接是列名，还可以包含**算术运算、字符串操作与函数映射**，并使用 `AS` 赋予易读别名：
```sql
-- 查询全体学生的姓名及其出生年份 (当前年份减去实足年龄)
SELECT 
    Sname AS 姓名,
    'Birth Year:' AS 标识标签,
    2026 - Sage AS 出生年份,
    LOWER(Sdept) AS 院系编码小写
FROM Student;
```

---

### 3. WHERE 子句过滤谓词全景解构

`WHERE` 子句通过逻辑联结词（`AND`, `OR`, `NOT`）组合各类谓词条件，以精确界定候选元组集合：

| 查询条件分类 | 谓词符号 / 关键字 | 语法模式示范 |
| :--- | :--- | :--- |
| **比较大小** | `=`, `>`, `<`, `>=`, `<=`, `!=`, `<>` | `WHERE Sage >= 20` |
| **确定闭区间范围** | `BETWEEN ... AND ...` / `NOT BETWEEN` | `WHERE Sage BETWEEN 18 AND 22` |
| **确定有限集合** | `IN (...)` / `NOT IN (...)` | `WHERE Sdept IN ('CS', 'MA', 'IS')` |
| **字符模糊匹配** | `LIKE` / `NOT LIKE` | `WHERE Sname LIKE '张%'` |
| **空值判断** | `IS NULL` / `IS NOT NULL` | `WHERE Grade IS NULL` |
| **多重复合逻辑** | `AND`, `OR`, `NOT`（优先级：NOT > AND > OR） | `WHERE Sdept = 'CS' AND Sage < 20` |

---

#### 3.1 字符匹配（LIKE）与转义机制（ESCAPE）

模糊匹配的语法格式为：
```sql
[NOT] LIKE '<匹配串>' [ESCAPE '<换码字符>']
```

##### ① 两大标准通配符：
- **百分号 `%`**：代表**任意长度（包括长度为 0）**的字符串。
  - 例如 `Sname LIKE '刘%'` 可匹配“刘邦”、“刘备”、“刘德华”，甚至单字“刘”。
- **下划线 `_`**：代表**任意单个字符**。
  - 例如 `Sname LIKE '欧阳_'` 只能匹配“欧阳修”、“欧阳锋”（恰好 3 个字），不能匹配“欧阳震华”。

##### ② ESCAPE 显式转义字符机制：
> **核心难点**：如果被检索的文本本身就包含 `%` 或 `_` 符号（例如要查询课程名为 `DB_Design` 的课程），如何防止下划线被系统误判为单字通配符？

- **解决方案**：使用 `ESCAPE` 子句自定义换码字符：
  ```sql
  -- 将 '\' 声明为转义符，紧随其后的 '_' 将作为纯文本字面值对待
  SELECT * FROM Course 
  WHERE Cname LIKE 'DB\_%' ESCAPE '\';
  ```

---

#### 3.2 空值（NULL）判定与数据库三值逻辑（Three-Valued Logic）

在数据库中，`NULL` 代表“未知（Unknown）”、“不存在”或“无意义”，**它不是空字符串 `""`，也不是数字零 `0`**。

##### ① 空值判断的语法铁律：
> **【致命误区】**：严禁写 `WHERE Grade = NULL`！
> **必须且只能写**：`WHERE Grade IS NULL` 或 `WHERE Grade IS NOT NULL`。

##### ② 关系数据库的三值逻辑系统：
当对包含 `NULL` 的字段执行算术比较时，逻辑运算的结果不是单纯的“真（TRUE）”或“假（FALSE）”，而是引入了第三种状态——**未知（UNKNOWN）**：
- 任何数值与 `NULL` 进行算术比较（如 `NULL = 100`, `NULL = NULL`, `NULL > 50`），**其判定结果一律为 UNKNOWN**；
- `WHERE` 子句有一条根本法则：**只有当谓词条件的最终计算结果为严格的 TRUE 时，该行元组才会被选入结果集；结果为 FALSE 或 UNKNOWN 的行均被直接丢弃**！
- 这就是为什么 `WHERE Grade = NULL` 永远查不出任何记录的原因（因为等式评估结果恒为 UNKNOWN，永远不会为 TRUE）。

```text
                  三值逻辑真值表 (Three-Valued Logic)
         AND      TRUE      FALSE     UNKNOWN
       +--------+---------+---------+---------+
       | TRUE   | TRUE    | FALSE   | UNKNOWN |
       | FALSE  | FALSE   | FALSE   | FALSE   |
       | UNKNOWN| UNKNOWN | FALSE   | UNKNOWN |
       +--------+---------+---------+---------+
         OR       TRUE      FALSE     UNKNOWN
       +--------+---------+---------+---------+
       | TRUE   | TRUE    | TRUE    | TRUE    |
       | FALSE  | TRUE    | FALSE   | UNKNOWN |
       | UNKNOWN| TRUE    | UNKNOWN | UNKNOWN |
       +--------+---------+---------+---------+
```

SELECT Sname, Sno

## 第 6 章：第3章  关系数据库标准语言SQL（6）
> 对应分集：P21 | 原始标题：《第3章  关系数据库标准语言SQL（6）》

### 1. 核心概念与本质内涵：从单行过滤到集合级度量与重排

在单表数据检索中，除了对单行元组进行投影和谓词过滤外，实际业务场景往往需要两项关键处理能力：
1. **结果排序（ORDER BY）**：按业务优先级呈现有序列表（如按成绩由高到低排名）；
2. **多行聚合度量（Aggregate Functions）**：将多行数据汇聚、提炼为宏观的统计指标（如班级总人数、课程平均分、历史最高分）。

```text
                  SELECT 语句的后置阶段执行流向
+-------------------------------------------------------------+
| 1. FROM & WHERE: 载入基表并过滤单行元组                     |
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 2. 聚集计算: COUNT / SUM / AVG / MAX / MIN (汇总多行聚合指标)|
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 3. ORDER BY 子句: 对最终输出的结果集进行物理重排 (ASC/DESC) |
+-------------------------------------------------------------+
```

---

### 2. 结果排序机制（ORDER BY 子句）

```sql
ORDER BY <列名> [ASC | DESC] [, <列名> [ASC | DESC]]...
```

#### 2.1 排序核心规则
- **`ASC`（Ascending）**：升序排序（数值从小到大，字母从 A 到 Z），为系统**默认排序方向**；
- **`DESC`（Descending）**：降序排序（数值从大到小，日期由新到旧）。

#### 2.2 多属性列层级排序（Hierarchical Sorting）
当 `ORDER BY` 包含多个排序列时，系统严格执行优先级次序：
- **先按第一个列的值排序**；
- **仅当第一个列的值完全相同时，才使用第二个列的值进行内部微调排序**。

```sql
-- 查询选修 1 号课程的学生学号与成绩，结果按成绩降序排；成绩相同时按学号升序排
SELECT Sno, Grade 
FROM SC 
WHERE Cno = '1'
ORDER BY Grade DESC, Sno ASC;
```

#### 2.3 排序与空值（NULL）的交互行为
在 SQL 标准中，`NULL` 在排序时被视作具有特殊位阶：
- 大多数数据库（如 Oracle, PostgreSQL）默认在 `ASC` 升序时将 `NULL` 置于最后（或最前），`DESC` 降序时相反；
- 标准 SQL 允许使用 `NULLS FIRST` 或 `NULLS LAST` 显式固定空值行在报表中的呈现位置。

---

### 3. 五大标准聚集函数（Aggregate Functions）深度解构

聚集函数以一组数值为输入，经过聚合计算后返回一个单一的数值。

```text
                         五大标准聚集函数矩阵
                                  │
      ┌───────────────────┬───────┴───────┬───────────────────┐
      ▼                   ▼               ▼                   ▼
  COUNT()               SUM()           AVG()            MAX() / MIN()
(统计元组/值的个数)    (计算数值列总和)  (计算数值列平均值)   (求一列中的极值)
```

#### 3.1 聚集函数功能矩阵

| 聚集函数名 | 输入参数形式 | 功能描述与语义规约 | 适用数据类型 |
| :--- | :--- | :--- | :--- |
| `COUNT(*)` | `*` | 统计元组的总行数，**无论某行是否包含 NULL，一律计入** | 任意表 |
| `COUNT(<列名>)` | `[DISTINCT\|ALL] 列` | 统计该列非空值的总行数，**自动忽略 NULL** | 任意类型 |
| `SUM(<列名>)` | `[DISTINCT\|ALL] 列` | 计算该列数值的总和，**自动忽略 NULL** | 仅限数值型 |
| `AVG(<列名>)` | `[DISTINCT\|ALL] 列` | 计算该列数值的平均值，**自动忽略 NULL** | 仅限数值型 |
| `MAX(<列名>)` | `[DISTINCT\|ALL] 列` | 求该列的最大值，**自动忽略 NULL** | 数值/字符/日期 |
| `MIN(<列名>)` | `[DISTINCT\|ALL] 列` | 求该列的最小值，**自动忽略 NULL** | 数值/字符/日期 |

---

#### 3.2 聚集函数关于空值（NULL）的处理铁律

> **【极度易错点】**：除 `COUNT(*)` 外，**其余所有聚集函数在计算时均自动忽略空值（NULL）**！

##### 深度案例推导：
设有表 `SC` 中某门课程只有三名学生的成绩：`[100, 80, NULL]`（第三位学生缺考）。
1. `COUNT(*)` 的结果为：**3**（表中有 3 行记录）；
2. `COUNT(Grade)` 的结果为：**2**（只有两行有非空成绩）；
3. `AVG(Grade)` 的计算公式为：
   $$\text{AVG} = \frac{100 + 80}{2} = \mathbf{90.0}$$
   **绝不是** $\frac{100 + 80 + 0}{3} = 60.0$！
   如果业务逻辑要求缺考者按 0 分计入全班平均分，必须使用 `COALESCE` 显式转换：
   ```sql
   SELECT AVG(COALESCE(Grade, 0)) FROM SC; -- 结果为 60.0
   ```

---

#### 3.3 DISTINCT 修饰符在聚合中的乘数效应

在聚集函数内部使用 `DISTINCT`，会在计算指标前**先消除重复值**：
```sql
-- 统计全校选修了课程的学生总人数 (同一学生选修多门课只能算 1 人)
SELECT COUNT(DISTINCT Sno) FROM SC;

-- 统计学生参与选修的所有不同学分的总和
SELECT SUM(DISTINCT Ccredit) FROM Course;
```

---

### 4. 核心执行铁律：WHERE 子句严禁使用聚集函数

> **【编译期致命错误】**：初学者常写出以下非法语句：
> ```sql
> -- 严重错误: WHERE 子句严禁包含聚集函数!
> SELECT Sname FROM Student WHERE Sage = MAX(Sage);
> ```

#### 为什么 WHERE 子句不能用聚集函数？
- **时序与作用域矛盾**：
  - `WHERE` 子句的作用是**在数据聚合之前**，针对基表中的**每一行单行元组**逐一评估过滤条件；
  - 在扫描某一行时，整张表的全局数据尚未读取完，全表的 `MAX(Sage)` 根本尚未计算出来；
  - 聚集函数只能作用于已经形成的行集合。要在条件中比对聚集结果，必须通过**子查询（Subquery）**或 **`HAVING` 子句**来实现：
    ```sql
    -- 正确写法: 嵌套子查询先计算出最大年龄
    SELECT Sname FROM Student 
    WHERE Sage = (SELECT MAX(Sage) FROM Student);
    ```

### 5. 随堂巩固自测

#### 自测题 1（单项选择题）
在选课表 `SC` 中，已知 1 号课程有 5 名学生选修，其中 4 人的成绩分别为 90, 80, 70, 60，第 5 人因故缺考成绩为 NULL。则下列 SQL 语句的执行结果分别是（ ）
`SELECT COUNT(*), COUNT(Grade), AVG(Grade) FROM SC WHERE Cno = '1';`
A. 5, 5, 60  
B. 5, 4, 75  
C. 4, 4, 75  
D. 5, 4, 60  

**【答案】**：B  
**【解析】**：
- `COUNT(*)` 统计总元组数，包含 NULL 行，结果为 5；
- `COUNT(Grade)` 自动忽略 NULL，非空行有 4 条，结果为 4；
- `AVG(Grade)` 忽略 NULL，分子为 $90+80+70+60 = 300$，分母为非空行数 4，$300 \div 4 = 75$。故选 B。

#### 自测题 2（SQL 书写实战题）
编写一条标准 SQL 查询语句：
“查询选修了 2 号课程的学生最高分、最低分以及平均分，并将平均分字段重命名为 `AvgScore`，且仅统计成绩在 60 分以上的记录”。

## 第 7 章：第3章  关系数据库标准语言SQL（7）
> 对应分集：P22 | 原始标题：《第3章  关系数据库标准语言SQL（7）》

### 1. 核心概念与本质内涵：从全表度量到多维微观分组

在上一讲中，聚集函数（`COUNT`, `AVG`, `SUM` 等）的作用范围是**整个结果集**（例如计算全校学生的平均年龄，输出单行单列的标量结果）。

但在真实的分析决策场景中，我们往往需要更细粒度的宏观对比：
- 不是求全校平均分，而是求“**每一个院系**的平均分”；
- 不是求总选课人次，而是求“**每一门课程**的选修人数与最高分”；
- 不是统计全库订单，而是统计“**每一个客户**的年度消费总金额”。

为了满足将全表数据切分为若干独立子集分别进行聚合度量的需求，SQL 提供了强大的 **`GROUP BY` 分组机制**与 **`HAVING` 分组过滤机制**。

```text
                     GROUP BY 的逻辑执行矩阵
                     
   原始数据集 (SC 表)               GROUP BY Cno 分组              每组独立聚合输出
+--------+------+-------+        +---------------------+        +------+-------+----------+
|  Sno   | Cno  | Grade |        | Group 1 (Cno = '1') | ───>   | Cno  | 人数  | 平均成绩 |
+--------+------+-------+        | (202601, 1, 90)     |        +------+-------+----------+
| 202601 |  1   |  90   |        | (202602, 1, 80)     |        |  1   |   2   |   85.0   |
| 202602 |  1   |  80   |        +---------------------+        +------+-------+----------+
| 202601 |  2   |  85   |        | Group 2 (Cno = '2') | ───>   |  2   |   3   |   80.0   |
| 202602 |  2   |  75   |        | (202601, 2, 85)     |        +------+-------+----------+
| 202603 |  2   |  80   |        | (202602, 2, 75)     |
+--------+------+-------+        | (202603, 2, 80)     |
                                 +---------------------+
```

---

### 2. GROUP BY 子句的核心规约与投影合法性铁律

#### 2.1 GROUP BY 的执行语义
- `GROUP BY <列名1> [, <列名2>]...`
- 系统扫描结果表，将所有在指定分组列上**取值完全相同的元组归为同一个组**；
- 一旦执行了分组，后续所有的聚集函数将**不再针对全表计算，而是针对每一个独立的组分别进行独立计算**。

#### 2.2 投影列表合法性铁律（The Single-Value Rule）

> **【编译期高危红线】**：在包含 `GROUP BY` 的查询中，`SELECT` 目标列表达式中出现的属性，**有且仅能属于以下两类**：
> 1. **出现在 `GROUP BY` 子句中的分组列**；
> 2. **被聚集函数（`COUNT`, `SUM`, `AVG`, `MAX`, `MIN`）包裹的聚合项**。

##### 为什么严禁出现未参与分组的“裸属性”？
- 假设执行如下非法语句：
  ```sql
  -- 非法语句: Sname 既不在 GROUP BY 中，也没有聚集函数!
  SELECT Sdept, Sname, AVG(Sage) 
  FROM Student 
  GROUP BY Sdept;
  ```
- **机理剖析**：按 `Sdept`（系别）分组后，每个系只输出**唯一的一行数据**。然而在“计算机系”这个组内，存在张三、李四、王五等多名学生。系统在输出该组唯一的这一行时，根本无法从逻辑上决定该把哪一个学生的 `Sname` 填入该行的单元格中！这在逻辑上产生了多义性，标准 SQL 会直接报错拦截。

---

### 3. HAVING 子句的过滤机制与执行流向

当我们不仅需要分组统计，还需要对**分组计算出来的统计指标**施加条件过滤时（例如“筛选出平均成绩在 80 分以上的课程”），必须使用 `HAVING` 子句。

```sql
SELECT Cno, COUNT(Sno) AS 选课人数, AVG(Grade) AS 平均分
FROM SC
GROUP BY Cno
HAVING AVG(Grade) >= 80;
```

---

### 4. WHERE 子句与 HAVING 子句的终极横向辨析

理解 `WHERE` 与 `HAVING` 的本质区别，是掌握复杂 SQL 调优与书写的核心门槛：

```text
               SELECT 完整生命周期的时序流向
+-------------------------------------------------------------+
| 1. FROM 子句: 确定物理基表并执行 JOIN 连接                  |
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 2. WHERE 子句: 针对单行元组进行逐行扫描过滤 (不可用聚集函数)|
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 3. GROUP BY 子句: 将通过 WHERE 的合格元组划分为各个组       |
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 4. 聚集计算: 对各个组独立计算 COUNT / AVG / SUM 等指标      |
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 5. HAVING 子句: 针对各组的统计指标进行组级别过滤 (可用聚集) |
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 6. SELECT & ORDER BY: 提取指定投影列并对结果组重排输出      |
+-------------------------------------------------------------+
```

#### 核心对比维度矩阵：

| 比较维度 | WHERE 子句 | HAVING 子句 |
| :--- | :--- | :--- |
| **作用对象** | **单行元组（Row）** | **已划分的数据组（Group）** |
| **执行时机** | 在 `GROUP BY` 分组**之前**执行 | 在 `GROUP BY` 分组与聚集计算**之后**执行 |
| **聚集函数支持** | **严禁使用聚集函数**（行过滤时尚无聚合值） | **高度依赖聚集函数**（针对聚合指标做阈值筛选） |
| **性能影响** | 越早执行越好：减少参与后续分组的数据量 | 较后执行：无法减少分组过程本身的计算开销 |

---

### 5. 典型例题与深度演算

#### 题例 1：复合条件分组实战
**查询至少有 3 名学生选修，且及格成绩（$\ge 60$）的平均分高于 75 分的课程号、选课总人数与及格平均分**：

```sql
SELECT 
    Cno, 
    COUNT(Sno) AS 选课总人数, 
    AVG(Grade) AS 及格平均分
FROM SC
WHERE Grade >= 60                   -- 第 1 步: 先过滤掉不及格的单行记录
GROUP BY Cno                        -- 第 2 步: 按课程号进行分组
HAVING COUNT(Sno) >= 3              -- 第 3 步: 过滤出及格人数在 3 人以上的组
   AND AVG(Grade) > 75;             --         且该组平均成绩大于 75
```

关于 SQL 查询中 `WHERE` 子句和 `HAVING` 子句的叙述，正确的是（ ）
A. `WHERE` 子句和 `HAVING` 子句都可以使用聚集函数  
B. `HAVING` 子句用于对分组后的组进行过滤，可以使用聚集函数；而 `WHERE` 子句用于对行进行过滤，不能使用聚集函数

**【答案】**：B

#### 自测题 2（SQL 排错与重构题）
某程序员编写了如下 SQL 语句，试图查询“平均年龄大于 20 岁的各系别名称以及该系学生最高年龄”：

## 第 8 章：第3章  关系数据库标准语言SQL（8）

### 1. 核心概念与本质内涵：跨表数据拼接的 SQL 实现

在实际的关系数据库应用中，业务实体的数据通常高度范式化地切分存储在多张不同的基本表中（如 `Student` 表存储学籍、`Course` 表存储课纲、`SC` 表存储选课成绩）。

当需要获取跨实体的综合业务视图时，必须使用 **SQL 连接查询（Join Query）**。SQL 支持现代 ANSI 语法与传统隐式连接语法，覆盖等值连接、自身连接以及保留未匹配元组的外连接。

```text
                       SQL 连接查询的语法进化
                                 │
     ┌───────────────────────────┴───────────────────────────┐
     ▼                                                       ▼
【传统隐式连接 (WHERE 子句)】                      【现代 ANSI SQL 显式连接 (JOIN ... ON)】
 SELECT * FROM A, B                               SELECT * FROM A 
 WHERE A.id = B.id                                [INNER] JOIN B ON A.id = B.id
 (易遗漏 WHERE 条件导致笛卡尔积灾难)              (逻辑解耦: 连接条件在 ON，行过滤在 WHERE)
```

---

### 2. 核心连接类型深度剖析与代码实战

#### 2.1 等值连接与自然连接

##### 1. 等值连接（Equi-join）
通过在连接谓词中使用等号（`=`）来关联两张表的同域属性：
```sql
-- 查询每个学生及其选修课程的详细信息 (显式 ANSI 语法)
SELECT Student.*, SC.*
FROM Student
INNER JOIN SC ON Student.Sno = SC.Sno;
```

##### 2. 自然连接（NATURAL JOIN）
自然连接自动寻找两张表中的**所有同名公共列**，执行等值比对，并在最终输出中**自动去除重复的同名列**：
```sql
-- 自然连接: 自动按 Sno 等值匹配，结果中 Sno 仅出现一次
SELECT * FROM Student NATURAL JOIN SC;
```

> **工程提示**：在工业级生产代码中，**推荐显式使用 `JOIN ... ON` 而非 `NATURAL JOIN`**。因为如果未来某张表被添加了同名但业务无关的列（如两张表都新增了 `Status` 或 `Remark` 列），`NATURAL JOIN` 会自动将该列加入连接条件，导致查询结果意外变成空集。

---

#### 2.2 自身连接（Self-Join）——单表的多重角色映射

当一张表中的某个属性参照了本表的主码时（典型的自参照外码，如课程与其先修课程、员工与其主管），要查询实体间的层级关联，必须执行**自身连接（Self-Join）**。

##### 核心语法规约：
必须为同一张物理表在 `FROM` 子句中赋予**两个不同的表别名（Alias）**，使其在逻辑上分裂为两张互不干扰的虚拟表：

```sql
-- 查询每一门课程的直接先修课名及其先修课的先修课名 (二重自身连接)
SELECT 
    C1.Cname AS 本门课程,
    C2.Cname AS 直接先修课,
    C3.Cname AS 间接先修课
FROM Course C1
LEFT JOIN Course C2 ON C1.Cpno = C2.Cno
LEFT JOIN Course C3 ON C2.Cpno = C3.Cno;
```

---

#### 2.3 外连接族（Outer Join）——彻底拯救悬浮元组

在普通内连接（`INNER JOIN`）中，只有在两张表中均能成功匹配的元组才会被输出。未能匹配的元组作为**悬浮元组（Dangling Tuple）**被系统默认丢弃。外连接通过将悬浮元组纳入结果集，有效防止了数据信息的非预期丢失。

```text
【左外连接 (LEFT JOIN)】                【全外连接 (FULL JOIN)】
      表 A          表 B                     表 A          表 B
   ┌───────┐     ┌───────┐                ┌───────┐     ┌───────┐
   │ 匹配  │<───>│ 匹配  │                │ 匹配  │<───>│ 匹配  │
   │ 元组  │     │ 元组  │                │ 元组  │     │ 元组  │
   ├───────┤     └───────┘                ├───────┤     ├───────┤
   │ A悬浮 │ ──> (B列填NULL)              │ A悬浮 │     │ B悬浮 │
   └───────┘                              └───────┘     └───────┘
                                           (缺失方属性一律填 NULL)
```

1. **左外连接（LEFT [OUTER] JOIN）**：
   - 核心规则：以左表为基准，左表的所有行全部保留；右表若无匹配行，对应字段全部填 `NULL`；
   - 典型业务场景：查询全校所有学生及其选修情况（即使该生刚入学从未选课，也必须列出其姓名，课程信息填 `NULL`）：
     ```sql
     SELECT Student.Sno, Student.Sname, SC.Cno, SC.Grade
     FROM Student
     LEFT JOIN SC ON Student.Sno = SC.Sno;
     ```

2. **右外连接（RIGHT [OUTER] JOIN）**：
   - 核心规则：以右表为基准，右表的所有行全部保留；左表无匹配填 `NULL`；
   - 语法等价：`A RIGHT JOIN B` 完全等价于 `B LEFT JOIN A`。

3. **全外连接（FULL [OUTER] JOIN）**：
   - 核心规则：左右两表的所有悬浮元组全部保留，任何未匹配方均补 `NULL`。

---

### 3. 多表连续连接的执行机理

在复杂报表开发中，连接往往跨越三张甚至更多表：

```sql
-- 查询选修了"信息系统"课程且成绩在 80 分以上的计算机系学生名单
SELECT 
    Student.Sno, 
    Student.Sname, 
    Course.Cname, 
    SC.Grade
FROM Student
INNER JOIN SC ON Student.Sno = SC.Sno
INNER JOIN Course ON SC.Cno = Course.Cno
WHERE Student.Sdept = 'CS'
  AND Course.Cname = '信息系统'
  AND SC.Grade >= 80;
```

## 第 9 章：第3章  关系数据库标准语言SQL（9）
> 对应分集：P24 | 原始标题：《第3章  关系数据库标准语言SQL（9）》

### 1. 核心概念与本质内涵：什么是嵌套查询？

在 SQL 语法中，一个标准的 `SELECT-FROM-WHERE` 语句被称为一个**查询块（Query Block）**。
当我们在一个查询块的 `WHERE` 条件或 `HAVING` 短语中，嵌入了另一个查询块时，这种语法结构被称为**嵌套查询（Nested Query）**，被嵌入的内部查询称为**子查询（Subquery）**或内层查询，包含子查询的外部结构称为**父查询（Parent Query）**或外层查询。

嵌套查询使得 SQL 能够像数学函数复合一样，将多层数据检索逻辑优雅地递归串联起来，而无须编写冗长的临时表存储脚本。

```text
               嵌套查询的层级结构示意
SELECT ... FROM ... WHERE 属性 [比较谓词] 
    (
        SELECT ... FROM ... WHERE ...  <── 内层子查询 (Subquery)
    );
▲
└──────────────────────────────────────── 父查询 / 外层查询 (Outer Query)
```

---

### 2. 不相关子查询 vs 相关子查询（核心执行模型区分）

根据内层子查询的执行是否依赖于外层父查询的当前元组，嵌套查询被划分为两大本质截然不同的执行类别：

```text
                      嵌套查询的两大执行类别
                                │
        ┌───────────────────────┴───────────────────────┐
        ▼                                               ▼
【不相关子查询 (Uncorrelated)】                 【相关子查询 (Correlated)】
 • 内层子查询完全独立，不依赖父查询任何字段       • 内层子查询的 WHERE 条件中引用了外层表的属性
 • 调度策略: 自底向上，内层仅执行一次!           • 调度策略: 类似双重 for 循环，外层每流转一行，
 • 产出静态常量值/集合，直接交由外层比对         • 内层带着该行的属性值重新执行一次计算!
```

#### 2.1 不相关子查询（Uncorrelated Subquery）
- **执行时机**：**由内向外，内层只执行一次**；
- **执行流程**：
  1. 数据库引擎首先独立执行内层子查询；
  2. 内层子查询产出一个固定的单值或集合；
  3. 系统将该结果直接替换为父查询条件中的字面常量；
  4. 父查询单次扫描，完成最终结果输出。

#### 2.2 相关子查询（Correlated Subquery）
- **执行时机**：**内外联动，内层循环执行多次**；
- **执行流程（嵌套循环模型）**：
  1. 从外层关系中取出第一个元组，将其相关属性值传入内层子查询；
  2. 内层子查询带着该参数值执行，计算出本次循环的条件真值；
  3. 外层根据该真值决定是否输出当前元组；
  4. 外层游标移动到下一个元组，重复上述步骤，直至外层全表扫描完毕。

---

### 3. 带有比较运算符的子查询

当用户通过业务先验逻辑能够**百分之百确信内层子查询只返回单个标量值（Single Value）**时，可以在父查询属性与子查询之间直接使用常规比较运算符（`=, <>, <, <=, >, >=`）。

#### 3.1 经典应用 1：同质实体比对（不相关子查询）
**需求**：查询与“刘晨”在同一个系学习的所有学生学号、姓名与所在系。

```sql
SELECT Sno, Sname, Sdept
FROM Student
WHERE Sdept = (
    -- 内层子查询: 独立查出刘晨所在的系 (假定全校只有一个叫刘晨的学生)
    SELECT Sdept 
    FROM Student 
    WHERE Sname = '刘晨'
);
```

> **致命异常防范（Cardinality Violation）**：
> 若全校重名有两个叫“刘晨”的学生，分别在计算机系和数学系，则内层子查询会返回包含两个元素的集合 `('CS', 'MA')`。
> 此时标量比较运算符 `=` 无法与多元素集合直接比对，系统会抛出严重运行时错误：`Subquery returns more than 1 row`！
> **避坑防线**：若无法完全排除多行可能性，应使用下一讲介绍的 `IN` 谓词替代 `=`。

---

#### 3.2 经典应用 2：超越局部群体平均水平（经典相关子查询）
**需求**：查询选修了某门课程的学生中，**其成绩高于该门课程平均成绩**的学生学号、课程号及其实际得分。

```sql
SELECT Sno, Cno, Grade
FROM SC x                             -- 外层表赋予别名 x
WHERE Grade > (
    -- 内层相关子查询: 必须带入外层当前行的课程号 x.Cno!
    SELECT AVG(Grade)
    FROM SC y                         -- 内层表赋予别名 y
    WHERE y.Cno = x.Cno               -- 关联条件: 计算当前特定课程的平均分
);
```

##### 深度执行推导演练：
1. 引擎取外层 `SC x` 的第 1 行：`(202601, 'C01', 92)`；
2. 将 `x.Cno = 'C01'` 代入内层子查询，计算全校选修 `C01` 的平均分为 `85.0`；
3. 比对外层当前行成绩：$92 > 85.0$ 为真，第 1 行入选结果；
4. 引擎取外层 `SC x` 的第 2 行：`(202601, 'C02', 70)`；
5. 将 `x.Cno = 'C02'` 代入内层，重新计算 `C02` 的平均分为 `78.0`；
6. 比对：$70 > 78.0$ 为假，该行被过滤丢弃；
7. 依次遍历，直至全表完成。

### 4. 随堂巩固自测

## 第 10 章：第3章  关系数据库标准语言SQL（10）
> 对应分集：P25 | 原始标题：《第3章  关系数据库标准语言SQL（10）》

### 1. 核心概念与本质内涵：从单标量比对到集合多值比较

在上一讲中，带有普通比较运算符（`=`、`>` 等）的子查询要求内层必须且只能返回单个标量值。然而，在真实数据库应用中，绝大多数子查询过滤出来的中间结果都是一个**多行值的集合（Multi-valued Set）**。

当外层属性需要与内层返回的这个多值集合进行逻辑关联时，SQL 提供了两类核心谓词：
1. **`IN` / `NOT IN` 谓词**：用于判断某个属性值是否属于（或不属于）子查询返回的值集合；
2. **`ANY`（或 `SOME`）与 `ALL` 谓词**：配合比较运算符使用，用于表达“与集合中某一元素比对满足”或“与集合中全部元素比对均满足”的量词逻辑。

```text
                  多值集合比较谓词的形式化谱系
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
 【集合归属判定: IN 族】                      【集合序关系比较: ANY / ALL】
  • expr IN (Subquery)                        • expr θ ANY (Subquery)
  • expr NOT IN (Subquery)                      (只要集合中存在至少一个值满足即可)
                                              • expr θ ALL (Subquery)
                                                (必须对集合中的每一个值都满足)
```

---

### 2. 带有 IN 谓词的子查询深度应用

#### 2.1 经典多表穿透检索（不相关 IN 子查询）
**业务需求**：查询选修了课程名为“信息系统”的学生学号和姓名。

```sql
SELECT Sno, Sname
FROM Student
WHERE Sno IN (
    -- 第二层子查询: 查询选修了该课的学生学号集合
    SELECT Sno
    FROM SC
    WHERE Cno IN (
        -- 第三层子查询: 查询"信息系统"对应的课程号
        SELECT Cno 
        FROM Course 
        WHERE Cname = '信息系统'
    )
);
```

#### 2.2 子查询与连接查询的等价替换（Query Unnesting）
许多带有 `IN` 谓词的嵌套查询，在逻辑上完全等价于多表 `INNER JOIN` 连接查询：
```sql
-- 等价的连接查询写法
SELECT Student.Sno, Student.Sname
FROM Student
INNER JOIN SC ON Student.Sno = SC.Sno
INNER JOIN Course ON SC.Cno = Course.Cno
WHERE Course.Cname = '信息系统';
```
> **优化器幕后机理**：现代高级 DBMS 的查询优化器在执行时，会自动将满足条件的 `IN` 嵌套子查询**解嵌套（Unnesting）改写为半连接（Semi-Join）或内连接**，以便利用多表连接的哈希关联（Hash Join）或排序合并（Merge Join）算法加速执行。

### 3. 带有 ANY（SOME）或 ALL 谓词的子查询

`ANY` 和 `ALL` 谓词不能单独使用，**必须紧跟在比较运算符之后**（如 `> ANY`, `< ALL`, `= ANY`）。

#### 3.1 ANY 与 ALL 的逻辑真值规约

| 谓词表达式 | 形式化数学语义 | 现实语言直观解释 | 等价聚集函数变换 |
| :--- | :--- | :--- | :--- |
| `> ANY (Subquery)` | $\exists x \in S (v > x)$ | 大于子查询集合中的**某个（至少一个）值** | `> (SELECT MIN(...) ...)` |
| `> ALL (Subquery)` | $\forall x \in S (v > x)$ | 大于子查询集合中的**所有值** | `> (SELECT MAX(...) ...)` |
| `< ANY (Subquery)` | $\exists x \in S (v < x)$ | 小于子查询集合中的**某个（至少一个）值** | `< (SELECT MAX(...) ...)` |
| `< ALL (Subquery)` | $\forall x \in S (v < x)$ | 小于子查询集合中的**所有值** | `< (SELECT MIN(...) ...)` |
| `= ANY (Subquery)` | $\exists x \in S (v = x)$ | 等于集合中的某个值 | **等价于 `IN` 谓词** |
| `<> ALL (Subquery)` | $\forall x \in S (v 
eq x)$ | 不等于集合中的任何一个值 | **等价于 `NOT IN` 谓词** |

---

#### 3.2 经典实战：跨部门极值比对

**需求**：查询非计算机科学系中，比计算机科学系（`CS`）**任意一个（其中某一个）**学生年龄都要小的学生姓名和年龄。

##### 写法 A：使用 `ANY` 谓词
```sql
SELECT Sname, Sage
FROM Student
WHERE Sdept <> 'CS'
  AND Sage < ANY (
      SELECT Sage 
      FROM Student 
      WHERE Sdept = 'CS'
  );
```

##### 写法 B：等价聚集函数转换（推荐工程写法）
> **思维转换**：“比 CS 系任意一个学生的年龄小” $\iff$ “只要比 CS 系中年龄最大的学生小即可”：

```sql
SELECT Sname, Sage
FROM Student
WHERE Sdept <> 'CS'
  AND Sage < (
      SELECT MAX(Sage) 
      FROM Student 
      WHERE Sdept = 'CS'
  );
```

##### 写法对比与工程价值：
- 写法 B 使用 `MAX(Sage)` 聚集函数，语义清晰直观，且内层产出的仅为单行标量，数据库引擎在检索 `MAX` 时若有 B+ 树索引，可直接进行 $O(1)$ 树右侧边缘探针命中，执行性能通常大幅优于 `ANY` 列表比对。

### 1. 核心概念与本质内涵：EXISTS 谓词的布尔存在性检验

在 SQL 嵌套查询中，`EXISTS` 谓词代表数学逻辑中的**存在量词（Existential Quantifier, $\exists$）**。

与此前学过的子查询不同，**`EXISTS` 子查询不返回任何实际的业务数据行或列值，它只产生一个纯粹的布尔逻辑真值——`TRUE` 或 `FALSE`**：
- **`EXISTS (Subquery)`**：若内层子查询的结果集**至少包含一行元组（非空）**，则外层条件评估为 **`TRUE`**；若内层子查询结果为空集，则评估为 **`FALSE`**；
- **`NOT EXISTS (Subquery)`**：逻辑取反。若内层子查询**为空集**，返回 **`TRUE`**；若内层子查询非空，返回 **`FALSE`**。

```text
               EXISTS 谓词的求值机制
                 内层子查询 (Subquery)
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
      [结果集非空 (≥1 行)]       [结果集为空集 (0 行)]
              │                       │
     EXISTS:     TRUE                EXISTS:     FALSE
     NOT EXISTS: FALSE               NOT EXISTS: TRUE
```

> **语法规范提示**：由于 `EXISTS` 只关心“有没有结果行”，完全不关心内层投影了什么字段，因此在内层子查询的目标列表中，**统一规范书写为 `SELECT *` 或 `SELECT 1`**，系统优化器会自动将其视为存在性短路扫描（找到第一条即可立即返回 `TRUE`，无需全量读取）。

---

### 2. 经典单重 EXISTS 与相关子查询应用

**需求**：查询所有选修了 1 号课程（`Cno = '1'`）的学生姓名。

```sql
SELECT Sname
FROM Student S
WHERE EXISTS (
    -- 内层相关子查询: 带着外层当前学生学号 S.Sno 去找选课记录
    SELECT *
    FROM SC
    WHERE SC.Sno = S.Sno AND SC.Cno = '1'
);
```

##### 执行机理解析：
1. 外层遍历 `Student` 表中的每一个学生元组；
2. 将当前学生的 `S.Sno` 代入内层子查询；
3. 内层检查 `SC` 表中是否存在一条选修 `Cno = '1'` 的记录；
4. 若存在，`EXISTS` 返回 `TRUE`，外层输出该学生的 `Sname`；若不存在，返回 `FALSE`，过滤掉该行。

---

### 3. 理论巅峰：利用双重 NOT EXISTS 实现全称量词（$\forall$）

在 SQL 标准中，**并没有提供 `FOR ALL` 这种全称量词关键字**。在关系代数中我们使用除运算（$\div$）求解包含“全部”、“所有”的查询，而在 SQL 中，这一类问题必须通过一阶谓词逻辑中的**反演律（德·摩根定律）**进行变换，最终通过**双重 `NOT EXISTS`** 求解。

#### 3.1 形式化数学等价定理推导

一阶逻辑中的核心等价定理：

$$\forall x P(x) \iff 
eg \exists x (
eg P(x))$$

> **语言语义转译**：  
> **“所有的 $x$ 都满足性质 $P$”**  
> $\iff$ **“不存在任何一个 $x$，它不满足性质 $P$”**！

---

#### 3.2 经典世纪名题：查询选修了全部课程的学生姓名

- **原始自然语言需求**：查询选修了**全部课程**的学生姓名。
- **第一步（谓词逻辑语义转换）**：
  原命题：“选修了所有课程的学生 $S$”  
  $\implies$ 转换为否定形式：“**不存在一门课程 $C$，该学生 $S$ 没有选修过**”。
- **第二步（结构化层级拆解）**：
  1. 外层：学生 $S$；
  2. 中间层：全校所有的课程 $C$；
  3. 最内层：该学生 $S$ 选修了该课程 $C$ 的事实记录。
- **第三步（SQL 标准双重 NOT EXISTS 模板构建）**：

```sql
SELECT Sname
FROM Student S
WHERE NOT EXISTS (
    -- 中间层: 遍历全校所有的课程 C (寻找该学生没选过的课)
    SELECT *
    FROM Course C
    WHERE NOT EXISTS (
        -- 最内层: 寻找学生 S 选修课程 C 的记录
        SELECT *
        FROM SC
        WHERE SC.Sno = S.Sno AND SC.Cno = C.Cno
    )
);
```

```text
               双重 NOT EXISTS 逻辑执行拓扑
[外层 Student S] ────── 取出某个学生 (例如: 张三)
       │
       ▼
[中间层 Course C] ───── 遍历全校课程 (例如: 数据库, 操作系统, 算法)
       │
       ▼
[最内层 SC] ────────── 检查张三是否选了该门课?
       │
       ├── 若最内层找到了记录 ──> 内层 NOT EXISTS 为 FALSE
       └── 若最内层没找到 ────> 内层 NOT EXISTS 为 TRUE (抓到了张三没选的课!)
                                        │
                                        ▼
若中间层抓到哪怕一门没选的课，外层 NOT EXISTS 立即被判定为 FALSE (张三被淘汰出局!)
只有张三把所有课都选了，中间层永远为空集，外层 NOT EXISTS 才为 TRUE，张三成功当选!
```

### 4. 逻辑蕴涵（$p \to q$）的经典双重 NOT EXISTS 求解

**高难度考研真题需求**：查询**至少选修了学生 202601 选修的全部课程**的学生学号。

#### 4.1 数学逻辑蕴涵等价变换
设命题 $p$ 为“课程 $y$ 是学生 202601 选修的课程”，命题 $q$ 为“学生 $x$ 选修了课程 $y$”。  
需求可形式化表达为逻辑蕴涵：$p \to q$。
利用命题逻辑恒等式：

$$p \to q \iff 
eg p \lor q \iff 
eg (p \land 
eg q)$$

> **语言语义转译**：  
> **“不存在这样一门课程 $y$：学生 202601 选修了它（$p$ 为真），而学生 $x$ 却没选修它（$
eg q$ 为真）”**！

#### 4.2 标准 SQL 实现代码：
```sql
SELECT DISTINCT Sno
FROM SC SCX
WHERE NOT EXISTS (
    -- 寻找学生 202601 选修的课程
    SELECT *
    FROM SC SCY
    WHERE SCY.Sno = '202601'
      AND NOT EXISTS (
          -- 检查当前候选学生 SCX 是否也选了这门课
          SELECT *
          FROM SC SCZ
          WHERE SCZ.Sno = SCX.Sno AND SCZ.Cno = SCY.Cno
      )
);
```

## 第 12 章：第3章  关系数据库标准语言SQL（12）
> 对应分集：P27 | 原始标题：《第3章  关系数据库标准语言SQL（12）》

### 1. 核心概念与本质内涵：结果集维度的代数运算

在此前的查询中，多表关联大多是通过 `JOIN` 连接（水平拼接列）或 `WHERE` 嵌套（纵深条件过滤）来实现的。

而在某些复杂业务统计中，我们需要对两个或多个独立 `SELECT` 查询所返回的**中间结果集直接进行集合论层面的代数运算**（垂直合并行）：
- **并操作（UNION）**：将多个查询的结果行合并为一个统一的集合；
- **交操作（INTERSECT）**：提取同时在多个查询结果中出现的公共行；
- **差操作（EXCEPT / MINUS）**：从第一个查询结果中扣除在第二个查询中出现的行；
- **派生表查询（Derived Tables）**：直接在 `FROM` 子句中将一个子查询视作临时内存二维表使用。

```text
                     SQL 结果集层面的集合运算
                                │
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
【并操作: UNION / ALL】        【交操作: INTERSECT】     【差操作: EXCEPT】
 两个查询结果行相加合并         仅保留双方共有的重合行    A 结果集扣除 B 结果集
 • UNION:     自动去重          (完全等价于关系代数 ∩)    (Oracle 中写为 MINUS)
 • UNION ALL: 极速保留重复行
```

---

### 2. 集合查询的核心规约与四大操作符

#### 2.1 集合查询的并相容性硬性约束
参与 `UNION`, `INTERSECT`, `EXCEPT` 运算的各个 `SELECT` 语句，必须满足与关系代数并相容性完全相同的规则：
1. **列数必须完全一致**：每个 `SELECT` 目标列表达式中包含的属性个数必须相同；
2. **对应位置的数据类型必须兼容**：第一个查询的第 $i$ 列与第二个查询的第 $i$ 列，必须属于可相互隐式转换的数据类型或相同域。

#### 2.2 UNION 与 UNION ALL 的性能分水岭

```sql
SELECT ... FROM ...
UNION [ALL]
SELECT ... FROM ...;
```

> **【极度关键的性能分水岭】**：
> 1. **`UNION`**：系统在将两个查询结果拼接后，**会自动启动昂贵的去重排序（Sort-Unique）或哈希去重操作**，将所有分量完全相同的多余行剔除，最终输出纯数学集合；
> 2. **`UNION ALL`**：系统直接将两个查询返回的数据行简单拼装在一起，**绝不做任何去重扫描**。

##### 工程选型最佳实践：
- 若业务场景下已知两个集合不可能产生重复（例如一个查今年在校生，一个查已毕业校友），或者业务逻辑本身就允许重复统计，**必须 100% 选用 `UNION ALL`**！
- 相比 `UNION`，`UNION ALL` 省去了海量数据的内存/磁盘外部排序开销，执行速度往往快数倍乃至数十倍。

---

#### 2.3 交操作（INTERSECT）与差操作（EXCEPT）

```sql
-- 1. 查询计算机科学系中年龄即在 19 岁以下又在 20 岁以上的异常或特定交集群体
SELECT Sno FROM Student WHERE Sdept = 'CS'
INTERSECT
SELECT Sno FROM Student WHERE Sage <= 19;

-- 2. 查询选修了 1 号课程但没有选修 2 号课程的学生学号 (差运算)
SELECT Sno FROM SC WHERE Cno = '1'
EXCEPT
SELECT Sno FROM SC WHERE Cno = '2';
```

#### 2.4 ORDER BY 子句的放置纪律
> **语法铁律**：整个集合查询中，**`ORDER BY` 排序子句只能在最后一个 `SELECT` 语句的末尾出现一次**。
> 它对前面所有集合运算产出的**最终总结果集**统一进行排序呈现，严禁在中间的各个单体子查询中各自添加独立的 `ORDER BY`。

---

### 3. 基于派生表的查询（Derived Table in FROM Clause）

除了在 `WHERE` 条件中使用子查询外，SQL 允许直接在 `FROM` 子句中将一个完整的子查询作为临时基本表来使用，这就是**派生表（Derived Table）**或内联视图（Inline View）。

#### 3.1 核心语法与强制别名规则
> **【编译硬性要求】**：在 `FROM` 子句中放置派生表时，**必须且强制为其显式赋予一个表别名（AS Alias）**！未指定别名会导致数据库解析器报错。

```sql
SELECT 派生表别名.属性1, ...
FROM (
    SELECT ... FROM ... WHERE ...
) AS 派生表别名
WHERE ...;
```

#### 3.2 经典实战：解决聚集结果的二次连接
**需求**：查询选修了 3 门以上课程的学生学号、姓名以及该生所选课程的平均成绩。

```sql
SELECT 
    S.Sno, 
    S.Sname, 
    AvgSc.AvgGrade
FROM Student S
-- 派生表: 先在 SC 表中按学号聚合出选修超 3 门的学生学号与平均成绩
INNER JOIN (
    SELECT Sno, AVG(Grade) AS AvgGrade
    FROM SC
    GROUP BY Sno
    HAVING COUNT(Cno) > 3
) AS AvgSc ON S.Sno = AvgSc.Sno;
```

## 第 13 章：第3章  关系数据库标准语言SQL（13）
> 对应分集：P28 | 原始标题：《第3章  关系数据库标准语言SQL（13）》

### 1. 核心概念与本质内涵：数据操纵语言（DML）的职责

在关系数据库的完整生命周期中，数据不仅需要被高效检索，更需要随着业务运转进行持续的写入、修正与淘汰。

SQL 中的数据更新由**数据操纵语言（Data Manipulation Language, DML）**实现，主要包括三大操作：
1. **插入数据（INSERT）**：向基本表中添加新的数据行；
2. **修改数据（UPDATE）**：对基本表中既有记录的一个或多个属性值进行覆写或计算更新；
3. **删除数据（DELETE）**：从基本表中移除不再需要的陈旧元组。

```text
                        SQL 数据更新 DML 三大操作
                                   │
       ┌───────────────────────────┼───────────────────────────┐
       ▼                           ▼                           ▼
【INSERT: 数据写入】         【UPDATE: 属性修改】        【DELETE: 元组清除】
 • 单行常量插入 (VALUES)      • 批量属性覆写 (SET ... )   • 谓词条件筛选删除 (WHERE)
 • 子查询批量灌入 (SELECT)    • 支持子查询动态计算        • 省略 WHERE 即清空整表
       │                           │                           │
       └───────────────────────────┼───────────────────────────┘
                                   ▼
                【DBMS 底层强制执行三大完整性约束防御】
                (实体主码校验 / 参照外码联动 / CHECK 范围判定)
```

---

### 2. 插入数据（INSERT 语句）

#### 2.1 插入单条元组（INSERT ... VALUES）

```sql
INSERT INTO <表名> [(<属性列1> [, <属性列2>]...)]
VALUES (<常量1> [, <常量2>]...);
```

##### 规则与最佳实践：
1. **显式指明列名列表（推荐规范）**：
   ```sql
   INSERT INTO Student (Sno, Sname, Ssex, Sdept, Sage)
   VALUES ('2026101', '陈晓', '女', 'CS', 19);
   ```
   `INTO` 子句中指定的列名次序可以与建表时的物理列序不一致，只需确保 `VALUES` 中的常量值类型与顺序与之严格一一对应。
2. **省略列名列表的隐式规则**：
   ```sql
   INSERT INTO Student 
   VALUES ('2026102', '赵雷', '男', 20, 'MA');
   ```
   若省略列名列表，**必须且强制按照建表定义时的全量属性物理次序**，提供全部字段的值，极易因后续表结构加列而导致代码失效。
3. **部分列缺省与空值处理**：
   在指定列名时，未列出的字段将自动填充其建表时定义的 `DEFAULT` 默认值；若无默认值且未声明 `NOT NULL`，则系统自动填入 `NULL`。

---

#### 2.2 插入子查询结果（批量数据灌入）

SQL 允许将一个 `SELECT` 查询抽取出来的海量结果集，直接一次性批量插入到目标表中，这在数据清洗、历史归档与数仓聚合中极其普遍：

```sql
-- 1. 创建一张专门存放每个系平均年龄的汇总表
CREATE TABLE Dept_Age (
    Sdept VARCHAR(20) PRIMARY KEY,
    AvgAge NUMERIC(4, 1)
);

-- 2. 通过子查询将统计结果批量灌入该汇总表
INSERT INTO Dept_Age (Sdept, AvgAge)
SELECT Sdept, AVG(Sage)
FROM Student
GROUP BY Sdept;
```

---

### 3. 修改数据（UPDATE 语句）

```sql
UPDATE <表名>
SET <列名> = <表达式> [, <列名> = <表达式>]...
[WHERE <条件>];
```

#### 3.1 核心操作规约
- `SET` 子句指定需要更新的列及其赋予的新值或计算表达式；
- `WHERE` 子句用于限定哪些元组需要被修改。
- **高危警告**：**若省略 `WHERE` 子句，则该表中的所有元组都会被同时修改**！

```sql
-- 1. 单行修改: 将学号为 202601 的学生年龄加 1 岁
UPDATE Student 
SET Sage = Sage + 1 
WHERE Sno = '202601';

-- 2. 批量带子查询修改: 将计算机系所有学生的成绩清零
UPDATE SC 
SET Grade = 0 
WHERE Sno IN (
    SELECT Sno FROM Student WHERE Sdept = 'CS'
);
```

---

### 4. 删除数据（DELETE 语句）

```sql
DELETE FROM <表名>
[WHERE <条件>];
```

#### 4.1 核心规约与辨析
- `DELETE` 语句只删除基本表中的**数据元组（行）**，**表的结构、约束、索引完整保留**；
- 若省略 `WHERE` 子句，则清空表中的所有记录（如 `DELETE FROM SC;`）；
- **与 `TRUNCATE TABLE` 的工程区别**：
  - `DELETE` 是标准 DML，逐行删除并记录完整的事务回滚重做日志（Undo/Redo Log），支持事务回滚（Rollback）；
  - `TRUNCATE` 是 DDL 操作，通过直接释放物理数据页快速清空全表，不可精细过滤，执行极快但无法按行恢复。

---

### 5. DML 过程中的数据库完整性防御体系

在执行任何 `INSERT`, `UPDATE`, `DELETE` 时，DBMS 事务内核会触发一系列自动化的完整性校验钩子（Hook）：

```text
【DML 操作与三大完整性规则检查流向】
 写入/更新/删除请求
         │
         ▼
 1. 实体完整性校验: 主码是否冲突? 主码属性是否被赋了 NULL? 
    (若违约 ──> 立即抛错中断，事务回滚)
         │
         ▼
 2. 参照完整性校验:
    • INSERT/UPDATE: 外码值是否在被参照主表中存在?
    • DELETE 主表: 是否存在外键依赖? 
      (根据级联配置执行: RESTRICT 报错 / CASCADE 连带删除 / SET NULL 置空)
         │
         ▼
 3. 用户定义完整性校验: CHECK 表达式、NOT NULL、UNIQUE 是否全通过?
         │
         ▼
 全部合规 ──> 写入重做日志 ──> 持久化生效
```

## 第 14 章：第3章  关系数据库标准语言SQL（14）
> 对应分集：P29 | 原始标题：《第3章  关系数据库标准语言SQL（14）》

### 1. 核心概念与本质内涵：虚表的定义与外模式落地

在关系数据库三级模式体系中，**视图（View）**是外模式（子模式）在 SQL 标准中最直接、最核心的工程承载机制。

#### 1.1 视图与基本表的本质分野
- **基本表（Base Table）**：是物理磁盘上有真实数据文件落盘、占有实际存储空间的“实表”；
- **视图（View）**：是从一个或几个基本表（或其他视图）导出的**虚拟表（Virtual Table）**：
  - **数据库中只存放视图的定义（保存在数据字典中的一段 `SELECT` 语句文本），而不存放视图对应的数据记录**；
  - 基表中的数据一旦发生插入或修改，通过视图查询到的数据随之自动同步动态展现；
  - 视图就像是一扇“透明的窗口”，用户透过它只能看到数据库中被特定规则圈定的局部数据。

```text
                  视图作为外模式窗口的映射机制
+-----------------------------------------------------------------+
| 基本表空间 (Base Tables: 存储全体物理数据行)                    |
|                                                                 |
|   Student(Sno, Sname, Ssex, Sage, Sdept)                        |
|   SC(Sno, Cno, Grade)                                           |
+-----------------------------------------------------------------+
          ▲                                       ▲
          │                                       │
     【视图定义 1】                           【视图定义 2】
  CREATE VIEW V_CS_Student                 CREATE VIEW V_Honor_Student
  AS SELECT Sno, Sname, Sage               AS SELECT Student.Sname, Grade
  FROM Student WHERE Sdept='CS'            FROM Student ⋈ SC WHERE Grade>=90
          │                                       │
          ▼                                       ▼
+-----------------------+               +-----------------------+
| 计算机系教务员专属窗口|               | 奖学金评审专员专属窗口|
| (不可见其他系学生)    |               | (不可见不及格与隐私信息)
+-----------------------+               +-----------------------+
```

---

### 2. 视图的定义、删除与 WITH CHECK OPTION

#### 2.1 创建视图（CREATE VIEW）

```sql
CREATE VIEW <视图名> [(<列名> [, <列名>]...)]
AS <子查询>
[WITH CHECK OPTION];
```

##### 明确指定视图列名的四种刚性场景：
通常视图的列名默认继承内层子查询的列名，但在以下四种情况下**必须显式定义视图列名列表**：
1. 某个目标列不是单纯的属性，而是**聚集函数或算术表达式**（如 `AVG(Grade)`）；
2. 多表连接中出现了**同名属性列**（如 `Student.Sno` 与 `SC.Sno`）；
3. 试图在视图中为某些列启用更符合特定用户习惯的别名；
4. 需要对真实列名进行脱敏。

---

#### 2.2 WITH CHECK OPTION 的核心防御价值

> **【极度关键的安全机制】**：若在创建视图时追加了 `WITH CHECK OPTION` 子句，则以后通过该视图执行 `INSERT`, `UPDATE`, `DELETE` 时，**DBMS 会强制自动追加视图定义中的子查询条件**！

##### 经典对比案例：
```sql
CREATE VIEW V_CS_Student
AS 
SELECT Sno, Sname, Sage, Sdept
FROM Student
WHERE Sdept = 'CS'
WITH CHECK OPTION;
```
1. **执行修改**：若某用户执行 `UPDATE V_CS_Student SET Sdept = 'MA' WHERE Sno = '202601'`：
   - 试图将该计算机系学生的系别改为数学系；
   - 一旦修改成功，该学生将从 `V_CS_Student` 视图中“神秘消失”，导致该视图的操作者再也看不到自己刚刚改过的数据；
   - **系统响应**：因声明了 `WITH CHECK OPTION`，DBMS 自动检测到新值 `Sdept = 'MA'` 违反了 `WHERE Sdept = 'CS'` 的准入约束，**立即拦截并抛错拒绝更新**！
2. **执行插入**：若试图通过该视图插入一个 `Sdept = 'IS'` 的学生，同样会被直接拦截。

#### 2.3 删除视图（DROP VIEW）
```sql
DROP VIEW <视图名> [CASCADE];
```
删除视图只会从数据字典中注销该视图的 SQL 定义文本，**底层基本表及其业务数据丝毫不受影响**。

---

### 3. 视图消解算法（View Resolution）

当用户像操作普通表一样，对一个视图发起 `SELECT` 查询时，数据库内部是如何执行的？

主流关系数据库采用的是**视图消解（View Resolution）机制**：
- **步骤 1**：从系统数据字典中提取该视图的定义（即建视图时的内层 `SELECT` 语句）；
- **步骤 2**：将用户针对视图编写的外层查询与视图本身的子查询进行**语义合并与条件拼接**；
- **步骤 3**：生成一段直接针对底层物理基本表的等价综合查询语句，交给查询优化器编译执行。

```text
【用户编写的查询】:
SELECT Sno, Sage FROM V_CS_Student WHERE Sage < 20;

           ▼  【DBMS 内部视图消解合并】
【消解后实际执行的 SQL】:
SELECT Sno, Sage FROM Student 
WHERE Sdept = 'CS' AND Sage < 20;
```

---

### 4. 视图的可更新性边界（Updatable Views）

在实际工程中，用户不仅希望通过视图“读”数据，还希望通过视图“写”（`INSERT`, `UPDATE`, `DELETE`）数据。

> **核心冲突**：由于视图是虚表，对视图的修改最终必须转换为对底层基本表的修改。如果视图的数据是由多行聚合而来的，或者缺少原表主键，这种“逆向映射”在数学上将是不可逆的多对一映射，无法确定应该修改底层物理表的哪一行！

#### 4.1 可更新视图（Updatable Views）
- 理论上，只有**行列子集视图（Row-and-column Subset View）**是确定可更新的；
- **特征**：视图仅仅来自**单一物理基本表**，仅仅通过简单的选择（行筛选）与投影（列提取）产生，且**完整包含了原基本表的主码**。

#### 4.2 绝对不可更新的视图类型
若视图定义中包含以下任何语法成分，该视图一律被 DBMS 判定为**只读视图，严禁更新**：
1. 包含聚集函数（`SUM`, `AVG`, `MAX`, `MIN`, `COUNT`）的视图；
2. 包含 `GROUP BY` 分组子句或 `HAVING` 子句的视图；
3. 包含 `DISTINCT` 去重修饰符的视图；
4. 包含 `UNION` 等集合操作符的视图；
5. 由多表复杂连接导出，且缺少关键外码参照约束的混合视图。

---

### 5. 视图在软件工程中的四大核心价值

1. **简化复杂用户查询**：将冗长、烧脑的跨四五张表的外连接与嵌套逻辑固化为视图，终端开发者只需简单 `SELECT * FROM View` 即可使用，大幅降低业务代码编写门槛；
2. **多视角看同一数据（个性化外模式）**：财务部、人事部、市场部可针对同一张底层员工大表，建立各自视角契合的专属视图，各取所需；
3. **提供逻辑独立性支持**：当底层基本表因性能优化拆分为两张子表时，可以通过建立一个同名的视图将两张子表联合起来，既有应用程序保持调用视图，业务代码无需修改；
4. **精细化行级与列级安全防护**：通过在视图中排除敏感薪资、身份证字段（列级防护），并在 `WHERE` 条件中限定部门（行级防护），配合权限管理系统只对用户授予视图访问权，从物理上杜绝数据越权泄露。

### 6. 随堂巩固自测

#### 自测题 1（单项选择题）
在关系数据库中，下列关于视图（View）的描述中，错误的是（ ）
A. 视图是虚表，数据库中只存储其定义文本，不存储其对应的数据行  
B. 所有定义的视图都可以像基本表一样自由地进行 INSERT、UPDATE 和 DELETE 操作  
C. 带有 `WITH CHECK OPTION` 子句的视图，在更新时会自动校验是否满足视图定义的条件表达式  
D. 删除视图不会删除其派生所依据的底层基本表中的数据  

**【答案】**：B  
**【解析】**：包含聚集函数、GROUP BY 分组、DISTINCT 去重等复杂视图在逻辑上不可逆，无法转换为对底层基本表单行记录的唯一修改，属于不可更新视图。故选项 B 错误。

#### 自测题 2（视图设计与安全实战题）
现有学生表 `Student(Sno, Sname, Ssex, Sage, Sdept)` 与选课表 `SC(Sno, Cno, Grade)`。学校现需开发一个面向“计算机系辅导员”的数据查询接口。出于隐私与职责管理考量：
1. 辅导员只能查看计算机系（`Sdept = 'CS'`）的学生；
2. 辅导员可以查看学生的学号、姓名、选修课程号及其实际成绩；
3. 允许辅导员通过该接口修改成绩，但不允许将成绩改为负数或超过 100 分。  
请编写创建该视图的标准 SQL 语句。

**【参考答案】**：
```sql
CREATE VIEW V_CS_Student_Grade (Sno, Sname, Cno, Grade)
AS
SELECT 
    Student.Sno, 
    Student.Sname, 
    SC.Cno, 
    SC.Grade
FROM Student
INNER JOIN SC ON Student.Sno = SC.Sno
WHERE Student.Sdept = 'CS'
  AND SC.Grade BETWEEN 0 AND 100
WITH CHECK OPTION;
```
*(注：通过 INNER JOIN 整合两表，通过 WHERE 限定计算机系与合规成绩区间，并使用 WITH CHECK OPTION 确保任何后续修改均无法越过设定的安全与数值边界)*。
