## 第 1 章：第5章  数据库完整性（1）
> 对应分集：P36 | 原始标题：《第5章  数据库完整性（1）》

### 1. 核心概念与本质内涵：完整性控制是数据质量的守护神

在关系数据库系统中，数据的有效性与真实性取决于**数据库完整性（Database Integrity）**。
- 完整性保证数据符合客观世界业务规律的逻辑正确性（例如成绩不能是负数、学生的选课必须绑定有效的在籍学号）；
- 关系模型将完整性内建于系统内核之中，由 DBMS 的完整性子系统负责统一自动化检查，从而将应用程序员从编写海量、繁琐的防御性校验代码中彻底解放出来。

```text
                  关系数据库完整性控制核心体系
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
【实体完整性 (Entity Integrity)】              【参照完整性 (Referential Integrity)】
 • 主码唯一且绝对非空                          • 外码表间参照链路维护
 • DBMS 自动构建 B+ 树唯一索引                 • 违约处理动作:
 • 毫秒级防重冲突拦截                            NO ACTION (报错拒绝)
                                                 CASCADE   (级联更新/删除)
                                                 SET NULL  (自动置空)
```

---

### 2. 实体完整性的底层实现与检验机制

#### 2.1 形式化声明与语法规范

实体完整性通过 `PRIMARY KEY`（主码）短语进行显式形式化定义：
- **单属性主码**：可以在列定义处声明为**列级约束**，也可以在表末尾声明为**表级约束**；
- **复合主码（由两个或更多属性联合构成）**：**必须且只能在表末尾声明为表级约束**。

```sql
-- 1. 单列主码 (列级约束)
CREATE TABLE Student (
    Sno CHAR(9) PRIMARY KEY,
    Sname VARCHAR(20) NOT NULL
);

-- 2. 复合主码 (表级约束)
CREATE TABLE SC (
    Sno CHAR(9) NOT NULL,
    Cno CHAR(4) NOT NULL,
    Grade SMALLINT,
    PRIMARY KEY (Sno, Cno) -- 复合主码必须在表级声明
);
```

#### 2.2 DBMS 内核对实体完整性的检查机理

当用户向表中发起 `INSERT` 或对主码列执行 `UPDATE` 时，DBMS 事务层按以下两步严格执行判定：

```text
               实体完整性自动检查流向
新数据行写入 / 修改主码属性
         │
         ▼
[第 1 步: 非空检查 (NOT NULL Check)]
 扫描主码各分量是否存在 NULL
 ├── 存在 NULL ──> 立即报错拒绝，抛出实体完整性违约异常
 ▼ 全部非空
[第 2 步: 唯一性二分快速比对 (Uniqueness Check)]
 借助底层自动创建的 B+ 树主键索引快速探针寻道
 ├── 索引中已存在相同键值 ──> 立即报错拒绝，拦截主键冲突
 ▼ 无冲突
允许数据页写入落盘
```

> **底层性能机制**：为了防止每一次插入数据都去进行全表遍历扫重，**主流关系数据库会在定义 `PRIMARY KEY` 的同时，自动在底层为该主码列（或属性组）构建一个唯一的 B+ 树索引**。通过 B+ 树的对数级二分查找，使得主键唯一性校验的耗时被严格锁定在几微秒以内。

---

### 3. 参照完整性的实现与违约联动策略（Referential Action）

参照完整性将不同基本表之间的实体关联通过外码（`FOREIGN KEY`）严格绑定。

#### 3.1 违约动作的四大策略

当发生对被参照表（主表）的删除或修改，或者对参照表（从表）的新增或修改时，极易破坏两表之间的关联一致性。SQL 标准允许在定义外码时，显式指定四大违约处理策略：

| 违约动作策略 | 关键字语法 | 核心行为与业务语义 |
| :--- | :--- | :--- |
| **拒绝执行（默认）** | `ON DELETE NO ACTION` / `RESTRICT` | 只要从表中有任何一条外码记录引用了主表当前行，**严禁主表行被删除或修改**，系统抛错中断事务 |
| **级联联动** | `ON DELETE CASCADE` / `ON UPDATE CASCADE` | 主表记录被删除或主键修改时，**自动连带将从表中所有引用该主键的行同步删除或修改** |
| **自动置空** | `ON DELETE SET NULL` / `ON UPDATE SET NULL` | 主表记录被删除或修改时，**自动将从表中所有引用该行的外码列值更新为 NULL**（前提是该外码列允许为空） |
| **设为默认值** | `ON DELETE SET DEFAULT` | 主表行删除时，从表外码自动回退填充为其预设的默认值 |

---

#### 3.2 经典三表外码级联联动生产实战

```sql
CREATE TABLE SC (
    Sno CHAR(9) NOT NULL,
    Cno CHAR(4) NOT NULL,
    Grade SMALLINT CHECK (Grade >= 0 AND Grade <= 100),
    PRIMARY KEY (Sno, Cno),
    
    -- 外码 1: 绑定 Student 表，配置级联策略
    CONSTRAINT FK_SC_Student 
        FOREIGN KEY (Sno) REFERENCES Student(Sno)
        ON DELETE CASCADE       -- 现实语义: 学生退学注销档案时，其所有选课记录自动被级联抹除
        ON UPDATE CASCADE,      -- 现实语义: 学生学号因升学规则变更时，其选课表中的学号同步联动
        
    -- 外码 2: 绑定 Course 表，配置拒绝限制策略
    CONSTRAINT FK_SC_Course 
        FOREIGN KEY (Cno) REFERENCES Course(Cno)
        ON DELETE RESTRICT      -- 现实语义: 只要尚有任何学生选修了这门课，该课程绝不允许被教学办擅自删除!
        ON UPDATE CASCADE
);
```

### 4. 典型例题与深度认知辨析

#### 辨析 1：外码可以取空值，那什么时候绝对不能取空值？

- **深度判定**：
  - 一般情况下，外码若未声明 `NOT NULL`，允许取 `NULL`（代表暂时未分配关联，如新员工未分配部门）；
  - 但如果**外码属性同时是本表主码的组成部分**（如选课表 `SC(Sno, Cno)` 中的 `Sno` 和 `Cno`），根据**实体完整性必须非空的最高铁律**，此时它们绝对不能取空值！

### 5. 随堂巩固自测

#### 自测题 1（单项选择题）
在关系数据库中，定义外码约束时声明了子句：`ON DELETE CASCADE`。若从被参照主表中删除了主键为 `'1001'` 的一条记录，则数据库系统将（ ）
A. 报错并拒绝删除主表记录  
B. 删除主表记录，并将从表中所有外码为 `'1001'` 的记录自动同步删除  
C. 删除主表记录，并将从表中所有外码为 `'1001'` 的字段修改为 NULL  
D. 只删除从表记录，保留主表记录  

**【答案】**：B  
**【解析】**：`CASCADE`（级联）选项表示当主表中的父记录被删除时，系统自动将所有依赖它的子从表记录一并级联删除，以维持参照完整性。故选 B。

#### 自测题 2（SQL DDL 设计题）
设有两张表：部门表 `Dept(DeptID, DeptName)`，员工表 `Emp(EmpID, EmpName, DeptID)`。
请为员工表编写建表语句，要求：
1. `EmpID` 为主码；
2. `DeptID` 为外码，参照 `Dept` 表的 `DeptID`；
3. 当部门被删除时，该部门的所有员工的 `DeptID` 自动置为 `NULL`（不删除员工）；
4. 当部门编号发生变更时，员工表中的 `DeptID` 自动同步联动修改。

**【参考答案】**：
```sql
CREATE TABLE Emp (
    EmpID INT PRIMARY KEY,
    EmpName VARCHAR(30) NOT NULL,
    DeptID INT,
    CONSTRAINT FK_Emp_Dept 
        FOREIGN KEY (DeptID) REFERENCES Dept(DeptID)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);
```

## 第 2 章：第5章  数据库完整性（2）
> 对应分集：P37 | 原始标题：《第5章  数据库完整性（2）》

### 1. 核心概念与本质内涵：什么是用户定义的完整性？

实体完整性捍卫了主键的可识别性，参照完整性保障了表间关联的有效性。然而，客观商业世界中绝大多数业务规则要比“主外键”具体得多：
- “员工的基本月薪不能低于城市法定最低工资 2200 元”；
- “信用卡的有效期必须晚于发卡日期”；
- “学生的性别只能在‘男’与‘女’中二选一”。

这些直接体现特定业务领域规则、语义契约与法律条文的约束，在数据库理论中被归类为**用户定义的完整性（User-defined Integrity）**。SQL 提供了强大的属性级与元组级约束体系，由 DBMS 在数据存入时强制执行严密门禁。

```text
                  用户定义完整性的层级控制体系
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
【属性级约束 (Column-level)】                  【元组级约束 (Tuple-level)】
 • 作用对象: 某一个具体单列                    • 作用对象: 整行元组，涉及多个列
 • NOT NULL (非空)                             • 跨列逻辑关系比对 (如 开始时间 ≤ 结束时间)
 • UNIQUE (列值唯一，允许NULL)                 • 跨列复合业务判定 (必须声明在表级)
 • CHECK (范围、枚举、格式正则)
```

---

### 2. 属性级与元组级完整性约束详解

#### 2.1 属性级约束条件（Column-level Constraints）

属性级约束直接定义在某个列的数据类型定义之后：
1. **非空约束（`NOT NULL`）**：
   - 强制该列在任何元组中都必须有明确赋值，严禁录入 `NULL`。
2. **唯一性约束（`UNIQUE`）**：
   - 限制该属性的所有非空值互不相同。
   - **与 `PRIMARY KEY` 的核心区别**：
     - 一个表只能有一个主键，但可以有**多个 `UNIQUE` 列**；
     - 主键绝对不允许为 NULL，但 **`UNIQUE` 约束通常允许包含空值（NULL）**，且在大多数数据库中，多个元组的 `UNIQUE` 列都可以是 NULL（因为根据三值逻辑，NULL 与 NULL 不相等，互不冲突）。
3. **检查约束（`CHECK`）**：
   - 使用布尔表达式限制该列的合法取值范围：
     ```sql
     -- 范围限制
     Sage SMALLINT CHECK (Sage >= 15 AND Sage <= 45),
     -- 枚举限制
     Ssex CHAR(2) CHECK (Ssex IN ('男', '女')),
     -- 格式模式限制
     ZipCode CHAR(6) CHECK (ZipCode LIKE '[0-9][0-9][0-9][0-9][0-9][0-9]')
     ```

---

#### 2.2 元组级约束条件（Tuple-level Constraints）

当一个完整性业务规则**涉及同一张表中的多个属性列之间的逻辑关系**时，属性级约束无法满足要求，必须在建表语句的末尾声明为**表级约束（元组级约束）**：

```sql
CREATE TABLE Project (
    ProjID CHAR(10) PRIMARY KEY,
    ProjName VARCHAR(50) NOT NULL,
    StartDate DATE NOT NULL,
    EndDate DATE NOT NULL,
    Budget NUMERIC(12, 2) CHECK (Budget > 0),
    
    -- 元组级约束: 跨两列的时间先后逻辑校验
    CHECK (StartDate <= EndDate)
);
```

##### 典型案例 2：性别与尊称的跨列业务一致性
```sql
CREATE TABLE VIP_Member (
    MID CHAR(10) PRIMARY KEY,
    Mname VARCHAR(30) NOT NULL,
    Msex CHAR(2) CHECK (Msex IN ('男', '女')),
    Title VARCHAR(10),
    
    -- 元组级约束: 女性可以称 Ms.，但如果性别为男，尊称严禁写为 Ms.
    CHECK (Msex = '女' OR Title NOT IN ('Ms.', 'Mrs.'))
);
```

### 3. 完整性约束命名子句（CONSTRAINT）与动态治理

在实际企业级系统开发中，**严禁写匿名的完整性约束**！必须为每一个约束赋予全局唯一的语义化名称。

```sql
CONSTRAINT <约束名> <约束条件>
```

#### 3.1 为什么必须显式命名约束？
1. **报错定位精确**：若不命名，当用户插入违约数据时，系统抛出类似 `Error: CHECK constraint SYS_C0038192 violated`，排查人员完全不知道是哪一列违反了什么规则；若命名为 `C_Student_Age_Range`，发生报错时一目了然；
2. **支持动态维护与修改**：当未来业务规则调整需要废弃或修改某条约束时，只有具备名称的约束才能通过 `ALTER TABLE` 被精准删除。

---

#### 3.2 动态修改与维护约束（ALTER TABLE）

```sql
-- 1. 创建学生表并规范化显式命名每一个约束
CREATE TABLE Student (
    Sno CHAR(9),
    Sname VARCHAR(20) NOT NULL,
    Ssex CHAR(2),
    Sage SMALLINT,
    Sdept VARCHAR(20),
    
    CONSTRAINT PK_Student PRIMARY KEY (Sno),
    CONSTRAINT C_Student_Sex CHECK (Ssex IN ('男', '女')),
    CONSTRAINT C_Student_Age CHECK (Sage BETWEEN 15 AND 35)
);

-- 2. 业务变更: 国家放宽入学年龄，删除原有的年龄约束
ALTER TABLE Student 
    DROP CONSTRAINT C_Student_Age;

-- 3. 重新追加新的年龄范围约束
ALTER TABLE Student 
    ADD CONSTRAINT C_Student_Age_New CHECK (Sage BETWEEN 15 AND 60);
```

### 4. 随堂巩固自测

#### 自测题 1（单项选择题）
在关系表中为某个属性定义了 `UNIQUE` 唯一性约束，关于该属性中空值（NULL）的存取行为，说法正确的是（ ）
A. 该属性完全不允许录入任何 NULL 值  
B. 该属性只能允许最多一条记录取 NULL 值，后续再录入 NULL 会触发唯一性冲突  
C. 在标准 SQL 规范中，该属性允许多条记录同时取 NULL 值，因为 NULL 代表未知，两两互不冲突  
D. 必须同时配合 PRIMARY KEY 才能处理 NULL  

**【答案】**：C  
**【解析】**：标准 SQL 中，`UNIQUE` 约束仅限制非空值必须互异。在关系理论的三值逻辑下，`NULL = NULL` 的计算结果是 UNKNOWN，并不被判定为相等，因此多个元组在此列取 NULL 并不破坏唯一性。故选 C。

现需施加两项业务完整性约束：
1. 借款金额（`Amount`）必须严格大于 0，约束命名为 `CK_Contract_Amount`；
2. 还款金额必须大于等于借款金额（`RepayAmount >= Amount`），约束命名为 `CK_Contract_Repay`。  
请写出为该表定义上述约束的 SQL DDL 代码片段。

```sql

    Borrower VARCHAR(50) NOT NULL,

    RepayAmount NUMERIC(12, 2) NOT NULL,

```

## 第 3 章：第5章  数据库完整性（3）
> 对应分集：P38 | 原始标题：《第5章  数据库完整性（3）》

### 1. 核心概念与本质内涵：跨表复杂业务规则的实现困境

前文介绍的列级与元组级 `CHECK` 约束，其作用边界严格局限在**单张基本表内部**。
然而在实际大型信息系统中，海量的业务完整性规则是**跨越多张表的全局动态强约束**：
- “全校任何一名教授所主持的科研项目经费总和，不得超过该教授所在院系年度总预算的 $20\%$”；
- “每一门专业选修课的选修人数上限为 60 人，达到 60 人后系统必须自动封顶拒绝新选课”；
- “员工的薪资一旦录入，后续调整只能上调、绝不允许单向调低”。

为了解决涉及跨表聚合与过程化复杂逻辑的完整性控制，数据库理论与 SQL 标准引入了**断言（Assertion）机制**与**触发器（Trigger）机制**。

```text
               数据库高级完整性控制双引擎
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
【断言机制 (Assertion)】                        【触发器机制 (Trigger)】
 • 声明性跨表全局约束                           • 过程化、事件驱动的业务规则 (ECA)
 • 任何表变动自动触发全量验证                   • 事件 (Event) + 条件 (Condition) + 动作 (Action)
 • 理论优雅但系统全局开销巨大                   • 行级 (FOR EACH ROW: :OLD/:NEW) vs 语句级
```

---

### 2. 断言机制（Assertion）的形式化规约

#### 2.1 创建断言（CREATE ASSERTION）

```sql
CREATE ASSERTION <断言名> CHECK (<谓词表达式>);
```

- **执行机理**：断言创建后，系统视其为全库级别的常态监控规则。**只要数据库中涉及该断言所依托的任何基本表发生修改（增删改），DBMS 必须自动重新评估该断言**；
- 若某次操作导致断言的谓词评估结果为 `FALSE`，该操作被立即强制拒绝并全部回滚。

#### 2.2 经典断言实战
**需求**：限制每一门课程最多只能被 60 名学生选修。

```sql
CREATE ASSERTION Asse_Max_Students
CHECK (
    60 >= ALL (
        SELECT COUNT(Sno) 
        FROM SC 
        GROUP BY Cno
    )
);
```

#### 2.3 断言的工业界困境与删除
```sql
DROP ASSERTION <断言名>;
```
> **工程现实说明**：由于断言要求在全库任意相关表发生任何细微变动时，都必须重新执行复杂的跨表聚合查询，会给高并发事务带来灾难性的性能开销。因此，主流商业关系数据库（如 Oracle, MySQL）通常选择不直接支持声明式断言，而是将这类跨表复杂约束全面交由**触发器（Trigger）**灵活实现。

---

### 3. 触发器机制（Trigger）与 ECA 核心规则

触发器是用户定义在基本表上的一类由**事件驱动的特殊交互式存储过程**。它不需要应用程序手动调用（如 `CALL`），而是在特定的数据库写操作发生时，由 DBMS 引擎自动隐式“触发”执行。

#### 3.1 触发器的 ECA 规则（Event-Condition-Action）
- **事件（Event）**：究竟在发生什么底层写操作时唤醒触发器？包括 `INSERT`, `UPDATE`, `DELETE`；
- **条件（Condition）**：唤醒后是否必须无脑执行？通过 `WHEN <条件>` 进行二次评估，只有条件为真时才激活动作；
- **动作（Action）**：具体执行什么业务逻辑？通常是一个由 `BEGIN ... END` 包裹的过程化 SQL 代码块。

---

#### 3.2 触发器的两大核心分类维度

```text
                     触发器的正交分类矩阵
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
【触发时机维度】                                【触发执行粒度】
 • BEFORE (前置触发):                            • 行级触发器 (FOR EACH ROW):
   在数据落盘前执行，专门用于拦截、校验与篡改修正  SQL 影响了 N 行，触发器就循环执行 N 次!
 • AFTER (后置触发):                             提供了 :OLD 与 :NEW 伪行变量访问新旧值
   在数据成功写入后执行，专门用于连带级联更新    • 语句级触发器 (FOR EACH STATEMENT):
                                                   整条 SQL 无论影响多少行，仅执行 1 次!
```

---

#### 3.3 行级触发器的伪行引用（OLD 与 NEW）

在行级触发器（`FOR EACH ROW`）中，系统提供了两个极其强大的伪行变量：
- **`:OLD`**：代表该行元组在被修改或被删除**之前的原始旧值快照**；
- **`:NEW`**：代表该行元组正准备被插入或修改**之后的新目标值**。

| 操作类型 | `:OLD` 的可用性 | `:NEW` 的可用性 | 核心典型用途 |
| :--- | :--- | :--- | :--- |
| `INSERT` | **不可用（为 NULL）** | **可用**（即准备写入的新行） | 检查新录入字段是否合规、补充默认计算字段 |
| `UPDATE` | **可用**（修改前的老值） | **可用**（修改后的新值） | 比较新旧属性变化幅度（如防降薪、防跳变） |
| `DELETE` | **可用**（被删行的全量数据） | **不可用（为 NULL）** | 归档已删除历史记录到审计备份表 |

### 4. 经典触发器开发生产实战

#### 案例 1：业务合规防降薪与变动审计（BEFORE 行级触发器）
**业务规则**：在员工表 `Employee(EmpID, EmpName, Salary)` 中，任何员工的调薪操作，调整后的工资必须大于调整前的工资（只能涨不能降），否则抛出自定义错误中断事务。

```sql
CREATE OR REPLACE TRIGGER Tri_Salary_Check
BEFORE UPDATE OF Salary ON Employee   -- 仅在修改 Salary 列之前触发
FOR EACH ROW                          -- 行级触发器
WHEN (NEW.Salary < OLD.Salary)        -- 触发条件: 新工资小于旧工资
BEGIN
    -- 抛出异常中断事务
    RAISE_APPLICATION_ERROR(-20001, '业务违规: 员工薪资调整只能上调，严禁下调!');
END;
```

---

#### 案例 2：跨表自动级联统计（AFTER 行级触发器）
**业务规则**：课程表中有 `StudentCount` 字段记录当前选课人数。当选课表 `SC` 成功插入一条新选课记录时，对应课程的选课人数自动加 1；当退选删除记录时，对应人数自动减 1。

```sql
CREATE OR REPLACE TRIGGER Tri_Update_StudentCount
AFTER INSERT OR DELETE ON SC
FOR EACH ROW
BEGIN
    IF INSERTING THEN
        UPDATE Course 
        SET StudentCount = StudentCount + 1 
        WHERE Cno = :NEW.Cno;
    ELSIF DELETING THEN
        UPDATE Course 
        SET StudentCount = StudentCount - 1 
        WHERE Cno = :OLD.Cno;
    END IF;
END;
```

### 6. 随堂巩固自测

#### 自测题 1（单项选择题）
在关系数据库管理系统中，当执行如下触发器创建语句时：
```sql
CREATE TRIGGER Tri_Audit AFTER INSERT ON Orders FOR EACH ROW ...
```
该触发器属于（ ）
A. 前置语句级触发器  
B. 后置行级触发器，每次批量插入 N 条订单时，触发器动作将执行 N 次  
C. 后置语句级触发器，每次批量插入 N 条订单时，触发器动作只执行 1 次  
D. 声明性全局断言  

**【答案】**：B  
**【解析】**：语句中包含关键字 `AFTER`（后置触发）与 `FOR EACH ROW`（行级触发）。行级触发器对受 SQL 影响的每一行元组都会触发执行一次动作。因此批量插入 N 条时，将循环执行 N 次动作。故选 B。

#### 自测题 2（触发器实战设计题）
设有商品表 `Goods(GID, Gname, Stock)`（商品编号、名称、库存量）与订单明细表 `OrderDetail(OrderID, GID, Quantity)`（订单号、商品编号、购买数量）。
请编写一个数据库触发器，满足如下要求：
“当用户向 `OrderDetail` 插入一条购买记录时，自动检查 `Goods` 表中对应商品的库存量是否足够：
- 若库存不足（`Stock < Quantity`），则阻止该订单插入并报错；
- 若库存充足，则自动在 `Goods` 表中将对应商品的库存量扣减掉本次购买数量”。

**【参考答案】**：
```sql
CREATE OR REPLACE TRIGGER Tri_Deduct_Stock
BEFORE INSERT ON OrderDetail
FOR EACH ROW
DECLARE
    v_CurrentStock INT;
BEGIN
    -- 1. 查询当前商品的实际库存
    SELECT Stock INTO v_CurrentStock
    FROM Goods
    WHERE GID = :NEW.GID;
    
    -- 2. 判定库存充裕性
    IF v_CurrentStock < :NEW.Quantity THEN
        RAISE_APPLICATION_ERROR(-20002, '库存不足，无法完成下单支付!');
    ELSE
        -- 3. 库存充足，直接扣减
        UPDATE Goods
        SET Stock = Stock - :NEW.Quantity
        WHERE GID = :NEW.GID;
    END IF;
END;
```
