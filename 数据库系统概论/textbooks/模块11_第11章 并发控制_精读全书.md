## 第 1 章：第11章 并发控制（1）
> 对应分集：P70 | 原始标题：《第11章 并发控制（1）》

### 1. 核心概念与本质内涵：为什么多用户系统必须进行并发控制？

在单用户环境中，事务是严格按时间顺序排队、串行（Serial）执行的，一个事务彻底完成后，下一个事务才启动。此时数据的完整性与一致性易于维护。

但在现代高性能企业级数据库中，通常有成千上万个并发客户端在同一时刻向数据库发起事务请求：
- **多事务并发执行（Concurrency）**能够极大地提升系统 CPU 和磁盘 I/O 的利用率，成倍缩短事务的排队等待时间；
- 但是，**如果对并发操作不加任何隔离与协调控制，并发事务交叉存取同一数据项时，将引发严重的“数据不一致性（Data Inconsistency）”灾难**！

负责对多事务并发访问进行正确性调度、防止数据不一致的子系统，就是 DBMS 的**并发控制子系统（Concurrency Control Subsystem）**。

---

### 2. 并发操作带来的三大经典数据不一致性异常

如果不施加任何封锁保护，并发事务的交错执行必然导致以下三种经典破坏异常：

```text
               三大并发数据不一致性异常谱系
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
【1. 丢失修改 (Lost Update)】                   【2. 读"脏"数据 (Dirty Read)】
 事务 T1 的更新被并发事务 T2 强制覆写抹除        事务 T1 读取了事务 T2 尚未提交的数据，
 (造成 T1 的修改凭空蒸发，数据永久丢失!)        随后 T2 回滚，T1 手中拿着一堆幽灵假数据!
                                                       │
                               ┌───────────────────────┘
                               ▼
                 【3. 不可重复读 (Non-repeatable Read)】
                  事务 T1 读取某数据后，并发事务 T2 进行了修改/删除/插入，
                  导致 T1 再次读取同一范围时，数据发生了诡异变动或行数漂移!
```

---

#### 2.1 异常 1：丢失修改（Lost Update）

- **现象定义**：两个事务 $T_1$ 和 $T_2$ 读入同一数据并修改，$T_2$ 提交的结果无情地覆盖了 $T_1$ 提交的结果，导致 $T_1$ 的修改全部丢失。
- **经典飞机订票场景推导演练**：
  设某趟航班目前机票余额 $A = 16$ 张：

```text
时序轴   事务 T1 (购票 1 张)              事务 T2 (购票 1 张)              数据库中 A 实际值
─────────────────────────────────────────────────────────────────────────────────
t1      读入 A (得到 A=16)                                                A = 16
t2                                      读入 A (得到 A=16)                A = 16
t3      计算 A = A - 1 (为 15)                                            A = 16
t4      写回 A = 15                                                       A = 15
t5                                      计算 A = A - 1 (为 15)            A = 15
t6                                      写回 A = 15 (覆盖了 T1 的写入!)    A = 15
─────────────────────────────────────────────────────────────────────────────────
```
- **毁灭性结果**：两位旅客明明各自购买了 1 张机票（共卖出 2 张票），但数据库中机票余量却只扣减了 1 张！**$T_1$ 的扣减被 $T_2$ 彻底冲刷抹杀，产生了丢失修改**！

---

#### 2.2 异常 2：读“脏”数据（Dirty Read）

- **现象定义**：事务 $T_1$ 修改了某一数据并将其写入磁盘，事务 $T_2$ 随后读取了该数据；紧接着，$T_1$ 因发生异常被迫执行 `ROLLBACK` 撤销回滚；此时 **$T_2$ 读到的数据就变成了客观上从未真实合法存在过的“脏数据（Dirty Data）”**。

```text
时序轴   事务 T1                          事务 T2                          数据库中 C 实际值
─────────────────────────────────────────────────────────────────────────────────
t1      将 C 从 100 修改为 200 并写盘                                     C = 200 (脏值)
t2                                      读取 C (得到 C=200 并用于核心计算) C = 200
t3      T1 发生异常，执行 ROLLBACK!                                       C = 100 (恢复原状)
─────────────────────────────────────────────────────────────────────────────────
```
- **业务后果**：事务 $T_2$ 拿着幽灵值 `200` 去执行了后续的财务支付与决策计算，导致后续全链条业务全面崩溃。

---

#### 2.3 异常 3：不可重复读（Non-repeatable Read）

- **现象定义**：事务 $T_1$ 读取数据后，事务 $T_2$ 执行了更新操作，使 $T_1$ 在同一个事务周期内无法再现前一次读取到的数据结果。
- **三种具体表现形态**：
  1. **虚假修改（Value Drift）**：$T_1$ 读取某行 $A = 50$ 后，$T_2$ 将其修改为 $A = 100$ 并提交；$T_1$ 再次读取时发现同一行数据变成了 $100$（前后不一致）；
  2. **虚假删除（Row Missing）**：$T_1$ 按条件读取出某组元组，$T_2$ 删除了其中的部分元组；$T_1$ 再次读取时发现原本存在的数据离奇消失；
  3. **幻读（Phantom Read / 幻影现象）**：$T_1$ 按条件扫描出 10 条记录，$T_2$ 插入了 3 条满足该条件的新元组；$T_1$ 再次扫描时发现记录凭空多出了 3 条（如同见鬼一般的幻影数据）。

---

### 3. 随堂巩固自测

#### 自测题 1（单项选择题）
在数据库并发操作中，若事务 $T_1$ 读取了事务 $T_2$ 更新后但尚未提交的数据，随后 $T_2$ 因故障发生回滚，导致 $T_1$ 读到了不存在的无效数据，这种并发不一致性现象被称为（ ）
A. 丢失修改  
B. 读“脏”数据  
C. 不可重复读  
D. 活锁  

**【答案】**：B  
**【解析】**：读脏数据（Dirty Read）的本质特征是读取了并发事务未提交的中间暂态数据，随后该事务发生回滚撤销。故选 B。

---

#### 自测题 2（概念分析推导题）
请详细推导说明：在电商秒杀大促场景中，如果系统没有做并发控制，多个用户同时并发下单抢购某一件限量商品（库存为 1），可能会发生哪类并发不一致性异常？并说明由此带来的商业恶果。

**【参考答案与解析】**：
1. **发生的并发异常**：将发生典型的**丢失修改（Lost Update）**异常；
2. **推导过程**：
   - 用户 A 和用户 B 的下单事务同时并发读取库存，均读到 `Stock = 1`；
   - 两个事务分别在内存中执行减 1 操作（各自算得 `1 - 1 = 0`）；
   - 用户 A 的事务先写回 `Stock = 0` 并提交；
   - 用户 B 的事务紧接着也写回 `Stock = 0` 并提交（后提交的写操作覆盖并掩盖了前一个事务的写操作）；
3. **商业恶果**：系统判定两位用户均下单成功并完成了扣款，但实际上库存只有 1 件商品，导致系统严重**超卖（Overselling）**，企业面临违约赔偿与声誉危机。

## 第 2 章：第11章 并发控制（2）
> 对应分集：P71 | 原始标题：《第11章 并发控制（2）》

### 1. 核心概念与本质内涵：什么是封锁（Locking）？

为了彻底根除上一讲中由于并发交叉存取所引发的三大数据不一致性灾难（丢失修改、读脏数据、不可重复读），关系数据库系统最核心、最成熟的经典控制武器就是——**封锁（Locking）机制**。

#### 1.1 封锁的基本运行模式
- **事前申请，获得准入**：事务在对某个数据对象（表、数据页或单行元组）执行读、写操作之前，必须首先向 DBMS 的**锁管理器（Lock Manager）**提出加锁申请；
- **排他独占或并发共享**：锁管理器根据该数据对象当前是否已经被其他事务锁定，决定是立即批准加锁，还是令当前事务进入**阻塞挂起等待（Blocked / Waiting）状态**；
- **事后释放**：加锁的事务在完成既定操作或事务结束（`COMMIT` / `ROLLBACK`）时释放锁。在锁释放之前，其他并发事务受封锁规则的严格制约。

---

### 2. 两大基本封锁类型：X 锁（排他锁）与 S 锁（共享锁）

DBMS 在底层形式化定义了两种功能特异的基础锁模式：

```text
                     两大基础封锁类型体系
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
【排他锁 (Exclusive Lock, 简记 X 锁)】          【共享锁 (Share Lock, 简记 S 锁)】
 又称: 写锁 (Write Lock)                         又称: 读锁 (Read Lock)
 • 针对数据修改操作 (INSERT/UPDATE/DELETE)       • 针对数据只读查询操作 (SELECT)
 • 霸道独占: 一旦被加锁，其他事务既不能加 X 锁， • 宽容共享: 允许多个并发事务同时加 S 锁
   也不能加 S 锁! (排斥一切他人加锁请求!)          • 但严禁任何事务加 X 锁! (防范并发篡改)
```

---

#### 2.1 排他锁（X 锁 / 写锁）的形式化规约
- **加锁规则**：若事务 $T$ 对数据对象 $A$ 成功加上了排他锁（记作 $XLock(A)$）：
  1. 事务 $T$ 可以**既读又写（Read & Write）**数据对象 $A$；
  2. **系统严禁其他任何事务再对数据 $A$ 加上任何类型的锁**（无论是 X 锁还是 S 锁均被立即拦截挂起）；
  3. 直到事务 $T$ 正式释放了 $A$ 上的 X 锁为止。
- **核心保障**：排他锁保证了在数据被修改期间，**没有任何其他事务能够读取该数据的中间未提交暂态，更没有任何事务能同时插手修改该数据**。

---

#### 2.2 共享锁（S 锁 / 读锁）的形式化规约
- **加锁规则**：若事务 $T$ 对数据对象 $A$ 成功加上了共享锁（记作 $SLock(A)$）：
  1. 事务 $T$ 可以**读取（Read Only）**数据对象 $A$，但**绝对不能修改 $A$**；
  2. **其他事务可以同时对数据对象 $A$ 叠加申请并加上 S 锁**；
  3. 但是，**系统绝对不允许任何事务对 $A$ 加上 X 锁**，直到 $A$ 上的所有并发 S 锁全部被释放为止。
- **核心保障**：共享锁保证了在多个用户同时进行并发读取时，系统能维持高并发吞吐；同时强行杜绝了任何“写事务”在他人正在读取的关头插入篡改数据。

---

### 3. 封锁相容矩阵（Lock Compatibility Matrix）

锁相容矩阵形式化地定义了当数据对象 $A$ 当前已被某一事务施加了某种锁时，另一事务再次对 $A$ 申请锁的准入结果：

```text
                    锁相容性判定矩阵 (Lock Matrix)
                                    另一事务已持有的锁模式
                                ──────────────────────────────
                                 无锁 (None)    S 锁      X 锁
    申请的锁模式 ┌─────────────┬─────────────┬─────────┬─────────┐
                 │    S 锁     │      Y      │    Y    │    N    │
                 ├─────────────┼─────────────┼─────────┼─────────┤
                 │    X 锁     │      Y      │    N    │    N    │
                 └─────────────┴─────────────┴─────────┴─────────┘
                 (注: Y 代表兼容批准授予锁; N 代表冲突拒绝，申请事务挂起等待)
```

#### 3.1 锁相容的三大黄金公理（口诀）
1. **【读读相容】**：已有 S 锁，再申请 S 锁 $\implies$ **批准（Y）**（多读并发不冲突）；
2. **【读写互斥】**：已有 S 锁，再申请 X 锁 $\implies$ **阻塞（N）**（有人在读，绝不能改！）；
3. **【写写互斥】**：已有 X 锁，再申请任何锁（S 或 X）$\implies$ **全部阻塞（N）**（独占霸道到底！）。

### 4. 随堂巩固自测

#### 自测题 1（单项选择题）
在关系数据库封锁机制中，若事务 $T_1$ 已经对数据对象 $A$ 加上了共享锁（S 锁），此时事务 $T_2$ 试图对数据对象 $A$ 发起加锁请求，能够立即被锁管理器批准的是（ ）
A. $T_2$ 对 $A$ 申请排他锁（X 锁）  
B. $T_2$ 对 $A$ 申请共享锁（S 锁）  
C. 无论是 S 锁还是 X 锁都会被系统拦截等待  
D. 必须先等待 $T_1$ 提交才能处理  

**【答案】**：B  
**【解析】**：根据锁相容矩阵，“读读相容（S 锁与 S 锁兼容）”。当已有 S 锁时，其他事务申请 S 锁可以立即共享持有；但申请 X 锁会被拒绝挂起。故选 B。

---

#### 自测题 2（锁冲突时序分析大题）
设有事务 $T_1$ 和 $T_2$ 按如下时序对数据项 $A$ 发起访问：
1. $t_1$ 时刻：$T_1$ 申请并成功对 $A$ 加上了 $X$ 锁；
2. $t_2$ 时刻：$T_2$ 试图对 $A$ 申请加 $S$ 锁；
3. $t_3$ 时刻：$T_1$ 对 $A$ 执行修改并提交事务（COMMIT），释放了 $X$ 锁。  
请从封锁机制与相容矩阵角度，详细描述 $T_2$ 在 $t_2$ 到 $t_3$ 期间的状态变化以及最终执行时机。

**【参考答案与时序解析】**：
1. **$t_2$ 时刻状态**：数据 $A$ 已被 $T_1$ 持有 $X$ 锁。根据写读互斥公理，相容矩阵判定为“不相容（N）”。锁管理器**拒绝 $T_2$ 的加锁请求，将事务 $T_2$ 置于阻塞等待队列中挂起休眠**；
2. **$t_2 \sim t_3$ 期间**：$T_2$ 一直处于等待状态，不占用 CPU，直到 $T_1$ 释放锁；
3. **$t_3$ 时刻及之后**：$T_1$ 提交并释放 $A$ 上的 $X$ 锁。锁管理器立即被唤醒，重新评估等待队列，**批准向 $T_2$ 授予数据 $A$ 上的 $S$ 锁**，$T_2$ 被唤醒恢复执行，安全读取 $T_1$ 提交后的最新合法数据。

## 第 3 章：第11章 并发控制（3）
> 对应分集：P72 | 原始标题：《第11章 并发控制（3）》

### 1. 核心概念与本质内涵：为什么有了锁还必须制定“封锁协议”？

在上一讲中，我们形式化定义了排他锁（X 锁）与共享锁（S 锁）。
但是，单纯拥有锁并不足以自动保障并发事务的正确性：
- 事务在什么时候申请锁？是在事务开头一次性申请，还是在操作前按需申请？
- 最关键的是：**事务在什么时候释放锁？是在读写完数据后立即释放，还是必须一直死守到事务提交（COMMIT）时才释放？**

对“**加锁的时机、持锁的时间跨度以及释放锁的节点**”所做出的规则约束，在数据库理论中被称为**封锁协议（Locking Protocol）**。

关系数据库理论严格确立了**三级封锁协议体系（1st, 2nd, 3rd Level Locking Protocols）**，每一级协议都对应着对特定并发异常的精准定点防御。

```text
                     三级封锁协议递进防御阶梯
                               │
       ┌───────────────────────┼───────────────────────┐
       ▼                       ▼                       ▼
【一级封锁协议】              【二级封锁协议】              【三级封锁协议】
 • 修改前必须加 X 锁           • 在一级协议基础上            • 在一级协议基础上
 • 事务结束 (COMMIT) 才释放!   • 读前必须加 S 锁             • 读前必须加 S 锁
 • 防御成果:                   • 【读完后立即释放 S 锁】!    • 【事务结束才释放 S 锁】!
   ★ 防止丢失修改!             • 防御成果:                   • 防御成果:
                                 ★ 防止丢失修改!               ★ 防止丢失修改!
                                 ★ 防止读"脏"数据!             ★ 防止读"脏"数据!
                                                               ★ 防止不可重复读!
```

---

### 2. 三级封锁协议形式化规则深度剖析

#### 2.1 一级封锁协议（1st Level Protocol）——捍卫写操作

- **形式化规约**：
  1. 事务 $T$ 在修改数据 $R$ 之前，必须先对其加上 **X 锁**；
  2. **该 X 锁必须一直持有，直到事务结束（`COMMIT` 或 `ROLLBACK`）时才允许释放**；
  3. 事务在读取数据时不申请任何锁。
- **防御成果分析（彻底消除“丢失修改”）**：
  - 设事务 $T_1$ 准备修改机票余量 $A$，按协议先行加上 X 锁；
  - 并发事务 $T_2$ 若也想修改 $A$，根据写写互斥原则，$T_2$ 申请 X 锁会被锁管理器强制挂起；
  - 只有等 $T_1$ 彻底完成修改并正式提交释放 X 锁后，$T_2$ 才能获得 X 锁并读入 $T_1$ 修改后的新值继续修改；
  - **$T_1$ 的更新绝不可能被 $T_2$ 覆写，丢失修改被彻底终结**。
- **协议局限**：因为读数据完全不加锁，其他事务可以随时读取到 $T_1$ 正在修改但尚未提交的中间脏数据，**无法防范“读脏数据”与“不可重复读”**。

---

#### 2.2 二级封锁协议（2nd Level Protocol）——斩断读脏数据

- **形式化规约**：
  1. 完全遵循一级封锁协议（写前加 X 锁，事务结束才放）；
  2. **事务 $T$ 在读取数据 $R$ 之前，必须先对其加上 S 锁**；
  3. **【关键特征】读完数据后即可立即释放 S 锁（Short-term S Lock）**。
- **防御成果分析（彻底消除“读脏数据”）**：
  - 若事务 $T_1$ 正在修改数据 $C$（持有着 X 锁）；
  - 事务 $T_2$ 试图读取数据 $C$，按照二级协议必须先申请 S 锁；
  - 根据读写互斥公理，$T_2$ 申请 S 锁被直接拦截挂起；
  - $T_2$ 根本没有机会读到 $T_1$ 未提交的中间修改！直到 $T_1$ 提交（或回滚完毕）释放 X 锁后，$T_2$ 才能读到合法数据，**读脏数据被彻底根除**。
- **协议局限**：因为 S 锁在“读完后立即释放”，如果 $T_2$ 读完放锁后，并发事务 $T_3$ 紧接着插入篡改了该数据，导致 $T_2$ 在稍后同一事务中第二次读取时发现数据变动，**无法防范“不可重复读”**。

---

#### 2.3 三级封锁协议（3rd Level Protocol）——终极防线

- **形式化规约**：
  1. 完全遵循一级封锁协议（写前加 X 锁，事务结束才放）；
  2. 事务 $T$ 在读取数据 $R$ 之前，必须先对其加上 S 锁；
  3. **【终极特征】S 锁严禁提前释放，必须一直持有直到事务结束（`COMMIT` 或 `ROLLBACK`）时才允许释放（Long-term S Lock）**！
- **防御成果分析（彻底消除“不可重复读”）**：
  - 事务 $T$ 首次读取数据 $A$ 后，将其 S 锁一直攥在手中不放；
  - 在 $T$ 整个事务存活期间，任何其他事务由于无法申请到 X 锁，**绝对不可能对数据 $A$ 进行修改或删除**；
  - 当事务 $T$ 在后续任意时刻再次读取 $A$ 时，数据必然与第一次读取完全一致，**不可重复读异常被彻底剿灭**。

---

### 3. 三级封锁协议与并发异常全景对照矩阵

这是数据库考研与架构师面试中最高频考查的黄金对照表：

| 封锁协议级别 | 加 X 锁要求 | 释放 X 锁节点 | 加 S 锁要求 | 释放 S 锁节点 | 防止丢失修改 | 防止读脏数据 | 防止不可重复读 |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| **一级封锁协议** | 修改前加 | **事务结束** | 不加锁 | 无 | **可以防止** | 不能防止 | 不能防止 |
| **二级封锁协议** | 修改前加 | **事务结束** | 读取前加 | **读完立即释放** | **可以防止** | **可以防止** | 不能防止 |
| **三级封锁协议** | 修改前加 | **事务结束** | 读取前加 | **事务结束** | **可以防止** | **可以防止** | **可以防止** |

### 4. 封锁协议与 SQL 标准四大隔离级别的对应映射

ANSI/ISO SQL 92 标准定义了著名的**四大事务隔离级别（Isolation Levels）**，其底层物理实现机制正是以三级封锁协议为蓝本演化而来的：

```text
SQL 事务隔离级别 (Isolation Level)              底层封锁协议实现机制对应
──────────────────────────────────              ────────────────────────────
1. 读未提交 (Read Uncommitted)        <=======>    一级封锁协议 (写加锁，读裸奔)
2. 读已提交 (Read Committed)          <=======>    二级封锁协议 (读完立即释放 S 锁)
3. 可重复读 (Repeatable Read)         <=======>    三级封锁协议 (S 锁持续到事务结束)
4. 可串行化 (Serializable)           <=======>    三级封锁协议 + 范围锁/谓词锁 (防幻读)
```

## 第 4 章：第11章 并发控制（4）

### 1. 核心概念与本质内涵：封锁机制带来的不可避免副作用

封锁机制是保障并发事务 ACID 隔离性的一剂猛药。
然而，在计算机科学中，任何控制资源的独占互斥机制都会不可避免地带来并发副作用。在数据库并发封锁的世界里，伴生的两大核心副作用就是：**活锁（Livelock）**与**死锁（Deadlock）**。

```text
               并发封锁的两大核心副作用
                               │
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
【活锁 (Livelock / 事务饥饿)】                  【死锁 (Deadlock / 循环互锁)】
 • 事务并未卡死，但永远得不到执行机会           • 多个事务相互持有并等待对方的资源
 • 现象: T1 申请加锁，被后来者 T2, T3 频繁插队  • 现象: T1 等 T2，T2 等 T1，死循环僵局!
 • 根治策略: 【先来先服务 (FCFS) 排队】         • 根治策略: 【等待图环路检测 + 牺牲者回滚】
```

---

### 2. 活锁（Livelock）的产生机制与消解之道

#### 2.1 活锁产生机理（事务被“饿死”）
1. 事务 $T_1$ 请求对数据 $R$ 加锁，由于 $R$ 当前已被其他事务占用，锁管理器将 $T_1$ 置入等待队列；
2. 随后数据 $R$ 的锁被释放；但此时，另一个新启动的事务 $T_2$ 也发起了加锁申请，且锁管理器优先批准了 $T_2$；
3. 接着 $T_2$ 释放，$T_3$ 又插入插队……
4. **悲惨后果**：事务 $T_1$ 虽然一直存活、代码没有死循环，但**由于不断被后续事务恶意或偶然“插队抢占”，导致 $T_1$ 永远处于等待饥饿（Starvation）状态**，这就是活锁。

#### 2.2 活锁的消解法则：先来先服务（FCFS）
- 锁管理器内部对每一个数据对象维护一个严格的 **FIFO（先进先出）加锁等待队列**；
- 当数据上的锁被释放时，锁管理器**必须严格按照事务申请到达的时间先后顺序**依次出队并授予锁，绝不允许后来者越级插队，从制度上彻底根治活锁。

---

### 3. 死锁（Deadlock）的产生机制与经典时序推导

#### 3.1 什么是死锁？
**死锁是指两个或多个事务各自持有了某些数据对象的锁，同时又在申请对方正在持有的锁；导致所有事务都在无休止地等待对方先释放锁，在没有外部系统介入的情况下，没有任何一个事务能够向前推进一步**。

```text
               经典死锁时序形成全过程
时序    事务 T1                          事务 T2
─────────────────────────────────────────────────────────────
t1     成功对数据 A 加 X 锁 (持有 A)
t2                                      成功对数据 B 加 X 锁 (持有 B)
t3     申请对数据 B 加 X 锁 ──> 被阻塞!
       (因为 B 被 T2 持有，T1 挂起休眠等待 T2 放锁...)
t4                                      申请对数据 A 加 X 锁 ──> 被阻塞!
                                        (因为 A 被 T1 持有，T2 挂起休眠等待 T1 放锁...)
─────────────────────────────────────────────────────────────
此时局面:
T1 在等待 T2 释放 B，而 T2 必须等 T1 释放 A 才能继续推进执行到 COMMIT 放锁!
===> 双方陷入永久死循环挂起，系统被彻底锁死!
```

---

### 4. 预防死锁（Deadlock Prevention）的局限性

在理论上，有两类预防死锁的静态策略，但在高并发企业级生产系统中往往代价高昂：

```text
【一次封锁法】: 事务在开始前，必须一次性申请齐后续全部可能用到的数据锁，否则不运行。
  - 致命短板: 严重削弱并发度; 业务分支多变，无法在运行前准确预知需要锁哪些行。

【顺序封锁法】: 为全库所有数据规定全局物理编号 (1, 2, 3..)，所有事务必须按编号升序加锁。
  - 致命短板: 生产系统中数据动态增删，为亿级数据行动态维护全局顺序号在工程上极其困难。
```

---

### 5. 死锁的诊断与解除（Detection & Recovery）——现代数据库事实标准

既然静态预防代价太大，现代主流 DBMS（Oracle, MySQL InnoDB, PostgreSQL）均采取**“允许死锁发生，但能在毫秒级快速自动诊断并优雅解除”**的动态策略。

```text
               死锁动态诊断与解除流水线
 后台死锁检测线程定期运行 (Deadlock Detection Engine)
                        │
                        ▼
 [第 1 步: 构建事务等待图 (Wait-For Graph, WFG)]
 扫描全库锁等待信息，构建有向图 (节点为事务，边为等待依赖)
                        │
                        ▼
 [第 2 步: 拓扑有向环检测 (Cycle Detection)]
 利用深度优先搜索 (DFS) 寻找图中是否存在闭合回路
 ├── 无环 ──> 系统健康安全，继续运行
 ▼ 发现有向环 (确认存在死锁!)
 [第 3 步: 挑选最小代价牺牲者 (Victim Selection)]
 权衡各事务代价: 哪个事务修改的行数最少、耗费 CPU 最少?
                        │
                        ▼
 [第 4 步: 强制回滚牺牲者 (Rollback Victim)]
 强制中止该事务，释放其持有的全部锁，打破死循环，成全其他事务推进!
```

---

#### 5.1 事务等待图（Wait-For Graph, WFG）判定准则

- **有向图形式化定义**：$G = (V, E)$；
  - 节点集 $V$：当前正在运行的所有活跃事务；
  - 有向边集 $E$：若事务 $T_i$ 正在等待被事务 $T_j$ 持有的锁，则在图中画一条有向边：
    $$T_i \to T_j$$
- **【死锁判定的数学充要条件】**：  
  **系统存在死锁的充分必要条件是：事务等待图 $G$ 中存在至少一个闭合有向环路（Cycle）！**

```text
【事务等待图中的死锁闭合环路】
      [ 事务 T1 ] ──────────────> [ 事务 T2 ]
           ▲                             │
           │                             │
           └────────────── [ 事务 T3 ] <─┘
     (T1 等 T2，T2 等 T3，T3 等 T1 ===> 形成闭环，必发生死锁!)
```

---

#### 5.2 挑选牺牲者事务（Victim Selection）的裁决考量
当检测出环路后，系统必须且只需强行杀死（`ROLLBACK`）环中的某一个事务，即可瞬间打破僵局。优化器通常按以下指标选择代价最小的牺牲者：
1. **已修改的数据行数最少**（回滚撤销的 I/O 代价最低）；
2. **事务已运行的时间最短**（重试成本最低）；
3. **持有的锁数量最少**。

## 第 5 章：第11章 并发控制（5）
> 对应分集：P74 | 原始标题：《第11章 并发控制（5）》

### 1. 核心概念与本质内涵：什么是“正确的”并发调度？

在多事务并发执行的环境中，事务的各项操作（读、写）交织穿插在一起，构成了复杂的**并发调度（Schedule）**。

> **【并发控制的最高哲学问题】**：什么样的并发调度才算是“正确”的？系统如何判定并发执行的结果没有产生逻辑紊乱？

数据库理论给出了唯一的数学评判准绳——**可串行性（Serializability）**：
- **定义**：多个事务并发执行是正确的，**当且仅当其执行结果与按某一种顺序串行（Serial）执行这些事务时的结果完全相同**，这种调度称为**可串行化的调度（Serializable Schedule）**；
- 串行调度（一个接一个排队执行）由于完全没有交叉干扰，天生具有百分之百的一致性正确性；
- 因此，任何一个并发调度，只要其逻辑计算产出与某一个串行执行序列等价，它就是合法的、正确的！

```text
               可串行化调度的数学等价性
   并发交叉调度 S                               等价的串行调度 S'
────────────────────────                    ────────────────────────
T1: 读A ───> 写A                            T1: 读A ──> 写A ──> 提交
T2:               读B ──> 写B               T2: 读B ──> 写B ──> 提交
(宏观并发高效运行，多核满载)                (微观逻辑结果完全严密等价!)
```

---

### 2. 冲突可串行化（Conflict Serializability）形式化理论

在实际系统中，直接判定任意两个调度的计算结果是否相等极其困难。学术界引入了更具机械可操作性的**冲突可串行化**判定准则。

#### 2.1 冲突操作（Conflicting Operations）
在并发调度中，针对**不同事务中针对同一个数据项的两个相邻操作**：
- **读-读操作（Read-Read）**：**不冲突**（任意交换次序不影响结果）；
- **读-写操作（Read-Write）**：**必冲突（Conflicting）**！交换次序会改变读取到的数据值；
- **写-写操作（Write-Write）**：**必冲突（Conflicting）**！交换次序会改变最终物理落盘的覆写结果。

```text
                  操作交换相容性矩阵
              同一数据项的操作      读操作 (Read)    写操作 (Write)
              ─────────────────    ──────────────   ──────────────
              读操作 (Read)        可交换 (不冲突)  不可交换 (冲突!)
              写操作 (Write)       不可交换 (冲突!) 不可交换 (冲突!)
```

---

#### 2.2 冲突可串行化定理与优先图（Precedence Graph）判定法

一个并发调度 $S$ 在不改变冲突操作先后次序的前提下，**若能通过一系列非冲突操作的合法交换，将其等价变形为一个串行调度**，则称 $S$ 是**冲突可串行化的调度**。

> **【冲突可串行化充分条件】**：  
> **一个冲突可串行化的调度，必然是可串行化调度！**

##### 优先图（Precedence Graph，又称序列化图）判定算法：
1. **构图规则**：
   - 图的节点为所有并发事务 $T_1, T_2, \dots, T_n$；
   - 若在调度中存在针对同一数据项的冲突操作，且**事务 $T_i$ 的操作先于 $T_j$ 的操作执行**，则在图中画一条有向边：
     $$T_i \to T_j$$
2. **【核心充要判定定理】**：  
   **调度 $S$ 是冲突可串行化的充分必要条件是：其优先图（Precedence Graph）中不存在任何有向环路（Acyclic，即为一个有向无环图 DAG）！**
3. 若无环，对优先图执行**拓扑排序（Topological Sort）**，所得的线性序列就是与之等价的串行调度序列。

```text
【优先图判定示例】
  有向无环 (DAG):  [ T1 ] ─────> [ T2 ] ─────> [ T3 ]  ===> 冲突可串行化! 等价串行序列: T1 -> T2 -> T3
  存在回路 (Cycle):[ T1 ] <────> [ T2 ]                ===> 非冲突可串行化! (调度发生逻辑紊乱)
```

### 3. 两段锁协议（Two-Phase Locking, 2PL）——可串行化的实现保障

虽然优先图可以检验可串行性，但优化器不可能在事务运行完之后再去“事后验尸”。DBMS 必须在事务运行过程中，实时施加一种能够**自动天然保证可串行化**的动态封锁协议，这就是著名的 **两段锁协议（2PL）**。

#### 3.1 两段锁协议的核心规约
2PL 要求所有事务在存活期间，加锁和解锁必须严格划分为**两个单调的独立阶段**：

```text
                     两段锁协议 (2PL) 状态转移
加锁数量
   ▲
   │        【阶段 1: 扩展阶段 (Growing Phase)】
   │         • 只能申请并获得任何锁 (S锁/X锁)
   │         • 【绝对不能释放任何锁!】
   │                         │
   │                         ▼ [获得全部锁达到峰值 (Lock Point)]
   │                         │
   │        【阶段 2: 收缩阶段 (Shrinking Phase)】
   │         • 一旦释放了第一个锁，正式进入收缩期!
   │         • 只能释放锁，【绝对不能再申请任何新锁!】
   └─────────────────────────────────────────────────────> 时间轴
```

---

#### 3.2 两段锁协议的至高里程碑定理

> **【两段锁充分性定理】**：  
> **若并发执行的所有事务都严格遵守两段锁协议（2PL），则这些事务的任何并发调度策略都必然是冲突可串行化的！**

- **理论价值**：只要让每个事务在代码层面遵守 2PL（在放锁前把该拿的锁全拿完，一旦放锁就只放不拿），DBMS 无需关心复杂的交叉时序，调度结果必然天然百分之百正确！

#### 3.3 2PL 与死锁的辩证辨析
> **【高频考研易错命门】**：遵循两段锁协议（2PL）的事务，会发生死锁吗？

- **答案是：依然可能发生死锁！**
- **机理分析**：2PL 只规定了“加锁必须在放锁前”，但**并未规定各个事务以何种顺序加锁**。事务 $T_1$ 在其扩展阶段拿了 $A$ 并申请 $B$，事务 $T_2$ 在其扩展阶段拿了 $B$ 并申请 $A$，双方都在其合法的“扩展阶段”，但仍然会爆发死锁！
- **结论：2PL 是可串行化的充分条件，但不是无死锁的保证！**

### 1. 核心概念与本质内涵：什么是封锁粒度？

在关系数据库并发控制中，加锁的对象究竟应该多大？
封锁的对象可以是很大的逻辑单元（如整个数据库、一张完整的基本表），也可以是很小的逻辑单元（如表中的某一行元组、某个具体的属性字段），甚至可以是物理单元（如一个 16KB 数据页或磁盘块）。

**封锁对象的大小，在数据库理论中被称为封锁粒度（Lock Granularity）**。

```text
               封锁粒度的并发度与系统开销权衡天平
           粗粒度 (如: 表锁 Table Lock)           细粒度 (如: 行锁 Row Lock)
     ───────────────────────────────────   ───────────────────────────────────
     • 系统需要管理的锁对象极少             • 系统需要为每行维护锁结构，内存开销大
     • 锁冲突概率极大，并发度极低           • 锁冲突概率极小，高并发性能极其强悍
     • 适合: 批量离线数据备份、整表重构     • 适合: 互联网高并发在线联机事务 (OLTP)
```

### 2. 多粒度封锁树与全表扫描性能瓶颈

为了兼顾不同业务场景的需求，现代数据库系统支持**多粒度树形封锁机制（Multiple Granularity Tree）**：

```text
               多粒度树形层次拓扑结构
                    [ 数据库 (Database) ]
                              │
                    [ 关系表 (Relation) ]
                              │
                    [ 数据页 (Page) ]
                              │
                    [ 单行元组 (Tuple) ]
```

#### 2.1 隐式封锁与显式封锁
- **显式封锁（Explicit Locking）**：事务直接向某个节点施加的锁（如事务对表加了表锁）；
- **隐式封锁（Implicit Locking）**：当上层父节点被显式加锁后，其**所有下层后裔节点自然自动受到该锁的约束**（例如：对整张表加了 X 锁，表中所有的 100 万行元组隐式自动全部被上了 X 锁）。

---

#### 2.2 致命性能瓶颈：多粒度共存下的全量遍历检查难题

> **【没有意向锁时的架构灾难】**：
> 1. 事务 $T_1$ 正在对某电商订单表中的**某一行元组**执行更新，持有该行的行级 X 锁；
> 2. 事务 $T_2$ 随后由于要执行整表重组，试图对该订单表申请一个**表级的排他 X 锁**；
> 3. 此时，锁管理器如何判定 $T_2$ 的申请能否批准？
>    - 按照多粒度规则，如果表中有任何一行被加了 X 锁，表级 X 锁就绝不能批准；
>    - **恐怖代价**：锁管理器必须沿着树形结构，**将表中的全部 1000 万行元组逐行扫描遍历一遍**，以确认其中是否藏有一把行锁！
>    - 每次申请表锁都要耗费数秒进行全表数千万次比对，系统并发性能彻底崩溃！

### 3. 破局神器：意向锁（Intent Lock）机制

为了彻底消除申请表级锁时对整张表成千上万行元组进行无休止遍历扫描的恐怖开销，数据库理论引入了**意向锁（Intent Lock）**。

> **意向锁的核心思想（挂门牌机制）**：  
> **如果一个事务想要对底层的某个具体后裔节点（如行）加锁，必须首先在它的所有上层祖先节点（如表）上，挂上一把“意向锁”！**

```text
               意向锁的门牌机制直观映射
当事务想修改房间里的某张桌子 (行级 X 锁):
1. 事务必须先在大门 (表头) 上挂一个 "内有人正打算写数据" 的意向牌 (IX 锁);
2. 随后进入房间给桌子加行级 X 锁。
                               │
                               ▼
随后另一事务想把整个大楼全封锁 (申请表级 X 锁):
只需看一眼大门上的 "意向牌"，瞬间获知里面有人在加锁，立即原地等待!
彻底无需派人把整栋大楼的一万个房间逐一敲门翻查!
```

### 4. 三大意向锁形式化定义与五元锁相容矩阵

根据下层后裔节点所申请的锁类型不同，意向锁形式化地定义为三种：

1. **意向共享锁（Intent Share Lock，IS 锁）**：
   - 语义：如果要对某个数据对象的后裔节点加 **S 锁**，必须先对该数据对象加上 **IS 锁**；
2. **意向排他锁（Intent Exclusive Lock，IX 锁）**：
   - 语义：如果要对某个数据对象的后裔节点加 **X 锁**，必须先对该数据对象加上 **IX 锁**；
3. **共享意向排他锁（Share Intent Exclusive Lock，SIX 锁）**：
   - 语义：对当前整个数据对象加 **S 锁**（本表全表可读），同时打算对其某些后裔节点加 **X 锁**进行修改（即 $\text{SIX} = \text{S} + \text{IX}$）。

---

#### 4.1 完整的五元锁相容矩阵（Lock Compatibility Matrix）

这是数据库并发控制领域最全、最高阶的锁相容矩阵：

```text
                  五元锁相容判定矩阵 (Compatibility Matrix)
                                    已有事务持有的锁
               ────────────────────────────────────────────────────────
                无 (None)     IS          IX          S          SIX         X
  申请的锁模式 ┌───────────┬───────────┬───────────┬───────────┬───────────┬─────┐
        IS     │     Y     │     Y     │     Y     │     Y     │     Y     │  N  │
        IX     │     Y     │     Y     │     Y     │     N     │     N     │  N  │
        S      │     Y     │     Y     │     N     │     Y     │     N     │  N  │
        SIX    │     Y     │     Y     │     N     │     N     │     N     │  N  │
        X      │     Y     │     N     │     N     │     N     │     N     │  N  │
               └───────────┴───────────┴───────────┴───────────┴───────────┴─────┘
               (注: Y 代表兼容批准; N 代表冲突阻塞挂起)
```

##### 矩阵核心口诀与记忆秘籍：
1. **IS 锁最宽容**：除了与霸道的 X 锁冲突外，与其余所有锁（包括 S, IS, IX, SIX）全部相容；
2. **IX 与 IX 相容**：两个事务分别在同一个表上持有 IX 锁，代表它们各自打算修改表内**不同**的行，表头互相不冲突，行级自会排队；
3. **IX 与 S 互斥**：有人持有 S 锁表明全表正在被整表只读扫描，此时绝不允许有人带着 IX 意图去改行；
4. **X 锁排斥一切**：只要有 X 锁存在，全矩阵一律为 N！

---

#### 4.2 意向锁加锁与释放的四步时序规约
在多粒度树形结构中，事务加锁和释放锁必须严格遵循：
1. **【自上而下加锁（Top-Down Locking）】**：对任一节点加锁（S 或 X），必须先对其所有祖先节点施加对应的意向锁（IS 或 IX）；
2. **【自下而上放锁（Bottom-Up Unlocking）】**：释放锁时，必须先释放叶子节点上的显式锁，最后才能释放祖先节点上的意向锁。

   - 遵循**自上而下加锁（Top-Down）**原则：
   - **第一步（表级加意向锁）**：$T_1$ 必须首先在父节点 `Student` 表上申请并获得**意向排他锁（IX 锁）**；
   - **第二步（行级加排他锁）**：在持有表级 IX 锁后，系统才允许 $T_1$ 进入表内，对目标行 `Row_100` 申请并获得**行级排他锁（X 锁）**。
2. **事务 $T_2$ 的申请与判定流程**：
   - 事务 $T_2$ 试图对 `Student` 表申请表级 $X$ 锁；
   - 锁管理器直接检查 `Student` 表当前的持锁状态，发现当前表上已被 $T_1$ 挂上了 $IX$ 锁；
   - **查阅锁相容矩阵**：$X$ 锁与已有的 $IX$ 锁判定为**不相容（N）**！
   - **判定结论与执行结果**：锁管理器无需对表内的数据行进行任何遍历扫描，**当场拒绝 $T_2$ 的加锁请求，直接将事务 $T_2$ 置于阻塞等待队列中挂起休眠**，直到事务 $T_1$ 彻底完成修改并提交（COMMIT）、自下而上释放了行级 X 锁和表级 IX 锁之后，$T_2$ 才会被唤醒并授予表级 X 锁继续执行。这一机制完美捍卫了系统的并发隔离性与极致运行效率。
