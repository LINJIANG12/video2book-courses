相比之下，GPU 的网络思路就很不一样了，它更像是一种全对全的模式。它的网络连接方式有点像一棵树，通常被称为胖树（Fat-Tree）。在最底层，GPU 之间的连接速度极快，接着 GPU 会组成一个个 pod，在 pod 内部进行连接，随后 pod 可能会配备几台交换机，让它们能够互相通信。这意味着随着节点数量的增加，这种树状结构会变得越来越大。

随着你把所有这些节点进行全互联，通信成本会上升，通信拓扑结构也会变得更加复杂。这种设计理念的差异意味着如果你只跟相邻节点通信，TPU 的表现非常出色。它们性价比高，而且可以在相同功耗下让每个连接更强大，对吧？但如果你是以高度随机、难以预测的方式来连接，那么 GPU 的这种网络就会更灵活，对吧？

好，那么我觉得数据并行是最容易理解的，它的概念非常简单，这也是并行化语言模型训练这类算法的标准做法。所以先别管 Adam，我们暂时只用最基础的 SGD。咱们有一个批次大小记为 B，对吧？所以每次更新我都会取 B 个样本。我会把梯度加起来，然后执行更新。所以针对这种情况，最基础的并行做法就是把批次 B 拿来用。我可以把它分给 M 台机器。如果 B 能被 M 整除，每台机器就能分到大小为 B/M 的小批次。接着每台机器分别计算梯度，最后把所有梯度同步起来求和。

好，不错。从计算扩展性的角度看，这非常完美，只要每个 GPU 上的样本量足够就没问题。那通信开销呢？咱们得互相传多少数据？每个批次咱们基本上得传输两倍于参数量大小的数据，对吧？因为我要做的就是把梯度在机器间来回传输。好，至于内存扩展性，那完全没有。每个 GPU 都存有模型的相同副本。激活值的大小得保持一致。所以在这种方案里，你其实一点内存都没省下来。

那现在的问题出在哪儿？咱们虽然多少解决了计算问题，但内存问题压根儿没碰。咱们来看看这个内存问题，做一点简单的核算。粗一看内存情况好像挺糟，但事实是咱们的内存状况简直糟糕透顶。内存为啥这么糟？你稍微算算参数就知道了。哎，事实证明你得存好多东西，而且要存的东西其实比参数本身还多。

所以按经验法则，具体取决于精度，我们大概需要五份权重副本，以及每个参数 16 字节来存模型。哎，所以咱们肯定得存模型参数，还得有个地方放梯度，对吧？在把它们放进模型参数之前，这些东西算是某种累加器，所以咱们得把这些东西存下来。不过实际上你可能还得存点别的东西，比如你可能需要一个更高精度的累加器用来往 SGD 里累加数据。这可能只是临时的，但你确实得留着。要是你在用 Adam，麻烦正是从这儿冒出来的，你得同时跟踪梯度的一阶矩和二阶矩，而且你得一直跟踪它们，对吧？所以你得备两份。不幸的是视稳定性的要求而定，你可能得用高精度来存，这开销可不小。

我们一般管那些叫优化器状态，也就是你用来累加一阶矩和二阶矩的那些数据。这些开销其实挺大的。你要是细算一下账会发现做 SGD 更新时，内存成本的大头就在这儿。所以我觉得这地方有个特别优雅的做法，就是想办法省点内存，把它们分散到各个加速器上，而且是用一种结构化的方式。这么干的话你几乎是白捡了这些收益。就像我刚才在上一张幻灯片里说的，优化器状态占了你绝大部分的内存。来看，优化器状态是绿色的，占了大头，橙色是梯度，蓝色是参数。你看参数和梯度一样大，但状态数据更大。要是用朴素的数据并行，就是把这一堆东西全复制到每个 GPU 上。跨 GPU 复制，这不太妙，对吧？毕竟你占用的显存远超实际需要，而且显存占用会随着加速器数量线性增加。

这确实不太好。我们可以把优化器状态分片放到不同的 GPU 上，这样能省不少空间。如果我们把其他需要跟踪的部分也分片处理，那也能省很多。比如梯度也可以分片到不同的 GPU 上，或者极端点，把所有东西都分片到不同的加速器上。这样你看，随着数值从 1.0 一路降到 0.19，右边显示的显存节省效果会非常惊人。接下来咱们主要研究一下这么做代价有多大。大家可能觉得天下没有免费的午餐，基线方案肯定是最快的。当我们往下走到这一步时，为了省下这些显存，就得付出巨大的通信代价。我觉得最棒的一点是很多部分其实是免费的，不过我会一步步带大家过一遍。

好，咱们先从大家常说的零阶段一开始。对应这几个步骤会有三个阶段。所以第一阶段是最简单的，我只对优化器状态做分片，并把它分散到各个 GPU 上。每个人手里都有参数和梯度，你可以这么想：每个工作进程负责更新参数中的一块。比如如果我是 0 号 GPU，那我就只管更新这里最前面的这一块，其他的更新跟我没关系。那具体怎么运作呢？我们要做的就是大家各自计算，每个人处理不同的数据项。所以第一步是在各自的数据项上算出完整的梯度。接下来我会把自己算好的梯度拿出来，用 ReduceScatter 操作分发给其他所有机器，毕竟大家都需要我的梯度。不过他们不需要全部的梯度，只需要那些跟他们自己参数更新有关的部分。所以每个工作节点会从我这儿拿到梯度，但只拿参数空间里属于他们的那一块。这样一来这部分的通信开销就相当于一整套参数的量级，因为我虽然发的是完整梯度，但会把它拆开分别发给每个 GPU。现在每台机器都可以进行参数更新了，他们手里有自己的参数，从别人那儿拿到的梯度，还有自己跟踪维护的状态。参数更新完之后，我会用 AllGather 操作把它们都收回来。我负责的，比方说四分之一的参数，所以我把这些更新后的参数发回给其他所有机器。

所以瞧啊，这就是一个 AllGather，你看这种等价关系其实挺有用的。我到底做了多少种操作？在朴素的数据并行方案里，我得做一次 AllReduce，我得跟所有人交换梯度，然后再做更新，所以通信开销是参数量的两倍。在 Zero Stage 1 阶段，我做了两个操作，先用 ReduceScatter 把梯度发出去，再用 AllGather 把更新后的参数收回来。不过我们之前提过，ReduceScatter 加上 AllGather 其实就等价于一个 AllReduce。所以 Zero Stage 1 的通信特性跟朴素 DDP 是一模一样的。这意味着我们白捡了一笔内存节省，太棒了。再看看内存占用，我们基本上是把参数以及所有非优化器状态的东西都除以了 GPU 数量 NGPU。太棒了，太棒了，太棒了。

好，你可能已经注意到了，对吧？不过，当我们拆分内容时，有些切法是按列来的。所以按列的张量并行会发生在输入端，对吧？也就是说，MLP 的输入和注意力的投影在每个 Transformer 块里都会按列切分，这就是按列切分，然后在相对应的第二阶段会有按行切分。所以在 MLP 的下投影和注意力的输出部分，你会看到按行切分。

像层归一化、非线性激活或者 MoE 里的路由器，这些比较小的层都会在每台机器上完整复制一份。咱们真没必要去折腾拆分它们带来的那些额外开销。

这些操作的数据量跟激活值差不多，而且执行得特别频繁。所以这非常耗通信带宽，咱们一般只在节点内部做这个。所以对于 GPU 来说，8 个 GPU 通常会在一个机箱里紧密连在一起。所以最多到 8 个的时候，你可能还愿意搞点张量并行，但一旦超过这个数，你就得跨节点通信了。

节点和互联的速度要慢得多，所以一旦跨出单台机器的范围，性能就会大幅下跌。所以咱们得记住，张量并行非常吃通信带宽。一般咱们会把它用在手头最快的互联网络上。

接下来我想回到之前提到的 TPU 的话题。记住，对 TPU 来说，不存在那种前 8 个 GPU 很快，后面机器就慢的区别。它就是一个大的网格结构。所以 TPU 团队常强调的一个优势是，他们能很好地支持张量并行。

相比 GPU，他们能支持大得多的规模，因为在这个网格上，这种高度规则的通信模式能提供高带宽，对吧？所以用 TPU 还是 GPU 做并行差别很大。你分配给张量并行和流水线并行的比例实际上会截然不同。

那么咱们怎么比较这两种方案呢？它们都属于模型切分策略，它们都能帮咱们节省参数和激活值的开销。张量并行的好处是通常不会出现流水线气泡。如果你的网络够快，咱们就能实现充分利用。它的复杂度也低，就是把一些矩阵乘法切分一下。不过缺点就是通信量会大很多。
