好的，你可能会问的一个问题是：为什么我们需要 thread block？为什么不能只使用由 thread 组成的 grid，让每个 thread 直接获取一部分数据并执行操作？如果你只想执行 element-wise 操作，这种设计通常是可以的，我们稍后会看到。例如 GELU 是一种按 element-wise 方式应用的激活函数。在这种情况景下，thread 的设计非常自然，每个 thread 处理一个元素，这就像是对数据集中的每个元素 $i$ 执行函数 $f(i)$。但对于涉及 thread 间通信的操作，例如 Softmax 或矩阵乘法，这种视角就不够用了。原因在于如果你愿意承担写入和读取 HBM 的开销，这种视角或许还勉强可行，因为那样你仍然能行得通。比如说处理矩阵时后面会讲到，你可以让每个单元去计算矩阵里对应的那个元素，然后直接读写 HBM。但正如我们所注意到的，HBM 非常慢，因此这并不是一个好策略。

所以我们应该改用 Shared Memory。Shared Memory 是某个 SM 独有的，而 thread block 让你把一组线程看作一个整体，这些线程都会去访问 Shared Memory。谢谢。所以你不仅把这样一个 thread block 看作一个整体，该 thread block 会被调度到其中某个 Streaming Multiprocessor 上执行它的任务。它会先从 HBM 读取大量数据，然后进行处理。处理过程中，线程之间可能通过 Shared Memory 进行通信，然后再把结果写回去。好的，所以这是后面会讲到的一个关键点。

接下来谈谈一些注意事项。这里有个叫 warp 的东西，我之前没提过。简单来说，warp 其实不属于我们刚才描述的那种干净的程序模型范畴。你有 thread、thread block 组成 grid。技术上你也可以用到 warp，但编程时不一定非要用。那 warp 是什么呢？每个 thread block 包含一组 thread，但这些 thread 实际上是按 warp 分组的。每个 warp 通常包含 32 个 thread。举个例子，如果一个 thread block 有 64 个 thread，那就对应两个 warp：前 32 个和后 32 个。没错。正如 Tatsu 上次所说，同一个 warp 里的所有 thread 必须步调一致地执行相同的指令。所以每个时钟周期里，它们都得执行一模一样的指令。控制发散是指 warp 内的不同线程需要执行不同指令的情况。例如假设你有一个分支结构，如果条件 A 成立就执行 A，否则执行 B。接下来的情况是，你只能先执行 warp 中那些走 A 分支的线程，然后再执行走 B 分支的，所以这个过程就被串行化了，这样既不好又低效。所以一般来说，分支是你应该尽量避免的东西。

我觉得 warps 有个特别酷的地方，那就是 SM 实际上它同时在运行多个 warp。这里有一个 warp 调度器，还有一堆即将运行的驻留 warp。每个 warp 也有一些东西，而线程则拥有寄存器。而且 SM 可以在它们之间切换，没有任何开销。这在一般情况下并不成立，比如在 CPU 上就不是这样。但它之所以这样设计，正是为了隐藏延迟。所以这一点很重要，因为比如某个 warp 正在从 HBM 读取数据，要记住这代价很高，可能需要大约 100 个周期。你不想干等着那个 warp 闲着没事做，而是立刻切换到另一个 warp，让它去执行实际的 Tensor Core 运算。好的，这是关于 warp 需要注意的一点。

事实上有一个例子能说明你可能会想这么做：让线程数量减少，这就是线程粗化（thread coarsening）的思路。假设你有一个 element-wise 操作，你可以让一个线程只对一个元素执行运算。这样你就会有大量线程，但你也可以让每个线程处理多个元素，比如某个常数，也许是 8 个。这样线程数量就减少了，使得调度等操作更容易，但每个线程执行的工作量也增加了。因此如果你的线程负载非常轻，或许应该稍微增加它们的工作量。
